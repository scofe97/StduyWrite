(1) head 세 이름에서 head 블록을 "저장 요청 오면 메모리에서 모아 디스크로 넣는 공간"으로, head chunk 를 "청크 묶음의 시작점" 으로 답했습니다(chunks_head 는 정확). 이어 "활성 Chunk 가 헤드 청크? (head)----120개----(head)---- 이런 청크란 건가? 잘라낸다는 게 정확히 뭔지 헷갈린다" 를 물었습니다. (2) WAL 은 자력 통과 — "복원 때문", "메모리는 시스템이 내려가면 사라진다", "WAL 은 복원 단계 조회용으로만 쓰인다", "WAL 이 먼저". (3) "시스템콜은 동일하고 사전 과정이 비싸다" 는 자력으로 짚었으나 네 단계 각각의 이유는 "이렇게까지 필요한 이유는 정확히 모른다", 목적 차이는 "하나는 순수 append, 블록 쓰기는 모르겠음". 덧붙여 "영속 블록은 결국 chunks_head 저장할 때 나오는 개념이지?" 로 ③④ 를 같은 사건으로 봤습니다.     2026-07-28 — "그래서 무엇이 갈리는가"까지 못 감 (01-01 Phase 1)¶

    • 자기 답: 01-01 네 축을 예측·채점으로 돌린 결과. (1) 체크 기반이 월~목 OK 만 남긴다는 것은 자력 정답했으나, 금요일 경고에서 모르는 것을 "어떻게 예외로 왔는지를 모른다" 까지만 답하고 그것이 왜 문제인지에 못 닿았습니다. (2) 체크 기반이 "내가 상상하지 못한 예외를 잡지 못한다"는 자력 정답. 다만 원인 기반의 반대가 무엇이냐에 "단순 특정 값의 임계값이 아닌 다른 거? 잘 모르겠다" 로 막혔습니다. (3) pull·push 에서 push 는 "일정 시간 데이터가 안 올 때 인지한다"까지 맞혔으나 "확인하려면 다시 pull 해 봐야 한다" 고 답했습니다(push 에는 pull 수단이 없음). pull 의 단점으로 "한 서버에서 모두 가져오니 과부하"(정확 — 6장 샤딩)와 "앱이 죽었을 때도 지속적으로 체크해야 하는 번거로움"(오해)을 들었습니다. (4) 상세도·비용 4칸에서 메트릭=싸고 대략적, 트레이스=비싸고 상세, 빈 칸=싸고 상세를 전부 자력 통과했습니다.
    • 정답: (1) 모르는 것은 기울기입니다. 82% 라는 경고만으로는 며칠에 걸쳐 서서히 찬 것(A)인지 10분 만에 튄 것(B)인지 구분할 수 없고, 대응이 정반대입니다 — A 는 증설 계획을 세울 일이고 B 는 지금 당장 로그를 뒤져야 할 사고입니다. 원인은 압축 — 78.3 이 WARNING 으로 눌리면 되돌릴 수 없습니다. 시계열은 숫자와 시각을 쌍으로 남겨 기울기가 보존되므로 임계치 도달 전에 계산할 수 있습니다(predict_linear). 체크 기반의 한계는 두 축입니다 — 알려진 미지(무엇을 감시할지)와 압축(어떻게 기록할지). (2) 반대는 증상 기반(symptom-based) 입니다. 비대칭이 핵심 — 원인의 목록은 무한하지만(커넥션 풀·데드락·외부 API·인증서·DNS·배포…) 드러나는 창구는 유한합니다(실패하는가·느린가). 그래서 증상에 걸면 원인을 미리 상상하지 않아도 잡힙니다. 단 완전 대체는 아니고 실무는 증상엔 호출, 원인엔 티켓으로 나눕니다. (3) push 의 진짜 어려움은 중앙 서버가 누가 보내야 하는지 모른다는 것입니다 — "안 오는 것"과 "없는 것"(오토스케일 정상 축소·애초에 없던 대상)이 구별되지 않습니다. pull 은 서비스 디스커버리로 대상 목록을 알아 up == 0 으로 부재를 데이터화합니다. 죽은 대상을 계속 긁는 것은 낭비가 아니라 회복 감지의 필수 조건입니다 — 멈추면 언제 살아났는지 알 수 없습니다. (4) 자력 통과. 빈 칸이 없는 이유는 상세함을 유지하려면 개별 사건을 다 남겨야 하고 값을 싸게 하려면 집계해야 하므로, 둘은 거래 관계입니다.
    • 원인 추정: 공통 결은 "사실은 인출하고 그것이 무엇을 갈리게 하는지에서 멈춤" 입니다. (1)에서 OK 만 남는 것은 맞혔는데 그래서 대응이 정반대로 갈린다는 데까지 못 갔고, (3)에서 push 가 시간으로 판정한다는 것은 맞혔는데 "무엇과 구별이 안 되는가"를 안 세웠습니다. 어제 k8s 12-01·13-01 의 "결론은 맞고 근거가 얕음" 과 같은 유형입니다.
