# 어휘와 연결 제약

이 문서는 값을 정의하지 않습니다. 정본은 [`schema/vocabulary.json`](schema/vocabulary.json)이고, 여기서는 **왜 그렇게 정했는지**를 설명합니다. `tools/build.go`가 그 JSON을 읽어 검증하므로, 어휘를 늘릴 때 Go 코드를 건드릴 필요가 없습니다.

## 왜 어휘집이 필요했나

예시 세 개를 만들고 나서 세어보니 노드 `type`이 24종이었고, **그중 16종이 딱 한 번만** 쓰였습니다. 같은 성격의 것을 예시마다 다르게 불렀기 때문입니다.

```
interface · endpoint · device · socket   ← 전부 "패킷이 드나드는 지점" 계열
```

반면 닫힌 목록으로 관리한 `role`(4종)과 `kind`(3종)는 갈라지지 않았습니다. 통제된 어휘와 자유 어휘의 차이가 그대로 나타난 셈입니다.

그래서 권장 어휘집을 두되, 강제하지는 않습니다. 이유는 아래에 있습니다.

## role 과 type 은 하는 일이 다릅니다

| | `role` | `type` |
|---|---|---|
| 값 | **닫힌 4종** (process·store·external·decision) | **자유 문자열** |
| 하는 일 | 노드를 어떻게 **그릴지** 결정 | 도메인에서 **무엇이라 부르는지** 적는 라벨 |
| 검증 | 목록에 없으면 빌드 실패 | 예약어만 아니면 통과 |

`type`을 자유롭게 둔 이유는 **렌더링에 전혀 관여하지 않기** 때문입니다. 시각은 `role`이, 내부 동작 표시는 `mechanisms`가 결정합니다. `type`을 닫힌 목록으로 만들면 새 도메인(예: 데이터베이스 트랜잭션 흐름)을 그릴 때마다 목록을 늘려야 하고, 그러면 "확장하기 쉽게"라는 목적과 어긋납니다.

대신 도메인별 권장 어휘를 제시해 자연스럽게 수렴하도록 합니다. 지금은 `net` · `k8s` · `linux` · `tls` 네 도메인이 있습니다.

### 딱 하나 강제하는 것 — 예약어

메커니즘 이름 9개(`table-lookup` · `crypt` · `filter` · `queue` 등)는 노드 `type`으로 쓸 수 없습니다. 쓰면 빌드가 실패합니다.

같은 단어가 "이 노드는 무엇인가"와 "이 노드는 무엇을 하는가" 양쪽에 쓰이면 읽는 사람이 혼동합니다. 노드가 무엇인지는 `type`에, 하는 일은 `mechanisms`에 적습니다.

## 새 도메인 추가하기

`vocabulary.json`의 `domains`에 항목 하나를 더하면 끝입니다. 코드 수정도 재컴파일도 없습니다.

```json
"db": {
  "label": "데이터베이스",
  "nodeTypes": {
    "transaction":  "커밋 단위로 묶인 작업 덩어리입니다.",
    "lock-manager": "잠금을 주고받는 관리자입니다."
  }
}
```

## 연결 제약 — 두 단계로 나눈 이유

제약을 전부 에러로 막으면 **정당한 흐름도가 막힙니다**. VXLAN 캡슐화는 payload가 다시 패킷으로 감싸지고, TCP 3-way handshake는 외부 노드가 여러 번 주고받습니다. 도구가 목적을 방해하는 셈입니다.

그래서 성격을 나눴습니다.

| severity | 성격 | 빌더 | Phase B 에디터 |
|---|---|---|---|
| `error` | **불변식** — 어기면 흐름도가 성립하지 않음 | 빌드 실패 | 드래그 드롭 자체를 거부 |
| `warn` | **도메인 관습** — 대개 맞지만 예외가 있음 | 메시지만, 빌드는 통과 | 노드에 경고 배지 |

`warn`은 "이게 의도한 것입니까?"를 묻는 역할입니다. 의도한 것이면 그대로 두면 됩니다. 실제로 TLS 예시의 `app-data` 노드는 흐름의 종착점이라 출력이 없고, 빌더가 경고를 내지만 올바른 상태입니다.

### Phase B 에디터가 같은 파일을 씁니다

React Flow의 `IsValidConnection = (edge: Edge | Connection) => boolean`이 드래그 중 호출되어 `false`를 반환하면 연결이 거부됩니다. `severity: "error"` 규칙이 이 함수로, `warn`은 경고 배지로 갑니다.

규칙을 지금 **데이터로** 만들어 둔 이유가 이것입니다. 문서로만 적었다면 에디터를 만들 때 코드에 다시 옮겨 적어야 하고, 그 순간 문서와 동작이 갈라집니다.

## 규칙이 예시를 막으면 규칙을 의심합니다

이 원칙은 실제로 한 번 발동했습니다.

처음에 `decision` 노드는 출구가 2개 이상이어야 한다는 규칙을 넣었습니다. 그런데 TLS의 ServerHello와 리눅스의 syscall 경계가 걸렸습니다. 두 노드를 들여다보니 **선택은 분명히 하고 있었습니다** — ServerHello는 암호 방식을 고르고(`weighted-select`), syscall 경계는 통과 여부를 판정합니다(`filter`). 다만 그 선택이 갈래로 갈라지지 않고 노드 **안에서** 일어날 뿐이었습니다.

규칙이 틀렸던 것입니다. "분기 노드는 갈래가 여럿"과 "분기 노드는 무언가를 고른다"를 제가 뒤섞었습니다. K8s의 KUBE-SERVICES가 우연히 둘 다 해당해서 눈치채지 못했습니다.

그래서 규칙을 고쳤습니다 — 갈래가 여럿이거나, **선택을 보여주는 메커니즘이 있거나** 둘 중 하나면 통과합니다. 예시를 규칙에 맞추지 않고 규칙을 현실에 맞췄습니다.
