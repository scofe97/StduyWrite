# 고도화 후보 — Jenkins JVM Tuning Lab

기본 랩([`roadmap.md`](roadmap.md))을 완주한 뒤 하나씩 골라 붙이는 옵션 목록이다. 전부 다 할 필요는 없다. 면접에서 어느 방향을 강조하고 싶은지에 따라 한두 개를 골라 진득하게 파는 편이, 얕게 여럿 건드리는 것보다 낫다.

세 축으로 나눈다. 축 A는 Jenkins Controller JVM을 깊게 파는 쪽, 축 B는 배포 대상인 Spring Boot 앱을 최적화하는 쪽, 축 C는 둘을 잇는 연동을 강화하는 쪽이다. 기본 틀이 Spring Boot ↔ Jenkins 호출 구조이므로 축 B와 C가 이 랩의 자연스러운 확장이고, 축 A는 원래 주제였던 Controller 튜닝의 심화다.

## 표기 규약

- **면접 한 줄**: 그 작업을 했을 때 면접에서 말할 수 있는 문장.
- **난이도**: 하(반나절)·중(1~2일)·상(3일+). 기본 랩 위에 얹는 증분 기준이다.
- ⚠️ 표시: 세부를 아직 검증하지 않은 항목. 깊은 질문을 받으면 "문서 확인 필요"로 솔직히 답한다.
- 모든 수치는 실측 뒤에만 이력서에 올린다. 하기 전엔 "했다"고 쓰지 않는다.

## 축 A. Jenkins Controller JVM 심화

원래 주제인 Controller 튜닝을 더 파고든다. Controller는 큐·Run 객체를 heap에 이고 사는 장기 실행 프로세스라, 여기서 나오는 이야기는 "장기 실행 자바 서버를 어떻게 오래 안정적으로 돌리나"로 이어진다.

### A-1. G1 ↔ ZGC 비교 측정 (난이도 중)
- **한다**: 같은 200건 부하를 G1과 ZGC 두 프로파일에 걸어 STW pause 분포를 비교한다.
- **면접 한 줄**: "지연이 민감한 모듈이라 GC 로그를 분석해 ZGC로 STW를 줄였습니다."
- **왜 강한가**: GC를 "안다"가 아니라 "골라서 측정해 봤다"로 격상. 수치로 다루는 백엔드는 드물다.

### A-2. Metaspace 압박 재현 (난이도 중) ⚠️
- **한다**: 플러그인을 늘려 Metaspace를 압박하고, 상한을 걸었을 때와 안 걸었을 때의 거동을 본다.
- **면접 한 줄**: "플러그인 증가가 Metaspace를 어떻게 미는지 재현하고 상한으로 방어했습니다."
- **왜 강한가**: heap만 보는 사람이 많은데 Metaspace까지 본다는 건 JVM 메모리 구조를 안다는 신호. 학습노트 0편 영역이라 격차도 직격.

### A-3. Safepoint 분석 (난이도 중) ⚠️
- **한다**: `-Xlog:safepoint`로 pause가 GC 때문인지 safepoint 동기화 때문인지 가른다.
- **면접 한 줄**: "긴 pause의 원인을 GC와 safepoint로 분리해 짚었습니다."
- **왜 강한가**: pause를 무조건 GC 탓으로 돌리지 않는 것 자체가 깊이의 증거. 학습노트 0편 영역.

### A-4. 힙덤프 histogram 누수 추적 (난이도 중)
- **한다**: 부하 후 heap이 안 내려오는 상황을 만들고 histogram으로 어떤 객체가 점유하는지 짚는다.
- **면접 한 줄**: "heap 기저선이 안 내려와 histogram으로 큐 잔여 객체를 찾았습니다."
- **왜 강한가**: `jvm-practice/ch04-troubleshooting` 진단 기법과 직결. "누수를 잡아 봤다"는 실전 냄새.

### A-5. `-XX:+AlwaysPreTouch` 효과 측정 (난이도 하)
- **한다**: PreTouch 유무로 기동 시간과 첫 GC 거동의 차이를 잰다.
- **면접 한 줄**: "기동 시 페이지를 미리 잡아 첫 부하의 지연 스파이크를 줄였습니다."
- **왜 강한가**: `01-01 §4`가 나열만 한 플래그를 실측으로 검증. 나열과 측정의 차이를 보여 줌.

### A-6. JCasC로 JVM 옵션 형상관리 (난이도 중) ⚠️
- **한다**: Controller 설정과 JVM 옵션 프로파일을 JCasC(YAML)로 코드화해 드리프트를 없앤다.
- **면접 한 줄**: "이미지·플러그인은 코드화했는데 설정 드리프트가 남아 JCasC로 설정까지 내렸습니다."
- **왜 강한가**: 본인 ArgoCD·IaC 강점과 결합. seed에 `casc.yaml`이 이미 있어 출발점이 있음.

## 축 B. Spring Boot 앱 최적화 (기본 틀)

배포 대상인 Spring Boot 앱을 튜닝한다. 이쪽은 요청을 받아 외부를 호출하는 처리량 중심이라, 스레드 모델과 커넥션풀이 핵심이다. 사용자가 든 예시(가상 스레드·톰캣 대체)가 모두 여기 속한다.

### B-1. 가상 스레드(Loom) 전환 + 외부 호출 처리량 (난이도 중)
- **한다**: 외부 호출을 흉내 내는 엔드포인트를 플랫폼 스레드와 가상 스레드로 각각 돌려, 같은 동시성에서 처리량과 스레드 점유를 비교한다.
- **면접 한 줄**: "외부 호출로 스레드가 막히는 구간을 가상 스레드로 풀어 처리량을 올렸습니다."
- **왜 강한가**: 최신 기능을 "왜 쓰는지"까지 답할 수 있음. `jvm-practice/ch05-optimization/native-thread-oom`의 네이티브 스레드 OOM을 대비 근거로 쓰면 "왜 스레드를 무한정 못 늘리나"까지 설명됨.

### B-2. Tomcat ↔ Undertow ↔ Jetty 비교 (난이도 중) ⚠️
- **한다**: 내장 서버를 바꿔 같은 부하에서 처리량·메모리·기동 시간을 비교한다.
- **면접 한 줄**: "기본 톰캣 대신 Undertow로 바꿨을 때의 트레이드오프를 측정으로 확인했습니다."
- **왜 강한가**: "스프링 부트 기본값을 그냥 쓴다"가 아니라 "골라 봤다". 서버 교체는 의존성 한 줄이라 실현 쉬움.

### B-3. HikariCP 커넥션풀 튜닝 (난이도 중)
- **한다**: 풀 크기를 바꿔 가며 동시 요청 아래 대기 시간과 처리량의 변곡점을 찾는다.
- **면접 한 줄**: "풀이 병목인지 DB가 병목인지 대기 지표로 가려 풀 크기를 정했습니다."
- **왜 강한가**: 커넥션풀은 실무 단골 병목. "크게 잡으면 빠르다"는 오해를 수치로 깨는 이야기가 됨.

### B-4. Actuator → Micrometer → Prometheus 앱 메트릭 (난이도 하)
- **한다**: 앱 핫패스에 Micrometer Counter/Timer를 심어 처리량·지연을 Grafana에 노출한다.
- **면접 한 줄**: "앱 핵심 경로에 메트릭을 심어 지연 분포를 대시보드에서 봤습니다."
- **왜 강한가**: `06_observability/05_SpringActuator` 노트가 이미 있어 근거가 탄탄. 관측 인프라와 앱 메트릭을 잇는 그림.

### B-5. 네이티브 스레드 OOM 재현 → 가상 스레드로 해소 (난이도 중)
- **한다**: 플랫폼 스레드를 무한정 늘려 네이티브 OOM을 재현하고, 가상 스레드로 같은 동시성을 흡수한다.
- **면접 한 줄**: "스레드를 늘리다 네이티브 OOM을 만나, 스택을 안 쓰는 가상 스레드로 돌파했습니다."
- **왜 강한가**: `jvm-practice/ch05-optimization/native-thread-oom`에 실측 로그가 이미 있음. B-1과 한 세트로 묶으면 강력.

### B-6. GraalVM native image 기동 시간 비교 (난이도 상) ⚠️
- **한다**: JIT JVM과 native image의 기동 시간·메모리·첫 응답 지연을 비교한다.
- **면접 한 줄**: "서버리스·빠른 스케일 상황을 염두에 두고 native image의 기동 이점을 측정했습니다."
- **왜 강한가**: 최신 주제라 임팩트 큼. 다만 빌드 난이도가 높고 라이브러리 호환 이슈가 있어 시간 투자 필요.

## 축 C. Spring Boot ↔ Jenkins 연동 강화

두 덩어리를 잇는 파이프라인 자체를 두껍게 만든다. 배포가 성공했는지, 배포한 앱이 건강한지, 문제가 생기면 어떻게 알리는지를 다룬다.

### C-1. 배포 후 Actuator `/health` 게이트 (난이도 하)
- **한다**: Jenkins가 앱을 배포한 뒤 `/actuator/health`를 폴링해, 헬스가 UP일 때만 파이프라인을 성공 처리한다.
- **면접 한 줄**: "배포가 끝났다가 아니라 앱이 실제로 떴는지를 헬스체크로 확인하고 넘겼습니다."
- **왜 강한가**: "배포했다"와 "배포가 됐다"의 차이를 아는 사람으로 보임. 구현이 가볍고 효과가 분명.

### C-2. 빌드·배포 결과 Slack/webhook 알람 (난이도 하)
- **한다**: 파이프라인 성공·실패를 webhook으로 알린다. seed Jenkinsfile의 `post` 블록에 이미 TODO로 자리가 있다.
- **면접 한 줄**: "실패를 사람이 로그를 뒤져 찾는 대신 채널로 바로 알리게 했습니다."
- **왜 강한가**: 운영 감각의 기본기. seed에 `slackSend` 힌트가 주석으로 있어 출발점이 명확.

### C-3. 부하 게이트로 배포 승인 (난이도 중) ⚠️
- **한다**: 배포 후 앱 엔드포인트에 부하를 걸어 p95가 기준을 넘으면 배포를 롤백하거나 승인을 막는다.
- **면접 한 줄**: "배포된 앱의 지연이 기준을 넘으면 파이프라인이 스스로 막게 했습니다."
- **왜 강한가**: 성능을 배포 게이트로 삼는다는 발상이 신선. `05-05`의 k6 게이트 개념과 이어짐.

### C-4. 파이프라인 메트릭을 Grafana에 통합 (난이도 중)
- **한다**: 빌드 소요·큐 대기·성공률을 Jenkins `/prometheus/`에서 뽑아, 앱 메트릭과 한 대시보드에 올린다.
- **면접 한 줄**: "CI 파이프라인과 앱 성능을 한 화면에서 보며 병목이 어디인지 짚었습니다."
- **왜 강한가**: FR-6 관측 스택의 자연스러운 확장. 인프라와 앱을 한눈에 보는 그림은 설득력이 큼.

## 고르는 기준

한 방향으로 묶으면 이야기가 강해진다. 세 갈래를 제안한다.

- **JVM 깊이를 파고 싶으면**: A-1(G1↔ZGC) + A-3(Safepoint) + A-4(힙덤프). "튜닝할 줄 안다"를 GC·메모리·진단 세 각도로.
- **Spring Boot 성능을 어필하고 싶으면**: B-1(가상 스레드) + B-5(네이티브 OOM) + B-3(커넥션풀). "외부 호출이 많은 앱을 어떻게 버티게 하나"의 완결된 이야기.
- **DevOps 연동을 어필하고 싶으면**: C-1(헬스 게이트) + C-2(알람) + C-4(메트릭 통합). "배포가 끝이 아니라 배포 후를 책임진다"의 흐름.

어느 것을 고르든 기본 랩이 먼저다. 고도화는 before/after 수치가 나온 뒤에 얹는 증분이지, 랩 없이 단독으로 서지 않는다.
