# 무엇을 보려면 무엇을 치는가

---

> 네트워크 진단 도구는 각자 다른 단위를 봅니다. 도구가 모자라서 못 보는 것이 아니라 단위가 달라서 안 보이는 것이라, 무엇을 알고 싶은지가 도구를 정합니다.

## 이 노트가 있는 이유

> 도구 이름은 알아도 "지금 이 상황에 무엇을 치나"에서 계속 멈췄습니다.

드릴에서 여덟 회차 동안 같은 자리에 걸렸습니다. 가설과 처방은 대는데 확인 명령이 안 나옵니다. [오답 노트](../_drill/_mistakes.md) 반복 패턴 표의 1위 항목입니다.

2026-09-12 회차에 갈래가 드러났습니다. **무언가를 하는 도구는 나오고 상태를 읽기만 하는 도구는 안 나옵니다.** `tcpdump` 와 `exec` 는 되물음 없이 나왔는데 `ethtool -S`·`jcmd`·`conntrack -S` 는 세 문항 연속 안 나왔습니다. 공교롭게 셋 다 `-S` 계열이라 우연으로 보기 어렵습니다.

원인은 도구를 모르는 것이 아니라 **단위를 안 물어서**입니다. "네트워크를 본다"는 한 덩어리로 두면 어느 도구든 될 것 같지만, 실제로는 패킷을 볼지 흐름을 볼지 소켓을 볼지에 따라 칠 것이 정해집니다. 그래서 이 노트는 도구를 나열하지 않고 **단위부터 묻습니다.**



## 단위가 도구를 정합니다

> 같은 사건도 어느 단위로 세느냐에 따라 다른 도구에 잡힙니다.

| 알고 싶은 것 | 단위 | 도구 |
|-------------|------|------|
| 무엇이 오갔나 — 내용까지 | 패킷 하나하나 | `tcpdump` |
| 몇 개가 열려 있나, 누가 무엇에 붙었나 | 소켓 | `ss` |
| 몇 개의 흐름이 살아 있나, 추적에 실패했나 | 흐름(커넥션) | `conntrack` |
| 이 인터페이스가 얼마나 버렸나 | 인터페이스 카운터 | `ethtool -S`, `/proc/net/dev` |
| 프로토콜 층에서 무슨 일이 있었나 | 커널 MIB 카운터 | `nstat`, `netstat -s` |

가장 헷갈리는 쌍이 `tcpdump` 와 `conntrack` 입니다. 커넥션 하나가 3-way 핸드셰이크와 데이터 왕복과 4-way 종료를 거치면 `tcpdump` 에는 수십 줄이 찍히지만 `conntrack` 에는 **한 줄**입니다. 전자는 패킷을 세고 후자는 관계를 셉니다.

`ss` 와 `conntrack` 도 겹쳐 보이지만 다릅니다. `ss` 는 **이 호스트의 소켓**을 보므로 내 프로세스가 연 것만 나옵니다. `conntrack` 은 **이 장비를 지나는 모든 흐름**이라 라우팅만 하고 지나가는 것도 들어갑니다.



## 도구별로 무엇을 보고 무엇을 못 보나

> 못 보는 쪽을 알아야 빈 출력을 오해하지 않습니다.

### `tcpdump` — 패킷의 내용

정체를 알아야 할 때 씁니다. 카운터는 개수만 세므로 "무엇이" 버려졌는지는 여기서만 나옵니다.

```bash
# 이더넷 헤더까지 (-e) · 이름 해석 없이 (-nn) · IP 가 아닌 것만
tcpdump -i br0 -e -nn not ip and not ip6

# 특정 호스트와의 SYN 만
tcpdump -i any -nn 'tcp[tcpflags] & tcp-syn != 0 and host 10.0.1.5'
```

못 보는 것이 있습니다. **이미 버려진 뒤**의 자리에서는 안 잡힙니다. netfilter 가 버린 패킷은 캡처 지점보다 뒤에서 사라지므로 보이지만, NIC 링 버퍼에서 넘친 것은 커널에 올라오지도 못해 캡처에 안 나옵니다.

### `ss` — 소켓의 현재 상태

```bash
ss -lnt                      # LISTEN 중인 TCP 소켓
ss -tan state close-wait     # 특정 상태만
ss -tanp                     # 프로세스까지 (-p)
ss -s                        # 상태별 요약
```

`LISTEN` 줄의 Recv-Q 와 Send-Q 는 [다른 뜻](./패킷이-사라지는-네-자리.md)입니다. 상태에 따라 의미가 바뀌는 것이 이 도구의 함정입니다.

### `conntrack` — 흐름의 장부

```bash
conntrack -C     # 지금 열려 있는 흐름의 개수
conntrack -S     # 통계 — CPU 마다 한 줄
conntrack -L     # 장부 전체를 나열
```

`-C` 와 `-S` 가 갈리는 자리가 중요합니다. `-C` 는 **몇 개인지**만 알려 주므로 포화를 보는 데 쓰고, `-S` 는 **무슨 일이 있었는지**를 알려 줍니다.

```bash
$ conntrack -S
cpu=0   found=0 invalid=171 insert=0 insert_failed=8 drop=8 ...
```

`insert_failed` 는 장부에 적으려다 실패한 횟수이고 `drop` 이 같이 오릅니다. 2026-09-12 B 문항이 이것이었습니다 — 자리는 남아도는데 **같은 자리를 두 번 집어** 실패한 경우라, `-C` 로는 영원히 안 보입니다.

CPU 마다 한 줄인 이유는 통계를 코어별로 세기 때문입니다. `/proc/net/softnet_stat` 이 CPU 마다 한 줄인 것과 같은 구조입니다.

### `ethtool -S` — 드라이버가 세는 값

```bash
ethtool -S eth0 | grep -E 'rx_missed|rx_dropped|rx_fifo'
```

이름이 직관과 어긋나는 자리가 있습니다. 링 버퍼 포화는 `rx_dropped` 가 아니라 `rx_missed_errors` 입니다. 자세한 구분은 [패킷이 사라지는 네 자리](./패킷이-사라지는-네-자리.md)에 있습니다.

가상 인터페이스에서는 의미가 줄어듭니다. `br0` 나 `veth` 는 물리 NIC 이 아니라 링 버퍼가 없으므로, 하드웨어 카운터를 기대하면 빈 출력이나 0 을 봅니다.

### `nstat` — 증가분을 주는 카운터

```bash
nstat -a | grep -E 'ListenOverflows|TCPReqQFull|Retrans'
```

`netstat -s` 와 같은 값을 보지만 **직전 호출 이후의 증가분**을 줍니다. 누적값을 두 번 찍어 빼는 손동작이 도구 하나로 끝납니다.



## 누적인지 순간인지 먼저 봅니다

> 같은 숫자라도 누적값과 현재값은 읽는 법이 다릅니다.

| 성격 | 예 | 읽는 법 |
|------|-----|--------|
| 누적 | `/proc/net/dev` 의 drop, `conntrack -S`, `netstat -s` | 두 번 찍어 **증가분**을 본다 |
| 현재 | `conntrack -C`, `ss` 의 큐 길이 | 한 번 찍고 **상한과 비교**한다 |
| 증가분 | `nstat` | 그대로 읽는다 |

부팅한 지 30일 된 서버에서 누적 `1246` 을 봤다면, 어제 하루에 몰린 것인지 30일에 흩어진 것인지 그 숫자로는 못 가릅니다. 10초 간격으로 두 번 찍으면 갈립니다.

현재값은 반대로 **혼자서는 아무것도 말해 주지 않습니다.** `conntrack -C` 의 `18431` 이 많은지 적은지는 `nf_conntrack_max` 와 나란히 봐야 정해집니다. 비교할 값은 나란히 읽습니다.



## 층이 다르면 서로 안 보입니다

> 도구를 고르기 전에 그 사건이 어느 층에서 일어났는지 먼저 정합니다.

이 원칙은 [패킷이 사라지는 네 자리](./패킷이-사라지는-네-자리.md)에 자세히 적었고, 도구 선택에서는 이렇게 나타납니다.

`iptables -L -v -n` 은 IP 패킷만 봅니다. 이더타입 `0x8912` 같은 비 IP 프레임은 룰이 부족해서가 아니라 **IP 계층에 도달하지 않아서** 안 잡힙니다. 그럴 때는 브리지 계층 도구인 `ebtables` 를 씁니다.

반대 방향도 있습니다. netfilter 가 버린 패킷은 `/proc/net/dev` 의 `drop` 에 안 오릅니다. 인터페이스 입장에서는 수신에 성공해 위로 넘긴 것이라, 그 층의 장부에는 성공으로 적힙니다.

**빈 출력이 "문제 없음"을 뜻하지 않습니다.** 층을 틀렸을 수도 있습니다.



## 증상에서 도구로

> 자주 만나는 증상마다 첫 명령을 고정합니다.

| 증상 | 첫 명령 | 무엇과 무엇을 가르나 |
|------|--------|-------------------|
| 드롭 카운터가 오른다 | `tcpdump` 로 정체 확인 | 우리 트래픽이면 포화, 모르는 프레임이면 정상 |
| 연결이 간헐적으로 느리다 | 지연 값의 분포를 본다 | 1·3·7초 계단이면 SYN 재전송 |
| 응답이 아예 없다 | `ss -tanp` | 소켓이 있으면 앱 문제, 없으면 경로 문제 |
| 거절당한다 | 상대 포트의 `ss -lnt` | 듣는 소켓이 없으면 프로세스 문제 |
| 부하 때만 실패한다 | `conntrack -S` · `nstat` | 증가하는 카운터가 곧 사라진 자리 |

첫 줄이 이 표의 요령입니다. **숫자의 분포도 관측 도구입니다.** 2026-09-12 B 문항은 명령을 치기 전에 응답 시간 분포만 보고 재전송이라는 것이 정해졌습니다. 1·3·7·15 초는 리눅스 SYN 재전송의 기본 간격이라 그 계단 자체가 서명입니다.



## 근거

> 등급을 붙입니다. 확인하지 않은 것은 확인하지 않았다고 적습니다.

- `ss` 옵션과 상태별 컬럼 의미 — [man7 ss(8)](https://man7.org/linux/man-pages/man8/ss.8.html) · 1차. 단 `LISTEN` 상태의 Recv-Q·Send-Q 의미는 man page 에 없습니다
- `rx_dropped` 와 `rx_missed_errors` 의 구분 — [커널 공식 문서 Network statistics](https://docs.kernel.org/networking/statistics.html) · 1차
- `conntrack -S` 의 `insert_failed` — 2026-09-12 B 문항의 원본 포스트모템 · 2차. 필드 의미는 `conntrack-tools` 문서와 대조했습니다
- SYN 재전송 간격 1·3·7·15초 — 리눅스 기본 `tcp_syn_retries` 동작. 배수 규칙은 확인했으나 배포판별 기본값은 미확인이므로 해당 호스트에서 직접 읽습니다
