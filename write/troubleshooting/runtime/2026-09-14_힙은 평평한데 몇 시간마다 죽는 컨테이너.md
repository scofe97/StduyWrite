## 푸는 동안

> 증상만 읽고 세 칸을 채웁니다. 다 채운 뒤 맨 아래 대조로 내려갑니다.

명령의 출력을 적을 때는 그것이 예상인지 실제로 돌려 본 것인지 표시합니다. 코드블록 안에 `# 예상` 또는 `# 실측` 을 붙이면 됩니다. 지면 풀이는 대개 예상만 적으므로, 표시가 없으면 나중에 둘을 구분할 수 없습니다.

### 증상

쿠버네티스에서 도는 Spring Boot 서비스입니다. JDK 25 에 G1 컬렉터를 명시했고, 최대 힙은 `MaxRAMPercentage=70` 으로 컨테이너 한도에서 잡습니다. requests 와 limits 를 같게 둬 Guaranteed QoS 입니다.

Redis 를 많이 부르는 경로가 있어 Netty 기반 Lettuce 클라이언트를 씁니다. OpenTelemetry 자바 에이전트도 붙여 두었습니다. 컨테이너에 준 CPU 는 2 코어이고 그 컨테이너가 올라간 노드는 40 코어입니다.

얼마 전 GC 와 힙 크기를 손봤고 효과가 분명했습니다. 힙 사용량은 며칠 내내 최대 힙의 40~50% 에서 평평했습니다. GC 로그도 조용해져 Full GC 도 긴 멈춤도 없었고, p99 지연도 가라앉았습니다.

그리고 일주일 뒤부터 Pod 이 `OOMKilled` 로 죽기 시작했습니다.

```bash
# 컨테이너 메모리 한도          4 GB
# 최대 힙 (한도의 70%)          약 2.8 GB
# 힙 사용량                     최대 힙의 40~50% — 며칠째 평평
# container working set         시간이 지나며 조금씩 올라 한도에 닿음
# 애플리케이션 로그              java.lang.OutOfMemoryError 없음
```

힙 압박도 없고 GC 도 멀쩡합니다. 그런데 컨테이너의 working set 이 조금씩 올라 한도에 닿으면 커널이 조용히 SIGKILL 을 보냅니다. 재시작하면 몇 시간은 버티고, 같은 일이 되풀이됩니다.

힙이 절반도 안 찼는데 4 GB 를 채운 것은 무엇일까요?

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

**출처** · [Rohlik · Taming JVM Memory on JDK 25 — Part 2: OOMs While the Heap Is Flat](https://blog.rohlik.group/blog/taming-jvm-memory-jdk25-part2) (2026). 푸는 동안에는 제목만으로 답이 보일 수 있어 여기 둡니다. 정리할 때 프론트매터와 문제 소개로 옮깁니다.

**원인 (원문 확정).** JVM 이 세지 않는 메모리였습니다. glibc `malloc` 의 arena 가 쪼개진 채 반납되지 않고 쌓였습니다.

커널이 컨테이너 한도와 비교하는 것은 `-Xmx` 가 아니라 프로세스가 물리 메모리에 올려 둔 전부입니다. JVM 이 스스로 세는 영역에 더해, 그 밑에서 C 라이브러리가 `malloc` 으로 내주는 것까지 들어갑니다.

```bash
# 커널이 세는 것 (RSS)
JVM 이 아는 영역   힙 · 메타스페이스 · 코드 캐시 · 스레드 스택 · direct buffer · GC 자료구조
JVM 이 모르는 영역  C 라이브러리가 malloc 으로 내준 메모리
```

원문에서 RSS 와 힙의 차이는 4 GB 컨테이너에서 약 2 GB 였습니다. 그중 NMT 가 설명한 네이티브 메모리는 약 1.5 GB 였고, 원문은 나머지를 glibc 몫으로 판정했습니다.

glibc 는 여러 스레드가 락을 덜 다투도록 힙을 arena 여럿으로 나눕니다. 64비트에서 arena 수의 기본 상한은 CPU 수의 8 배였습니다. 원문의 요점은 그 CPU 수가 **컨테이너의 CPU 한도가 아니라 노드의 CPU 수**라는 것입니다. 2 코어짜리 컨테이너가 40 코어 노드에 올라가면 상한이 320 이 됩니다. 한 번 쓴 arena 는 거의 비어도 잘 반납되지 않고, 살아 있는 할당 몇 개가 영역 하나를 통째로 붙잡습니다.

이 서비스는 거기에 스레드가 많았습니다. Lettuce 의 `ClientResources` 를 하나로 공유하지 않고 여러 개 만들어 Netty 이벤트 루프가 그만큼 늘었습니다. OpenTelemetry 에이전트는 할당 경로를 더했습니다. 원문의 표현으로 arena 는 설계대로 동작했고 컨테이너가 그것을 감당하지 못했을 뿐입니다.

**배제의 급소.** "힙이 평평하다"는 관찰은 힙 누수를 지우지만 메모리 누수 전체를 지우지 않습니다. 자바 대시보드가 보여 주는 것은 JVM 이 아는 영역뿐입니다. `OutOfMemoryError` 가 없다는 것도 같은 방향의 증거입니다. JVM 이 자기 한도에 걸린 것이 아니라 커널이 바깥에서 죽였기 때문입니다.

**첫 확인 (원문의 순서).**

```bash
# 1. RSS 와 committed 힙을 한 그래프에 — 차이가 끝없이 벌어지면 네이티브 쪽
#    (process.rss 옆에 jvm.memory.committed)

# 2. NMT — JVM 을 -XX:NativeMemoryTracking=summary 로 띄워 둬야 한다
jcmd <pid> VM.native_memory baseline
# ... 시간이 지난 뒤 ...
jcmd <pid> VM.native_memory summary.diff

# 3. NMT 의 Total committed 가 RSS 보다 한참 작으면 할당기를 본다
#    /proc/<pid>/smaps 에서 약 64 MB 짜리 익명 매핑이 길게 늘어서는지
pmap -x <pid>
```

갈림은 2번에서 납니다. NMT 의 어느 영역이 함께 자라면 JVM 이 아는 곳이므로 그 영역을 따라갑니다. NMT 합계는 평평한데 RSS 만 오르면 JVM 바깥이라 3번으로 내려갑니다.

64 MB 라는 크기는 glibc 소스에서 나옵니다. arena 힙의 최대 크기가 `2 * DEFAULT_MMAP_THRESHOLD_MAX` 입니다. 64비트에서 뒤의 값은 `4 * 1024 * 1024 * sizeof(long)` 이라 32 MB 이고, 두 배가 64 MB 입니다.

**처방 (원문).**

- **응급**: 컨테이너 환경 변수로 `MALLOC_ARENA_MAX` 를 낮춥니다. Redis 를 많이 쓰는 경로에서 잰 결과는 아래와 같고, 원문은 4 를 골랐습니다
- **재발 방지**: `ClientResources` 를 하나로 공유하고, 안 쓰는 OpenTelemetry 계측을 끄고, `-XX:MaxDirectMemorySize` 와 Netty 의 arena 수를 노드 CPU 에 맡기지 않고 명시합니다. 그래도 안 되면 `LD_PRELOAD` 로 jemalloc 이나 tcmalloc 으로 할당기를 바꿉니다

| `MALLOC_ARENA_MAX` | 정상 상태 RSS | p99 지연 |
|---|---|---|
| 설정 안 함 (노드 40 코어 × 8) | 몇 시간 안에 OOMKilled | — |
| 8 | 약 3.2 GB | 기준 |
| 4 | 약 2.4 GB | 기준 대비 +2% |
| 2 | 약 2.0 GB | 기준 대비 +11% |

**같은 증상, 다른 원인.** [Docker 컨테이너 네이티브 메모리와 OOMKilled](../../01_language/book/Inside%20the%20Java%20Virtual%20Machine%20JVM%20Advanced%20Features%20and%20Best%20Practices/ch02_automatic-memory-management/01-05.%EC%8B%A4%EC%A0%84%20%E2%80%94%20Docker%20%EC%BB%A8%ED%85%8C%EC%9D%B4%EB%84%88%20%EB%84%A4%EC%9D%B4%ED%8B%B0%EB%B8%8C%20%EB%A9%94%EB%AA%A8%EB%A6%AC%EC%99%80%20OOMKilled.md) 의 사례도 힙은 멀쩡한데 RSS 가 터졌지만, 거기는 닫지 않은 `Inflater` 의 네이티브 zlib 메모리였습니다. 둘 다 NMT 밖이라 NMT 만으로는 안 갈립니다. 할당 주체를 보는 도구(jemalloc 프로파일, 힙 덤프의 `Inflater` 개수)와 `MALLOC_ARENA_MAX` 에 반응하는지가 가릅니다.

- 2023-11 커밋 `472894d2` 가 CPU 수를 procfs 와 sysfs 를 읽는 `__get_nprocs()` 로 되돌렸습니다. 버그 번호는 BZ 30945 입니다
- 이 사례 뒤인 2026-06-04 에 glibc master 커밋 `93e61359` "malloc: Reduce maximum arenas" 가 상한을 코어 수의 8 배에서 `max(8, 코어 수)` 로 줄였습니다. 이 변경이 담긴 릴리스와 배포판 반영 여부는 확인하지 않았습니다
- `M_ARENA_MAX` 의 뜻은 [mallopt(3)](https://man7.org/linux/man-pages/man3/mallopt.3.html) 에 있습니다
