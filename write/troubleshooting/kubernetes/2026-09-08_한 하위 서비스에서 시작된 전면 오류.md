## 푸는 동안

> 증상만 읽고 세 칸을 채웁니다. 다 채운 뒤 맨 아래 대조로 내려갑니다.

### 증상

커머스 사이트의 상품 페이지가 한 시간 넘게 대량 오류를 냅니다. 처음에는 한 화면만 이상했는데 곧 클러스터 안의 서비스 전반이 서로를 못 부르는 상태가 됐습니다.

시작은 이렇습니다. 여러 하위 서비스를 모아 페이지를 만드는 집계 계층이 있습니다. 그중 핵심이 아닌 하위 서비스 하나의 응답이 느려져 타임아웃이 나기 시작했습니다.

집계 계층은 그 실패를 404 로 돌려줍니다. 클라이언트는 재시도합니다.

그 뒤로 지표가 이렇게 움직였습니다.

```pseudocode
집계 계층 인입 요청    ↑ 급증
CoreDNS 질의(QPS)     ↑ 인입과 비슷한 폭으로 급증
CoreDNS Pod 메모리     ↑ 급증 후 반복 재시작
클러스터 전체 이름 해석  ✕ 실패
```

집계 계층은 Node.js 이고 호스트명으로 하위 서비스를 부릅니다. 커넥션 최대 수명이 짧게 잡혀 있어 커넥션을 오래 붙들지 않습니다.

CoreDNS Deployment 의 메모리 limit 은 `100Mi` 입니다. 과거 사용량을 근거로 정한 값입니다.

한 가지가 더 있습니다. 이 사고가 나는 동안 **내부 모니터링도 같이 죽어서** 무슨 일이 벌어지는지 보는 것 자체가 늦어졌습니다.

처음 느려진 그 하위 서비스는 페이지에 없어도 되는 부가 정보를 주는 쪽이었습니다.

### 나의 진단

가설 — 무엇을 의심하고, 무엇을 왜 배제합니까.

```pseudocode
초기 방향 (빗나감)
  느려진 하위 서비스 쪽을 봐야 한다.
  → 그 서비스는 없어도 되는 부가 정보를 주는 쪽이라 방아쇠일 뿐,
    한 시간짜리 전면 장애의 원인이 될 수 없다.

수정
  CoreDNS 가 터져서 페이지 전체가 죽었다.
  범위로 배제 — CoreDNS 는 클러스터 하나의 것이라 모든 Pod 가 공통으로 쓴다.
  conntrack 이 노드 하나의 것이었다면 이쪽은 한 단계 더 넓다.

순서 (초기에 거꾸로 세웠던 것)
  DNS 실패는 원인이 아니라 결과다.
  404 → 재시도 → 질의 폭증 → CoreDNS OOM → 그제야 이름 해석 실패.
```

(명령까지는 대지 못함. 증폭 기전은 대화에서 채웠습니다.)

ndots 미만이면 search 도메인을 차례로 붙여 시도하므로 질의 1 개가 여러 개가 된다.

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

출처는 Zalando 의 공개 포스트모템 [Total DNS outage in Kubernetes cluster (2019-01-07)](https://github.com/zalando-incubator/kubernetes-on-aws/blob/dev/docs/postmortems/jan-2019-dns-outage.md) 입니다. 저장소에 문서로 커밋된 정식 포스트모템입니다.

DNS 실패는 원인이 아니라 결과입니다. 처음부터 이름 해석이 아팠던 것이 아니라, 맨 마지막에 무너졌습니다.

```pseudocode
부가 정보 서비스 하나 타임아웃
  → 집계 계층이 404 반환                     설계 결함 (1)
  → 클라이언트·CDN 재시도 → 인입 급증
  → 호출마다 DNS 질의, 질의 하나가 열 개로     증폭 (2)(3)(4)
  → CoreDNS 메모리 급증 → 100Mi 초과 → OOMKilled
  → 재시작해도 트래픽이 여전해 또 죽음 (크래시 루프)
  → 클러스터 전체 이름 해석 불가
  → 집계 계층이 하위 서비스를 더 못 찾음 → 404 증가 → 되먹임
  → 내부 모니터링도 DNS 의존이라 함께 마비      관측 실패 (5)
```

기여 요인은 포스트모템이 일곱을 적었고 그중 핵심이 다섯입니다.

| 번호 | 요인 | 왜 문제인가 |
|---|------|------------|
| 1 | 핵심 아닌 의존이 페이지 전체를 죽임 | 실패를 격리하지 않음 |
| 2 | Node.js 가 DNS 를 캐시하지 않음 | 해석마다 실제 질의가 나감 |
| 3 | 커넥션 최대 수명이 짧음 | 호출마다 새로 해석 |
| 4 | `ndots:5` 와 search 도메인 | 외부 도메인 1회 조회가 질의 10개 |
| 5 | CoreDNS limit `100Mi` | 피크가 아니라 과거 사용량 기준 |

여기에 CoreDNS 에 VPA 가 없어 자동으로 늘지 못한 것과, 알람이 클러스터 안에 있어 함께 죽은 것이 더해집니다.

아무도 큰 실수를 하지 않았습니다. 각각은 흔한 기본값인데 곱해지면서 자릿수가 바뀌었습니다.

곱셈이 이렇게 붙습니다. 요청이 몇 배로 늘어납니다. 그 요청 하나가 하위 서비스 여럿을 부릅니다. 그 호출 하나가 다시 질의 열 개를 만듭니다.

404 가 사고를 키운 이유가 따로 있습니다. 하위 서비스가 404 를 준 것이 아니라 집계 계층이 스스로 만들어 낸 것인데, 404 는 "원래 없는 리소스"라는 뜻이라 받는 쪽이 영구적 사실로 취급합니다. 503 이었다면 CDN 과 클라이언트가 물러서고 backoff 가 걸렸을 텐데 그 완충이 작동하지 않았습니다. 실패를 어떤 상태 코드로 표현하느냐가 재시도 동작을 바꿉니다.

복구는 온콜이 CoreDNS 메모리 limit 을 `100Mi` 에서 `2000Mi` 로 손수 올려서 이뤄졌습니다. 스무 배입니다. 이것은 응급 조치이지 근본 해결이 아닙니다 — 질의 수 자체를 줄이지 않으므로 더 큰 스파이크가 오면 같은 자리로 돌아옵니다.

그래서 액션 아이템이 셋이었습니다.

- 노드마다 dnsmasq 를 CoreDNS 앞에 두어 캐시로 질의를 앞에서 끊습니다. 쿠버네티스 표준 기능으로는 NodeLocal DNSCache 가 같은 역할입니다
- 알람을 클러스터 바깥에 둡니다. 안에 두면 DNS 와 함께 죽어 눈이 멉니다
- 사고 대응 도구를 개선합니다
