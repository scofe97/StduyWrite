### 증상

**출처** · Grafana Labs 블로그 · "How … caused an outage in Grafana Cloud Logs — and how we resolved it" (사건 날짜 원문에 없음 · 발표 2022-09-01)
> 제목 앞부분의 원인어를 가렸습니다. 전문과 링크는 대조 절에 있습니다.

Grafana Cloud Logs 는 로그 저장 시스템 Loki 를 여러 셀로 나눠 운영하는 서비스입니다. 쓰기는 세 단계를 거칩니다.

```bash
# 쓰기 경로
gateway      인증을 확인하고 쿠버네티스 API 로 distributor 를 찾아 넘긴다
distributor  Deployment, 이 셀에서 140 개. 들어온 로그를 검사하고 복제해 넘긴다
ingester     받은 로그를 메모리에 두었다가 저장소에 쓴다
```

어느 날 한 셀에서 내부 저장소 마이그레이션의 첫 단계를 배포했습니다. 외부 키-값 저장소에 기대던 부분을 내장 방식으로 옮기는 작업이고, 설정이 바뀌어 distributor 롤아웃이 시작됐습니다.

그 셀의 쓰기 경로가 약 25분 멈췄습니다.

| 관찰 | 내용 |
|------|------|
| distributor | OOM 으로 죽고 다시 뜨기를 반복하며 준비 검사를 통과하지 못합니다 |
| 롤아웃 | 새 판으로 갱신된 레플리카가 16/140 에서 멈췄습니다 (`kube_deployment_status_replicas_updated`) |
| 부하 | 쓰기 요청률과 활성 스트림 수는 사고 직전과 같습니다 |
| 분산 | distributor 마다 내는 요청 지표로 세면 쓰기를 받고 있는 레플리카는 16/140 입니다 |
| 다른 셀 | 같은 변경을 먼저 배포한 셀들은 롤아웃 때 늘 보이는 정도의 작은 오류만 냈습니다 |

부하는 그대로인데 일부만 일합니다. 왜 하필 그 일부일까요?

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

**출처** · [Grafana Labs · How adding Kubernetes label selectors caused an outage in Grafana Cloud Logs — and how we resolved it](https://grafana.com/blog/how-adding-kubernetes-label-selectors-caused-an-outage-in-grafana-cloud-logs-and-how-we-resolved-it/) (발표 2022-09-01)

사건 날짜는 원문에 적혀 있지 않습니다.

**재출제 내역.** 2026-09-14 B 문항(업그레이드 2분 뒤 멈춘 클러스터)의 재출제입니다. 같은 지식을 다른 증상으로 냈습니다.

**원인.** 마이그레이션 코드가 distributor Pod 에 새 라벨 하나를 더했습니다. 그런데 이 팀의 설정 라이브러리는 Deployment 의 라벨을 **전부 복사해** Service 셀렉터로 만드는 함수를 쓰고 있었습니다. 그래서 새 라벨이 Service 셀렉터에도 들어갔습니다.

Service 셀렉터는 바뀌는 즉시 적용되지만 Pod 의 라벨은 롤아웃 속도로만 바뀝니다. 그 사이 Service 가 고를 수 있는 Pod 는 새 판으로 갱신된 16 대뿐이었고, gateway 는 쓰기 전부를 그 16 대에 보냈습니다.

> *"We ended up sending 100% of our write traffic to 10% of our distributors."*

16 대는 감당하지 못하고 OOM 으로 죽었습니다. 죽은 Pod 는 준비 검사를 통과하지 못하고, 쿠버네티스는 새 판이 건강해져야 헌 판을 더 갈아 끼우므로 롤아웃이 멈췄습니다. 새 판이 늘지 않으니 같은 16 대가 계속 두들겨 맞는 고리가 됐습니다.

**배제의 급소.** 쓰기 요청률과 활성 스트림이 그대로라는 관찰이 부하 급증을 지웁니다. 갱신된 레플리카 수와 쓰기를 받는 레플리카 수가 똑같이 16 이라는 것이 이 문항의 급소입니다. 새 판과 헌 판을 가르는 무언가가 **누가 트래픽을 받는지까지 정하고 있다**는 뜻이고, 쿠버네티스에서 그 자리에 있는 것이 Service 의 셀렉터입니다.

다른 셀이 멀쩡했던 것도 설명이 붙습니다. 원문은 다른 셀들이 이 셀보다 가로 확장이 덜 돼 있고 메모리 한도에 여유가 있었다고 적습니다. 새 판이 몰린 부하를 조금 더 오래 버티는 사이 롤아웃이 계속 진행돼 새 판 비율이 늘었고, 부하가 퍼졌습니다. 같은 결함이 거기서는 롤아웃 중 흔한 작은 오류로만 보였습니다.

> *"we saw some minor errors when rolling out the migration in other environments and didn't think anything was out of the ordinary."*

**첫 확인.** Service 가 지금 몇 개의 Pod 를 고르고 있는지와, 그 조건이 무엇인지를 나란히 봅니다.

```bash
# 예상
kubectl get endpointslices -l kubernetes.io/service-name=<distributor 서비스> \
  -o jsonpath='{range .items[*]}{range .endpoints[*]}{.addresses[0]}{"\n"}{end}{end}' | wc -l
# 140 이 아니라 16 이면 Service 가 고르는 집합이 줄었다

kubectl get svc <distributor 서비스> -o jsonpath='{.spec.selector}'
kubectl get pods -l <셀렉터의 키=값> --no-headers | wc -l
# 셀렉터에 새 판에만 있는 키가 들어 있는지
```

갈림은 엔드포인트 수에서 납니다. 16 이면 Service 가 고르는 집합이 새 판으로 좁혀진 것이고, 셀렉터와 Pod 라벨을 대조해 어느 키 때문인지 찾습니다. 140 이면 이 가설을 버리고 gateway 쪽이 distributor 목록을 어떻게 캐시하고 나누는지로 갑니다. 원문 팀은 모든 PR 에 붙는 매니페스트 diff 에서 Service 에 셀렉터가 더해진 것을 찾아 확정했습니다.

**처방.**

- **응급**: distributor 레플리카를 늘립니다. 원문 팀이 원인을 알기 전에 한 일이고 실제로 회복이 시작됐습니다. 새로 뜨는 레플리카는 모두 새 라벨을 달고 뜨므로 Service 가 고르는 집합에 들어가 부하를 나눠 받고, 덜 죽으니 롤아웃도 다시 진행됩니다. 그다음 마이그레이션 단계를 되돌려 사고를 끝냈습니다
- **재발 방지**: Service 를 만드는 함수에 셀렉터에서 뺄 라벨 목록을 넘깁니다. 원문의 수정이 `service_ignored_labels` 입니다. 다른 팀이 이미 이 문제를 짚고 선택 인자를 만들어 두었는데 쓰지 않았던 것이 원인의 한 축이었습니다
- **재발 방지(제안)**: 매니페스트 diff 에서 Service 셀렉터가 바뀌면 배포 전에 멈춰 세우고, 롤아웃 중에는 "트래픽을 받는 레플리카 수" 를 레플리카 수와 나란히 보는 경보를 둡니다. 원문에 없는 해석입니다

**1차 확인 (2026-09-22).**

- 원문은 grafana.com 이 403 을 돌려줘 web.archive.org 의 2026-01-16 사본으로 읽었습니다. 25분, 16/140, 100% 를 10% 에, 다른 셀의 작은 오류, 레플리카 증설, `service_ignored_labels` 가 거기 있습니다
- **확인 안 함**: 사건 날짜. 원문은 발표일만 적습니다
- **확인 안 함**: 셀렉터 변경이 기존 Service 를 고친 것인지 새로 만든 것인지의 세부. 원문은 *"resulted in the recreation of the distributor service"* 라고만 적습니다

**정리할 때 할 일.** 채점이 끝나면 2026-09-07 B 문항(Pod 로는 되고 이름으로는 안 되는 호출)의 관련 문서에 이 사고를 "비슷한 실제 사례" 로 겁니다. 그 문항은 연습 문제가 원본이라 실제 사례가 없습니다. 이 문항을 풀기 전에 걸어 두면 이 문항의 답이 거기서 먼저 읽힙니다.
