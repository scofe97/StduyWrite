## 푸는 동안

> 증상만 읽고 세 칸을 채웁니다. 다 채운 뒤 맨 아래 대조로 내려갑니다.

명령의 출력을 적을 때는 그것이 예상인지 실제로 돌려 본 것인지 표시합니다. 코드블록 안에 `# 예상` 또는 `# 실측` 을 붙이면 됩니다. 지면 풀이는 대개 예상만 적으므로, 표시가 없으면 나중에 둘을 구분할 수 없습니다.

### 증상

AWS 위에서 운영하는 쿠버네티스 클러스터입니다. 워커 노드는 가용 영역 세 곳에 고르게 퍼져 있습니다.

주문 애플리케이션은 두 계층입니다. 사용자 요청을 받는 `frontend` 가 비즈니스 로직을 맡은 `backend` 를 ClusterIP Service 로 부릅니다. 두 Deployment 모두 HPA 가 붙어 있고, `backend` 의 HPA 는 Pod 들의 평균 CPU 사용률을 봅니다. 일부 서비스에는 Helm 차트의 조건에 따라 업무 시간 전에 늘리고 퇴근 뒤 줄이는 KEDA 예약 스케일러가 붙습니다.

금요일 저녁, 애플리케이션이 극도로 느려졌다는 Slack 알림이 왔습니다. 데이터베이스와 외부 시스템부터 봤는데 둘 다 정상이었습니다.

`backend` Pod 여섯을 나란히 놓으면 이렇습니다. CPU request 와 limit 은 둘 다 1 코어입니다.

| Pod | 노드 | CPU 사용률 | 초당 요청 (앱 메트릭) | 상태 |
|-----|------|-----------|---------------------|------|
| `backend-6d9f7c8b5-4xk2p` | `ip-10-0-11-23` | 100% | 약 180 | Running · Ready · 재시작 0 |
| `backend-6d9f7c8b5-9qm7d` | `ip-10-0-11-57` | 100% | 약 175 | Running · Ready · 재시작 0 |
| `backend-6d9f7c8b5-t2wpl` | `ip-10-0-42-10` | 100% | 약 185 | Running · Ready · 재시작 0 |
| `backend-6d9f7c8b5-h8znc` | `ip-10-0-42-88` | 100% | 약 180 | Running · Ready · 재시작 0 |
| `backend-6d9f7c8b5-c5rdx` | `ip-10-0-73-14` | 0% 근처 | 0 | Running · Ready · 재시작 0 |
| `backend-6d9f7c8b5-m1vsk` | `ip-10-0-73-41` | 0% 근처 | 0 | Running · Ready · 재시작 0 |

같은 시각에 본 것들입니다.

```bash
# kubectl get endpointslice -l kubernetes.io/service-name=backend
NAME            ADDRESSTYPE   PORTS   ENDPOINTS                                      AGE
backend-x7k2p   IPv4          8080    10.0.11.201,10.0.11.87,10.0.42.15 + 3 more...   47d

# kubectl get hpa backend
NAME      REFERENCE            TARGETS        MINPODS   MAXPODS   REPLICAS   AGE
backend   Deployment/backend   cpu: 67%/70%   6         20        6          47d

# kubectl get deploy frontend
NAME       READY   UP-TO-DATE   AVAILABLE   AGE
frontend   4/4     4            4           47d
```

넷은 한계에 붙어 있는데 HPA 는 늘리지 않습니다. 나머지 둘은 멀쩡히 떠 있고 Service 의 endpoint 목록에도 올라 있습니다.

같은 이미지로 뜬 멀쩡한 Pod 둘이 요청을 하나도 받지 못하는 이유는 무엇일까요?

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

**출처** · [Serhii Kaidalov · Cut Cross-AZ Traffic Costs in Kubernetes with Topology Aware Routing](https://kaidalov.com/posts/2025/02/topology-aware-routing/) (2025). 푸는 동안에는 제목만으로 답이 보여 여기 둡니다. 정리할 때 프론트매터와 문제 소개로 옮깁니다.

개인 블로그에 실린 1인칭 장애 기록이라 [출처 등급표](../_drill/sources.md)로는 가설 칸입니다. 그래서 기전과 기본 동작은 맨 아래 1차 확인에서 공식 문서로 따로 확인했습니다.

**문항용으로 지어 넣은 값.** 원문이 준 사실은 여기까지입니다. 가용 영역 셋, frontend 와 backend 두 계층, 금요일 저녁 알림, 데이터베이스와 외부 시스템 정상, 한 영역의 backend 는 요청 0 이고 나머지 두 영역은 CPU 100%, frontend Pod 4 개가 세 영역 중 둘에만 있었다는 것, backend HPA 가 평균 CPU 기준이었다는 것입니다. Pod 이름·노드 이름·주소·backend Pod 수·HPA 목표 70%·초당 요청 수는 풀 수 있게 지어 넣은 값입니다.

**원인 (원문 확정).** backend Service 에 토폴로지 인지 라우팅이 켜져 있었습니다. 어노테이션 `service.kubernetes.io/topology-mode: Auto` 한 줄입니다. 요청은 보낸 쪽과 같은 영역의 backend 로만 갔는데, 요청을 보내는 frontend 가 두 영역에만 남아 있었습니다. 세 번째 영역의 backend 는 받아 줄 호출자가 그 영역에 없어 놀았습니다.

frontend 가 한쪽으로 쏠린 경위도 원문에 있습니다. 스케일 인이 영역을 가리지 않고 Pod 를 지워 한 영역에서 frontend 가 사라졌습니다. 그 스케일 인은 Helm 차트의 조건식 버그에서 왔습니다. 토폴로지 인지 라우팅을 켠 서비스에는 예약 스케일러를 붙이지 않으려 했는데, `default` 의 인자 순서가 뒤바뀌어 조건이 늘 참이 됐습니다.

```yaml
# 원문의 버그 — default 는 "기본값, 주어진 값" 순서다. 1 은 늘 비어 있지 않으니 결과는 늘 1
{{- if lt (int (default .Values.autoscaling.minReplicas 1)) 2 }}

# 고친 식
{{- if lt (int (default 1 .Values.autoscaling.minReplicas)) 2 }}
```

HPA 가 늘리지 않은 것도 같은 뿌리입니다. 원문은 backend 의 3 분의 1 이 놀아서 평균이 임계 아래에 머물렀다고 적었습니다. 이 문항의 숫자로 옮기면 (100 × 4 + 0 × 2) ÷ 6 ≈ 67% 이고, 목표 70% 와의 비율이 0.96 이라 `ceil(6 × 0.96) = 6` 으로 복제본이 그대로입니다. 비율이 허용 오차 기본값 0.1 안이기도 합니다.

**배제의 급소.**

- 노는 둘이 Ready 이고 EndpointSlice 에 여섯이 다 올라 있습니다. 이 관찰이 selector 불일치와 readiness 탈락을 지웁니다. 후보 목록에는 있는데 선택되지 않는 것이라, 문제는 등록 단계가 아니라 고르는 단계에 있습니다
- 데이터베이스와 외부 시스템이 정상이고, 같은 이미지의 Pod 가 한쪽은 요청 0 입니다. 공통 의존성이나 코드 성능이 문제라면 여섯이 함께 느려져야 합니다. 요청 수 0 은 느리다는 뜻이 아니라 오지 않는다는 뜻입니다
- 가장 크게 망가진 것은 CPU 100% 인 넷이지만 원인은 거기 없습니다. [오답 노트](../_drill/_mistakes.md) 반복 패턴의 "크게 망가진 것을 원인으로 읽음" 자리입니다
- 노는 둘의 노드가 `10.0.73.x` 로 같은 대역입니다. AWS 서브넷은 가용 영역 하나에 속하므로 같은 대역이면 같은 영역일 가능성이 큽니다. 확정은 노드 라벨로 합니다
- HPA 의 `67%/70%` 는 넷이 한계인데 평균은 여유라는 모순입니다. 평균이 편중을 가린 자리입니다

**첫 확인.** 알고 싶은 것이 둘입니다. kube-proxy 가 후보를 영역으로 거르고 있는가, 그리고 요청을 보내는 쪽이 어느 영역에 있는가입니다.

```bash
# 1. 힌트가 박혔는가 — 짧은 출력에는 힌트가 안 나오므로 yaml 로 본다
kubectl get endpointslice -l kubernetes.io/service-name=backend -o yaml | grep -A2 forZones

# 2. 노드의 영역과 호출자의 자리
kubectl get nodes -L topology.kubernetes.io/zone
kubectl get pods -l app=frontend -o wide
```

증상에 준 EndpointSlice 출력은 여섯 endpoint 를 다 보여 주면서도 답은 가렸습니다. 짧은 출력이 `hints` 를 찍지 않기 때문입니다. 관측 도구에서 막히던 [약한 영역](../_drill/sources.md)과 같은 자리입니다.

갈림은 1번에서 납니다. `hints.forZones` 가 있고 2번에서 frontend 가 두 영역에만 있으면, 영역 필터링과 호출자 편중이 겹친 것입니다.

반대로 힌트가 없으면 kube-proxy 는 모든 endpoint 를 씁니다. 그러면 영역 가설을 버리고 연결 단위 분산으로 갑니다. ClusterIP 는 연결 단위로 나누므로, 오래 사는 연결이 처음 붙은 Pod 에 묶였을 수 있습니다. 노는 Pod 가 나중에 뜬 것인지 `AGE` 를 보고, frontend 가 도는 노드의 conntrack 표에서 Service 주소로 간 연결이 실제로 어느 Pod 주소로 바뀌었는지 봅니다.

**처방.** 원문은 응급 조치를 적지 않았습니다. 아래 응급은 기전에서 나오는 선택지이고, 재발 방지는 원문의 개선안과 제 제안을 나눠 적었습니다.

- **응급**: 둘 중 하나입니다
  - backend Service 에서 `topology-mode` 어노테이션을 걷어 영역 필터링을 끕니다. 걷은 뒤 첫 확인 1번으로 `forZones` 가 실제로 사라졌는지 봅니다
  - frontend 를 늘려 세 번째 영역에도 호출자를 둡니다. 새 Pod 가 비어 있는 영역에 뜬다는 보장은 스케줄러 설정에 달려 있어 앞의 것보다 불확실합니다
- **재발 방지 (원문)**: 차트 조건식을 고칩니다. 제약을 어긴 Pod 를 다시 배치하는 descheduler 를 둡니다. HPA 를 가용 영역마다 따로 둡니다. 토폴로지 인지 라우팅 대신 Linkerd 같은 서비스 메시를 쓰는 것도 원문이 든 대안입니다
- **재발 방지 (제안)**: 평균 CPU 만 보는 HPA 는 편중을 못 봅니다. Pod 별 최대값이나 영역별 사용률에 알림을 따로 겁니다

**원문과 1차 문서가 어긋나는 곳.** 원문은 이 기능이 시스템 상태와 상관없이 영역 간 트래픽을 엄격히 막는다고 적었습니다. 공식 문서에는 보호 장치 다섯이 있습니다. endpoint 가 영역 수보다 적거나, 균형 배분이 불가능하거나, 힌트가 빠진 endpoint 가 있으면 전체 endpoint 로 돌아갑니다.

다만 그 보호 장치는 전부 endpoint 와 노드 용량만 봅니다. 요청이 어느 영역에서 오는지는 보지 않습니다. 문서는 유입 트래픽이 영역별 노드 용량에 대략 비례한다고 가정한다고 밝힙니다. 이 사례는 backend 가 영역마다 있어 보호 장치가 발동할 조건이 없었고, 편중은 호출자 쪽에서 났습니다.

원문의 "HPA 가 Pod 를 무작위로 지운다"도 주체가 다릅니다. HPA 는 복제본 수만 바꾸고, 지울 Pod 는 ReplicaSet 컨트롤러가 고릅니다. 그 기준에 영역이 없다는 결론은 같습니다.

**같은 증상, 다른 원인.** 일부 Ready Pod 가 요청을 거의 못 받는 모습은 연결 고정에서도 나옵니다. 둘을 가르는 것은 노는 Pod 들의 공통점입니다. 같은 영역에 모여 있으면 이 문항이고, 나중에 뜬 Pod 들이면 연결 고정입니다.

**1차 확인 (2026-09-15).**

- [Topology Aware Routing](https://kubernetes.io/docs/concepts/services-networking/topology-aware-routing/) — 보호 장치 다섯, "incoming traffic will be roughly proportional to the capacity of the Nodes in each zone" 라는 가정, 자동 확장과 잘 맞지 않을 수 있다는 제약. `topology-mode` 어노테이션은 1.27 부터이고 그 전은 `topology-aware-hints`
- [ReplicaSet · Scaling a ReplicaSet](https://kubernetes.io/docs/concepts/workloads/controllers/replicaset/#scaling-a-replicaset) — 스케일 다운 때 지울 Pod 순서는 Pending, `pod-deletion-cost`, 같은 노드에 몰린 수, 생성 시각이고 나머지는 무작위. 영역은 없음
- [Pod Topology Spread Constraints · Known limitations](https://kubernetes.io/docs/concepts/scheduling-eviction/topology-spread-constraints/#known-limitations) — Pod 를 지울 때는 제약 유지가 보장되지 않고, 재분배는 Descheduler 를 안내
- [HPA · Algorithm details](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/#algorithm-details) — `desiredReplicas = ceil(currentReplicas × currentMetricValue ÷ desiredMetricValue)`, 허용 오차 기본 0.1
- [Helm 함수 목록 · default](https://helm.sh/docs/chart_template_guide/function_list/#default) — `default "foo" .Bar` 는 `.Bar` 가 비어 있지 않으면 `.Bar` 를 쓴다
- 확인하지 않은 것: 어노테이션을 걷었을 때 EndpointSlice 컨트롤러가 기존 힌트를 지우는 시점. 응급 첫째 안 뒤에 직접 봐야 합니다
