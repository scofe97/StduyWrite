## 푸는 동안

> 증상만 읽고 세 칸을 채웁니다. 다 채운 뒤 맨 아래 대조로 내려갑니다.

명령의 출력을 적을 때는 그것이 예상인지 실제로 돌려 본 것인지 표시합니다. 코드블록 안에 `# 예상` 또는 `# 실측` 을 붙이면 됩니다. 지면 풀이는 대개 예상만 적으므로, 표시가 없으면 나중에 둘을 구분할 수 없습니다.

### 증상

**출처** — 없음. 학습 노트에서 구성한 문항입니다. 재출제 내역은 대조 절에 적었습니다.
> 구성 문항이라 아래 상황은 기전에 필요한 조건만 담았습니다. 대수와 비율은 적지 않았습니다.

사내 애플리케이션 여러 대가 로그를 UDP 로 수집기에 보냅니다. 오래된 구성이고 몇 년째 잘 돌았습니다.

지난주에 수집기를 늘렸습니다. 전에는 서버 한 대가 다 받았는데, 처리량이 부족해져 **가상 IP 하나 뒤에 서버 넷**을 두는 구성으로 바꿨습니다. 앞단은 들어오는 트래픽을 네 대에 나눠 줍니다. 애플리케이션 쪽 설정은 목적지 주소도 포트도 그대로입니다.

바꾼 다음 날부터 로그가 빠지기 시작했습니다.

| 관찰 | 내용 |
|------|------|
| 유실 대상 | 긴 로그만 빠집니다. 스택트레이스가 붙은 레코드가 특히 그렇습니다 |
| 짧은 로그 | 한 줄짜리 로그는 전부 도착합니다 |
| 빈도 | 긴 레코드 중 일부만 빠지고, 어느 것이 빠지는지는 회차마다 다릅니다 |
| 수집기 로그 | 빠진 레코드는 네 대 어디에도 없습니다. 잘린 채 들어온 것도 없습니다 |
| 직접 전송 | 서버 한 대에 주소를 박아 보내면 길이와 상관없이 다 도착합니다 |
| 다른 팀 | 같은 수집기에 TCP 로 보내도록 바꾼 팀은 유실이 없습니다 |
| 보내는 쪽 | 송신 애플리케이션의 실패 카운터는 0 입니다. 송신 호스트에서 잡으면 패킷은 나갑니다 |

```bash
# 바뀐 것 하나
수집기   서버 1 대  →  가상 IP 뒤 서버 4 대

# 안 바뀐 것
애플리케이션 설정 · 목적지 주소 · 목적지 포트 · 로그 형식
```

길이에 따라서만 갈리는 유실입니다. 무엇이 긴 레코드만 골라 버리고 있을까요?

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

**출처** — 없음. 학습 노트에서 구성한 문항입니다. 2026-09-14 A 문항(몇몇 사용자만 들어오지 못하는 사이트)의 재출제이고, 같은 지식을 다른 증상으로 냈습니다. 그 회차의 오답 노트에 적은 "다시 볼 것"이 **흐름을 가르는 값과, 바깥 헤더에 그 값이 없는 패킷** 이었습니다.

**원인.** 긴 레코드가 링크의 MTU 를 넘어 IP 조각으로 나뉩니다. 전송 계층 헤더는 **첫 조각에만** 실리므로 비선두 조각에는 포트가 없습니다.

앞단이 주소와 포트를 함께 해시해 서버를 고르면, 포트가 있는 첫 조각과 포트가 없는 나머지 조각이 서로 다른 서버로 갑니다. 각 서버는 조각 일부만 받아 재조립을 끝내지 못하고, 대기 시간이 지나면 가진 조각을 버립니다. 그래서 레코드가 통째로 사라지고 잘린 흔적도 남지 않습니다.

짧은 레코드는 조각나지 않아 한 패킷으로 도착합니다. 길이가 유일한 갈림인 이유입니다.

수집기가 한 대일 때는 조각이 갈릴 곳이 없었습니다. 앞단에 분산이 생긴 날부터 증상이 시작된 것이 그 때문입니다.

**배제의 급소.** "패킷은 나간다"와 "보내는 쪽 카운터가 0"은 송신 측을 지웁니다. "잘린 레코드가 없다"는 수신 애플리케이션의 파싱이나 버퍼 부족을 지웁니다. 버퍼가 넘쳤다면 레코드가 잘리거나 드롭 카운터가 오릅니다. 서버 한 대에 직접 보낼 때 정상이라는 관찰은 **경로 중간의 분산**을 남기고 서버 자체를 지웁니다.

**첫 확인.** 재조립이 실패하는지를 서버에서 봅니다. 네 대에서 동시에 봐야 합니다.

```bash
# 예상 — 수집기 네 대에서
nstat | grep -i reasm          # IpReasmFails · IpReasmTimeout 이 오르는지
netstat -s | grep -i reasm     # "packet reassembles failed" 같은 줄

# 조각이 어디로 떨어지는지 — 네 대에서 동시에
tcpdump -ni any 'ip[6:2] & 0x3fff != 0'   # 조각 플래그·오프셋이 있는 패킷만
```

갈림은 카운터에서 납니다. 재조립 실패가 오르면 조각이 흩어진 것이고, 오르지 않으면 이 가설을 버리고 수신 큐 드롭과 앞단의 드롭 통계로 갑니다.

**처방.**

- **응급**: 앞단이 조각을 첫 조각과 같은 곳으로 보내게 합니다. 해시를 주소와 프로토콜만 쓰도록 바꾸거나, 장비가 조각 전용 처리를 지원하면 켭니다
- **응급 (다른 길)**: 보내는 쪽에서 레코드를 링크 MTU 안으로 자릅니다. 로그 라이브러리의 최대 길이를 박는 쪽이 앞단 설정보다 손이 덜 갈 수 있습니다
- **재발 방지**: UDP 경로에서 조각이 아예 생기지 않게 애플리케이션 레벨 최대 길이를 고정하고, 긴 레코드는 TCP 로 보냅니다. 그리고 재조립 실패 카운터를 관측 대상에 넣습니다. 이 사고는 그 카운터가 대시보드에 없어 길이별 유실로만 드러났습니다

**1차 확인 (2026-09-21).**

- **RFC 2991** *Multipath Issues in Unicast and Multicast Next-Hop Selection* (Thaler·Hopps, 2000-11, Informational)

  [원문](https://www.rfc-editor.org/rfc/rfc2991.txt) **§3 Requirements** 이 다음 홉 선택에 전송 계층 정보를 넣지 말라고 적습니다

  > *"including transport-layer information in the next-hop selection process can actually be problematic. For example, if packets are fragmented, the transport-layer information may not be available in every packet."*

- **RFC 1213** *MIB-II* (McCloghrie·Rose 편, 1991-03, RFC 1158 폐지)

  [원문](https://www.rfc-editor.org/rfc/rfc1213.txt) **§6 Definitions** 의 `ipReasmFails ::= { ip 16 }` 가 이 카운터를 규정합니다

  > *"The number of failures detected by the IP re-assembly algorithm (for whatever reason: timed out, errors, etc). Note that this is not necessarily a count of discarded IP fragments since some algorithms (notably the algorithm in RFC 815) can lose track of the number of fragments by combining them as they are received."*

  버린 조각 수와 같지 않은 이유를 규격이 직접 적어 둡니다. RFC 815 방식이 조각을 받는 대로 합치면서 개수를 놓치기 때문입니다. 그래서 이 값은 실패가 났는지를 가르는 데 쓰고, 몇 개가 버려졌는지를 재는 데는 쓰지 않습니다
- **확인 안 함**: 리눅스가 이 값을 `/proc/net/snmp` 로 내보내는지 — RFC 1213 에는 없는 별개 주장이고 이 회차에서 리눅스 호스트로 확인하지 않았습니다
- **확인 안 함**: 재조립 대기 시간과 버퍼 한도를 정하는 sysctl 의 기본값, 그리고 흔한 로드밸런서·라우터가 조각을 어떻게 처리하는지의 제품별 기본값
