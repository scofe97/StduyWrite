### 증상

**출처** · Kubernetes 이슈 트래커 · kubernetes/kubernetes#126468 "kube-proxy: … leads to …" (사건 2024-07-23 · 발표 2024-07-30)
> 제목의 원인어 두 곳을 가렸습니다. 전문과 링크는 대조 절에 있습니다. 회사 사고 보고가 아니라 AKS 엔지니어가 고객 사례를 올린 이슈라 등급은 준1차입니다. 사건일은 이슈에 붙은 로그 시각 기준이고, 같은 일이 몇 달째 반복됐다고 적혀 있습니다.

관리형 쿠버네티스(AKS) 위에서 서비스를 크게 돌리는 고객입니다. 클러스터 하나에 Service 가 약 1만 개, 엔드포인트가 약 6천 개 있고, 애플리케이션 앞에는 Envoy 가 붙어 있습니다.

플랫폼은 보안 패치가 나오면 노드마다 도는 kube-proxy 를 새 이미지로 다시 배포합니다. 고객이 따로 무엇을 바꾸지 않아도 일어나는 일입니다.

그 재배포 뒤에 이런 일이 반복됐습니다.

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

**출처** · [kubernetes/kubernetes#126468 · kube-proxy: initialization check race leads to stale UDP conntrack](https://github.com/kubernetes/kubernetes/issues/126468) (사건 2024-07-23 · 발표 2024-07-30)

수정은 [PR #126532](https://github.com/kubernetes/kubernetes/pull/126532) 이고 2024-08-14 에 병합됐습니다.

**재출제 내역.** 2026-09-14 A 문항(몇몇 사용자만 들어오지 못하는 사이트)의 재출제입니다. 09-21 에 낸 첫 재출제는 출제자가 원인을 흘려 무효가 됐고, 이 문항이 그 자리를 다시 메웁니다. 같은 지식을 다른 증상으로 냈습니다.

**원인.** kube-proxy 가 다시 뜬 직후 첫 규칙 적용이 Service 캐시가 다 차기 전에 돌았습니다. 첫 적용은 9,605 개 중 4,658 개만 담았습니다. 로그만으로는 kube-dns 가 거기 빠졌는지 보이지 않는다고 원문도 적습니다. 제보자는 코드를 읽어, kube-dns 가 빠지면 그 서비스 주소를 CoreDNS Pod 로 바꿔 주는 DNAT 규칙이 첫 적용에 들어가지 않는다고 짚었습니다. 그리고 재현과 패치로 그것을 확인했습니다.

그 몇 초 사이에 Envoy 가 질의를 보냈습니다. 커널은 그 첫 패킷으로 연결 추적 항목을 만들었습니다. DNAT 규칙이 없었으니 항목은 서비스 주소를 그대로 목적지로 적었습니다. 원문의 `conntrack` 출력을 읽으면 응답 방향의 출발지가 CoreDNS Pod 가 아니라 서비스 주소 자신이고, 이것이 변환 없이 만들어진 항목의 모양입니다.

```bash
# 원문 출력 — 응답 방향 src 가 서비스 주소(192.168.0.10) 그대로다
udp 17 29 src=10.120.1.150 dst=192.168.0.10 sport=49660 dport=53 [UNREPLIED] src=192.168.0.10 dst=10.120.1.150 sport=53 dport=49660 mark=0 use=1
```

규칙은 3초 뒤 두 번째 적용에서 돌아왔습니다. 그런데 NAT 는 **새 연결을 만드는 첫 패킷에서만** 정해지고, 같은 연결의 뒤 패킷은 그 결정을 그대로 따릅니다. Envoy 의 DNS 클라이언트(c-ares)는 같은 출발지 주소와 포트로 질의를 계속 보내므로 커널이 보기엔 늘 같은 연결입니다. 항목의 남은 시간(출력의 `29`)이 다 가기 전에 다음 질의가 와서 항목을 되살리니, 이 흐름은 새 규칙을 한 번도 타지 못합니다.

> *"Envoy c-ares DNS client would send repeated DNS queries to the kube-dns service VIP from the same src IP address, creating a UDP conntrack entry to the svc VIP and keeping it alive"*

**배제의 급소.** 규칙이 빠졌던 것은 3초뿐인데 막힘은 몇 시간입니다. 규칙만의 문제라면 두 번째 적용 뒤 풀려야 합니다. 그러니 남아 있는 것은 규칙이 아니라 **규칙보다 먼저 정해져 버린 상태**입니다.

큰 클러스터에서만 난다는 관찰은 창의 길이를 가리킵니다. Service 가 많을수록 캐시가 차는 데 오래 걸려, 첫 적용이 모자란 채로 도는 틈이 생깁니다. 재현이 안 됐던 것은 그 틈이 작은 환경에서는 거의 열리지 않기 때문입니다.

사람이 명령 하나로 풀었다는 것은 지울 대상이 하나의 항목이라는 뜻입니다. 원문의 그 명령이 `conntrack -D -p udp --src 10.120.1.150 --sport 49660` 입니다.

**첫 확인.** 막힌 Pod 가 있는 노드에서 kube-dns 서비스 주소로 가는 UDP 연결 추적 항목을 봅니다.

```bash
# 예상 — 막힌 노드에서
conntrack -L -p udp --dst <kube-dns 서비스 주소>
# 응답 방향 src 가 CoreDNS Pod IP 면 정상 변환된 흐름
# 응답 방향 src 가 서비스 주소 자신이고 [UNREPLIED] 면 변환 없이 굳은 흐름

# 굳은 흐름이 있으면 그 출발지 포트가 계속 같은지
conntrack -L -p udp --src <막힌 Pod IP>
```

갈림은 응답 방향의 출발지 칸에서 납니다. 서비스 주소 자신이면 변환 없이 만들어진 흐름이 살아 있는 것이고, 거기서 이 가설이 섭니다. 모든 항목이 CoreDNS Pod 로 정상 변환돼 있으면 이 가설을 버리고 CoreDNS 쪽 상태와 노드 사이 경로로 갑니다.

**처방.**

- **응급**: 굳은 항목을 지웁니다. 원문의 `conntrack -D -p udp --src <ip> --sport <port>` 입니다. 메인테이너(aojea)는 임시 우회로 init container 를 제안했습니다. kube-proxy 가 뜰 때 규칙을 비우고 UDP 항목을 한꺼번에 지웁니다. 명령은 `kube-proxy --cleanup && conntrack -D -p udp` 입니다. 다만 제보자(wedaly)는 그것만으로는 첫 적용과 두 번째 적용 사이의 틈을 막지 못한다고 짚었습니다
- **재발 방지**: kube-proxy 를 수정판으로 올립니다. PR #126532 가 Service 와 엔드포인트 핸들러의 동기화를 기다린 뒤 첫 규칙을 적용하게 바꿨고, 제보자는 이 패치로 재현이 멎었다고 적었습니다
- **재발 방지(클라이언트 쪽)**: 같은 UDP 소켓을 계속 재사용하는 DNS 클라이언트는 서비스 가상 주소와 궁합이 나쁩니다. 같은 문제가 nginx 에도 [이슈 #279](https://github.com/nginx/nginx/issues/279) 로 올라와 있습니다

**1차 확인 (2026-09-22).**

- 이슈 #126468 본문과 댓글을 GitHub API 로 원문 그대로 읽었습니다. 규모(Service 약 1만·엔드포인트 약 6천), 빈도(주 1~5회), 로그의 4,658 → 9,605, `conntrack` 출력과 삭제 명령, 메인테이너의 우회와 제보자의 반론이 거기 있습니다
- PR #126532 는 이슈 타임라인에서 2024-08-14 병합으로 확인했습니다
- NAT 결정 시점은 `iptables(8)` 에서 확인했습니다

  > *"nat: This table is consulted when a packet that creates a new connection is encountered."*

  `iptables-extensions(8)` DNAT 절도 *"all future packets in this connection will also be mangled"* 라고 적습니다
- **확인 안 함**: 수정이 어느 kube-proxy 판본들로 역이식됐는지, UDP 연결 추적 항목의 기본 수명 값. 출력의 `29` 는 남은 초이고 기본값은 커널 문서로 재 보지 않았습니다
