## 푸는 동안

> 증상만 읽고 세 칸을 채웁니다. 다 채운 뒤 맨 아래 대조로 내려갑니다.

명령의 출력을 적을 때는 그것이 예상인지 실제로 돌려 본 것인지 표시합니다. 코드블록 안에 `# 예상` 또는 `# 실측` 을 붙이면 됩니다.

### 증상

집계 서비스에서 며칠 전부터 오류율이 올라가 있습니다. 트래픽이 많은 서비스들에서만 나고, 한산한 서비스는 조용합니다.

애플리케이션 로그에는 이것이 쌓입니다.

```pseudocode
org.apache.http.NoHttpResponseException: xxxxx failed to respond
```

앞단 HAProxy 지표에서는 커넥션 리셋 카운트가 꾸준히 올라가고 있습니다. 떨어지지 않고 계속 오릅니다.

증상은 항상 나는 것이 아니라 요청량이 높을 때 몰립니다. 이 서비스는 평시 10,000 req/s 를 넘게 처리하고 스파이크 때는 그 4배까지 갑니다.

배포 이력을 확인했습니다. 애플리케이션 코드와 HAProxy 설정 모두 문제가 시작된 시점 전후로 변경이 없습니다. 다만 인프라 쪽에 최근 두 가지가 있었습니다.

- 비용 절감으로 **노드풀 사양을 낮췄습니다** — 대당 사양이 절반이 되고 대수가 늘었습니다
- 이 서비스가 부르는 **하위 서비스가 샤딩되어 붙는 대상 수가 두 배**가 됐습니다

상대 서비스 쪽 로그에는 이 요청이 도착한 흔적이 없는 경우가 섞여 있습니다.

### 나의 진단

가설 — 무엇을 의심하고, 무엇을 왜 배제합니까.

```pseudocode
1차 가설 (빗나감)
  요청량 폭증으로 HAProxy 에서 문제가 생겼다.

배제 — 관찰에서 끌어낸 것
  상대 서비스 로그에 요청이 아예 안 남는 경우가 있다
    → 서비스가 낸 예외가 아니다. 상대가 거절한 게 아니라 가는 길에 사라졌다.

수정 가설
  리눅스 커널이 in/out 커넥션을 conntrack 장부에 기록한다.
  이 장부에는 상한이 있고, 그 값은 관리자가 아니라 커널이 자체적으로 정한다.
  꽉 차면 새 패킷은 거절 응답 없이 조용히 버려진다.
    → 상대 로그에 안 남는 것과 HAProxy 리셋 카운트가 오르는 것이 동시에 설명된다.
```

첫 확인 — 명령 하나와, 그 출력이 무엇과 무엇을 가릅니까. 그리고 예상과 반대 결과가 나오면 어느 가설을 버리고 다음에 무엇을 봅니까.

```pseudocode
(채우지 못함 — 커널 파라미터를 읽는 명령을 대지 못했습니다.
 방향은 "HAProxy 가 아니라 노드에서, 프로세스가 아니라 커널에게 묻는다"까지 잡았습니다.)
```

처방 — 응급 조치와 재발 방지를 나눠서 적습니다.

```pseudocode
(첫 확인이 갈리지 않아 미작성. 원인에 따라 처방이 달라진다는 판단만.)
```

### 대조

> 세 칸을 *먼저 다 채운 뒤* 읽습니다. 자답 없이 먼저 읽으면 훈련 효과가 0 입니다.

**출처**: loveholidays 의 공개 사례 [Kubernetes networking problems due to the conntrack](https://deploy.live/blog/kubernetes-networking-problems-due-to-the-conntrack/) 입니다. [k8s.af](https://k8s.af/) 실패 사례 모음에 실린 건입니다.

원인은 **일부 노드가 conntrack 테이블 공간을 다 쓴 것** 이었습니다. 넘친 뒤에 온 패킷은 조용히 버려집니다.

여기서 **버려지는 것(DROP)과 리셋(RST)은 같은 사건이 아닙니다.** 앞뒤로 이어진 다른 사건이고, 순서로 풀어야 증상이 맞아떨어집니다.

1. conntrack 이 꽉 차 새 커넥션의 SYN 이 **조용히 버려집니다.** 커널은 거절 응답을 만들어 주지 않습니다 → 상대에 닿지 않고, 상대 로그에 남지 않습니다
2. HAProxy 는 응답이 없으니 **타임아웃**에 걸립니다
3. 타임아웃을 처리하며 반쯤 열린 소켓을 정리할 때 **RST 가 나가고**, HAProxy 는 그것을 커넥션 리셋으로 셉니다

즉 RST 는 커널의 drop 이 직접 만든 것이 아니라, **drop 때문에 응답을 못 받은 프록시가 뒤늦게 소켓을 정리하며 만든 것**입니다. 애플리케이션의 `NoHttpResponseException` 도 같은 자리입니다 — "응답 없이 연결이 끊겼다"입니다.

테이블이 포화된 상태에서는 기존에 잘 돌던 커넥션의 항목이 **밀려나** 돌아온 응답이 매칭 실패로 버려지는 경우도 섞입니다. 이쪽은 정말로 중간에서 끊긴 것처럼 보입니다.

여기서 핵심은 **아무도 무엇을 잘못 바꾸지 않았다** 는 점입니다. 세 가지가 겹쳐서 한도를 넘었습니다.

1. 노드 사양을 절반으로 낮췄습니다 → **한도가 같이 줄었습니다**
2. 하위 서비스 샤딩으로 추적할 커넥션 수가 두 배가 됐습니다 → **수요가 늘었습니다**
3. 평시 10,000 req/s 에 4배 스파이크 → 여유가 없습니다

1번이 이 사례의 함정입니다. `nf_conntrack_max` 는 관리자가 정한 값이 아니라 기본값이 **총 메모리에서 유도** 됩니다. 커널 공식 문서(`nf_conntrack-sysctl`)가 이렇게 적습니다.

- `nf_conntrack_buckets`: "모듈 로딩 시 인자로 지정하지 않으면 기본 크기는 **총 메모리를 16384 로 나눠** 버킷 수를 정한다." 하한 1,024 · 상한 262,144
- `nf_conntrack_max`: "허용되는 연결 추적 항목의 최대 수. 기본적으로 이 값은 **`nf_conntrack_buckets` 와 같게** 설정된다"

즉 **RAM 을 줄이면 커널이 조용히 커넥션 추적 한도도 같이 줄입니다.** 사양 축소는 CPU·메모리 여유만 건드리는 결정으로 보이지만 네트워크 상태 테이블의 상한까지 함께 내립니다. 이 연결이 안 보이면 "인프라는 안 건드렸는데"라는 말이 나옵니다.

> 커널 버전에 따라 배수가 다릅니다. 5.15 이전에는 `nf_conntrack_max` 가 buckets 의 **4배** 였고 5.15 부터 **같은 값** 입니다. 배수를 외우지 말고 **그 노드에서 직접 읽는 것** 이 맞습니다.

첫 확인은 현재값과 한도를 나란히 보는 것입니다.

```bash
# 지금 얼마나 쓰고 있는가 / 한도는 얼마인가
sysctl net.netfilter.nf_conntrack_count net.netfilter.nf_conntrack_max

# 넘쳐서 버린 적이 있는가 — 있으면 커널이 남깁니다
dmesg | grep -i "nf_conntrack: table full"
```

이 출력이 무엇을 가르는가 — count 가 max 에 붙어 있으면 이 방향이 확정에 가깝고, 한참 여유가 있으면 conntrack 은 지우고 애플리케이션 쪽 커넥션 풀·타임아웃이나 상대 서버로 내려갑니다. 노드마다 값이 다르므로 **증상이 나는 노드에서** 봐야 합니다. 사양이 섞인 클러스터라면 작은 노드만 넘치고 있을 수 있습니다.

### 그 전에 — HAProxy 를 먼저 지웁니다

"상대 로그에 안 남는다"가 지우는 것은 **상대 서비스** 이지 **HAProxy** 가 아닙니다. 둘은 다른 후보이므로 따로 갈라야 합니다. HAProxy 가 스스로 무엇 때문에 세션을 끝냈다고 적는지를 봅니다.

```bash
# HAProxy 로그의 termination state 두 글자가 종료 사유를 구분합니다
# sC = 서버 연결 단계에서 실패(서버가 응답 안 함) / cD = 클라이언트 쪽 데이터 단계 끊김 등
tail -f /var/log/haproxy.log

# HAProxy 자신의 커넥션 한도에 걸린 것은 아닌가
echo "show stat" | socat stdio /var/run/haproxy.sock
#   scur = 현재 세션 수, slim = 세션 한도, econ = 서버 연결 실패 수
```

여기서 HAProxy 가 **"내 한도에 걸렸다"** 고 말하면 원인이 HAProxy 이고, **"서버가 응답을 안 줬다"** 고 말하면 HAProxy 는 피해자이므로 그 아래 커널 층으로 내려갑니다. 이 구분을 먼저 하면 conntrack 으로 가는 길이 추측이 아니라 소거가 됩니다.

원 사례는 Prometheus 로 이 둘을 봤습니다. 노드 단위로 상시 보려면 이쪽이 맞습니다.

```pseudocode
node_nf_conntrack_entries / node_nf_conntrack_entries_limit
```

조치는 이렇습니다.

- **응급**: 이 서비스를 RAM 이 큰 노드에 배치하고 노드당 Pod 수를 제한했습니다. 한도가 RAM 에서 나오므로 배치를 바꾸는 것이 곧 한도를 올리는 일입니다. `nf_conntrack_max` 직접 상향도 가능하지만 항목당 메모리를 쓰므로 노드 여유 안에서만 올립니다
- **재발 방지**: `entries / limit > 0.75` 알람을 걸었습니다. 이 지표가 없으면 다음에 사양이나 샤딩이 바뀔 때 같은 자리로 돌아옵니다
- **검증**: 조치 뒤 같은 피크 구간에서 비율이 임계 아래로 내려가고 `NoHttpResponseException` 과 HAProxy 리셋 카운트가 함께 떨어지는지 봅니다

**이 문항이 겨냥한 것**. 오답 노트 반복 패턴 표에 "확인할 명령을 내지 못함"이 3회로 올라 있습니다. 여기서 요구한 것은 `sysctl` 두 값을 **나란히** 읽는 것 하나입니다. 그리고 "용량은 내가 정한 값"이라는 가정을 깨는 것이 두 번째 노림수입니다 — 커널이 하드웨어에서 유도하는 한도가 있고, 그것은 사양을 바꿀 때 말없이 따라 움직입니다.

## 나온 개념

> 이 문항에서 갈라져 나온 것들입니다. 이론은 여러 문항에 걸리므로 [개념 노트](../_concepts/패킷이-사라지는-네-자리.md)에 모아 두고 여기서는 **이 문항에서 걸린 지점만** 적습니다.

### [패킷이 사라지는 네 자리](../_concepts/패킷이-사라지는-네-자리.md)

이 문항에서 conntrack 한 자리를 채웠습니다. 걸린 지점 셋입니다.

- **한도를 커널이 하드웨어에서 유도한다** — 관리자가 정한 값이라고 가정해 사양 축소와 증상을 잇지 못했습니다
- **읽는 명령이 `sysctl`** — 프로세스(HAProxy)에게 물으려 했고, 커널에게 묻는 명령을 대지 못했습니다
- **비교값은 나란히** — `count` 만으로는 아무것도 모르고 `max` 와 함께 봐야 비율이 나옵니다

같은 노트의 accept 큐 자리도 이 회차 대화에서 함께 채웠습니다. NIC 링 버퍼와 SYN 큐는 빈칸으로 남았습니다.
