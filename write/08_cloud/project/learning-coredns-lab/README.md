# learning-coredns-lab — 프로젝트 인덱스

---

> 『Learning CoreDNS』 1~4장을 사내 DNS 장애 일곱 개로 다시 확인하는 실습의 기록 폴더입니다. Corefile 과 존 파일은 실습 저장소에 두고, 이 폴더에는 시나리오마다 예측·관측·원인을 적은 기록만 둡니다.

## 이 폴더는 무엇인가

> 책 노트를 읽고 맞힌 예측이 실제 서버에서도 그대로인지 장애 상황으로 확인합니다. 개념 설명은 책 노트에 있으므로 여기서는 링크로 대신합니다.

4장 학습에서 막힌 개념이 많아, 이 상태로 9장까지 이론만 이어 가면 뒤 장의 전제가 흔들립니다. 그래서 5장에 들어가기 전에 1~4장을 손으로 확인하기로 했습니다. 특히 존(데이터)과 서버 블록(설정)의 구분이 흔들렸기 때문에, 그 차이가 장애 원인으로 드러나는 시나리오를 넣었습니다.

실습 파일은 `~/study/runners-lab/net/learning-coredns`(GitHub 모노레포 `scofe97/StudyLab`)에 있습니다. 가상의 쇼핑몰 서비스 `shop.example` 이 사내 DNS 로 CoreDNS 1.15.0 한 대를 쓰고, 맥북에서 포트 1053 으로 띄웁니다.



## 진행 방식

> 신고 문장만 보고 원인을 예측한 뒤, 직접 입력한 설정과 `dig` 출력으로 확인합니다.

시나리오 하나는 다섯 단계로 진행합니다. 먼저 신고 문장과 현재 설정 조각을 받고 그 설정을 직접 입력해 장애를 재현합니다.

그다음 원인과 `dig` 결과를 예측하고 관측 명령을 돌려 예측과 비교합니다. 마지막으로 설정을 직접 고쳐 다시 확인합니다.

예측은 실행 전에 적고 실행 뒤에도 고치지 않습니다. 어긋난 자리가 다음에 다시 볼 곳이기 때문입니다.



## 시나리오와 기록

> 일곱 시나리오의 신고 문장과 기록 자리입니다. 원인은 실습을 마친 뒤 기록에만 적습니다.

| # | 신고 문장 | 관련 노트 | 기록 |
|---|---|---|---|
| S1 | DB 장애조치 후 `db.shop.example` 을 새 IP 로 고쳤는데, 앱이 계속 옛 DB 에 붙는다 | `02-02`, `04-01` | 완료 2026-11-02 |
| S2 | S1 을 고쳤는데 몇 분 동안 일부 요청은 여전히 옛 IP 로 간다 | `03-02` | 완료 2026-11-02 |
| S3 | 신규 서비스 `coupon` 레코드를 넣었는데 한동안 "그런 이름 없음"이 나온다 | `02-02`, `03-02` | 완료 2026-11-03 |
| S4 | 사내 존 블록을 추가한 뒤, 사내 이름 질의가 외부 DNS 로 새어 나간다 | `03-01` | 아직 |
| S5 | 상위 DNS 두 대 중 하나가 죽은 뒤, 결제사 API 이름 해석이 가끔 느리다 | `03-02` | 아직 |
| S6 | 팀마다 존이 늘어 `auto` 로 바꿨는데, 새 팀 존 하나만 응답하지 않는다 | `04-01` | 아직 |
| S7 | 긴급히 이름 하나를 `hosts` 로 덮어썼더니 그 존의 다른 이름이 전부 실패한다 | `03-02`, `04-01` | 아직 |

S1 과 S2 는 같은 장애가 이어지는 이야기라 순서대로 진행합니다. 나머지는 각각 따로 해도 됩니다.



## S1·S2 기록 (2026-11-02)

> 두 시나리오 모두 증상은 "옛 IP"였지만, 옛 데이터를 들고 있던 자리가 S1 은 `file`, S2 는 그 앞의 `cache` 였습니다.

S1 에서는 존 파일의 `db` 주소만 고쳤더니 서버가 계속 옛 주소로 답했습니다. 터미널 로그에 다시 읽었다는 줄이 없었고, `dig shop.example SOA` 의 시리얼이 파일과 같았습니다. `reload` 는 2초마다 SOA 시리얼을 비교해 다시 읽을지 정합니다. 그래서 시리얼을 `2026110202` 로 올리자 `Successfully reloaded` 줄이 찍히고 새 주소가 나왔습니다.

S2 에서는 `cache` 를 켠 뒤 주소와 시리얼을 함께 고쳤습니다. 다시 읽은 로그가 먼저 찍혔는데도 답은 약 30초 동안 옛 주소였습니다. TTL 이 27·17·7 로 줄다가 만료된 뒤에야 새 주소가 TTL 30 으로 나왔습니다. 질의를 `cache` 가 먼저 받아 담아 둔 답을 주고 `file` 까지 넘기지 않았기 때문입니다.

| 시나리오 | 내 예측 | 실제 | 판정 |
|---|---|---|---|
| S1 | 다시 읽었으면 20, 안 읽었으면 10 (하나를 고르지 못함) | 10 | 채점 생략 |
| S1 원인 | 다시 읽지 않았고 메모리로 답함, 시리얼이 그대로라서 | 같음 | 맞음 |
| S2 | 캐시가 있어도 결국 갱신하니 바로 새 주소 | 다시 읽은 뒤에도 TTL 동안 옛 주소 | 잘못 알던 인과 |
| S2 대응 | 미리 바꿔 두면 꼬이지 않는다 | 미리 바꿀 것은 IP 가 아니라 TTL | 몰랐던 사실 |

실무 대응은 장애조치 전에 TTL 을 미리 낮추는 것입니다. 낮춘 TTL 도 옛 TTL 을 단 채 이미 퍼진 답이 만료돼야 효과가 납니다. 그래서 옛 TTL 한 번만큼 앞서(예: 하루 전 `3600` → `60`) 바꾸고, 당일 주소를 바꾼 뒤 안정되면 되돌립니다. 실제 서비스에서는 앱 서버의 OS 리졸버와 다른 DNS 서버도 같은 TTL 만큼 답을 담아 둡니다. 담은 시점이 저마다 달라 일부는 새 IP, 일부는 옛 IP 로 섞입니다.



## S3 기록 (2026-11-03)

> "없다는 답"도 캐시에 남았고, CoreDNS 에서 그 시간을 정한 것은 SOA 의 MINIMUM 칸이 아니라 SOA 레코드 자신의 TTL 이었습니다.

배포 전 조회로 `coupon.shop.example` 의 NXDOMAIN 을 받은 뒤 레코드를 넣고 시리얼을 올렸습니다. 다시 읽었다는 로그가 찍혔는데도 약 30초 동안 NXDOMAIN 이 나왔습니다. 권한 절 SOA 의 TTL 은 14·11·8·5·2 로 줄었습니다. 그 SOA 의 시리얼이 파일의 새 값이 아니라 옛 값(`2026110301`)이어서, 이 답이 `cache` 에 담겨 있던 것임을 알 수 있었습니다.

다음으로 `$TTL` 만 300 으로 올리고 MINIMUM 은 20 으로 두었습니다. 없는 이름의 SOA TTL 은 300 에서 시작했습니다. `file` 이 SOA 를 레코드 TTL 그대로 실어 보내고, `cache` 는 응답 안 레코드 TTL 의 가장 작은 값만 보기 때문입니다. MINIMUM 칸은 RFC 2308 을 따르는 다른 리졸버가 읽습니다.

| 단계 | 내 예측 | 실제 | 판정 |
|---|---|---|---|
| 넣은 뒤 답 | 캐시가 지날 때까지 NXDOMAIN | 같음 | 맞음 |
| 걸린 시간 | 30초, 리로드까지 치면 최대 32초 | 첫 조회부터 약 30초, 리로드는 더해지지 않음 | 몰랐던 사실 |
| 시간을 정한 칸 | 시리얼 | SOA 레코드의 TTL | 잘못 알던 인과 |
| `$TTL 300`, MINIMUM 20 | 300 | 300 | 맞음 |

대응은 다른 레코드의 TTL 은 두고 SOA 의 TTL 만 낮추는 것입니다. 파일 맨 앞에 `$TTL 30` 을 두고 SOA 줄 바로 뒤에 `$TTL 300` 을 두자, 없는 이름의 SOA 는 30 으로 나왔습니다. SOA 줄에만 `@ 30 IN SOA` 처럼 TTL 을 적어도 같습니다. 이 서버의 캐시만 줄이려면 `cache { denial 9984 30 }` 으로 상한을 둡니다. 이미 캐시에 든 부정 답은 고친 뒤에도 그 TTL 이 다할 때까지 남습니다.
