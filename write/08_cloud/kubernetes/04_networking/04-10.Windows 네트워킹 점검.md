# Windows 네트워킹 점검
---
> Windows 네트워킹의 구성 요소, 모드, Service 기능, 제한을 장애 시나리오 중심으로 확인합니다.



## 점검 방법

> Linux와 다른 이유를 포함해 답하고 Windows 환경에서 실행하지 않은 결과를 추측하지 않습니다.

각 질문에는 구성 요소와 패킷 경로를 연결해 답합니다. CNI 공급자별 세부 구현은 공식 직접 페이지의 범위를 벗어나므로, 여기서는 Kubernetes v1.36 문서가 설명하는 공통 모델과 명시된 제약을 기준으로 합니다.



## 1. 구성 요소

> HCS와 HNS의 책임 및 Linux 파일 기반 구성과의 차이를 확인합니다.

### 질문 1

Windows Pod의 네트워크는 어떤 구성 요소로 만들어집니까?

### 모범 답변 1

컨테이너마다 vNIC가 있고 Hyper-V vSwitch에 연결됩니다. CNI plugin이 Windows 네트워크 구성을 요청하며, HCS는 컨테이너를 관리하고 HNS는 virtual network, endpoint와 vNIC, namespace, encapsulation·load balancing·ACL·NAT policy를 관리합니다.

### 질문 2

Linux처럼 호스트의 `/etc/resolv.conf`를 컨테이너에 매핑하면 왜 같은 결과를 기대할 수 없습니까?

### 모범 답변 2

Windows는 DNS, route, metric 같은 많은 네트워크 구성을 파일이 아니라 Registry에 저장합니다. 컨테이너 Registry는 host와 분리되어 있으므로 Linux식 파일 매핑으로 설정이 전달되지 않습니다. Windows CNI는 컨테이너 문맥에서 Windows API와 HNS를 호출해야 합니다.



## 2. 네트워크 모드

> underlay, overlay, 주소 변환의 차이로 모드를 선택할 수 있는지 확인합니다.

### 질문 3

L2bridge와 Overlay 모드의 차이를 설명해 보세요.

### 모범 답변 3

L2bridge는 컨테이너를 외부 vSwitch와 underlay에 연결하고 container MAC을 host MAC으로 바꿉니다. 성능이 좋지만 노드 간 Pod 연결을 위한 사용자 정의 route가 필요할 수 있습니다. Overlay는 network별 subnet을 만들고 VXLAN으로 캡슐화해 underlay와 격리하며 VNID가 다른 network에서 IP를 재사용할 수 있습니다.

### 질문 4

L2tunnel, Transparent, NAT는 각각 언제 사용됩니까?

### 모범 답변 4

L2tunnel은 Azure 전용 L2bridge 특수 형태로 모든 패킷을 가상화 host에 보내 SDN 정책을 적용합니다. Transparent는 ovn-kubernetes 특수 사례로 외부 vSwitch와 GENEVE 또는 STT tunnel을 사용하며 분산 ACL과 kube-proxy 없는 부하 분산을 지원할 수 있습니다. NAT는 내부 vSwitch와 WinNAT를 쓰지만 Kubernetes에서는 사용하지 않습니다.

### 질문 5

혼합 OS 클러스터에서 네트워크 모드를 고를 때 가장 먼저 확인할 것은 무엇입니까?

### 모범 답변 5

선택한 CNI가 Linux와 Windows 양쪽에서 필요한 mode와 Kubernetes 기능을 지원하는지 확인합니다. Windows 자체가 mode를 제공한다는 사실만으로 Linux node와 동일한 주소 관리, NetworkPolicy, Service dataplane이 보장되지는 않습니다. Flannel이라면 Windows VXLAN은 win-overlay, host-gateway는 win-bridge에 위임한다는 구조도 고려합니다.



## 3. IPAM과 Service

> 주소 할당과 Service 부하 분산 기능의 조건을 점검합니다.

### 질문 6

Windows에서 공식 문서가 열거하는 IPAM 선택지는 무엇입니까?

### 모범 답변 6

일반적인 `host-local`, Azure CNI에서만 사용하는 `azure-vnet-ipam`, 명시적 IPAM이 없을 때 fallback인 Windows Server IPAM입니다. 사용할 CNI, network mode, 클라우드 환경과 호환되는 조합을 선택해야 합니다.

### 질문 7

DSR은 무엇이며 왜 사용합니까?

### 모범 답변 7

Direct Server Return은 IP fixup과 LBNAT를 container vSwitch port에서 처리하고 backend의 응답이 load balancer를 우회해 client로 직접 가게 하는 방식입니다. load balancer 부하와 전체 지연을 줄이며 원본 source IP 보존에 필요합니다. `WinDSR`은 Kubernetes v1.34에서 stable이 되었고 기본으로 활성화되지만, 기능 게이트 상태와 Windows node의 실제 Service dataplane 설정은 구분해야 합니다. Windows Server 2019 이상인지 확인하고 kube-proxy를 `--enable-dsr=true`로 구성합니다.

### 질문 8

Windows에서 client IP를 보존하려면 어떤 조건이 필요합니까?

### 모범 답변 8

Windows Server 2019 이상에서 Service의 `externalTrafficPolicy`를 `Local`로 설정하고 kube-proxy에서 DSR을 활성화합니다. 이 설정은 ingress source IP를 보존하지만 node 간 forwarding을 끄므로 local endpoint가 없는 node의 동작까지 확인해야 합니다.

### 질문 9

Windows Service 하나에 backend를 100개 연결하려는 설계에 어떤 문제가 있습니까?

### 모범 답변 9

공식 페이지는 Windows node에서 Service 하나당 backend Pod 또는 고유 destination address가 64개를 초과하는 구성을 지원하지 않는다고 명시합니다. 따라서 해당 설계는 지원 범위를 벗어나며 Service 분할이나 데이터플레인 대안을 검토해야 합니다.



## 4. 장애 진단

> Windows 고유 제한 때문에 정상 기능을 장애로 오판하거나 그 반대가 되는 상황을 확인합니다.

### 질문 10

Windows Pod에서 외부 주소로 `ping`이 실패하지만 HTTP 요청은 성공합니다. 어떻게 해석합니까?

### 모범 답변 10

win-overlay, win-bridge, Azure CNI 경로에서 VFP는 외부 network로 나가는 ICMP packet transposition을 지원하지 않습니다. 같은 network의 Pod 간 ICMP와 TCP/UDP는 동작할 수 있지만 외부 `ping` 응답은 source로 돌아오지 못할 수 있습니다. 따라서 외부 연결은 `curl` 등 실제 TCP/UDP port로 검증하고 `ping` 실패만으로 network 장애라고 결론 내리지 않습니다.

### 질문 11

Windows node 자신에서 local NodePort가 열리지 않습니다. 반드시 장애입니까?

### 모범 답변 11

아닙니다. Windows node에서는 node 자신에서 local NodePort 접근을 지원하지 않으며 다른 node 또는 외부 client에서의 접근은 지원합니다. 시험 위치를 바꿔 결과를 분리해야 합니다.

### 질문 12

overlay를 사용하는 Windows Pod 간 IPv6 연결이 실패합니다. 무엇을 확인합니까?

### 모범 답변 12

Windows는 overlay network에 연결된 Pod 사이 IPv6 통신을 지원하지 않습니다. dual-stack 자체는 Windows Server 2019부터 지원되지만 모든 network mode에서 모든 IPv6 경로가 된다는 뜻은 아닙니다. CNI mode와 실제 통신 경로를 먼저 확인합니다.

### 질문 13

Windows node에서 host networking을 사용하는 DaemonSet을 배치할 수 있습니까?

### 모범 답변 13

Windows node는 host networking mode를 지원하지 않습니다. Linux용 `hostNetwork` 전제를 그대로 가져오지 말고 Windows가 지원하는 HostProcess나 공급자별 node agent 배치 모델을 별도 공식 문서에서 검토해야 합니다.



## 5. 최종 체크

> 아래 사실을 이유와 함께 설명하면 Windows 네트워킹의 핵심 경계를 이해한 것입니다.

- HCS는 컨테이너를, HNS는 network resource와 policy를 관리합니다.
- 혼합 클러스터의 CNI는 Linux와 Windows를 모두 지원해야 합니다.
- NAT mode는 Windows에 존재하지만 Kubernetes에서는 사용하지 않습니다.
- DSR은 source IP 보존과 직접 반환 경로에 연결됩니다.
- `WinDSR`은 Kubernetes v1.34 stable·기본 활성 기능이지만 실제 Windows kube-proxy DSR 구성은 별도로 확인합니다.
- 외부 `ping` 실패는 TCP/UDP 실패를 뜻하지 않습니다.
- host networking, 64개 초과 backend, overlay Pod 간 IPv6에는 명시적 제한이 있습니다.
