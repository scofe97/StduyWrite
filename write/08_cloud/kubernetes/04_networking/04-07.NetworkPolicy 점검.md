# NetworkPolicy 점검
---
> 허용 목록의 합산, 양방향 판정, selector 들여쓰기와 구현별 예외를 말로 설명할 수 있는지 점검합니다.



## 점검 목표

> 정답 암기보다 주어진 연결을 방향별로 판정하고 운영 실패의 원인을 좁히는 능력을 확인합니다.

질문을 읽은 뒤 먼저 답을 가리고 말로 설명합니다. 각 답에는 정책 대상, 격리 방향, 상대 selector, 포트 조건을 포함해야 합니다.



## 1. 핵심 개념 질문

> NetworkPolicy의 실행 주체와 허용 모델을 정확히 구분하는 질문입니다.

### Q1. NetworkPolicy 오브젝트를 만들었는데 통신이 그대로인 이유는 무엇입니까?

NetworkPolicy는 API 선언일 뿐이며 CNI 네트워크 플러그인이 규칙을 집행합니다. 플러그인이 NetworkPolicy를 지원하지 않으면 오브젝트 생성은 성공해도 데이터 경로가 변하지 않습니다. 따라서 설치된 CNI와 해당 버전의 NetworkPolicy·SCTP·`endPort` 지원 범위를 먼저 확인해야 합니다.

### Q2. Pod는 언제 ingress 또는 egress 격리 상태가 됩니까?

해당 Pod를 `podSelector`로 선택하는 정책이 있고 그 정책의 `policyTypes`에 방향이 포함될 때 그 방향만 격리됩니다. 정책이 없으면 두 방향 모두 비격리이고, ingress 격리가 egress 격리를 자동으로 만들지는 않습니다.

### Q3. 두 정책이 같은 Pod에 적용될 때 더 제한적인 정책이 이깁니까?

아닙니다. 같은 방향에 적용되는 모든 허용 규칙을 합집합으로 계산하므로 정책 순서는 결과에 영향을 주지 않습니다. 표준 API에는 명시적 deny나 우선순위가 없어서 새 정책으로 기존 허용을 취소할 수 없습니다.

### Q4. client에서 db로 연결하려면 어느 쪽 정책이 허용해야 합니까?

client가 egress 격리 상태라면 client의 적용 정책이 목적지와 포트를 허용해야 하고, db가 ingress 격리 상태라면 db의 적용 정책이 출발지와 포트를 허용해야 합니다. 어느 한쪽의 격리 방향에서 허용하지 않으면 새 연결은 성립하지 않습니다.



## 2. YAML 판독 질문

> 목록 항목의 경계가 AND와 OR를 어떻게 바꾸는지 점검합니다.

### Q5. 아래 `from`은 누구를 허용합니까?

```yaml
from:
  - namespaceSelector:
      matchLabels:
        team: payments
    podSelector:
      matchLabels:
        role: client
```

`team=payments`인 namespace 안에서 `role=client`인 Pod만 허용합니다. 두 selector가 하나의 목록 항목에 있으므로 AND입니다.

### Q6. 아래처럼 항목을 둘로 나누면 무엇이 달라집니까?

```yaml
from:
  - namespaceSelector:
      matchLabels:
        team: payments
  - podSelector:
      matchLabels:
        role: client
```

두 항목은 OR입니다. `team=payments`인 모든 namespace의 모든 Pod 또는 정책과 같은 namespace의 `role=client` Pod를 허용하므로 Q5보다 범위가 넓습니다.

### Q7. `podSelector: {}`와 `ingress: []`는 각각 무엇을 뜻합니까?

빈 `podSelector`는 정책 namespace의 모든 Pod를 정책 대상으로 선택합니다. 빈 `ingress` 목록은 허용할 ingress 규칙이 없다는 뜻이므로 `policyTypes: [Ingress]`와 함께 쓰면 모든 대상의 ingress를 거부합니다. 반면 `ingress: [{}]`는 모든 ingress를 허용합니다.

### Q8. namespace 이름을 정책에 직접 지정할 수 있습니까?

전용 이름 필드는 없습니다. `namespaceSelector`에서 모든 namespace에 자동으로 붙는 불변 label `kubernetes.io/metadata.name`을 사용하면 특정 이름을 선택할 수 있습니다. 여러 namespace를 논리 그룹으로 묶을 때는 운영자가 별도 label을 관리합니다.



## 3. 장애 시나리오 질문

> 기본 거부를 적용한 뒤 자주 나타나는 장애와 구현 정의 영역을 구분합니다.

### Q9. default-deny egress 적용 뒤 Service 이름만 해석되지 않는 이유는 무엇입니까?

DNS 질의도 Pod의 egress 트래픽이므로 함께 차단됐기 때문입니다. 클러스터 DNS Pod의 실제 namespace와 label을 확인하고 UDP·TCP 53을 허용해야 합니다. 환경에 따라 DNS 대상이 달라질 수 있으므로 예시 IP를 그대로 복사하면 안 됩니다.

### Q10. 외부 CIDR 허용 정책이 LoadBalancer 경로에서 예상과 다르게 동작할 수 있는 이유는 무엇입니까?

Service, 노드, LoadBalancer가 소스나 목적지 IP를 변환할 수 있고 그 변환이 NetworkPolicy 처리 전인지 후인지 표준이 정하지 않았기 때문입니다. CNI·클라우드·Service 구현 조합에 따라 정책이 원본 클라이언트 IP가 아니라 노드나 LoadBalancer IP를 볼 수 있습니다.

### Q11. 정책 생성 직후 새 Pod가 잠시 통신하지 못하는 현상은 항상 버그입니까?

아닙니다. 격리 규칙이 허용 규칙보다 먼저 분산 반영되면 새 Pod가 잠시 모든 연결을 잃을 수 있습니다. API에는 반영 완료 시각이 없으므로 애플리케이션은 일시적 실패를 견뎌야 하고, 시작 전 필수 의존성은 init container에서 기다릴 수 있습니다.

### Q12. 새 deny 효과가 기존 TCP 연결을 즉시 끊습니까?

보장하지 않습니다. 정책이나 선택 label이 바뀌었을 때 기존 연결에 적용할지는 CNI 구현 정의입니다. 정책 변경은 앞으로의 연결 제어로 보고 기존 세션 종료가 필요하면 별도 운영 절차를 사용해야 합니다.

### Q13. `hostNetwork` Pod도 일반 Pod와 똑같이 selector로 제어됩니까?

표준이 한 가지 동작을 보장하지 않습니다. 일부 CNI는 구분해 정책을 적용하지만, 흔한 구현은 selector에서 `hostNetwork` Pod를 무시하고 노드 IP 트래픽으로 취급합니다. 해당 Pod가 상주하는 노드에서 오가는 트래픽은 차단할 수 없다는 예외도 있습니다.



## 4. 설계 질문

> 표준 API의 경계를 알고 적절한 보완 계층을 선택하는지 확인합니다.

### Q14. NetworkPolicy로 HTTP `/admin` 경로만 막을 수 있습니까?

할 수 없습니다. 표준 NetworkPolicy는 TCP·UDP와 선택적 SCTP의 L3·L4 연결을 다루므로 HTTP 경로나 TLS 신원을 보지 못합니다. L7 요구는 ingress controller, service mesh 또는 다른 L7 proxy 정책으로 해결해야 합니다.

### Q15. `endPort`를 쓸 때 확인할 조건은 무엇입니까?

`endPort`는 `port`와 함께 숫자로 지정하고 시작 포트보다 크거나 같아야 합니다. Kubernetes v1.25부터 stable이지만 CNI가 지원하지 않으면 시작 포트 하나만 적용될 수 있으므로 구현 지원을 확인해야 합니다.

### Q16. namespace 전체에 기본 거부를 적용한 뒤 최소 허용 정책을 설계하는 순서는 무엇입니까?

먼저 실제 통신 의존성을 출발지, 목적지, protocol, port로 목록화합니다. 양방향 default-deny를 배치한 뒤 DNS와 관측·제어 경로를 포함한 필수 egress, 애플리케이션별 ingress를 작은 정책으로 추가합니다. 정책은 합집합이므로 각 정책이 한 책임만 갖게 하면 리뷰와 회수가 쉬워집니다.



## 5. 자가 판정 체크리스트

> 다음 항목을 자료 없이 설명하면 핵심 모델을 습득한 것입니다.

- [ ] 정책 대상과 허용 상대를 구분해 설명할 수 있습니다.
- [ ] ingress와 egress를 독립적으로 판정할 수 있습니다.
- [ ] 같은 항목의 selector는 AND, 다른 항목은 OR임을 YAML로 설명할 수 있습니다.
- [ ] 빈 목록과 빈 객체의 차이를 설명할 수 있습니다.
- [ ] DNS, 주소 변환, 반영 지연, `hostNetwork` 예외를 진단할 수 있습니다.
- [ ] 표준 NetworkPolicy가 제공하지 않는 L7·전역 deny 요구를 구분할 수 있습니다.
