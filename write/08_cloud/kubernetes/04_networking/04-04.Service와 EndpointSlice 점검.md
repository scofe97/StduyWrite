# Service와 EndpointSlice 점검
---

> 정답을 외우기보다 요청 경로의 어느 계약이 끊겼는지 설명할 수 있는지 점검합니다.



## 점검 방법
> 먼저 답을 말하거나 적은 뒤 해설과 비교해야 기억 인출과 오개념 교정이 함께 일어납니다.

각 질문에 Service 주소, EndpointSlice 상태, 실제 backend 중 어떤 계층을 근거로 판단했는지 포함합니다. 단순히 명령만 나열하지 말고 해당 명령의 어떤 필드가 가설을 증명하거나 기각하는지 설명합니다.



## 1. 개념 점검
> Service와 EndpointSlice의 책임 경계를 말로 재구성합니다.

### Q1. Service가 있는데 EndpointSlice가 필요한 이유는 무엇인가요?

Service는 클라이언트에게 안정적인 이름, VIP, port 계약을 제공합니다. 그러나 실제 Pod IP와 상태는 계속 바뀌므로 현재 전달 가능한 backend 목록을 별도 API로 게시해야 합니다. EndpointSlice는 이 목록을 IP family·protocol·port 조합별 작은 객체로 나눠, kube-proxy와 다른 consumer가 변경분을 효율적으로 watch하게 합니다.

### Q2. `port`, `targetPort`, `nodePort`는 각각 누구의 계약인가요?

`port`는 클라이언트가 Service에 접속하는 port이고, `targetPort`는 backend process가 실제로 listen하는 port입니다. `nodePort`는 외부 client가 Node IP로 접근할 때 쓰는 port입니다. `targetPort`를 생략하면 `port`와 같고, NodePort의 기본 allocation 범위는 30000~32767입니다.

### Q3. named `targetPort`가 rollout에 유리한 이유는 무엇인가요?

Service는 `targetPort: app-http`처럼 port 이름을 계약으로 유지하고, 각 Pod 버전은 그 이름을 서로 다른 숫자에 붙일 수 있습니다. 구버전은 8080, 신버전은 9090을 사용해도 EndpointSlice가 port 조합별로 표현하므로 client의 Service port는 바뀌지 않습니다.

### Q4. EndpointSlice의 세 조건은 어떻게 다른가요?

`serving`은 endpoint가 응답할 수 있음을, `terminating`은 삭제 과정에 들어갔음을 나타냅니다. `ready`는 보통 `serving && !terminating`의 축약입니다. 모든 endpoint가 terminating이면 Service proxy가 트래픽 손실을 줄이려고 serving 중인 terminating endpoint를 사용할 수 있으므로 세 조건을 함께 봐야 합니다.

### Q5. Endpoints API를 새 코드에서 사용하면 안 되는 이유는 무엇인가요?

Endpoints와 mirroring은 v1.33부터 deprecated입니다. Endpoints는 dual-stack과 `trafficDistribution` 정보를 표현하지 못하고 backend가 1000개를 넘으면 목록을 truncate합니다. 새 consumer는 Service에 연결된 모든 EndpointSlice를 합치고 중복 endpoint를 제거해야 합니다.

Mirroring은 skip-mirror label, leader-election annotation, 대응 Service 부재, selector가 있는 Service 중 하나에 해당하면 수행되지 않습니다. 수행되더라도 Endpoints subset마다 최대 1000개 주소만 mirror됩니다.



## 2. 설계 선택 점검
> 노출 범위와 실패 의미를 기준으로 Service 형태를 선택합니다.

### Q6. 클러스터 내부 API에는 어떤 타입이 기본인가요?

`ClusterIP`가 기본입니다. 외부 노출이 필요하지 않은데 NodePort나 LoadBalancer를 쓰면 불필요한 공격 표면과 provider 비용이 생깁니다. HTTP 외부 노출은 ClusterIP Service 앞에 Ingress 또는 Gateway를 두는 구성을 먼저 검토합니다.

### Q7. 외부 데이터베이스를 Service 이름으로 노출할 때 어떤 선택지가 있나요?

IP endpoint를 직접 제어하려면 selector 없는 Service와 수동 EndpointSlice를 사용합니다. DNS 이름만 별칭으로 만들려면 ExternalName을 쓸 수 있지만 이는 CNAME일 뿐 proxy가 아닙니다. HTTP Host header나 TLS 인증서가 원본 이름과 맞아야 하는 프로토콜에서는 ExternalName이 실패할 수 있습니다.

### Q8. headless Service는 언제 필요한가요?

StatefulSet의 개별 Pod 발견이나 client-side load balancing처럼 client가 endpoint를 직접 선택해야 할 때 사용합니다. `clusterIP: None`이므로 kube-proxy의 VIP load balancing은 없지만 DNS와 EndpointSlice 기반 discovery는 유지됩니다.

### Q9. `internalTrafficPolicy: Local`과 `trafficDistribution: PreferSameNode`의 차이는 무엇인가요?

`Local`은 같은 Node endpoint만 허용하는 엄격한 정책입니다. 로컬 endpoint가 없으면 다른 Node에 건강한 Pod가 있어도 실패합니다. `PreferSameNode`는 같은 Node를 우선하는 선호이므로 로컬 후보가 없을 때 다른 endpoint로 fallback할 수 있습니다.

### Q10. 고정 ClusterIP는 어느 주소 대역에서 고르는 편이 안전한가요?

Service CIDR의 낮은 band에서 고르는 편이 동적 allocation과 충돌할 가능성이 낮습니다. allocator는 높은 band부터 동적으로 사용하고 소진되면 낮은 band로 내려옵니다. 낮은 band는 별도 예약 공간이 아니므로 API 생성 시 중복 검증은 여전히 필요합니다.



## 3. 장애 시나리오
> 관찰 결과로 원인을 좁히고 다음 확인 대상을 결정합니다.

### Q11. Service는 있지만 EndpointSlice가 하나도 없습니다. 무엇을 확인하나요?

selector가 있는 Service라면 selector와 Pod label이 일치하는지 먼저 확인합니다. selector가 없는 Service라면 자동 생성되지 않는 것이 정상이며 관리자가 EndpointSlice를 만들었는지 확인합니다. Service 이름 label이 틀리면 Slice가 존재해도 해당 Service와 연결되지 않습니다.

```bash
kubectl get svc my-service -o jsonpath='{.spec.selector}'
kubectl get pods --show-labels
kubectl get endpointslice -l kubernetes.io/service-name=my-service -o yaml
```

### Q12. Pod는 Running인데 Service traffic을 받지 못합니다. 어디를 보나요?

Running은 process 생존만 나타내며 traffic 준비를 보장하지 않습니다. EndpointSlice의 `conditions.ready`와 Pod readiness probe 결과를 봅니다. 그다음 Slice port가 실제 container listener와 같은지 확인합니다.

### Q13. `internalTrafficPolicy: Local` Service가 Node A에서만 실패합니다. 가장 유력한 원인은 무엇인가요?

Node A에 Ready endpoint가 없는 경우가 가장 유력합니다. 이 정책에서는 다른 Node의 endpoint가 후보가 아니므로 Service가 Node A에서 endpoint 0개처럼 동작합니다. EndpointSlice의 `nodeName`, `ready`, `terminating`을 함께 확인합니다.

```bash
kubectl get endpointslice \
  -l kubernetes.io/service-name=my-service \
  -o custom-columns='NAME:.metadata.name,ADDRESS:.endpoints[*].addresses,NODE:.endpoints[*].nodeName,READY:.endpoints[*].conditions.ready'
```

### Q14. Pod IP 연결은 성공하지만 ClusterIP 연결만 실패합니다. 무엇이 좁혀졌나요?

selector, endpoint 주소, 애플리케이션 listener는 대체로 정상이라는 증거입니다. Service port와 EndpointSlice port를 다시 확인한 뒤 kube-proxy 또는 CNI의 Service 데이터 플레인 규칙과 로그를 조사합니다. ClusterIP는 일반적으로 `ip addr`에 bind된 주소가 아니므로 인터페이스에 없다는 사실만으로 장애라고 판단하지 않습니다.

### Q15. LoadBalancer Service의 `EXTERNAL-IP`가 pending입니다. Service selector 문제인가요?

대개 selector보다 외부 load balancer controller 또는 cloud provider integration 부재를 뜻합니다. LoadBalancer 생성은 비동기이고 구현체가 `.status.loadBalancer`를 채웁니다. selector와 EndpointSlice가 정상이더라도 provider 구현이 없으면 외부 주소는 생기지 않습니다.

### Q16. selector 없는 Service에 `kubectl port-forward service/...`가 실패하는 이유는 무엇인가요?

API server는 Pod에 매핑되지 않은 endpoint로 proxy하는 것을 허용하지 않습니다. 호출자가 접근 권한이 없는 외부 주소로 API server를 우회 proxy하는 상황을 막기 위한 보안 제약입니다. 일반 Service traffic이 동작하는지와 port-forward 가능 여부는 별개입니다.

### Q17. EndpointSlice consumer에서 같은 요청 대상이 두 번 보입니다. controller 오류인가요?

반드시 오류는 아닙니다. 여러 Slice의 watch event와 cache가 서로 다른 시점에 반영되면 endpoint가 잠시 중복될 수 있습니다. consumer는 해당 Service의 모든 Slice를 집계하고 주소·port 기준으로 deduplication해야 합니다.



## 4. 버전과 폐기 상태 점검
> v1.36 기준으로 지원 상태를 구분해야 오래된 운영 지식을 새 설계에 옮기지 않습니다.

| 기능 | v1.36에서의 판단 | 대안 또는 주의점 |
|---|---|---|
| EndpointSlice | v1.21 stable | Service backend discovery의 기본 API입니다. |
| `serving`, `terminating` 조건 | v1.26 stable | `ready`만 보지 말고 종료 상태를 함께 봅니다. |
| Internal Traffic Policy | v1.26 stable | `Local`은 fallback 없는 제한입니다. |
| Endpoints API·mirroring | v1.33 deprecated | EndpointSlice를 직접 사용합니다. |
| `spec.loadBalancerIP` | v1.24부터 deprecated | provider annotation이나 Gateway API를 검토합니다. |
| `trafficDistribution: PreferClose` | deprecated alias | `PreferSameZone`을 사용합니다. |
| `externalIPs` | v1.36 deprecated | load balancer controller나 Gateway API로 이전합니다. |



## 5. 최종 체크리스트
> 아래 질문에 모두 근거를 붙여 답할 수 있으면 Service 요청 경로를 독립적으로 진단할 수 있습니다.

- Service selector가 어떤 Pod를 선택하는지 label로 증명할 수 있나요?
- `port`, `targetPort`, `nodePort`의 관찰 위치를 구분할 수 있나요?
- 모든 EndpointSlice를 조회하고 endpoint 조건과 Node 분포를 해석할 수 있나요?
- `Local` 정책에서 로컬 endpoint 부재가 실패라는 점을 예측할 수 있나요?
- ClusterIP 정적·동적 band가 충돌을 완전히 방지하지는 않는다고 설명할 수 있나요?
- LoadBalancer의 구현 책임이 Kubernetes API가 아닌 provider/controller에 있음을 구분할 수 있나요?
- deprecated Endpoints, `externalIPs`, `loadBalancerIP`를 새 설계에서 피할 수 있나요?
- v1.36의 완화된 Service 이름 규칙과 63자 제한을 설명할 수 있나요?

현재 연결된 Kubernetes v1.36 클러스터가 없어 위 명령은 실행하지 않았고 출력도 기록하지 않았습니다. 실습할 때는 본문의 재현 절차에 따라 실제 EndpointSlice의 `hostname`, 조건, Node 분포를 관찰합니다.
