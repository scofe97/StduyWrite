# 외부 진입과 트래픽 분할 — Ingress·가중치·컨테이너 네트워크

---

> 트래픽이 목적지에 안 닿는 문제는 계층마다 다른 얼굴을 합니다. Ingress 의 경로 규칙, Service 의 라벨, 컨테이너 네트워크의 분리가 각각 다른 지점에서 길을 끊습니다.

앞 문서가 클러스터 안에서 서로를 찾는 문제였다면, 이 문서는 밖에서 들어오는 길과 안에서 갈라지는 길입니다.

세 번째 사례는 쿠버네티스가 아니라 Docker입니다. 컨테이너 네트워크 분리라는 같은 개념이 오케스트레이터 없이 드러나는 형태라, 앞의 두 사례를 이해하는 바닥으로 함께 둡니다.



## 길이 끊기는 지점은 계층마다 다릅니다

> 같은 "연결 안 됨"이라도 Ingress 에서 끊기면 404, Service 에서 끊기면 연결 거부, 네트워크가 분리돼 있으면 이름 해석 실패로 나타납니다.

트래픽 문제를 만나면 어느 계층부터 볼지 정해야 합니다. 계층이 여럿이라 아무 데나 찌르면 시간이 오래 걸립니다.

응답의 형태가 계층을 알려 줍니다. HTTP 404가 왔다면 어딘가가 요청을 받아 처리했다는 뜻이므로 Ingress 컨트롤러까지는 도달한 것입니다. 연결 자체가 거부되면 그보다 앞에서 끊긴 것이고, 이름을 못 찾으면 더 앞입니다.

이 순서를 따라가면 확인할 곳이 하나씩 줄어듭니다. 세 사례가 각각 다른 지점에서 끊긴 예입니다.

| 응답 | 끊긴 지점 | 확인할 것 |
|------|-----------|-----------|
| HTTP 404 | Ingress 의 경로 규칙 | `path` 와 `pathType` (사례 1) |
| 특정 버전에만 트래픽이 감 | Service 의 라벨 매칭 | `kubectl get endpoints` (사례 2) |
| 이름 해석 실패, 경로 없음 | 네트워크 자체가 분리됨 | 컨테이너가 붙은 네트워크 (사례 3) |



## 사례 1 — 한 경로는 되는데 다른 경로만 404 입니다

> `pathType: Exact` 는 그 경로와 정확히 같은 요청만 받습니다. 하위 경로는 매칭되지 않습니다.

Ingress로 API를 노출하는데 `/api/v1/users`는 되고 `/api/v2/users`는 404가 납니다. v2 백엔드는 정상입니다.

```yaml
      paths:
      - path: /api/v1(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: api-v1
            port:
              number: 8080
      - path: /api/v2
        pathType: Exact
        backend:
          service:
            name: api-v2
            port:
              number: 8080
```

```bash
curl -H "Host: api.example.com" http://ingress-ip/api/v1/users
{"status": "ok", "version": "v1", "data": [...]}
```

```bash
curl -H "Host: api.example.com" http://ingress-ip/api/v2/users
<html><body><h1>404 Not Found</h1></body></html>
```

```bash
curl http://api-v2.default.svc:8080/users
{"status": "ok", "version": "v2", "data": [...]}
```

마지막 확인이 범위를 좁혀 줍니다. ClusterIP로 직접 요청하면 v2가 정상 응답하므로 Service와 Pod는 문제가 없습니다. 남은 곳은 Ingress입니다.

두 경로 규칙을 나란히 놓으면 `pathType`이 다릅니다. v1은 `ImplementationSpecific`에 정규식을 써서 하위 경로까지 잡고, v2는 `Exact`라 정확히 `/api/v2`인 요청만 받습니다.

`/api/v2/users`는 `/api/v2`와 같은 문자열이 아닙니다. 그래서 어떤 규칙에도 걸리지 않고 Ingress 컨트롤러의 기본 백엔드가 404를 돌려줍니다.

`rewrite-target: /$2` 애노테이션이 함께 걸려 있다는 점도 봐야 합니다. 이 값은 정규식의 두 번째 캡처 그룹을 참조하는데, v2 규칙에는 캡처 그룹이 없어 재작성도 의도대로 동작하지 않습니다.

### 조치

```yaml
      - path: /api/v2(/|$)(.*)
        pathType: ImplementationSpecific
        backend:
          service:
            name: api-v2
            port:
              number: 8080
```

```bash
kubectl edit ingress api-gateway
curl -H "Host: api.example.com" http://ingress-ip/api/v2/users
```

`pathType` 세 가지의 차이를 알아 두면 이 계열 문제가 줄어듭니다. `Exact`는 완전 일치, `Prefix`는 경로 조각 단위의 접두사 일치, `ImplementationSpecific`은 컨트롤러가 정하는 방식이고 nginx 컨트롤러에서는 정규식을 씁니다.

새 버전 경로를 추가할 때는 잘 동작하는 기존 규칙을 통째로 복사한 뒤 버전 숫자만 고치는 편이 안전합니다. `rewrite-target`처럼 규칙과 짝을 이루는 애노테이션이 있으면 특히 그렇습니다.



## 사례 2 — 카나리 배포인데 새 버전으로 트래픽이 안 갑니다

> 쿠버네티스 기본 카나리는 같은 Service 아래 두 버전을 두는 방식입니다. 라벨이 갈리면 트래픽도 갈리지 않고 아예 안 갑니다.

기존 버전 옆에 새 버전을 배포해 트래픽을 나누려 했는데 전부 기존 버전으로만 갑니다.

```bash
NAME                      READY   STATUS    RESTARTS   AGE   LABELS
app-v1-7d8f9b6c5-a1b2c   1/1     Running   0          1h    app=my-app,version=v1
app-v1-7d8f9b6c5-d3e4f   1/1     Running   0          1h    app=my-app,version=v1
app-v2-5c6d7e8f9-g5h6i   1/1     Running   0          5m    app=my-app-v2,version=v2
```

```yaml
spec:
  selector:
    app: my-app
  ports:
  - port: 80
    targetPort: 80
```

```bash
NAME          ENDPOINTS                         AGE
my-app-svc    10.244.1.10:80,10.244.2.11:80     1h
```

```yaml
  template:
    metadata:
      labels:
        app: my-app-v2
        version: v2
```

엔드포인트 목록에 IP가 두 개뿐입니다. Pod는 셋인데 둘만 잡혔으므로 v2 Pod가 빠졌다는 뜻이고, 앞 문서 사례 1과 같은 라벨 매칭 문제입니다.

Service 셀렉터는 `app: my-app`인데 v2 Pod의 라벨은 `app: my-app-v2`입니다. 버전을 구분하려고 `app` 라벨 자체를 바꾼 것이 원인입니다.

쿠버네티스 기본 카나리의 구조를 알면 왜 이것이 잘못인지가 분명해집니다. 두 버전이 같은 Service에 함께 들어가고, 트래픽 비율은 각 버전의 Pod 개수로 정해집니다. 버전 구분은 `app`이 아니라 `version` 같은 별도 라벨이 맡습니다.

즉 `app` 라벨은 두 버전이 공유해야 하는 값입니다. 그것을 바꾸면 카나리가 아니라 그냥 아무도 안 부르는 별도 워크로드가 됩니다.

### 조치

```yaml
  selector:
    matchLabels:
      app: my-app
      version: v2
  template:
    metadata:
      labels:
        app: my-app        # Service 셀렉터와 공유하는 값
        version: v2        # 버전 구분은 이 라벨이 맡는다
```

```bash
kubectl apply -f app-v2-deployment.yaml
kubectl get endpoints my-app-svc -n canary

# 비율을 눈으로 확인
for i in $(seq 1 30); do
  kubectl exec deploy/testpod -n canary -- curl -s my-app-svc | grep -o 'v[12]'
done | sort | uniq -c
```

이 방식의 한계도 함께 알아 둡니다. 비율이 Pod 개수로만 정해지므로 v1 두 개와 v2 한 개면 대략 2 대 1이고, 5%처럼 세밀한 비율은 만들 수 없습니다.

정밀한 분할이 필요하면 Gateway API의 가중치나 서비스 메시로 올라가야 합니다. 그 경우 트래픽 분할이 Service 라벨이 아니라 라우팅 규칙의 몫이 됩니다.



## 사례 3 — 컨테이너끼리 통신이 안 됩니다

> 서로 다른 브리지 네트워크에 붙은 컨테이너는 기본적으로 통신하지 않습니다. 같은 호스트에 있다는 사실은 상관이 없습니다.

같은 호스트에서 도는 두 Docker 컨테이너 사이에 HTTP 요청이 실패합니다.

```bash
CONTAINER ID   IMAGE          PORTS                  NAMES       NETWORK
a1b2c3d4e5f6   web:latest     0.0.0.0:80->80/tcp     web         bridge
f6e5d4c3b2a1   api:latest     0.0.0.0:8080->8080/tcp api         my-app-network
```

```bash
curl http://api:8080/health
curl: (6) Could not resolve host: api

curl http://172.18.0.2:8080/health
curl: (7) Failed to connect to 172.18.0.2 port 8080: No route to host
```

```json
{
    "Name": "bridge",
    "Containers": {
        "a1b2c3d4e5f6": { "Name": "web", "IPv4Address": "172.17.0.2/16" }
    }
}
```

```json
{
    "Name": "my-app-network",
    "Driver": "bridge",
    "Containers": {
        "f6e5d4c3b2a1": { "Name": "api", "IPv4Address": "172.18.0.2/16" }
    }
}
```

두 실패가 서로 다른 이야기를 합니다. 이름으로 부르면 해석이 안 되고, IP로 부르면 경로가 없습니다. 두 증상이 함께 나오면 네트워크 자체가 분리된 것입니다.

`docker ps`의 네트워크 열이 이를 확인해 줍니다. `web`은 기본 `bridge`에, `api`는 사용자 정의 `my-app-network`에 붙어 있고 대역도 각각 172.17과 172.18로 다릅니다.

이름 해석이 안 되는 데는 별도의 이유가 있습니다. Docker의 내장 DNS는 사용자 정의 네트워크에서만 컨테이너 이름을 풀어 주고, 기본 `bridge` 네트워크에서는 동작하지 않습니다. `web`이 기본 브리지에 있으니 이름으로는 아무도 못 찾습니다.

이 사례를 쿠버네티스 문서에 둔 이유가 있습니다. 쿠버네티스는 모든 Pod가 서로 직접 통신할 수 있다는 전제 위에 서 있어서, 여기서 겪는 분리를 기본적으로 없애 줍니다. 그 전제가 없을 때 무엇을 직접 해야 하는지를 보여 주는 대비입니다.

### 조치

```bash
# 컨테이너를 같은 네트워크에 붙인다
docker network connect my-app-network web
docker exec web curl http://api:8080/health
```

```bash
# 더 깔끔한 방법 — 처음부터 같은 네트워크로 띄운다
docker run -d --name web --network my-app-network -p 80:80 web:latest
```

Compose를 쓰면 같은 파일에 정의된 서비스들이 자동으로 한 네트워크를 공유하므로 이 문제가 생기지 않습니다. 이름으로 서로를 부르는 것도 그 네트워크의 내장 DNS가 처리합니다.

네트워크를 나누는 것 자체는 나쁜 선택이 아닙니다. 서로 통신할 필요가 없는 컨테이너를 갈라 두면 그만큼 노출이 줄어들고, 필요한 것만 연결하는 방식이 보안상 낫습니다.



## 세 사례를 관통하는 것

> 세 사례 모두 "닿을 수 있는 길이 있는가"를 묻습니다. 길을 정하는 것이 Ingress 규칙인지 Service 라벨인지 네트워크 소속인지만 다릅니다.

증상의 형태가 계층을 알려 준다는 점이 실전에서 가장 쓸모 있습니다. 404는 무언가가 요청을 받았다는 뜻입니다. 연결 거부는 보낼 곳이 없다는 뜻이고 이름 해석 실패는 그보다 앞에서 끊겼다는 뜻입니다. 이 셋을 구분하면 처음 볼 곳이 정해집니다.

라벨이 두 사례에서 다시 등장합니다. 앞 문서의 대소문자 불일치와 여기 카나리의 `app` 라벨 변경은 같은 종류의 실수입니다. 라벨은 사람이 읽으라고 있는 것이 아니라 컨트롤러가 매칭하라고 있는 값이고, 그래서 의미가 아니라 문자열이 기준입니다.

마지막으로 Docker 사례가 남기는 대비를 기억해 둡니다. 쿠버네티스에서 Pod끼리 그냥 통신되는 것은 당연한 일이 아니라 CNI가 만들어 준 결과입니다. 그 층이 무엇을 해 주는지 알면 NetworkPolicy로 그것을 다시 제한할 때 무슨 일이 벌어지는지도 이해됩니다.
