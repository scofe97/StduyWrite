# 볼륨 — PVC 확장·StorageClass·권한

---

> 스토리지 문제는 세 층에서 갈립니다. StorageClass 가 있는가, 그 클래스가 원하는 동작을 지원하는가, 그리고 마운트된 파일을 컨테이너가 쓸 수 있는가.

컨테이너에 디스크를 붙이는 일은 선언 한 줄로 끝나 보이지만, 그 뒤에서 프로비저너와 파일 권한이 함께 움직입니다.

세 사례가 그 층을 아래에서 위로 훑습니다. 클래스가 없어 볼륨이 안 만들어지는 경우, 만들어졌는데 확장이 안 되는 경우, 붙었는데 쓸 수 없는 경우입니다.



## PVC 는 요청서이고 StorageClass 가 그것을 해석합니다

> PVC 는 "이만큼의 디스크가 필요하다"는 선언일 뿐입니다. 실제로 만들 수 있는지는 StorageClass 와 그 프로비저너가 정합니다.

PVC를 만들었는데 `Pending`이면 클러스터에 디스크가 없다고 생각하기 쉽습니다. 그런데 실제 원인은 대개 요청을 처리할 주체가 없는 것입니다.

PVC는 요청서이고 StorageClass는 그 요청을 어떤 방식으로 처리할지 적어 둔 정책입니다. 그 안의 `provisioner`가 실제로 볼륨을 만드는 구성 요소이고, `allowVolumeExpansion` 같은 필드가 나중에 무엇을 할 수 있는지를 정합니다.

그래서 볼륨 문제는 PVC만 봐서는 안 풀립니다. 세 사례 모두 답이 PVC 바깥에 있습니다.

| 증상 | 답이 있는 곳 | 사례 |
|------|--------------|------|
| PVC 가 `Pending` | 지정한 StorageClass 의 존재 여부 | 사례 1 |
| 확장이 거절됨 | StorageClass 의 프로비저너와 확장 지원 | 사례 2 |
| 마운트는 됐는데 쓰기 실패 | 파일 소유권과 `securityContext` | 사례 3 |



## 사례 1 — PVC 가 Pending 에서 안 넘어갑니다

> `describe pvc` 의 이벤트가 이유를 한 줄로 적어 줍니다. 대개 존재하지 않는 StorageClass 이름입니다.

PVC를 만들었는데 5분째 `Pending`이고 그것을 쓰는 Pod도 시작되지 못합니다.

```bash
NAME         STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
expand-pvc   Pending                                      fast-sc        5m
```

```bash
Events:
  Warning  ProvisioningFailed  10s (x15 over 5m)  persistentvolume-controller  storageclass.storage.k8s.io "fast-sc" not found
```

```bash
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  30d
```

```yaml
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: fast-sc
  resources:
    requests:
      storage: 1Gi
```

이벤트가 그대로 답입니다. PVC가 `fast-sc`를 요청했는데 그런 이름의 StorageClass가 없습니다.

목록을 보면 클러스터에는 `standard` 하나만 있고 그것이 기본값으로 표시돼 있습니다. 여기서 알아 둘 점은 `storageClassName`을 명시하면 기본값이 적용되지 않는다는 것입니다. 이름을 적는 순간 그 이름이 반드시 있어야 합니다.

`Pending`이 영구적이라는 점도 중요합니다. 컨트롤러는 15번을 재시도하고도 같은 결과를 냈고, 클래스가 생기기 전까지는 계속 그럴 것입니다. 시간이 해결해 주지 않습니다.

`VOLUMEBINDINGMODE`가 `WaitForFirstConsumer`인 것도 함께 봐 둡니다. 이 모드에서는 Pod가 스케줄될 때까지 볼륨을 만들지 않으므로, 정상적인 상황에서도 PVC가 잠시 `Pending`으로 보입니다. 이벤트를 확인하지 않으면 정상 대기와 영구 실패를 구분할 수 없습니다.

### 조치

```bash
# 이유는 이벤트에 있다
kubectl describe pvc expand-pvc -n storage

# 클러스터에 어떤 클래스가 있는지 확인
kubectl get storageclass
```

```bash
# 필요한 클래스를 만들되 확장 지원을 함께 켠다
kubectl apply -f - <<'EOF'
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: fast-sc
provisioner: rancher.io/local-path
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
allowVolumeExpansion: true
EOF

kubectl get pvc -n storage
```

클래스를 새로 만들지 않고 PVC 쪽에서 이름을 고치는 선택지도 있습니다. 어느 쪽이 맞는지는 그 이름이 팀의 표준인지 오타인지에 달렸습니다.

`allowVolumeExpansion: true`를 처음부터 켜 두면 다음 사례를 피할 수 있습니다. 나중에 이 필드를 바꿔도 이미 만들어진 볼륨에는 소급되지 않는 경우가 있어, 표준 클래스에 미리 넣어 두는 편이 낫습니다.



## 사례 2 — 용량을 늘리려는데 거절당합니다

> 확장은 동적으로 만들어진 볼륨에만 허용됩니다. 정적 PV 를 전제로 한 클래스에서는 필드를 켜도 되지 않습니다.

디스크 사용량이 늘어 PVC를 1Gi에서 5Gi로 확장하려는데 수정이 거부됩니다.

```bash
error: persistentvolumeclaims "data-pvc" could not be patched: persistentvolumeclaims "data-pvc" is forbidden: only dynamically provisioned pvc can be resized and the StorageClass that provisions the pvc must support resize
```

```bash
NAME       STATUS   VOLUME     CAPACITY   ACCESS MODES   STORAGECLASS    AGE
data-pvc   Bound    pv-abc12   1Gi        RWO            expandable-sc   1d
```

```yaml
provisioner: kubernetes.io/no-provisioner
reclaimPolicy: Delete
volumeBindingMode: WaitForFirstConsumer
```

에러 문장이 조건 두 개를 함께 말합니다. 동적으로 프로비저닝된 PVC여야 하고, 그 StorageClass가 리사이즈를 지원해야 합니다.

StorageClass를 보면 `provisioner: kubernetes.io/no-provisioner`입니다. 이름 그대로 프로비저너가 없다는 뜻이라, 이 클래스는 미리 만들어 둔 정적 PV에 PVC를 이어 주는 용도입니다. 쿠버네티스가 볼륨을 만든 적이 없으니 늘려 줄 수도 없습니다.

`allowVolumeExpansion` 필드도 보이지 않습니다. 두 번째 조건도 만족하지 않는 셈이지만, 이 필드를 켠다고 해결되지는 않습니다. 프로비저너가 없다는 첫 번째 조건이 그대로 남습니다.

클래스 이름이 `expandable-sc`라는 점이 오해를 부릅니다. 이름은 의도를 담을 뿐 동작을 정하지 않습니다. 실제 동작은 `provisioner`와 필드가 정합니다.

### 조치

```bash
# 현재 클래스가 무엇을 지원하는지 확인
kubectl get storageclass expandable-sc -o yaml
```

```bash
# 확장이 되는 클래스로 새 PVC 를 만들고 데이터를 옮긴다
kubectl apply -f new-data-pvc.yaml

# 임시 Pod 를 띄워 기존 PVC 에서 새 PVC 로 복사한 뒤 워크로드를 옮긴다
kubectl apply -f app-with-new-pvc.yaml
```

정적 볼륨 구성에서는 확장 대신 마이그레이션이 답입니다. 새 PVC를 만들고 데이터를 복사한 뒤 워크로드가 그것을 보게 바꾸는 절차이고, 서비스 중단 시간을 계획에 넣어야 합니다.

이 사례가 알려 주는 것은 스토리지 선택이 나중에 되돌리기 어렵다는 점입니다. 확장 가능한 CSI 기반 클래스를 처음부터 표준으로 정해 두면 이 마이그레이션 자체가 생기지 않습니다.



## 사례 3 — 볼륨은 붙었는데 쓸 수가 없습니다

> `fsGroup` 은 마운트 시 그룹 소유권을 바꿔 주지만 이미 있던 파일의 사용자 소유권은 그대로입니다. 이 차이가 마이그레이션에서 드러납니다.

보안 정책에 따라 PostgreSQL을 non-root로 바꿨더니 Pod가 `CrashLoopBackOff`에 빠졌습니다. PVC는 정상 바인딩돼 있습니다.

```bash
2025-01-20 10:30:01.123 UTC [1] FATAL:  data directory "/var/lib/postgresql/data" has wrong ownership
2025-01-20 10:30:01.123 UTC [1] HINT:  The server must be started by the user that owns the data directory.
chmod: changing permissions of '/var/lib/postgresql/data': Operation not permitted
```

```yaml
      securityContext:
        runAsUser: 999
        runAsGroup: 999
      containers:
      - name: postgres
        image: postgres:16
        volumeMounts:
        - name: pgdata
          mountPath: /var/lib/postgresql/data
```

```bash
total 12
drwxr-xr-x 3 root root 4096 Jan 15 08:00 .
drwxr-xr-x 1 root root 4096 Jan 20 10:30 ..
drwx------ 19 root root 4096 Jan 15 08:00 data
```

로그의 두 줄이 상황을 다 설명합니다. 데이터 디렉터리의 소유자가 틀렸고, 컨테이너가 그것을 고치려다 권한이 없어 실패했습니다.

파일시스템을 보면 `data` 디렉터리가 `root:root` 소유이고 권한은 `drwx------`입니다. 소유자만 접근할 수 있는데 컨테이너는 UID 999로 돌고 있습니다.

이 상태가 만들어진 경위도 읽힙니다. 예전에 root로 돌 때 만들어진 파일이 PVC에 그대로 남아 있고, 실행 사용자만 바뀌었습니다. 볼륨은 워크로드보다 오래 살기 때문에 이런 어긋남이 생깁니다.

`securityContext`에 `fsGroup`이 없다는 점이 결정적입니다. 이 필드가 있으면 kubelet이 마운트할 때 볼륨의 그룹 소유권을 그 값으로 바꿔 주는데, 지금은 그 처리가 일어나지 않습니다.

### 조치

```yaml
      securityContext:
        runAsUser: 999
        runAsGroup: 999
        fsGroup: 999          # 마운트 시 그룹 소유권을 바꾼다
      initContainers:
      - name: fix-permissions  # 기존 파일의 사용자 소유권은 한 번 직접 고친다
        image: busybox
        command: ["sh", "-c", "chown -R 999:999 /var/lib/postgresql/data"]
        securityContext:
          runAsUser: 0
        volumeMounts:
        - name: pgdata
          mountPath: /var/lib/postgresql/data
```

```bash
kubectl rollout status statefulset postgres
kubectl logs postgres-0
```

`fsGroup`과 초기화 컨테이너의 역할이 다릅니다. 앞의 것은 앞으로 마운트될 때마다 그룹 소유권을 맞춰 주고, 뒤의 것은 이미 남아 있는 파일의 사용자 소유권을 한 번 정리합니다. 마이그레이션에는 둘 다 필요합니다.

초기화 컨테이너를 root로 돌린다는 점이 걸린다면, 이것이 일회성이라는 점을 함께 봅니다. 소유권을 한 번 정리한 뒤에는 `fsGroup`만으로 유지되므로 다음 배포에서 빼도 됩니다.

새 볼륨에서 시작한다면 이 문제가 없습니다. 처음부터 non-root로 만들면 파일 소유권이 처음부터 맞기 때문에, 문제가 되는 것은 언제나 기존 데이터가 있는 볼륨입니다.



## 세 사례를 관통하는 것

> 볼륨은 워크로드보다 오래 삽니다. 그래서 스토리지 문제는 대개 지금 만든 매니페스트가 아니라 과거에 만들어진 상태와 부딪히는 형태로 나타납니다.

사례 2와 사례 3이 그 성질을 잘 보여 줍니다. 이미 정적으로 만들어진 볼륨은 확장할 수 없고, 이미 root로 쓰인 파일은 사용자를 바꿔도 그대로입니다. 매니페스트를 고치는 것만으로는 과거가 정리되지 않습니다.

세 사례 모두 PVC 바깥에서 답이 나왔다는 점도 반복됩니다. StorageClass 목록, 프로비저너 종류, 파일 소유권이 각각의 답이었습니다. `kubectl get pvc`만 반복해서 쳐서는 아무것도 안 보입니다.

마지막으로 스토리지 선택이 나중에 바꾸기 어렵다는 점을 기억해 둡니다. 확장 가능한 클래스를 표준으로 정하는 것과 처음부터 non-root로 볼륨을 만드는 것 두 가지가, 이 문서의 사례 대부분을 미리 없앱니다.
