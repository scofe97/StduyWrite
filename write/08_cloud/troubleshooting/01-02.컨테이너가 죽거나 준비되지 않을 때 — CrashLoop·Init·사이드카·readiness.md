# 컨테이너가 죽거나 준비되지 않을 때 — CrashLoop·Init·사이드카·readiness

---

> Pod 기동은 Init 컨테이너, 메인 컨테이너, 사이드카, readiness 순으로 관문을 통과합니다. 어느 관문에서 멈췄는지는 `STATUS`와 `READY` 두 열이 알려 줍니다.

앞 문서가 이미지를 못 가져오는 단계였다면, 이 문서는 이미지를 받은 뒤 컨테이너가 실제로 돌기까지의 단계입니다.

네 사례를 기동 순서대로 놓았습니다. Init 컨테이너가 안 끝나는 경우, 메인 컨테이너가 시작하자마자 죽는 경우, 사이드카만 죽는 경우, 다 떴는데 트래픽을 못 받는 경우입니다.



## STATUS 와 READY 두 열이 관문을 지목합니다

> `Init:0/1`·`CrashLoopBackOff`·`1/2`·`0/1 Running`은 각각 다른 관문에서 멈춘 모습입니다. 두 열만 읽어도 볼 곳이 절반으로 줄어듭니다.

`kubectl get pods` 출력은 좁아 보이지만 기동 단계를 꽤 정확히 담고 있습니다. 그런데 `STATUS` 하나만 보고 로그를 열면 어느 관문에서 멈췄는지를 알 수 없습니다.

`READY` 열의 분수가 특히 유용합니다. 분모는 Pod 안의 컨테이너 수이고 분자는 그중 준비된 개수라, `1/2`는 두 컨테이너 중 하나만 정상이라는 뜻입니다. 이 한 글자가 멀티 컨테이너 Pod의 조사 범위를 반으로 줄입니다.

Init 단계는 별도로 표시됩니다. `Init:0/1`은 Init 컨테이너 하나 중 0개가 끝났다는 뜻이고, 이 상태에서는 메인 컨테이너가 아직 시작조차 하지 않았습니다.

| 보이는 모습 | 멈춘 관문 | 먼저 볼 곳 | 사례 |
|-------------|-----------|------------|------|
| `Init:0/1` | Init 컨테이너 | `kubectl logs <pod> -c <init 이름>` | 사례 1 |
| `0/1 CrashLoopBackOff` | 메인 컨테이너 기동 | 컨테이너 로그의 마지막 줄 | 사례 2 |
| `1/2 CrashLoopBackOff` | 사이드카 | 죽은 컨테이너만 지정해 로그 확인 | 사례 3 |
| `0/1 Running` | readiness probe | `describe` 의 `Unhealthy` 이벤트 | 사례 4 |



## 사례 1 — Init 컨테이너가 끝나지 않습니다

> `Init:0/1`은 메인 컨테이너가 아직 시작도 안 했다는 뜻입니다. 애플리케이션 로그를 열어도 아무것도 없습니다.

신규 서비스를 배포했는데 Pod가 `Init:0/1`에서 멈춰 8분째 그대로입니다.

```bash
NAME                            READY   STATUS     RESTARTS   AGE
order-service-5c8d7f9b6-tn4k2  0/1     Init:0/1   0          8m
order-service-5c8d7f9b6-gx7m3  0/1     Init:0/1   0          8m
```

```yaml
Init Containers:
  wait-for-db:
    Image:   busybox:1.36
    Command:
      - sh
      - -c
      - until nslookup postgres-primary.database.svc.cluster.local; do echo "Waiting for DB..."; sleep 2; done
    State:       Running
      Ready:     False
Containers:
  order-api:
    State:   Waiting
      Reason: PodInitializing
```

```bash
nslookup: can't resolve 'postgres-primary.database.svc.cluster.local'
Waiting for DB...
nslookup: can't resolve 'postgres-primary.database.svc.cluster.local'
Waiting for DB...
```

```bash
NAME              TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)    AGE
postgres-main     ClusterIP   10.96.45.120   <none>        5432/TCP   30d
```

메인 컨테이너의 상태가 `PodInitializing`이라는 점을 먼저 확인합니다. Init 컨테이너가 성공으로 끝나야 메인이 시작되는 구조라, 지금은 애플리케이션 코드가 한 줄도 실행되지 않은 상태입니다.

Init 컨테이너의 명령을 읽으면 의존 서비스의 DNS가 해석될 때까지 기다리는 패턴입니다. 로그에는 그 해석이 계속 실패하고 있습니다.

마지막 자료가 원인을 확정합니다. 기다리는 이름은 `postgres-primary`인데 실제 Service 이름은 `postgres-main`입니다. 존재하지 않는 이름을 기다리므로 이 루프는 영원히 끝나지 않습니다.

`until` 루프에 종료 조건이 없다는 점도 함께 봅니다. 의존 서비스가 진짜로 늦게 뜨는 경우와 이름이 틀린 경우를 이 구조로는 구분할 수 없습니다.

### 조치

```bash
# Init 컨테이너의 로그는 이름을 지정해야 나온다
kubectl logs order-service-5c8d7f9b6-tn4k2 -c wait-for-db

# 기다리는 이름이 실재하는지 확인
kubectl get svc -n database

# 매니페스트의 Service 이름을 고쳐 다시 적용
kubectl edit deployment order-service
kubectl rollout status deployment order-service
```

```bash
# 무한 대기 대신 시간 상한을 둔다
timeout 120 sh -c 'until nslookup postgres-main.database.svc.cluster.local; do sleep 2; done'
```

`timeout`을 씌우면 Init 컨테이너가 실패로 끝나고 Pod가 `Init:Error`가 됩니다. 영원히 `Running`인 것보다 낫습니다. 실패한 상태는 알림에 걸리지만 조용히 기다리는 상태는 아무도 모릅니다.

의존 서비스 이름을 명령에 직접 쓰지 않고 ConfigMap이나 환경 변수로 빼면 이 오타가 매니페스트 리뷰에서 잡힙니다.



## 사례 2 — 시작하자마자 죽고 다시 뜨기를 반복합니다

> `CrashLoopBackOff`는 재시작 루프의 이름입니다. 원인은 죽기 직전 로그의 마지막 몇 줄에 거의 항상 있습니다.

새 버전 API 서버를 배포했더니 Pod가 `CrashLoopBackOff`에 빠졌습니다. 이전 버전은 여전히 정상입니다.

```bash
NAME                          READY   STATUS             RESTARTS      AGE
api-server-7d4f8b6c9-x2k8p   0/1     CrashLoopBackOff   5 (30s ago)   3m
api-server-7d4f8b6c9-m9n3q   0/1     CrashLoopBackOff   5 (28s ago)   3m
api-server-6b5c9d8f7-j4h2l   1/1     Running             0             2d
```

```yaml
Containers:
  api:
    Image:       registry.example.com/api-server:v2.1.0
    Environment:
      DB_HOST:       <set to the key 'host' in secret 'db-credentials'>
      DB_PORT:       <set to the key 'port' in secret 'db-credentials'>
      DB_NAME:       <set to the key 'name' of config map 'api-config'>
      REDIS_URL:     <set to the key 'redis_url' of config map 'api-config'>
      NEW_FEATURE:   <set to the key 'new_feature_flag' of config map 'api-config'>  OPTIONAL: optional
    State:          Waiting
      Reason:       CrashLoopBackOff
    Last State:     Terminated
      Reason:       Error
      Exit Code:    1
      Started:      Mon, 15 Jan 2024 10:25:00 +0000
      Finished:     Mon, 15 Jan 2024 10:25:02 +0000
```

```bash
2024-01-15T10:25:00Z [INFO]  Starting API server v2.1.0...
2024-01-15T10:25:01Z [INFO]  Database connection established.
2024-01-15T10:25:02Z [INFO]  Redis connection established.
2024-01-15T10:25:02Z [ERROR] Failed to load configuration: required environment variable "CACHE_TTL" is not set
2024-01-15T10:25:02Z [FATAL] Application startup failed. Exiting.
```

`Last State`의 `Started`와 `Finished` 시각 차이가 2초입니다. 이미지도 받았고 컨테이너도 만들어졌으니 실패는 애플리케이션 안에서 났습니다. 종료 코드 1은 애플리케이션이 스스로 비정상 종료했다는 뜻입니다.

로그의 마지막 두 줄이 원인을 그대로 적어 줍니다. DB와 Redis 연결까지는 성공했고, 설정을 읽는 단계에서 `CACHE_TTL` 환경 변수가 없어 종료했습니다.

`describe` 출력의 환경 변수 목록을 보면 다섯 개가 주입되는데 그중 `CACHE_TTL`이 없습니다. 새 버전에서 필수가 된 값을 Pod 스펙에 반영하지 않은 것입니다.

여기서 확정할 수 없는 것도 분명히 해 둡니다. ConfigMap에 `cache_ttl` 키가 이미 있는지는 주어진 자료에 없으므로 별도로 확인해야 합니다.

### 조치

```bash
# 재시작 루프에서는 현재 로그가 비어 있을 수 있다. 직전 컨테이너의 로그를 본다
kubectl logs api-server-7d4f8b6c9-x2k8p --previous

# 값의 출처가 될 ConfigMap 확인
kubectl get configmap api-config -o yaml

# 없으면 키를 넣고, Pod 스펙에 환경 변수 매핑을 추가한 뒤 재배포
kubectl patch configmap api-config --type merge -p '{"data":{"cache_ttl":"300"}}'
kubectl edit deployment api-server
kubectl rollout status deployment api-server
```

`--previous`가 중요합니다. `CrashLoopBackOff` 상태에서는 컨테이너가 대기 중이라 현재 로그가 비어 있거나 아직 아무것도 안 찍힌 경우가 많고, 원인은 방금 죽은 인스턴스의 로그에 있습니다.

새 버전이 요구하는 설정이 늘었다면 매니페스트와 ConfigMap을 같은 릴리스로 묶어야 합니다. Helm이나 Kustomize를 쓰면 이 둘이 한 단위로 배포돼 누락이 줄어듭니다.



## 사례 3 — 컨테이너 둘 중 하나만 죽습니다

> `READY 1/2`는 한 컨테이너만 문제라는 뜻입니다. 사이드카가 마운트한 볼륨 이름과 경로가 메인과 맞는지 봅니다.

로그 수집 사이드카를 추가한 뒤 Pod가 반복해서 재시작합니다. 메인 애플리케이션은 정상입니다.

```bash
NAME                          READY   STATUS             RESTARTS      AGE
web-app-6f9d8c4b7-r2p5k      1/2     CrashLoopBackOff   4 (18s ago)   3m
```

```yaml
Containers:
  app:
    Image:       nginx:1.25
    State:       Running
    Ready:       True
    Mounts:
      /var/log/nginx from app-logs (rw)
  log-collector:
    Image:       fluent/fluentd:v1.16
    State:       Waiting
      Reason:    CrashLoopBackOff
    Mounts:
      /var/log/app from nginx-logs (ro)
Volumes:
  app-logs:
    Type: EmptyDir
```

```bash
2025-01-20 09:15:01 +0000 [info]: parsing config file is succeeded path="/fluentd/etc/fluent.conf"
2025-01-20 09:15:01 +0000 [error]: config error file="/fluentd/etc/fluent.conf" error_class=Errno::ENOENT error="No such file or directory @ rb_sysopen - /var/log/app/access.log"
2025-01-20 09:15:01 +0000 [error]: Worker 0 finished with error. Shutting down.
```

`1/2`가 조사 범위를 정해 줍니다. 두 컨테이너 중 하나는 `Ready: True`이므로 메인은 건드릴 필요가 없습니다.

마운트 정보를 나란히 놓으면 두 가지가 어긋나 있습니다. 메인은 `app-logs` 볼륨을 `/var/log/nginx`에 붙였고, 사이드카는 `nginx-logs`라는 볼륨을 `/var/log/app`에 붙이려 합니다. 그런데 Pod 스펙의 `Volumes`에는 `app-logs`만 정의돼 있습니다.

볼륨 이름이 틀리면 마운트가 되지 않고, 설령 같은 볼륨을 붙였더라도 경로가 달라 사이드카는 메인이 쓴 파일을 볼 수 없습니다. 두 실수가 겹쳐 있습니다.

사이드카가 파일을 못 찾고 즉시 종료한다는 점도 설계 문제입니다. 로그 수집기는 대상 파일이 늦게 생길 수 있는 위치에 있으므로, 없을 때 기다리는 편이 안전합니다.

### 조치

```bash
# 죽은 컨테이너만 지정해 로그를 본다
kubectl logs web-app-6f9d8c4b7-r2p5k -c log-collector --previous

# 볼륨 이름과 마운트 경로를 양쪽 컨테이너에서 맞춘다
kubectl edit deployment web-app

kubectl rollout status deployment web-app
kubectl get pods
```

```yaml
# 두 컨테이너가 같은 볼륨 이름과 같은 경로를 가리키게 한다
      containers:
      - name: app
        volumeMounts:
        - name: app-logs
          mountPath: /var/log/nginx
      - name: log-collector
        volumeMounts:
        - name: app-logs
          mountPath: /var/log/nginx
          readOnly: true
      volumes:
      - name: app-logs
        emptyDir: {}
```

멀티 컨테이너 Pod에서 볼륨을 공유할 때는 이름과 경로를 양쪽에서 같은 값으로 쓰는지 확인하는 것이 사실상 전부입니다. 이름이 다르면 마운트 실패이고 경로가 다르면 조용한 불일치입니다.

수집기 쪽 설정도 함께 손봅니다. Fluentd라면 대상 파일이 없을 때 즉시 죽지 않도록 옵션을 조정해, 메인 컨테이너가 첫 로그를 쓰기 전에 사이드카가 먼저 떠도 견디게 만듭니다.



## 사례 4 — Running 인데 트래픽을 못 받습니다

> `0/1 Running`은 컨테이너는 살아 있지만 준비되지 않았다는 뜻입니다. 준비되지 않은 Pod 는 Service 의 엔드포인트에서 빠집니다.

Service로 접근해도 응답이 없습니다. Pod는 `Running`인데 `READY`가 `0/1`입니다.

```bash
NAME        READY   STATUS    RESTARTS   AGE
web-ready   0/1     Running   0          2m
```

```yaml
Containers:
  nginx:
    Image:       nginx:latest
    Port:        80/TCP
    Readiness:   http-get http://:8080/ delay=0s timeout=1s period=10s #success=1 #failure=3
    State:       Running
    Ready:       False
Events:
  Warning  Unhealthy  10s (x12 over 2m)  kubelet   Readiness probe failed: Get "http://10.244.1.5:8080/": dial tcp 10.244.1.5:8080: connect: connection refused
```

```yaml
spec:
  containers:
  - name: nginx
    image: nginx:latest
    ports:
    - containerPort: 80
    readinessProbe:
      httpGet:
        path: /
        port: 8080
```

`Running`과 `Ready: False`가 함께 있는 조합이 이 사례의 특징입니다. 컨테이너 프로세스는 살아 있고 재시작도 없습니다. 죽지 않았으니 로그를 열어도 이상한 것이 없습니다.

원인은 이벤트에 있습니다. readiness probe가 8080번으로 요청했는데 `connection refused`를 받았습니다. 매니페스트를 보면 컨테이너가 여는 포트는 80이고 probe가 검사하는 포트는 8080입니다.

nginx 기본 이미지는 80번에서만 듣습니다. 8080번에는 아무도 없으니 커널이 즉시 거절합니다. probe 는 실패를 반복하고 kubelet 은 이 Pod 를 준비되지 않은 것으로 표시합니다.

그 결과가 Service 쪽에서 나타납니다. 준비되지 않은 Pod는 엔드포인트 목록에서 제외되므로 Service에는 보낼 곳이 없습니다. "Pod는 떠 있는데 접속이 안 된다"는 상황의 전형적인 원인입니다.

### 조치

```bash
# 왜 준비되지 않았는지는 이벤트에 있다
kubectl describe pod web-ready

# probe 포트를 컨테이너가 실제로 여는 포트로 맞춘 뒤 재적용
kubectl apply -f web-ready-pod.yaml

# Service 가 이 Pod 를 다시 잡았는지 확인
kubectl get pods web-ready
kubectl get endpoints
```

확인의 마지막 단계로 `kubectl get endpoints`를 보는 습관이 유용합니다. Pod가 `1/1 Ready`가 되면 그 IP가 엔드포인트 목록에 들어오고, 들어오지 않았다면 문제가 probe가 아니라 Service 셀렉터 쪽이라는 뜻입니다.

probe 값은 컨테이너의 실제 동작과 맞춰야 합니다. 포트뿐 아니라 경로도 마찬가지이고, 애플리케이션이 시작에 오래 걸린다면 `initialDelaySeconds`나 startup probe를 함께 씁니다.



## 네 사례를 관통하는 것

> 네 사례 모두 Pod 스펙에 적힌 값과 컨테이너의 실제 동작이 어긋나서 생겼습니다. 어긋난 값이 이름·환경 변수·볼륨·포트로 달랐을 뿐입니다.

기동 실패의 원인이 클러스터 쪽에 있는 경우는 생각보다 드뭅니다. 네 사례에서 잘못된 것은 Service 이름 하나, 빠진 환경 변수 하나, 볼륨 이름 하나, 포트 번호 하나였습니다. 전부 매니페스트에 적힌 문자열입니다.

조사 도구도 반복됩니다. `kubectl describe pod`가 상태와 이벤트를, `kubectl logs`가 애플리케이션의 마지막 말을 줍니다. 컨테이너가 여럿이면 `-c`로 지정하고, 죽고 다시 뜨는 중이면 `--previous`를 붙입니다. 이 세 가지 조합이 네 사례 전부를 커버합니다.

마지막으로 각 관문이 실패를 드러내는 방식이 다르다는 점을 기억해 둡니다. 죽는 실패는 재시작 횟수로 눈에 띄지만, Init 무한 대기와 readiness 실패는 조용합니다. 조용한 실패일수록 알림 설계에서 빠지기 쉽습니다.
