# 서비스 디스커버리 — Service·EndpointSlice·DNS

---

> Service 이름으로 접속이 안 될 때 볼 곳은 하나입니다. `kubectl get endpoints` 가 비어 있으면 라벨 문제이고, 채워져 있으면 DNS 나 Service 종류 문제입니다.

Pod가 다 떠 있는데 이름으로 서로를 못 찾는 상황이 있습니다. 세 사례가 그 상황의 다른 얼굴들입니다.

하나는 Service 가 Pod 를 못 잡은 경우이고, 나머지 둘은 Service 종류가 목적에 안 맞아 DNS 응답이 기대와 다른 경우입니다.



## endpoints 가 비었는지부터 봅니다

> Service 는 라벨로 Pod 를 모으고 그 결과가 EndpointSlice 에 남습니다. 이 목록이 비어 있으면 그 뒤 단계는 볼 필요가 없습니다.

Service 이름으로 접속이 안 될 때 DNS부터 의심하기 쉽습니다. 그런데 DNS가 정상이어도 보낼 곳이 없으면 연결은 실패합니다.

Service는 그 자체로 무언가를 실행하지 않습니다. 셀렉터에 맞는 Pod를 모아 EndpointSlice에 목록으로 남기고, kube-proxy가 그 목록을 보고 전달 규칙을 만듭니다. 목록이 비면 규칙도 비어 있습니다.

그래서 확인 순서가 정해집니다. `kubectl get endpoints`가 비었으면 라벨 매칭을 보고, 채워져 있는데도 안 되면 DNS와 Service 종류를 봅니다.

| 증상 | endpoints | 원인 후보 |
|------|-----------|-----------|
| 연결 거부 | `<none>` | 셀렉터와 Pod 라벨 불일치 (사례 1) |
| DNS 가 IP 하나만 반환 | 채워져 있음 | ClusterIP Service 의 정상 동작 (사례 2) |
| DNS 가 `NXDOMAIN` | 채워져 있음 | Headless 가 아니어서 Pod 레코드가 없음 (사례 3) |



## 사례 1 — Service 에 붙은 Pod 가 하나도 없습니다

> `Endpoints: <none>`은 셀렉터가 아무 Pod 도 못 잡았다는 뜻입니다. 라벨 매칭은 대소문자를 구분합니다.

백엔드에 ClusterIP Service를 만들었는데 프론트엔드에서 연결이 거부됩니다. Pod는 정상이고 Pod IP로 직접 요청하면 응답합니다.

```bash
NAME      TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)    AGE
backend   ClusterIP   10.96.32.150   <none>        8080/TCP   10m
```

```bash
Name:              backend
Selector:          app=Backend
Port:              http  8080/TCP
TargetPort:        8080/TCP
Endpoints:         <none>
```

```bash
NAME                       READY   STATUS    RESTARTS   AGE   LABELS
backend-6d8f9c4b7-k3m2n   1/1     Running   0          10m   app=backend,version=v1
backend-6d8f9c4b7-r8n5p   1/1     Running   0          10m   app=backend,version=v1
```

```bash
curl: (7) Failed to connect to backend.default.svc port 8080: Connection refused
```

Pod IP로 직접 요청하면 응답한다는 사실이 범위를 크게 좁혀 줍니다. 애플리케이션과 컨테이너 포트는 정상이므로 문제는 Service 계층에 있습니다.

`describe`의 `Endpoints: <none>`이 답입니다. 셀렉터 `app=Backend`와 Pod 라벨 `app=backend`를 나란히 놓으면 첫 글자의 대소문자가 다릅니다.

쿠버네티스의 라벨 매칭은 문자열 완전 일치입니다. 사람 눈에는 같은 단어로 보여도 `Backend`와 `backend`는 다른 값이라 아무 Pod도 잡히지 않습니다.

이 실패가 `Connection refused`로 나타나는 것도 설명이 됩니다. 보낼 곳이 없는 ClusterIP로 간 요청은 전달될 규칙이 없어 커널이 즉시 거절합니다.

### 조치

```bash
# 가장 먼저 볼 것
kubectl get endpoints backend

# 셀렉터를 Pod 라벨과 같은 값으로 맞춘다
kubectl patch svc backend -p '{"spec":{"selector":{"app":"backend"}}}'

# 목록이 채워졌는지 확인한 뒤 접속 테스트
kubectl get endpoints backend
kubectl exec -it frontend-pod -- curl http://backend.default.svc:8080/api/health
```

`kubectl get endpoints <서비스>`를 먼저 치는 습관이 이 계열 문제의 절반을 즉시 해결합니다. 비어 있으면 라벨, 채워져 있으면 그다음 단계라는 분기가 명확합니다.

라벨 표기를 팀 규칙으로 정해 두면 이 실수 자체가 줄어듭니다. 소문자와 하이픈만 쓰는 규칙이 흔하고, 매니페스트 검증 도구로 강제할 수도 있습니다.



## 사례 2 — DNS 가 Pod IP 대신 하나의 IP 만 돌려줍니다

> ClusterIP Service 는 가상 IP 하나를 이름에 붙입니다. 개별 Pod 를 찾아야 하는 애플리케이션에는 맞지 않는 종류입니다.

피어 Pod를 DNS로 발견해 클러스터를 구성해야 하는 애플리케이션이 개별 Pod를 찾지 못합니다.

```bash
NAME                             READY   STATUS    RESTARTS   AGE   IP
discovery-app-7d8f9c6b5-x1a2b   1/1     Running   0          10m   10.244.1.10
discovery-app-7d8f9c6b5-y3c4d   1/1     Running   0          10m   10.244.2.11
discovery-app-7d8f9c6b5-z5e6f   1/1     Running   0          10m   10.244.3.12
```

```yaml
spec:
  selector:
    app: discovery
  ports:
  - port: 80
    targetPort: 8080
  type: ClusterIP
  clusterIP: 10.96.45.123
```

```bash
Name:      discovery-svc.disco.svc.cluster.local
Address:   10.96.45.123
```

DNS가 돌려준 주소를 Service 정의와 대조하면 정체가 드러납니다. `10.96.45.123`은 Pod IP가 아니라 Service의 `clusterIP`입니다.

이것은 고장이 아니라 설계된 동작입니다. ClusterIP Service는 여러 Pod 앞에 가상 IP 하나를 세우고, 그 IP로 온 요청을 kube-proxy가 Pod 중 하나로 넘깁니다. 클라이언트는 뒤에 몇 개가 있는지 알 필요가 없습니다.

문제는 이 애플리케이션의 요구가 정반대라는 점입니다. 피어를 각각 알아야 클러스터를 구성할 수 있는데, ClusterIP는 그 정보를 일부러 감춥니다.

이럴 때 쓰는 것이 Headless Service입니다. `clusterIP: None`으로 두면 가상 IP를 만들지 않고, DNS 조회에 백엔드 Pod들의 IP를 A 레코드로 모두 돌려줍니다.

### 조치

```bash
# clusterIP 는 나중에 바꿀 수 없으므로 지우고 다시 만든다
kubectl delete svc discovery-svc -n disco

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: discovery-svc
  namespace: disco
spec:
  clusterIP: None
  selector:
    app: discovery
  ports:
  - port: 80
    targetPort: 8080
EOF

# 이제 Pod IP 들이 돌아오는지 확인
kubectl exec deploy/testpod -n disco -- nslookup discovery-svc.disco.svc.cluster.local
```

`clusterIP` 필드는 생성 후 변경할 수 없어 패치로는 바뀌지 않습니다. 지우고 다시 만드는 동안 그 이름으로 오는 요청이 잠시 실패한다는 점을 감안해야 합니다.

Headless로 바꾸면 로드밸런싱도 함께 사라집니다. kube-proxy가 개입하지 않으므로 어느 Pod에 보낼지는 클라이언트가 정해야 하고, 그 선택 로직이 없는 애플리케이션에 Headless를 주면 오히려 나빠집니다.



## 사례 3 — StatefulSet Pod 이름이 해석되지 않습니다

> `<pod>.<service>` 형태의 이름은 Headless Service 가 있어야 만들어집니다. StatefulSet 의 `serviceName` 만으로는 부족합니다.

분산 데이터베이스를 StatefulSet으로 배포했는데 Pod들이 안정적인 DNS 이름으로 서로를 찾지 못합니다.

```bash
NAME        READY   STATUS    RESTARTS   AGE
dns-app-0   1/1     Running   0          5m
dns-app-1   1/1     Running   0          4m
dns-app-2   1/1     Running   0          3m
netshoot    1/1     Running   0          10m
```

```bash
** server can't find dns-app-0.dns-app.dev.svc.cluster.local: NXDOMAIN
```

```yaml
spec:
  selector:
    app: dns-app
  ports:
  - port: 80
    targetPort: 80
  type: ClusterIP
  clusterIP: 10.96.78.123
```

```yaml
spec:
  serviceName: dns-app
  replicas: 3
```

`NXDOMAIN`은 그런 이름이 없다는 응답입니다. 조회 실패나 타임아웃이 아니라 DNS 서버가 명확히 없다고 답한 것이라, resolver 설정 문제도 아닙니다.

StatefulSet 쪽은 제대로 돼 있습니다. `serviceName: dns-app`으로 짝이 될 Service를 지정했고 Pod 이름도 `dns-app-0`부터 순서대로 붙었습니다.

빠진 것은 Service 종류입니다. `clusterIP: 10.96.78.123`이 박혀 있으니 일반 ClusterIP Service이고, 이 종류는 Pod 하나하나에 대한 DNS 레코드를 만들지 않습니다.

앞 사례와 같은 원인이 다른 증상으로 나타난 셈입니다. 사례 2에서는 Service 이름 조회가 ClusterIP를 돌려줬고, 여기서는 Pod 이름 조회가 아예 실패했습니다. 둘 다 Headless가 아니어서 생긴 일입니다.

### 조치

```bash
kubectl delete svc dns-app -n dev

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: Service
metadata:
  name: dns-app
  namespace: dev
spec:
  clusterIP: None
  selector:
    app: dns-app
  ports:
  - port: 80
    targetPort: 80
EOF

kubectl rollout restart statefulset dns-app -n dev

kubectl exec -it netshoot -n dev -- nslookup dns-app-0.dns-app.dev.svc.cluster.local
```

StatefulSet과 Headless Service는 사실상 한 세트입니다. `serviceName` 필드가 가리키는 Service 가 Headless 여야 각 Pod 가 예측 가능한 이름을 갖습니다.

이름 형식도 함께 기억해 둡니다. `<pod 이름>.<service 이름>.<네임스페이스>.svc.cluster.local`이고, 앞의 두 조각이 짝을 이루므로 둘 중 하나만 어긋나도 해석되지 않습니다.



## 세 사례를 관통하는 것

> 세 사례 모두 Service 가 무엇을 하는 물건인지에서 갈립니다. 라벨로 모으고, 가상 IP 를 세우거나 세우지 않으며, 그 선택이 DNS 응답을 바꿉니다.

사례 1은 모으는 단계가 실패했고, 사례 2와 3은 모으기는 했는데 이름을 붙이는 방식이 요구와 달랐습니다. 그래서 첫 확인이 `kubectl get endpoints`인 것이 합리적입니다. 이 한 줄이 두 갈래를 가릅니다.

ClusterIP와 Headless의 차이도 반복해서 등장합니다. 앞은 뒤에 무엇이 있는지 감추고 뒤는 그대로 드러냅니다. 감추는 쪽이 기본값인 이유는 대부분의 클라이언트가 어느 Pod인지 알 필요가 없기 때문이고, 알아야 하는 애플리케이션만 Headless를 씁니다.

마지막으로 `clusterIP` 필드가 나중에 못 바뀐다는 제약이 두 사례에서 같은 조치를 만들었습니다. Service 종류는 만들 때 정해야 하므로, StatefulSet이나 피어 디스커버리가 필요한 워크로드는 설계 단계에서 Headless를 정해 두는 편이 낫습니다.
