# 이미지를 못 가져올 때 — ImagePullBackOff·시크릿·롤백

---

> `ImagePullBackOff`는 상태 이름일 뿐 원인이 아닙니다. 같은 상태 뒤에 오타, 인증 누락, 잘못된 배포가 각각 숨어 있고 셋의 조치가 다릅니다.

Pod가 안 뜨는 문제 중 가장 흔한 것이 이미지를 못 가져오는 경우입니다. 그런데 `kubectl get pods`가 보여 주는 상태 문자열은 셋 다 똑같습니다.

구분은 `kubectl describe pod`의 `Events` 아래쪽에서 납니다. 레지스트리가 돌려준 원문 에러가 거기 그대로 실려 있고, 그 문장 하나가 조치를 정합니다.



## Events 의 에러 문장이 원인을 가릅니다

> `not found`·`403: denied`·`tag does not exist`는 각각 다른 실패입니다. 이름이 틀렸는지, 권한이 없는지, 배포가 잘못됐는지가 여기서 갈립니다.

Pod가 `ImagePullBackOff`로 멈추면 매니페스트를 다시 열어 보게 됩니다. 그런데 매니페스트만 봐서는 이미지 이름이 틀렸는지 권한이 없는지 알 수 없습니다.

kubelet은 레지스트리와 통신한 결과를 이벤트에 그대로 남깁니다. `kubectl describe pod`의 맨 아래 `Events` 섹션이 그 자리이고, `Failed` 이벤트의 메시지 끝부분이 레지스트리의 응답입니다.

`BackOff`라는 이름 자체도 정보를 담고 있습니다. kubelet이 실패한 pull을 점점 긴 간격으로 재시도하는 상태라, 원인을 고치면 다음 재시도에서 자동으로 회복됩니다.

| Events 의 메시지 | 실패한 것 | 조치 |
|------------------|-----------|------|
| `not found` 또는 `tag does not exist` | 그 이름의 이미지가 레지스트리에 없음 | 태그를 고치거나 이전 버전으로 되돌린다 |
| `403: denied` 또는 `unauthorized` | 인증 없이 프라이빗 레지스트리에 접근 | `imagePullSecrets` 를 붙인다 |
| `dial tcp ... timeout` | 레지스트리에 닿지 못함 | 노드의 네트워크와 프록시 설정을 본다 |



## 사례 1 — 존재하지 않는 태그를 적었습니다

> 레지스트리가 `not found`를 돌려주면 매니페스트의 태그가 실재하는지부터 확인합니다. 이미지 이름은 맞고 태그만 틀린 경우가 흔합니다.

새 버전 매니페스트를 적용했는데 Pod가 `Running`으로 넘어가지 못합니다.

```bash
NAME                             READY   STATUS             RESTARTS   AGE
web-frontend-7f8d9b4c5d-x2j4k    0/1     ImagePullBackOff   0          5m
```

```yaml
    spec:
      containers:
      - name: frontend
        image: nginx:1.25.12-alpine
        ports:
        - containerPort: 80
```

```bash
Events:
  Normal   Scheduled  5m               default-scheduler  Successfully assigned default/web-frontend-7f8d9b4c5d-x2j4k to node-01
  Normal   Pulling    4m (x3 over 5m)  kubelet            Pulling image "nginx:1.25.12-alpine"
  Warning  Failed     4m (x3 over 5m)  kubelet            Failed to pull image "nginx:1.25.12-alpine": failed to resolve reference "docker.io/library/nginx:1.25.12-alpine": docker.io/library/nginx:1.25.12-alpine: not found
  Warning  Failed     4m (x3 over 5m)  kubelet            Error: ErrImagePull
  Normal   BackOff    3m (x4 over 4m)  kubelet            Back-off pulling image "nginx:1.25.12-alpine"
```

첫 이벤트가 `Scheduled`라는 점을 먼저 확인합니다. Pod가 노드에 배정됐다는 뜻이므로 스케줄링과 자원은 문제가 아닙니다. 실패는 그 뒤 kubelet 단계에서 났습니다.

메시지 끝의 `not found`가 레지스트리의 답입니다. 이미지 이름 `nginx`는 맞고 태그 `1.25.12-alpine`이 없습니다. 존재하지 않는 패치 버전을 적은 오타이고, 실제 nginx 공식 이미지에 그 버전은 없습니다.

`ErrImagePull`과 `ImagePullBackOff`가 순서대로 나오는 것도 읽어 둘 만합니다. 앞은 이번 시도의 실패이고 뒤는 재시도 간격을 늘리며 대기하는 상태입니다.

### 조치

```bash
# 태그가 실재하는지 배포 전에 확인하는 습관
docker manifest inspect nginx:1.25.4-alpine > /dev/null && echo "tag exists"

# 매니페스트의 태그를 고쳐 다시 적용
kubectl apply -f web-frontend-deployment.yaml

# 회복 확인
kubectl get pods -w
```

태그를 고치면 kubelet이 다음 재시도에서 성공하므로 Pod를 지울 필요가 없습니다. `BackOff` 간격 때문에 반영이 몇십 초 늦을 수 있는데, 급하면 Pod를 지워 새로 만들면 즉시 시도합니다.

배포 전에 태그 존재를 검증하는 단계를 파이프라인에 넣으면 이 사례가 클러스터까지 오지 않습니다. `docker manifest inspect`나 레지스트리 API 한 번이면 충분합니다.



## 사례 2 — 프라이빗 레지스트리에 인증 없이 접근했습니다

> `403: denied`는 이미지가 없다는 뜻이 아니라 볼 권한이 없다는 뜻입니다. 이름을 고쳐도 풀리지 않습니다.

`dev` 네임스페이스의 Deployment Pod가 `ImagePullBackOff`에 머물러 있습니다. 앞 사례처럼 태그를 고쳐 봐도 상태가 바뀌지 않습니다.

```bash
NAME                       READY   STATUS             RESTARTS   AGE
backend-6c8d7f9b5-q2w3e    0/1     ImagePullBackOff   0          3m
```

```bash
Events:
  Normal   Pulling  2m (x3 over 3m)  kubelet  Pulling image "ghcr.io/prepare-sh/alpine:3.23.2"
  Warning  Failed   2m (x3 over 3m)  kubelet  Failed to pull image "ghcr.io/prepare-sh/alpine:3.23.2": failed to resolve reference: pulling from host ghcr.io failed with status 403: denied
  Warning  Failed   2m (x3 over 3m)  kubelet  Error: ErrImagePull
```

```yaml
    spec:
      containers:
      - name: backend
        image: ghcr.io/prepare-sh/alpine:3.23.2
        ports:
        - containerPort: 8080
```

```bash
NAME                  TYPE                                  DATA   AGE
default-token-abc12   kubernetes.io/service-account-token   3      5d
```

`403: denied`는 앞 사례의 `not found`와 성격이 다릅니다. 레지스트리가 요청을 이해했고 그 이미지의 존재 여부와 무관하게 접근을 거절했다는 뜻입니다. 태그를 아무리 고쳐도 같은 응답이 돌아옵니다.

두 자료가 원인을 확정해 줍니다. 매니페스트의 Pod 스펙에 `imagePullSecrets` 항목이 없고, 네임스페이스의 시크릿 목록에도 서비스 어카운트 토큰만 있습니다. 레지스트리 자격 증명이 클러스터 어디에도 없는 상태입니다.

여기서 자주 하는 실수가 시크릿을 다른 네임스페이스에 만들어 두는 것입니다. 시크릿은 네임스페이스 안에서만 참조되므로 `dev`에 있는 Pod는 `default`의 시크릿을 볼 수 없습니다.

### 조치

```bash
# 레지스트리 자격 증명 시크릿을 그 네임스페이스에 만든다
kubectl create secret docker-registry ghcr-secret -n dev \
  --docker-server=ghcr.io \
  --docker-username=<username> \
  --docker-password=<access-token>

# Pod 스펙에 시크릿을 붙인다
kubectl patch deployment backend -n dev -p \
  '{"spec":{"template":{"spec":{"imagePullSecrets":[{"name":"ghcr-secret"}]}}}}'

kubectl get pods -n dev -w
```

```bash
# 네임스페이스 전체에 적용하려면 ServiceAccount 에 붙인다
kubectl patch serviceaccount default -n dev -p \
  '{"imagePullSecrets":[{"name":"ghcr-secret"}]}'
```

Deployment마다 시크릿을 붙이는 방식은 새 워크로드가 생길 때마다 빠뜨리기 쉽습니다. 서비스 어카운트에 기본값으로 붙이면 그 네임스페이스의 Pod가 자동으로 상속합니다.

토큰 만료도 함께 관리해야 합니다. 어제까지 잘 돌던 배포가 갑자기 `403`을 받는다면 매니페스트가 아니라 토큰의 수명이 끝났을 가능성이 큽니다.



## 사례 3 — 잘못된 이미지를 배포해 롤아웃이 멈췄습니다

> 롤링 업데이트 중 새 Pod가 안 뜨면 기존 Pod가 남아 서비스는 살아 있습니다. 그 시간 안에 되돌리는 것이 가장 빠른 조치입니다.

API 서버 이미지를 올렸는데 새 Pod가 전부 `ImagePullBackOff`입니다. 기존 Pod는 아직 살아 있지만 점차 교체되는 중입니다.

```bash
NAME                          READY   STATUS             RESTARTS   AGE
api-server-7b8c9d6f5-h4k2n   1/1     Running            0          2d
api-server-7b8c9d6f5-j9m3p   1/1     Running            0          2d
api-server-5a3f8e7d2-w2x4q   0/1     ImagePullBackOff   0          4m
api-server-5a3f8e7d2-v6y8r   0/1     ImagePullBackOff   0          4m
```

```bash
REVISION  CHANGE-CAUSE
1         initial deployment v2.3.0
2         image update to v2.4.0
3         image update to v2.5.0
```

```bash
Events:
  Normal   Pulling  2m (x3 over 4m)  kubelet  Pulling image "registry.example.com/api-server:v2.5.O"
  Warning  Failed   2m (x3 over 4m)  kubelet  Failed to pull image "registry.example.com/api-server:v2.5.O": tag does not exist
  Warning  Failed   2m (x3 over 4m)  kubelet  Error: ImagePullBackOff
```

이벤트의 태그를 한 글자씩 봅니다. `v2.5.O`의 마지막 문자가 숫자 0이 아니라 영문 대문자 O입니다. 화면에서 구분이 거의 안 되는 종류의 오타이고, 그래서 매니페스트를 다시 읽어도 잘 안 보입니다.

앞의 두 사례와 다른 점은 시간 압박입니다. 롤링 업데이트는 새 Pod가 준비될 때까지 기존 Pod를 남겨 두므로 지금은 서비스가 살아 있습니다. 그러나 `maxUnavailable` 설정에 따라 기존 Pod도 줄어들 수 있어 여유가 무한하지 않습니다.

그래서 여기서는 원인을 완전히 파악하기 전에 되돌리는 것이 옳습니다. 롤백은 몇 초 만에 끝나고 되돌린 뒤에 태그를 고쳐 다시 올리면 됩니다.

### 조치

```bash
# 어느 리비전으로 돌아갈지 확인
kubectl rollout history deployment/api-server

# 직전 정상 리비전으로 즉시 롤백
kubectl rollout undo deployment/api-server --to-revision=2

# 롤백 완료 확인
kubectl rollout status deployment/api-server
kubectl get pods -l app=api-server

# 원인을 고친 뒤 다시 올린다
kubectl set image deployment/api-server api=registry.example.com/api-server:v2.5.0
```

`rollout history`의 `CHANGE-CAUSE`가 채워져 있으면 어느 리비전이 정상이었는지 바로 보입니다. 이 값은 배포할 때 애노테이션으로 남기지 않으면 비어 있으므로, 파이프라인에서 채우도록 해 두는 편이 좋습니다.

롤백 자체보다 중요한 것은 되돌릴 수 있는 상태를 유지하는 일입니다. 리비전 이력이 남아 있고 이전 이미지가 레지스트리에서 지워지지 않았어야 이 명령이 통합니다.



## 세 사례를 관통하는 것

> `kubectl get pods`의 상태 문자열은 증상이고, `kubectl describe pod`의 Events 가 원인입니다. 세 사례의 차이는 전부 뒤쪽에서만 보입니다.

같은 `ImagePullBackOff`가 세 가지 다른 문제를 가리켰습니다. 오타는 매니페스트를 고치는 일이고 인증 누락은 시크릿을 만드는 일이며, 잘못된 배포는 되돌리는 일입니다. 상태만 보고 조치를 고르면 셋 중 둘은 틀립니다.

`Events`를 읽는 순서도 반복됩니다. `Scheduled`가 있으면 스케줄링은 통과한 것이고, `Pulling` 다음의 `Failed` 메시지 끝부분이 레지스트리의 답이며, 그 문장이 조치를 정합니다. 이 순서는 다음 문서의 컨테이너 기동 실패에서도 그대로 쓰입니다.

마지막으로 세 사례 모두 배포 전에 막을 수 있었습니다. 태그 존재 검증, 시크릿 존재 검증, 리비전 기록 세 가지가 파이프라인에 있으면 클러스터에서 볼 일이 크게 줄어듭니다.
