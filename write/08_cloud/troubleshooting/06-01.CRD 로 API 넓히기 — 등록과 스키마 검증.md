# CRD 로 API 넓히기 — 등록과 스키마 검증

---

> CRD 는 API 서버에 새 자원 종류를 등록하는 선언입니다. 등록이 안 되면 아무것도 만들 수 없고, 검증이 느슨하면 잘못된 것이 그대로 만들어집니다.

두 사례가 CRD 운영의 양 끝을 보여 줍니다. 하나는 등록 단계에서 막히는 경우이고 다른 하나는 등록은 됐는데 아무거나 통과시키는 경우입니다.

뒤쪽이 더 위험합니다. 앞은 즉시 에러가 나지만, 뒤는 잘못된 자원이 조용히 만들어져 나중에 컨트롤러를 무너뜨립니다.



## CRD 는 API 를 늘리는 대신 검증도 떠맡습니다

> 내장 자원은 API 서버가 검증 규칙을 갖고 있습니다. CRD 는 그 규칙을 스키마로 직접 적어 줘야 합니다.

Deployment 매니페스트에 이상한 값을 넣으면 API 서버가 거절합니다. 그 검증 규칙은 쿠버네티스가 미리 갖고 있습니다.

커스텀 자원에는 그런 것이 없습니다. CRD를 만들 때 `openAPIV3Schema`로 어떤 필드가 있고 무엇이 필수이며 값의 범위가 어떻게 되는지를 직접 적어야 하고, 안 적으면 API 서버는 검사할 것이 없어 그냥 통과시킵니다.

여기서 흔한 오해가 생깁니다. 스키마에 필드를 나열했으니 검증이 된다고 생각하는 것입니다. 실제로는 타입만 맞으면 통과이고, 필수 여부와 값 범위는 별도 키워드로 적어야 합니다.

| 적는 것 | 없으면 | 사례 |
|---------|--------|------|
| `served: true` | 그 버전으로 자원을 만들 수 없다 | 사례 1 |
| `required` | 필드를 빠뜨린 자원이 만들어진다 | 사례 2 |
| `minimum`, `maximum`, `enum` | 범위를 벗어난 값이 통과한다 | 사례 2 |



## 사례 1 — CRD 는 등록됐는데 자원을 못 만듭니다

> `served` 와 `storage` 는 다른 일을 합니다. `served: false` 인 버전은 API 서버가 요청을 받지 않습니다.

커스텀 자원을 쓰려고 CRD를 등록했는데 인스턴스 생성에서 에러가 납니다.

```bash
error: resource mapping not found for name: "sample-widget" namespace: "extensions" from "sample-widget.yaml": no matches for kind "Widget" in version "mycompany.io/v1"
ensure CRDs are installed first
```

```bash
NAME                    CREATED AT
widgets.mycompany.io    2025-01-15T08:00:00Z
```

```yaml
  versions:
  - name: v1
    served: false
    storage: true
```

에러가 "CRD를 먼저 설치하라"고 안내하지만 그것은 이미 돼 있습니다. 목록에 `widgets.mycompany.io`가 보입니다.

CRD 정의를 보면 `served: false`입니다. 이 값이 `false`면 API 서버는 그 버전에 대한 클라이언트 요청을 처리하지 않습니다. 등록은 돼 있지만 창구가 닫힌 상태입니다.

`storage: true`가 함께 있어 헷갈릴 수 있습니다. 두 필드는 역할이 다릅니다. `served`는 요청을 받을지를 정하고 `storage`는 etcd에 어느 버전 형태로 저장할지를 정합니다.

이 조합은 버전 마이그레이션에서 의도적으로 쓰이기도 합니다. 옛 버전을 `served: false`로 두면 새 자원 생성은 막으면서 이미 저장된 것은 유지할 수 있습니다. 지금은 그 설정이 첫 버전에 잘못 들어간 경우입니다.

### 조치

```yaml
  versions:
  - name: v1
    served: true
    storage: true
```

```bash
kubectl apply -f widget-crd.yaml

# 자원이 놓일 네임스페이스가 있는지도 함께 확인
kubectl create namespace extensions --dry-run=client -o yaml | kubectl apply -f -

kubectl apply -f sample-widget.yaml
kubectl get widgets -n extensions
```

`kubectl api-resources | grep widgets`로 그 종류가 실제로 노출되는지 확인할 수 있습니다. 목록에 안 나오면 `served` 설정을 먼저 봅니다.

CRD를 고친 뒤 클라이언트 캐시 때문에 잠시 옛 상태가 보일 수 있습니다. `kubectl` 이 API 자원 목록을 캐시하므로, 바뀌지 않은 것처럼 보이면 잠시 뒤 다시 시도합니다.



## 사례 2 — 잘못된 자원이 만들어져 컨트롤러가 죽습니다

> 스키마에 필드를 적는 것과 그 필드를 강제하는 것은 다릅니다. `required` 와 `minimum` 이 없으면 API 서버는 아무것도 막지 않습니다.

운영 중인 커스텀 자원 몇 개가 만들어진 뒤 컨트롤러가 반복해서 에러를 내고 종료합니다.

```bash
2025-01-15T10:00:01Z [ERROR] Reconcile failed for widget "bad-widget": spec.size is required but was nil
2025-01-15T10:00:01Z [ERROR] Reconcile failed for widget "negative-widget": spec.size must be positive, got -5
2025-01-15T10:00:02Z [FATAL] Too many errors, controller shutting down
```

```yaml
spec:
  color: "red"
```

```yaml
spec:
  color: "blue"
  size: -5
```

```yaml
          spec:
            type: object
            properties:
              color:
                type: string
              size:
                type: integer
```

컨트롤러 로그가 두 종류의 잘못된 자원을 지목합니다. 하나는 `size`가 없고 다른 하나는 음수입니다.

스키마를 보면 왜 이것들이 만들어졌는지 알 수 있습니다. `size`가 `type: integer`로 선언돼 있을 뿐 `required` 목록에도 없고 `minimum`도 없습니다. 타입만 맞으면 통과하므로 필드를 빼도, 음수를 넣어도 API 서버가 받아 줍니다.

이 상황의 성격을 분명히 해 두는 편이 좋습니다. 컨트롤러가 죽은 것은 결과이고 원인은 스키마입니다. 컨트롤러에 방어 코드를 넣어 죽지 않게 만들 수도 있지만, 그러면 잘못된 자원이 계속 만들어지면서 조용히 무시됩니다.

검증을 API 수준에 두는 편이 나은 이유가 여기 있습니다. 만들어지는 순간 거절하면 사용자가 즉시 알 수 있고, 컨트롤러는 유효한 입력만 다루면 됩니다.

### 조치

```yaml
          spec:
            type: object
            required: ["size"]
            properties:
              color:
                type: string
              size:
                type: integer
                minimum: 1
```

```bash
kubectl apply -f widget-crd.yaml

# 이미 만들어진 잘못된 자원은 스키마를 고쳐도 사라지지 않는다
kubectl delete widget bad-widget negative-widget -n extensions

# 검증이 실제로 막는지 확인한다
kubectl apply -f bad-widget.yaml
```

마지막 단계를 빼지 않는 것이 중요합니다. 스키마를 고쳤다는 사실과 그것이 실제로 막는다는 사실은 다르고, 위반하는 자원을 일부러 만들어 봐야 확인됩니다.

이미 저장된 자원은 스키마 변경의 영향을 즉시 받지 않습니다. 검증은 만들거나 고칠 때 일어나므로, 기존 자원은 직접 찾아 정리해야 합니다.

더 복잡한 조건이 필요하면 `x-kubernetes-validations`의 CEL 표현식을 쓸 수 있습니다. 필드 사이의 관계처럼 단일 필드 제약으로 표현되지 않는 규칙이 여기 해당합니다.



## 두 사례를 관통하는 것

> CRD 는 선언 한 장으로 API 를 늘려 주지만, 내장 자원이 공짜로 주던 검증까지 함께 넘겨받습니다.

두 사례의 잘못된 값은 모두 CRD 정의 안의 짧은 필드였습니다. `served: false` 하나가 자원 생성을 전부 막았고, `required`와 `minimum`이 없어 잘못된 자원이 전부 통과했습니다.

발견 시점이 정반대라는 점도 대비가 됩니다. 사례 1은 첫 시도에서 에러가 나므로 늦어질 수 없고, 사례 2는 몇 주 뒤 컨트롤러가 죽고 나서야 드러납니다. 조용한 쪽이 언제나 더 비쌉니다.

그래서 CRD를 설계할 때 스키마를 뒤로 미루지 않는 편이 좋습니다. 자원 종류를 늘리는 일은 그 종류가 무엇을 허용하고 무엇을 거절하는지 정하는 일과 같습니다.
