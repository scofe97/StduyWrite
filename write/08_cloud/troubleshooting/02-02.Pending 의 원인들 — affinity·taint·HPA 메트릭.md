# Pending 의 원인들 — affinity·taint·HPA 메트릭

---

> `Pending`은 스케줄러가 놓을 자리를 못 찾았다는 뜻입니다. `FailedScheduling` 이벤트가 노드 몇 대가 왜 탈락했는지를 한 줄로 적어 줍니다.

앞 문서가 자리를 잡은 뒤의 문제였다면, 이 문서는 자리를 잡지 못하거나 자리를 늘리지 못하는 문제입니다.

세 사례 중 둘은 스케줄링 조건이 실제 노드와 어긋난 경우이고, 나머지 하나는 오토스케일러가 판단 근거를 못 얻은 경우입니다. 셋 다 매니페스트에 적힌 값과 클러스터의 실제 값이 다릅니다.



## FailedScheduling 이벤트가 탈락 사유를 셉니다

> 스케줄러는 노드를 하나씩 걸러 낸 뒤 남은 것이 없으면 그 이유를 종류별로 세어 이벤트에 적습니다. 그 문장이 곧 진단입니다.

`Pending`을 보면 노드가 모자란 것으로 짐작하기 쉽습니다. 그런데 자원 부족은 여러 탈락 사유 중 하나일 뿐입니다.

스케줄러는 필터 단계에서 조건에 맞지 않는 노드를 제외합니다. 전부 제외되면 `FailedScheduling` 이벤트를 남기는데, 이때 사유를 종류별로 묶어 개수와 함께 적습니다. `0/4 nodes are available: 1 node(s) had untolerated taint ..., 3 node(s) didn't match Pod's node affinity/selector.` 같은 형태입니다.

이 문장을 읽는 요령은 개수와 사유를 짝지어 보는 것입니다. 사유마다 확인할 곳이 다르고, 개수가 전체 노드 수와 맞는지 보면 빠진 사유가 있는지도 알 수 있습니다.

| 이벤트의 사유 | 어긋난 것 | 확인 명령 |
|---------------|-----------|-----------|
| `didn't match Pod's node affinity/selector` | 라벨 키나 값 | `kubectl get nodes --show-labels` |
| `had untolerated taint` | taint 와 toleration 의 값 | `kubectl describe node <노드>` |
| `Insufficient cpu/memory` | 남은 자원 | `kubectl describe node <노드>` 의 Allocated |



## 사례 1 — GPU 노드가 있는데 스케줄링되지 않습니다

> 라벨 매칭은 키와 값이 모두 같아야 합니다. GPU 노드가 있다는 사실과 그 노드가 조건에 맞는다는 사실은 다릅니다.

추론 서비스를 GPU 노드에 배포하려고 nodeAffinity를 걸었는데 Pod가 12분째 `Pending`입니다.

```bash
NAME                           READY   STATUS    RESTARTS   AGE
ml-inference-6f8d9c4b7-x2k5n  0/1     Pending   0          12m
```

```bash
Events:
  Warning  FailedScheduling  8s (x15 over 12m)  default-scheduler  0/4 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 3 node(s) didn't match Pod's node affinity/selector.
```

```yaml
      affinity:
        nodeAffinity:
          requiredDuringSchedulingIgnoredDuringExecution:
            nodeSelectorTerms:
            - matchExpressions:
              - key: gpu-type
                operator: In
                values:
                - nvidia-a100
```

```bash
NAME          STATUS   ROLES           LABELS
control-01    Ready    control-plane   node-role.kubernetes.io/control-plane=
worker-01     Ready    <none>          accelerator=nvidia-a100,node-pool=gpu
worker-02     Ready    <none>          accelerator=nvidia-a100,node-pool=gpu
worker-03     Ready    <none>          node-pool=general
```

이벤트의 숫자부터 맞춰 봅니다. 노드 4대 중 1대는 컨트롤 플레인 taint로, 나머지 3대는 affinity 불일치로 탈락했습니다. 자원 부족은 사유에 없으므로 용량 문제가 아닙니다.

매니페스트와 노드 라벨을 나란히 놓으면 어긋난 곳이 보입니다. Pod는 `gpu-type=nvidia-a100`을 찾는데 노드에는 `accelerator=nvidia-a100`이 붙어 있습니다. 값은 같고 키가 다릅니다.

`requiredDuringSchedulingIgnoredDuringExecution`이라는 긴 이름도 여기서 의미를 갖습니다. 앞부분이 필수 조건이라는 뜻이라, 맞는 노드가 없으면 스케줄러는 기다리지 않고 계속 실패합니다. 선호 조건인 `preferred...`였다면 아무 노드에나 배치됐을 것입니다.

### 조치

```bash
# 실제 노드 라벨을 먼저 확인한다
kubectl get nodes --show-labels

# 매니페스트의 키를 실제 라벨에 맞춘다
kubectl edit deployment ml-inference

kubectl get pods -w
```

```bash
# 매니페스트를 못 고치는 상황이면 노드에 라벨을 더한다
kubectl label node worker-01 gpu-type=nvidia-a100
kubectl label node worker-02 gpu-type=nvidia-a100
```

두 방향 중 어느 쪽이 맞는지는 라벨의 소유권으로 정합니다. 노드 라벨을 노드 풀 자동화가 붙이고 있다면 매니페스트를 고치는 편이 안전하고, 라벨 규칙 자체가 미정이면 이참에 정해 문서로 남깁니다.

배포 전에 `kubectl get nodes --show-labels`를 한 번 보는 습관이 이 사례를 통째로 막습니다. 라벨 이름은 클러스터마다 다르고 환경마다 다릅니다.



## 사례 2 — 전용 노드를 만들었는데 그 워크로드도 못 들어갑니다

> `operator: Equal`은 값까지 정확히 같아야 합니다. `data`와 `data-processing`은 사람 눈에 비슷해도 스케줄러에게는 다른 값입니다.

데이터 처리 전용 노드에 taint를 걸어 일반 워크로드를 막았는데, 정작 데이터 파이프라인 Pod도 `Pending`입니다.

```bash
NAME                                READY   STATUS    RESTARTS   AGE
data-pipeline-6d8f9c4b7-k3m2n      0/1     Pending   0          8m
data-pipeline-6d8f9c4b7-r8n5p      0/1     Pending   0          8m
```

```bash
Events:
  Warning  FailedScheduling  5s (x12 over 8m)  default-scheduler  0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 node(s) had untolerated taint {workload: data-processing}.
```

```bash
Taints:   workload=data-processing:NoSchedule
```

```yaml
      nodeSelector:
        node-pool: data
      tolerations:
      - key: "workload"
        operator: "Equal"
        value: "data"
        effect: "NoSchedule"
```

이벤트가 taint 이름까지 적어 줍니다. `untolerated taint {workload: data-processing}`이므로 노드가 요구하는 값은 `data-processing`입니다.

매니페스트의 toleration을 보면 키는 `workload`로 맞는데 값이 `data`입니다. `operator: Equal`은 키와 값이 모두 일치해야 하므로 이 toleration은 그 taint를 허용하지 못합니다.

`nodeSelector`가 올바르게 설정돼 있다는 점이 이 사례를 헷갈리게 만듭니다. `node-pool: data`는 정확히 맞지만, taint 허용이 먼저 통과해야 라벨 매칭까지 갈 수 있습니다. 순서가 있는 조건이라 앞쪽에서 막히면 뒤쪽이 맞아도 소용없습니다.

taint 값과 라벨 값이 비슷하면서 다르다는 점도 이 실수를 부릅니다. 라벨은 `data`이고 taint 값은 `data-processing`이라, 하나를 보고 다른 하나를 짐작하면 틀립니다.

### 조치

```bash
# 노드가 요구하는 정확한 taint 값을 확인
kubectl describe node worker-01 | grep -A2 Taints

# toleration 의 value 를 그 값과 일치시킨다
kubectl edit deployment data-pipeline

kubectl get pods -o wide
```

```yaml
# 값 비교가 필요 없으면 Exists 로 키만 맞춘다
      tolerations:
      - key: "workload"
        operator: "Exists"
        effect: "NoSchedule"
```

`Exists`는 값을 비교하지 않아 이런 불일치가 생기지 않습니다. 대신 그 키를 가진 모든 taint를 허용하므로, 전용 노드를 엄격히 가르는 것이 목적이라면 `Equal`을 유지하고 값을 문서로 관리하는 편이 맞습니다.

taint와 toleration은 짝으로만 의미가 있는 값이라 한쪽만 바뀌면 조용히 깨집니다. 노드 풀 정의와 워크로드 매니페스트를 같은 저장소에 두면 이 짝이 함께 리뷰됩니다.



## 사례 3 — HPA 가 사용률을 계산하지 못합니다

> HPA 는 CPU 사용률을 `requests` 대비 백분율로 계산합니다. 기준이 없으면 사용량이 아무리 높아도 판단할 수 없습니다.

트래픽에 대비해 HPA를 걸었는데 CPU가 90%를 넘어도 스케일아웃되지 않습니다. 현재 값이 `<unknown>/50%`로 표시됩니다.

```bash
NAME          REFERENCE                TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
web-app-hpa   Deployment/web-app       <unknown>/50%   2         10        2          15m
```

```bash
Conditions:
  Type            Status  Reason                   Message
  AbleToScale     True    SucceededGetScale        the HPA controller was able to get the target's current scale
  ScalingActive   False   FailedGetResourceMetric  the HPA was unable to compute the replica count: failed to get cpu utilization: missing request for cpu in container "web"
```

```yaml
        resources:
          limits:
            cpu: "500m"
            memory: "256Mi"
```

```bash
NAME                       CPU(cores)   MEMORY(bytes)
web-app-6d8f9c4b7-k3m2n   456m         180Mi
web-app-6d8f9c4b7-r8n5p   478m         175Mi
```

`kubectl top`이 실제 사용량을 보여 준다는 점이 이 사례의 함정입니다. 메트릭 수집 자체는 되고 있으므로 metrics-server 문제가 아닙니다.

조건 목록이 정확히 짚어 줍니다. `AbleToScale`은 True인데 `ScalingActive`가 False이고, 사유가 `missing request for cpu`입니다. 스케일 대상은 찾았는데 계산을 못 하는 상태입니다.

이유는 HPA의 계산식에 있습니다. HPA는 사용량 자체가 아니라 `requests` 대비 비율을 목표와 비교합니다. Deployment에는 `limits`만 있고 `requests`가 없어 분모가 비어 있습니다.

앞 문서의 사례 1과 이어지는 지점이 여기입니다. `requests` 누락은 축출 위험만 만드는 것이 아니라 오토스케일링까지 함께 멈춥니다. 하나의 빠진 값이 두 곳에서 다르게 드러납니다.

### 조치

```yaml
        resources:
          requests:
            cpu: "200m"
            memory: "128Mi"
          limits:
            cpu: "500m"
            memory: "256Mi"
```

```bash
kubectl edit deployment web-app

# Pod 가 새로 뜬 뒤 TARGETS 에 백분율이 나오는지 확인
kubectl get hpa web-app-hpa

# 왜 못 읽는지는 조건에 남는다
kubectl describe hpa web-app-hpa
```

`requests`를 얼마로 잡느냐가 곧 HPA의 민감도를 정합니다. 목표가 50%일 때 requests가 작으면 사용률이 쉽게 100%를 넘어 자주 늘어나고, 크게 잡으면 좀처럼 늘지 않습니다.

일반적인 기준은 requests를 평소 사용량에, limits를 최대 허용량에 맞추는 것입니다. 두 값의 간격이 그 워크로드가 허용하는 변동 폭이 됩니다.



## 세 사례를 관통하는 것

> 셋 다 매니페스트의 값과 클러스터의 값이 어긋나서 생겼습니다. 라벨 키, taint 값, 그리고 아예 없는 `requests` 였습니다.

스케줄링 문제에서 가장 먼저 볼 곳은 언제나 `FailedScheduling` 이벤트입니다. 이 문장은 노드 몇 대가 어떤 사유로 탈락했는지를 세어 주므로, 추측 없이 확인할 곳을 지목해 줍니다.

세 사례 모두 클러스터의 실제 값을 조회하는 명령이 조치의 첫 줄입니다. `kubectl get nodes --show-labels`, `kubectl describe node`, `kubectl top pods`가 각각 그 역할을 합니다. 매니페스트만 다시 읽어서는 어긋남이 안 보입니다.

마지막으로 `requests` 하나가 두 문서에 걸쳐 세 번 등장했다는 점을 기억해 둡니다. 축출 대상 선정, QoS 클래스, HPA 계산이 모두 이 값을 씁니다. 빠뜨리기는 쉽고 드러나는 자리는 여럿입니다.
