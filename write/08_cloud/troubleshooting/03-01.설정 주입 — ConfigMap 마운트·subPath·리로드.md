# 설정 주입 — ConfigMap 마운트·subPath·리로드

---

> ConfigMap 을 볼륨으로 붙이면 그 경로는 통째로 대체됩니다. 이 한 가지 성질이 세 사례의 원인을 전부 설명합니다.

설정을 파일로 주입하는 일은 간단해 보이지만 실패하는 자리가 여럿입니다. 이름이 안 맞아 만들어지지 않거나, 만들어졌는데 원래 파일을 덮거나, 값이 바뀌었는데 애플리케이션이 모릅니다.

세 사례가 그 셋을 순서대로 보여 줍니다. 앞으로 갈수록 실패가 조용해지고 발견이 늦어집니다.



## 볼륨 마운트는 덮어쓰기입니다

> 리눅스에서 디렉터리에 무언가를 마운트하면 원래 내용이 가려집니다. ConfigMap 볼륨도 같은 규칙을 따릅니다.

ConfigMap을 "설정을 넣는 기능"으로만 이해하면 세 번째 사례가 설명되지 않습니다. 실제로 일어나는 일은 파일시스템 마운트이고, 마운트에는 마운트의 규칙이 있습니다.

디렉터리 위에 다른 것을 마운트하면 원래 있던 내용이 보이지 않게 됩니다. 삭제된 것은 아니지만 그 경로로는 접근할 수 없습니다. 컨테이너 이미지에 들어 있던 기본 설정 파일이 사라진 것처럼 보이는 이유가 이것입니다.

`subPath`는 이 문제를 피하려고 파일 하나만 골라 붙이는 방식입니다. 대신 다른 성질을 잃습니다. 자동 갱신이 되지 않습니다.

| 방식 | 원래 파일 | 값 변경 시 자동 반영 |
|------|-----------|----------------------|
| 디렉터리 마운트 | 가려진다 | 반영된다 (약 1~2분 지연) |
| `subPath` 파일 마운트 | 유지된다 | 반영되지 않는다 |
| 환경 변수 주입 | 해당 없음 | 반영되지 않는다 (재시작 필요) |



## 사례 1 — Pod 가 아예 만들어지지 않습니다

> 이 실패는 API 서버가 거절하는 단계라 컨테이너가 뜨지도 않습니다. 그래서 메시지가 가장 친절합니다.

설정값을 ConfigMap으로 만들어 Pod에 파일로 붙이려는데 생성 단계에서 막힙니다.

```yaml
apiVersion: v1
kind: ConfigMap
metadata:
  name: settings
  namespace: default
data:
  MODE: "dev"
  VERSION: "1.0"
```

```yaml
spec:
  containers:
  - name: app
    image: busybox:latest
    command: ["sleep", "3600"]
    volumeMounts:
    - name: config-volume
      mountPath: /etc/config
  volumes:
  - name: config-vol
    configMap:
      name: settings
```

```bash
Error from server (Invalid): error when creating "config-pod.yaml":
Pod "config-pod" is invalid: spec.containers[0].volumeMounts[0].name: Not found: "config-volume"
```

에러가 필드 경로까지 찍어 줍니다. `volumeMounts[0].name`이 참조하는 `config-volume`을 찾을 수 없다는 뜻입니다.

매니페스트를 보면 `volumeMounts`는 `config-volume`을 부르는데 `volumes`는 `config-vol`로 정의돼 있습니다. 두 이름은 Pod 안에서 볼륨을 잇는 유일한 연결 고리라 한 글자만 달라도 끊깁니다.

ConfigMap 자체는 문제가 없다는 점도 확인해 둡니다. `settings`는 실제로 존재하고 데이터도 들어 있습니다. 실패한 것은 ConfigMap을 찾는 단계가 아니라 Pod 안에서 볼륨을 참조하는 단계입니다.

이 사례가 가장 다루기 쉬운 이유는 실패 시점이 이르기 때문입니다. API 서버가 검증 단계에서 거절하므로 클러스터에 아무것도 만들어지지 않고, 메시지가 고칠 곳을 그대로 지목합니다.

### 조치

```bash
# volumes.name 을 volumeMounts.name 과 같은 값으로 맞춘 뒤 적용
kubectl apply -f config-pod.yaml

# 마운트 결과를 컨테이너 안에서 확인
kubectl exec config-pod -- ls /etc/config
kubectl exec config-pod -- cat /etc/config/MODE
```

```bash
# 배포 전에 서버 검증만 돌려 본다
kubectl apply -f config-pod.yaml --dry-run=server
```

`--dry-run=server`는 실제로 만들지 않고 API 서버의 검증만 통과시켜 봅니다. 이 사례 같은 참조 오류는 여기서 전부 걸립니다.

이름 불일치는 복사해 붙여 쓰는 과정에서 자주 생깁니다. 볼륨 이름을 짧게 짓고 매니페스트 안에서 두 번 등장한다는 사실을 의식하면 실수가 줄어듭니다.



## 사례 2 — 설정을 넣었더니 원래 파일이 사라졌습니다

> 디렉터리 마운트는 그 경로를 통째로 대체합니다. 파일을 더하려던 의도가 파일을 지우는 결과가 됩니다.

`/config` 디렉터리에 설정 파일을 추가하려고 ConfigMap을 붙였는데 그 뒤로 Pod가 시작되지 않습니다.

```bash
NAME                      READY   STATUS             RESTARTS      AGE
webapp-5d8f9b7c6-k3m2n    0/1     CrashLoopBackOff   4 (20s ago)   3m
```

```bash
2025-01-15T09:00:01Z [INFO]  Starting webapp v3.2.0...
2025-01-15T09:00:01Z [ERROR] Configuration file not found: /config/defaults.yaml
2025-01-15T09:00:01Z [FATAL] Cannot start without default configuration. Exiting.
```

```yaml
    volumeMounts:
    - name: extra-config
      mountPath: /config
  volumes:
  - name: extra-config
    configMap:
      name: webapp-extra
```

```yaml
data:
  override.yaml: |
    feature_flags:
      dark_mode: true
      beta_api: false
```

로그가 정확히 말해 줍니다. 애플리케이션이 `/config/defaults.yaml`을 찾는데 없습니다. 그런데 이 파일은 컨테이너 이미지에 들어 있던 것이라 원래는 있어야 합니다.

ConfigMap의 내용을 보면 `override.yaml` 하나뿐입니다. 그리고 마운트 경로는 `/config` 디렉터리 전체입니다. 그 디렉터리에 ConfigMap이 마운트되면서 이미지가 갖고 있던 `defaults.yaml`이 가려졌습니다.

의도와 결과가 정반대로 간 사례입니다. 파일을 하나 더하려던 설정이 원래 있던 파일을 전부 치웠습니다. 이름이 `extra-config`인 것도 의도가 추가였음을 보여 줍니다.

`kubectl exec`로 그 디렉터리를 열어 보면 바로 확인됩니다. 다만 Pod가 `CrashLoopBackOff`라 컨테이너 안으로 들어갈 수 없어, 매니페스트에서 먼저 원인을 추론해야 합니다.

### 조치

```yaml
# 디렉터리가 아니라 파일 하나만 붙인다
    volumeMounts:
    - name: extra-config
      mountPath: /config/override.yaml
      subPath: override.yaml
```

```bash
kubectl apply -f webapp-deployment.yaml
kubectl get pods -n prod

# 두 파일이 함께 있는지 확인
kubectl exec deploy/webapp -n prod -- ls /config/
```

`subPath`를 쓰면 원래 파일이 유지됩니다. 대신 그 파일은 ConfigMap이 바뀌어도 자동으로 갱신되지 않습니다. 다음 사례가 다루는 문제와 정확히 맞바꾸는 셈입니다.

둘 다 필요하면 마운트 지점을 바꾸는 방법이 있습니다. 빈 디렉터리를 새로 만들어 거기에 통째로 붙이고, 애플리케이션이 기본 설정과 추가 설정을 각각 다른 경로에서 읽게 구성하는 방식입니다.



## 사례 3 — 파일은 바뀌었는데 애플리케이션이 모릅니다

> 볼륨 갱신과 애플리케이션 반영은 다른 문제입니다. 쿠버네티스는 파일까지만 책임집니다.

ConfigMap 값을 바꿨는데 애플리케이션이 새 설정을 인식하지 못합니다. Pod를 재시작하지 않고 반영해야 하는 상황입니다.

```yaml
data:
  settings.conf: "debug=false"
```

```yaml
    volumeMounts:
    - name: config
      mountPath: /etc/config
  volumes:
  - name: config
    configMap:
      name: app-config
```

```bash
kubectl patch configmap app-config -p '{"data":{"settings.conf":"debug=true"}}'
```

```bash
# 2분 뒤 파일과 애플리케이션 상태
debug=true
{"debug": false}
```

마지막 두 줄이 이 사례의 핵심입니다. 파일 내용은 `debug=true`로 바뀌었는데 애플리케이션은 여전히 `false`를 보고합니다.

즉 쿠버네티스 쪽은 제 할 일을 했습니다. ConfigMap 볼륨은 kubelet이 주기적으로 동기화하므로 1~2분 안에 파일이 갱신되고, 실제로 갱신됐습니다.

멈춘 곳은 애플리케이션입니다. 대부분의 프로그램은 시작할 때 설정 파일을 한 번 읽어 메모리에 들고, 그 뒤로는 파일을 다시 보지 않습니다. 파일이 바뀌어도 다시 읽으라고 말해 주는 장치가 없으면 계속 옛 값으로 동작합니다.

여기서 확정할 수 없는 것도 있습니다. 이 애플리케이션에 리로드 엔드포인트나 파일 감시 기능이 있는지는 주어진 자료에 없으므로, 해결 방식은 그것이 있느냐에 따라 갈립니다.

### 조치

```bash
# 가장 단순한 방법 — 롤링 재시작으로 새로 읽게 한다
kubectl rollout restart deployment app
```

```yaml
# 앱이 리로드 엔드포인트를 제공한다면 감시 사이드카를 둔다
      - name: config-watcher
        image: busybox:1.36
        command: ["sh", "-c", "SUM=''; while true; do NEW=$(md5sum /etc/config/settings.conf | cut -d' ' -f1); [ \"$SUM\" != \"$NEW\" ] && { SUM=$NEW; wget -qO- --post-data='' http://127.0.0.1:80/-/reload || true; }; sleep 10; done"]
        volumeMounts:
        - name: config
          mountPath: /etc/config
```

무중단 반영이 꼭 필요한 것이 아니라면 롤링 재시작이 가장 단순합니다. 새 Pod가 뜨면서 갱신된 설정을 읽고, 기존 Pod는 그 뒤에 내려가므로 서비스도 끊기지 않습니다.

운영에서는 Reloader 같은 컨트롤러를 쓰는 방식이 흔합니다. ConfigMap이나 Secret이 바뀌면 참조하는 워크로드를 자동으로 롤링 업데이트해 줍니다.

핫 리로드가 진짜로 필요한 경우는 애플리케이션이 먼저 그 기능을 제공해야 합니다. 파일 감시든 리로드 엔드포인트든 재적용 경로가 없으면 사이드카를 붙여도 호출할 대상이 없습니다.



## 세 사례를 관통하는 것

> 세 사례의 난이도는 실패가 얼마나 시끄러운지에 반비례합니다. API 거절은 즉시 보이고, 덮어쓰기는 로그로 보이며, 미반영은 아무 데도 안 보입니다.

사례 1은 배포가 아예 안 되므로 놓칠 수 없습니다. 사례 2는 Pod가 죽어 알림에 걸립니다. 사례 3은 Pod도 정상이고 파일도 정상이라, 누군가 동작이 이상하다고 말하기 전까지 아무도 모릅니다.

이 순서는 그대로 대응 방식을 정합니다. 조용한 실패일수록 사후 발견이 아니라 사전 설계로 막아야 하고, 그래서 사례 3의 답이 "설정 변경 시 어떻게 반영되는가"를 배포 구조에 미리 정해 두는 것입니다.

마지막으로 세 사례 모두 마운트라는 한 가지 성질에서 나왔다는 점을 기억해 둡니다. 볼륨 이름으로 잇습니다. 경로를 통째로 대체하고 갱신은 파일까지만 책임집니다. 이 셋을 알면 새로 만나는 설정 주입 문제도 대개 같은 자리에서 갈립니다.
