# 자원 한계 — requests·limits와 OOMKilled

---

> `requests`가 없으면 축출 대상이 되고 `limits`가 낮으면 죽습니다. 두 값이 각각 다른 위험을 만들기 때문에 하나만 채우면 다른 쪽이 열립니다.

컨테이너가 정상적으로 떴는데도 사라지는 경우가 있습니다. 원인은 애플리케이션이 아니라 그 컨테이너에 준 자원 값입니다.

두 사례가 정반대의 실수를 보여 줍니다. 하나는 값을 아예 안 준 경우이고 다른 하나는 값을 너무 작게 준 경우입니다.



## requests 와 limits 는 서로 다른 일을 합니다

> `requests`는 스케줄러가 자리를 잡는 기준이고 `limits`는 커널이 강제하는 상한입니다. 이름이 비슷해서 자주 섞이지만 역할이 겹치지 않습니다.

두 값을 그냥 "자원 설정"으로 묶어 이해하면 왜 하나만 빠져도 문제가 되는지 설명되지 않습니다.

`requests`는 스케줄러에게 하는 예약입니다. 이 값을 근거로 노드에 자리가 있는지 판단하고, 노드가 압박을 받을 때 누구를 먼저 내보낼지도 이 값으로 정합니다. 값이 없으면 예약이 없는 셈이라 가장 먼저 밀려납니다.

`limits`는 kubelet이 cgroup에 새기는 상한입니다. 컨테이너가 이 선을 넘으면 커널이 개입합니다. CPU는 스로틀링으로 늦추고 메모리는 프로세스를 죽입니다.

| 빠진 것 | 무엇이 생기나 | 증상 |
|---------|---------------|------|
| `requests` 없음 | QoS 가 BestEffort 가 되어 축출 1순위 | `Evicted` (사례 1) |
| `limits` 가 실사용보다 낮음 | 커널 OOM Killer 가 프로세스를 종료 | `OOMKilled`, 종료 코드 137 (사례 2) |
| `requests` 없이 `limits` 만 | HPA 가 사용률을 계산할 기준을 잃음 | `<unknown>/50%` (다음 문서 사례 3) |



## 사례 1 — Pod 가 축출됐습니다

> `Evicted`는 컨테이너가 죽은 것이 아니라 kubelet 이 내보낸 것입니다. 누구를 먼저 내보낼지는 QoS 클래스가 정합니다.

운영 중인 Pod가 갑자기 `Evicted` 상태가 됩니다. 노드 메모리가 부족한 것으로 의심되지만 어느 Pod가 왜 선택됐는지 알 수 없습니다.

```bash
NAME           READY   STATUS    RESTARTS   AGE
resource-pod   0/1     Evicted   0          10m
```

```bash
Status:    Failed
Reason:    Evicted
Message:   The node was low on resource: memory.
QoS Class: BestEffort
```

```yaml
spec:
  containers:
  - name: app
    image: nginx:latest
    ports:
    - containerPort: 80
```

```bash
Conditions:
  Type               Status   Reason
  MemoryPressure     True     KubeletHasInsufficientMemory
  DiskPressure       False    KubeletHasNoDiskPressure

Allocated resources:
  Resource           Requests    Limits
  cpu                1800m (90%) 3200m (160%)
  memory             3.5Gi (87%) 5Gi (125%)
```

노드 조건의 `MemoryPressure: True`가 상황을 설명합니다. 노드에 메모리가 모자라 kubelet이 Pod를 내보내기 시작했습니다.

왜 하필 이 Pod가 선택됐는지는 `QoS Class: BestEffort`가 답합니다. 매니페스트에 `resources` 항목이 전혀 없어 이 Pod는 아무것도 예약하지 않은 상태이고, 쿠버네티스는 그런 Pod를 가장 먼저 내보냅니다.

노드 자원 표도 함께 읽어 둘 만합니다. limits 합계가 메모리 125%로 실제 용량을 넘습니다. 모든 컨테이너가 상한까지 쓰면 노드가 견딜 수 없는 구성이라, 압박은 예정된 것이었습니다.

QoS 클래스는 세 가지입니다. requests와 limits가 모두 같으면 Guaranteed, 일부만 있으면 Burstable, 아무것도 없으면 BestEffort이고 축출 순서는 그 역순입니다.

### 조치

```yaml
# 매니페스트에 requests 와 limits 를 함께 준다
    resources:
      requests:
        cpu: "100m"
        memory: "64Mi"
      limits:
        cpu: "200m"
        memory: "128Mi"
```

```bash
# 축출된 Pod 는 자동 복구되지 않으므로 정리 후 재배포한다
kubectl delete pod resource-pod
kubectl apply -f resource-pod.yaml

# QoS 클래스가 바뀌었는지 확인
kubectl describe pod resource-pod | grep "QoS Class"
```

값을 넣는 것보다 넣도록 강제하는 편이 낫습니다. 네임스페이스에 `LimitRange`를 두면 `resources`를 빠뜨린 Pod에 기본값이 자동으로 붙어 BestEffort가 만들어지지 않습니다.

노드 쪽 과할당도 별도로 봐야 합니다. limits 합계가 용량을 넘는 구성은 어느 한 Pod가 튀는 순간 다른 Pod가 축출되는 구조입니다.



## 사례 2 — 시작하자마자 OOMKilled 로 죽습니다

> 종료 코드 137 은 커널이 `SIGKILL`을 보냈다는 뜻입니다. 애플리케이션이 스스로 종료한 것이 아니므로 로그에는 마지막 말이 남지 않습니다.

메모리를 많이 쓰는 애플리케이션이 `CrashLoopBackOff`에 빠졌습니다. Pod가 시작되자마자 종료되기를 반복합니다.

```bash
NAME       READY   STATUS             RESTARTS      AGE
oom-demo   0/1     CrashLoopBackOff   5 (30s ago)   4m
```

```yaml
Containers:
  stress:
    Image:       polinux/stress
    Command:     ["stress", "--vm", "1", "--vm-bytes", "50M", "--timeout", "60"]
    Limits:
      memory:  20Mi
    Requests:
      memory:  10Mi
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
      Started:      Wed, 15 Jan 2025 10:25:00 +0000
      Finished:     Wed, 15 Jan 2025 10:25:01 +0000
```

`Last State`의 두 값이 원인을 확정합니다. `Reason: OOMKilled`와 종료 코드 137이 함께 나오면 더 볼 것이 없습니다. 137은 128에 시그널 번호 9를 더한 값이고, 즉 `SIGKILL`로 강제 종료됐다는 뜻입니다.

명령과 상한을 나란히 놓으면 산수가 맞지 않습니다. 컨테이너는 `--vm-bytes 50M`으로 50MB를 할당하려 하는데 `limits.memory`는 20Mi입니다. 할당이 상한을 넘는 순간 커널이 개입합니다.

앞 문서의 `CrashLoopBackOff` 사례와 여기서 갈리는 점이 있습니다. 애플리케이션이 스스로 종료한 경우에는 로그에 이유가 남지만, `SIGKILL`은 프로세스에 정리할 틈을 주지 않아 로그가 중간에서 끊깁니다. 그래서 로그가 아니라 `describe`의 종료 사유를 봐야 합니다.

시작 시각과 종료 시각의 차이가 1초라는 점도 단서입니다. 부팅 직후 죽는 패턴은 점진적 누수가 아니라 초기 할당이 상한을 넘는 형태입니다.

### 조치

```bash
# 종료 사유는 로그가 아니라 describe 에 있다
kubectl describe pod oom-demo -n apps | grep -A3 "Last State"

# 실사용을 담을 수 있게 상한을 올린다
kubectl edit pod oom-demo -n apps

kubectl delete pod oom-demo -n apps
kubectl apply -f oom-demo-pod.yaml

# 실제 사용량을 보면서 값이 맞는지 확인
kubectl top pod oom-demo -n apps
```

상한을 올리는 것이 늘 정답은 아닙니다. 애플리케이션이 실제로 그만큼 필요한지, 아니면 누수로 계속 자라는지를 먼저 갈라야 합니다. 시작 직후 죽으면 값이 작은 것이고, 몇 시간 뒤 죽으면 누수를 의심합니다.

값은 짐작이 아니라 측정으로 정합니다. 부하를 걸어 실제 사용량을 재고 그 위에 여유를 얹는 순서이며, `kubectl top`이나 메트릭 대시보드가 그 근거가 됩니다.



## 두 사례를 관통하는 것

> 두 사례는 같은 자원 설정의 양 끝입니다. 값을 안 주면 밖에서 밀려나고 너무 작게 주면 안에서 죽습니다.

축출과 OOMKill 은 결과가 비슷해 보이지만 같은 문제가 아닙니다. 둘은 주체가 다릅니다. 축출은 kubelet이 노드를 지키려고 Pod를 내보내는 것이고, OOMKill은 커널이 cgroup 상한을 지키려고 프로세스를 죽이는 것입니다. 전자는 노드 전체 상황이 원인이고 후자는 그 컨테이너 하나가 원인입니다.

증거가 있는 자리도 다릅니다. 축출은 Pod의 `Status`와 `Message`에, OOMKill은 `Last State`의 `Reason`과 종료 코드에 남습니다. 둘 다 `kubectl logs`로는 안 보이므로 `describe`를 먼저 여는 습관이 필요합니다.

두 사례가 함께 말하는 것은 자원 값을 짐작으로 채우지 말라는 것입니다. requests는 평소 사용량에서, limits는 최대 사용량에서 나와야 하고, 그 숫자는 측정에서 옵니다.
