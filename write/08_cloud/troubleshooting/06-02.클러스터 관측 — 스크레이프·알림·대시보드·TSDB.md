# 클러스터 관측 — 스크레이프·알림·대시보드·TSDB

---

> 관측 스택은 수집·저장·질의·알림 네 단계로 이어집니다. 어느 단계가 끊겨도 화면에는 똑같이 아무것도 안 나옵니다.

이 문서만 관측 스택 자체를 대상으로 삼습니다. 앞의 문서들이 워크로드를 다뤘다면 여기는 그 워크로드를 지켜보는 도구가 고장난 경우입니다.

관측 스택의 고장은 특히 위험합니다. 눈이 감긴 상태라는 것을 알려 줄 눈이 없기 때문입니다.



## 어느 단계에서 끊겼는지를 먼저 가릅니다

> 대시보드가 비었다는 사실만으로는 아무것도 모릅니다. 수집이 안 되는지, 저장이 안 되는지, 질의가 틀렸는지가 각각 다른 화면에서 갈립니다.

"모니터링이 안 된다"는 신고를 받으면 Grafana부터 열게 됩니다. 그런데 Grafana의 빈 화면은 네 단계 중 어디가 끊겨도 똑같이 나타납니다.

가르는 방법은 단계를 거슬러 올라가는 것입니다. Grafana가 비었으면 Prometheus에서 같은 질의를 직접 던져 보고, 거기서도 비었으면 Targets 페이지에서 수집 상태를 봅니다. 한 단계씩 내려갈 때마다 후보가 줄어듭니다.

알림은 별도 경로입니다. 메트릭이 정상이어도 라우팅이 어긋나면 알림만 조용히 사라집니다.

| 확인 지점 | 정상인데 다음이 비면 | 사례 |
|-----------|----------------------|------|
| Prometheus Targets | 수집 대상 설정이 문제 | 사례 1 |
| Prometheus 질의 화면 | 대시보드의 질의문이 문제 | 사례 3 |
| Alertmanager UI | 라우팅과 receiver 이름이 문제 | 사례 2 |
| TSDB 시계열 수 | 저장 계층 자체가 무너지는 중 | 사례 4 |



## 사례 1 — 타겟이 DOWN 이고 연결이 거부됩니다

> `connection refused` 는 그 주소에 아무도 안 듣는다는 뜻입니다. 스크레이프 주소가 어떻게 만들어졌는지를 봐야 합니다.

새로 배포한 서비스의 메트릭이 대시보드에 안 나옵니다. Targets 페이지에서 그 타겟이 DOWN입니다.

```bash
Endpoint                                    State   Error
http://10.244.1.15:8080/metrics             DOWN    Get "http://10.244.1.15:8080/metrics": dial tcp 10.244.1.15:8080: connect: connection refused
http://10.244.2.8:9090/metrics              UP
http://10.244.3.12:9090/metrics             UP
```

```yaml
Containers:
  payment:
    Ports:       8080/TCP (http), 9090/TCP (metrics)
    Ready:       True
Annotations:
  prometheus.io/scrape: "true"
  prometheus.io/port: "9090"
  prometheus.io/path: "/metrics"
```

```yaml
    relabel_configs:
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        target_label: __address__
        regex: (.+)
        replacement: ${1}
```

정상인 타겟들과 비교하면 차이가 바로 보입니다. UP인 것들은 9090번을 긁고 있는데 DOWN인 것만 8080번입니다.

Pod의 애노테이션은 메트릭 포트가 9090이라고 적어 두었습니다. 컨테이너도 두 포트를 열고 있고, 8080은 애플리케이션용이라 그쪽에는 `/metrics` 경로가 없습니다.

원인은 relabel 규칙입니다. 애노테이션의 포트 값을 `__address__`에 그대로 넣도록 돼 있는데, `__address__`는 호스트와 포트를 함께 담는 값입니다. 포트만 넣으면 주소가 제대로 만들어지지 않아 기본 컨테이너 포트가 그대로 쓰입니다.

올바른 형태는 기존 `__address__`에서 호스트 부분을 뽑고 애노테이션의 포트를 붙이는 것입니다. 두 값을 함께 읽어 조합해야 합니다.

### 조치

```bash
# 메트릭이 그 포트에서 실제로 나오는지 먼저 확인
kubectl exec -it payment-service-6b8f9c7d4-k2m5n -- curl -s http://localhost:9090/metrics | head -5
```

```yaml
# 주소와 포트를 함께 읽어 조합한다
      - source_labels: [__address__, __meta_kubernetes_pod_annotation_prometheus_io_port]
        action: replace
        target_label: __address__
        regex: ([^:]+)(?::\d+)?;(\d+)
        replacement: ${1}:${2}
```

```bash
curl -X POST http://prometheus:9090/-/reload
```

Targets 페이지가 진단의 출발점이라는 점을 기억해 둡니다. 어떤 주소를 긁으려 했고 무엇 때문에 실패했는지가 한 줄에 다 적혀 있어, 설정을 읽기 전에 결과부터 볼 수 있습니다.

relabel 규칙은 읽기 어려워서 팀 안에서 표준 패턴 하나를 정해 두고 복사해 쓰는 편이 안전합니다.



## 사례 2 — 알림은 발생했는데 Slack 에 안 옵니다

> `<no matching receiver>` 는 라우팅에서 갈 곳을 못 찾았다는 뜻입니다. 이름이 한 글자만 달라도 매칭되지 않습니다.

알림 규칙이 발동했고 Alertmanager UI에도 보이는데 Slack 채널에는 아무것도 오지 않습니다.

```bash
Alert: HighMemoryUsage
  severity: warning
  namespace: production
  summary: Memory usage is above 85%
  Status: active (not inhibited, not silenced)
  Receiver: <no matching receiver>
```

```yaml
  routes:
    - match:
        severity: critical
      receiver: "slack-critical"
    - match:
        severity: warning
      receiver: "slack_warning"

receivers:
  - name: "slack-critical"
  - name: "slack-warning"
```

UI가 원인을 그대로 적어 줍니다. `Receiver: <no matching receiver>`이므로 알림은 살아 있는데 보낼 곳이 정해지지 않았습니다.

`not inhibited, not silenced`도 함께 확인해 둡니다. 억제 규칙이나 무음 처리 때문이 아니라는 뜻이라 후보가 라우팅 하나로 좁혀집니다.

설정을 보면 `warning` 라우트가 `slack_warning`을 가리키는데 정의된 receiver 이름은 `slack-warning`입니다. 언더스코어와 하이픈 차이입니다.

`critical` 쪽은 이름이 맞아서 정상 동작한다는 점이 대비를 만듭니다. 심각한 알림만 오고 경고는 안 오는 상태라, 알림이 아예 안 오는 것보다 발견이 늦어집니다.

### 조치

```bash
# 이름을 맞춘 뒤 문법을 검사한다
amtool check-config alertmanager.yml

# 각 라벨 조합이 어느 receiver 로 가는지 직접 확인한다
amtool config routes test --config.file=alertmanager.yml severity=warning
amtool config routes test --config.file=alertmanager.yml severity=critical

curl -X POST http://alertmanager:9093/-/reload
```

`amtool check-config`만으로는 부족하다는 점이 이 사례의 교훈입니다. 문법은 맞으므로 통과하고, 이름이 안 맞는 것은 잡히지 않습니다.

`config routes test`가 그 빈틈을 메웁니다. 실제 라벨 값을 넣어 어느 receiver로 가는지 출력하므로, 배포 파이프라인에 넣어 두면 이 계열 실수가 사라집니다.



## 사례 3 — 패널 하나만 No data 입니다

> 다른 패널이 정상이면 데이터소스는 문제가 아닙니다. 그 패널의 질의문만 남습니다.

Grafana 대시보드에서 CPU 사용률 패널만 비어 있습니다. 다른 패널은 정상입니다.

```json
{
  "title": "CPU Usage by Pod",
  "datasource": "Prometheus-Production",
  "targets": [
    {
      "expr": "rate(container_cpu_usage_seconds[5m]) * 100",
      "legendFormat": "{{pod}}"
    }
  ]
}
```

```bash
# 쿼리: container_cpu_usage_seconds_total
결과: 142개 시계열 반환 (정상)

# 쿼리: rate(container_cpu_usage_seconds[5m])
결과: empty query result

# 쿼리: rate(container_cpu_usage_seconds_total[5m])
결과: 142개 시계열 반환 (정상)
```

```bash
Name: Prometheus-Production
URL: http://prometheus-server.monitoring.svc:9090
Status: "Data source is working"
```

세 번의 질의가 답을 확정해 줍니다. 접미사가 없는 이름은 빈 결과이고 `_total`이 붙은 이름은 142개를 돌려줍니다.

패널의 질의문을 보면 `container_cpu_usage_seconds`로 되어 있어 `_total`이 빠졌습니다. Prometheus는 존재하지 않는 메트릭에 대해 에러 대신 빈 결과를 돌려주므로, 화면에는 오타가 아니라 데이터 없음으로 보입니다.

이 접미사에는 규칙이 있습니다. 계속 증가하는 counter 타입 메트릭은 관례적으로 `_total`로 끝나고, `rate()`는 그런 counter에 쓰는 함수입니다. 함수와 이름이 짝을 이룬다는 점을 알면 실수를 줄일 수 있습니다.

다른 패널이 정상이라는 사실이 조사 범위를 좁혀 준 점도 기억해 둡니다. 데이터소스 연결과 시간 범위는 공유되는 설정이라 후보에서 빠집니다.

### 조치

```bash
# 존재하는 메트릭 이름을 먼저 확인한다
curl -s 'http://prometheus:9090/api/v1/label/__name__/values' | grep container_cpu
```

```json
{
  "expr": "rate(container_cpu_usage_seconds_total[5m]) * 100"
}
```

Grafana 질의 편집기의 Metrics Browser를 쓰면 존재하는 이름만 고를 수 있어 이 오타 자체가 생기지 않습니다. 손으로 적을 때만 생기는 실수입니다.

빈 결과와 에러를 구분해서 읽는 습관도 필요합니다. Prometheus는 없는 메트릭에 에러를 내지 않으므로, "No data"를 볼 때마다 이름부터 확인하는 것이 빠릅니다.



## 사례 4 — Prometheus 가 메모리를 늘려도 계속 죽습니다

> 한도를 두 배로 늘렸는데 여전히 죽는다면 한도 문제가 아닙니다. 늘어나는 쪽을 찾아야 합니다.

Prometheus 가 OOMKilled 로 반복 재시작합니다. 메모리 제한을 4Gi 에서 8Gi 로 늘렸는데도 증상이 바뀌지 않습니다.

```yaml
    Limits:
      memory: 8Gi
    Last State:  Terminated
      Reason:    OOMKilled
      Exit Code: 137
    Restart Count: 7
```

```bash
prometheus_tsdb_head_series:             2,847,531
prometheus_tsdb_head_series (1주 전):      312,408
prometheus_tsdb_head_chunks:             8,542,593
prometheus_tsdb_compactions_failed_total: 3
```

```bash
Top 10 label names with highest cumulative label value count:
  request_id         2,104,832
  trace_id             421,506
  pod                    1,247
  namespace                 12

Top 10 series count by metric name:
  http_request_duration_seconds_bucket    1,892,416
  http_request_duration_seconds_count       214,773
  node_cpu_seconds_total                        128
```

```bash
commit a3f2e1d (3일 전)
Message: feat: add distributed tracing labels to HTTP metrics
  - Added request_id and trace_id labels to http_request_duration histogram
```

한도를 늘렸는데도 죽는다는 사실이 첫 단서입니다. 필요한 양이 고정돼 있다면 8Gi로 해결됐어야 하므로, 필요한 양 자체가 계속 늘고 있다는 뜻입니다.

TSDB 지표가 그것을 확인해 줍니다. head series가 일주일 만에 31만에서 285만으로 아홉 배가 됐습니다. Prometheus는 활성 시계열의 최신 데이터를 메모리에 들고 있으므로 이 숫자가 곧 메모리 사용량입니다.

카디널리티 분석이 원인을 지목합니다. `request_id` 라벨 하나가 210만 개의 고유 값을 갖고 있습니다. 요청마다 다른 값이라 요청이 올 때마다 새 시계열이 생깁니다.

커밋 이력이 마지막 조각을 채웁니다. 사흘 전에 HTTP 메트릭에 `request_id`와 `trace_id`를 라벨로 추가했습니다. 히스토그램은 버킷 수만큼 시계열이 곱해지므로 증가가 특히 가파릅니다.

### 조치

```yaml
# 긴급 — 문제 메트릭의 수집을 끊어 메모리를 회수한다
    metric_relabel_configs:
      - source_labels: [__name__]
        regex: "http_request_duration_seconds_(bucket|count|sum)"
        action: drop
```

```bash
curl -X POST http://prometheus:9090/-/reload

# 시계열 수가 줄어드는지 확인
curl -s http://prometheus:9090/api/v1/status/tsdb | python3 -m json.tool
```

근본 수정은 애플리케이션 쪽입니다. `request_id`와 `trace_id`는 요청마다 고유한 값이라 메트릭 라벨로는 쓸 수 없습니다. 이런 식별자는 트레이싱 시스템이 다루도록 설계된 데이터입니다.

메트릭과 트레이스의 역할 구분이 여기서 드러납니다. 메트릭은 집계된 수치를 시간축으로 보는 것이라 라벨 값의 종류가 적어야 하고, 개별 요청을 따라가는 일은 트레이스의 몫입니다.

예방은 알림으로 합니다. `prometheus_tsdb_head_series`에 임계값을 걸어 두면 시계열이 급증할 때 OOM보다 먼저 알 수 있습니다. 라벨 하나를 잘못 추가한 배포는 몇 시간 안에 표가 나므로 조기 경보가 잘 통합니다.



## 네 사례를 관통하는 것

> 관측 스택의 고장은 스스로를 알리지 못합니다. 그래서 이 스택에는 스택 자신을 감시하는 지표가 따로 필요합니다.

네 사례 모두 화면에는 "데이터 없음"이나 "알림 없음"으로 나타났습니다. 그런데 원인은 수집 주소, 라우팅 이름, 질의문, 저장 계층으로 전부 달랐습니다. 증상이 같고 원인이 다르면 단계별로 거슬러 올라가는 방법밖에 없습니다.

사전 검증 도구가 단계마다 있다는 점도 반복됩니다. Targets 페이지, `amtool config routes test`, 메트릭 이름 API, TSDB 상태 API가 각각 그 자리입니다. 넷 다 사람이 화면을 보기 전에 기계가 확인할 수 있는 것들입니다.

마지막으로 사례 4가 남기는 원칙을 따로 적어 둡니다. 고유 식별자를 메트릭 라벨에 넣지 않는다는 것 하나가, 관측 스택을 무너뜨리는 가장 흔한 사고를 막습니다.
