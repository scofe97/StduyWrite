# 배치 워크로드 — Job·CronJob·네임스페이스

---

> 배치 작업의 실패는 조용합니다. 사용자 요청 경로에 없어서 아무도 즉시 알아채지 못하고, 안 도는 것과 실패하는 것도 겉으로는 구분되지 않습니다.

세 사례를 배치 관점으로 묶었습니다. 배포가 아예 안 되는 경우, 실행됐지만 실패로 끝나는 경우, 실행 자체가 시작되지 않는 경우입니다.

셋 다 상시 서비스였다면 몇 분 안에 드러났을 문제입니다. 배치라서 며칠 뒤에 "그러고 보니 그거 안 돌았네"로 발견됩니다.



## 배치는 실패가 드러나는 자리가 다릅니다

> Deployment 는 Pod 목록에서 상태가 보이지만, Job 은 완료 수로, CronJob 은 마지막 실행 시각으로 봅니다. 볼 열이 다릅니다.

배치 워크로드를 Deployment 보듯 보면 놓치는 것이 생깁니다. Job은 끝나는 것이 정상이라 Pod가 사라져 있는 것이 문제가 아니고, CronJob은 평소에 아무 Pod도 없는 것이 정상입니다.

그래서 확인할 열이 리소스마다 다릅니다. Job은 `COMPLETIONS`가 목표에 닿았는지를 보고, CronJob은 `LAST SCHEDULE`이 언제였는지를 봅니다. 이 값이 `<none>`이면 한 번도 안 돌았다는 뜻입니다.

배치의 또 다른 특징은 오래 안 도는 상태가 알림에 잘 안 걸린다는 점입니다. 실패는 이벤트로 남지만 실행되지 않은 것은 아무 이벤트도 만들지 않습니다.

| 리소스 | 정상인지 보는 열 | 이상 신호 |
|--------|------------------|-----------|
| Job | `COMPLETIONS` | `0/1` 이 계속 유지된다 |
| CronJob | `LAST SCHEDULE` | `<none>` 이거나 예상보다 오래됐다 |
| CronJob | `SUSPEND` | `True` 면 의도적으로 멈춰 있다 |



## 사례 1 — 네임스페이스가 없어 배포가 거절됐습니다

> 리소스는 네임스페이스 안에 만들어지고, 그 네임스페이스는 미리 있어야 합니다. 매니페스트가 스스로 만들어 주지 않습니다.

신규 프로젝트를 배포하려는데 `kubectl apply`가 에러를 내고 아무것도 만들어지지 않습니다.

```bash
Error from server (NotFound): error when creating "app-deployment.yaml": namespaces "playground" not found
```

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: sample-app
  namespace: playground
```

```bash
NAME              STATUS   AGE
default           Active   30d
kube-system       Active   30d
kube-public       Active   30d
kube-node-lease   Active   30d
```

에러가 그대로 답입니다. 매니페스트가 `playground` 네임스페이스를 지정했는데 클러스터에는 그 이름이 없습니다.

네임스페이스는 다른 리소스를 담는 그릇이라 먼저 존재해야 합니다. Deployment 매니페스트에 이름만 적는다고 자동으로 만들어지지 않습니다.

이 사례가 배치 문서에 들어간 이유가 있습니다. 새 배치 작업을 전용 네임스페이스에 두는 구성이 흔하고, 그 네임스페이스를 매니페스트 묶음에 넣지 않으면 첫 배포에서 정확히 이 에러를 만납니다.

### 조치

```bash
# 네임스페이스를 먼저 만든다
kubectl create namespace playground
kubectl get namespace playground

kubectl apply -f app-deployment.yaml
kubectl get pods -n playground
```

```yaml
# 매니페스트 묶음에 네임스페이스도 함께 넣어 둔다
apiVersion: v1
kind: Namespace
metadata:
  name: playground
```

명령으로 만들고 넘어가면 다음 환경에서 같은 일이 반복됩니다. 네임스페이스 정의를 매니페스트에 포함시키면 클러스터를 새로 만들 때도 한 번에 적용됩니다.

Helm을 쓴다면 `--create-namespace` 옵션이 같은 일을 합니다. 어느 쪽이든 네임스페이스가 배포 단위 안에 들어 있어야 한다는 점은 같습니다.



## 사례 2 — Job 이 반복 실패하고 완료되지 않습니다

> Job 의 성공 여부는 종료 코드로 정해집니다. 로그가 정상으로 보여도 마지막 종료 코드가 0 이 아니면 실패입니다.

배치 작업을 Job으로 띄웠는데 Pod가 `Error`로 반복 실패하고 Job이 끝나지 않습니다.

```bash
NAME       COMPLETIONS   DURATION   AGE
fail-job   0/1           2m         2m
```

```bash
NAME             READY   STATUS   RESTARTS   AGE
fail-job-7x2kp   0/1     Error    0          2m
fail-job-r9m4d   0/1     Error    0          90s
```

```yaml
spec:
  backoffLimit: 1
  template:
    spec:
      restartPolicy: Never
      containers:
      - name: worker
        image: busybox
        command: ["sh", "-c", "echo 'Processing...'; exit 1"]
```

```bash
Processing...
```

로그만 보면 이상한 것이 없습니다. `Processing...`이 정상적으로 찍혔고 에러 메시지도 없습니다.

원인은 명령의 마지막에 있습니다. `exit 1`이 붙어 있어 컨테이너가 항상 비정상 종료 코드로 끝납니다. 쿠버네티스는 Job의 성공을 종료 코드 0으로 판정하므로 이 Pod는 매번 실패로 기록됩니다.

Pod가 두 개인 것도 설명됩니다. `restartPolicy: Never`라 컨테이너를 재시작하는 대신 새 Pod를 만들고, `backoffLimit: 1`이라 재시도가 한 번으로 끝나 총 두 개가 남았습니다.

이 조합을 이해해 두면 Job의 실패 패턴을 읽기 쉬워집니다. `Never`는 Pod를 새로 만들고 `OnFailure`는 같은 Pod 안에서 컨테이너를 다시 띄우며, `backoffLimit`이 그 시도의 총 횟수를 정합니다.

### 조치

```bash
# 실패한 Pod 의 로그로 마지막 동작을 확인
kubectl logs fail-job-7x2kp -n batch

# 명령이 성공 시 0 으로 끝나도록 고친 뒤 Job 을 다시 만든다
kubectl delete job fail-job -n batch
kubectl apply -f fail-job.yaml

kubectl get jobs -n batch
```

Job은 한 번 만들어지면 스펙을 대부분 바꿀 수 없어 지우고 다시 만들어야 합니다. Deployment처럼 `edit`으로 고쳐지지 않는다는 점이 처음에는 낯섭니다.

스크립트를 호출하는 Job이라면 그 안에서 종료 코드를 관리하는 것이 중요합니다. 파이프로 이은 명령은 마지막 명령의 코드만 반환하므로, 중간 실패를 잡으려면 `set -o pipefail` 같은 장치가 필요합니다.



## 사례 3 — CronJob 이 한 번도 실행되지 않았습니다

> `LAST SCHEDULE` 이 `<none>` 이면 실패한 것이 아니라 시작조차 안 한 것입니다. 실패와 미실행은 조사할 곳이 다릅니다.

매분 임시 파일을 정리해야 할 CronJob이 배포 후 5분이 지나도 한 번도 실행되지 않았습니다.

```bash
NAME      SCHEDULE      SUSPEND   ACTIVE   LAST SCHEDULE   AGE
cleanup   0 0 1 1 *     False     0        <none>          5m
```

```bash
No resources found in ops namespace.
```

```yaml
spec:
  schedule: "0 0 1 1 *"
  jobTemplate:
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
          - name: cleaner
            image: busybox
            command: ["sh", "-c", "echo 'Cleaning temp files...' && rm -rf /tmp/cache/*"]
```

`LAST SCHEDULE`이 `<none>`이고 Job 목록도 비어 있습니다. 실행됐다가 실패한 것이 아니라 아예 시작되지 않았다는 뜻이라, 컨테이너나 이미지 쪽은 볼 필요가 없습니다.

`SUSPEND`가 `False`이므로 의도적으로 멈춘 것도 아닙니다. 남은 것은 스케줄뿐입니다.

`0 0 1 1 *`을 필드 순서대로 읽으면 분 0, 시 0, 일 1, 월 1, 요일 무관입니다. 즉 매년 1월 1일 자정에 한 번 도는 설정입니다. 매분 실행하려면 다섯 필드가 모두 `*`여야 합니다.

숫자 0과 1이 섞여 있어 언뜻 "매분"처럼 보인다는 점이 이 실수를 부릅니다. cron 표현식은 각 자리가 무엇을 뜻하는지 기억에 의존하지 말고 검증 도구로 확인하는 편이 안전합니다.

### 조치

```yaml
spec:
  schedule: "* * * * *"
  timeZone: "Asia/Seoul"
```

```bash
kubectl apply -f cleanup-cronjob.yaml

# 1분 정도 기다리며 LAST SCHEDULE 이 채워지는지 본다
kubectl get cronjob -n ops -w
kubectl get jobs -n ops
```

`timeZone`을 함께 명시하면 클러스터 시간대에 의존하지 않아 예상 시각이 분명해집니다. 이번 장애의 직접 원인은 아니지만, 시간대가 다른 환경으로 옮길 때 같은 표현식이 다른 시각에 도는 문제를 미리 막습니다.

이력 보존 개수도 함께 정해 둡니다. 매분 도는 CronJob은 완료된 Job이 빠르게 쌓이므로 `successfulJobsHistoryLimit`을 조정하지 않으면 목록이 금세 지저분해집니다.



## 세 사례를 관통하는 것

> 배치의 실패는 사람이 보러 가지 않으면 드러나지 않습니다. 세 사례 모두 며칠 뒤에 발견돼도 이상하지 않은 형태였습니다.

사례 1은 배포 시점에 에러가 나므로 그나마 즉시 보입니다. 사례 2는 Job이 실패 상태로 남지만 아무도 조회하지 않으면 그대로이고, 사례 3은 리소스가 아예 만들어지지 않아 목록에 흔적도 없습니다.

그래서 배치에는 감시 대상이 하나 더 필요합니다. 실패 알림뿐 아니라 "정해진 시간 안에 성공한 실행이 있었는가"를 함께 봐야 합니다. 앞의 것은 실패를 잡고 뒤의 것은 미실행을 잡습니다.

마지막으로 세 사례의 잘못된 값이 전부 짧은 문자열이었다는 점을 기억해 둡니다. 네임스페이스 이름, 종료 코드, cron 표현식입니다. 배포 전에 한 번 검증하는 비용이 며칠 뒤 발견하는 비용보다 훨씬 쌉니다.
