# 권한과 격리 — RBAC·NetworkPolicy·TLS·nonroot

---

> 보안 설정을 조인 뒤 무언가 안 되기 시작했다면 대개 조인 것이 정확히 그것을 막고 있습니다. 문제는 무엇을 막았는지가 로그마다 다른 말로 적혀 있다는 점입니다.

다섯 사례를 보안 관점으로 묶었습니다. API 호출 권한, 네트워크 접근, 인증서 발급, 실행 사용자가 각각 다른 층에서 접근을 통제합니다.

공통점은 하나입니다. 다섯 모두 "기본은 거절"이라는 규칙 위에서 필요한 것만 열어 주는 구조이고, 그 열어 주는 선언이 빠지거나 어긋나서 생긴 문제입니다.



## 무엇이 거절했는지가 층을 알려 줍니다

> `forbidden`은 API 서버가, 타임아웃은 네트워크 정책이, `CreateContainerConfigError`는 kubelet 이 막은 것입니다. 거절의 주체가 다르면 볼 곳도 다릅니다.

보안 설정을 적용한 뒤 문제가 생기면 무엇이 막았는지부터 정해야 합니다. RBAC과 NetworkPolicy와 `securityContext`는 서로 다른 층이라 조사 방향이 갈립니다.

다행히 각 층은 자기만의 표현을 씁니다. API 서버는 `forbidden`이라는 단어와 함께 어떤 주체가 어떤 동작을 어떤 자원에 하려 했는지를 전부 적어 줍니다. 네트워크 정책은 거절 메시지를 안 주고 그냥 응답이 없습니다. kubelet은 컨테이너를 만들기 전에 막고 그 이유를 이벤트에 남깁니다.

| 막은 주체 | 나타나는 형태 | 볼 곳 | 사례 |
|-----------|---------------|-------|------|
| API 서버 (RBAC) | `... is forbidden: User "system:serviceaccount:..."` | Role 과 RoleBinding | 사례 1, 2 |
| CNI (NetworkPolicy) | 응답 없음, 타임아웃 | `kubectl get networkpolicy` | 사례 3 |
| cert-manager | 리소스가 `Ready: False` | 발급 체인의 각 단계 | 사례 4 |
| kubelet (securityContext) | `CreateContainerConfigError` | 이미지의 기본 사용자 | 사례 5 |



## 사례 1 — ServiceAccount 를 만들었는데 권한이 없습니다

> ServiceAccount 는 신원일 뿐 권한이 아닙니다. Role 과 RoleBinding 이 없으면 아무것도 할 수 없습니다.

모니터링 앱이 Pod 목록을 조회해야 하는데 권한 에러가 납니다. 전용 ServiceAccount는 만들어 두었습니다.

```bash
2025-01-15T10:00:01Z [ERROR] Failed to list pods: pods is forbidden: User "system:serviceaccount:demo:reader-sa" cannot list resource "pods" in API group "" in the namespace "demo"
```

```bash
NAME        SECRETS   AGE
default     0         5d
reader-sa   0         1h
```

```bash
No resources found in demo namespace.
```

에러 메시지가 필요한 정보를 다 담고 있습니다. 주체는 `demo` 네임스페이스의 `reader-sa` 이고 하려던 동작은 `list` 입니다. 대상은 코어 API 그룹의 `pods` 입니다.

세 번째 출력이 원인을 확정합니다. 그 네임스페이스에 Role도 RoleBinding도 없습니다.

여기서 알아 둘 것은 ServiceAccount의 성격입니다. 이것은 워크로드에 붙는 신원이지 권한 묶음이 아닙니다. 만들어 놓기만 하면 아무 자원에도 접근할 수 없고, Role이 권한을 정의하고 RoleBinding이 그 둘을 이어야 비로소 동작합니다.

### 조치

```bash
# 권한을 정의하고
kubectl create role pod-reader -n demo --verb=get,list,watch --resource=pods

# 신원에 연결한다
kubectl create rolebinding pod-reader-binding -n demo \
  --role=pod-reader --serviceaccount=demo:reader-sa

# 실제로 되는지 그 신원으로 물어본다
kubectl auth can-i list pods -n demo --as=system:serviceaccount:demo:reader-sa
```

`kubectl auth can-i --as=`는 배포 전에 권한을 확인하는 가장 빠른 방법입니다. 애플리케이션을 띄워 에러를 보는 것보다 훨씬 짧은 순환입니다.

권한은 필요한 만큼만 줍니다. 급하다고 `cluster-admin`을 붙이면 그 임시 조치가 그대로 남아 다음 감사에서 문제가 됩니다.



## 사례 2 — Role 은 있는데 여전히 거절당합니다

> `get`과 `list`는 별개의 권한입니다. `kubectl get pods` 는 목록 조회라 `list` 를 씁니다.

Job이 API를 호출해 Pod 목록을 가져와야 하는데 권한 에러로 실패합니다. RBAC 설정은 되어 있다고 합니다.

```bash
Connecting to Kubernetes API...
Error: pods is forbidden: User "system:serviceaccount:ops:loader-sa" cannot list resource "pods" in API group "" in the namespace "ops"
```

```bash
NAME                         CREATED AT
role.rbac.authorization.k8s.io/loader-role   2025-01-15T08:00:00Z

NAME                                   ROLE                AGE
rolebinding.rbac.authorization.k8s.io/loader-binding   Role/loader-role   30m
```

```yaml
rules:
- apiGroups: [""]
  resources: ["pods"]
  verbs: ["get"]
```

```yaml
      containers:
      - name: loader
        image: bitnami/kubectl:latest
        command: ["kubectl", "get", "pods", "-n", "ops"]
```

앞 사례와 달리 Role과 RoleBinding이 둘 다 있습니다. 연결도 제대로 돼 있어 얼핏 문제가 없어 보입니다.

에러 문장과 Role의 `verbs`를 나란히 놓으면 어긋난 곳이 드러납니다. 에러는 `cannot list`인데 Role은 `["get"]`만 허용합니다.

이 구분이 헷갈리는 이유는 명령 이름 때문입니다. `kubectl get pods`라고 치지만 이름을 지정하지 않았으므로 실제로는 목록 조회이고, API 수준에서는 `list` 동사를 씁니다. 이름을 지정한 `kubectl get pod my-pod`가 `get`입니다.

명령 이름과 API 동사가 다르다는 점만 알면 이 계열 실수가 사라집니다. 조회 권한을 줄 때 `get`·`list`·`watch` 셋을 묶어 주는 관행도 여기서 나왔습니다.

### 조치

```bash
# Role 에 list 를 더한다
kubectl patch role loader-role -n ops --type=json \
  -p='[{"op":"replace","path":"/rules/0/verbs","value":["get","list"]}]'

# Job 은 스펙을 바꿀 수 없으므로 지우고 다시 만든다
kubectl delete job data-loader -n ops
kubectl apply -f data-loader-job.yaml

kubectl logs job/data-loader -n ops
```

권한을 고친 뒤에도 Job이 자동으로 다시 돌지 않는다는 점을 기억해 둡니다. 이미 실패로 끝난 Job은 그대로 남고, 새로 만들어야 새 권한으로 실행됩니다.

배포 전 검증은 여기서도 같습니다. `kubectl auth can-i list pods --as=...`를 한 번 치면 이 사례는 클러스터까지 오지 않습니다.



## 사례 3 — 네임스페이스가 나뉘어 있는데 서로 다 보입니다

> 네임스페이스는 이름을 가르는 경계이지 네트워크 경계가 아닙니다. 트래픽을 막으려면 NetworkPolicy 가 따로 필요합니다.

두 팀이 네임스페이스로 나뉘어 클러스터를 공유하는데, 필요한 한 경로만 남기고 나머지를 막아야 합니다. 지금은 전부 열려 있습니다.

```bash
kubectl exec client -n team-a -- curl -s --max-time 3 api.team-b:8080
{"status": "ok"}

kubectl exec client -n team-a -- curl -s --max-time 3 web.team-b:80
<!DOCTYPE html><html>...

kubectl exec api -n team-b -- curl -s --max-time 3 client.team-a:80
{"status": "ok"}
```

```bash
No resources found
```

세 방향이 모두 통합니다. 네임스페이스로 나눴는데도 서로 자유롭게 오간다는 것이 이 상황의 핵심입니다.

네 번째 출력이 이유입니다. NetworkPolicy가 하나도 없습니다. 쿠버네티스의 기본은 모든 Pod가 서로 통신할 수 있는 것이고, 네임스페이스는 이름과 권한을 가르는 경계일 뿐 패킷을 막지 않습니다.

그래서 이 사례는 고장이 아니라 아직 안 만든 상태입니다. 원하는 상태를 만들려면 두 단계가 필요합니다. 먼저 전부 막고, 그다음 필요한 것만 엽니다.

순서가 반대면 위험합니다. 허용 정책만 먼저 넣으면 그 정책이 적용되지 않는 경로는 계속 열려 있고, 어디가 열려 있는지 파악하기 어려워집니다.

### 조치

```yaml
# 1단계 — 양쪽 네임스페이스를 기본 차단으로 만든다
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: default-deny
  namespace: team-a
spec:
  podSelector: {}
  policyTypes:
  - Ingress
  - Egress
```

```yaml
# 2단계 — team-a 에서 team-b 의 api:8080 만 연다
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata:
  name: allow-team-a-to-api
  namespace: team-b
spec:
  podSelector:
    matchLabels:
      app: api
  policyTypes:
  - Ingress
  ingress:
  - from:
    - namespaceSelector:
        matchLabels:
          kubernetes.io/metadata.name: team-a
    ports:
    - protocol: TCP
      port: 8080
```

```bash
# 열려야 할 것과 막혀야 할 것을 둘 다 확인한다
kubectl exec client -n team-a -- curl -s --max-time 3 api.team-b:8080
kubectl exec client -n team-a -- curl -s --max-time 3 web.team-b:80
```

egress를 막을 때 DNS를 함께 열어 주는 것을 빠뜨리기 쉽습니다. 이름 해석이 막히면 허용한 경로조차 주소를 못 찾아 실패하므로, `kube-system`의 53번 UDP를 예외로 두어야 합니다.

전제 조건도 확인해야 합니다. NetworkPolicy는 CNI 플러그인이 구현해야 실제로 동작하고, 지원하지 않는 CNI에서는 리소스가 만들어져도 아무것도 막지 않습니다. 정책을 넣은 뒤 막혀야 할 경로가 실제로 막혔는지 확인하는 단계가 그래서 필요합니다.



## 사례 4 — 인증서 체인 중간이 비어 있습니다

> cert-manager 의 발급은 사슬입니다. 한 고리가 없으면 그 뒤가 전부 `Ready: False` 로 멈춥니다.

내부 서비스 간 TLS를 위해 인증서를 발급하려는데 최종 인증서가 준비되지 않습니다.

```bash
NAME       READY   SECRET          AGE
ca-cert    True    ca-secret       10m
web-cert   False   web-cert-tls    5m
```

```bash
Events:
  Normal   Issuing            5m               cert-manager-certificates-trigger  Issuing certificate as Secret does not exist
  Warning  ErrIssuerNotReady  3m (x5 over 5m)  cert-manager-certificates-issuing  Referenced "Issuer" not ready: issuer.cert-manager.io "ca-issuer" not found
```

```bash
NAMESPACE    NAME                                             READY   AGE
             clusterissuer.cert-manager.io/selfsigned-issuer  True    10m
```

```yaml
spec:
  secretName: web-cert-tls
  issuerRef:
    name: ca-issuer
    kind: Issuer
  dnsNames:
  - web.preparesh.svc
```

`ca-cert`는 `True`인데 `web-cert`만 `False`라는 대비가 출발점입니다. 앞 단계는 성공했으므로 그 뒤에서 끊겼습니다.

이벤트가 정확히 지목합니다. `web-cert`가 참조하는 `ca-issuer`라는 Issuer를 찾을 수 없습니다. 목록을 보면 `selfsigned-issuer` 하나만 있고 `ca-issuer`는 만들어지지 않았습니다.

발급 체인의 구조를 알면 왜 이 고리가 필요한지 이해됩니다. 자체 서명 발급자가 CA 인증서를 만들고, 그 CA 인증서를 쓰는 Issuer를 따로 만들어야, 최종 인증서가 그 Issuer에게 서명을 받을 수 있습니다.

즉 CA 인증서가 있다는 것과 그것으로 서명해 줄 발급자가 있다는 것은 다른 이야기입니다. `ca-secret`은 만들어졌지만 그것을 쓰는 Issuer가 없어 아무도 서명해 주지 않습니다.

### 조치

```yaml
# 빠진 고리를 만든다 — ca-secret 을 CA 로 쓰는 Issuer
apiVersion: cert-manager.io/v1
kind: Issuer
metadata:
  name: ca-issuer
  namespace: preparesh
spec:
  ca:
    secretName: ca-secret
```

```bash
kubectl get issuer ca-issuer -n preparesh
kubectl get certificate web-cert -n preparesh -w
kubectl get secret web-cert-tls -n preparesh
```

Issuer가 준비되면 cert-manager가 자동으로 재시도하므로 인증서를 다시 만들 필요가 없습니다. `-w`로 지켜보면 `False`가 `True`로 바뀌는 것이 보입니다.

문제가 생기면 체인을 역순으로 짚는 것이 요령입니다. 최종 인증서에서 시작해 그것이 참조하는 Issuer, 그 Issuer가 쓰는 Secret, 그 Secret을 만든 인증서로 거슬러 올라가면 끊긴 고리가 나옵니다.



## 사례 5 — 이미지가 root 로 도는 바람에 정책에 걸립니다

> `runAsNonRoot: true` 는 root 로 뜨려는 컨테이너를 막습니다. 이미지의 기본 사용자가 무엇인지 확인하지 않으면 이 정책은 배포를 멈춥니다.

보안 정책으로 모든 Pod에 `runAsNonRoot: true`를 적용한 뒤 일부 워크로드가 시작되지 않습니다.

```bash
NAME                            READY   STATUS                       RESTARTS   AGE
nginx-proxy-7c9d8f6b5-k4m2n    0/1     CreateContainerConfigError   0          5m
app-backend-5a3f7d8c2-w2x4q    1/1     Running                      0          5m
```

```bash
Events:
  Normal   Pulled  5m                Successfully pulled image "nginx:1.25"
  Warning  Failed  3s (x12 over 5m)  Error: container has runAsNonRoot and image will run as root (container: nginx-proxy)
```

```yaml
      securityContext:
        runAsNonRoot: true
      containers:
      - name: nginx-proxy
        image: nginx:1.25
```

```yaml
      securityContext:
        runAsNonRoot: true
      containers:
      - name: backend
        image: registry.example.com/app-backend:v2.0
        securityContext:
          runAsUser: 1000
```

같은 정책 아래에서 한쪽은 뜨고 한쪽은 못 뜬다는 대비가 답을 줍니다. 정상인 쪽에는 컨테이너 수준의 `runAsUser: 1000`이 있고 실패한 쪽에는 없습니다.

`runAsNonRoot: true`는 실행 사용자를 정하는 설정이 아니라 검사입니다. 컨테이너가 UID 0으로 뜨려 하면 kubelet이 시작을 거절합니다. 실제 사용자를 정하는 것은 `runAsUser`이거나 이미지의 기본값입니다.

공식 nginx 이미지의 기본 사용자는 root입니다. 그래서 `runAsUser`를 명시하지 않으면 root로 뜨려 하고, 검사에 걸립니다.

상태가 `CreateContainerConfigError`라는 점도 읽어 둡니다. 컨테이너가 만들어지기 전에 막힌 것이라 로그가 아예 없고, 원인은 이벤트에만 있습니다.

### 조치

```yaml
# 방법 1 — 이미지 안에 있는 비특권 사용자를 지정한다
        securityContext:
          runAsUser: 101
          allowPrivilegeEscalation: false
```

```yaml
# 방법 2 — 애초에 비특권으로 만들어진 이미지를 쓴다
        image: nginxinc/nginx-unprivileged:1.25
```

```bash
kubectl rollout status deployment nginx-proxy
```

방법 1에는 함정이 하나 있습니다. 표준 nginx는 80번 포트를 여는데 1024 미만 포트는 특권이 필요하므로, 사용자만 바꾸면 이번에는 바인딩이 실패합니다. 컨테이너 포트를 8080처럼 높은 번호로 함께 바꿔야 합니다.

그래서 비특권 이미지를 쓰는 방법 2가 대개 더 깔끔합니다. 포트와 파일 권한이 처음부터 비특권 실행에 맞춰져 있습니다.

정책을 적용하기 전에 이미지들의 기본 사용자를 미리 확인해 두면 이 사고를 한 번에 예방할 수 있습니다. `docker inspect <이미지> --format='{{.Config.User}}'`가 비어 있으면 root입니다.



## 다섯 사례를 관통하는 것

> 보안 설정은 켜는 순간 무언가를 막습니다. 다섯 사례 모두 막힌 것이 의도한 것인지 아닌지를 확인하는 단계가 빠져 있었습니다.

RBAC 과 NetworkPolicy 와 `runAsNonRoot` 는 모두 열려 있던 것을 막는 장치라, 켠 뒤에 무엇이 막혔는지 확인하지 않으면 의도한 것만 막혔는지 알 수 없습니다. 그래서 정책을 넣은 뒤에는 두 가지를 함께 확인해야 합니다. 막혀야 할 것이 막혔는지와 통해야 할 것이 통하는지입니다. 앞만 확인하면 사례 3의 절반이고, 뒤만 확인하면 정책이 있으나 마나입니다.

사전 검증 도구가 층마다 있다는 점도 기억해 둡니다. RBAC은 `kubectl auth can-i`, 이미지 사용자는 `docker inspect`, 네트워크 정책은 실제 요청 두 번입니다. 셋 다 배포 전에 몇 초면 끝납니다.

마지막으로 다섯 사례의 에러 메시지가 전부 원인을 명시했다는 점을 짚어 둡니다. 어떤 주체가 어떤 동작을 어떤 대상에 하려다 막혔는지가 문장에 들어 있습니다. 보안 계층은 다른 어느 층보다 진단 메시지가 친절한 편입니다.
