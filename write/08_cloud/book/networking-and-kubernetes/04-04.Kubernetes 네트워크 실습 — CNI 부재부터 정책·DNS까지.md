# Kubernetes 네트워크 실습 — CNI 부재부터 정책·DNS까지

---

## 핵심 요약
> 이 편이 매달린 하나의 생각은 4장에서 읽은 것들이 실제로 어느 파일과 어느 규칙 줄에 있는지 손으로 확인한다는 것입니다.

CNI 가 없는 노드가 멈추는 장면에서 출발해 주소 조각, 서비스 규칙 11줄, readiness 를 잃은 Pod 의 줄이 사라지는 자리를 차례로 확인합니다.

정책은 Pod 를 고르는 순간 그 방향을 잠급니다. 이름 하나는 검색 경로 때문에 질의 2~8개로 불어납니다. Cilium L7 정책은 응답 코드로 어디서 멈췄는지를 드러냅니다. 노드 밖에서 Pod 로 가는 길은 경로 한 줄로 열리지만 나가는 쪽은 여전히 노드 주소로 바뀝니다.



## 학습 목표
> 읽어서 아는 것과 규칙 줄에서 찾아내는 것 사이의 거리를 좁히는 것이 목표입니다.

1. CNI 가 없는 클러스터의 증상을 노드와 Pod 상태로 판별할 수 있습니다.
2. 클러스터 전체 대역이 노드별 조각으로 잘려 내려온 자리를 명령으로 짚을 수 있습니다.
3. 서비스 하나가 만드는 체인 셋을 실제 규칙에서 찾아 읽을 수 있습니다.
4. readiness 실패가 규칙 줄을 지우는 것과 그 Pod 의 나가는 길이 살아 있는 것을 동시에 확인할 수 있습니다.
5. 정책이 선택되는 순간 무엇이 함께 끊기는지, 어느 Pod 가 영향을 안 받는지를 실측할 수 있습니다.
6. 이름 하나가 검색 경로 때문에 질의 몇 개로 불어나는지 세고, 끝의 점 하나로 줄일 수 있습니다.
7. Cilium L7 정책이 만드는 응답 서명 셋(`200`·`403`·`000`)으로 어디서 막혔는지 가를 수 있습니다.
8. 노드 밖에서 Pod 로 가는 길이 경로 한 줄로 열리는 것과, 나가는 쪽이 노드 주소로 바뀌는 것을 방향별로 나눠 설명할 수 있습니다.

아래 지도는 여덟 묶음을 네 구역으로 나눠 왼쪽에서 오른쪽으로 읽습니다. 노드와 주소 구역에서는 CNI 가 없는 노드가 멈추는 장면과 대역이 조각으로 내려오는 자리를 봅니다. 서비스 구역에서는 규칙 줄 열한 개와 readiness 를 잃은 Pod 의 줄이 사라지는 장면을 봅니다. 정책과 이름 구역에서는 선택되는 순간의 잠금, 이름 하나의 질의 횟수, 경로까지 보는 L7 정책을 봅니다. 마지막 구역은 노드 밖에서 Pod 로 가는 길입니다.

> ⚠️ 사내 클러스터에서는 만들지 않습니다. 이 문서의 명령은 전부 로컬 KIND 클러스터를 대상으로 합니다. 이 폴더는 공개 배포되므로 사내 주소나 이름을 적지 않습니다.

## CNI 없는 클러스터

> 읽어서 아는 "CNI 없으면 네트워크 없음"을 눈으로 봅니다. 관리형 클러스터는 이미 깔린 채로 오기 때문에 이 장면을 볼 일이 없습니다.

### 풀려는 문제

[04-02](./04-02.CNI%EC%99%80%20kube-proxy%20%E2%80%94%20Pod%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC%EC%9D%98%20%EB%B0%B0%EC%84%A0%EA%B3%B5%EA%B3%BC%20%EB%A1%9C%EB%93%9C%EB%B0%B8%EB%9F%B0%EC%84%9C.md) 의 「CNI 명세는 연산 여섯과 JSON 두 줄기뿐」 에서 Kubernetes 는 CNI 플러그인을 싣고 오지 않는다고 읽었습니다. 그 문장이 실제로 어떤 증상으로 나타나는지는 없는 상태를 만들어 봐야 압니다.

### 클러스터 만들기

```yaml
apiVersion: kind.x-k8s.io/v1alpha4

  - role: control-plane
  - role: worker
  - role: worker
networking:
  disableDefaultCNI: true    # 기본 CNI 를 꺼야 Cilium 을 올릴 수 있다
```

```bash
kind create cluster --name k8s-net --config kind-config.yaml
kubectl config use-context kind-k8s-net

kubectl -n kube-system get pods
```

### Cilium 올리기

`ipam.mode=kubernetes` 는 Cilium 의 KIND 설치 안내가 `image.pullPolicy` 와 함께 주는 옵션입니다.[^ipam] 빼면 Cilium 이 자기 주소 풀에서 Pod 주소를 내줘서 노드의 `podCIDR` 밖 주소가 나옵니다. 그 결과는 「주소 재고가 내려온 자리」 묶음에서 봅니다.

### 확인된 것

CNI 가 없을 때의 증상은 통신 실패가 아닙니다. 노드 셋이 `NotReady` 인 것은 노드끼리 못 닿아서가 아니라 kubelet 이 네트워크가 준비되지 않았다고 보고했기 때문입니다. 노드 컨디션의 `NetworkReady=false` 와 `cni plugin not initialized` 가 그 보고입니다.

Pod 가 뜨느냐를 가르는 기준은 자기 IP 가 필요한가 하나입니다. `hostNetwork` 인 `etcd`·`kube-apiserver`·`kube-controller-manager`·`kube-scheduler`·`kube-proxy` 는 CNI 없이도 뜹니다. `CoreDNS` 만 Pod IP 를 받아야 해서 걸립니다.

걸린 모양은 `ContainerCreating` 이 아니라 `Pending` 입니다. 노드가 `NotReady` 라 `not-ready` taint 가 붙어 스케줄러가 배치 자체를 못 합니다. 컨테이너를 만들다 실패한 것이 아니라 만들 자리를 못 정한 것입니다.



## 주소 재고가 내려온 자리

> [04-01](./04-01.Kubernetes%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%82%B9%20%EB%AA%A8%EB%8D%B8%20%E2%80%94%20Pod%20IP%C2%B7%EB%A0%88%EC%9D%B4%EC%95%84%EC%9B%83%C2%B7Probe.md) 의 「주소 대역을 정하는 플래그」 에서 읽은 `--cluster-cidr` 이 노드의 `spec.podCIDR` 로 잘려 내려온 것을 확인합니다.

### 풀려는 문제

플래그와 필드를 읽어서는 그 둘이 같은 값의 앞뒤인지 감이 안 옵니다. 한 클러스터에서 나란히 꺼내 보면 관계가 보입니다.

### 대역 확인

```bash
# 클러스터 전체 예산
docker exec k8s-net-control-plane \
  grep -E 'cluster-cidr|service-cluster-ip-range|node-cidr-mask-size' \
  /etc/kubernetes/manifests/kube-controller-manager.yaml

# 노드가 받아 간 조각
kubectl get nodes -o custom-columns=NAME:.metadata.name,PODCIDR:.spec.podCIDR

# 플러그인이 읽는 설정과 바이너리
docker exec k8s-net-worker ls /etc/cni/net.d/
docker exec k8s-net-worker ls /opt/cni/bin/
```

Cilium 을 올리기 전에도 `/etc/cni/net.d/` 를 한 번 봐 두면 설치 전후가 비교됩니다. 재실행에서 컨트롤 플레인의 플래그는 `--cluster-cidr=10.244.0.0/16` 과 `--service-cluster-ip-range=10.96.0.0/16` 이었습니다.[^svc16]

### Pod 하나 띄워 주소 보기

```bash
kubectl create deployment web --image=nginx:alpine --replicas=3
kubectl wait --for=condition=Ready pod -l app=web --timeout=120s

kubectl get pods -l app=web -o wide
kubectl exec deploy/web -- ip -4 addr show eth0
kubectl exec deploy/web -- ip route
```

### 확인된 것

재고가 위에서 아래로 잘려 내려오는 것은 값으로 확인됩니다. 클러스터 예산이 노드마다 `/24` 조각으로 갈리고, 각 Pod 의 주소는 자기 노드가 받은 조각 안에 들어 있습니다. 이 그림은 Cilium 이 노드의 `podCIDR` 을 쓰도록 `ipam.mode=kubernetes` 를 줬을 때 성립합니다.

2026-09 관찰은 `ipam.mode` 를 주지 않은 명령에서 나왔는데도 `podCIDR` 안 주소였습니다. 2026-11-08 의 1.20.4 에서는 같은 명령이 `10.0.0.x` 를 줬고 차트 기본값도 `cluster-pool`(`10.0.0.0/8`)입니다.[^ipamdef] 2026-09 에 어떤 버전이었는지는 기록이 없어 두 조건이 같다고는 말할 수 없습니다.

조각 번호는 노드 이름 순서가 아닙니다. 관찰 칸의 "등록된 순서로 잘려 나간다"는 배정 결과만으로 입증되지 않는 인과입니다. 재실행에서 확실한 것은 번호가 클러스터를 만들 때마다 달랐다는 것뿐입니다. 이름으로 대역을 추측하면 안 된다는 결론도 거기서 나옵니다.

Cilium 의 `05-cilium.conflist` 에는 `ipam` 칸이 없습니다. CNI 명세가 배선과 주소 할당을 갈라 놓기는 하지만 그것이 강제는 아니라는 실물입니다. `/opt/cni/bin/` 에 `host-local` 같은 바이너리가 놓여 있어도 이 클러스터에서는 실행되지 않습니다. 놓여 있는 것과 쓰이는 것은 다릅니다. 파일 배치는 [04-02](./04-02.CNI%EC%99%80%20kube-proxy%20%E2%80%94%20Pod%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC%EC%9D%98%20%EB%B0%B0%EC%84%A0%EA%B3%B5%EA%B3%BC%20%EB%A1%9C%EB%93%9C%EB%B0%B8%EB%9F%B0%EC%84%9C.md) 의 「런타임이 설정과 바이너리를 찾는 자리」 에 정리돼 있습니다.



## 서비스 하나의 규칙 줄

> [04-02](./04-02.CNI%EC%99%80%20kube-proxy%20%E2%80%94%20Pod%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC%EC%9D%98%20%EB%B0%B0%EC%84%A0%EA%B3%B5%EA%B3%BC%20%EB%A1%9C%EB%93%9C%EB%B0%B8%EB%9F%B0%EC%84%9C.md) 의 「서비스 하나가 내려앉는 체인 셋」 에서 읽은 체인 셋을 실제 규칙에서 찾습니다.

### 풀려는 문제

진입 체인에서 서비스 체인으로, 거기서 엔드포인트 체인으로 이어진다고 읽었습니다. 그 줄이 실제로 어떻게 생겼고 확률이 어떤 값으로 박히는지는 꺼내 봐야 압니다.

### 서비스 만들고 규칙 찾기

```bash
kubectl expose deployment web --port=80 --target-port=80
kubectl get svc web

# 서비스 체인 찾기
docker exec k8s-net-worker iptables-save -t nat | grep -i 'KUBE-SERVICES' | head
docker exec k8s-net-worker iptables-save -t nat | grep -i "KUBE-SVC" | head

# 위에서 찾은 서비스 체인 이름을 넣어 그 안을 본다
docker exec k8s-net-worker iptables-save -t nat | grep '<KUBE-SVC-체인이름>'
```

### 가상 주소라는 것 확인

```bash
SVC_IP=$(kubectl get svc web -o jsonpath='{.spec.clusterIP}')
echo "$SVC_IP"

# nginx:alpine 의 busybox 에 ping 과 wget 이 둘 다 들어 있어 별도 이미지가 필요 없습니다
POD=$(kubectl get pod -l app=web -o jsonpath='{.items[0].metadata.name}')
kubectl exec "$POD" -- ping -c 2 -W 2 "$SVC_IP" ; echo "exit=$?"
kubectl exec "$POD" -- wget -qO- -T 3 "http://$SVC_IP/" | head -3
```

### 규칙이 어느 노드에 있는지

```bash
kubectl get pods -l app=web -o wide
for n in k8s-net-control-plane k8s-net-worker k8s-net-worker2; do
  echo -n "$n : "
  docker exec "$n" iptables-save -t nat | grep -c 'default/web'
done
```

| 3-1 | 백엔드가 3개일 때 서비스 체인 안에 줄이 몇 개일까요 | 확률 줄 2개 | 맞았습니다. 백엔드 줄은 3개인데 확률이 붙은 것은 2개입니다. 마지막 줄은 앞을 다 통과한 것을 무조건 받습니다. 마킹 줄까지 세면 체인 전체가 4줄입니다 | 같음. 세 노드 모두 `default/web` 줄이 11개입니다 |
| 3-2 | 각 줄의 확률값은 얼마일까요? 마지막 줄에도 확률이 붙을까요 | 0.33 → 0.5, 마지막엔 없음 | 맞았습니다. 실제 값은 `0.33333333349` 와 `0.50000000000` 입니다. 1/3 이 2진수로 안 떨어져 끝자리가 어긋납니다 | 같은 값 |
| 3-3 | ClusterIP 로 `ping` 은 되고 `curl` 은 될까요? 다르다면 이유는 | ping 실패 · curl 성공, ICMP 라서 | 절반 맞았습니다. ping 은 `100% packet loss`, wget 은 HTML 수신. ICMP 인 것도 이유지만 더 근본은 규칙 조건이 `-p tcp --dport 80` 이라 ICMP 가 체인에 **진입조차 못 한다**는 것입니다. 번역 안 된 패킷은 그 주소를 가진 인터페이스가 없어 조용히 사라집니다 | 같음. ClusterIP 는 `10.96.138.19` 였고 ping 은 `100% packet loss`, wget 은 HTML 을 받았습니다 |
| 3-4 | 이 규칙이 세 노드에 다 있을까요, 백엔드가 있는 노드에만 있을까요 | 모든 노드 (단 마스터는 몰라도 될 듯) | 앞은 맞고 뒤는 틀렸습니다. 세 노드 모두 정확히 11줄입니다. web Pod 가 없는 control-plane 도 같습니다. taint 가 막는 것은 **스케줄링**이지 호출이 아닙니다 | 같음. 세 노드 모두 11줄입니다. kube-proxy 는 `mode: iptables` 이고 iptables 는 v1.8.11 (nf_tables 백엔드)입니다 |

### 확인된 것

11줄은 진입 줄 1, 서비스 체인 4줄(마킹 1 + 확률 2 + 나머지 1), 엔드포인트 체인 셋의 6줄(각 2줄)을 더한 값입니다.

![서비스 하나가 만드는 11줄의 구성](_assets/04-04.service-line-breakdown.svg)

세 노드가 똑같이 11줄인 것은 kube-proxy 가 노드마다 따로 돌면서 서로 조율하지 않기 때문입니다. 각자 같은 EndpointSlice 를 보고 같은 규칙을 만들 뿐이라서, 어느 노드에서 출발해도 같은 서비스에 닿습니다.

엔드포인트 체인이 따로 있는 이유는 확률 판정이 한 줄에서 한 번만 일어나는데 뽑힌 뒤 할 일은 두 줄(헤어핀 마킹, DNAT)이기 때문입니다. 같은 확률을 두 줄에 따로 적으면 줄마다 따로 굴러 서로 다른 백엔드가 뽑힐 수 있어서, 한 번의 판정을 두 동작에 잇는 방법은 점프뿐입니다. 자세한 설명은 [04-02](./04-02.CNI%EC%99%80%20kube-proxy%20%E2%80%94%20Pod%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%81%AC%EC%9D%98%20%EB%B0%B0%EC%84%A0%EA%B3%B5%EA%B3%BC%20%EB%A1%9C%EB%93%9C%EB%B0%B8%EB%9F%B0%EC%84%9C.md) 의 「서비스 하나가 내려앉는 체인 셋」 에 있습니다.

같은 서비스를 nftables 모드로 보면 규칙의 자리가 바뀝니다. 단일 노드 kind 에서 설정에 `kubeProxyMode: "nftables"` 를 주고[^kindcfg] `web` 서비스(백엔드 셋)를 만든 뒤 `nft list table ip kube-proxy` 로 봅니다.

서비스 주소는 `map service-ips` 의 `10.96.243.89 . tcp . 80 : goto service-PFISGYVC-default/web/tcp/` 줄에 있습니다. 세션 어피니티가 없는 서비스에서는 체인의 본체가 `dnat ip to numgen random mod 3 map {…}` 한 줄이라, 확률 줄과 엔드포인트 체인이 하던 일을 난수 맵 하나가 맡습니다. 이 모드의 kube-proxy 는 iptables 에 아무것도 쓰지 않으므로 `iptables-save | grep KUBE-SVC` 는 0줄입니다.



## readiness 를 잃을 때 사라지는 줄

> [04-01](./04-01.Kubernetes%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%82%B9%20%EB%AA%A8%EB%8D%B8%20%E2%80%94%20Pod%20IP%C2%B7%EB%A0%88%EC%9D%B4%EC%95%84%EC%9B%83%C2%B7Probe.md) 의 「readiness 실패가 규칙까지 가는 길」 에서 읽은 전파 경로를 끝에서부터 확인합니다.

### 풀려는 문제

readiness 가 실패하면 명단에서 빠진다고 읽었습니다. 그런데 그 Pod 자신은 멀쩡한지, 나가는 길은 살아 있는지가 그 서술만으로는 확인되지 않습니다. 이 묶음의 목적은 두 가지를 동시에 보는 것입니다.

### 프로브를 붙이고 일부러 떨어뜨리기

```bash
# patch 로 나중에 붙이면 새 Pod 가 Ready 가 안 돼 롤아웃이 멈춥니다 — 처음부터 달고 만듭니다.
cat <<'EOF' | kubectl apply -f -
apiVersion: apps/v1
kind: Deployment
metadata:
  name: probe-web
spec:
  replicas: 3
  selector:
    matchLabels: { app: probe-web }
  template:
    metadata:
      labels: { app: probe-web }
    spec:
      containers:
        - name: nginx
          image: nginx:alpine
          readinessProbe:
            exec: { command: ["cat", "/tmp/ready"] }
            periodSeconds: 5
            failureThreshold: 2
EOF

kubectl get pods -l app=probe-web
```

프로브가 `/tmp/ready` 를 보므로 파일을 만들어야 Ready 가 됩니다. 명단은 EndpointSlice 로 봅니다. `kubectl get endpoints` 는 `Warning: v1 Endpoints is deprecated in v1.33+; use discovery.k8s.io/v1 EndpointSlice` 를 찍기 때문입니다.

```bash
for p in $(kubectl get pods -l app=probe-web -o name); do
  kubectl exec "$p" -- touch /tmp/ready
done
kubectl expose deployment probe-web --port=80
kubectl get endpointslice -l kubernetes.io/service-name=probe-web -o yaml | grep -E 'ready|addresses' 
```

이제 하나만 떨어뜨립니다. 시간을 재려면 출발선을 먼저 맞춥니다. 파일을 만들고 명단이 `true` 가 되기를 기다린 뒤에 `rm` 을 칩니다. 이미 지운 상태에서 `rm` 을 다시 치면 `No such file or directory` 가 나고, 루프는 이미 내려가 있던 상태를 `+1s` 로 읽습니다.

```bash
VICTIM=$(kubectl get pods -l app=probe-web -o name | head -1)
kubectl exec "$VICTIM" -- rm /tmp/ready
# 명단에서 빠지는지
kubectl get endpointslice -l kubernetes.io/service-name=probe-web -o yaml | grep -E 'ready|addresses'

# 규칙 줄이 사라지는지
docker exec k8s-net-worker iptables-save -t nat | grep 'KUBE-SVC' | head

# 그 Pod 는 나갈 수 있는지
# kubernetes.default.svc 는 443/HTTPS 라 http 로는 못 칩니다. 「서비스 하나의 규칙 줄」 묶음에서 만든 web 서비스를 씁니다.
kubectl exec "$VICTIM" -- sh -c 'wget -qO- -T 3 http://web.default.svc.cluster.local/ >/dev/null && echo OUT-OK || echo OUT-FAIL'
```

|---|----------|--------|------|------|
| 4-1 | 파일을 지운 뒤 명단에서 빠지기까지 몇 초쯤 걸릴까요 | 프로브 확인 간격만큼 | **8초.** 축은 맞고 값이 없었습니다 — `failureThreshold: 2` 를 셈에 안 넣었습니다. `rm` 부터 첫 검사까지 0~5초, 거기서 다시 5초라 범위는 5~10초입니다 | 9.9초. 잰 값에 `kubectl` 호출 시간이 들어 있고, 범위 5~10초 안입니다 |
| 4-2 | 서비스 체인의 줄이 몇 개로 줄고 확률값은 어떻게 바뀔까요 | 33·50 에서 50 만 남는다 | 맞았습니다. `--probability 0.50000000000` 한 줄과 확률 없는 줄 하나입니다. **명단과 규칙의 표현이 다릅니다** — EndpointSlice 는 주소를 남기고 깃발만 `false` 로 내리는데, kube-proxy 는 그 주소의 `KUBE-SEP` 체인을 **아예 만들지 않습니다** | 같음. 빠진 Pod 의 `KUBE-SEP` 체인은 만들어지지 않았고 `probe-web` 의 DNAT 줄은 둘이었습니다[^topo] |
| 4-3 | 떨어진 Pod 는 밖으로 나갈 수 있을까요 | 나갈 수 있다 · 명단에서 빠진 것이지 IP 는 살아 있다 | 맞았고 근거도 정확했습니다. `OUT-OK`. 반대 방향도 확인했습니다 — 정상 Pod 에서 떨어진 Pod 의 IP 로 직접 요청하면 nginx 가 HTML 을 돌려줍니다. 끊긴 것은 **Service 를 통과하는 길 하나**뿐입니다 | 같음. `OUT-OK` |
| 4-4 | 그 Pod 의 컨테이너가 재시작될까요 | 재시작되지 않는다 | 맞았습니다. `0/1 Running · RESTARTS 0 · AGE 16h` — 16시간 동안 Ready 가 아닌 채로 한 번도 재시작하지 않았습니다. 죽이는 것은 liveness 입니다 | 같음. `RESTARTS 0` |
| 4-5 | 파일을 다시 만들면 몇 초 만에 명단에 돌아올까요 | 4-1 과 같다 | **반증. 1초·4초로 절반 이하입니다.** `successThreshold` 가 **1** 이라 한 번만 성공하면 뒤집힙니다. 우리가 안 적은 필드라 API 서버가 기본값으로 채웠고, `kubectl get deploy -o jsonpath='{...readinessProbe}'` 로 확인했습니다[^probedef] | 3.3초. 낙하보다 짧은 비대칭이 다시 나왔습니다. 스펙에 `successThreshold: 1` · `timeoutSeconds: 1` 이 채워져 있었습니다 |

### 확인된 것

프로브 스펙을 꺼내 보면 우리가 적지 않은 필드가 채워져 있습니다. `successThreshold: 1` 과 `timeoutSeconds: 1` 입니다. 앞의 값이 낙하와 복귀의 시간 차를 만듭니다. kube-proxy 가 쓰는 것은 Ready 엔드포인트이고, Ready 가 하나도 없을 때만 종료 중인 serving 엔드포인트로 대체합니다.[^topo]

```json
{"exec":{"command":["cat","/tmp/ready"]},"failureThreshold":2,"periodSeconds":5,
 "successThreshold":1,"timeoutSeconds":1}
```

![readiness 를 잃고 되찾는 시간](_assets/04-04.readiness-timeline.svg)

이 비대칭은 직관과 반대입니다. 고장 났으면 빨리 빼고 돌아왔으면 천천히 넣어야 안전해 보입니다. 기본값은 그 반대로 되어 있습니다.

빼는 쪽을 느리게 두는 이유가 둘입니다. 일시적인 흔들림마다 명단이 뒤집히면 모든 노드가 규칙을 다시 써야 합니다. 하나가 빠지면 남은 Pod 의 부하가 올라 연쇄로 함께 빠질 수도 있습니다. 넣는 쪽은 방금 프로브에 성공한 것이라 안 넣으면 멀쩡한 용량이 노는 것뿐입니다. 프로브의 타이밍 계산은 [04-01](./04-01.Kubernetes%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%82%B9%20%EB%AA%A8%EB%8D%B8%20%E2%80%94%20Pod%20IP%C2%B7%EB%A0%88%EC%9D%B4%EC%95%84%EC%9B%83%C2%B7Probe.md) 의 「프로브 상태 전이와 타이밍」 에 있습니다.

`timeoutSeconds: 1` 도 같은 표에서 읽습니다. 프로브 명령이 1초 안에 안 끝나면 그것도 실패로 셉니다. 앱은 멀쩡한데 응답이 느려서 명단에서 빠지는 사고가 이 값에서 납니다.



## 선택되는 순간의 잠금

> [04-03](./04-03.NetworkPolicy%EC%99%80%20DNS%20%E2%80%94%20%ED%81%B4%EB%9F%AC%EC%8A%A4%ED%84%B0%20%EC%95%88%EC%9D%98%20%EB%B0%A9%ED%99%94%EB%B2%BD%EA%B3%BC%20%EC%9D%B4%EB%A6%84.md) 의 「세 단계로 조여 보기」 의 3단계를 그대로 재현하고, 정책에 적은 포트만 통제되는지와 이름이 안 나온 Pod 도 함께 잠기는지를 실측합니다.

### 풀려는 문제

두 가지를 손으로 확인합니다. 정책에 적은 포트만 통제되는지, 정책에 이름이 안 나온 Pod 도 함께 잠기는지입니다. 말로 읽은 규칙이 실제 응답 코드와 같은지 봅니다.

### 세 컴포넌트 띄우기

```bash
kubectl create ns polylab
kubectl -n polylab run demo    --image=nicolaka/netshoot --labels=app=demo    --command -- sleep infinity
kubectl -n polylab run cart    --image=nicolaka/netshoot --labels=app=cart    --command -- sleep infinity
kubectl -n polylab run demo-db --image=nginx:alpine      --labels=app=demo-db
kubectl -n polylab expose pod demo-db --port=80
kubectl -n polylab wait --for=condition=Ready pod --all --timeout=120s
```

정책 없는 상태부터 재 봅니다. Pod 가 Ready 가 된 직후의 첫 요청은 타임아웃(`000`)이 날 수 있으므로 같은 명령을 두세 번 쳐서 `200` 이 안정된 뒤에 정책을 겁니다.

```bash
kubectl -n polylab exec demo -- curl -s -o /dev/null -w 'demo→db %{http_code}\n' --max-time 3 http://demo-db
kubectl -n polylab exec cart -- curl -s -o /dev/null -w 'cart→db %{http_code}\n' --max-time 3 http://demo-db
kubectl -n polylab exec cart -- sh -c 'nslookup demo-db >/dev/null && echo cart-dns-OK || echo cart-dns-FAIL'
kubectl -n polylab exec demo-db -- sh -c 'wget -qO- -T 3 http://web.default >/dev/null 2>&1 && echo db-out-OK || echo db-out-FAIL'
```

### 2단계 — 규칙 없이 선택만

```yaml
# lock.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: demo-db-lockdown, namespace: polylab }
spec:
  podSelector: { matchLabels: { app: demo-db } }
  policyTypes: [Ingress, Egress]
```

```bash
kubectl apply -f lock.yaml
kubectl -n polylab exec demo -- curl -s -o /dev/null -w 'demo→db %{http_code}\n' --max-time 3 http://demo-db
kubectl -n polylab exec cart -- curl -s -o /dev/null -w 'cart→db %{http_code}\n' --max-time 3 http://demo-db
kubectl -n polylab exec cart -- curl -s -o /dev/null -w 'cart→web %{http_code}\n' --max-time 3 http://web.default
kubectl -n polylab exec demo-db -- sh -c 'wget -qO- -T 3 http://web.default >/dev/null 2>&1 && echo db-out-OK || echo db-out-FAIL'
```

### 3단계 — 예외 하나 추가

```yaml
# allow.yaml
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: demo-db-allow-demo, namespace: polylab }
spec:
  podSelector: { matchLabels: { app: demo-db } }
  policyTypes: [Ingress, Egress]
  ingress:
    - from: [{ podSelector: { matchLabels: { app: demo } } }]
      ports: [{ protocol: TCP, port: 80 }]
```

```bash
kubectl apply -f allow.yaml
kubectl -n polylab exec demo -- curl -s -o /dev/null -w 'demo→db:80 %{http_code}\n' --max-time 3 http://demo-db
kubectl -n polylab exec cart -- curl -s -o /dev/null -w 'cart→db:80 %{http_code}\n' --max-time 3 http://demo-db
```

"Ingress 가 요청이면 Egress 는 응답"으로 보셨는데 **둘은 방향이고, 방향은 누가 연결을 시작했느냐로 정해집니다.** 실패 모양이 앞의 둘과 다른 것도 관측됐습니다 — `demo→db` 는 5초 타임아웃인데 `db-out` 은 `bad address` 로 즉시 실패했습니다. DNS 질의부터 나가는 연결이라 **이름 푸는 단계에서** 죽습니다 | 같음. `demo-db` 에서 `wget` 으로 `web.default` 를 부르면 `bad address` 로 즉시 끝났습니다. 같은 자리의 `nslookup kubernetes.default` 도 실패했지만 점이 있는 이름이라 정책 없이도 실패하므로 판정에 쓰지 않습니다 |
| 5-4 | 3단계에서 `demo→db` 와 `cart→db` 는 각각 어떻게 될까요 | demo 는 되고 cart 는 안 된다 | 맞았습니다. `demo→db 200` · `cart→db 000 5.00s`. 그리고 **Egress 는 여전히 빈 채로 200 이 돌아왔습니다** — 판정은 연결이 시작될 때 한 번뿐이고 응답은 conntrack 이 알아봅니다. "Egress = 응답"이었다면 나올 수 없는 결과입니다 | 같음. `demo→db 200` · `cart→db 000` |
| 5-5 | 정책의 `port: 80` 을 바꾸거나 지우면 무엇이 달라질까요 | 8080 으로 바꾸면 80 은 막힌다 / `ports` 를 지우면 둘 다 막힌다 | **앞은 정답, 뒤는 반증.** 8080 으로 바꾸니 `demo→db:80` 이 막혀 "적은 포트만 **허용**된다"가 확정됐습니다. 그런데 `ports` 를 통째로 지우자 `200` 으로 열렸습니다. **비어 있음이 두 층에서 뜻이 반대입니다** — `ingress` 목록이 비면 허용 0개지만, 목록 안 항목에서 `ports` 를 생략하면 "포트를 제한하지 않는다"입니다. `cart` 가 계속 막힌 것은 `from` 이 남아 있어서입니다 | 같음. 8080 이면 둘 다 `000`, `ports` 를 생략하면 demo `200` · cart `000` 입니다 |
| 5-6 | 두 정책이 같은 Pod 를 고르고 있습니다. 나중 것이 앞 것을 덮어쓸까요 | 순서대로 적용되며 덮어쓸 것 | **반증. 덮어쓰지 않고 합쳐집니다.** `demo-db-lockdown` 을 지웠는데 세 결과가 한 글자도 안 바뀌었습니다. 그 정책의 허용 목록이 빈 집합이라 합집합에 아무 기여를 안 하고 있었습니다. **잠근 것은 그 정책이 아니라 "어느 정책에든 선택되었다는 사실"** 이었습니다 | 같음. `demo-db-lockdown` 을 지워도 결과가 바뀌지 않았습니다 |

### 확인된 것

정책은 문을 닫는 도구가 아닙니다. Pod 를 닫힌 상태로 옮겨 놓는 도구입니다. 적힌 규칙은 그 위에 다시 여는 문입니다. `lockdown` 이라는 이름의 정책을 지워도 아무것도 안 풀린 것이 그 증거입니다.

![정책 단계별 응답 코드](_assets/04-04.policy-stage-matrix.svg)

표준 NetworkPolicy 끼리는 이미 선택된 Pod 를 정책을 더해서 더 막을 수 없습니다. 허용만 더해지기 때문입니다. 더 막으려면 기존 정책의 허용을 줄여야 합니다.

같은 정책 하나에서 실패한 모양이 둘로 갈린 것은 막힌 지점이 달라서입니다. 들어오는 쪽은 이름을 이미 풀었고 TCP 패킷이 버려져 타임아웃까지 기다렸습니다(`000`). 나가는 쪽은 DNS 질의부터 나가는 연결이라 이름 푸는 단계에서 죽어 `bad address` 가 바로 났습니다.

Egress 를 잠그면 앱이 "DNS 오류"를 냅니다. CoreDNS 를 의심하고 거기부터 뒤지기 쉽지만 원인은 방금 건 정책입니다.

정책 뒤 DNS 확인에 `nslookup` 대신 `wget` 을 쓴 데에는 이유가 있습니다. busybox 의 `nslookup` 은 점이 없는 이름에만 `search` 꼬리표를 붙입니다.[^nslookup] `kubernetes.default` 는 점이 있어 그대로 한 번만 묻고 NXDOMAIN 을 받으므로 정책이 없어도 실패합니다. 같은 컨테이너의 `wget` 은 musl 리졸버를 거쳐 `ndots:5` 규칙대로 검색 경로를 붙이므로 같은 이름이 풀립니다. 그래서 정책 전 기준선에도 같은 `wget` 명령을 넣었습니다.



## 이름 하나의 질의 횟수

> [04-03](./04-03.NetworkPolicy%EC%99%80%20DNS%20%E2%80%94%20%ED%81%B4%EB%9F%AC%EC%8A%A4%ED%84%B0%20%EC%95%88%EC%9D%98%20%EB%B0%A9%ED%99%94%EB%B2%BD%EA%B3%BC%20%EC%9D%B4%EB%A6%84.md) 의 「검색 경로와 이름 하나의 질의」 에서 읽은 검색 경로의 비용을 셉니다.

### 풀려는 문제

검색 도메인이 셋이고 각 시도가 두 질의를 낸다는 계산은 읽었습니다. 실제로 몇 번 나가는지는 세 봐야 합니다.

### 정책을 걷고 resolv.conf 부터

```bash
kubectl -n polylab delete networkpolicy --all
kubectl -n polylab exec demo -- cat /etc/resolv.conf
```

재실행에서 `resolv.conf` 는 `search polylab.svc.cluster.local svc.cluster.local cluster.local`, `nameserver 10.96.0.10`, `options ndots:5` 였습니다.[^ndots]

### 나가는 질의 세기

시간을 재는 것보다 질의를 직접 세는 편이 낫습니다. 시간은 캐시와 네트워크 상태에 흔들리지만, 질의 수에는 규칙이 그대로 드러납니다. `demo` Pod 안에서 CoreDNS 로 나가는 53번 트래픽을 잡습니다. 이름을 푸는 호출은 `getent ahosts` 로 합니다. netshoot 은 Alpine 위에 만든 이미지라 이 값은 musl 리졸버의 결과입니다.[^netshoot] `curl` 은 c-ares 로 A 와 AAAA 를 따로 풀어 질의 수가 실행마다 달랐습니다([04-03](./04-03.NetworkPolicy%EC%99%80%20DNS%20%E2%80%94%20%ED%81%B4%EB%9F%AC%EC%8A%A4%ED%84%B0%20%EC%95%88%EC%9D%98%20%EB%B0%A9%ED%99%94%EB%B2%BD%EA%B3%BC%20%EC%9D%B4%EB%A6%84.md) 의 「클라이언트마다 다른 질의 횟수」 에 클라이언트별 차이가 있습니다).

```bash
dnsq() {
  echo "===== $1 ====="
  kubectl -n polylab exec demo -- sh -c "
    tcpdump -l -n -i any 'udp port 53' > /tmp/cap.txt 2>/dev/null &
    TP=\$!
    sleep 1
    getent ahosts '$1' >/dev/null 2>&1
    sleep 1
    kill \$TP 2>/dev/null; sleep 0.3
    grep -oE '(A|AAAA)\? [^ ]+' /tmp/cap.txt
    echo -n '  총 질의 '; grep -cE '(A|AAAA)\? ' /tmp/cap.txt
  "
  echo
}

dnsq demo-db
dnsq github.com
dnsq github.com.
dnsq demo-db.polylab.svc.cluster.local
```

### 예측하고 확인할 것

| # | 예측 질문 | 내 예측 | 관찰 (2026-09, curl) | 재실행 (2026-11-08, getent) |
|---|----------|--------|------|------|
| 6-1 | `polylab` 의 Pod 에서 `demo-db` 를 부르면 시도가 몇 번일까요 | 1번 — 첫 꼬리표가 내 네임스페이스다 | 맞았습니다. 다만 **총 질의는 5개**입니다. A 는 1회로 끝났는데 AAAA 가 목록을 끝까지 돌았습니다 | 총 질의 2개. 세 번 모두 같았습니다 |
| 6-2 | `github.com` 은 몇 번일까요 | 4번 | 맞았습니다. 총 8개. 이유가 한 칸 어긋났습니다 — search 가 "안 먹히는" 것이 아니라 셋 다 붙여 보고 실패한 **뒤에야** 원래 이름을 시도합니다 | 총 8개. 세 번 모두 같았습니다 |
| 6-3 | `github.com.` 은 몇 번일까요 | 1번 | 맞았습니다. 총 2개 | 총 2개 |
| 6-4 | `demo-db.polylab.svc.cluster.local` 은 점이 4개입니다. 몇 번일까요 | 4번 — search 를 다 소진한다 | 맞았습니다. 총 8개 | 총 8개 |

### 확인된 것

넷을 나란히 놓으면 두 가지가 직관과 반대로 뒤집혀 있습니다.

| 부른 이름 | curl (2026-09) A · AAAA · 합 | getent (2026-11-08) A · AAAA · 합 |
|-----------|:---:|:---:|
| `demo-db` | 1 · 4 · **5** | 1 · 1 · **2** |
| `github.com` | 4 · 4 · **8** | 4 · 4 · **8** |
| `github.com.` | 1 · 1 · **2** | 1 · 1 · **2** |
| `demo-db.polylab.svc.cluster.local` | 4 · 4 · **8** | 4 · 4 · **8** |

![이름 하나가 내는 질의 수](_assets/04-04.dns-query-count.svg)

긴 이름이 짧은 이름보다 비쌉니다. 완전한 클러스터 이름을 정성껏 다 적으면 8이고 `demo-db` 라고만 쓰면 2입니다. `ndots:5` 라서 점이 다섯 개 미만인 이름은 검색 경로를 먼저 붙여 봅니다. `demo-db` 는 첫 꼬리표에서 풀리지만 점이 4개인 완전한 이름은 꼬리표 셋이 모두 실패한 뒤에야 원래 이름이 나갑니다.

줄이는 것은 끝의 점 하나입니다. `github.com` 8에서 `github.com.` 2로 떨어집니다.

`demo-db` 의 관찰 칸 5와 재실행 칸 2가 다른 것은 리졸버가 달라서입니다. CoreDNS 는 IPv4 전용 Service 의 AAAA 에 NXDOMAIN 이 아니라 빈 답(NODATA)을 줍니다.[^nodata] musl 의 `getent` 는 그 빈 답에서 멈춰 2입니다.

c-ares 를 쓰는 `curl` 은 AAAA 가 남은 꼬리표를 도는 때가 있다고 보면 맞아떨어지며, 세 번 재면 `demo-db` 는 5·2·2, `github.com` 은 8·10·10 이었습니다. 이 Service 는 `SingleStack` 이고 `ipFamilies` 가 `["IPv4"]` 이며 `getent ahostsv6 demo-db` 도 질의 2개로 끝났습니다. 기본값의 근거는 [04-03](./04-03.NetworkPolicy%EC%99%80%20DNS%20%E2%80%94%20%ED%81%B4%EB%9F%AC%EC%8A%A4%ED%84%B0%20%EC%95%88%EC%9D%98%20%EB%B0%A9%ED%99%94%EB%B2%BD%EA%B3%BC%20%EC%9D%B4%EB%A6%84.md) 의 「ipFamilyPolicy 와 기본값 근거」 에 있습니다.



## Cilium L7 정책

> [04-03](./04-03.NetworkPolicy%EC%99%80%20DNS%20%E2%80%94%20%ED%81%B4%EB%9F%AC%EC%8A%A4%ED%84%B0%20%EC%95%88%EC%9D%98%20%EB%B0%A9%ED%99%94%EB%B2%BD%EA%B3%BC%20%EC%9D%B4%EB%A6%84.md) 의 「표준 정책 밖의 규칙과 확장」 에서 이관한 묶음입니다. 표준 정책이 "누가 어느 포트로"까지라면 여기서는 "어떤 경로로"까지 갑니다.

### 풀려는 문제

같은 Pod 의 같은 포트에서 조회 경로는 열고 관리 경로는 막고 싶은 요구가 있습니다. 표준 문법으로는 적을 방법이 없습니다. Cilium 이 L7 을 보므로 그 요구를 정책으로 직접 적습니다.

### 정책 하나가 만드는 세 서명

```bash
cat <<'EOF' > l7.yaml
apiVersion: cilium.io/v2
kind: CiliumNetworkPolicy
metadata: { name: l7-only-root, namespace: polylab }
spec:
  endpointSelector: { matchLabels: { app: demo-db } }
  ingress:
    - fromEndpoints: [{ matchLabels: { app: demo } }]
      toPorts:
        - ports: [{ port: "80", protocol: TCP }]
          rules: { http: [{ method: GET, path: "/" }] }
EOF

kubectl -n polylab delete networkpolicy --all      # 표준 정책을 치우고 깨끗하게 본다
kubectl apply -f l7.yaml
sleep 5

kubectl -n polylab exec demo -- curl -s -o /dev/null -w 'GET /        → %{http_code}  %{time_total}s\n' --max-time 3 http://demo-db/
kubectl -n polylab exec demo -- curl -s -o /dev/null -w 'GET /health  → %{http_code}  %{time_total}s\n' --max-time 3 http://demo-db/health
kubectl -n polylab exec cart -- curl -s -o /dev/null -w 'cart GET /   → %{http_code}  %{time_total}s\n' --max-time 3 http://demo-db/
```

### 프록시와 서버 구분

정책에 없는 경로와, 정책에는 있지만 서버에 없는 경로를 나란히 칩니다. 둘 다 "없는 경로"인데 답하는 쪽이 다릅니다.

```bash
kubectl -n polylab exec demo -- curl -s -i --max-time 3 http://demo-db/health | head -8
kubectl -n polylab exec demo -- curl -s --max-time 3 http://demo-db/health | head -6

# 정책에 /nope 를 허용으로 추가한 뒤 다시
kubectl -n polylab exec demo -- curl -s -o /dev/null -w '/nope → %{http_code}\n' --max-time 3 http://demo-db/nope
```

### 넓은 표준 정책을 옆에 두면

```bash
cat <<'EOF' | kubectl apply -f -
apiVersion: networking.k8s.io/v1
kind: NetworkPolicy
metadata: { name: std-wide, namespace: polylab }   # demo 에게 포트 제한 없이 허용
spec:
  podSelector: { matchLabels: { app: demo-db } }
  policyTypes: [Ingress]
  ingress:
    - from: [{ podSelector: { matchLabels: { app: demo } } }]
EOF
sleep 5
kubectl -n polylab exec demo -- curl -s -o /dev/null -w '/health → %{http_code}\n' --max-time 3 http://demo-db/health
kubectl -n polylab get networkpolicy,ciliumnetworkpolicy
```

### 예측하고 확인할 것

| # | 예측 질문 | 내 예측 | 관찰 (2026-09, Linux VM) | 재실행 (2026-11-08) |
|---|----------|--------|------|------|
| 7-1 | `/health` 는 어떤 응답을 받을까요? 타임아웃일까요 거절일까요 다른 코드일까요 | 연결이 이미 맺어졌으니 `000` 이 아니라 정상적인 예외 코드일 것 | 맞았습니다. **`403` · 0.006초**입니다. L3·L4 로 막았을 때의 `000` · 5초와 서명이 전혀 다릅니다 | 같음. `GET /` 은 `200`, `/health` 는 `403`, `cart` 는 `000` 입니다. 응답 시간은 호스트 부하로 흔들렸습니다 |
| 7-2 | 이 구분을 표준 `NetworkPolicy` 로 적으려면 | (모름) | 적을 수 없습니다. 표준 문법에는 `from` 과 `ports` 뿐이고 경로를 적을 칸이 아예 없습니다 | — |
| 7-3 | L7 을 보려면 무엇이 더 필요할까요 | (모름) | **프록시**입니다. `GET /health` 는 봉투가 아니라 본문이라, 연결을 받아 완성해야 읽힙니다. Cilium 은 Envoy 를 씁니다. 대가는 지연과 자원, 그리고 프록시가 아는 프로토콜에서만 된다는 제약입니다 | — |
| 7-4 | 넓은 표준 정책을 옆에 두면 L7 제약이 살아남을까요 | (예측 없음) | **무력화됩니다.** `/health` 가 403 에서 404 로 바뀌었습니다. 묶음 5 의 합집합이 계층을 넘어서도 그대로입니다 | 같음. `/health` 가 `404` 로 바뀝니다 |

### 확인된 것

한 화면에 서명 셋이 다 나왔습니다. `200` 은 nginx 까지 갔습니다. `403` 은 프록시까지만 갔습니다. `000 3.00s` 는 아무 데도 못 갔습니다.

![응답 서명 셋](_assets/04-04.response-signatures.svg)

`cart` 가 `000` 인 것이 순서를 보여 줍니다. L7 규칙이 걸려 있어도 출발지 판정이 먼저입니다. 허용 목록에 없으면 커널 단에서 버려지고, HTTP 를 읽어 볼 일 자체가 없습니다. L7 은 문을 더 여는 것이 아니라 이미 열린 문을 더 좁히는 것입니다.

막은 쪽이 누구인지는 코드와 본문으로 갈립니다. `/health` 는 `403` 에 `Access denied` 한 줄(`content-length: 15`)이었습니다. 정책에 더한 `/nope` 는 `404` 에 nginx HTML 이었습니다. 응답의 버전 표기는 2026-09 에 `nginx/1.31.5`, 2026-11-08 에 `nginx/1.31.8` 이었는데 `nginx:alpine` 태그가 움직이기 때문입니다.

`Server` 헤더는 판정에 쓸 수 없습니다. nginx 가 만든 404 에도 `server: envoy` 가 붙습니다. Envoy 가 지나가는 응답의 그 헤더를 자기 이름으로 덮어쓰기 때문입니다.

넓은 표준 정책을 옆에 두면 L7 제약이 사라지는데도 응답에는 여전히 `server: envoy` 가 붙습니다. 연결은 계속 프록시를 거치지만 거기서 아무것도 안 막는 상태입니다. 보안은 없고 지연만 남으므로 점검할 때는 `get networkpolicy,ciliumnetworkpolicy` 로 두 종류를 함께 봐야 합니다.

Envoy 는 `cilium-envoy` 라는 별도 DaemonSet 으로 노드마다 하나씩 떠 있습니다(「CNI 없는 클러스터」의 1-5). 설정의 `enable-l7-proxy: true` 와 `external-envoy-proxy: true` 가 그 결과입니다. L7 규칙을 처음 적기 전까지는 경로에 끼지 않아 없는 것처럼 보였을 뿐입니다.



## 노드 밖에서 Pod 로 가는 길

> [04-01](./04-01.Kubernetes%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%82%B9%20%EB%AA%A8%EB%8D%B8%20%E2%80%94%20Pod%20IP%C2%B7%EB%A0%88%EC%9D%B4%EC%95%84%EC%9B%83%C2%B7Probe.md) 의 「세 가지 레이아웃」 에서 읽은 레이아웃 셋을 손으로 확인합니다. 읽기만 했던 Flat 과 Island 를 만들어 보는 자리입니다.

### 풀려는 문제

레이아웃 세 가지를 표로 읽었습니다. Pod IP 가 밖에서 보이느냐로 갈린다고 했는데, "밖"이 어디이고 "보인다"가 무슨 뜻인지는 손으로 재 보지 않으면 남의 말입니다.

kind 클러스터를 VM 안에 세우면 그 VM 이 곧 "노드 밖"입니다. 노드 컨테이너는 VM 의 도커 네트워크에 붙어 있고, Pod 대역은 그 안쪽에 한 겹 더 있습니다.

### 현재 레이아웃

```bash
# 노드 컨테이너가 받은 주소 — 이것이 "노드 IP"다
docker inspect -f '{{.Name}} {{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' k8s-net-control-plane k8s-net-worker k8s-net-worker2

# Pod 하나의 주소 — 이것이 "Pod IP"다
kubectl get pods -l app=web -o wide

# VM 의 라우팅 테이블에 Pod 대역이 있는가
ip route | grep -E '10.244|172.1[78]'
```

### 밖에서 두드려 보기

```bash
POD_IP=$(kubectl get pod -l app=web -o jsonpath='{.items[0].status.podIP}')
NODE=$(kubectl get pod -l app=web -o jsonpath='{.items[0].spec.nodeName}')
echo "pod=$POD_IP node=$NODE"

# VM 에서 Pod IP 로 바로
curl -s -o /dev/null -w 'VM→PodIP %{http_code} (%{time_total}s)\n' --max-time 3 "http://$POD_IP" || echo 'VM→PodIP 실패'
```

### 경로를 손으로 넣어 Flat 흉내 내기

```bash
# 그 Pod 가 있는 노드 컨테이너의 IP 를 다음 홉으로 준다
NODE_IP=$(docker inspect -f '{{range .NetworkSettings.Networks}}{{.IPAddress}}{{end}}' "$NODE")
POD_CIDR=$(kubectl get node "$NODE" -o jsonpath='{.spec.podCIDR}')
echo "node_ip=$NODE_IP pod_cidr=$POD_CIDR"

sudo ip route add "$POD_CIDR" via "$NODE_IP"
curl -s -o /dev/null -w 'VM→PodIP(경로추가후) %{http_code}\n' --max-time 3 "http://$POD_IP" || echo '여전히 실패'

# 원복
sudo ip route del "$POD_CIDR" via "$NODE_IP"
```

### 나가는 쪽 출발지 보기

```bash
# Pod 가 VM 을 부를 때 VM 이 보는 출발지는 무엇인가
kubectl run out --rm -it --image=nicolaka/netshoot --restart=Never -- sh -c "curl -s --max-time 3 http://192.168.139.1:9 ; echo done" &
sudo timeout 8 tcpdump -ni any 'port 9' -c 4 2>/dev/null || echo '캡처 없음'
```

### 예측하고 확인할 것

| # | 예측 질문 | 내 예측 | 관찰 (2026-09, Linux VM) |
|---|----------|--------|------|
| 8-1 | 노드 IP 와 Pod IP 는 같은 대역일까요 다른 대역일까요 | (예측 없음) | 다릅니다. 노드는 `172.18.0.2·3·4` 로 VM 의 도커 브리지(`br-3afe…`)에 붙어 있고, Pod 는 `10.244.x.x` 입니다. **두 대역 사이에 아무 연결도 없습니다** |
| 8-2 | VM 의 라우팅 테이블에 Pod 대역이 있을까요 | (예측 없음) | 없습니다. `172.17.0.0/16`·`172.18.0.0/16`·`192.168.139.0/24` 셋뿐이고 `10.244` 는 한 줄도 없습니다. **이 상태가 Island 입니다** |
| 8-3 | 경로를 넣기 전에 VM 에서 Pod IP 로 두드리면 어떻게 될까요? 거절일까요 타임아웃일까요 | (예측 없음) | **`000 · 4.00s` 타임아웃**입니다. 거절이 아닙니다. VM 은 그 대역을 모르니 기본 경로로 내보내고, 밖에서는 아무도 답하지 않습니다 |
| 8-4 | 경로를 하나 넣으면 닿게 될까요? 된다면 이 클러스터는 어느 레이아웃이 된 것일까요 | (예측 없음) | 닿습니다. `ip route add 10.244.2.0/24 via 172.18.0.4` 한 줄로 `000 4.00s` 가 **`200 0.03s`** 가 됐습니다. 그 노드의 다른 Pod(`10.244.2.4`)도 함께 열립니다 — `/24` 한 줄이 그 노드 몫 전체를 덮습니다. **그런데 다른 노드의 Pod(`10.244.1.35`)는 여전히 `000` 입니다.** 한 줄은 한 노드만 엽니다 |
| 8-5 | Pod 가 VM 을 부를 때 VM 이 보는 출발지는 Pod IP 일까요 노드 IP 일까요 | (예측 없음) | **노드 IP** 입니다. `10.244.2.153` 이 보냈는데 VM 의 로그에는 `172.18.0.4` 가 찍혔습니다. 그 노드의 `CILIUM_POST_nat` 에 있는 `-s 10.244.2.0/24 ! -d 10.244.2.0/24 … -j MASQUERADE` 한 줄이 원인입니다 |

2026-11-08 의 Cilium 1.20.4 에서 `CILIUM_POST_nat` 의 마스커레이드 줄은 `-s 10.244.1.0/24 ! -d 10.244.1.0/24 ! -o cilium_+ … -j MASQUERADE` 입니다. 출발지가 그 노드의 Pod 대역이고 목적지가 그 대역 밖이며 나가는 인터페이스가 `cilium_` 로 시작하지 않을 때 노드 IP 로 바꿉니다. 8-5 의 인용은 가운데를 줄여 적은 것이므로 2026-11-08 의 전문은 위 줄로 읽습니다.

### 확인된 것

레이아웃은 클러스터가 가진 속성이 아니라 주변이 그 대역을 아느냐에 달린 상태입니다. 아무것도 안 바꾸고 VM 의 라우팅 테이블에 줄 하나를 넣었더니 Island 가 Flat 이 됐습니다. Pod 도 노드도 Cilium 설정도 그대로였습니다.

한 줄이 연 것은 한 노드의 몫뿐입니다. 노드가 셋이면 줄도 셋이고, 노드가 늘면 줄도 늘어야 합니다. [04-01](./04-01.Kubernetes%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%82%B9%20%EB%AA%A8%EB%8D%B8%20%E2%80%94%20Pod%20IP%C2%B7%EB%A0%88%EC%9D%B4%EC%95%84%EC%9B%83%C2%B7Probe.md) 의 「세 가지 레이아웃」 이 Flat 의 값으로 적은 "네트워크 장비의 협조"가 이 늘어나는 줄입니다. 실제 환경에서는 사람이 손으로 넣는 대신 BGP 로 광고합니다.

한 노드만 경유하게 하면 되지 않느냐는 물음이 여기서 나옵니다. 라우팅은 보내는 쪽이 정하므로 그 경유도 VM 이 정해 줘야 합니다. VM 의 테이블에 `10.244.1.0/24` 로 가는 줄이 없으면 VM 은 그 대역을 기본 경로로 내보내고 그쪽에서는 아무도 답하지 않습니다. 8-3 에서 본 `000 · 4.00s` 가 그 상태입니다. 경유할 노드를 정해 주는 것도 결국 VM 의 테이블에 줄을 넣는 일이라, 줄 없이 경유만 시킬 방법이 없습니다.

큰 대역을 한 노드에 통째로 걸면 줄 하나짜리 경유가 성립할 수 있습니다. `10.244.0.0/16` 을 노드 하나로 보내고 그 노드가 나머지로 넘겨 준다면 줄은 하나로 끝납니다. 대신 다른 노드로 갈 트래픽이 전부 그 노드를 지납니다. 그 노드가 병목이 되고 죽으면 클러스터 전체가 밖에서 안 보입니다. 줄 하나를 아끼고 단일 장애점을 얻는 거래이므로 노드마다 한 줄씩 넣는 쪽이 낫습니다.

방향이 또 갈렸습니다. 들어오는 쪽은 Flat 인데 나가는 쪽은 Island 인 상태가 만들어졌습니다. VM 은 `10.244.2.153` 으로 직접 요청을 보낼 수 있는데, 그 Pod 가 VM 을 부르면 출발지가 `172.18.0.4` 로 바뀌어 도착합니다. [04-01](./04-01.Kubernetes%20%EB%84%A4%ED%8A%B8%EC%9B%8C%ED%82%B9%20%EB%AA%A8%EB%8D%B8%20%E2%80%94%20Pod%20IP%C2%B7%EB%A0%88%EC%9D%B4%EC%95%84%EC%9B%83%C2%B7Probe.md) 의 레이아웃 표를 방향 축으로 나눠 적어 둔 이유가 여기서 값을 합니다.

실습이 끝난 뒤 넣었던 경로를 빼고 다시 두드리니 `000 · 4.00s` 로 돌아왔습니다. 되돌려서 원래 증상이 재현되는 것까지가 한 실험입니다.
