# networking-and-kubernetes 오답 노트

> 복습 회차에서 quality ≤ 3 인 질문을 박제한다. 같은 패턴이 3회 이상 반복되면 원본 챕터 본문 보강 트리거.

## 2026-09-06 — 01-02 Transport 계층 Q1: 시퀀스 번호는 무엇을 세는가

- **자기 답**: "서버와 클라이언트가 가진 연속된 번호" — 무엇의 연속인지 미도달
- **정답**: 바이트를 센다. 경로 중간에서 세그먼트가 쪼개져 패킷 경계를 신뢰할 수 없으므로, 바이트를 세야 쪼개짐과 무관하게 양쪽 셈이 유지된다 (원본 §2·§4)
- **원인 추정**: 개념 혼동 — "연속"이라는 성질만 남고 단위가 빠짐. 8일 만의 2연속 재발
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-06 — 01-02 Transport 계층 Q2: TIME_WAIT 은 어느 쪽에 남는가

- **자기 답**: "일반적으로 서버에서 발생". 확인 질문에서도 "받는 입장에서 발생"으로 방향을 뒤집음
- **정답**: 먼저 `close` 를 호출한 쪽. 역할이 아니라 순서가 정한다. 마지막 ACK 유실에 대비해 2MSL 대기 (원본 §3)
- **원인 추정**: 방향 오류 — 능동/수동 종료자 구분이 서 있지 않음. 2연속 재발
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-06 — 01-02 Transport 계층 Q4: HTTPS 첫 요청의 왕복 수

- **자기 답**: "대략 15번". 구성 요소(3-way·hello·키 교환) 분해는 정확
- **정답**: 3 왕복 = TCP 1 + TLS 1.2 2. RTT 150ms 경로면 첫 바이트 전 450ms (원본 §5)
- **원인 추정**: 계수 단위 혼동 — 메시지 수와 왕복 수를 구분하지 못함. 지연 환산 미실시
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-06 — 01-02 Transport 계층 Q5: CLOSE_WAIT 과 TIME_WAIT 중 버그 신호

- **자기 답**: TIME_WAIT (상태 표를 미리 제공한 뒤에도 반대로 답함)
- **정답**: CLOSE_WAIT. 타이머가 없어 애플리케이션이 `close` 를 부르지 않으면 영구히 남는다. TIME_WAIT 은 2MSL 뒤 자동 소멸 (원본 §3)
- **원인 추정**: 판별 기준(타이머 유무) 미보유. 상태 이름은 알아도 소멸 주체를 모름
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-06 — 01-01 OSI 모델 Q2: NCP 몰락과 IP 분리

- **자기 답**: 몰락 원인을 "유지보수 난이도"로 잡고, NCP→7계층→4계층을 한 줄기로 이음. IP 분리 후 책임 분담 미답
- **정답**: 원인은 네트워크의 **다양성·규모**를 감당 못한 것. RFC 791 이후 전달은 IP 가 best-effort, 신뢰성은 양 끝단 TCP (원본 §1·§3)
- **원인 추정**: NCP 몰락과 OSI 패배를 한 사건으로 묶는 오해 — 2026-08-15 Phase 4 에서 나와 §3 을 보강했던 바로 그 자리의 **재발**
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-06 — 01-01 OSI 모델 Q3: PDU 이름

- **자기 답**: Frame 하나만. 캡슐화는 "헤더를 붙이며 내려간다"까지
- **정답**: `Data → Segment(TCP)·Datagram(UDP) → Packet → Frame → Bit`. 송신은 내려가며 붙이고 수신은 올라가며 벗긴다 (원본 §2)
- **원인 추정**: 용어 회상 약점. 원리(헤더가 붙을 때마다 이름이 갈림)와 이름표가 연결돼 있지 않음
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-06 — 01-01 OSI 모델 Q5: NCP 몰락 ≠ OSI 패배

- **자기 답**: "다른 사건"·NCP 확장성까지는 도달. 묶었을 때 생기는 오해 자체를 못 짚음
- **정답**: 묶으면 "OSI 는 안 쪼갠 쪽"이라는 정반대 오해가 생긴다. **NCP 는 덜 쪼개서 졌고 OSI 는 더 쪼갰는데도 졌다** (원본 §3)
- **원인 추정**: 같은 회차 Q2 에서 교정한 직후였으므로 깨끗한 인출 아님. 재확인 필요
- **재방문 트리거**: 2026-09-07 재학습

## 2026-09-17 — 02-01 §4 Q7: 규칙에 없는데 패킷이 막힌다

- **자기 답**: "iptables 에서 변조하고 이후에 드랍" → 되묻기 1회 "방화벽?" → 되묻기 2회 후 "정확히 모르겠음"
- **정답**: **Martian 패킷 검사와 reverse path filter(rp_filter)**. 둘 다 Netfilter 훅이 아니라 **라우팅 코드에서 발화**하므로 `iptables -L` 에 안 보인다. rp_filter 는 출발지로 라우팅을 거꾸로 조회해 되돌아갈 경로가 들어온 인터페이스와 맞는지 본다(`0` 안 함 · `1` 엄격 · `2` 느슨). 로그는 `log_martians` (원본 02-01 §4)
- **원인 추정**: **경계 인식 오류** — "패킷을 버리는 일"을 전부 Netfilter 훅 안쪽으로 봄. 같은 회차 Q3 에서 본인이 "PRE_ROUTING → 라우팅 판단 → FORWARD"라고 적었는데 그 가운데 단계를 후보로 떠올리지 못함
- **재방문 트리거**: 2026-09-20 회차 2 — 최우선

## 2026-09-17 — 02-02 §3 Q5: gRPC 스케일아웃 뒤 쏠림

- **자기 답**: "iptables 의 이슈였고 **IPVS 에서는 해결된다**". 쏠림 양상도 "50/50 → 50/20×5" 로 그림
- **정답**: 규칙을 보는 것은 **연결의 첫 패킷뿐**이다. DNAT 한 순간 conntrack 항목이 생기고 이후 패킷은 규칙을 다시 평가하지 않는다. HTTP/2 연결을 재사용하는 gRPC 클라이언트는 처음의 2개에 계속 붙는다. **모드를 바꿔도 안 풀린다** — 원인이 분배 알고리즘이 아니라 연결이 새로 맺어지지 않는 데 있다. 기존 연결은 2개에 그대로 있고 **새 연결만** 6개로 갈린다 (원본 02-02 §3)
- **원인 추정**: **층 혼동** — "규칙 평가"와 "변환 적용"을 한 층으로 봄. 같은 오해가 뒤에 다시 나옴("첫 패킷만 DNAT 되면 10번 중 1번만 성공하는 것 아닌가"). DNAT 은 계속 걸리고, 다시 뽑지 않을 뿐이다
- **재방문 트리거**: 2026-09-20 회차 2
- **본문 보강 후보**: *"규칙 평가와 변환 적용은 다른 층"* 을 콕 집는 도식이 02-01 §5·02-02 §3 어디에도 없다. 이 오해가 그 공백의 증거

## 2026-09-17 — 02-01 §4 Q2: 테이블 순서가 왜 그 순서인가

- **자기 답**: "데이터 변경이나 캡처, 필터가 되는 **위치가 모두 달라서**" + "필터가 먼저면 NAT 로직이 원하는 대로 안 될 수 있음"
- **정답**: 뒤 절반은 맞다(값을 바꾸는 쪽이 먼저, 그 값으로 결정하는 쪽이 나중 — filter 가 앞서면 ClusterIP 를 보게 되어 Pod IP 허용 규칙이 발화하지 않는다). 빠진 것은 **왜 그렇게 불리는가** — 네 테이블이 같은 훅에 **우선순위 정수**로 등록돼 있고 커널이 숫자 순으로 부른다(raw -300 · conntrack -200 · mangle -150 · DNAT -100 · filter 0 · SNAT 100). raw 가 conntrack 보다 100 앞서 있어서 `NOTRACK` 이 raw 에서만 성립한다 (원본 02-01 §4, 02-02 §1)
- **원인 추정**: 순서를 **iptables 의 규약**으로 봄. 실제로는 커널 상수라 백엔드(nftables)가 바뀌어도 같다. "위치가 다르다"는 훅 축의 답이고 질문은 같은 훅 *안*의 순서였다
- **재방문 트리거**: 2026-09-20 회차 2

## 2026-09-17 — 02-01 §4 Q3: INPUT 과 FORWARD 가 갈리는 기준

- **자기 답**: "INPUT 은 **노드 안에 파드가 있는 경우**, 아닌 경우 FORWARD". 되묻기 1회 뒤 "파드로 바뀌면 자신의 주소가 아니라 FORWARD" 로 도달
- **정답**: 기준은 Pod 의 물리적 위치가 아니라 **DNAT 후 목적지 IP 가 이 호스트의 것인가**이다. Pod 는 별도 네트워크 네임스페이스라 같은 노드에 있어도 목적지는 `10.244.1.66` 이지 노드 IP 가 아니다 — **같은 노드든 다른 노드든 둘 다 FORWARD**. `LOCAL` 은 누가 만들었는가가 아니라 이 호스트가 종점·기점인가를 가리킨다 (원본 02-01 §4)
- **원인 추정**: 훅 갈림을 **배치(topology)** 로 읽음. 커널이 보는 것은 주소 하나다
- **재방문 트리거**: 2026-09-20 회차 2

## 2026-09-17 — 02-05 §1 Q6: ICMP unreachable 두 줄 읽기

- **자기 답**: 출발지 `10.10.1.1` 은 짚었으나 "도달 못했다고 뜬다"에서 멈춤. 결론(누가 거절을 만들었나) 미도달, 첫 줄(SYN)을 못 읽음
- **정답**: 둘째 줄을 두 토막으로 갈라야 한다 — `10.10.1.1 > 10.10.1.11` 이 **봉투**(출발지·목적지)이고 `192.168.139.238 tcp port 9000 unreachable` 은 **내용**이다. `10.10.1.1` 은 브리지 `br0`, 곧 **중계 호스트가 거절을 지어내 보냈다**. 보조 근거는 0.3ms 라는 간격 — 옆 노드까지 갔다 왔다면 불가능. 첫 줄은 `ns1` 이 보낸 SYN(`Flags [S]`) (원본 02-05 §1)
- **원인 추정**: ICMP 페이로드의 인용 주소를 **패킷의 발신인**으로 읽음. 축을 갈라야 한다 — 출발지 IP 는 "중간이냐 끝이냐"만, "규칙이냐 소켓 없음이냐"는 프로토콜(ICMP vs RST)이 가른다
- **재방문 트리거**: 2026-09-20 회차 2
