# Cilium IPAM 모드는 Pod 대역을 누가 나눠 주는지로 갈린다

---

> Pod IP 는 클러스터 대역, 노드 PodCIDR, 개별 주소 순서로 좁혀지고 IPAM 모드는 가운데 단계인 노드 PodCIDR 을 누가 나눠 주는지에 따라 다섯 갈래로 나뉩니다.



## 핵심 요약

> 노드 PodCIDR 을 누가 정하고 나눠 주는지에 따라 Cilium IPAM 모드가 다섯 갈래로 갈립니다. 이 선택이 운영 중 대역 확장 가능 여부와 노드당 대역 수를 결정합니다.

**IPAM**(IP Address Management)은 Pod 에 IP 주소를 나눠 주고 회수하는 기능입니다. **PodCIDR** 은 한 노드의 Pod 들이 나눠 쓸 IP 서브넷 대역입니다. `10.0.1.0/24` 의 `/24` 는 주소 앞 24비트가 네트워크 부분이라는 뜻입니다.

Host Scope 는 쿠버네티스가 나눈 대역을 읽습니다. Cluster Scope 는 `cilium-operator` 가 `CiliumNode` 리소스로 대역을 나눕니다. `cilium-operator` 는 클러스터 전역 작업을 맡는 컨트롤러입니다. `cilium-agent`(에이전트)는 노드마다 도는 Cilium 데몬입니다. `CiliumNode` 는 Cilium 이 노드별 IPAM 상태와 네트워크 정보를 적는 커스텀 리소스입니다.

Multi-Pool 은 네임스페이스나 주석마다 다른 풀에서 주소를 줍니다. CRD-backed 와 ENI 는 주소의 출처가 Cilium 밖(외부 오퍼레이터, AWS ENI)에 있습니다. 기준은 Cilium 1.20.5 문서(v1.20)입니다.

주소 계열은 IPv4 단독, 듀얼 스택(IPv4 와 IPv6 를 함께 쓰는 구성), IPv6 전용 중에서 고릅니다. 듀얼 스택은 Pod 와 Service 가 주소를 둘씩 받습니다. IPv6 전용은 외부 의존성을 파악한 새 클러스터에 맞습니다. IPAM 모드와 주소 계열 모두 운영 중에 바꾸면 연결이 끊길 수 있어 클러스터를 만들 때 정합니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

1. Pod IP 를 세 단계로 나누는 이유와 모드를 고르는 기준을 설명할 수 있습니다.
2. Host Scope 에서 노드 대역이 내려오는 순서와 바꾸기 어려운 이유를 말할 수 있습니다.
3. Cluster Scope 의 기본값과 대역 소진 때의 증상, 확장 방법을 설명할 수 있습니다.
4. Multi-Pool 의 풀 선택 순서와 라우팅을 맡는 장치를 설명할 수 있습니다.
5. CRD-backed·ENI 의 주소 출처와 듀얼 스택·IPv6 전용의 차이를 비교할 수 있습니다.

아래 그림은 「노드 PodCIDR 을 누가 나눠 주는가」라는 물음에서 다섯 모드가 갈리는 줄기를 한 장으로 보입니다. 맨 위 1절의 3단계 분할 가운데에서 다섯 모드가 세 갈래로 나뉩니다.

아래 점선 칸의 주소 계열 선택은 이 배분 갈래 밖의 별도 축이며 6절이 다룹니다. 모드 카드에 적힌 칩 번호가 그 모드를 다루는 절입니다.

![Pod 대역을 누가 나누는지로 갈리는 IPAM 모드 다섯 가지와 3단계 분할 구조](./_assets/04-01.chapter-overview.svg)



## Pod 대역을 누가 나누는가

> Pod IP 는 클러스터 풀, 노드 PodCIDR, 개별 Pod IP 세 단계를 거치며 가운데 단계를 누가 맡느냐로 다섯 모드가 갈립니다. 주소 계열(IPv4·듀얼 스택·IPv6 전용)은 이 배분 흐름 밖에서 따로 고릅니다.

Pod 마다 IP 를 주려면 클러스터 대역을 쪼개야 합니다. 이때 어느 모드를 고르는지 모르면 운영 중 대역이 바닥나거나 모드를 바꾸지 못해 통신이 막히는 문제에 부딪힙니다.

| 단계 또는 갈래 | 주체 | 하는 일 | 받치는 개념 | 절 |
|---|---|---|---|---|
| 1 클러스터 풀 → 2 노드 몫 → 3 Pod IP | 관리자 · 에이전트 | 대역을 미리 쪼개 경합을 피하고 모드를 고름 | 3단계 분할과 모드 선택 | 1 |
| 2 노드 몫(갈래 A: Host Scope) | `kube-controller-manager` → 에이전트 | 쿠버네티스가 `Node` 에 적은 `podCIDRs` 를 읽음 | `Node.spec.podCIDRs` | 2 |
| 2 노드 몫(갈래 B-1: Cluster Scope) | `cilium-operator` → 에이전트 | 오퍼레이터가 `CiliumNode` 에 노드 몫을 나눔 | `CiliumNode` 와 마스크 크기 | 3 |
| 2 노드 몫(갈래 B-2: Multi-Pool) | `cilium-operator` → 에이전트 | 워크로드 속성마다 다른 풀에서 `/27` 등을 뗌 | `CiliumPodIPPool` 과 별도 라우팅 | 4 |
| 2 노드 몫(갈래 C: CRD-backed·ENI) | 외부 오퍼레이터, 또는 `cilium-operator` 와 EC2 API → 에이전트 | 외부 주소 목록이나 VPC ENI 보조 IP 를 받음 | 외부 주소 목록과 VPC ENI | 5 |

6절은 이 배분 흐름 밖에서 주소 계열(IPv4 단독·듀얼 스택·IPv6 전용)을 고르는 기준과 설정을 다룹니다.



## 1. 3단계 IP 분할과 모드 선택

> 클러스터 풀을 노드 단위로 미리 쪼개 두면 Pod 가 뜰 때 중앙과 통신하지 않아도 됩니다. 모드를 고르는 질문은 이 쪼개는 일을 누가 하느냐입니다.

흐름 위치: 1 클러스터 풀 → 2 노드 몫 → 3 Pod IP · 받치는 개념 — 3단계 분할과 모드 선택

Pod 가 뜰 때마다 수백 대의 노드가 하나의 클러스터 풀에서 주소를 직접 꺼내면 중앙 저장소에 경합이 생겨 지연과 충돌을 피할 수 없습니다. 이를 막으려고 Cilium 은 주소를 클러스터 풀, 노드 PodCIDR, 개별 Pod IP 세 단계로 쪼개고 가운데 단계의 주체를 모드로 나눕니다.

![클러스터 풀에서 Pod IP 까지 세 단계](./_assets/04-01.ipam-layers.svg)

### 노드별 PodCIDR 선할당 이유

위 그림처럼 `cilium-operator` 는 큰 클러스터 풀 `10.0.0.0/8` 에서 노드 몫 `/24` 를 떼어 줍니다. 노드의 에이전트는 중앙과 통신하지 않고 자기 몫 안에서 Pod IP `10.0.1.235` 를 내줍니다. Cilium 의 [Cluster Scope 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/cluster-pool/)도 노드마다 PodCIDR 을 배정한 뒤 각 노드의 에이전트가 IP 를 나눠 준다고 설명합니다. 문서가 이 노드 안 할당기를 host-scope 할당기라 부르지만 Host Scope 모드와는 다른 말입니다. 노드 대역 안에서는 Pod 주소 외에도 노드 내부 라우터(`router`)와 헬스체크(`health`) 주소가 함께 나갑니다.

쿠버네티스의 노드 대역 배분은 [Kubernetes 네트워킹 모델 3절](../networking-and-kubernetes/04-01.Kubernetes%20네트워킹%20모델%20—%20Pod%20IP·레이아웃·Probe.md)에, CIDR 계산은 [IP — 데이터그램과 주소 2절](../../../02_os/book/cntd_computer-networking-top-down/04-03.IP%20—%20데이터그램과%20주소.md)에 있습니다.

### IPAM 모드 다섯 가지 비교와 선택

| 모드 | 대역 배분 주체 | 노드당 대역 · 확장 차이 | 고를 상황 |
|---|---|---|---|
| Host Scope | 쿠버네티스 (`Node`) | 노드당 1개 고정 · 동적 확장 불가 | 쿠버네티스가 이미 PodCIDR 을 주고 바꿀 일이 없다 |
| Cluster Scope | `cilium-operator` (`CiliumNode`) | 노드당 1개 · 클러스터 풀 여러 개 가능 | 쿠버네티스 설정과 무관하게 Cilium 이 관리한다 |
| Multi-Pool | `cilium-operator` (`CiliumPodIPPool`) | 풀마다 여러 개 · 동적 추가 가능 | 테넌트마다 다른 대역이 필요하거나 대역을 키워야 한다 |
| CRD-backed | 외부 오퍼레이터 (`CiliumNode`) | 가용 주소 목록 · 직접 라우팅만 지원 | 별도 오퍼레이터나 관리형 클라우드가 주소를 관리한다 |
| ENI | `cilium-operator` · EC2 API | ENI 별 보조 IP `/32` · `PD`(prefix delegation) 시 `/28` | AWS 에서 Pod 가 VPC 주소를 직접 받아야 한다 |

**Helm** 은 쿠버네티스 패키지·설정 배포 도구입니다. Helm 의 `ipam.mode` 기본값은 `cluster-pool` 입니다([Helm 레퍼런스](https://docs.cilium.io/en/v1.20/helm-reference/)). 모드는 운영 중에 바꾸지 않는 것이 원칙입니다. 가장 안전한 길은 새 클러스터를 만드는 것입니다. 온라인 이전은 `cluster-pool` 에서 `multi-pool` 로 가는 경로뿐입니다([IPAM 개요](https://docs.cilium.io/en/v1.20/network/concepts/ipam/)).



## 2. Host Scope 와 Node 대역

> Host Scope 에서 Cilium 은 대역을 정하지 않고 노드에 적힌 값을 읽습니다. 배우기는 쉽지만 대역 크기와 개수가 쿠버네티스 설정에 묶입니다.

흐름 위치: 2 노드 몫(갈래 A: Host Scope) · 받치는 개념 — Node.spec.podCIDRs

### 노드 합류 시 PodCIDR 전달 순서

쿠버네티스가 노드 대역을 이미 나눠 주는 환경이면 Cilium 은 대역을 따로 쪼갤 필요가 없습니다. 관리자가 `kube-controller-manager` 에 `--allocate-node-cidrs` 옵션을 줍니다. 그러면 새 노드의 `Node` 에 `spec.podCIDRs` 가 기록됩니다. `kube-controller-manager` 는 쿠버네티스의 기본 컨트롤러입니다. Cilium 에이전트는 시작할 때 이 값이 나타날 때까지 기다렸다가 그 범위에서 Pod IP 를 배정합니다([Host Scope 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/kubernetes/)).

![노드 합류 시 Host Scope 대역 전달 순서](./_assets/04-01.host-scope-swimlane.svg)

이 모드는 `ipam.mode=kubernetes` 이고 [03-01](./03-01.Cilium%20은%20kind%20클러스터에%20Helm%20으로%20설치하고%20정책과%20Hubble%20로%20동작을%20확인한다.md)의 설치 실습과 같은 값입니다. **kind** 는 Docker 컨테이너로 노드를 띄우는 로컬 쿠버네티스 도구입니다. 기본 Pod 대역으로 `10.244.0.0/16` 을 씁니다([kind 설정 문서](https://kind.sigs.k8s.io/docs/user/configuration/)). 쿠버네티스는 노드마다 `/24` 를 주므로 예시 노드의 값과 Pod 주소(`10.244.1.20`)는 다음과 같습니다.

```bash
kubectl get node kind-worker -o jsonpath='{.spec.podCIDRs}'
["10.244.1.0/24"]

kubectl get pods -o wide
NAME              READY   STATUS    IP            NODE
netshoot-client   1/1     Running   10.244.1.20   kind-worker
```

### 대역 확장 제약과 모드 변경 위험

Host Scope 에는 한계가 둘 있습니다. 노드 PodCIDR 크기는 클러스터 전체에 하나만 정할 수 있습니다. 또한 클러스터나 개별 노드에 CIDR 을 더하거나 뺄 수도 없습니다. 1절 비교표에서 클러스터 풀도 하나뿐이고 노드당 대역도 1개로 고정된 모드는 Host Scope 뿐입니다. 이 한계가 다음 모드를 찾게 만듭니다.

운영 중 IPAM 모드를 바꾸는 작업도 위험합니다. 실제로 `cluster-pool` 환경에서 Helm 업그레이드 중 `ipam.mode` 를 `kubernetes` 로 잘못 바꿔 머지한 사례가 있습니다. 노드의 Pod CIDR 이 갑자기 바뀌면서 Pod 간 통신이 전면 중단됐습니다.

Helm 롤백으로 **CNI**(Container Network Interface, Pod 에 네트워크를 붙이는 플러그인 규격) 자체는 수습했습니다. 하지만 헬스체크 실패가 누적된 분산 데이터베이스는 정합성이 깨져 복구 작업이 크게 늘어났습니다. IPAM 모드는 클러스터 설계 단계에서 확정해야 합니다. 이후 업그레이드에서는 Helm values 의 diff 를 최소 두 사람이 교차 점검해야 이런 사고를 막을 수 있습니다.



## 3. Cluster Scope 대역 배분

> Cluster Scope 는 대역 배분을 쿠버네티스에서 Cilium 으로 가져옵니다. 쿠버네티스가 PodCIDR 을 주도록 설정되어 있지 않아도 동작하므로 기본 모드가 됩니다.

흐름 위치: 2 노드 몫(갈래 B-1: Cluster Scope) · 받치는 개념 — CiliumNode 와 마스크 크기

Host Scope 와 달리 Cluster Scope 에서는 `cilium-operator` 가 노드 몫을 직접 정해 `CiliumNode` 에 씁니다. 풀을 너무 작게 잡으면 에이전트가 몫을 다 써 새 Pod 가 멈추기까지 어떤 순서로 진행되는지 아래 흐름이 보여 줍니다.

![Cluster Scope 의 대역 기록과 소진](./_assets/04-01.cluster-scope-sequence.svg)

### Helm 기본값과 CiliumNode 몫

`cilium-operator` 는 노드별 PodCIDR 을 `CiliumNode` 의 `spec.ipam.podCIDRs` 에 적습니다. 에이전트는 그 값이 나온 뒤 자기 몫에서 주소를 고릅니다([Cluster Scope 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/cluster-pool/)). 대역 배분을 노드마다 하지 않고 클러스터에 하나뿐인 오퍼레이터가 맡는 이유는 [02-01 2절](./02-01.Cilium%20은%20에이전트·CNI%20플러그인·오퍼레이터로%20나눠%20노드와%20클러스터를%20맡는다.md)에서 다뤘습니다.

기본값은 클러스터 풀 `10.0.0.0/8` 과 노드 몫 `/24` 입니다. 풀 목록은 Helm 값 `ipam.operator.clusterPoolIPv4PodCIDRList` 로 바꿉니다. 노드 몫은 `ipam.operator.clusterPoolIPv4MaskSize` 로 바꿉니다([Helm 레퍼런스](https://docs.cilium.io/en/v1.20/helm-reference/)). `/24` 마스크는 주소 256개를 뜻하고, 네트워크·브로드캐스트 주소 둘을 뺀 254개를 할당할 수 있습니다. 예시 kind 클러스터에서는 이렇게 나옵니다.

```bash
cilium config view | grep cluster-pool
cluster-pool-ipv4-cidr                                      10.0.0.0/8
cluster-pool-ipv4-mask-size                                 24
ipam                                                        cluster-pool

kubectl get ciliumnode -o json | jq -r '.items[] |
    "NODE: \(.metadata.name) CIDR: \(.spec.ipam.podCIDRs[0])"'
NODE: kind-control-plane CIDR: 10.0.0.0/24
NODE: kind-worker CIDR: 10.0.1.0/24
NODE: kind-worker2 CIDR: 10.0.2.0/24
```

기본 풀 `10.0.0.0/8` 이 노드 네트워크와 겹치면 다른 노드로 가는 트래픽을 Pod 로 오인해 연결이 끊깁니다. 설치 전에 `clusterPoolIPv4PodCIDRList` 를 노드 대역과 겹치지 않게 바꿉니다.

### 몫 소진 시 ContainerCreating 멈춤

작은 풀로 소진을 재현하는 예시는 `/28` 두 개를 풀로 주고 노드 몫을 `/29` 로 잡은 설정입니다.

```yaml
ipam:
  mode: cluster-pool
  operator:
    clusterPoolIPv4MaskSize: 29
    clusterPoolIPv4PodCIDRList:
      - 10.0.42.0/28
      - 10.0.84.0/28
```

`/28` 하나에는 `/29` 가 둘 들어갑니다. 그래서 세 번째 노드는 두 번째 블록에서 몫을 받습니다(`10.0.84.8/29`). 할당기는 CIDR 블록마다 네트워크·브로드캐스트 주소 둘을 뺍니다([Cluster Scope 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/cluster-pool/)). 주소 8개인 `/29` 에서 할당 대상은 6개입니다.

마지막 노드에 replica 10개를 고정하면 일부 Pod 가 `ContainerCreating` 에서 멈추고 에이전트가 몫 소진을 보고합니다. `ContainerCreating` 은 컨테이너가 아직 만들어지지 않은 상태입니다. Pod 에 IP 를 붙이지 못해도 이 상태에 머뭅니다.

```bash
kubectl exec -it cilium-qrw2f -n kube-system -- cilium-dbg status
IPAM:                            IPv4: 6/6 allocated from 10.0.84.8/29,
```

`/24` 노드에서 `cilium-dbg status --ver` 를 보면 Pod `10.0.1.235` 말고도 두 주소가 같은 대역에서 나갑니다. 노드 내부 라우터(`router`, `10.0.1.133`)와 헬스체크 엔드포인트(`health`, `10.0.1.238`)입니다. [에이전트 소스](https://github.com/cilium/cilium/blob/v1.20.2/daemon/infraendpoints/infra_ip_allocation.go)를 보면 두 주소는 Pod 와 같은 IPAM 기본 풀에서 할당됩니다. 따라서 `/29` 노드에서도 실제 Pod 에 줄 수 있는 주소는 6개보다 적습니다.

풀이 바닥나면 `clusterPoolIPv4PodCIDRList` 에 새 항목을 덧붙입니다. 기존 항목을 고치면 예기치 않은 동작이 생깁니다. `clusterPoolIPv4MaskSize` 도 바꿀 수 없으므로 풀은 처음부터 넉넉히 잡습니다. 모든 Pod 가 같은 풀에서 받는다는 한계는 Multi-Pool 이 풀어 줍니다.



## 4. Multi-Pool 과 다중 풀 배분

> Multi-Pool 은 풀을 여러 개 두고 워크로드 속성으로 풀을 고릅니다. 한 노드가 풀마다 대역을 따로 받으므로 테넌트별 대역 분리와 동적 확장이 가능합니다.

흐름 위치: 2 노드 몫(갈래 B-2: Multi-Pool) · 받치는 개념 — CiliumPodIPPool 과 별도 라우팅

### CiliumPodIPPool 선언과 주석 선택

테넌트마다 다른 IP 대역을 쓰거나 실행 중 몫이 모자랄 때는 풀을 여러 개 둡니다. **CiliumPodIPPool** 커스텀 리소스로 풀을 선언하고 주석이나 셀렉터로 연결합니다. 아래 흐름은 한 노드가 풀마다 `/27` 을 따로 받고 수요가 40개로 늘 때 두 번째 `/27` 을 동적으로 붙이는 모습입니다.

![네임스페이스별 풀 선택과 동적 /27 확장](./_assets/04-01.multi-pool-flow.svg)

`multi-pool` 모드에서 `autoCreateCiliumPodIPPools` 를 주면 오퍼레이터가 시작할 때 `default` 풀을 만듭니다. 아래 설정은 그 예시입니다. `routingMode: native` 는 터널 캡슐화 없이 노드 사이를 직접 라우팅하는 방식입니다. `endpointRoutes` 는 `cilium_host` 인터페이스를 거치는 대신 Pod 마다 개별 경로를 만듭니다. `ipv4NativeRoutingCIDR` 은 직접 라우팅할 Pod 대역 전체를 알려 줍니다. 이 범위로 가는 트래픽에는 SNAT 를 적용하지 않습니다([Helm 레퍼런스](https://docs.cilium.io/en/v1.20/helm-reference/)).

```yaml
ipam:
  mode: multi-pool
  operator:
    autoCreateCiliumPodIPPools:
      default:
        ipv4:
          cidrs: ["10.10.0.0/16"]
          maskSize: 27
endpointRoutes:
  enabled: true
routingMode: native
autoDirectNodeRoutes: true
ipv4NativeRoutingCIDR: 10.0.0.0/8
```

테넌트 둘의 풀을 만들고 네임스페이스에 풀 이름을 주석으로 답니다. `foobar-pool` 은 `10.30.0.0/16` 입니다.

```yaml
apiVersion: cilium.io/v2alpha1
kind: CiliumPodIPPool
metadata:
  name: acme-pool
spec:
  ipv4:
    cidrs: ["10.20.0.0/16"]
    maskSize: 27
```

```bash
kubectl annotate ns acme-corp ipam.cilium.io/ip-pool=acme-pool
kubectl annotate ns foobar-inc ipam.cilium.io/ip-pool=foobar-pool
```

[Multi-Pool 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/multi-pool/)가 정한 풀 선택 순서는 셋입니다. 먼저 Pod 나 네임스페이스의 `ipam.cilium.io/ip-pool` 주석을 봅니다. 없으면 풀의 `podSelector`·`namespaceSelector` 에 맞는 풀을 씁니다. 어느 것에도 맞지 않으면 `default` 풀을 씁니다.

Pod 는 주소 계열마다 하나의 풀에만 맞아야 하고 둘 이상에 맞으면 할당이 실패합니다. 주석은 Pod 를 만들 때만 읽힙니다. `ipam.cilium.io/require-pool-match="true"` 를 달면 맞는 풀이 없을 때 `default` 로 떨어지는 대신 할당을 막습니다. Pod 가 직접 풀을 요청할 수도 있어 이 선택은 격리 수단이 아닌 운영 편의 장치입니다.

같은 노드가 풀마다 대역을 받는 모습은 `CiliumNode` 에 드러납니다. `acme` 디플로이먼트를 40 replica 로 키운 뒤 `kind-worker2` 의 값입니다.

```yaml
pools:
  allocated:
    - {cidrs: [10.20.0.0/27, 10.20.0.32/27], pool: acme-pool}
    - {cidrs: [10.10.0.0/27], pool: default}
    - {cidrs: [10.30.0.0/27], pool: foobar-pool}
  requested:
    - {needed: {ipv4-addrs: 40}, pool: acme-pool}
    - {needed: {ipv4-addrs: 16}, pool: default}
    - {needed: {ipv4-addrs: 10}, pool: foobar-pool}
```

`requested` 는 에이전트가 적는 수요이고 `allocated` 는 오퍼레이터가 채우는 공급입니다. 블록의 첫·끝 주소는 예약되므로 `/27` 에서 쓸 수 있는 주소는 30개입니다. `acme` Pod 는 `10.20.0.25`, `foobar` Pod 는 `10.30.0.28` 처럼 자기 풀의 `/27` 에서 주소를 받습니다. replica 10개는 블록 하나로 충분하지만 40개는 모자라 두 번째 `/27`(`10.20.0.32/27`)이 붙었습니다.

에이전트는 `default` 풀에서만 주소 8개를 미리 확보하는 것이 기본 설정(`default=8`)입니다. 필요한 수는 사용 중인 주소와 대기 중인 요청에 8을 더한 값을 8의 배수로 올려 구합니다(`roundUp(사용 중 + 대기 + 8, 8)`). `router`·`health` 둘이 쓰는 상태면 2 + 0 + 8 = 10 을 올려 16입니다. 미리 잡는 몫이 없는 풀은 사용 중인 개수가 그대로 10과 40입니다.

### 다중 풀 환경의 별도 라우팅

같은 노드의 Pod 가 서로 다른 대역을 받으면 다른 노드는 두 대역이 모두 그 노드에 있다는 사실을 알아야 합니다. IPAM 은 주소만 나눠 주고 경로는 만들지 않습니다. 같은 L2(스위치로 직접 이어진 망)의 노드끼리는 `autoDirectNodeRoutes` 가 경로를 만듭니다. L3 경계 밖으로는 Cilium BGP Control Plane 이 PodCIDR 을 광고합니다. BGP 는 라우터끼리 경로를 주고받는 프로토콜입니다([Multi-Pool 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/multi-pool/)).

위 실습이 `routingMode: native` 와 `autoDirectNodeRoutes: true` 를 함께 둔 이유입니다. 다만 Multi-Pool 은 패킷을 VXLAN 등으로 감싸 넘기는 터널 라우팅도 지원하므로 `native` 가 필수 조건은 아닙니다([IPAM 개요](https://docs.cilium.io/en/v1.20/network/concepts/ipam/)). 풀끼리는 CIDR 이 겹칠 수 없습니다. 한 번 만든 풀의 마스크 크기도 바꿀 수 없습니다. 새 풀과 새 CIDR 은 실행 중에 더할 수 있습니다.



## 5. CRD-backed 와 AWS ENI 모드

> 두 모드는 에이전트가 주소 목록을 `CiliumNode` 에서 읽는다는 점이 같습니다. 주소의 출처(외부 오퍼레이터나 AWS ENI)가 Cilium 밖에 있으므로 라우팅과 한도도 외부 조건에 묶입니다.

흐름 위치: 2 노드 몫(갈래 C: CRD-backed·ENI) · 받치는 개념 — 외부 주소 목록과 VPC ENI

### CRD-backed 의 외부 주소 목록

클라우드 제어 평면이나 별도 오퍼레이터가 이미 IP 를 배분하고 있을 때는 Cilium 이 대역을 다시 쪼개면 충돌이 납니다. `ipam.mode=crd` 로 켜면 외부 시스템이 `CiliumNode` 에 적어 준 주소만 에이전트가 받아 씁니다.

![CRD-backed 의 주소 목록 전달과 사용 기록](./_assets/04-01.crd-ipam-flow.svg)

에이전트는 자기 노드 이름과 같은 `CiliumNode` 를 지켜봅니다. `spec.ipam.available` 의 가용 목록에서 Pod IP 를 고릅니다. 할당한 주소는 `status.ipam.inuse` 에 적습니다([CRD-backed 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/crd/)). 목록을 채우는 쪽은 사용자나 외부 오퍼레이터입니다. `CiliumNode` 의 상태 갱신은 15초당 최대 1회로 제한되므로 Pod 가 한꺼번에 뜨면 `status` 반영이 뒤따를 수 있습니다.

이 모드에서 Cilium 은 할당된 CIDR 로 가는 경로를 만들지 않습니다. 노드 사이 라우팅은 관리자 몫이며 직접 라우팅만 지원합니다([IPAM 개요](https://docs.cilium.io/en/v1.20/network/concepts/ipam/)). 클라우드가 주소와 라우팅을 맡는 관리형 쿠버네티스에서 주로 쓰입니다.

### ENI 보조 IP 와 VPC 직접 라우팅

AWS 환경에서 Pod 가 VPC(AWS 가상 사설 네트워크) 주소를 직접 받아야 한다면 ENI 모드를 씁니다. **ENI**(Elastic Network Interface)는 EC2 인스턴스에 붙는 가상 네트워크 인터페이스입니다. 아래 배치는 ENI 의 보조 IP 가 Pod 주소로 이어지는 구조입니다.

![ENI 보조 IP 에서 Pod 주소까지](./_assets/04-01.eni-deployment.svg)

ENI 모드는 AWS 에서만 의미가 있고 EKS 든 EC2 위에 직접 구축한 클러스터든 쓸 수 있습니다. 켤 때는 `ipam.mode=eni` 와 Helm 값 `eni.enabled=true` 가 필요합니다([ENI 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/eni/)).

에이전트는 EC2 메타데이터(인스턴스 정보 조회 서비스)에서 인스턴스·VPC 정보를 읽어 `CiliumNode` 를 채웁니다. 에이전트가 필요한 주소 총수를 `spec.ipam.pools.requested` 에 적으면 오퍼레이터가 부족분을 계산합니다. 오퍼레이터는 EC2 API 로 ENI 와 IP 를 늘려 `status.eni.enis` 에 적습니다. 보조 IP 하나는 `/32` CIDR 로 `default` 풀에 올라갑니다. EC2 API 를 부르는 것은 오퍼레이터 하나뿐입니다.

예시 EKS 클러스터(eu-west-1)에 `echoserver` Pod 다섯 개를 띄웠습니다. Pod 들은 `192.168.156.61`, `192.168.142.65`, `192.168.131.53` 같은 주소를 받습니다. 노드 `ip-192-168-132-54` 의 `CiliumNode` 에는 ENI `eni-02f39382678db84b5` 아래 주소 아홉 개가 있습니다. 위 세 주소도 이 목록 안에 있습니다. Pod 주소가 VPC 안에서 바로 라우팅되므로 VPC 안 통신에는 NAT 가 필요 없습니다.

기본 설정에서는 `eni.awsEnablePrefixDelegation` 이 `false` 입니다([Helm 레퍼런스](https://docs.cilium.io/en/v1.20/helm-reference/)). 이때 노드 IP 상한은 인스턴스 타입별 ENI 수와 ENI 당 IP 수의 곱입니다([EC2 문서](https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/AvailableIpPerENI.html)). 노드당 Pod 수 공식은 [AWS 네트워킹과 EKS 5절](../networking-and-kubernetes/06-01.AWS%20네트워킹과%20EKS%20—%20VPC%20부품으로%20조립하는%20클러스터.md)에, VPC CNI 의 직접 할당 구조는 같은 문서 6절에 있습니다.

이 값을 `true` 로 두어 prefix delegation 을 켜면 보조 IP 칸마다 `/28` 블록이 위임됩니다([Cilium ENI 문서](https://docs.cilium.io/en/v1.20/network/concepts/ipam/eni/)). 그만큼 노드당 Pod 상한이 커집니다. 켠 상태에서 특정 노드만 끄려면 `spec.eni.disable-prefix-delegation` 을 씁니다. ENI 모드는 터널 라우팅을 지원하지 않습니다. IPv6 지원은 Cilium 1.20 문서 기준 베타입니다. 다른 CNI 가 먼저 깔릴 수 있는 환경에서는 `node.cilium.io/agent-not-ready` 테인트로 Pod 기동을 늦춥니다([테인트 문서](https://docs.cilium.io/en/v1.20/installation/taints/)).



## 6. 듀얼 스택과 IPv6 전용 클러스터

> 주소 계열은 기술보다 조직 전략과 운영 준비도가 먼저 정합니다. 듀얼 스택은 전환용으로 안전하고 IPv6 전용은 주변 도구를 모두 파악한 새 클러스터에서만 현실적입니다.

흐름 위치: 흐름 밖 — 주소 계열 선택(IPv4·듀얼 스택·IPv6 전용)

어떤 IPAM 모드를 고르든 주소 계열(IPv4 단독·듀얼 스택·IPv6 전용)을 따로 정해야 합니다. IPv4 를 끄고 IPv6 전용으로 가면 외부 IPv4 전용 서비스에 닿지 못하는 문제가 생기므로 아래처럼 변환 경로까지 함께 준비해야 합니다.

![듀얼 스택과 IPv6 전용의 주소·외부 통신 경로](./_assets/04-01.dual-vs-ipv6-only.svg)

| 항목 | 듀얼 스택 | IPv6 전용 |
|---|---|---|
| kind `ipFamily` | `dual` | `ipv6` (`podSubnet`, `serviceSubnet` 지정) |
| Cilium Helm 값 | `ipv6.enabled=true` | `ipv6.enabled=true`, `ipv4.enabled=false` |
| Pod 주소 | `10.244.1.117`, `fd00:10:244:1::8204` | `2001:db8:10:1::4d69` |
| Service 정책 · IP | `PreferDualStack` (`10.96.181.159`, `fd00:10:96::d4d5`) | `SingleStack` · `IPv6` (`2001:db8:10:96::6f43`) |
| 외부 IPv4 의존 | 직접 IPv4 통신 | NAT64 · DNS64 필요 |

### 듀얼 스택 Pod·Service 구성

단독 스택에서는 Pod 와 Service 가 주소 하나를 받습니다. 듀얼 스택에서는 IPv4 와 IPv6 를 하나씩 받아 두 계열로 클러스터 밖과 통신합니다. Cilium 은 IPv6 가 기본으로 꺼져 있어 `ipv6.enabled=true` 로 켭니다([Helm 레퍼런스](https://docs.cilium.io/en/v1.20/helm-reference/)).

예시 kind 클러스터는 설정에 `ipFamily: dual` 을 줍니다. 노드마다 IPv4 `/24` 와 IPv6 `/64` 를 하나씩 받습니다(예: `10.244.1.0/24`, `fd00:10:244:1::/64`). 예시는 Host Scope 모드라서 Pod 주소가 이 PodCIDR 에서 나옵니다. Pod 하나는 `10.244.1.117` 과 `fd00:10:244:1::8204` 를 받습니다. 다른 노드의 Pod 로 `ping6` 을 보내면 응답이 옵니다.

Service 는 `ipFamilyPolicy` 와 `ipFamilies` 로 계열을 고릅니다. **ClusterIP** 는 클러스터 안에서만 쓰는 가상 서비스 IP 입니다. `PreferDualStack` 은 가능하면 두 계열의 ClusterIP 를 받고 안 되면 단일 스택이 됩니다([Kubernetes 문서](https://kubernetes.io/docs/concepts/services-networking/dual-stack/)).

```yaml
spec:
  ipFamilyPolicy: PreferDualStack
  ipFamilies:
    - IPv6
    - IPv4
```

예시 Service 는 `fd00:10:96::d4d5` 와 `10.96.181.159` 두 ClusterIP 를 받습니다. 클라이언트가 `curl -4` 와 `curl -6` 을 보내면 모두 200 응답을 받습니다.

### IPv6 전용과 NAT64·DNS64

IPv6 전용은 외부 의존도가 문제입니다. 일부 컨테이너 레지스트리는 IPv6 를 지원하지 않습니다. IPv4 전용 엔드포인트에 닿으려면 NAT64 와 DNS64 가 필요합니다. NAT64 는 IPv6 트래픽을 IPv4 로 바꾸고([RFC 6146](https://www.rfc-editor.org/rfc/rfc6146)), DNS64 는 A 레코드로 AAAA 레코드를 합성합니다([RFC 6147](https://www.rfc-editor.org/rfc/rfc6147)). 로깅·관측·보안 도구도 IPv6 를 이해해야 합니다.

그래서 IPv4 단독이 가장 안전한 기본이고 듀얼 스택은 전환 전략입니다. IPv6 전용은 의존성을 파악하고 NAT64/DNS64 를 안정적으로 둘 수 있는 새 클러스터에 맞습니다. IPv6 주소 체계는 [IPv6 와 일반화 포워딩](../../../02_os/book/cntd_computer-networking-top-down/04-04.IPv6%20와%20일반화%20포워딩.md)에 있습니다.

예시 IPv6 전용 kind 클러스터는 문서용 대역 `2001:db8::/32` 안에서 대역을 직접 지정합니다. 이 블록은 [RFC 3849](https://www.rfc-editor.org/rfc/rfc3849)가 예제용으로 예약했습니다. Cilium 은 IPv4 가 기본으로 켜져 있어 설치할 때 끕니다.

```yaml
# kind
networking:
  ipFamily: ipv6
  disableDefaultCNI: true
  podSubnet: "2001:db8:10:244::/48"
  serviceSubnet: "2001:db8:10:96::/112"
---
# Cilium Helm values
ipv6:
  enabled: true
ipv4:
  enabled: false
ipam:
  mode: kubernetes
routingMode: native
autoDirectNodeRoutes: true
ipv6NativeRoutingCIDR: 2001:db8:10:244::/48
```

`podSubnet` 의 `/48` 은 앞 세 블록(`2001:db8:10`)만 고정합니다. 그래서 노드는 네 번째 블록을 바꿔 가며 `2001:db8:10:1::/64` 같은 `/64` 대역을 받습니다. 설치 후 Pod 는 `2001:db8:10:1::4d69` 처럼 IPv6 주소 하나만 받습니다. Service 는 `SingleStack` 에 `ipFamilies: [IPv6]` 으로 설정합니다. 이때 받은 ClusterIP 는 `2001:db8:10:96::6f43` 입니다. 이 주소로 `curl -6` 을 보내면 200 응답을 받습니다.

실제 클러스터에서는 문서용 대역 대신 조직이 받은 공인 IPv6 대역에서 Pod 대역을 받습니다. 네이티브 라우팅이면 Pod 가 NAT 없이 그 주소를 그대로 쓰므로, 노드당 `/116` 만 나눠도 주소가 4,096개입니다.



## 면접 대비

> IPAM 모드와 주소 계열 선택에 관한 핵심 질문입니다.

1. Host Scope 와 Cluster Scope 는 노드 PodCIDR 의 출처와 기록 위치가 어떻게 다릅니까?
2. 노드 몫이 `/29` 인 Cluster Scope 에서 Pod 가 ContainerCreating 에 머무는 이유와 해결은 무엇입니까?
3. Multi-Pool 의 풀 선택 순서와 라우팅을 맡는 장치는 무엇입니까?
4. ENI 모드가 AWS 에서만 의미 있는 이유와 이점·제약은 무엇입니까?
5. 듀얼 스택과 IPv6 전용은 각각 어떤 상황에 맞고 IPv6 전용이 어려운 이유는 무엇입니까?



## 정답 (자답 후 펼치기)

> 면접 질문에 대한 키워드 중심의 모범 답안입니다.

### 정답 1 — Node 대역과 CiliumNode 대역

Host Scope 는 쿠버네티스가 `Node` 의 `spec.podCIDRs` 에 적은 대역을 읽습니다. Cluster Scope 는 cilium-operator 가 `CiliumNode` 의 `spec.ipam.podCIDRs` 에 적으므로 쿠버네티스 설정에 기대지 않고 풀 목록에 CIDR 을 덧붙여 키울 수 있습니다.

### 정답 2 — 마스크가 정한 노드 몫과 목록에 덧붙이기

`/29` 는 주소 8개에서 네트워크·브로드캐스트 2개를 뺀 6개가 할당 대상이고 router 와 health 도 그 안에서 나갑니다. 몫이 바닥나면 새 Pod 는 ContainerCreating 에 남고 풀은 목록에 새 CIDR 을 덧붙여 키웁니다.

### 정답 3 — 풀 선택 순서와 별도 라우팅

`ipam.cilium.io/ip-pool` 주석, 풀의 셀렉터, `default` 풀 순서입니다. 라우팅은 IPAM 의 일이 아니라서 BGP Control Plane 이 PodCIDR 을 광고하거나 같은 L2 에서 `autoDirectNodeRoutes` 가 경로를 만듭니다.

### 정답 4 — ENI 보조 IP 구조와 한도

주소가 AWS ENI 의 보조 IP 이고 오퍼레이터가 EC2 API 로 만들므로 AWS 위에서만 성립합니다. VPC 안에서 바로 라우팅되어 NAT 가 필요 없는 것이 이점입니다. 제약은 두 가지입니다. prefix delegation 을 끈 경우 인스턴스 타입의 ENI 수와 ENI 당 IP 수가 주소 수를 막습니다. 터널 라우팅은 쓰지 못합니다.

### 정답 5 — 전환 전략과 외부 의존성

IPv4 단독은 호환성이 가장 넓은 기본값이고 듀얼 스택은 전환 전략입니다. IPv6 전용은 IPv4 전용 서비스에 닿으려면 NAT64/DNS64 가 필요해 의존성을 파악한 새 클러스터에 맞습니다.
