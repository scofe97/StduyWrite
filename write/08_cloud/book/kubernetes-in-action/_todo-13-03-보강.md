| 상황 | `apply` | status | 학습자 답 |

## 보강 항목 (5개)

### 1. §1 — SNI 기전은 12-02를 정본으로 링크 (⛔ 중복 서술 금지)

학습자가 세션 중 "SNI가 뭐였지?"를 물었다. 현재 40행은 "SNI(Server Name Indication) 확장으로 수신자 호스트명만 압니다"라고 **이름만 던진다** — 왜 그것만 보이는지가 없다.

핵심 기전은 **핸드셰이크가 암호화 *전에* 일어나므로 SNI만 평문**이라는 것이다. 한 IP에 여러 도메인이 있을 때 서버가 어느 인증서를 내밀지 알아야 하는데, 인증서 전송 시점에는 아직 암호화가 없고 `Host` 헤더는 너무 늦다.

⛔ **12-02 §1에 이미 보강돼 있다**(`12-02-termination-vs-passthrough-visibility.svg` 포함). 여기서는 **한 줄 요약 + 12-02 링크**로 처리하고 기전을 다시 풀어쓰지 않는다.

### ⭐ 2. §1 — listener 프로토콜 `HTTPS` vs `TLS`의 의미 차이

현재 56·73행이 주석으로 "termination은 HTTPS", "passthrough는 TLS(HTTPS 아님)"라고만 적어 *왜 이름이 다른지*가 없다.

- **`protocol: HTTPS`** = "TLS를 풀면 **HTTP다**"라는 선언 → 그래서 **HTTPRoute**로 경로·헤더 라우팅
- **`protocol: TLS`** = "**TLS인 것만 안다**, 안은 모른다"는 선언 → 그래서 **TLSRoute**로 SNI 호스트명만

학습자 오해 교정도 함께 — **"TCP·UDP·gRPC는 프록시를 안 쓰는 프로토콜"이 아니다.** 프록시는 어느 프로토콜에서든 있고, 갈리는 것은 **내용을 이해하는가**다.

| | 프록시 | 내용 이해 | 라우팅 범위 |
|---|---|---|---|
| HTTP(termination) | 있음 | 이해함 | 경로·헤더·메서드·쿼리 |
| TLS passthrough | 있음 | 못 함 | **SNI 호스트명만** |
| TCP | 있음 | 못 함 | **없음**(조건 없이 전달) |

⚠️ **TLSRoute는 experimental**(79행 `v1alpha2`)이므로 13-01 §2의 두 축이 여기 걸린다 — **"규격에 있다 ≠ 안정적이다 ≠ 이 구현이 지원한다"**. 12-02에서 "passthrough는 표준이 아니라 annotation 의존"이었던 것이 Gateway API에서 **정식 리소스로 승격**됐다는 대비도(표준의 정의 = API에 정식 필드로 있는가). 13-01 TODO 항목 2와 교차 참조.

### ⭐ 3. §3 — 왜 막아 두는가 + 네트워크 통신 vs 오브젝트 참조 (시각화 · 최우선)

학습자가 **"흐르지 않을까요? 네임스페이스가 달라도 통신은 되잖아"** 로 두 층을 혼동했다. 현재 186행은 "ReferenceGrant가 없는 한 `ResolvedRefs`가 `RefNotPermitted`로 False가 됩니다"라는 **사실만** 적는다.

**없는 것 ① — 두 층 구분**

| | 네임스페이스를 넘나 |
|---|---|
| **파드 간 네트워크 통신** | **된다** (11-01 flat 네트워크, FQDN으로 호출하면 그냥 됨) |
| **오브젝트 간 참조** | **기본은 안 된다** (허가 필요) |

흐르지 않는 이유는 네트워크가 막혀서가 아니라 **참조 권한이 없어서**다.

**없는 것 ② — 위협 모델(왜 막는가)**

안 막으면 아무 네임스페이스에서 HTTPRoute를 만들어 `backendRefs`에 **남의 팀 내부 전용 서비스**를 적어 자기 Gateway로 외부에 노출할 수 있다. **서비스 소유자는 노출된 걸 모른다** — 참조하는 쪽만으로 결정되면 소유자 의사가 빠진다.

**없는 것 ③ — 그래서 오브젝트 위치가 그렇다**

허가 주체가 소유자이므로 `ReferenceGrant`를 **참조 대상(서비스)의 네임스페이스**에 만든다. 205행이 위치를 적기는 하나 *왜 거기인지*가 없다 — 설계 근거를 붙이면 위치를 외울 필요가 없어진다.

**없는 것 ④ — 가장 교활한 "조용히 실패"**

⭐ 이 케이스는 **오타도 없고 서비스도 실제로 존재해 YAML만으로는 못 찾는다.** status를 봐야만 안다. `Accepted: True` / `ResolvedRefs: False (RefNotPermitted)` — 13-02 TODO 항목 1의 **방향 대응**(위/아래)이 그대로 적용되므로 **짝으로 설계**한다.

13-01 Q1의 역할 분리와도 잇는다 — RBAC으로 "각 팀은 자기 네임스페이스만"을 강제해도 **참조는 네임스페이스를 넘어 뻗을 수 있어** 별도 허가 장치가 필요했다.

### ⭐ 4. §2 — 세 실패 양상 대비 + API 서버 ≠ 컨트롤러 (시각화)

현재 131·152행은 "status가 비어 있으면 어떤 컨트롤러도 처리하지 않았다는 뜻"이라고 **결론만** 적는다. 학습자는 "apply가 실패할 것"이라 오답했다.

**없는 것 ① — API 서버와 컨트롤러는 별개**

`apply`를 받는 것은 **API 서버**이고, 확인하는 것은 **CRD가 설치돼 있는가 + 스키마에 맞는가**뿐이다. 13-01에서 experimental 채널 CRD를 설치했으니 `UDPRoute`도 스키마 검증을 통과한다. **Istio가 그것을 안 본다는 사실을 API 서버는 모른다.**

**없는 것 ② — status를 채우는 주체가 컨트롤러다**

그래서 컨트롤러가 이 리소스 종류를 아예 안 보면 **채울 사람이 없어 status가 빈다.** 이것이 "미지원"의 신호다.

**없는 것 ③ — 세 양소 대비표**(위 "왜 보강하나"의 표를 본문에 넣는다). 특히 **거부(이유가 찍힘)와 무처리(빔)가 다른 양상**임을 강조.

**없는 것 ④ — 같은 결의 사례 셋**

13-01 `attachedRoutes: 0` · 12-02 기본 IngressClass 부재 · 여기 status 빔 — 모두 **"아무도 처리하지 않아 조용히 아무 일도 안 일어남"** 이고 진단법도 같다("빈지/0인지 보라"). 이 교차 참조가 항목의 값이다.

또한 support level(13-01)과의 구분도 — support level은 **명세에 적힌 규범**이고, "지금 내 클러스터의 이 컨트롤러가 실제로 지원하는가"는 **status로 확인**한다. 학습자가 "support level로 명시한 거 아님?"이라 답한 지점.

### ⭐ 5. §4 — `parentRefs` 의미의 재해석 (미학습 축)

학습자가 **두 번 "모르겠음"** 으로 막혀 Phase 1 게이트를 닫지 못한 축이다. 현재 217행은 "parentRefs에 Gateway 대신 Service를 두는 것"이라는 **결론만** 적어 *왜 그게 가능한지*가 없다.

핵심 재해석 — **`parentRefs`의 뜻은 "부모 Gateway"가 아니라 "이 규칙이 적용될 트래픽 진입점"이고, Gateway는 그 한 형태일 뿐이다.**

```
[north/south]  parentRef: Gateway  → "이 게이트웨이로 들어온 트래픽에 적용"
[east/west]    parentRef: Service  → "이 서비스로 향하는 트래픽에 적용"
```

- 왜 Service인가 — 11-01에서 배운 대로 클라이언트는 파드 IP가 아니라 **변하지 않는 대표 이름**(Service)을 부른다. `http://payment-api` 를 호출하는 트래픽 전체를 하나로 가리키는 것이 그 Service다.
- **호출하는 쪽 코드는 안 바뀐다** — 여전히 `payment-api` 를 부르는데 중간에서 규칙이 걸린다.
- 13-02 기능이 그대로 east/west에 적용된다는 대응표:

| 13-02에서 배운 것 | east/west 적용 |
|---|---|
| `weight` 분할 | 내부 카나리 (결제 v2에 1%) |
| `RequestMirror` | 내부 미러링 (클라이언트 영향 0) |
| 헤더 조작·URLRewrite | 서비스 간 호출에도 |

⚠️ **mesh 자체의 상세는 231행이 이미 `service-mesh` 정본에 위임했으니 거기까지만.** GAMMA 이니셔티브 역사·SMI 비교·Istio 구현 상세로 번지지 않게 한다.
