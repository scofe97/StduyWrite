# Job 병렬·실패·완료 모드

> Job은 파드 하나로 끝나지 않습니다. 여러 번, 여러 개를 동시에 돌리고, 실패를 어느 수준에서 어떻게 다룰지 고르고, 각 파드에 고유 번호를 줄 수 있습니다.

읽고 나면 `completions`·`parallelism` 조합이 만드는 실행 패턴을 설명하고, 파드 레벨과 Job 레벨의 실패 처리를 구분하고, `backoffLimit`·`activeDeadlineSeconds`가 무엇을 제한하는지 말하고, `Indexed` 완료 모드가 각 파드에 인덱스를 어떻게 넘기는지 설명할 수 있습니다.



## 진입 — 같은 작업을 여러 번, 각기 다른 작업을 나눠서
> 한 번 실행으로 끝나지 않는 작업은 순차·병렬로 반복하거나, 데이터를 조각내 파드마다 다른 부분을 처리하게 합니다.

앞 편([18-01](./18-01.Job%20%EA%B8%B0%EC%B4%88%20%E2%80%94%20%EC%8B%A4%ED%96%89%C2%B7%EC%83%81%ED%83%9C%C2%B7suspend%C2%B7%EC%9E%90%EB%8F%99%EC%82%AD%EC%A0%9C.md))의 Job은 파드 하나를 완료까지 실행했습니다. 하지만 같은 작업을 여러 번 실행하도록 설정할 수도 있습니다. 컨테이너가 한 번에 한 항목만 처리할 수 있어 전체 입력을 여러 번 돌려야 하거나, 여러 노드에 나눠 처리해 성능을 높이고 싶을 때 그렇습니다.



## 1. 여러 번 실행 — completions와 parallelism
> `completions`는 성공해야 할 파드 수를, `parallelism`은 동시에 돌릴 파드 수를 정합니다.

퀴즈 데이터베이스에 가짜 응답을 넣는 Job을 생각해 보겠습니다. 파드 하나가 아니라 다섯 개가 데이터를 넣되, 동시에 최대 두 개만 돌게 하려 합니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: generate-responses
  labels:
    app: quiz
spec:
  completions: 5      # 이 Job은 다섯 번 성공해야 완료
  parallelism: 2      # 최대 두 파드가 동시에 실행
  template:
    metadata:
      labels:
        app: quiz
    spec:
      restartPolicy: OnFailure
      containers:
        - name: mongo
          image: mongo:5
          command: [...]
```

`completions`는 성공적으로 완료돼야 할 파드 수를, `parallelism`은 그중 몇 개가 동시에 실행될 수 있는지를 지정합니다. 상한은 없지만, 클러스터 용량 때문에 실제 동시 실행 수는 제한됩니다.

<img src="./_assets/18-02-completions-parallelism.svg" alt="completions=5, parallelism=2인 Job: 동시에 두 파드가 돌고, 하나가 끝나면 다음이 채워져 총 다섯 파드가 완료되는 타임라인" />

`parallelism=2`이므로 Job 컨트롤러는 먼저 파드 두 개를 만들고 그중 하나가 완료되기를 기다립니다. 하나가 끝나면 즉시 다음 파드를 만들어 실행 중인 파드 수를 다시 둘로 유지합니다. 다섯 파드가 성공적으로 완료될 때까지 이 과정을 반복합니다.

### 1.1 completions와 parallelism 조합

두 필드를 각각 설정할 수도, 하나만 설정할 수도, 둘 다 생략할 수도 있습니다. 조합에 따라 동작이 달라집니다.

| completions | parallelism | 동작 |
|:-----------:|:-----------:|------|
| 미설정 | 미설정 | 파드 하나 생성. `completions`·`parallelism` 모두 1인 것과 같음 (기본) |
| 1 | 1 | 파드 하나 생성. 성공하면 완료, 완료 전에 지워지면 새 파드로 교체 |
| 2 | 5 | 파드 세 개만 생성됨(`parallelism`이 2인 것과 같음 — `completions`가 상한) |
| 5 | 2 | 두 파드로 시작, 하나 끝나면 다음 생성. 반복해 다섯 번째 파드까지 |
| 5 | 5 | 다섯 파드 동시 실행. 완료 전에 하나 지워지면 교체. 다섯 성공 시 완료 |
| 5 | 미설정 | 다섯 파드 순차 실행(앞 파드가 완료·실패해야 다음 생성) |
| 미설정 | 5 | 다섯 파드 동시 실행하지만 하나만 성공하면 Job 완료 |

`completions`를 `parallelism`보다 높게 두면(예: 5/2), Job 컨트롤러는 처음에 `parallelism`만큼만 파드를 만들고, 성공한 파드 수가 `completions`에 도달할 때까지 새 파드를 채웁니다. 파드 몇 개가 실패하면 성공 수를 채우기 위해 총 생성 파드 수가 `completions`보다 많아질 수 있습니다.



## 2. 실패 처리 — 파드 레벨과 Job 레벨
> 컨테이너 실패는 Kubelet이 파드 안에서 처리하거나, Job 컨트롤러가 새 파드로 처리합니다. `restartPolicy`가 어느 쪽인지를 결정합니다.

Job으로 작업을 돌리는 이유는, 개별 파드나 노드가 실패해도 Kubernetes가 작업 완료를 보장하기 때문입니다. 이 실패는 두 수준에서 다룹니다. 하나는 파드 레벨, 다른 하나는 Job 레벨입니다.

<img src="./_assets/18-02-restart-policy-failure.svg" alt="restartPolicy에 따른 실패 처리: OnFailure는 같은 파드에서 컨테이너를 재시작하고, Never는 파드를 실패로 표시하고 Job 컨트롤러가 새 파드를 만드는 두 흐름" />

컨테이너가 실패하면 Pod의 `restartPolicy`가 실패를 파드 레벨(Kubelet)에서 다룰지 Job 레벨(Job 컨트롤러)에서 다룰지 결정합니다.

- `restartPolicy: OnFailure` — 실패한 컨테이너를 **같은 파드 안에서** 재시작합니다. 같은 노드에서 빠르게 다시 시도합니다. 여러 번 실패하면 지수 백오프로 재시작 간격이 늘어납니다.
- `restartPolicy: Never` — 파드 전체를 실패로 표시하고, Job 컨트롤러가 **새 파드**를 만듭니다. 새 파드는 다른 노드에 스케줄될 수 있습니다.

`OnFailure`는 실패가 일시적이고 같은 노드에서 재시도하면 되는 경우에, `Never`는 파드를 아예 새로 띄우고 싶은 경우에 씁니다. 새 파드가 다른 노드에 뜨면 컨테이너 이미지를 다시 내려받아야 할 수 있습니다.



## 3. Job 실패 한계 — backoffLimit과 activeDeadlineSeconds
> `backoffLimit`은 재시도 횟수를, `activeDeadlineSeconds`는 Job 전체 실행 시간을 제한합니다. 한계를 넘으면 Job이 실패합니다.

앞의 `generate-responses`는 코드에 25% 실패율을 심어 두었습니다. 파드 몇 개가 재시작을 거쳐 결국 성공합니다. 하지만 너무 많이 실패하면 Job 컨트롤러가 포기합니다.

### 3.1 backoffLimit — 재시도 횟수

항상 실패하는 Job으로 확인해 보겠습니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: demo-always-fails
spec:
  completions: 10
  parallelism: 3
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: demo
          image: busybox
          command:
            - 'false'        # 항상 non-zero exit code → 컨테이너 실패로 처리
```

파드의 컨테이너가 계속 실패하면 Kubelet이 재시작하고, 몇 번 재시작한 뒤 Job 컨트롤러가 이 파드들이 실패하고 있음을 알아채고 파드를 지운 뒤 Job을 실패로 표시합니다.

```bash
$ kubectl get job
NAME               STATUS   COMPLETIONS   DURATION   AGE
demo-always-fails  Failed   0/10          2m48s      2m48s
```

`describe`의 이벤트 맨 아래에 `BackoffLimitExceeded` 경고가 나옵니다. Job은 여섯 번 재시도 후 끝났는데, 이 값이 기본 backoff 한계입니다. 매니페스트의 `spec.backoffLimit`으로 조정할 수 있습니다. Job이 이 한계를 넘으면 Job 컨트롤러는 실행 중인 파드를 전부 지우고 새 파드를 더 만들지 않습니다. 실패한 Job을 다시 돌리려면 지우고 새로 만들어야 합니다.

### 3.2 activeDeadlineSeconds — 실행 시간

Job이 제때 끝나지 않아 실패할 수도 있습니다. 기본적으로 시간 제한은 없지만, `spec.activeDeadlineSeconds`로 최대 실행 시간을 정할 수 있습니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: demo-deadline
spec:
  completions: 2
  parallelism: 1
  activeDeadlineSeconds: 90    # Job 전체가 90초 안에 끝나야 함
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: demo-suspend
          image: busybox
          command: [sleep, "60"]
```

`completions=2`, `parallelism=1`이므로 두 파드가 순차로 돕니다. 각 파드가 60초 걸리니 전체는 120초를 조금 넘습니다. 하지만 `activeDeadlineSeconds`가 90이라 이 시나리오는 성공할 수 없습니다. Job은 `DeadlineExceeded` 이벤트를 내며 실패합니다.

> `activeDeadlineSeconds`는 Job **전체**에 적용됩니다. 그 Job 안에서 만들어진 개별 파드에 적용되는 것이 아닙니다.

### 3.3 podFailurePolicy — 커스텀 실패 규칙

기본 실패 정책 대신 직접 규칙을 정할 수도 있습니다. `spec.podFailurePolicy`에 규칙을 넣어, 특정 컨테이너가 특정 exit code로 끝나면 Job 전체를 실패로 표시하게 합니다.

```yaml
kind: Job
spec:
  podFailurePolicy:
    rules:
      - onExitCodes:
          containerName: main   # main 컨테이너가
          operator: In
          values: [123]         # exit code 123으로 끝나면
        action: FailJob         # Job 전체를 즉시 실패로 표시
```

Job 전체를 실패시키는 대신, 특정 인덱스만 실패로 표시하거나 특정 exit code를 무시할 수도 있습니다. `kubectl explain job.spec.podFailurePolicy`로 규칙을 확인합니다.



## 4. 완료 모드 — NonIndexed와 Indexed
> 기본 `NonIndexed`는 파드를 서로 구분하지 않지만, `Indexed`는 각 파드에 0부터 시작하는 인덱스를 줘 데이터의 특정 부분만 처리하게 합니다.

지금까지 Job이 만든 파드는 전부 동일했습니다. 하지만 각 파드가 서로 다른 데이터 조각을 처리하게 하려면 어떻게 할까요? `spec.completionMode` 필드가 답입니다. 작성 시점 기준 두 모드가 있습니다.

- `NonIndexed`(기본) — 이 Job이 만든 모든 파드는 서로 구별되지 않습니다. 성공한 파드 수가 `spec.completions`와 같아지면 Job이 완료됩니다.
- `Indexed` — 각 파드에 0부터 시작하는 완료 인덱스(completion index)를 줍니다. 파드는 이 인덱스로 서로 구분되고, 각자 전체 작업의 한 부분만 수행합니다.

<img src="./_assets/18-02-indexed-completion.svg" alt="Indexed 완료 모드에서 하나의 템플릿으로 만든 12개 파드가 각각 인덱스 0~11을 받아 서로 다른 데이터를 처리하는 그림" />

### 4.1 왜 Indexed가 필요한가

퀴즈 응답을 월별로 집계하는 스크립트를 예로 들겠습니다. 2020년 12개월치를 처리하려면 파드 12개가 필요하고, 각 파드는 서로 다른 월을 받아야 합니다. `NonIndexed`에서는 모든 파드가 동일하므로 각 파드에 다른 월(환경 변수)을 넘길 수 없습니다. 월마다 별도의 Job 매니페스트를 만들어야 합니다(템플릿 엔진이나 셸 for 루프로). Job이 12개면 관리 부담이 커집니다.

`Indexed` 모드는 단일 Job 하나로 이 문제를 풉니다. `spec.completions`로 파드 수를 정하고, 각 파드는 인덱스로 자신이 처리할 부분을 결정합니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: aggregate-responses-2021
spec:
  completionMode: Indexed     # 각 파드가 인덱스를 받음
  completions: 12             # 12개월치 → 파드 12개(인덱스 0~11)
  parallelism: 3              # 최대 3개 동시 실행
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: updater
          image: mongo:5
          env:
            - name: YEAR
              value: "2021"   # 연도만 넘김 (월은 인덱스로 결정)
          command: [...]
```

### 4.2 JOB_COMPLETION_INDEX 환경 변수

Job 컨트롤러는 `Indexed` 모드의 파드에 인덱스를 두 방법으로 전달합니다.

첫째, `JOB_COMPLETION_INDEX` 환경 변수를 각 파드에 자동으로 넣습니다(0부터 시작). 코드는 이 값으로 처리할 부분을 정합니다. 이 예에서 월은 1부터라, 스크립트는 인덱스에 1을 더해 월을 구합니다.

```javascript
var year = parseInt(process.env["YEAR"]);
var month = parseInt(process.env["JOB_COMPLETION_INDEX"]) + 1;
```

둘째, 같은 인덱스를 파드의 `batch.kubernetes.io/job-completion-index` 어노테이션에도 넣습니다. 환경 변수 대신, 7장에서 배운 Downward API로 이 어노테이션 값을 원하는 이름의 환경 변수에 넘길 수 있습니다.

```yaml
env:
  - name: MONTH
    valueFrom:
      fieldRef:
        fieldPath: metadata.annotations['batch.kubernetes.io/job-completion-index']
```

### 4.3 인덱스로 파드 구분

`Indexed` 모드 파드를 나열하면 이름과 hostname에 인덱스가 들어갑니다.

```bash
$ kubectl get pods -l job-name=aggregate-responses-2021
NAME                             READY   STATUS    RESTARTS   AGE
aggregate-responses-2021-0-...   1/1     Running   0          24s  # 인덱스 0
aggregate-responses-2021-1-...   1/1     Running   0          24s  # 인덱스 1
aggregate-responses-2021-2-...   1/1     Running   0          24s  # 인덱스 2
```

파드 이름은 `<job>-<index>-<random>` 형태이고, hostname은 `<job-name>-<index>` 형태입니다. hostname에 인덱스가 들어가는 덕분에 인덱스 Job의 파드끼리 통신이 쉬워집니다([18-03](./18-03.work%20queue%C2%B7pod%20%ED%86%B5%EC%8B%A0%C2%B7sidecar%C2%B7CronJob.md)에서 다룹니다).

`Indexed` 모드는 단순 정수를 넘기지만, init 컨테이너를 붙이면 이 정수를 훨씬 복잡한 입력으로 바꿀 수 있습니다. 예컨대 네트워크 볼륨에 1,000개 파일이 있고 각 파드가 한 파일을 처리해야 할 때, init 컨테이너가 인덱스에 해당하는 파일을 찾아 로컬 공유 볼륨에 심볼릭 링크(`file.bin`)로 걸어 두면, 메인 컨테이너는 인덱스나 파일이 1,000개라는 사실을 몰라도 됩니다.



## 5. Spring 관점 — 파티셔닝을 Kubernetes로 밀어내기
> Spring Batch의 파티셔닝을 앱 안에 두는 대신, Indexed Job으로 데이터를 조각내면 각 파드가 독립적으로 한 조각만 처리합니다.

Spring Batch는 큰 데이터를 파티션으로 나눠 병렬 처리하는 파티셔닝(partitioning) 기능을 제공합니다. 이 나눔을 애플리케이션 안에서 마스터-워커로 조율할 수도 있지만, `Indexed` Job은 그 조율을 Kubernetes로 밀어냅니다. `completions`를 파티션 수로 두고, 각 파드가 `JOB_COMPLETION_INDEX`로 자신이 맡을 파티션(예: 월·샤드 번호)을 계산하면, 파드는 서로를 몰라도 각자 한 조각만 처리합니다.

두 방식의 트레이드오프는 조율 위치입니다. 앱 내부 파티셔닝은 진행 상황·재시도를 JobRepository로 한곳에서 추적하지만, 파드가 죽으면 그 조율까지 함께 흔들립니다. `Indexed` Job은 각 파드를 독립적으로 만들어 하나가 실패해도 그 인덱스만 재시도하지만, 전체 진행을 한눈에 보려면 별도 집계가 필요합니다. 조각들이 서로 독립적이고 실패 격리가 중요하면 `Indexed` Job이, 파티션 간 공유 상태가 있으면 앱 내부 조율이 더 맞습니다.



## 면접에서 받을 만한 질문
> 아래 질문에 스스로 답해 본 뒤, 챕터 끝 `## 정답`과 맞춰 봅니다.

1. `completions: 5`, `parallelism: 2`인 Job은 파드를 어떻게 생성하고 실행합니까?
2. `restartPolicy` `OnFailure`와 `Never`는 컨테이너 실패를 각각 어느 수준에서 처리합니까?
3. `backoffLimit`과 `activeDeadlineSeconds`가 제한하는 대상은 각각 무엇입니까?
4. `NonIndexed`와 `Indexed` 완료 모드의 핵심 차이는 무엇입니까?
5. `Indexed` Job에서 각 파드는 자신의 인덱스를 어떻게 알 수 있습니까(두 방법)?



## 정답 (자답 후 펼치기)
> 위 질문을 스스로 답한 뒤 여기서 확인합니다. 질문 번호와 1:1로 대응합니다.

### 정답 1 — completions 5, parallelism 2
Job 컨트롤러는 먼저 파드 두 개를 만들고 하나가 완료되기를 기다립니다. 하나가 끝나면 즉시 새 파드를 만들어 실행 중인 파드 수를 둘로 유지합니다. 성공한 파드 수가 5에 도달할 때까지 반복합니다. 파드가 실패하면 성공 수를 채우느라 총 생성 파드 수가 5보다 많아질 수 있습니다.

### 정답 2 — OnFailure vs Never의 실패 처리 수준
`OnFailure`는 파드 레벨에서 처리합니다. Kubelet이 같은 파드 안에서 실패한 컨테이너를 재시작합니다(같은 노드·지수 백오프). `Never`는 Job 레벨에서 처리합니다. 파드 전체를 실패로 표시하고 Job 컨트롤러가 새 파드를 만듭니다(다른 노드 가능).

### 정답 3 — backoffLimit과 activeDeadlineSeconds
`backoffLimit`은 Job의 재시도 횟수를 제한합니다(기본 6). 초과하면 `BackoffLimitExceeded`로 Job이 실패하고 실행 중인 파드가 모두 지워집니다. `activeDeadlineSeconds`는 Job **전체**의 실행 시간을 제한합니다(개별 파드가 아님). 초과하면 `DeadlineExceeded`로 실패합니다.

### 정답 4 — NonIndexed vs Indexed
`NonIndexed`(기본)는 모든 파드가 동일하고 서로 구별되지 않습니다. 성공 파드 수가 `completions`에 도달하면 완료됩니다. `Indexed`는 각 파드에 0부터 시작하는 완료 인덱스를 줘 파드를 구분하고, 각 파드가 전체 작업의 한 부분만 처리하게 합니다.

### 정답 5 — 인덱스를 아는 두 방법
첫째, `JOB_COMPLETION_INDEX` 환경 변수로 인덱스가 자동 주입됩니다(0부터). 둘째, 같은 값이 `batch.kubernetes.io/job-completion-index` 어노테이션에도 들어가므로, Downward API(`fieldRef`)로 원하는 이름의 환경 변수에 넘길 수 있습니다. hostname(`<job>-<index>`)에도 인덱스가 들어갑니다.
