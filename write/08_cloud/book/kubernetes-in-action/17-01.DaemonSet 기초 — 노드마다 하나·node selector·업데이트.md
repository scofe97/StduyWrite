# DaemonSet 기초 — 노드마다 하나·node selector·업데이트
---
> DaemonSet은 클러스터의 각 노드에 파드 replica를 정확히 하나씩 띄웁니다. replica 수를 지정하지 않습니다. 컨트롤러가 노드 수만큼 파드를 만들어 각기 다른 노드에 스케줄합니다. node selector로 일부 노드에만 배포할 수 있고, control plane 노드에는 taint를 직접 tolerate해야 배포됩니다. 노드 건강과 관련된 taint는 컨트롤러가 자동으로 tolerate합니다.



> 이 문서를 읽고 나면 DaemonSet이 ReplicaSet과 무엇이 다른지 설명하고, 왜 노드 수보다 파드가 적을 수 있는지 taint로 근거를 대며, node selector와 업데이트 전략(RollingUpdate·OnDelete)을 말할 수 있습니다.



## 진입 — 노드마다 정확히 하나

> 앞 장들에서 Deployment·StatefulSet으로 여러 replica를 노드에 분산했습니다. 하지만 노드마다 정확히 하나를 돌리고 싶을 때 — 메트릭 수집·로그 집계 같은 노드별 시스템 서비스 — 는 DaemonSet을 씁니다.

DaemonSet은 각 클러스터 노드에 파드 replica가 정확히 하나 돌도록 보장하는 API 오브젝트입니다. 기본적으로 모든 노드에 배포되지만, node selector로 일부 노드로 제한할 수 있습니다.

"노드마다 하나"라는 말에는 주어를 붙여 두는 편이 낫습니다. 하나로 제한되는 것은 **같은 DaemonSet의** 파드입니다. 클러스터에는 DaemonSet을 여러 개 만들 수 있고 실제로 그렇습니다. 워커 노드 한 대에 kube-proxy 파드와 CNI 파드, 로그 수집기 파드가 **동시에** 돕니다. 서로 다른 DaemonSet 소속이라 무관합니다.

뒤에서 볼 lock 충돌도 이 범위를 따릅니다. 같은 로그 수집기 인스턴스 둘이 한 파일을 잡으면 충돌합니다. 로그 수집기 하나와 메트릭 수집기 하나는 서로 다른 자원을 보니 문제가 없습니다.

아래는 이 편 전체를 한 장으로 이은 지도입니다. 다섯 단계가 세로로 이어지는 파이프라인이고, DaemonSet의 생애주기를 그대로 따라갑니다. 각 상자 오른쪽의 절 번호가 그 부분을 다루는 곳입니다.

- §1 이해 — replica 수 대신 노드 수가 기준이 됩니다
- §2 배포 — 노드가 셋인데 파드가 둘인 이유를 taint로 풉니다
- §3 범위 — node selector로 대상 노드를 좁힙니다
- §4 업데이트 — Deployment와 기본값이 다른 이유를 봅니다
- §5 삭제 — 파드를 남길지 함께 지울지 정합니다

색이 붙은 곳은 두 군데뿐이고 둘 다 주의 표시입니다. 나머지 상자는 전부 같은 회색이라 색을 해석할 일이 없습니다.

2단계의 앰버 띠는 taint 중 일부를 컨트롤러가 알아서 tolerate한다는 뜻입니다. 4단계의 앰버 띠는 maxSurge를 0보다 크게 두면 데몬이 lock 충돌로 ready가 되지 못한다는 뜻입니다.

![17-01 전체 지도 — 노드 수가 기준이 된다](_assets/17-01.chapter-overview.svg)



## 1. DaemonSet 오브젝트

> DaemonSet은 Pod 템플릿·label selector를 갖지만 replica 수는 지정하지 않습니다. 컨트롤러가 노드 수만큼 파드를 만들어 각기 다른 노드에 하나씩 스케줄합니다. ReplicaSet은 여러 파드를 한 노드에 몰 수 있지만 DaemonSet은 노드당 하나입니다.

![DaemonSet은 각 노드에 파드 하나씩, ReplicaSet은 파드를 클러스터에 흩뿌립니다(한 노드에 여러 개 가능)](_assets/17-01-daemonset-vs-replicaset.svg)

### 어떤 워크로드인가

DaemonSet은 각 노드에 시스템 수준 서비스를 제공하는 인프라 파드를 배포합니다. 다음과 같은 것들입니다.

- 노드 시스템 프로세스·파드의 로그 수집
- 프로세스 모니터링 데몬
- 클러스터 네트워크·스토리지 제공
- 소프트웨어 패키지 설치·업데이트
- 노드 장치 인터페이스

대표적인 둘은 실제 클러스터에서 바로 확인됩니다. Service 트래픽을 라우팅하는 **Kube Proxy**와 파드 통신 네트워크를 제공하는 **CNI 플러그인**이 DaemonSet(kube-system 네임스페이스)으로 배포됩니다.

init 스크립트나 systemd로도 노드에 시스템 소프트웨어를 돌릴 수 있지만, DaemonSet을 쓰면 클러스터의 모든 워크로드를 같은 방식으로 관리하게 됩니다.

무엇이 같아지는지는 노드 100대를 예로 들면 분명해집니다. 세 가지 일이 이렇게 갈립니다.

| 하는 일 | systemd | DaemonSet |
|---|---|---|
| 배포 | 100대에 접속 | 매니페스트 하나를 `kubectl apply` |
| 버전 올리기 | 100대를 다시 순회 | 이미지 태그 변경 → RollingUpdate가 대신 순회 |
| 죽은 노드 찾기 | 각 노드의 `journalctl` | `kubectl get ds` 한 줄 |

- 배포·업데이트·롤백·로그·모니터링에 쓰는 도구가 애플리케이션 파드와 **같은 것**이 됩니다.

### kubelet은 왜 DaemonSet이 아닌가

그러면 노드마다 도는 것을 전부 DaemonSet으로 옮기면 되는가 하면, 그럴 수 없는 것이 하나 있습니다. **kubelet**입니다. kube-proxy는 DaemonSet인데 kubelet은 systemd 유닛으로 돕니다.

이유는 control plane taint 같은 스케줄링 장벽이 아니라 **순환 의존**입니다. kubelet은 daemon 파드가 아니라 노드에서 **파드를 실행하는 주체**입니다.

kubelet을 DaemonSet으로 배포한다면 그 kubelet 파드를 누군가 실행해야 합니다. 그 실행 주체가 바로 kubelet입니다. kubelet이 없으면 kubelet 파드를 띄울 수 없고, kubelet 파드가 없으면 kubelet이 없습니다. 고리가 닫혀 성립하지 않습니다.

그래서 kubelet은 파드 밖 systemd 유닛으로 먼저 뜨고, 그 위에서야 나머지 모든 파드가 존재할 수 있습니다.

kube-proxy는 이 고리 밖에 있습니다. Service 트래픽 라우팅은 파드 실행의 전제가 아닙니다. kubelet이 떠 있는 상태에서 파드로 띄우면 됩니다. 뒤에 나올 `not-ready` 자동 toleration이 끊어 주는 CNI 교착도 같은 계통의 순환입니다. 다만 그쪽은 toleration으로 끊을 수 있었고, kubelet 쪽은 끊을 방법이 없어 아예 파드 밖으로 빼냈습니다.

### reconciliation loop

DaemonSet은 Pod 템플릿과 label selector를 갖습니다. 컨트롤러는 reconciliation 루프마다 selector에 맞는 파드를 찾아, **각 노드에 정확히 하나**가 있는지 확인하고 부족하면 만들고 남으면 지웁니다.

![DaemonSet 컨트롤러의 reconciliation 루프 — DaemonSet·파드·노드 변화를 감시하고, 노드마다 파드 하나를 보장](_assets/17-01-daemonset-reconciliation.svg)

- 노드를 추가하면 컨트롤러가 그 노드용 파드를 만듭니다. 노드를 제거하면 연결된 Pod 오브젝트를 지웁니다. 
- daemon 파드가 사라지면(수동 삭제 등) 즉시 재생성하고, selector에 맞는 파드가 추가로 나타나면(사용자가 만든 경우) 즉시 삭제합니다.



## 2. DaemonSet으로 파드 배포

> DaemonSet 매니페스트는 ReplicaSet과 비슷하되 replicas가 없습니다. status는 파드 수가 아니라 노드 수를 나타내는 정수 필드로 구성됩니다.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: demo
spec:
  selector:          # 이 DaemonSet에 속하는 파드를 정하는 label selector
    matchLabels:
      app: demo
  template:          # 파드를 만드는 템플릿(selector와 label 일치 필수)
    metadata:
      labels:
        app: demo
    spec:
      containers:
      - name: demo
        image: busybox
        command:
        - sleep
        - infinity
```

selector는 불변입니다. 다만 selector에 계속 맞는 한 label은 바꿀 수 있습니다. selector 자체를 바꾸려면 DaemonSet을 삭제·재생성해야 합니다.

이때 `--cascade=orphan`을 주면 파드가 노드에 남습니다. 뒤이어 **같은 selector로 새 DaemonSet을 만들면 그 파드들을 입양**합니다[^orphan-adopt]. 교체가 필요한 파드는 새 DaemonSet의 `updateStrategy`에 따라 처리됩니다.

```bash
kubectl get ds           # ds는 DaemonSet 약어
# NAME  DESIRED  CURRENT  READY  UP-TO-DATE  AVAILABLE  NODE SELECTOR  AGE
# demo  2        2        2      2           2          <none>         7s

kubectl get ds -o wide   # 컨테이너·이미지·selector 추가 표시
kubectl describe ds demo # Node-Selector·status·template·events
```

### status는 노드 수

```yaml
status:
  currentNumberScheduled: 2   # DaemonSet 파드가 하나 이상 도는 노드 수
  desiredNumberScheduled: 2   # daemon 파드가 돌아야 하는 노드 수
  numberAvailable: 2          # available daemon 파드가 도는 노드 수
  numberMisscheduled: 0       # 돌면 안 되는데 도는 노드 수
  numberReady: 2              # ready daemon 파드가 도는 노드 수
  updatedNumberScheduled: 2   # 최신 템플릿 파드가 도는 노드 수
```

모든 status 필드가 파드 수가 아니라 **노드 수**입니다. 일부 설명이 노드에 파드가 둘 이상일 수 있음을 암시합니다. 업데이트 시 새 파드가 available이 될 때까지 옛 파드 옆에서 잠시 돌기 때문입니다. DaemonSet status의 관심사는 클러스터 전체 파드 수가 아니라 DaemonSet이 서비스하는 노드 수입니다.

뒤에서 볼 `maxSurge` 기본값이 0인데도 파드가 겹치는 것이 어색하게 보일 수 있습니다. maxSurge 0이 보장하는 것은 "옛 파드에게 **종료를 먼저 지시한다**"입니다. "한순간도 겹치지 않는다"가 아닙니다.

지시를 받은 옛 파드는 `Terminating` 상태로 graceful shutdown 시간을 쓰며 남아 있습니다. 그 사이에 새 파드가 만들어집니다.

그래서 3 노드 중 2 노드에 배포된 DaemonSet을 업데이트하는 동안 `kubectl get ds`가 `DESIRED 2`에 `CURRENT 3`을 함께 보여 줄 수 있습니다. 두 숫자의 단위가 갈리는 순간입니다.

이때 `AVAILABLE`이 2로 그대로인 것이 단서입니다. 겹친 파드가 커버하는 노드를 하나 더 늘려 주지는 않기 때문입니다.

### 왜 노드 수보다 파드가 적은가 — control plane taint

3 노드 클러스터인데 파드가 2개만 생기는 경우가 있습니다. node selector가 없어도 그렇습니다.

```bash
kubectl get pods -l app=demo -o wide   # kind-worker·kind-worker2에만
kubectl get nodes                       # control-plane·worker·worker2 (3개)
```

컨트롤러가 worker 노드에만 배포하고 **control plane 노드(kind-control-plane)에는 배포하지 않습니다**. control plane 노드는 클러스터를 제어하는 쿠버네티스 컴포넌트만 돌리기 위한 것입니다.

컨테이너 격리는 별도 VM이나 머신만큼 강하지 않습니다. 그래서 control plane에서 오작동하는 워크로드가 클러스터 전체 운영에 악영향을 줄 수 있습니다. 쿠버네티스는 명시적으로 허용할 때만 control plane에 워크로드를 스케줄하며, DaemonSet도 마찬가지입니다.

### taint와 toleration — 노드가 밀어내고 파드가 견딘다

taint는 **노드가 파드를 밀어내는 표식**입니다. node selector와 방향이 반대라는 점이 핵심입니다. node selector는 파드가 "나는 이런 노드에 가고 싶다"고 고르는 것이고, taint는 노드가 "아무나 오지 마라"고 막는 것입니다. 고르는 쪽과 막는 쪽이 다르니 둘은 각자 성립합니다 — node selector를 통과해도 taint에 걸려 못 붙을 수 있습니다.

taint는 `key=value:effect` 형태입니다. control plane 노드에 걸린 taint를 보면 형태가 드러납니다.

```bash
kubectl get node <control-plane 노드명> -o jsonpath='{.spec.taints}'
# [{"effect":"NoSchedule","key":"node-role.kubernetes.io/control-plane"}]
```

toleration은 그 표식을 **견디겠다는 파드 쪽의 선언**입니다. 파드에 노드의 taint와 맞는 toleration이 있으면 그 노드에 붙을 수 있습니다. 주의할 점은 toleration이 파드를 그 노드로 *보내지는* 않는다는 것입니다. 막힌 문을 열어 줄 뿐이고, 어느 노드로 갈지는 여전히 node selector·nodeAffinity·자원 여유가 정합니다. 그래서 toleration만 붙이면 그 노드에 갈 수도 있고 안 갈 수도 있습니다.

### effect — 미는 강도가 셋으로 갈린다

같은 taint라도 `effect`에 따라 무엇을 막는지가 달라집니다. 갈리는 축은 둘입니다. **새로 오는 파드를 막는가**와 **이미 도는 파드를 쫓아내는가**입니다[^taint-effects].

| effect | 새 파드 스케줄 | 이미 도는 파드 | 쓰이는 자리 |
|---|---|---|---|
| `NoSchedule` | 막습니다 | 그대로 둡니다 | control plane 보호, `cordon`으로 막아 둔 노드 |
| `PreferNoSchedule` | 되도록 피하지만, 다른 자리가 없으면 붙입니다 | 그대로 둡니다 | 선호만 표현하는 약한 제약 |
| `NoExecute` | 막습니다 | **쫓아냅니다** | 노드가 not-ready·unreachable이 됐을 때 파드를 다른 노드로 옮김 |

`NoSchedule`과 `NoExecute`의 차이가 실무에서 갈리는 지점입니다. `NoSchedule`은 이미 뜬 파드를 건드리지 않으니 노드에 taint를 새로 걸어도 돌던 워크로드는 계속 돕니다. `NoExecute`는 걸린 순간 조건에 안 맞는 파드가 축출됩니다. 뒤에 나올 자동 toleration 표에서 `not-ready`·`unreachable`만 `NoExecute`인 이유가 여기 있습니다 — 노드가 죽었을 때 파드를 옮겨야 하니까요.

`PreferNoSchedule`은 강제가 아니라 선호입니다. 스케줄러가 다른 노드를 먼저 보되, 붙일 곳이 없으면 taint를 무시하고 붙입니다.

### control plane에 배포 — tolerations

일반 파드가 control plane에 스케줄되지 못하게 막는 메커니즘이 이 **taints and tolerations**입니다. 노드에는 `NoSchedule` taint가 있는데 일반 파드에는 맞는 toleration이 없으니 스케줄러가 그 노드를 후보에서 뺍니다. daemon 파드가 모든 노드에 필요한 중요 서비스면(Kube Proxy 등) 배포해야 합니다.

```bash
kubectl get ds -n kube-system
# kindnet     3  3  3  3  3  <none>            # CNI 네트워크
# kube-proxy  3  3  3  3  3  kubernetes.io...  # 모든 노드(3)
```

kube-proxy·kindnet은 3 노드 전부에 배포됩니다. 매니페스트를 보면 방법이 드러납니다.

```yaml
spec:
  template:
    spec:
      tolerations:
      - operator: Exists   # 이 파드는 모든 노드 taint를 tolerate
```

`operator: Exists`는 모든 taint를 tolerate해 파드를 절대적으로 모든 노드에 배포합니다. 이 줄은 Pod 템플릿의 일부이지 DaemonSet 직접 속성이 아닙니다. 그래도 노드가 거부할 파드를 만들 이유가 없어 DaemonSet 컨트롤러가 이 값을 고려합니다.

taint·toleration 자세한 규칙은 [스케줄링과 노드 선택](../../kubernetes/05_scheduling/05-01.%EC%8A%A4%EC%BC%80%EC%A4%84%EB%A7%81%EA%B3%BC%20%EB%85%B8%EB%93%9C%20%EC%84%A0%ED%83%9D.md) 개념본을 참고합니다.

### 컨트롤러가 알아서 붙이는 toleration

위의 `operator: Exists`는 kube-proxy 매니페스트가 *직접* 적어 둔 것입니다. 그런데 아무것도 안 적어도 DaemonSet 컨트롤러는 daemon 파드에 toleration 몇 가지를 **자동으로 추가**합니다[^auto-toleration].

toleration을 한 줄도 안 적은 DaemonSet을 만들어 파드 spec을 들여다보면 확인됩니다.

```bash
# 1. 매니페스트에 toleration 이 없음을 먼저 센다 — 0 이 나온다
grep -c tolerations daemonset-demo-plain.yaml

# 2. 배포한 뒤 파드에 실제로 박힌 toleration 을 조회한다
kubectl apply -f daemonset-demo-plain.yaml
kubectl rollout status ds demo --timeout=60s
kubectl get po -l app=demo -o jsonpath='{range .items[0].spec.tolerations[*]}{.key}{"  "}{.effect}{"\n"}{end}'
```

![매니페스트에 toleration이 0개인데 배포된 파드에는 6개가 붙어 있다](_assets/17-01-auto-toleration.gif)

첫 명령의 `0`과 마지막 출력의 여섯 줄을 붙여 읽는 자리입니다. 내가 쓴 적 없는 `not-ready`·`unreachable`이 `NoExecute`로, 나머지 넷이 `NoSchedule`로 붙어 있습니다. 컨트롤러가 채워 넣은 값입니다.

그래서 아래 상황에서도 daemon 파드가 뜹니다.

| 자동 toleration | effect | 결과 |
|---|---|---|
| `node.kubernetes.io/not-ready` | NoExecute | 아직 ready가 아닌 노드에도 스케줄되고, 이미 도는 파드는 축출되지 않습니다 |
| `node.kubernetes.io/unreachable` | NoExecute | 노드가 끊겨도 daemon 파드는 축출되지 않습니다 |
| `node.kubernetes.io/disk-pressure` · `memory-pressure` · `pid-pressure` | NoSchedule | 자원 압박 중인 노드에도 스케줄됩니다 |
| `node.kubernetes.io/unschedulable` | NoSchedule | `kubectl cordon`으로 막아 둔 노드에도 스케줄됩니다 |
| `node.kubernetes.io/network-unavailable` | NoSchedule | **`hostNetwork: true`인 daemon 파드에만** 붙으며, 네트워크가 아직 없는 노드에도 스케줄됩니다 |

not-ready toleration이 왜 필요한지는 CNI로 보면 분명합니다. 네트워크 플러그인이 안 떠서 노드가 ready가 못 되는데, 노드가 ready가 아니라서 플러그인도 못 뜨는 **교착**이 생깁니다[^auto-toleration]. 앞에서 본 kindnet이 바로 그 플러그인입니다. 이 자동 toleration이 교착을 끊습니다.

즉 control plane taint를 넘으려면 매니페스트에 직접 toleration을 써야 하지만, 노드 건강 상태와 관련된 taint는 컨트롤러가 알아서 처리합니다. 둘을 구분해 두면 "왜 어떤 taint는 넘고 어떤 taint는 못 넘는가"가 정리됩니다.

### daemon 파드 검사 — nodeAffinity

daemon 파드 매니페스트를 보면 Pod 템플릿 label 외에 컨트롤러가 추가한 label이 둘 있습니다.

- `controller-revision-hash` — StatefulSet과 같은 역할입니다. 업데이트 시 옛 템플릿 파드와 새 템플릿 파드를 구분합니다
- `pod-template-generation` — obsolete합니다

ownerReferences는 daemon 파드가 **DaemonSet에 직접 속함**을 나타냅니다. Deployment처럼 중간 오브젝트가 없습니다.

```yaml
spec:
  affinity:
    nodeAffinity:
      requiredDuringSchedulingIgnoredDuringExecution:
        nodeSelectorTerms:
        - matchFields:
          - key: metadata.name
            operator: In
            values:
            - kind-worker   # 이 파드는 특정 노드에 스케줄
```

각 파드에 `spec.affinity.nodeAffinity`가 다르게 설정되어 특정 노드에 스케줄됩니다. 이 부분은 템플릿에 없고 컨트롤러가 파드마다 추가합니다.

옛 버전은 `spec.nodeName`을 직접 설정해 Scheduler 없이 스케줄했다고 원서(§17.1)는 적습니다. 지금은 nodeAffinity를 설정하고 nodeName은 비워 **Scheduler에 스케줄을 맡깁니다**[^ds-scheduling]. 그래서 리소스 요구사항 같은 다른 조건도 함께 고려됩니다.

- `nodeName`이 채워진 파드는 스케줄러를 건너 뛰고 kubelet이 그대로 받습니다. 그러면 스케줄러가 하던 검사가 전부 생략됩니다.
- 대상 노드에 남은 메모리가 500Mi인데 파드가 `resources.requests.memory: 2Gi`를 요청해도 스케줄링은 "성공"합니다. 파드는 그 노드에 도착해서 자원 부족으로 실패합니다. 문제를 노드까지 배달한 뒤에 터지는 셈입니다.
- nodeAffinity로 넘기면 자원 여유·taint 매칭·다른 affinity 규칙을 다 보고 붙습니다. 즉 이 변경으로 daemon 파드도 **다른 파드와 똑같은 스케줄링 검증**을 받게 되었습니다.

`nodeName` 직접 지정은 어디에 쓰는가 하면, 스케줄러를 **의도적으로 우회해야 할 때**입니다. 대표가 control plane의 **static pod**입니다.

- api-server·etcd·scheduler는 노드의 `/etc/kubernetes/manifests/`에 매니페스트를 두면 kubelet이 그 디렉토리를 직접 읽어 띄웁니다. api-server가 없는 상태에서 api-server를 띄워야 하니, api-server를 거치는 스케줄러를 쓸 수가 없습니다. 앞서 본 kubelet의 순환 의존을 같은 방식으로 푼 것입니다.
- 나머지 일반 워크로드에서는 조건으로 표현하고 스케줄러에 맡기는 것이 정석입니다. `nodeName` 직접 지정은 특정 노드에서만 재현되는 문제를 확인할 때 쓰는 임시 수단 정도입니다.

템플릿에 nodeAffinity를 직접 써 두면 어떻게 될까요. 그 값은 **어느 노드가 대상인지 고르는 데**만 쓰입니다. 실제로 만들어진 파드에서는 대상 노드 이름을 가리키는 affinity로 교체됩니다[^ds-scheduling]. 노드를 고르는 단계와 파드를 그 노드에 묶는 단계가 나뉘어 있는 셈입니다.



## 3. node selector로 노드 서브셋에 배포

> DaemonSet은 taint를 tolerate하지 않는 노드를 제외한 모든 노드에 배포하지만, node selector로 특정 노드 서브셋에만 배포할 수 있습니다. node selector와 pod selector는 다릅니다. 전자는 노드를, 후자는 파드를 필터링합니다.

![node selector가 gpu:cuda label을 가진 노드에만 파드를 배포합니다 — label이 안 맞는 노드는 제외](_assets/17-01-daemonset-node-selector.svg)

특수 하드웨어가 일부 노드에만 있으면 관련 소프트웨어를 그 노드에만 돌리고 싶습니다. `spec.template.spec.nodeSelector`로 지정합니다.

```yaml
spec:
  template:
    spec:
      nodeSelector:
        gpu: cuda    # 이 label을 가진 노드에만 배포
```

```bash
kubectl get ds
# demo  0  0  0  0  0  gpu=cuda  46m   ← 맞는 노드 없어 파드 0

kubectl get nodes -l gpu=cuda
# No resources found
```

### label로 노드를 범위에 넣고 빼기

DaemonSet 컨트롤러는 DaemonSet·Pod뿐 아니라 **Node 오브젝트도 감시**합니다. 노드 label을 바꾸면 reconciliation을 돌립니다.

```bash
kubectl label node kind-worker2 gpu=cuda   # label 추가 → 파드 생성
kubectl label node kind-worker2 gpu-       # label 제거 → 파드 삭제
```

label 하나가 붙는 순간 DaemonSet이 어떻게 반응하는지 직접 돌려 보겠습니다. 아래 순서를 그대로 실행하면 됩니다.

```bash
# 1. node selector가 걸린 DaemonSet 생성 — 아직 맞는 노드가 없다
kubectl apply -f daemonset-demo-gpu.yaml
kubectl get ds demo                              # DESIRED 0

# 2. 노드에 label 부여 — 컨트롤러가 reconciliation을 돌린다
kubectl label node <노드명> gpu=cuda

# 3. 결과 확인 — 그 노드에만 파드가 뜬다
kubectl rollout status ds demo --timeout=60s
kubectl get ds demo                              # DESIRED 1
kubectl get po -l app=demo -o custom-columns=NAME:.metadata.name,STATUS:.status.phase,NODE:.spec.nodeName
```

![node selector가 걸린 DaemonSet에 노드 label을 붙이자 파드가 생기는 과정](_assets/17-01-node-selector-transition.gif)

흐름이 빠르게 지나가므로 앞뒤 상태를 따로 붙잡았습니다. label을 붙이기 전에는 조건에 맞는 노드가 없어 `DESIRED`부터 0입니다. 파드가 안 뜬 게 아니라 **띄울 노드를 못 찾은** 상태입니다.

![label 추가 전 — DESIRED 0, 조건에 맞는 노드가 없다](_assets/17-01-node-selector-pending.png)

label을 붙이면 컨트롤러가 곧바로 reconciliation을 돌려 그 노드에 파드를 만듭니다. `DESIRED`가 1로 바뀌고 파드가 그 노드에 뜹니다.

![label 추가 후 — DESIRED 1, 해당 노드에 파드 생성](_assets/17-01-node-selector-scheduled.png)

### 표준 노드 label 활용

쿠버네티스가 자동으로 붙이는 표준 label을 node selector에 쓸 수 있습니다. `kubernetes.io/arch`·`kubernetes.io/os`·`kubernetes.io/hostname` 셋입니다. AMD·ARM 노드가 섞인 클러스터면 아키텍처별 이미지를 배포하도록 DaemonSet 두 개를 만듭니다.

```yaml
      nodeSelector:
        kubernetes.io/arch: amd64   # 다른 DaemonSet은 arm
```

이미지뿐 아니라 컴퓨트 리소스도 다르게 주려면 이 다중 DaemonSet 방식이 이상적입니다. 단 이미지만 다르고 나머지가 같다면 multiarch 이미지 하나로 단일 DaemonSet이 낫습니다.

### node selector 변경 — 가변

pod label selector와 달리 node selector는 **가변**입니다. JSON patch 형식으로 바꿀 수 있습니다.

```bash
kubectl patch ds demo --type='json' -p='[{"op": "remove", "path": "/spec/template/spec/nodeSelector"}]'
```



## 4. DaemonSet 업데이트

> Pod 템플릿을 바꾸면 컨트롤러가 파드를 교체합니다. RollingUpdate(기본·maxSurge 0)와 OnDelete를 지원합니다. daemon은 노드당 하나만 돌아야 해 maxSurge 기본이 0입니다.

| 값 | 설명 |
|----|------|
| RollingUpdate | 파드를 하나씩 교체. 새 파드가 ready가 되고 minReadySeconds가 지난 뒤 다음 노드로. **기본** |
| OnDelete | 반자동. 각 파드를 수동 삭제하면 새 템플릿으로 교체. 원하는 속도로 |

RollingUpdate는 Deployment의 것과, OnDelete는 StatefulSet의 것과 비슷합니다. Deployment처럼 maxSurge·maxUnavailable를 설정하지만 **기본값이 다릅니다**. `maxUnavailable`은 1, `maxSurge`는 0, `minReadySeconds`는 0입니다[^update-defaults].

### RollingUpdate — maxSurge 0

```yaml
spec:
  minReadySeconds: 30
  updateStrategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 0          # 기본값
      maxUnavailable: 1    # 기본값
```

`maxSurge`가 0이라 컨트롤러가 기존 daemon 파드를 **먼저 중지**한 뒤 새것을 만듭니다. 0이 기본이자 가장 합리적입니다. daemon 워크로드는 보통 노드 에이전트라 한 번에 한 인스턴스만 돌아야 하기 때문입니다.

maxSurge를 0보다 크게 하면 업데이트 중 한 노드에 인스턴스 둘이 돕니다. 대부분의 데몬은 lock으로 다중 인스턴스를 막습니다. 그래서 새 파드가 lock을 못 얻어 ready가 안 되고 업데이트가 실패합니다.

`maxUnavailable` 1은 한 번에 노드 하나만 업데이트합니다. 이전 노드 파드가 ready·available이 되기 전엔 다음으로 넘어가지 않습니다. 더 빠르게 하려면 maxUnavailable을 올립니다. 노드 수보다 크게 하면 모든 노드가 동시에 업데이트됩니다 — Deployment의 Recreate처럼 동작합니다.

> **주의.** DaemonSet에 Recreate를 구현하려면 maxSurge 0·maxUnavailable을 10000 이상으로 둡니다. 항상 노드 수보다 크기 때문입니다. 또 기존 daemon 파드의 readiness probe가 실패하면 컨트롤러가 즉시 삭제·교체하며, 이때 maxSurge·maxUnavailable은 무시됩니다.

### OnDelete — 반자동

```yaml
spec:
  updateStrategy:
    type: OnDelete   # 파라미터 없음
```

수동 삭제한 파드만 교체합니다. 원서(§17.1)의 실습에서는 `kubectl delete po demo-k2d6k --wait=false`로 삭제하면 새 v3 파드로 교체되고 다른 파드는 v2로 남습니다. `--wait=false`는 삭제 완료를 기다리지 않고 종료하라는 뜻입니다.

클러스터 중요 파드를 더 통제된 방식으로 업데이트할 때 유용합니다. RollingUpdate는 첫 노드 업데이트가 그 노드의 다른 파드를 망가뜨려도 minReadySeconds만 지나면 다음으로 진행해 연쇄 장애를 낼 수 있습니다. OnDelete는 각 daemon 파드 업데이트 후 다른 파드의 정상 동작을 확인하고 다음을 지울 수 있습니다.



## 5. DaemonSet 삭제

> DaemonSet을 삭제하면 모든 daemon 파드가 함께 삭제됩니다.

```bash
kubectl delete ds demo   # demo 파드 전부 Terminating
```

daemon 파드는 Deployment·StatefulSet 파드와 달리 노드 파일시스템·네트워크 인터페이스·기타 하드웨어에 접근하는 경우가 많습니다. 다음 편에서 다룹니다.

> **Spring 관점.** Spring Boot 앱은 보통 Deployment로 배포하지 DaemonSet으로 하지 않습니다. DaemonSet은 그 아래 인프라를 배포합니다. 노드마다 도는 Fluent Bit(로그)·node-exporter(메트릭)·Datadog agent 같은 관측 에이전트입니다. Boot 앱은 이 에이전트가 수집한 데이터를 소비하는 쪽입니다. 에이전트 자체를 DaemonSet으로 노드마다 하나씩 띄우는 것이 노드별 완전 커버리지를 보장합니다.

## 정답 (자답 후 펼치기)

> 위 질문에 답해 본 다음 아래와 맞춰 봅니다. 순서는 질문과 1:1로 대응합니다.

### 정답 1 — DaemonSet vs ReplicaSet

DaemonSet은 Pod 템플릿·label selector를 갖는 점이 ReplicaSet과 같습니다. 다른 점은 **replica 수를 지정하지 않는다**는 것입니다. 컨트롤러가 클러스터 노드 수만큼 파드를 만들고 각기 다른 노드에 정확히 하나씩 스케줄합니다.

ReplicaSet은 파드를 클러스터에 흩뿌려 한 노드에 여러 개가 갈 수 있지만, DaemonSet은 노드당 하나입니다. 목적이 "몇 개를 돌릴까"가 아니라 "모든 노드에 하나씩"이라 replicas가 의미 없습니다.

### 정답 2 — control plane taint

DaemonSet이 node selector 없이도 control plane 노드(kind-control-plane)에는 배포하지 않기 때문입니다. control plane 노드는 클러스터 제어 컴포넌트만 돌리기 위한 것이라 **taint**가 걸려 있습니다. 쿠버네티스는 명시적으로 허용(toleration)할 때만 워크로드를 스케줄합니다. 오작동 워크로드가 클러스터 전체에 악영향을 줄 위험 때문입니다.

그래서 worker 2개에만 배포되어 파드가 2개입니다. 모든 노드에 배포하려면 Pod 템플릿에 `tolerations: [{operator: Exists}]`를 둡니다.

### 정답 3 — status는 노드 수, selector 구분

DaemonSet의 status 필드는 `currentNumberScheduled`·`numberReady`처럼 이름이 파드를 세는 것 같지만, 실제로는 모두 **노드 수**를 셉니다. 관심사가 클러스터 전체 파드 수가 아니라 DaemonSet이 서비스하는 노드 수이기 때문입니다.

업데이트 중에는 한 노드에 파드가 잠시 둘일 수 있어 파드 수와 노드 수가 갈립니다.

두 selector도 대상이 다릅니다.

- **node selector** — 파드를 스케줄할 *노드*를 필터링합니다.
- **pod(label) selector** — 어느 *파드*가 DaemonSet에 속하는지를 정합니다.

### 정답 4 — maxSurge 0 기본

daemon 워크로드는 보통 노드 에이전트·데몬이라 한 노드에 **한 인스턴스만 돌아야** 하기 때문입니다. maxSurge가 0이면 컨트롤러가 기존 파드를 먼저 중지한 뒤 새것을 만들어, 노드에 인스턴스가 하나만 유지됩니다.

maxSurge를 0보다 크게 하면 업데이트 중 한 노드에 둘이 돕니다. 대부분의 데몬은 lock으로 다중 인스턴스를 막아, 새 파드가 lock을 못 얻어 ready가 안 되고 업데이트가 실패합니다.

### 정답 5 — OnDelete의 안전성

RollingUpdate는 첫 노드의 daemon 파드 업데이트가 그 노드의 **다른 파드들을 망가뜨려도** minReadySeconds만 지나면 다음 노드로 진행합니다. daemon의 readiness probe가 같은 노드의 다른 파드 상태까지 확인하지는 않기 때문입니다. 그래서 연쇄 장애가 클러스터 전체를 무너뜨릴 수 있습니다.

OnDelete는 각 daemon 파드를 수동 삭제해야 교체됩니다. 한 파드 업데이트 후 그 노드의 다른 파드가 정상인지 확인하고 다음을 지울 수 있어 클러스터 중요 daemon에 더 안전합니다.

### 정답 6 — 컨트롤러가 붙이는 toleration

DaemonSet 컨트롤러가 daemon 파드에 toleration을 **자동으로 추가**하기 때문입니다[^auto-toleration].

`node.kubernetes.io/not-ready`·`unreachable`은 NoExecute라 그런 노드에도 스케줄되고 이미 도는 파드가 축출되지 않습니다. `unschedulable`은 NoSchedule이라 `kubectl cordon`한 노드에도 뜹니다. 자원 압박(disk·memory·pid) taint도 마찬가지입니다. `network-unavailable`은 같은 NoSchedule이되 `hostNetwork: true`인 daemon 파드에만 붙습니다.

이유는 교착 방지입니다. CNI 플러그인이 안 떠서 노드가 ready가 못 되는데 노드가 ready가 아니라서 플러그인도 못 뜨는 상황을, not-ready toleration이 끊어 줍니다. 반면 control plane taint는 이 자동 목록에 없습니다. 넘으려면 매니페스트에 직접 toleration을 써야 합니다.

[^auto-toleration]: 공식 문서 [DaemonSet — Taints and tolerations](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/#taints-and-tolerations). 이 절은 DaemonSet 컨트롤러가 daemon 파드에 toleration 묶음을 자동으로 추가한다고 밝히고, 표로 일곱 항목을 나열합니다(원문 문장에는 용어 링크 마크업이 섞여 있어 축자 인용하지 않습니다). 본문 표는 그중 pressure 3종을 한 행으로 묶어 다섯 행으로 줄인 것입니다. `network-unavailable` 행에는 "**Only added for DaemonSet Pods that request host networking**, i.e., Pods having `spec.hostNetwork: true`"라는 단서가 붙습니다. 교착 설명은 같은 절의 "you could end up in a deadlock situation where the node is not marked as ready because the network plugin is not running there, and at the same time the network plugin is not running on that node because the node is not yet ready."입니다. `unschedulable` toleration에 대해서는 "Kubernetes can run DaemonSet Pods on nodes that are marked as _unschedulable_"이라고 적습니다.
[^taint-effects]: 공식 문서 [Taints and Tolerations](https://kubernetes.io/docs/concepts/scheduling-eviction/taint-and-toleration/). `NoSchedule`은 "no new Pods will be scheduled on the tainted node unless they have a matching toleration. Pods currently running on the node are **not** evicted."이고, `PreferNoSchedule`은 "a *preference* or *soft* version of `NoSchedule`. The control plane will *try* to avoid placing a Pod that does not tolerate the taint on the node, but it is not guaranteed."입니다. `NoExecute`에 대해서는 "Pods that do not tolerate the taint are evicted immediately"라고 적습니다. 본문 표의 세 번째 열(쓰이는 자리)은 원문 서술이 아니라 이 문서 §2의 자동 toleration 표와 대조해 붙인 것입니다.
[^ds-scheduling]: 공식 문서 [DaemonSet — How Daemon Pods are scheduled](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/#how-daemon-pods-are-scheduled). "The DaemonSet controller creates a Pod for each eligible node and adds the `spec.affinity.nodeAffinity` field of the Pod to match the target host. After the Pod is created, the default scheduler typically takes over and then binds the Pod to the target host by setting the `.spec.nodeName` field." 템플릿에 쓴 nodeAffinity에 대해서는 "is taken into consideration by the DaemonSet controller when evaluating the eligible nodes, but is replaced on the created Pod with the node affinity that matches the name of the eligible node."라고 적습니다.
[^update-defaults]: 공식 문서 [Perform a Rolling Update on a DaemonSet](https://kubernetes.io/docs/tasks/manage-daemon/update-daemon-set/). `maxUnavailable`은 "(default to 1)", `minReadySeconds`는 "(default to 0)", `maxSurge`는 "(defaults to 0)"입니다. 같은 문서가 `RollingUpdate`를 "This is the default update strategy."로, `OnDelete`를 "new DaemonSet pods will *only* be created when you manually delete old DaemonSet pods"로 설명합니다.
[^orphan-adopt]: 공식 문서 [DaemonSet — Updating a DaemonSet](https://kubernetes.io/docs/concepts/workloads/controllers/daemonset/#updating-a-daemonset). "If you specify `--cascade=orphan` with `kubectl`, then the Pods will be left on the nodes. If you subsequently create a new DaemonSet with the same selector, the new DaemonSet adopts the existing Pods. If any Pods need replacing the DaemonSet replaces them according to its `updateStrategy`."
