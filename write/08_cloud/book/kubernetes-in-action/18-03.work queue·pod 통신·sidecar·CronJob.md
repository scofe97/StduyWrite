# work queue·pod 통신·sidecar·CronJob

> Job은 정적으로 나눈 일뿐 아니라 큐에서 동적으로 일을 꺼내 처리하고, 파드끼리 통신하며, 사이드카를 담을 수 있습니다. 그리고 이 모든 Job을 시간표에 따라 돌리는 것이 CronJob입니다.

읽고 나면 다음을 할 수 있습니다.

- work queue를 coarse·fine 방식으로 처리하는 Job을 구분합니다.
- 인덱스 Job의 파드가 어떻게 서로를 찾는지 설명합니다.
- Job에 사이드카를 올바르게 넣는 법을 말합니다.
- CronJob의 schedule·동시성 정책·자동 삭제를 설정합니다.



## 진입 — 정적 분할에서 동적 큐로, 그리고 예약 실행으로
> 앞 편의 Job은 일을 미리 정해 나눴습니다. 실제로는 큐에서 일을 꺼내 쓰거나, 정해진 시각에 반복 실행해야 할 때가 많습니다.

앞 편([18-02](./18-02.Job%20%EB%B3%91%EB%A0%AC%C2%B7%EC%8B%A4%ED%8C%A8%C2%B7%EC%99%84%EB%A3%8C%20%EB%AA%A8%EB%93%9C.md))의 Job은 정적인 일(월별 집계)을 파드에 나눴습니다. 하지만 처리할 일이 동적으로 정해지는 경우도 많습니다. 이때는 입력을 Job에 박아 넣는 대신, 파드가 큐에서 일을 꺼내 처리합니다.

아래는 이 편 전체를 한 장으로 이은 지도입니다. 위 두 층은 Job 하나를 넓히는 이야기이고, 맨 아래 층의 CronJob은 층위가 다릅니다. Job을 고치는 게 아니라, 그 Job을 시간표에 올려 반복시키는 바깥 껍질입니다.

- §1 큐 — 일을 미리 나누지 않고 파드가 꺼내 씁니다
- §2 통신 — 인덱스 Job의 파드가 DNS로 서로를 찾습니다
- §3 사이드카 — Job 파드에 넣는 자리가 따로 있습니다
- §4~§6 CronJob — 시간표·동시성·보존을 정합니다

상자의 색은 상태의 성격을 나타냅니다. 초록은 진행 중, 보라는 성공, 붉은색은 주의가 필요한 자리, 노란색은 대기입니다. 점선에 `if:`가 붙은 전이는 조건이 맞을 때만 일어납니다.

위층 오른쪽의 `exit 0`이 이 편 전체의 이음매입니다. Kubernetes는 큐를 모르므로, 컨테이너가 "큐가 비었다"를 종료 코드로 번역해 주어야 Job이 완료를 압니다. 가운데 층 오른쪽의 `사이드카`는 일반 컨테이너에 두면 Job이 영영 끝나지 않는 자리이고, 아래층 오른쪽의 `동시성 정책`은 같은 CronJob이 만든 Job 사이에만 적용된다는 제약을 담습니다.

## 1. work queue로 일 처리
> 큐와 아이템 인출은 Kubernetes가 아니라 컨테이너가 구현합니다. Job은 파드 수만 관리합니다.

Kubernetes 자체가 큐 기능을 제공하는 것은 아닙니다. 큐와, 큐에서 아이템을 꺼내는 컴포넌트를 컨테이너 안에 직접 구현해야 합니다. 그런 다음 그 컨테이너를 파드로 돌리는 Job을 만듭니다. 큐 처리에는 두 방식이 있습니다.

`kind: Queue` 같은 리소스는 없습니다. Redis·RabbitMQ·Kafka·MongoDB 중 무엇을 쓰든 Kubernetes는 관여하지 않습니다. [18-01](./18-01.Job%20%EA%B8%B0%EC%B4%88%20%E2%80%94%20%EC%8B%A4%ED%96%89%C2%B7%EC%83%81%ED%83%9C%C2%B7suspend%C2%B7%EC%9E%90%EB%8F%99%EC%82%AD%EC%A0%9C.md)의 층 구분으로 보면 큐를 아는 것은 맨 아래 한 층뿐입니다.

| 층 | 큐를 아는가 |
|---|---|
| Job 컨트롤러 | 모름 — 완료된 파드 수만 셈 |
| kubelet | 모름 — 컨테이너 종료 코드만 봄 |
| Container | **앎** — 큐에 붙어 아이템을 꺼냄 |

그래서 두 층 사이의 유일한 통신 수단이 **종료 코드**입니다. 컨테이너가 "큐가 비었다"를 exit 0으로 번역해 주어야 Job이 완료를 압니다. 이 번역이 아래 두 방식의 뼈대입니다.

> **큐에는 참조를 넣습니다.** 이미지 변환처럼 큰 데이터를 다룰 때 원본 바이트를 큐에 싣지 않습니다. 원본은 오브젝트 스토리지에 두고 큐에는 `{"bucket": "uploads", "key": "img-8821.png"}` 같은 위치만 넣습니다. 큐 메시지에는 대개 크기 제한이 있고(Kafka 기본 1MB, SQS 256KB), 바이트를 실으면 큐가 스토리지 노릇을 하게 되어 재처리와 보관이 까다로워집니다. 아래 예제의 `monthsToProcess` 컬렉션도 "몇 월"이라는 참조만 담습니다.

![coarse 병렬 처리는 파드마다 큐 아이템 하나를 처리하고, fine 병렬 처리는 파드마다 여러 아이템을 큐가 빌 때까지 처리하는 두 방식 비교](_assets/18-03-work-queue-coarse-fine.svg)

### 1.1 coarse — 파드당 아이템 하나

coarse(굵은) 병렬 처리에서 각 파드는 큐에서 아이템 하나를 꺼내 처리하고 종료합니다. 따라서 work 아이템당 파드 하나가 나옵니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: aggregate-responses-queue-coarse
spec:
  completions: 6      # 여섯 개 아이템 처리 (파드당 하나)
  parallelism: 3      # 세 파드 동시 실행
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: processor
          image: mongo:5
          command: [...]   # 큐에서 하나 꺼내 처리하는 스크립트
```

스크립트는 큐에서 아이템 하나(`findOneAndDelete`)를 꺼내 처리합니다. 큐가 비면 exit code 0으로 종료해 처리 완료를 알립니다.

```javascript
var workItem = db.monthsToProcess.findOneAndDelete({});
if (workItem == null) {
    print("No work item found. Processing is complete.");
    quit(0);            // 큐가 비면 성공으로 종료
}
// ... 아이템 처리 ...
quit(0);
```

`completions=6`이므로 파드 여섯 개가 각각 아이템 하나씩 처리합니다.

### 1.2 fine — 파드당 여러 아이템

fine(가는) 병렬 처리에서 각 파드는 큐가 빌 때까지 여러 아이템을 처리합니다. 아이템을 꺼내 처리하고, 다음 아이템을 꺼내 반복합니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: aggregate-responses-queue-fine
spec:
  parallelism: 3      # completions는 설정하지 않음
  template:
    spec:
      ...
```

fine 방식은 `completions`를 설정하지 않습니다. 파드 하나가 성공적으로 완료됐다는 것은 큐의 모든 아이템이 처리됐음을 뜻하기 때문입니다(마지막 아이템을 처리한 파드가 성공으로 종료). 스크립트는 큐가 빌 때까지 루프를 돕니다.

```javascript
while (true) {
    var workItem = db.monthsToProcess.findOneAndDelete({});
    if (workItem == null) {
        print("No work item found. Processing is complete.");
        quit(0);        // 큐가 비면 루프 종료
    }
    // ... 아이템 처리 ...
}
```

한 파드가 성공을 보고했을 때 다른 파드가 아직 아이템을 처리 중이면, Job 컨트롤러는 다른 파드들이 일을 마치도록 놔둡니다. 죽이지 않습니다.

죽이지 않는 이유가 있습니다. 파드는 `findOneAndDelete`로 아이템을 **큐에서 이미 꺼낸** 상태입니다. 여기서 강제로 종료시키면 큐에도 없고 결과도 없는 아이템이 생깁니다. 그래서 컨트롤러는 새 파드를 만들지 않을 뿐, 도는 파드는 건드리지 않습니다.

파드를 끝내는 것도 컨트롤러가 아닙니다. **컨테이너가 스스로 종료합니다.** 루프를 돌다 빈 큐에서 `null`을 받으면 `quit(0)`으로 끝나고, 나머지 파드도 곧 같은 길을 갑니다.

#### completions를 설정하지 않는 이유

fine 방식에서 파드 하나의 성공은 곧 **큐가 비었다는 뜻**입니다. 그 파드가 `null`을 받아야 exit 0 하기 때문입니다. 그러니 "몇 번 성공해야 끝"을 셀 이유가 없습니다. 한 번이면 충분합니다.

[18-02](./18-02.Job%20%EB%B3%91%EB%A0%AC%C2%B7%EC%8B%A4%ED%8C%A8%C2%B7%EC%99%84%EB%A3%8C%20%EB%AA%A8%EB%93%9C.md) §1.1 조합표의 마지막 행이 이 동작입니다 — `completions` 미설정, `parallelism` N이면 "N개 파드가 동시에 돌지만 하나만 성공하면 Job 완료"입니다.

여기에 아이템 수를 넣으면 오히려 헛일이 생깁니다. 아이템 6개를 파드 3개가 나눠 처리하고 큐가 비면 성공 파드는 3개입니다. `completions: 6`이라면 컨트롤러가 3개를 더 만들고, 그 파드들은 빈 큐를 보고 즉시 종료합니다. **일 없이 뜨고 죽는 파드**만 늘어납니다.

두 방식을 나란히 두면 이렇습니다.

| | coarse | fine |
|---|---|---|
| 파드당 아이템 | 1개 | 큐가 빌 때까지 |
| `completions` | 아이템 수 | 설정하지 않음 |
| `parallelism` | 동시 실행 수 | 동시 실행 수 |
| 아이템 수를 미리 알아야 하나 | 알아야 함 | 몰라도 됨 |

마지막 줄이 fine의 존재 이유입니다. 처리할 일이 몇 개인지 모를 때 쓸 수 있는 쪽은 fine뿐입니다.

### 1.3 Job은 지속 감시가 아니다

Job이 완료된 뒤 큐에 새 아이템을 넣으면 어떻게 될까요? Kubernetes는 큐를 모릅니다. 파드 안 컨테이너만 큐의 존재를 압니다. 그래서 Job이 끝난 뒤 새 아이템을 추가해도, Job을 다시 만들지 않는 한 처리되지 않습니다.

Job은 작업을 완료까지 실행하도록 설계됐지, 지속적으로 감시하도록 설계되지 않았습니다. 큐를 계속 감시하는 워커 파드가 필요하면 Deployment로 돌려야 합니다. 정해진 주기로 Job을 돌리려면 CronJob을 씁니다(아래 4절).

#### 큐 컨슈머를 Deployment로 둘지 Job으로 둘지

큐 처리라고 해서 Job이 기본은 아닙니다. 갈리는 기준은 **"끝났다"는 시점이 필요한가**입니다.

| | Deployment 워커 | Job |
|---|---|---|
| 언제 끝나나 | 끝나지 않음(계속 대기) | 큐가 비면 끝 |
| 맞는 일 | 상시 유입되는 요청 | 한 묶음을 다 처리해야 하는 배치 |
| 완료 통보 | 없음 | Job이 `Complete`가 됨 |
| 유휴 비용 | 일이 없어도 파드가 떠 있음 | 없음 |
| 기동 비용 | 한 번 | 실행할 때마다 |

이미지 업로드처럼 트래픽이 상시 들어오면 Deployment가 맞습니다. 반면 "어젯밤 쌓인 정산 건을 새벽에 다 처리하고 끝나면 다음 단계로 넘어간다"면 Job입니다. 완료 시점이 있어야 후속 작업을 걸 수 있기 때문입니다.

Job 쪽 이점은 자원 회수와 완료 판정입니다. 처리할 일이 없을 때 파드가 놀지 않고, 실패와 타임아웃을 `backoffLimit`·`activeDeadlineSeconds`로 Kubernetes에 위임할 수 있습니다. 대신 매번 파드를 띄우는 비용을 치릅니다. 이 트레이드오프는 §7에서 `@Scheduled`와 CronJob을 비교할 때 다시 나옵니다.

#### 완료된 파드는 언제 사라지는가

파드가 exit 0으로 끝나도 목록에서 사라지지 않습니다. `Completed` 상태로 남아 로그를 볼 수 있게 합니다([18-01](./18-01.Job%20%EA%B8%B0%EC%B4%88%20%E2%80%94%20%EC%8B%A4%ED%96%89%C2%B7%EC%83%81%ED%83%9C%C2%B7suspend%C2%B7%EC%9E%90%EB%8F%99%EC%82%AD%EC%A0%9C.md) §4). 치우는 경로는 넷이고 주체가 각각 다릅니다.

| 계기 | 주체 | 지워지는 것 | 시점 |
|---|---|---|---|
| 컨테이너 exit 0 | 없음 | 아무것도 안 지워짐 | 파드는 `Completed`로 남음 |
| `ttlSecondsAfterFinished` | TTL 컨트롤러 | Job과 그 파드들 | 완료 후 지정 초 |
| `kubectl delete job` | 가비지 컬렉터 | Job과 그 파드들 | 소유자가 사라진 직후 |
| CronJob history limit | CronJob 컨트롤러 | 오래된 Job과 그 파드들 | 성공 3개·실패 1개 초과분 |

첫 줄이 핵심입니다. 아무도 치우지 않는 것이 기본이라 방치하면 `Completed` 파드가 쌓입니다. 지울 때는 파드를 직접 겨냥하지 않고 **Job 오브젝트를 지웁니다**. 파드의 `ownerReferences`가 Job을 가리키므로([18-02](./18-02.Job%20%EB%B3%91%EB%A0%AC%C2%B7%EC%8B%A4%ED%8C%A8%C2%B7%EC%99%84%EB%A3%8C%20%EB%AA%A8%EB%93%9C.md) §1), 소유자가 사라지면 가비지 컬렉터가 딸린 파드를 회수합니다.



## 2. Job 파드 간 통신
> 인덱스 Job 파드는 headless Service와 `subdomain`을 쓰면, peer의 이름을 DNS로 계산해 서로 통신할 수 있습니다.

대부분 Job 파드는 서로 독립적으로 돌지만, 일부 작업은 파드끼리 통신해야 합니다. 파드가 특정 peer(임의의 파드가 아니라)와 통신하려면 세 가지를 하면 됩니다.

1. Job의 `completionMode`를 `Indexed`로 설정합니다.
2. headless Service를 만듭니다.
3. Pod 템플릿의 `subdomain`을 그 Service로 설정합니다.

### 2.1 headless Service와 subdomain

```yaml
apiVersion: v1
kind: Service
metadata:
  name: demo-service
spec:
  clusterIP: none         # headless Service (11장 참조)
  selector:
    job-name: comm-demo   # Job이 만든 파드에 자동으로 붙는 레이블
  ports:
    - name: http
      port: 80
```

셀렉터는 Job이 만든 파드와 일치해야 하는데, 가장 쉬운 방법은 자동으로 붙는 `job-name` 레이블을 쓰는 것입니다. 이 값은 Job 이름과 같으므로, 셀렉터의 값이 Job 이름과 일치해야 합니다.

`clusterIP: none`이 하는 일은 **가상 IP를 만들지 않는 것**입니다. 보통 Service는 VIP 하나를 받아 그 뒤 파드들로 부하를 나누므로 특정 파드를 지목할 수 없습니다. headless Service는 VIP가 없어, DNS가 Service 이름을 **각 파드의 개별 이름**으로 답합니다. 등록되는 주소는 각 파드의 **파드 IP**입니다. 노드 IP가 아닙니다 — 그것은 [17-02](./17-02.%EB%85%B8%EB%93%9C%20%EC%97%90%EC%9D%B4%EC%A0%84%ED%8A%B8%20%ED%8A%B9%EC%88%98%20%EA%B8%B0%EB%8A%A5%20%E2%80%94%20privileged%C2%B7hostPath%C2%B7hostNetwork%C2%B7PriorityClass.md)에서 본 `hostNetwork: true`인 파드에만 해당합니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: comm-demo         # 위 Service 셀렉터의 값과 일치
spec:
  completionMode: Indexed
  completions: 2
  parallelism: 2          # 두 파드가 병렬로 돌며 서로 통신
  template:
    spec:
      subdomain: demo-service   # headless Service 이름
      restartPolicy: Never
      containers:
        - name: comm-demo
          image: busybox
          command: [sleep, "600"]
```

`completionMode`를 `Indexed`로 두고 `subdomain`을 headless Service 이름으로 설정하면, 파드들은 DNS로 서로를 찾을 수 있습니다.

### 2.2 peer 이름 계산

첫 파드의 hostname을 확인하면 다음과 같습니다.

```bash
kubectl exec comm-demo-0-mrvlp -- hostname -f
```

```pseudocode
comm-demo-0.demo-service.kiada.svc.cluster.local
```

두 번째 파드는 이 주소로 첫 파드와 통신할 수 있습니다. 파드 이름은 임의(random)임에도, Job 안 파드는 다음 패턴으로 peer 이름을 계산할 수 있습니다.

```pseudocode
comm-demo-0.demo-service.kiada.svc.cluster.local
└── Job 이름 + 인덱스 ┘ └ Service ┘ └ NS ┘ └ 클러스터 도메인 ┘
```

같은 네임스페이스라면 FQDN이 아니라 짧은 이름(`comm-demo-0.demo-service`)으로도 접속할 수 있습니다. 파드는 `completions` 값으로 몇 개의 파드가 같은 Job에 속하는지 알기에, DNS로 모든 peer 이름을 계산할 수 있습니다. Kubernetes API 서버에 물을 필요가 없습니다. 이 방식은 16장 StatefulSet의 per-pod DNS(`<pod>-<ordinal>.<service>`)와 같은 패턴입니다.

이름이 계산 가능한 것은 hostname에 **임의 문자열이 들어가지 않기** 때문입니다. 파드 이름은 `comm-demo-0-mrvlp`처럼 뒤에 임의 부분이 붙지만, hostname은 `comm-demo-0`까지입니다. 인덱스가 0부터 연속이므로 `completions`만 알면 나머지 peer를 전부 짚어 낼 수 있습니다.

여기서 Downward API와의 경계가 갈립니다. Downward API는 자기 노드 IP나 자기 인덱스처럼 **자기 정보**만 줍니다. 0번 파드가 그것으로 알 수 있는 것은 "나는 0번"까지입니다.

**남의 주소는 DNS가 답합니다.** 자기 정보는 Downward API([17-03](./17-03.%EB%A1%9C%EC%BB%AC%20daemon%20%ED%8C%8C%EB%93%9C%20%ED%86%B5%EC%8B%A0%20%E2%80%94%20hostPort%C2%B7hostNetwork%C2%B7internalTrafficPolicy.md)), peer 주소는 headless Service로 나뉘는 셈입니다.



## 3. Job 파드의 사이드카
> Job 파드에서 사이드카는 반드시 `restartPolicy: Always`인 init 컨테이너로 정의해야 합니다. 일반 컨테이너에 두면 Job이 영원히 완료되지 않습니다.

Job 파드도 일반 파드처럼 사이드카를 담을 수 있습니다. 단 한 가지 주의점이 있습니다. Job 파드는 **모든 컨테이너가 멈춰야** 완료로 간주됩니다. 메인 컨테이너는 작업이 끝나면 종료하지만, 사이드카는 보통 무한히 돕니다. 사이드카를 Pod 템플릿의 `spec.containers`에 두면 파드가 완료되지 못합니다.

### 3.1 잘못된 방법 — 일반 컨테이너

메인과 사이드카를 둘 다 `spec.containers`에 정의하면, 사이드카가 절대 멈추지 않아 파드가 완료되지 않습니다.

```bash
kubectl get jobs
```

```pseudocode
NAME              STATUS    COMPLETIONS   DURATION   AGE
demo-bad-sidecar  Running   0/1           2m46s      2m46s
```

메인 컨테이너가 완료돼도 파드는 계속 돌고 `NotReady`(2/2 → 1/2)로 표시됩니다. 메인 컨테이너가 더 이상 ready가 아니기 때문입니다. Job은 무한히 실행 중으로 남습니다. 이 상태를 해결할 방법은 Job을 지우는 것뿐입니다.

### 3.2 올바른 방법 — 네이티브 사이드카

Job 파드에 사이드카를 넣는 올바른 방법은 5장에서 배운 대로 `initContainers`에 `restartPolicy: Always`로 정의하는 것입니다.

```yaml
apiVersion: batch/v1
kind: Job
metadata:
  name: demo-good-sidecar
spec:
  completions: 1
  template:
    spec:
      restartPolicy: OnFailure
      initContainers:
        - name: sidecar
          restartPolicy: Always    # 네이티브 사이드카 = restartPolicy Always인 init 컨테이너
          image: busybox
          command:
            - sh
            - -c
            - "while true; do echo 'Sidecar still running...'; sleep 5; done"
      containers:
        - name: demo             # 메인 컨테이너는 평범하게 정의
          image: busybox
          command: [sleep, "20"]
```

이렇게 하면 메인 컨테이너가 끝났을 때 파드가 `Completed`로 표시되고, 사이드카는 그 뒤 종료됩니다. 파드가 완료됐으므로 Job도 완료됩니다.

이름은 init 컨테이너인데 동작이 다릅니다. 보통 init 컨테이너는 **끝나야** 다음 단계가 시작되지만, `restartPolicy: Always`가 붙으면 시작만 하고 메인 컨테이너와 나란히 돕니다. 그리고 결정적으로 **파드 완료 판정에서 빠집니다**.

**같은 컨테이너를 어느 목록에 넣느냐로 판정이 갈리는 셈입니다.**

| 넣는 자리 | 완료 판정에 포함되나 | 결과 |
|---|---|---|
| `containers` | 포함 | 사이드카가 안 끝나 Job이 영영 `Running` |
| `initContainers` + `restartPolicy: Always` | 제외 | 메인이 끝나면 파드가 `Completed` |

[18-01](./18-01.Job%20%EA%B8%B0%EC%B4%88%20%E2%80%94%20%EC%8B%A4%ED%96%89%C2%B7%EC%83%81%ED%83%9C%C2%B7suspend%C2%B7%EC%9E%90%EB%8F%99%EC%82%AD%EC%A0%9C.md) §2에서 본 `Succeeded` 정의가 여기서 그대로 걸립니다. "파드 안 **모든** 컨테이너가 성공으로 종료"해야 하므로, 끝나지 않는 컨테이너가 그 목록에 하나라도 있으면 판정이 성립하지 않습니다.



## 4. CronJob — Job을 예약 실행
> CronJob은 Job 템플릿과 schedule을 감싸, 정해진 시각·주기마다 Job을 자동으로 만듭니다.

Job 오브젝트를 만들면 즉시 실행됩니다. suspend로 만든 뒤 나중에 재개할 수는 있어도, 특정 시각에 실행하도록 설정할 수는 없습니다. 이를 위해 Job을 `CronJob`으로 감쌉니다.

CronJob에는 Job 템플릿과 schedule을 지정합니다. CronJob 컨트롤러는 이 schedule에 따라 템플릿에서 새 Job 오브젝트를 만듭니다. 하루 여러 번, 특정 시각, 특정 요일 등으로 설정할 수 있습니다. CronJob 오브젝트를 지울 때까지 컨트롤러는 계속 Job을 만듭니다.

![CronJob 동작: schedule에 맞춰 새 Job 오브젝트가 만들어지고, 그 Job이 파드를 띄워 완료까지 실행하는 주기 반복](_assets/18-03-cronjob-operation.svg)

### 4.1 CronJob 생성

매분 Job을 도는 CronJob입니다.

```yaml
apiVersion: batch/v1
kind: CronJob            # CronJob도 batch/v1
metadata:
  name: aggregate-responses-every-minute
spec:
  schedule: "* * * * *"  # crontab 형식. 이 값은 매분 실행
  jobTemplate:           # CronJob은 Job 템플릿을 지정해야 함
    metadata:
      labels:
        app: aggregate-responses-today
    spec:
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: updater
              image: mongo:5
              command: [...]
```

CronJob은 Job을 감싼 얇은 래퍼입니다. `spec`의 핵심은 `schedule`과 `jobTemplate` 둘뿐입니다. 조회는 `kubectl get cj`(cj는 CronJob의 약어)로 합니다.

```bash
kubectl get cj
```

```pseudocode
NAME                               SCHEDULE    ...  ACTIVE  LAST SCHEDULE  AGE
aggregate-responses-every-minute   * * * * *   ...  0       <none>         2s
```

CronJob 컨트롤러는 Job 컨트롤러와 달리 Job에 레이블을 자동으로 붙이지 않습니다. 특정 CronJob이 만든 Job을 나열하려면 Job 템플릿에 직접 레이블을 넣어야 합니다(위 예의 `app: aggregate-responses-today`).

> 언제든 CronJob에서 Job을 수동으로 만들 수 있습니다. `kubectl create job my-job --from=cronjob/my-cronjob`은 예약 시각을 기다리지 않고 CronJob을 테스트할 때 유용합니다.

### 4.2 상세 상태

`kubectl get cj`는 현재 활성 Job 수와 마지막 예약 시각만 보여 줄 뿐, 마지막 Job이 성공했는지는 알려 주지 않습니다. Job을 직접 나열하거나 CronJob의 `status`를 YAML로 봅니다.

```bash
kubectl get cj aggregate-responses-every-minute -o yaml
```

```pseudocode
...
status:
  active:                # 현재 실행 중인 Job 목록
    - apiVersion: batch/v1
      kind: Job
      name: aggregate-responses-every-minute-27755221
      ...
  lastScheduleTime: "2022-10-09T11:01:00Z"    # 마지막 예약 시각
  lastSuccessfulTime: "2022-10-09T11:00:41Z"  # 마지막 성공 시각
```

`lastScheduleTime`과 `lastSuccessfulTime`을 비교하면 마지막 실행이 성공했는지 추론할 수 있습니다.



## 5. crontab schedule 형식
> schedule은 다섯 필드(분·시·일·월·요일)로 이뤄지며, 각 필드에 단일 값·범위·목록·간격을 쓸 수 있습니다.

`schedule`은 crontab 형식으로 씁니다. 다섯 필드가 왼쪽부터 분·시·일(월중)·월·요일입니다.

```pseudocode
schedule: "* * * * *"
           │ │ │ │ └── 요일 (0-6 또는 SUN-SAT)
           │ │ │ └──── 월 (1-12 또는 JAN-DEC)
           │ │ └────── 일 (1-31)
           │ └──────── 시 (0-23)
           └────────── 분 (0-59)
```

별표(`*`)는 해당 필드의 모든 값과 일치합니다. 각 필드에 별표만 있으면 매분 실행됩니다.

| 값 | 의미 |
|----|------|
| `5` | 단일 값. 월 필드에 `5`면 5월에만 |
| `MAY` | 월·요일 필드는 세 글자 이름 사용 가능 |
| `1-5` | 범위(양끝 포함). 월 필드에 `1-5`면 1~5월 |
| `1,2,5-8` | 목록·범위 조합. 월 필드면 1·2·5·6·7·8월 |
| `*/3` | 첫 값부터 N칸마다. 월 필드에 `*/3`면 1·4·7·10월 |
| `5/2` | 지정 값부터 N칸마다. 월 필드에 `5/2`면 5·7·9·11월 |
| `3-10/2` | 범위 안에서 N칸마다. 월 필드에 `3-10/2`면 3·5·7·9월 |

몇 가지 예입니다.

| schedule | 설명 |
|----------|------|
| `* * * * *` | 매분 |
| `15 * * * *` | 매시 15분 |
| `0 0 * 1-3 *` | 1~3월 매일 자정 |
| `*/5 18 * * *` | 매일 18:00~18:59 사이 5분마다 |
| `0 0 * * 1-5` | 평일(월~금) 매일 0시 |

> **일(월중)과 요일 필드의 함정.** CronJob은 모든 필드가 현재 시각과 일치할 때 Job을 만들지만, 일과 요일 필드는 예외입니다. **둘 다 `*`가 아닐 때** 두 필드는 AND가 아니라 OR로 묶여, 하나라도 일치하면 실행합니다. 예컨대 `* * 13 * 5`는 "13일이면서 금요일"이 아니라 "매월 13일 또는 매주 금요일"에 실행됩니다. 한쪽이 `*`이면(`* * 13 * *`) OR가 성립하지 않고 그냥 13일에만 돕니다[^cron-macro].

단순한 스케줄에는 다섯 필드 대신 특수 값을 쓸 수 있습니다.

| 특수 값 | 같은 의미 | 같은 crontab 식 |
|---|---|---|
| `@hourly` | 매시 정각 | `0 * * * *` |
| `@daily` (또는 `@midnight`) | 매일 자정 | `0 0 * * *` |
| `@weekly` | 매주 일요일 0시 | `0 0 * * 0` |
| `@monthly` | 매월 1일 0시 | `0 0 1 * *` |
| `@yearly` (또는 `@annually`) | 매년 1월 1일 0시 | `0 0 1 1 *` |

세 번째 열이 있어야 앞 절에서 배운 다섯 필드 문법과 이어집니다. 특수 값은 문법을 대체하는 게 아니라 자주 쓰는 식에 이름을 붙인 것뿐입니다[^cron-macro].

### 5.1 시간대 설정

CronJob 컨트롤러는 기본적으로 Controller Manager의 시간대로 스케줄을 계산합니다. Control Plane이 의도와 다른 지역에서 돌면 예상치 못한 시각에 실행될 수 있습니다. `spec.timeZone`으로 시간대를 지정합니다.

```yaml
apiVersion: batch/v1
kind: CronJob
metadata:
  name: runs-at-3am-cet
spec:
  schedule: "0 3 * * *"
  timeZone: CET          # 이 CronJob은 CET 03:00에 실행
  jobTemplate:
    ...
```



## 6. CronJob 운영 — suspend·자동삭제·deadline·동시성
> CronJob은 일시 중단, 완료된 Job 자동 삭제, 시작 마감 시각, 동시 실행 정책을 설정할 수 있습니다.

### 6.1 suspend와 재개

Job처럼 CronJob도 중단할 수 있습니다. 전용 명령이 없어 `kubectl patch`를 씁니다.

```bash
kubectl patch cj aggregate-responses-every-minute -p '{"spec":{"suspend": true}}'
```

중단된 동안 컨트롤러는 새 Job을 시작하지 않지만, 이미 도는 Job은 끝까지 놔둡니다[^cj-suspend]. 공식 문서는 이때 실행이 "취소"되는 게 아니라 **예약은 그대로이되 컨트롤러가 시작만 하지 않는** 상태라고 설명합니다. `suspend`를 `false`로 되돌리면 재개됩니다.

### 6.2 완료된 Job 자동 삭제

CronJob 컨트롤러는 완료된 Job을 자동으로 지웁니다. 기본으로 성공 Job 세 개와 실패 Job 한 개를 남깁니다. `spec.successfulJobsHistoryLimit`과 `spec.failedJobsHistoryLimit`으로 조정합니다. 남긴 Job의 파드도 함께 보존되므로 로그를 볼 수 있습니다.

```bash
kubectl get job -l app=aggregate-responses-today
```

```pseudocode
NAME                                     STATUS     COMPLETIONS   ...
aggregate-responses-every-minute-...408  Complete   1/1
aggregate-responses-every-minute-...409  Complete   1/1
aggregate-responses-every-minute-...410  Complete   1/1           # 성공 3개만 남음
aggregate-responses-every-minute-...411  Running    0/1
```

### 6.3 시작 마감 — startingDeadlineSeconds

CronJob 컨트롤러는 예약 시각 즈음에 Job을 만들지만, 클러스터가 바쁘거나 컨트롤러가 오프라인이면 지연될 수 있습니다. Job이 예약 시각에서 너무 늦게 시작되면 안 될 때 `startingDeadlineSeconds`를 씁니다.

```yaml
spec:
  schedule: "* * * * *"
  startingDeadlineSeconds: 30    # 예약 시각 30초 안에 시작 못 하면 그 Job은 실패로 간주
```

컨트롤러가 30초 안에 Job을 만들지 못하면 만들지 않고 `MissSchedule` 이벤트를 냅니다[^cj-events].

이 필드를 설정하지 않으면 어떻게 될까요. 컨트롤러가 오래 오프라인이었다가 복귀하면 그동안 놓친 Job을 한꺼번에 모두 만드는 바람직하지 않은 동작이 생길 수 있습니다. 놓친 스케줄이 100개를 넘으면 컨트롤러는 Job을 만들지 않고 `too many missed start times…`로 시작하는 오류를 로그에 남깁니다[^starting-deadline]. 시작 마감을 설정하면 이 사태를 막을 수 있습니다.

> **너무 짧게 두면 아예 안 돕니다.** CronJob 컨트롤러는 10초마다 상태를 확인합니다. 그래서 `startingDeadlineSeconds`를 **10초보다 작게** 두면 점검 주기 사이에 마감이 지나 버려 Job이 스케줄되지 않을 수 있습니다[^starting-deadline]. 위 예제의 30초처럼 점검 주기보다 넉넉한 값을 줍니다.

### 6.4 동시성 정책 — concurrencyPolicy

매분 도는 CronJob에서 Job이 1분 넘게 걸리면, 이전 Job이 아직 도는데 새 Job이 뜰까요? 기본적으로 그렇습니다. `spec.concurrencyPolicy`로 이 동작을 바꿉니다.

![concurrencyPolicy 세 정책 비교: Allow는 겹쳐 실행, Forbid는 새 Job을 건너뜀, Replace는 이전 Job을 지우고 새 Job으로 교체](_assets/18-03-concurrency-policy.svg)

| 값 | 동작 |
|----|------|
| `Allow`(기본) | 여러 Job이 동시에 실행될 수 있음 |
| `Forbid` | 동시 실행 금지. 이전 실행이 아직 활성이면 새 Job을 만들지 않고 `JobAlreadyActive` 이벤트를 냄(건너뜀)[^cj-events] |
| `Replace` | 활성 Job을 취소하고 새 Job으로 교체. CronJob이 이전 Job을 지우면 Job 컨트롤러가 파드를 우아하게 종료. 잠시 두 Job이 공존(하나는 종료 중) |

이 정책이 걸리는 범위를 오해하기 쉽습니다. `concurrencyPolicy`는 **같은 CronJob이 만든 Job 사이에만** 적용됩니다. CronJob이 여럿이면 서로의 Job은 언제나 동시에 돌 수 있습니다[^concurrency]. "겹쳐 돌면 안 되는" 작업이 여러 CronJob에 흩어져 있으면 이 필드로는 막지 못한다는 뜻입니다.

`Forbid`도 완전한 차단은 아닙니다. 이전 Job이 끝나는 시점에 `startingDeadlineSeconds`가 다시 계산되어, 건너뛴 줄 알았던 실행이 뒤늦게 시작될 수 있습니다[^concurrency].

### 6.5 CronJob 삭제

CronJob을 지우면 그 CronJob이 만든 모든 Job도 함께 지워지고, 파드도 우아하게 종료됩니다.

```bash
kubectl delete cj aggregate-responses-every-minute
```

Job과 파드는 남기고 CronJob만 지우려면 `--cascade=orphan`을 씁니다. 활성 Job이 있을 때 이 옵션으로 CronJob을 지우면, 그 Job은 보존되어 작업을 마칠 수 있습니다.



## 7. Spring 관점 — @Scheduled를 CronJob으로 옮기기
> 앱 안 `@Scheduled` 대신 CronJob을 쓰면, 스케줄이 인스턴스 수와 무관해지고 중복 실행을 정책으로 막을 수 있습니다.

Spring의 `@Scheduled`(또는 Quartz)로 앱 안에서 주기 작업을 돌리면, 애플리케이션 인스턴스를 여러 개 띄웠을 때 같은 작업이 인스턴스마다 중복 실행되는 문제가 생깁니다. 이를 막으려면 ShedLock 같은 분산 락을 붙여야 합니다. CronJob으로 옮기면 스케줄이 앱 인스턴스 수와 분리되고, `concurrencyPolicy: Forbid`로 중복 실행을 컨트롤러 레벨에서 막을 수 있습니다.

트레이드오프는 실행 단위입니다. `@Scheduled`는 이미 떠 있는 프로세스 안에서 도니 JVM warm-up·커넥션 풀을 재활용하지만, CronJob은 매번 새 파드를 띄워 그 비용을 매번 치릅니다. 초 단위로 자주 도는 가벼운 작업은 앱 안 스케줄러가, 분·시 단위로 도는 무거운 배치는 CronJob이 더 맞습니다. 후자는 실패·재시도·타임아웃을 Job의 `backoffLimit`·`activeDeadlineSeconds`로 위임할 수 있다는 이점도 있습니다.

1. Kubernetes에 큐 리소스가 있습니까? 큐를 아는 층은 어디이고, 그 층은 Job에 무엇으로 완료를 알립니까?
2. work queue의 coarse 방식과 fine 방식은 파드와 `completions` 설정에서 어떻게 다릅니까?
3. fine 방식에 `completions`를 아이템 수로 넣으면 무슨 일이 생깁니까?
4. 큐 컨슈머를 Deployment로 둘지 Job으로 둘지는 무엇으로 가릅니까?
5. Job이 완료된 뒤 큐에 새 아이템을 넣으면 왜 처리되지 않습니까? 계속 감시가 필요하면 무엇을 씁니까?
6. 완료된 파드는 언제 사라집니까? 지울 때 무엇을 겨냥합니까?
7. `Indexed` Job의 파드가 peer 주소를 계산하려면 무엇이 필요합니까? Downward API로는 왜 안 됩니까?
8. Job 파드에 사이드카를 넣는 올바른 방법은 무엇이고, 일반 컨테이너에 넣으면 왜 안 됩니까?
9. CronJob의 crontab에서 일(월중)과 요일 필드를 둘 다 설정하면 어떻게 동작합니까?
10. `concurrencyPolicy`의 `Allow`·`Forbid`·`Replace`는 각각 어떻게 동작합니까?



## 정답 (자답 후 펼치기)
> 위 질문을 스스로 답한 뒤 여기서 확인합니다. 질문 번호와 1:1로 대응합니다.

### 정답 1 — 큐를 아는 층
`kind: Queue` 같은 리소스는 **없습니다**. 큐와 인출 로직을 컨테이너 안에 직접 구현하며, Redis·RabbitMQ·Kafka·MongoDB 중 무엇을 쓰든 Kubernetes는 관여하지 않습니다.

큐를 아는 것은 **Container 층뿐**입니다. Job 컨트롤러는 완료된 파드 수만 세고, kubelet은 컨테이너 종료 코드만 봅니다. 그래서 컨테이너가 "큐가 비었다"를 **exit 0**으로 번역해 주어야 Job이 완료를 압니다. 종료 코드가 두 층 사이의 유일한 통신 수단입니다.

### 정답 2 — coarse vs fine
coarse는 파드마다 큐 아이템 하나를 처리하고 종료하므로, `completions`를 아이템 수(N)로 설정합니다. fine은 파드마다 큐가 빌 때까지 여러 아이템을 처리하므로, `completions`를 설정하지 않습니다(파드 하나의 성공이 곧 큐가 비었음을 뜻하기 때문). 둘 다 `parallelism`으로 동시 파드 수를 조절합니다.

### 정답 3 — fine에 completions를 넣으면
헛도는 파드가 생깁니다. 아이템 6개를 파드 3개가 나눠 처리하고 큐가 비면 성공 파드는 3개입니다. `completions: 6`이면 컨트롤러가 3개를 더 만들고, 그 파드들은 빈 큐를 보고 즉시 종료합니다. **일 없이 뜨고 죽는 파드**만 늘어납니다.

fine에서 파드 하나의 성공은 곧 큐가 비었다는 뜻이라, 셀 필요가 없습니다. `completions`를 비워 두면 "하나만 성공하면 완료"가 적용됩니다.

### 정답 4 — Deployment 워커와 Job의 갈림
**"끝났다"는 시점이 필요한가**로 가릅니다.

상시 유입되는 트래픽이면 Deployment가 맞습니다. 계속 대기하며 처리하면 되고 기동 비용도 한 번뿐입니다. 반면 "쌓인 묶음을 다 처리하고 끝나면 다음 단계로"라면 Job입니다. 완료 시점이 있어야 후속 작업을 걸 수 있습니다.

Job의 이점은 자원 회수와 완료 판정입니다. 일이 없을 때 파드가 놀지 않고, 실패·타임아웃을 `backoffLimit`·`activeDeadlineSeconds`로 위임합니다. 대신 매번 파드를 띄우는 비용을 치릅니다.

### 정답 5 — Job은 지속 감시가 아님
Kubernetes는 큐를 모릅니다. 큐의 존재를 아는 것은 파드 안 컨테이너뿐입니다. Job이 끝난 뒤 아이템을 추가해도 Job을 다시 만들지 않는 한 처리되지 않습니다. 큐를 계속 감시해야 하면 Deployment로 워커를 돌리고, 정해진 주기로 돌리려면 CronJob을 씁니다.

### 정답 6 — 완료된 파드의 삭제
컨테이너가 exit 0으로 끝나도 **아무도 치우지 않습니다**. 파드는 `Completed`로 남아 로그를 볼 수 있게 합니다. 치우는 경로는 셋입니다.

- `ttlSecondsAfterFinished` — TTL 컨트롤러가 완료 후 지정 초에 Job과 파드를 지움
- `kubectl delete job` — 소유자가 사라져 가비지 컬렉터가 파드를 회수
- CronJob history limit — CronJob 컨트롤러가 성공 3개·실패 1개 초과분을 지움

지울 때는 파드를 직접 겨냥하지 않고 **Job 오브젝트를 지웁니다**. 파드의 `ownerReferences`가 Job을 가리키므로 소유자가 사라지면 딸린 파드가 함께 회수됩니다.

### 정답 7 — peer 주소 계산
세 가지가 필요합니다. `completionMode: Indexed`, headless Service(`clusterIP: none`), Pod 템플릿의 `subdomain`입니다. 그러면 hostname이 `<Job 이름>-<인덱스>.<Service>.<네임스페이스>.svc.cluster.local` 형태가 됩니다.

계산이 가능한 이유는 hostname에 **임의 문자열이 들어가지 않기** 때문입니다. 파드 이름은 `comm-demo-0-mrvlp`지만 hostname은 `comm-demo-0`까지입니다. 인덱스가 0부터 연속이라 `completions`만 알면 모든 peer를 짚어 낼 수 있고, API 서버에 물을 필요가 없습니다.

Downward API로는 안 됩니다. 그것은 자기 인덱스·자기 노드 IP처럼 **자기 정보**만 주기 때문입니다. 남의 주소는 DNS가 답합니다.

### 정답 8 — Job 파드 사이드카
올바른 방법은 사이드카를 `restartPolicy: Always`인 init 컨테이너(네이티브 사이드카)로 정의하는 것입니다. 일반 `spec.containers`에 두면 사이드카가 절대 멈추지 않아 파드가 완료되지 못하고, Job이 영원히 실행 중으로 남습니다(해결책은 Job 삭제뿐).

### 정답 9 — 일·요일 필드 함정
CronJob은 다른 필드는 모두 일치해야(AND) 하지만, 일(월중)과 요일 필드는 **둘 다 `*`가 아닐 때** 하나라도 일치하면(OR) 실행합니다. `* * 13 * 5`는 "13일이면서 금요일"이 아니라 "매월 13일 또는 매주 금요일"에 실행됩니다. 한쪽이 `*`이면 OR가 성립하지 않고 나머지 한쪽만 적용됩니다[^cron-macro].

### 정답 10 — concurrencyPolicy 3종
`Allow`(기본)는 여러 Job이 동시에 실행되도록 허용합니다. `Forbid`는 동시 실행을 금지해, 이전 실행이 활성이면 새 Job을 만들지 않고 건너뜁니다(`JobAlreadyActive`). `Replace`는 활성 Job을 취소(삭제)하고 새 Job으로 교체하며, 이전 Job의 파드는 우아하게 종료됩니다.
