# Kubernetes in Action 오답 노트

## 2026-07-27 — 묻는 "층"을 잘못 짚음 (12-02 Phase 1)

- **자기 답**: 12-02 세 축을 예측·채점으로 돌린 결과. (1) TLS termination/passthrough에서 **"중단도 동일 지점 아닌가요?"** 로 답해 두 방식이 같은 곳에서 암호를 푼다고 봤습니다(termination 논리 자체 — "백엔드는 몰라도 된다, 내부 통신에선 필요 없다" — 는 자력 정답). 암호를 푸는 주체를 "인그레스 컨트롤러"라 했습니다. "표준? 그런 게 있는가?"로 표준 개념 자체를 몰랐습니다. (2) Secret은 자력 정답이나 참조 방법을 **"config로 가져가는 거 아니야?"** 로 오답. 인증서·host 불일치는 "못 쓰는 거 아니야?"로 방향만. (3) annotation을 못 떠올려 **"ConfigMap에서 다룬다?"** 로 오답(두 번째 ConfigMap 오답). spec 필드로 안 들어간 이유를 **"Ingress에서 하기에는 무거운 작업이기 때문"** 으로 답했습니다. (4) 쿠키 어피니티는 **자력 통과**(L4/L7 축 + NAT 뒤 동일 IP 구분 불가). 단 "세션 어피니티에 LOCAL/CLUSTER 정책 상관없이 L7을 쓸 수 있단 건가?"로 층을 섞어 물었습니다. (5) IngressClass에서 (a) **`rules`로 담당 API를 적기**, (b) 컨트롤러 이름 직접, (c) **"2개 중 아무거나 로드밸런싱"** 으로 셋 다 오답. 이어 "Ingress 1개를 컨트롤러 2개가 나눠 처리하는 것"으로 전제를 오해했습니다.
- **정답**: (1) **암호가 풀리는 지점이 다른 것이 두 방식의 정의**입니다 — termination은 프록시가(인증서를 프록시가 쥠), passthrough는 파드가(인증서를 파드가 쥠) 풉니다. 푸는 주체는 컨트롤러가 아니라 **프록시**입니다(12-01의 컨트롤러=설정 생성 / 프록시=트래픽 처리 구분). **"표준"은 쿠버네티스 API에 정식 필드로 있는가**를 뜻하고, termination은 `spec.tls`가 정식 필드라 어느 컨트롤러든 통하지만 passthrough는 필드가 없어 annotation + 컨트롤러 플래그에 의존합니다. **passthrough가 "L7 라우팅 포기"인 이유**: TLS가 암호화하는 대상이 바로 프록시가 읽어야 할 `GET /quote` · `Host:` 부분이라, 프록시 눈에는 암호문만 보여 `pathType` 매칭이 작동할 수 없습니다. 분기에 쓸 수 있는 건 핸드셰이크의 **SNI**(암호화 전이라 평문)뿐이므로 호스트 단위까지가 한계입니다. (2) `spec.tls[].secretName`으로 참조합니다 — ConfigMap이 아니고, 12-01에서 확인한 spec 필드 넷 중 하나입니다. host 불일치는 **오브젝트 생성이 성공하고 런타임에 브라우저가 거부**합니다(`ERR_CERT_COMMON_NAME_INVALID`) — 검증 주체가 서버가 아니라 **클라이언트**라 배포 파이프라인은 초록불인데 사용자만 막힙니다. (3) **annotation**입니다(07-03). spec 필드로 못 들어간 이유는 무게가 아니라 **의미를 API가 보장할 수 없어서** — `rateLimit`의 단위·기준·초과 응답이 구현마다 다르고 AWS ALB엔 개념 자체가 없습니다. annotation/ConfigMap은 층이 갈립니다: **Ingress별 프록시 설정 = annotation(컨트롤러가 API에서 읽음) / 컨트롤러 전역 설정 = ConfigMap**. (4) 어피니티와 `externalTrafficPolicy`는 **다른 구간의 일**입니다 — 프록시는 cluster IP를 건너뛰므로 프록시→백엔드 구간에 Service가 개입하지 않습니다. 단 LB→프록시 구간에 `Cluster` 정책이면 SNAT이 걸려 **프록시가 보는 클라이언트 IP가 노드 IP로 오염**되므로 컨트롤러 LB Service에 `Local`을 거는 것이 관행입니다(유일한 교차점). (5) **`ingressClassName`** 이고, 컨트롤러가 아니라 **IngressClass를 가리킵니다** — 한 단계를 두는 이유는 같은 컨트롤러를 다른 파라미터로 여러 번 쓰기 위해서(ALB `internet-facing` vs `internal`)입니다. 미지정 시 기본 클래스가 받고, 기본이 없으면 **아무도 처리하지 않습니다**(로드밸런싱이 아님). **Ingress 1개를 처리하는 컨트롤러는 항상 하나**이고, 컨트롤러 여럿은 트래픽이 아니라 **Ingress 집합(일감)을 나눠 갖는 것**입니다.
- **원인 추정**: 12-01의 "결론 맞고 근거 틀림"과 **다른 결** — 여기서는 **묻는 층·오브젝트를 잘못 짚습니다.** annotation 자리에 ConfigMap 2회, 소유권(누가 처리하나) 문제에 `rules`(라우팅), 어피니티 층에 `externalTrafficPolicy`, 컨트롤러 개수를 Ingress 개수와 혼동. 인접하고 익숙한 개념으로 빈칸을 메우는 패턴입니다. 반대로 **L4/L7 축은 세 번 다 정확히 인출**했습니다(termination 논리·쿠키 가능 이유·NAT 구분 불가) — 11-01부터 반복해 온 축이라 굳었습니다. 즉 개별 사실은 쌓였고 **"이 결정은 어느 층의 일인가"라는 배치 감각**이 다음 과제입니다.
- **참고 챕터**: 12-02 §1(TLS)·§2(annotation·어피니티)·§3(IngressClass). 보강 TODO는 `_todo-12-02-보강.md`(10항목, 시각화 6장). "**termination=프록시가 풂(표준 `spec.tls`)/passthrough=파드가 풂(SNI만 보임→경로 라우팅 불가) / 구현마다 의미가 달라 보장 못 하는 설정은 annotation / `ingressClassName`은 컨트롤러가 아니라 IngressClass를 가리킨다**" 한 줄.
- **재방문 트리거**: 다음 복습에서 (1) 두 TLS 방식의 **암호 해제 지점과 인증서 소유자**를 각각 적고 "프록시가 볼 수 있는 것"까지 대기, (2) "passthrough면 `pathType: Prefix` 규칙이 동작하나"에 예·아니오와 이유로 답하기, (3) 프록시별 세부 설정을 **어디에** 적는지 한 단어로 답하고 ConfigMap과의 차이 대기, (4) 인증서 host가 안 맞으면 **어느 시점에 무엇이** 실패하는지(생성/접속, 검증 주체) 답하기, (5) `ingressClassName`이 가리키는 대상과 **왜 컨트롤러를 직접 안 적는지**, (6) 클래스 미지정 시 두 분기와 기본 클래스가 둘일 때의 함정.

## 2026-07-27 — 결론은 맞고 근거가 다른 모델에서 나옴 (12-01 Phase 1)

- **자기 답**: 12-01 네 축을 예측·채점으로 돌린 결과. (1) "IP 하나로 왜 갈라낼 수 없나"에 **"애초에 매핑이 1대1이지 않은가?"** 로 답했습니다(path 라우팅·L4=ip:port는 자력). (2) 선언/집행 분리 구조는 스스로 봤으나 그 일을 **kube-proxy가 한다**고 답했습니다 — "노드포트·로드밸런서 때도 kube-proxy가 변환해줬으니 이번에도 동일하게 해야 하는 거 아닌가". (3) 프록시가 파드로 직접 보내는 이유는 "모르겠음"(미학습). (4) Prefix 매칭에서 `/foo/bar`·`/foo` 매칭, `/foobar` 불일치를 **맞혔으나** 근거를 "`/foo`로 시작하는 경우를 보는 거니깐"(문자열 접두사)으로 답했습니다. (5) Exact 우선을 **맞혔으나** 근거를 "규칙 중 먼저 만족하는 위에 선언된 것"(선언 순서)으로 답했습니다.
- **정답**: (1) 1대다는 L4에서도 됩니다(11-01의 cluster IP → 파드 다수). 문제는 **갈라지긴 하는데 기준을 정할 재료가 없다**는 것 — 커널이 파드를 고른 근거는 확률뿐이었습니다. 기준은 한 계층 위 페이로드(`GET /quote`, `Host:`)에 있고, **L4는 봉투만 보고 L7은 편지를 읽습니다.** DNAT은 헤더의 고정 위치 숫자를 덮어쓰는 일이고 L7 파싱은 TCP 스트림 재조립+구문 분석이라, 커널이 안 하고 사용자 공간 프로그램(Nginx·Envoy)이 합니다. (2) **kube-proxy는 Ingress를 감시조차 하지 않습니다**(Service·EndpointSlice만). 심을 수 있는 규칙이 "목적지 IP:port가 X면 Y로" 형태뿐이라 "경로가 /quote면"을 쓸 자리가 없습니다. 그 역할은 **Ingress 컨트롤러**(감시→`nginx.conf` 생성)와 **L7 프록시**(집행)가 맡습니다 — 구조는 11장과 같고 배우만 바뀝니다. (3) 컨트롤러가 **EndpointSlice를 감시**하므로 프록시는 파드 명단을 이미 압니다. 얻는 것은 DNAT 홉 제거 + **부하 분산의 주인이 커널의 확률에서 프록시의 L7 판단으로 이동**(쿠키 어피니티·재시도·정밀 카나리가 그래서 가능). cluster IP를 거치면 프록시가 애써 파싱한 판단이 커널의 확률에 버려집니다. (4) 기준은 문자열이 아니라 **`/`로 쪼갠 요소 단위** — `/foobar`는 `["foobar"]` 한 덩어리라 `foo`와 다른 요소입니다. 문자열 접두사로 보면 `/foobar`가 걸려야 하는데 실제로는 안 걸립니다. (5) 기준은 순서가 아니라 **구체성** — Prefix를 위로 올려도 Exact가 이깁니다. 순서 의존이면 §5의 Ingress 병합이 위험해지고, 구체성 우선이어야 "일반 규칙 + 예외" 패턴이 성립합니다.
- **원인 추정**: 11-03의 "규모를 안 곱함"과 **다른 결**입니다. 여기서는 **결론을 맞히면서 근거가 다른 모델에서 나옵니다.** (4)는 문자열 접두사 모델, (5)는 방화벽·`if-else` 체인 모델이 전이된 것 — 둘 다 일상적으로 익숙한 모델이라 답이 우연히 맞아떨어졌습니다. 답이 맞으니 그냥 넘어가기 쉬운데, 조건이 조금 바뀌면 무너집니다(순서를 뒤집은 반례가 증거). (1)(2)도 같은 결 — 11장에서 익힌 "cluster IP 1대1", "kube-proxy가 변환한다"를 **적용 범위를 확인하지 않고** 그대로 옮겼습니다. 반면 (2)의 선언/집행 분리 직관과 "파드 IP는 자주 바뀌는데 직접 통신하면 단점 아닌가"는 스스로 찾은 좋은 의문이었습니다(11장 원칙과의 충돌 감지 = 개념이 연결되는 신호).
- **2026-07-27 §5·§6 추가 인출**: (6) §5에서 "Ingress를 하나로 모으면 왜 IP가 하나인가"를 **자력 정답**("로드밸런서가 1개만 생겨서") — IP가 붙는 대상이 Ingress 오브젝트가 아니라 *그 때문에 생긴 LB*라는 것을 스스로 끌어냈습니다. 와일드카드는 오답 — `*.example.com`에 `foo.kiada.example.com`이 매칭될 것이라 봤으나, **`*`는 정확히 한 요소만 덮으므로** 4요소는 불일치입니다(`example.com`도 `*`가 덮을 요소가 없어 불일치). **경로는 `/`, 호스트는 `.`으로 쪼갠 요소 단위**라는 같은 원리이고, Prefix는 뒤에 요소가 더 붙어도 되지만 와일드카드는 개수가 고정이라는 대비가 핵심. (7) §6은 (a) 404·(b) 지정 서비스로 감을 자력 정답, (c) 규칙 없는 Ingress를 LB 대신 쓰는 이유는 "HTTP를 쓴다는 장점"까지만 — 정답은 **누가 HTTP를 이해하느냐**입니다(LB도 HTTP를 나르지만 L4라 봉투만 봄). 규칙이 없어도 **L7 중간자가 생기는 것 자체가 이득**이라 TLS 종료·인증·쿠키 어피니티·재작성·rate limit이 딸려 옵니다. 즉 §4·§5의 "결론 맞고 근거 틀림"이 §5 와일드카드에서 **세 번째로 반복**됐습니다(문자열 접두사 → 선언 순서 → 와일드카드 개수).
- **Phase 3 보류(생략 아님)**: 13장 환경 구축 시점으로 합칩니다. 이유 — ① **ingress-nginx 유지보수 종료**(공식 README 실측: 2026-03 이후 릴리스·버그픽스·보안 패치 없음, "새로 배포하지 말고 Gateway API 구현을 쓰라") ② 대체 컨트롤러(Traefik·Envoy 기반)는 Ingress API도 지원하므로 13장 준비가 12장 실습 환경을 겸함 ③ `cluster/kind-config.yaml`에 `extraPortMappings`가 없어 80·443 접근 불가 — 12·13장 공통 전제. ⛔ 단 **13장 실습으로 12장을 덮을 수는 없습니다** — `Ingress`와 `Gateway`+`HTTPRoute`는 다른 API이고 `defaultBackend`는 Gateway API에 대응물이 없습니다. 검증 목표 A~D와 전제는 `_todo-12-01-보강.md` §Phase 3 섹션에 기록.

## 2026-07-20 — externalTrafficPolicy Local: SNAT 정체 + "노드는 균등, 파드는 불균등"

- **자기 답**: 11-02 Phase 4 Q2에서 "Cluster는 ClusterIP로 치환한다"고 답해 *목적지(DNAT)와 출발지(SNAT)를 혼동*했습니다. Q5(Local의 두 번째 대가 = 불균등 분산 + healthCheckNodePort)는 "그게 있나?"로 막혀 설명이 필요했습니다.
- **정답**: 노드가 받은 요청을 다른 노드 파드로 넘길 때 두 NAT이 겹칩니다. **DNAT**(목적지 `노드IP:30080`→`파드IP:8080`)는 두 정책 다 함. **SNAT/masquerade**(출발지 `클라이언트IP`→`받은 노드IP`)는 **Cluster만** 함 — 응답이 반드시 받은 노드로 되돌아오게(비대칭 경로 방지) 출발지를 위조하는 대가로 파드가 보는 Client IP가 노드 IP가 됨. **Local은 SNAT을 안 해** 원본 IP 보존, 대신 "로컬 파드로만 라우팅"이라 파드 없는 노드는 타임아웃. 불균등: LB는 **노드 단위**로 균등 분배하는데 노드마다 파드 수가 달라(A:3, B:1) 파드당 부하가 어긋남(A 파드 11% vs B 파드 33%). 타임아웃 우회는 **healthCheckNodePort**(로컬 파드 있으면 200, 없으면 503) + LB 헬스체크로 파드 없는 노드를 분배에서 제외.
- **원인 추정**: (1) NAT을 "IP를 바꾸는 것" 하나로 뭉뚱그려 목적지/출발지 방향 구분을 안 세움. (2) Local의 대가를 "타임아웃" 하나만 알고 "불균등 분산"은 노드/파드 분배 단위가 다르다는 데서 나온다는 걸 못 떠올림. 오늘 3세션 공통 약점 "자동으로 채워지는 것의 내부 기전"과 같은 결(kube-proxy가 심는 SNAT 규칙).
- **참고 챕터**: 11-02 §3(externalTrafficPolicy). 뿌리는 `02_os/networking/01-02.K8s 패킷 여정` §1.2(POSTROUTING=SNAT)·§2(kube-proxy). "Cluster=SNAT함(Client IP=노드 IP), Local=SNAT안함(원본 보존)+로컬 파드만+healthCheckNodePort로 죽은 노드 제외" 한 줄.
- **재방문 트리거**: 다음 복습에서 (1) 한 요청이 다른 노드 파드로 갈 때 DNAT·SNAT이 각각 무엇을 바꾸는지 화살표로 그리기, (2) Local에서 노드별 파드 수를 임의로 주고 파드당 트래픽 비율을 계산.

## 2026-07-20 — kubectl expose의 selector 함정: 파드 라벨을 전부 가져간다

- **참고 챕터**: 11-01 §3(kubectl expose)·§4(set selector). "expose는 파드 라벨을 전부 selector로 가져가니, canary를 받으려면 app=quiz로 좁혀라" 한 줄. (canary = 신버전을 일부 트래픽에만 흘려 검증하는 배포. k8s 기본은 파드 개수 비율로 대략 조절, 정밀 %는 L7 필요.)
- **재방문 트리거**: 다음 복습에서 `kubectl expose pod`가 만든 selector를 예측하고 `kubectl get svc -o wide`로 실제 SELECTOR와 대조. canary 파드가 왜 트래픽을 못 받는지 설명.

## 2026-07-20 — 스냅샷 복원 시 dataSourceRef.apiGroup: 왜 스냅샷만 필수인가

- **정답**: 스냅샷을 소스로 쓸 때만 `apiGroup: snapshot.storage.k8s.io`를 명시해야 합니다. PVC/PV는 **core 그룹**(`apiVersion: v1`, 그룹명이 빈 문자열 `""`)이라 `apiGroup`을 생략하면 core로 해석돼 찾아지지만, VolumeSnapshot은 **named 그룹**(`snapshot.storage.k8s.io/v1`)이라 생략하면 "core 그룹의 VolumeSnapshot"을 찾다 실패합니다. core 그룹은 Pod·Service·PVC·ConfigMap 등 초기 근본 오브젝트의 예약 공간(`/api/v1/...`)이고, 그 외는 전부 `apps/v1`·`snapshot.storage.k8s.io/v1`처럼 그룹명이 붙는 named 그룹(`/apis/<group>/...`)입니다.
- **원인 추정**: 오브젝트의 `apiVersion:` 접두어가 곧 API 그룹 소속이고, "생략 = core 그룹" 규칙이라 core에 없는 오브젝트는 그룹 명시가 필수라는 연결을 안 짚었습니다.
- **참고 챕터**: 10-03 §3(스냅샷에서 PV 복원). "apiGroup 생략 = core 그룹을 뒤져라, 스냅샷은 core에 없으니 그룹명 명시 필수" 한 줄.
- **재방문 트리거**: 다음 복습에서 (1) PVC 소스 복제 YAML과 스냅샷 소스 복원 YAML의 dataSourceRef를 나란히 쓰고 차이를 설명, (2) `kubectl api-resources` 출력에서 core(`v1`)와 named 그룹 오브젝트를 각각 두 개씩 골라내기.

- **참고 챕터**: 08-03 §3(env 주입 경고)·Spring 관점(configtree). "편의는 env, 안전은 볼륨" 한 줄.

## 2026-07-14 — label selector: equality-based와 set-based의 구분

- **자기 답**: Phase 4 Q2(셀렉터 두 종류)와 Q3(nodeSelector vs nodeAffinity)에서 연달아 "모르겠다"로 막혔습니다. `in`·`OR` 조건이 된다는 것만 알았고, 이것이 두 종류 중 어디에 속하는지, AND(콤마)가 별도 종류인지 아닌지를 구분하지 못했습니다.
- **정답**: 셀렉터는 두 종류뿐입니다. **equality-based**는 등호로 끝나는 것(`=`, `!=`)이고, **set-based**는 등호로 안 되는 것 넷(`in`·`notin`·키 존재(`rel`)·키 부재(`!rel`))입니다. 콤마(`app=payment,rel=stable`)는 세 번째 종류가 아니라 두 종류를 잇는 AND 연결일 뿐입니다. `nodeSelector`는 equality-based만, `nodeAffinity`는 set-based까지 쓰는 확장이라, 둘의 차이도 결국 이 한 구분에서 나옵니다.
- **원인 추정**: `in`을 개별 기능으로만 외웠고 "등호로 되나 안 되나"라는 상위 분류 축을 잡지 못했습니다. Q2·Q3이 같은 뿌리에서 함께 막힌 것이 그 증거입니다.
- **참고 챕터**: 07-02 §4(셀렉터 두 종류)·§5(nodeSelector/nodeAffinity). 다지기 세션에서 "등호로 되면 equality, 안 되면 set-based, 콤마는 AND" 한 줄로 정리함.
- **재방문 트리거**: 2026-07-15 복습에서 다섯 요구(값 일치·여러 값 중 하나·키 존재·키 부재·값 불일치)를 셀렉터 문법으로 빈칸 채우기. set-based 4형제를 문서 안 보고 나열.
