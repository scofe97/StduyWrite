# 노드 에이전트 특수 기능 — privileged·hostPath·hostNetwork·PriorityClass
---
> 노드 에이전트·데몬은 일반 워크로드와 달리 노드에 더 넓은 접근이 필요합니다. securityContext로 커널 접근(privileged 또는 capabilities), hostPath로 노드 파일시스템, hostNetwork로 노드 네트워크를 열고, PriorityClass로 시스템 파드를 중요하게 표시합니다.



> 이 문서를 읽고 나면 privileged와 capabilities의 차이를 설명하고, hostPath·hostNetwork가 daemon 파드에서 왜 허용되면서 일반 워크로드에는 위험한지 근거를 대며, PriorityClass와 preemption으로 노드 중요 파드를 어떻게 보호하는지 말할 수 있습니다.



## 진입 — 노드로부터 격리를 풀어야 할 때

> 일반 워크로드는 노드에서 격리됩니다 — 컨테이너는 자기 Linux 네임스페이스에 살아 노드의 장치·파일·커널 시스템 콜에 접근하지 못합니다. 노드 에이전트·데몬이 이 제약을 벗어나려면 Pod 매니페스트에 명시해야 합니다.

kube-system 네임스페이스의 DaemonSet(kube-proxy·kindnet)이 이 특수 기능의 좋은 예입니다. 이 편은 kube-proxy를 중심으로 각 기능을 봅니다.

아래는 이 편 전체를 2×2로 압축한 지도입니다. 앞 편과 달리 단계가 순서대로 이어지지 않습니다. 네 영역은 각각 독립하고, 나누는 기준은 **무엇을 열어 줄 것인가**입니다.

- §1 커널 — privileged로 전부 열거나 capabilities로 골라 엽니다
- §2 파일시스템 — hostPath로 노드의 경로를 마운트합니다
- §3 네트워크 — hostNetwork로 노드의 네트워크를 그대로 씁니다
- §4 우선순위 — 앞의 셋과 달리 격리를 여는 게 아니라 스케줄 자리를 지킵니다

네 영역 사이에는 순서가 없습니다. 필요한 영역만 골라 읽으면 됩니다. `privileged`는 커널 권한 검사를 통째로 우회하고, `hostNetwork`는 파드가 자기 IP 없이 노드 IP를 쓰게 만듭니다.

![17-02 전체 지도 — 무엇을 열어 줄 것인가](_assets/17-02.chapter-overview.svg)



## 1. 커널 접근 — privileged와 capabilities

> 커널 시스템 콜 일부는 노드나 다른 컨테이너에 악영향을 줄 수 있어 기본적으로 막힙니다. 컨테이너에 커널 전체 접근을 주려면 privileged, 필요한 시스템 콜 그룹만 주려면 capabilities를 씁니다.

### privileged 컨테이너

컨테이너 프로세스에 OS 커널 전체 접근을 주려면 privileged로 표시합니다.

```yaml
spec:
  template:
    spec:
      containers:
      - name: kube-proxy
        securityContext:
          privileged: true   # 커널 전체 접근
```

kube-proxy 컨테이너의 `securityContext.privileged`가 true입니다. 프로세스에 호스트 커널 root 접근을 줘, 노드의 네트워크 패킷 필터링 규칙을 수정할 수 있게 합니다 — 쿠버네티스 Service가 이렇게 구현됩니다.

### capabilities — 최소 권한

privileged 컨테이너는 모든 커널 권한 검사를 우회해 커널 전체 접근을 갖습니다. 그런데 노드 에이전트는 보통 시스템 콜의 일부만 필요합니다. 그래서 보안상 privileged는 이상적이지 않습니다. 필요한 **최소 시스템 콜만** 주는 편이 낫고, 그 지정을 capabilities로 합니다[^capabilities].

```yaml
spec:
  template:
    spec:
      containers:
      - name: kindnet-cni
        securityContext:
          capabilities:
            add:
            - NET_RAW      # 특수 소켓·임의 주소 바인딩
            - NET_ADMIN    # 인터페이스 설정·방화벽·라우팅 테이블
          privileged: false
```

kindnet은 privileged 대신 NET_RAW·NET_ADMIN만 추가합니다. 두 capability가 여는 것은 이렇습니다.

- **NET_RAW**: 특수 소켓 타입 사용과 임의 주소 바인딩
- **NET_ADMIN**: 인터페이스 설정, 방화벽 관리, 라우팅 테이블 변경

노드의 모든 파드 네트워크를 설정하는 컨테이너에 필요한 것들입니다. 커널 모듈을 적재하거나 다른 프로세스를 죽일 이유는 없으니, 그 권한까지 딸려 오는 privileged를 피한 것입니다.

### drop — 기본 세트를 먼저 걷어낸다

`add`만 보면 capabilities가 "아무것도 없는 상태에 더하는 것"처럼 읽힙니다. 실제로는 다릅니다. 컨테이너 런타임은 아무 설정이 없어도 **기본 capability 세트**를 붙여 줍니다[^cap-default]. `CHOWN`, `SETUID`, `NET_BIND_SERVICE` 같은 것들입니다.

그래서 최소 권한을 제대로 지키려면 기본 세트부터 걷어냅니다. `drop`이 그 일을 합니다.

```yaml
securityContext:
  capabilities:
    drop:
    - ALL              # 기본 세트까지 전부 제거
    add:
    - NET_BIND_SERVICE # 실제로 필요한 것만 되돌림
```

`drop: [ALL]`을 먼저 두고 `add`로 되돌리는 순서입니다. 화이트리스트 방식이죠. Pod Security Standards의 `restricted` 프로파일이 요구하는 형태이기도 합니다[^pss].

privileged는 이 세트를 전부 주는 데서 그치지 않습니다. 공식 문서는 privileged 파드가 "대부분의 보안 메커니즘을 해제한다"고 적고, 그래서 `baseline` 프로파일에서 금지합니다[^pss-privileged]. capability를 전부 add 한 것보다 넓은 상태입니다. "커널 권한 검사를 통째로 우회한다"는 표현이 정확한 이유입니다.



## 2. 노드 파일시스템 접근 — hostPath

> 노드 에이전트가 호스트 파일시스템에 접근하려면 hostPath 볼륨을 씁니다. kube-proxy는 노드의 xtables.lock과 커널 모듈 디렉토리에 접근합니다.

노드 에이전트는 호스트 노드 파일시스템 접근이 필요할 수 있습니다 — 예를 들어 모든 노드에 소프트웨어 패키지를 설치하는 에이전트입니다. hostPath 볼륨으로 접근하며(8장에서 학습), daemon 파드 맥락에서 쓰임을 봅니다.

```yaml
spec:
  template:
    spec:
      volumes:
      - hostPath:
          path: /run/xtables.lock   # iptables/nftables lock 파일
          type: FileOrCreate
        name: xtables-lock
      - hostPath:
          path: /lib/modules        # 노드에 설치된 커널 모듈
          type: ""
        name: lib-modules
```

첫 볼륨은 kube-proxy 프로세스가 노드의 xtables.lock 파일에 접근하게 합니다 — IP 패킷 필터링을 조작하는 iptables/nftables 도구가 쓰는 파일입니다. 둘째 볼륨은 노드에 설치된 커널 모듈에 접근하게 합니다.

### 왜 일반 워크로드에는 금지되는가

hostPath는 Pod Security Standards의 `baseline` 프로파일부터 금지 목록에 올라 있습니다[^pss]. 노드 경로를 파드 안으로 그대로 끌어오기 때문입니다.

노드 위에는 그 노드에 스케줄된 다른 파드들의 것도 놓여 있습니다. 아무 파드나 띄울 수 있는 사람이 hostPath를 자유롭게 쓴다면 손에 들어오는 것이 이렇습니다. 아래 경로는 kubeadm 기준의 일반적인 배치이며, 배포 방식에 따라 다를 수 있습니다[^hostpath-paths].

- `/var/lib/kubelet/pods/`: 같은 노드 다른 파드들의 Secret이 평문 파일로 놓인 곳
- `/etc/kubernetes/`: kubelet 인증서와 kubeconfig
- 컨테이너 런타임 소켓: 런타임을 직접 조종해 privileged 컨테이너를 새로 띄울 수 있음
- 쓰기 가능한 systemd·cron 경로: 노드에서 코드를 실행

여기서 깨지는 격리는 **mount 네임스페이스**입니다. 그런데 위험을 키운 건 따로 있습니다. 쿠버네티스는 오랫동안 user 네임스페이스를 쓰지 않았고, 그래서 컨테이너 안의 root가 노드의 root와 같은 UID였습니다. 노드 파일을 노드 root 권한으로 읽고 쓸 수 있었다는 뜻입니다.

이 지점을 막는 것이 user 네임스페이스입니다. `hostUsers: false`를 주면 파드가 전용 user 네임스페이스를 받습니다[^userns].

```yaml
spec:
  hostUsers: false   # 컨테이너 root를 노드의 비특권 UID로 매핑
```

컨테이너 안 프로세스는 여전히 자기를 root로 봅니다. 하지만 노드 입장에서는 매핑된 비특권 사용자입니다. 탈출이 일어나도 손에 쥐는 권한이 줄어듭니다.

주의할 점은 이 기능이 **옵트인**이라는 것입니다[^userns]. v1.36에서 stable이 되고 기본 활성화됐습니다. 그것은 필드를 쓸 수 있다는 뜻입니다. 파드마다 `hostUsers: false`를 명시해야 적용됩니다. 명시하지 않은 파드는 여전히 노드와 UID 공간을 공유합니다.

### DaemonSet에서는 왜 괜찮은가

같은 기능인데 daemon 파드에서는 권장됩니다. 권한의 크기가 달라서가 아니라, **의도된 접근이냐**가 다르기 때문입니다.

노드 에이전트가 하려는 일 자체가 그 노드를 관리하는 것입니다. 노드 파일시스템 접근은 우발적 권한이 아니라 요구사항입니다.

노드 지역성도 문제가 되지 않습니다. DaemonSet 파드는 노드 사이를 옮겨 다니지 않기 때문입니다. DaemonSet 컨트롤러는 레플리카 수를 세지 않고 노드 목록을 순회합니다. 자기 파드가 없는 노드를 찾으면 그 노드용 파드를 만드는데, 이때 **파드 스펙에 노드 이름을 박아 넣습니다**[^ds-sched].

```yaml
# DaemonSet 컨트롤러가 주입하는 nodeAffinity
affinity:
  nodeAffinity:
    requiredDuringSchedulingIgnoredDuringExecution:
      nodeSelectorTerms:
      - matchFields:
        - key: metadata.name
          operator: In
          values: [node-1]
```

노드 이름이 스펙에 고정되니 스케줄러는 다른 노드를 고를 수 없습니다. 파드가 죽으면 같은 노드에 다시 뜹니다. "옮겨 갔더니 데이터가 없다"는 상황이 구조적으로 생기지 않습니다.

다만 노드마다 그 경로의 내용이 다르다는 사실은 남습니다. 에이전트가 hostPath에 상태를 쌓으면 그것은 노드별 로컬 상태입니다. 노드가 교체되면 사라집니다. daemon 파드의 hostPath는 노드를 읽거나 조작하는 용도이지, 데이터를 보관하는 용도가 아닙니다.



## 3. 노드 네트워크·네임스페이스 — hostNetwork

> 각 파드는 보통 자기 네트워크 인터페이스를 갖지만, daemon 파드는 hostNetwork로 노드의 인터페이스를 직접 쓸 수 있습니다. 그러면 파드가 노드 IP를 쓰고 자기 IP를 안 받습니다. hostIPC·hostPID로 IPC·PID 네임스페이스도 공유할 수 있습니다.

```yaml
spec:
  template:
    spec:
      dnsPolicy: ClusterFirst
      hostNetwork: true   # 자기 네트워크 대신 노드 네트워크 사용
```

`hostNetwork: true`면 파드가 자기 것 대신 호스트 노드의 네트워크 환경(장치·스택·포트)을 씁니다 — 컨테이너가 아니라 노드에서 직접 도는 프로세스처럼요. 파드는 자기 IP도 안 받고 노드 주소를 씁니다.

```bash
kubectl -n kube-system get po -o wide
# kube-proxy-gj9pd   ...   172.18.0.4   ← 파드 IP = 노드 IP
# kube-proxy-rhjqr   ...   172.18.0.2
# kube-proxy-vq5g8   ...   172.18.0.3
```

각 kube-proxy 파드 IP가 자기 노드 IP와 일치합니다. 프로세스가 노드 IP의 네트워크 포트로 접근 가능해야 할 때 유용합니다.

파드 IP와 노드 IP를 나란히 뽑으면 그 일치를 한눈에 확인할 수 있습니다. 아래 명령은 두 값을 같은 표에 세웁니다.

```bash
kubectl -n kube-system get po -o custom-columns=NAME:.metadata.name,POD-IP:.status.podIP,NODE-IP:.status.hostIP
```

![kube-system 파드의 파드 IP와 노드 IP를 나란히 조회하는 과정](_assets/17-02-hostnetwork-pod-ip.gif)

읽을 곳은 `POD-IP` 와 `NODE-IP` 두 열입니다. 

1. kube-proxy·kindnet·etcd 처럼 `hostNetwork: true` 인 파드는 두 값이 같습니다. 
2. coredns 는 `10.244.x` 대역의 자기 IP를 따로 받아 노드 IP와 다릅니다 — 같은 네임스페이스에 두 방식이 섞여 있어 대조가 됩니다.

### Service 뒤에 두면 경로가 달라진다

hostNetwork를 켜면 Service의 DNAT 목적지가 바뀝니다. 먼저 제어 경로와 패킷 경로를 구분해야 합니다. kube-proxy는 패킷이 올 때마다 EndpointSlice를 조회하지 않습니다. API server에 Service·EndpointSlice `LIST/WATCH`를 요청하고, 초기 목록과 변경 이벤트를 받아 노드의 iptables·IPVS 규칙을 미리 동기화합니다[^service-proxy].

![kube-proxy가 EndpointSlice 목록과 변경 이벤트를 받아 커널 규칙을 동기화하는 왕복](_assets/17-02-service-endpoint-sync.svg)

위 왕복에서 일반 파드의 엔드포인트는 `10.244.1.7:8080`, hostNetwork 파드의 엔드포인트는 `172.18.0.4:8080`입니다. 이 차이가 `10.96.0.10:80` Service VIP 규칙의 DNAT 목적지에 반영됩니다. 동기화가 끝난 뒤 실제 패킷은 kube-proxy 프로세스나 EndpointSlice를 통과하지 않고 노드 커널 규칙을 탑니다.

일반 파드에서는 목적지가 `10.96.0.10:80`인 요청 패킷이 Service 규칙의 VIP·port와 매치됩니다. 규칙은 엔드포인트 하나를 선택하고 패킷의 목적지 IP·port를 `10.244.1.7:8080`으로 재작성합니다.

![일반 파드 — 노드 커널 규칙에서 DNAT를 거쳐 파드 전용 netns 안 컨테이너가 받는 경로](_assets/17-02-hostnetwork-normal.svg)

`hostNetwork: true`에서는 EndpointSlice의 같은 자리에 노드 IP가 기록됩니다. 같은 `10.96.0.10:80` 요청이 Service 규칙과 매치된 뒤, 목적지 IP·port가 `172.18.0.4:8080`으로 재작성됩니다. 패킷은 노드 네트워크 네임스페이스의 프로세스가 받으므로 같은 포트는 노드당 한 프로세스만 열 수 있습니다.

![hostNetwork 파드 — veth 없이 노드 netns를 그대로 써서 노드 포트를 점유하고 같은 포트를 쓰려는 다른 파드와 충돌하는 경로](_assets/17-02-hostnetwork-node.svg)

나가는 트래픽은 그대로입니다. 노드 네트워크에서 출발하니 노드에 걸린 패킷 필터링 규칙을 그대로 탑니다. ClusterIP로 다른 서비스를 부르는 것은 정상 동작합니다.

바뀌는 것은 들어오는 쪽입니다. Service 셀렉터가 이 파드를 잡으면 EndpointSlice에 기록되는 주소가 파드 IP가 아니라 **노드 IP**입니다. Service를 거친 트래픽은 노드 IP의 그 포트로 갑니다. 거기서 받는 것은 파드가 아니라 노드에서 그 포트를 여는 프로세스입니다.

NetworkPolicy는 한 단계 더 불확실합니다. 공식 문서가 hostNetwork 파드에 대한 NetworkPolicy 동작을 **undefined**로 두기 때문입니다[^np-hostnetwork]. 허용되는 구현은 둘입니다.

1. 네트워크 플러그인이 hostNetwork 파드의 트래픽을 구분할 수 있으면, 일반 파드와 똑같이 정책을 적용합니다.
2. 구분하지 못하면 `podSelector`·`namespaceSelector` 매칭에서 그 파드를 무시하고, 노드 IP의 트래픽으로 취급합니다.

공식 문서는 둘째가 더 흔한 구현이라고 적습니다. 그래서 hostNetwork 파드에 정책이 의도대로 걸릴지는 쓰는 CNI에 달렸습니다.

그래서 일반 애플리케이션에 hostNetwork를 켜면 세 가지가 걸립니다.

- **포트 충돌**: 노드에서 그 포트를 쓰는 프로세스와 부딪힙니다. 같은 노드에 두 번째 레플리카가 뜨지 못하고 `Pending`으로 남습니다. 결국 레플리카 수가 노드 수를 넘지 못합니다.
- **추상화 약화**: Service가 파드 단위로 동작하지 않고, NetworkPolicy 적용 여부는 CNI에 달립니다[^np-hostnetwork].
- **노드 네트워크 노출**: 파드가 노드의 loopback을 통해 노드 로컬 서비스에 닿습니다. 원래 보이지 않던 것들입니다.

앱에 노드 포트 하나만 필요하다면 hostNetwork 대신 `hostPort`를 씁니다. 파드는 자기 IP를 유지하고 지정한 포트만 노드로 포워딩됩니다.

> **주의.** 다른 방법은 파드가 자기 네트워크를 쓰되 컨테이너 포트 목록의 `hostPort` 필드로 하나 이상의 호스트 포트를 컨테이너로 포워딩하는 것입니다([17-03](./17-03.%EB%A1%9C%EC%BB%AC%20daemon%20%ED%8C%8C%EB%93%9C%20%ED%86%B5%EC%8B%A0%20%E2%80%94%20hostPort%C2%B7hostNetwork%C2%B7internalTrafficPolicy.md)).

`hostNetwork: true` 파드도 다른 네임스페이스 타입은 계속 자기 것을 써서 다른 면에서는 노드로부터 격리됩니다 — 자기 IPC·PID 네임스페이스를 써 다른 프로세스를 보거나 IPC로 통신하지 못합니다. 노드의 IPC·PID 네임스페이스를 쓰려면 Pod spec의 `hostIPC`·`hostPID`를 설정합니다.



## 4. daemon 파드를 중요하게 표시 — PriorityClass

> 노드는 소수의 시스템 파드와 다수의 일반 파드를 돌립니다. 시스템 파드가 더 중요하므로, PriorityClass로 우선순위를 매겨 노드가 꽉 찼을 때 일반 파드를 밀어내고 시스템 파드를 스케줄하게 합니다.

기본적으로 DaemonSet 파드는 Deployment·StatefulSet 파드보다 더 중요하지 않습니다. daemon 파드를 더(또는 덜) 중요하게 표시하려면 **PriorityClass** 오브젝트를 씁니다.

```bash
kubectl get priorityclasses
# system-cluster-critical   2000000000   false   9h
# system-node-critical      2000001000   false   9h
```

- 쿠버네티스는 이 두 PriorityClass를 기본으로 내장합니다[^priority-range]. system-cluster-critical 파드는 클러스터 운영에, system-node-critical 파드는 개별 노드 운영에 중요합니다. 후자는 다른 노드로 옮길 수 없습니다.

직접 만들 수도 있지만 제약이 있습니다. 값은 **10억 이하**여야 하고, 이름은 유효한 DNS subdomain이어야 하며 `system-` 접두사를 붙일 수 없습니다[^priority-range]. 10억을 넘는 값은 위 두 내장 클래스처럼 시스템 파드용으로 예약돼 있습니다.

```pseudocode
system-cluster-critical: 2000000000  — 클러스터에 도는 시스템 파드(필요 시 다른 노드로 이동 가능)
system-node-critical:    2000001000  — 현재 노드에서 이동 불가한 시스템 파드
```

값이 높을수록 우선순위가 높습니다. 위 출력의 세 번째 열(`false`)은 `globalDefault`로, `priorityClassName`을 안 쓴 파드에 이 클래스를 기본 적용할지를 나타냅니다. 기본 클래스가 하나도 없으면 그런 파드의 우선순위는 0입니다[^priority-range].

### 자리는 preemption이 만든다

우선순위가 높다고 빈자리가 저절로 생기지는 않습니다. 자리를 만드는 동작에는 이름이 있습니다. **preemption(선점)** 입니다[^priority-range].

파드가 스케줄에 실패하면 스케줄러가 바로 포기하지 않습니다. 자기보다 낮은 우선순위 파드를 몇 개 비우면 자리가 나는 노드가 있는지 따집니다. 있으면 그 파드들을 축출하고 들어갑니다.

축출 여부는 별도 필드가 정합니다. `preemptionPolicy`이고, 파드가 아니라 **PriorityClass 오브젝트**에 답니다. 클래스를 직접 만들면 이렇게 생겼습니다.

```yaml
apiVersion: scheduling.k8s.io/v1
kind: PriorityClass
metadata:
  name: high-priority-nonpreempting
value: 1000000                    # 우선순위 값 (10억 이하)
preemptionPolicy: Never           # 줄은 서되 남을 밀어내지 않음
globalDefault: false
description: "축출 없이 먼저 스케줄되기만 하면 되는 워크로드용"
```

`value`와 나란히 놓이는 최상위 필드입니다. 기본값은 `PreemptLowerPriority`라서 안 적으면 낮은 우선순위 파드를 밀어냅니다. `Never`로 두면 대기 줄에서는 앞서되 축출은 하지 않고, 자원이 자연히 빌 때까지 기다립니다[^priority-range].

두 축이 갈린다는 점이 중요합니다. `value`는 **줄 세우기**를, `preemptionPolicy`는 **남을 밀어낼지**를 정합니다. 그래서 "우선순위는 높지만 돌고 있는 작업을 죽이고 싶지는 않다"를 표현할 수 있습니다. 공식 문서는 데이터 과학 작업을 예로 듭니다 — 먼저 실행되면 좋지만 남의 계산을 버리게 하고 싶지는 않은 경우입니다[^priority-range]. 다만 non-preempting 파드도 자기보다 높은 우선순위 파드에는 밀려날 수 있습니다.

여기까지가 클래스 쪽 이야기입니다. 만들어 둔 클래스를 파드에 붙이는 것은 별개이고, Pod spec의 `priorityClassName` 한 줄이 그 일을 합니다.

```yaml
spec:
  template:            # DaemonSet의 파드 템플릿
    spec:              # 여기부터가 Pod spec
      priorityClassName: system-node-critical
```

들여쓰기 위치를 보는 게 중요합니다. `priorityClassName`은 DaemonSet 자체가 아니라 **파드 템플릿 안의 Pod spec**에 둡니다. DaemonSet·Deployment·StatefulSet 모두 `spec.template.spec` 아래이고, 파드를 직접 만들 때는 최상위 `spec` 바로 아래입니다.

값으로 쓰는 것은 PriorityClass 오브젝트의 **이름**이지 숫자가 아닙니다. `2000001000`을 적는 게 아니라 `system-node-critical`을 적습니다. 이름을 숫자로 바꾸는 것은 priority admission controller의 일입니다. 그 컨트롤러가 클래스를 찾아 정수 값을 파드의 `priority` 필드에 채웁니다. 그래서 없는 이름을 적으면 파드가 **거부됩니다**[^priority-range].

이름으로 한 번 거치는 구조라 파드와 클래스의 수명이 갈립니다. 클래스를 지우면 그 이름을 쓰던 기존 파드는 그대로 남지만, 같은 이름으로 새 파드를 만들 수는 없습니다. 반대로 `globalDefault: true`인 클래스를 나중에 추가해도 이미 떠 있는 파드의 우선순위는 바뀌지 않습니다. 그 값은 추가 이후 만들어지는 파드에만 적용됩니다[^priority-range].

kube-proxy는 system-node-critical입니다 — 노드는 kube-proxy 파드 없이 제대로 동작할 수 없기(그 노드 파드가 쿠버네티스 Service를 못 씀) 때문에 다른 파드보다 우선순위가 높아야 합니다. 노드 운영에 중요한 노드 에이전트용 DaemonSet을 만들 때 priorityClassName을 적절히 설정합니다.

> **Spring 관점.** 관측 에이전트(로그·메트릭 수집)를 DaemonSet으로 배포할 때, 노드가 꽉 차면 에이전트가 일반 앱 파드에 밀려 스케줄 안 될 수 있습니다.
>
> 에이전트가 노드 관측에 필수라면 커스텀 PriorityClass(또는 system-node-critical)를 줘, 리소스 압박 시에도 에이전트가 살아남게 합니다. 반대로 애플리케이션 파드가 리소스 경쟁에서 밀리지 않게 하려면, 중요 앱에도 높은 PriorityClass를 부여하는 판단이 필요합니다.

## 정답 (자답 후 펼치기)

> 위 질문에 답해 본 다음 아래와 맞춰 봅니다. 순서는 질문과 1:1로 대응합니다.

### 정답 1 — privileged vs capabilities

privileged 컨테이너는 모든 커널 권한 검사를 우회해 **커널 전체 접근**을 갖습니다(root 수준). capabilities는 필요한 **시스템 콜 그룹만** 선별해 주는 방식으로, 예를 들어 NET_RAW·NET_ADMIN만 추가합니다. 보안 관점에서는 capabilities가 낫습니다 — 노드 에이전트는 보통 커널 기능 일부만 필요한데 privileged로 돌리면 전체 접근을 줘 공격면이 커지기 때문입니다. 최소 권한 원칙에 따라 필요한 capability만 주는 것이 권장됩니다.

### 정답 2 — drop의 역할

컨테이너 런타임은 아무 설정이 없어도 **기본 capability 세트**를 붙여 줍니다[^cap-default]. `add`만 쓰면 그 기본 세트가 그대로 남습니다. 필요한 것을 더하기만 할 뿐, 안 쓰는 권한은 손대지 않는 셈입니다.

`drop`은 이 기본 세트를 걷어냅니다. 그래서 최소 권한을 제대로 지키는 형태는 `drop: [ALL]`로 전부 비운 뒤 `add`로 필요한 것만 되돌리는 화이트리스트 방식입니다. Pod Security Standards의 `restricted` 프로파일이 요구하는 형태입니다[^pss].

### 정답 3 — hostPath와 kube-proxy

daemon 파드가 노드 파일시스템에 접근하려면 **hostPath 볼륨**을 씁니다. 노드의 경로를 컨테이너에 마운트하는 방식입니다. kube-proxy가 쓰는 두 볼륨은 이렇습니다.

- `/run/xtables.lock`: iptables/nftables가 IP 패킷 필터링을 조작할 때 쓰는 lock 파일
- `/lib/modules`: 노드에 설치된 커널 모듈

둘 다 노드의 패킷 필터링 규칙을 조작해 Service를 구현하는 데 필요합니다.

### 정답 4 — hostPath의 위험과 DaemonSet의 예외

hostPath는 노드 경로를 파드 안으로 그대로 끌어옵니다. 노드 위에는 그 노드의 다른 파드들의 것도 놓여 있습니다. `/var/lib/kubelet/pods/`의 남의 Secret, `/etc/kubernetes/`의 인증서, 컨테이너 런타임 소켓이 전부 노출 대상입니다. 깨지는 격리는 mount 네임스페이스이고, 컨테이너 root가 노드 root와 같은 UID였다는 점이 위험을 키웠습니다. 그래서 Pod Security Standards의 `baseline`부터 금지합니다[^pss].

DaemonSet에서 괜찮은 이유는 권한이 작아서가 아닙니다. 노드 에이전트가 하려는 일 자체가 그 노드를 관리하는 것이라, 노드 접근이 요구사항이기 때문입니다. 게다가 daemon 파드는 노드를 옮겨 다니지 않습니다. 컨트롤러가 파드 스펙에 노드 이름을 nodeAffinity로 박아 넣기 때문입니다[^ds-sched].

### 정답 5 — hostNetwork의 효과

`hostNetwork: true`면 파드가 자기 네트워크 대신 **호스트 노드의 네트워크 환경**을 씁니다. 장치·스택·포트가 모두 노드 것입니다. 노드에서 직접 도는 프로세스처럼 동작합니다.

파드는 자기 IP를 받지 않고 **노드 IP를 씁니다**. kube-proxy 파드 IP가 노드 IP와 같은 이유입니다.

다른 네임스페이스 타입은 계속 자기 것을 씁니다. IPC·PID 네임스페이스는 여전히 격리돼 다른 프로세스를 보지 못합니다. 노드의 IPC·PID를 쓰려면 별도 필드를 각각 켭니다.

```yaml
spec:
  hostNetwork: true   # 노드 네트워크
  hostIPC: true       # 노드 IPC 네임스페이스 — 공유 메모리·세마포어
  hostPID: true       # 노드 PID 네임스페이스 — 노드의 모든 프로세스가 보임
```

셋은 서로 독립입니다. `hostNetwork`를 켠다고 나머지가 따라 켜지지 않습니다. 필요한 것만 골라 여는 편이 낫습니다 — `hostPID: true`면 컨테이너가 노드의 모든 프로세스를 보게 되므로, 프로세스 목록에 노출되는 인자나 환경이 그만큼 넓어집니다.

### 정답 6 — Service 뒤의 hostNetwork 파드

Service 셀렉터가 hostNetwork 파드를 잡으면 EndpointSlice에 **노드 IP**가 기록됩니다. 파드 IP가 아닙니다. Service를 거친 트래픽은 노드 IP의 그 포트로 가고, 거기서 받는 것은 노드에서 그 포트를 여는 프로세스입니다.

나가는 트래픽은 달라지지 않습니다. 노드에 걸린 패킷 필터링 규칙을 그대로 타므로 ClusterIP 호출은 정상 동작합니다.

NetworkPolicy는 단정할 수 없습니다. 공식 문서가 hostNetwork 파드에 대한 동작을 undefined로 두기 때문입니다[^np-hostnetwork]. 플러그인이 그 트래픽을 구분하면 일반 파드처럼 정책이 걸리고, 구분하지 못하면 셀렉터 매칭에서 무시된 채 노드 IP 트래픽으로 취급됩니다. 문서는 후자가 더 흔하다고 적습니다.

### 정답 7 — daemon 파드를 다르게 취급

시스템 파드가 일반 워크로드 파드보다 중요하기 때문입니다. 노드가 꽉 차 시스템 파드를 스케줄하지 못하면, 쿠버네티스가 일부 일반 파드를 축출해 자리를 만들어야 합니다. 이 축출 동작이 preemption입니다.

**PriorityClass** 오브젝트로 우선순위를 매깁니다. 값이 높을수록 우선합니다. Pod spec의 `priorityClassName`으로 지정합니다. 노드 운영에 필수인 daemon에는 system-node-critical 같은 높은 클래스를 줍니다. kube-proxy가 그 예입니다.

### 정답 8 — 자리를 만드는 동작

**preemption(선점)** 입니다[^priority-range]. 파드가 스케줄에 실패하면 스케줄러가 바로 포기하지 않습니다. 자기보다 낮은 우선순위 파드를 비우면 자리가 나는 노드가 있는지 따지고, 있으면 그 파드들을 축출한 뒤 들어갑니다.

이 동작을 끄는 필드가 `preemptionPolicy`입니다. 기본값 `PreemptLowerPriority`가 축출을 수행하고, `Never`로 두면 대기 줄에서만 앞서고 축출은 하지 않습니다.

### 정답 9 — preemptionPolicy: Never

우선순위 자체는 그대로입니다. 달라지는 것은 **축출 여부**입니다.

기본값 `PreemptLowerPriority`는 초과 예약된 노드에 스케줄될 때 낮은 우선순위 파드를 밀어냅니다. `Never`로 두면 그 파드는 대기 줄에서 낮은 우선순위 파드보다 **앞서지만**, 자리를 만들려고 남을 축출하지는 않습니다[^priority-range]. 빈자리가 날 때까지 기다립니다.

이 필드는 파드가 아니라 **PriorityClass 오브젝트**에 답니다. `value`와 나란한 최상위 필드입니다. 그래서 `value`는 줄 세우기를, `preemptionPolicy`는 남을 밀어낼지를 각각 정합니다. "먼저 스케줄되고 싶지만 남을 죽이면서까지는 아니다"를 표현할 때 씁니다. 단 non-preempting 파드도 더 높은 우선순위 파드에는 밀려날 수 있습니다.

### 정답 10 — 사용자 생성 클래스의 제약

값은 **10억 이하**의 32비트 정수여야 하고, 이름은 유효한 DNS subdomain이면서 `system-` 접두사를 쓸 수 없습니다[^priority-range]. 실제 허용 범위는 -2147483648부터 1000000000까지입니다. 음수도 됩니다 — 기본값 0보다 덜 중요한 파드를 표현할 때 씁니다.

이유는 예약입니다. 10억을 넘는 값은 내장 시스템 클래스용으로 잡혀 있습니다. 실제로 두 내장 클래스는 20억대(2000000000·2000001000)입니다. 그래서 사용자가 만드는 어떤 클래스도 값만으로는 이 둘을 넘지 못합니다. 애플리케이션이 실수로든 고의로든 kube-proxy 같은 노드 필수 파드를 밀어내지 못하게 막는 장치입니다.

### 정답 11 — 지정하지 않은 파드의 우선순위

기본 클래스가 하나도 없으면 **0**입니다[^priority-range].

이 기본값을 바꾸는 것이 PriorityClass의 `globalDefault` 필드입니다. `kubectl get priorityclasses` 출력의 세 번째 열이 그것이고, 내장 두 클래스는 `false`입니다. 어떤 클래스에 `globalDefault: true`를 주면 `priorityClassName`을 지정하지 않은 파드가 그 클래스를 물려받습니다. 이 클래스는 클러스터에 **하나만** 존재할 수 있습니다[^priority-range].

### 정답 12 — node-critical vs cluster-critical

둘의 차이는 "그 파드가 이 노드에 반드시 있어야 하는가"입니다.

- **system-node-critical**(값 2000001000) — 개별 노드 운영에 중요한 파드입니다. 현재 노드에서 **다른 노드로 이동할 수 없습니다**. kube-proxy처럼 그 노드에 반드시 있어야 하는 것들입니다.
- **system-cluster-critical**(값 2000000000) — 클러스터 운영에 중요하지만 필요하면 **다른 노드로 이동 가능**한 파드입니다.

node-critical 값이 더 높아 우선순위도 더 높습니다. 노드 없이 못 도는 파드가 클러스터 전역 파드보다 그 노드에서 우선한다는 뜻입니다. 두 값이 20억대인 것도 우연이 아닙니다. 사용자가 만드는 PriorityClass는 값이 **10억을 넘을 수 없으므로**[^priority-range], 값 기준으로는 20억대인 내장 두 클래스보다 낮은 것만 만들 수 있습니다.
