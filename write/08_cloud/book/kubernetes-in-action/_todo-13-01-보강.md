## 보강 항목 (4개 · 전부 시각화감)

### ⭐ 1. §1 — 역할 분리를 "구체적 마찰"로 (시각화)

현재 53행은 "개발자가 게이트웨이까지 관리하거나 관리자가 개발자 대신 해야 했다"는 **결과만** 적어 *왜 그게 문제인지*가 없다. 학습자는 "어차피 호스트와 패스는 거의 동일하지 않나?"로 쪼갠 이유 자체를 못 봤다.

**결정 주체·변경 빈도 대비표**를 넣는다 — 내용이 비슷해 보이지만 이 둘이 다르다는 것이 분리의 근거다.

| | 누가 정하나 | 얼마나 자주 바뀌나 |
|---|---|---|
| 호스트·포트·인증서·공인 IP | **플랫폼/인프라 팀** | 거의 안 바뀜(도메인 하나 사면 몇 년) |
| 경로 → 어느 서비스로 | **각 앱 개발자** | 배포마다 바뀜(`/orders/v2` 추가) |

Ingress 에서 한 오브젝트에 있으면 생기는 마찰 둘을 명시한다.
- 개발자에게 수정 권한을 주면 → **RBAC 은 오브젝트 단위**라 "이 Ingress 의 이 경로만"은 줄 수 없다. 주문팀이 결제팀 경로나 TLS 설정을 깨뜨릴 수 있다
- 인프라 팀이 대신 하면 → 앱 배포마다 티켓. **배포 속도가 인프라 팀 처리량에 묶인다**

Gateway API 로 쪼개면 RBAC 경계가 조직 경계와 맞아떨어진다는 것을 네임스페이스 배치로 도식화.

```
플랫폼 팀 → Gateway 1개
주문 팀   → HTTPRoute (orders 네임스페이스)    ← 자기 것만
결제 팀   → HTTPRoute (payments 네임스페이스)  ← 서로 못 건드림
```

### ⭐ 2. §2 — 두 축이 왜 필요한가 + standard+extended 함정 (시각화)

현재 65·78행은 "동작·기능 차이를 막으려고"라는 결과만 적는다. 학습자는 (a)를 "모르겠음"(인터페이스를 만들어야 할 텐데)으로, (b)를 **"필드가 바뀌면 예외가 발생하고 구현체가 없으면 예외가 터진다"** 로 오답했다.

**핵심은 스키마가 모양은 강제하지만 행동은 강제하지 못한다는 것.** 이게 없어서 학습자가 "예외"를 기대했다.

```
HTTPRoute 에 어떤 필터 지정
  → CRD 스키마에 있는 필드라 apply 성공 ✅
  → 이 구현은 그 필터를 구현하지 않음
  → 컨트롤러가 조용히 무시 → 필터 없이 트래픽이 흐름
```

12-02 의 annotation 함정과 **동일 구조**임을 교차 참조한다(정식 스키마로 올려도 "구현이 처리하는가"는 보장 못 함). 인터페이스 비유도 유효 — 구현하면 메서드 존재는 확인되지만 빈 몸통이어도 컴파일된다.

**2×3 조합 매트릭스**로 함정을 드러낸다.

```
standard     + core                    → 가장 안전
standard     + extended                → ⚠️ 함정: API 는 안 바뀌지만 이 구현이 지원할지는 별개
experimental + core                    → 다 지원하나 API 가 바뀔 수 있음
experimental + implementation-specific → 가장 위험
```

`extended` 의 정의("지원하면 **동작이 같다**")가 Ingress annotation 과의 결정적 차이라는 것도 — Ingress 는 같은 기능을 구현마다 다른 이름·문법으로 했지만 extended 는 **이름과 의미를 규격이 고정**한다.

### ⭐ 3. §4 — 왜 전용 프록시인가 + IP 비용 트레이드오프 (시각화)

현재 170행은 "Gateway 마다 전용 프록시가 생긴다"는 **사실만** 적고 이유가 없어, 학습자가 "입구가 여러 개일 수는 없으니 하나를 공유"라고 오답했다.

**공유하지 않는 이유 셋**을 명시한다.
- 성능 격리 — 주문팀 폭주가 결제팀을 느리게 만들지 않는다
- 장애 범위 — 프록시 재시작·설정 오류가 모든 팀을 동시에 죽이지 않는다
- 관측 — 로그·메트릭이 팀 단위로 갈린다

즉 §1 의 RBAC(선언) 경계에 더해 **런타임 경계**까지 생긴다는 것이 역할 분리의 완성이다.

**12-01 과 반대 방향 트레이드오프**를 표로 대비(이게 이 항목의 핵심 값).

| | Ingress | Gateway API |
|---|---|---|
| 프록시·LB 개수 | 대개 하나(여러 Ingress 가 공유) | **Gateway 마다** |
| 얻는 것 | IP 비용 절감 | 팀별 격리 + RBAC 경계 |

해소책까지 이어 붙인다 — Gateway 를 팀마다가 아니라 **"격리가 필요한 단위"마다** 만들고, Route 는 **다른 네임스페이스의 Gateway 를 참조**할 수 있으므로(55행의 세 번째 이점) 공개용 Gateway 하나에 여러 팀 Route 를 붙인다. 권한 통제는 `ReferenceGrant`(13-03). 이렇게 하면 "Gateway 마다 프록시"와 "IP 하나로 여러 팀"이 모순되지 않는다.

### ⭐ 4. §5 — "PROGRAMMED: True 인데 404" 진단 흐름 (시각화)

현재 188행은 `attachedRoutes` 가 0이라 404 가 난다는 사실을 적으나, **Gateway 전체 conditions 가 listener 층 문제를 가린다**는 구조가 안 보인다. 학습자는 (a) Route 없음을 자력으로 맞혔으나 (b)에서 "게이트웨이 내부 이벤트를 봐야 할 것 같다"며 층을 못 짚었다.

3층 중 어느 층이 무엇을 숨기는지 도식화한다.

```
Gateway status
├─ addresses     → 172.18.255.200
├─ conditions    → Accepted/Programmed 둘 다 True   ← kubectl get gtw 가 보여주는 것
└─ listeners[]   → attachedRoutes: 0                ← 문제는 여기 있는데 위에서 안 보인다
```

- `PROGRAMMED: True` 의 의미를 정확히 — "설정이 생성돼 게이트웨이가 **접근 가능해졌다**"이고 "라우팅이 완성됐다"가 아니다. **입구는 열렸고 안내판이 없는 상태.**
- 명령 두 개를 나란히: `kubectl get gtw`(전체 조건)와 `kubectl get gtw kiada -o jsonpath='{.status.listeners[*].attachedRoutes}'`(listener 층).
- listener 조건 표(`Accepted`·`Conflicted`·`ResolvedRefs`)와 각각이 무엇을 뜻하는지.
- ⭐ **`ResolvedRefs: False` 는 12-02 TLS Secret 오지정을 status 에서 잡아 준다** — Ingress 에서는 오브젝트가 정상 표시되고 **접속 시점 브라우저 오류로만** 드러났다(12-02 보강 후보 ④와 짝). Gateway API 의 진단 가능성 개선이자, 12-02 오답 노트의 "배포 파이프라인은 초록불인데 사용자만 막힌다"가 완화되는 지점. 두 편을 잇는 교차 참조로서 값이 크다.
