# 정적 프로비저닝과 node-local 볼륨
---
> 정적 프로비저닝은 운영자가 스토리지를 미리 만들고 PV 오브젝트로 등록해, 쿠버네티스가 사용자의 PVC에 맞는 PV를 찾아 바인딩하게 하는 방식입니다. node-local 볼륨은 노드에 직접 붙은 디스크를 쓰되, hostPath와 달리 스케줄러가 파드를 항상 그 노드로 보냅니다.



> 이 문서를 읽고 나면 정적 프로비저닝과 동적 프로비저닝의 차이를 설명하고, node-local PV를 nodeAffinity와 함께 정의하는 매니페스트를 작성하며, PV가 Released에서 Available로 재사용되는 절차와 삭제 시 Terminating에 걸리는 이유를 진단할 수 있습니다.



## 진입 — 왜 정적 프로비저닝인가

> 동적 프로비저닝이 대세지만, 운영자가 로컬 디스크를 미리 준비하는 경우처럼 정적 프로비저닝이 맞는 시나리오가 있습니다. 이 편은 node-local 볼륨을 정적으로 프로비저닝하는 절차를 다룹니다.

이 개념은 [10-01편의 동적 프로비저닝](./10-01.PV%C2%B7PVC%C2%B7StorageClass%EC%99%80%20%EB%8F%99%EC%A0%81%20%ED%94%84%EB%A1%9C%EB%B9%84%EC%A0%80%EB%8B%9D.md)의 반대 방향입니다. 동적에서는 PVC를 만들면 프로비저너가 PV를 자동으로 만들지만, 정적에서는 운영자가 스토리지와 PV 오브젝트를 *먼저* 만들어 두고, 쿠버네티스가 사용자의 PVC에 맞는 기존 PV를 찾습니다.

정적 프로비저닝은 하나 이상의 지속 스토리지 볼륨을 미리 준비하고, 각각을 대표하는 PV 오브젝트를 만든 뒤, 사용자가 만드는 PVC마다 적절한 기존 PV를 쿠버네티스가 찾게 하는 것입니다. 지원되는 어떤 스토리지 기술로도 PV를 미리 준비할 수 있습니다. StorageClass의 자동 프로비저너가 하는 일과 비슷하되, 차이는 PV가 그것을 청구할 PVC보다 *먼저* 만들어진다는 점입니다.

이 편은 예로 node-local PV를 정적 프로비저닝합니다. 네트워크 연결 스토리지의 정적 프로비저닝도 절차가 비슷해, 같은 흐름으로 이해할 수 있습니다. 전체 흐름은 다음과 같습니다.

![정적 프로비저닝의 흐름 — 운영자가 PV를 먼저 만든다](_assets/10-02-static-provisioning.svg)



## 1. node-local PV가 필요한 경우

> 어떤 애플리케이션은 노드에 직접 붙은 로컬 스토리지에서 가장 잘 동작합니다. node-local PV는 hostPath와 달리 스케줄러가 파드를 항상 볼륨이 붙은 노드로 보내고, 운영자가 관리해 보안도 낫습니다.

앞 절들에서는 PV와 청구로 네트워크 연결 스토리지를 파드에 제공했습니다. 다만 어떤 애플리케이션은 로컬 연결 스토리지에서 가장 잘 동작하고, 이때 node-local PV를 씁니다.

[09장](./09-02.image%C2%B7hostPath%20%EB%B3%BC%EB%A5%A8.md)에서 hostPath 볼륨으로 파드가 호스트 파일시스템 일부에 접근하게 했습니다. hostPath는 파드가 보는 데이터가 어느 노드에 스케줄됐는지에 달렸습니다. 파드가 지워지고 다시 만들어지면 다른 노드로 가서 같은 데이터를 못 볼 수 있었습니다. local PV를 쓰면 이 문제가 풀립니다 — 스케줄러가 파드를 항상 로컬 볼륨이 붙은 노드로 보냅니다.

> **local PV가 hostPath보다 나은 점**: 보안입니다. hostPath는 일반 사용자에게 아예 허용하지 않는 게 좋았습니다. PV는 운영자가 관리하므로, 일반 사용자가 이를 통해 호스트의 임의 경로에 접근할 수 없습니다.

### local StorageClass와 PV 만들기

운영자로서 노드에 초저지연 디스크를 설치했다고 가정합니다(GKE·Kind에서는 노드에 디렉터리를 만들어 흉내). 이 디스크는 새 스토리지 클래스이므로 StorageClass 오브젝트로 대표합니다.

```yaml
apiVersion: storage.k8s.io/v1
kind: StorageClass
metadata:
  name: local
provisioner: kubernetes.io/no-provisioner   # 수동 프로비저닝 → 프로비저너 없음
volumeBindingMode: WaitForFirstConsumer      # 파드 스케줄 후 바인딩(노드 종속)
```

수동으로 프로비저닝하므로 provisioner를 `kubernetes.io/no-provisioner`로 둡니다. 로컬 볼륨은 물리적으로 연결된 노드 안에서만 접근되므로, volumeBindingMode를 `WaitForFirstConsumer`로 두어 파드가 스케줄될 때까지 바인딩을 미룹니다.

그다음 디스크를 대표하는 PV 오브젝트를 만듭니다.

```yaml
kind: PersistentVolume
apiVersion: v1
metadata:
  name: local-disk-on-my-node
spec:
  accessModes:
  - ReadWriteOnce
  storageClassName: local       # 앞서 만든 local 클래스
  capacity:
    storage: 10Gi
  local:                        # 노드 파일시스템의 경로에 마운트
    path: /tmp/my-disk
  nodeAffinity:                             # 어느 노드가 접근 가능한지
    required:
      nodeSelectorTerms:
      - matchExpressions:
        - key: kubernetes.io/hostname
          operator: In
          values:
          - insert-the-name-of-the-node-with-the-disk   # 디스크가 붙은 노드
```

PV의 spec은 용량·access mode·밑바탕 스토리지 기술을 지정합니다. 이 PV는 특정 노드에 붙은 로컬 디스크라 `local` 볼륨으로 정의하고 마운트 경로(`/tmp/my-disk`)를 지정합니다. 매니페스트 아래쪽 nodeAffinity는 이 볼륨에 어떤 노드가 접근할 수 있는지를 정합니다. 디스크가 한 노드에만 붙어 있으므로 그 노드에서만 접근 가능합니다([07장에서 파드의 node affinity를 배웠습니다](./09-02.image%C2%B7hostPath%20%EB%B3%BC%EB%A5%A8.md)).

PV를 만든 뒤 `Available` 상태를 확인하면, CLAIM 컬럼이 비어 있어 아직 어느 PVC에도 바인딩되지 않았음을 보여 줍니다. 운영자로서 사전 프로비저닝 작업은 여기서 끝나고, 사용자가 PVC로 이 볼륨을 청구할 수 있습니다.



## 2. 사전 프로비저닝된 PV 청구하기

> 사전 프로비저닝된 PV를 청구하는 것은 동적 청구와 다르지 않습니다. PVC를 만들되, WaitForFirstConsumer 모드라 파드까지 만들어야 바인딩됩니다.

애플리케이션 개발자로서 파드와 PVC를 배포합니다. local PV용 청구 생성은 다른 PVC와 다르지 않습니다.

```yaml
apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: quiz-data-local
spec:
  storageClassName: local      # local 클래스에서 PV 요청
  resources:
    requests:
      storage: 1Gi
  accessModes:
    - ReadWriteOnce
```

이 PVC는 local StorageClass가 `WaitForFirstConsumer`라 만들자마자 바인딩되지 않습니다. 파드도 만들어야 합니다.

```yaml
spec:
  volumes:
  - name: quiz-data
    persistentVolumeClaim:
      claimName: quiz-data-local   # quiz-local 파드가 이 PVC를 사용
```

파드를 만들면 다음이 일어납니다.

1. PVC가 PV에 바인딩됩니다.
2. 스케줄러가 그 볼륨이 특정 노드에서만 접근 가능함을 알고 파드를 그 노드로 보냅니다.
3. 파드 컨테이너가 로컬 볼륨을 마운트한 채 시작됩니다.

바인딩을 확인하면 `quiz-data-local`이 `local-disk-on-my-node` PV에 Bound 상태가 됩니다. 노드의 `/tmp/my-disk`를 보면 MongoDB가 거기 파일을 만든 것을 확인할 수 있습니다.

> local 필드 대신 다른 지원 볼륨 타입이나 `csi` 필드를 쓰면, 같은 절차로 네트워크 연결 PV를 정적 프로비저닝할 수 있습니다. StorageClass만 다르게 만들면 됩니다.



## 3. 수동 프로비저닝 PV의 해제와 재사용

> 동적 PV는 PVC와 함께 삭제되지만(Delete policy), 정적 PV는 보통 Retain policy라 해제되면 Released에 머뭅니다. 재사용하려면 PV 오브젝트를 지우고 다시 만들거나 claimRef를 제거합니다.

파드를 지워도 PVC·PV·스토리지는 영향받지 않지만, PVC를 지우면 PV에 영향이 갑니다. 동적 프로비저닝에서는 프로비저너가 PV의 policy를 Delete로 설정해 PVC와 함께 PV가 삭제되지만, 정적 프로비저닝 PV는 보통 `Retain`을 씁니다. `local-disk-on-my-node` PV도 그렇습니다.

quiz-local 파드와 quiz-data-local PVC를 지우면 PV 상태가 Bound에서 Released로 바뀝니다.

```bash
$ kubectl get pv local-disk-on-my-node
NAME                    RECLAIM POLICY   STATUS     CLAIM
local-disk-on-my-node   Retain           Released   default/quiz-data-local
```

CLAIM 컬럼에 이전 PVC가 아직 보이지만 바인딩은 풀렸습니다. 여기서 PVC를 다시 만들면 어떻게 될까요? 놀랍게도 파드와 PVC 둘 다 Pending에 걸립니다. 볼륨이 이전에 쓰여 데이터가 남아 있을 수 있어, 다른 PVC가 청구하기 전에 지워야 하기 때문입니다. 그래서 상태가 `Available`이 아니라 `Released`이고, 청구 이름이 아직 표시됩니다 — 운영자가 데이터를 안전하게 지워도 되는지 판단하게 돕는 장치입니다.

### 재사용 가능하게 만들기

볼륨을 다시 쓰려면 PV 오브젝트를 지우고 다시 만듭니다. 데이터가 사라질까요? 사전 프로비저닝된 PV에서 오브젝트 삭제는 *데이터 포인터를 지우는 것*과 같습니다. PV 오브젝트는 스토리지를 *가리킬* 뿐 데이터를 저장하지 않습니다. 지우고 다시 만들면 같은 스토리지를 가리키는 새 포인터가 생기므로 데이터는 그대로입니다.

> **대안**: PV 오브젝트를 편집해 spec의 `claimRef`를 제거해도 볼륨을 다시 Available로 만들 수 있습니다.

PV를 다시 만들면 잠깐 `Available`이 됐다가, 대기 중이던 quiz-local 파드·quiz-data-local PVC가 이를 바인딩해 곧 `Bound`가 됩니다. 파드는 이제 이전 파드가 만든 MongoDB 파일에 접근합니다.



## 4. 사용 중인 PV·PVC 삭제와 Terminating

> 파드가 쓰는 PV·PVC를 지우면 즉시 삭제되지 않고 Terminating에 걸립니다. 쿠버네티스는 운영자가 디스크를 회수하려 한다고 파드를 죽이지 않습니다 — 파드를 지워야 삭제가 완료됩니다.

바인딩된 상태에서 운영자가 PV를 지우면 어떻게 될까요? `kubectl delete pv`는 API에 삭제를 지시하고 컨트롤러가 완료할 때까지 기다립니다. 하지만 PV가 PVC에서 해제되기 전엔 완료될 수 없습니다.

```bash
$ kubectl delete pv local-disk-on-my-node
persistentvolume "local-disk-on-my-node" deleted    # 여기서 멈춤(블록)

# Ctrl-C로 대기만 취소(삭제는 이미 진행 중)
$ kubectl get pv local-disk-on-my-node
NAME                    STATUS        CLAIM
local-disk-on-my-node   Terminating   default/quiz-data-local
```

PV 상태가 Terminating이 되고, PVC 오브젝트를 지울 때까지 그 상태에 머뭅니다. PVC도 파드가 쓰는 중이라, 지우려 하면 마찬가지로 Terminating에 걸립니다. PVC 삭제가 파드에 의해 막힌 것입니다.

PV나 PVC를 지워도 그것을 쓰는 파드에는 즉시 영향이 없습니다. 파드 안 애플리케이션은 영향 없이 계속 돕니다. 쿠버네티스는 운영자가 디스크 공간을 되찾고 싶다는 이유만으로 파드를 죽이지 않습니다. PVC·PV의 종료를 완료하려면 파드를 지워야 합니다(`kubectl delete po quiz-local`).

### 밑바탕 스토리지 수동 삭제

정적 프로비저닝된 PV를 지워도 밑바탕 스토리지(`/tmp/my-disk` 디렉터리 등)는 삭제되지 않습니다. 클라우드 스토리지 볼륨도 그럴 수 있으니, 불필요한 비용을 막으려면 수동으로 지웁니다. GKE에서는 `gcloud compute disks list`로 나열하고 `gcloud compute disks delete <name>`로 지웁니다. 동적 프로비저닝된 디스크는 보통 PV 삭제 시 자동으로 지워집니다.

## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문의 5개에 *먼저 자답한 뒤* 아래를 읽으세요.

### 정답 1 — 정적 vs 동적 프로비저닝

핵심 차이는 *PV가 언제 만들어지는가*입니다. 동적에서는 사용자가 PVC를 만들면 프로비저너가 PV와 밑바탕 스토리지를 그때 자동으로 만듭니다. 정적에서는 운영자가 스토리지와 PV 오브젝트를 *먼저* 만들어 두고, 사용자가 PVC를 만들면 쿠버네티스가 요구사항(크기·access mode)에 맞는 *기존* PV를 찾아 바인딩합니다. 정적은 운영자가 로컬 디스크를 미리 준비하는 시나리오에 맞습니다.

### 정답 2 — node-local이 hostPath보다 나은 점

첫째, *스케줄링*입니다. hostPath는 파드가 어느 노드에 가느냐에 따라 다른 데이터를 보지만, local PV는 스케줄러가 파드를 항상 볼륨이 붙은 노드로 보내 같은 데이터를 보장합니다. 둘째, *보안*입니다. hostPath는 일반 사용자에게 허용하면 호스트 임의 경로 접근을 열어 주지만, local PV는 운영자가 관리하므로 일반 사용자가 임의 경로에 접근할 수 없습니다.

### 정답 3 — nodeAffinity와 WaitForFirstConsumer

nodeAffinity는 이 volume에 *어떤 노드가 접근할 수 있는지*를 정합니다. 디스크가 한 노드에만 붙어 있으므로 그 노드로 제한합니다. volumeBindingMode를 `WaitForFirstConsumer`로 두는 이유는, 로컬 볼륨이 특정 노드 안에서만 접근되기 때문입니다. 파드가 어느 노드에 스케줄될지 정해진 *뒤* 바인딩해야, PVC가 그 노드의 PV에 올바로 묶입니다. Immediate로 두면 소비자를 모르는 채 바인딩돼 노드 종속 볼륨에는 맞지 않습니다.

### 정답 4 — Released를 Available로, 그리고 데이터

두 방법은 (1) PV 오브젝트를 지우고 다시 만들기, (2) PV 오브젝트를 편집해 spec의 `claimRef`를 제거하기입니다. 사전 프로비저닝된 PV에서 오브젝트 삭제는 *데이터 포인터를 지우는 것*이라, 데이터는 사라지지 않습니다. PV 오브젝트는 스토리지를 가리킬 뿐 데이터를 저장하지 않으므로, 지우고 다시 만들면 같은 스토리지를 가리키는 새 포인터가 생겨 같은 데이터에 접근합니다.

### 정답 5 — 사용 중 삭제와 Terminating

쿠버네티스가 운영자의 디스크 회수 요청만으로 실행 중인 파드를 죽이지 않기 때문입니다. `kubectl delete pv/pvc`는 삭제를 지시하고 컨트롤러 완료를 기다리지만, PV는 PVC에서 해제되기 전엔, PVC는 파드가 놓아주기 전엔 완료될 수 없습니다. 그래서 Terminating에 머뭅니다. 파드 안 애플리케이션은 영향 없이 계속 돌고, 파드를 지워야 종료가 완료됩니다.
