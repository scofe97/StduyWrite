# command·args와 환경변수
---
> 컨테이너화된 애플리케이션도 보통의 애플리케이션처럼 커맨드라인 인자·환경변수·파일로 설정합니다. 이 편에서는 이미지에 박힌 기본값(ENTRYPOINT·CMD·ENV)을 Pod 매니페스트의 command·args·env 필드로 덮어쓰는 법과, $(VAR_NAME) 변수 참조가 통하는 경우와 안 통하는 경우를 정리합니다.



## 진입 — 이 문서를 읽고 나면 무엇을 할 수 있는가

> 이 문서를 읽고 나면 Dockerfile의 ENTRYPOINT·CMD가 Pod 매니페스트의 command·args에 어떻게 대응하는지 설명할 수 있습니다. 이미지를 다시 빌드하지 않고 실행 명령·인자·환경변수를 바꾸며 $(VAR_NAME) 참조가 해석되지 않는 세 가지 상황도 구분할 수 있습니다.

이 개념은 "빌드 산출물에는 기본값만 두고 실행 시점에 덮어쓴다"는 익숙한 설정 원칙입니다. 다만 쿠버네티스는 그 덮어쓰기 지점을 컨테이너 실행 명령(command·args)과 환경(env)으로 나눠 Pod 매니페스트에 선언하게 한다는 점이 다릅니다.



## 1. 이미지의 기본값 — ENTRYPOINT·CMD·ENV

> 컨테이너에서 실행될 명령·인자·환경변수의 기본값은 Dockerfile의 ENTRYPOINT·CMD·ENV 디렉티브로 이미지에 정의됩니다. 설정 파일은 COPY로 담깁니다.

컨테이너에서 실행되는 명령은 보통 컨테이너 이미지에 정의됩니다. Dockerfile에서 명령은 `ENTRYPOINT` 디렉티브로, 인자는 `CMD` 디렉티브로, 환경변수는 `ENV` 디렉티브로 지정합니다. 설정 파일이 필요하면 `COPY`로 이미지에 담습니다.

`ENTRYPOINT`와 `CMD`를 나눈 이유는 우선순위가 아니라 **고정할 실행 프로그램과 교체 가능한 기본값을 분리하기 위해서**입니다. 애플리케이션 이미지에서는 `ENTRYPOINT`에 항상 실행할 프로그램을 둡니다. `CMD`에는 사용자가 실행 시점에 바꿀 수 있는 기본 인자를 두는 조합이 흔합니다. 반면 여러 명령을 자유롭게 실행하는 범용 이미지라면 `CMD`만 정의하는 편이 자연스러울 수 있습니다.

```dockerfile
ENTRYPOINT ["java", "-jar"]
CMD ["app.jar", "--server.port=8080"]
```

별도 인자를 주지 않으면 두 배열이 결합돼 `java -jar app.jar --server.port=8080`이 실행됩니다. 다른 JAR을 인자로 넘기면 `ENTRYPOINT`는 유지되고 `CMD`만 교체돼 `java -jar other.jar`가 됩니다. 따라서 `ENTRYPOINT`가 언제나 더 좋은 것이 아니라, 이미지가 하나의 고정된 실행 도구인지에 따라 선택해야 합니다.

Kiada 0.4 버전은 `--listen-port` 커맨드라인 인자로 리스닝 포트를 설정합니다. `INITIAL_STATUS_MESSAGE` 환경변수로 초기 상태 메시지도 바꿀 수 있습니다.

응답에는 호스트명 대신 Pod 이름·IP와 노드 이름까지 담습니다. 이 정보는 환경변수로 받으며 08-03의 Downward API에서 채웁니다. 그 Dockerfile은 다음과 같습니다.

```dockerfile
FROM node:12
COPY app.js /app.js
COPY html/ /html

ENV INITIAL_STATUS_MESSAGE="This is the default status message"

ENTRYPOINT ["node", "app.js"]
CMD ["--listen-port", "8080"]
```

`ENV`는 환경변수 기본값, `ENTRYPOINT`는 컨테이너 시작 시 실행할 명령, `CMD`는 그 명령에 넘길 기본 인자입니다. 주석을 코드 밖에 둔 이유가 있습니다 — Dockerfile의 `#`은 **줄 첫머리에서만** 주석이고, 명령 뒤에 붙인 `#`은 인자의 일부로 파싱됩니다. 위 리스팅에 행말 주석을 달면 그대로 빌드되지 않습니다.

리스팅은 `node:12`를 베이스로 적지만, 레지스트리에 올라간 `luksa/kiada:0.4`를 실제로 열어 보면 `NODE_VERSION=16.11.1`입니다. 뒤 §4에서 `$(NODE_VERSION)` 을 예로 들 때 나오는 값이 그것입니다.

- 여기 정의된 환경변수·명령·인자는 옵션 없이 컨테이너를 돌릴 때 쓰이는 **기본값**일 뿐입니다. 쿠버네티스는 이 기본값을 Pod 매니페스트에서 덮어쓸 수 있게 해 줍니다.



## 2. command와 args — 명령·인자 덮어쓰기

> Pod 매니페스트의 command는 ENTRYPOINT를, args는 CMD를 덮어씁니다. 실행되는 전체 명령은 두 배열을 이어 붙여 만들어집니다.

컨테이너가 실행될 때 ENTRYPOINT 배열과 CMD 배열이 이어 붙어 전체 명령이 됩니다. 쿠버네티스는 이 둘에 대응하는 두 필드를 제공합니다 — 컨테이너 정의의 `command`와 `args`입니다. 마찬가지로 두 배열을 이어 붙인 결과가 컨테이너에서 실행됩니다.

| Dockerfile | Pod 매니페스트 | 설명 |
|-----------|---------------|------|
| ENTRYPOINT | command | 컨테이너에서 실행되는 실행 파일(인자를 함께 담을 수도 있으나 보통 안 담음) |
| CMD | args | 명령에 전달되는 추가 인자 |

명령과 인자가 두 디렉티브·두 필드로 나뉘어 있어, 명령은 그대로 두고 인자만 바꾸거나 그 반대가 모두 가능합니다.

![Dockerfile 기본값과 Pod 매니페스트의 command·args 덮어쓰기 — 세 가지 조합](_assets/08-01-command-args-override.svg)

### command만 덮어쓰기

Kiada를 CPU·힙 프로파일링을 켜서 돌리고 싶다면, Dockerfile을 고쳐 이미지를 다시 빌드하는 대신 매니페스트에서 명령을 바꿉니다.

```yaml
kind: Pod
spec:
  containers:
  - name: kiada
    image: luksa/kiada:0.4
    command: ["node", "--cpu-prof", "--heap-prof", "app.js"]   # 이미지의 명령 대신 실행됨
```

여기서 흔히 오해하는 지점이 있습니다. `args`를 생략했으니 이미지의 CMD인 `--listen-port 8080`이 남아 붙을 것 같습니다. 그렇지 않습니다. **`command`를 지정하는 순간 이미지의 CMD는 버려집니다.**

최종 명령은 `node --cpu-prof --heap-prof app.js`뿐입니다. 위 매니페스트의 컨테이너는 리스닝 포트 인자 없이 뜹니다. 프로파일링을 켜려다 포트 설정을 잃는 셈입니다. 그러니 `command`를 덮어쓸 때는 필요한 인자를 `args`에 함께 적습니다.

```yaml
    command: ["node", "--cpu-prof", "--heap-prof", "app.js"]
    args: ["--listen-port", "8080"]      # command를 덮어썼으면 CMD도 직접 적는다
```

네 조합을 한 번에 정리하면 이렇습니다.[^cmd-args]

| `command` | `args` | 실제 실행되는 명령 |
|---|---|---|
| 생략 | 생략 | 이미지 ENTRYPOINT + 이미지 CMD |
| 생략 | 지정 | 이미지 ENTRYPOINT + 매니페스트 `args` |
| 지정 | 생략 | 매니페스트 `command` 만 — **이미지 CMD 는 버려진다** |
| 지정 | 지정 | 매니페스트 `command` + 매니페스트 `args` |

규칙은 하나입니다. 생략한 쪽만 이미지 기본값이 채워지는데, **`command` 를 채우면 CMD 자리는 기본값 대신 빈 채로 남습니다.** `args` 를 생략했을 때 CMD 가 살아남는 것은 `command` 도 함께 생략했을 때뿐입니다.

배열 표기는 원소가 적을 때는 좋지만 늘어나면 읽기 어려워지므로, 그때는 리스트 표기가 낫습니다.

```yaml
    command:
    - node
    - --cpu-prof
    - --heap-prof
    - app.js
```

> YAML 파서가 문자열이 아닌 것으로 해석할 값은 따옴표로 감싸야 합니다. `1234` 같은 숫자와 `true`·`false`가 대표적입니다. `yes`·`no`·`on`·`off`·`y`·`n` 까지 불리언으로 보는 것은 YAML 1.1 기준이며, 1.2 core schema는 `true`·`false`만 불리언으로 봅니다. 파서 구현에 따라 갈리므로 command 배열에서는 따옴표를 두는 편이 안전합니다.

### args만 덮어쓰기

리스닝 포트만 바꾸고 싶다면 args를 지정합니다.

```yaml
    args: ["--listen-port", "9090"]   # 이미지의 CMD를 덮어씀
```

이 Pod를 배포하면 컨테이너에서 실행되는 전체 명령은 `node app.js --listen-port 9090`입니다 — Dockerfile의 ENTRYPOINT와 매니페스트의 args가 이어 붙은 결과입니다.



## 3. env — 컨테이너별 환경변수

> 환경변수는 env 필드에 name-value 목록으로 정의합니다. Pod 전역이 아니라 컨테이너별로만 설정할 수 있습니다.

명령·인자처럼 환경변수도 Pod의 각 컨테이너에 설정할 수 있습니다.

> 집필 시점 기준, 환경변수는 컨테이너별로만 설정할 수 있습니다. Pod 전체에 전역 환경변수 집합을 정의해 모든 컨테이너가 상속하게 하는 방법은 없습니다.

```yaml
kind: Pod
metadata:
  name: kiada
spec:
  containers:
  - name: kiada
    image: luksa/kiada:0.4
    env:                                # 이 컨테이너의 환경변수 목록
    - name: POD_NAME
      value: kiada
    - name: INITIAL_STATUS_MESSAGE
      value: This status message is set in the pod spec.
```

> 환경변수 값은 문자열이어야 하므로, 문자열이 아닌 값(숫자, yes·no·true·false 등)은 따옴표로 감쌉니다.
>
> 매니페스트에 정의된 환경변수 목록은 `kubectl set env pod <pod-name> --list`로 볼 수 있습니다 — 단 이것은 매니페스트에 정의된 것만 보여주지, 컨테이너 안의 실제 변수를 보여주지는 않습니다.

위 매니페스트처럼 이름이 `kiada`인 Pod를 생성했다면, 컨테이너 안의 실제 환경은 다음 명령으로 확인합니다.

```bash
kubectl exec kiada -- env
```

Deployment가 Pod를 생성했다면 Pod 이름에 `kiada-7bc9cd6878-2vm7s`처럼 해시와 임의 문자열이 붙으므로, 실제 이름을 조회해 넘겨야 합니다.

```bash
POD=$(kubectl get pod -l app=kiada -o jsonpath='{.items[0].metadata.name}')
kubectl exec "$POD" -- env
```

출력에는 매니페스트에서 설정한 변수 외에도 이미지와 쿠버네티스가 설정한 변수가 함께 보입니다.

| 출처 | 예시 | 확인 위치 |
|------|------|----------|
| 컨테이너 런타임·쿠버네티스가 설정 | HOSTNAME | Pod의 이름·hostname 설정 |
| 컨테이너 이미지가 설정(ENV) | PATH, NODE_VERSION, YARN_VERSION | Dockerfile의 `ENV` 또는 이미지의 `Config.Env` |
| Pod 매니페스트가 설정 | POD_NAME, INITIAL_STATUS_MESSAGE | `spec.containers[].env` |
| 쿠버네티스가 설정 | KUBERNETES_SERVICE_HOST 등(Service 관련, 11장) | 기본 `kubernetes` Service 정보 |

`KUBERNETES_SERVICE_HOST` 계열은 Pod의 `enableServiceLinks`와 무관하게 항상 들어옵니다. 그 필드가 끄고 켜는 것은 **같은 네임스페이스의 다른 Service**를 Docker link 스타일(`<SVCNAME>_SERVICE_HOST` 등)로 주입하는 쪽이지, 기본 `kubernetes` Service 정보가 아닙니다. `enableServiceLinks: false`로 둔 파드 안에서도 `KUBERNETES_SERVICE_HOST=10.96.0.1`은 그대로 보입니다.

이 표의 `PATH`는 Kiada가 기반으로 삼는 Node.js 이미지의 `ENV`에서 온 값입니다. `PATH`처럼 이미지나 런타임 모두가 설정할 수 있는 변수는 이름만 보고 출처를 단정하면 안 됩니다. 각 변수의 출처를 직접 표시하는 명령은 없으므로, Pod 매니페스트의 `spec.containers[].env`와 이미지의 Dockerfile 또는 `Config.Env`를 실제 출력과 대조해 출처를 가립니다.



## 4. $(VAR_NAME) 변수 참조 — 통하는 곳과 안 통하는 곳

> 매니페스트 안에서는 $(VAR_NAME)으로 다른 환경변수를 참조할 수 있습니다. env 목록에서는 먼저 정의된 변수만 해석되고 이미지의 변수는 문자열 그대로 남습니다.

환경변수 값 안에서 `$(VAR_NAME)` 문법으로 다른 변수를 참조할 수 있습니다.

```yaml
env:
- name: POD_NAME
  value: kiada
- name: INITIAL_STATUS_MESSAGE
  value: My name is $(POD_NAME). I run NodeJS version $(NODE_VERSION).
```

이 Pod를 배포하면 상태 메시지는 다음과 같이 나옵니다.

```pseudocode
My name is kiada. I run NodeJS version $(NODE_VERSION).
```

`POD_NAME`은 해석됐지만 `NODE_VERSION`은 그대로 남았습니다. `env[].value`의 `$(VAR_NAME)` 문법은 같은 컨테이너의 env 목록에서 참조하는 항목보다 **먼저 정의된 변수**와 쿠버네티스가 주입한 Service 환경변수를 해석합니다. NODE_VERSION은 Node.js 이미지의 Dockerfile에만 정의돼 있으므로 이 시점에는 보이지 않습니다.

> 참조가 해석되지 못하면 참조 문자열이 그대로 남습니다.
> 변수를 해석하지 말고 문자 그대로 `$(VAR_NAME)`을 담고 싶으면 달러 기호를 겹쳐 `$$(VAR_NAME)`으로 씁니다 — 쿠버네티스가 달러 하나를 제거하고 해석을 건너뜁니다.

`$(VAR_NAME)` 참조는 다른 변수뿐 아니라 **command·args 필드**에서도 쓸 수 있습니다.

```yaml
    args:
    - --listen-port
    - $(LISTEN_PORT)      # 아래에 정의된 변수로 해석됨
    env:
    - name: LISTEN_PORT
      value: "8080"
```

지금은 포트를 직접 쓰는 것과 다를 게 없어 보입니다. 이 값을 외부 소스(ConfigMap)에서 받아오게 되면 이 참조 방식으로 그 값을 명령·인자에 주입할 수 있게 됩니다(08-02).

### 매니페스트에 없는 변수는 셸에게 맡긴다

command·args의 `$(VAR_NAME)`은 컨테이너 시작 전에 Kubernetes가 구성한 환경을 참조합니다. 이미지의 `ENV`는 이 확장에 쓰이지 않습니다. 이미지에 정의된 변수 등을 쓰려면 명령을 **셸을 거쳐** 실행해야 합니다. 셸에서 쓰는 문법은 `$VAR_NAME` 또는 `${VAR_NAME}`입니다(괄호와 중괄호의 차이에 주의).

여기서는 **값의 출처**와 **치환 주체**를 분리해서 봐야 합니다. Pod의 `env`와 이미지의 `ENV`는 컨테이너가 받을 환경을 구성합니다. 명령 문자열에 적힌 문법이 실제 치환 주체를 결정합니다.

| 문법 | 치환 주체·시점 | 참조 범위 | 해석할 수 없을 때 |
|------|---------------|----------|------------------|
| `$(VAR_NAME)` | Kubernetes, 컨테이너 시작 준비 시점 | 앞서 정의된 `env`와 Service 환경변수 | 참조 문자열을 그대로 유지 |
| `$VAR_NAME`·`${VAR_NAME}` | 컨테이너 내부 셸, 명령 실행 시점 | 이미지 `ENV`, Pod `env`, 시스템이 구성한 실제 환경 | 셸 규칙에 따라 보통 빈 문자열 |

```yaml
containers:
- name: main
  image: alpine
  command:
  - sh                # 컨테이너의 최상위 명령은 셸
  - -c
  - 'echo "Hostname is $HOSTNAME."; sleep infinity'   # 셸이 $HOSTNAME을 해석
```

`HOSTNAME`은 매니페스트에 없습니다. 운영체제가 초기화한 변수를 셸이 echo 실행 전에 해석하므로 올바로 출력됩니다.



## 5. Pod의 호스트명과 FQDN 설정

> Pod의 호스트명은 기본적으로 Pod 이름과 같습니다. hostname·subdomain 필드로 바꾸면 클러스터 내부 FQDN을 구성할 수 있습니다.

기본적으로 Pod의 호스트명은 Pod 이름과 같습니다. spec의 `hostname` 필드로 덮어쓸 수 있으며, `subdomain` 필드까지 설정하면 Pod의 FQDN(fully qualified domain name)은 다음 형태가 됩니다.

```pseudocode
<hostname>.<subdomain>.<pod namespace>.svc.<cluster domain>
```

이것은 Pod의 내부 FQDN일 뿐이며 추가 단계(11장) 없이는 DNS로 해석되지 않습니다.



## 6. Spring 앱 배포 관점에서

> Spring 애플리케이션 설정은 `env`, Spring Boot 인자는 `args`, JVM 실행 방식은 `command`로 조정합니다. 바꾸려는 대상에 맞는 필드를 골라야 이미지의 기본 실행 계약을 불필요하게 깨뜨리지 않습니다.

| 바꾸려는 대상 | Pod 필드 | 예시 |
|--------------|----------|------|
| 애플리케이션 프로퍼티 | `env` | `SERVER_PORT`, `SPRING_DATASOURCE_URL` |
| Spring Boot 커맨드라인 인자 | `args` | `--spring.profiles.active=prod` |
| JVM 옵션과 실행 명령 | `command` | `-XX:+HeapDumpOnOutOfMemoryError`, `-Xlog:gc*` |

### env로 애플리케이션 설정 주입하기

Spring Boot의 relaxed binding은 대문자 환경변수를 프로퍼티 이름으로 변환합니다. 예를 들어 `SERVER_PORT`는 `server.port`로, `SPRING_DATASOURCE_URL`은 `spring.datasource.url`로 연결됩니다.

```yaml
env:
- name: SERVER_PORT
  value: "9090"
- name: SPRING_DATASOURCE_URL
  value: jdbc:postgresql://postgres:5432/app
```

환경변수는 컨테이너별 설정입니다. 애플리케이션과 Envoy 사이드카에 같은 값이 필요하면 두 컨테이너에 각각 정의해야 합니다. 중복되는 변수가 많아지면 08-02에서 다룰 ConfigMap과 `envFrom`으로 설정 묶음을 분리할 수 있습니다.

다른 컨테이너에 선언된 변수는 빈 문자열로 공유되는 것이 아니라 **아예 존재하지 않습니다**. 예를 들어 `LOG_LEVEL`을 앱 컨테이너에만 선언했다면 사이드카에서 `printenv LOG_LEVEL`을 실행했을 때 값이 출력되지 않고 명령이 실패합니다. 같은 ConfigMap을 사용하더라도 각 컨테이너의 `envFrom`에 참조를 각각 선언해야 합니다.

### args로 Spring Boot 인자 바꾸기

Spring Boot는 `--이름=값` 형태의 커맨드라인 인자를 프로퍼티로 읽습니다. 이미지의 실행 명령은 유지하면서 프로파일만 바꾸려면 `args`를 사용합니다.

```yaml
args:
- --spring.profiles.active=prod
```

이 값은 이미지의 CMD를 교체합니다. Spring Boot의 프로퍼티 우선순위에서도 환경변수보다 앞섭니다. 예를 들어 `SERVER_PORT=8080`과 `args: ["--server.port=9090"]`을 함께 지정하면 애플리케이션은 9090 포트로 실행됩니다.

여기서 우선순위를 결정하는 주체는 Kubernetes가 아니라 **Spring Boot**입니다. Kubernetes는 환경변수와 프로세스 인자를 컨테이너에 전달할 뿐입니다. Spring Boot가 두 설정 소스를 읽은 뒤 커맨드라인 프로퍼티를 더 높은 우선순위로 적용합니다. 한 설정을 두 경로에 중복 선언하지 않는 편이 좋습니다.

### command로 JVM 실행 방식 바꾸기

GC 로그나 힙 덤프처럼 JVM 시작 전에 필요한 옵션은 `java`와 `-jar` 사이에 와야 합니다. 이때는 전체 실행 명령을 배열로 명시할 수 있습니다.

```yaml
command:
- java
- -XX:+HeapDumpOnOutOfMemoryError
- -Xlog:gc*
- -jar
- app.jar
```

`command`는 이미지의 ENTRYPOINT를 교체하므로 기존 실행 명령을 빠뜨리지 않았는지 확인해야 합니다. 이때 이미지의 CMD도 함께 버려지므로, 원래 CMD에 있던 인자가 필요하면 `args`에 직접 옮겨 적어야 합니다.

이미지의 `JAVA_OPTS`처럼 셸이 해석해야 하는 변수를 사용한다면 `sh -c`가 필요합니다. 이 경우 셸이 PID 1로 남지 않도록 `exec`로 JVM을 교체해야 Kubernetes의 종료 신호가 JVM에 직접 전달됩니다.

다음처럼 배열 인자에 `$JAVA_OPTS`를 직접 적는 것만으로는 변수가 확장되지 않습니다. Kubernetes와 컨테이너 런타임은 이 문자열을 셸 문법으로 해석하지 않으므로 JVM은 `$JAVA_OPTS`라는 문자열 하나를 그대로 인자로 받습니다.

```yaml
command: ["java"]
args: ["$JAVA_OPTS", "-jar", "app.jar"]   # $JAVA_OPTS가 그대로 전달됨
```

변수를 여러 JVM 인자로 펼쳐야 한다면 셸이 문자열을 해석하도록 합니다. 해석이 끝난 뒤 `exec`로 셸을 JVM으로 교체합니다.

```yaml
command: ["sh", "-c"]
args:
- 'exec java $JAVA_OPTS -jar app.jar'
```

### 실측 — exec 전후 PID 1 비교

`k8s_in_action/08-configuring-apps/command-env/` 실습에서는 같은 `sleep 3600` 명령을 `exec` 유무만 바꿔 실행했습니다. 컨테이너 안에서 `ps -o pid,ppid,comm,args`로 확인한 결과는 다음과 같습니다.

```pseudocode
# exec 없음: sh -c 'sleep 3600 & wait'
PID   PPID  COMMAND
1     0     sh
11    1     sleep

# exec 사용: sh -c 'exec sleep 3600'
PID   PPID  COMMAND
1     0     sleep
```

`PPID`는 부모 프로세스의 PID입니다. exec가 없으면 PID 11인 `sleep`의 PPID가 1이므로 `sh`가 부모임을 알 수 있습니다. Kubernetes의 종료 신호는 우선 PID 1인 셸에 도착하므로, 셸이 신호를 자식에게 전달하지 않으면 애플리케이션이 정상 종료 절차를 실행하지 못할 수 있습니다.

exec를 사용하면 셸이 새 자식을 만드는 대신 자기 프로세스를 대상 명령으로 교체합니다. PID 값 1은 유지되고 실행 프로그램만 `sh`에서 `sleep`으로 바뀝니다. Spring 컨테이너에서도 같은 원리로 `exec java ...`를 사용하면 JVM이 PID 1이 되어 `SIGTERM`을 직접 받고 graceful shutdown을 수행할 수 있습니다.

실습 중 `kubectl exec`로 추가 실행한 `ps`의 PPID가 0으로 보일 수 있습니다. 이 프로세스는 기존 PID 1이 만든 자식이 아닙니다. 컨테이너 런타임이 외부에서 추가했습니다. PID namespace 안에서는 그 부모가 보이지 않기 때문입니다.

### args만 덮어쓴 결과

이미지의 ENTRYPOINT를 유지한 채 Pod의 `args`로 CMD만 `9090`으로 교체했습니다.

```bash
kubectl apply -f 08-configuring-apps/command-env/pod-args-only.yaml
kubectl wait --for=condition=Ready pod/args-only \
  -n learning-command-args --timeout=60s
kubectl logs args-only -n learning-command-args
```

실제 로그는 이미지의 엔트리포인트와 환경변수는 유지되고 포트 인자만 바뀌었음을 보여 줍니다.

```pseudocode
entrypoint=/entrypoint.sh port=9090 image_only=image-default
```

### Kubernetes 확장과 셸 확장 결과

Pod의 `env` 정의 순서와 이미지 환경변수가 확장 결과에 미치는 영향을 확인했습니다.

```bash
kubectl apply -f 08-configuring-apps/command-env/pod-env-expansion.yaml
kubectl wait --for=condition=Ready pod/env-expansion \
  -n learning-command-args --timeout=60s
kubectl logs env-expansion -n learning-command-args
kubectl exec env-expansion -n learning-command-args -- \
  sh -c 'printenv UNKNOWN; printf "exit=%s\n" "$?"'
```

실제 출력에서 앞서 선언된 `EARLY`만 Kubernetes가 확장했습니다. 뒤에서 선언된 `LATE`와 이미지에만 있는 `IMAGE_ONLY`의 참조는 문자열로 남았습니다. 셸은 실행 시점의 실제 환경에서 `IMAGE_ONLY=image-default`를 읽었습니다. `UNKNOWN`은 컨테이너 환경에 존재하지 않으므로 `printenv`가 값 없이 종료 코드 1을 반환했습니다.

```pseudocode
MESSAGE=early=kiada, late=$(LATE), image=$(IMAGE_ONLY), escaped=$(EARLY)
shell sees IMAGE_ONLY=image-default
exit=1
```

### exec 전후 프로세스 트리

두 Pod에서 `ps -o pid,ppid,comm,args`를 실행한 결과는 §6의 실측과 같았습니다. exec가 없으면 `sh`가 PID 1이고 `sleep`은 PPID 1인 자식입니다. exec를 사용하면 셸이 교체돼 `sleep`이 PID 1이 되므로, 실행 프로그램이 종료 신호를 직접 받습니다.



## 8. 면접 대비

> command·args·env의 역할과 두 환경변수 확장 시점을 한 문장과 세 질문으로 회상합니다.

### 한 줄 정의

Kubernetes의 `command`와 `args`는 이미지의 ENTRYPOINT와 CMD 기본값을 실행 시점에 교체합니다. `env`는 각 컨테이너의 환경을 구성합니다.

### 자주 묻는 질문

#### Q1. command와 args는 Dockerfile의 무엇에 대응합니까?

`command`는 ENTRYPOINT를, `args`는 CMD를 교체합니다. 다만 "한쪽을 생략하면 그쪽 기본값이 온다"는 반쪽만 맞습니다. `command`를 생략하면 ENTRYPOINT가 오지만, `args`를 생략했을 때 CMD가 오는 것은 `command`도 함께 생략했을 때뿐입니다. `command`를 지정하면 이미지 CMD는 버려집니다.

#### Q2. $(NAME)과 $NAME은 무엇이 다릅니까?

`$(NAME)`은 kubelet이 컨테이너를 시작하기 전에 Pod 스펙의 환경을 기준으로 확장합니다. `$NAME`은 컨테이너 안의 셸이 명령 실행 시점에 실제 환경을 읽어 확장합니다.

#### Q3. sh -c로 JVM을 실행할 때 왜 exec를 붙입니까?

`exec`가 셸을 JVM으로 교체하면 JVM이 PID 1이 됩니다. Kubernetes의 종료 신호가 JVM에 직접 도착하므로 Spring의 graceful shutdown과 종료 훅이 실행될 수 있습니다.



[^cmd-args]: [Define a Command and Arguments for a Container](https://kubernetes.io/docs/tasks/inject-data-application/define-command-argument-container/)는 한 방향만 적습니다 — "If you define args, but do not define a command, the default command is used with your new arguments." 반대 방향은 서술이 없어 kind v1.35 실측으로 확인했습니다.
