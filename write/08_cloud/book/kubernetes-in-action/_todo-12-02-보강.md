## 왜 보강하나

Phase 1 결과, 12-01과 이어지면서 **다른 결의 문제**가 나왔다. 12-01이 "결론은 맞고 근거가 다른 모델에서 나옴"이었다면, 12-02는 **묻는 층을 잘못 짚는 패턴**이다.

- annotation 자리에 **ConfigMap**을 두 번 (Q3-b, Q2-b)
- 소유권(누가 처리하나) 문제에 **`rules`**(라우팅)를 (Q5-a)
- 어피니티 층에 **`externalTrafficPolicy`** 를 (Q4 후속 질문)
- 컨트롤러 여럿을 "Ingress 1개를 나눠 처리"로 (Q5 후속 질문)

반대로 **L4/L7 축은 세 번 다 정확히 인출**했다(Q1 termination 논리, Q4 쿠키 가능 이유, NAT 뒤 구분 불가). 그 축은 굳었고 남은 과제는 **"이 결정은 어느 층·어느 오브젝트의 일인가"** 다. 현재 문서는 각 사실을 한 문장씩 적어 두었으나 *층의 경계*를 그려 주지 않아 학습자가 인접 개념으로 메운다.

## 보강 항목 (10개)

### ⭐ 1. §1 — termination vs passthrough 대비 (시각화)

현재 39행 SVG는 **termination만** 그리고 passthrough는 69행 산문 한 단락뿐이라 둘의 대비가 없다. 학습자는 "중단도 동일 지점 아닌가요?"라며 **두 방식이 같은 지점에서 암호를 푼다**고 답했다.

3단으로 대비한다 — ① 암호가 풀리는 지점(프록시 vs 파드) ② 인증서를 쥔 주체 ③ **프록시가 볼 수 있는 것**.

```
[termination]  클라이언트 ══TLS══> 프록시 ──평문 HTTP──> 파드
                                    ↑ 여기서 푼다 (인증서: 프록시)
[passthrough]  클라이언트 ══════════TLS═══════════════> 파드
                                    ↑ 못 푼다 (인증서: 파드)
```

⛔ 용어 교정도 함께 — 암호를 푸는 것은 **컨트롤러가 아니라 프록시**다(학습자가 "인그레스 컨트롤러 지점"이라 답했다). 12-01에서 갈라 둔 컨트롤러(설정 생성) / 프록시(트래픽 처리) 구분을 재확인한다.

### ⭐ 2. §1 — "L7 라우팅 포기"가 무슨 뜻인가 (시각화 · 학습자가 직접 물음)

학습자 질문: "흘려보내는 게 L7 라우팅 포기라는 게 무슨 말인가?" 현재 문서에는 이 설명이 **아예 없다**(69행은 "비표준이라 termination에 집중하는 편이 낫다"로만 끝난다).

TLS가 암호화하는 대상이 바로 프록시가 읽어야 할 그 부분임을 보인다.

```
[termination]  복호화 후 →  GET /quote HTTP/1.1 · Host: api.example.com  → 경로 분기 ✅
[passthrough]  프록시가 봄 →  17 03 03 04 a1 9f 2c ... (암호문)          → 경로 알 수 없음 ❌
```

| | termination | passthrough |
|---|---|---|
| 호스트 분기 | 가능 (Host 헤더) | 가능 (**SNI** — 핸드셰이크는 암호화 전이라 평문) |
| **경로 분기** (`pathType`) | 가능 | **불가능** |
| 헤더 조작·재작성·쿠키 어피니티 | 가능 | 불가능 |

핵심 프레임 — **passthrough는 L7 중간자의 눈을 가리는 것**이라 12-01 §6에서 정리한 "Ingress를 쓰는 이유"와 상충한다. 그래서 표준이 되지 못했다. 12-01 §4의 `pathType` 매칭이 작동할 수 없다는 교차 참조를 건다.

### 3. §1 — "표준"의 의미 + 두 방식의 선택 기준

학습자는 "표준? 그런 게 있는가?"라고 되물었다. 문서가 "표준"을 정의 없이 쓰고 있다.

- **표준 = 쿠버네티스 API에 정식 필드로 있는가.** termination은 `spec.tls`가 정식 필드라 어느 컨트롤러든 같은 YAML이 통한다. passthrough는 필드가 없어 annotation + 컨트롤러 플래그(`--enable-ssl-passthrough`)에 의존하고, 컨트롤러를 바꾸면 통째로 안 통한다.
- 학습자 질문 "2026년 기준 어떤 걸 주로 쓰는가"에 답하는 선택 기준 표:

| | termination | passthrough |
|---|---|---|
| 장점 | L7 기능 전부 · 인증서를 인프라에 모아 관리(cert-manager 자동 갱신) · 파드는 평문만 | **종단 간 암호화**(프록시조차 못 봄) · mTLS를 앱이 직접 검증 |
| 단점 | 프록시↔파드 구간 평문 · 인증서 유출 시 프록시가 단일 실패점 | 경로 라우팅 불가 · 인증서를 파드마다 배포·갱신 · 컨트롤러 의존 |
| 쓰는 곳 | 일반 웹·API | 규제 산업(금융·의료) 종단 간 암호화, 앱이 mTLS 검증 |

- **termination이 사실상 기본이 된 이유 둘** — ① cert-manager + Let's Encrypt로 발급·갱신이 자동화됨 ② "프록시↔파드 평문" 문제는 passthrough가 아니라 **서비스 메시**(사이드카 mTLS)로 푸는 흐름이 됐다 → 13-03 mesh 교차 참조.
- ⚠️ 시점 단서를 달 것 — "2026년 기준" 판단은 근거 범위를 명시하고, 재확인이 필요하면 공식 문서를 조회하도록 안내.

### ⭐ 4. §1 — 인증서·host 불일치의 실패 양상 (시각화 · 학습자가 직접 요청)

학습자는 (c)를 "못 쓰는 거 아니야?"로 방향만 맞혔다. 현재 65행은 "`tls.hosts`는 인증서 이름과 반드시 일치해야 합니다"라는 **당위만** 적고 어기면 어떻게 되는지가 없다.

핵심은 **조용히 지나가고 접속할 때 터진다**는 것.

```
kubectl apply         → 성공 (쿠버네티스는 인증서 내용과 host 규칙을 검증하지 않음)
kubectl get ingress   → 정상 표시, 로그에도 에러 없음
프록시 설정 반영       → 정상
클라이언트 접속        → 브라우저가 거부: ERR_CERT_COMMON_NAME_INVALID
```

- **검증 주체가 서버가 아니라 클라이언트**다. 서버는 잘못된 인증서라도 그냥 내밀고, 브라우저가 CN·SAN과 접속 도메인을 비교해 끊는다. 그래서 **배포 파이프라인은 초록불인데 사용자만 막힌다.**
- 와일드카드 인증서에도 12-01 §5의 **요소 단위 규칙**이 그대로 적용된다 — `*.example.com`은 `api.example.com`을 덮지만 `foo.api.example.com`은 못 덮는다. 같은 원리가 **DNS 매칭 · Ingress host 매칭 · 인증서 SAN 검증** 셋에 공통이라는 교차 참조가 이 편의 값이다.

### ⭐ 5. §2 — 왜 spec 필드로 못 넣는가 (구체적 근거)

현재 79행은 "모든 구현의 모든 설정을 스키마에 담기란 사실상 불가능"이라는 **추상어뿐**이다. 학습자는 이유를 "Ingress에서 하기에는 무거운 작업이기 때문"으로 오답했다 — 무게 문제가 아니라 **의미를 API가 보장할 수 없는** 문제다.

실물 예로 보인다.

- `rateLimit: 100` — 단위가 초당인지 분당인지, 기준이 IP인지 사용자인지, 초과 시 429인지 503인지가 구현마다 다르고 **AWS ALB엔 개념 자체가 없다.**
- `rewrite` — Nginx는 정규식 캡처 그룹, GKE는 다른 문법. 같은 필드 값이 컨트롤러를 바꾸면 안 통한다.

**필드를 만들면 그 의미를 API가 보장해야 하는데, 구현이 제각각이면 보장할 수 없다.** 그래서 최소 공통분모(라우팅·TLS·클래스 지정)만 spec에 두었다. 12-01 §4의 `pathType: ImplementationSpecific`이 같은 결 — 표준화 불가를 **명시적으로 인정한** 장치라는 교차 참조.

### 6. §2 — annotation vs ConfigMap 층 구분 (오답 2회)

학습자가 annotation 자리에 **ConfigMap을 두 번** 답했다(Q2-b, Q3-b). 문서에 이 구분이 없다.

| | 담는 것 | 읽는 주체 | 전달 경로 |
|---|---|---|---|
| **annotation** | 오브젝트에 붙은 메타데이터 (Ingress별 프록시 설정) | 컨트롤러 | API에서 읽음 |
| **ConfigMap** | 앱이 읽는 설정 | 앱 | 볼륨·환경변수로 주입 |

- 07-03(annotation)에서 다룬 "스키마에 없는 부가 정보를 붙이는 수단"이 바로 이것이라는 연결.
- 다만 **Nginx 컨트롤러에 ConfigMap도 쓰인다** — 컨트롤러 전역 설정(워커 수·기본 타임아웃)은 컨트롤러의 ConfigMap. 즉 **Ingress별 = annotation / 컨트롤러 전역 = ConfigMap**으로 층이 갈린다. 학습자 답이 무관한 게 아니라 층을 잘못 짚은 것이므로 이 대비가 교정에 효과적이다.
- ⚠️ **접두사가 소유자를 표시하고 다른 컨트롤러는 조용히 무시한다** — 컨트롤러를 갈아타면 annotation이 아무 일도 하지 않는데 **에러가 나지 않아 더 위험**하다. 93행이 "다른 구현은 무시함을 나타냅니다"까지만 적어 위험성이 안 드러난다.

### ⭐ 7. §2 — IP 기준 어피니티의 실패 사례 (시각화)

현재 93행은 쿠키가 **어떻게** 동작하는지만 적고 *왜 IP보다 나은지*가 없다. 11-01의 L4 한계 서술과 이어지지 않는다. (학습자는 이 축을 자력으로 맞혔으나, 문서에 근거가 없어 다음 독자가 같은 추론을 못 한다.)

```
[IP 기준]   사무실 100명 → 모두 203.0.113.7 → 파드 A 하나로 전원 고정 → A 과부하, B·C 유휴
[쿠키 기준] 사무실 100명 → 각자 다른 쿠키    → A·B·C 고르게 + 개인별로는 같은 파드 유지
```

실패가 **양방향**임을 보인다.
- NAT 뒤 여럿을 **한 명으로** 본다 → 어피니티와 분산이 충돌(어피니티를 켜는 대가로 분산을 잃음)
- 모바일 Wi-Fi↔LTE 전환으로 IP가 바뀌면 한 명을 **여럿으로** 본다 → 세션 끊김

프레임 한 줄: **IP는 사용자의 신원이 아니라 경로의 속성**이라 어피니티 키로 부적합하다.

### 8. §2 — 어피니티와 externalTrafficPolicy의 층 구분 (학습자가 직접 물음)

학습자 질문: "세션 어피니티에 대해서 LOCAL, CLUSTER 정책 상관없이 L7을 쓸 수 있단 건가?" 층이 섞인 질문이므로 문서가 경계를 그려야 한다.

```
클라이언트 → LB → 프록시 파드 → (파드 IP 직접) → 백엔드 파드
             ↑ Service 소관        ↑ 프록시 소관 (Service를 거치지 않음)
```

- 12-01에서 확인한 대로 **프록시는 cluster IP를 건너뛰므로**, 프록시→백엔드 구간에는 Service가 개입하지 않고 `externalTrafficPolicy`·`sessionAffinity`가 적용되지 않는다. "정책과 무관하게 L7 어피니티를 쓴다"는 맞지만 이유는 **애초에 다른 구간의 일이라 만나지 않아서**다.
- ⚠️ **단 한 곳에서 만난다** — LB→프록시 구간에 `Cluster` 정책이면 SNAT이 걸려 **프록시가 보는 클라이언트 IP가 노드 IP로 오염된다**(11-02 §3). 그러면 IP 기반 어피니티가 무의미해지고 접근 로그도 오염되므로, 실무에서 컨트롤러의 LB Service에 `externalTrafficPolicy: Local`을 거는 것이 관행이다. 이 교차 지점이 이 항목의 값.

### ⭐ 9. §3 — 왜 컨트롤러를 직접 적지 않고 IngressClass를 거치는가

학습자는 (b)에서 "컨트롤러 이름을 적어야 할 것 같다"고 답했다. 현재 127행은 관계만 서술하고 **간접 참조의 이유**가 없다.

```
Ingress.spec.ingressClassName: "alb-public"
        ↓
IngressClass "alb-public"
  spec.controller: ingress.k8s.aws/alb        ← 실제 컨트롤러
  spec.parameters: → IngressClassParams (scheme: internet-facing)
```

- 이유는 **같은 컨트롤러를 다른 파라미터로 여러 번 쓰기** 위해서다. ALB 하나로 `alb-public`(internet-facing) / `alb-internal`(internal) 두 클래스를 만드는 예. 컨트롤러 이름을 직접 적는 구조면 이 구분이 불가능하다.
- **관심사 분리** — 앱 개발자는 `alb-public`이라는 이름만 알고, 파라미터는 인프라팀이 IngressClass에서 관리한다.
- `kubernetes.io/ingress.class` **annotation → 정식 필드로 승격**된 사례라는 것도 명시. 항목 5의 "표준화 못 하면 annotation으로"와 **반대 방향**이어서 대비가 학습 값이 크다(모든 구현에 공통으로 필요하다고 판단되면 필드로 올라온다).

### ⭐ 10. §3 — 개수 관계 + 클래스 미지정 시 분기 (오해 2건)

학습자가 두 가지를 오해했다. ① "Ingress 1개를 컨트롤러 2개가 나눠 처리하는 것"으로 봄 ② 클래스를 안 적으면 "2개 중 아무거나 로드밸런싱"으로 봄. 현재 136행은 "컨트롤러가 여럿이면 IngressClass도 여럿"까지만 적어 오해 여지를 남긴다.

**개수 관계표**

| 개수 | 무엇 |
|---|---|
| 컨트롤러 여럿 | 한 클러스터에 공존 가능 (Nginx + ALB) |
| IngressClass 여럿 | 컨트롤러마다 하나 이상. 같은 컨트롤러 + 다른 파라미터도 가능 |
| Ingress 여럿 | 각각 **클래스 하나**를 지목 |
| **Ingress 1개를 처리하는 컨트롤러** | **항상 하나** |

컨트롤러 여럿의 의미는 **트래픽을 나눠 갖는 것이 아니라 Ingress 집합(일감)을 나눠 갖는 것**이다. 사내 관리자 페이지 → `ingressClassName: nginx`, 외부 공개 API → `ingressClassName: alb-public` 두 Ingress 예시를 넣으면 바로 잡힌다.

**미지정 시 분기 도식** (로드밸런싱이 아님)

```
ingressClassName 생략
  ├─ 기본 IngressClass 있음 → 그 클래스가 적용
  └─ 기본 없음 → 아무 컨트롤러도 처리하지 않음 → ADDRESS 영원히 비어 있음
```

- 12-01 §3의 "주소가 안 뜨면 컨트롤러 실행 여부와 `ingressClassName`을 확인" 증상과 교차 참조 — 원인이 바로 이것이다.
- ⚠️ **기본 클래스를 둘 이상 두면** 여러 컨트롤러가 같은 Ingress를 각자 처리해 프록시·LB가 **중복 생성되고 비용이 이중**이다. 학습자가 상상한 "둘이 동시에 달라붙는" 상황이 실제로 벌어지는 유일한 경우이므로 함정으로 명시.

## 우선순위

⭐는 7개(1·2·4·5·7·9·10)이고 그중 **시각화가 필요한 것은 6개**(1·2·4·7·9·10)다. 5는 산문 우선(`rateLimit`·`rewrite` 논거)이나 중요도가 높아 ⭐를 달았다. **층 경계**를 그리는 것이 이 편 보강의 축이므로 묶음으로 본다.

1. **TLS 층** (1·2·3·4) — 암호가 풀리는 지점 → 그래서 프록시가 무엇을 볼 수 있나(2가 핵심) → 표준의 의미와 선택 기준 → 어기면 어떻게 실패하나. **2를 1번으로** 두는 이유: 학습자가 직접 물었고 문서에 아예 없으며, 12-01 §1의 L4/L7 축과 바로 이어져 SVG를 짝으로 만들 수 있다.
2. **설정 층** (5·6·8) — 왜 필드가 아닌가 → annotation vs ConfigMap → 어피니티와 정책은 다른 구간. **6이 오답 2회 지점**이라 우선.
3. **클래스 층** (9·10) — 왜 간접 참조인가 → 개수 관계와 미지정 분기. 둘이 같은 절(§3)이고 오해 2건이 여기 몰려 있어 함께 설계한다.
4. 7 (IP 어피니티 실패) — 학습자는 자력 통과했으나 문서에 근거가 없어 다음 독자를 위해 필요.

**공통 축**: 이 편의 오답은 전부 "**어느 층·어느 오브젝트의 일인가**"에서 나왔다(ConfigMap↔annotation, rules↔ingressClassName, 정책↔어피니티, 컨트롤러 개수↔Ingress 개수). 각 항목의 시각화가 **경계선을 명시적으로 그리는** 형태여야 효과가 있다 — 무엇이 무엇의 소관인지 화살표와 구획으로.
