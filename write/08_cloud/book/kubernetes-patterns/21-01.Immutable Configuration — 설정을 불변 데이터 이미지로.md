# Immutable Configuration — 설정을 불변 데이터 이미지로
---
> 『Kubernetes Patterns』 21장 정독. **Immutable Configuration**은 설정 데이터를 불변으로 만들어 앱 설정이 늘 알려진·기록된 상태에 있게 하는 패턴입니다. 불변·버전 관리되는 설정을 쓸 뿐 아니라, 환경변수·ConfigMap에 저장되는 설정의 크기 한계(1MB)도 넘습니다.



## 핵심 요약

> 환경변수(19장)는 단순하지만 개수가 임계치를 넘으면 관리가 어렵습니다. Configuration Resource(20장)로 어느 정도 다룰 수 있고 1.21+는 불변 선언도 되지만 ConfigMap은 여전히 크기 제한이 있어 큰 설정 데이터(ML 사전학습 모델 등)에는 부적합합니다. 여기서 불변성은 앱 시작 후 설정을 못 바꿔 늘 잘 정의된 상태를 보장하고 버전 관리·변경 통제를 가능케 함을 뜻합니다.

가장 단순하고 선호되는 선택은 **immutable ConfigMap/Secret**입니다(20장). 설정이 ConfigMap에 담기고 유지가 쉬우면 이것이 1순위입니다. 하지만 실제로는 설정 데이터가 빠르게 커지고 YAML 안에 XML·YAML을 중첩해야 할 때 들여쓰기 지옥이 되며 수십·수백 항목 관리가 악몽이 되고 무엇보다 1MB 백엔드 한계로 큰 데이터셋은 불가능합니다.

이때 환경별 설정을 하나의 **수동 데이터 이미지**에 담아 일반 컨테이너 이미지처럼 배포하고 런타임에 앱과 링크해 설정을 추출합니다. Docker에서는 `VOLUME` 지시어로 config 컨테이너 디렉토리를 공유하고 `--volumes-from`으로 앱에 링크합니다. Kubernetes는 컨테이너 볼륨을 지원하지 않으므로 **Init Container**(15장)로 빈 공유 볼륨(emptyDir)에 설정을 복사합니다(busybox 베이스에 `cp` ENTRYPOINT). 개발→운영 전환은 init 이미지만 교체합니다. 장점 — 봉인·버전 관리·레지스트리 배포·임의 크기. 단점 — 복잡성 증가, 보안 미해결, 이미지 볼륨 미지원, 환경마다 다른 Deployment 관리입니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

- 불변 설정의 의미(시작 후 변경 불가·버전 관리·변경 통제)를 설명한다.
- immutable ConfigMap이 1순위이고 데이터 컨테이너는 그것이 부적합할 때만임을 안다.
- Docker 볼륨 방식과 Kubernetes init container 복사 방식의 차이를 구분한다.
- 데이터 이미지의 장점 4가지와 단점 4가지를 설명한다.
- 이 패턴과 Configuration Template(22장)의 경계를 안다.



## 본문 정리

### 문제 — 크고 불변인 설정

환경변수는 개수가 임계치를 넘으면 관리가 어렵습니다. Configuration Resource로 어느 정도 다룰 수 있고 1.21+는 불변 선언도 되지만 ConfigMap은 크기 제한이 있어 큰 설정 데이터(ML 사전학습 모델 등)에는 불변으로 표시해도 부적합합니다. 불변성은 앱 시작 후 설정을 못 바꿔 늘 잘 정의된 상태를 보장하는 것이고 더해 불변 설정을 버전 관리하고 변경 통제 프로세스를 따를 수 있음을 뜻합니다.

### 해법 — 1순위는 immutable ConfigMap

여러 선택지가 있지만 가장 단순하고 선호되는 것은 선언에서 immutable로 표시한 ConfigMap·Secret입니다. 설정이 ConfigMap에 담기고 유지가 합리적으로 쉬우면 첫 선택이어야 합니다. 하지만 현실에서 설정 데이터는 빠르게 커집니다. WildFly 애플리케이션 서버 설정은 ConfigMap에 들어갈 수 있어도 꽤 큽니다. YAML 안에 XML·YAML을 중첩해야 하면(설정 내용도 YAML인 경우) 정말 지저분해집니다 — 에디터 지원이 제한적이라 들여쓰기에 극도로 조심해야 하고 그래도 여러 번 망칩니다. 수십·수백 항목을 한 ConfigMap에 유지하는 것도 악몽입니다. 무엇보다 ML 사전학습 모델 같은 큰 데이터셋은 1MB 백엔드 제한 때문에 ConfigMap으로 불가능합니다.

이를 다루려면 환경별 설정 데이터를 하나의 **수동(passive) 데이터 이미지**에 담아 일반 컨테이너 이미지처럼 배포합니다. 런타임에 앱과 데이터 이미지를 링크해 앱이 설정을 추출합니다. 이 방식은 환경마다 다른 설정 이미지를 만들기 쉽고 다른 이미지처럼 버전을 매길 수 있습니다. 데이터 이미지 만들기는 데이터만 담은 단순 컨테이너라 자명하고 도전은 시작 시 **링크 단계**입니다.

### 방법 A — Docker 볼륨

Docker에서는 컨테이너가 자기 데이터를 볼륨으로 노출할 수 있습니다. Dockerfile의 `VOLUME` 지시어로 나중에 공유할 디렉토리를 지정하면, 시작 시 그 디렉토리 내용이 공유 디렉토리로 복사됩니다. 개발용 설정 이미지는 `FROM scratch`(OS 파일 없는 빈 이미지)에 프로퍼티를 `/config`로 추가하고 `VOLUME /config`로 만듭니다. 그 뒤 `docker run --volumes-from config-dev 앱이미지`로 앱 컨테이너를 config 컨테이너에 링크합니다. 개발→운영 전환은 시작 명령만 바꾸면 됩니다 — 앱 이미지 자체는 안 바꾸고 운영 config 컨테이너에 볼륨 링크만 바꿉니다.

### 방법 B — Kubernetes Init Container

Kubernetes에는 현재 **컨테이너 볼륨 지원이 없습니다.** 컨테이너는 (외부) 볼륨을 공유할 수 있지만 컨테이너 안 디렉토리를 직접 공유하지는 못합니다. 그래서 Init Container 패턴(15장)으로 시작 시 빈 공유 볼륨을 초기화합니다.

Docker 예에서는 `scratch`를 베이스로 썼지만 init container는 설정을 공유 볼륨에 복사할 도구가 필요하므로 `busybox`를 씁니다(작지만 `cp`를 쓸 수 있음). 설정 이미지는 `FROM busybox`에 프로퍼티를 추가하고 `ENTRYPOINT sh -c "cp /config-src/* $1"`로, 인자로 받은 디렉토리에 복사합니다. Deployment의 `initContainers`에서 이 이미지를 참조하고 `/config` 인자를 줍니다.

Pod 템플릿에는 볼륨 하나와 컨테이너 둘이 있습니다 — `config-directory`는 `emptyDir` 타입이라 노드에 빈 디렉토리로 생성되고 init container는 만든 이미지로 실행되어 그 내용을 `/config`(= `config-directory` 마운트)에 복사하며 앱 컨테이너는 같은 볼륨을 마운트해 복사된 설정을 읽습니다. 개발→운영 전환은 init container 이미지만 교체하면 됩니다(YAML 수정 또는 `kubectl` 갱신).

환경마다 리소스 서술자를 편집하는 것은 이상적이지 않습니다. OpenShift라면 **OpenShift Template**로 리소스 서술자를 파라미터화(`${CONFIG_IMAGE}`)해 하나의 템플릿에서 환경별 서술자를 만들 수 있습니다 — `oc new-app demo -p CONFIG_IMAGE=k8spatterns/config-prod:1`처럼 인스턴스화합니다.

### 논의 — 장단점

데이터 컨테이너 방식은 다소 번거로우니, immutable ConfigMap·Secret이 부적합할 때만 씁니다.

**장점** — 환경별 설정이 컨테이너에 봉인되어 다른 이미지처럼 버전 관리됩니다. 레지스트리로 배포되어 클러스터 없이도 검사할 수 있습니다. 설정이 컨테이너 이미지처럼 불변이라 변경엔 버전 업데이트와 새 이미지가 필요합니다. 환경변수·ConfigMap에 넣기엔 너무 복잡한 큰 설정(임의 크기)을 담을 수 있습니다.

**단점** — 추가 이미지를 빌드·배포해야 해 복잡성이 높습니다. 민감 설정 데이터의 보안 문제는 해결하지 못합니다. Kubernetes 워크로드에 이미지 볼륨 지원이 없어(2023 기준 실험적 CSI만) init container에서 복사하는 오버헤드가 있습니다. Kubernetes에서는 추가 init container 처리가 필요해 환경마다 다른 Deployment 오브젝트를 관리해야 합니다. 이런 개입이 정말 필요한지 신중히 평가해야 합니다. 환경마다 조금만 다른 큰 설정 파일은 다음 장 Configuration Template이 더 나은 대안입니다.



## 심화 학습

### immutable ConfigMap이 1순위인 이유 — 복잡성 예산 (실무 판단)

이 장의 가장 중요한 메시지는 화려한 데이터 컨테이너 기법이 아니라 **"immutable ConfigMap이 1순위, 데이터 컨테이너는 그것이 부적합할 때만"** 이라는 순서입니다. 데이터 컨테이너는 추가 이미지 빌드·레지스트리 배포·환경별 Deployment 관리라는 상당한 운영 복잡성을 들여옵니다. 그 비용은 설정이 정말 클 때(ML 모델처럼 수백 MB) 또는 설정을 이미지처럼 엄격히 버전 관리해야 할 때만 정당화됩니다.

Spring Boot 앱의 일반적 설정(수십 KB 프로퍼티)은 거의 언제나 immutable ConfigMap으로 충분합니다. 데이터 컨테이너를 꺼내는 순간은 "설정"이 아니라 "설정처럼 다루고 싶은 큰 에셋"(사전학습 모델, 대용량 룩업 테이블, 방대한 서버 설정 트리)일 때입니다. 이 판단선을 넘기 전에 정말 ConfigMap으로 안 되는지 먼저 확인하는 것이 이 장의 실천적 결론입니다.

> 참고: 2023년 이후 [이미지 볼륨(Image Volume)](https://kubernetes.io/docs/tasks/configure-pod-container/image-volumes/)이 1.31에서 알파, 이후 베타로 진행되어 OCI 이미지를 볼륨으로 직접 마운트하는 길이 열렸습니다(책이 "future에 가능하길 바란다"고 한 기능). 이는 init container 복사 오버헤드를 없애는 방향입니다(책 범위 밖 최신 동향).

### 불변성의 스펙트럼 — 19장부터 21장까지

19~21장은 "불변성"을 점점 강하게 만드는 스펙트럼입니다. **19장 EnvVar**의 불변성은 프로세스 시작 후 env를 못 바꾸는 수동적 불변입니다. **20장 immutable ConfigMap**은 리소스 자체를 갱신 못 하게 막는 선언적 불변입니다. **21장 데이터 이미지**는 설정을 컨테이너 이미지로 봉인해 버전·다이제스트로 고정하는 가장 강한 불변입니다. 뒤로 갈수록 재현성·버전 추적이 강해지지만 복잡성도 함께 커집니다. 어느 수준이 맞는지는 설정의 크기·변경 빈도·감사 요구에 달렸습니다.



## 실무 적용

- **먼저 immutable ConfigMap/Secret으로 되는지 확인합니다.** 데이터 컨테이너는 그것이 부적합한 큰 설정일 때만 씁니다.
- **큰 에셋(ML 모델·대용량 테이블)만 데이터 이미지로 봉인합니다.** 일반 프로퍼티 설정은 ConfigMap으로 충분합니다.
- **Kubernetes에서는 init container로 emptyDir에 복사합니다.** busybox 베이스에 `cp` ENTRYPOINT를 두고 앱 컨테이너가 그 볼륨을 읽습니다.
- **환경 전환은 init 이미지 교체로 합니다.** 앱 이미지·Deployment 로직은 그대로 두고 config 이미지만 바꿉니다.
- **환경별 서술자 편집이 번거로우면 파라미터화합니다.** OpenShift Template이나 Helm/Kustomize로 config 이미지를 파라미터로 뺍니다.
- **보안은 별도로 다룹니다.** 데이터 이미지는 민감 데이터 보안을 해결하지 않으니 25장 Secure Configuration을 병행합니다.

## 면접 관점

- **Immutable Configuration이 필요한 이유는?** — 설정을 앱 시작 후 못 바꿔 늘 알려진 상태를 보장하고 버전 관리·변경 통제를 가능케 하며 ConfigMap의 1MB 크기 한계를 넘기 위해서입니다.
- **1순위 선택은 무엇입니까?** — immutable ConfigMap/Secret입니다. 설정이 ConfigMap에 담기고 유지가 쉬우면 그것을 쓰고 데이터 컨테이너는 그것이 부적합한 큰 설정일 때만 씁니다.
- **Kubernetes에서 데이터 컨테이너를 어떻게 링크합니까?** — Kubernetes는 컨테이너 볼륨을 지원하지 않으므로 init container로 emptyDir 공유 볼륨에 설정을 복사합니다. busybox 베이스에 cp ENTRYPOINT를 두고 앱 컨테이너가 그 볼륨을 마운트합니다.
- **데이터 이미지의 단점은?** — 추가 이미지 빌드·배포로 복잡성이 높고 민감 데이터 보안을 해결하지 않으며 이미지 볼륨 미지원으로 복사 오버헤드가 있고 환경마다 다른 Deployment를 관리해야 합니다.
- **이 패턴과 Configuration Template의 차이는?** — 데이터 이미지는 설정 전체를 이미지로 봉인합니다. Configuration Template은 환경마다 조금만 다른 큰 설정을, 차이 값만 ConfigMap에 두고 템플릿으로 생성해 중복을 없앱니다.
