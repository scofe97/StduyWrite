# 28장 · Operator — CRD로 도메인 지식을 자동화하기

> Controller 패턴을 CRD로 확장한 것입니다. 특정 애플리케이션의 운영 지식을 알고리즘적·자동화된 형태로 캡슐화해, 보통 사람이 해야 할 운영 작업을 코드로 대신합니다.

![Operator 개요](./_assets/28-01.operator-crd.svg)



## 핵심 요약

> Operator는 CRD를 써서 운영 지식을 캡슐화하는 컨트롤러입니다. 한 문장으로, Operator = Controller + CRD입니다.

27장에서 커스텀 컨트롤러로 플랫폼을 확장하는 법을 봤지만 순수 컨트롤러는 Kubernetes 고유 리소스만 감시·관리할 수 있어 한계가 있습니다. 때로는 새로운 도메인 개념 자체를 플랫폼에 추가하고 싶습니다. 예를 들어 Prometheus를 모니터링 수단으로 쓰면서 다른 Kubernetes 리소스처럼 `Prometheus`라는 리소스로 모니터링 설정을 기술할 수 있다면 어떨까요.

이것이 CustomResourceDefinition(CRD)이 필요한 지점입니다. CRD는 Kubernetes API를 확장해 커스텀 리소스를 native 리소스처럼 다루게 합니다. 커스텀 리소스와 그것에 작동하는 컨트롤러가 합쳐지면 Operator 패턴이 됩니다. Jimmy Zelinskie의 정의가 이를 잘 압축합니다 — Operator는 Kubernetes와 또 다른 도메인 둘 다를 이해하는 컨트롤러로, 두 지식을 결합해 보통 두 도메인을 아는 인간 운영자가 해야 할 작업을 자동화합니다.



## 학습 목표

> 이 장을 읽고 나면 다음을 설명할 수 있어야 합니다.

- Operator가 Controller와 CRD의 결합이라는 점을 설명할 수 있습니다.
- CRD의 주요 정의 필드와 scale·status 서브리소스를 압니다.
- Installation CRD와 Application CRD를 구분할 수 있습니다.
- CRD 대신 ConfigMap을 쓸 때의 득실을 설명할 수 있습니다.
- Kubebuilder·Operator Framework·Metacontroller의 역할 차이를 압니다.



## 본문 정리

### CustomResourceDefinition — API를 확장하는 뼈대

CRD로 우리는 Kubernetes 플랫폼 위에서 도메인 개념을 관리할 수 있습니다. 커스텀 리소스는 다른 리소스처럼 Kubernetes API로 관리되고 결국 백엔드 저장소인 etcd에 저장됩니다. CRD 정의는 몇 가지 핵심 필드로 이루어집니다 — `group`(속한 API 그룹), `names`(kind와 plural 형태), `scope`(Namespaced 또는 Cluster-wide), `versions`(그중 정확히 하나가 저장 버전, 각각 served 여부 지정), 그리고 `schema`의 OpenAPI V3 스키마입니다. 스키마는 커스텀 리소스를 검증하게 해주며 단순한 경우 생략할 수 있지만 프로덕션급 CRD에는 설정 오류를 조기에 잡기 위해 제공하는 것이 좋습니다.

CRD는 두 가지 서브리소스를 가질 수 있습니다. **scale**은 replica 수를 어떻게 관리하는지 선언하는데, 이 서브리소스가 있어야 HorizontalPodAutoscaler(29장)와 함께 쓸 수 있습니다. **status**는 리소스의 status 필드만 갱신하는 별도 API 호출을 열어줍니다. spec에 선언된 상태와 다를 수 있는 실제 상태를 Operator가 반영하게 해주며 커스텀 리소스를 통째로 갱신할 때 status 섹션은 무시됩니다(표준 리소스와 동일).

커스텀 리소스만으로는 쓸모가 없습니다. 그 리소스에 의미를 주려면, 리소스의 lifecycle을 감시하며 그 안의 선언에 따라 작동하는 익숙한 컨트롤러가 필요합니다. 이 결합이 Operator입니다.

### CRD 분류 — Installation과 Application

Operator의 동작을 기준으로 CRD는 크게 둘로 나뉩니다. **Installation CRD**는 Kubernetes 플랫폼에 애플리케이션을 설치·운영하기 위한 것으로, Prometheus 자체를 설치·관리하는 Prometheus CRD가 전형입니다. **Application CRD**는 애플리케이션 고유의 도메인 개념을 표현합니다. 예를 들어 Prometheus Operator가 쓰는 `ServiceMonitor` CRD는 스크랩할 특정 Kubernetes Service를 등록하는 데 쓰입니다. 다만 이 두 범주의 경계는 흐릿해서, 하나의 Operator가 여러 종류의 CRD에 작동할 수 있습니다.

### 확장 스펙트럼 — ConfigMap, CRD, API Aggregation

CRD가 늘 정답은 아닙니다. 기본 Kubernetes 리소스로는 부족하지만 CRD 생성이 여의치 않은 상황에서는 **ConfigMap**이 훌륭한 중간 지점입니다. ConfigMap의 이점은 CRD 등록에 필요한 cluster-admin 권한이 없어도 된다는 것으로, OpenShift Online 같은 공개 클러스터에서는 CRD 등록 자체가 불가능할 수 있습니다. 다만 ConfigMap을 쓰면 `kubectl get` 같은 도구 지원, API 서버 수준의 검증, API 버전 관리를 잃고 status 필드 모델링의 자유도 없으며 CRD처럼 kind별로 세밀하게 조정하는 RBAC(26장)도 불가능합니다(한 namespace의 모든 ConfigMap이 같은 권한을 공유하기 때문입니다).

더 고급 확장은 **API Aggregation**입니다. Kubernetes가 관리하는 CRD로 문제 도메인을 표현하기 부족할 때, `APIService` 리소스로 자체 구현한 커스텀 API 서버를 새 URL 경로로 추가할 수 있습니다. 이 경우 Kubernetes가 리소스를 완전히 관리하는 CRD와 달리, 요청 처리와 영속화를 커스텀 Service가 직접 맡습니다. 자유도는 최대지만 구현할 로직도 훨씬 많아지므로, 전형적인 use case에는 CRD를 다루는 Operator로 충분합니다.

### 개발 프레임워크 셋

Operator 개발을 돕는 주요 프로젝트는 셋입니다.

**Kubebuilder**는 SIG API Machinery의 프로젝트로, CRD로 Kubernetes API를 만드는 프레임워크이자 라이브러리입니다. Go 기반 Operator 생성에 초점을 두고 고수준 추상화와 프로젝트 스캐폴딩을 제공하며 문서가 뛰어납니다. 다른 프로젝트가 이를 라이브러리로 소비할 수 있습니다.

**Operator Framework**는 CNCF 프로젝트로 여러 하위 컴포넌트를 가집니다. Operator SDK는 클러스터 접근용 고수준 API와 스캐폴딩을 제공하고 Operator Lifecycle Manager(OLM)는 Operator와 CRD의 릴리스·업데이트를 관리하며 Operator Hub는 커뮤니티가 만든 Operator를 공유하는 카탈로그입니다. 흥미로운 역사가 있습니다 — 1판에서 저자들은 Kubebuilder와 Operator SDK가 언젠가 병합될 거라 추측했는데, 실제로는 겹치는 부분을 Kubebuilder로 옮기고 Operator SDK가 Kubebuilder를 의존성으로 쓰는 방식으로 정리됐습니다. 2023년 기준 SDK는 Ansible playbook, Helm Chart, Quarkus 런타임 기반 Java Operator를 위한 플러그인을 제공합니다.

**Metacontroller**는 나머지 둘과 사뭇 다릅니다. 커스텀 컨트롤러 작성의 공통 부분을 API로 캡슐화해 Kubernetes를 확장하며 웹훅으로 컨트롤러 로직을 위임합니다. 우리는 비즈니스 로직만 담긴 함수를 제공하고 Metacontroller가 Kubernetes API 상호작용과 조정 루프를 대신 돌린 뒤 웹훅으로 우리 함수를 호출합니다. 이 위임 덕에 HTTP와 JSON을 이해하는 어떤 언어로든, Kubernetes 클라이언트 라이브러리 의존 없이 함수를 쓸 수 있습니다.



## 심화 학습

### Spring/Java로 Operator를 — Strimzi와 Java Operator SDK

Java 진영에도 성숙한 Operator 사례가 있습니다. 책이 꼽는 대표는 [Strimzi Operator](https://strimzi.io/)로, Apache Kafka 같은 복잡한 메시징 시스템을 Kubernetes에서 관리하는 Java 기반 Operator입니다. 실무에서 Kafka를 운영해 본 개발자라면, 브로커 롤링 업데이트·토픽 관리·인증 설정 같은 손 많이 가는 작업이 얼마나 번거로운지 알 것입니다. Strimzi는 그 운영 지식을 CRD(`Kafka`, `KafkaTopic`, `KafkaUser` 등)와 컨트롤러로 캡슐화해, 사람이 하던 절차를 선언으로 바꿉니다.

Spring 개발자가 직접 Operator를 만든다면 Operator SDK의 [Java Operator Plugin](https://github.com/operator-framework/java-operator-sdk)이 출발점입니다. Quarkus 런타임 기반이라 Spring과는 스택이 다르지만 CRD를 정의하고 reconciler를 구현하는 흐름은 27장의 조정 루프 그대로입니다. 여기서 26장 Access Control이 다시 등장합니다 — Operator가 커스텀 리소스를 관리하려면 적절한 권한을 가진 ServiceAccount를 Role/RoleBinding으로 붙여줘야 합니다. 책의 예시에서도 `ConfigWatcher` CRD에 대한 모든 API 작업을 허용하는 Role을 정의해 Operator의 ServiceAccount에 연결합니다.

### 언제 Operator를 쓰고 언제 쓰지 말아야 하나

Operator는 은탄환이 아닙니다. 책은 사용 전에 use case가 Kubernetes 패러다임에 맞는지 신중히 볼 것을 권합니다. 많은 경우 표준 리소스로 작동하는 순수 컨트롤러로 충분하고 이 편이 CRD 등록에 필요한 cluster-admin 권한이 없어도 된다는 이점이 있습니다(대신 보안·검증에서는 한계가 있습니다). Operator가 잘 맞는 것은 선언적 Kubernetes 방식에 어울리는 커스텀 도메인 로직을 모델링할 때입니다. 구체적으로는 kubectl 같은 기존 도구와 긴밀히 통합하고 싶을 때, greenfield 프로젝트라 처음부터 설계할 수 있을 때, 그리고 리소스 경로·API 그룹·API 버전·namespace 같은 Kubernetes 개념의 이점을 누릴 때입니다. 반대로 use case가 선언적이지 않거나, 관리할 데이터가 Kubernetes 리소스 모델에 맞지 않거나, 플랫폼과의 긴밀한 통합이 필요 없다면, 독립 API를 만들어 일반 Service나 Ingress로 노출하는 편이 낫습니다.



## 실무 적용

- **CRD에는 OpenAPI V3 스키마를 붙입니다.** 프로덕션급이라면 검증으로 설정 오류를 조기에 잡습니다.
- **HPA 연동이 필요하면 scale 서브리소스를 정의합니다.** 이것이 없으면 커스텀 리소스를 오토스케일할 수 없습니다.
- **CRD와 ConfigMap을 상황으로 고릅니다.** cluster-admin 권한이 없거나 공개 클러스터라면 ConfigMap이 현실적 차선입니다.
- **Operator의 ServiceAccount에 최소 권한 Role을 붙입니다.** 관리하는 CRD 종류에 대해서만 권한을 부여합니다(26장).
- **바퀴를 다시 만들지 않습니다.** Kubebuilder나 Operator SDK로 스캐폴딩하고 기존 Operator(Prometheus, Strimzi 등)를 Operator Hub에서 찾습니다.

- [ ] use case가 선언적 Kubernetes 방식에 실제로 맞는지 판단했는가?



## 면접 관점

**Q. Operator와 Controller의 관계를 설명해 주세요.**
Operator는 is-a 관계로 Controller의 특성을 모두 가지면서 CRD를 더한 것입니다. Controller가 표준 Kubernetes 리소스를 조정한다면, Operator는 CRD로 정의한 커스텀 리소스를 조정해 특정 애플리케이션의 운영 지식을 캡슐화합니다. Operator = Controller + CRD로 요약할 수 있고 Kubernetes와 또 다른 도메인 둘 다를 아는 컨트롤러입니다.

**Q. CRD 대신 ConfigMap을 쓰면 무엇을 잃나요?**
가장 큰 이점은 cluster-admin 권한 없이 쓸 수 있다는 것입니다. 하지만 `kubectl get` 같은 도구 지원, API 서버 수준의 검증, API 버전 관리를 잃고 status 필드를 자유롭게 모델링할 수 없으며 kind별 세밀한 RBAC도 불가능합니다. 한 namespace의 모든 ConfigMap이 같은 권한을 공유하기 때문입니다. 그래서 가능하면 CRD가 권장되고 권한 제약이 있을 때만 ConfigMap이 차선입니다.

**Q. Kubebuilder와 Operator SDK는 어떤 관계인가요?**
원래 둘은 기능이 많이 겹쳐 병합이 예상됐지만 실제로는 겹치는 부분을 Kubebuilder로 모으고 Operator SDK가 Kubebuilder를 의존성으로 쓰는 방식으로 정리됐습니다. Kubebuilder는 Go 기반 API 생성 프레임워크이고 Operator SDK는 그 위에 OLM·Operator Hub 통합과 Ansible·Helm·Java 플러그인을 더한 상위 도구입니다.
