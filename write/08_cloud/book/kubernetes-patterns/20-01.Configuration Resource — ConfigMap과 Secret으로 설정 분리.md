# Configuration Resource — ConfigMap과 Secret으로 설정 분리
---
> 『Kubernetes Patterns』 20장 정독. **Configuration Resource**는 일반 데이터용 ConfigMap과 민감 데이터용 Secret이라는 Kubernetes 네이티브 리소스로, 설정 생애주기를 앱 생애주기에서 분리하는 패턴입니다. 두 리소스의 개념·사용법과 한계를 다룹니다. 환경변수(19장)로는 감당 못 하는 복잡·중앙집중 설정을 플랫폼 내장 기능으로 해결합니다.



## 핵심 요약

> 환경변수 패턴의 큰 단점은 소수의 변수·단순 설정에만 맞고 여러 곳에 정의될 수 있어 정의를 찾기 어렵다는 것입니다. 설정 데이터를 한곳에 모으되, 전체 설정 파일을 환경변수에 넣는 것은 말이 안 되므로, 약간의 간접 계층이 필요합니다 — Kubernetes 설정 리소스가 그것입니다.

**ConfigMap**(일반)과 **Secret**(민감)은 둘 다 key-value를 저장·관리해 사용법이 같습니다. 유일한 기술적 차이는 Secret 값이 **Base64 인코딩**이라는 점입니다. 소비 방법은 두 가지 — **환경변수 참조**(`configMapKeyRef`/`secretKeyRef`, `envFrom`으로 일괄, prefix 지정 가능)와 **볼륨 마운트**(키가 파일명, 값이 내용)입니다. 볼륨은 ConfigMap 갱신 시 파일이 자동 업데이트되어 **hot reload**가 가능하지만(앱이 파일을 감시해야 함), 환경변수는 프로세스 시작 후 못 바꿉니다.

**Secret 보안**의 진실 — Base64는 암호화가 아니라 보안상 평문과 같습니다(바이너리 저장용). 그런데도 Secret이 더 안전한 이유는 구현 세부입니다 — Secret이 필요한 Pod가 도는 노드에만 배포되고 노드에서 tmpfs 메모리에만 저장되며(물리 스토리지에 안 씀), etcd에서 암호화 저장될 수 있습니다. 다만 Pod 생성 권한자는 서비스 계정을 사칭해 namespace의 모든 Secret을 읽을 수 있어 앱 레벨 추가 암호화가 흔합니다. **1.21+의 `immutable` 필드**는 갱신을 막고 API 서버 성능을 높입니다. 한계 — Secret 1MB 제한, namespace당 ConfigMap 쿼터입니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

- ConfigMap과 Secret이 설정을 앱 생애주기에서 분리하는 방식을 설명한다.
- 두 리소스의 유일한 차이(Base64)와 같은 사용법을 안다.
- 환경변수 참조와 볼륨 마운트 두 소비 방법, hot reload 차이를 구분한다.
- Base64가 암호화가 아님과 Secret이 더 안전한 실제 이유를 설명한다.
- immutable 필드의 이점과 ConfigMap/Secret의 한계를 안다.



## 본문 정리

### 문제 — 환경변수의 한계

환경변수 패턴의 큰 단점은 소수의 변수·단순 설정에만 맞다는 것입니다. 또 환경변수가 여러 곳(OCI 이미지, Deployment)에 정의될 수 있어 정의를 찾기 어렵고 찾아도 다른 곳에서 오버라이드되지 않는다고 확신하기 어렵습니다. 설정 데이터를 여러 리소스 파일에 흩뿌리지 않고 한곳에 모으는 편이 낫지만 전체 설정 파일을 환경변수에 넣는 것은 말이 안 됩니다. 약간의 간접 계층이 유연성을 주는데, 그것이 Kubernetes 설정 리소스입니다.

### 해법 — ConfigMap과 Secret

Kubernetes는 순수 환경변수보다 유연한 전용 설정 리소스를 제공합니다 — 일반 데이터용 ConfigMap과 민감 데이터용 Secret입니다. 둘 다 key-value를 저장·관리하므로 같은 방식으로 씁니다. ConfigMap 설명은 대개 Secret에도 적용됩니다. 실제 데이터 인코딩(Secret은 Base64)을 빼면 기술적 차이가 없습니다.

ConfigMap의 키는 두 가지로 씁니다 — 키가 환경변수 이름이 되는 **환경변수 참조**, 그리고 키가 파일명이 되어 Pod 볼륨에 매핑되는 **파일**입니다. 볼륨으로 마운트된 ConfigMap 파일은 Kubernetes API로 ConfigMap이 갱신되면 함께 업데이트됩니다. 앱이 설정 파일 hot reload를 지원하면 즉시 이 갱신의 이득을 봅니다. 하지만 환경변수로 쓰면 프로세스 시작 후 못 바꾸므로 갱신이 반영되지 않습니다.

ConfigMap은 `data` 섹션에 key-value를 담습니다. Spring Boot `application.properties` 같은 전체 설정 파일 내용도 담을 수 있습니다(비자명한 경우 이 섹션이 꽤 커집니다). `kubectl create cm ... --from-literal=... --from-file=...`로 만들 수도 있습니다. 권장 관례는 EnvVar 용도 키는 대문자로, 파일 용도는 적절한 파일명으로 쓰는 것입니다.

### 소비 방법 — 환경변수 참조

`valueFrom.configMapKeyRef.{name, key}`로 개별 참조합니다. 항목이 많으면 `envFrom`으로 ConfigMap의 유효한 키 전체를 한 번에 노출할 수 있고 `prefix`로 접두어를 붙일 수 있습니다. 환경변수로 못 쓰는 키(`illeg.al` 등)는 무시됩니다. 여러 ConfigMap을 지정하면 뒤 항목이, 직접 `env`로 설정한 동명 변수가 더 높은 우선순위입니다. Secret은 `configMapKeyRef`를 `secretKeyRef`로 바꾸면 됩니다.

### 소비 방법 — 볼륨 마운트

ConfigMap을 볼륨으로 쓰면 전체 내용이 볼륨에 투영되고 키가 파일명이 됩니다. Example 20-1을 볼륨으로 마운트하면 `/config` 폴더에 네 파일(`application.properties`와 `PATTERN`·`EXTRA_OPTIONS`·`SEED`)이 생깁니다. `items`로 노출할 키·파일 경로(`spring/myapp.properties`)·권한(`mode: 0400`)을 세밀하게 고를 수 있습니다.

ConfigMap 변경은 투영된 볼륨에 바로 반영되어 앱이 파일을 감시해 즉시 반영할 수 있습니다. 이 hot reload는 재배포로 인한 서비스 중단을 피해 유용하지만 라이브 변경은 어디에도 추적되지 않아 재시작 시 사라질 수 있고 감지·분석하기 어려운 **설정 드리프트**를 낳습니다. 많은 이가 배포 후 불변인 설정을 선호하는 이유입니다(21장).

### Secret은 얼마나 안전한가

Secret은 Base64 인코딩 데이터를 담고 Pod에 넘기기 전 디코딩합니다. 이것이 보안 기능으로 자주 오해됩니다. **Base64는 암호화가 아니라 보안상 평문과 같습니다** — 바이너리 데이터를 담기 위한 것입니다. 그런데도 Secret이 더 안전한 이유는 구현 세부입니다.

- Secret은 접근이 필요한 Pod가 도는 노드에만 배포됩니다.
- 노드에서 tmpfs 메모리에만 저장되고 물리 스토리지에 안 쓰이며 Pod 제거 시 삭제됩니다.
- etcd에서 암호화 형태로 저장될 수 있습니다.

그래도 root 사용자나 Pod를 만들어 Secret을 마운트하는 방법으로 접근할 수 있습니다. RBAC(26장)를 적용할 수 있지만 namespace에 Pod를 만들 수 있는 사용자는 더 높은 권한의 서비스 계정으로 Pod를 띄워 Secret을 읽어 권한을 상승시킬 수 있습니다 — 즉 Pod 생성 권한자는 그 namespace의 모든 Secret·ConfigMap에 접근할 수 있습니다. 그래서 민감 정보의 추가 암호화를 앱 레벨에서 하는 경우가 많습니다(GitOps 맥락은 25장 Secure Configuration).

### immutable 필드와 한계

1.21부터 ConfigMap·Secret에 `immutable` 필드를 지원합니다. `true`면 생성 후 갱신을 막습니다. 원치 않는 갱신을 막을 뿐 아니라, API 서버가 불변 오브젝트의 변경을 감시할 필요가 없어 **클러스터 성능이 크게 향상됩니다.** 바꾸려면 삭제·재생성하고 참조하는 Pod도 재시작해야 합니다.

가장 큰 이점은 **설정 정의와 사용의 분리**입니다. 설정을 쓰는 오브젝트를 설정 정의와 독립적으로 관리할 수 있고 플랫폼 내장 기능이라 21장 같은 커스텀 구조가 필요 없습니다. 한계도 있습니다 — Secret은 1MB 제한이라 임의로 큰 데이터를 담을 수 없고(Base64라 실효 ~700KB), 실제 클러스터는 namespace·프로젝트당 ConfigMap 개수에 쿼터를 둡니다. ConfigMap은 golden hammer가 아닙니다. 큰 설정은 Immutable Configuration(21장)·Configuration Template(22장)으로 다룹니다.



## 심화 학습

### Spring Cloud Kubernetes의 hot reload (Spring 관점)

ConfigMap 볼륨의 hot reload는 Spring 진영에서 [Spring Cloud Kubernetes Config](https://docs.spring.io/spring-cloud-kubernetes/reference/property-source-config.html)로 매끄럽게 쓸 수 있습니다. 이 라이브러리는 ConfigMap·Secret을 Spring의 `PropertySource`로 노출하고 `spring.cloud.kubernetes.reload.enabled=true`면 ConfigMap 변경을 감지해 `@ConfigurationProperties`·`@RefreshScope` 빈을 재바인딩합니다. 즉 본문이 말한 "앱이 파일을 감시해야 함"을 프레임워크가 대신 처리합니다.

주의할 점은 본문이 경고한 **설정 드리프트**입니다. hot reload로 라이브 변경한 값은 Git·매니페스트에 추적되지 않아, Pod 재시작 시 원래 ConfigMap 값으로 돌아갑니다. 그래서 hot reload는 "임시 튜닝"에는 편하지만 영구 변경은 반드시 매니페스트(ConfigMap YAML)를 고쳐 GitOps 파이프라인으로 반영해야 합니다. 편의(hot reload)와 재현성(불변) 사이의 트레이드오프가 21장 Immutable Configuration으로 이어지는 지점입니다.

### env 참조 vs 볼륨 마운트 — 갱신 반영의 근본 차이

두 소비 방법의 hot reload 차이는 19장에서 본 프로세스 모델 때문입니다. **환경변수**는 프로세스 시작 시 환경 블록에 복사되어 그 뒤 불변입니다 — ConfigMap을 바꿔도 이미 뜬 프로세스엔 안 들어갑니다. **볼륨 마운트**는 kubelet이 tmpfs에 파일을 계속 동기화하므로, ConfigMap이 바뀌면 파일 내용이 갱신됩니다(다만 심볼릭 링크 교체 방식이라 원자적이고 반영에 수십 초 지연이 있을 수 있습니다). 그래서 "갱신을 반영해야 한다"면 볼륨, "불변이 낫다"면 환경변수를 고르는 것이 실무 판단 축입니다.



## 실무 적용

- **설정을 ConfigMap·Secret으로 한곳에 모읍니다.** Pod 정의에 흩뿌리지 말고 설정 정의와 사용을 분리합니다.
- **민감값은 Secret에, 하지만 보안을 과신하지 않습니다.** Base64는 암호화가 아니므로 GitOps·앱 레벨 암호화(25장)를 병행합니다.
- **갱신 반영이 필요하면 볼륨 마운트를, 불변이 낫다면 환경변수를 씁니다.** hot reload는 편하지만 설정 드리프트 위험이 있습니다.
- **영구 변경은 매니페스트로 반영합니다.** hot reload 라이브 변경은 재시작 시 사라지니 ConfigMap YAML을 고쳐 GitOps로 넣습니다.
- **안정된 설정엔 immutable: true를 씁니다.** 원치 않는 갱신을 막고 API 서버 성능을 높입니다.
- **큰 설정은 ConfigMap에 억지로 넣지 않습니다.** 1MB 한계와 쿼터가 있으니 21~22장 패턴을 고려합니다.



## 체크리스트

- [ ] 설정을 ConfigMap·Secret으로 모아 정의와 사용을 분리했는가?
- [ ] 민감값을 Secret에 두되 Base64를 암호화로 착각하지 않았는가?
- [ ] Pod 생성 권한 통제(RBAC)로 Secret 접근을 제한했는가?
- [ ] 갱신 반영 여부에 따라 환경변수/볼륨 마운트를 옳게 골랐는가?
- [ ] hot reload 라이브 변경을 매니페스트에도 반영해 드리프트를 막았는가?
- [ ] 안정된 설정에 immutable: true를 적용했는가?
- [ ] 설정이 1MB·쿼터 한계에 걸리지 않는가?(걸리면 21~22장)



## 면접 관점

- **ConfigMap과 Secret의 차이는?** — 사용법은 같고 유일한 기술적 차이는 Secret 값이 Base64 인코딩이라는 점입니다. ConfigMap은 일반 데이터, Secret은 민감 데이터용입니다.
- **Base64 인코딩이 Secret을 안전하게 만듭니까?** — 아니요. Base64는 암호화가 아니라 보안상 평문과 같습니다. Secret이 더 안전한 건 필요한 노드에만 배포·tmpfs 저장·etcd 암호화 같은 구현 세부 때문입니다.
- **환경변수 참조와 볼륨 마운트는 무엇이 다릅니까?** — 볼륨은 ConfigMap 갱신 시 파일이 업데이트되어 hot reload가 가능하지만 환경변수는 프로세스 시작 후 못 바꿉니다. 갱신 반영이 필요하면 볼륨입니다.
- **immutable 필드의 이점은?** — 생성 후 갱신을 막아 원치 않는 변경을 방지하고 API 서버가 변경을 감시하지 않아 클러스터 성능이 향상됩니다.
- **ConfigMap/Secret의 한계는?** — Secret 1MB(실효 ~700KB), namespace당 ConfigMap 쿼터가 있습니다. 큰 설정은 Immutable Configuration·Configuration Template으로 다룹니다.
