# Configuration Template — 큰 설정을 시작 시 템플릿으로 생성
---
> 『Kubernetes Patterns』 22장 정독. **Configuration Template**은 크고 복잡한 설정을 앱 시작 시 생성·처리하는 패턴입니다. 생성된 설정은 템플릿 처리에 쓰인 파라미터로 반영된 대상 런타임 환경에 특화됩니다. 설정(Configuration) 카테고리를 마무리하는 편으로, Configuration Resource(20장) 위에 세워집니다.



## 핵심 요약

> ConfigMap·Secret으로 앱을 설정할 수 있지만 설정 파일이 크고 복잡해지면 리소스 정의에 정확히 임베드하기가 문제가 됩니다 — 따옴표 같은 특수문자로 Kubernetes 리소스 문법을 깨지 않게 조심해야 하고 1MB(etcd 백엔드) 한계도 있습니다. 큰 설정 파일은 대개 실행 환경마다 조금만 다른데, 이 유사성이 ConfigMap에 많은 중복·중복성을 낳습니다.

중복을 줄이려면 **차이 나는 값만**(DB 연결 파라미터 등) ConfigMap이나 환경변수에 저장하고 컨테이너 시작 시 이 값들을 **템플릿 프로세서**(Gomplate·Tiller)로 처리해 전체 설정 파일(WildFly `standalone.xml` 등)을 만듭니다. 처리 방법은 두 가지 — Dockerfile **ENTRYPOINT**에 프로세서를 넣거나, Kubernetes **init container**로 처리하는 것입니다. init container 방식이 ConfigMap을 파라미터로 직접 쓸 수 있어 권장됩니다.

init container 흐름은 세 디렉토리로 나뉩니다 — `/in`은 이미지에 담긴 템플릿, `/params`는 ConfigMap 볼륨(데이터 소스), `/out`은 처리 결과를 담는 emptyDir로 앱 컨테이너가 마운트합니다. WildFly 예에서 개발/운영은 로그 접두어(`DEVELOPMENT:`/`PRODUCTION:`)만 다르며 **Deployment 서술자는 그대로 두고 ConfigMap 파라미터만 바꿉니다.** 이것이 **DRY** — 설정이 모든 환경에서 바뀌면 init의 단일 템플릿만 갱신하면 되어 설정 드리프트 위험이 없습니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

- 큰 설정을 통째로 ConfigMap에 넣을 때의 문제(중첩·중복·1MB)를 설명한다.
- 차이 값만 저장하고 나머지는 템플릿으로 생성하는 아이디어를 안다.
- ENTRYPOINT 방식과 init container 방식을 구분하고 후자가 권장되는 이유를 안다.
- init container의 /in·/params·/out 흐름을 설명한다.
- 이 패턴이 DRY를 이루는 방식과 언제 쓸지의 경계를 안다.



## 본문 정리

### 문제 — 큰 설정의 중복

20장에서 ConfigMap·Secret으로 앱을 설정했습니다. 하지만 설정 파일이 크고 복잡해질 수 있습니다. 설정 파일을 ConfigMap에 직접 넣으면 리소스 정의에 정확히 임베드되어야 해 문제가 됩니다 — 따옴표 같은 특수문자로 Kubernetes 리소스 문법을 깨지 않게 조심해야 합니다. 크기도 문제입니다. ConfigMap·Secret 모든 값의 합에 1MB 한계(etcd 백엔드)가 있습니다.

큰 설정 파일은 대개 실행 환경마다 조금만 다릅니다. 이 유사성이 ConfigMap에 많은 중복·중복성을 낳습니다 — 환경마다 대부분 같은 데이터를 갖기 때문입니다. Configuration Template이 이 문제를 다룹니다.

### 해법 — 차이 값만 저장하고 템플릿으로 생성

중복을 줄이려면 DB 연결 파라미터처럼 차이 나는 설정값만 ConfigMap이나 환경변수에 저장하는 것이 합리적입니다. 컨테이너 시작 시 이 값들을 설정 템플릿으로 처리해 전체 설정 파일(WildFly `standalone.xml` 등)을 만듭니다. Tiller(Ruby)나 Gomplate(Go) 같은 도구가 앱 초기화 시 템플릿을 처리합니다. 앱이 시작되기 전에 완전히 처리된 설정 파일이 다른 설정 파일처럼 바로 쓸 수 있는 위치에 놓입니다.

런타임 라이브 처리는 두 방법이 있습니다.

- **Dockerfile ENTRYPOINT** — 프로세서를 이미지 진입점에 넣습니다. 진입점은 대개 먼저 템플릿을 처리하고 앱을 시작하는 스크립트이고 파라미터는 환경변수에서 옵니다.
- **Kubernetes init container** — Pod의 init container에서 프로세서가 돌아 앱 컨테이너용 설정을 만듭니다. Kubernetes에서는 ConfigMap을 템플릿 파라미터로 직접 쓸 수 있어 이 방식이 가장 매력적입니다.

### init container 흐름

앱 Pod 정의는 최소 두 컨테이너로 구성됩니다 — 템플릿 처리용 init container와 앱 컨테이너입니다. init container는 템플릿 프로세서뿐 아니라 설정 템플릿 자체도 담습니다. 볼륨도 둘입니다 — ConfigMap이 백킹하는 템플릿 파라미터 볼륨과, 처리된 템플릿을 init과 앱이 공유하는 emptyDir 볼륨입니다.

시작 시 단계는 이렇습니다.

1. init container가 시작되어 템플릿 프로세서를 실행합니다. 프로세서는 이미지의 템플릿과 마운트된 ConfigMap 볼륨의 파라미터를 받아 결과를 emptyDir 볼륨에 저장합니다.
2. init container가 끝나면 앱 컨테이너가 시작되어 emptyDir 볼륨에서 설정 파일을 로드합니다.

WildFly 예는 개발·운영 두 환경의 전체 WildFly 설정 파일을 관리합니다. 둘은 거의 같고 로그 방식만 다릅니다 — 각 로그 줄에 `DEVELOPMENT:` 또는 `PRODUCTION:` 접두어가 붙습니다. 로그 패턴은 `standalone.xml`에 저장되고 Go 템플릿 문법으로 파라미터화됩니다. Gomplate를 프로세서로 쓰며 데이터 소스로 템플릿 파라미터를 참조합니다. 이 데이터 소스는 init container에 마운트된 ConfigMap 볼륨에서 옵니다.

베이스 이미지 `k8spatterns/gomplate`는 프로세서와 진입점 스크립트를 담고 기본 디렉토리를 씁니다 — `/in`은 WildFly 설정 템플릿(파라미터화된 `standalone.xml` 포함, 이미지에 직접 추가), `/params`는 Gomplate 데이터 소스(YAML)를 찾는 곳(ConfigMap 볼륨에서 마운트), `/out`은 처리된 파일을 저장하는 곳(WildFly 앱 컨테이너에 마운트되어 설정으로 사용)입니다.

**핵심은 개발→운영 전환에 Deployment 리소스 서술자를 바꿀 필요가 없다는 것입니다.** 템플릿 파라미터를 담은 ConfigMap만 다릅니다.

### DRY와 논의

이 기법으로 큰 설정 파일을 복사·중복 유지하지 않는 DRY 설정을 쉽게 만듭니다. WildFly 설정이 모든 환경에서 바뀌면 init container의 단일 템플릿 파일 하나만 갱신하면 됩니다. 유지보수에 큰 이점이 있고 설정 드리프트 위험이 없습니다.

Configuration Template은 Configuration Resource 위에 세워지며 비슷한 복잡 설정으로 여러 환경을 운영할 때 특히 적합합니다. 다만 설정이 더 복잡하고 잘못될 수 있는 움직이는 부품이 많으니, 앱이 큰 설정 데이터를 요구할 때만 씁니다. 그런 앱은 대개 상당한 설정이 필요하고 그중 작은 일부만 환경 의존적입니다 — 전체를 환경별 ConfigMap에 복사하면 처음엔 되지만 시간이 지나며 발산해 유지보수 부담이 됩니다. 이런 상황에 템플릿 방식이 완벽합니다. OpenShift라면 리소스 서술자 파라미터화로 대안을 쓸 수 있지만 이는 큰 설정 문제를 풀지는 않습니다.

디버깅 팁 — emptyDir 내용은 노드의 `/var/lib/kubelet/pods/{podid}/volumes/kubernetes.io~empty-dir/`에서 확인하거나, 실행 중 Pod에 `kubectl exec`로 들어가 마운트 디렉토리(`/config`)를 살펴봅니다.



## 심화 학습

### Helm·Kustomize와 이 패턴의 관계 (실무 관점)

이 장의 템플릿 처리는 **런타임(앱 시작 시)** 에 일어난다는 점이 중요합니다. 반면 오늘날 더 흔한 도구인 **Helm**·**Kustomize**는 **배포 시(client-side)** 에 매니페스트를 렌더링합니다. 둘은 푸는 문제가 다릅니다.

- Helm/Kustomize는 **Kubernetes 리소스 서술자**(Deployment·Service·ConfigMap YAML)를 환경별로 렌더링합니다 — "매니페스트의 DRY".
- 이 장의 Configuration Template은 **앱 내부 설정 파일**(WildFly `standalone.xml`)을 런타임에 렌더링합니다 — "앱 설정 파일의 DRY".

그래서 둘은 배타적이지 않고 층이 다릅니다. Helm으로 ConfigMap(파라미터)과 Deployment를 환경별로 배포하고 그 안에서 init container가 앱 설정 파일을 런타임에 생성하는 조합도 가능합니다. 다만 대부분의 현대 앱은 설정 파일이 그리 크지 않아 Helm/Kustomize의 매니페스트 템플릿만으로 충분하고 이 장의 런타임 템플릿 프로세서(init container + Gomplate)는 WildFly처럼 방대한 설정 트리를 가진 레거시 앱에서 진가를 발휘합니다.

> 참고: [Helm](https://helm.sh/docs/chart_template_guide/)·[Kustomize](https://kubectl.docs.kubernetes.io/references/kustomize/)가 매니페스트 수준 템플릿/오버레이의 사실상 표준입니다(책 범위 밖). 이 장은 그 아래층, 앱 설정 파일 수준의 런타임 생성을 다룹니다.

### Configuration 카테고리 네 패턴의 결정 흐름

19~22장은 설정 복잡도가 커지는 순서로 배치된 결정 트리입니다. **설정값이 적으면** 환경변수(19장). **더 많거나 파일 단위면** ConfigMap·Secret(20장). **불변·버전 관리가 필요하거나 1MB를 넘으면** Immutable Configuration의 데이터 이미지(21장). **환경마다 조금만 다른 큰 설정이면** Configuration Template(22장)입니다. 뒤로 갈수록 강력하지만 복잡하므로, 항상 **가장 단순한 것부터** 시도하고 그것이 부족할 때만 다음으로 넘어가는 것이 네 장을 관통하는 원칙입니다. 21장과 22장은 둘 다 init container + 공유 볼륨을 쓰지만 21장은 설정을 **통째로 이미지에 봉인**하고 22장은 **차이만 파라미터로 두고 나머지를 템플릿으로 생성**한다는 점이 다릅니다.



## 실무 적용

- **큰 설정 파일이 환경마다 조금만 다르면 템플릿으로 DRY화합니다.** 차이 값만 ConfigMap에, 나머지는 템플릿에 둡니다.
- **Kubernetes에서는 init container 방식을 씁니다.** ConfigMap을 파라미터로 직접 쓸 수 있어 ENTRYPOINT 방식보다 낫습니다.
- **/in·/params·/out 세 디렉토리로 흐름을 나눕니다.** 템플릿·파라미터·결과를 명확히 분리합니다.
- **환경 전환은 ConfigMap 파라미터만 바꿉니다.** Deployment 서술자는 그대로 둡니다.
- **매니페스트 DRY는 Helm/Kustomize, 앱 설정 파일 DRY는 이 패턴으로 층을 나눕니다.**
- **큰 설정일 때만 씁니다.** 움직이는 부품이 많아 복잡하니, 일반 앱은 ConfigMap이나 Helm으로 충분합니다.

## 면접 관점

- **Configuration Template이 푸는 문제는?** — 큰 설정 파일이 환경마다 조금만 다를 때 생기는 중복입니다. 차이 값만 ConfigMap에 저장하고 나머지는 시작 시 템플릿으로 생성해 DRY를 이룹니다.
- **왜 init container 방식이 권장됩니까?** — Kubernetes에서 ConfigMap을 템플릿 파라미터로 직접 쓸 수 있기 때문입니다. init container가 /in의 템플릿과 /params의 ConfigMap을 받아 /out(emptyDir)에 결과를 만들고 앱이 그것을 로드합니다.
- **환경 전환 시 무엇만 바꿉니까?** — ConfigMap의 템플릿 파라미터만 바꿉니다. Deployment 리소스 서술자는 그대로 둡니다.
- **이 패턴과 Immutable Configuration의 차이는?** — Immutable Configuration은 설정을 통째로 이미지에 봉인합니다. Configuration Template은 차이만 파라미터로 두고 나머지를 템플릿으로 생성해 중복을 없앱니다. 둘 다 init container를 씁니다.
- **Helm/Kustomize와는 어떻게 다릅니까?** — Helm/Kustomize는 배포 시 매니페스트(리소스 YAML)를 렌더링합니다. 이 패턴은 런타임에 앱 내부 설정 파일을 렌더링합니다. 층이 달라 함께 쓸 수 있습니다.
