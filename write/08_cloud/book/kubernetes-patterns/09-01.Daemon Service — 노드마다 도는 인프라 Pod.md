# Daemon Service — 노드마다 도는 인프라 Pod
---
> 『Kubernetes Patterns』 9장 정독. **Daemon Service**는 우선순위 높은 인프라 중심 Pod를 대상 노드에 배치·실행하는 패턴입니다. 주로 관리자가 노드별 Pod로 Kubernetes 플랫폼 능력을 보강하는 데 씁니다. OS의 데몬(httpd·sshd)이나 JVM의 데몬 스레드(GC)가 배경에서 지원 서비스를 제공하듯, **DaemonSet**은 클러스터 노드에서 돌며 나머지 클러스터에 배경 능력을 제공합니다.



## 핵심 요약

> ReplicaSet은 **사용자 부하·가용성 요구**가 Pod 개수를 정하며 노드 수와 무관합니다. **DaemonSet**은 다르게, 소비자 부하가 아니라 **노드**가 개수를 정해 — 모든 노드(또는 특정 노드)에 **Pod 하나씩** — 둡니다. 주 용도는 클러스터 스토리지 제공자·로그 수집기·메트릭 익스포터·kube-proxy 같은 클러스터 전역 인프라 프로세스입니다.

DaemonSet만의 특성이 있습니다 — DaemonSet Pod는 `nodeName`이 이미 지정돼 **스케줄러 없이도** 뜰 수 있고(다른 Pod보다 먼저, 스케줄러 시작 전에도), 노드의 `unschedulable` 필드를 무시하며 `restartPolicy`는 `Always`만 가능하고 여러 컨트롤러가 더 높은 우선순위로 취급합니다(descheduler 축출 회피 등). **v1.17+** 부터는 `nodeName` 대신 `nodeAffinity`를 써서 기본 스케줄러가 필수 의존이 되지만 그 대가로 taint·toleration·우선순위·preemption을 얻습니다.

DaemonSet과 비슷한 대안으로 **static Pod**(kubelet이 로컬 디렉토리에서 관리)가 있지만 API로 관리할 수 없어 플랫폼과 잘 통합되는 DaemonSet이 권장됩니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

- DaemonSet과 ReplicaSet의 차이(노드가 개수를 정함 vs 부하가 정함)를 설명한다.
- DaemonSet Pod가 스케줄러 없이 뜰 수 있는 이유(nodeName 지정)와 그 함의를 안다.
- v1.17에서 nodeName→nodeAffinity로 바뀐 이유와 얻은 것을 설명한다.
- DaemonSet Pod에 닿는 세 방법(Service·headless DNS·hostPort)을 안다.
- static Pod와 DaemonSet의 차이, DaemonSet이 권장되는 이유를 설명한다.



## 본문 정리

### 문제 — 노드마다 도는 배경 프로세스

데몬 개념은 여러 층위에 있습니다. OS 수준에서 데몬은 배경 프로세스로 도는 장기 실행·자가 복구 프로그램입니다(Unix에서 이름이 `d`로 끝남: httpd·named·sshd). 앱 수준에도 있습니다 — JVM의 데몬 스레드는 낮은 우선순위로 배경에서 GC·finalization 같은 지원 작업을 합니다. Kubernetes에도 **DaemonSet**이 있습니다 — 여러 노드에 퍼진 분산 플랫폼에서, 클러스터 노드에 돌며 나머지 클러스터에 배경 능력을 제공하는 Pod입니다.

### Solution — DaemonSet 리소스

ReplicaSet(과 전신 ReplicationController)은 특정 수의 Pod가 늘 돌게 보장합니다. DaemonSet도 비슷하게 일정 수의 Pod가 늘 돌게 하지만 **차이는 개수를 정하는 주체**입니다. 앞 둘은 노드 수와 무관하게 앱의 HA·사용자 부하 요구로 개수가 정해집니다. DaemonSet은 소비자 부하가 아니라 **모든 노드 또는 특정 노드에 Pod 하나씩** 두는 것이 목적입니다.

```yaml
apiVersion: apps/v1
kind: DaemonSet
metadata:
  name: random-refresher
spec:
  selector:
    matchLabels:
      app: random-refresher
  template:
    spec:
      nodeSelector:
        feature: hw-rng          # feature=hw-rng 라벨 노드에만
      containers:
      - image: k8spatterns/random-generator:1.0
        name: random-generator
        volumeMounts:
        - mountPath: /host_dev
          name: devices
      volumes:
      - name: devices
        hostPath:
          path: /dev             # 노드 디렉토리 직접 접근 (유지보수 작업에 흔함)
```

![DaemonSet vs ReplicaSet — 무엇이 개수를 정하는가](_assets/09-01.daemonset-vs-replicaset.svg)

주 후보는 인프라 프로세스입니다 — 클러스터 스토리지 제공자, 로그 수집기, 메트릭 익스포터, kube-proxy 등. DaemonSet과 ReplicaSet의 주요 관리 차이는 이렇습니다.

- 기본적으로 DaemonSet은 **모든 노드에 Pod 하나**를 둡니다. `nodeSelector`·`affinity`로 노드 부분집합에 제한할 수 있습니다.
- DaemonSet Pod는 **`nodeName`이 이미 지정**돼, DaemonSet은 스케줄러 없이도 컨테이너를 돌립니다. 그래서 Kubernetes 컴포넌트 실행에도 씁니다.
- DaemonSet Pod는 **스케줄러 시작 전에도** 돌 수 있어, 다른 Pod가 노드에 놓이기 전에 실행됩니다.
- 스케줄러를 안 쓰니 노드의 **`unschedulable` 필드를 무시**합니다.
- `restartPolicy`는 **`Always`만**(미지정 시 기본 Always). liveness 실패 시 컨테이너를 죽이고 늘 재시작하기 위함입니다.
- 대상 노드에서만 돌아야 하므로 많은 컨트롤러가 **높은 우선순위로 취급**합니다(descheduler 축출 회피, cluster autoscaler 별도 관리 등).

### v1.17 — nodeName에서 nodeAffinity로

DaemonSet 컨트롤러는 대상 노드에 Pod의 `nodeName`을 직접 설정해 배치합니다. 이 방식은 노드에 자원이 충분하고 다른 Pod보다 먼저 이뤄지는 한 잘 동작하지만 노드에 자원이 부족하면 DaemonSet 컨트롤러가 Pod를 못 만들고 preemption 같은 조치도 못 합니다. 스케줄링 로직이 DaemonSet 컨트롤러와 스케줄러에 **중복**돼 유지보수 난제가 되고 affinity·anti-affinity·preemption 같은 새 스케줄러 기능도 못 씁니다.

그래서 **v1.17+** 부터 DaemonSet은 `nodeName` 대신 **`nodeAffinity`** 를 설정해 기본 스케줄러로 스케줄합니다. 기본 스케줄러가 DaemonSet 실행의 필수 의존이 되지만 동시에 **taint·toleration·Pod 우선순위·preemption**을 DaemonSet에 가져와, 자원 기근에서도 원하는 노드에 Pod를 돌리는 경험을 개선합니다.

### DaemonSet Pod에 닿는 법

DaemonSet은 보통 노드마다(또는 부분집합에) Pod 하나를 만듭니다. 닿는 방법은 셋입니다.

- **Service**: DaemonSet과 같은 셀렉터의 Service를 만들어, 랜덤 노드로 로드밸런싱된 daemon Pod에 닿습니다.
- **DNS(headless Service)**: 같은 셀렉터의 headless Service로 모든 Pod IP·포트를 담은 여러 A 레코드를 DNS에서 가져옵니다.
- **Node IP + hostPort**: Pod가 hostPort를 지정해 노드 IP·포트로 닿습니다. 노드 IP·hostPort·프로토콜 조합이 고유해야 해 스케줄 위치가 제한됩니다.

또는 DaemonSet Pod의 앱이 외부의 알려진 위치·서비스로 **데이터를 push**할 수도 있습니다(소비자가 Pod에 닿을 필요 없음).

> **Static Pod.** DaemonSet과 비슷하게 컨테이너를 돌리는 다른 방법이 static Pod입니다. kubelet이 API 서버뿐 아니라 **로컬 디렉토리**에서 리소스 정의를 읽습니다. 이렇게 정의된 Pod는 kubelet만 관리하고 한 노드에서만 돕니다. API 서비스가 관찰하지 않고 컨트롤러·헬스체크가 없으며 kubelet이 크래시 시 재시작하고 디렉토리 변경을 주기 스캔합니다. static Pod로 Kubernetes 시스템 프로세스의 컨테이너 버전을 띄울 수 있지만 **DaemonSet이 플랫폼과 더 잘 통합돼 권장**됩니다.

### Discussion — 관리자 도구지만 개발자에게도

노드마다 데몬을 돌리는 다른 방법(static Pod, bare Pod, systemd 같은 init 스크립트)은 모두 한계가 있습니다 — static Pod는 API로 관리 못 하고 bare Pod는 삭제·노드 장애를 못 견디며 init 스크립트는 별도 툴체인이 필요해 Kubernetes 도구의 이점을 못 받습니다. 이 책은 관리자보다 개발자가 주로 쓰는 패턴을 다루지만 DaemonSet은 중간쯤이라(관리자 도구 쪽에 가깝지만 개발자에게도 유의미) 포함합니다. DaemonSet과 CronJob은 crontab·daemon 스크립트 같은 단일 노드 개념을 다중 노드 클러스터 프리미티브로 바꾼 좋은 예입니다.

### 관측 스택이 DaemonSet인 이유 — 노드 로컬 수집

이 장이 로그 수집기·메트릭 익스포터를 DaemonSet의 대표 용례로 든 것은, 관측(observability) 스택 설계의 근본 이유와 맞닿습니다. Node Exporter(호스트 CPU·메모리·디스크 메트릭), Fluent Bit/Promtail(노드의 컨테이너 로그 수집), Grafana Alloy 같은 것이 DaemonSet인 까닭은 **수집 대상이 노드에 묶여 있기** 때문입니다. 각 노드의 `/proc`·`/var/log`·커널 메트릭은 그 노드에서만 읽을 수 있으니, "노드마다 하나"의 DaemonSet이 정확히 이 요구에 맞습니다. ReplicaSet으로 3 replica를 띄우면 어느 3개 노드만 수집되고 나머지는 빠지지만 DaemonSet은 노드가 추가되면 자동으로 그 노드에도 수집기가 뜹니다.

여기서 이 장이 언급한 `hostPath` 마운트와 노드 접근이 관측 스택의 핵심 메커니즘으로 드러납니다 — 로그 수집기 DaemonSet은 `hostPath`로 노드의 `/var/log/containers`를 마운트해 그 노드 모든 Pod의 로그를 읽습니다. Prometheus 생태계에서 Node Exporter가 이 패턴의 교과서적 예이고 이는 정독 노트 옆 폴더 *Mastering Prometheus* 8장(Node Exporter)과 이어집니다 — 그 책은 Node Exporter를 DaemonSet으로 배포해 클러스터 전 노드 메트릭을 긁는 것을 다룹니다.

> DaemonSet의 기초(노드마다 하나·node selector·업데이트)와 노드 에이전트 특수 기능(privileged·hostPath·hostNetwork)은 형제 정독본 [DaemonSet 기초](../kubernetes-in-action/17-01.DaemonSet%20%EA%B8%B0%EC%B4%88%20%E2%80%94%20%EB%85%B8%EB%93%9C%EB%A7%88%EB%8B%A4%20%ED%95%98%EB%82%98%C2%B7node%20selector%C2%B7%EC%97%85%EB%8D%B0%EC%9D%B4%ED%8A%B8.md)에 상세합니다.

## 실무 적용

- **노드마다 필요한 인프라 프로세스는 DaemonSet으로.** 로그 수집·메트릭·스토리지·CNI처럼 노드에 묶인 수집·기능은 ReplicaSet이 아니라 DaemonSet입니다.
- **특정 노드에만 두려면 `nodeSelector`·affinity.** GPU·특수 하드웨어 노드에만 도는 데몬은 라벨로 제한합니다.
- **control plane 노드에도 돌리려면 toleration을 건다.** v1.17+ DaemonSet은 taint를 존중하므로, control plane taint를 견디는 toleration이 필요합니다.
- **노드 접근엔 `hostPath`.** 노드 로그·디바이스를 읽어야 하면 `hostPath`로 노드 디렉토리를 마운트합니다.
- **static Pod보다 DaemonSet.** kubeadm이 control plane을 static Pod로 띄우는 경우 외에는, API로 관리되는 DaemonSet이 낫습니다.



## 체크리스트

- [ ] DaemonSet(노드가 개수를 정함)과 ReplicaSet(부하가 정함)의 차이를 설명할 수 있다.
- [ ] DaemonSet Pod가 스케줄러 없이 뜰 수 있는 이유(nodeName 지정)와 unschedulable 무시를 안다.
- [ ] DaemonSet의 restartPolicy가 Always만 가능한 이유를 안다.
- [ ] v1.17에서 nodeName→nodeAffinity로 바뀐 이유와 얻은 것(taint·preemption)을 설명할 수 있다.
- [ ] DaemonSet Pod에 닿는 세 방법(Service·headless DNS·hostPort)을 안다.
- [ ] static Pod와 DaemonSet의 차이, DaemonSet이 권장되는 이유를 설명할 수 있다.
- [ ] 로그 수집기·Node Exporter가 왜 DaemonSet인지(노드 로컬 수집·hostPath) 안다.



## 면접 관점

**Q. DaemonSet과 ReplicaSet은 무엇이 다릅니까?**
둘 다 정해진 수의 Pod가 늘 돌게 보장하지만 그 수를 정하는 주체가 다릅니다. ReplicaSet은 사용자 부하·가용성 요구로 개수가 정해지고 노드 수와 무관합니다. DaemonSet은 노드가 개수를 정해, 모든 노드(또는 특정 노드)에 Pod 하나씩 둡니다. 그래서 노드가 추가되면 자동으로 그 노드에도 Pod가 뜹니다.

**Q. DaemonSet Pod가 스케줄러 없이 뜰 수 있는 이유는?**
DaemonSet 컨트롤러가 Pod의 nodeName을 직접 지정하기 때문입니다(v1.17 이전). 그래서 스케줄러 시작 전에도, 노드의 unschedulable 상태와 무관하게 뜰 수 있어 Kubernetes 컴포넌트 실행에도 씁니다. v1.17+부터는 nodeName 대신 nodeAffinity를 써서 기본 스케줄러가 필수 의존이 되지만 taint·toleration·우선순위·preemption을 얻습니다.

**Q. 로그 수집기나 Node Exporter가 왜 DaemonSet입니까?**
수집 대상이 노드에 묶여 있기 때문입니다. 각 노드의 `/proc`·`/var/log`·커널 메트릭은 그 노드에서만 읽을 수 있어, "노드마다 하나"의 DaemonSet이 정확히 맞습니다. `hostPath`로 노드 디렉토리를 마운트해 그 노드의 로그·메트릭을 읽고 노드가 추가되면 수집기도 자동으로 그 노드에 뜹니다.

**Q. static Pod와 DaemonSet은 어떻게 다릅니까?**
static Pod는 kubelet이 로컬 디렉토리에서 정의를 읽어 관리하고 한 노드에서만 돕니다. API 서버가 관찰하지 않고 컨트롤러·헬스체크가 없어 API로 관리할 수 없습니다. DaemonSet은 API로 관리되고 플랫폼과 잘 통합돼 권장됩니다. kubeadm의 control plane 컴포넌트처럼 부트스트랩 단계에서만 static Pod를 씁니다.
