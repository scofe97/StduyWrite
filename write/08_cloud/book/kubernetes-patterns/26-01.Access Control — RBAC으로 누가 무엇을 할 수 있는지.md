# 26장 · Access Control — RBAC으로 "누가 무엇을 할 수 있는지"

> API 서버 요청이 "누가 무엇을 할 수 있는가"를 통제하는 패턴입니다. Kubernetes는 이를 RBAC(Role-Based Access Control)으로 구현하며 Security 카테고리의 마지막 겹을 이룹니다.

![Access Control 개요](./_assets/26-01.access-control-rbac.svg)



## 핵심 요약

> Access Control은 모든 API 요청을 인증·인가·어드미션 3단계로 거르며 그중 인가를 RBAC이 담당하는 패턴입니다.

23장부터 25장까지가 프로세스·네트워크·설정을 지켰다면, 26장은 Kubernetes API 서버 자체에 대한 접근을 통제합니다. 클러스터를 조작하는 모든 행위 — Pod 생성, Secret 조회, Deployment 수정 — 는 API 서버를 거치므로, 여기서 "누가 무엇을 할 수 있는가"를 통제하는 것이 곧 클러스터 통제입니다.

모든 API 요청은 세 단계 파이프라인을 지납니다. 인증(누구인가), 인가(할 수 있는가), 어드미션(검증·변형). RBAC은 이 중 인가 단계를 맡아, 권한을 정의(Role/ClusterRole)하고 그것을 주체에 부여(RoleBinding/ClusterRoleBinding)하는 두 축으로 동작합니다.



## 학습 목표

> 이 장을 읽고 나면 다음을 설명할 수 있어야 합니다.

- API 요청의 3단계(인증·인가·어드미션)가 각각 무엇을 하는지 설명할 수 있습니다.
- Role과 ClusterRole의 범위 차이를 구분할 수 있습니다.
- RoleBinding과 ClusterRoleBinding이 권한을 어떻게 주체에 부여하는지 압니다.
- RBAC의 additive 성질과 기본 거부 원칙을 이해합니다.
- ServiceAccount가 워크로드의 신원으로 어떻게 쓰이는지 설명할 수 있습니다.



## 본문 정리

### API 요청의 3단계 파이프라인

Kubernetes API 서버에 도달한 모든 요청은 순서대로 세 관문을 통과합니다.

**인증(Authentication)**은 요청자가 누구인지 확립합니다. 클라이언트 인증서, 베어러 토큰, ServiceAccount 토큰 등 여러 방식으로 신원을 확인합니다. 이 단계를 통과하지 못하면 요청은 거기서 끝납니다.

**인가(Authorization)**는 확립된 신원이 이 동작을 할 자격이 있는지 판단합니다. RBAC이 바로 이 단계에서 동작합니다. 요청한 동작이 그 주체에게 허용되지 않았다면 거부됩니다.

**어드미션(Admission)**은 인가를 통과한 요청을 검증하거나 변형합니다. 정책을 강제하거나(예: 특정 필드 필수) 기본값을 채워 넣는 등의 처리를 하며 23·25장에서 본 admission 기반 정책 강제도 여기에 속합니다. 검증(validating)과 변형(mutating) 두 종류가 있어, 게이트 역할과 자동 보정 역할을 함께 수행합니다.

### RBAC의 두 축 — 권한을 정의하고 부여한다

RBAC은 개념적으로 두 축으로 나뉩니다. 하나는 "무엇을 할 수 있는가"를 정의하는 축이고 다른 하나는 그 권한을 "누구에게" 부여하는 축입니다.

**권한 정의 — Role과 ClusterRole.**
`Role`은 namespace 범위의 권한 묶음입니다. 특정 리소스(pods, configmaps 등)에 대한 verb 집합을 규정합니다. verb는 `get`, `list`, `watch`, `create`, `update`, `patch`, `delete` 같은 동작이고 이 Role은 자신이 속한 namespace 안에서만 유효합니다.

`ClusterRole`은 클러스터 범위의 권한 묶음입니다. 여러 namespace에 재사용하거나, namespace에 속하지 않는 리소스(노드, PersistentVolume, namespace 자체 등)에 대한 권한을 표현할 때 씁니다. 여기에 **aggregation**이라는 기능이 있어, 라벨 셀렉터로 여러 ClusterRole을 하나로 합칠 수 있습니다. 기본 역할에 새 권한을 라벨만 붙여 확장하는 식으로, 컨트롤러나 오퍼레이터가 자신의 권한을 기존 역할에 얹을 때 유용합니다.

**권한 부여 — RoleBinding과 ClusterRoleBinding.**
`RoleBinding`은 Role(또는 ClusterRole)을 특정 namespace의 주체(subject)에 연결합니다. 흥미로운 점은 RoleBinding이 ClusterRole을 참조할 수도 있다는 것인데, 이 경우에도 부여되는 권한의 범위는 그 RoleBinding이 속한 namespace로 한정됩니다. 그래서 "공용 ClusterRole 하나를 정의해두고 namespace마다 RoleBinding으로 그것을 각 팀에 부여"하는 재사용 관용구가 성립합니다. 같은 권한 정의를 여러 namespace에서 재활용하되 실제 부여는 각 namespace로 격리하는 것입니다.

`ClusterRoleBinding`은 ClusterRole을 클러스터 전역에 걸쳐 주체에 부여합니다. 모든 namespace에 적용되므로 강력하고 그만큼 신중해야 합니다. cluster-admin 같은 강한 ClusterRole을 ClusterRoleBinding으로 넓게 부여하면 사실상 클러스터 전체 통제권을 넘기는 셈이 됩니다.

주체(subject)는 세 종류입니다 — 사람 사용자(User), 그룹(Group), 그리고 워크로드의 신원인 ServiceAccount.

### ServiceAccount — 워크로드의 신원

주체 중 앱과 직접 관련된 것이 **ServiceAccount**입니다. Pod가 API 서버에 접근할 때 쓰는 앱의 신원으로, 사람 사용자가 아니라 워크로드의 계정입니다. Pod에 ServiceAccount를 지정하면 그 토큰이 자동으로 마운트되고 앱은 그 토큰으로 API를 호출합니다.

주의할 점은 ServiceAccount를 지정하지 않으면 namespace의 `default` ServiceAccount가 쓰인다는 것입니다. 그래서 워크로드마다 전용 ServiceAccount를 만들어 그 워크로드가 필요로 하는 최소 권한만 부여하는 것이 정석입니다. default를 여러 워크로드가 공유하면 권한 경계가 흐려지고 default에 강한 권한이 붙으면 그 namespace의 모든 Pod가 그것을 상속받는 위험이 생깁니다.

### RBAC의 성질 — additive, 기본 거부

RBAC은 additive입니다. 오직 허용 규칙만 존재하고 deny 규칙은 없습니다. 한 주체에게 부여된 여러 권한은 합집합으로 결정되며 아무것도 부여되지 않았다면 기본적으로 거부됩니다. "막는" 규칙을 쓰는 것이 아니라 "여는" 규칙만 쌓아가는 모델입니다. 그래서 실수로 넓게 열지 않도록, 필요한 것만 최소한으로 여는 규율이 중요합니다.

피해야 할 것도 분명합니다. 와일드카드(`verbs: ["*"]`, `resources: ["*"]`)를 남발하거나 cluster-admin을 함부로 부여하면 최소 권한 원칙이 무너집니다. 특히 default ServiceAccount에 강한 권한을 붙이는 것은, 그 namespace의 모든 Pod가 그 권한을 물려받게 만들어 위험합니다.



## 심화 학습

### Role과 RoleBinding 예시 — Pod를 읽는 최소 권한

특정 namespace에서 Pod를 조회만 할 수 있는 최소 권한을 ServiceAccount에 주는 전형적인 조합입니다.

```yaml
# ① 권한 정의 — default namespace에서 pod를 읽는 Role
apiVersion: rbac.authorization.k8s.io/v1
kind: Role
metadata:
  namespace: default
  name: pod-reader
rules:
  - apiGroups: [""]
    resources: ["pods"]
    verbs: ["get", "list", "watch"]
---
# ② 권한 부여 — 그 Role을 order-sa ServiceAccount에 연결
apiVersion: rbac.authorization.k8s.io/v1
kind: RoleBinding
metadata:
  namespace: default
  name: read-pods
subjects:
  - kind: ServiceAccount
    name: order-sa
    namespace: default
roleRef:
  kind: Role
  name: pod-reader
  apiGroup: rbac.authorization.k8s.io
```

이 조합에서 `order-sa`를 쓰는 Pod는 default namespace의 Pod를 읽을 수만 있고 생성·삭제나 다른 리소스 접근은 부여되지 않았으므로 모두 거부됩니다. RBAC의 정확한 필드와 동작은 [Kubernetes 공식 RBAC 문서](https://kubernetes.io/docs/reference/access-authn-authz/rbac/)에서 확인할 수 있습니다.

### Spring 관점 — 앱이 API 서버를 부를 때만 필요하다

대부분의 Spring 애플리케이션은 사실 Kubernetes API를 직접 호출하지 않습니다. 비즈니스 로직만 처리하는 앱이라면 default ServiceAccount의 토큰조차 자동 마운트할 필요가 없어, `automountServiceAccountToken: false`로 아예 꺼두는 것이 안전합니다. 앱이 클러스터 API를 몰라도 되는데 토큰을 들고 있을 이유가 없기 때문입니다.

반대로 Spring Cloud Kubernetes를 써서 ConfigMap을 감시하거나, 오퍼레이터 성격의 컨트롤러를 Spring으로 구현해 커스텀 리소스를 다룬다면, 그때는 API 접근이 필요합니다. 이 경우 전용 ServiceAccount를 만들고 그 앱이 실제로 읽고 쓰는 리소스에 대한 최소 권한만 Role로 정의해 부여합니다. "ConfigMap을 감시한다"면 `configmaps`에 대한 `get`, `list`, `watch`만 주면 되고 그 이상은 필요 없습니다.

여기서 Access Control이 Security 카테고리 전체를 어떻게 마무리하는지 드러납니다. Process Containment(23장)가 프로세스의 권한을, Network Segmentation(24장)이 통신 경로를, Secure Configuration(25장)이 시크릿의 접근을 지켰다면, Access Control은 그 모두를 조작하는 API 접근 자체를 지킵니다. 특히 25장에서 "Secret을 누가 읽는가"를 RBAC으로 좁힌다고 했는데, 그 RBAC의 실체가 바로 이 장의 Role과 RoleBinding입니다. 네 패턴은 서로 다른 지점에서 겹겹이 방어를 이루는 심층 방어의 구성 요소입니다.



## 실무 적용

- **워크로드마다 전용 ServiceAccount를 만듭니다.** default 공유를 피하고 각 워크로드의 권한을 독립적으로 관리합니다.
- **최소 권한으로 시작합니다.** 필요한 verb와 리소스만 부여하고 "일단 넓게 주고 나중에 좁히자"는 접근을 경계합니다 — 넓힌 권한은 거의 좁혀지지 않습니다.
- **와일드카드와 cluster-admin을 남발하지 않습니다.** `verbs: ["*"]`나 cluster-admin 부여는 정말 필요한 경우로 한정하고 이유를 문서화합니다.
- **API를 호출하지 않는 앱은 토큰 마운트를 끕니다.** `automountServiceAccountToken: false`로 불필요한 자격을 제거합니다.
- **공용 ClusterRole + namespace별 RoleBinding으로 재사용합니다.** 같은 권한 정의를 여러 팀에 부여하되 범위는 각 namespace로 격리합니다.



## 체크리스트

- [ ] 각 워크로드가 default가 아닌 전용 ServiceAccount를 쓰는가?
- [ ] Role/ClusterRole이 필요한 verb·리소스만 담고 있는가? (와일드카드 지양)
- [ ] cluster-admin이나 넓은 ClusterRoleBinding이 꼭 필요한 곳에만 부여됐는가?
- [ ] API를 호출하지 않는 앱은 토큰 자동 마운트가 꺼져 있는가?
- [ ] default ServiceAccount에 불필요하게 강한 권한이 붙어 있지 않은가?
- [ ] Secret을 읽는 주체가 RBAC으로 최소한으로 좁혀져 있는가? (25장 연계)



## 면접 관점

**Q. Kubernetes API 요청은 어떤 단계를 거쳐 처리되나요?**
세 단계입니다. 인증(Authentication)에서 요청자가 누구인지 확립하고 인가(Authorization)에서 그 신원이 이 동작을 할 자격이 있는지 판단하며 어드미션(Admission)에서 통과한 요청을 검증하거나 변형합니다. RBAC은 이 중 인가 단계를 담당합니다.

**Q. Role과 ClusterRole, RoleBinding과 ClusterRoleBinding은 어떻게 다른가요?**
Role은 namespace 범위의 권한 정의이고 ClusterRole은 클러스터 범위이거나 노드·PV 같은 non-namespaced 리소스까지 다루는 정의입니다. RoleBinding은 권한을 특정 namespace의 주체에 부여하고(ClusterRole을 참조해도 범위는 그 namespace로 한정), ClusterRoleBinding은 클러스터 전역에 걸쳐 부여합니다. 공용 ClusterRole 하나를 namespace별 RoleBinding으로 재사용하는 것이 흔한 관용구입니다.

**Q. RBAC에서 deny 규칙으로 특정 접근을 막을 수 있나요?**
없습니다. RBAC은 additive라 허용 규칙만 존재하고 부여된 권한들의 합집합으로 결정되며 아무것도 부여되지 않으면 기본 거부입니다. 특정 접근을 막고 싶으면 애초에 그 권한을 부여하지 않으면 됩니다. 그래서 최소 권한으로 시작해 필요한 것만 여는 규율이 중요합니다.

**Q. ServiceAccount는 무엇이고 왜 전용으로 만들어야 하나요?**
ServiceAccount는 Pod가 API 서버에 접근할 때 쓰는 워크로드의 신원입니다. 지정하지 않으면 namespace의 default가 쓰이는데, default를 여러 워크로드가 공유하면 권한 경계가 흐려지고 default에 붙은 권한을 모든 Pod가 상속받습니다. 워크로드마다 전용 ServiceAccount를 만들어 필요한 최소 권한만 부여하면 권한을 워크로드 단위로 격리할 수 있습니다.
