# EnvVar Configuration — 환경변수로 설정을 외부화하기
---
> 『Kubernetes Patterns』 19장 정독. **EnvVar Configuration**은 앱을 설정하는 가장 단순한 방법입니다. 적은 수의 설정값은 어디서나 지원되는 환경변수로 외부화하는 것이 가장 쉽습니다. Kubernetes에서 환경변수를 선언하는 여러 방법과, 복잡한 설정에 환경변수를 쓸 때의 한계를 함께 다룹니다. 설정(Configuration) 카테고리의 첫 편입니다.



## 핵심 요약

> 모든 비자명한 앱은 데이터 소스·외부 서비스 접근이나 운영 튜닝을 위한 설정이 필요합니다. 12-factor 매니페스토 이전부터 앱에 설정을 하드코딩하는 것은 나쁜 일로 알려졌습니다 — 설정은 외부화되어 빌드 후에도 바꿀 수 있어야 합니다. 불변 아티팩트 공유를 촉진하는 컨테이너 세계에서는 더욱 그렇습니다.

12-factor는 설정 저장에 환경변수를 권장합니다. 모든 OS와 언어가 환경변수를 정의·전파·접근할 줄 알아 **보편적**입니다. 전형적 패턴은 빌드타임에 하드코딩 기본값을 두고 런타임에 오버라이드하는 것입니다. 선언 방법은 세 가지 — **Dockerfile ENV**(빌드타임 기본값), **docker run -e**(런타임 오버라이드), **Pod spec env**(리터럴 `value`, `configMapKeyRef`/`secretKeyRef` 위임)입니다. 부가 기능으로 downward API(14장), `envFrom` 일괄 임포트, **dependent variables**(`$(IP):$(PORT)` 참조, 앞서 정의된 것만 해석)가 있습니다.

한계가 분명합니다 — 환경변수는 **안전하지 않고**(로그 유출 가능, Secret도 env로는 평문), 값이 많아지면 관리가 불가능하며 여러 수준에서 설정할 수 있어 파편화되고 시작 전에만 설정 가능해 실행 중 변경이 안 됩니다. 이 불변성은 단점이자 **장점**입니다 — 설정도 불변으로 두고 바꿀 때는 컨테이너를 버리고 새 복사본을 롤링 업데이트로 띄우면 늘 정의된 설정 상태를 유지합니다. 복잡한 설정에는 Configuration Resource·Immutable Configuration·Configuration Template이 대안입니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

- 설정을 외부화해야 하는 이유와 12-factor의 환경변수 권장을 설명한다.
- Dockerfile ENV·docker run -e·Pod spec env 세 선언 방법을 구분한다.
- dependent variables(`$(...)`)의 참조 순서 규칙을 안다.
- 환경변수의 네 가지 한계(비보안·확장성·파편화·불변)를 설명한다.
- 기본값의 함정과 "90% 확신 없으면 기본값을 두지 말라"는 지침을 안다.



## 본문 정리

### 문제 — 설정을 어디에 두나

모든 비자명한 앱은 설정이 필요하고 하드코딩은 나쁩니다. 설정은 외부화되어 빌드 후에도 바꿀 수 있어야 합니다. 불변 아티팩트를 공유·촉진하는 컨테이너 앱에서는 더 큰 가치가 있습니다. 그렇다면 컨테이너 세계에서 이를 어떻게 가장 잘 할까요.

### 해법 — 환경변수, 보편적 방법

12-factor는 환경변수를 권장합니다. 단순하고 어느 환경·플랫폼에서나 동작합니다. 모든 OS가 환경변수를 정의·전파할 줄 알고 모든 언어가 쉽게 접근하게 해줍니다. 전형적 패턴은 빌드타임에 하드코딩 기본값을 두고 런타임에 오버라이드하는 것입니다.

- **Dockerfile ENV** — `ENV SEED "1349093094"`처럼 빌드타임 기본값을 둡니다. Java 앱은 `System.getenv("SEED")`로 읽습니다. 직접 실행하면 기본값을 쓰지만 대개는 이미지 밖에서 오버라이드합니다.
- **docker run -e** — `docker run -e SEED="147110834325" 이미지`로 런타임에 오버라이드합니다.
- **Pod spec env** — Deployment·ReplicaSet의 Pod 스펙에서 설정합니다. `value`로 리터럴을 직접 붙이거나, `valueFrom.configMapKeyRef`·`secretKeyRef`로 ConfigMap·Secret에 위임합니다. 위임의 이점은 환경변수를 Pod 정의와 독립적으로 관리할 수 있다는 것입니다(ConfigMap·Secret은 20장).

Secret에서 온 값이라도 환경변수는 안전하지 않습니다. 민감한 읽기 가능 정보를 환경변수에 넣으면 읽기 쉽고 로그에 유출될 수도 있습니다.

### 부가 기능 — envFrom, downward API, dependent variables

개별 참조 대신 `envFrom`으로 특정 ConfigMap·Secret의 모든 값을 임포트할 수 있습니다(20장). downward API(14장)로 Pod IP 같은 메타데이터를 주입할 수 있습니다.

**dependent variables**는 `env` 목록에서 앞서 정의된 변수를 `$(...)` 표기로 참조합니다 — 예: `MY_URL: "https://$(IP):$(PORT)"`. Kubernetes가 컨테이너 시작 시 해석합니다. 순서에 주의해야 합니다 — 뒤에 정의된 변수를 참조하면 해석되지 않고 `$(...)`가 리터럴로 남습니다. 이 문법은 컨테이너 command에서도 `$(OUTPUT_FILE)`처럼 쓸 수 있습니다.

### 기본값의 함정

기본값은 편리하고 convention over configuration 패러다임에 중요하지만 늘 좋은 것은 아니고 진화하는 앱에는 안티패턴일 수 있습니다. 사후 변경이 어렵기 때문입니다 — 코드 안 기본값을 바꾸면 재빌드가 필요하고 기본값에 의존하던 사람들이 변경에 놀랍니다. 시맨틱 버저닝을 쓴다면 기본값 변경은 major 버전을 올릴 정도의 중대 변경입니다.

기본값을 처음부터 옳게 잡기는 어렵습니다. 만족스럽지 않으면 기본값을 아예 없애고 사용자가 값을 안 주면 에러를 던지는 편이 낫습니다 — 조용히 예상 밖으로 동작하는 것보다 조기에 눈에 띄게 실패하는 게 낫습니다. 합리적 기본값이 오래갈 것을 90% 확신할 수 없다면 처음부터 기본값을 피하는 것이 최선입니다. 비밀번호·DB 연결 파라미터가 그런 후보입니다 — 환경에 크게 의존해 예측이 어렵고 기본값이 없으면 설정을 명시하게 되어 문서 역할도 합니다.

### 논의 — 한계와 불변성

환경변수는 쉽고 모두가 알며 컨테이너에 매끄럽게 매핑됩니다. 하지만 안전하지 않고 적당한 수의 설정값에만 좋습니다. 파라미터가 많아지면 관리가 버거워집니다. 그래서 여러 설정 파일(환경마다 하나)을 두고 환경변수 하나로 파일을 고르는 우회책을 쓰기도 합니다 — Spring Boot 프로필이 그 예입니다. 하지만 프로필 파일이 앱(컨테이너) 안에 저장되면 설정이 앱과 강결합되어, 개발·운영 설정이 같은 이미지에 나란히 들어가고 어느 쪽 변경에도 이미지 재빌드가 필요해집니다(권장하지 않습니다).

환경변수는 여러 수준에서 설정할 수 있어 정의가 파편화되고 중앙 정의처가 없으면 설정 문제 디버깅이 어렵습니다. 또 시작 전에만 설정할 수 있고 나중에 못 바꿉니다. 실행 중 "핫" 튜닝이 안 되는 것은 단점이지만 많은 이가 이를 **불변성을 설정에까지 확장하는 장점**으로 봅니다 — 실행 중인 컨테이너를 버리고 수정된 설정으로 새 복사본을 롤링 업데이트로 띄우면 늘 정의된·알려진 설정 상태를 유지합니다. 복잡한 요구에는 다음 세 패턴이 한계를 넘습니다.



## 심화 학습

### Spring Boot 프로필과 이 패턴의 긴장 (Spring 관점)

본문이 Spring Boot 프로필을 **명시적으로 비판**한다는 점이 Spring 개발자에게 중요합니다. `application-dev.yml`·`application-prod.yml`을 이미지에 굽고 `SPRING_PROFILES_ACTIVE` 환경변수로 고르는 흔한 방식은, 설정이 컨테이너 안에 들어가 앱과 강결합됩니다. 개발·운영 설정이 같은 이미지에 공존하고 어느 쪽을 바꾸든 이미지를 재빌드해야 합니다. 12-factor의 "설정은 앱 밖에" 원칙에 어긋납니다.

Kubernetes 친화적 대안은 프로필로 **구조만** 정의하고 값은 밖에서 주입하는 것입니다 — `application.yml`에 플레이스홀더(`${DB_URL}`)를 두고 실제 값은 ConfigMap·Secret에서 환경변수로 주입합니다. Spring Boot는 환경변수를 프로퍼티로 자동 바인딩하므로(`SPRING_DATASOURCE_URL` → `spring.datasource.url`), 이미지 하나로 모든 환경을 돌릴 수 있습니다. 프로필은 코드 경로 분기(개발용 mock 빈 활성화 등)에만 쓰고 환경별 값은 환경변수·ConfigMap으로 빼는 것이 이 장의 결론과 맞습니다.

> 참고: Spring Boot의 [환경변수 → 프로퍼티 relaxed binding](https://docs.spring.io/spring-boot/reference/features/external-config.html#features.external-config.typesafe-configuration-properties.relaxed-binding.environment-variables)이 이 주입을 가능케 합니다(책 범위 밖).

### env는 왜 실행 중 못 바꾸나 — 프로세스 모델

환경변수를 실행 중 못 바꾸는 것은 Kubernetes의 제약이 아니라 **OS 프로세스 모델**의 성질입니다. 환경변수는 프로세스가 fork/exec될 때 커널이 프로세스의 환경 블록에 복사하며 그 뒤에는 그 프로세스(와 자식)만의 사본이 됩니다. 부모(kubelet·컨테이너 런타임)가 원본을 바꿔도 이미 뜬 프로세스에는 전달되지 않습니다. 그래서 env 기반 설정은 본질적으로 불변이고 실행 중 갱신이 필요하면 20장의 ConfigMap **볼륨 마운트**(파일은 갱신 반영됨)로 가야 합니다. 이 차이가 19장과 20장을 가르는 핵심 축입니다.



## 실무 적용

- **적은 설정값은 환경변수로 외부화합니다.** 단순하고 보편적이라 소~중 규모 설정에 적합합니다.
- **값은 ConfigMap·Secret에 위임합니다.** Pod 정의에 리터럴로 박지 말고 `valueFrom`으로 참조해 독립적으로 관리합니다.
- **Secret을 env로 노출하는 것을 경계합니다.** 로그 유출 위험이 있으니 민감값은 볼륨 마운트나 앱 레벨 암호화를 고려합니다.
- **dependent variables는 순서를 지킵니다.** `$(...)`는 앞서 정의된 변수만 해석되므로 참조 대상을 먼저 선언합니다.
- **위험한 설정엔 기본값을 두지 않습니다.** 비밀번호·DB 연결은 기본값 대신 없으면 에러로 조기 실패시킵니다.
- **Spring 프로필을 이미지에 굽지 않습니다.** 값은 환경변수·ConfigMap으로 주입하고 프로필은 코드 경로 분기에만 씁니다.

## 면접 관점

- **왜 설정을 환경변수로 외부화합니까?** — 12-factor 권장이며 모든 OS·언어가 지원해 보편적입니다. 빌드타임 기본값을 런타임에 오버라이드하는 패턴으로, 불변 이미지 하나를 여러 환경에서 재사용할 수 있습니다.
- **환경변수의 한계는?** — 안전하지 않고(로그 유출), 값이 많아지면 관리가 어렵고 여러 수준 설정으로 파편화되며 시작 전에만 설정 가능해 실행 중 변경이 안 됩니다.
- **env를 실행 중 못 바꾸는 게 왜 장점이 되기도 합니까?** — 설정도 불변으로 만들기 때문입니다. 바꿀 때 컨테이너를 버리고 새 복사본을 롤링 업데이트로 띄우면 늘 정의된·알려진 설정 상태를 유지합니다.
- **기본값은 언제 두지 말아야 합니까?** — 합리적 기본값이 오래갈 것을 90% 확신할 수 없을 때, 특히 비밀번호·DB 연결처럼 환경 의존적인 값입니다. 기본값 없이 에러로 조기 실패시키는 편이 안전합니다.
- **dependent variables의 주의점은?** — `$(...)`는 앞서 정의된 변수만 해석됩니다. 뒤에 정의된 변수를 참조하면 리터럴로 남으니 순서를 지켜야 합니다.
