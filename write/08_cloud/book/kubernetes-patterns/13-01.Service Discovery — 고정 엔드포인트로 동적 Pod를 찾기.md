# Service Discovery — 고정 엔드포인트로 동적 Pod를 찾기
---
> 『Kubernetes Patterns』 13장 정독. **Service Discovery**는 서비스를 제공하는 인스턴스에 소비자가 접근할 안정된 엔드포인트를 제공하는 패턴입니다. 스케줄러가 Pod를 동적으로 배치하고 탄력적으로 스케일하므로, 소비자는 바뀌는 Pod IP 대신 고정 엔드포인트를 부릅니다. 소비자·제공자가 클러스터 안이냐 밖이냐에 따라 Kubernetes가 여러 메커니즘을 제공합니다.



## 핵심 요약

> 클러스터 이전 시대의 서비스 디스커버리는 **client-side**였습니다 — 소비자 안에 discovery agent(ZooKeeper·Consul·Ribbon)를 두어 레지스트리를 조회했습니다. Kubernetes는 이를 **server-side**로 옮겼습니다. 소비자는 고정 가상 Service 엔드포인트만 부르고 인스턴스의 등록·조회는 플랫폼이 뒤에서 처리합니다.

메커니즘은 소비자·제공자의 위치에 따라 갈립니다. **내부 디스커버리**(둘 다 클러스터 안)는 `type: ClusterIP` Service를 씁니다. 소비자는 이 Service의 clusterIP를 **환경변수**(Pod 시작 시 주입, 시간 의존적)나 **DNS**(`random-generator.default.svc.cluster.local`, 시간 의존 없음)로 찾습니다. **수동 디스커버리**는 selector 없는 Service에 Endpoints를 수동 지정해 외부 IP를 가리키거나(Manual IP), `type: ExternalName`으로 DNS CNAME 별칭을 만듭니다(Manual FQDN).

**외부에서의 디스커버리**(소비자가 클러스터 밖)는 강력·복잡 순으로 세 가지입니다. **NodePort**는 모든 노드에 포트를 열고(비-HTTP 트래픽에 선호), **LoadBalancer**는 그 위에 클라우드 제공자 LB를 얹으며 **Ingress**는 Service 앞의 별도 리소스로 L7 HTTP 스마트 라우팅을 제공해 IP·LB 하나로 여러 Service를 노출합니다.



## 학습 목표

> 이 편을 읽고 나면 다음을 설명할 수 있습니다.

- client-side와 server-side 디스커버리의 차이, Kubernetes가 후자임을 설명한다.
- ClusterIP Service를 환경변수와 DNS로 찾는 두 방법, 환경변수의 시간 의존 문제를 안다.
- selector 없는 Service(Manual IP·ExternalName)로 외부 목적지를 클러스터 추상으로 감싸는 법을 설명한다.
- NodePort·LoadBalancer·Ingress의 차이와 각자의 트레이드오프를 구분한다.
- headless Service가 왜 StatefulSet에 유용한지 안다.



## 본문 정리

### 문제 — 동적 Pod를 어떻게 찾나

Kubernetes에 배포된 앱은 대개 다른 서비스와 상호작용합니다. 앱이 **먼저 나가는 연결**을 여는 경우(파일 서버·메시지 브로커·DB 폴링)는 Kubernetes에 추가 설정이 필요 없습니다 — 앱이 스스로 목적지를 알고 연결합니다.

문제는 반대 방향, **외부 자극을 기다리는 장기 실행 서비스**입니다. 다른 Pod나 외부 시스템이 HTTP로 들어오려면, 스케줄러가 동적으로 배치하고 탄력적으로 스케일하는 Pod를 소비자가 **발견**할 수 있어야 합니다. 엔드포인트를 우리가 직접 추적·등록·조회하는 것은 큰 부담이므로, Kubernetes가 여러 메커니즘으로 이를 구현합니다.

### 내부 디스커버리 — ClusterIP Service

Deployment를 만들면 각 Pod가 클러스터 내부 IP를 받지만 다른 Pod의 클라이언트가 이 IP들을 미리 알 방법이 없습니다. **Service** 리소스가 이를 해결합니다 — 같은 기능을 제공하는 Pod 집합에 안정된 진입점을 줍니다. `kubectl expose`로 쉽게 만들거나, 완전한 제어를 위해 직접 정의합니다. `type: ClusterIP`(기본)는 가상 IP를 얻어 selector에 맞는 Pod로 트래픽을 라우팅합니다(Pod 생성 시점·방식과 무관).

clusterIP를 앱이 아는 방법은 두 가지입니다.

- **환경변수** — Pod 시작 시 그때까지 존재한 Service들의 정보가 env로 주입됩니다(`RANDOM_GENERATOR_SERVICE_HOST`·`_PORT`). 어떤 언어에서도 쓸 수 있고 클러스터 밖에서 흉내 내기도 쉽습니다. 문제는 **시간 의존**입니다 — 이미 실행 중인 Pod에는 주입할 수 없어, Service보다 먼저 뜬 Pod는 그 정보를 못 받습니다(재시작 필요).
- **DNS 조회** — 클러스터 DNS 서버에 Service마다 항목이 자동 등록됩니다. `random-generator.default.svc.cluster.local`(Service명.네임스페이스.svc.클러스터 접미사)로 접근합니다. 시간 의존 문제가 없어 Service 정의 즉시 모든 Pod가 조회할 수 있습니다. 같은 네임스페이스면 이름만으로도 됩니다.

ClusterIP의 다른 특성으로 다중 포트(HTTP 8080·HTTPS 8443을 한 Service에), `sessionAffinity: ClientIP`(L4 로드밸런싱이라 HTTP 쿠키 기반 어피니티는 불가), readiness 실패 Pod의 엔드포인트 제외, 가상 IP(kube-proxy가 iptables 갱신, ICMP 규칙이 없어 ping 불가)가 있습니다.

### 수동 디스커버리 — selector 없는 Service

selector를 생략하고 Endpoints 리소스를 직접 만들면 외부 IP를 가리킬 수 있습니다(**Manual IP**). Service와 같은 이름의 Endpoints에 외부 IP:포트를 지정합니다. 이 방식의 이점은 Service IP를 유지한 채 제공자 구현을 온프렘에서 Kubernetes로 이관할 수 있다는 것입니다 — 클라이언트는 같은 Service IP를 계속 씁니다. Endpoints는 Pod IP는 담을 수 있지만 다른 Service의 가상 IP는 담지 못합니다.

`type: ExternalName`(**Manual FQDN**)은 프록시·IP 없이 DNS CNAME 별칭만 만듭니다. `database-service.<ns>.svc.cluster.local`이 `my.database.example.com`을 가리키게 합니다 — 클러스터 밖 엔드포인트에 대한 또 다른 Kubernetes 추상입니다.

### 외부에서의 디스커버리 — NodePort·LoadBalancer·Ingress

지금까지는 클러스터 안에서만 접근 가능한 가상 IP였습니다. 외부 클라이언트가 Pod에 닿으려면 세 가지가 있습니다.

- **NodePort** — 모든 노드에 포트(예 30036)를 예약해 외부 노출합니다. 방화벽 규칙이 필요하고 클라이언트가 건강한 노드를 직접 골라야 하며(앞에 LB 두는 게 좋음), 소스 NAT로 클라이언트 IP가 노드 주소로 가려집니다. `externalTrafficPolicy: Local`을 주면 추가 홉과 IP 마스킹을 피하지만 다른 노드의 Pod로는 못 가므로 모든 노드에 Pod가 있어야 합니다. 비-HTTP 트래픽에 선호됩니다.
- **LoadBalancer** — NodePort 위에 클라우드 제공자의 LB를 얹습니다. 클라우드가 Kubernetes를 지원하고 LB를 프로비저닝할 때만 동작하며 Service마다 외부 IP를 하나씩 소비합니다.
- **Ingress** — Service 타입이 아니라 **별도 리소스**입니다. Service 앞에 서서 스마트 라우터·진입점 역할을 합니다. URI 경로 기반 fan-out, TLS 종료, 이름 기반 가상 호스팅을 제공합니다. 진짜 힘은 **외부 LB·IP 하나를 재사용해 여러 Service를 노출**해 인프라 비용을 줄이는 데 있습니다. 동작하려면 Ingress 컨트롤러가 필요하고 컨트롤러마다 어노테이션으로 추가 설정을 받습니다. 가장 강력하지만 가장 복잡합니다.

**Headless Service**(`clusterIP: None`)는 전용 IP를 요청하지 않습니다. 백킹 Pod가 내부 DNS에 직접 등록되며 StatefulSet(12장) 구현에 가장 유용합니다.

Table 13-1은 이를 단순→복잡 순으로 정리합니다 — 내부는 언제나 Service 리소스(ClusterIP/Manual IP/Manual FQDN/Headless), 외부는 그 위에 쌓인 NodePort/LoadBalancer/Ingress입니다.



## 심화 학습

### Spring 앱에서 Service를 부르는 법 (Spring 관점)

Spring Boot 앱이 클러스터 안 다른 서비스를 부를 때는 DNS 이름을 그대로 씁니다. `RestClient`·`WebClient`의 base URL을 `http://random-generator/`(같은 네임스페이스) 또는 `http://random-generator.default.svc.cluster.local/`로 두면 kube-proxy가 알아서 건강한 Pod로 L4 로드밸런싱합니다. 클라이언트 사이드 로드밸런싱 라이브러리(과거 Netflix Ribbon 같은)는 Kubernetes에서 불필요해집니다 — 그 책임이 플랫폼으로 내려갔기 때문입니다. 이것이 본문의 "client-side에서 server-side로" 이동을 Spring 진영에서 체감하는 지점입니다.

환경변수 방식은 시간 의존 문제 때문에 Spring 앱에서 base URL을 하드코딩하는 근거로 삼지 않는 편이 안전합니다. Service가 앱보다 늦게 생기면 env가 비어 있으므로, DNS 이름을 설정값(`application.yml`)으로 주입하는 것이 견고합니다.

> 참고: Spring Cloud Kubernetes의 [DiscoveryClient 구현](https://docs.spring.io/spring-cloud-kubernetes/reference/discovery-client.html)은 Kubernetes Service·Endpoints를 Spring의 `DiscoveryClient` 추상으로 노출해, 기존 Spring Cloud 디스커버리 코드를 그대로 쓰게 해줍니다(책 범위 밖).

### L4 로드밸런싱과 세션 어피니티의 한계

ClusterIP Service는 **L4(전송 계층)** 로드밸런싱만 합니다. 패킷 내부를 보지 못하므로 HTTP 쿠키 기반 세션 어피니티 같은 애플리케이션 레벨 라우팅은 불가능합니다. `sessionAffinity: ClientIP`로 같은 클라이언트 IP를 같은 Pod에 붙일 수는 있지만 여러 클라이언트가 같은 NAT 뒤에 있으면 뭉뚱그려집니다. HTTP 쿠키 기반 스티키 세션이 필요하면 L7을 이해하는 Ingress 컨트롤러 레벨에서 해결해야 합니다 — 이것이 11장 Stateless Service에서 "세션은 외부화하라"고 한 이유와 이어집니다.



## 실무 적용

- **클러스터 내부 호출은 DNS 이름을 씁니다.** 환경변수는 시간 의존 문제가 있으니 base URL은 DNS 이름을 설정으로 주입합니다.
- **외부 목적지도 Service로 감쌉니다.** Manual IP·ExternalName으로 외부 DB·API를 Kubernetes 추상 뒤에 두면, 나중에 클러스터 내부로 이관해도 클라이언트가 안 바뀝니다.
- **노출 방식은 최소 복잡도로 고릅니다.** 비-HTTP면 NodePort, 단일 HTTP Service면 LoadBalancer, 여러 HTTP Service를 한 IP로 묶으려면 Ingress입니다.
- **Ingress로 비용을 줄입니다.** Service마다 LoadBalancer를 두면 외부 IP가 늘어납니다. Ingress 하나로 여러 Service를 경로 기반 라우팅하면 IP·LB를 아낍니다.
- **소스 IP가 필요하면 externalTrafficPolicy를 확인합니다.** NodePort·LoadBalancer의 소스 NAT로 클라이언트 IP가 가려질 수 있습니다.
- **StatefulSet에는 headless Service를 씁니다.** 개별 Pod에 안정 DNS가 필요하기 때문입니다(12장).

- [ ] base URL을 환경변수가 아니라 설정으로 주입해 시간 의존을 피했는가?
- [ ] 외부 목적지를 Service(Manual IP·ExternalName)로 감싸 이관 여지를 남겼는가?

- [ ] 여러 HTTP Service를 Ingress 하나로 묶어 IP·LB 비용을 줄였는가?
- [ ] 소스 IP가 필요한 경우 externalTrafficPolicy: Local을 고려했는가?
- [ ] StatefulSet이라면 headless Service를 썼는가?



## 면접 관점

- **Kubernetes의 서비스 디스커버리는 client-side입니까 server-side입니까?** — server-side입니다. 소비자는 고정 Service 엔드포인트만 부르고 인스턴스의 등록·조회·로드밸런싱은 플랫폼이 뒤에서 처리합니다. 과거 client-side(discovery agent를 소비자에 내장)의 책임이 플랫폼으로 내려간 것입니다.
- **ClusterIP를 앱이 아는 두 방법과 각자의 문제는?** — 환경변수와 DNS입니다. 환경변수는 Pod 시작 시점에 주입되어 Service보다 먼저 뜬 Pod엔 안 들어갑니다(시간 의존). DNS는 시간 의존이 없어 권장됩니다.
- **NodePort·LoadBalancer·Ingress의 차이는?** — NodePort는 모든 노드에 포트를 열고(비-HTTP 선호), LoadBalancer는 그 위에 클라우드 LB를 얹으며(Service마다 외부 IP 소비), Ingress는 L7 스마트 라우터로 IP·LB 하나에 여러 HTTP Service를 경로 기반 라우팅합니다.
- **selector 없는 Service는 무엇에 씁니까?** — 외부 목적지를 Kubernetes 추상으로 감쌉니다. Endpoints를 수동 지정하면 외부 IP(Manual IP), ExternalName이면 DNS CNAME 별칭(Manual FQDN)입니다. Service IP를 유지한 채 제공자를 이관할 수 있습니다.
- **headless Service는 왜 씁니까?** — 가상 IP 없이 백킹 Pod를 DNS에 직접 등록해 개별 Pod에 접근하게 합니다. StatefulSet처럼 Pod마다 정체성이 다른 경우에 유용합니다.
