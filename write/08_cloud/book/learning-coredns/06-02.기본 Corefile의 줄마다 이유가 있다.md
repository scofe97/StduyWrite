# 기본 Corefile의 줄마다 이유가 있다

---

> 클러스터에 배포되는 CoreDNS 설정은 열두 줄 남짓입니다. 그 줄들이 왜 거기 있는지 알면 어떤 줄을 지워도 되는지가 함께 드러납니다.



## 핵심 요약

> 이 편이 매달린 하나의 생각은 CoreDNS 가 레코드를 쌓아 두지 않는다는 것이고, 기본 설정의 어색한 줄들은 대부분 거기서 나옵니다.

`kubernetes` 플러그인은 컨트롤러처럼 동작하되 API 서버에 아무것도 되쓰지 않습니다. Services 와 EndpointSlices 에 watch 를 걸어 메모리에 들고 있다가, 질의가 오면 그 자리에서 레코드를 만들어 답합니다.

쿠버네티스 객체가 이미 메모리에 있어 클러스터 안 이름은 빠르게 만들 수 있으므로 `cache 30` 이 그 응답을 다시 저장해 얻는 이득은 작습니다. kubeadm 기본값도 클러스터 도메인을 캐시에서 제외합니다.

- `pods insecure` 는 kube-dns 하위 호환입니다.
- `upstream` 은 불필요해진 유산이고 지금 버전에서는 넣으면 오히려 오류가 납니다.
- `fallthrough` 는 역방향 CIDR 을 다 적지 못했을 때의 안전장치입니다.



## 학습 목표

이 내용을 읽고 나면:

1. `kubernetes` 플러그인이 컨트롤러와 무엇이 같고 무엇이 다른지 말할 수 있습니다.
2. 쿠버네티스 인메모리 캐시와 `cache` 플러그인이 왜 별개인지 설명할 수 있습니다.
3. Endpoints 감시가 큰 서비스에서 비싼 이유를 watch 의 동작으로 유도할 수 있습니다.
4. 기본 Corefile 의 각 줄이 무엇을 켜고 왜 있는지 짚고, `cache` 의 상한과 하한으로 응답이 캐시에 남는 시간을 계산할 수 있습니다.
5. 스텁 도메인이 왜 새 서버 블록으로 표현되는지 3장의 최장 일치와 이어 말할 수 있습니다.

아래 지도는 기본 Corefile 에 질의 여섯을 차례로 물었을 때 어느 줄이 받고 어떻게 끝나는지 보여줍니다.

![질의 종류마다 기본 Corefile 에서 처음 받는 줄과 처리 결과](./_assets/06-02.chapter-overview.svg)

## 1. 되쓰지 않는 컨트롤러

> 앞 편에서 컨트롤러가 읽고 쓰는 루프를 돈다고 했습니다. `kubernetes` 플러그인은 그 루프에서 쓰는 쪽을 통째로 뺀 모양입니다.

![watch 로 받아 두고 질의가 올 때 만든다](./_assets/06-02.plugin-flow.svg)

CoreDNS 의 `kubernetes` 플러그인은 컨트롤러처럼 동작하되 API 서버에 데이터를 되쓰지 않습니다.
Services 와 EndpointSlices 자원에 watch 를 걸어 메모리에 유지하다가, 질의가 오면 해당 자원을 조회해 응답합니다.

### 즉석 레코드 생성

응답 레코드를 미리 만들어 저장하지 않고 들어온 요청에 맞춰 그 자리에서 만듭니다.

쿠버네티스 자원은 인메모리 캐시, 곧 CoreDNS 프로세스가 메모리에 들고 있는 사본에 있고 watch 로 변화를 따라갑니다. 그래서 정상적으로 동기화된 상태에서는 DNS 질의마다 API 서버를 조회할 필요가 없고 응답도 빠르게 만들 수 있습니다.

`kubernetes` 플러그인은 클러스터 상태를 변경하지 않는 읽기 전용 소비자이므로 RBAC 에서도 쓰기 권한을 요구하지 않습니다.



## 2. 서로 다른 두 캐시

> 쿠버네티스 객체의 인메모리 캐시와 `cache` 플러그인의 DNS 캐시는 서로 다르고 이름만 같습니다. 이 구분을 놓치면 기본 설정의 `cache 30` 을 잘못 읽습니다.

기본 Corefile 에는 인메모리로 자원을 쥐고 있는 `kubernetes` 플러그인 외에 `cache 30` 이 함께 들어갑니다. 이미 메모리에 든 자원을 다시 캐시하는 이유는 두 캐시의 대상이 다르기 때문입니다. 인메모리 캐시는 Service 같은 자원 객체를 담고, `cache` 플러그인은 완성된 DNS 응답 레코드를 담습니다.

클러스터 안 질의는 이미 메모리에 있는 자원에서 즉석으로 응답을 만듭니다. 이를 다시 캐시해도 해싱과 조회 오버헤드로 인해 실익이 적고 빗나가면 오히려 성능이 떨어집니다. 클러스터 밖 질의는 실제로 네트워크를 타야 하므로 캐시가 값을 합니다.

아래 그림은 두 종류의 이름을 캐시가 적중했을 때와 빗나갔을 때로 나눴습니다.

![응답 캐시가 아끼는 몫은 이름마다 다르다](./_assets/06-02.two-caches.svg)



## 3. Endpoints 감시가 큰 서비스에서 비싼 이유

> `kubernetes` 플러그인은 Services 와 Endpoints 를 둘 다 감시합니다. 뒤엣것이 문제를 일으키는데, 이유가 자원의 이름에 이미 들어 있습니다.

![파드 하나가 바뀌면 객체가 통째로 온다](./_assets/06-02.endpoints-watch.svg)

ClusterIP 서비스 질의에는 Services 가 필요하고 헤드리스 서비스 질의에는 EndpointSlices 가 필요합니다. 헤드리스 서비스를 지원할 필요가 없다면 플러그인 옵션 `noendpoints` 로 Endpoints watch 를 끌 수 있습니다.

### 복수형 이름의 문제

자원 이름이 Endpoints 로 복수인 이유는, Endpoints 자원 하나가 서비스 하나의 엔드포인트 주소를 준비 여부와 무관하게 전부 담기 때문입니다. 백엔드가 많은 서비스라면 아주 큰 자료구조가 됩니다.

watch 는 자원이 바뀔 때마다 객체 전체를 전송하므로, 파드 하나가 생성·삭제되거나 준비 상태가 바뀔 때마다 Endpoints 객체 전체가 전송됩니다.

부담은 두 방향에서 늘어납니다.

- 서비스의 백엔드가 많을수록 Endpoints 객체가 커집니다.
- 백엔드가 많을수록 그중 하나가 바뀔 가능성도 높아집니다.

두 요인이 겹쳐 대규모 서비스에서는 큰 객체가 자주 전송되며 CoreDNS 의 메모리와 CPU 를 크게 소모합니다.

이 문제는 쿠버네티스가 EndpointSlice 를 도입하면서 완화되었습니다. 서비스 하나의 주소를 여러 조각(slice)으로 나눠 담으므로, 파드 하나가 바뀌어도 그 파드가 든 조각만 다시 전송됩니다.[^slicewatch] 조각 하나에는 기본으로 엔드포인트가 100개까지 들어갑니다.[^eps][^epsmax] 옛 Endpoints API 쪽에는 상한이 있습니다. 백엔드가 1000개를 넘으면 쿠버네티스가 Endpoints 객체를 1000개에서 자르고 `endpoints.kubernetes.io/over-capacity: truncated` 주석을 답니다.[^overcap]

현재 `kubernetes` 플러그인은 EndpointSlice API 로 감시합니다.[^k8splugin]
그래도 큰 클러스터에서 API 서버 부담이 걱정되면 `apiserver_qps`·`apiserver_burst`·`apiserver_max_inflight` 로 플러그인이 보내는 요청의 초당 한도·순간 폭주 한도·동시 진행 상한을 조일 수 있습니다.[^k8splugin]

아래 그림은 백엔드 수가 다른 두 서비스에서 파드 하나가 바뀔 때 다시 오는 주소의 수를 막대 길이로 견줍니다.

![파드 하나가 바뀔 때 다시 오는 주소의 수](./_assets/06-02.endpoints-slices.svg)

`noendpoints` 옵션을 켜면 모든 엔드포인트와 헤드리스 서비스 질의에 `NXDOMAIN` 으로 응답합니다.[^k8splugin] 헤드리스를 쓰는 워크로드가 하나라도 남아 있으면 조회가 깨지므로, 클러스터 전체에서 헤드리스 서비스를 쓰지 않을 때만 꺼야 합니다.



## 4. 기본 Corefile 열두 줄

> 배포 도구가 만들어 넣는 Corefile 은 CoreDNS 팀의 권고를 거의 그대로 씁니다. 줄마다 켜는 것과 그 줄이 있는 이유가 다릅니다.

![기본 Corefile 의 줄과 그 줄을 지울 수 있는 조건](./_assets/06-02.corefile-lines.svg)

클러스터에 배포되는 Corefile 은 대개 배포 도구가 자동 생성하므로 처음 보면 각 줄의 역할을 파악하기 어렵습니다.
배포 도구는 대부분 CoreDNS 팀의 deployment 권고를 바탕으로 기본 설정을 만듭니다.[^deptmpl]
deployment 템플릿과 kubeadm 기본값은 `pods insecure`·`ttl`·`cache` 의 `disable` 에서 갈립니다.[^deptmpl][^kubeadm1372]

아래는 쿠버네티스 v1.37.2 kubeadm 이 생성하는 기본 Corefile 입니다.[^kubeadm1372] `{{ .DNSDomain }}` 자리는 `CLUSTER_DOMAIN` 으로 표기했습니다. `cache` 의 `disable` 두 줄은 클러스터 도메인이 주어졌을 때만 들어갑니다.

```bash
.:53 {
    errors
    health {
       lameduck 5s
    }
    ready
    kubernetes CLUSTER_DOMAIN in-addr.arpa ip6.arpa {
       pods insecure
       fallthrough in-addr.arpa ip6.arpa
       ttl 30
    }
    prometheus :9153
    forward . /etc/resolv.conf {
       max_concurrent 1000
    }
    cache 30 {
       disable success CLUSTER_DOMAIN
       disable denial CLUSTER_DOMAIN
    }
    loop
    reload
    loadbalance
}
```

아래는 위 블록에서 `lameduck`·`ready`·`ttl`·`max_concurrent`·`disable` 을 걷어 내고 값 자리를 변수로 남긴 Corefile 입니다.

```bash
.:53 {
    errors
    health
    kubernetes CLUSTER_DOMAIN REVERSE_CIDRS {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
    }
    prometheus :9153
    forward . UPSTREAMNAMESERVER
    cache 30
    loop
    reload
    loadbalance
}
```

대문자로 표기된 값은 배포 도구가 환경에 맞게 치환하는 변수입니다. 쿠버네티스 자체는 이 변수를 이해하지도 않고 아무 일도 하지 않으므로, 이 파일을 그대로 쓰면 클러스터의 CoreDNS 배포가 깨집니다.

### 서버 블록과 로깅

`.:53 {` 은 53번 포트에서 루트 도메인(`.`)과 그 하위의 모든 질의를 처리하는 서버 블록을 엽니다.
더 구체적으로 일치하는 서버 블록이 없는 한 모든 질의가 이 블록을 거칩니다.

`errors` 는 상류 타임아웃 등 질의 처리 중 발생한 오류를 로그에 남깁니다. 실제 DNS 응답 코드는 바꾸지 않으며 장애 추적에 쓰입니다. 없어도 CoreDNS 는 대개 `SERVFAIL` 로 응답하되 아무것도 남기지 않습니다.

`health` 는 kubelet 활성 프로브를 위한 HTTP 엔드포인트(`:8080/health`)를 엽니다.

### kubernetes 블록 안의 세 줄

`kubernetes CLUSTER_DOMAIN REVERSE_CIDRS {` 는 `kubernetes` 플러그인을 켜고 `CLUSTER_DOMAIN` 에 대한 권한을 부여합니다.

서비스와 파드의 PTR 요청에 답하려면 `REVERSE_CIDRS` 에 쿠버네티스 서비스 CIDR 과 파드 CIDR 을 지정합니다. 서비스 CIDR 과 파드 CIDR 은 쿠버네티스 API 로 발견할 수 없어서 CoreDNS 가 스스로 알아낼 수 없습니다. CIDR 대신 `in-addr.arpa` 와 `ip6.arpa` 를 적으면 모든 역방향 DNS 요청을 플러그인이 받습니다.

`pods insecure` 는 파드 IP 조회를 지원하던 폐기된 DNS 명세를 kube-dns 하위 호환을 위해 제공합니다. `pods` 를 아예 적지 않으면 기본값은 `disabled` 라서, 이 줄은 꺼져 있던 기능을 켜는 줄입니다. 필요 없다면 이 줄을 지웁니다.[^k8splugin]

`upstream` 은 과거 CNAME 을 풀 때 CoreDNS 가 자신에게 재질의하도록 지시하던 옵션입니다. 이 동작이 기본화되면서 1.7.0 에서 옵션이 제거되었으므로, 현재 설정에 넣으면 `unknown property` 오류로 CoreDNS 가 시작되지 않습니다.[^rel170][^unkprop][^upsdefault]

`fallthrough in-addr.arpa ip6.arpa` 는 PTR 조회에서 레코드를 찾지 못했을 때 요청을 플러그인 체인 아래로 넘깁니다.
역방향 CIDR 대신 `in-addr.arpa`·`ip6.arpa` 전체를 넘긴 경우, 이 줄이 없으면 플러그인이 외부 IP 의 PTR 요청까지 모두 삼켜 `NXDOMAIN` 으로 답합니다.
이 줄이 있어야 모르는 IP 요청이 `forward` 로 내려갑니다.

![fallthrough 가 없으면 모르는 IP 의 PTR 을 삼킨다](./_assets/06-02.ptr-fallthrough.svg)

### 나머지 여섯 줄

`prometheus :9153` 은 메트릭을 노출합니다. 기본값은 localhost 청취이므로 Prometheus 서버가 수집할 수 있도록 `:9153` 으로 모든 주소에 엽니다.

`forward . UPSTREAMNAMESERVER` 는 플러그인 체인에서 처리되지 않은 질의를 상류 네임서버로 전달합니다. 컴파일 시점에 플러그인 순서가 고정되므로 Corefile 안의 줄 순서는 플러그인 실행 순서에 영향을 주지 않습니다. 다만 한 서버 블록 안에 여러 인스턴스를 허용하는 플러그인이라면 그 순서는 의미가 있습니다.

`cache 30` 은 캐시 플러그인을 켜고 최대 TTL 을 30초로 제한합니다. 실제 캐시 기간은 레코드 TTL 에 하한 5초와 상한 30초를 적용한 값입니다.[^cache][^cacheclamp] 외부 질의에는 유용하지만, 메모리에서 즉석 생성되는 클러스터 도메인 응답에는 실익이 적습니다.

![상한 30 으로 자르고 하한 5 로 받친다](./_assets/06-02.cache-ttl.svg)

`loop` 는 시작 시 단순 포워딩 루프만 탐지하는 방어 플러그인입니다.[^loop] 루프가 탐지되면 오류 로그를 남기고 종료하여 원인 추적이 어려운 장애를 예방합니다.

`reload` 는 Corefile 의 SHA512 체크섬을 주기적으로 확인해(기본 30초, 지터 15초) 프로세스 재시작 없이 설정을 반영합니다.[^reload][^reload150] 지터는 검사 간격에 무작위로 더하고 빼는 폭입니다.
`kubectl -n kube-system edit configmap coredns` 로 고치면 변경이 자동으로 반영됩니다. ConfigMap 을 바꾸면 그 변경이 필요한 모든 노드에 전파되는 데 1~2분 걸릴 수 있습니다.
설정에 문법 오류가 있으면 기존 설정을 유지하지만, 이후 파드가 재스케줄되어 새로 뜨면 시작에 실패하므로 사전 시험이 필요합니다.

`loadbalance` 는 응답의 A·AAAA·MX 레코드를 무작위로 섞습니다.[^lb][^lb150] 헤드리스 서비스를 쓰면 클라이언트마다 다른 순서로 레코드를 받게 됩니다. 많은 클라이언트가 그냥 첫 번째 IP 를 쓰기 때문에, 이것만으로도 부하가 모든 인스턴스에 퍼집니다.

kubeadm 기본 Corefile 은 변수 형태의 열두 줄에 몇 가지를 더합니다.[^kubeadmdns][^kubeadm1372]
`health` 에 `lameduck 5s` 가 붙어 종료 신호를 받은 뒤에도 5초 동안 종료를 미룹니다. 그동안 `/health` 는 계속 200 OK 를 답하고, 따로 들어간 준비 상태 플러그인 `ready` 는 OK 를 답하지 않습니다.[^health][^lameduck150]

`kubernetes` 블록에는 `ttl 30`, `forward` 에는 `max_concurrent 1000` 이 붙습니다. `cache 30` 은 클러스터 도메인을 `disable success`·`disable denial` 로 지정해 내부 이름 캐시 오버헤드를 피합니다.



## 5. 스텁 도메인과 서버 블록

> 특정 도메인만 다른 네임서버로 보내고 싶을 때가 있습니다. CoreDNS 는 그것을 옵션이 아니라 서버 블록을 하나 더 만들어 표현합니다.

`forward` 는 첫 인자로 매칭할 도메인을 받으니 같은 블록에 한 줄 더 적는 길도 있습니다. 그런데 배포 도구가 만드는 Corefile 은 그 길 대신 서버 블록을 따로 나눕니다. 서버 블록마다 플러그인 체인이 독립이므로, 블록을 나누면 그 도메인의 질의만 다른 캐시 설정과 다른 `loop` 감시를 받게 할 수 있습니다. 한 블록 안에 `forward` 를 한 줄 더 얹으면 그 질의도 클러스터 질의와 같은 체인을 지납니다. 배포 템플릿의 `STUBDOMAINS` 변수도 서버 블록 바깥에 위치해 새 서버 블록으로 치환됩니다.[^depfed]

### 스텁 도메인의 두 서버 블록

아래 설정은 스텁 도메인의 서버 블록 구조를 보여줍니다.

```bash
.:53 {
    errors
    health
    kubernetes cluster.local in-addr.arpa ip6.arpa {
        pods insecure
        fallthrough in-addr.arpa ip6.arpa
    }
    prometheus :9153
    forward . /etc/resolv.conf
    cache 30
    loop
    reload
    loadbalance
}

corp.example.com:53 {
    errors
    cache 30
    loop
    forward . 10.0.0.10:53
}
```

질의는 라벨이 가장 길게 일치하는 서버 블록으로 향합니다.
`corp.example.com` 하위 질의는 두 번째 서버 블록으로 전달되어 사내 네임서버(`10.0.0.10:53`)가 처리합니다.

![라벨이 더 길게 맞는 블록이 질의를 가져간다](./_assets/06-02.stub-match.svg)

CoreDNS 에는 스텁 도메인 전용 문법이 없으며, [3장에서 본](./03-01.Corefile%EC%9D%80%20%EB%9D%BC%EB%B2%A8%EB%A1%9C%20%EC%84%9C%EB%B2%84%EB%A5%BC%20%EA%B0%80%EB%A5%B8%EB%8B%A4.md) 최장 일치 규칙 하나로 처리됩니다. 서버 블록마다 플러그인 체인이 독립적이므로 둘째 블록에도 `cache` 와 `loop` 등을 개별 선언합니다.



## 6. 페더레이션 유산

> `FEDERATIONS` 변수는 이미 개발이 멈춘 기능을 위해 있던 유산입니다. 변수도 그 기능도 사라졌습니다.

과거 배포 템플릿의 `FEDERATIONS` 변수는 쿠버네티스 federation v1 을 지원하던 설정이었습니다.
`federation` 플러그인은 1.7.0 에서 제거됐고 지금 기본 빌드 목록에 없습니다.[^plugincfg][^fedgone] 옛 설정에서 `FEDERATIONS` 를 만나면 없는 기능으로 읽고 넘어가면 됩니다.
현재 다중 클러스터 서비스는 Multi-Cluster Services API 규격을 따르는 `multicluster` 옵션으로 지원합니다.[^k8splugin][^k8splugin150]



## 결정 치트시트

> 기본 Corefile 의 각 줄을 지울 수 있는 조건입니다.

| 줄 | 왜 있나 | 지울 수 있는 조건 |
|----|---------|------------------|
| `errors` | 오류를 로그에 남긴다 | 지우지 않는다 · 문제 추적이 어려워진다 |
| `health` | kubelet 이 감시할 엔드포인트 | 지우지 않는다 · 프로브가 이것을 부른다 |
| `pods insecure` | kube-dns 하위 호환 | 폐기된 파드 레코드가 필요 없으면 지운다 |
| `upstream` | CNAME 을 되질의해 푼다 | 반드시 지운다 · 지금은 넣으면 CoreDNS 가 뜨지 않는다 |
| `fallthrough in-addr.arpa ip6.arpa` | 모르는 IP 의 PTR 을 체인 아래로 | 서비스·파드 CIDR 을 전부 열거했으면 지울 수 있다 |
| `prometheus :9153` | 메트릭을 네트워크에 연다 | Prometheus 로 긁지 않으면 지운다 |
| `forward . …` | 나머지 질의를 상류로 | 역방향 CIDR 을 전부 열거했고 외부 이름을 풀 필요가 없으면 |
| `cache 30` | 응답을 메모리에 둔다 | 클러스터 안 질의만 다루면 값이 거의 없다 |
| `loop` | 질의 루프를 탐지하고 종료 | 지우지 않는다 · 디버깅 불가능한 실패를 막는다 |
| `reload` | Corefile 을 다시 읽는다 | 남기되 문법 오류를 조심한다 |
| `loadbalance` | A·AAAA·MX 를 섞는다 | 헤드리스를 안 쓰면 이득이 적다 |
| 헤드리스를 아무도 안 쓴다 | — | `noendpoints` 로 Endpoints watch 를 끈다 |
| 큰 서비스에서 API 서버가 힘들어한다 | — | `apiserver_qps` 계열로 요청 속도를 조인다 |



## 적용 관점

> 이 편은 도는 클러스터가 있으면 ConfigMap 하나를 열어 대조하는 것으로 끝납니다.

**한 가지 실행**: 지금 도는 Corefile 을 꺼내 4절의 열두 줄과 대조합니다. 명령은 `kubectl -n kube-system get configmap coredns -o yaml` 입니다. `upstream` 이 남아 있는지, `pods insecure` 가 필요한지, 역방향 CIDR 이 실제 값으로 채워졌는지 봅니다. 이 셋으로 클러스터 설정의 권고 버전을 파악할 수 있습니다.

**한 가지 확인**: 그 Corefile 을 고치기 전에 실험 클러스터나 복제 배포에서 먼저 시험합니다. ConfigMap 만 다른 이름으로 복제해서는 아무것도 시험되지 않습니다. 그 ConfigMap 을 마운트해 뜨는 CoreDNS Deployment 가 따로 있어야 문법 오류가 드러납니다. 잘못된 Corefile 은 실행 중인 파드는 유지하지만 새로 시작하는 파드의 기동을 막기 때문입니다.

Spring 애플리케이션 관점에서는 `cache 30` 이 판단 지점이 됩니다. 클러스터 안 서비스 이름만 부르는 애플리케이션이라면 이 캐시가 응답 시간에 기여하는 바가 거의 없습니다. 그보다 먼저 CoreDNS 에 질의가 가는 빈도를 정하는 것은 JVM 의 이름 캐시입니다. OpenJDK 는 `networkaddress.cache.ttl` 을 따로 정하지 않으면 성공한 조회를 30초 동안 들고 있습니다. 이 값은 DNS 응답의 TTL 과 상관없이 적용됩니다.[^jdkttl]

그래서 `RestTemplate` 이나 `WebClient` 가 `http://orders.default.svc.cluster.local` 을 초당 수백 번 불러도 JVM 하나가 CoreDNS 에 묻는 것은 30초에 한 번꼴입니다. 레코드 TTL 을 5초로 줄여도 그 JVM 이 새 주소를 아는 시점은 30초 캐시가 정합니다. 외부 API 를 자주 부른다면 반대로 이 캐시가 실제로 일합니다.

## 정답 (자답 후 펼치기)

### 정답 1 — 컨트롤러와의 차이

같은 점은 API 서버에 watch 를 걸고 자원 변화를 좇는다는 것입니다. 다른 점은 API 서버에 아무것도 되쓰지 않는다는 것입니다. 조정 루프의 셋째 걸음인 조치와 `Status` 기록을 둘 다 하지 않는 읽기 전용 소비자입니다.

### 정답 2 — `cache 30` 을 지우면

클러스터 안 이름은 거의 달라지지 않습니다. 레코드가 이미 메모리에 있는 쿠버네티스 자원에서 즉석으로 만들어지므로, 캐시가 아껴 주던 것은 해싱과 조회 비용만큼입니다. 외부 이름은 느려집니다. 매 질의가 `forward` 를 거쳐 상류 네임서버까지 네트워크를 타야 하기 때문입니다. 그래서 지금 kubeadm 은 캐시를 지우지 않고 클러스터 도메인만 `disable` 로 뺍니다.

### 정답 3 — 헤드리스를 쓰는데 `noendpoints` 를 켜면

StatefulSet 파드 이름을 묻는 질의가 전부 `NXDOMAIN` 을 받습니다. `noendpoints` 는 Endpoints 감시를 꺼서 헤드리스 서비스와 엔드포인트 질의에 답할 재료를 없애기 때문입니다. 끄기 전에 볼 것은 헤드리스를 쓰는 워크로드가 하나라도 남아 있는지입니다.

### 정답 4 — Endpoints 가 비싼 두 요인

첫째, Endpoints 자원 하나가 서비스 하나의 모든 엔드포인트 주소를 준비 여부와 무관하게 담아서 백엔드가 많을수록 객체가 커집니다. 둘째, watch 는 자원이 바뀔 때마다 객체를 통째로 보내는데 백엔드가 많을수록 그중 하나가 바뀔 확률이 높습니다. 둘이 같은 방향으로 나빠져서 큰 객체가 더 자주 전송됩니다. 지금 CoreDNS 는 EndpointSlice 를 감시해 조각 단위로 받으므로 이 비용이 크게 줄었습니다.

### 정답 5 — `fallthrough` 를 지우면

역방향 존을 넓게(`in-addr.arpa`·`ip6.arpa`) 잡아 둔 경우, `kubernetes` 플러그인이 클러스터와 무관한 IP 의 PTR 요청까지 전부 삼킵니다. 체인 아래의 `forward` 로 내려가지 못하므로 외부 IP 의 역방향 조회가 답을 못 받습니다.

### 정답 6 — Corefile 순서와 처리 순서

바뀌지 않습니다. 플러그인 사이의 처리 순서는 컴파일 시점에 고정됩니다. 다만 한 서버 블록 안에 여러 인스턴스를 허용하는 플러그인이라면 그 인스턴스들 사이의 순서는 의미가 있습니다.

### 정답 7 — 스텁 도메인이 서버 블록인 이유

CoreDNS 가 질의를 가장 길게 일치하는 서버 블록으로 보내기 때문입니다. `corp.example.com:53` 블록은 `.:53` 블록보다 라벨이 길어서 그 도메인의 질의를 가져갑니다. 스텁 도메인이라는 별도 개념 없이 기존 규칙 하나로 같은 일이 됩니다.

### 정답 8 — 캐시의 상한과 하한

외부 이름은 5초, 클러스터 안 이름은 0초입니다. 외부 응답의 TTL 2초는 상한 30 에 걸리지 않지만 최소 캐시 기간 5초에 받쳐 5초로 올라갑니다.[^cache] 클러스터 안 이름은 `disable success cluster.local` 때문에 성공 응답이 캐시에 아예 들어가지 않으므로, 질의마다 `kubernetes` 플러그인이 메모리에서 새로 만듭니다.
