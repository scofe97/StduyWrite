# Learning CoreDNS — 노트 보강 후보

> 장별 Phase 1~2(예측→채점·점검)에서 드러난 노트의 빈 곳과 학습자 오개념을 번호로 쌓는다. 그때마다 보강을 맡기지 않고, 마지막 장을 마친 뒤 통합 보강 프롬프트 한 장으로 묶는다.
> 후보마다 고칠 절, 학습자가 실제로 한 말, 근거를 적는다. AI 가 제시한 해석은 학습자 생각으로 적지 않는다.

## 전체에 걸친 요청

1. **현행 기준을 본문으로, 원서 시점은 한 줄로** (2026-10-30, 1장 Phase 1 질문 7)
   - 학습자 말: "원서기준과 현대 기준이 다른데 현대 기준으로만 작성해줘 — 과거에는 이랬다가 수정했다 정도만 언급"
   - 대상: 18편 전체. 지금은 원서 서술을 본문에 두고 현행 차이를 뒤 문단·"버전 차이"로 덧붙이는 구조(예: 01-01 §5 표 1-1 뒤 `:161~167`)
   - 보강 때 정할 것: 정오·버전 차이 블록을 어디까지 줄일지, README 의 "버전 차이 기록" 집계를 어떻게 바꿀지

## 1장 (01-01)

2. **§5 표 1-1 의 "동적 업데이트" 줄이 현행 대조에서 빠짐**
   - 근거: `01-01:161` 은 "세 줄이 달리 읽힌다"며 완전 재귀·DoT·DNSSEC 만 현행과 대조한다. 동적 업데이트 줄은 2019년 값 그대로다
   - 할 일: 현행 공식 플러그인 목록·소스로 RFC 2136 UPDATE 지원 여부를 1차 자료로 확인해 한 줄 추가
   - 학습자 말: "업데이트가 CoreDNS 가 안된다고 알고 있다 (API로 직접 수정이 안되는걸로 알고있음, 내부에 직접 넣거나 적어야하는듯?)" — etcd 플러그인(5장)처럼 외부 저장소의 API 로 레코드를 바꾸는 길과 DNS UPDATE 메시지를 받는 기능을 구분하는 한 줄이 §5 에 있으면 좋다

3. **§1 "이름이 바뀌는 IP 를 가리킨다"에 TTL 단서가 없음**
   - 학습자 말(질문 2): "뒤의 IP가 계속 바뀌어도 요청하는 입장에서는 이 DNS로 요청하면 자동으로 매핑이됩니다"
   - 할 일: §1 끝에 "캐시된 답은 TTL 동안 그대로 쓰이고 서버가 변경을 밀어 주지 않는다"는 한 줄 + 05-01 링크

4. **§3 "안 켠 플러그인"에서 '실행 파일에 들어 있음'과 '질의가 지나감'의 구분이 약함**
   - 학습자 말(질문 4): "플러그인 자체가 외부에서 가져오는 의존성이라 그런거 아닐까요?"
   - 할 일: 기본 빌드 플러그인은 대부분 in-tree 이고 실행 파일에 들어 있지만, Corefile 에 적은 것만 질의 경로에 놓인다는 문장. 공격 표면 정의를 예시와 함께

5. **§4 "메모리를 관리합니다"가 두 장치를 뭉뚱그림**
   - 학습자 말(질문 5 설명 뒤): "자동관리한다 (GC처리 말하는거지?)"
   - 할 일: dangling pointer 는 GC, 버퍼 오버플로는 실행 중 범위 검사(bounds check → panic)로 나눠 적기

6. **"쿠버네티스가 CoreDNS를 쓰는 이유"를 구현 언어로 오해할 여지**
   - 학습자 말(역방향 설명): "Bind는 c언어로 되어있고 고언어 환경인 쿠버네티스와 어울리지않아"
   - 근거: `01-01:79` 는 가장 큰 이점을 "etcd나 쿠버네티스 같은 기반 시설과 통신하는 능력"으로 적고, Go 는 §4 에서 메모리 안전성 축으로만 다룬다. 두 축을 잇는 문장이 없다
   - 할 일: §1 또는 §6 에 "선택 이유는 같은 언어가 아니라 쿠버네티스 API 를 직접 읽는 통합(`kubernetes` 플러그인)"이라는 한 줄. 질문 5 의 GC 혼동(5번)이 역방향 설명에서도 다시 나옴
