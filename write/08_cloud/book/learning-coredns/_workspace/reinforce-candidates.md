# Learning CoreDNS — 노트 보강 후보

> 장별 Phase 1~2(예측→채점·점검)에서 드러난 노트의 빈 곳과 학습자 오개념을 번호로 쌓는다. 장의 Phase 2 를 마칠 때마다 메인(학습 통합 제어 창)에 보고해 보강을 진행시킨다(학습자 지시 2026-11-01. 처음엔 마지막에 한 번에 묶기로 했다가 바꿈). 1장 후보 1~8 은 2026-11-01 보고.
> 후보마다 고칠 절, 학습자가 실제로 한 말, 근거를 적는다. AI 가 제시한 해석은 학습자 생각으로 적지 않는다.

## 전체에 걸친 요청

1. **현행 기준을 본문으로, 원서 시점은 한 줄로** (2026-10-30, 1장 Phase 1 질문 7)
   - 학습자 말: "원서기준과 현대 기준이 다른데 현대 기준으로만 작성해줘 — 과거에는 이랬다가 수정했다 정도만 언급"
   - 대상: 18편 전체. 지금은 원서 서술을 본문에 두고 현행 차이를 뒤 문단·"버전 차이"로 덧붙이는 구조(예: 01-01 §5 표 1-1 뒤 `:161~167`)
   - 보강 때 정할 것: 정오·버전 차이 블록을 어디까지 줄일지, README 의 "버전 차이 기록" 집계를 어떻게 바꿀지

## 1장 (01-01)

2. **§5 표 1-1 의 "동적 업데이트" 줄이 현행 대조에서 빠짐**
   - 근거: `01-01:161` 은 "세 줄이 달리 읽힌다"며 완전 재귀·DoT·DNSSEC 만 현행과 대조한다. 동적 업데이트 줄은 2019년 값 그대로다
   - 할 일: 현행 공식 플러그인 목록·소스로 RFC 2136 UPDATE 지원 여부를 1차 자료로 확인해 한 줄 추가
   - 학습자 말: "업데이트가 CoreDNS 가 안된다고 알고 있다 (API로 직접 수정이 안되는걸로 알고있음, 내부에 직접 넣거나 적어야하는듯?)" — etcd 플러그인(5장)처럼 외부 저장소의 API 로 레코드를 바꾸는 길과 DNS UPDATE 메시지를 받는 기능을 구분하는 한 줄이 §5 에 있으면 좋다

3. **§1 "이름이 바뀌는 IP 를 가리킨다"에 TTL 단서가 없음**
   - 학습자 말(질문 2): "뒤의 IP가 계속 바뀌어도 요청하는 입장에서는 이 DNS로 요청하면 자동으로 매핑이됩니다"
   - 할 일: §1 끝에 "캐시된 답은 TTL 동안 그대로 쓰이고 서버가 변경을 밀어 주지 않는다"는 한 줄 + 05-01 링크

4. **§3 "안 켠 플러그인"에서 '실행 파일에 들어 있음'과 '질의가 지나감'의 구분이 약함**
   - 학습자 말(질문 4): "플러그인 자체가 외부에서 가져오는 의존성이라 그런거 아닐까요?"
   - 할 일: 기본 빌드 플러그인은 대부분 in-tree 이고 실행 파일에 들어 있지만, Corefile 에 적은 것만 질의 경로에 놓인다는 문장. 공격 표면 정의를 예시와 함께
   - Phase 2 재확인(§3 만 읽고 답함): "이 플러그인이라면 이제 외부에서 가져오는 정보를 말하는 것 같습니다" — "플러그인 = 외부 정보·외부 의존성" 오개념이 질문 4, 역방향 설명("외부에서 가져오는 기능이 플러그인"), Phase 2 에서 세 번 나옴. §3 첫머리에 "플러그인 = 기능 한 칸(캐시·로그처럼 바깥과 무관한 것 포함)"이라는 정의가 필요. 안전성 문장(공격 표면)은 §3 에 있으나 학습자가 뽑아내지 못함 — 원서가 이유를 풀지 않아 "노트의 읽기"로 한 문장에 묻혀 있는 탓으로 보임

5. **§4 "메모리를 관리합니다"가 두 장치를 뭉뚱그림**
   - 학습자 말(질문 5 설명 뒤): "자동관리한다 (GC처리 말하는거지?)"
   - 할 일: dangling pointer 는 GC, 버퍼 오버플로는 실행 중 범위 검사(bounds check → panic)로 나눠 적기
   - Phase 2 재확인(§4 만 읽고 답함): "GC 언어인 고에서는 이런 위험이 덜하기 때문에", "C나 러스와 같은 경우에는 직접 제어를 하지만 사람이 실수한 경우 이런 게 노출" — GC 혼동 세 번째, 그리고 Rust 를 C 와 같은 쪽으로 묶음. "메모리 안전 = GC" 로 읽히지 않도록, GC 없이 메모리 안전을 얻는 언어(Rust)가 있다는 한 줄도 후보. 학습자가 덧붙인 "민감한 정보 노출"은 §4 에 없음(노트는 서버 중단·OS 장악만 적음) — 버퍼 과다 읽기로 메모리가 새는 경우를 넣을지는 보강 때 판단

6. **"쿠버네티스가 CoreDNS를 쓰는 이유"를 구현 언어로 오해할 여지**
   - 학습자 말(역방향 설명): "Bind는 c언어로 되어있고 고언어 환경인 쿠버네티스와 어울리지않아"
   - 근거: `01-01:79` 는 가장 큰 이점을 "etcd나 쿠버네티스 같은 기반 시설과 통신하는 능력"으로 적고, Go 는 §4 에서 메모리 안전성 축으로만 다룬다. 두 축을 잇는 문장이 없다
   - 할 일: §1 또는 §6 에 "선택 이유는 같은 언어가 아니라 쿠버네티스 API 를 직접 읽는 통합(`kubernetes` 플러그인)"이라는 한 줄. 질문 5 의 GC 혼동(5번)이 역방향 설명에서도 다시 나옴

7. **§4 에 도식이 없음**
   - 학습자 말(Phase 2): "4번 목차에 대해서 도식이 없는데 도식 하나 있으면 좋을 것 같네요"
   - 후보 그림: 바깥 패킷 → 파싱 코드의 칸 넘기기 → C 는 옆 메모리 덮어씀(서버 중단·OS 장악) / Go 는 범위 검사에서 panic, 반납 메모리는 GC — 5번의 두 장치 구분을 그림이 받치게

8. **§5 표 1-1 묶음 읽기가 현행과 어긋남, DoT 와 DNSSEC 구분 부재**
   - 근거: 표 아래 "CoreDNS가 앞서는 줄도 셋 … DoT, 곧 컨테이너와 클라우드 쪽 기능" 문단은 원서 시점 표를 그대로 묶음. 같은 절 뒤쪽은 BIND 9.18(2022)부터 DoT·DoH 지원이라 적으므로, 현행으로는 CoreDNS 쪽 우위가 연동 둘뿐이다. DoT 는 컨테이너·클라우드 기능도 아니다(1번 현행 우선 요청과 함께 처리)
   - 학습자 말: "DNS 색을 지원할 때 DNS 서버 TLS를 지원 안 하는 게 무슨 차이지?" — DNSSEC(답의 진위·무결성, 암호화 없음)과 DoT(전송 구간 암호화, 답의 출처 증명 없음)가 다른 문제를 푼다는 한 문단 필요

## 2장 (02-01) — 02-02 를 마친 뒤 2장 묶음으로 보고

9. **§2 본문에 `NS` 레코드와 글루가 이름으로 나오지 않음**
   - 근거: §2 는 위임 뒤 부모에 남는 것을 "`cs.berkeley.edu` 안의 정보를 어디서 찾을 수 있는지뿐"이라고만 적는다. 글루는 문서 끝 결정 치트시트(`02-01:255`)에 한 줄 나올 뿐이다
   - 학습자 말(Phase 1 질문 2): 순환 문제와 "부모가 IP 도 들고 있어야 한다"는 해법은 스스로 예측함. Phase 2(§2 만 읽고): "자식서버가 본인의 부모정보를 이제 만약 글루서버를 통해서 가져오려고 할 때" — 방향이 거꾸로(질의하는 첫 서버가 부모에게서 자식 네임 서버의 이름·IP 를 받아 감)
   - 할 일: §2 위임 문단 뒤에 "부모에 남는 것 = 자식 존의 `NS` + (네임 서버 이름이 자식 존 안에 있을 때만) 그 주소인 글루" 한 문단. 바깥 이름이면 글루 없이 첫 서버가 루트부터 한 번 더 찾는다는 대조도

10. **"존(이름 범위)"과 "네임 서버(대답하는 컴퓨터)"의 구분이 노트에 없음**
    - 학습자 말(Phase 1 질문 2 뒤): "근데 .net으로 끝나는데 왜 애드존이지?", "존과 이 네임 서버의 이름. 이 구분이 좀 어떤 구조인지 살짝 헷갈리려네요"
    - 할 일: §2 또는 §4 첫머리에 "존은 이름의 범위, 네임 서버는 그 범위를 답하는 컴퓨터이고 네임 서버의 이름은 어느 도메인 아래에 있어도 된다(`a.edu-servers.net` 이 `edu` 를 맡음)" 한 줄. AI 가 든 비유(관할 구역과 다른 도시의 콜센터)는 학습자가 받아들였음

11. **"점(라벨)마다 존이 생긴다"는 오개념을 막는 문장이 약함**
    - 학습자 말(Phase 2, §2 만 읽고): "www.google.com이라 했을 때 이제 3개의 존에 묶여있는 거죠. 이제 com과 google.com과 www.google.com", 이어서 "그럼 이게 구글.com과 com이 똑같은 존일 수도 있다는 건가?", 마지막 확인 질문엔 "잘 모르겠네요"
    - 근거: §2 에 "위임이 없다면 도메인과 존은 같은 노드를 담습니다"가 있으나 학습자가 이 문장에서 "존은 위임한 곳에서만 갈라진다"를 뽑아내지 못함
    - 할 일: "존은 점이 아니라 위임에서 갈라진다. `www.google.com` 은 보통 `google.com` 존 안의 레코드 한 줄이다. 도메인을 등록하는 일이 곧 TLD 존에 `NS` 를 넣는 위임이다" 를 예와 함께

12. **리졸버(OS 클라이언트) · 첫 서버(재귀 서버) · 루트 서버의 역할 구분 표가 없음**
    - 학습자 말(Phase 1): "통신사 DNS가 8.8.8.8 이제 루트 DNS라는 의미인가요?", "리졸버가 따로 조회한다는 게 … 리졸버 컴프(resolv.conf)를 조회한다는 건가? 아니 etc/host?", "즉 일종의 작은 프로세스라는 개념이군", "쿠버네티스 클러스에서는 이제 DHCP가 코어 DNS에 있다는 말인가요?"
    - 근거: §5 는 "리졸버"를 OS 의 클라이언트 쪽 절반(libc·glibc)으로, §6 은 재귀를 지는 쪽을 "첫 서버"로 부른다. 요즘 흔한 말(스텁 리졸버·재귀 리졸버)과 대응, 누가 첫 서버를 정해 주는가(DHCP, 쿠버네티스에서는 kubelet 이 파드 `/etc/resolv.conf` 에 적음)가 없다. AI 설명 중 "리졸버가 루트부터 따로 찾는다"고 노트와 다른 뜻으로 말해 혼동을 키운 일도 있었음
    - 할 일: §5 끝 또는 §6 첫머리에 세 역할 표(이름·하는 일·예: libc 리졸버 / 통신사 DNS·8.8.8.8·CoreDNS / a~m.root-servers.net). 애니캐스트는 §7 이 언급하므로 cntd 04-04 §1·05-02 §5 링크 후보(학습자가 "IP는 기계당 한 대 아니었나"라고 물음)

13. **재귀 질의·반복 질의와 포워더의 관계가 한 그림에 없음**
    - 학습자 말(Phase 2, §6 만 읽고): "제기적인 질의를 통해서 이제 저희가 요청한 www.google.com을 이제 IP를 알아냅니다"(두 질의가 섞임), 포워더 이름이 직관과 반대인 이유는 "잘 모르겠습니다", 설명 뒤 "이게 루트 서버에 넘기는 거하고 뭐 똑같은 말이죠"(포워더로 가는 재귀 질의와 루트로 가는 반복 질의를 같은 것으로 봄)
    - 할 일: §6 도식(referral-chain)에 포워더 갈래를 덧붙이거나, "루트에는 반복 질의(참조만 받음) / 포워더에는 재귀 질의(끝까지 맡김)" 대조 한 줄. 1장 `forward` 플러그인(넘기는 동작)과 노트의 포워더(넘겨받는 서버)가 이름이 엇갈린다는 한 줄도 후보

## 2장 (02-02)

14. **§4 MX·SRV 를 `###` 로 나누고 동작 규칙을 앞에 둘 것**
    - 학습자 말(Phase 2, §4 만 읽고): "이 네번째 문단에 대해서 내용을 샵샵샵 단위로 좀 나눠 볼 수도 있지 않을까? 그리고 약간 너무 설명이 장황한 것 같기도 하고". 답은 정의(16비트·0~65535, "MX 를 넓힌다")만 옮기고 동작(낮은 값부터 시도, 같은 우선순위 안에서 가중치 비례)은 빠짐. MX 가 없을 때 규칙은 "주소레코드로 돌아간다. 금지되고"로 조건이 흐려짐
    - Phase 1 질문 3(SRV 칸 예측)은 "모르겠는데", 이어서 "MX와 SRV나 이번에 처음 들었는데 나중에 좀 더 자세하게 설명해 주세요"
    - 할 일: `### MX — 선호도 하나로 순서` / `### SRV — 우선순위로 후보, 가중치로 비율, 포트` 로 나누고 각 `###` 첫 문장을 동작 규칙으로. "MX 0개면 주소가 선호도 0 MX, 1개라도 있으면 주소 배달 금지"를 한 문장으로 앞에. 현행 한 줄 후보: 웹은 SRV 대신 HTTPS·SVCB(RFC 9460, 2023), 쿠버네티스는 이름 붙인 포트에 SRV(6장 링크)

15. **§7 시리얼 — "존을 고치면 시리얼을 올려야 한다, 안 올리면 보조 서버가 기한 없이 옛 데이터"가 문장으로 없음**
    - 학습자 말(Phase 1 질문 5): "1시간 뒤면 이제 바뀐 걸 확인하고 보조 서버도 이제 다시 바꿔주겠죠"(내용 비교로 오해), 채점 뒤 "시리얼을 깜빡한다는 게 정확히 무슨 말이었지?", Phase 2 에서 다시 "시리얼을 뺀다는 게 무슨 말인가?". 세 번째 확인에서 refresh·retry·expire 순서는 노트로 맞게 말함
    - 근거: `### 존 전송을 좌우하는 네 칸` 은 "마스터 쪽 시리얼이 더 높은지 확인"까지만 적고, 시리얼을 안 올렸을 때 결과(확인은 매번 성공해 expire 도 안 걸림, 주·보조 답이 갈림)와 날짜형 시리얼 관례가 없음
    - 할 일: 그 `###` 끝에 실패 사례 한 문단 + 시리얼 관례 한 줄. SOA 앞 두 칸(MNAME·RNAME)을 학습자가 "자식 노드·서버"로 읽었으니 "서버가 아닌 메모"라는 표현을 더 앞으로

16. **문체 — 핵심 문장 먼저, 책 옮기듯 늘어진 문단 줄이기 (02-02 전반)**
    - 학습자 말(Phase 2, §7 점검 뒤): "문장이 좀 긴 것 같아요. 이게 내가 알고 싶은 핵심 정보만 좀 그냥 문서에 적혀있으면 좋겠는데 약간 책 쓰듯이 적어서 그런가? 물론 책 쓰듯이 쓰면 좋긴 한데 핵심 문장만 좀 있으면 좋을 것 같네요"

17. **§2 생략 규칙 — 위험(줄 끼워 넣기·앞 공백)이 노트에 없음, §3 CNAME 꼭대기 금지의 실무 결과 없음**

    - 할 일: §2 에 "줄을 끼워 넣으면 아래 빈칸 줄이 다른 이름에 붙는다" 한 줄. §3 규칙 2 뒤에 "그래서 꼭대기(`example.com`)는 CDN 이름을 CNAME 으로 못 가리킨다 → 업체별 ALIAS·flattening(비표준)" 한 줄. `www` 없는 이름을 존 꼭대기라고 부르는 것도 함께

## 3장 (03-01)

18. **§6 REFUSED — DNS 응답 코드와 연결 거절(`connection refused`)·DROP 구분을 참조 링크로**
    - 학습자 말(Phase 1 질문 7 뒤): "REFUSED는 방화벽 거부도 있는데 이렇게 DNS가 없어서도 거부할 수 있는 걸 봤는데 이거 어떻게 구분함", 이어서 "REFUSED 관련은 다른 문서에서도 다르니 참고로 넘기거나 참조해서 보게 해주면 좋을 것 같습니다"
    - 근거: §6 은 "세 조건을 모두 채우는 서버 블록이 하나도 없으면 … 거부(`REFUSED`)로 답합니다" 한 문장뿐. 어떤 블록도 듣지 않는 포트는 CoreDNS 가 열지 않아 DNS 응답 자체가 없다는 점도 없음
    - 할 일: 그 문장 뒤에 한두 줄 — REFUSED 는 DNS 응답 안의 응답 코드(`dig` 의 `status: REFUSED`)이고, 포트가 닫혔거나 방화벽이 막으면 DNS 응답 없이 `connection refused`·timeout 으로 끝난다. 설명은 풀지 말고 [networking-and-kubernetes 02-06 §1 DROP과 REJECT](../../networking-and-kubernetes/02-06.커널%20네트워킹%20실습%202%20—%20막고,%20진단하고,%20나누기.md) 로 넘긴다(인코딩은 반영 때 확인)

    - 학습자 말(Phase 2, §2 점검 때): "명령줄 옵션 여덟 -> 여기서 명령줄 예시도 넣어줘"

## 4장 (04-01)

20. **§1 — "온전한 존"과 존 자체의 정의가 없음, 존과 서버 블록·Corefile 이 구분되지 않음**

    - 할 일: §1 첫머리에 두세 문장 — 존은 이름 범위 하나와 그 레코드 묶음(데이터), 서버 블록은 그 범위의 질문을 받을 플러그인을 정하는 설정, Corefile 은 서버 블록 묶음. `foo.example { file db.foo.example }` 한 줄로 라벨(거르는 표시)과 존 데이터(파일)를 가르는 예. 정의는 [02-01](./02-01.위임이%20그은%20경계가%20질의%20경로를%20정한다.md)·[03-01](./03-01.Corefile은%20라벨로%20서버를%20가른다.md) 링크로 넘김(인코딩은 반영 때 확인). "온전한 존 = `SOA` 를 가진 존, `SOA` 는 권한 시작 선언이자 보조 서버가 변경을 가리는 시리얼" 한 문장

21. **§2 — 상대 이름 파일 하나로 여러 존: origin 이 "그 파일을 어느 존으로 읽느냐"에서 정해진다는 연결이 없음**

    - 근거: §2(`:95-103`)는 "레코드가 전부 상대 도메인 이름이면 파일 하나로 여러 존" 과 "내용이 똑같기를 바랄 때" 만 적음. 왜 그런지(같은 파일을 존마다 다른 origin 으로 읽음)와 점으로 끝나는 이름이 섞이면 어떻게 되는지가 없음
    - 할 일: `:95` 뒤에 작은 표 하나 — 파일에 적힌 `www` 와 `www.foo.example.` 이 `foo.example`·`bar.example` 으로 읽힐 때 각각 무엇이 되는지. origin 규칙은 [02-02 NAME 칸](./02-02.레코드%20한%20줄을%20읽으면%20존%20파일이%20읽힌다.md) 링크

22. **§5 — `0.0.0.0` 으로 보내는 것이 왜 광고 차단이 되는지 없음**
    - 학습자 말(Phase 2 §5 점검 뒤): "광고에 쓰이는 도메인 이름을 호스트 테이블에 담아 읽은 뒤 보낸다?"
    - 근거: §5(`:236`)와 결정 치트시트(`:315`)가 "`0.0.0.0` 으로 보내는 용례" 만 적고, 그 주소로 답하면 클라이언트가 광고 서버에 닿지 못한다는 결과를 적지 않음. Phase 1 에서 학습자는 hosts 를 "노드에서 직접 관리하는 도메인 IP" 로 읽음(CoreDNS 가 읽으면 묻는 모든 클라이언트가 받는다는 점도 없음)
    - 할 일: `:236` 에 한 문장 — 광고 도메인의 답을 `0.0.0.0` 으로 주면 클라이언트가 실제 광고 서버 주소를 얻지 못해 광고를 불러오지 못한다(그래서 차단). `/etc/hosts` 는 그 컴퓨터만 보지만 CoreDNS 의 `hosts` 는 CoreDNS 에 묻는 모든 클라이언트에 적용된다는 한 줄. `0.0.0.0` 접속 시 OS 동작은 반영 때 확인하고 단정하지 않음

    - 할 일: §6 첫머리 요약 다음에 흐름 도식 한 장(Route 53 원본 → AWS API, `refresh` 1분 → CoreDNS 사본 → 클라이언트 질의). "DNS 존 전송이 아니라 API 라서 IP·글루가 아니라 ID·자격증명이 필요하다" 한 문장. `:285` 뒤에 Public/Private 두 줄 정의와 `www.corp.example` 이 밖에서는 공인 주소, 안에서는 내부 주소로 가는 예. Public/Private 정의는 AWS 공식 문서로 확인 후 각주

### 27. `02-02` 「부정 응답을 좌우하는 한 칸」 — CoreDNS 에서는 MINIMUM 이 아니라 SOA 레코드 TTL 이 부정 캐시 시간을 정함

- 학습자 말: 처음 예측 "시리얼 넘버가 정한다, 30초 뒤(최대 32초)". 변형 예측 "20 은 처음부터 있었는데 30 을 따랐으니 300".
- 근거: S3 실측(CoreDNS 1.15.0, `cache` + `file`) — `$TTL 30`·MINIMUM 20 에서 NXDOMAIN 의 SOA TTL 30 → 14·11·8·5·2 → 새 답. `$TTL 300`·MINIMUM 20 에서 SOA TTL 300 → 297. RFC 2308 §5 규칙(둘 중 작은 값)이면 20 이어야 함. `file` 은 SOA 를 레코드 TTL 그대로 실어 보내고, `cache` 는 메시지 안 레코드 TTL 의 최솟값만 씀(`plugin/pkg/dnsutil/ttl.go` `MinimalTTLWithMaximum`, MINIMUM 칸을 읽지 않음).
- 할 일: 그 절 끝에 "CoreDNS 의 `cache` 는 MINIMUM 을 보지 않고 응답에 실린 SOA 레코드의 TTL 을 쓰므로, 부정 캐시를 줄이려면 SOA 의 TTL 을 낮추거나 `cache` 의 `denial` 로 상한을 둔다" 한 문단. MINIMUM 은 RFC 2308 을 따르는 다른 리졸버가 읽는다는 한 줄. 방법 셋(파일 앞 `$TTL 30` 뒤 `$TTL 300`, `@ 30 IN SOA`, `cache { denial 9984 30 }`)은 2026-11-03 실측 확인.

### 29. `04-01` 「hosts」 fallthrough 문단 — 넘기지 않을 때 못 찾은 이름은 NXDOMAIN 이 아니라 SERVFAIL

- 학습자 말(S7): 처음엔 "파일에 둘 다 있으니 둘 다 정상"이라고 봄. `fallthrough` 를 넣은 뒤에는 "api 는 존 파일 값 .40 으로 온다"고 예측(실제는 hosts 의 .99).
- 근거: S7 실측(CoreDNS 1.15.0) — `shop.example { hosts { 198.51.100.99 api.shop.example }  file db.shop.example }` 에서 db 는 SERVFAIL. hosts 에 SOA 가 없어 NXDOMAIN 을 만들 수 없다(`plugin/hosts/hosts.go:72-74` 주석). `03-02` 「fallthrough」 는 "없으면 NXDOMAIN 이나 빈 응답"이라고 일반화하는데, SOA 가 없는 hosts 는 이 규칙에서 벗어난다. `fallthrough` 뒤에도 api 는 hosts 답(TTL 3600, AUTHORITY 0)이었다. `04-01` 277줄은 "답을 못 찾았을 때 넘긴다"고 맞게 적었지만, 찾은 이름은 계속 hosts 가 답한다는 반대쪽은 적지 않았다.
- 할 일: `04-01` hosts fallthrough 문단 끝에 두 문장 — "넘기지 않으면 호스트 테이블에 없는 이름은 SERVFAIL 로 끝난다. hosts 에는 SOA 가 없어 NXDOMAIN 을 만들 수 없기 때문이다." "넘기더라도 테이블에 있는 이름은 hosts 가 답하므로, 같은 이름을 존 파일 값으로 되돌리려면 그 줄을 지워야 한다." `03-02` 는 다른 창이 고치는 중이라 손대지 않고, 필요하면 "SOA 가 있는 플러그인 기준"이라는 한정만 나중에 검토.

### 34. `06-01` §2 「폴링을 대신하는 watch」 — watch 가 연결 위에서 어떻게 생겼는지

### 35. `06-01` §4 「`clusterIP` 한 필드와 부하 분산 위치」 — 가상 IP 가 어떻게 통하고 왜 겹치지 않는지

- 학습자 말: "A 가 사실 저 IP 가 실제 통신되는지도 모르고, 겹치는지도 모르지 않는가?", "DNAT 였나? MASQUERADE 였던 걸로 기억하는데", "nftables 가 뭔가?". Q5 는 부하 분산 위치를 말하지 못해 몰랐던 사실.
- 근거: 노트는 kube-proxy 가 규칙을 만들고 무작위로 고른다고만 적고, 가상 IP 가 어느 인터페이스에도 없고 노드에서 목적지를 바꾼다(DNAT)는 점, ClusterIP 가 서비스 전용 대역에서 API 서버가 겹치지 않게 나눠 준다는 점이 없다. 이 내용은 `networking-and-kubernetes/02-03` §3 「kube-proxy의 Service 규칙」(최소 DNAT 경로)과 같은 책 nftables 설명에 있다.
- 할 일: §4 kube-proxy 문단 뒤에 두 문장과 링크 — 가상 IP 는 붙은 곳이 없고 패킷이 노드를 떠나기 전에 DNAT 로 파드 IP 가 된다, 준비된 엔드포인트만 규칙에 들어간다. ClusterIP 는 `--service-cluster-ip-range` 대역에서 할당되어 겹치지 않는다(공식 문서 「Service」 확인 뒤). 자세한 규칙은 nak 02-03 링크로 넘긴다.
- Phase 2 덧붙임(2026-11-05): "파드가 바뀌면 누가 알아채나"에서 ClusterIP 쪽을 빠뜨림. §4 는 헤드리스의 대가(능동 재질의)만 적고, ClusterIP 에서는 kube-proxy 가 EndpointSlice 를 watch 해 규칙을 고치며 가상 IP 는 그대로라 클라이언트 캐시와 무관하다는 대조가 없다. 할 일: 헤드리스 대가 문장 앞에 대조 한 문장.

### 36. `06-01` §6·§7 — 이름 두 층(Service 이름·파드 이름)과 hostname·subdomain 라벨 자리

- 학습자 말: "hostname 과 subdomain 옵션이 뭔지 정확히 모릅니다. 같은 이름을 파드가 모두 받는다는 게 무슨 의미인가요? (원래도 서비스가 가지는 도메인으로 같은 이름을 받는 게 아닌가요?)", 이어서 "db / db-1.db 가 호스트 이름, 이후가 서브도메인"으로 라벨 자리를 잘못 나눔, "subdomain 에 헤드리스 서비스 이름이라는 건 그냥 서비스 이름? 헤드리스 아니면 안 붙이나?". 예측은 "StatefulSet 은 상태를 유지하니 DNS·IP 모두 같다"(Q8, 잘못 알던 인과).
- 근거: §6 「PodSpec 이 정하는 대상 이름」과 §7 은 필드 이름과 결과 응답은 있지만, 묶음 이름(`svc` 이름)과 개인 이름(`hostname.subdomain.…`)이 두 층이라는 그림이 없다. 예제 Service 이름이 `headless` 라 `headless-0.headless.default…` 에서 라벨 역할이 가려진다. subdomain 이 같은 네임스페이스의 헤드리스 Service 이름과 맞아야 한다는 조건은 §6 에 "맞지 않으면"으로만 있다. StatefulSet 이 지키는 것이 이름과 볼륨이고 IP 는 아니라는 점은 "A 레코드의 주소만 바뀌어 있습니다" 한 문장에 묻혀 있다.
- 할 일: §7 첫머리에 라벨 분해 그림 한 장(hostname · subdomain(=헤드리스 Service 이름) · namespace · svc · 클러스터 도메인)과 "Service 이름은 묶음, 그 아래 hostname 은 개인" 한 문장. 「StatefulSet 의 서수 기반 호스트 이름」 끝에 "지키는 것은 이름과 볼륨이고 IP 는 바뀐다, 그래서 멤버끼리는 이름으로 적는다" 한 문장. 예제 이름 변경은 원서 출력과 맞춰야 하니 선택(라벨 주석으로 대신할 수 있음).
- Phase 2 덧붙임(2026-11-06): §6 에서 이름 없는 포트에 SRV 가 없는 이유를 "서비스(또는 파드) 이름을 못 만들어서"로 봄. 노트는 "첫 라벨 `_http` 는 포트 이름에 대응"과 "이름 없는 포트는 SRV 를 받지 못한다"를 따로 적어, 질의 이름 첫 칸이 비면 이름 자체를 못 만든다는 인과가 이어지지 않는다. §7 에서는 Deployment 에 hostname 을 고정하면 "분산이 필요 없어진다"고 읽음 — "서비스 이름을 쓰는 것과 기능적으로 다르지 않다"가 무엇을 잃는지(파드 하나를 집는 이름)를 말하지 않는다. 할 일: 라벨 분해 그림에 SRV 질의 이름(`_포트이름._프로토콜.서비스…`)도 한 줄, §7 끝 문장에 "파드 하나를 집는 이름이 사라진다" 덧붙임.

### 37. `06-01` §8 「파드 A 레코드의 폐기 배경」 — 이름으로 소속을 확인하는 쪽의 관점

- 학습자 말: 예측 "네임스페이스를 체크 안 하면 잘못된 DNS 로 통신에 실패하게 된다"(Q9, 잘못 알던 인과), 이어서 "이게 무슨 소리인지 잘 모르겠음, 신원 위장을 한다는 건가?", "evil 네임스페이스에서 IP 보냈는데 왜 shop 에 물어보는 건가?". 확인하는 쪽이 따로 있다는 설명을 세 번째에 이해.
- 근거: §8 은 "신원 보장을 약화", "네임스페이스 밖의 파드를 … 안의 파드인 것처럼 보이게"라고 결과만 적고, 누가 그 이름을 믿고 무엇을 확인하는지(이름으로 소속을 판단하는 서비스·와일드카드 인증서)가 없다. `pod-record-spoof.svg` 도 공격 순서는 있으나 확인하는 쪽 질문이 드러나지 않는다.
- 할 일: §8 둘째 문단 앞에 한 문단 — "shop 파드만 받는" 서비스가 상대 IP 를 `a-b-c-d.shop.pod…` 로 바꿔 물어 소속을 확인한다고 하면, 옛 규칙은 아무 IP 에나 "있다"고 답하므로 evil 의 파드도 통과한다. `pods verified` 는 그 질문에 실제 명단을 보고 답한다. 이 예는 설명용 가정임을 밝힌다.
- Phase 2 덧붙임(2026-11-06): 옛 방식을 "shop 에 있는지 안 보고 전체에서 찾아 어디든 있으면 통과"로 Phase 1 오개념(실제 IP 가 있으면)을 반복했고, 이어 "insecure 로 물으면 거부하는 거 아냐?". 첫 문단 "그 IP 주소를 가진 파드가 **지정된 네임스페이스에** 실제로 있는지 확인하지 않는다"가 다른 곳은 확인한다는 뜻으로 읽힌다. insecure 가 API 를 보지 않고 대시를 점으로 바꾸기만 해 아무도 안 쓰는 IP 에도 답한다는 점, `pods` 가 Corefile 옵션이고 값이 disabled·insecure·verified 셋이라는 점은 06-04 §2 로만 미뤄져 있다. 할 일: 그 문장을 "그 IP 를 어떤 파드가 쓰는지 아예 보지 않는다"로 바꾸고, 세 값 비교(`10-99-99-99.shop.pod…` 질의 결과)를 §8 에 짧게 두거나 06-04 §2 링크 옆에 한 줄.
- 06-02 Phase 1 덧붙임(2026-11-06): 06-01 Phase 2 를 닫은 다음 날 `kubernetes` 블록을 "쿠버네티스 존이 만들어지고 파드 검증 진행"으로 읽음 — 이름의 인상으로 재발. 06-02 §4 「kubernetes 블록 안의 세 줄」의 `pods insecure` 문단도 "kube-dns 하위 호환"만 말하고 검증이 없다는 점을 말하지 않는다. 할 일 덧: 그 문단에 "이름 속 IP 를 확인 없이 돌려준다(06-01 §8)" 한 구절.

### 40. `06-02` §4 「kubernetes 블록 안의 세 줄」 — 클러스터에서 PTR 이 왜 필요한지와 2장 역방향 이름공간으로 가는 링크가 없음

- 06-02 Phase 2 덧붙임(2026-11-06): "PTR 이 어떤 방식으로 존 선택이 되는지는 모르겠다", 첫 답에서 `fallthrough` 를 지운 경우를 빠뜨림. `10.96.0.10` → `10.0.96.10.in-addr.arpa`, `8.8.8.8` → `8.8.8.8.in-addr.arpa` 둘 다 끝 라벨 `in-addr.arpa` 로 `kubernetes` 에 들어가고, 바깥 IP 는 사본에 없으니 `fallthrough` 없으면 그 자리 NXDOMAIN 이라는 두 이름 대조를 보여 주자 바로 통과했다. 할 일 덧: 위 문장 옆에 이 두 줄 대조(IP → 묻는 이름 → 어디로 → 결과) 표 하나.

### 43. `06-03` §4 「안쪽 겹 — 컨테이너 하나에 담긴 넷」 — CPU·메모리 상한의 비대칭이 "넘으면 어떻게 되나"로 안 보임

- 학습자 말: 예측 "CoreDNS 가 메모리에 서비스 정보를 과하게 가지고 있지 않게 하기 위함"(Q4, 잘못 알던 인과), 채점 뒤 "스로틀링 다른 문서에서 자세하게 다루는가", "os 관련에서는 스로틀링 안 다뤄?".
- 근거: §4 는 "CPU 바운드라 남는 연산 능력을 쓰려고"와 "메모리를 너무 많이 먹으면 커널이 프로세스를 죽이기 시작할 수 있다"를 쓰지만, CPU 상한을 넘으면 죽지 않고 스로틀링된다는 말과 상한이 담는 양을 줄이지 않고 넘는 순간 그 컨테이너를 OOMKill 한다(피해를 CoreDNS 안에 가둠)는 말이 없다. 같은 비대칭을 `kubernetes-in-action/02-03` 「cgroup이 다루는 자원과 한도를 넘었을 때」(원리, CFS·`cpu.stat`)와 `02_os/book/systems-performance/11-03` 「CPU throttling 판별 — 다섯 지표」(진단)가 이미 다룬다.
- 할 일: CPU 문단 뒤에 "넘으면 CPU 는 느려지고(스로틀링) 메모리는 죽는다(OOMKill)" 두 줄 대조와 두 노트 링크. 메모리 문단에 "상한은 사본 크기를 줄이지 않는다 — CoreDNS 는 담을 객체를 고를 수 없다(06-01)" 한 구절.
- 06-03 Phase 2 덧붙임(2026-11-06): CPU 쪽(스로틀링→쌓임→시간 초과)은 스스로 맞혔고, 메모리 쪽은 "상한 170 인데 초과가 날 수 있는 거야? 애초에 못 올라가게 막는 줄 알았다". 상한이 미리 잘라 두는 문이 아니라 합계가 닿는 순간 죽이는 장치라는 점, 그리고 재시작해도 같은 규모를 다시 채우다 또 죽는 되풀이(CrashLoopBackOff, 복제본이 함께 빠지면 DNS 전체 중단)가 노트에 없어 설명으로 채웠다. 두 줄 대조에 "되풀이" 한 구절을 넣으면 좋다.

### 44. `06-03` §2 「왜 네임스페이스를 읽어야 하는가」 — "서비스가 하나라도 있으면"이 소스 동작과 어긋남

- 학습자 말: 예측 "네임스페이스에 있는 전체 서비스 목록을 설마 조회하는 건가? (너무 많이 들고 올 거 같은데) 그래서 네임스페이스 정보를 가져온다?"(Q5, 몰랐던 사실).
- 근거: 노트는 "그 네임스페이스에 서비스가 하나라도 있으면 존재하지 않는 도메인이 아니므로 `NXDOMAIN` 을 돌려주면 안 됩니다"라고 쓴다. CoreDNS master `plugin/kubernetes/namespace.go` 의 `namespaceExposed()` 는 네임스페이스 informer 사본에 `GetNamespaceByName()` 으로 존재만 묻고, `kubernetes.go` 의 빈 이름 분기는 존재하면 NODATA·없으면 NXDOMAIN(`errNoItems`)이다. 노트 문장대로면 빈 네임스페이스가 NXDOMAIN 이어야 하는데 실제는 NODATA 다. 그리고 서비스 목록은 이미 메모리에 있으니 "많이 가져온다"가 아니라 "빈 네임스페이스와 없는 네임스페이스를 서비스 목록으로는 구별 못 한다"가 네임스페이스 권한의 이유다.
- 할 일: 문장을 "그 네임스페이스가 있으면"으로 바로잡고(소스 각주), 빈 네임스페이스 한 줄 예를 덧붙임. 그림(`06-03.ns-nxdomain.svg`) 라벨도 같은 기준인지 확인.
- 06-03 Phase 2 덧붙임(2026-11-06): 네임스페이스 확인을 "해당 IP 가 그 네임스페이스에 있는지 확인"(`pods verified` 의 일)으로 섞었다. 노트가 "서비스가 하나라도 있으면"으로 서비스 목록과 엮어 쓴 것이 이 혼동을 부추긴다. 고칠 때 "이름 하나(네임스페이스)가 있는지만 본다"를 한 문장으로 못 박고, IP 소속 확인은 06-04 `pods verified` 몫이라고 한 줄 넘기면 좋다.

### 45. `06-03` §3 고정 clusterIP — `resolv.conf` 를 써 넣는 주체와 필드 이름이 흐림

- 학습자 말: 예측 "core-dns 가 써서 넣을 거 같고(각 노드에 하나씩 배포돼서?) … 저 주소는 아마 coredns 주소 같음"(Q2, 잘못 알던 인과), 채점 뒤 "kubelet 의 설정은 클러스터가 뜨기 전에 이미 정해져 있어야 한다(왜지?)", "가상 IP 로 먼저 한다는 거지?".
- 근거: §3 은 "같은 IP 주소가 각 kubelet 인스턴스에 전달되고 kubelet 이 … `resolv.conf` 를 만들 때 그 값을 씁니다"까지 쓰고, 그 값이 KubeletConfiguration `clusterDNS` 라는 점, kubelet 이 시작할 때 한 번 읽어 그 뒤 만드는 파드에만 쓴다는 점(바꾸면 기존 파드는 재생성해야 함), kubeadm 이 서비스 대역의 열 번째 주소를 고른다는 점이 없다. 고정값이 Service 의 가상 IP 이고 CoreDNS 파드 IP 와 다르다는 대조도 없다.
- 할 일: 그림 옆에 `clusterDNS` 필드 이름과 "kubelet 시작 때 읽음 → 파드 생성 때 씀" 한 문장. 가상 IP vs 파드 IP 두 줄 대조는 선택.
- 06-03 Phase 2 덧붙임(2026-11-06): §3 첫 답이 "이름을 쓰는 외부 시스템·파일이 많아서"로 돌아가 Phase 1 의 불변 필드를 놓쳤고, "생성 전에 꼭 필요하다는 흐름을 잘 모르겠다(이거 어디서 자세히 다룸?)". 파드를 만드는 순간 resolv.conf 를 써야 하는데 그때 kubelet 이 물어볼 곳이 없다(DNS 를 찾으려면 DNS 주소가 먼저 필요) → 그래서 시작 설정에 미리 박아 둔다는 흐름이 핵심이다. 가까운 문서는 `kubernetes-in-action/11-01` §7 「파드의 /etc/resolv.conf는 어떻게 채워지고 사용되나」뿐이고 `clusterDNS` 를 읽는 시점은 어디에도 없다. 바꿀 곳 셋(DNS Service·모든 노드 kubelet·이미 뜬 파드)은 설명 뒤 스스로 정리했다.

### 46. `06-03` §4 「가운데 겹 — 이름이 헷갈리는 DNS 정책」 — `Default` 일 때 실제로 들어가는 값이 없음

- 학습자 말: Q3 채점 뒤 "Default 를 쓰면 어떤 값이 들어가는 거지?".
- 근거: §4 는 "`Default` 는 호스트 노드의 DNS 설정을 쓴다는 뜻"까지만 쓴다. kubelet `resolvConf` 가 가리키는 노드 파일(기본 `/etc/resolv.conf`)을 복사하고 클러스터 search 도메인은 넣지 않는다는 점, systemd-resolved 노드에서는 `127.0.0.53` 이 파드 자기 자신이 되어 루프가 생기므로 kubeadm 이 `/run/systemd/resolve/resolv.conf` 로 바꾼다는 점이 없다. 후보 #41(06-02 `loop` 의 전형 원인)과 같은 사실이라 둘을 한 번에 보강하면 좋다.
- 할 일: `ClusterFirst`/`Default` 두 정책의 `resolv.conf` 예시를 나란히 보이는 짧은 블록 + #41 과 상호 링크.

### 47. `06-03` §6 — `cache` 상한이 TTL 을 줄이기만 한다는 규칙과 `REVERSE_CIDRS` 의 모양이 없음

- 학습자 말: 예측 "아래 블록에서 30 이 빠지는 건 … 쿠버네티스 클러스터의 DNS 는 어차피 바로바로 조회하기도 하고 재귀 요청을 거의 안 하기 때문에 캐싱을 하면 데이터만 꼬일 수 있어서"(Q8, 잘못 알던 인과 — 아래 `.` 블록이 클러스터 이름을 받는다고 봄), 채점 뒤 "cache 900 이면 상류가 300 일 때 600 초 더 물고 있는 거 아님?", "역방향 존이 뭐임?", "UPSTREAMNAMESERVER 이거는 뭐임?".
- 근거: §6 은 "외부 질의는 상류 네임서버의 TTL 대로 캐시하므로 30초 상한도 뗍니다"라고 쓰지만, 보관 시간이 min(레코드 TTL, 상한)이라는 규칙과 숫자를 빼면 성공 3600초·부정 1800초가 상한이 된다는 점(CoreDNS `cache` README)이 없다. 두 질의(`web.shop.svc.cluster.local`·`google.com`)가 각각 어느 블록으로 가는지 한 줄 대조도 없고, `REVERSE_CIDRS` 에 CIDR 을 적으면 역방향 존들로 펼쳐진다는 설명도 없다.
- 할 일: 1단계 Corefile 아래에 "TTL 300·5·86400 × `cache 30`/숫자 없음" 작은 표, 두 질의 경로 한 줄, `REVERSE_CIDRS`·`UPSTREAMNAMESERVER` 변수 뜻 한 줄씩.

### 48. `06-03` §4 프로브 — 동기화 전 응답(SERVFAIL)과 준비성 프로브의 몫이 갈리지 않음

- 학습자 말: 예측 "준비가 되어 있지 않으면 엔드포인트 슬라이스에서 제거되고 저 도메인 요청이 NXDOMAIN 으로 받게 됩니다"(Q9, 일치 — 보호 동작과 문제 장면을 한 문장에 섞음), 채점 뒤 "실제로는 있는데 DNS 로 정상 조회를 못 한다는 건가? 어떻게 감지하는 거지?".
- 근거: §4 는 "준비성 프로브를 통과하면 … 부하 분산 풀에 추가"만 쓴다. CoreDNS master `plugin/kubernetes/handler.go` 는 `HasSynced()` 가 거짓이면 NXDOMAIN 대신 SERVFAIL 을 돌려주고, 시작 때 `startup_timeout` 동안 사본을 기다린다(README 기본값 확인 뒤 각주). NXDOMAIN 은 클라이언트 부정 캐시에 남지만 SERVFAIL 은 재시도로 넘어간다는 차이가 준비성 프로브가 왜 필요한지를 보여 준다.
- 할 일: 프로브 문단 뒤에 "준비 전 질의가 오면 → SERVFAIL(지금) / NXDOMAIN(옛 동작·부정 캐시)" 한두 문장과 소스 각주.

### 49. `06-04` §2 「켜지 않는 이유가 둘」 — 메모리 추정식이 측정값의 직선이라는 점과 기울기의 뜻이 없음

- 학습자 말: Q1 예측에서 비용 축이 비어 "이거보다 더 정확한 방법?"(몰랐던 사실), 채점 뒤 "저 추정식이 어떤 기준인 건가요? 왜 위쪽은 /1000 이고 검증은 /250 인가요?".
- 근거: §2 는 두 식과 "객체 1,000개당 약 4 MiB"만 쓴다. 원 출처 `coredns/deployment` `kubernetes/Scaling_CoreDNS.md` 는 e2e 테스트 클러스터 셋(파드 15,000·60,000·150,000, 쿠버네티스 1.12 무렵, CoreDNS 1.2.4~1.2.5)에서 잰 최대 메모리에 맞춘 직선(best fit)이라고 쓰고, 상수에 응답 캐시 30MB·처리 여유 5MB 가 들어 있다고 밝힌다. `insecure` 식에도 파드 수가 들어가는 이유(파드가 EndpointSlice 주소 한 줄로 들어감)와 `verified` 에서 파드 객체 자체를 더 든다는 대조가 노트에 없다. 원문 식의 제목은 "w/ autopath" 다.
- 할 일: 표 아래에 "측정값의 직선이고 측정 버전이 오래됐다" 한 문장, 1KB vs 4KB(객체 하나당) 한 줄, 상수의 구성 한 줄.

### 50. `06-04` §3 「쓸모가 분명한 자리가 하나」 — 와일드카드가 묻던 자리와 "헤드리스를 하나 더"가 기존 서비스를 안 바꾼다는 점이 흐림

- 학습자 말: Q2 예측 "IP 2개를 직접 보려면 보통 헤드리스로 조회 … 서비스 수정 안 한다고 했으니 … 잘 모르겠다"(몰랐던 사실), 채점 뒤 "와일드카드 질의가 엔드포인트를 받는다(이게 뭐지? 이렇게 조회하면 보통 그냥 하나만 주는 거 아냐 가상 IP 를 쓴다는 가정하에?)".
- 근거: §3 은 `*.<service>.<namespace>…` 질의 예와 "같은 셀렉터의 헤드리스 서비스를 하나 더 두어"를 쓰지만, 서비스 자리·엔드포인트 자리·`*` 자리의 세 질의 이름을 나란히 놓은 대조가 없다. "하나 더"가 기존 ClusterIP 를 그대로 두고 같은 파드를 두 Service 가 함께 고르는 것이라는 설명과 매니페스트 예도 없다(학습자는 "서비스를 바꾸지 않는다"를 "헤드리스를 못 쓴다"로 읽음). kube-prometheus-stack 차트가 CoreDNS 메트릭을 긁으려고 같은 셀렉터의 헤드리스를 만드는 것이 공개된 실례다.
- 할 일: 질의 이름 세 줄 표, 헤드리스 매니페스트 6줄 예, 실례 한 문장.
- 06-04 Phase 2 덧붙임(2026-11-09): §3 에서 와일드카드가 지금(1.11)도 된다고 답하고 1.11 을 1.9 보다 앞 버전으로 읽었다. 노트는 "1.9.0 에서 제거"만 쓰니, 표에 "1.9.0 이후(1.10·1.11 …) 모두 없음"을 한 구절 붙이고 지금 쓰는 두 길(같은 셀렉터 헤드리스 하나 더·`kubectl get endpointslices -l kubernetes.io/service-name=<이름>`)을 한 줄로 남기면 좋다.

### 51. `06-04` §4 「네 해법」 NodeLocal DNSCache — 캐시가 맞으면 중앙으로 가지 않는다는 점과 꼬리 지연·TCP 의 뜻이 없음

- 학습자 말: Q4 예측 "왜 좋은지 모르겠다(작게 빌드했다는데 장기간 쓰면 모두 검사하는 거 아닌가?) // 질의 그대로 아닌가? 앞에서 조회하고 뒤에서도 똑같이 6번 조회하는 거 아냐?"(잘못 알던 인과), 채점 뒤 "꼬리 지연이 뭐지? 그리고 TCP 가 이걸 줄여 줘?", "TCP 도 ACK 대기 시간이 있는데 그렇게 짧아?".
- 근거: §4 는 "캐시에 없는 것은 중앙 CoreDNS 서비스로 넘긴다"와 "TCP 로 올리면 … 꼬리 지연이 줄어든다"를 쓰지만, 파드 쪽 질의 수는 그대로이고 적중(NXDOMAIN 부정 캐시 포함)이면 중앙으로 0번이라는 대조가 없다. "작게 빌드"가 `kubernetes` 플러그인을 뺀 빌드라 watch·사본이 없다는 뜻, 응답 캐시는 TTL·항목 수 상한으로 묶인다는 점, 꼬리 지연(p99) 정의, UDP 유실=리졸버 `timeout` 5초 대기 vs 열린 TCP 연결의 커널 재전송(RTO 하한 200ms)도 없다. 사례집 `troubleshooting/kubernetes/2026-09-08_한 하위 서비스에서 시작된 전면 오류.md`(Zalando, ndots 로 질의 10배·100Mi OOMKill·노드 캐시가 재발 방지)와 `2026-09-12_정확히 1초씩 늦는 요청.md`(5초 계단=DNS, 1·3·7초=TCP)가 같은 주제다.
- 할 일: "첫 조회 / TTL 안 재조회" 두 줄 표, "작게 빌드" 한 구절, 꼬리 지연 한 문장, 두 사례로 링크.
- 06-04 Phase 2 덧붙임(2026-11-09): 곁질문 "TCP 로 바꾸는 건 어떤 방식으로 진행되지? 플러그인 뭐 쓰는가?". 쿠버네티스 저장소 `cluster/addons/dns/nodelocaldns/nodelocaldns.yaml` 의 Corefile 은 `cluster.local`·`in-addr.arpa`·`ip6.arpa` 블록만 `forward . __PILLAR__CLUSTER__DNS__ { force_tcp }` 로 중앙에 넘기고, `.:53` 블록은 `force_tcp` 없이 `__PILLAR__UPSTREAM__SERVERS__`(노드의 상류 DNS)로 바로 보낸다. 그래서 §4 의 "캐시에 없는 것은 중앙 CoreDNS 서비스로 넘깁니다"는 바깥 이름에는 맞지 않는다(사실 정정 후보, 학습 대화에서도 첫 조회 5번이 모두 중앙으로 간다고 설명했다가 중앙 3번·상류 2번으로 정정). 캐시 설정 `success 9984 30`·`denial 9984 5` 와 `bind` 의 링크 로컬 주소도 한 줄로 넣으면 "부정 응답도 캐시"가 근거를 갖는다. 학습자는 꼬리 지연을 "꼬리물기"라고 불렀다가 스스로 고쳤다.

### 52. `06-04` §5 「autopath」 — 이름만으로는 안 되는 이유와 서버가 후보를 조립하는 절차가 없음

- 학습자 말: Q5 예측 일치. Q6 예측 일치(방향) 뒤 "example.com.default.svc.cluster.local 에 네임스페이스 정보가 있는데 파드 사본이 필요해?", "3번에서 직접 조립한다는 게 뭔 말임?", "2번째 파드에서 후보를 다 실패한다는 게 무슨 말임?", "네임스페이스 없는 svc.cluster.local 은 뭔가?", "서버 쪽 autopath 에만 해당된다고?".
- 근거: §5 는 "출발지 IP 로 파드 네임스페이스를 역추적하려면 `pods verified`"와 "검색 경로의 첫 항목으로 끝나지 않는 질의에는 손대지 않는다"를 쓰지만, 같은 이름 `foo.default.svc.cluster.local` 이 "default 파드의 첫 단계"와 "다른 네임스페이스 파드가 앱에 직접 쓴 이름의 마지막 단계" 두 경우로 올 수 있어 이름만으로 가를 수 없다는 대조가 없다. 서버가 첫 접미사를 떼어 원래 이름을 되찾고 다음 접미사를 붙이는 절차, 클라이언트는 원래 이름을 메모리에 들고 붙이기만 한다는 대조도 없다. 점 4개짜리 FQDN 도 `ndots:5` 때문에 검색 경로를 먼저 탄다는 점은 학습자가 이 대화에서 처음 연결했다. IP 재할당 부작용은 질의 끝이 옛 네임스페이스 접미사와 맞을 때만 틀린 답이 되고, 아니면 `autopath` 가 비켜선다(최적화만 빠짐).
- 할 일: 같은 이름 두 경우 표(누가 접미사를 붙였나), 조립 네 단계, 부작용 문단에 "맞지 않으면 비켜섬" 한 줄. §4 검색 경로 목록에 "앱이 이렇게 쓰면 → 붙인 결과" 열을 더하면 `svc.cluster.local` 칸의 쓰임이 보인다.
- 06-04 Phase 2 덧붙임(2026-11-09): §5 답에서 이름만으로 못 가르는 이유(리졸버가 붙인 값인지 모름 → 실제 파드의 네임스페이스 확인)와 메모리 부담은 맞혔지만, API 서버 watch 부하가 Q1 에 이어 두 번째로 빠졌다. §2 와 §5 의 비용 문장을 "메모리와 API 서버 부하" 한 쌍으로 같은 말로 맞추면 좋다.

### 53. `06-04` §6 「클러스터 밖에서 닿게 하기」 — "누가 묻나"와 "무슨 이름을 묻나"가 갈리지 않음

- 학습자 말: Q7 처음 "기존과 뭐가 다른 건가? … 질문 의도를 잘 모르겠다 더 쉽게"(묻는 쪽이 파드에서 사무실 PC 로 바뀐 것을 못 봄), 힌트 뒤 일치. 채점 뒤 "(디플로이먼트는 왜?)", "k8s_external, kubernetes 플러그인 비교도 해 줄래", "클러스터 밖 클라이언트의 주소라 함은 google.com 이런 걸 의미하는 게 아닌가?".
- 근거: §6 은 두 길(external-dns·`k8s_external`)과 "외부 이름 전용 CoreDNS 인스턴스를 별도 배포"를 쓰지만, 묻는 쪽(안 파드/밖 클라이언트) × 이름(클러스터 이름/바깥 이름) 2×2 가 없어 학습자가 `google.com`(파드가 묻는 바깥 이름, `forward`)과 섞었다. 전용 인스턴스가 클러스터 안에 06-03 의 네 종류 자원을 한 벌 더 만드는 것이라는 점, `kubernetes` 와 `k8s_external` 의 대조(답하는 서비스·돌려주는 IP·데이터 출처)도 없다.
- 할 일: 2×2 표 하나, "전용 인스턴스 = 자원 네 벌 한 벌 더(클러스터 밖이 아님)" 한 문장, 두 플러그인 대조 표(짧게).
- 06-04 Phase 2 덧붙임(2026-11-09): §6 에서 전용 인스턴스·DoS 격리는 맞혔으나 "이걸 내부에 하는지 외부에 띄우는지는 잘 기억이 안 남". §6 마지막 문단에 "클러스터 안에 띄우고 Service 를 LoadBalancer 로 연다(`k8s_external` 이 기대는 `kubernetes` 플러그인이 API 를 watch 해야 하므로)" 한 문장이 필요하다는 앞 판단이 다시 확인됐다. 두 축 표는 이번에도 설명으로 채웠다.

### 54. `06-04` §7 「NXDOMAIN 을 신호로 쓰기」 — 기본 동작의 실패 위치, 장애 조치의 구성, 언제 의미 있는지가 없음

- 학습자 말: Q8 예측 "가상 IP 받음 → 준비된 파드 없으니 요청 실패(NXDOMAIN 으로 떨어질지는 모르겠음), NXDOMAIN 이면 이 문제를 조기에 방지?"(몰랐던 사실), 채점 뒤 "보조 클러스터가 뭐임?", "1~4 를 더 쉽게", "아직 파드가 준비되지 않아 조회 안 되는 걸 백업 DNS 를 k8s_external 로 받아오는 의미가 있어?", "이 클러스터에서는 실패했다 판단하고 다른 클러스터로 보낸다는 거야?".
- 근거: §7 은 "클라이언트는 질의 실패를 확인하고 검색 경로의 다음 도메인(예: 보조 클러스터)으로 장애 조치"만 쓴다. 기본 동작에서는 DNS 가 성공하고 실패가 TCP 접속 단계에서 난다는 점, 장애 조치가 돌려면 검색 경로(dnsConfig)·보조 도메인 `forward`·상대 클러스터의 바깥 노출(§6)이 함께 있어야 한다는 점, 부정 캐시 때문에 짧은 공백에는 손해이고 오래 전멸일 때 이득이라는 판단 기준, CoreDNS 는 ready 개수만 기계적으로 보고 "실패 판단"은 준비성 프로브가 한다는 몫 나눔이 없다(마지막 둘은 노트 밖 분석).
- 할 일: "기본 / 옵션 × 정상 / ready 0" 표, 구성 요소 한 줄(§6 링크), "언제 켜나" 두 문장.
- 06-04 Phase 2 덧붙임(2026-11-09): §7 답 "엔드포인트 슬라이스에서 IP 조회가 안 되고 가상 IP 로 연결을 시도할 때 refused". 결과는 맞지만 ClusterIP 의 DNS 답은 ready 엔드포인트 수와 무관하게 VIP 라는 점과 섞였다. 접속 실패는 kube-proxy 가 엔드포인트 없는 서비스에 넣는 REJECT 규칙에서 난다(iptables 모드). 표를 "DNS 단계 / 접속 단계"로 나눠 적으면 섞이지 않는다. Phase 1 에서 기본 동작도 NXDOMAIN 이라고 봤던 혼동은 풀렸다.

### 55. `07-01` §2 「같은 인증서를 쓰려다 트래픽이 밖으로 나갔다 온다」 — 헤어핀의 뜻과, DNS 가 IP 만 바꾸고 이름은 그대로라 TLS 가 통과한다는 흐름이 없음

- 학습자 말: Q3 예측 "둘다 search의 추가 도메인이 붙어서 검색된다? … 가장 이상적인건 … .찍기?"(헤어핀·TLS 두 축을 모름), 채점 뒤 "헤어핀현상(이게뭐임?)", "rewrite플러그인이 이를 해결 -> 관련해서 더 설명해줄래", "DNS는 단순 결과조회시 이후 실제 조회는 다른거 아닌가? (다시 저걸로 던져주면 다시 외부로 가는거 아냐?)", "IP만 저렇게 응답한거고 내부에서도 DNS이름은 여전히 저거란거지?", 마지막에 "좀 더 자세하게 문서에서 설명해줬으면한다".
- 근거: §2 는 "헤어핀 현상"을 정의 없이 쓰고, `rewrite` 가 두 문제를 푸는 이유를 "CNAME 처럼 동작하지만 클라이언트에게는 원래 물은 이름 그대로 답이 전달됩니다" 한 문장으로만 말한다. 이름→IP 는 DNS 에서 한 번만 일어나고 접속은 그 IP(ClusterIP)로 정해진다는 점, 이름은 TLS SNI·HTTP `Host` 이름표로만 실려 인증서 이름과 비교된다는 점이 없어 학습자가 "되돌린 이름으로 다시 밖으로 가지 않나"를 물었다. 적용 조건도 없다 — 인증서를 클라우드 로드밸런서가 아니라 클러스터 안(파드·Ingress·게이트웨이)이 내놓아야 하고, ClusterIP 서비스가 앱이 쓰는 포트(443)를 열어야 한다(AI 덧붙임, 공식 문서 확인 필요).
- 할 일: 헤어핀 한 문장 정의 + 경로 그림(파드→LB 공인 IP→클러스터 안 / rewrite 뒤 파드→ClusterIP), "이름→IP(DNS) → IP 로 접속(TCP) → 이름은 SNI·Host 로만(TLS·HTTP)" 세 단계, 되돌리기 전/뒤 Answer 레코드 두 줄(IP 칸은 그대로), 적용 조건 두 줄. 끝 점(FQDN)은 검색 경로 헛조회만 없애고 헤어핀·TLS 는 그대로라는 한 줄과 06-04 링크.

### 56. `07-01` §1 「template」 — 와일드카드와의 대조, `SERVFAIL` 인 이유, 존이 안 맞는 질의는 그냥 지나간다는 점이 없음

- 학습자 말: Q1 예측 "대역을 그대로 주면 되는거 아닌가? host-0.0.20.10/16"(대역을 덮는 레코드 하나), 채점 뒤 "템플릿을 쓰고 정규식처럼 처리한다는거지 받은 문자열로?". Q2 예측 "패턴에서 실패해서 애초에 NXDOMAIN으로 던질거같음", 채점 뒤 "template은 자기 정규식 모양만 알뿐 실제 형태를 모른다 -> 그래서 없다고 단언하지 않고 실패로 돌려준다"로 정리(이유 해석은 AI 설명).
- 근거: §1 은 "요청만 보고 즉석에서 답을 지어냅니다"만 쓰고, DNS 레코드는 이름 하나에 붙어 대역을 덮는 레코드가 없다는 점, 가장 가까운 와일드카드(`*.20.10.in-addr.arpa`)는 모든 이름에 같은 답을 줘 주소마다 다른 PTR 을 못 만든다는 대조가 없다. §1 「매칭이 안 되면」은 `SERVFAIL` 을 쓰지만 `NXDOMAIN` 과 뜻이 어떻게 다른지(없다는 단언·부정 캐시 vs 답을 못 만듦)가 없다. CoreDNS v1.15.0 `plugin/template/template.go:111-114` 가 `!match && !fthrough` 에서 `dns.RcodeServerFailure` 를 돌려주고, `:202-209` 는 클래스·유형·존이 안 맞으면 `fthrough=true` 로 다음 플러그인에 넘긴다 — 막히는 것은 존은 맞고 정규식만 틀린 경우뿐이다.
- 할 일: §1 첫 문단 뒤 "와일드카드는 같은 답, template 은 이름마다 계산" 한 문장, 「매칭이 안 되면」에 `SERVFAIL`/`NXDOMAIN` 뜻 한 줄과 "존이 안 맞으면 `fallthrough` 없이도 지나감" 한 줄(소스 줄 각주).

### 57. `07-01` §3·§9 — CNAME 으로 대응을 지키는 방법과 `rewrite` 의 이름 되돌리기가 나란히 비교되지 않음

- 학습자 말: Q4 예측 "그래서 CNAME으로 동일하게 맞춰준다고 했던거 같은데 맞는가?", 채점 뒤 정리에서 "일반적으로 CANME 응답을 통해 해결한다"(CNAME 을 일반 해법으로 봄), "MITM -> 풀네임이 뭐냐".
- 근거: §2 `:174` 는 `rewrite` 를 "CNAME 처럼 동작"한다고 쓰고, §9 `:525` 는 CNAME 응답이 대응을 지킨다고 쓴다. 두 방법(답에 CNAME 사슬을 덧붙임 vs Answer 이름 칸을 되돌림)이 다른 장치라는 대조가 없어 학습자가 둘을 섞었다. §3 `:190` 은 "중간자 공격(MITM)"의 풀네임(Man-In-The-Middle)과 왜 의심하는지(묻지 않은 이름의 레코드 = 끼워 넣기 가능성)를 쓰지 않는다.
- 할 일: §3 에 세 줄 표(이름만 바꾸고 되돌리지 않음 / `rewrite` 가 되돌림 / CNAME 사슬) × (Question·Answer 이름·IP·클라이언트 반응), §9 로 링크. MITM 풀네임과 의심 이유 한 구절.

### 58. `07-01` §2 제목과 `>` 요약 — 제목을 복창하고 해법 `rewrite` 가 빠짐, 제목이 문장형

- 학습자 말: "## 2. 같은 인증서를 쓰려다 트래픽이 밖으로 나갔다 온다 / > 클러스터 안의 파드가 … 되돌아옵니다. (이 문서의 목차와 핵심을 보면 내용이 중복된다 그리고 ##에는 이 절에서 무엇을 다루는지 설명하는데 핵심인 rewrite플러그인이 전혀 표현되지 않음)". 학습자가 스킬 규칙으로도 확인해 달라고 함.
- 근거: writing-method `01-markdown-structure.md` 규칙 1 — H2 `>` 요약은 결론과 범위를 먼저(BLUF), 요약에서 제목을 복창하지 않는다. §2 `:151` 요약은 제목 `:149` 의 "트래픽이 밖으로 나갔다 온다"를 다시 말할 뿐 결론(`rewrite` 가 DNS 답의 IP 만 안쪽 것으로 바꾸고 앱은 이름을 그대로 써 TLS 가 통과)이 없다. 같은 파일 85행 — 제목에 문제와 해결 키워드를 넣는다. §2 제목에 `rewrite` 가 없다. 87행 — `##` 는 25자 안팎 명사구, `~다` 로 끝내지 않는다. §2 를 포함해 §3·§5·§6·§7·§9 제목이 `~다` 로 끝나는 문장형이다.
- 할 일: §2 제목을 문제+해법 명사구로(예: 「헤어핀과 rewrite 이름 재작성」), `>` 요약을 결론 한두 문장으로 교체(헤어핀 정의는 본문으로, 후보 55 와 함께). 다른 `~다` 제목 다섯도 같은 규칙으로 고치고 앵커·`§N 「옛 제목」` 인용을 grep 으로 고침.

### 59. `07-01` §5 「EDNS0 옵션 싣기와 metadata 읽기」 — 처음부터 끝까지 값 하나를 따라가는 예와 EDNS0 가 메시지 어디에 실리는지가 없음 — 반영됨 2026-11-10 (w3 메인, 미커밋, 보고서 `~/claude/.omc/handoffs/relay-cc-coredns-0701-s5-report.md`, 남은 것: RFC 6891 서술 별도 창 대조)

- 학습자 말: Q8 예측 "원래 요청정보도 포함해서 DNS를 넘겨야하나?"(방향 일치), 채점 뒤 "EDNS0 옵션과 metadata읽기? (이거 더 자세하게 설명해줘 무슨 소리인지 모르겠음)".
- 근거: §5 는 EDNS0 를 "추가 옵션을 싣는 통로"로만 쓰고, 옵션이 DNS 메시지의 Additional 섹션에 OPT 의사 레코드로 실린다는 점(RFC 6891)과 옵션 코드가 "어떤 스티커인지 가리키는 번호"라는 점이 없다. `rewrite edns0 local set 0xffed {client_ip}` 와 `metadata_edns0 { client_id 0xffed address }` 가 같은 코드 `0xffed` 로 짝을 이룬다는 것이 절 끝 한 문장에만 있고, 값 하나(예: PC 10.1.2.3)가 지사 → 본사 → 로그까지 어떻게 바뀌는지 따라가는 예가 없다. `metadata` 가 왜 따로 필요한지(로그·정책 플러그인은 EDNS0 옵션을 직접 읽지 못하고 이름 붙은 값 `{/metadata_edns0/client_id}` 만 읽는다)도 흩어져 있다.
- 할 일: §5 첫 문단 뒤 "옵션 없을 때 본사 로그(모두 지사 주소) / 옵션 실은 뒤 본사 로그(PC 주소)" 두 줄 대조, 값 하나를 따라가는 4단계 표(PC → 지사 rewrite → 본사 metadata_edns0 → log/firewall), OPT 레코드 한 구절과 RFC 6891 각주.

### 60. `07-01` §5 — EDNS0 옵션이 실린 실제 `dig` 출력 전문과 줄별 주석이 없음 — 반영됨 2026-11-10 (w3 메인, 미커밋, 보고서 `~/claude/.omc/handoffs/relay-cc-coredns-0701-s5-report.md`, 남은 것: RFC 6891 서술 별도 창 대조)
