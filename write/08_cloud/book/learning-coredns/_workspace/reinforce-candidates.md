# Learning CoreDNS — 노트 보강 후보

> 장별 Phase 1~2(예측→채점·점검)에서 드러난 노트의 빈 곳과 학습자 오개념을 번호로 쌓는다. 장의 Phase 2 를 마칠 때마다 메인(학습 통합 제어 창)에 보고해 보강을 진행시킨다(학습자 지시 2026-11-01. 처음엔 마지막에 한 번에 묶기로 했다가 바꿈). 1장 후보 1~8 은 2026-11-01 보고.
> 후보마다 고칠 절, 학습자가 실제로 한 말, 근거를 적는다. AI 가 제시한 해석은 학습자 생각으로 적지 않는다.

## 전체에 걸친 요청

1. **현행 기준을 본문으로, 원서 시점은 한 줄로** (2026-10-30, 1장 Phase 1 질문 7)
   - 학습자 말: "원서기준과 현대 기준이 다른데 현대 기준으로만 작성해줘 — 과거에는 이랬다가 수정했다 정도만 언급"
   - 대상: 18편 전체. 지금은 원서 서술을 본문에 두고 현행 차이를 뒤 문단·"버전 차이"로 덧붙이는 구조(예: 01-01 §5 표 1-1 뒤 `:161~167`)
   - 보강 때 정할 것: 정오·버전 차이 블록을 어디까지 줄일지, README 의 "버전 차이 기록" 집계를 어떻게 바꿀지

## 1장 (01-01)

2. **§5 표 1-1 의 "동적 업데이트" 줄이 현행 대조에서 빠짐**
   - 근거: `01-01:161` 은 "세 줄이 달리 읽힌다"며 완전 재귀·DoT·DNSSEC 만 현행과 대조한다. 동적 업데이트 줄은 2019년 값 그대로다
   - 할 일: 현행 공식 플러그인 목록·소스로 RFC 2136 UPDATE 지원 여부를 1차 자료로 확인해 한 줄 추가
   - 학습자 말: "업데이트가 CoreDNS 가 안된다고 알고 있다 (API로 직접 수정이 안되는걸로 알고있음, 내부에 직접 넣거나 적어야하는듯?)" — etcd 플러그인(5장)처럼 외부 저장소의 API 로 레코드를 바꾸는 길과 DNS UPDATE 메시지를 받는 기능을 구분하는 한 줄이 §5 에 있으면 좋다

3. **§1 "이름이 바뀌는 IP 를 가리킨다"에 TTL 단서가 없음**
   - 학습자 말(질문 2): "뒤의 IP가 계속 바뀌어도 요청하는 입장에서는 이 DNS로 요청하면 자동으로 매핑이됩니다"
   - 할 일: §1 끝에 "캐시된 답은 TTL 동안 그대로 쓰이고 서버가 변경을 밀어 주지 않는다"는 한 줄 + 05-01 링크

4. **§3 "안 켠 플러그인"에서 '실행 파일에 들어 있음'과 '질의가 지나감'의 구분이 약함**
   - 학습자 말(질문 4): "플러그인 자체가 외부에서 가져오는 의존성이라 그런거 아닐까요?"
   - 할 일: 기본 빌드 플러그인은 대부분 in-tree 이고 실행 파일에 들어 있지만, Corefile 에 적은 것만 질의 경로에 놓인다는 문장. 공격 표면 정의를 예시와 함께
   - Phase 2 재확인(§3 만 읽고 답함): "이 플러그인이라면 이제 외부에서 가져오는 정보를 말하는 것 같습니다" — "플러그인 = 외부 정보·외부 의존성" 오개념이 질문 4, 역방향 설명("외부에서 가져오는 기능이 플러그인"), Phase 2 에서 세 번 나옴. §3 첫머리에 "플러그인 = 기능 한 칸(캐시·로그처럼 바깥과 무관한 것 포함)"이라는 정의가 필요. 안전성 문장(공격 표면)은 §3 에 있으나 학습자가 뽑아내지 못함 — 원서가 이유를 풀지 않아 "노트의 읽기"로 한 문장에 묻혀 있는 탓으로 보임

5. **§4 "메모리를 관리합니다"가 두 장치를 뭉뚱그림**
   - 학습자 말(질문 5 설명 뒤): "자동관리한다 (GC처리 말하는거지?)"
   - 할 일: dangling pointer 는 GC, 버퍼 오버플로는 실행 중 범위 검사(bounds check → panic)로 나눠 적기
   - Phase 2 재확인(§4 만 읽고 답함): "GC 언어인 고에서는 이런 위험이 덜하기 때문에", "C나 러스와 같은 경우에는 직접 제어를 하지만 사람이 실수한 경우 이런 게 노출" — GC 혼동 세 번째, 그리고 Rust 를 C 와 같은 쪽으로 묶음. "메모리 안전 = GC" 로 읽히지 않도록, GC 없이 메모리 안전을 얻는 언어(Rust)가 있다는 한 줄도 후보. 학습자가 덧붙인 "민감한 정보 노출"은 §4 에 없음(노트는 서버 중단·OS 장악만 적음) — 버퍼 과다 읽기로 메모리가 새는 경우를 넣을지는 보강 때 판단

6. **"쿠버네티스가 CoreDNS를 쓰는 이유"를 구현 언어로 오해할 여지**
   - 학습자 말(역방향 설명): "Bind는 c언어로 되어있고 고언어 환경인 쿠버네티스와 어울리지않아"
   - 근거: `01-01:79` 는 가장 큰 이점을 "etcd나 쿠버네티스 같은 기반 시설과 통신하는 능력"으로 적고, Go 는 §4 에서 메모리 안전성 축으로만 다룬다. 두 축을 잇는 문장이 없다
   - 할 일: §1 또는 §6 에 "선택 이유는 같은 언어가 아니라 쿠버네티스 API 를 직접 읽는 통합(`kubernetes` 플러그인)"이라는 한 줄. 질문 5 의 GC 혼동(5번)이 역방향 설명에서도 다시 나옴

7. **§4 에 도식이 없음**
   - 학습자 말(Phase 2): "4번 목차에 대해서 도식이 없는데 도식 하나 있으면 좋을 것 같네요"
   - 후보 그림: 바깥 패킷 → 파싱 코드의 칸 넘기기 → C 는 옆 메모리 덮어씀(서버 중단·OS 장악) / Go 는 범위 검사에서 panic, 반납 메모리는 GC — 5번의 두 장치 구분을 그림이 받치게

8. **§5 표 1-1 묶음 읽기가 현행과 어긋남, DoT 와 DNSSEC 구분 부재**
   - 근거: 표 아래 "CoreDNS가 앞서는 줄도 셋 … DoT, 곧 컨테이너와 클라우드 쪽 기능" 문단은 원서 시점 표를 그대로 묶음. 같은 절 뒤쪽은 BIND 9.18(2022)부터 DoT·DoH 지원이라 적으므로, 현행으로는 CoreDNS 쪽 우위가 연동 둘뿐이다. DoT 는 컨테이너·클라우드 기능도 아니다(1번 현행 우선 요청과 함께 처리)
   - 학습자 말: "DNS 색을 지원할 때 DNS 서버 TLS를 지원 안 하는 게 무슨 차이지?" — DNSSEC(답의 진위·무결성, 암호화 없음)과 DoT(전송 구간 암호화, 답의 출처 증명 없음)가 다른 문제를 푼다는 한 문단 필요

## 2장 (02-01) — 02-02 를 마친 뒤 2장 묶음으로 보고

9. **§2 본문에 `NS` 레코드와 글루가 이름으로 나오지 않음**
   - 근거: §2 는 위임 뒤 부모에 남는 것을 "`cs.berkeley.edu` 안의 정보를 어디서 찾을 수 있는지뿐"이라고만 적는다. 글루는 문서 끝 결정 치트시트(`02-01:255`)에 한 줄 나올 뿐이다
   - 학습자 말(Phase 1 질문 2): 순환 문제와 "부모가 IP 도 들고 있어야 한다"는 해법은 스스로 예측함. Phase 2(§2 만 읽고): "자식서버가 본인의 부모정보를 이제 만약 글루서버를 통해서 가져오려고 할 때" — 방향이 거꾸로(질의하는 첫 서버가 부모에게서 자식 네임 서버의 이름·IP 를 받아 감)
   - 할 일: §2 위임 문단 뒤에 "부모에 남는 것 = 자식 존의 `NS` + (네임 서버 이름이 자식 존 안에 있을 때만) 그 주소인 글루" 한 문단. 바깥 이름이면 글루 없이 첫 서버가 루트부터 한 번 더 찾는다는 대조도

10. **"존(이름 범위)"과 "네임 서버(대답하는 컴퓨터)"의 구분이 노트에 없음**
    - 학습자 말(Phase 1 질문 2 뒤): "근데 .net으로 끝나는데 왜 애드존이지?", "존과 이 네임 서버의 이름. 이 구분이 좀 어떤 구조인지 살짝 헷갈리려네요"
    - 할 일: §2 또는 §4 첫머리에 "존은 이름의 범위, 네임 서버는 그 범위를 답하는 컴퓨터이고 네임 서버의 이름은 어느 도메인 아래에 있어도 된다(`a.edu-servers.net` 이 `edu` 를 맡음)" 한 줄. AI 가 든 비유(관할 구역과 다른 도시의 콜센터)는 학습자가 받아들였음

11. **"점(라벨)마다 존이 생긴다"는 오개념을 막는 문장이 약함**
    - 학습자 말(Phase 2, §2 만 읽고): "www.google.com이라 했을 때 이제 3개의 존에 묶여있는 거죠. 이제 com과 google.com과 www.google.com", 이어서 "그럼 이게 구글.com과 com이 똑같은 존일 수도 있다는 건가?", 마지막 확인 질문엔 "잘 모르겠네요"
    - 근거: §2 에 "위임이 없다면 도메인과 존은 같은 노드를 담습니다"가 있으나 학습자가 이 문장에서 "존은 위임한 곳에서만 갈라진다"를 뽑아내지 못함
    - 할 일: "존은 점이 아니라 위임에서 갈라진다. `www.google.com` 은 보통 `google.com` 존 안의 레코드 한 줄이다. 도메인을 등록하는 일이 곧 TLD 존에 `NS` 를 넣는 위임이다" 를 예와 함께

12. **리졸버(OS 클라이언트) · 첫 서버(재귀 서버) · 루트 서버의 역할 구분 표가 없음**
    - 학습자 말(Phase 1): "통신사 DNS가 8.8.8.8 이제 루트 DNS라는 의미인가요?", "리졸버가 따로 조회한다는 게 … 리졸버 컴프(resolv.conf)를 조회한다는 건가? 아니 etc/host?", "즉 일종의 작은 프로세스라는 개념이군", "쿠버네티스 클러스에서는 이제 DHCP가 코어 DNS에 있다는 말인가요?"
    - 근거: §5 는 "리졸버"를 OS 의 클라이언트 쪽 절반(libc·glibc)으로, §6 은 재귀를 지는 쪽을 "첫 서버"로 부른다. 요즘 흔한 말(스텁 리졸버·재귀 리졸버)과 대응, 누가 첫 서버를 정해 주는가(DHCP, 쿠버네티스에서는 kubelet 이 파드 `/etc/resolv.conf` 에 적음)가 없다. AI 설명 중 "리졸버가 루트부터 따로 찾는다"고 노트와 다른 뜻으로 말해 혼동을 키운 일도 있었음
    - 할 일: §5 끝 또는 §6 첫머리에 세 역할 표(이름·하는 일·예: libc 리졸버 / 통신사 DNS·8.8.8.8·CoreDNS / a~m.root-servers.net). 애니캐스트는 §7 이 언급하므로 cntd 04-04 §1·05-02 §5 링크 후보(학습자가 "IP는 기계당 한 대 아니었나"라고 물음)

13. **재귀 질의·반복 질의와 포워더의 관계가 한 그림에 없음**
    - 학습자 말(Phase 2, §6 만 읽고): "제기적인 질의를 통해서 이제 저희가 요청한 www.google.com을 이제 IP를 알아냅니다"(두 질의가 섞임), 포워더 이름이 직관과 반대인 이유는 "잘 모르겠습니다", 설명 뒤 "이게 루트 서버에 넘기는 거하고 뭐 똑같은 말이죠"(포워더로 가는 재귀 질의와 루트로 가는 반복 질의를 같은 것으로 봄)
    - 할 일: §6 도식(referral-chain)에 포워더 갈래를 덧붙이거나, "루트에는 반복 질의(참조만 받음) / 포워더에는 재귀 질의(끝까지 맡김)" 대조 한 줄. 1장 `forward` 플러그인(넘기는 동작)과 노트의 포워더(넘겨받는 서버)가 이름이 엇갈린다는 한 줄도 후보

## 2장 (02-02)

14. **§4 MX·SRV 를 `###` 로 나누고 동작 규칙을 앞에 둘 것**
    - 학습자 말(Phase 2, §4 만 읽고): "이 네번째 문단에 대해서 내용을 샵샵샵 단위로 좀 나눠 볼 수도 있지 않을까? 그리고 약간 너무 설명이 장황한 것 같기도 하고". 답은 정의(16비트·0~65535, "MX 를 넓힌다")만 옮기고 동작(낮은 값부터 시도, 같은 우선순위 안에서 가중치 비례)은 빠짐. MX 가 없을 때 규칙은 "주소레코드로 돌아간다. 금지되고"로 조건이 흐려짐
    - Phase 1 질문 3(SRV 칸 예측)은 "모르겠는데", 이어서 "MX와 SRV나 이번에 처음 들었는데 나중에 좀 더 자세하게 설명해 주세요"
    - 할 일: `### MX — 선호도 하나로 순서` / `### SRV — 우선순위로 후보, 가중치로 비율, 포트` 로 나누고 각 `###` 첫 문장을 동작 규칙으로. "MX 0개면 주소가 선호도 0 MX, 1개라도 있으면 주소 배달 금지"를 한 문장으로 앞에. 현행 한 줄 후보: 웹은 SRV 대신 HTTPS·SVCB(RFC 9460, 2023), 쿠버네티스는 이름 붙인 포트에 SRV(6장 링크)

15. **§7 시리얼 — "존을 고치면 시리얼을 올려야 한다, 안 올리면 보조 서버가 기한 없이 옛 데이터"가 문장으로 없음**
    - 학습자 말(Phase 1 질문 5): "1시간 뒤면 이제 바뀐 걸 확인하고 보조 서버도 이제 다시 바꿔주겠죠"(내용 비교로 오해), 채점 뒤 "시리얼을 깜빡한다는 게 정확히 무슨 말이었지?", Phase 2 에서 다시 "시리얼을 뺀다는 게 무슨 말인가?". 세 번째 확인에서 refresh·retry·expire 순서는 노트로 맞게 말함
    - 근거: `### 존 전송을 좌우하는 네 칸` 은 "마스터 쪽 시리얼이 더 높은지 확인"까지만 적고, 시리얼을 안 올렸을 때 결과(확인은 매번 성공해 expire 도 안 걸림, 주·보조 답이 갈림)와 날짜형 시리얼 관례가 없음
    - 할 일: 그 `###` 끝에 실패 사례 한 문단 + 시리얼 관례 한 줄. SOA 앞 두 칸(MNAME·RNAME)을 학습자가 "자식 노드·서버"로 읽었으니 "서버가 아닌 메모"라는 표현을 더 앞으로

16. **문체 — 핵심 문장 먼저, 책 옮기듯 늘어진 문단 줄이기 (02-02 전반)**
    - 학습자 말(Phase 2, §7 점검 뒤): "문장이 좀 긴 것 같아요. 이게 내가 알고 싶은 핵심 정보만 좀 그냥 문서에 적혀있으면 좋겠는데 약간 책 쓰듯이 적어서 그런가? 물론 책 쓰듯이 쓰면 좋긴 한데 핵심 문장만 좀 있으면 좋을 것 같네요"
    - 할 일: 각 `##`·`###` 첫 문장을 규칙 한 줄로, 원서 귀속 서술("저자는 …")은 뒤로. 1번(현행 우선) 요청과 같이 처리. 미사여구 걷기이지 내용 삭제가 아님

17. **§2 생략 규칙 — 위험(줄 끼워 넣기·앞 공백)이 노트에 없음, §3 CNAME 꼭대기 금지의 실무 결과 없음**

    - 할 일: §2 에 "줄을 끼워 넣으면 아래 빈칸 줄이 다른 이름에 붙는다" 한 줄. §3 규칙 2 뒤에 "그래서 꼭대기(`example.com`)는 CDN 이름을 CNAME 으로 못 가리킨다 → 업체별 ALIAS·flattening(비표준)" 한 줄. `www` 없는 이름을 존 꼭대기라고 부르는 것도 함께

## 3장 (03-01)

18. **§6 REFUSED — DNS 응답 코드와 연결 거절(`connection refused`)·DROP 구분을 참조 링크로**
    - 학습자 말(Phase 1 질문 7 뒤): "REFUSED는 방화벽 거부도 있는데 이렇게 DNS가 없어서도 거부할 수 있는 걸 봤는데 이거 어떻게 구분함", 이어서 "REFUSED 관련은 다른 문서에서도 다르니 참고로 넘기거나 참조해서 보게 해주면 좋을 것 같습니다"
    - 근거: §6 은 "세 조건을 모두 채우는 서버 블록이 하나도 없으면 … 거부(`REFUSED`)로 답합니다" 한 문장뿐. 어떤 블록도 듣지 않는 포트는 CoreDNS 가 열지 않아 DNS 응답 자체가 없다는 점도 없음
    - 할 일: 그 문장 뒤에 한두 줄 — REFUSED 는 DNS 응답 안의 응답 코드(`dig` 의 `status: REFUSED`)이고, 포트가 닫혔거나 방화벽이 막으면 DNS 응답 없이 `connection refused`·timeout 으로 끝난다. 설명은 풀지 말고 [networking-and-kubernetes 02-06 §1 DROP과 REJECT](../../networking-and-kubernetes/02-06.커널%20네트워킹%20실습%202%20—%20막고,%20진단하고,%20나누기.md) 로 넘긴다(인코딩은 반영 때 확인)

19. **§2 명령줄 옵션 — 옵션 표만 있고 실제로 띄우는 명령줄 예시가 없음**
    - 학습자 말(Phase 2, §2 점검 때): "명령줄 옵션 여덟 -> 여기서 명령줄 예시도 넣어줘"
    - 근거: §2 는 옵션 여덟을 표로만 적고, 옵션을 붙인 실행 한 줄이 없음. Phase 1 에서 학습자가 "Corefile 에 명령줄 옵션이 담겨 있다"고 읽었다(둘의 관계 혼동)
    - 할 일: 표 아래 코드 블록 하나 — 로컬 실행 예(`./coredns -conf ./Corefile -dns.port 1053 -log-format json`)와 k8s Deployment 의 `args: ["-conf", "/etc/coredns/Corefile"]`. `-conf` 가 "어느 Corefile 을 읽을지" 잇는 고리라는 한 문장. Deployment args 는 반영 때 kubeadm 매니페스트 원문으로 확인

## 4장 (04-01)

20. **§1 — "온전한 존"과 존 자체의 정의가 없음, 존과 서버 블록·Corefile 이 구분되지 않음**
    - 학습자 말(Phase 2 거꾸로 설명 직전): "존이라 함은 사실 내가 잘 이해못한거 같은데 Corefile에서 . {} 이런식의 단위를 말하는게 아니었나?", 이어서 "Corefile은 그러면 뭐임? 존이 아니야?"
    - 근거: §1(`:69-73`)은 "`SOA` 를 포함한 온전한 존" 을 첫째 물음으로 쓰지만 존이 무엇인지, 서버 블록 라벨에 적는 존 이름과 플러그인이 읽는 존 데이터가 어떻게 다른지 적지 않음. 4장이 "존 데이터를 Corefile 밖 어디에 두는가"를 다루는데 그 전제가 비어 있음
    - 할 일: §1 첫머리에 두세 문장 — 존은 이름 범위 하나와 그 레코드 묶음(데이터), 서버 블록은 그 범위의 질문을 받을 플러그인을 정하는 설정, Corefile 은 서버 블록 묶음. `foo.example { file db.foo.example }` 한 줄로 라벨(거르는 표시)과 존 데이터(파일)를 가르는 예. 정의는 [02-01](./02-01.위임이%20그은%20경계가%20질의%20경로를%20정한다.md)·[03-01](./03-01.Corefile은%20라벨로%20서버를%20가른다.md) 링크로 넘김(인코딩은 반영 때 확인). "온전한 존 = `SOA` 를 가진 존, `SOA` 는 권한 시작 선언이자 보조 서버가 변경을 가리는 시리얼" 한 문장

21. **§2 — 상대 이름 파일 하나로 여러 존: origin 이 "그 파일을 어느 존으로 읽느냐"에서 정해진다는 연결이 없음**

    - 근거: §2(`:95-103`)는 "레코드가 전부 상대 도메인 이름이면 파일 하나로 여러 존" 과 "내용이 똑같기를 바랄 때" 만 적음. 왜 그런지(같은 파일을 존마다 다른 origin 으로 읽음)와 점으로 끝나는 이름이 섞이면 어떻게 되는지가 없음
    - 할 일: `:95` 뒤에 작은 표 하나 — 파일에 적힌 `www` 와 `www.foo.example.` 이 `foo.example`·`bar.example` 으로 읽힐 때 각각 무엇이 되는지. origin 규칙은 [02-02 NAME 칸](./02-02.레코드%20한%20줄을%20읽으면%20존%20파일이%20읽힌다.md) 링크

22. **§5 — `0.0.0.0` 으로 보내는 것이 왜 광고 차단이 되는지 없음**
    - 학습자 말(Phase 2 §5 점검 뒤): "광고에 쓰이는 도메인 이름을 호스트 테이블에 담아 읽은 뒤 보낸다?"
    - 근거: §5(`:236`)와 결정 치트시트(`:315`)가 "`0.0.0.0` 으로 보내는 용례" 만 적고, 그 주소로 답하면 클라이언트가 광고 서버에 닿지 못한다는 결과를 적지 않음. Phase 1 에서 학습자는 hosts 를 "노드에서 직접 관리하는 도메인 IP" 로 읽음(CoreDNS 가 읽으면 묻는 모든 클라이언트가 받는다는 점도 없음)
    - 할 일: `:236` 에 한 문장 — 광고 도메인의 답을 `0.0.0.0` 으로 주면 클라이언트가 실제 광고 서버 주소를 얻지 못해 광고를 불러오지 못한다(그래서 차단). `/etc/hosts` 는 그 컴퓨터만 보지만 CoreDNS 의 `hosts` 는 CoreDNS 에 묻는 모든 클라이언트에 적용된다는 한 줄. `0.0.0.0` 접속 시 OS 동작은 반영 때 확인하고 단정하지 않음

    - 학습자 말(Phase 1 질문 8 예측): "존의 도메인 이름말고 실제 IP도 필요하겠죠? (내부인경우 글루 서버를 통해 받았는데 외부인 경우는 IP도 받아오나?)", 채점 보충 뒤 "퍼블릭 호스트 존(도메인 이름가진) - 이게뭐임, 프라이빗 호스트존?", "저거 2개 존에 대해서는 누가 가지고 있는데", 끝으로 "그냥 모르는거 같은데 일단 넘어가자"

    - 할 일: §6 첫머리 요약 다음에 흐름 도식 한 장(Route 53 원본 → AWS API, `refresh` 1분 → CoreDNS 사본 → 클라이언트 질의). "DNS 존 전송이 아니라 API 라서 IP·글루가 아니라 ID·자격증명이 필요하다" 한 문장. `:285` 뒤에 Public/Private 두 줄 정의와 `www.corp.example` 이 밖에서는 공인 주소, 안에서는 내부 주소로 가는 예. Public/Private 정의는 AWS 공식 문서로 확인 후 각주

24. **§1·§6 — `route53` 이 `SOA` 를 갖는데도 전송이 안 되는 이유가 본문에 없음(도식에만 "못 한다")**

### 27. `02-02` 「부정 응답을 좌우하는 한 칸」 — CoreDNS 에서는 MINIMUM 이 아니라 SOA 레코드 TTL 이 부정 캐시 시간을 정함

- 학습자 말: 처음 예측 "시리얼 넘버가 정한다, 30초 뒤(최대 32초)". 변형 예측 "20 은 처음부터 있었는데 30 을 따랐으니 300".
- 근거: S3 실측(CoreDNS 1.15.0, `cache` + `file`) — `$TTL 30`·MINIMUM 20 에서 NXDOMAIN 의 SOA TTL 30 → 14·11·8·5·2 → 새 답. `$TTL 300`·MINIMUM 20 에서 SOA TTL 300 → 297. RFC 2308 §5 규칙(둘 중 작은 값)이면 20 이어야 함. `file` 은 SOA 를 레코드 TTL 그대로 실어 보내고, `cache` 는 메시지 안 레코드 TTL 의 최솟값만 씀(`plugin/pkg/dnsutil/ttl.go` `MinimalTTLWithMaximum`, MINIMUM 칸을 읽지 않음).
- 할 일: 그 절 끝에 "CoreDNS 의 `cache` 는 MINIMUM 을 보지 않고 응답에 실린 SOA 레코드의 TTL 을 쓰므로, 부정 캐시를 줄이려면 SOA 의 TTL 을 낮추거나 `cache` 의 `denial` 로 상한을 둔다" 한 문단. MINIMUM 은 RFC 2308 을 따르는 다른 리졸버가 읽는다는 한 줄. 방법 셋(파일 앞 `$TTL 30` 뒤 `$TTL 300`, `@ 30 IN SOA`, `cache { denial 9984 30 }`)은 2026-11-03 실측 확인.

### 29. `04-01` 「hosts」 fallthrough 문단 — 넘기지 않을 때 못 찾은 이름은 NXDOMAIN 이 아니라 SERVFAIL

- 학습자 말(S7): 처음엔 "파일에 둘 다 있으니 둘 다 정상"이라고 봄. `fallthrough` 를 넣은 뒤에는 "api 는 존 파일 값 .40 으로 온다"고 예측(실제는 hosts 의 .99).
- 근거: S7 실측(CoreDNS 1.15.0) — `shop.example { hosts { 198.51.100.99 api.shop.example }  file db.shop.example }` 에서 db 는 SERVFAIL. hosts 에 SOA 가 없어 NXDOMAIN 을 만들 수 없다(`plugin/hosts/hosts.go:72-74` 주석). `03-02` 「fallthrough」 는 "없으면 NXDOMAIN 이나 빈 응답"이라고 일반화하는데, SOA 가 없는 hosts 는 이 규칙에서 벗어난다. `fallthrough` 뒤에도 api 는 hosts 답(TTL 3600, AUTHORITY 0)이었다. `04-01` 277줄은 "답을 못 찾았을 때 넘긴다"고 맞게 적었지만, 찾은 이름은 계속 hosts 가 답한다는 반대쪽은 적지 않았다.
- 할 일: `04-01` hosts fallthrough 문단 끝에 두 문장 — "넘기지 않으면 호스트 테이블에 없는 이름은 SERVFAIL 로 끝난다. hosts 에는 SOA 가 없어 NXDOMAIN 을 만들 수 없기 때문이다." "넘기더라도 테이블에 있는 이름은 hosts 가 답하므로, 같은 이름을 존 파일 값으로 되돌리려면 그 줄을 지워야 한다." `03-02` 는 다른 창이 고치는 중이라 손대지 않고, 필요하면 "SOA 가 있는 플러그인 기준"이라는 한정만 나중에 검토.

### 30. `05-01` §6 리스 TTL — `min-lease-ttl`·`max-lease-ttl` 이 보안 수정에서 나왔다는 배경

- 학습자 말: "왜 30초인지는 모른다는데 조사 좀", 이어서 "etcd 값은 원래 한번 저장되면 굉장히 오래 쓰는데 TTL 을 도입해 극단적 캐싱을 막았다"로 오해.
- 근거: CoreDNS 보안 권고 GHSA-93mf-426m-g6x9(CVE-2025-58063, high, 2025-09-09) — v1.2.0(#1702)부터 `TTL()` 이 리스 **ID** 를 `uint32` 로 잘라 TTL 로 써 캐시 고정(cache pinning)이 가능했음. 수정 커밋 `e1768a5d2`(v1.12.4) 메시지: "fix the TTL() function to use etcd time-to-live API … Add configurable min-lease-ttl and max-lease-ttl options to prevent extreme TTL values … 30s to 1d as the min/max." 숫자 30 의 근거는 커밋·권고 어디에도 없음.
- 할 일: §6 "둘 다 v1.12.4 에 붙었습니다" 뒤에 한 문장 — 리스 ID 를 TTL 로 쓰던 버그의 수정으로 들어왔고, 그래서 리스 유래 TTL 은 실제 남은 시간을 30초~1일로 가둔다. 각주로 권고문 링크. 30 의 이유는 적지 않음.

### 31. `05-01` 「TTL 에 기대는 클라이언트」 — 클라이언트가 어디서 캐시하는지(캐시 겹)가 없음

- 학습자 말: "지금 어떤 구조로 캐싱되는 건지 궁금함", "저 DNS 캐시 계층은 문서에서 잘 다루는가? 꽤 중요해 보이는데".
- 근거: 노트 전체 grep(2026-11-04) — JVM `networkaddress.cache.ttl` 은 `06-02`·`06-04`·`07-01`, NodeLocal DNSCache 는 6장, CoreDNS `cache` 는 `03-02` 에 흩어져 있고, OS 캐시(systemd-resolved·nscd·mDNSResponder)는 어디에도 없음. 겹을 한 그림으로 쌓은 곳도 없음. 05-01 이 "클라이언트는 TTL 을 기다린다"를 처음 꺼내는 자리.
- 할 일: 그 절에 겹 그림 한 장(앱/런타임 → OS → 노드·중간 리졸버 → CoreDNS `cache` → `etcd` 플러그인은 매번 읽음)과 한 문단, `06-02`·`07-01` 링크. OS 캐시는 공식 문서 확인 뒤 한 줄. Go 기본 리졸버·glibc `getaddrinfo` 는 자체 캐시가 없다는 점도 소스·문서로 확인 뒤.

### 32. `05-01` §4·§5 — 등록→etcd, etcd→CoreDNS, CoreDNS→클라이언트 세 구간의 속도를 한곳에서
