# 모니터링 개요와 트러블슈팅 루틴 — 관찰의 세 기둥과 장애 진단 순서

---

> 클러스터 운영에서 관찰 가능성의 세 기둥인 메트릭·로그·트레이스를 구분하고, 장애가 발생했을 때 이벤트에서 시작해 리소스까지 내려가는 디버깅 루틴을 체계화합니다.



## 학습 목표

> 관측 신호의 역할 차이를 익히고 `kubectl` 기반 장애 진단 순서를 고정합니다.

1. 메트릭·로그·트레이스의 역할 차이와 수집 방식을 설명할 수 있습니다.
2. 이벤트·로그·내부 접속·리소스 확인으로 이어지는 4단계 디버깅 흐름을 수행할 수 있습니다.
3. `CrashLoopBackOff`, `OOMKilled`, `Pending`, `ImagePullBackOff` 장애 패턴을 진단할 수 있습니다.



## 1. 관찰 가능성의 세 기둥

> 메트릭, 로그, 트레이스가 각각 어떤 질문에 답하는지 먼저 구분합니다.

주문 API 의 응답이 느려졌다는 알림을 받았다고 합시다. 대시보드의 그래프, 애플리케이션 로그, 요청 하나가 지나간 경로를 모두 열 수 있습니다. 하지만 어느 화면이 지금 질문에 답하는지 정해 두지 않으면 세 화면을 오가며 시간을 씁니다. 그래서 장애 진단 순서(§2)보다 먼저 세 신호가 각각 무엇을 알려 주는지 나눕니다.

### 1.1 메트릭·로그·트레이스

세 가지는 서로 다른 질문에 답합니다. 메트릭은 "무엇이 얼마나 나쁜가"를 수치로 나타냅니다. CPU 사용률, HTTP 요청 수, 에러율 같은 집계 데이터입니다. 시간 경과에 따른 추세를 파악하고 임계값 기반 알림을 걸기에 적합합니다. 로그는 "무슨 일이 일어났는가"를 이벤트 스트림으로 기록합니다. 메트릭이 이상 징후를 포착하면 로그로 구체적인 에러 메시지를 확인합니다. 트레이스는 "어떤 경로를 거쳐 느려졌는가"를 서비스 간 요청 흐름으로 시각화합니다. 마이크로서비스 환경에서 어느 서비스가 병목인지 찾을 때 씁니다.

세 가지의 비용이 다릅니다. 메트릭은 집계 데이터라 저장 비용이 낮습니다. 로그는 양이 많아 비용이 높고 적절한 레벨(INFO/WARN/ERROR) 관리가 중요합니다. 트레이스는 전체 요청을 기록하면 오버헤드가 크므로 샘플링을 조정합니다. 로그를 수집하고 레이블 단위로 인덱싱해 메트릭과 연계하는 구조는 [Grafana Loki](../../../../06_observability/02_LGTMStack/02-03.Grafana%20Loki.md)를 참고합니다.

### 1.2 Prometheus의 Pull 모델

Prometheus는 Pull 모델을 씁니다. Prometheus가 주기적으로 각 대상의 `/metrics` 엔드포인트를 호출해 데이터를 수집합니다. Push 모델(대상이 Prometheus에 직접 전송)과 달리, 대상이 죽으면 Prometheus가 다음 수집에서 바로 압니다. 수집 실패 자체가 알림 대상이 됩니다. Prometheus FAQ 도 Pull 의 장점으로 대상이 내려갔는지를 더 쉽고 믿을 만하게 알 수 있다는 점을 듭니다. 단기 배치 작업처럼 존재 기간이 짧아 폴링이 불가한 경우에는 Pushgateway를 중간에 두고 Push 방식을 보완합니다.

여기서 헷갈리기 쉬운 점이 있습니다. `kubectl top`이 보여주는 CPU·메모리 사용량은 보통 `Metrics Server`가 제공하는 간이 메트릭입니다. Prometheus는 이와 별도인 모니터링 스택입니다. 즉 HPA나 운영자가 빠르게 사용량을 보는 경로와, 장기 저장·알림·대시보드용 관측 스택은 보통 분리돼 있습니다.



## 2. 장애 진단 순서와 디버깅 흐름

> 장애가 났을 때 무엇부터 확인할지 순서를 고정합니다.

관측 신호로 이상 징후를 감지했다면, 실제 클러스터에서 장애 원인을 좁혀 들어가는 체계적인 진단 순서가 필요합니다.

### 2.1 kubectl 기반 디버깅 흐름

순서는 바깥에서 안으로 들어갑니다. 쿠버네티스가 이미 기록해 둔 이벤트를 먼저 보고, 컨테이너가 남긴 로그, 컨테이너 안, 자원 사용량 순으로 좁힙니다.

```pseudocode
이벤트 → 로그 → 내부 접속 → 리소스
```

```bash
# 1단계: 이벤트 확인
kubectl describe pod <pod-name> -n <namespace>
# Events 섹션에 스케줄링 실패, 이미지 풀 에러, 프로브 실패 원인이 기록됨

# 2단계: 로그 확인
kubectl logs <pod-name> -n <namespace>
kubectl logs <pod-name> -n <namespace> --previous   # 이전 컨테이너 로그

# 3단계: 내부 접속
kubectl exec -it <pod-name> -n <namespace> -- /bin/sh
# 컨테이너 안에서 curl, nslookup, env 등으로 직접 확인

kubectl port-forward <pod-name> 8080:8080 -n <namespace>
# Service를 거치지 않고 로컬↔Pod를 직접 터널링해, 앱 자체가 뜬 건지 Service/Ingress 문제인지 가려냄

# 4단계: 리소스 확인
kubectl top pod -n <namespace>
kubectl top node
```

`port-forward`는 연결성 장애의 범위를 좁히는 데 특히 유용합니다. port-forward로 Pod에 직접 붙어 정상이면 앱은 살아 있는 것입니다. 그러면 문제는 그 앞단의 Service selector·EndpointSlice·Ingress·NetworkPolicy 쪽에 있을 가능성이 큽니다.

### 2.2 주요 장애 패턴

`CrashLoopBackOff`는 컨테이너가 시작했다가 즉시 종료되는 패턴입니다. `--previous` 플래그로 이전 컨테이너 로그를 먼저 확인합니다. 애플리케이션 시작 에러, 설정 오류, 의존 서비스 미준비가 주요 원인입니다.

kubelet 은 종료된 컨테이너를 10초, 20초, 40초처럼 두 배씩 늘린 간격으로 다시 띄웁니다. 간격은 300초(5분)에서 멈춥니다. `describe pod` 의 Events 에는 `BackOff` 와 `Back-off restarting failed container` 가 남습니다.

STATUS 칸이 늘 `CrashLoopBackOff` 를 보여 주지는 않습니다. 공식 문서도 STATUS 는 사람이 보기 좋게 만든 표시 칸이지 Pod phase 가 아니라고 적습니다. 그래서 STATUS 이름보다 `RESTARTS` 가 늘어나는지와 Events 의 `BackOff` 를 봅니다.

kind(Kubernetes v1.35.0)에서 바로 `exit 1` 하는 컨테이너를 띄워 보면 이 차이가 보입니다. 처음 3분 남짓은 STATUS 가 마지막 종료 이유인 `Error` 였습니다. 재시작 5회째에 `CrashLoopBackOff` 로 바뀌었고 대기 메시지는 `back-off 2m40s` 였습니다. 10초를 네 번 두 배로 늘리면 160초, 곧 2분 40초이니 위 간격과 맞습니다.

`--previous` 가 언제나 통하는 것도 아닙니다. 같은 실측에서 컨테이너 상태가 아직 `terminated` 로 남아 있던 동안에는 `kubectl logs` 만으로 마지막 에러 메시지가 나왔습니다. 이때 `--previous` 는 `unable to retrieve container logs` 로 실패했습니다. 상태가 `waiting`(`CrashLoopBackOff`)으로 바뀐 뒤에는 두 명령이 같은 메시지를 보여 줬습니다. 하나가 비면 다른 하나를 봅니다.

`OOMKilled`는 메모리 Limits를 초과해 커널 OOM killer 가 컨테이너 프로세스를 SIGKILL 로 끝낸 상태입니다. `kubectl describe pod`의 `Last State`에 `OOMKilled` 와 종료 코드 137(128+9)이 표시됩니다. Limits를 올리거나 메모리 누수를 찾아야 합니다. 아래는 kind v1.35.0 에서 `limits.memory: 50Mi` 컨테이너가 200MiB 버퍼를 잡았을 때의 출력 일부입니다.

```bash
kubectl describe pod <pod-name> -n <namespace>
```

```bash
    Last State:     Terminated
      Reason:       OOMKilled
      Exit Code:    137
```

`Pending`은 Pod phase 의 이름입니다. phase 로서의 Pending 은 스케줄링을 기다리는 시간과 이미지를 내려받는 시간을 모두 포함합니다. 그래서 STATUS 칸이 `Pending` 으로만 남아 있을 때 먼저 스케줄링 실패를 의심합니다.

이때 `describe pod` 의 Events 에는 `FailedScheduling` 이 찍힙니다. 메시지는 "0/3 nodes are available: 3 Insufficient cpu." 같은 모양입니다. 노드 리소스 부족, NodeSelector/Affinity 불일치, PVC 미바인딩이 원인인 경우가 많습니다. 아래는 kind 단일 노드에서 `requests.cpu` 를 100 으로 준 Pod 의 Events 한 줄입니다.

```bash
  Warning  FailedScheduling  17s (x2 over 75s)  default-scheduler  0/1 nodes are available: 1 Insufficient cpu. ...
```

`ImagePullBackOff`는 이미지를 내려받지 못한 상태입니다. 첫 실패는 STATUS 에 `ErrImagePull` 로 보입니다. kubelet 이 간격을 늘려 다시 받는 동안에는 `ImagePullBackOff` 로 바뀌고 간격은 300초(5분)에서 멈춥니다. 이 동안 Pod phase 는 `Pending` 입니다. 이미지 이름 오타, 태그 미존재, Private 레지스트리 인증 실패를 순서대로 확인합니다.

### 2.3 ephemeral 컨테이너와 kubectl debug

셸이 없는 이미지에는 1단계의 `kubectl exec ... -- /bin/sh` 가 통하지 않습니다. pause 이미지 컨테이너에서 해 보면 `exec: "/bin/sh": stat /bin/sh: no such file or directory` 로 끝납니다. 이럴 때 ephemeral container를 통해 실행 중인 Pod에 디버깅 도구를 주입할 수 있습니다.

```bash
# distroless 같이 셸이 없는 컨테이너 디버깅
kubectl debug -it <pod-name> --image=busybox --target=<container-name>
```

`--target` 은 대상 컨테이너의 프로세스 네임스페이스를 함께 쓰게 합니다. kind 에서 busybox 디버그 컨테이너로 `ps` 를 돌리면 PID 1 에 대상 컨테이너의 `/pause` 가 보였습니다. kubectl v1.33 은 `--profile` 을 주지 않으면 경고를 찍습니다. `--profile=legacy` 가 폐지 예정이니 `--profile=general` 처럼 명시하라는 내용입니다.

Pod 내부뿐 아니라 노드 자체를 진단할 때도 `kubectl debug node/<node-name>` 패턴을 사용할 수 있습니다. 공식 문서 기준으로 이 디버깅 Pod 는 호스트의 IPC·Network·PID 네임스페이스에서 돌고 노드의 루트 파일시스템을 `/host` 에 마운트합니다. 그래서 kubelet 로그나 디스크 상태처럼 Pod 바깥 문제를 확인할 때 유용합니다.

다만 특권 Pod 는 아니어서 `chroot /host` 처럼 슈퍼유저 권한이 필요한 작업은 실패합니다. kind 에서 만든 디버깅 Pod 의 spec 을 보면 `hostPID`·`hostNetwork`·`hostIPC` 가 모두 `true` 였습니다. 이 Pod 는 쓰고 나서 직접 지웁니다.
