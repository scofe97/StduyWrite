# 사이드카 시동·종료 순서 — holdApplicationUntilProxyStarts·네이티브 사이드카·terminationDrainDuration

---

> 메시 안의 파드는 앱과 프록시(`istio-proxy`)가 거의 동시에 시작하고 종료해서, 순서가 어긋나면 시작 직후나 종료 직전의 요청이 실패합니다. 이 문서는 시작 순서를 맞추는 두 방법과 종료 쪽 설정을 다룹니다.

근거는 Istio 1.32 공식 문서와 Kubernetes 사이드카 문서입니다. Istio 쪽은 MeshConfig·pilot-agent·pilot-discovery 레퍼런스와 네이티브 사이드카 블로그입니다.

규칙은 모두 문서의 문장에서 가져왔고, 클러스터에서 재현하지는 않았습니다. 문서의 YAML 은 문법만 확인했습니다. 문서에 없어서 해석이거나 확인하지 못한 문장은 본문에서 그렇게 밝혔습니다.

네이티브 사이드카가 init 컨테이너 규칙 위에서 어떻게 도는지는 [05-03 노트](../../book/kubernetes-in-action/05-03.멀티%20컨테이너·init·네이티브%20사이드카와%20삭제.md)가 풉니다. 사이드카 컨테이너 자체의 구성은 [사이드카를 이루는 넷](../../book/istio-in-action/a0-02.부록%20—%20사이드카를%20이루는%20넷과%20VM%20이%20받는%20다섯%20파일.md) 노트가 맡습니다.



## 1. 앱이 프록시보다 먼저 뜨면 생기는 일

> 프록시가 준비되기 전에 앱이 요청을 보내면 그 요청은 나갈 길이 없습니다. 반대로 프록시가 먼저 내려가거나, 앱이 끝났는데 프록시가 남는 경우도 문제입니다.

파드의 컨테이너들은 거의 동시에 시작합니다. 앱이 시작하자마자 설정 서버에 접속하거나 DB 연결 풀을 만들면, 프록시가 아직 트래픽을 받을 준비가 안 돼 연결이 거부됩니다.

앱이 재시도 없이 종료하면 파드가 `CrashLoopBackOff` 로 들어갑니다. 몇 번 재시작한 뒤에야 정상이 되기도 해서, 간헐 오류처럼 보이고 원인을 찾기 어렵습니다.

Istio 블로그는 이 문제를 네 가지로 나눠 적습니다.[^blog-problems]

- 앱 컨테이너가 프록시보다 빨리 시작하면 네트워크를 쓸 수 없습니다.
- 종료할 때 프록시가 앱보다 먼저 내려가면 앱이 네트워크를 쓸 수 없습니다.
- 앱이 일부러 끝나는 `Job` 에서는 프록시가 계속 돌아 파드가 끝나지 않습니다.
- init 컨테이너는 프록시보다 먼저 실행되므로 네트워크를 쓸 수 없습니다.

![기본 동작과 두 해법의 시작·종료 순서 비교](./_assets/%EC%82%AC%EC%9D%B4%EB%93%9C%EC%B9%B4%20%EC%8B%9C%EB%8F%99%C2%B7%EC%A2%85%EB%A3%8C%20%EC%88%9C%EC%84%9C.startup-order.svg)

해법은 둘입니다. 하나는 앱 시작을 미루는 Istio 설정 `holdApplicationUntilProxyStarts` 입니다. 다른 하나는 Kubernetes 가 순서를 보장하는 네이티브 사이드카입니다.

두 방법이 다루는 범위가 다릅니다. 앞의 것은 시작만 다루고, 뒤의 것은 시작·종료·`Job` 종료·init 컨테이너 네트워크를 모두 다룹니다. 증상이 시작 순서뿐인지 먼저 가립니다.



## 2. 앱 시작을 미루는 훅 설정

> 이 값을 켜면 프록시가 트래픽을 받을 준비가 될 때까지 앱 컨테이너 시작을 미룹니다. 기본값은 `false` 입니다.

MeshConfig 레퍼런스는 이 필드를 `BoolValue` 로 정의합니다. 프록시가 트래픽을 받을 준비가 될 때까지 앱 시작을 미루는 훅을 붙여, 시작 경쟁 상태를 줄인다고 설명합니다.[^mesh-hold]

레퍼런스에 구현 설명은 이 문장이 전부입니다. Istio 1.32 문서에서 이 설정을 다룬 곳은 MeshConfig 레퍼런스뿐이었습니다. 트러블슈팅 페이지(`ops/common-problems/network-issues`)에는 `holdApplicationUntilProxyStarts` 가 나오지 않습니다. 사이드카 주입 페이지(`setup/additional-setup/sidecar-injection`)에도 없습니다.[^mesh-hold] 훅이 어떤 컨테이너에 어떤 lifecycle 훅으로 붙는지는 열어 본 문서에 없었고, 이 문서도 확인하지 못했습니다.

메시 전체에 켜는 방법은 `meshConfig.defaultConfig` 입니다.

```yaml
apiVersion: install.istio.io/v1alpha1
kind: IstioOperator
spec:
  meshConfig:
    defaultConfig:
      holdApplicationUntilProxyStarts: true
```

파드 하나에만 켜려면 파드 템플릿에 annotation `proxy.istio.io/config` 를 씁니다.

```yaml
apiVersion: apps/v1
kind: Deployment
metadata:
  name: client
spec:
  replicas: 1
  selector:
    matchLabels: { app: client }
  template:
    metadata:
      labels: { app: client }
      annotations:
        proxy.istio.io/config: |
          holdApplicationUntilProxyStarts: true
    spec:
      containers:
      - name: app
        image: example/client:1.0
```

`client`, `example/client:1.0` 은 구조를 보이려고 지은 값입니다.

두 설정이 겹치면 필드 단위로 병합합니다. annotation 에서 지정한 필드는 메시 기본값의 같은 필드를 통째로 대체하고, 다른 필드는 기본값이 그대로 남습니다.[^mesh-merge]

레퍼런스는 이것이 protobuf 의 깊은 병합과 다르다고 덧붙입니다. 예로 `tracing.sampling` 만 지정하면 기본값에 있던 zipkin 같은 tracing 설정이 모두 사라집니다.

프록시 설정은 동적으로 바뀌지 않습니다. 레퍼런스에 따르면 `ProxyConfig` 필드를 바꾼 뒤에는 워크로드를 재시작해야 반영됩니다.[^mesh-merge] 켠 뒤에는 파드를 다시 만듭니다.



## 3. 네이티브 사이드카로 순서 맡기기

> 네이티브 사이드카는 `restartPolicy: Always` 를 가진 init 컨테이너입니다. Kubernetes 가 시작·종료 순서를 보장하므로 Istio 가 훅을 붙일 필요가 없습니다.

Kubernetes 는 사이드카 컨테이너를 init 컨테이너의 특수한 경우로 구현하고, 사이드카는 파드가 시작한 뒤에도 계속 돕니다.[^k8s-sidecar]

init 컨테이너의 순서 보장이 그대로 적용됩니다. Kubernetes 문서가 직접 적은 것은 여기까지입니다. 사이드카가 시작(`started`)된 뒤에 kubelet 이 다음 init 컨테이너를 시작합니다.[^k8s-sidecar]

일반 컨테이너가 그 뒤에 시작된다는 말은 이 순서 보장에서 이끌어 낸 설명이고, Kubernetes 문서에 직접 쓰인 문장은 찾지 못했습니다. 직접 쓴 문장은 Istio 블로그에 있습니다. 블로그는 프록시가 준비될 때까지 뒤쪽 initContainers 와 모든 일반 컨테이너가 시작하지 않는다고 적습니다.[^blog-problems]

사이드카가 시작됐다는 판정은 프로세스가 돌고 있으면 참이고, `startupProbe` 가 있으면 그것이 성공했을 때 참입니다.

종료는 반대입니다. 파드를 종료할 때 kubelet 은 주 애플리케이션 컨테이너가 완전히 멈출 때까지 사이드카 종료를 미룹니다. 그다음 사이드카를 파드 스펙에 적힌 순서의 역순으로 내립니다.[^k8s-sidecar]

Kubernetes 문서의 기능 상태 표기는 세 시점입니다. v1.28 에서 처음 제공됐습니다. v1.29 부터 기본으로 켜졌고 v1.33 부터 stable 입니다.[^k8s-sidecar]

Istio 가 이 기능을 쓰면 `istio-proxy` 가 `containers` 가 아니라 `initContainers` 에 나타납니다. 블로그는 이를 `restartPolicy: Always` 를 가진 initContainer 라고 설명합니다.[^blog-problems]

그 결과가 세 가지입니다. 프록시가 준비된 뒤에 다른 init 컨테이너가 돕니다. 앱이 끝난 뒤에 프록시가 내려갑니다. `Job` 은 앱이 끝나면 프록시가 남아 있어도 파드가 끝납니다.

네이티브 사이드카는 istiod 환경 변수 `ENABLE_NATIVE_SIDECARS` 로 제어합니다. `pilot-discovery` 레퍼런스에 따르면 기본값은 `auto` 입니다.[^pd-native]

| 값 | 뜻 |
|----|-----|
| `true` | 무조건 켭니다 |
| `false` | 무조건 끕니다 |
| `auto` | 지원되는 경우에 자동으로 켭니다 |

이 변수는 Kubernetes 의 `SidecarContainers` 기능 게이트를 전제로 합니다. 블로그의 설치 예는 다음과 같습니다.[^blog-problems]

```bash
istioctl install --set values.pilot.env.ENABLE_NATIVE_SIDECARS=true
```

`auto` 가 실제로 켜지는 조건(Kubernetes 버전·주입 방식)은 확인하지 못했습니다. 블로그 글은 Istio 1.19 시험판과 알파 시기를 기준으로 쓰였습니다. 현재 상태는 Kubernetes 문서와 레퍼런스 쪽을 따릅니다.

두 방법을 함께 켰을 때의 상호작용도 열어 본 문서에 없었습니다.



## 4. 종료 쪽 설정

> 프록시가 요청을 다 처리하기 전에 내려가면 진행 중인 연결이 끊깁니다. 문서로 확인된 설정은 `terminationDrainDuration` 과 환경 변수 둘입니다.

앱은 SIGTERM 을 받은 뒤에도 마무리 요청을 보냅니다. 그때 프록시가 이미 내려가 있으면 마무리 요청이 실패합니다. 반대로 프록시가 너무 오래 남으면 파드 종료가 늦어집니다.

`terminationDrainDuration` 은 프록시를 종료할 때 연결이 끝나도록 허용하는 시간입니다. SIGTERM 이나 SIGINT 를 받으면 `istio-agent` 가 활성 Envoy 에게 우아하게 비우기(draining)를 시작시킵니다. 새 연결은 막고 기존 연결이 끝나기를 기다립니다.[^mesh-drain]

`istio-agent` 는 그다음 이 시간만큼 기다린 뒤 남은 Envoy 프로세스를 죽입니다. 설정하지 않으면 기본 5초가 적용됩니다.

```yaml
meshConfig:
  defaultConfig:
    terminationDrainDuration: 30s
```

연결이 일찍 끝나도 계속 기다리지 않게 하는 환경 변수가 둘 있습니다.[^pa-env]

| 환경 변수 | 형식·기본값 | 뜻 |
|-----------|-------------|-----|
| `EXIT_ON_ZERO_ACTIVE_CONNECTIONS` | Boolean, `false` | `true` 면 비우는 동안 활성 연결이 0 이 되는 즉시 프록시를 끝냅니다 |
| `MINIMUM_DRAIN_DURATION` | Duration, `5s` | 에이전트가 활성 연결을 확인하기 전에 기다리는 최소 시간입니다 |

MeshConfig 의 `proxyMetadata` 는 프록시에 추가할 환경 변수 맵입니다.[^mesh-env] 그래서 이 변수들도 같은 자리에 넣어 전달한다고 읽을 수 있습니다.

```yaml
meshConfig:
  defaultConfig:
    proxyMetadata:
      EXIT_ON_ZERO_ACTIVE_CONNECTIONS: "true"
```

이 예는 레퍼런스의 두 문장을 이어서 만든 것이고, 레퍼런스가 이 변수를 `proxyMetadata` 로 전달하라고 직접 적지는 않습니다. 돌려 보지 않았습니다.

`terminationDrainDuration` 은 파드의 `terminationGracePeriodSeconds` 와 같이 봅니다. Kubernetes 는 유예 시간이 끝나면 남은 프로세스에 KILL 신호를 보냅니다.[^k8s-grace] 그러므로 drain 시간이 유예 시간보다 길면 그 시간을 다 쓰지 못하고 강제 종료될 것으로 읽힙니다.

이 관계는 Istio 문서가 두 값을 함께 적은 문장이 아니라 위 두 문서를 이은 추론입니다. 네이티브 사이드카를 쓰면 주 컨테이너가 멈춘 뒤에야 사이드카 종료가 시작되므로 같은 유예 시간 안에서 둘이 순서대로 시간을 씁니다. 이 점도 문서에서 계산해 보지 않았습니다.
