# 노드 압박 축출과 디스크 관리 — DiskPressure는 무엇을 보고 켜지는가

---

> kubelet 은 메모리와 디스크와 프로세스 ID 를 10초마다 재고, 그 값이 임계를 건드리면 노드에 압박 컨디션을 답니다. 그다음 하는 일은 파드를 죽이는 것이 아니라 죽은 컨테이너와 안 쓰는 이미지를 지우는 것입니다. 그래도 모자랄 때 비로소 파드를 고릅니다.

## 학습 목표

> 이 문서를 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. node-pressure 축출과 API 기반 축출을 결정 주체로 갈라 설명할 수 있습니다.
2. `DiskPressure` 가 어떤 신호를 보고 켜지는지 여섯 신호의 이름과 출처로 말할 수 있습니다.
3. `nodefs`·`imagefs`·`containerfs` 가 실제 디스크에 어떻게 대응하는지 세 배치로 구분할 수 있습니다.
4. 디스크가 찼을 때 kubelet 이 무엇을 어떤 순서로 지우는지 설명하고, 그 순서가 파일시스템 배치에 따라 달라지는 이유를 말할 수 있습니다.
5. 파드가 `ephemeral-storage` 로 자기 몫을 선언하는 법과 노드가 `Allocatable` 로 미리 떼어 두는 몫을 구분해 설정할 수 있습니다.

아래는 신호에서 축출까지의 사다리를 한 장으로 이은 지도입니다. 각 단이 본문의 어느 절에 해당하는지를 오른쪽에 적어 두었습니다.

![압박 신호에서 파드 축출까지의 다섯 단](_assets/01-01-eviction-ladder.svg)

다루지 않는 범위가 둘 있습니다. `PodDisruptionBudget` 과 `drain` 이 얽히는 계획된 중단은 [토폴로지 분산과 중단 정책](../../kubernetes/05_scheduling/05-02.%ED%86%A0%ED%8F%B4%EB%A1%9C%EC%A7%80%20%EB%B6%84%EC%82%B0%EA%B3%BC%20%EC%A4%91%EB%8B%A8%20%EC%A0%95%EC%B1%85.md)에 있습니다. 컨테이너 하나가 메모리 한도를 넘어 커널에 죽는 `OOMKilled` 의 사례 추적은 [OOMKilled 사례 분석](../../kubernetes/09_operations/09-02.OOMKilled%20%EC%82%AC%EB%A1%80%20%EB%B6%84%EC%84%9D.md)이 다룹니다.



## 1. 축출은 두 종류이고, 결정 주체가 다릅니다

> 노드 압박 축출은 kubelet 이 스스로 정하고, API 기반 축출은 밖에서 요청합니다. 지켜 주는 것도 서로 다릅니다.

`kubectl drain` 을 걸면 파드가 사라지고, 노드 디스크가 차도 파드가 사라집니다. 둘 다 "축출"이라 불리지만 공식 문서는 두 페이지로 나눠 두었고, 실제로 다르게 동작합니다.

node-pressure 축출은 kubelet 이 노드 위에서 스스로 내리는 결정입니다. 공식 문서는 이때 kubelet 이 무엇을 지키지 *않는지*를 먼저 못 박습니다. 설정한 `PodDisruptionBudget` 을 지키지 않고, 파드의 `terminationGracePeriodSeconds` 도 지키지 않습니다.[^k8s-eviction] hard 임계로 걸리면 유예 없이 즉시 종료합니다. soft 임계로 걸린 경우에만 `eviction-max-pod-grace-period` 를 지킵니다.

여기서 오해가 자주 생깁니다. PDB 를 걸어 두었으니 최소 가용 파드 수가 보장된다고 믿는 것입니다. 그 보장은 API 기반 축출에만 걸립니다. 노드가 디스크로 압박을 받으면 PDB 는 아무것도 막지 못합니다.

| 구분 | node-pressure 축출 | API 기반 축출 |
|------|-------------------|--------------|
| 결정 주체 | 노드 위의 kubelet | 사용자·컨트롤러의 API 호출 |
| 계기 | 자원 신호가 임계를 건드림 | `drain`, 스케일 다운, 노드 정비 |
| PDB 준수 | 안 함 | 함 |
| graceful 종료 | hard 는 즉시, soft 만 유예 | 함 |
| 파드 최종 상태 | `Failed` | 정상 종료 절차 |

이 문서는 왼쪽 열만 다룹니다. 오른쪽 열은 [토폴로지 분산과 중단 정책](../../kubernetes/05_scheduling/05-02.%ED%86%A0%ED%8F%B4%EB%A1%9C%EC%A7%80%20%EB%B6%84%EC%82%B0%EA%B3%BC%20%EC%A4%91%EB%8B%A8%20%EC%A0%95%EC%B1%85.md) §3 과 §5 에 있습니다.



## 2. kubelet 이 보는 신호는 여덟 개입니다

> 신호는 그 순간의 잔량이고, 임계는 남아 있어야 할 최소치입니다. 둘을 비교해 축출을 정합니다.

공식 문서는 축출 신호를 "특정 시점의 자원 상태"로 정의하고, 임계값을 "노드에 남아 있어야 할 자원의 최소량"으로 정의합니다.[^k8s-eviction] kubelet 은 이 둘을 견줍니다.

| 신호 | 계산식 | Linux 전용 |
|------|--------|-----------|
| `memory.available` | `capacity[memory]` − `memory.workingSet` | |
| `nodefs.available` | `fs.available` | |
| `nodefs.inodesFree` | `fs.inodesFree` | • |
| `imagefs.available` | `runtime.imagefs.available` | |
| `imagefs.inodesFree` | `runtime.imagefs.inodesFree` | • |
| `containerfs.available` | `runtime.containerfs.available` | |
| `containerfs.inodesFree` | `runtime.containerfs.inodesFree` | • |
| `pid.available` | `rlimit.maxpid` − `rlimit.curproc` | • |

각 신호는 절대값과 백분율을 모두 받습니다. 백분율은 그 신호에 딸린 총량을 기준으로 계산합니다.

용량뿐 아니라 inode 도 신호에 들어 있다는 점을 놓치기 쉽습니다. 작은 파일을 대량으로 만드는 워크로드는 `df` 로 보면 여유가 있는데도 `nodefs.inodesFree` 로 먼저 걸립니다. 디스크가 찼다는 말이 두 가지 뜻을 가진다는 것을 신호 목록이 알려 줍니다.

### 메모리 신호는 `free -m` 과 다릅니다

Linux 노드에서 `memory.available` 은 `free -m` 같은 도구가 아니라 cgroupfs 에서 나옵니다.[^k8s-eviction] 컨테이너 안에서는 `free -m` 이 제대로 동작하지 않고, node allocatable 을 쓰면 판단이 파드가 속한 cgroup 계층에서도 이뤄지기 때문입니다.

kubelet 은 계산에서 `inactive_file` 을 뺍니다. 압박이 오면 회수될 수 있는 메모리로 보기 때문입니다. 반대로 `active_file` 은 회수 불가로 취급합니다. 그래서 블록 기반 로컬 스토리지를 많이 쓰는 워크로드는 커널 캐시가 `active_file` 로 쌓여 노드가 메모리 압박으로 오인될 수 있습니다.[^k8s-eviction] 공식 문서가 권하는 우회는 I/O 가 많은 컨테이너의 메모리 request 와 limit 을 같게 두는 것입니다.



## 3. 디스크가 세 갈래인 이유

> `nodefs`·`imagefs`·`containerfs` 는 세 개의 마운트를 뜻하지 않습니다. kubelet 이 관찰한 역할 이름입니다.

세 식별자는 각각 이렇게 정의됩니다.[^k8s-eviction]

- `nodefs`: 노드의 주 파일시스템입니다. 로컬 디스크 볼륨, 메모리 기반이 아닌 `emptyDir`, 로그 저장, 임시 스토리지가 여기 들어갑니다. `/var/lib/kubelet` 이 여기 있습니다.
- `imagefs`: 컨테이너 런타임이 이미지를 두는 선택적 파일시스템입니다. 이미지는 읽기 전용 레이어입니다. 별도의 `containerfs` 가 없으면 컨테이너 쓰기 레이어도 여기 함께 들어갑니다.
- `containerfs`: 컨테이너 쓰기 레이어를 두는 선택적 파일시스템입니다. 이것을 쓰면 `imagefs` 는 이미지만 담게 됩니다.

공식 문서는 이 이름들이 "kubelet 이 관찰한 파일시스템"을 가리킬 뿐이며 언제나 세 개의 마운트 지점을 뜻하지는 않는다고 적습니다.[^k8s-eviction] 흔한 배치에서는 둘 또는 셋이 같은 파일시스템을 가리킵니다.

kubelet 이 지원하는 배치는 셋입니다.

| 배치 | `nodefs` | `imagefs` | `containerfs` |
|------|----------|-----------|---------------|
| 단일 rootfs | 디스크 1 | 디스크 1 | 디스크 1 |
| split disk | 디스크 1 | 디스크 2 | 디스크 2 |
| split image | 디스크 1 | 디스크 2 | 디스크 1 |

kubelet 은 이 배치를 컨테이너 런타임에서 직접 자동 탐지하고, 그 밖의 로컬 파일시스템은 무시합니다.[^k8s-eviction] 지원하는 배치 밖에서 `/var/lib/kubelet` 이나 `/var/log` 아래에 별도 파일시스템을 물리면 kubelet 이 임시 스토리지를 정확히 보고하지 못할 수 있습니다.[^k8s-ephemeral]

`containerfs` 는 아직 조건이 붙습니다. 원문이 조건을 거는 대상은 특정 배치가 아니라 `containerfs` 식별자를 쓰는 것 자체입니다. 이 식별자를 쓰려면 `KubeletSeparateDiskGC` 피처 게이트가 켜져 있어야 하고, 공식 문서 기준 시점에 `containerfs` 파일시스템을 지원하는 런타임은 CRI-O v1.29 이상뿐입니다.[^k8s-eviction] containerd 를 쓰고 있다면 실질적으로 앞의 두 배치 중 하나입니다.



## 4. 임계가 컨디션이 되기까지

> hard 는 유예 없이, soft 는 관리자가 정한 유예를 채운 뒤 걸립니다. 컨디션은 유예와 무관하게 붙습니다.

임계값의 형식은 `[신호][연산자][수량]` 입니다. `memory.available<10%` 와 `memory.available<1Gi` 는 같은 뜻일 수 있지만 둘을 함께 쓸 수는 없습니다.[^k8s-eviction]

hard 임계는 유예가 없습니다. 걸리는 순간 kubelet 이 파드를 즉시 죽여 자원을 회수합니다. soft 임계는 관리자가 정한 유예 기간과 짝을 이루며, 유예를 넘기기 전에는 축출하지 않습니다. 유예를 지정하지 않으면 kubelet 이 기동 시점에 오류를 냅니다.

기본 hard 임계는 이렇게 정해져 있습니다.[^k8s-eviction]

```bash
memory.available   < 100Mi   # Linux
memory.available   < 500Mi   # Windows
nodefs.available   < 10%
imagefs.available  < 15%
nodefs.inodesFree  < 5%      # Linux
imagefs.inodesFree < 5%      # Linux
```

### 하나를 바꾸면 나머지가 0 이 됩니다

여기에 함정이 하나 있습니다. 위 기본값은 어느 항목도 건드리지 않았을 때만 적용됩니다. 하나라도 값을 바꾸면 나머지 항목은 기본값을 물려받지 않고 0 으로 설정됩니다.[^k8s-eviction]

메모리 임계만 조정하려고 `evictionHard` 에 `memory.available` 한 줄을 적으면, 디스크 임계가 전부 0 이 되어 `DiskPressure` 가 영영 켜지지 않습니다. 디스크가 가득 차도 축출이 걸리지 않는다는 뜻입니다.

다만 노드가 아무 방어도 없는 상태가 되는 것은 아닙니다. §6 의 이미지 가비지 컬렉션은 `imageGCHighThresholdPercent` 라는 별개 임계로 돌기 때문에 축출 임계가 0 이어도 계속 동작합니다. 사라지는 것은 압박 컨디션과 그에 따른 파드 축출입니다.

피하는 방법은 둘입니다. 필요한 임계를 전부 명시하거나, kubelet 설정에서 `mergeDefaultEvictionSettings` 를 `true` 로 두는 것입니다. 이 값을 켜면 바꾸지 않은 항목이 기본값을 물려받습니다. 기본값은 `false` 입니다.[^k8s-kubelet-config]

### 신호가 컨디션으로 옮겨 가는 지도

kubelet 은 유예 설정과 무관하게 노드 컨디션을 보고합니다.[^k8s-eviction] 매핑은 이렇습니다.

| 노드 컨디션 | 이 신호들이 걸리면 |
|------------|------------------|
| `MemoryPressure` | `memory.available` |
| `DiskPressure` | `nodefs.available`, `nodefs.inodesFree`, `imagefs.available`, `imagefs.inodesFree`, `containerfs.available`, `containerfs.inodesFree` |
| `PIDPressure` | `pid.available` |

문서 제목의 질문에 대한 답이 이 표의 가운데 줄입니다. `DiskPressure` 는 한 값이 아니라 여섯 신호 중 *어느 하나라도* 임계를 건드리면 켜집니다. 그래서 `DiskPressure=True` 를 봤다고 곧바로 용량 부족이라 단정하면 안 됩니다. inode 일 수도 있고, 루트 디스크가 아니라 이미지 디스크일 수도 있습니다.

컨트롤 플레인은 이 컨디션을 다시 taint 로 옮깁니다. 주기도 알아 둘 값이 셋입니다. kubelet 은 `housekeeping-interval` 마다 임계를 평가하고 기본값은 10초입니다. 노드 컨디션은 `--node-status-update-frequency` 마다 갱신하며 기본값은 역시 10초입니다. 컨디션이 참과 거짓을 오가는 진동을 막는 `eviction-pressure-transition-period` 는 기본 5분입니다.[^k8s-eviction]



## 5. kubelet 은 파드부터 죽이지 않습니다

> 공식 문서의 표현대로 kubelet 은 최종 사용자 파드를 종료하기 전에 노드 레벨 자원부터 회수합니다.

이 절이 이 문서에서 가장 자주 오해받는 대목입니다. `DiskPressure` 가 켜졌다고 곧바로 파드가 죽는 것이 아닙니다. kubelet 은 먼저 자기가 지울 수 있는 것을 지웁니다.[^k8s-eviction]

회수 순서는 파일시스템 배치에 따라 갈립니다.

- **`imagefs` 도 `containerfs` 도 없을 때**: 죽은 파드와 컨테이너를 수거하고, 그다음 안 쓰는 이미지를 지웁니다.
- **`imagefs` 가 따로 있을 때**: `nodefs` 가 임계에 걸리면 죽은 파드와 컨테이너를 수거하고, `imagefs` 가 걸리면 안 쓰는 이미지를 전부 지웁니다.
- **`imagefs` 와 `containerfs` 가 갈려 있을 때**: `containerfs` 가 걸리면 죽은 파드와 컨테이너를 수거하고, `imagefs` 가 걸리면 안 쓰는 이미지를 지웁니다.

세 갈래가 다르게 보이지만 규칙은 하나입니다. **찬 디스크에 실제로 얹혀 있는 것을 지웁니다.** 이미지가 다른 디스크에 있는데 루트가 찼다면 이미지를 지워 봐야 소용이 없기 때문입니다. §3 의 배치 표를 알아야 이 순서가 이해되는 이유가 여기 있습니다.

### 그래도 모자라면 파드를 고릅니다

노드 레벨 회수로 신호가 임계 아래로 내려가지 않으면 그때 파드를 축출합니다. 고르는 기준은 셋이고 순서가 있습니다.[^k8s-eviction]

1. 파드의 자원 사용량이 requests 를 넘었는가
2. 파드 Priority
3. requests 대비 사용량이 얼마나 넘었는가

그 결과 순위는 이렇게 정해집니다. 먼저 `BestEffort` 또는 `Burstable` 이면서 사용량이 requests 를 넘은 파드가 나가고, 그 안에서는 Priority 와 초과 폭이 순서를 정합니다. `Guaranteed` 파드와 requests 미만을 쓰는 `Burstable` 파드가 마지막입니다.

여기서 공식 문서가 직접 못 박는 문장이 있습니다. kubelet 은 축출 순서를 정할 때 파드의 QoS 클래스를 *쓰지 않습니다*.[^k8s-eviction] QoS 는 메모리 같은 자원을 회수할 때 순서를 어림하는 데 도움이 될 뿐입니다. 특히 QoS 분류는 `ephemeral-storage` requests 에는 적용되지 않으므로, 노드가 `DiskPressure` 인 상황에서는 QoS 로 순서를 짐작하면 틀립니다.

inode 나 PID 가 마른 경우에는 기준이 더 단순해집니다. inode 와 PID 에는 requests 라는 개념이 없으므로 kubelet 은 상대 Priority 만 보고 순서를 정합니다.[^k8s-eviction]

정렬 기준도 배치에 따라 달라집니다.[^k8s-eviction] §3 의 세 배치가 여기서 다시 갈립니다.

- **단일 rootfs**: `nodefs` 가 부르면 총 디스크 사용량으로 정렬합니다. 로컬 볼륨과 로그와 모든 컨테이너의 쓰기 레이어를 합한 값입니다.
- **split disk**: `nodefs` 가 부르면 로컬 볼륨과 로그로, `imagefs` 가 부르면 모든 컨테이너의 쓰기 레이어 사용량으로 정렬합니다.
- **split image**: `containerfs` 가 부르면 로컬 볼륨과 로그와 쓰기 레이어를 합해 정렬하고, `imagefs` 가 부르면 이미지의 디스크 사용량을 나타내는 순위로 정렬합니다.

### 축출이 반복되면 최소 회수량을 봅니다

파드 하나를 죽여도 회수량이 적으면 kubelet 이 임계를 다시 건드려 축출을 반복합니다. `evictionMinimumReclaim` 은 임계 아래로 내려간 뒤에도 지정한 양만큼 더 회수하게 만들어 이 반복을 끊습니다. 모든 자원의 기본값은 0 입니다.[^k8s-eviction]



## 6. 가비지 컬렉션이 실제로 지우는 것

> kubelet 은 안 쓰는 이미지를 5분마다, 안 쓰는 컨테이너를 1분마다 수거합니다. 압박이 없어도 상시 돕니다.

§5 의 회수 단계에서 kubelet 이 부르는 것이 이 가비지 컬렉션입니다. 다만 압박이 있을 때만 도는 것은 아닙니다. 공식 문서는 kubelet 이 안 쓰는 이미지를 5분마다, 안 쓰는 컨테이너를 1분마다 수거한다고 적습니다.[^k8s-gc]

같은 문서가 경고를 하나 답니다. 외부 가비지 컬렉션 도구를 쓰지 말라는 것입니다. kubelet 의 동작을 깨고 남아 있어야 할 컨테이너를 지울 수 있기 때문입니다.[^k8s-gc] 디스크가 찬다고 노드에서 `docker system prune` 류를 크론으로 도는 것이 위험한 이유가 여기 있습니다.

### 이미지 가비지 컬렉션

이미지 수거는 두 개의 디스크 사용률 임계로 움직입니다. 사용률이 `imageGCHighThresholdPercent` 를 넘으면 수거가 시작되고, `imageGCLowThresholdPercent` 에 닿을 때까지 지웁니다. 지우는 순서는 마지막으로 쓴 시각 기준으로 오래된 것부터입니다.[^k8s-gc]

필드의 정확한 이름과 기본값은 kubelet 설정 레퍼런스에 있고, 각각 85 와 80 입니다.[^k8s-kubelet-config] 가비지 컬렉션 페이지 쪽은 같은 값을 `HighThresholdPercent` 와 `LowThresholdPercent` 로 부릅니다.[^k8s-gc] 사용률이 85% 를 넘으면 80% 가 될 때까지 오래된 이미지를 지운다는 뜻입니다.

나이를 기준으로 지우는 축도 있습니다.

- `imageMinimumGCAge`: 이미지가 이만큼은 안 쓰인 뒤에야 수거 대상이 됩니다. 기본값 `2m` 입니다.[^k8s-kubelet-config]
- `imageMaximumGCAge`: 디스크 사용률과 무관하게 이만큼 안 쓰이면 지웁니다. 기본값은 `0s` 이고, 이 값은 기능이 꺼져 있다는 뜻입니다.[^k8s-kubelet-config]

`imageMaximumGCAge` 에는 한 가지 성질이 있습니다. kubelet 재시작을 가로질러 이미지 사용을 추적하지 않습니다. kubelet 이 재시작하면 추적하던 나이가 초기화되어, 다시 전체 기간을 기다려야 나이 기준 수거 대상이 됩니다.[^k8s-gc] kubelet 이 자주 재시작하는 노드에서는 이 설정이 사실상 동작하지 않습니다.

### 컨테이너 가비지 컬렉션

컨테이너 쪽은 세 변수로 움직입니다.[^k8s-gc]

- `MinAge`: kubelet 이 컨테이너를 수거할 수 있는 최소 나이입니다. 0 으로 두면 비활성화됩니다.
- `MaxPerPodContainer`: 파드마다 남길 수 있는 죽은 컨테이너 수입니다. 음수로 두면 비활성화됩니다.
- `MaxContainers`: 클러스터가 가질 수 있는 죽은 컨테이너 총수입니다. 음수로 두면 비활성화됩니다.

이 값들을 크게 잡아 두면 죽은 컨테이너의 쓰기 레이어와 로그가 디스크에 오래 남습니다. `CrashLoopBackOff` 로 재시작을 반복하는 파드가 있으면 그 잔해가 쌓여 `DiskPressure` 를 부르기도 합니다.



## 7. 파드가 미리 자기 몫을 선언하는 법

> 축출은 사후 대응입니다. 파드가 `ephemeral-storage` 를 선언해 두면 사전에 경계가 생깁니다.

노드의 로컬 임시 스토리지는 내구성을 보장하지 않는 저장 공간입니다. 노드에 장애가 나면 그 데이터는 사라질 수 있습니다.[^k8s-ephemeral] 파드는 이 공간을 스크래치와 캐시와 로그에 씁니다.

kubelet 은 로컬 임시 스토리지 용량 격리를 켜 둔 경우에 한해 사용량을 잽니다.[^k8s-ephemeral-mgmt] 그때 파드 몫으로 세는 것은 넷입니다.

- 컨테이너 쓰기 레이어와 이미지에 쓴 양
- 로컬 `emptyDir` 볼륨에 쓴 양
- 파드 자신의 로그. 보통 `/var/log/pods` 아래에 있습니다
- 쿠버네티스가 파드에 매핑하는 시스템 파일. `/etc/hosts` 같은 것입니다

컨테이너마다 `spec.containers[].resources.requests.ephemeral-storage` 와 `.limits.ephemeral-storage` 를 둘 수 있습니다.[^k8s-ephemeral] 단위는 바이트이며 `E`, `P`, `T`, `G`, `M`, `k` 와 2의 거듭제곱 접미사 `Ei` 부터 `Ki` 까지를 씁니다.

접미사를 틀리면 조용히 어긋납니다. 공식 문서가 드는 예가 `400m` 입니다. 이렇게 적으면 400 메비바이트가 아니라 0.4 바이트를 요청한 것이 됩니다.[^k8s-ephemeral]

공식 문서의 예제는 컨테이너가 둘입니다.

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  containers:
  - name: app
    image: images.my-company.example/app:v4
    resources:
      requests:
        ephemeral-storage: "2Gi"
      limits:
        ephemeral-storage: "4Gi"
    volumeMounts:
    - name: ephemeral
      mountPath: "/tmp"
  - name: log-aggregator
    image: images.my-company.example/log-aggregator:v6
    resources:
      requests:
        ephemeral-storage: "2Gi"
      limits:
        ephemeral-storage: "4Gi"
    volumeMounts:
    - name: ephemeral
      mountPath: "/tmp"
  volumes:
    - name: ephemeral
      emptyDir:
        sizeLimit: 500Mi
```

값이 파드 단위로 합산된다는 점이 중요합니다. 컨테이너마다 request 2GiB 와 limit 4GiB 이므로 파드의 request 는 4GiB 이고 limit 은 8GiB 입니다.[^k8s-ephemeral] `emptyDir` 의 `sizeLimit` 500Mi 는 그 **파드 limit 8GiB 가운데** 이 볼륨이 쓸 수 있는 몫입니다.

주의할 예외가 하나 있습니다. `tmpfs` 로 만든 `emptyDir` 은 kubelet 이 임시 스토리지가 아니라 컨테이너 메모리 사용으로 셉니다.[^k8s-ephemeral] 메모리 기반 `emptyDir` 을 디스크 절약책으로 쓰면 대신 메모리 압박이 옵니다.



## 8. 노드가 애초에 떼어 두는 몫

> 축출 임계는 파드에게 팔지 않고 남겨 두는 자리이기도 합니다. `Allocatable` 이 그 계산의 결과입니다.

공식 문서는 `Allocatable` 을 "파드가 쓸 수 있는 컴퓨트 자원의 양"으로 정의하고, 스케줄러가 이 값을 초과 판매하지 않는다고 적습니다. 지원 자원은 `cpu` 와 `memory` 와 `ephemeral-storage` 입니다.[^k8s-reserve]

공식 도해는 노드 용량을 네 조각으로 나눠 보여 줍니다. `kube-reserved`, `system-reserved`, `eviction-threshold`, 그리고 파드가 쓸 수 있는 `allocatable` 입니다.[^k8s-reserve] 축출 임계로 남긴 자리는 파드에게 가지 않습니다.

- `kubeReserved`: kubelet 과 컨테이너 런타임처럼 쿠버네티스 시스템 데몬 몫입니다.
- `systemReserved`: `sshd` 나 커널처럼 OS 데몬 몫입니다. 커널 메모리는 파드 계정에 잡히지 않으므로 여기서 잡아 줘야 합니다.
- `evictionHard`: 축출을 부르기 위해 남기는 여유입니다.

`enforceNodeAllocatable` 은 kubelet 이 무엇에 이 경계를 강제할지 정합니다. 기본값은 `[pods]` 이고, `[pods,system-reserved,kube-reserved]` 처럼 넓힐 수 있습니다.[^k8s-reserve] 다만 `kube-reserved` 를 강제하려면 `kubeReservedCgroup` 을, `system-reserved` 를 강제하려면 `systemReservedCgroup` 을 함께 지정해야 합니다.

### 예약과 임계를 함께 계산하는 예

공식 문서가 드는 예를 그대로 따라가 보겠습니다. 조건은 셋입니다.

- 노드 메모리는 10GiB 입니다.
- 시스템 데몬 몫으로 총량의 10% 를 남기려 합니다.
- 사용률 95% 에서 파드를 축출해 시스템 OOM 을 줄이려 합니다.

이때 kubelet 은 이렇게 뜹니다.[^k8s-eviction]

```bash
--eviction-hard=memory.available<500Mi
--system-reserved=memory=1.5Gi
```

`system-reserved` 의 1.5GiB 는 총 메모리의 10% 에 축출 임계량을 더한 값입니다. 파드가 자기 request 보다 많이 쓰거나 시스템이 1GiB 를 넘겨 쓰면 `memory.available` 이 500MiB 아래로 떨어지며 임계가 걸립니다.

두 값을 따로 정하면 안 되는 이유가 여기 드러납니다. 축출 임계로 남길 몫까지 예약에 포함해야, 스케줄러가 배치한 파드가 뜨자마자 축출을 부르는 상황을 피할 수 있습니다.

`Capacity` 와 `Allocatable` 을 `kubectl describe node` 에서 읽는 법과 requests·limits·QoS 의 관계는 [자원 관리](../../kubernetes/02_configuration/02-02.%EC%9E%90%EC%9B%90%20%EA%B4%80%EB%A6%AC.md)가 다룹니다. 이 절은 그 값이 *어떻게 정해지는가* 쪽입니다.



## 9. 점검 질문

> 현장에서 실제로 갈리는 지점을 질문으로 정리합니다.

### Q1. `DiskPressure=True` 를 봤습니다. 무엇부터 확인합니까

용량이라고 단정하지 않는 것이 첫걸음입니다. `DiskPressure` 는 여섯 신호 중 아무거나 걸려도 켜집니다. 용량 셋과 inode 셋이 섞여 있습니다.

확인 순서는 이렇습니다. 먼저 노드의 파일시스템 배치가 셋 중 무엇인지 봅니다. 그다음 걸린 것이 용량인지 inode 인지 봅니다. 마지막으로 그것이 `nodefs` 인지 `imagefs` 인지 봅니다. 셋을 알아야 kubelet 이 무엇을 지우려 할지 예측할 수 있습니다.

### Q2. PDB 를 걸어 두면 노드 압박에도 최소 파드 수가 지켜집니까

지켜지지 않습니다. kubelet 은 node-pressure 축출에서 `PodDisruptionBudget` 을 준수하지 않습니다. `terminationGracePeriodSeconds` 도 마찬가지입니다. hard 임계로 걸리면 유예 없이 즉시 종료합니다.

PDB 가 지켜지는 것은 `drain` 같은 API 기반 축출입니다. 노드 압박에서 파드를 지키고 싶다면 PDB 가 아니라 Priority 와 requests 를 손봐야 합니다. 축출 순위의 첫 기준이 "requests 를 넘겼는가"이므로, requests 를 실제 사용량에 맞게 올려 두는 것이 가장 직접적인 보호입니다.

### Q3. `evictionHard` 에 메모리 임계 한 줄만 넣었습니다. 괜찮습니까

괜찮지 않습니다. 한 항목이라도 값을 바꾸면 나머지 항목이 기본값을 물려받지 않고 0 이 됩니다. 디스크 임계가 0 이 되면 `DiskPressure` 가 켜지지 않고, 디스크가 가득 차도 kubelet 이 회수를 시작하지 않습니다.

필요한 임계를 전부 명시하거나 `mergeDefaultEvictionSettings` 를 `true` 로 둡니다. 이 설정의 기본값은 `false` 이므로 명시하지 않으면 켜지지 않습니다.

### Q4. 디스크가 자주 찹니다. 노드에서 이미지 정리 크론을 돌려도 됩니까

공식 문서는 외부 가비지 컬렉션 도구를 피하라고 명시합니다. kubelet 의 동작을 깨고 남아 있어야 할 컨테이너를 지울 수 있기 때문입니다.

kubelet 쪽 설정으로 푸는 것이 맞습니다. `imageGCHighThresholdPercent` 를 85 보다 낮춰 더 일찍 수거를 시작하거나, `imageMaximumGCAge` 를 켜서 오래 안 쓴 이미지를 나이로 지웁니다. 다만 후자는 kubelet 재시작을 가로질러 추적하지 않으므로, 재시작이 잦은 노드에서는 기대한 대로 동작하지 않습니다.

### Q5. `Guaranteed` 파드는 축출되지 않습니까

전제를 먼저 봐야 합니다. 공식 문서가 말하는 `Guaranteed` 보장은 파드의 *모든* 컨테이너에 requests 와 limits 가 지정되고 그 둘이 같을 때만 성립합니다.[^k8s-eviction] 그 조건을 채운 파드는 "다른 파드의 자원 소비 때문에는" 축출되지 않습니다. 그러나 예외가 있습니다. kubelet 이나 journald 같은 시스템 데몬이 `system-reserved` 나 `kube-reserved` 로 예약한 양보다 많이 쓸 때입니다. 그 상태에서 노드에 requests 미만을 쓰는 `Guaranteed` 와 `Burstable` 파드만 남아 있으면, kubelet 은 노드 안정성을 위해 그중 하나를 골라야 합니다. 이때는 Priority 가 가장 낮은 파드가 나갑니다.

그리고 QoS 로 순서를 짐작하는 습관 자체를 조심해야 합니다. kubelet 은 축출 순서에 QoS 클래스를 쓰지 않고, QoS 분류는 `ephemeral-storage` requests 에 적용되지도 않습니다. `DiskPressure` 상황에서 QoS 기반 예측은 빗나갑니다.

> 임계와 회수를 알았으니 그 값을 무엇으로 관측하는지로 넘어갑니다.

이 문서는 kubelet 이 무엇을 보고 어떤 순서로 움직이는지를 다뤘습니다. 그런데 그 신호값을 사람이 보려면 별도의 경로가 필요합니다. `kubectl top` 이 읽는 값은 어디서 오고, 축출 신호와 같은 값인지 다른 값인지가 다음 질문입니다. [자원 모니터링 파이프라인](../cluster-administration/01-01.%EC%9E%90%EC%9B%90%20%EB%AA%A8%EB%8B%88%ED%84%B0%EB%A7%81%20%ED%8C%8C%EC%9D%B4%ED%94%84%EB%9D%BC%EC%9D%B8%20%E2%80%94%20kubelet%EC%9D%B4%20%EC%9E%AC%EB%8A%94%20%EA%B2%83%EA%B3%BC%20kubectl%20top%EC%9D%B4%20%EC%9D%BD%EB%8A%94%20%EA%B2%83.md)이 그 경로를 따라갑니다.

파일시스템 배치를 실제로 바꾸는 일은 스토리지 설계와 닿습니다. PV 와 PVC 로 다루는 영속 스토리지 쪽은 [스토리지와 상태](../../kubernetes/03_storage/03-01.%EC%8A%A4%ED%86%A0%EB%A6%AC%EC%A7%80%EC%99%80%20%EC%83%81%ED%83%9C.md)에 있습니다.
