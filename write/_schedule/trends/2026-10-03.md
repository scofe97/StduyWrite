### 1. Compact Object Headers 기본값 · G1 전면 기본 (JDK 27)

- 무엇인가: 64비트 HotSpot 의 객체 헤더를 12바이트에서 8바이트로 줄이는 Compact Object Headers 가 JDK 27 에서 기본값이 됐습니다(JEP 534). 같은 릴리즈에서 G1 이 작은 환경까지 포함해 모든 곳의 기본 GC 가 됐습니다(JEP 523). 이전에는 CPU·메모리가 작은 컨테이너에서 JVM 이 Serial 을 골랐습니다.
- 왜 지금인가: 9/28 inside.java 가 JDK 27 성능 정리 글을 냈습니다. 글이 인용한 수치는 SPECjbb2015 에서 힙 사용 22% 감소 · CPU 8% 감소, G1/Parallel 수집 횟수 15% 감소입니다. Object Monitor Table 기본화로 생긴 30% 회귀를 스핀 횟수 조정으로 줄였다는 내용도 있습니다. [inside.java 9/28](https://inside.java/2026/09/28/performance-update-jdk27/)
- 내 학습과의 연결: JVM 로드맵 1단계 `객체 레이아웃 · 헤더`, 4단계 `컬렉터 · GC 선택`. 기존 문서 `01_language/book/Inside the Java Virtual Machine JVM Advanced Features and Best Practices/ch02_automatic-memory-management/01-02.핫스팟의 객체 들여다보기.md` 가 이미 compact header 를 언급하므로 "기본값이 바뀐 뒤" 절을 덧붙이는 확장입니다. `01_language/book/jpf_java-performance/05-02.GC 알고리즘 선택 — serial·throughput·G1·CMS.md` 의 "작은 컨테이너는 Serial" 전제도 고쳐야 합니다. 로드맵 README 의 "컨테이너가 OOMKilled 로 죽는 이유" 진입 경로와도 닿습니다.
- 해볼 것: hub-lab 이 쓰는 Java 25 에서 `-XX:+UseCompactObjectHeaders` 를 켜고 끈 두 실행을 JOL 로 비교합니다(작은 객체 100만 개의 인스턴스 크기, `jcmd <pid> GC.class_histogram` 총량). 이어서 `-XX:ActiveProcessorCount=1 -Xmx512m` 로 띄워 `-Xlog:gc` 첫 줄에서 어떤 GC 가 골라지는지 확인해 두면, JDK 27 로 올렸을 때 달라지는 지점이 기록으로 남습니다. 1시간.

### 3. 오브젝트 스토리지 기반 로그 (Cloudflare K2)

- 무엇인가: 브로커가 로컬 디스크와 리더·팔로워 복제를 갖지 않고, 쓰기를 메모리에 모았다가 세그먼트 파일로 오브젝트 스토리지에 올리는 로그 설계입니다. 순서와 오프셋 증가는 별도 합의 서비스 없이 스토리지의 원자적 연산에 맡깁니다. 복제와 합의를 저장 계층으로 내려보내는 구조입니다.
- 왜 지금인가: 10/1 Cloudflare 가 Birthday Week 에서 K2(서버리스 이벤트 스트림)를 공개 베타로 냈습니다. R2 의 강한 일관성 API 위에 로그를 쌓고, 소비는 배치 임차(lease) · ack · nack 모델입니다. Kafka 클라이언트 호환은 로드맵 항목이고 아직 없습니다. [Cloudflare 10/1](https://blog.cloudflare.com/cloudflare-k2-streams/) 같은 날 나온 Workers KV Instant 는 반대 방향(모든 엣지에 밀어 넣는 복제, 네임스페이스당 초당 1회 쓰기 제한)이라 비교 대상이 됩니다. [Cloudflare 10/1](https://blog.cloudflare.com/workers-kv-instant/)
- 내 학습과의 연결: 데이터 로드맵 3단계 `세그먼트 로그`, 8단계 `Replicated Log · 합의`, 9단계 `오브젝트 스토어 · 로그 기반 브로커`. 기존 문서 `05_data/book/designing-data-intensive-applications/12-01.스트림 전송 — 메시지 브로커와 로그 기반 브로커.md` 와 `04_messaging/04_BrokerArchitecture/` 가 "브로커가 디스크와 복제를 소유한다"는 전제로 쓰여 있어, 그 전제를 뒤집는 한 편이 빠져 있습니다.
- 해볼 것: Go 로 미니 로그를 짭니다. 조건부 PUT(`If-None-Match`)을 지원하는 S3 호환 저장소(예: MinIO)에 `segment-<baseOffset>` 객체를 올리고, 같은 base offset 을 노리는 writer 둘을 경쟁시켜 한쪽만 성공하는지 봅니다. "누가 오프셋을 정하는가"를 합의 없이 풀 수 있는 조건과, 배치 지연이 곧 쓰기 지연이 되는 대가를 적습니다. 2시간.

### 4. Strict Field Initialization (JEP 539) 와 Value Objects (JEP 401)

- 무엇인가: 클래스 파일에 필드 단위 플래그 `ACC_STRICT_INIT` 를 추가해, "필드가 채워지기 전에는 누구도 그 객체를 볼 수 없다"를 컴파일러가 아니라 JVM 검증기가 강제하게 합니다. 소스 문법은 없고 컴파일러가 value class 필드에 자동으로 붙입니다. 정체성 없는 객체(JEP 401)가 기본값 상태로 관찰되지 않는다는 보장의 토대입니다.
- 왜 지금인가: 9/26 JEP 539 가 JDK 28 대상으로 확정됐습니다. 9/20 JEP 401 확정에 이은 것으로, Valhalla 첫 프리뷰의 두 조각이 같은 릴리즈에 모였습니다. [inside.java 9/26](https://inside.java/2026/09/26/jep539-target-jdk28/) · [JEP 539](https://openjdk.org/jeps/539) · [JEP 401 해설, InfoQ](https://www.infoq.com/news/2026/08/jep401-value-objects-preview/) 같은 주에 JEP 541(macOS/x64 포트 제거 예고, 9/29)과 JEP 540(Simple JSON API 인큐베이터, 10/2)도 JDK 28 대상이 됐습니다. [inside.java](https://inside.java/)
- 내 학습과의 연결: JVM 로드맵 2단계 `클래스 파일 구조 · 검증 · 초기화`, 1단계 `객체 레이아웃`(flattening 은 헤더가 없는 배치입니다). 저장소에는 Valhalla 가 `ch06_exotic-hardware` 에 지나가는 언급으로만 있고 독립 문서가 없습니다. JEP 401 은 `==` 의미를 바꾸고 `Integer` · `LocalDate` 같은 값 기반 클래스를 value class 로 만들어, 5단계 `동기화`(value 객체에는 `synchronized` 불가)에도 걸립니다.
- 해볼 것: Java 25 에서 "기본값 관찰" 버그를 재현합니다. 상위 생성자가 오버라이드 메서드를 불러 하위 `final` 필드를 0/null 로 읽게 만든 뒤, flexible constructor bodies 로 `super()` 앞에서 필드를 채워 고칩니다. 그 다음 JDK 28 EA 빌드에서 `--enable-preview` 로 `value class` 를 컴파일하고 `javap -v` 로 필드 플래그를 확인합니다. 1~2시간. GA 는 2027년 3월 프리뷰이므로 급하지 않습니다.

### 5. 강제 `tool_choice` 폐기 · strict tool use · cache diagnostics (Claude Sonnet 5.5)

- 무엇인가: Sonnet 5.5 는 `tool_choice` 의 `any` · `tool`(강제 호출)에 400 을 돌려주고, `auto` 와 strict tool use 조합을 쓰게 합니다. thinking 을 끄는 방식도 `disabled` 대신 `between_tools` 로 바뀌었고, thinking 블록은 만든 계정에 묶입니다. 별개로 캐시 적중 실패 이유를 응답에 실어 주는 cache diagnostics 가 정식이 됐습니다.
- 왜 지금인가: 9/28 Sonnet 5.5 출시 공지가 "Sonnet 5 용 코드가 깨지는 다섯 가지"를 명시했고, 9/30 에는 Sonnet 4.5 폐기(2026-11-30 종료)가 공지됐습니다. cache diagnostics 정식화는 9/23 입니다. [Claude 플랫폼 릴리즈 노트](https://platform.claude.com/docs/en/release-notes/overview)
- 내 학습과의 연결: AI 로드맵 3단계 `도구 호출 · 도구 스키마 · tool_choice`, 1단계 `구조화 출력 · 추론 노력 조절`, 2단계 `프롬프트 캐싱 · 접두 일치`. 기존 문서 `10_AI/02-02.Harness Engineering — 모델을 감싸는 오케스트레이션 층.md`, `10_AI/02-03.Token Optimization — 비용·지연·context rot를 줄이는 법.md`, `10_AI/02-06.Prompt Engineering — 지시·역할·형식·예시로 모델을 조종하기.md` 를 확장합니다. 02-06 의 111행은 "Claude 는 tool 을 강제(`tool_choice`)해 구조화 출력을 얻는다"고 적고 있고 02-02 는 `tool_choice` 네 값을 설명하므로, 최신 모델에서는 강제 값이 막힌다는 주석이 필요합니다.
- 해볼 것: 강제 `tool_choice` 로 JSON 을 뽑던 짧은 스크립트 하나를 `auto` + strict 스키마로 옮기고, 실패 형태(400, 도구 미호출)를 표로 적습니다. 같은 요청에 `diagnostics` 객체를 넣어 시스템 프롬프트 한 글자를 바꿨을 때 캐시 miss 사유가 어떻게 찍히는지 봅니다. `접두 일치`를 눈으로 확인하는 실습입니다. 1시간.

### 6. PostgreSQL 19 `WAIT FOR` — standby 의 read-your-writes

- 무엇인가: standby 가 지정한 지점까지 WAL 을 재생할 때까지 기다리게 하는 명령입니다. 쓰기 직후 복제본에서 읽어도 자기 쓰기가 보이도록 애플리케이션이 직접 조율할 수 있습니다. 같은 릴리즈의 `REPACK` 은 `VACUUM FULL` 과 `CLUSTER` 를 합치고 `CONCURRENTLY` 로 읽기·쓰기를 막지 않습니다.
- 왜 지금인가: 9/24 Beta 4 가 나왔고(창 이틀 앞) RC 는 10월 초, GA 는 10월로 예고됐습니다. 이번 베타에서 SQL/PGQ, `FOR PORTION OF`, 파티션 MERGE/SPLIT, 온라인 체크섬 전환이 안정성 때문에 되돌려졌습니다. "무엇이 빠졌는가"가 이번 주 소식입니다. [Beta 4 공지](https://www.postgresql.org/about/news/postgresql-19-beta-4-released-3386/) · [19 릴리즈 노트](https://www.postgresql.org/docs/19/release-19.html)
- 내 학습과의 연결: 데이터 로드맵 5단계 `복제 지연 · 읽기 후 쓰기`. 기존 문서 `05_data/book/designing-data-intensive-applications/06-03.복제 지연 문제와 일관성 보장.md`, `05_data/01_foundation/02-03.복제.md` 는 원리까지만 다룹니다. 주 스택인 MariaDB 의 `MASTER_GTID_WAIT()` 와 같은 자리의 기능이어서, hub-lab Phase 3(다중 데이터소스)에서 읽기·쓰기 라우팅을 다룰 때 비교 축이 됩니다.
- 해볼 것: Docker 로 PG 19 beta4 primary + standby 를 띄우고 standby 에 `recovery_min_apply_delay` 로 지연을 넣습니다. 쓰기 직후 standby 조회가 옛 값을 주는 것을 본 뒤, 쓰기 시점 LSN 으로 `WAIT FOR` 를 걸어 고칩니다(문법은 19 문서 확인). 같은 실험을 MariaDB GTID 로 한 번 더 해 차이를 적습니다. 2시간.

### 7. Go 1.27 `simd` 실험 패키지

- 무엇인가: amd64(AVX 계열) · arm64(NEON) · Wasm 에서 같은 코드로 도는 플랫폼·벡터 폭 독립 SIMD API 입니다. `GOEXPERIMENT=simd` 로 켜는 실험 기능이고, `simd.LoadFloat32s` · `MulAdd` · `Store` 같은 연산을 줍니다. 모든 플랫폼이 효율적으로 낼 수 있는 연산의 교집합만 들어 있습니다.
- 왜 지금인가: 9/24 Go 블로그가 해설 글을 냈습니다(창 이틀 앞). 1.27 에는 벡터 전체 합(`ReduceSum`)이 없고 다음 릴리즈 예정이라는 한계도 적혀 있습니다. [go.dev 9/24](https://go.dev/blog/simd-experiment) 같은 달 글인 size-specialized allocation(9/16), goroutine leak profile(9/2)은 5단계에 더 직접 닿습니다. [go.dev/blog](https://go.dev/blog/)
- 내 학습과의 연결: Go 로드맵 5단계 `benchmark · escape analysis · 할당 줄이기`, 6단계 `프로토콜 설계 — 체크섬`. 저장소에 SIMD 문서는 없습니다. gonet-lab 미션(계층에 맞는 도구 고르기)과는 거리가 있어 우선순위를 낮췄습니다.
- 해볼 것: gonet-lab 에서 쓰는 바이트 버퍼로 Internet checksum(RFC 1071) 스칼라 버전과 `simd` 버전을 짜 `go test -bench` 로 비교합니다. `ReduceSum` 이 없어 마지막 합산을 어떻게 우회하는지가 관찰 지점입니다. 1시간. goroutine leak profile 을 gonet-lab Phase 1 의 "조용한 연결" 실험에 붙여 보는 쪽이 지금 랩에는 더 쓸모 있습니다.
