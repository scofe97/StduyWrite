# 서브네팅과 CIDR — 주소 공간을 자르는 법
---
> CIDR 표기를 읽는 것과 주소 공간을 직접 나누는 것은 다른 기술입니다. 앞쪽만 익힌 채 넘어가면 VPC와 클러스터의 대역이 겹쳐 터지는 사고를 설계 단계에서 못 막습니다. prefix 길이 하나가 무엇을 정하는지에서 출발해, 그 감각이 라우팅 결정과 Kubernetes CIDR 충돌로 이어지는 데까지 갑니다.

## 1. 클래스가 사라진 이유

> 고정된 A·B·C 경계는 필요한 크기와 맞지 않아 주소를 낭비했습니다. 그 경계를 없애고 임의 길이의 prefix로 바꾼 것이 CIDR입니다.

옛 주소 체계는 앞쪽 비트로 클래스를 판정하고, 클래스가 네트워크 부분의 길이를 정했습니다. 경계는 8비트, 16비트, 24비트 세 곳에 고정돼 있었습니다. 호스트 300대가 필요한 조직은 254개짜리 블록으로는 모자라서 65534개짜리 블록을 받아야 했습니다.

CIDR은 이 판정을 없앴습니다. 명세는 RFC 4632이며 BCP 122로 지정된 2006년 문서입니다.[^rfc4632] 주소 뒤에 슬래시와 0에서 32 사이의 값을 붙여, 앞에서부터 몇 비트가 네트워크를 가리키는지 직접 적습니다.

- `172.16.0.0/16`: 앞 16비트가 네트워크, 뒤 16비트가 호스트
- `192.168.99.0/24`: 앞 24비트가 네트워크, 뒤 8비트가 호스트

경계가 임의의 비트 위치로 풀리면서, 2의 거듭제곱 크기라면 어떤 블록이든 표현할 수 있게 됐습니다. 서브네팅은 이 자유를 실제로 쓰는 일입니다.



## 2. prefix 길이 하나가 정하는 것

> 호스트 비트가 하나 줄면 블록 크기는 절반이 됩니다. 이 대응 관계 하나가 서브네팅 감각의 대부분입니다.

prefix가 `/n`이면 호스트 비트는 `32 - n`개이고 블록에는 `2^(32-n)`개의 주소가 들어갑니다. 통상 그중 둘은 호스트에 배정하지 않습니다. 호스트 비트가 전부 0인 주소는 네트워크 자체를 가리키고, 전부 1인 주소는 그 네트워크의 브로드캐스트에 쓰입니다.

| prefix | 주소 수 | 배정 가능 호스트 | 흔한 쓰임 |
|---|---|---|---|
| /16 | 65,536 | 65,534 | VPC 전체, 큰 Pod CIDR |
| /20 | 4,096 | 4,094 | 노드 서브넷 |
| /24 | 256 | 254 | 일반 서브넷, 노드당 Pod 할당 |
| /26 | 64 | 62 | 소규모 서브넷 |
| /28 | 16 | 14 | 관리 대역 |
| /31 | 2 | 2 | 점대점 링크 |
| /32 | 1 | 1 | 단일 호스트 경로 |

마지막 두 줄이 예외입니다. `/31`은 점대점 링크에 한해 두 주소를 모두 호스트로 씁니다. RFC 3021이 정한 규칙이며, 링크 하나에 주소 넷을 쓰던 것을 둘로 줄입니다.[^rfc3021] `/32`는 호스트 하나를 가리키는 경로 표현으로 쓰이며 세그먼트를 만들지 않습니다.

숫자를 외울 필요는 없습니다. `/24`가 256개라는 것 하나만 붙들고, 비트가 줄면 두 배 늘면 절반이라는 방향만 잡으면 나머지는 따라옵니다.



## 3. 손으로 한 번 계산해 보기

> 마스크와 주소를 비트 단위로 AND 하면 네트워크 주소가 나옵니다. 개념이 선 뒤에는 도구로 확인하는 편이 빠릅니다.

`192.168.10.130/26`이 어느 네트워크에 속하는지 봅니다. `/26`이므로 마스크는 앞 26비트가 1이고, 넷째 옥텟은 `11000000`, 곧 192입니다. 주소의 넷째 옥텟 130은 `10000010`입니다. 둘을 AND 하면 `10000000`, 곧 128이 나옵니다.

따라서 네트워크는 `192.168.10.128/26`이고 범위는 128부터 191까지입니다. 배정 가능한 호스트는 129부터 190까지 62개입니다.

같은 계산을 표준 라이브러리로 확인합니다.

```bash
python3 -c "
import ipaddress
net = ipaddress.ip_network('192.168.10.130/26', strict=False)
print(net, net.netmask, net.num_addresses, net[1], net[-2])
"
```

`strict=False`는 호스트 비트가 섞인 주소를 넣어도 소속 네트워크를 돌려주게 합니다. 겹침 여부도 같은 모듈로 판정할 수 있습니다.

```bash
python3 -c "
import ipaddress
a = ipaddress.ip_network('10.0.0.0/16')
b = ipaddress.ip_network('10.0.128.0/17')
print(a.overlaps(b), list(a.subnets(new_prefix=18)))
"
```

계산기를 쓰는 것과 개념을 건너뛰는 것은 다릅니다. prefix를 바꿔 가며 호스트 수가 어떻게 변하는지 눈으로 확인하는 단계를 거치면, 밑에 깔린 비트 연산이 임의의 규칙이 아니라 당연한 결과로 읽힙니다.



## 4. VLSM — 한 블록을 서로 다른 크기로 쪼갠다

> 필요한 크기가 제각각인데 같은 길이로만 자르면 남는 자리가 생깁니다. 큰 것부터 배치하면 조각이 덜 납니다.

한 블록을 균등하게 나누는 방식은 단순하지만 낭비가 큽니다. 호스트 100대가 필요한 세그먼트와 2대가 필요한 링크에 같은 `/24`를 주면 뒤쪽에서 252개가 놀게 됩니다. 가변 길이 서브넷 마스크는 세그먼트마다 필요한 크기에 맞춰 다른 prefix를 씁니다.

`192.168.1.0/24` 하나를 세 용도로 나눠 봅니다.

1. 호스트 100대가 필요한 서버 세그먼트에 `/25`를 줍니다. `192.168.1.0/25`이고 126대를 담습니다.
2. 호스트 50대가 필요한 사무 세그먼트에 `/26`을 줍니다. `192.168.1.128/26`이고 62대를 담습니다.
3. 점대점 링크에 `/30`을 줍니다. `192.168.1.192/30`부터 시작해 링크마다 하나씩 늘려 갑니다.

순서가 중요합니다. 큰 블록부터 배치해야 정렬 경계가 맞습니다. 작은 것을 먼저 흩어 놓으면 뒤에 큰 블록이 들어갈 연속 공간이 남지 않습니다.

주소 계획에는 여유를 둡니다. 나중에 늘릴 가능성이 있는 세그먼트 뒤에는 빈 공간을 남겨야, 확장할 때 블록을 옮기지 않고 prefix만 넓힐 수 있습니다.



## 5. 사설 대역과 겹침의 배경

> RFC 1918이 준 세 블록을 모두가 쓰기 때문에, 서로 다른 조직과 클러스터가 같은 주소를 들고 만나는 일이 흔합니다.

사설 주소는 RFC 1918이 정한 세 블록입니다. BCP 5로 지정된 1996년 문서입니다.[^rfc1918]

- `10.0.0.0/8`: 주소 약 1670만 개
- `172.16.0.0/12`: `172.16`부터 `172.31`까지
- `192.168.0.0/16`: `192.168.0`부터 `192.168.255`까지

이 대역은 IANA나 레지스트리와 조율 없이 누구나 쓸 수 있습니다. 편의가 곧 문제의 원인이기도 합니다. 아무 계획 없이 시작하면 대부분 `10.0.0.0/16`이나 `192.168.0.0/24` 같은 익숙한 값을 고르고, 나중에 두 네트워크를 잇는 순간 양쪽이 같은 대역을 쓰고 있다는 사실이 드러납니다.

VPC 피어링, 사이트 간 VPN, 회사 네트워크와 클러스터의 연결이 전부 이 순간에 걸립니다. 겹치면 라우팅 테이블이 목적지를 구분할 수 없어 연결 자체가 성립하지 않습니다.



## 6. Kubernetes에서 겹침이 터지는 세 축

> 클러스터에는 서로 겹치면 안 되는 대역이 최소 셋 있고, 그중 일부는 클러스터를 띄운 뒤에는 바꿀 수 없습니다.

- 노드 서브넷: 노드의 NIC가 받는 주소이며 VPC 서브넷에서 나옵니다
- Pod CIDR: 파드에 배정되는 대역이고, CNI가 노드마다 조각을 떼어 씁니다
- Service CIDR: ClusterIP에 배정되는 가상 대역이며 실제 인터페이스에 붙지 않습니다

셋은 서로 겹치면 안 되고, 클러스터 밖에서 통신할 상대의 대역과도 겹치면 안 됩니다. Service CIDR는 실재하지 않는 주소라 겹쳐도 당장은 조용하다가, 그 대역과 같은 주소를 쓰는 외부 시스템을 호출할 때 그쪽으로 안 가고 kube-proxy 규칙에 먹히는 형태로 드러납니다.

용량 계산도 여기서 어긋납니다. 노드마다 `/24`를 떼어 주는 구성이라면 Pod CIDR가 `/16`일 때 노드는 256대가 상한입니다. 파드 수가 아니라 노드 수가 먼저 막히는 구조라, 스케일 계획을 세울 때 노드당 할당 prefix와 전체 Pod CIDR를 함께 봐야 합니다.

바꾸기 어려운 값이라는 점이 이 절의 요점입니다. Pod CIDR와 Service CIDR는 클러스터 생성 시점에 정해지고 이후 변경은 사실상 재구축입니다. 설계 단계에서 종이에 한 번 그려 보는 비용이 나중에 클러스터를 다시 세우는 비용보다 훨씬 쌉니다.

클러스터 안에서 이 대역들이 실제로 어떻게 배선되는지는 [K8s 패킷 여정](./01-02.K8s%20%ED%8C%A8%ED%82%B7%20%EC%97%AC%EC%A0%95%20%E2%80%94%20netfilter%C2%B7conntrack%C2%B7%EB%9D%BC%EC%9A%B0%ED%8C%85.md)과 [IP·라우팅·Ethernet](../../08_cloud/book/networking-and-kubernetes/01-03.IP%C2%B7%EB%9D%BC%EC%9A%B0%ED%8C%85%C2%B7Ethernet%20%E2%80%94%20%ED%8C%A8%ED%82%B7%EC%9D%B4%20%EA%B8%B8%EC%9D%84%20%EC%B0%BE%EB%8A%94%20%EB%B2%95.md)이 다룹니다.



## 7. 라우팅은 가장 긴 prefix를 고른다

> 한 목적지에 여러 경로가 맞아떨어질 때 커널은 더 구체적인 쪽, 곧 prefix가 긴 쪽을 씁니다.

라우팅 테이블에는 겹치는 항목이 함께 있을 수 있습니다. `10.0.0.0/8`과 `10.0.5.0/24`가 동시에 있고 목적지가 `10.0.5.7`이면 둘 다 맞습니다. 이때 커널은 더 긴 `/24` 쪽을 택합니다.

이 규칙이 기본 경로의 정체도 설명합니다. `0.0.0.0/0`은 prefix 길이가 0이라 모든 주소에 맞지만 가장 짧으므로 언제나 마지막 후보입니다. 다른 경로가 하나도 맞지 않을 때만 쓰이는 이유가 여기 있습니다.

어느 경로가 실제로 선택되는지는 커널에 직접 물어보는 편이 확실합니다.

```bash
ip route
ip route get 10.0.5.7
```

`ip route get`은 커널이 지금 이 목적지로 쓸 경로와 출발지 주소를 그대로 돌려줍니다. 겹치는 대역을 의심할 때 테이블을 눈으로 훑는 것보다 빠릅니다.



## 8. 다루지 않은 것

> 범위를 좁힌 자리를 밝혀 둡니다.

IPv6 주소 계획은 넣지 않았습니다. prefix 개념은 같지만 크기 감각과 관례가 달라 별도로 다뤄야 합니다.

정책 라우팅과 다중 라우팅 테이블은 7절에서 롱기스트 프리픽스 매치만 짚고 넘어갔습니다. `ip rule`이 테이블 자체를 고르는 층은 [로드맵](./roadmap.md) 8절이 예고한 범위입니다.

NAT로 겹침을 우회하는 방법도 범위 밖입니다. 겹친 대역을 잇는 실무 수단이지만 주소 계획의 실패를 덮는 쪽이라, 계획을 다루는 이 문서와 축이 다릅니다.
