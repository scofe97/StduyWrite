# 리눅스 네트워킹 기초

---
> Kubernetes 네트워킹 문서들이 "Pod에 IP가 붙고 노드 사이로 패킷이 간다"는 추상을 다룬다면, 이 문서는 그 한 칸 아래 — 커널이 어떤 자료구조와 hook으로 그 추상을 만드는지 — 를 정리합니다. 컨테이너에 한정되지 않는 Linux 자체 메커니즘이며, 추상 어디가 깨졌을 때 어디를 봐야 하는지의 지도가 됩니다.



## 학습 목표
> Linux 커널이 제공하는 네트워크 자료구조와 hook을 알아 두면, K8s/CNI 추상이 깨졌을 때 어디로 내려가야 하는지 분명해집니다.

이 문서에서 확인할 목표는 다음과 같다:

1. 네트워크 네임스페이스가 커널에서 어떤 단위로 격리되는지 설명할 수 있다.
2. veth pair의 전송 의미와 Linux bridge의 학습·전달 동작을 그릴 수 있다.
3. 라우팅 테이블이 main·local 같은 여러 테이블로 나뉜 구조와 policy routing(`ip rule`)을 활용할 수 있다. ARP neighbor의 NUD 상태로 통신 장애를 진단할 수 있다.
4. netfilter hook 5개와 iptables/nftables가 그 위에 어떻게 얹히는지 설명할 수 있다.
5. conntrack 테이블이 만드는 상태 추적의 부수효과(SNAT 응답 매핑, NAT 일관성, 테이블 포화)를 진단할 수 있다.
6. TC qdisc와 eBPF 어태치 포인트(XDP, TC, kprobe)가 패킷 경로의 어디에 끼어드는지 매핑할 수 있다.



## 1. 네트워크 네임스페이스
> **네트워크 네임스페이스**는 인터페이스, 라우팅 테이블, ARP 캐시, netfilter ruleset, 포트 점유 상태를 통째로 격리한 커널 자료구조입니다. 컨테이너의 모든 네트워크 격리는 이 단일 메커니즘 위에 얹힙니다.
>
> - "컴퓨터 안에 만든 작은 가상 네트워크 방"

일반적으로 한 리눅스 서버에는 기본 네트워크 공간이 하나 있습니다. 이 공간 안에 실제 NIC인 `eth0`, 루프백 `lo`, 라우팅 테이블, ARP 캐시, 방화벽 규칙, 사용 중인 포트 목록이 통째로 들어 있습니다.

그런데 컨테이너를 만들면, 리눅스는 컨테이너에게 별도의 네트워크 공간을 하나 줍니다. 아래 그림은 root와 두 Pod가 각자 격리된 공간을 갖고, 셋이 동시에 8080 포트를 점유하는 모습입니다.

![네트워크 네임스페이스 격리 — 소켓 해시가 따로라 포트가 겹친다](./_assets/01-01-netns-isolation.svg)

각 네임스페이스가 자기만의 포트 목록을 갖기 때문에, 셋 다 같은 8080을 중복해서 쓸 수 있습니다. 왜 이게 가능한지는 바로 아래에서 자료구조로 봅니다.

### 무엇이 격리되는가

> `struct net` = 네트워크 네임스페이스 하나를 표현하는 커널 객체

```bash
struct net
 ├─ 네트워크 인터페이스 목록
 ├─ 라우팅 테이블
 ├─ ARP/NDP 캐시
 ├─ 방화벽 규칙
 ├─ 소켓 목록
 └─ 포트 사용 상태
```

- `struct net_device` 리스트(인터페이스), `struct fib_table`(라우팅), `struct neigh_table`(ARP/NDP), netfilter ruleset, 소켓 hash가 모두 들어 있습니다. 같은 네임스페이스 안에서만 이 자료구조가 공유됩니다.
- 두 프로세스가 서로 다른 네임스페이스에 들어 있으면 각자의 `struct net`에 별도 소켓 hash가 있고, 점유 충돌이 일어나지 않습니다. 위 그림에서 셋이 8080을 겹쳐 쓸 수 있던 근거가 바로 이 소켓 hash 분리입니다.

### 만들기와 들어가기

```bash
ip netns add demo                         # /var/run/netns/demo 생성
ip netns list
ip netns exec demo ip addr                # 그 네임스페이스에서 명령 실행
nsenter --net=/var/run/netns/demo bash    # 셸로 진입
```

- `ip netns add`는 새 `struct net`을 만드는 쪽입니다. 내부적으로 자식에서 `unshare(CLONE_NEWNET)`으로 새 네임스페이스를 만든 뒤, `/proc/self/ns/net`을 `/var/run/netns/<이름>` 아래에 bind-mount해 살려 둡니다. `setns(2)`는 *만드는* 게 아니라 *이미 있는* 네임스페이스에 *들어가는* syscall이라, `ip netns exec`가 이걸 씁니다.
- `/var/run/netns/<이름>`은 그 네임스페이스를 잡아 두는 마운트 포인트일 뿐이고, 실제 격리 단위는 커널 안의 `struct net` 객체입니다.

컨테이너 런타임은 보통 `/var/run/netns/`에 등록하지 않고 자기 프로세스가 잡고 있는 fd만으로 네임스페이스를 유지합니다. K8s에서 Pause 컨테이너의 PID를 알면 `nsenter -t <PID> -n`으로 그 Pod의 네임스페이스에 들어갈 수 있습니다.

### 인터페이스 이동

인터페이스는 만들 때 root 네임스페이스에 속하지만, `ip link set <iface> netns <ns>`로 다른 네임스페이스로 이동할 수 있습니다. 이동하면 더 이상 원래 네임스페이스에서는 보이지 않습니다. CNI가 veth pair의 한쪽을 Pod 네임스페이스로 옮기는 동작이 이 syscall입니다.

## 2. veth pair와 Linux bridge
> veth pair는 쌍으로 만들어지는 가상 네트워크 인터페이스입니다.
>
> - bridge는 root 네임스페이스에 있는 가상 L2 스위치입니다. 둘이 결합해 컨테이너의 외부 통로를 만듭니다.

### veth의 전송 의미

Pod는 자기만의 네트워크 네임스페이스 안에 있고, 바깥과 통신하려면 노드의 네트워크 공간과 연결되어야 합니다. 그 연결선이 veth pair입니다. Pod 안에서는 `eth0`이 자기 네트워크 카드처럼 보이지만, 실제로는 veth pair의 한쪽 끝입니다.

```bash
# veth0 와 veth1 이라는 가상 네트워크 카드 2개를 만들고, 둘을 서로 연결된 한 쌍으로 묶어라.
ip link add veth0 type veth peer name veth1
```

핵심은 이 쌍 사이에 **케이블도 qdisc도 없다**는 점입니다. 한쪽으로 송신된 패킷이 즉시 반대쪽의 수신 처리로 들어갑니다. 커널 내부에서 보면 송신 함수 `veth_xmit`가 반대쪽 끝의 RX 경로(NAPI/GRO backlog)로 패킷을 곧장 넘깁니다.

![veth pair — 케이블이 아니라 커널이 곧장 넘긴다](./_assets/01-01-veth-xmit.svg)

이 모델 덕분에 veth는 빠릅니다. 다만 패킷이 두 번의 softirq를 타며 CPU 캐시 미스가 날 수 있습니다.

그래서 대량 트래픽 환경에서는 veth 대신 macvlan 또는 ipvlan을 쓰는 패턴이 검토됩니다. 둘의 차이는 MAC을 다루는 방식입니다. macvlan은 서브 인터페이스마다 별도 MAC을 주고, ipvlan은 부모 인터페이스의 MAC을 공유한 채 L3에서 나눕니다.

### bridge의 학습·전달

Linux bridge는 가상 L2 스위치입니다. 현실 네트워크가 여러 컴퓨터를 스위치에 꽂아 묶듯, 리눅스는 여러 veth를 하나의 bridge에 꽂아 여러 Pod를 같은 네트워크로 묶습니다.

![Linux bridge와 FDB — MAC을 학습하는 가상 L2 스위치](./_assets/01-01-bridge-fdb.svg)

Linux bridge는 `struct net_bridge`로 표현되며, 안에 forwarding database(FDB)를 갖습니다.

같은 bridge에 꽂힌 인터페이스에서 source MAC을 본 적이 있으면 그 MAC이 어느 포트에서 왔는지 FDB에 학습됩니다. 다음 패킷이 그 MAC으로 향할 때 곧장 해당 포트로 전달됩니다. 아직 학습되지 않은 MAC은 모든 포트로 flooding해 답을 찾습니다.

```bash
bridge link show
bridge fdb show br cni0
ip -d link show br cni0
```

bridge는 STP(Spanning Tree Protocol)도 지원하지만 컨테이너 환경에서는 보통 비활성화합니다. STP가 켜지면 listening·learning 두 단계를 거치느라, 노드를 다시 부팅했을 때 forwarding 시작 전 30초 정도 지연이 생깁니다.

### CNI가 만드는 토폴로지

CNI 플러그인이 Pod 하나를 만들 때 일반적으로 다음 순서를 밟습니다. netns를 만들고, veth 쌍의 한쪽을 그 netns 안 `eth0`으로 넣고, 다른 쪽을 `cni0` bridge에 꽂은 뒤 주소와 기본 경로를 잡습니다.

```bash
ip netns add pod-x
ip link add veth-host-x type veth peer name eth0 netns pod-x
ip link set veth-host-x master cni0
ip link set veth-host-x up
ip -n pod-x addr add 10.244.0.5/24 dev eth0
ip -n pod-x route add default via 10.244.0.1
```

bridge에 꽂힌 모든 veth는 같은 L2 도메인에 있으므로 ARP로 서로를 찾습니다. 그래서 같은 노드 Pod 사이 통신은 bridge 안에서 L2로 끝납니다.

### MTU와 단편화 — 오버레이가 부딪히는 벽

인터페이스마다 한 번에 실어 보낼 수 있는 최대 페이로드 크기가 정해져 있고, 이를 MTU(Maximum Transmission Unit)라 부릅니다. 표준 이더넷 MTU는 1500바이트입니다.

문제는 오버레이 네트워크입니다. VXLAN처럼 원본 패킷을 다시 포장하는 방식은 바깥 헤더가 붙는 만큼 실을 수 있는 페이로드가 줄어듭니다. IPv4 위 VXLAN의 포장 오버헤드는 50바이트입니다.

- 바깥 이더넷 헤더 14바이트
- 바깥 IP 헤더 20바이트
- UDP 헤더 8바이트
- VXLAN 헤더 8바이트

그래서 Pod MTU를 `1500 - 50 = 1450`으로 낮춰 잡는 것이 표준 대응입니다.

이 조정을 빠뜨리면 어떻게 될까요. 1500바이트로 꽉 채운 패킷이 포장 후 1550바이트가 되어 물리망 MTU를 넘습니다. 그 결과 단편화가 일어나거나, DF 비트가 켜져 있으면 패킷이 그냥 버려집니다.

"큰 응답만 멈추고 작은 요청은 되는" 미묘한 장애가 여기서 나옵니다. IPv6 언더레이라면 오버헤드가 70바이트라 더 낮춰야 합니다.



## 3. 라우팅 테이블과 policy routing
> **Linux는 라우팅 테이블이 하나가 아니라 여러 개입니다.** 
>
> - `ip rule`이 어느 테이블을 볼지 결정하고, 각 테이블이 next-hop을 결정합니다. 
> - 이 두 단계가 풀리지 않으면 Pod CIDR 라우팅 디버깅이 안 됩니다.

![policy routing — 두 단계다: 어느 테이블을 볼지, 그 안에서 어디로 보낼지](./_assets/01-01-policy-routing.svg)

### main, local, default

기본 테이블은 세 개입니다. `local`(255)은 자기 노드 IP에 대한 항목, `main`(254)이 일반 라우팅, `default`(253)는 비어 있는 폴백입니다. `ip route`만 치면 main 테이블만 보입니다.

```bash
ip route show table main
ip route show table local       # 자기 IP 항목
ip route show table all         # 모든 테이블
```

K8s 환경에서 main 테이블에는 다음과 같은 항목이 박힙니다.

```
default via 172.18.0.1 dev eth0
10.244.0.0/24 dev cni0 scope link    # 자기 노드 Pod CIDR
10.244.1.0/24 via 172.18.0.3 dev eth0 # 다른 노드 Pod CIDR
172.18.0.0/16 dev eth0 scope link
```

### policy routing — `ip rule`

여러 테이블을 분기시키려면 `ip rule`이 필요합니다. 트래픽 출발지·목적지·인터페이스·firewall mark에 따라 다른 테이블을 보게 만듭니다.

```bash
ip rule list
# 0:  from all lookup local
# 32766: from all lookup main
# 32767: from all lookup default
```

`fwmark`로 분기시키는 패턴이 흔합니다. iptables가 패킷에 mark를 박고, `ip rule`이 그 mark에 해당하는 테이블로 보냅니다. Cilium은 자체 routing을 위해 이 패턴을 쓰며, MetalLB BGP 모드도 같은 방식으로 outbound 경로를 잡습니다.

```bash
ip rule add fwmark 0x100 table 100
ip route add default via 192.168.50.1 table 100
iptables -t mangle -A OUTPUT -d 10.99.0.0/16 -j MARK --set-mark 0x100
```

### ARP와 neighbor 상태(NUD)

라우팅이 next-hop IP를 정하면, 그 IP의 MAC을 알아야 실제로 프레임을 보낼 수 있습니다. 이 IP→MAC 대응을 관리하는 커널 자료구조가 `struct neigh_table`입니다.

각 항목은 지금 얼마나 믿을 만한지를 나타내는 NUD(Neighbour Unreachability Detection) 상태를 갖습니다.

| 상태 | 의미 |
|------|------|
| `INCOMPLETE` | 해석 중 (ARP 요청 보내고 응답 대기) |
| `REACHABLE` | 최근에 확인됨, 믿을 수 있음 |
| `STALE` | 유효하지만 오래됨, 다음 사용 시 재확인 |
| `DELAY` | 재탐색 전 잠깐 대기 |
| `PROBE` | 능동적으로 재확인 중 |
| `FAILED` | 해석 실패 |
| `PERMANENT` | 정적 항목, 만료되지 않음 |

`ip neigh`로 현재 상태를 볼 수 있습니다.

```bash
ip neigh show
ip neigh show dev eth0
```

Calico가 이 상태를 활용합니다. 노드 간 통신용 next-hop 항목을 `PERMANENT`로 주입하는데, Calico felix의 `vxlanfdb`가 `NUD_PERMANENT`로 심습니다.

일반 ARP 캐시처럼 시간이 지나 만료되면 노드 사이 통신이 ARP 타임아웃으로 끊기는데, 정적 항목으로 못 박아 그 사고를 막는 것입니다. 핑 로스 장애에서 `ip neigh` 항목이 `PERMANENT`인지부터 보는 이유가 여기 있습니다.



## 4. netfilter와 iptables / nftables
> 패킷이 커널 네트워크 스택을 흐르며 거치는 다섯 hook이 netfilter입니다. iptables와 nftables는 이 hook 위에 룰을 얹는 두 표현입니다.

### 5개의 hook

L3(IP) 레이어에서 패킷이 거치는 hook은 다음과 같습니다.

| Hook | 시점 | 흔한 용도 |
|------|------|----------|
| `NF_IP_PRE_ROUTING` | 패킷 수신 직후, 라우팅 결정 전 | DNAT, conntrack zone |
| `NF_IP_LOCAL_IN` | 라우팅이 "자기 호스트로" 결정 후 | 호스트 INPUT 필터 |
| `NF_IP_FORWARD` | 라우팅이 "전달"로 결정 후 | 노드를 거쳐 가는 트래픽 필터 |
| `NF_IP_LOCAL_OUT` | 자기 호스트가 송신할 때 | 송신 필터, OUTPUT mark |
| `NF_IP_POST_ROUTING` | 송신 직전, NIC 보내기 전 | SNAT, masquerade |

iptables의 `INPUT/OUTPUT/FORWARD/PREROUTING/POSTROUTING` 체인 이름이 이 hook과 일대일 대응입니다.

```mermaid
graph TB
    NIN["NIC 수신"]
    PRE["PRE_ROUTING<br/>DNAT, conntrack 진입"]
    R{라우팅 결정}

    HOST --> LOUT --> POST --> NOUT
    R -->|"전달"| FWD --> POST

    style NIN fill:#d4a853,stroke:#ca8a04,color:#0d0d0d
    style NOUT fill:#d4a853,stroke:#ca8a04,color:#0d0d0d
```

K8s Service의 ClusterIP DNAT는 PRE_ROUTING에서, NodePort의 SNAT는 POST_ROUTING에서 일어납니다. iptables 규칙이 어디 hook에 등록됐는지를 보면 그 규칙의 책임이 곧장 보입니다.

### iptables — 체인과 테이블

iptables는 4개의 테이블(`filter`, `nat`, `mangle`, `raw`)을 가지고, 각 테이블이 일부 hook에 체인을 등록합니다. 트래픽이 hook을 지날 때 테이블별 체인을 정해진 우선순위 순으로 평가합니다.

| 테이블 | 우선순위 | 등록 hook |
|--------|----------|-----------|
| raw | -300 | PREROUTING, OUTPUT |
| mangle | -150 | 모든 hook |
| nat | -100 | PREROUTING, OUTPUT, POSTROUTING |
| filter | 0 | INPUT, FORWARD, OUTPUT |

```bash
iptables -t nat -L -n -v
iptables-save | grep KUBE-SERVICES | head
```

### nftables — 더 나은 표현

nftables는 같은 netfilter hook 위에서 표현을 더 효율적으로 다시 짭니다. 핵심 차이는 셋(set)과 맵(map)입니다. iptables는 규칙을 선형으로 평가해 규칙 수에 비례한 비용이 들지만, nftables는 set/map 안에서 해시 조회가 가능해 매칭 시간이 일정합니다.

```bash
nft list ruleset
nft list table ip kube-proxy
```

K8s kube-proxy의 `nftables` 모드(1.31 beta, 1.33 GA)는 같은 KUBE-SERVICES 의미를 nft set/map으로 다시 적되 Service 수가 늘어도 매칭 비용이 일정하도록 만듭니다.

### 디버깅

규칙이 매칭되는지 알고 싶을 때는 LOG 타겟이나 `nftrace`를 씁니다.

```bash
iptables -t nat -A PREROUTING -d 10.96.50.20 -j LOG --log-prefix "MATCH: "
journalctl -kf | grep "MATCH:"

nft monitor trace
nft 'add rule inet filter input ip saddr 10.244.0.5 meta nftrace set 1'
```



## 5. conntrack — 연결 추적
> NAT를 쓰는 모든 노드는 conntrack 테이블을 갖습니다. 한 흐름이 만들어지면 응답 패킷도 같은 NAT 변환을 받기 위해 추적이 필요합니다. 이 테이블이 가득 차면 새 연결이 silently drop 됩니다.

### 무엇이 기록되는가

conntrack 엔트리는 5-tuple(src IP, dst IP, src port, dst port, protocol) 두 방향(original, reply)과 NAT 변환, 상태(NEW, ESTABLISHED, RELATED, INVALID), TTL을 갖습니다. 새 연결은 PREROUTING의 raw 테이블에서 시작점을 만나고, ESTABLISHED 패킷은 이미 만들어진 엔트리를 바로 참조합니다.

![conntrack 상태 머신 — 첫 패킷부터 양방향 확인까지](./_assets/01-01-conntrack-states.svg)

여기서 상태와 플래그를 구분해 두면 좋습니다. NEW·ESTABLISHED·RELATED·INVALID는 흐름이 어디까지 왔는지를 나타내는 *상태*입니다.

반면 `ASSURED`는 그와 별개인 *플래그*입니다. 양방향 트래픽이 모두 확인되면 켜지고, 뒤에서 볼 테이블 포화 때 이 플래그가 없는 엔트리부터 먼저 정리됩니다.

```bash
conntrack -L | head
conntrack -L -p tcp --dport 80
cat /proc/sys/net/netfilter/nf_conntrack_max
cat /proc/net/stat/nf_conntrack    # drop, insert_failed 통계
```

### K8s에서 자주 보이는 두 패턴

K8s Service의 ClusterIP DNAT가 일어나면 conntrack에 변환이 기록됩니다. 응답 패킷은 같은 5-tuple을 reply 방향에서 매칭해 자동으로 NAT를 거꾸로 풀어 클라이언트로 돌아갑니다. 이 자동 reverse가 없으면 클라이언트는 모르는 IP에서 응답을 받게 되어 패킷을 버립니다.

NodePort/LoadBalancer + `externalTrafficPolicy: Cluster` 조합에서 SNAT가 추가로 일어납니다. 이때도 conntrack이 응답을 노드 자신으로 돌려 와 다시 클라이언트로 풀어 주는 역할을 합니다.

### 포화 문제

포화를 이해하려면 TCP와 UDP의 conntrack 수명 차이를 먼저 봐야 합니다. 둘은 성격이 반대입니다.

- **TCP** — 타임아웃이 깁니다. TCP 상태 머신을 따라가므로, ESTABLISHED 기본 수명이 `432000`초, 즉 5일입니다. 연결이 살아 있는 동안 엔트리가 오래 유지되지만, 대신 개수 자체는 실제 연결 수만큼입니다.
- **UDP** — 연결이라는 개념이 없어 타임아웃이 짧습니다. 한쪽 방향만 봤으면 30초(`nf_conntrack_udp_timeout`), 양방향이 확인돼 `ASSURED`가 붙으면 120초(`nf_conntrack_udp_timeout_stream`)입니다. 짧게 사라지지만, 문제는 개수입니다.

CoreDNS처럼 UDP 질의가 폭주하는 환경에서는 짧은 수명에도 엔트리가 쌓이는 속도가 사라지는 속도를 앞질러, conntrack 테이블이 포화되고 새 연결이 silently drop됩니다. 대처법은 두 가지입니다.

첫째, `nf_conntrack_max`를 올립니다. 이 값은 노드 메모리에 비례해 자동 계산됩니다(`nf_conntrack_buckets × 4`, buckets는 RAM에서 산정).

포화가 잦은 환경에서는 수동으로 수 배 키워 여유를 줍니다. 정해진 배수가 있는 건 아니고 트래픽에 맞춰 조정하는 튜닝입니다.

```bash
sysctl -w net.netfilter.nf_conntrack_max=1048576
```

둘째, DNS 캐시(NodeLocal DNS Cache)를 도입해 노드 외부 conntrack 엔트리 발생 자체를 줄입니다. 원인을 줄이는 쪽이라 근본 대처에 가깝습니다. K8s 04-05 NodeLocal DNS Cache 절이 이 패턴을 다룹니다.



## 6. Traffic Control(TC)와 qdisc
> TC는 큐잉·셰이핑·필터링·policing을 담당하는 Linux 네트워크 계층의 또 다른 hook 지점입니다. eBPF가 가장 흔하게 어태치되는 자리이기도 합니다.

### qdisc 트리

각 인터페이스에는 outgoing qdisc(보통 `pfifo_fast` 또는 `fq_codel`)와 ingress qdisc가 따로 붙습니다. qdisc 안에 class와 filter가 트리 형태로 쌓이고, filter가 패킷을 분류해 class로 보냅니다.

```bash
tc qdisc show dev eth0
tc class show dev eth0
tc filter show dev eth0
```

ingress qdisc는 entry point 하나만 있는 특수한 qdisc입니다. eBPF/cls 기반 필터를 붙여 진입 패킷을 처리합니다.

### TC eBPF — Cilium의 진입점

Cilium은 노드 인터페이스의 ingress와 egress 양쪽 TC hook에 eBPF 프로그램을 어태치합니다. 이 프로그램이 Service VIP DNAT, NetworkPolicy 평가, Pod 식별, 메트릭 수집을 모두 수행합니다. iptables/nftables를 거치지 않는 이유가 여기 있습니다.

```bash
tc filter show dev eth0 ingress
bpftool net show          # 모든 BPF 어태치 포인트
bpftool prog show          # 로드된 BPF 프로그램
```



## 7. eBPF — 핵심 메커니즘만
> eBPF는 별도 문서에서 깊게 다뤄도 좋은 주제지만, 네트워킹 진단에서 자주 쓰는 부분만 정리합니다.

eBPF 프로그램은 verifier가 정적 분석으로 안전성을 확인한 뒤 JIT 컴파일되어 커널 hook에서 실행됩니다. 어태치 가능한 hook은 다음과 같습니다.

| 어태치 포인트 | 시점 | 용도 |
|--------------|------|------|
| XDP | NIC 드라이버 직후 | 가장 빠른 패킷 처리, DDoS 차단 |
| TC ingress/egress | qdisc 진입/송출 시 | Cilium의 주된 dataplane |
| cgroup connect/sendmsg | 소켓 syscall 시 | Service VIP socket-level 로드밸런싱 |
| kprobe / tracepoint | 커널 함수 호출 | Hubble의 L7 정보 수집 |

이 어태치 포인트들이 수신 패킷 경로의 어디에 끼는지를 보면 왜 순서가 성능을 가르는지 드러납니다.

![eBPF 어태치 지점 — 수신 패킷 경로 위 어디에 끼는가](./_assets/01-01-ebpf-attach-points.svg)

핵심은 두 가지입니다. XDP는 skb가 만들어지기도 전에 실행되어, 여기서 버린 패킷은 conntrack을 아예 거치지 않습니다. 그리고 TC ingress는 iptables PREROUTING보다 앞서 돌기 때문에, Cilium이 TC에서 처리를 끝내고 netfilter 계층을 통째로 건너뛸 수 있습니다. 이게 Cilium이 kube-proxy 없이도 동작하는 성능 근거입니다.

eBPF 맵은 커널과 유저스페이스가 공유하는 자료구조입니다. Cilium은 Service endpoint 테이블, NetworkPolicy 결정 트리, 연결 추적 정보를 맵에 담아 두고 dataplane이 O(1) 해시로 조회합니다.

```bash
bpftool map show
bpftool prog dump xlated id <prog_id>
cat /sys/kernel/debug/tracing/trace_pipe   # bpf_trace_printk 출력
```

상세는 `eBPF와 Cilium` <!-- 링크 끊김(2026-08): ../../08_cloud/service-mesh/14-02.eBPF와 Cilium.md --> 본편을 봅니다.



## 8. 통합 디버깅 시퀀스
> "패킷이 안 가는데" 같은 막연한 증상을 만났을 때, 위 메커니즘을 따라 좁히는 순서를 정리해 둡니다.

확인 순서는 다음과 같습니다.

1. 어느 네임스페이스에서 보내고 받는지 확인합니다(`ip netns`, `nsenter -t <PID> -n`).
2. 출발 네임스페이스의 라우팅 테이블이 의도한 next-hop으로 보내고 있는지 봅니다(`ip route`, `ip rule`).
3. veth/bridge가 정상인지 확인합니다(`ip link`, `bridge link`, `bridge fdb`).
4. netfilter가 drop 또는 reject 하지 않는지 봅니다(`iptables -L -n -v` 카운터, `nft monitor trace`).
5. conntrack에 흐름이 잡혔는지, 테이블이 포화 상태가 아닌지 확인합니다(`conntrack -L`, `/proc/net/stat/nf_conntrack`).
