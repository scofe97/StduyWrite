# 포트 스캐너 실습 기록

---

> 04-01 이 설명한 판정과 정확도·속도의 맞교환을 CONNECT 스캐너로 자기 소유 호스트(OrbStack VM 의 127.0.0.1)에만 돌려 본 기록입니다. 단 1 CONNECT 는 실험까지 마쳤고, 단 2 SYN 은 코드까지만 쓰고 실험은 심화로 미뤘습니다.

## 학습 목표와 범위

> 이 문서를 따라 하면 같은 VM 에서 실험을 다시 돌려 같은 모양의 결과를 얻어야 합니다. 걸린 시간의 ms 는 달라져도 무엇이 시간을 정했는지 알 수 있어야 합니다.

| 목표 | 어떻게 확인하나 |
|---|---|
| 스캔 시간을 정하는 것이 timeout·worker·rate 중 무엇인지 경우마다 가립니다 | 실험 1·2B |
| 방화벽 DROP·REJECT 세 종류가 같은 포트를 각각 어떤 판정·errno 로 만드는지 봅니다 | 실험 2 |
| 재시도가 어떤 포트의 오판만 줄이는지 손실을 걸어 셉니다 | 실험 3 |
| 너무 빨리 물으면 스캐너가 스스로 무응답을 만든다는 것을 커널 카운터로 봅니다 | 실험 4 |

개념 설명은 [04-01](./04-01.%EB%AC%B4%EC%9D%91%EB%8B%B5%EC%9D%80%20%EC%A6%9D%EA%B1%B0%EA%B0%80%20%EC%95%84%EB%8B%88%EB%8B%A4%20-%20CONNECT%C2%B7SYN%C2%B7UDP%20%ED%8F%AC%ED%8A%B8%20%EC%8A%A4%EC%BA%94.md) 이 정본입니다. 여기서는 실행과 관측만 다룹니다. 스캔 대상은 늘 자기 소유 호스트입니다.

| 키워드 | 뜻 | 학습 포인트·연결 개념 | 어디서 |
|---|---|---|---|
| ephemeral port | 연결을 시작할 때 커널이 고르는 임시 출발지 포트 | 32768–60999, 고갈되면 EADDRNOTAVAIL | §4 |
| errno | syscall 이 실패한 이유로 돌려주는 번호 | ECONNREFUSED·EHOSTUNREACH·timeout | §3 |
| TIME-WAIT | 먼저 닫은 쪽에 2MSL 동안 남는 소켓 상태 | 고속 스캔이 스캐너 쪽에 쌓는다 | §4 |
| ListenOverflows | accept 대기열이 꽉 차 연결을 못 받은 횟수 | `nstat` 카운터 | §4 |



## 1. 실습 환경과 코드

> CONNECT 스캐너 한 명령으로 포트를 묻고, 터미널을 나눠 서버·캡처·스캔을 돌렸습니다. 코드는 AI 가 작성했고 실행과 해석은 학습자가 했습니다.

`gonet scan` 을 실행하면 `runScan` → `scan.Run` → `probeWithRetry` → `ProbeConnect` 순서로 내려갑니다. 구조는 04-01 §4 의 코드와 같습니다.

| 파일 | 하는 일 |
|---|---|
| `internal/scan/scan.go` | `Run`: 포트를 채널에 넣고 worker goroutine 들이 꺼내 간다. 티커 하나를 모든 worker 가 나눠 받아 전체 속도를 초당 Rate 로 묶는다. `probeWithRetry`: 무응답일 때만 Retries 번 더 묻는다 |
| `internal/scan/connect.go` | `ProbeConnect`: `net.DialTimeout` 결과를 성공→open, ECONNREFUSED→closed, EHOSTUNREACH→filtered(근거 있음), timeout→filtered 로 가른다 |
| `cmd/gonet/scan.go` | `gonet scan [-ports] [-workers] [-rate] [-retries] [-timeout] [-v] [-s] <host>` |
| `internal/scan/scan_test.go` | loopback 실제 소켓으로 열림·닫힘 판정, worker 가 기다림을 겹치는지, 재시도가 무응답에만 걸리는지 테스트 |

worker 마다 결과를 `results[i]` 의 서로 다른 칸에 씁니다. 그래서 여러 goroutine 이 같은 값을 동시에 고치는 경쟁 조건이 생기지 않습니다. 04-01 §4 에서 짚은 내용입니다.



## 2. 실험 1 - 무엇이 스캔 시간을 정하는가

> 포트 1,025 개를 묻는 데 몇 초가 걸릴지, 그 시간을 정하는 것이 timeout·worker·rate 중 무엇인지 손잡이를 하나씩 풀어 가렸습니다.

열린 포트(8080)와 닫힌 포트 1,024 개를 세 가지 설정으로 물었습니다. 실행 전 예측은 "worker 가 가장 중요하다"였습니다.

```bash
./bin/gonet-linux listen :8080                                      # 터미널 1
sudo tcpdump -i lo -nn 'tcp port 8080 or tcp port 81'               # 터미널 2
./bin/gonet-linux scan -ports 1-1024,8080 127.0.0.1                 # 터미널 3 (기본값)
./bin/gonet-linux scan -ports 1-1024,8080 -rate 0 127.0.0.1         # rate 제한 없음
./bin/gonet-linux scan -ports 1-1024,8080 -rate 0 -workers 1 127.0.0.1
```

```bash
# worker 25, rate 1000
--- open 1  closed 1024  filtered 0  unknown 0  (2.657s)
시도     1번=1025
# worker 25, rate 0
--- open 1  closed 1024  filtered 0  unknown 0  (10ms)
# worker 1, rate 0
--- open 1  closed 1024  filtered 0  unknown 0  (21ms)
```

시간을 정한 것은 rate 였습니다. rate 를 풀자 2.657초가 10ms 로 260배 줄었습니다. worker 는 25배로 늘려도 21ms 가 10ms 로 두 배 줄었을 뿐입니다.

학습자는 worker 효과가 작은 이유를 "스레드 개수가 고정돼 있어서"로 봤습니다. 방향이 어긋났습니다. 진짜 이유는 기다림이 없기 때문입니다.

tcpdump 에서 81번 포트의 SYN 과 RST 사이는 6µs 였습니다. loopback 의 닫힌 포트는 RST 가 곧바로 돌아와 기다릴 것이 없습니다. worker pool 은 기다리는 동안 다른 포트를 묻는 장치이므로, 기다림이 없으면 겹칠 것도 없습니다.

25개로 두 배 빨라진 것은 기다림을 겹쳐서가 아니라 CPU 코어 여러 개가 syscall 을 나눠 처리한 몫입니다. 기다리는 goroutine 은 스레드를 붙잡지 않으므로([01-01](./01-01.%EC%A1%B0%EC%9A%A9%ED%95%9C%20%EC%97%B0%EA%B2%B0%EC%9D%B4%20%EC%84%9C%EB%B2%84%EB%A5%BC%20%EB%A9%88%EC%B6%98%EB%8B%A4%20-%20goroutine%C2%B7FD%C2%B7idle%20timeout.md) §1), 스레드 수는 원인이 아닙니다.

tcpdump 에서 8080 쪽은 `S → S. → .` 로 handshake 가 끝까지 맺어진 뒤 스캐너가 먼저 `F.` 를 보냈습니다. CONNECT 스캔이 연결을 끝까지 맺는다는 04-01 §1 의 설명이 선로에 그대로 찍혔습니다. 점(`.`)은 ACK 플래그입니다.

rate 1000 이면 이론상 1초여야 할 스캔이 2.657초였습니다. 캡처로 센 실효 속도는 초당 390개쯤이었습니다. 1ms 간격 티커가 VM 에서 제 간격을 못 지켰을 가능성을 가설로만 둡니다(미확인).



## 3. 실험 2·2B - 방화벽 네 종류와, 기다림이 길 때의 worker

> 실제로 열린 8080 을 방화벽 네 가지로 막고, 같은 포트가 각각 무엇으로 판정되는지 봤습니다. 이어서 기다림이 길면 worker 가 시간을 정하는 것을 확인했습니다.

### 실험 2 - 같은 포트를 네 가지로 막기

네 가지 방화벽 규칙은 모두 `ProbeConnect` 의 `switch` 에서 갈립니다. 갈리는 기준은 `net.Dial` 이 돌려준 에러 하나뿐입니다. 규칙을 하나 넣고 스캔한 뒤 바로 지웁니다. 아래 표의 errno 는 그 에러의 이름이고, tcpdump 열은 그때 선로에 찍힌 패킷입니다.

```bash
sudo tcpdump -i lo -nn 'tcp port 8080 or icmp'                      # 터미널 2
sudo iptables -I INPUT -i lo -p tcp --dport 8080 -j DROP
./bin/gonet-linux scan -ports 8080 -v 127.0.0.1
sudo iptables -D INPUT -i lo -p tcp --dport 8080 -j DROP
# REJECT(기본) / REJECT --reject-with tcp-reset / REJECT --reject-with icmp-admin-prohibited 를 같은 틀로 반복
```

| 규칙 | 판정 | errno | 걸린 시간 | tcpdump |
|---|---|---|---|---|
| DROP | filtered | timeout | 2.005초 | SYN 두 번, 답 없음 |
| REJECT 기본 | closed | ECONNREFUSED | 5ms | ICMP port unreachable |
| REJECT tcp-reset | closed | ECONNREFUSED | 2ms | `[R.]` (RST) |
| REJECT admin-prohibited | filtered | EHOSTUNREACH | 3ms | ICMP admin prohibited |

예측은 네 경우 모두 closed 나 filtered 를 맞혔는데 admin-prohibited 만 빗나갔습니다. 학습자는 이것을 closed 로 봤으나 실제는 filtered 였습니다. `icmp-admin-prohibited` 는 ICMP 종류 3·코드 13, "관리 정책으로 통신이 금지됨"입니다. 방화벽이 막았다고 사실대로 알리는 거절이고, 스캐너 쪽 커널이 이것을 `EHOSTUNREACH` 로 바꿔 filtered 갈래(04-01 §3)로 보냅니다. 넷 가운데 실제 상태(열림)에 대해 가장 정직한 답입니다.

tcp-reset 이 보낸 `[R.]` 은 실험 1 에서 81번 포트가 보낸 진짜 RST 와 모양이 똑같았습니다. 그래서 패킷을 직접 읽는 SYN 스캐너도 이것은 닫힌 포트와 구별하지 못합니다. REJECT 기본의 ICMP 는 선로에서는 다르게 찍히지만, 커널이 `ECONNREFUSED` 로 바꿔 버려 CONNECT 스캐너만 구별하지 못합니다.

실제로 열린 8080 을 DROP 은 filtered, tcp-reset 은 closed 로 판정했습니다. 진실에서 더 멀리 간 쪽은 closed 입니다. filtered 는 "막혀서 모르겠다"는 판정이라 틀린 말을 하지 않지만, closed 는 "여기는 아무도 안 듣는다"고 단정하는데 실제로는 서버가 듣고 있습니다. 실무에서 closed 를 본 사람은 그 포트를 지워 버리므로, `tcp-reset` 은 바로 이렇게 속이려고 쓰는 설정입니다.

### 실험 2B - 기다림이 길 때의 worker

실험 1 에서 worker 효과가 작았던 이유가 기다림이 없어서였으니, 이번에는 포트 100개를 모두 DROP 으로 무응답으로 만들어 포트마다 timeout 1초를 기다리게 했습니다. 재시도는 꺼 계산을 단순하게 했습니다.

```bash
sudo iptables -I INPUT -i lo -p tcp --dport 1:100 -j DROP
./bin/gonet-linux scan -ports 1-100 -retries 0 127.0.0.1                 # worker 25
./bin/gonet-linux scan -ports 1-100 -retries 0 -workers 100 127.0.0.1    # worker 100
sudo iptables -D INPUT -i lo -p tcp --dport 1:100 -j DROP
```

```bash
# worker 25:  4.071s
# worker 100: 1.215s
```

worker 25 는 100 ÷ 25 = 네 묶음을 1초씩 기다려 4초, worker 100 은 한 묶음이라 1초였습니다. 1초를 넘은 0.2초는 rate 가 SYN 100개를 내보내는 데 걸린 시간입니다. 기다림이 있어야 worker pool 이 제값을 합니다.



## 4. 실험 3·4 - 재시도와 고속 스캔의 대가

> 재시도가 어떤 포트의 오판만 줄이는지 손실을 걸어 셌고, worker 를 과하게 늘렸을 때 스캐너가 스스로 무응답을 만드는 것을 커널 카운터로 봤습니다.

### 실험 3 - 손실 속의 재시도

재시도는 `probeWithRetry` 의 반복문이 담당합니다. 열린 포트도 SYN 이나 SYN-ACK 가 사라지면 timeout 이 나 filtered 로 잘못 적힙니다. 열린 포트 8080 을 100번 반복해 물으며 재시도 수만 바꿨습니다.

```bash
sudo tc qdisc add dev lo root netem loss 20%
P=$(printf '8080,%.0s' $(seq 99))8080
./bin/gonet-linux scan -ports $P -retries 0 127.0.0.1 | tail -3
./bin/gonet-linux scan -ports $P -retries 1 127.0.0.1 | tail -3
./bin/gonet-linux scan -ports $P -retries 2 127.0.0.1 | tail -3
sudo tc qdisc del dev lo root
```

| 재시도 | 계산상 오판 (0.36ⁿ⁺¹) | 실측 filtered | 걸린 시간 |
|---|---|---|---|
| 0 | 36% | 35 | 2.07초 |
| 1 | 13% | 8 | 3.04초 |
| 2 | 4.7% | 3 | 4.04초 |

주의: 이번 측정은 `tc qdisc add` 가 "Exclusivity flag on" 으로 실패한 상태에서 돌았습니다. `lo` 에 이미 다른 qdisc 가 붙어 있었다는 뜻입니다. 마지막 `del` 로 지워져 그 정체는 확인하지 못했습니다(미확인). 숫자가 계산과 같은 방향이지만, 기록으로 쓰려면 `tc qdisc show dev lo` 가 `noqueue` 인 깨끗한 상태에서 다시 돌려야 합니다.

재시도를 한 번 늘릴 때마다 오판이 줄고 시간이 1초씩 늘었습니다. 닫힌 포트는 첫 시도에 RST 가 돌아와 바로 끝나므로 재시도를 아예 타지 않습니다. 재시도가 건지는 것은 답이 있는 포트인데 그 답이 중간에 사라진 경우뿐입니다. 그래서 DROP 이 대부분인 대상에서는 재시도를 올려도 시간만 늘고 정확도는 그대로입니다.

학습자가 "재시도는 커널이 하는 것 아닌가"를 물었습니다. 단 1 은 일반 소켓이라 재시도가 두 층에 있습니다. 커널은 같은 연결의 SYN 을 1·3초 간격으로 다시 보내고(최대 10번·131초, 04-01 §1), 우리 코드는 timeout 1초마다 연결을 버리고 새 연결로 다시 묻습니다. 우리 timeout 이 커널 첫 재전송 시점과 같아 커널 재전송은 사실상 일어나지 않습니다. 증거는 실험 2(a) 의 tcpdump 에 있습니다. SYN 두 개의 출발지 포트와 seq 가 달랐으니, 커널 재전송이 아니라 우리 코드가 만든 새 연결입니다.

### 실험 4 - 고속 스캔이 스캐너에 남기는 것

열린 포트를 물을 때마다 `ProbeConnect` 는 연결을 끝까지 맺고 `conn.Close()` 로 먼저 FIN 을 보냅니다. 연결 하나마다 임시 포트 하나를 씁니다(이 VM 은 32768–60999, 28,232개). 8080 에 3만 번 연결했습니다. 명령줄 인자 하나가 128KiB(`MAX_ARG_STRLEN`)를 넘어 실패해서, 1만 5천 개짜리 두 프로세스로 나눠 돌렸습니다.

```bash
ss -tan state time-wait | wc -l                                         # 기준선
P=$(printf '8080,%.0s' $(seq 14999))8080
for i in 1 2; do ./bin/gonet-linux scan -ports "$P" -rate 0 -workers 200 127.0.0.1 | tail -2 & done; wait
nstat -az TcpExtListenOverflows TcpExtListenDrops
```

```bash
시도     1번=14050 2번=950
시도     1번=14000 2번=1000
TcpExtListenOverflows  4032
TcpExtListenDrops      4032
```

열린 포트인데 `시도 2번` 이 950·1,000개 나왔습니다. 재실행에서는 끝내 75개(39+36)가 filtered 로 오판됐습니다. 원인은 서버의 accept 대기열(한도 4096)이 4,032번 넘친 것이었습니다.

400개 worker 가 제한 없이 몰아치자 넘친 연결의 SYN·ACK 가 버려졌고, 스캐너는 1초를 기다려 다시 물었습니다. 방화벽도 손실도 없는 깨끗한 loopback 에서, 04-01 §4 의 "너무 빨리 물으면 스캐너가 스스로 무응답을 만든다"가 그대로 일어난 것입니다.

TIME-WAIT 는 예측대로 먼저 닫은 스캐너 쪽에 쌓였습니다. `ss state time-wait` 출력에서 네 번째 열은 State 가 빠져 Local 이 아니라 Peer 입니다. 그래서 "peer 가 8080 인 TIME-WAIT" 가 곧 스캐너 쪽 소켓입니다(처음 AI 가 이 열을 Local 로 잘못 읽었습니다).

3만 번 연결했는데 임시 포트 고갈(`EADDRNOTAVAIL`)은 없었습니다. 이 VM 의 `tcp_tw_reuse` 가 `2` 라 loopback 의 TIME-WAIT 포트를 재사용했기 때문으로 보입니다(가설, `tw_reuse=0` 재실행은 미실행).

임시 포트가 바닥나면 `net.Dial` 은 SYN 을 보내기도 전에 실패합니다. SYN 의 출발지 포트 칸을 채울 포트를 `connect()` 안에서 커널이 먼저 골라야 하는데, 고를 포트가 없기 때문입니다. 이 실패는 대상의 판정이 아니므로 unknown 으로 둡니다.



## 5. 단 2 SYN 은 코드까지, 그리고 남은 것

> 단 2 SYN 스캔은 raw 소켓으로 TCP 헤더를 직접 짜는 심화 과정이라 코드만 쓰고 실험은 미뤘습니다.

`internal/scan/tcphdr.go` 와 `syn.go` 에 SYN 스캐너를 썼습니다. `net.ListenPacket("ip4:tcp", …)` 로 커널 TCP 를 건너뛰고, TCP 헤더 20바이트와 pseudo-header 체크섬을 직접 만들어 SYN 하나만 보냅니다. 돌아온 플래그가 SYN-ACK 면 open, RST 면 closed 입니다. 바이트 레벨 테스트 6개(체크섬 검산·짝 맞추기·IPv4 헤더 건너뛰기)는 `make check` 로 통과했습니다. 실행에는 `sudo` 나 `setcap cap_net_raw+ep` 가 필요하고 Linux 전용입니다.

03 DNS 가 UDP 가 날라 주는 짐(DNS 메시지)을 바이트로 짰다면, 단 2 는 TCP 라는 운송 수단 자체를 바이트로 짭니다. 손대는 경계가 한 계층 더 내려갑니다.

아직 돌리지 않은 실험을 모읍니다. 자기 소유 호스트에만 한정합니다.

| 후보 | 확인할 것 | 연결 |
|---|---|---|
| 단 2 실험 1 | 직접 짠 SYN 을 `tcpdump -X` 로 찍어 커널이 만든 SYN 과 바이트 대조 | 04-01 §2, 03-02 실험 1 |
| 단 2 실험 2 | SYN 스캔 중 스캐너 쪽에서 나가는 RST, `ss` 에 SYN-SENT 없음 | 04-01 §2 |
| 단 2 실험 3 | 대상 쪽 `ss state syn-recv` 에 반쯤 열린 연결이 잠깐만 남는지 | 04-01 §2 |
| 단 3 UDP 스캔 | DNS 질의 페이로드로 open\|filtered, netns 에서 ICMP 대상별 제한 재현 | 04-01 §3, 03 인코더 |
| 실험 3 재측정 | `noqueue` 깨끗한 상태에서 netem loss 20% 를 다시 걸어 오판율 확정 | 이 문서 §4 |
| 실험 4 가설 2 | `tcp_tw_reuse=0` 으로 임시 포트 고갈과 `EADDRNOTAVAIL` 재현 | 이 문서 §4 |

loopback 에는 현실과 다른 예외가 둘 있어, 단 3 과 재측정은 netns+veth 나 원격 VM 에서 하는 편이 낫습니다. `tcp_tw_reuse=2` 가 loopback 에서만 TIME-WAIT 재사용을 켜고, 대상별 ICMP 제한이 loopback 에는 걸리지 않습니다(04-01 §2).



## 검증과 복습

> 실험을 어떻게 진행했고 무엇을 도움받았는지 적습니다.

- Phase 3: 2026-10-05~06. 단 1 CONNECT 는 실험 1~4 와 가설 확인까지 실행했고, 단 2 SYN 은 코드와 바이트 테스트까지만 했습니다. 회차별 구분은 [STATE.md](./STATE.md) 에 있습니다.
- 스스로 도달: rate 가 손잡이, 기다림이 있어야 worker 가 효용, closed 가 filtered 보다 멀리 속는다, TIME-WAIT 는 스캐너 쪽에 쌓인다, SYN 을 보내기 전에 임시 포트가 없어 실패한다
- 설명으로 채움(도움받은 응답): worker 효과가 작은 진짜 이유(기다림 없음), admin-prohibited 가 filtered 인 이유, 커널 재전송 vs 앱 재시도, accept 대기열 넘침
- AI 실수: 명령줄 인자 길이 초과, `ss` 의 Peer 열을 Local 로 읽음 — 둘 다 바로잡아 기록함
- 복습 표적: 시간을 정하는 손잡이의 경우 구분, 방화벽 네 종류의 판정표, 재시도가 효과 있는 포트, 고속 스캔의 자기 오판
