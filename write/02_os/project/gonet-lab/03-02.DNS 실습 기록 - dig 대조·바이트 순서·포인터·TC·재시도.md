# DNS 실습 기록

---

> 03-01 이 설명한 질의·응답의 바이트를 직접 만든 클라이언트로 주고받은 다섯 실험의 기록입니다. 실험마다 명령, 학습자의 예측, 실제 출력, 해석을 차례로 적었습니다.

## 학습 목표와 범위

> 이 문서를 따라 하면 같은 VM 에서 다섯 실험을 다시 돌려 같은 모양의 결과를 얻어야 합니다. ID·TTL·답의 순서처럼 매번 바뀌는 값이 달라져도 어디를 보면 되는지 알 수 있어야 합니다.

| 목표 | 어떻게 확인하나 |
|---|---|
| 직접 지은 질의 29바이트가 `dig` 의 질의와 어느 칸만 다른지 찾고 그 이유를 말합니다 | 실험 1 |
| 바이트 순서를 어긴 질의가 에러 없이 끝나는 모습을 봅니다 | 실험 2 |
| 응답의 압축 포인터가 이름 한가운데를 가리키는 것을 봅니다 | 실험 3 |
| TC 가 켜진 UDP 응답을 받고 길이 2바이트를 붙여 TCP 로 다시 묻습니다 | 실험 4 |
| 손실 속에서 같은 ID 로 다시 보내는 이유를 말합니다 | 실험 5 |

개념 설명은 [03-01](./03-01.DNS%20%EC%A7%88%EC%9D%98%20%ED%95%9C%20%EC%9E%A5%EC%9D%84%20%EB%B0%94%EC%9D%B4%ED%8A%B8%EB%A1%9C%20-%20%ED%97%A4%EB%8D%94%C2%B7%EB%9D%BC%EB%B2%A8%C2%B7%EC%95%95%EC%B6%95%20%ED%8F%AC%EC%9D%B8%ED%84%B0%C2%B7TC.md) 가 정본입니다. 여기서는 실행과 관측만 다룹니다.

| 키워드 | 뜻 | 학습 포인트·연결 개념 | 어디서 |
|---|---|---|---|
| 재귀 리졸버 | 클라이언트 대신 루트부터 차례로 물어 답을 가져오는 서버 | 1.1.1.1, RD 비트 | §1 |
| AD 비트 | 서명 검증 결과를 알려 달라는 플래그 | dig 9.20 이 기본으로 켬 | §2 |
| NODATA | 이름은 있지만 그 타입 레코드는 없다는 응답 | rcode 0·답 0개·권한 절 SOA | §2 |
| TXT 레코드 | 도메인에 붙이는 자유 형식 글자 | 소유 확인 토큰·SPF | §3 |



## 1. 실습 환경과 코드

> 남이 만든 클라이언트는 바이트를 숨기므로, 질의를 직접 짓고 보낸 바이트와 받은 바이트를 그대로 찍는 클라이언트를 만들었습니다. 터미널 둘로 패킷 캡처와 질의를 나눠 돌렸습니다.

`net.LookupHost` 나 `dig` 는 결과만 보여 주고 선로의 바이트는 보여 주지 않습니다. 그래서 질의를 바이트로 짓고, 응답을 칸별로 풀어 찍는 `gonet dns` 를 만들었습니다. 코드는 AI 가 작성했고 실행과 해석은 학습자가 했습니다.

| 파일 | 하는 일 |
|---|---|
| `internal/dns/query.go` | `Encode`: 헤더 12바이트(RD), 라벨 인코딩(라벨 1–63·이름 255 검사), 타입·클래스. `-flip` 이면 `put16` 이 일부러 리틀엔디언으로 씀 |
| `internal/dns/parse.go` | `Parse`: ID 와 질문 칸을 보낸 바이트와 대조. `readName`: 압축 포인터를 따라가되 앞쪽만 허용해 고리를 막음. 답 절의 A·AAAA·CNAME·TXT 를 풂 |
| `internal/dns/client.go` | `queryUDP`: 시도마다 timeout, 짝이 안 맞는 데이터그램은 버림, 같은 ID 로 재전송. `QueryTCP`: 길이 2바이트 접두. `Resolve`: TC 면 TCP 로 다시 물음 |
| `cmd/gonet/dns.go` | `gonet dns [-server] [-type] [-tcp] [-flip] [-timeout] [-attempts] <name>` |
| `internal/dns/dns_test.go` | loopback 가짜 서버로 29바이트 골든 값·포인터·ID 불일치·재전송·TC 재질의 11개 테스트 |

질의는 모두 Cloudflare 의 공개 재귀 리졸버 1.1.1.1 로 보냈습니다. 03-01 을 쓸 때와 같은 서버입니다.

```bash
# macOS
make build-linux

# 터미널 1 (ubuntu) — 1.1.1.1 과 오가는 DNS 패킷을 바이트로 찍는다
sudo tcpdump -i any -nn -X 'port 53 and host 1.1.1.1'

# 터미널 2 (ubuntu, ~/study/gonet-lab)
./bin/gonet-linux dns ...
```



## 2. 실험 1·2 - 질의 바이트를 남의 것과 맞대고, 일부러 틀린다

> 내 인코더가 맞는지는 내 코드로 확인할 수 없어서 dig 의 질의와 바이트로 맞댔습니다. 이어 바이트 순서를 일부러 어겨 서버가 어떻게 받아들이는지 봤습니다.

### 실험 1 - gonet 질의와 dig 질의

```bash
./bin/gonet-linux dns example.com
dig +noedns example.com @1.1.1.1
```

`+noedns` 는 dig 가 질의 끝에 붙이는 확장 레코드(EDNS)를 뺍니다. 빼야 두 질의가 같은 29바이트 틀이 됩니다.

실행 전 예측은 "명령이 다르니 차이는 있겠지만 어디일지는 모르겠다"였습니다. tcpdump 에서 IP·UDP 헤더 28바이트를 뺀 DNS 부분은 이렇습니다.

```text
gonet  bb6a 0100 0001 0000 0000 0000 0765 7861 6d70 6c65 0363 6f6d 0000 0100 01
dig    015c 0120 0001 0000 0000 0000 0765 7861 6d70 6c65 0363 6f6d 0000 0100 01
```

| 칸 | gonet | dig |
|---|---|---|
| ID | `bb 6a` (47978) | `01 5c` (348) |
| 플래그 | `01 00` (RD) | `01 20` (RD + AD) |
| 개수·이름·타입·클래스 | 같음 | 같음 |
| UDP 출발지 포트 | 58657 | 49852 |

ID·플래그·출발지 포트 말고는 한 바이트도 다르지 않았습니다. 직접 만든 인코더가 dig 와 같은 질의를 짓는다는 것을 바깥 기준으로 확인한 셈입니다. 플래그의 `0x0020` 은 AD 비트이고 dig 9.20 이 기본으로 켭니다.

응답은 둘 다 61바이트였습니다. 답 두 개의 이름 자리가 모두 `c0 0c` 였고, 디코더는 `포인터 @29 → 12`, `@45 → 12` 로 찍었습니다. 두 응답에서 주소 두 개의 순서와 TTL(290, 94)이 달랐습니다. 학습자는 이것을 처음에 "IP 가 다르다"고 읽었습니다. 리졸버가 답의 순서를 돌려 주고 질의마다 다른 캐시가 답할 수 있다는 것은 설명으로 채웠습니다.

학습자는 dig 의 `id: 348` 이 다른 것을 스스로 찾았습니다. 그러고는 "ID 가 재귀로 알아보라는 명령"이라고 RD 와 섞었습니다. ID 는 뜻이 없는 16비트 번호표이고, 서버가 응답에 그대로 복사해 짝 맞추기에 쓴다고 바로잡았습니다.

ID 와 포트를 매번 무작위로 고르는 이유에 학습자는 처음에 "요청마다 따로 짝을 맞춰야 하니까"라고 답했습니다. 겹치지 않게만 하려면 차례 번호로도 충분하다는 힌트 뒤에는 "예측하지 못하게"까지 갔습니다. 예측되면 무엇이 달라지는지는 설명으로 채웠습니다. 경로 밖 공격자가 출발지를 1.1.1.1 로 속인 가짜 응답의 ID 와 포트를 맞히면, 진짜보다 먼저 도착한 가짜가 짝으로 받아들여집니다. 리졸버가 이렇게 속으면 TTL 동안 모든 사용자에게 퍼지는 캐시 오염이 됩니다.[^rfc5452]

### 실험 2 - 바이트 순서 뒤집기

```bash
./bin/gonet-linux dns -flip qdcount example.com   # 질문 개수 1 을 01 00 (=256) 으로
./bin/gonet-linux dns -flip qtype example.com     # 타입 A(1) 를 01 00 (=256) 으로
```

예측은 "타입을 틀리면 에러 응답, 개수는 큰 차이 없거나 버그가 날 것"이었습니다.

```text
# -flip qdcount
00000000  4c d3 01 00 01 00 00 00  00 00 00 00 07 65 78 61  |L............exa|
헤더   id=0x4cd3 qr=true tc=false rd=true ra=true rcode=0 qd=1 an=2 ns=0 ar=0
답     example.com A ttl=47 172.66.147.243
답     example.com A ttl=47 104.20.23.154

# -flip qtype
00000010  6d 70 6c 65 03 63 6f 6d  00 01 00 00 01           |mple.com.....|
← udp 응답 91 바이트
헤더   id=0xf865 qr=true tc=false rd=true ra=true rcode=0 qd=1 an=0 ns=1 ar=0
```

질문이 256 개라고 말한 질의에는 정상 답이 왔습니다. 1.1.1.1 은 첫 질문만 읽고 답했고 응답의 개수 칸은 1 로 적었습니다. 서버가 봐준 것이라 다른 서버에서는 형식 오류가 될 수 있습니다.

타입을 뒤집은 질의도 에러가 아니었습니다. 타입 256 은 URI 레코드라는 실제 타입입니다.[^rfc7553] 우리는 A 를 물으려다 "URI 레코드를 달라"는 다른 질문을 올바른 형식으로 보낸 셈입니다. 서버는 rcode 0·답 0개에 권한 절 SOA 하나를 붙인 NODATA 로 답했습니다. 권한 절의 `c0 0c 00 06` 이 이름(포인터)·타입 6(SOA)이고, 그 안의 `elliott.ns.cloudflare.com`·`dns.cloudflare.com` 도 `c0 14`·`c0 34` 포인터로 압축돼 있었습니다. 우리 디코더는 답 절만 풀어서 이 SOA 는 화면에 찍지 않았습니다.

학습자는 "틀린 질문을 보냈는데 없다고 하니, 정말 없다고 착각한다"고 스스로 정리했습니다. 에러는 고칠 곳을 알려 주지만 NODATA 는 아무것도 알려 주지 않습니다. 03-01 §2 가 말한 "바이트 순서 실수는 '없다'로 끝나 알아채기 어렵다"를 실측으로 본 것입니다.

이 실수를 감지할 방법도 학습자가 물었습니다. 서버는 256 과 1 이 둘 다 정상 숫자라 가를 수 없으니, 감지는 보내는 쪽이 해야 합니다.

- 기준 구현과 바이트로 맞대는 골든 테스트(`TestEncodeExampleComA`)를 둡니다.
- tcpdump 같은 독립 디코더로 읽어 봅니다.
- 응답에 복사된 질문의 타입을 *의도한* 타입과 비교합니다.

인코더와 디코더에 같은 실수가 있으면 왕복 테스트는 통과하므로 바깥 기준이 필요합니다.



## 3. 실험 3·4 - 응답을 읽는 두 가지 장치

> 이름을 다시 쓰지 않으려는 압축 포인터와, 512바이트를 넘는 응답을 받으려는 TCP 재질의를 실제 응답에서 봤습니다.

### 실험 3 - 이름 한가운데를 가리키는 포인터

```bash
./bin/gonet-linux dns www.github.com
```

`www.github.com` 은 CNAME(별명)으로 `github.com` 을 가리킵니다. 그래서 응답에 이름이 세 번 나옵니다. 예측은 "CNAME 값은 github.com, A 레코드는 포인터일 것"이었고 가리킬 자리는 정하지 못했습니다.

```text
00000020  c0 0c 00 05 00 01 00 00  0c 8f 00 02 c0 10 c0 10  |................|
포인터 @32(0x20) → 12(0x0c)
포인터 @44(0x2c) → 16(0x10)
포인터 @46(0x2e) → 16(0x10)
답     www.github.com CNAME ttl=3215 github.com
답     github.com A ttl=29 20.200.245.247
```

학습자는 "12번과 16번을 재활용해 이름을 다시 쓰지 않았다"고 읽었습니다. 16번은 질문 이름 `03 www 06 github 03 com 00` 의 한가운데, `06 github` 가 시작하는 자리입니다. 이름은 길이와 라벨을 반복하다 `00` 으로 끝나므로 어느 라벨에서 읽기 시작해도 완전한 이름이 됩니다.[^rfc1035-414] 그 덕에 CNAME 값의 길이가 `00 02` 로 2바이트뿐이고, 그대로 썼다면 12바이트였습니다.

### 실험 4 - TC 와 TCP 재질의

```bash
./bin/gonet-linux dns -type TXT google.com
```

우리 질의에는 EDNS 가 없어서 서버는 UDP 로 512바이트까지만 보낼 수 있다고 봅니다.[^rfc1035-421] 실행 전 예측은 "TCP 는 바이트가 이어 붙어 경계를 가를 수 없으니 길이 방식으로 2바이트를 붙인다"였고 맞았습니다. 03-02 이전 메타인지에서 "다시 설명해 달라"고 남겼던 TCP·UDP 경계 차이를 이번에는 스스로 설명했습니다.

```text
← udp 응답 28 바이트, TC=1 이라 TCP 로 다시 묻습니다 (길이 접두 00 1c)
00000000  a1 50 83 80 00 01 00 00  00 00 00 00 06 67 6f 6f  |.P...........goo|
← tcp 응답 1176 바이트 (길이 접두 04 98)
헤더   id=0xa150 qr=true tc=false rd=true ra=true rcode=0 qd=1 an=17 ns=0 ar=0
답     google.com TXT ttl=287 "v=spf1 include:_spf.google.com ~all"
(답 17개 중 하나만 옮김)
```

UDP 응답은 플래그 `83 80`(TC 켜짐)에 답 0개였습니다. 서버는 답을 하나도 담지 않고 "잘렸으니 TCP 로 다시 물어라"만 알렸습니다. TCP 로는 질의 28바이트 앞에 `00 1c` 를 붙여 보냈고, 응답은 `04 98` 곧 1176바이트에 답 17개였습니다.[^rfc1035-422] 17개 답의 이름은 모두 `c0 0c` 포인터였습니다.

학습자는 hex 덤프에서 2바이트를 찾지 못했습니다. `QueryTCP` 가 길이를 먼저 읽어 떼어 낸 뒤 본문만 돌려주므로 프로그램 덤프에는 없고 머리 줄에만 값을 적습니다. 선로 위의 `001c a150 …` 은 TCP 세그먼트 캡처를 붙이지 않아 확인하지 못했습니다(미실행).

TXT 레코드가 무엇에 쓰이는지도 학습자가 물었습니다. 17개는 둘로 나뉩니다. `google-site-verification=…`·`facebook-domain-verification=…` 처럼 외부 서비스가 도메인 소유를 확인하려고 넣게 한 토큰과, `v=spf1 …` 처럼 이 도메인 이름으로 메일을 보낼 수 있는 서버를 알리는 SPF 정책입니다.[^rfc7208]



## 4. 실험 5 - 손실 속에서 같은 ID 로 다시 보낸다

> UDP 는 사라진 질의를 알려 주지 않으므로 클라이언트가 시간을 재고 다시 보냅니다. 손실을 걸고 재시도가 몇 번 일어나는지, 왜 같은 ID 를 쓰는지 봤습니다.

```bash
sudo tc qdisc add dev eth0 root netem loss 50%
for i in 1 2 3 4 5; do ./bin/gonet-linux dns -timeout 500ms -attempts 5 example.com | tail -1; done
sudo tc qdisc del dev eth0 root
```

```text
udp 시도 5 번, 짝이 맞지 않아 버린 데이터그램 0 개
udp 시도 1 번, 짝이 맞지 않아 버린 데이터그램 0 개
udp 시도 1 번, 짝이 맞지 않아 버린 데이터그램 0 개
udp 시도 1 번, 짝이 맞지 않아 버린 데이터그램 0 개
udp 시도 3 번, 짝이 맞지 않아 버린 데이터그램 0 개
```

학습자는 숫자가 들쭉날쭉해 카운팅 오류를 의심했습니다. 다섯 줄은 서로 다른 질의 다섯 번이고, 숫자는 그 질의가 답을 받기까지 보낸 횟수입니다. 시간 초과 에러 줄이 없으니 다섯 번 모두 결국 답을 받았습니다.

첫 시도 성공이 셋인 이유는 손실을 건 자리에 있습니다. `root` 에 건 netem 은 장치에서 나가는 패킷에만 걸립니다.[^netem] `eth0` 에서는 질의만 50% 로 사라지고 응답은 그대로 옵니다. 그래서 시도 한 번의 성공 확률이 50% 입니다. [02-03](./02-03.UDP%20%EC%8B%A4%EC%8A%B5%20%EA%B8%B0%EB%A1%9D%20-%20%EA%B2%BD%EA%B3%84%C2%B7%EC%9E%98%EB%A6%BC%C2%B7%EC%86%8C%EC%BC%93%C2%B7netem%20%EC%86%90%EC%8B%A4%EA%B3%BC%20%EC%88%9C%EC%84%9C.md) 에서는 `lo` 에 걸었습니다. `lo` 는 가는 길과 오는 길이 같은 장치라 두 방향이 모두 떨어졌습니다.

`queryUDP` 는 시간이 초과되면 새 ID 를 뽑지 않고 같은 ID 로 다시 보냅니다. 학습자의 첫 답은 "몇 번 시도했는지 알려고"였습니다. 시도 횟수는 코드의 변수가 따로 세므로 어긋났습니다. 질의는 도착했는데 응답이 늦는 경우를 힌트로 받은 뒤에는 이렇게 답했습니다. "앞서 보낸 질의의 응답이 늦게 와도 받고, 그 뒤 것은 버리면 된다." 새 ID 를 썼다면 늦은 첫 응답은 ID 가 맞지 않아 버려지고 두 번째 응답을 또 기다려야 합니다.

짝이 맞는 응답을 받으면 `queryUDP` 가 돌아오며 `defer conn.Close()` 로 소켓을 닫습니다. 그 뒤에 오는 응답은 받을 소켓이 없는 포트로 온 데이터그램이라 커널이 버리고 ICMP port unreachable 을 돌려보냅니다. [04-01](./04-01.%EB%AC%B4%EC%9D%91%EB%8B%B5%EC%9D%80%20%EC%A6%9D%EA%B1%B0%EA%B0%80%20%EC%95%84%EB%8B%88%EB%8B%A4%20-%20CONNECT%C2%B7SYN%C2%B7UDP%20%ED%8F%AC%ED%8A%B8%20%EC%8A%A4%EC%BA%94.md) §2 의 "소켓이 없으면 UDP 는 ICMP 로 답한다"가 여기서도 일어납니다.
