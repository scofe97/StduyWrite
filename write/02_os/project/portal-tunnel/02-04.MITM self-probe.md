# MITM self-probe

---

> 릴레이의 악의적인 TLS 가로채기(종단 후 재암호화)를 런타임에 능동적으로 감지하는 자가 프로브 메커니즘과 TLS exporter의 검증 원리를 다룹니다.



## 릴레이의 TLS 종단 의혹과 TLS Exporter

> 릴레이가 패스스루 약속을 어기고 세션을 중간에서 가로채면 같은 암호학적 비밀에서 도출되는 TLS 키 재료 추출기 값이 어긋납니다.

터널 에이전트와 외부 브라우저는 릴레이를 거쳐 종단간 암호화 통신을 한다고 가정합니다. 그런데 릴레이 서버는 네트워크 중간에서 패킷을 직접 전달하는 물리적 위치에 있습니다. 악의적인 릴레이 운영자가 자체 인증서를 끼워 넣어 클라이언트 연결을 가로채는 상황을 가정해 봅니다. 릴레이가 앞뒤로 별도의 TLS 연결을 맺고 평문을 엿보거나 변조하는 중간자 공격(MITM)을 시도할 때 터널 에이전트는 이를 어떻게 알아차릴 수 있을까요?

수신된 HTTP 평문 데이터나 TCP 페이로드만 보아서는 중간에서 재암호화가 일어났는지 판별할 수 없습니다. 터널이 받는 바이트 스트림은 겉보기에 정상적인 요청과 똑같기 때문입니다.

표준 TLS는 이 문제를 풀 수단으로 **키 재료 추출기**(TLS Exporter) 규약을 제공합니다. TLS 1.2는 RFC 5705, TLS 1.3은 RFC 8446 §7.5에 정의되어 있습니다. TLS 핸드셰이크가 성공하면 양 끝단(클라이언트와 서버)은 동일한 마스터 비밀을 공유합니다. Exporter 인터페이스는 이 비밀과 애플리케이션 식별 라벨, 컨텍스트 값, 원하는 바이트 길이를 입력받아 의사난수 바이트열을 도출합니다.

동일한 TLS 세션을 공유하는 양 끝단은 같은 마스터 비밀과 라벨을 입력받아 결정론적인 HKDF 도출(RFC 8446 §7.5)을 거치므로 언제나 같은 바이트열을 추출합니다. 반면 중간에서 릴레이가 연결을 종단하고 재암호화했다면 클라이언트와 릴레이 사이의 세션과 릴레이와 터널 사이의 세션은 독립적인 Diffie-Hellman 키 교환을 거쳐 서로 다른 비밀을 가집니다. 두 세션에서 각각 추출한 32바이트 Exporter 값이 우연히 일치할 확률은 암호학적으로 무시할 수 있을 만큼 극히 희박합니다.

Go 언어 표준 라이브러리 `crypto/tls`는 `tls.ConnectionState.ExportKeyingMaterial` 메서드를 제공합니다. 포털 터널은 소스코드 `sdk/mitm.go:35-37`에서 이를 추상화한 `keyingMaterialExporter` 인터페이스를 선언합니다.

```go
type keyingMaterialExporter interface {
	ExportKeyingMaterial(label string, context []byte, length int) ([]byte, error)
}
```

포털 터널의 커스텀 TLS 스택은 `keyless_tls` 패키지입니다. 이 패키지의 연결은 RFC 8446 §7.5를 직접 만족해 이 인터페이스를 구현합니다. Go 표준 `crypto/tls.Conn`은 내부 콜백 필드가 비공개(unexported)라서 외부에서 직접 채울 수 없습니다. 그래서 `sdk/mitm.go:44-55`의 `probeExporter` 함수가 연결 타입을 판별해 `ConnectionState().ExportKeyingMaterial`을 호출하도록 분기합니다.

## 자가 프로브의 발화와 수신 대조 흐름

> 터널이 자기 공개 도메인으로 직접 시험 연결을 걸고 양 끝단에서 32바이트 키 재료를 추출하여 패스스루 여부를 대조합니다.

외부 사용자의 연결에 임의의 시험용 암호 데이터를 주입하면 사용자 웹 트래픽이 손상됩니다. 그래서 터널 에이전트가 스스로 클라이언트 역할을 맡아야 합니다. 릴레이를 거쳐 자기 자신에게 돌아오는 가상 연결을 시험하면 일반 사용자 트래픽에는 영향을 주지 않습니다. 이것이 포털 터널의 **중간자 자가 점검**(MITM Self-Probe)입니다.

주요 상수는 `sdk/mitm.go:57-65`에 선언되어 있습니다.

| 상수 이름 | 설정값 | 코드 위치 | 주 목적 |
|---|---|---|---|
| `mitmProbeExporterLabel` | `"Portal-MITM-Probe-v1"` | `sdk/mitm.go:58` | 키 재료 도출용 전용 라벨 문자열 |
| `mitmProbePeekTimeout` | `100 * time.Millisecond` | `sdk/mitm.go:59` | 수신 측 16바이트 논스 엿보기 타임아웃 |
| `mitmProbePaddingMin` | `96` | `sdk/mitm.go:60` | 프로브 프레임 최소 난수 패딩 바이트 |
| `mitmProbePaddingMax` | `320` | `sdk/mitm.go:61` | 프로브 프레임 최대 난수 패딩 바이트 |
| `defaultMITMProbeCooldown` | `30 * time.Second` | `sdk/mitm.go:63` | 연속 프로브 실행 방지 쿨다운 시간 |
| `defaultMITMProbeTimeout` | `30 * time.Second` | `sdk/mitm.go:64` | 프로브 연결 및 핸드셰이크 전체 제한 시간 |

프로브를 상시 보내지는 않습니다. `sdk/mitm.go:254-290`의 `maybeStart`가 네 가지 조건을 검사합니다.

1. `responderCapable`이 참이어야 합니다. 테넌트 TLS 스택이 Exporter를 지원하지 않으면 비교 자체가 불가능합니다.
2. 정적 캐시(`l.cache != nil`)가 비어 있어야 합니다. 정적 캐시 모드는 릴레이가 정적 파일을 서빙하도록 TLS 종단을 명시적으로 허용하는 모드(`sdk/mitm.go:263`)라서 프로브를 비활성화합니다.
3. 리스너가 종료 채널(`<-l.doneCh`)을 받지 않은 활성 상태여야 합니다.
4. 이미 실행 중인 프로브가 없어야 하고(`!m.inFlight`) 마지막 성공 프로브 이후 30초 쿨다운(`defaultMITMProbeCooldown`)이 지나야 합니다.

프로브를 트리거하는 것은 실제 트래픽입니다. `sdk/listener.go:456`은 연결 수락 시 소켓을 `mitmProbeConn`(`sdk/mitm.go:451-483`)으로 감쌉니다. 외부 클라이언트가 유입되어 첫 번째 읽기(`Read`) 또는 쓰기(`Write`)가 발생할 때 `startOnce.Do`로 `maybeStart`를 백그라운드에서 호출합니다.

조건을 통과하면 백그라운드에서 `probeTLSPassthrough`(`sdk/mitm.go:125-231`)가 동작합니다. 먼저 암호학적 난수로 16바이트 논스(`mitmProbeNonce`)를 생성하고 릴레이로 TCP 연결을 수립합니다.

TCP 연결이 맺어지면 TLS 핸드셰이크 전에 `m.reserveProbe(nonce)`를 호출해 논스를 등록합니다 (`sdk/mitm.go:189`). 역방향 수신 리스너는 핸드셰이크 직후 연결을 수락해 패킷을 읽습니다. 논스를 미리 등록하지 않으면 이 읽기가 클라이언트 측의 Exporter 계산보다 앞서는 경합이 생길 수 있습니다 (`sdk/mitm.go:184-188`).

핸드셰이크가 끝나면 클라이언트 측에서 32바이트 Exporter 값을 도출합니다 (`sdk/mitm.go:196`). 이 값을 `m.attachExpected(nonce, expected)`로 예약 엔트리에 연결합니다. 이어 96바이트에서 320바이트 사이의 무작위 패딩을 생성해 `[16바이트 nonce] + [패딩]` 형태의 프레임을 만들고 TLS 스트림으로 전송합니다.

패딩을 붙이는 것은 릴레이가 고정된 크기의 프로브 패킷 메타데이터를 식별하지 못하게 하려는 것입니다. 릴레이가 16바이트 크기만 보고 프로브 연결을 눈치채면 그 연결만 정직하게 통과시키고 실제 사용자 트래픽만 가로챌 수 있는데, 패딩은 이런 기만을 억제합니다. 다만 공식 문서 `security-model/+page.md:188-190`에서 밝히듯 난수 패딩이 프로브와 일반 트래픽의 완전한 구별 불가능성을 보장하는 것은 아닙니다.

릴레이를 거쳐 돌아온 연결은 터널 리스너의 `maybeHandleConn`(`sdk/mitm.go:348-397`)이 판별합니다. 100밀리초 이내에 앞부분 16바이트를 엿봅니다(`reader.Peek(16)`). 읽은 바이트가 대기 중인 논스와 다르면 일반 사용자 트래픽이므로 버퍼된 리더와 함께 상위 애플리케이션으로 넘깁니다.

등록된 논스와 일치하면 프로브 연결로 확정합니다. 수신 측도 똑같이 32바이트 Exporter 값을 추출하고 `m.completeProbe(nonce, actual)`를 호출해 기대값과 일치하는지 비교합니다. 대조를 마친 프로브 소켓은 즉시 닫히며 상위 애플리케이션에는 노출되지 않습니다.

![중간자 자가 점검(MITM Self-Probe) 시퀀스](_assets/02-04-probe.svg)

위 시퀀스 도식은 정직한 릴레이와 악의적인 릴레이가 프로브를 처리하는 경로를 위아래 두 경우로 나눠 대조합니다. 상단의 정직한 릴레이는 암호화 패킷을 그대로 전달하므로 클라이언트와 서버가 단일 TLS 1.3 세션을 공유하고 동일한 32바이트 키 재료를 도출합니다. 하단의 악의적인 릴레이는 세션을 중간에서 종단하고 재암호화하므로 세션 A와 세션 B의 암호학적 비밀이 갈라집니다. 양 끝단의 키 재료가 어긋나므로 릴레이가 프로브 연결을 종단하면 무단 감청이 곧바로 적발됩니다.



## 판정 결과 기록과 릴레이 차단 정책

> 단순 통신 장애와 악의적인 암호학적 불일치를 분리하여 처리하며 차단 옵션 활성화 시 해당 릴레이를 즉시 격리합니다.

프로브가 끝나면 `sdk/mitm.go:292-346`의 `logResult` 메서드가 결과를 세 가지 유형으로 나누어 처리합니다.

```go
switch {
case closed:
	return
case err != nil:
	// 에러 처리 및 경고 로그
case report.Reason == types.MITMProbeReasonProbeTimeout:
	// 타임아웃 경고 로그
case report.Detected:
	// MITM 의혹 적발 및 차단 처리
default:
	// 검증 통과 디버그 로그
}
```

첫 번째 유형은 타임아웃(`types.MITMProbeReasonProbeTimeout`) 또는 일시적 네트워크 장애입니다. 패킷 유실이나 지연은 중간자 공격의 결정적 증거가 될 수 없습니다. 그래서 공식 보안 모델(`docs/src/routes/security-model/+page.md:182-183`)에 명시된 대로 경고 로그(`log.Warn()`)만 기록하고 릴레이를 차단하지 않습니다.

정상 통과(`!report.Detected`)라면 디버그 로그(`log.Debug()`, `"tls passthrough self-probe passed"`)를 남기고 다음 30초 쿨다운 타이머를 작동시킵니다.

Exporter 불일치가 적발된 경우(`report.Detected`)에는 릴레이의 무단 TLS 종단 의혹을 경고 로그로 기록합니다. 이때 `--ban-mitm` (환경 변수 `BAN_MITM`) 플래그가 설정되어 있다면 터널은 해당 릴레이를 격리합니다 (`sdk/mitm.go:332-336`).

터널 리스너는 `RelayFailed` 상태와 `RelayFailureMITM` 실패 코드를 발행하고 소켓을 즉시 닫습니다 (`l.Close()`). 이 조치로 현재 노출(Exposure) 범위 안에서 해당 릴레이와의 역방향 연결이 모두 종료됩니다.

동적 릴레이 탐색(Discovery)이 활성화되어 있다면 격리 범위가 탐색 풀 전체로 넓어집니다. SDK의 `Exposure`는 `RelayFailureMITM`을 디스커버리 전용 실패 유형인 `discovery.FailureMITM`으로 변환해 보고합니다 (`sdk/expose.go:689-690`). 디스커버리 컨트롤러(`portal/discovery/controller.go:78-79`)는 `c.relaySet.BanRelayURL(relayURL)`을 호출해 해당 릴레이를 영구 차단 목록에 등록합니다.

일반 런타임 오류는 일시적 백오프 후 재시도 기회를 얻지만 MITM 차단에는 백오프 유효기간이 없습니다. 주기적 새로고침이나 재탐색이 일어나도 배제 상태가 영구히 유지됩니다 (`security-model/+page.md:179-181`). 사용자가 `AddRelay()`를 수동 호출하기 전까지 복구되지 않습니다. 다만 이 차단 기록은 메모리 상의 상태이므로 프로세스가 재시작되면 초기화됩니다.

터널을 기동할 때도 엄격한 방어 검사가 동작합니다. 사용자가 `--ban-mitm`을 켰는데 테넌트 TLS 스택이 Exporter를 지원하지 않으면 `sdk/listener.go:1145`(`ensureMITMProbeSupport`, `sdk/mitm_test.go:193-233`)에서 기동이 거부됩니다. 정적 캐시 모드(`--cache`)와 함께 지정한 경우에도 기동 단계(`sdk/expose.go:227`, `cmd/portal-tunnel/tunnel/runtime.go:103`)에서 에러를 내며 종료됩니다. 검증할 수 없는 보호를 약속하지 않으려는 설계입니다.



## 표본 검증의 본질적 한계와 적응형 회피

> 주기적 표본 검사 방식은 다른 연결의 무결성을 증명하지 못하며 지능적인 릴레이의 선별적 감청을 완벽히 차단하기 어렵습니다.

자가 프로브가 성공했다고 해서 릴레이가 앞으로 중계할 모든 사용자 트래픽을 정직하게 다룬다고 확신할 수는 없습니다. 공식 보안 모델 문서(`docs/src/routes/security-model/+page.md:185-201`)와 오픈소스 이슈 토론에서 확인된 주요 한계는 다음과 같습니다.

### 표본 연결 검증의 국소성

프로브의 성공은 방금 실행된 그 단 하나의 표본 연결이 암호학적으로 통과했다는 증거일 뿐입니다. 실제 사용자 트래픽은 프로브 통과를 기다리지 않고 비동기로 처리됩니다. 그래서 선택적 중간자 공격(Selective MITM)은 즉시 감지하기 어렵습니다. 릴레이가 대부분의 일반 사용자 연결은 복호화하면서 간헐적으로 유입되는 연결만 그대로 통과시키는 공격입니다.

### 적응형 릴레이 회피 (열린 이슈 #645)

오픈소스 프로젝트의 열린 이슈 #645("adaptive relay evasion")는 악의적인 릴레이가 프로브 연결의 특성을 학습하여 회피할 가능성을 제기합니다.

프레임을 통과시키는 릴레이는 TLS 암호문만 보므로 복호화 전에는 내부 페이로드 구조를 볼 수 없습니다. 하지만 이슈 #645가 지적하듯 릴레이는 종단 여부를 결정하기 전에 에이전트 출발지 IP, ClientHello 핑거프린트, 트래픽 유입 직후 타이밍과 빈도, 난수 패딩에도 불구하고 노출되는 초기 레코드 크기 등의 외부 메타데이터를 관찰할 수 있습니다. 릴레이가 이러한 메타데이터를 학습하면 프로브 연결만 정상 패스스루하고 일반 트래픽만 가로챌 수 있습니다. 이 적응형 회피가 구조적 한계로 남습니다.

### 임대당 백그라운드 프로브 부하 관리 (열린 이슈 #647)

열린 이슈 #647("bounded background probes per lease")은 능동적 백그라운드 프로브 추가와 부하 관리를 제안합니다.

현재 구현에서는 새로 수락된 연결의 첫 읽기나 쓰기 시점에만 `maybeStart`가 호출됩니다(`sdk/mitm.go:254-290, 464-482`). 프로브는 동시에 하나만 실행되고 성공 후 30초 쿨다운을 두므로 무제한 재발송은 아닙니다. 하지만 방문자 유입이 없거나 장기 연결만 유지되는 유휴 노출 상태에서는 프로브가 다시 돌지 않아 점검 사각지대가 남습니다.

이슈 #647은 이를 보완할 방안으로 임대마다 백그라운드 워커를 두자고 제안합니다. 워커가 준비 완료 시점에 첫 프로브를 보내고 이후 평균 45초·상한 120초의 지수 분포 간격과 토큰 버킷(버스트 3)으로 능동 프로브를 추가하는 방식입니다.

### 환경적 제약

브라우저 및 WASM 환경에서는 운영체제 수준의 네이티브 소켓 기반 자가 프로브를 실행할 수 없어 이 옵션을 요청할 수 없습니다 (`security-model/+page.md:194-195`).



## 리뷰 노트

> 소스 코드와 공식 문서를 대조하며 확인한 주의점과 개선 검토 사항입니다.

- **Peek 타임아웃 100ms와 비정상 프레임 유입 추정 (`sdk/mitm.go:59, 367`)**: `maybeHandleConn`은 16바이트 논스 확인에 100ms 데드라인을 둡니다. 클라이언트는 Finished 직후 프레임을 바로 쓰므로(`sdk/mitm.go:191-216`) 100ms 안에 오지 않을 가능성은 드뭅니다. 하지만 극단적인 WAN 지연이 발생하면 프로브 연결임에도 일반 연결(`wrapBufferedConn`)로 오인되어 상위 핸들러로 전달될 수 있습니다. 이때 상위 애플리케이션이 HTTP 서버라면 규격에 맞지 않는 바이트열로 인해 400 Bad Request 등의 에러를 낼 수 있습니다. 프로브 클라이언트 쪽은 30초 타임아웃 경고를 유발할 것으로 추정됩니다.
- **프로브 완료 직후 즉시 연결 폐쇄와 TCP RST 우려 (`sdk/mitm.go:383`)**: `maybeHandleConn`은 논스 매칭과 Exporter 계산을 마친 직후 `defer conn.Close()`로 연결을 즉시 닫습니다. 프로브 클라이언트가 아직 패딩을 마저 전송 중이거나 소켓 버퍼에 잔여 데이터가 남아 있을 때 즉시 소켓을 닫으면 TCP 연결이 FIN이 아닌 RST로 끊어질 수 있습니다. 그러면 클라이언트 측에 비정상적인 전송 오류가 생길 수 있으므로 그레이스풀 셧다운 점검이 필요합니다.
- **미무장 상태의 fail-closed 검증 (`sdk/mitm.go:189, 200`, `sdk/mitm_test.go:60`)**: 논스 예약은 TCP 연결 직후 일어나고 `attachExpected`는 핸드셰이크 후에 호출됩니다. 정상 경로에서는 클라이언트가 `attachExpected`(:200)를 마친 뒤에야 논스 프레임을 쓰고(:216), 수신 측은 그 난수 논스를 읽어야만 `completeProbe`(:395)를 호출하므로 인과 순서가 보장되어 레이스가 일어나지 않습니다. 미무장 테스트는 레이스 증거가 아니라 기대값이 채워지지 않은 상태에서 프로브가 완료되더라도 통과되지 않고 불일치로 처리되도록 강제하는 fail-closed 검증입니다.



## 검증과 복습

> 이 문서에서 배운 핵심 동작 규약을 세 가지 질문으로 스스로 확인합니다.

1. **질문 1**: 릴레이가 클라이언트와의 연결을 중간에서 가로채 종단(MITM)하고 터널과 새 TLS 연결을 맺었을 때, 터널 클라이언트와 수신 리스너가 호출한 TLS Exporter 값은 왜 암호학적으로 일치할 수 없습니까?
2. **질문 2**: 터널 에이전트는 프로브 프레임에 왜 96~320바이트의 무작위 패딩을 붙입니까? 그리고 논스 예약(`reserveProbe`)을 TLS 핸드셰이크 전에 미리 수행하는 이유는 무엇입니까?
3. **질문 3**: 프로브 타임아웃과 Exporter 불일치 발생 시 `--ban-mitm` 옵션의 대응 동작은 어떻게 다릅니까? 그리고 discovery 컨트롤러의 영구 차단 동작은 어떻게 이어집니까?



## 정답 (자답 후 펼치기)

> 위 세 가지 질문에 대한 해답과 코드 근거입니다.

1. **정답 1**: RFC 8446 §7.5(TLS 1.3) 규약에 따라 Exporter 값은 해당 TLS 세션의 `exporter_master_secret`에서 결정론적 HKDF로 도출되기 때문입니다. 릴레이가 중간에서 종단 및 재암호화하면 앞뒤 두 세션은 독립적인 키 교환을 거쳐 서로 다른 마스터 비밀을 갖게 됩니다. 동일한 라벨(`"Portal-MITM-Probe-v1"`)과 길이를 넣더라도 서로 다른 비밀에서 유도된 의사난수 바이트열이 일치할 확률은 암호학적으로 무시할 수 있을 만큼 낮습니다.
2. **정답 2**: 무작위 패딩을 붙이는 것은 악의적인 릴레이가 패킷 크기 메타데이터로 16바이트 프로브 프레임을 쉽게 식별하지 못하게 하려는 것입니다. 논스를 TCP 연결 직후 예약해 두면 역방향 리스너의 수락 속도가 클라이언트의 Exporter 계산보다 앞서는 경합(Race)을 막을 수 있습니다 (`sdk/mitm.go:184-188`).
3. **정답 3**: 타임아웃은 일시적인 네트워크 지연이나 유실일 수 있으므로 `logResult`(`sdk/mitm.go:319-324`)에서 경고 로그만 남기고 릴레이를 차단하지 않습니다. 반면 Exporter 불일치가 적발되면 `--ban-mitm` 설정 시 리스너를 즉시 닫아(`l.Close()`) 역방향 연결을 종료합니다. discovery 컨트롤러(`portal/discovery/controller.go:78-79`)에도 `FailureMITM`을 보고해 인메모리 릴레이 집합에서 해당 릴레이 URL을 영구 차단(`c.relaySet.BanRelayURL`)합니다.
