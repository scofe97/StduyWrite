# 접근 요청 하나를 예·아니오로 바꾸는 법 — 주체·객체·접근과 ACL·capability

---

> 파일 하나를 여는 요청에 대해 운영체제는 허락 아니면 거절로 답해야 합니다. 이 편은 그 판정에 쓰는 두 자료구조, 객체에 붙은 목록(ACL)과 주체가 든 열쇠(capability)를 비교하고, 실제 리눅스가 둘을 어떻게 겹쳐 쓰는지를 다룹니다.

## 핵심 요약

> 접근 통제는 "누가 무엇을 어떻게 해도 되는가"를 요청마다 예·아니오로 바꾸는 일이며, 그 답을 객체 쪽 목록에서 찾으면 ACL, 주체 쪽 열쇠에서 찾으면 capability 입니다.

ACL 은 누가 이 파일에 접근할 수 있는지를 한곳에서 보여 줍니다. capability 는 이 프로세스가 무엇에 접근할 수 있는지를 한곳에서 보여 줍니다. 한쪽을 묻는 질문은 싸고 반대쪽을 묻는 질문은 모든 목록을 훑어야 해서 비쌉니다. 리눅스는 파일을 열 때 ACL 로 검사합니다. 열린 뒤에는 프로세스가 쥔 파일 디스크립터가 capability 처럼 작동해서 두 약점을 서로 가립니다.[^ver]



## 학습 목표

이 내용을 읽고 나면:

1. 접근 통제의 세 요소(주체·객체·접근)와 참조 모니터, 완전 중재가 무엇인지 설명할 수 있습니다.
2. 유닉스 아홉 비트가 ACL 을 어떻게 줄였고 무엇을 포기했는지 설명할 수 있습니다.
3. capability 가 위조 불가능해야 하는 이유와 커널이 그것을 보관하는 이유를 설명할 수 있습니다.
4. ACL 과 capability 가 각각 쉬운 질문과 어려운 질문을 짚을 수 있습니다.
5. 리눅스에서 `open()` 한 번이 ACL 검사이고 이후 `read()` 가 capability 검사인 이유를 실험으로 설명할 수 있습니다.



## 요청 하나가 판정되는 흐름

> 이 장의 절들은 파일 하나를 여는 요청이 요청·판정·표지 세 단계를 거치는 흐름 위에 놓입니다.

이 장의 모든 절은 `open("/data/foo", O_RDWR)` 한 건이 허락되기까지의 흐름 위에 놓입니다. 단계는 셋입니다. 프로세스가 시스템 콜로 요청합니다. 운영체제가 판정합니다. 허락이면 이후 접근을 싸게 하는 표지를 남깁니다.

| 단계 | 주체 | 받치는 개념 | 다루는 절 |
|------|------|-------------|-----------|
| 1 요청 | 프로세스(사용자 X 소속) | 주체·객체·접근 | §1 |
| 2 판정 | 커널의 참조 모니터 | ACL 또는 capability | §2, §3 |
| 3 표지 | 커널(프로세스 제어 블록) | 열린 파일이 남기는 capability 꼴 구조 | §4 |

이 편은 단계 2 의 두 방식을 차례로 다룹니다. 목록을 찾는 방식이 §2, 열쇠를 찾는 방식이 §3 입니다. 둘을 겹쳐 쓰는 실제 리눅스가 §4 입니다.

흐름 위치: 위 표의 1·2·3 단계를 아래 번호 절이 맡습니다.



## 1. 시스템 콜마다 필요한 예·아니오 — 접근 통제의 문제

> 사용자 X 의 프로세스가 `/data/foo` 를 읽고 쓰려 할 때 운영체제는 시스템 콜이 커널로 들어온 그 자리에서 허락 여부를 가려야 합니다. 이 판정은 빠르고 틀리면 안 됩니다.

흐름 위치: 1 요청 · 받치는 개념 — 주체·객체·접근

### 주체·객체·접근과 참조 모니터

접근 통제는 세 요소로 말합니다. **주체**는 접근하려는 쪽이고 사용자나 프로세스가 해당합니다. **객체**는 접근당하는 쪽이며 파일이나 장치입니다. **접근**은 읽기·쓰기 같은 방식입니다. 한 건의 판정은 "이 주체가 이 객체에 이 방식으로 접근해도 되는가"라는 질문입니다. 이를 가리는 일을 **인가**라고 합니다. 주체가 누구인지 확인하는 인증은 앞 장의 몫이며 이 장의 모든 방식은 인증이 끝났다고 전제합니다.

이 판정 알고리즘을 구현한 코드를 **참조 모니터**라고 합니다. 틀리면 엉뚱한 사람에게 문이 열립니다. 느리면 모든 시스템 콜이 그만큼 느려집니다. 보안 원칙은 요청이 올 때마다 검사하는 **완전 중재**를 요구합니다. 그러나 매번 검사하면 비용이 들어서 둘 사이를 맞춰야 합니다.

### 검사를 건너뛰어도 되는 경우와 그 한계

검사 비용을 없애는 한 가지 길은 객체를 처음부터 한 주체의 것으로 만드는 것입니다. 가상 메모리가 그 예입니다. 프로세스는 자기 가상 주소 공간을 쓸 때마다 운영체제의 접근 통제를 거치지 않습니다. 모든 메모리 참조마다 검사하면 시스템이 터무니없이 느려지기 때문입니다. 장치도 같은 방식입니다. 프로세스가 가상 장치를 받으면, 첫 허락 뒤에는 GPU 메모리에 쓰거나 명령을 보내는 일에 운영체제가 끼어들지 않습니다.

이것은 비용을 없앤 것이 아니라 아래로 미룬 것입니다. 가상화는 운영체제가 만든 환상이어서 실제로는 메모리와 장치를 모두가 나눠 쓰고, 그 환상이 깨지지 않게 막는 일은 여전히 운영체제의 몫입니다. 그래서 파일처럼 여럿이 공유하는 객체에는 결국 일반적인 판정 방법이 필요합니다. 컴퓨터 과학이 내놓은 방법은 둘입니다. 하나는 접근 통제 목록(ACL), 다른 하나는 capability 입니다.

회원제 클럽에 빗대면 쉽습니다. 문 앞의 경비원이 명단을 보고 들이면 ACL 이고, 회원에게 열쇠를 나눠 주고 자물쇠가 열리면 들이면 capability 입니다. 어느 쪽이든 입구에서 신원을 먼저 확인했다는 전제가 있습니다.



## 2. 객체에 목록을 붙이는 방식 — ACL 과 유닉스 아홉 비트

> ACL 은 객체마다 허용된 주체와 접근 방식을 목록으로 붙이는 방식이어서, 파일을 열 때 그 파일의 목록만 찾으면 됩니다. 목록이 어디에 얼마나 크게 저장되는가가 설계의 핵심입니다.

흐름 위치: 2 판정 · 받치는 개념 — ACL

### 목록은 파일마다 하나

한 시스템의 모든 파일에 대한 허용을 한 목록에 적으면 관리할 수 없게 되므로, ACL 은 파일마다 따로 둡니다. 그러면 목록이 짧아지고 검사도 빨라집니다. `open()` 이 커널로 들어오면 운영체제는 프로세스 제어 블록에서 이 프로세스를 소유한 사용자를 알아내고, `/data/foo` 의 ACL 을 저장 장치에서 가져와 그 사용자를 찾습니다. 없으면 거절, 있으면 그 항목이 요청한 접근 방식을 허락하는지를 봅니다. 읽기만 허락된 사용자가 쓰기로 열려 하면 오류가 돌아갑니다.

### 얼마나 크고 어디에 두는가

원칙은 단순하지만 구현에는 두 질문이 남습니다.

첫째는 목록을 장치 어디에 두는가입니다. ACL 은 보안 정책 자체여서 영구히 저장해야 합니다. 파일을 열 때마다 다른 곳을 또 읽으면 느려집니다. 그래서 이미 읽는 자리 가까이에 둡니다. 후보는 디렉터리 항목, 아이노드, 파일의 첫 데이터 블록이고 아이노드 안이 가장 낫습니다.

둘째는 목록이 얼마나 큰가입니다. 사용자 ID 와 접근 방식을 그대로 적으면 목록이 사용자 수만큼 커질 수 있습니다. 대부분의 파일은 소유자와 몇 사람만 쓰는데 모든 파일에 최대 크기를 잡아 두면 낭비입니다. 반대로 `ls`·`mv` 같은 실행 파일은 모든 사용자에게 열어 둡니다. 목록을 가변 크기로 만들면 검색 비용과 아이노드 배치가 문제가 됩니다.

### 아홉 비트로 줄인 유닉스의 답

유닉스 초기 설계의 답은 이 목록을 아이노드 안의 아홉 비트로 줄이는 것이었습니다. 저장 장치가 비싸서 파일마다 쓸 수 있는 ACL 이 그 정도뿐이었기 때문입니다. 접근 방식을 읽기·쓰기·실행 셋으로 잡았습니다. 항목은 소유자·그룹·나머지 모두 셋으로 나눴습니다. 그러면 비트가 3×3 이 됩니다. 소유자 ID 와 그룹 ID 는 이미 아이노드에 있습니다. "나머지 모두"는 앞 둘의 여집합이라 따로 표시할 필요가 없습니다. 아이노드는 어차피 읽으므로 추가 읽기가 없습니다. 임의 크기 목록을 훑는 대신 몇 비트에 간단한 논리만 적용하면 답이 나옵니다.

실제로 확인해 보면 이 아홉 비트가 `ls -l` 의 앞부분입니다. Rocky Linux 9 컨테이너에서 소유자가 alice 인 파일을 `rw-r-----` 로 만들면, 그룹도 아니고 소유자도 아닌 bob 은 읽을 수 없습니다.

```bash
stat -c "%A %U:%G %n" /data/foo
su bob -c "cat /data/foo"
```

```bash
-rw-r----- alice:alice /data/foo
cat: /data/foo: Permission denied
```

아홉 비트는 복잡한 공유 관계를 표현하지 못합니다. 그래서 윈도우 같은 시스템은 더 일반적인 ACL 확장을 허용합니다. 리눅스에서는 `setfacl` 로 특정 사용자 한 명에게만 읽기를 더하는 항목을 붙일 수 있습니다(사용법은 [getfacl·setfacl 시트](../../docs/cmd/perm/getfacl%C2%B7setfacl.md)).

```bash
setfacl -m u:bob:r /data/foo
getfacl -p /data/foo
su bob -c "cat /data/foo"
```

```bash
# file: /data/foo
# owner: alice
# group: alice
user::rw-
user:bob:r--
group::r--
mask::r--
other::---

secret
```

항목이 붙은 파일은 `ls -l` 의 권한 문자열 끝에 `+` 가 붙습니다.

```bash
ls -l /data/foo
```

```bash
-rw-r-----+ 1 alice alice 7 Nov 18 05:23 /data/foo
```

### 새 파일의 기본 권한

사람이 모든 파일의 권한을 직접 정할 수는 없으므로 시스템은 기본값을 둡니다. 유닉스·리눅스에서는 `open()` 으로 파일을 만들 때 초기 권한을 지정하고, `umask()` 가 프로세스가 만드는 모든 새 파일에 적용될 마스크를 정합니다. 같은 alice 셸에서 기본 마스크 0022 로 만든 파일과 `umask 077` 뒤에 만든 파일을 비교하면 기본값이 결과를 바로 정한다는 것이 보입니다([umask 시트](../../docs/cmd/perm/umask.md)).

```bash
umask; touch /tmp/u1; ls -l /tmp/u1
umask 077; touch /tmp/u2; ls -l /tmp/u2
```

```bash
0022
-rw-r--r-- 1 alice alice 0 Nov 18 05:23 /tmp/u1
-rw------- 1 alice alice 0 Nov 18 05:23 /tmp/u2
```

사용자는 이 초기 값을 거의 바꾸지 않습니다. 이론적으로 바꿀 수 있는 설정도 실제로는 기본값 그대로 쓰이므로 기본값을 잘 고르는 일이 중요합니다.

### ACL 이 잘하는 질문과 못하는 질문

ACL 에서는 "이 파일에 누가 접근할 수 있는가"를 목록 하나를 보면 답할 수 있습니다. 접근 대상을 바꾸는 일도 그 목록만 고치면 됩니다. 파일을 얻을 수 있으면 접근 통제 정보도 함께 얻어서 분산 시스템에도 이롭습니다.

반대로 "이 사용자가 접근할 수 있는 모든 자원은 무엇인가"를 알려면 시스템의 ACL 을 전부 확인해야 합니다. 분산 환경에서는 사용자 이름이 기계마다 같은 사람을 가리켜야 하는데, 이를 위한 일관된 이름 공간을 유지하기가 어렵습니다. UCLA 의 `remzi` 와 위스콘신의 `remzi` 가 같은 사람이라는 보장이 없으면 엉뚱한 사용자가 접근하게 됩니다.



## 3. 주체가 열쇠를 드는 방식 — capability

> capability 는 객체별로 만든 열쇠를 주체가 지니는 방식이어서, 열쇠가 있다는 사실이 곧 허락의 증거입니다. 그러므로 열쇠를 위조하거나 마음대로 복사하지 못하게 막는 일이 설계의 중심입니다.

흐름 위치: 2 판정 · 받치는 개념 — capability

### 열쇠는 결국 비트

순수한 capability 시스템에는 ACL 이 어디에도 없습니다. 프로세스가 가진 capability 모음이 그 프로세스의 접근 권한 전부입니다. 리눅스나 윈도우는 이렇게 동작하지 않지만 Hydra 같은 운영체제가 이 방식을 기본 통제 장치로 썼습니다. 이 방식의 `open()` 은 두 길 중 하나입니다. 응용이 해당 파일을 여는 capability 를 인자로 내거나 운영체제가 찾아 줍니다. 어느 쪽이든 운영체제는 그 capability 가 읽기·쓰기 열기를 허락하는지만 확인합니다.

capability 도 결국 컴퓨터 안의 비트입니다. 비트에는 두 성질이 있습니다. 누구나 원하는 비트 패턴을 만들 수 있고, 가진 비트는 얼마든지 복사할 수 있습니다. 첫째 성질은 누구나 원하는 capability 를 만들어 스스로에게 접근 권한을 줄 수 있다는 뜻입니다. 둘째 성질은 한번 준 권한을 거둘 수 없다는 뜻입니다. 복사본을 다른 기계에 보관할 수 있기 때문입니다. 이 약점을 가리는 요구가 위조 불가능성입니다.

### 커널이 보관하는 열쇠

흔한 해법은 프로세스가 capability 를 직접 손에 쥐지 못하게 하는 것입니다. 운영체제가 보호된 메모리에 capability 를 두고 프로세스는 시스템 콜로만 다룹니다. 프로세스 A 가 B 에게 `/data/foo` 접근을 주려면 비트 패턴을 보내는 것이 아닙니다. 운영체제에 capability 전달을 요청해야 합니다. 그 자리에서 운영체제가 정책에 맞는지 판정해 거절할 수 있습니다. 구현은 간단합니다. 프로세스마다 이미 있는 프로세스 제어 블록에 커널 메모리의 capability 목록을 가리키는 포인터를 붙입니다.

대안은 암호학으로 보호한 capability 입니다. 충분히 길고 강한 암호로 만든 값은 추측할 수 없어서 사용자 손에 두어도 됩니다. 이 방식은 분산 시스템에서 의미가 있고 [44-02 편의 「서명한 capability 로 권한 증명」](./44-02.%EC%95%94%ED%98%B8%EB%8A%94%20%EC%96%B4%EB%94%94%EC%84%9C%20%EA%B9%A8%EC%A7%80%EA%B3%A0%20OS%20%EB%8A%94%20%EC%96%B4%EB%94%94%EC%97%90%20%EC%95%94%ED%98%B8%EB%A5%BC%20%EC%93%B0%EB%8A%94%EA%B0%80%20%E2%80%94%20%ED%82%A4%20%EC%9C%A0%EC%B6%9C%C2%B7%EC%A0%80%EC%9E%A5%20%EB%8D%B0%EC%9D%B4%ED%84%B0%20%EC%95%94%ED%98%B8%ED%99%94%C2%B7%EC%95%94%ED%98%B8%ED%95%99%EC%A0%81%20capability.md#4-%EC%84%9C%EB%AA%85%ED%95%9C-capability-%EB%A1%9C-%EA%B6%8C%ED%95%9C-%EC%A6%9D%EB%AA%85)에서 다룹니다.

### 쉬운 질문, 어려운 질문, 그리고 최소 권한 프로세스

capability 에서는 "이 주체가 무엇에 접근할 수 있는가"가 쉽습니다. 그 주체의 목록만 보면 되기 때문입니다. 회수는 운영체제가 capability 를 독점하고 있다면 목록에서 지우면 끝이지만, 독점하지 못하면 어렵습니다. 메모리에 올려 둔 capability 는 확인도 쌉니다. 객체를 가리키는 포인터를 담을 수 있어서 포인터를 가졌다는 사실이 곧 구현일 수도 있습니다.

반대로 "이 객체에 접근할 수 있는 주체는 누구인가"는 모든 주체의 목록을 확인해야 해서 비쌉니다. 유닉스 아홉 비트처럼 목록을 짧게 유지하는 방법도 capability 에는 덜 발전했고, 위조를 막으면서 capability 를 만들고 저장하고 찾는 일도 어렵습니다.

capability 의 장점은 권한이 제한된 프로세스를 만들기 쉽다는 점입니다. ACL 에서는 자식 프로세스가 부모의 신원과 권한을 그대로 물려받아, 일부 권한만 주려면 제한된 새 주체를 만들고 ACL 을 여럿 고쳐야 합니다. capability 에서는 부모가 X·Y·Z 를 가졌을 때 자식에게 X 와 Y 만 넘기면 됩니다.

실제로 사용자가 보는 접근 통제는 대개 ACL 이고 capability 는 그 밑에서 널리 쓰입니다. 두 방식의 비교는 다음과 같습니다.

| 질문 | ACL | capability |
|------|-----|------------|
| 이 객체에 누가 접근하는가 | 쉽다: 그 객체의 목록을 본다 | 어렵다: 모든 주체의 목록을 본다 |
| 이 주체가 무엇에 접근하는가 | 어렵다: 모든 목록을 본다 | 쉽다: 그 주체의 목록을 본다 |
| 권한 회수 | 쉽다: 목록을 고친다 | 커널이 독점하면 쉽고 아니면 어렵다 |
| 일부 권한만 가진 자식 | 새 주체와 목록 수정이 필요하다 | 일부 열쇠만 넘기면 된다 |
| 위조 걱정 | 없다 | 막아야 한다 |
| 분산 환경의 걸림돌 | 기계 간 일관된 이름 공간 | 위조 방지를 암호로 해결해야 한다 |



## 4. 열 때는 ACL, 열린 뒤에는 capability — 리눅스의 겹쳐 쓰기

> 리눅스는 `open()` 에서 ACL 을 확인하고, 성공하면 프로세스 제어 블록에 capability 꼴의 구조를 남겨 이후 `read()`·`write()` 는 그 구조만 보게 합니다.

흐름 위치: 3 표지 · 받치는 개념 — 열린 파일이 남기는 capability 꼴 구조

### 한 번 열면 ACL 은 다시 보지 않는다

리눅스에서 `open()` 이 성공하면 파일을 열어 둔 동안 이후 읽기·쓰기 때 ACL 을 다시 보지 않습니다. 대신 이 프로세스가 그 파일을 읽고 쓸 수 있음을 나타내는 capability 에 해당하는 구조가 프로세스에 붙습니다. 파일을 닫으면 이 구조가 지워지고 다시 접근하려면 ACL 을 거치는 `open()` 을 해야 합니다. 이 구조는 포인터의 존재 여부일 뿐이라 검사가 쌉니다. ACL 이 한 번 통과된 뒤에만 만들어지므로 모든 객체의 capability 를 관리하는 부담도 없습니다. 프로세스가 열 수 있는 파일 가운데 실제로 여는 것은 극히 일부여서 규모 문제도 잘 생기지 않습니다.

이 구조의 정체는 파일 디스크립터입니다. 프로세스가 가진 파일 디스크립터 번호는 `/proc/<pid>/fd/` 아래의 링크로 보입니다. 아래 실험은 이 동작을 직접 확인합니다. bob 에게 읽기 ACL 을 준 파일을 bob 의 프로세스가 엽니다. 열려 있는 동안 ACL 에서 bob 을 지운 뒤 읽습니다.

```bash
# 터미널 1: bob 이 열고 2초 뒤에 읽는다 (r.py)
su bob -c "python3 /tmp/r.py"

# 터미널 2(열고 1초 뒤): ACL 에서 bob 을 지운다
setfacl -x u:bob /data/foo
```

```bash
open ok, fd 3
ACL entry for bob removed
read after ACL removed: b'secret\n'
reopen: [Errno 13] Permission denied: '/data/foo'
```

ACL 에서 bob 이 사라졌는데도 이미 열린 디스크립터로는 읽기가 성공했고, 같은 파일을 새로 `open()` 하자 거절되었습니다. 열기 시점에 한 번 한 ACL 판정이 디스크립터라는 열쇠로 남아 있었기 때문입니다.[^fd]

이 구조는 파일에만 쓰이지 않습니다. 유닉스 계열은 장치와 프로세스 간 통신 통로도 파일처럼 다루므로 같은 기법이 그것들에도 적용됩니다.

### 두 방식의 약점을 서로 가린다

이 조합은 두 방식의 대가를 서로 덜어 줍니다. 매 읽기·쓰기에서 ACL 을 찾는 비용은 디스크립터의 존재만 확인하는 비용으로 바뀌고, 모든 객체에 대한 capability 를 미리 관리하는 비용은 열기에 성공한 객체만 만드는 비용으로 바뀝니다. 대가도 있습니다. 위 실험에서 보았듯 열려 있는 동안에는 ACL 을 바꿔도 이미 연 프로세스에 반영되지 않아, 회수가 닫을 때까지 늦춰집니다.



## 결정 치트시트

> 이 편의 판단 기준은 아래 표와 같습니다.

| 상황 | 판단 | 근거 |
|------|------|------|
| 한 객체에 접근할 수 있는 주체를 묻는다 | ACL 이 쉽다 | 그 객체의 목록 하나만 본다 |
| 한 주체가 접근할 수 있는 객체를 묻는다 | capability 가 쉽다 | 그 주체의 목록 하나만 본다 |
| 자식에게 부모 권한의 일부만 주고 싶다 | capability 방식이 맞는다 | 일부 열쇠만 넘기면 된다 |
| 파일마다 권한 목록을 영구 저장한다 | 아이노드 안이나 근처에 둔다 | 이미 읽는 자리라 추가 읽기가 없다 |
| 사용자 한 명에게만 예외 권한을 준다 | 아홉 비트로는 안 되므로 확장 ACL 을 쓴다 | 아홉 비트는 소유자·그룹·나머지 셋만 표현한다 |
| 열려 있는 파일의 접근을 즉시 끊고 싶다 | ACL 변경만으로는 부족하다 | 이미 연 디스크립터는 ACL 을 다시 보지 않는다 |
| capability 를 사용자 손에 두려 한다 | 위조를 막는 암호 값으로 만든다 | 비트는 누구나 만들고 복사한다 |



## 면접 대비

> 이 편에서 물어볼 만한 정의와 핵심 포인트, 질문입니다.

### 한 줄 정의

- 주체·객체·접근: 접근하려는 쪽, 접근당하는 쪽, 접근 방식입니다.
- 참조 모니터: 접근 요청의 허락 여부를 가리는 판정 코드입니다.
- ACL: 객체에 붙어 허용된 주체와 접근 방식을 적은 목록입니다.
- capability: 주체가 지닌, 특정 객체에 대한 접근 권한의 증거입니다.

### 핵심 포인트 세 가지

1. ACL 은 객체별 목록이어서 "누가 접근하나"가 쉽고, capability 는 주체별 열쇠 모음이어서 "무엇에 접근하나"가 쉽습니다.
2. 유닉스 아홉 비트는 아이노드 안의 세 항목으로 ACL 을 줄인 것이고, 공유 관계가 복잡하면 확장 ACL 이 필요합니다.
3. 리눅스는 `open()` 에서 ACL 로 검사하고, 열린 파일 디스크립터가 이후 접근에서 capability 처럼 쓰입니다.

### 자주 묻는 질문

- *리눅스는 ACL 입니까 capability 입니까?* 열 때는 ACL 이고, 열린 뒤 읽기·쓰기는 디스크립터라는 capability 꼴 구조로 확인합니다. 둘이 겹쳐 있습니다.
- *capability 는 왜 커널이 보관해야 합니까?* 비트는 누구나 만들고 복사하므로 프로세스가 직접 쥐면 위조와 무한 복사를 막을 수 없습니다.
- *ACL 에서 한 사용자의 접근을 바꾸려면 어떻게 합니까?* 그 객체의 목록만 고치면 됩니다. 그러나 이미 열린 디스크립터에는 바로 반영되지 않습니다.
- *가상 메모리 접근에 ACL 검사가 없는 이유는 무엇입니까?* 객체가 처음부터 한 프로세스의 것이라 판정할 것이 없고, 매 참조마다 검사하면 시스템이 너무 느려지기 때문입니다.



## 연습 문제

> 1~3번은 본문을 떠올려 답하는 문제이고 4~5번은 직접 돌려 확인하는 문제입니다. 답을 적은 뒤 정답 절과 맞춰 봅니다.

1. 접근 통제에서 주체·객체·접근은 각각 무엇입니까? 참조 모니터는 무엇을 하고, 매번 검사하는 원칙과 비용은 어떻게 충돌합니까?
2. 유닉스가 ACL 을 아홉 비트로 줄일 수 있었던 이유는 무엇입니까? 그 대가로 표현하지 못하게 된 것은 무엇입니까?
3. capability 가 위조 불가능해야 하는 이유는 무엇이고, 일반적인 해법은 무엇입니까?
4. alice 소유 파일에 bob 읽기 ACL 을 주고 bob 이 열어 둔 뒤 ACL 을 지우면 읽기가 되겠습니까? 새로 열기는 어떻게 되겠습니까? 직접 돌려 보십시오.
5. "이 파일에 접근할 수 있는 사용자 목록"과 "bob 이 접근할 수 있는 파일 목록" 중 아홉 비트 ACL 로 싸게 답할 수 있는 쪽은 어느 쪽입니까? 반대쪽은 어떻게 구하겠습니까?



## 정답 (자답 후 펼치기)

### 정답 1

주체는 접근하려는 사용자나 프로세스, 객체는 파일·장치 같은 접근 대상, 접근은 읽기·쓰기 같은 방식입니다. 참조 모니터는 이 셋으로 허락 여부를 판정하는 코드입니다. 완전 중재는 요청마다 검사하라고 요구하지만 검사마다 오버헤드가 붙습니다. 그래서 가상 메모리처럼 객체가 한 주체의 것일 때는 검사를 줄입니다. 그 밖에는 비용과 안전을 저울질해야 합니다.

### 정답 2

파일마다 쓸 수 있는 저장 공간이 아홉 비트 정도였고, 접근 방식을 읽기·쓰기·실행 셋, 항목을 소유자·그룹·나머지 셋으로 줄이면 아홉 비트로 충분했습니다. 소유자와 그룹 ID 는 이미 아이노드에 있고 나머지는 여집합이라 비트가 필요 없습니다. 대가는 특정 사용자 한 명에게만 권한을 주는 것 같은 복잡한 공유 관계를 표현하지 못한다는 점입니다.

### 정답 3

비트는 누구나 어떤 패턴이든 만들 수 있어서, 위조 가능하면 프로세스가 스스로에게 접근 권한을 만들 수 있습니다. 복사도 자유로워 한번 준 권한을 거두기 어렵고 다른 프로세스에 몰래 넘길 수도 있습니다. 일반적인 해법은 capability 를 커널의 보호된 메모리에 두고 프로세스는 시스템 콜을 통해서만 다루게 하는 것입니다. 암호로 보호한 값을 쓰는 방법도 있습니다.

### 정답 4

읽기는 성공하고 새로 여는 것은 거절됩니다. Rocky Linux 9.3 컨테이너(acl 2.4.0)에서 bob 이 연 디스크립터로 `secret` 을 읽었고, `setfacl -x u:bob /data/foo` 뒤의 새 `open()` 은 `Errno 13 Permission denied` 였습니다. ACL 판정은 열 때 한 번 이루어지고 그 결과가 디스크립터에 남기 때문입니다.

### 정답 5

"이 파일에 접근할 수 있는 사용자"는 그 파일의 ACL(아이노드의 비트와 확장 ACL)만 보면 되므로 싸게 답할 수 있습니다. 반대쪽인 "bob 이 접근할 수 있는 파일"은 시스템의 모든 파일의 ACL 을 확인해야 합니다. 객체마다 목록이 따로 있어서 한 주체가 어디에 등장하는지 한곳에서 볼 수 없기 때문입니다.
