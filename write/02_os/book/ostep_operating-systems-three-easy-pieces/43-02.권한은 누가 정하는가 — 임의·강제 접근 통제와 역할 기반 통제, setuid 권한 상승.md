# 권한은 누가 정하는가 — 임의·강제 접근 통제와 역할 기반 통제, setuid 권한 상승

---

> 접근 통제 장치가 아무리 정확해도 그 장치는 받은 정책만 집행합니다. 이 편은 권한을 정하는 주체가 소유자냐 관리 기관이냐(임의·강제), 사람을 직무로 묶는 방법(역할 기반 통제), 권한을 잠깐 빌려 쓰는 방법(setuid)과 그 위험을 다룹니다.

## 핵심 요약

> 접근 통제에는 판정 자료구조(ACL·capability)와 별개로 "권한을 누가 정하는가"라는 축이 있습니다. 소유자가 정하면 임의 통제, 소유자가 바꿀 수 없는 규칙이 있으면 강제 통제입니다.

사람이 많은 조직에서는 개인별 권한 대신 직무(역할)에 권한을 묶는 편이 관리하기 쉽습니다. 사람은 역할을 오가면 됩니다. 리눅스에서 가장 단순한 역할 흉내는 setuid 와 sudo 입니다. 프로그램이 다른 사용자의 권한으로 잠깐 돕니다. 이 장치는 공격자가 가장 먼저 노리는 길이기도 합니다. 접근 통제 장치 자체가 틀려서 생기는 사고는 드물고 정책이 잘못 설계되어서 생기는 사고가 흔합니다.[^ver]



## 학습 목표

이 내용을 읽고 나면:

1. 임의 접근 통제와 강제 접근 통제의 차이를 "누가 권한을 정하는가"로 설명할 수 있습니다.
2. ACL·capability 선택과 임의·강제 선택이 서로 독립인 이유를 설명할 수 있습니다.
3. 역할 기반 통제가 그룹보다 강한 점과 타입 강제가 더하는 것을 설명할 수 있습니다.
4. setuid 와 sudo 가 권한을 빌려 주는 방식과 그 위험을 설명할 수 있습니다.
5. 강제 통제가 없을 때 sudo 로 얻은 역할이 새는 경로를 짚을 수 있습니다.



## 권한이 정해지고 쓰이는 흐름

> 이 편의 절들은 권한을 정하고, 직무로 묶고, 필요할 때 잠깐 올려 쓰는 세 단계 위에 놓입니다.

앞 편이 판정 자료구조를 다뤘다면 이 편은 그 자료에 권한을 적는 쪽을 다룹니다. 단계는 셋입니다. 권한을 정합니다. 사람을 직무로 묶습니다. 필요할 때 잠깐 올려 씁니다.

| 단계 | 주체 | 받치는 개념 | 다루는 절 |
|------|------|-------------|-----------|
| 1 정하기 | 소유자 또는 관리 기관 | 임의·강제 접근 통제 | §1 |
| 2 묶기 | 관리자 | 역할 기반 통제·타입 강제 | §2 |
| 3 빌리기 | 프로그램을 실행하는 사용자 | setuid·sudo·권한 상승 | §3 |

흐름 위치: 위 표의 1·2·3 단계를 아래 번호 절이 맡습니다.



## 1. 권한을 누가 정하는가 — 임의 통제와 강제 통제

> 대부분의 시스템은 소유자가 권한을 정하게 둡니다. 군사 기밀처럼 소유자가 풀 수 없어야 하는 정보에는 관리 기관이 권한을 강제하는 방식이 필요합니다.

흐름 위치: 1 정하기 · 받치는 개념 — 임의·강제 접근 통제

### 소유자의 재량이 정책이 되는 문제

답이 뻔해 보이는 질문입니다. 사용자의 파일은 사용자가, 시스템 자원은 관리자가 권한을 정하면 됩니다. 그런데 정보 보안을 가장 걱정하는 쪽은 이보다 강한 통제를 원하기도 합니다. 일급 기밀을 열람할 수 있는 사람은 그 내용을 직접 쓴 보고서가 아니더라도 다른 사람에게 보여 주면 안 됩니다. 보고서가 그 사람이 만든 파일일 때도 마찬가지입니다. 이 경우 만든 사람이 권한을 정한다는 답은 틀리고, 조직의 보안 책임자가 정해야 하며 사용자가 그 결정을 덮어쓸 수 없어야 합니다.

### 두 방식과 서로 독립이라는 점

흔한 쪽이 **임의 접근 통제**입니다. 거의 누구나 접근할 수 있게 하든 거의 아무도 못 하게 하든 소유자의 재량입니다. 더 엄격한 쪽이 **강제 접근 통제**입니다. 접근 통제 결정의 일부가 권한을 가진 기관에 의해 강제되고 소유자의 바람을 덮어쓸 수 있습니다. 강제 통제 시스템도 임의 요소를 포함할 수 있는데, 그 요소는 강제 통제를 더 조일 수만 있고 풀 수는 없습니다.

어느 쪽을 쓰느냐는 ACL 을 쓰느냐 capability 를 쓰느냐와 무관한 축입니다. 접근 정보를 어떻게 저장하고 다루는가와도 대개 별개입니다. 그래서 ACL 로 강제 통제를 구현할 수도, capability 로 임의 통제를 구현할 수도 있습니다.

| 질문 | 임의 접근 통제 | 강제 접근 통제 |
|------|----------------|----------------|
| 권한은 누가 정하는가 | 객체의 소유자 | 관리 기관 |
| 소유자가 바꿀 수 있는가 | 바꿀 수 있다 | 기관의 규칙을 덮어쓰지 못한다 |
| 임의 요소를 함께 쓸 수 있는가 | 해당 없음 | 쓸 수 있고, 조이는 방향으로만 작동한다 |
| 흔한 정도 | 대부분의 시스템 | 필요한 환경에서만 |

대부분의 사람은 강제 접근 통제를 쓰는 시스템을 만날 일이 없습니다. 필요한 환경에서는 곧 알게 됩니다. 리눅스에서 강제 통제를 구현한 것이 SELinux 이며 그 구조는 [SELinux 문서](../../docs/kernel/01-03.SELinux.md)에서 다룹니다.

### 기본값과 안드로이드의 방식

실무에서 사람이 수십만 개 파일의 권한을 일일이 정할 수는 없으므로 기본값이 중요합니다(새 파일의 기본 권한은 [43-01 §2](./43-01.%EC%A0%91%EA%B7%BC%20%EC%9A%94%EC%B2%AD%20%ED%95%98%EB%82%98%EB%A5%BC%20%EC%98%88%C2%B7%EC%95%84%EB%8B%88%EC%98%A4%EB%A1%9C%20%EB%B0%94%EA%BE%B8%EB%8A%94%20%EB%B2%95%20%E2%80%94%20%EC%A3%BC%EC%B2%B4%C2%B7%EA%B0%9D%EC%B2%B4%C2%B7%EC%A0%91%EA%B7%BC%EA%B3%BC%20ACL%C2%B7capability.md#2-%EA%B0%9D%EC%B2%B4%EC%97%90-%EB%AA%A9%EB%A1%9D%EC%9D%84-%EB%B6%99%EC%9D%B4%EB%8A%94-%EB%B0%A9%EC%8B%9D--acl-%EA%B3%BC-%EC%9C%A0%EB%8B%89%EC%8A%A4-%EC%95%84%ED%99%80-%EB%B9%84%ED%8A%B8) 참고). 설치 패키지도 실행 파일과 설정 파일의 권한을 조심스럽게 정합니다. 경험상 접근 통제를 함부로 건드리면 민감한 정보를 노출하거나, 반대로 조여서 백그라운드 데몬이 멈출 수 있어서 모르면 건드리지 않는 편이 안전합니다.

안드로이드는 앱마다 새 사용자 ID 를 부여해 리눅스의 접근 통제를 앱 단위로 씁니다. 그 위에 미들웨어를 얹어 앱이 요구하는 권한을 설치 때 사용자에게 보여 줍니다. 앱의 권한 라벨은 설치 때 정해지고 이후 사용자가 줄일 수 있습니다. 라벨을 가졌느냐가 곧 자격이라는 점에서 capability 와 닮았습니다. 라벨은 앱 설계 때 정해지는 것이라 강제 통제의 한 형태이기도 합니다. 약점은 사용자가 영향을 잘 모른 채 권한을 허락해 버린다는 점입니다.



## 2. 직무로 묶는 권한 — 역할 기반 통제와 타입 강제

> 병원의 의사와 약사처럼 직무마다 필요한 권한이 다르므로, 권한을 사람이 아니라 역할에 묶고 사람은 역할을 오가게 하면 관리가 쉬워집니다.

흐름 위치: 2 묶기 · 받치는 개념 — 역할 기반 통제·타입 강제

### 역할에 권한을 묶는 이유

큰 조직에서는 사람마다 권한을 따로 관리하기가 힘듭니다. 역할 기반 통제(RBAC)는 직무별 역할을 만들고 사용자를 역할에 배정합니다. 모든 프로그래머에게 새 라이브러리 접근을 열어 주려면 Programmer 역할에 권한 하나를 주면 됩니다. 프로그래머가 관리자로 승진해 접근이 필요 없어지면 그 사람에게서 Programmer 역할만 빼면 됩니다. 이렇게 하는 목적이 회계 담당을 의심해서가 아닙니다. 최소 권한은 상대의 정직뿐 아니라 신중함에도 기대지 않으려는 원칙이며, 접근 자체가 없으면 악의나 부주의로도 새어 나가지 않습니다.

### 그룹과 다른 점

RBAC 는 ACL 의 그룹과 비슷해 보이지만 더 강합니다. 한 사용자가 서로 겹치지 않는 여러 역할을 맡고 그 사이를 오갈 수 있다는 점이 다릅니다. 승진한 프로그래머가 팀원의 코드를 시험해야 할 때, 관리자 역할의 권한(인사 평가 열람)을 내려놓고 프로그래머 역할의 권한(라이브러리 접근)을 얻습니다. 그러면 누가 라이브러리에 악성 코드를 심어 인사 평가를 읽으려 해도, 시험 중인 사람은 그 역할로는 인사 평가를 볼 수 없어 유출되지 않습니다. 역할을 얻는 데 새 인증을 요구하고, 한 역할을 맡으면 이전 역할의 권한은 내려놓게 하는 시스템이 많습니다.

### 타입 강제와 보안 컨텍스트

RBAC 는 읽기·쓰기보다 더 잘게 나눌 수도 있습니다. 영업 담당 역할이 구매 기록을 추가하는 것은 허락하되 같은 파일에 재입고 기록을 추가하는 것은 막는 식입니다. 이 정도로 세밀한 통제를 **타입 강제**라고 부르며, 객체마다 **보안 컨텍스트**라는 이름의 상세한 접근 규칙을 붙입니다. 컨텍스트를 어디에 어떻게 저장하느냐가 성능과 저장 공간, 인증에 영향을 줍니다. 이 두 개념은 SELinux 에서 라벨(사용자·역할·타입)로 구체화됩니다.



## 3. 잠깐 빌리는 권한 — setuid·sudo 와 권한 상승의 위험

> 리눅스에서는 setuid 와 sudo 로 아주 단순한 역할 기반 통제를 흉내 낼 수 있습니다. 편리한 만큼 공격자가 가장 먼저 노리는 길이기도 합니다.

흐름 위치: 3 빌리기 · 받치는 개념 — setuid·sudo·권한 상승

### setuid 와 sudo

**권한 상승**은 프로그램이 실행하는 사용자의 권한을 넘어서는 권한으로 돌게 하는 기능입니다. 유닉스·리눅스에서는 이 기능을 setuid 라고 부릅니다. 프로그램이 평소 일반 사용자가 갖지 못한 다른 사용자(대개 root)의 권한으로 실행되며, 그 권한은 프로그램이 도는 동안만 유지됩니다. 신중하게 만든 setuid 프로그램은 제한된 작업만 수행해 권한을 남용할 수 없게 합니다. Rocky Linux 9 컨테이너에서 확인하면 `passwd` 와 `su` 가 setuid 프로그램입니다.

```bash
stat -c "%A %U %n" /usr/bin/passwd /usr/bin/su
```

```bash
-rwsr-xr-x root /usr/bin/passwd
-rwsr-xr-x root /usr/bin/su
```

소유자 실행 비트 자리의 `s` 가 setuid 비트입니다. 파일 소유자는 root 이고, 아무 사용자나 이 프로그램을 실행하면 프로세스의 유효 사용자 ID 가 root 로 바뀝니다.[^cred]

`sudo` 는 지정된 사용자에게 다른 신원으로 프로그램을 돌리게 합니다. 이 편의 눈으로 보면 단순한 역할 기반 통제입니다. 역할마다 가짜 사용자를 하나 만들고 권한을 붙입니다. 지정된 사람만 그 신원으로 명령을 돌리게 합니다. 실험에서는 bob 이 alice 신원으로 `id` 만 실행하도록 sudoers 에 한 줄을 넣었습니다.

```bash
echo "bob ALL=(alice) NOPASSWD: /usr/bin/id" > /etc/sudoers.d/b
su bob -c "sudo -u alice /usr/bin/id"
```

```bash
uid=1000(alice) gid=1000(alice) groups=1000(alice)
```

`ALL=(alice)` 는 "이 사용자로 실행해도 된다"는 허용 목록입니다. 목록에 없는 명령은 같은 줄의 `NOPASSWD` 를 받지 못해 비밀번호를 요구합니다. 안전하게 쓰려면 누가 어떤 프로그램을 어떤 신원으로 돌릴 수 있는지 정하는 설정 파일을 주의 깊게 관리해야 합니다. 대개 새 인증도 요구합니다.[^sudo]

### 권한 상승이 위험한 이유

공격자가 처음 침해하는 프로그램은 보통 아주 낮은 권한의 신원으로 돕니다. 쓰기 권한도 없는 파일 몇 개를 서비스하는 정도라 피해가 작아 보입니다. 그러나 공격자는 발판을 얻는 즉시 권한을 올릴 길을 찾습니다. 침해 직후의 첫 번째 일입니다. 최종 목표는 시스템의 모든 것을 바꿀 수 있는 superuser(root)가 되는 것입니다. root 가 되면 어떤 파일이든 읽을 수 있고 프로그램도 바꿀 수 있습니다. 다른 운영체제를 설치할 수도 있습니다. 

그래서 superuser 로 올라가는 길을 열 때는 신중해야 합니다. 모든 setuid 프로그램이 조심스럽게 만들어지지는 않았습니다. 그 때문에 오랫동안 많은 보안 문제가 생겼습니다.

### 강제 통제가 없으면 새는 곳

고급 RBAC 는 setuid·sudo 보다 더 세밀한 통제와 역할 배정 추적을 지원하고, 보통 강제 통제를 함께 씁니다. 강제 통제가 없으면 sudo 로 Programmer 신원이 된 사용자가 파일 권한을 바꾸는 명령을 실행해 설치 명령을 비프로그래머에게 열어 줄 수 있습니다. 강제 통제가 있으면 그 사용자가 Programmer 역할로 설치는 할 수 있어도, 그 역할로 영업이나 회계 담당에게 설치 권한을 퍼뜨릴 수는 없습니다.

### 정책이 틀리면 장치가 소용없다

장치가 완전히 정확하고 아주 빨라도 그것은 받은 정책을 집행할 뿐입니다. 접근 통제 장치 자체가 틀려서 일어나는 보안 사고는 드물고, 그 장치에 주어진 정책이 잘못 설계되어서 일어나는 사고는 드물지 않습니다.

> 이 편의 판단 기준은 아래 표와 같습니다.

| 상황 | 판단 | 근거 |
|------|------|------|
| 소유자가 풀 수 없어야 하는 규칙이 필요하다 | 강제 접근 통제를 쓴다 | 소유자가 아니라 관리 기관이 권한을 정한다 |
| 파일마다 소유자가 권한을 정해도 된다 | 임의 접근 통제를 쓴다 | 대부분의 시스템의 기본이다 |
| 직무별로 권한이 다르고 사람이 직무를 오간다 | 역할 기반 통제를 쓴다 | 역할에 권한을 묶고 사람은 역할을 바꾼다 |
| 같은 파일에 쓰되 기록 종류별로 막아야 한다 | 타입 강제와 보안 컨텍스트가 필요하다 | 읽기·쓰기보다 세밀하다 |
| 일반 사용자가 한정된 작업만 root 권한으로 해야 한다 | 신중하게 만든 setuid 나 sudo 허용 목록을 쓴다 | 권한이 프로그램 실행 동안만 유지된다 |
| sudo 만으로 역할을 흉내 내고 있다 | 그 역할로 다른 사람에게 권한을 퍼뜨릴 수 있음을 안다 | 강제 통제가 없으면 막지 못한다 |
| 접근 통제 장치를 의심하기 전에 | 정책 설계를 먼저 본다 | 사고는 장치보다 정책에서 더 자주 난다 |



## 면접 대비

> 이 편에서 물어볼 만한 정의와 핵심 포인트, 질문입니다.

### 한 줄 정의

- 임의 접근 통제: 객체의 소유자가 접근 권한을 정하는 방식입니다.
- 강제 접근 통제: 관리 기관이 권한을 강제하고 소유자가 덮어쓸 수 없는 방식입니다.
- 역할 기반 접근 통제(RBAC): 권한을 역할에 묶고 사용자에게 역할을 배정하는 방식입니다.
- 권한 상승: 프로그램이 실행한 사용자보다 높은 권한으로 도는 기능입니다. 유닉스에서는 setuid 입니다.

### 핵심 포인트 세 가지

1. 임의·강제는 "누가 권한을 정하는가"의 축이고, ACL·capability 와는 독립입니다.
2. RBAC 는 그룹과 달리 한 사용자가 서로 겹치지 않는 역할을 오가며, 역할을 바꿀 때 이전 역할의 권한은 내려놓습니다.
3. setuid·sudo 는 권한을 잠깐 빌려 주는 편리한 장치이지만 공격자가 root 로 오르는 첫 경로이므로 신중해야 합니다.

### 자주 묻는 질문

- *RBAC 는 그룹과 무엇이 다릅니까?* 그룹은 ACL 의 항목을 묶는 것이고, RBAC 는 한 사용자가 서로 겹치지 않는 여러 역할을 오가며 역할에 따라 권한이 바뀐다는 점이 다릅니다.
- *sudo 로 역할을 흉내 내면 충분합니까?* 아닙니다. 강제 통제가 없으면 그 역할로 파일 권한을 바꿔 다른 사람에게 퍼뜨릴 수 있습니다.
- *setuid 프로그램은 왜 위험합니까?* 프로그램이 도는 동안 높은 권한을 가지므로, 프로그램에 결함이 있으면 공격자가 그 권한을 얻습니다.
- *접근 통제가 맞는데 왜 사고가 납니까?* 장치는 받은 정책을 집행할 뿐이고 정책 자체가 잘못 설계되는 경우가 더 흔하기 때문입니다.



## 연습 문제

> 1~3번은 본문을 떠올려 답하는 문제이고 4~5번은 직접 돌려 확인하는 문제입니다. 답을 적은 뒤 정답 절과 맞춰 봅니다.

1. 임의 접근 통제와 강제 접근 통제는 무엇이 다릅니까? 이 선택은 ACL·capability 선택과 어떤 관계입니까?
2. RBAC 가 ACL 의 그룹보다 강한 점은 무엇입니까? 타입 강제는 무엇을 더합니까?
3. 침해 직후 공격자가 권한 상승을 가장 먼저 시도하는 이유는 무엇입니까?
4. Rocky Linux 9 컨테이너에서 `passwd` 와 `sudo` 의 권한 문자열을 확인하십시오. 어떤 칸이 setuid 를 나타냅니까?
5. sudoers 에 `bob ALL=(alice) NOPASSWD: /usr/bin/id` 를 넣었습니다. bob 이 `sudo -u alice /usr/bin/id` 를 실행하면 어떻게 됩니까? `sudo -u alice /usr/bin/cat /etc/hostname` 은 어떻게 됩니까?



## 정답 (자답 후 펼치기)

### 정답 1

임의 통제는 객체의 소유자가 권한을 정합니다. 강제 통제는 관리 기관이 정해서 소유자가 덮어쓸 수 없습니다. 이 선택은 ACL 이냐 capability 냐와 독립입니다. 어떤 자료구조로든 두 정책을 구현할 수 있습니다. 강제 통제 시스템에도 임의 요소가 있을 수 있으나 그 요소는 통제를 조이는 방향으로만 쓰입니다.

### 정답 2

RBAC 는 한 사용자가 서로 겹치지 않는 여러 역할을 맡고 오갈 수 있으며, 역할에 따라 권한이 바뀝니다. 그룹은 ACL 항목을 묶는 것에 가깝습니다. 타입 강제는 읽기·쓰기보다 더 세밀한 규칙(예: 구매 기록 추가는 되고 재입고 기록 추가는 안 됨)을 객체의 보안 컨텍스트로 붙입니다.

### 정답 3

처음 침해된 프로그램은 대개 권한이 아주 낮은 신원으로 돌아서 직접 할 수 있는 일이 적습니다. 그래서 공격자는 코드나 설정의 결함을 찾아 권한을 올리고, 최종적으로 root 가 되어 시스템 전체를 장악하려 합니다.

### 정답 4

Rocky Linux 9.3 컨테이너(`rockylinux:9`)에서 `passwd` 는 `-rwsr-xr-x root`, `su` 도 `-rwsr-xr-x root` 이고, `sudo` 는 `---s--x--x root` 입니다. 소유자 권한의 실행 자리(네 번째 문자)에 `x` 대신 `s` 가 있으면 setuid 입니다.

### 정답 5

`sudo -u alice /usr/bin/id` 는 `uid=1000(alice) gid=1000(alice) groups=1000(alice)` 를 출력해 alice 신원으로 실행됩니다. 허용 목록에 없는 `/usr/bin/cat` 은 `NOPASSWD` 가 적용되지 않아 비밀번호를 요구하고, 터미널이 없는 컨테이너에서는 `sudo: a password is required` 로 끝나 종료 코드 1 이 됩니다.
