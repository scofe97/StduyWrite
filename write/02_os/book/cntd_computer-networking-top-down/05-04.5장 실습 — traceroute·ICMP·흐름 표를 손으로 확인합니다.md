# 5장 실습 — traceroute·ICMP·흐름 표를 손으로 확인합니다

---

> 5장 세 편이 적은 주장을 이 기계에서 재현하고, 노트가 주장만 하고 넘어간 자리를 변수를 바꿔 가며 갈라 봅니다. 확인한 것보다 **틀리게 읽을 뻔한 것**과 **노트에 없던 것**이 이 편의 수확입니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 **한 번의 관찰은 잠정값이고, 변수를 바꿔 봐야 규칙이 갈린다**는 것입니다.

5장 세 편은 라우팅과 제어 평면을 다루면서 여러 주장을 합니다. 그중 손으로 확인할 수 있는 것을 골라 재현했더니 네 주장이 그대로 맞았습니다.

그런데 맞은 것보다 **하마터면 틀리게 읽을 뻔한 것**이 배움이 컸습니다. 별표 세 개를 네 번 연속 보고 "이 라우터는 침묵하도록 설정됐다"고 결론지었다가 다섯 번째에 답을 받았고, 같은 명령을 다섯 번 치는 동안 지나가는 라우터가 매번 달라졌습니다.

그리고 노트에 없던 것이 셋 나왔습니다. **인용된 TTL 이 "몇 홉 왔는지"를 거꾸로 말한다**는 것, **돌아오는 ICMP 자신의 TTL 로도 거리가 읽힌다**는 것, **호스트도 ICMP 오류를 만든다**는 것입니다. 마지막 것은 우연히 잡힌 DNS 패킷 한 쌍이 보여 주었습니다.



## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. `-q` 값을 바꿔 "포트가 홉마다 오르는가 탐침마다 오르는가"를 가르는 대조 실험을 설계할 수 있습니다.
2. ICMP 오류 메시지의 `length` 값에서 그 라우터가 원본을 얼마나 담았는지 역산할 수 있습니다.
3. 인용된 데이터그램의 TTL 과 돌아오는 ICMP 자신의 TTL 이 각각 무엇을 뜻하는지 가를 수 있습니다.
4. `* * *` 이 무엇을 뜻하고 무엇을 뜻하지 않는지 말할 수 있습니다.
5. 흐름 표에 일치하는 항목이 없을 때 무엇이 벌어지는지 예측하고 확인할 수 있습니다.

이 편에서 손으로 확인한 낱말입니다. `어디서` 는 그 확인이 실제로 적힌 절입니다.

| 키워드 | 뜻 | 학습 포인트·연결 개념 | 어디서 |
|---|---|---|---|
| 탐침 (probe) | 한 홉을 재려고 내보내는 데이터그램 하나 | 포트를 올리는 주체는 홉이 아니라 탐침 · `-q` 로 홉당 개수를 바꿔야 둘이 갈립니다 | §2 |
| 대조 실험 | 한 변수만 움직여 두 설명이 같은 출력을 내는 자리를 깹니다 | 기본값 `-q 3` 한 번만 잡으면 "홉마다 셋"과 "탐침마다 하나"가 구분되지 않습니다 | §2 |
| base 포트 (33434) | `traceroute` 가 목적지 포트를 올리기 시작하는 번호 | `man traceroute` 가 적은 기본값 · 05-03 이 "쓰이지 않을 법한 포트"라 부른 번호대 | §2 |

## 1. 무엇을 확인하려 했는가

> 5장 세 편의 주장 중 이 기계에서 재현할 수 있는 것을 골랐습니다. 어느 편의 어느 절이 근거인지를 함께 답니다.

노트는 "왜 그런가"를 적고, 이 편은 "정말 그런가"를 확인합니다. 확인 대상으로 고른 주장과 그 출처는 이렇습니다.

| 주장 | 어느 편 | 결과 |
|---|---|---|
| TTL 을 1 씩 올린 탐침을 보내고 라우터가 `ICMP 타입 11` 로 신원을 알립니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 | 확인 |
| 포트는 홉마다가 아니라 **탐침마다** 오릅니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 | 확인 — 대조 실험으로 |
| ICMP 는 원본의 헤더와 앞 8바이트를 담고, 실제 라우터는 더 담기도 합니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 | 확인 — 두 정책을 한 트레이스에서 |

| 인터넷은 라우터를 멍청하게 두기로 했고, 알려 줄 의무가 없습니다 | [`05-01`](./05-01.길은%20어떻게%20계산되는가.md) §1 | 확인 — 별표로 |

`ICMP` 가 IP 위 어디에 놓이는지, `traceroute` 가 왜 쓰이지 않는 포트를 고르는지 같은 배경은 [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 가 정본이라 여기서 되풀이하지 않습니다. 이 편은 **그 설명이 이 기계에서 어떻게 보이는가**만 적습니다.

원시 로그와 실행한 명령 전부는 `study/cntd-control-plane-lab/README.md` 에 있고, 이 편에는 다시 읽을 만한 것만 옮깁니다.



## 2. TTL 과 ICMP — traceroute 로 확인합니다

> 노트가 주장만 하고 넘어간 자리를 대조 실험으로 가르고, 노트에 없던 것 셋을 찾았습니다.

`traceroute` 가 TTL 을 올려 가며 일부러 죽는 탐침을 보낸다는 이야기는 [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 에 있습니다. 그 설명이 맞는지, 그리고 그 설명만으로는 가려지지 않는 것이 무엇인지를 봅니다.

### 포트는 탐침이 정합니다

노트는 포트가 **홉마다가 아니라 탐침마다** 오른다고 적습니다. 그런데 기본 설정으로 한 번만 잡으면 이 주장은 검증되지 않습니다. 홉당 탐침이 셋이므로 "홉마다 셋씩 오른다"와 "탐침마다 하나씩 오른다"가 **같은 출력을 내기** 때문입니다.

```bash
tcpdump -n -v -i en5 -c 24 'udp and dst host 1.1.1.1'
```

```bash
IP (tos 0x0, ttl 1, id 47845, ...)  192.168.0.184.47844 > 1.1.1.1.33435
IP (tos 0x0, ttl 1, id 47846, ...)  192.168.0.184.47844 > 1.1.1.1.33436
IP (tos 0x0, ttl 1, id 47847, ...)  192.168.0.184.47844 > 1.1.1.1.33437
IP (tos 0x0, ttl 2, id 47848, ...)  192.168.0.184.47844 > 1.1.1.1.33438
IP (tos 0x0, ttl 2, id 47849, ...)  192.168.0.184.47844 > 1.1.1.1.33439
IP (tos 0x0, ttl 2, id 47850, ...)  192.168.0.184.47844 > 1.1.1.1.33440
```

- `ttl` 은 세 줄마다 오르고 포트는 매 줄 오릅니다. 여기까지는 두 해석 모두와 맞습니다.

갈라 보려면 탐침 수를 바꿔야 합니다. `-q 1` 은 홉당 탐침을 하나로 줄입니다.

```bash
traceroute -m 3 -w 1 -q 1 1.1.1.1
```

```bash
ttl 1 → 33435
ttl 2 → 33436
ttl 3 → 33437
```

**포트가 홉마다 하나씩만 오릅니다.** 두 실행을 나란히 두면 규칙이 하나로 좁혀집니다.

| | 홉당 탐침 | 홉당 포트 소비 |
|---|---|---|
| `-q 3` (기본) | 3 | 3 |
| `-q 1` | 1 | 1 |

- 포트를 정하는 것은 홉이 아니라 **탐침**입니다. 홉이 정한다면 `-q 1` 에서도 홉당 셋씩 건너뛰었어야 합니다.

![탐침 셋과 탐침 하나를 잇달아 돌린 화면. 위쪽은 홉마다 ms 값이 셋씩 찍히고 아래쪽은 하나씩 찍힙니다](./_assets/05-04.traceroute-probes.gif)

- 위 묶음은 홉마다 값이 **셋**, 아래 묶음은 **하나**입니다. 위쪽 홉 4 는 세 탐침에 서로 다른 라우터가 답해 줄이 셋으로 갈렸고, 아래쪽은 탐침이 하나라 그런 갈림이 애초에 보이지 않습니다. **탐침 수를 줄이면 경로 다중성도 함께 안 보이게 됩니다.**

### ICMP 가 인용하는 것 — 36 과 48

양방향으로 잡으면 돌아오는 ICMP 안에 **원본 데이터그램이 통째로 들어 있는 것**이 보입니다.

```bash
tcpdump -n -v -i en5 -c 24 'icmp or (udp and dst host 1.1.1.1)'
```

```bash
192.168.0.1 > 192.168.0.184: ICMP time exceeded in-transit, length 48
    IP (tos 0x0, ttl 1, id 47845, offset 0, flags [none], proto UDP (17), length 40)
    192.168.0.184.47844 > 1.1.1.1.33435: UDP, length 12
```

- 들여쓰기된 두 줄이 **인용된 원본**입니다. `tcpdump` 가 그것까지 풀어서 보여 줍니다.

원문이 말하는 인용 범위를 그림으로 놓으면 이렇습니다.

```bash
문제가 된 원본 데이터그램
┌──────────────────┬──────────────────────────────────┐
│   IP 헤더 20B    │  적재량 — UDP 또는 TCP 세그먼트    │
└──────────────────┴──────────────────────────────────┘

ICMP 가 담는 최소치 (RFC 792)
┌──────────────────┬────────┐
│   IP 헤더 전체    │  앞 8B  │
└──────────────────┴────────┘
                      └─ UDP 면 헤더가 딱 8B 라 헤더 전체
                         TCP 면 출발지 포트 2 + 목적지 포트 2 + 순서 번호 4
```

**어느 경우든 포트 둘이 반드시 들어갑니다.** 그것이 8 이라는 수의 이유입니다. 포트가 있어야 받은 쪽이 자기 어느 소켓의 문제였는지 압니다.

잡힌 `length` 값 둘이 이 계산과 정확히 맞습니다.

| 보낸 라우터 | `length` | 계산 | 담은 것 |
|---|---|---|---|
| `10.204.127.21` | 36 | 8 + (IP 20 + UDP 8) | RFC 792 최소치 그대로 |
| `192.168.0.1` | 48 | 8 + (IP 20 + UDP 8 + 데이터 12) | 원본을 통째로 |

앞의 8 은 ICMP 자신의 헤더입니다. [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 의 「노트의 읽기」가 48 을 두고 "최소치를 규칙으로 읽으면 실제와 어긋난다"고 적었는데, 이번에는 **최소치 그대로 담는 라우터와 통째로 담는 라우터가 같은 트레이스에** 나왔습니다. 어긋남을 지적하는 데서 한 걸음 나아가 **정책이 라우터마다 다르다**는 것을 두 값으로 보인 셈입니다.

### TTL 이 두 자리에서 거리를 말합니다

같은 패킷인데 TTL 이 다릅니다.

```bash
나간 것   : ttl 3 , id 47851 , 포트 33441
인용된 것 : ttl 1 , id 47851 , 포트 33441
```

`id` 가 같으니 같은 패킷입니다. 그런데 나갈 때 3 이던 것이 인용에서는 1 입니다.

**인용은 그 라우터에 도착했을 때의 상태**이기 때문입니다. 3 으로 출발해 홉 둘을 지나며 `3 → 2 → 1` 로 깎였고, 세 번째 라우터가 1 을 받아 0 으로 만들고 폐기하면서 받은 그대로 인용했습니다.

그러니 인용된 TTL 은 **"얼마나 남았나"가 아니라 "얼마나 왔나"** 를 거꾸로 알려 줍니다. 출발값에서 빼면 지나온 홉 수가 나옵니다.

**돌아오는 ICMP 자신의 TTL** 도 같은 일을 합니다.

```bash
192.168.0.1    가 보낸 ICMP : ttl 64
10.204.127.21  가 보낸 ICMP : ttl 253
```

`253` 은 255 에서 출발해 두 홉을 지난 값입니다. **그 라우터가 나에게서 두 홉 거리**라는 뜻입니다. 공유기는 바로 옆이라 출발값 64 가 그대로 도착했습니다.

같은 필드가 한 화면에서 두 가지를 말합니다. 인용 안의 TTL 은 **내 패킷이 간 거리**를, 봉투의 TTL 은 **답이 온 거리**를 가리킵니다.

### 한 번의 관찰로는 못 가릅니다

홉 2 는 네 번 연속 별표 셋이었습니다. 그래서 설정으로 막힌 것이라 읽었는데, 다섯 번째 실행에서 답했습니다.

```bash
 1  192.168.0.1 (192.168.0.1)      1.462 ms  1.108 ms  0.605 ms
 2  1.223.246.73 (1.223.246.73)    3.190 ms  2.905 ms  *
 3  10.204.127.17 (10.204.127.17)  3.167 ms  2.243 ms  1.774 ms
```

**두 번 답하고 한 번만 별표**입니다. 설정으로 막았다면 셋 다 막혔어야 합니다.

속도 제한으로 읽는 편이 맞아 보입니다. 많은 라우터가 ICMP 오류 메시지 생성에 상한을 둡니다.

앞선 실행들에서 연달아 쏘는 동안 그 상한을 넘겼을 것입니다. 시간을 두고 다시 치니 여유가 생겨 답했습니다.

다만 이것도 추정입니다. 확정하려면 간격을 바꿔 가며 여러 번 재야 합니다.

별표 밑에서 실제로 무슨 일이 벌어지는지는 잡아 봐야 보입니다.

![탐침이 나가고 ICMP 가 돌아오는 왕복 세 쌍, 그다음 나가기만 하고 돌아오지 않는 세 줄](./_assets/05-04.icmp-roundtrip.gif)

앞의 여섯 줄이 **왕복 세 쌍**입니다. 포트 33435·33436·33437 이 나가고 그때마다 공유기가 `time exceeded` 를 돌려줍니다. 그런데 33438 부터는 **나가기만 하고 돌아오는 줄이 없습니다.** 그것이 화면에 `* * *` 로 찍히는 것의 정체입니다.

시각을 보면 기다림도 드러납니다. 33438 이 `08.672`, 33439 가 `09.675`, 33440 이 `10.679` 로 **정확히 1초씩** 벌어져 있습니다. `-w 1` 이 정한 대기 시간을 다 쓰고 다음 탐침으로 넘어간 흔적입니다.

확실한 것은 하나뿐입니다. `* * *` 은 **"답하지 않도록 설정됨"** 과 **"지금 못 답함"** 을 구별해 주지 않습니다. [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 도 같은 말을 하는데, **그것을 읽고도 네 번 보고 단정했습니다.** 읽은 것과 몸에 붙는 것은 다릅니다.

위상 자체는 일관됐습니다. 홉 3 이 앞선 실행들과 같은 `10.204.127.17` 이니 **홉 2 가 새로 생긴 것이 아니라 원래 있었는데 안 보였던 것**입니다.

경로도 마찬가지입니다. 한 실행 안에서도 갈립니다. 탐침 셋에 서로 다른 라우터가 답했습니다.

```bash
 5  100.76.9.5 (100.76.9.5)    4.236 ms
    100.76.10.1 (100.76.10.1)  2.584 ms
    100.76.1.5 (100.76.1.5)    3.891 ms
```

[`05-02`](./05-02.AS%20안과%20AS%20사이.md) §2 가 OSPF 의 진전으로 꼽은 **"같은 비용 경로 여럿"** 이 이것입니다. 목적지까지 비용이 같은 경로가 여럿이면 하나만 고르지 않고 함께 씁니다.

실행끼리 비교하면 더 선명합니다.

| 홉 | 1차 | 2차 | 3차 |
|---|---|---|---|
| 3 | `10.204.127.17` | `10.204.127.17` | `10.204.127.21` |
| 4 | `1.213.15.45` · `1.208.12.205` | `1.213.15.45` · `1.208.12.205` | `1.208.15.45` 하나만 |

3차에서는 홉 4 가 셋 다 같은 라우터라 **갈림이 아예 안 보였습니다.** 그 실행만 봤다면 이 자리엔 라우터가 하나라고 적었을 것입니다.

탐침 셋은 자원 하나를 두 목적에 나눠 씁니다.

| 상황 | 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| 같은 라우터가 셋 다 답 | 그 자리의 시간 변동 | 다른 경로가 있는지 |
| 다른 라우터가 하나씩 답 | 경로가 여럿이라는 사실 | 각 라우터의 변동 |

경로가 갈리는 순간 둘 다 어중간해집니다. 게다가 셋을 보내 셋이 다 달랐다면 **그것이 전부인지도 알 수 없습니다.** 제대로 재려면 탐침을 계속 보내야 하고, 그 일을 하는 도구가 `mtr` 입니다.

### 호스트도 ICMP 를 만듭니다

traceroute 와 무관한 패킷 한 쌍이 중간에 잡혔는데, 하필 종료 신호와 똑같은 메커니즘을 보여 주었습니다.

```bash
17:18:40  IP 192.168.0.184 > 192.168.0.1: ICMP 192.168.0.184 udp port 14212 unreachable
              IP 192.168.0.1.53 > 192.168.0.184.14212:  [|domain]
```

아래에서 위로 읽으면 이렇게 됩니다.

```bash
[1] 이 기계의 어떤 프로그램이 DNS 질의를 보냅니다      (공유기의 53번 포트로)
[2] 응답을 기다리다 포기하고 소켓을 닫습니다
[3] 뒤늦게 DNS 응답이 14212번 포트로 도착합니다
[4] 그 포트를 듣는 소켓이 없으니 port unreachable 을 돌려보냅니다
```

**traceroute 가 이제 멈춰도 된다고 판단하는 그 신호와 정확히 같은 메커니즘**입니다. 다만 방향이 반대라, 여기서는 **이 기계가 ICMP 를 만들어 보냈습니다.**

ICMP 는 라우터만 쓰는 것이 아니라 호스트도 씁니다. [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 첫 문장이 "호스트와 라우터가 네트워크 계층 정보를 서로 주고받는 데 쓰인다"고 적은 그대로인데, 읽을 때는 그냥 지나간 문장이었습니다. 실물을 보고서야 **"호스트와"** 가 왜 앞에 붙어 있는지 알았습니다.



## 3. Open vSwitch 흐름 표 — 규칙을 한 줄씩 세워 봅니다

> `05-03` 은 흐름 표를 그림으로 보여 주고 "어느 항목과도 일치하지 않은 패킷은 컨트롤러로 올라간다"고 적습니다. 그 문장이 **조건부였다**는 것이 이 절에서 드러납니다.

규칙을 하나도 넣지 않은 스위치는 패킷을 어떻게 할까요. 아무것도 안 하고 버릴 것 같은데, 그러면 그 스위치는 켜 놓아도 쓸모가 없습니다. 실제로 어느 쪽인지 보려면 표를 직접 만들어 놓고 줄을 넣고 빼 봐야 합니다.

무대는 OrbStack 우분투(arm64)입니다. Open vSwitch 3.7.1 을 올리면 커널 모듈이 적재되고, `ovs-vsctl` 로 브리지 하나를 만들어 네트워크 네임스페이스 둘을 붙였습니다.

```bash
          br0 (Open vSwitch 브리지)
           |
   +-------+-------+
   |               |
 포트 1          포트 2          <- 흐름 표가 일치를 거는 "진입 포트"
   |               |
 veth1           veth2
   |               |
  ns1             ns2
 10.10.0.1      10.10.0.2
```

포트 번호 1·2 가 `05-03` §1 이 말한 열두 일치 항목 중 하나입니다. 2·3장에서 본 TCP 포트 번호와 이름만 같고 층이 다릅니다.

§2 에서 "스위치는 TTL 을 만지지 않는다"고 적었는데, 그것은 **평범한 L2 브리징**의 이야기입니다. OVS 는 `dec_ttl` 이라는 동작을 갖고 있어 흐름 표로 지시하면 깎습니다. 층이 정하는 것이 아니라 규칙이 정합니다.

```bash
sudo ovs-ofctl add-flow br0 "priority=200,in_port=1,ip,actions=dec_ttl,output:2"
#  priority=200,ip,in_port=1 actions=dec_ttl,output:2
```

### 무대 — 브리지 하나에 네임스페이스 둘

```bash
sudo ovs-vsctl add-br br0 && sudo ip link set br0 up

for n in 1 2; do
  sudo ip netns add ns$n
  sudo ip link add veth$n type veth peer name ovs$n
  sudo ip link set veth$n netns ns$n
  sudo ovs-vsctl add-port br0 ovs$n
  sudo ip link set ovs$n up
  sudo ip netns exec ns$n ip link set lo up
  sudo ip netns exec ns$n ip link set veth$n up
  sudo ip netns exec ns$n ip addr add 10.10.0.$n/24 dev veth$n
done
```

`ovs-ofctl show br0` 이 붙은 포트에 번호를 매겨 보여 줍니다. 이 번호가 규칙에 쓰는 이름입니다.

```bash
 1(ovs1): addr:02:a2:9a:03:d3:b7
 2(ovs2): addr:72:16:0e:b9:d1:e2
 LOCAL(br0): addr:ca:dd:7a:9d:14:48
```

`ovs-vsctl` 과 `ovs-ofctl` 은 이름이 닮았지만 층이 다릅니다. 앞은 스위치의 **구성**을 만들고 뒤는 스위치의 **흐름 표**를 만집니다. `ovs-ofctl` 이 `05-03` §2 의 남향 인터페이스로 말을 거는 자리이고, 컨트롤러가 할 일을 사람이 CLI 로 하는 셈입니다.

### 빈 표가 아니라 NORMAL 한 줄이 있었습니다

규칙을 하나도 넣지 않은 상태에서 표를 덤프했습니다.

```bash
sudo ovs-ofctl dump-flows br0

 cookie=0x0, duration=515.509s, table=0, n_packets=37, n_bytes=2878, priority=0 actions=NORMAL
```

**비어 있지 않았습니다.** 브리지의 `fail_mode` 가 기본값인 `standalone` 이라 `ovs-vswitchd` 가 이 한 줄을 깔아 둔 것입니다. `fail_mode` 를 `secure` 로 두면 깔리지 않습니다.

```bash
sudo ovs-vsctl add-br bt
sudo ovs-ofctl dump-flows bt | grep -c NORMAL      # 1

sudo ovs-vsctl add-br bt2 && sudo ovs-vsctl set-fail-mode bt2 secure
sudo ovs-ofctl dump-flows bt2 | grep -c NORMAL     # 0
```

그러니 "브리지를 만들면 통한다"가 아니라 **"기본 `fail_mode` 에서는 통한다"** 가 정확합니다. `actions=NORMAL` 은 "이 패킷은 옛 L2 경로에 맡기라"는 뜻이라, 스위치가 MAC 을 배워 전달하는 평범한 동작으로 돌아갑니다. 컨트롤러 없는 브리지가 혼자서도 쓸모 있게 도는 이유입니다.

그래서 `ns1` → `ns2` ping 이 통합니다. 통한 이유는 "표가 없어서 스위치가 알아서 했다"가 아니라 **스위치처럼 굴라는 규칙 한 줄이 맞아서**입니다. 흐름 표와 OpenFlow 는 내내 있었고, 없던 것은 그 위에 앉을 컨트롤러뿐입니다.

계수기도 함께 읽힙니다. `n_packets=37` 은 포트가 아니라 **그 줄에 맞은** 누적 패킷 수입니다. 창(window)이 없고 줄이 설치된 뒤부터 계속 더해지므로, 옆의 `duration` 이 그 줄의 나이이면서 동시에 이 누적이 쌓인 기간이 됩니다. `05-03` §3 의 Read-State 가 모아 가는 값이 이것입니다.

### 한 방향만 넣으면 ARP 에서 끊깁니다

표를 비우고 한 방향만 넣었습니다.

```bash
sudo ovs-ofctl del-flows br0
sudo ovs-ofctl add-flow br0 "in_port=1,actions=output:2"
```

여기가 직관과 어긋나는 자리입니다. 물리 케이블은 꽂으면 양방향이지만 **흐름 표의 줄은 방향이 있습니다.** "둘을 연결한다"가 아니라 "들어온 곳에서 나갈 곳으로"라는 지시이기 때문입니다. `in_port=2` 에 대한 줄이 없으니 포트 2 로 들어오는 것은 맞는 줄이 없어 사라집니다.

ping 은 100% 손실인데, 끊긴 층이 ICMP 가 아닙니다.

```bash
sudo ip netns exec ns1 ip neigh show
10.10.0.2 dev veth1 FAILED

sudo ovs-ofctl dump-flows br0
 ... n_packets=6, n_bytes=336, in_port=ovs1 actions=output:ovs2
```

`ns1` 은 `ns2` 의 MAC 을 먼저 알아야 하는데 그 답이 포트 2 로 돌아오다 죽었습니다. **ping 은 시작조차 하지 못했습니다.**

`336 / 6 = 56` 을 프레임 크기로 읽지는 않습니다. 그 여섯 개가 다 ARP 라는 보장이 없어서 평균이 아무것도 가려 주지 않습니다. 균질한 집합에서 다시 재야 크기가 나옵니다.

```bash
sudo ovs-ofctl del-flows br0
sudo ovs-ofctl add-flow br0 "in_port=1,actions=output:2"
sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2

sudo ovs-ofctl dump-flows br0
#  ... n_packets=3, n_bytes=126, in_port=1 actions=output:2
```

`126 / 3 = 42`. 이더넷 헤더 14 에 ARP 28 을 더한 값이고, 이제 나간 것이 ARP 요청이라고 말할 수 있습니다. `ns2` 쪽에서 잡아도 `length 42` 로 찍힙니다.

42 는 `veth` 와 OVS 가 센 값입니다. 이더넷 최소 프레임은 FCS 를 포함해 64 바이트이고 FCS 를 빼면 60 바이트라, 선로에서는 패딩이 붙을 수 있습니다. 재는 자리에 따라 어느 계층에서 재는지에 따라 패딩이 보이기도 하고 안 보이기도 합니다. 그러니 **어디서 센 값인지를 함께 적지 않으면 크기가 크기를 말하지 못합니다.**

`FAILED` 라는 낱말도 눈여겨볼 자리입니다. 이것은 "항목이 없다"와 다릅니다. 항목이 없는 상태는 아직 물어보지 않았을 때도 나오고, 이 실습에서처럼 `ip neigh flush` 로 지웠을 때도 나옵니다. 원인이 하나가 아니라 **지금 항목이 없다**는 사실만 말합니다. 이웃 표는 `ns2` 가 채워 주는 것이 아니라 `ns1` 의 커널이 자기 행동을 적어 두는 수첩이고, 그래서 답이 없어도 물어봤다는 사실을 압니다.

이 실습에서 실제로 본 상태가 넷입니다.

| 상태 | 뜻 |
|---|---|
| 항목 없음 | 지금 항목이 없습니다. 아직 안 물어봤을 수도, `flush` 나 회수로 지워졌을 수도 있습니다 (상태가 아니라 부재입니다) |
| `INCOMPLETE` | 물어보는 중입니다. 재시도가 남았습니다 |
| `FAILED` | 재시도를 다 쓰고 포기했습니다 |
| `REACHABLE` | 답을 받아 MAC 을 알고 있습니다 |

넷이 전부는 아닙니다. 커널의 이웃 상태에는 `STALE`·`DELAY`·`PROBE`·`PERMANENT`·`NOARP` 도 있고, 손으로 넣어 보면 받아들입니다.

```bash
sudo ip netns exec ns1 ip neigh replace 10.10.0.9 lladdr 02:00:00:00:00:09 dev veth1 nud stale
sudo ip netns exec ns1 ip neigh show 10.10.0.9
# 10.10.0.9 dev veth1 lladdr 02:00:00:00:00:09 STALE
```

위 넷은 **이번 실습의 경로에서 지나간 단계**일 뿐이라, 상태 기계 전체로 읽으면 안 됩니다.

### 답이 왔는지 아무도 없었는지는 계수기가 가릅니다

`ns1` 이 보는 침묵은 원인을 담지 않습니다. `10.10.0.2` 라는 기계가 없는 경우와, 기계는 있고 답도 했는데 스위치가 그 답을 버린 경우가 **똑같이 `FAILED` 로 보입니다.**

§2 에서 `* * *` 을 두고 세운 규칙이 층을 바꿔 다시 나옵니다. 한쪽 끝에서 본 침묵으로는 못 가르고, 가르려면 중간에서 세야 합니다.

양방향을 채워 통하는 출발선을 먼저 박았습니다. 안 통할 때 그것이 내가 만든 결과인지 앞 회차의 잔재인지 가리려면 출발선이 명령으로 남아 있어야 합니다.

```bash
sudo ovs-ofctl add-flow br0 "in_port=2,actions=output:1"
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
sudo ip netns exec ns1 ip neigh show

# 2 packets transmitted, 2 received, 0% packet loss
10.10.0.2 dev veth1 lladdr 02:bd:9e:51:30:d9 REACHABLE
```

그 상태에서 돌아오는 방향만 `drop` 으로 바꿉니다. 버리더라도 **맞은 것은 세어지는지**가 물음입니다.

```bash
sudo ovs-ofctl add-flow br0 "in_port=2,actions=drop"
sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2
sudo ovs-ofctl dump-flows br0

# 2 packets transmitted, 0 received, 100% packet loss
 ... n_packets=17, n_bytes=966, in_port=ovs1 actions=output:ovs2
 ... n_packets=2,  n_bytes=84,  in_port=ovs2 actions=drop
```

`84 / 2 = 42`. 이더넷 헤더 14 에 ARP 28 을 더한 값입니다.

여기서 멈추면 추론이 하나 남습니다. `in_port=2` 규칙은 그 포트로 들어오는 **모든 것**을 세므로, 84 바이트가 ARP 응답이라는 보장이 아직 없습니다. 일치 조건을 ARP 로 좁혀 다시 쟀습니다.

```bash
# 표를 비우고 다시 쌓아야 합니다. add-flow 의 기본 우선순위가 32768 이라
# 앞서 넣은 in_port=2 줄을 지우지 않으면 priority=200 은 선택되지 않습니다.
sudo ovs-ofctl del-flows br0
sudo ovs-ofctl add-flow br0 "in_port=1,actions=output:2"
sudo ovs-ofctl add-flow br0 "priority=200,arp,in_port=2,actions=drop"

sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 2 -W 1 10.10.0.2

sudo ovs-ofctl dump-flows br0
#  ... n_packets=2, n_bytes=84, in_port=1 actions=output:2
#  ... n_packets=2, n_bytes=84, priority=200,arp,in_port=2 actions=drop
```

같은 2개 84 바이트입니다. **ARP 응답 두 개가 도착했고 스위치가 죽였습니다.** `ns2` 가 없었다면 이 계수기는 0 입니다. "없는 기계"와 "죽은 응답"이 숫자 하나로 갈렸습니다.

들어가는 쪽도 `882 → 966` 으로 84 바이트, 역시 42 바이트짜리 둘입니다. 오간 것이 처음부터 끝까지 ARP 였다는 뜻입니다.

### 같은 일치·같은 우선순위는 겨루지 않고 덮어씁니다

위에서 `in_port=2` 를 두 번 넣었습니다. 처음은 `output:1`, 다음은 `drop` 입니다. 표에 줄이 둘로 늘 것 같은데 그렇지 않았습니다.

```bash
sudo ovs-ofctl dump-flows br0        # add-flow 바로 뒤
 ... duration=0.017s, n_packets=0, n_bytes=0, in_port=ovs2 actions=drop
```

`duration` 이 0.017 초이고 계수기가 0 으로 돌아갔습니다. **같은 일치 조건에 같은 우선순위면 새 줄이 아니라 같은 줄로 취급해 교체합니다.** 둘을 겨루게 하려면 우선순위를 달리 주어야 합니다. 시계와 계수기가 처음으로 돌아간 것이 교체의 증거입니다.

### Packet-in 은 패킷을 올려보내고, 답이 없으면 거기서 끝납니다

마지막으로 동작을 `CONTROLLER` 로 바꿨습니다. 받을 상대는 `ovs-ofctl monitor` 가 대신합니다. 컨트롤러 흉내이고, 듣기만 하는 귀입니다.

```bash
nohup sudo ovs-ofctl monitor br0 65535 >/tmp/pktin.log 2>&1 &
sleep 1
sudo ovs-ofctl add-flow br0 "in_port=1,actions=CONTROLLER:65535"
sudo ip netns exec ns1 ip neigh flush all
sudo ip netns exec ns1 ping -c 1 -W 1 10.10.0.2
sleep 1 && sudo pkill -f "ovs-ofctl monitor"
```

올라간 것이 이렇습니다.

```bash
NXT_PACKET_IN2 (xid=0x0): cookie=0x0 total_len=42 in_port=1 (via action) data_len=42 (unbuffered)
arp,vlan_tci=0x0000,dl_src=26:d0:95:30:bd:f5,dl_dst=ff:ff:ff:ff:ff:ff,
    arp_spa=10.10.0.1,arp_tpa=10.10.0.2,arp_op=1,arp_sha=26:d0:95:30:bd:f5,
    arp_tha=00:00:00:00:00:00
```

Packet-in 이 나르는 것은 IP 주소 하나가 아니라 **패킷**입니다. 둘째 줄이 그 패킷을 디코드한 내용입니다.

다만 얼마나 실리는지는 조건에 달립니다. 이 출력은 `unbuffered` 이고 `data_len=42` 라 **42 바이트가 통째로** 올라갔습니다. 버퍼링을 쓰면 스위치가 패킷을 들고 있고 일부만 올려보내며, `CONTROLLER:<max_len>` 의 그 숫자가 상한입니다. 여기서 준 `65535` 가 "다 올려라"인 셈입니다.

올라오는 경로도 둘입니다. 표를 못 맞췄을 때와, `CONTROLLER` 동작에 **맞아서** 올라갈 때입니다. `(via action)` 이 여기 찍힌 것은 뒤쪽이라는 표시입니다. 그러니 이 관측은 "표에 규칙이 없어서"가 아니라 "올려보내라는 규칙이 맞아서" 생긴 것입니다.

`dl_dst=ff:ff:ff:ff:ff:ff` 도 함께 읽힙니다. 스위치가 목적지를 몰라 모든 포트에 뿌리는 플러딩과, 보낸 쪽이 이 주소를 적어 모두에게 가라고 요청한 브로드캐스트는 밖에서 보면 같아 보이지만 원인이 다릅니다. 여기 찍힌 것은 뒤쪽입니다.

그런데 ping 은 여전히 100% 손실이었습니다. **Packet-in 만으로는 아무 일도 일어나지 않습니다.** 진짜 컨트롤러라면 Packet-out 으로 이 패킷 하나를 어디로 보낼지 지시하거나, Modify-State 로 앞으로 같은 부류를 처리할 규칙을 내려보냅니다.

둘을 같이 하는 것이 **반응형** 컨트롤러의 얼개이고, 그럴 때만 "첫 패킷은 느리고 그다음부터는 표에서 바로"가 성립합니다. 규칙을 미리 깔아 두는 선제형 컨트롤러는 Packet-in 을 거의 받지 않습니다.

그러니 `05-03` §3 의 서술은 조건을 하나 더 달아야 정확합니다. **"컨트롤러가 붙어 있을 때" 일치 실패가 올라갑니다.** 올려보낼 상대가 없으면 버려지고, 이 실습의 표를 비웠을 때 나온 100% 손실이 그것이었습니다.

조건이 실은 둘입니다. 컨트롤러가 있어도 **OpenFlow 판에 따라 다릅니다.**

1.0 에서는 일치 실패가 저절로 컨트롤러로 올라갑니다. 1.3 이후로는 그 일을 하는 table-miss 항목을 명시해야 하고, 없으면 폐기입니다.

이 브리지는 `protocols` 가 비어 있어 판을 협상하며 `-O OpenFlow13` 으로도 말이 통합니다. 그러니 `05-03` 의 서술은 **OpenFlow 1.0 의 동작**을 적은 것으로 읽는 편이 맞습니다.

> 내용보다 방법에 대해 배운 것이 많습니다. 다음에 다른 것을 잴 때도 쓰입니다.

| 규칙 | 어디서 나왔나 |
|---|---|
| 변수를 하나 움직여야 구별되지 않던 두 해석이 갈립니다 | §2 — `-q 3` 만 봐서는 못 가립니다 |
| 한 번의 관찰은 잠정값입니다 | §2 — 네 번 보고 단정했다가 다섯 번째에 뒤집혔습니다 |
| 같은 명령을 여러 번 쳐야 경로 다중성이 보입니다 | §2 — 실행마다 홉이 달라졌습니다 |
| 필터가 무엇을 거르는지 알고 써야 합니다 | §2 — 한 방향만 잡으면 라우터 IP 가 안 보입니다 |
| 잡을 인터페이스는 관례로 짐작하지 않습니다 | 아래 치트시트 첫 줄 |
| 한쪽 방향만 세어 보면 "잘 나갔다"로 읽힙니다 | §3 — 나가는 계수기는 올라가는데 오는 길이 죽어 있었습니다 |
| 침묵은 원인을 담지 않습니다. 가르려면 중간에서 셉니다 | §3 — "없는 기계"와 "죽은 응답"이 계수기 하나로 갈렸습니다 |
| 출발선을 명령으로 박아 두지 않으면 앞 회차의 잔재를 결과로 읽습니다 | §3 — `drop` 실험 전에 통하는 상태를 먼저 확인했습니다 |
| 문서가 단정한 문장이 실은 조건부일 수 있습니다 | §3 — 일치 실패는 **컨트롤러가 있을 때만** 올라갑니다 |
| 평균을 단위 크기로 읽지 않습니다. 균질한 집합에서 다시 재야 합니다 | §3 — `336/6 = 56` 을 ARP 크기라 했다가 재측정에서 42 로 정정했습니다 |
| 관측한 단계를 상태 기계 전체로 읽지 않습니다 | §3 — 이웃 표 상태를 넷이라 적었는데 `STALE`·`PROBE`·`PERMANENT` 도 있었습니다 |
| "기본값에서는" 을 빼면 조건부가 단정이 됩니다 | §3 — `NORMAL` 한 줄은 `fail_mode=standalone` 일 때만 깔립니다 |
| 어디서 센 값인지가 크기의 일부입니다 | §3 — 42 바이트는 `veth`·OVS 기준이고 물리 이더넷이면 패딩이 붙습니다 |
| 문서의 명령 블록은 초기화까지 적어야 재현됩니다 | §3 — `del-flows` 를 빼먹어 `priority=200` 이 이길 수 없는 블록이 됐습니다 |

마지막 둘을 덧붙이면, `udp and dst host 1.1.1.1` 은 **나가는 탐침만** 잡습니다. 돌아오는 ICMP 는 UDP 도 아니고 출발지도 목적지 주소가 아니라 걸러집니다. 그리고 맥에서 `en0` 이 Wi-Fi 라는 것은 관례일 뿐이라, 목적지를 주고 물어야 실제로 나가는 인터페이스가 나옵니다.



## 실습 치트시트

### traceroute 와 ICMP (§2)

| 하려는 것 | 명령 |
|---|---|
| 목적지로 나가는 인터페이스 판별 | `route -n get 1.1.1.1 \| grep interface` |
| 나가는 탐침만 잡기 (TTL 포함) | `tcpdump -n -v -i <인터페이스> -c 24 'udp and dst host 1.1.1.1'` |
| 양방향 잡기 (라우터 IP 포함) | `tcpdump -n -v -i <인터페이스> -c 24 'icmp or (udp and dst host 1.1.1.1)'` |
| 짧게 돌리기 | `traceroute -m 3 -w 1 1.1.1.1` |
| 탐침 하나로 줄이기 | `traceroute -m 3 -w 1 -q 1 1.1.1.1` |

### 흐름 표 (§3)

| 하려는 것 | 명령 |
|---|---|
| 브리지·포트 **구성** 보기 | `ovs-vsctl show` |
| 포트에 매겨진 **번호** 보기 | `ovs-ofctl show br0` |
| 흐름 표 읽기 (Read-State) | `ovs-ofctl dump-flows br0` |
| 규칙 넣기 (Modify-State) | `ovs-ofctl add-flow br0 "in_port=1,actions=output:2"` |
| 표 비우기 | `ovs-ofctl del-flows br0` |
| 컨트롤러로 올려보내기 | `ovs-ofctl add-flow br0 "in_port=1,actions=CONTROLLER:65535"` |
| 올라오는 OpenFlow 메시지 엿듣기 | `ovs-ofctl monitor br0 65535` |

`ovs-vsctl` 은 **구성**, `ovs-ofctl` 은 **흐름 표**입니다. 이름이 닮아 헷갈리는데 앞은 배선이고 뒤는 규칙입니다.

### 네임스페이스와 이웃 표 (§3)

| 하려는 것 | 명령 |
|---|---|
| 네임스페이스 안에서 명령 돌리기 | `ip netns exec ns1 <명령>` |
| 그 안의 주소 보기 | `ip netns exec ns1 ip -br addr` |
| 이웃(ARP) 표 보기 | `ip netns exec ns1 ip neigh show` |
| 이웃 표 비우기 | `ip netns exec ns1 ip neigh flush all` |
| 네임스페이스 목록 | `ip netns list` |

`ip neigh` 의 `neigh` 는 이웃(neighbor)이고, IP 와 MAC 의 짝을 담은 표입니다. ARP 표라고 부르는 그것입니다. `flush all` 로 비우면 상대의 MAC 을 잊으므로 매번 같은 출발선에서 잴 수 있습니다.

`nohup <명령> >파일 2>&1 &` 는 셋을 한꺼번에 합니다. `nohup` 은 터미널이 닫혀도 죽지 않게 하고, `>파일 2>&1` 은 출력과 오류를 그 파일로 모으고, 끝의 `&` 는 배경으로 돌려 다음 명령을 바로 칠 수 있게 합니다. `ovs-ofctl monitor` 처럼 **계속 듣고 있어야 하는 명령**을 켜 두고 그 사이에 다른 명령으로 패킷을 만들 때 씁니다. 끌 때는 `pkill -f "ovs-ofctl monitor"` 로 이름을 집어 죽입니다.

`<인터페이스>` 는 첫 줄로 매번 구합니다. 이 기계는 한나절 사이에 `en5` 에서 `en0` 으로 바뀌었습니다. `-w 1` 은 응답 대기를 1초로 줄입니다. 기본값이면 답 없는 홉 하나에서 15초를 기다립니다. `tcpdump` 는 Wireshark 가 설치한 ChmodBPF 덕분에 `sudo` 없이 돕니다.
