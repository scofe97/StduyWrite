# 5장 실습 — traceroute·ICMP·흐름 표를 손으로 확인합니다

---

> 5장 세 편이 적은 주장을 이 기계에서 재현하고, 노트가 주장만 하고 넘어간 자리를 변수를 바꿔 가며 갈라 봅니다. 확인한 것보다 **틀리게 읽을 뻔한 것**과 **노트에 없던 것**이 이 편의 수확입니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 **한 번의 관찰은 잠정값이고, 변수를 바꿔 봐야 규칙이 갈린다**는 것입니다.

5장 세 편은 라우팅과 제어 평면을 다루면서 여러 주장을 합니다. 그중 손으로 확인할 수 있는 것을 골라 재현했더니 네 주장이 그대로 맞았습니다.

그런데 맞은 것보다 **하마터면 틀리게 읽을 뻔한 것**이 배움이 컸습니다. 별표 세 개를 네 번 연속 보고 "이 라우터는 침묵하도록 설정됐다"고 결론지었다가 다섯 번째에 답을 받았고, 같은 명령을 다섯 번 치는 동안 지나가는 라우터가 매번 달라졌습니다.

그리고 노트에 없던 것이 셋 나왔습니다. **인용된 TTL 이 "몇 홉 왔는지"를 거꾸로 말한다**는 것, **돌아오는 ICMP 자신의 TTL 로도 거리가 읽힌다**는 것, **호스트도 ICMP 오류를 만든다**는 것입니다. 마지막 것은 우연히 잡힌 DNS 패킷 한 쌍이 보여 주었습니다.



## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. `-q` 값을 바꿔 "포트가 홉마다 오르는가 탐침마다 오르는가"를 가르는 대조 실험을 설계할 수 있습니다.
2. ICMP 오류 메시지의 `length` 값에서 그 라우터가 원본을 얼마나 담았는지 역산할 수 있습니다.
3. 인용된 데이터그램의 TTL 과 돌아오는 ICMP 자신의 TTL 이 각각 무엇을 뜻하는지 가를 수 있습니다.
4. `* * *` 이 무엇을 뜻하고 무엇을 뜻하지 않는지 말할 수 있습니다.
5. 흐름 표에 일치하는 항목이 없을 때 무엇이 벌어지는지 예측하고 확인할 수 있습니다.

이 편에서 손으로 확인한 낱말입니다. `어디서` 는 그 확인이 실제로 적힌 절입니다.

| 키워드 | 뜻 | 학습 포인트·연결 개념 | 어디서 |
|---|---|---|---|
| 탐침 (probe) | 한 홉을 재려고 내보내는 데이터그램 하나 | 포트를 올리는 주체는 홉이 아니라 탐침 · `-q` 로 홉당 개수를 바꿔야 둘이 갈립니다 | §2 |
| 대조 실험 | 한 변수만 움직여 두 설명이 같은 출력을 내는 자리를 깹니다 | 기본값 `-q 3` 한 번만 잡으면 "홉마다 셋"과 "탐침마다 하나"가 구분되지 않습니다 | §2 |
| base 포트 (33434) | `traceroute` 가 목적지 포트를 올리기 시작하는 번호 | `man traceroute` 가 적은 기본값 · 05-03 이 "쓰이지 않을 법한 포트"라 부른 번호대 | §2 |
| ICMP 인용 길이 | 오류 메시지가 원본을 얼마나 담았는지 알려 주는 `length` 값 | 36 = 8 + IP 20 + UDP 8 (RFC 792 최소치) · 48 = 거기에 데이터 12 · **정책이 라우터마다 다릅니다** | §2 |
| 인용된 원본의 TTL | ICMP 안에 실린 원본 데이터그램의 TTL | 그 라우터에 **도착했을 때의 상태** 라 1 로 찍힙니다 · "얼마나 남았나"가 아니라 "얼마나 왔나" | §2 |
| 돌아오는 ICMP 의 TTL | 오류 메시지 자신의 TTL | 라우터에서 나를 향해 오며 깎인 값 · 위 낱말과 층이 달라 함께 보면 거리가 두 자리에서 읽힙니다 | §2 |
| `* * *` | 그 홉에서 답이 안 왔다는 표시 | 라우터가 없다는 뜻이 **아닙니다** — 응답을 안 하거나 속도 제한에 걸렸을 수 있습니다 · 1초씩 벌어진 시각이 대기 흔적 | §2 |
| 흐름 표 일치 실패 | 들어온 패킷이 어느 항목과도 안 맞는 상태 | 05-03 §3 의 Packet-in 이 일어나는 조건 · 기본 동작을 무엇으로 둘지가 설계 결정 | §3 |



## 1. 무엇을 확인하려 했는가

> 5장 세 편의 주장 중 이 기계에서 재현할 수 있는 것을 골랐습니다. 어느 편의 어느 절이 근거인지를 함께 답니다.

노트는 "왜 그런가"를 적고, 이 편은 "정말 그런가"를 확인합니다. 확인 대상으로 고른 주장과 그 출처는 이렇습니다.

| 주장 | 어느 편 | 결과 |
|---|---|---|
| TTL 을 1 씩 올린 탐침을 보내고 라우터가 `ICMP 타입 11` 로 신원을 알립니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 | 확인 |
| 포트는 홉마다가 아니라 **탐침마다** 오릅니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 | 확인 — 대조 실험으로 |
| ICMP 는 원본의 헤더와 앞 8바이트를 담고, 실제 라우터는 더 담기도 합니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 | 확인 — 두 정책을 한 트레이스에서 |
| 목적지까지 비용이 같은 경로가 여럿이면 **함께 씁니다** | [`05-02`](./05-02.AS%20안과%20AS%20사이.md) §2 | 확인 |
| 인터넷은 라우터를 멍청하게 두기로 했고, 알려 줄 의무가 없습니다 | [`05-01`](./05-01.길은%20어떻게%20계산되는가.md) §1 | 확인 — 별표로 |
| 일치하는 항목이 없는 패킷은 폐기가 아니라 컨트롤러로 올라갑니다 | [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §3 | §3 에 예정 |

`ICMP` 가 IP 위 어디에 놓이는지, `traceroute` 가 왜 쓰이지 않는 포트를 고르는지 같은 배경은 [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 가 정본이라 여기서 되풀이하지 않습니다. 이 편은 **그 설명이 이 기계에서 어떻게 보이는가**만 적습니다.

원시 로그와 실행한 명령 전부는 `study/cntd-control-plane-lab/README.md` 에 있고, 이 편에는 다시 읽을 만한 것만 옮깁니다.



## 2. TTL 과 ICMP — traceroute 로 확인합니다

> 노트가 주장만 하고 넘어간 자리를 대조 실험으로 가르고, 노트에 없던 것 셋을 찾았습니다.

`traceroute` 가 TTL 을 올려 가며 일부러 죽는 탐침을 보낸다는 이야기는 [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 에 있습니다. 그 설명이 맞는지, 그리고 그 설명만으로는 가려지지 않는 것이 무엇인지를 봅니다.

### 포트는 탐침이 정합니다

노트는 포트가 **홉마다가 아니라 탐침마다** 오른다고 적습니다. 그런데 기본 설정으로 한 번만 잡으면 이 주장은 검증되지 않습니다. 홉당 탐침이 셋이므로 "홉마다 셋씩 오른다"와 "탐침마다 하나씩 오른다"가 **같은 출력을 내기** 때문입니다.

```bash
tcpdump -n -v -i en5 -c 24 'udp and dst host 1.1.1.1'
```

```bash
IP (tos 0x0, ttl 1, id 47845, ...)  192.168.0.184.47844 > 1.1.1.1.33435
IP (tos 0x0, ttl 1, id 47846, ...)  192.168.0.184.47844 > 1.1.1.1.33436
IP (tos 0x0, ttl 1, id 47847, ...)  192.168.0.184.47844 > 1.1.1.1.33437
IP (tos 0x0, ttl 2, id 47848, ...)  192.168.0.184.47844 > 1.1.1.1.33438
IP (tos 0x0, ttl 2, id 47849, ...)  192.168.0.184.47844 > 1.1.1.1.33439
IP (tos 0x0, ttl 2, id 47850, ...)  192.168.0.184.47844 > 1.1.1.1.33440
```

- `ttl` 은 세 줄마다 오르고 포트는 매 줄 오릅니다. 여기까지는 두 해석 모두와 맞습니다.

갈라 보려면 탐침 수를 바꿔야 합니다. `-q 1` 은 홉당 탐침을 하나로 줄입니다.

```bash
traceroute -m 3 -w 1 -q 1 1.1.1.1
```

```bash
ttl 1 → 33435
ttl 2 → 33436
ttl 3 → 33437
```

**포트가 홉마다 하나씩만 오릅니다.** 두 실행을 나란히 두면 규칙이 하나로 좁혀집니다.

| | 홉당 탐침 | 홉당 포트 소비 |
|---|---|---|
| `-q 3` (기본) | 3 | 3 |
| `-q 1` | 1 | 1 |

- 포트를 정하는 것은 홉이 아니라 **탐침**입니다. 홉이 정한다면 `-q 1` 에서도 홉당 셋씩 건너뛰었어야 합니다.

![탐침 셋과 탐침 하나를 잇달아 돌린 화면. 위쪽은 홉마다 ms 값이 셋씩 찍히고 아래쪽은 하나씩 찍힙니다](./_assets/05-04.traceroute-probes.gif)

위 묶음은 홉마다 값이 **셋**, 아래 묶음은 **하나**입니다. 위쪽 홉 4 는 세 탐침에 서로 다른 라우터가 답해 줄이 셋으로 갈렸고, 아래쪽은 탐침이 하나라 그런 갈림이 애초에 보이지 않습니다. **탐침 수를 줄이면 경로 다중성도 함께 안 보이게 됩니다.**

### ICMP 가 인용하는 것 — 36 과 48

양방향으로 잡으면 돌아오는 ICMP 안에 **원본 데이터그램이 통째로 들어 있는 것**이 보입니다.

```bash
tcpdump -n -v -i en5 -c 24 'icmp or (udp and dst host 1.1.1.1)'
```

```bash
192.168.0.1 > 192.168.0.184: ICMP time exceeded in-transit, length 48
    IP (tos 0x0, ttl 1, id 47845, offset 0, flags [none], proto UDP (17), length 40)
    192.168.0.184.47844 > 1.1.1.1.33435: UDP, length 12
```

- 들여쓰기된 두 줄이 **인용된 원본**입니다. `tcpdump` 가 그것까지 풀어서 보여 줍니다.

원문이 말하는 인용 범위를 그림으로 놓으면 이렇습니다.

```bash
문제가 된 원본 데이터그램
┌──────────────────┬──────────────────────────────────┐
│   IP 헤더 20B    │  적재량 — UDP 또는 TCP 세그먼트    │
└──────────────────┴──────────────────────────────────┘

ICMP 가 담는 최소치 (RFC 792)
┌──────────────────┬────────┐
│   IP 헤더 전체    │  앞 8B  │
└──────────────────┴────────┘
                      └─ UDP 면 헤더가 딱 8B 라 헤더 전체
                         TCP 면 출발지 포트 2 + 목적지 포트 2 + 순서 번호 4
```

**어느 경우든 포트 둘이 반드시 들어갑니다.** 그것이 8 이라는 수의 이유입니다. 포트가 있어야 받은 쪽이 자기 어느 소켓의 문제였는지 압니다.

잡힌 `length` 값 둘이 이 계산과 정확히 맞습니다.

| 보낸 라우터 | `length` | 계산 | 담은 것 |
|---|---|---|---|
| `10.204.127.21` | 36 | 8 + (IP 20 + UDP 8) | RFC 792 최소치 그대로 |
| `192.168.0.1` | 48 | 8 + (IP 20 + UDP 8 + 데이터 12) | 원본을 통째로 |

앞의 8 은 ICMP 자신의 헤더입니다. [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 의 「노트의 읽기」가 48 을 두고 "최소치를 규칙으로 읽으면 실제와 어긋난다"고 적었는데, 이번에는 **최소치 그대로 담는 라우터와 통째로 담는 라우터가 같은 트레이스에** 나왔습니다. 어긋남을 지적하는 데서 한 걸음 나아가 **정책이 라우터마다 다르다**는 것을 두 값으로 보인 셈입니다.

### TTL 이 두 자리에서 거리를 말합니다

같은 패킷인데 TTL 이 다릅니다.

```bash
나간 것   : ttl 3 , id 47851 , 포트 33441
인용된 것 : ttl 1 , id 47851 , 포트 33441
```

`id` 가 같으니 같은 패킷입니다. 그런데 나갈 때 3 이던 것이 인용에서는 1 입니다.

**인용은 그 라우터에 도착했을 때의 상태**이기 때문입니다. 3 으로 출발해 홉 둘을 지나며 `3 → 2 → 1` 로 깎였고, 세 번째 라우터가 1 을 받아 0 으로 만들고 폐기하면서 받은 그대로 인용했습니다.

그러니 인용된 TTL 은 **"얼마나 남았나"가 아니라 "얼마나 왔나"** 를 거꾸로 알려 줍니다. 출발값에서 빼면 지나온 홉 수가 나옵니다.

**돌아오는 ICMP 자신의 TTL** 도 같은 일을 합니다.

```bash
192.168.0.1    가 보낸 ICMP : ttl 64
10.204.127.21  가 보낸 ICMP : ttl 253
```

`253` 은 255 에서 출발해 두 홉을 지난 값입니다. **그 라우터가 나에게서 두 홉 거리**라는 뜻입니다. 공유기는 바로 옆이라 출발값 64 가 그대로 도착했습니다.

같은 필드가 한 화면에서 두 가지를 말합니다. 인용 안의 TTL 은 **내 패킷이 간 거리**를, 봉투의 TTL 은 **답이 온 거리**를 가리킵니다.

### 한 번의 관찰로는 못 가릅니다

홉 2 는 네 번 연속 별표 셋이었습니다. 그래서 설정으로 막힌 것이라 읽었는데, 다섯 번째 실행에서 답했습니다.

```bash
 1  192.168.0.1 (192.168.0.1)      1.462 ms  1.108 ms  0.605 ms
 2  1.223.246.73 (1.223.246.73)    3.190 ms  2.905 ms  *
 3  10.204.127.17 (10.204.127.17)  3.167 ms  2.243 ms  1.774 ms
```

**두 번 답하고 한 번만 별표**입니다. 설정으로 막았다면 셋 다 막혔어야 합니다.

속도 제한으로 읽는 편이 맞아 보입니다. 많은 라우터가 ICMP 오류 메시지 생성에 상한을 둡니다. 앞선 실행들에서 연달아 쏘는 동안 상한을 넘겼고, 시간을 두고 다시 치니 여유가 생겨 답한 것입니다. 다만 이것도 추정이고, 확정하려면 간격을 바꿔 가며 여러 번 재야 합니다.

별표 밑에서 실제로 무슨 일이 벌어지는지는 잡아 봐야 보입니다.

![탐침이 나가고 ICMP 가 돌아오는 왕복 세 쌍, 그다음 나가기만 하고 돌아오지 않는 세 줄](./_assets/05-04.icmp-roundtrip.gif)

앞의 여섯 줄이 **왕복 세 쌍**입니다. 포트 33435·33436·33437 이 나가고 그때마다 공유기가 `time exceeded` 를 돌려줍니다. 그런데 33438 부터는 **나가기만 하고 돌아오는 줄이 없습니다.** 그것이 화면에 `* * *` 로 찍히는 것의 정체입니다.

시각을 보면 기다림도 드러납니다. 33438 이 `08.672`, 33439 가 `09.675`, 33440 이 `10.679` 로 **정확히 1초씩** 벌어져 있습니다. `-w 1` 이 정한 대기 시간을 다 쓰고 다음 탐침으로 넘어간 흔적입니다.

확실한 것은 하나뿐입니다. `* * *` 은 **"답하지 않도록 설정됨"** 과 **"지금 못 답함"** 을 구별해 주지 않습니다. [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 도 같은 말을 하는데, **그것을 읽고도 네 번 보고 단정했습니다.** 읽은 것과 몸에 붙는 것은 다릅니다.

위상 자체는 일관됐습니다. 홉 3 이 앞선 실행들과 같은 `10.204.127.17` 이니 **홉 2 가 새로 생긴 것이 아니라 원래 있었는데 안 보였던 것**입니다.

경로도 마찬가지입니다. 한 실행 안에서도 갈립니다. 탐침 셋에 서로 다른 라우터가 답했습니다.

```bash
 5  100.76.9.5 (100.76.9.5)    4.236 ms
    100.76.10.1 (100.76.10.1)  2.584 ms
    100.76.1.5 (100.76.1.5)    3.891 ms
```

[`05-02`](./05-02.AS%20안과%20AS%20사이.md) §2 가 OSPF 의 진전으로 꼽은 **"같은 비용 경로 여럿"** 이 이것입니다. 목적지까지 비용이 같은 경로가 여럿이면 하나만 고르지 않고 함께 씁니다.

실행끼리 비교하면 더 선명합니다.

| 홉 | 1차 | 2차 | 3차 |
|---|---|---|---|
| 3 | `10.204.127.17` | `10.204.127.17` | `10.204.127.21` |
| 4 | `1.213.15.45` · `1.208.12.205` | `1.213.15.45` · `1.208.12.205` | `1.208.15.45` 하나만 |

3차에서는 홉 4 가 셋 다 같은 라우터라 **갈림이 아예 안 보였습니다.** 그 실행만 봤다면 이 자리엔 라우터가 하나라고 적었을 것입니다.

탐침 셋은 자원 하나를 두 목적에 나눠 씁니다.

| 상황 | 알 수 있는 것 | 알 수 없는 것 |
|---|---|---|
| 같은 라우터가 셋 다 답 | 그 자리의 시간 변동 | 다른 경로가 있는지 |
| 다른 라우터가 하나씩 답 | 경로가 여럿이라는 사실 | 각 라우터의 변동 |

경로가 갈리는 순간 둘 다 어중간해집니다. 게다가 셋을 보내 셋이 다 달랐다면 **그것이 전부인지도 알 수 없습니다.** 제대로 재려면 탐침을 계속 보내야 하고, 그 일을 하는 도구가 `mtr` 입니다.

### 호스트도 ICMP 를 만듭니다

traceroute 와 무관한 패킷 한 쌍이 중간에 잡혔는데, 하필 종료 신호와 똑같은 메커니즘을 보여 주었습니다.

```bash
17:18:40  IP 192.168.0.184 > 192.168.0.1: ICMP 192.168.0.184 udp port 14212 unreachable
              IP 192.168.0.1.53 > 192.168.0.184.14212:  [|domain]
```

아래에서 위로 읽으면 이렇게 됩니다.

```bash
[1] 이 기계의 어떤 프로그램이 DNS 질의를 보냅니다      (공유기의 53번 포트로)
[2] 응답을 기다리다 포기하고 소켓을 닫습니다
[3] 뒤늦게 DNS 응답이 14212번 포트로 도착합니다
[4] 그 포트를 듣는 소켓이 없으니 port unreachable 을 돌려보냅니다
```

**traceroute 가 이제 멈춰도 된다고 판단하는 그 신호와 정확히 같은 메커니즘**입니다. 다만 방향이 반대라, 여기서는 **이 기계가 ICMP 를 만들어 보냈습니다.**

ICMP 는 라우터만 쓰는 것이 아니라 호스트도 씁니다. [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §5 첫 문장이 "호스트와 라우터가 네트워크 계층 정보를 서로 주고받는 데 쓰인다"고 적은 그대로인데, 읽을 때는 그냥 지나간 문장이었습니다. 실물을 보고서야 **"호스트와"** 가 왜 앞에 붙어 있는지 알았습니다.



## 3. Open vSwitch 흐름 표

> 흐름 표에 일치하는 항목이 없을 때 무엇이 벌어지는지를 손으로 확인할 자리입니다. 아직 하지 않았습니다.

### 확인하려는 것

- 흐름 표는 L2~L4 열두 필드로 일치를 걸고, 동작이 없는 항목이 곧 폐기입니다 — [`04-04`](./04-04.IPv6%20와%20일반화%20포워딩.md) §3 · [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §3
- 어느 항목과도 일치하지 않은 패킷은 폐기가 아니라 **컨트롤러로 올라갑니다** — [`05-03`](./05-03.제어를%20밖으로%20빼고%20망을%20들여다봅니다.md) §3

OrbStack 우분투(arm64)에 `openvswitch-switch` 를 올려 브리지 하나와 네임스페이스 둘을 만들고, `ovs-ofctl` 로 규칙을 직접 심는 순서로 갑니다. 예측할 자리는 **흐름 표가 비어 있을 때 `ping` 이 통하는가** 입니다. 직관과 어긋나는 답이 나오는 자리라 먼저 적어 두고 확인합니다.

절차와 결과는 채워지는 대로 이 절에 `###` 로 덧붙입니다.



## 이 편에서 얻은 관찰 규칙

> 내용보다 방법에 대해 배운 것이 많습니다. 다음에 다른 것을 잴 때도 쓰입니다.

| 규칙 | 어디서 나왔나 |
|---|---|
| 변수를 하나 움직여야 구별되지 않던 두 해석이 갈립니다 | §2 — `-q 3` 만 봐서는 못 가립니다 |
| 한 번의 관찰은 잠정값입니다 | §2 — 네 번 보고 단정했다가 다섯 번째에 뒤집혔습니다 |
| 같은 명령을 여러 번 쳐야 경로 다중성이 보입니다 | §2 — 실행마다 홉이 달라졌습니다 |
| 필터가 무엇을 거르는지 알고 써야 합니다 | §2 — 한 방향만 잡으면 라우터 IP 가 안 보입니다 |
| 잡을 인터페이스는 관례로 짐작하지 않습니다 | 아래 치트시트 첫 줄 |

마지막 둘을 덧붙이면, `udp and dst host 1.1.1.1` 은 **나가는 탐침만** 잡습니다. 돌아오는 ICMP 는 UDP 도 아니고 출발지도 목적지 주소가 아니라 걸러집니다. 그리고 맥에서 `en0` 이 Wi-Fi 라는 것은 관례일 뿐이라, 목적지를 주고 물어야 실제로 나가는 인터페이스가 나옵니다.



## 실습 치트시트

| 하려는 것 | 명령 |
|---|---|
| 목적지로 나가는 인터페이스 판별 | `route -n get 1.1.1.1 \| grep interface` |
| 나가는 탐침만 잡기 (TTL 포함) | `tcpdump -n -v -i <인터페이스> -c 24 'udp and dst host 1.1.1.1'` |
| 양방향 잡기 (라우터 IP 포함) | `tcpdump -n -v -i <인터페이스> -c 24 'icmp or (udp and dst host 1.1.1.1)'` |
| 짧게 돌리기 | `traceroute -m 3 -w 1 1.1.1.1` |
| 탐침 하나로 줄이기 | `traceroute -m 3 -w 1 -q 1 1.1.1.1` |

`<인터페이스>` 는 첫 줄로 매번 구합니다. 이 기계는 한나절 사이에 `en5` 에서 `en0` 으로 바뀌었습니다. `-w 1` 은 응답 대기를 1초로 줄입니다. 기본값이면 답 없는 홉 하나에서 15초를 기다립니다. `tcpdump` 는 Wireshark 가 설치한 ChmodBPF 덕분에 `sudo` 없이 돕니다.
