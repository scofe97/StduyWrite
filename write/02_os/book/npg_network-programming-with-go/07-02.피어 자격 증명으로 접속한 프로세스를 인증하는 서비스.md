# 피어 자격 증명으로 접속한 프로세스를 인증하는 서비스

---

> 7장 뒷부분은 Unix 도메인 소켓에서 운영체제 커널이 보증하는 피어 자격 증명(SO_PEERCRED)을 조회하여 접속한 프로세스의 신원을 검증하고 권한을 판정하는 인증 서비스를 구축합니다. 파일 시스템 권한을 넘어 프로세스 실행 사용자의 보조 그룹까지 식별해 무단 접근을 차단하는 기법을 다룹니다.



## 핵심 요약

> 이 편이 매달린 하나의 생각은, Unix 도메인 소켓 통신에서 커널이 직접 보증하는 피어 자격 증명을 조회하면 클라이언트가 위조할 수 없는 프로세스 신원 기반의 강력한 접근 제어를 구현할 수 있다는 사실입니다.

네트워크 소켓과 달리 Unix 도메인 소켓은 동일한 호스트의 단일 커널 안에서 실행되므로, 커널이 상대 프로세스의 PID, UID, GID 정보를 직접 추적하고 보증합니다. Go 표준 라이브러리의 `net.Conn` 인터페이스는 플랫폼 중립적 추상화이므로 저수준 소켓 옵션을 다루지 못합니다. 따라서 구체 타입인 `*net.UnixConn` 의 `File()` 메서드로 파일 디스크립터를 얻은 뒤 `golang.org/x/sys/unix` 패키지의 `GetsockoptUcred` 시스템 호출을 실행해야 합니다.

서비스는 실행 시 인가할 그룹 이름을 명령줄 인자로 받아 [`os/user.LookupGroup`](https://pkg.go.dev/os/user#LookupGroup) 으로 숫자 GID 집합(`map[string]struct{}`)을 미리 구축합니다. 접속이 수락될 때마다 커널로부터 얻은 UID 로 사용자의 모든 보조 그룹 목록을 조회하고 허용 목록과 대조하여 인가된 프로세스에는 환영 메시지를 보내며 미인가 프로세스는 통보 후 즉시 연결을 종료합니다.



## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. 피어 자격 증명(SO_PEERCRED)이 네트워크 소켓과 달리 위조 불가능한 이유와 플랫폼별 제약을 설명할 수 있습니다.
2. `net.Conn` 대신 `*net.UnixConn` 과 `File()` 메서드를 사용해 파일 디스크립터를 추출하는 이유를 밝힐 수 있습니다.
3. `user.LookupGroup` 과 `map[string]struct{}` 를 활용해 그룹 이름 기반의 인가 목록을 구성할 수 있습니다.
4. 접속한 피어의 UID 로부터 보조 그룹 목록을 조회해 다중 그룹 멤버십을 검증하는 인증 로직을 구현할 수 있습니다.
5. 인터럽트 시그널 수신 시 리스너를 닫아 파일 시스템의 소켓 파일을 안전하게 회수하는 절차를 설명할 수 있습니다.



## 1. 커널이 접속한 프로세스의 신원을 알려 준다

> 원격 네트워크 소켓은 상대방의 OS 사용자나 프로세스 신원을 검증할 수 없지만, 동일 커널에서 동작하는 Unix 도메인 소켓은 커널이 상대방 프로세스의 자격 증명을 직접 보증합니다.

### 네트워크 소켓의 신원 확인 한계와 피어 자격 증명

TCP 나 UDP 기반의 네트워크 통신에서는 IP 주소와 포트 번호만 패킷 헤더에 실려 전달됩니다. 패킷을 보낸 원격 호스트 내부에서 어떤 사용자가 어떤 프로세스 ID 로 소켓을 열었는지는 네트워크 프로토콜 계층에서 전혀 알 수 없습니다. 따라서 원격 클라이언트를 식별하려면 토큰, 패스워드, 상호 TLS(mTLS) 인증서 같은 애플리케이션 수준의 인증 메커니즘을 별도로 구축해야 합니다.

반면 [Unix 도메인 소켓](./07-01.Unix%20도메인%20소켓은%20파일%20경로로%20묶이고%20세%20가지%20타입이%20경계를%20다르게%20다룬다.md)은 동일한 머신 내부의 프로세스끼리 통신합니다. 두 프로세스 모두 하나의 운영체제 커널 통제 아래에 놓여 있으므로, [커널 소켓 버퍼](../../../08_cloud/book/networking-and-kubernetes/02-01.커널이%20패킷을%20주고받는%20자리%20—%20소켓·인터페이스·veth·브리지.md)를 거쳐 데이터를 주고받을 때 커널은 연결 양 끝단 프로세스의 소유자와 프로세스 ID 를 명확히 알고 있습니다.

이렇게 커널이 보관하는 상대 프로세스의 신원 정보를 **피어 자격 증명(Peer Credentials)** 이라고 부릅니다. 클라이언트가 자발적으로 보낸 값이 아니라 커널이 연결 수립 시점에 직접 채워 넣은 값이므로, 클라이언트 프로세스가 자신의 UID 나 PID 를 속이거나 위조할 수 없습니다.

소켓에는 `getsockopt` 와 `setsockopt` 시스템 호출로 읽고 쓰는 설정값인 소켓 옵션이 있습니다. `SO_REUSEADDR`·`SO_KEEPALIVE`·`SO_LINGER` 가 그 예시이며 이름 앞의 `SO_` 는 socket option 의 줄임입니다. `SO_PEERCRED` 는 그중 읽기 전용 옵션으로 연결 반대편 프로세스의 자격 증명을 커널에 묻습니다.

돌려주는 값은 상대가 `connect(2)` 를 호출한 시점의 신원입니다([unix(7)](https://man7.org/linux/man-pages/man7/unix.7.html)). 서버 쪽이면 `listen(2)` 시점이고 `socketpair(2)` 로 만든 쌍이면 생성 시점을 따릅니다. 접속한 뒤 클라이언트가 권한을 바꾸거나 소켓을 다른 프로세스에 넘겨도 처음 값이 그대로 나옵니다.

이 값을 속이는 길은 그 사용자로 실제 프로세스를 실행하는 것뿐입니다. root 권한이 있으면 원하는 UID 로 변경한 뒤 접속할 수 있습니다. 이것은 위조가 아니라 신원을 실제로 획득한 상태이므로 커널 입장에서는 정상 동작에 속합니다.

### 플랫폼별 제약 사항

피어 자격 증명을 다루는 시스템 호출 인터페이스는 운영체제마다 다릅니다.

* **Linux**: 소켓 레벨 옵션인 [`SO_PEERCRED`](https://man7.org/linux/man-pages/man7/unix.7.html) 를 지원합니다. 시스템 호출 결과로 프로세스 ID(`Pid`), 유효 사용자 ID(`Uid`), 유효(effective) 그룹 ID(`Gid`)를 담은 `ucred` 구조체를 돌려줍니다.
* **macOS (Darwin) 및 BSD**: `SO_PEERCRED` 대신 `LOCAL_PEERCRED` 소켓 옵션을 사용하며 반환 구조체 역시 `xucred` 로 다릅니다.
* **Windows**: Unix 도메인 소켓(`AF_UNIX`) 주소 체계는 지원하지만 피어 자격 증명을 조회하는 표준 소켓 옵션은 지원하지 않습니다.

따라서 Linux 전용 시스템 호출인 `unix.GetsockoptUcred` 를 사용할 때는 Go 파일 상단에 빌드 제약 지시자 [`//go:build linux`](https://pkg.go.dev/cmd/go#hdr-Build_constraints) 를 명시하거나 파일명을 `allowed_linux.go` 처럼 OS 접미사로 분리해야 합니다.

### net.Conn 대신 *net.UnixConn 과 File() 이 필요한 이유

Go 의 `net.Conn` 인터페이스는 플랫폼 독립적인 최소 입출력 계약만을 정의합니다. 운영체제 고유의 소켓 옵션을 제어하는 메서드는 `net.Conn` 에 포함되어 있지 않습니다. 따라서 피어 자격 증명을 추출하려면 리스너에서 구체 타입인 `*net.UnixConn` 포인터를 받아야 합니다. `net.Conn` 과 구체 타입의 경계는 [Go net 문서 01-01](../../../01_language/docs/go/net/01-01.Conn·Listener·PacketConn·Addr.md) §3 이 다룹니다.

운영체제 커널의 소켓 옵션 조회 함수를 부르려면 기본 파일 디스크립터(fd) 번호가 필요합니다. `conn.File()` 메서드를 호출하면 소켓과 연결된 [`*os.File`](https://pkg.go.dev/net#UnixConn.File) 객체를 얻을 수 있고 `int(file.Fd())` 로 파일 디스크립터 정수값을 꺼냅니다.

여기서 주의할 점이 있습니다. `conn.File()` 은 내부적으로 `dup` 시스템 호출을 사용하여 기존 소켓 디스크립터를 복제한 새로운 파일 객체를 반환합니다. 복제된 파일 디스크립터는 자동으로 닫히지 않으므로, 사용이 끝난 직후 `defer func() { _ = file.Close() }()` 로 명시적으로 닫지 않으면 파일 디스크립터 누수가 발생합니다.

프로세스가 파일이나 소켓을 열면 커널은 대상 소켓 객체를 프로세스의 fd 테이블에 등록하고 번호를 돌려줍니다. `dup` 은 같은 커널 객체를 가리키는 번호를 하나 더 만듭니다. 커널은 그 객체를 가리키는 번호가 모두 닫혀야 객체를 해제합니다.

`*net.UnixConn` 은 자기 fd 를 Go 런타임의 네트워크 폴러에 등록해 관리하고 `Close()` 때 닫습니다. `File()` 이 같은 번호를 그대로 내주면 주인이 둘이 되어 한쪽의 닫기가 다른 쪽의 번호를 없앱니다. Go 문서도 `c` 를 닫아도 `f` 에 영향이 없고 `f` 를 닫아도 `c` 에 영향이 없으며 다 쓰면 `f` 를 닫는 것은 호출자의 책임이라고 적고 있습니다([UnixConn.File](https://pkg.go.dev/net#UnixConn.File)).

```pseudocode
복제하지 않고 같은 번호를 넘긴다면
1. conn 이 7번 fd 를 가지고 있다
2. File() 이 같은 7번을 *os.File 에게도 준다      (주인 둘, 번호 하나)
3. 인증 확인 후 file.Close() → 7번이 닫히고 소켓이 해제된다
4. conn 은 아직 7번을 쥐고 있다고 믿는다
5. 다음 Accept 에서 커널이 비어 있는 7번을 새 접속에 다시 준다
6. 옛 conn 이 7번으로 Write 하면 새 접속에 데이터가 간다
```

```pseudocode
dup 으로 복제한다면
1. conn 은 7번, *os.File 은 dup 으로 받은 9번   (주인 둘, 번호 둘, 소켓 하나)
2. file.Close() → 9번만 닫힌다. 7번이 남았으니 소켓은 그대로다
3. conn 은 7번으로 통신하고, 끝나면 conn.Close() → 마지막 번호 → 소켓 해제
```

위 5번 단계에서 보듯 커널은 새 fd 에 비어 있는 가장 작은 번호를 배정하는 POSIX 규칙을 따릅니다. 만약 복제한 fd 를 닫지 않고 방치하면 두 가지 중대한 부작용이 발생합니다.

첫째는 fd 고갈입니다. 프로세스가 열 수 있는 fd 수에는 상한(`ulimit -n`, 흔히 1024)이 있습니다. 접속마다 하나씩 새면 언젠가 `Accept` 가 "too many open files"(EMFILE)로 실패합니다.

둘째는 연결이 끝나지 않는 문제입니다. 서버가 `conn.Close()` 를 불러도 복제 번호가 소켓을 붙잡고 있어 소켓이 해제되지 않습니다. 그 결과 클라이언트는 정상적인 EOF 를 받지 못합니다.

복제본을 제때 닫아도 남는 부작용이 하나 있습니다. Go 는 소켓을 논블로킹 모드로 열어 네트워크 폴러로 다룹니다. `File()` 은 번호만 복제하고 이 모드를 건드리지 않습니다. 모드를 바꾸는 쪽은 그 뒤에 부르는 `file.Fd()` 로, 번호를 돌려주기 전에 디스크립터를 블로킹 모드로 되돌립니다([go1.25.1 os/file_unix.go](https://github.com/golang/go/blob/go1.25.1/src/os/file_unix.go#L68-L84)).

블로킹 여부(`O_NONBLOCK`)는 fd 번호마다 따로 있는 값이 아니라 두 번호가 함께 가리키는 커널 객체에 붙은 값입니다([dup(2)](https://man7.org/linux/man-pages/man2/dup.2.html)). 그래서 복제본에서 바꾼 모드는 원본 `conn` 에도 적용되고 복제본을 닫은 뒤에도 남습니다. go1.25.1 로 빌드해 Linux 에서 확인하면 `conn.File()` 직후의 `conn` 은 논블로킹 그대로였고, `file.Fd()` 를 부른 뒤부터 블로킹이었습니다.

블로킹이 된 `conn` 에서는 읽기 데드라인이 듣지 않습니다. 같은 실험에서 `SetReadDeadline` 으로 200ms 를 걸고 `Read` 를 불렀을 때, `Fd()` 를 부르기 전의 연결은 200ms 뒤 `i/o timeout` 으로 돌아왔습니다. `Fd()` 를 부른 뒤의 연결은 2초가 지나도록 돌아오지 않다가 상대가 데이터를 보낸 뒤에야 돌아왔습니다. Go 문서도 `Fd` 를 부르면 그 파일의 데드라인 메서드가 동작을 멈춘다고 적고 대부분의 용도에는 `SyscallConn` 을 권합니다([os.File.Fd](https://pkg.go.dev/os#File.Fd)).

다음 절의 `Allowed` 는 `File()` 과 `Fd()` 를 차례로 부르므로 이 함수를 거친 연결은 블로킹 모드로 남습니다. 인증을 마친 연결에 데드라인을 걸어 쓸 서비스라면 이 점을 계산에 넣어야 합니다.

대안으로 `conn.SyscallConn()` 이 주는 `syscall.RawConn` 의 `Control` 메서드를 쓰면 복제 없이 원래 fd 를 콜백 안에서 잠깐 빌려 쓸 수 있습니다([UnixConn.SyscallConn](https://pkg.go.dev/net#UnixConn.SyscallConn)).

이 경로는 `Fd()` 를 거치지 않아 소켓의 모드를 바꾸지 않습니다. 같은 실험에서 `Control` 안에서 자격 증명을 조회한 연결은 논블로킹 그대로였고 데드라인도 200ms 에 맞춰 동작했습니다. `Allowed` 에서 자격 증명을 조회하는 부분만 이 방식으로 옮기면 다음과 같습니다.

```go
// 복제하지 않고 원래 fd 를 콜백 안에서만 빌려 쓴다
rc, err := conn.SyscallConn()
if err != nil {
	log.Println(err)
	return false
}

var (
	ucred *unix.Ucred
	cerr  error
)
// fd 는 콜백이 도는 동안에만 유효하므로 밖으로 들고 나가지 않는다
err = rc.Control(func(fd uintptr) {
	ucred, cerr = unix.GetsockoptUcred(int(fd), unix.SOL_SOCKET, unix.SO_PEERCRED)
})
if err != nil || cerr != nil {
	log.Println(err, cerr)
	return false
}
```

### 자격 증명 조회와 보조 그룹 검증 함수

아래 코드는 클라이언트의 Unix 도메인 소켓 연결을 받아 커널로부터 피어 자격 증명을 조회하고 허용 그룹에 속하는지 판별하는 함수입니다.

```go
//go:build linux

package auth

import (
	"log"
	"net"
	"os/user"
	"strconv"

	"golang.org/x/sys/unix"
)

func Allowed(conn *net.UnixConn, groups map[string]struct{}) bool {
	if conn == nil || groups == nil || len(groups) == 0 {
		return false
	}

	// underlying *os.File 복제 획득
	file, err := conn.File()
	if err != nil {
		log.Println(err)
		return false
	}
	// 복제된 파일 디스크립터 누수 방지
	defer func() { _ = file.Close() }()

	var ucred *unix.Ucred

	for {
		// Linux 커널에 SO_PEERCRED 소켓 옵션 질의
		ucred, err = unix.GetsockoptUcred(int(file.Fd()), unix.SOL_SOCKET, unix.SO_PEERCRED)
		if err == unix.EINTR {
			// 시스템 호출이 시그널에 의해 인터럽트되면 재시도
			continue
		}
		if err != nil {
			log.Println(err)
			return false
		}
		break
	}

	// UID 숫자를 10진수 문자열로 변환하여 사용자 정보 조회
	u, err := user.LookupId(strconv.Itoa(int(ucred.Uid)))
	if err != nil {
		log.Println(err)
		return false
	}

	// 사용자가 속한 모든 보조 그룹 ID 목록 조회
	gids, err := u.GroupIds()
	if err != nil {
		log.Println(err)
		return false
	}

	// 허용 그룹 맵과 대조
	for _, gid := range gids {
		if _, ok := groups[gid]; ok {
			return true
		}
	}

	return false
}
```

시스템 호출 [`unix.GetsockoptUcred`](https://pkg.go.dev/golang.org/x/sys/unix#GetsockoptUcred) 는 소켓 레벨 상수 `unix.SOL_SOCKET` 과 옵션 이름 `unix.SO_PEERCRED` 를 받습니다. 만약 호출 도중 OS 시그널이 전달되어 `unix.EINTR` 오류가 발생하면 루프를 통해 안전하게 재시도합니다.

반환된 `ucred.Uid` 는 `uint32` 타입입니다. Go 표준 라이브러리의 [`os/user.LookupId`](https://pkg.go.dev/os/user#LookupId) 함수는 문자열 형태의 UID 를 요구하므로 `strconv.Itoa(int(ucred.Uid))` 로 10진수 문자열로 변환하여 넘깁니다.

조회된 `*user.User` 객체에서 `u.GroupIds()` 를 호출하면 해당 사용자가 속한 기본 그룹뿐만 아니라 보조 그룹들의 GID 목록(`[]string`)을 모두 얻을 수 있습니다. 사용자의 그룹 중 하나라도 허용 목록에 포함되어 있으면 `true` 를 반환하여 인증을 통과시킵니다.

`ucred` 구조체에는 GID 필드가 하나뿐입니다. 사용자는 기본 그룹 하나와 보조 그룹 여러 개에 속할 수 있으므로 `ucred.Gid` 하나만 허용 목록과 대조하면 보조 그룹 소속을 놓치게 됩니다. 예를 들어 기본 그룹이 `alice` 이고 보조 그룹으로 `staff` 에 속한 사용자는 `Gid` 비교만으로는 접근이 거부됩니다.

본문 코드는 `ucred` 에서 `Uid` 만 취하고 `ucred.Gid` 는 읽지 않습니다. 대신 검증에 쓰이는 그룹 목록은 커널이 아니라 사용자 DB(`/etc/group` 또는 NSS)에서 가져옵니다.

| 단계 | 정보 출처 | 성질 |
| :--- | :--- | :--- |
| 접속한 프로세스의 UID | 커널(`SO_PEERCRED`) | 클라이언트가 바꿀 수 없습니다. |
| 그 UID 의 그룹 목록 | 사용자 DB(`u.GroupIds()`) | 장부에 적힌 소속이지 프로세스가 지금 가진 그룹이 아닙니다. |

이처럼 정보 출처가 갈리면 장부와 프로세스의 실제 상태가 어긋날 수 있습니다. 방금 그룹에 추가돼 아직 다시 로그인하지 않은 사용자의 프로세스는 그 그룹을 갖지 못하지만, 이 코드는 장부를 확인하므로 인증을 통과시킵니다. 프로세스가 실제로 가진 보조 그룹이 필요하면 Linux 4.13 부터 제공하는 `SO_PEERGROUPS` 소켓 옵션으로 얻습니다([커널 커밋 28b5ba2aa0f5](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/commit/?id=28b5ba2aa0f55d80adb2624564ed2b170c19519e)). 이 편의 코드는 이 옵션을 쓰지 않습니다.



## 2. 그룹 이름을 그룹 ID 로 바꿔 허용 목록을 만든다

> 관리자가 읽고 지정하기 편한 텍스트 그룹 이름을 시스템 데이터베이스에서 조회하여 빠른 멤버십 판정이 가능한 숫자 GID 집합으로 변환합니다.

### 그룹 이름과 그룹 ID 의 대응 관계

Linux 시스템 관리자는 통상 `users`, `staff`, `admin` 같은 사람이 읽기 쉬운 문자열 그룹 이름을 사용합니다. 그러나 커널 내부와 프로세스 자격 증명 체계에서는 모든 권한을 정수 형태의 그룹 ID(GID)로 식별합니다.

이 둘 사이의 매핑 정보는 전통적으로 `/etc/group` 파일이나 NSS(Name Service Switch)를 통한 중앙 디렉터리 서비스에 저장됩니다. 서비스 시작 시 명령줄 인자로 전달받은 문자열 그룹 이름을 미리 숫자 GID 로 변환해 두면 접속마다 불필요한 시스템 조회 비용을 치르지 않고 효율적으로 대조할 수 있습니다.

Linux 그룹에는 하위 그룹이 없습니다. 그룹 안에 들어가는 대상은 사용자뿐이며 그룹끼리는 계층 구조 없이 서로 나란합니다. **보조 그룹(supplementary group)** 은 그룹의 자식이 아니라 한 사용자가 기본 그룹 외에 추가로 속한 그룹을 부르는 이름입니다.

### LookupGroup 과 map[string]struct{} 집합 자료구조

Go 표준 라이브러리의 [`os/user.LookupGroup`](https://pkg.go.dev/os/user#LookupGroup) 함수는 그룹 이름을 인자로 받아 시스템 데이터베이스를 조회하고 `*user.Group` 객체를 반환합니다. 이 객체의 `Gid` 필드에 해당 그룹의 숫자 ID 문자열이 담겨 있습니다.

조회한 GID 들은 인가 목록으로 관리해야 합니다. Go 에서는 별도의 Set 자료형을 기본 제공하지 않으므로, 맵의 값(value) 타입을 빈 구조체 `struct{}` 로 지정한 `map[string]struct{}` 패턴을 사용합니다. `struct{}` 는 메모리를 0바이트 소비하므로 불필요한 메모리 할당 없이 O(1) 시간 복잡도로 키 존재 여부를 검사할 수 있습니다.

| 결정 | 이유 |
| :--- | :--- |
| 이름을 숫자 GID 로 바꿉니다. | 커널과 `u.GroupIds()` 가 주는 값이 숫자이기 때문입니다. `staff` 같은 이름은 `/etc/group` 에만 있는 표시입니다. |
| 시작할 때 한 번 바꿔 둡니다. | 접속마다 사용자 DB 를 다시 조회하는 비용을 없앱니다. |
| 집합(`map[string]struct{}`)에 넣습니다. | 허용 그룹이 여러 개일 수 있어 각 그룹의 허용 여부를 상수 시간에 묻기 위해서입니다. |

### 플래그 안내와 그룹 이름 파싱 구현

아래 코드는 서비스 실행 시 명령줄 인자를 파싱하고 사용법을 안내하는 `init()` 함수와 그룹 이름 목록을 GID 집합으로 변환하는 `parseGroupNames` 함수입니다.

```go
package main

import (
	"flag"
	"fmt"
	"log"
	"net"
	"os"
	"os/signal"
	"os/user"
	"path/filepath"

	"github.com/awoodbeck/gnp/ch07/creds/auth"
)

func init() {
	// 사용자가 올바른 인자를 전달하지 않았을 때 출력할 사용법 정의
	flag.Usage = func() {
		_, _ = fmt.Fprintf(flag.CommandLine.Output(),
			"Usage:\n\t%s <group names>\n", filepath.Base(os.Args[0]))
		flag.PrintDefaults()
	}
}

// 그룹 이름 슬라이스를 받아 GID 를 키로 갖는 맵으로 변환
func parseGroupNames(args []string) map[string]struct{} {
	groups := make(map[string]struct{})
	for _, arg := range args {
		grp, err := user.LookupGroup(arg)
		if err != nil {
			// 존재하지 않는 그룹 이름은 로깅 후 건너뜀
			log.Println(err)
			continue
		}
		// GID 를 집합 맵에 등록
		groups[grp.Gid] = struct{}{}
	}
	return groups
}
```

`parseGroupNames` 함수는 전달된 각 인자마다 `user.LookupGroup` 을 호출합니다. 만약 시스템에 등록되지 않은 그룹 이름이 들어오면 에러를 출력하고 해당 항목을 건너뜁니다. 유효한 그룹이면 `grp.Gid` 를 추출하여 `groups` 맵에 키로 등록하고 완성된 맵을 반환합니다.



## 3. 접속마다 자격 증명을 보고 허용하거나 끊는다

> 소켓 리스너에서 새 연결을 받아 피어 자격 증명을 대조하고 허용 여부에 따라 맞춤형 응답을 전송한 뒤 미인가 연결을 단호하게 차단합니다.

![피어 자격 증명 기반 프로세스 인증 흐름](./_assets/07-02.peer-cred-auth.svg)

### 서비스 메인 함수와 소켓 생애주기 관리

Unix 도메인 소켓 서비스는 파일 시스템에 실제 소켓 파일 노드를 생성합니다. 만약 서비스 프로세스가 비정상 종료되거나 Ctrl+C 같은 인터럽트 시그널을 받고 소켓 파일을 지우지 못한 채 죽으면, 다음번 실행 시 `bind: address already in use` 오류가 발생합니다.

따라서 서비스는 `os.Interrupt` 시그널을 비동기 채널로 등록하고 전용 고루틴에서 감청해야 합니다. 시그널이 도착했을 때 리스너 객체의 `s.Close()` 를 명시적으로 호출해야 Go 런타임이 파일 시스템에 남아 있는 소켓 파일을 안전하게 삭제(unlink)합니다.

### 접속 수락 및 인증 분기 구현

아래 코드는 리스너를 열고 들어오는 클라이언트 접속마다 피어 자격 증명을 검증하는 메인 서버 루프입니다.

```go
func main() {
	flag.Parse()

	// 명령줄 인자로 전달된 그룹 이름들을 GID 집합으로 변환
	groups := parseGroupNames(flag.Args())
	socket := filepath.Join(os.TempDir(), "creds.sock")
	addr, err := net.ResolveUnixAddr("unix", socket)
	if err != nil {
		log.Fatal(err)
	}

	// Unix 도메인 소켓 리스너 개설
	s, err := net.ListenUnix("unix", addr)
	if err != nil {
		log.Fatal(err)
	}

	// 인터럽트 시그널(Ctrl+C) 감청 채널 준비
	c := make(chan os.Signal, 1)
	signal.Notify(c, os.Interrupt)

	// 시그널 수신 시 리스너를 닫아 소켓 파일을 정상 정리하는 고루틴
	go func() {
		<-c
		_ = s.Close()
	}()

	fmt.Printf("Listening on %s ...\n", socket)

	for {
		// net.Conn 대신 *net.UnixConn 을 얻기 위해 AcceptUnix 호출
		conn, err := s.AcceptUnix()
		if err != nil {
			break
		}

		// 피어 자격 증명 기반 인가 검증
		if auth.Allowed(conn, groups) {
			_, err = conn.Write([]byte("Welcome\n"))
			if err == nil {
				// 데모는 연결을 닫지도 넘기지도 않고 다음 접속으로 넘어간다
				continue
			}
		} else {
			// 미인가 클라이언트에게 거부 메시지 전송
			_, err = conn.Write([]byte("Access denied\n"))
		}

		if err != nil {
			log.Println(err)
		}
		// 미인가 클라이언트 또는 전송 실패 연결 종료
		_ = conn.Close()
	}
}
```

메인 루프는 일반적인 `Accept()` 대신 `s.AcceptUnix()` 를 호출하여 구체 타입 `*net.UnixConn` 을 얻습니다. 그 후 앞서 작성한 `auth.Allowed(conn, groups)` 함수를 호출하여 접속한 프로세스의 자격 증명을 검증합니다.

인가된 클라이언트에게는 `"Welcome\n"` 메시지를 전송합니다. 실제 서비스라면 여기서 독립 고루틴을 띄워 비즈니스 로직을 수행하도록 연결을 넘기고 `continue` 문을 통해 소켓 닫기를 건너뜁니다. 반대로 허용 목록에 없는 클라이언트에게는 `"Access denied\n"` 메시지를 보낸 뒤 즉시 `conn.Close()` 를 호출하여 연결을 단호하게 끊어 버립니다.

이 데모 코드는 허용된 연결을 아무 데도 넘기지 않습니다. 연결 객체는 다음 반복에서 버려지지만 fd 는 열린 채 남습니다. Go 의 연결 객체에는 GC 가 수거할 때 fd 를 닫는 finalizer 가 붙어 있지만 언제 돌지 모르므로 기댈 수 없습니다.

그동안 허용 접속이 쌓이면 앞서 살펴본 fd 상한에 닿아 `AcceptUnix` 가 실패하고 루프가 `break` 로 끝나 서버가 멈춥니다. 클라이언트 쪽에서는 `Welcome` 뒤 아무런 후속 응답을 받지 못합니다. 서버가 그 연결을 읽지 않으므로 클라이언트가 계속 보내면 수신 버퍼가 차고 쓰기가 막힙니다.

실제 서비스에서는 아래와 같이 전담 고루틴을 띄워 연결을 처리하고 종료 시 닫도록 구현합니다.

```go
if auth.Allowed(conn, groups) {
	// 연결은 처리 고루틴이 맡아 끝나면 닫는다
	go func(c *net.UnixConn) {
		defer func() { _ = c.Close() }()
		_, _ = c.Write([]byte("Welcome\n"))
		// 이후 요청 처리
	}(conn)
	continue
}
```




## 4. netcat 으로 서비스를 시험한다

> 범용 네트워킹 유틸리티 netcat 을 사용하여 Unix 도메인 소켓에 접속하고 프로세스 실행 그룹을 전환하며 정상 접속과 접근 거부 동작을 직접 관측합니다.

### netcat 도구 준비와 소켓 접속 플래그

[TCP 바이트 스트림](./04-01.TCP%20는%20경계%20없는%20바이트%20흐름이라%20읽는%20쪽이%20메시지를%20자른다.md)이나 [UDP 데이터그램](./05-01.UDP%20는%20연결%20없이%20보내고,%20소켓%20하나가%20누구에게서든%20받는다.md)을 테스트할 때 널리 쓰이는 `netcat`(`nc`)은 Unix 도메인 소켓 연결도 기본 지원합니다. Linux 배포판에 따라 패키지 관리자로 쉽게 설치할 수 있습니다.

* Debian 및 Ubuntu: `sudo apt install netcat-openbsd`
* CentOS 및 RHEL: `sudo dnf install nmap-ncat`

설치가 완료되면 `nc` 명령에 `-U` 플래그를 넘겨 Unix 도메인 소켓 파일 경로로 접속할 수 있습니다.

### 서비스 기동과 허용 그룹 등록

먼저 서비스 바이너리를 빌드하거나 `go run` 으로 실행하면서 허용할 그룹 이름을 인자로 넘깁니다.

```bash
go run . -- users staff
```

명령을 실행하면 `Listening on /tmp/creds.sock ...` 로그가 출력되며 서버가 대기 상태에 들어갑니다. 이 예제에서는 `users` 또는 `staff` 그룹에 속한 사용자 프로세스만 연결을 허용하도록 설정했습니다. 만약 해당 환경에 이 그룹들이 없다면 시스템의 `/etc/group` 에 등록된 임의의 유효한 그룹 이름을 지정할 수 있습니다. 리스너는 `/tmp/creds.sock` 파일에 정상적으로 바인딩되어 연결을 대기합니다.

### sudo -g 를 이용한 그룹 전환과 인증 검증

현재 사용자가 실행한 셸에서 그대로 접속하면 자신의 기본 그룹으로 접속하게 됩니다. 서비스를 테스트하기 위해 서로 다른 그룹 권한을 시뮬레이션할 때는 `sudo` 명령의 `-g` 플래그를 활용합니다. `-g` 플래그는 실행할 명령의 기본(primary) 그룹을 지정한 그룹으로 바꿉니다([sudo(8)](https://www.sudo.ws/docs/man/sudo.man/)).

먼저 허용 목록에 등록된 `staff` 그룹으로 접속을 시도합니다.

```bash
sudo -g staff -- nc -U /tmp/creds.sock
```

커널은 이 프로세스의 GID 를 `ucred.Gid` 에 담아 주지만 `auth.Allowed` 는 그 값을 읽지 않고 `Uid` 의 사용자 DB 소속만 대조합니다. 따라서 `sudo -g` 로 바꾼 그룹은 판정에 들어가지 않으며, 결과는 명령이 어느 사용자로 실행됐고 그 사용자가 장부상 어느 그룹에 속하는지로 정해집니다. `-g` 로 바꾼 그룹까지 판정에 넣으려면 `ucred.Gid` 를 함께 대조해야 합니다. 테스트 후 Ctrl+C 로 연결을 마칩니다.

이번에는 허용 목록에 없는 `nogroup` 그룹으로 전환하여 접속해 봅니다.

```bash
sudo -g nogroup -- nc -U /tmp/creds.sock
```

서버의 판정 근거는 전달된 GID 가 아니라 실행 사용자의 UID 가 가진 장부 소속입니다. 만약 해당 사용자의 사용자 DB 등록 그룹 중 허용 목록에 든 그룹이 없다면 접근이 거부됩니다. 거부 시 서버 측에서 소켓을 닫아 버리므로 클라이언트의 `nc` 프로세스 역시 즉시 종료됩니다.

### 파일 시스템 권한과 피어 자격 증명의 차이

소켓 파일에 파일 시스템 권한(`chmod 0660`, `chown`)을 부여하는 방식은 클라이언트가 커널에 `connect()` 시스템 호출을 날리는 진입 시점에 커널이 1차로 통제합니다. 소켓 파일에 대한 쓰기 권한이 없는 사용자는 연결 수립 자체가 거부됩니다.

반면 피어 자격 증명(SO_PEERCRED)은 연결이 일단 수립된 이후 애플리케이션 계층에서 상대방 프로세스의 신원을 세밀하게 검증합니다. 이를 활용하면 단일 소켓 파일 하나를 열어 두고도 접속한 사용자의 보조 그룹이나 특정 역할에 따라 동적으로 세부 접근 권한을 분기하거나 감사 로그에 정확한 호출자 프로세스 ID 를 남기는 고급 보안 아키텍처를 유연하게 구축할 수 있습니다.

| 상황 | 파일 권한만으로는 | 피어 자격 증명으로는 |
| :--- | :--- | :--- |
| 사용자마다 다른 권한을 주고 싶을 때 | 소유자·그룹·기타 세 칸뿐이라 들어올 수 있는지만 정합니다. | 같은 소켓으로 받고 UID 를 보고 읽기 전용·관리 명령처럼 나눌 수 있습니다. |
| 누가 무엇을 했는지 남기고 싶을 때 | 접속한 사람이 누구인지 서버가 모릅니다. | PID·UID 를 감사 로그에 남길 수 있습니다. |
| 파일이 없는 소켓 | [Linux 추상 소켓](./07-01.Unix%20도메인%20소켓은%20파일%20경로로%20묶이고%20세%20가지%20타입이%20경계를%20다르게%20다룬다.md)(`@이름`)은 파일이 없어 권한을 걸 곳이 없습니다. | 신원을 확인할 수단이 이것뿐입니다. |

실제 시스템에서도 두 방식의 차이가 명확히 드러납니다. [PostgreSQL 공식 문서의 peer 인증](https://www.postgresql.org/docs/current/auth-peer.html)은 로컬 접속에서 커널로부터 클라이언트의 OS 사용자 이름을 얻어 그 이름을 DB 사용자 이름으로 씁니다. 덕분에 운영체제의 `postgres` 사용자는 비밀번호 없이 DB 의 `postgres` 계정으로 곧바로 들어갑니다.

반면 Docker 의 `/var/run/docker.sock` 은 파일 권한(docker 그룹)으로만 접근을 막습니다. [Docker 공식 문서](https://docs.docker.com/engine/install/linux-postinstall/)는 docker 그룹이 root 수준의 권한을 준다고 경고합니다. 이는 문 앞 검사만 있고 소켓 내부 구분이 없을 때 생기는 대표적인 현상입니다.



## 결정 치트시트

> 로컬 소켓에서 접속한 상대를 가려 받을 때 무엇을 어디서 읽는지 정리한 기준입니다.

| 알고 싶은 것 | 수단 | 값의 출처 | 주의할 점 |
| :--- | :--- | :--- | :--- |
| 접속할 수 있는 사용자를 미리 거르기 | 소켓 파일 권한(`chmod`·`chown`) | 파일시스템 | 들어온 뒤에는 누가 들어왔는지 구분하지 못합니다. |
| 접속한 프로세스의 PID·UID·GID | `SO_PEERCRED` (`unix.GetsockoptUcred`) | 커널, 상대가 `connect(2)` 를 부른 시점의 값 | Linux 전용이고 `Gid` 는 하나뿐입니다. |
| 그 사용자가 속한 그룹 전부 | `user.LookupId` 뒤 `u.GroupIds()` | 사용자 DB(`/etc/group` 또는 NSS) | 프로세스가 지금 가진 그룹과 다를 수 있습니다. |
| 소켓 옵션을 읽을 fd (복제) | `conn.File()` 뒤 `file.Fd()` | `dup` 으로 복제한 번호 | 닫지 않으면 fd 가 새고, `Fd()` 가 원본 연결까지 블로킹 모드로 바꿉니다. |
| 소켓 옵션을 읽을 fd (복제 없이) | `conn.SyscallConn()` 의 `Control` | 원래 번호 | fd 는 콜백 안에서만 유효합니다. |

이 편의 `Allowed` 가 판정에 쓰는 값은 둘째 행의 `Uid` 와 셋째 행의 그룹 목록입니다. 둘째 행의 `Gid` 는 읽지 않습니다.



## 면접 대비

> 아래 질문에 답하면서 커널이 보증하는 값과 사용자 DB 에서 읽는 값의 경계를 정리해 보세요.

1. TCP 서버는 접속한 상대의 OS 사용자를 알 수 없는데 Unix 도메인 소켓 서버는 `SO_PEERCRED` 로 알 수 있습니다. 왜 가능하고, 이 값은 어느 시점의 신원인가요?
2. `conn.File()` 로 받은 파일을 닫지 않으면 무슨 일이 생기나요? 그리고 이어서 부르는 `file.Fd()` 는 원래 연결에 무엇을 남기나요?
3. 서비스를 `staff` 그룹 하나만 허용하도록 띄웠습니다. 기본 그룹이 `alice` 이고 보조 그룹으로 `staff` 에 속한 사용자가 `sudo -g nogroup` 으로 `nc` 를 실행해 접속합니다. 이 편의 `Allowed` 는 어떻게 판정하고, 허용 그룹을 `nogroup` 하나로 바꾸면 결과가 어떻게 달라지나요?
4. 허용된 접속에 `Welcome` 을 보내고 `continue` 하는 데모 루프를 그대로 오래 돌리면 서버에 무슨 일이 생기나요?



## 정답 (자답 후 펼치기)

> 위 §면접 대비의 질문에 먼저 스스로 답한 뒤 읽으세요.

### 정답 1 — 양쪽 프로세스가 같은 커널 안에 있다

TCP 나 UDP 로는 IP 주소와 포트 번호만 전달됩니다. 상대 호스트 안에서 어느 사용자의 어느 프로세스가 소켓을 열었는지는 프로토콜에 실리지 않으므로, 서버는 토큰이나 인증서 같은 애플리케이션 수준의 수단으로 상대를 확인해야 합니다.

Unix 도메인 소켓은 양쪽 프로세스가 같은 커널 아래에 있습니다. 커널은 연결 양 끝의 프로세스를 직접 알고 있으므로 `SO_PEERCRED` 로 물으면 상대의 PID·UID·GID 를 돌려줍니다. 이 값은 클라이언트가 보낸 것이 아니라 커널이 채운 것이어서 클라이언트가 바꿀 수 없습니다.

돌려주는 값은 상대가 `connect(2)` 를 부른 시점의 신원입니다. 접속한 뒤 클라이언트가 권한을 바꾸거나 소켓을 다른 프로세스에 넘겨도 처음 값이 그대로 나옵니다.

### 정답 2 — 복제한 fd 는 새고, Fd() 는 연결을 블로킹으로 바꾼다

`File()` 은 `dup` 으로 번호를 하나 더 만들어 돌려주고 그 번호는 자동으로 닫히지 않습니다. 닫지 않으면 접속마다 fd 가 하나씩 새어 상한에 닿으면 `Accept` 가 EMFILE 로 실패합니다. 또 서버가 `conn.Close()` 를 불러도 복제 번호가 소켓을 붙잡고 있어 클라이언트가 EOF 를 받지 못합니다.

`file.Fd()` 는 디스크립터를 블로킹 모드로 바꿔서 돌려줍니다. 블로킹 여부는 복제한 두 번호가 함께 쓰는 값이라 원본 `conn` 도 블로킹이 되고, 복제본을 닫은 뒤에도 그대로 남습니다. 그 뒤로는 `conn` 에 건 읽기 데드라인이 듣지 않습니다.

두 문제를 함께 피하려면 `conn.SyscallConn()` 의 `Control` 콜백 안에서 원래 fd 로 `GetsockoptUcred` 를 부릅니다.

### 정답 3 — 판정에 들어가는 것은 UID 와 사용자 DB 다

`sudo -g nogroup` 은 `-u` 없이 쓰면 명령을 부른 사용자 그대로 실행하고 기본 그룹만 `nogroup` 으로 바꿉니다. 커널이 돌려주는 값은 `Uid` 가 그 사용자이고 `Gid` 가 `nogroup` 입니다.

`Allowed` 는 이 가운데 `Uid` 만 꺼내 사용자 DB 에서 그룹 목록을 읽습니다. 목록에 `staff` 가 있으므로 접속은 허용되고 `Welcome` 을 받습니다. `-g` 로 바꾼 `nogroup` 은 판정에 들어가지 않습니다.

허용 그룹을 `nogroup` 하나로 바꾸면 결과는 거부입니다. 프로세스의 `Gid` 는 `nogroup` 이지만 `Allowed` 는 `ucred.Gid` 를 읽지 않고, 사용자 DB 의 그룹 목록에는 `nogroup` 이 없기 때문입니다. `-g` 로 바꾼 그룹까지 판정에 넣으려면 `ucred.Gid` 를 허용 목록과 함께 대조해야 합니다.

### 정답 4 — 닫지 않은 연결이 fd 로 쌓인다

데모 루프는 허용된 연결을 닫지도 않고 다른 고루틴에 넘기지도 않습니다. 연결 객체는 다음 반복에서 버려지지만 fd 는 열린 채 남습니다. 연결 객체에 붙은 finalizer 가 GC 때 fd 를 닫아 주기는 하지만 언제 돌지 알 수 없어 기댈 수 없습니다.

허용 접속이 쌓여 fd 상한에 닿으면 `AcceptUnix` 가 실패하고 루프가 `break` 로 끝나 서버가 멈춥니다. 클라이언트 쪽에서는 `Welcome` 뒤로 아무 응답도 오지 않습니다.

실제 서비스에서는 허용된 연결을 전담 고루틴에 넘기고 그 고루틴이 끝날 때 `Close` 를 부르게 합니다.
