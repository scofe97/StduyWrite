# TFTP 서버는 블록마다 ACK 를 기다리고 재전송해 UDP 위에 신뢰성을 올린다

---

> 6장 뒷부분은 앞서 설계한 패킷 타입을 조립하여 실제 동작하는 TFTP 서버를 구축하고 무결성을 검증하는 과정을 다룹니다. 요청마다 고루틴과 전용 소켓을 분리하고 블록 단위 확인응답과 타임아웃 재전송 루프를 결합하여 UDP 통신 위에서 정지-대기 방식의 신뢰 전송을 완성합니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은, UDP 위의 신뢰성은 연결 분리를 통한 다중화와 블록 단위 정지-대기 재전송 루프라는 두 축으로 애플리케이션 계층에서 완성된다는 사실입니다.

서버는 69번 웰노운 포트에서 `net.PacketConn` 으로 진입 요청을 감청하다가 유효한 읽기 요청(RRQ)을 받으면 새 고루틴을 띄웁니다. 핸들러 고루틴은 `net.Dial` 로 클라이언트와 1:1 연결을 맺어 메인 수신 소켓을 즉시 해방하고 송수신 주소 필터링 오버헤드를 걷어냅니다.

실제 데이터 전송은 512바이트 블록 하나를 보내고 확인응답을 받을 때까지 멈추어 기다리는 정지-대기 방식을 따릅니다. 데드라인 기반 타임아웃이 발생하면 현재 블록을 최대 10회까지 재전송하며 패킷 손실을 복구합니다. 최종 블록 크기가 516바이트 미만임을 감지하여 전송을 안전하게 닫고 고속 64비트 해시인 SHA512/256 으로 전송 파일의 바이트 단위 무결성을 최종 확인합니다.



## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. `Server` 구조체의 기본 필드와 69번 포트 리스너의 역할을 설명할 수 있습니다.
2. 읽기 요청 수신 시 별도 고루틴과 `net.Dial` 연결을 여는 구조적 이유를 밝힐 수 있습니다.
3. 정지-대기 전송 흐름과 타임아웃 재전송 루프의 탈출 조건을 순서대로 재현할 수 있습니다.
4. TCP 슬라이딩 윈도와 TFTP 정지-대기 메커니즘의 성능상 차이를 비교할 수 있습니다.
5. SHA512/256 체크섬이 64비트 CPU 에서 갖는 속도 및 보안상 이점을 설명할 수 있습니다.

아래는 이 편의 키워드를 이은 개념도입니다. §1 줄은 69번 공용 소켓에서 요청을 받아 고루틴과 `net.Dial` 로 전용 소켓을 여는 연결 분리입니다. §2 줄은 512바이트 블록을 보내고 타임아웃 재전송을 거쳐 516바이트 미만까지 전진하는 정지-대기 전송입니다. §3 줄은 다운로드한 파일의 SHA512/256 해시를 계산해 원본과의 바이트 일치를 확인하는 무결성 검증입니다. 왼쪽 칩이 그 줄을 다루는 절이고, 각 단계는 독립 소켓에서 시작해 파일 무결성 확인으로 이어집니다.

## 1. 서버는 요청마다 새 연결로 따로 응답한다

> 서버는 공용 수신 소켓에서 읽기 요청을 받아 전용 고루틴으로 넘기고, 클라이언트 주소로 다이얼을 걸어 독립된 전송 소켓을 확보합니다.

### Server 타입의 필드와 기본값

아래 코드는 TFTP 서버 구조체와 진입점 메서드를 선언합니다.

```go
// Server 타입과 Serve 루프 (server.go, 일부)
package tftp

import (
	"errors"
	"log"
	"net"
	"time"
)

type Server struct {
	// 모든 읽기 요청에 응답할 파일 페이로드
	Payload []byte
	// 실패한 전송의 재시도 횟수
	Retries uint8
	// ACK 대기 타임아웃 시간
	Timeout time.Duration
}

func (s Server) ListenAndServe(addr string) error {
	conn, err := net.ListenPacket("udp", addr)
	if err != nil {
		return err
	}
	defer func() { _ = conn.Close() }()
	log.Printf("Listening on %s ...\n", conn.LocalAddr())
	return s.Serve(conn)
}

func (s *Server) Serve(conn net.PacketConn) error {
	if conn == nil {
		return errors.New("nil connection")
	}
	if s.Payload == nil {
		return errors.New("payload is required")
	}
	if s.Retries == 0 {
		// 기본 재시도 횟수 10회
		s.Retries = 10
	}
	if s.Timeout == 0 {
		// 기본 타임아웃 6초
		s.Timeout = 6 * time.Second
	}

	var rrq ReadReq
	for {
		buf := make([]byte, DatagramSize)
		_, addr, err := conn.ReadFrom(buf)
		if err != nil {
			return err
		}
		err = rrq.UnmarshalBinary(buf)
		if err != nil {
			log.Printf("[%s] bad request: %v", addr, err)
			continue
		}
		// 독립 고루틴으로 분기
		go s.handle(addr.String(), rrq);
	}
}
```

`Server` 구조체는 세 가지 필드를 갖습니다. 클라이언트에게 돌려줄 데이터 원본인 `Payload`, 전송 실패 시 패킷을 다시 보낼 최대 횟수 `Retries`, 확인응답을 기다리는 제한 시간 `Timeout` 입니다. 사용자가 값을 비워 두면 `Serve` 메서드가 각각 10회와 6초를 기본값으로 채웁니다.

`ListenAndServe` 메서드는 `net.ListenPacket("udp", addr)` 로 UDP 패킷 연결을 엽니다. [05-01 §2](./05-01.UDP%20는%20연결%20없이%20보내고,%20소켓%20하나가%20누구에게서든%20받는다.md)에서 다루었듯 `net.PacketConn` 은 누구에게서든 도착하는 데이터그램을 `ReadFrom` 으로 받아내는 열린 소켓입니다.

### 요청마다 고루틴과 net.Dial 을 분리하는 이유

수신한 패킷이 유효한 `ReadReq` 로 파싱되면 서버는 고루틴을 띄워 핸들러를 실행합니다. 메인 리스너가 직접 파일 데이터를 전송하지 않고 별도 고루틴을 띄우는 이유는 셋입니다.

첫째, 동시 다중 요청 처리입니다. 메인 루프에서 전송을 직접 수행하면 한 클라이언트에게 512바이트씩 수백 개 블록을 다 보낼 때까지 69번 포트가 블로킹되어 다른 클라이언트의 요청을 받을 수 없습니다.

둘째, RFC 1350 의 TID(전송 식별자) 규약 준수입니다. 표준 TFTP 는 69번 포트를 최초 요청 수신용으로만 쓰고 실제 데이터 교환은 서버가 임의로 선택한 임시 포트로 옮겨 진행하도록 규정합니다.

셋째, 소켓 레벨의 상대 고정입니다. 뒤이어 볼 핸들러는 `net.Dial("udp", clientAddr)` 로 소켓을 엽니다. [05-02 §1](./05-02.net.Conn%20으로%20상대를%20고정하고%20MTU%20아래로%20보내%20단편화를%20피한다.md)에서 배웠듯 UDP 소켓에 다이얼을 걸면 운영체제 커널이 해당 목적지 주소로 소켓을 고정합니다. 이제 핸들러는 매번 송신자 IP 와 포트를 대조할 필요 없이 일반 `conn.Read` 와 `conn.Write` 로 데이터를 편하게 주고받습니다.

소켓 하나를 고루틴 여럿이 함께 쓰면 무엇이 깨질까요? Go 의 `net.PacketConn` 은 여러 고루틴이 동시에 메서드를 불러도 안전하다고 [공식 문서](https://pkg.go.dev/net#PacketConn)가 보장합니다. 그래서 고루틴들이 69번 소켓 하나를 함께 써도 소켓 내부가 깨지는 데이터 레이스는 생기지 않습니다. 문제는 수신 큐가 하나뿐이라는 점입니다. 69번 소켓에 A 의 ACK 3, C 의 새 요청, B 의 ACK 7 이 이 순서로 쌓였다고 해 봅니다.

```pseudocode
69번 소켓의 수신 큐: [A 의 ACK 3] [C 의 새 요청] [B 의 ACK 7]

고루틴 A 가 ReadFrom → A 의 ACK 3      (운 좋게 자기 것)
고루틴 B 가 ReadFrom → C 의 새 요청     (B 의 것이 아님)
```

`ReadFrom` 은 큐 맨 앞의 데이터그램을 꺼내고, 꺼낸 순간 그 데이터그램은 큐에서 사라집니다. 고루틴 B 가 C 의 요청을 꺼내면 메인 루프는 그 요청을 영영 보지 못합니다. [05-01](./05-01.UDP%20는%20연결%20없이%20보내고,%20소켓%20하나가%20누구에게서든%20받는다.md) 처럼 남의 것을 버리고 다시 읽는 방식도 여기서는 다른 고루틴의 데이터를 없애는 셈이라 쓸 수 없습니다.

해법은 전송마다 소켓을 따로 두는 것입니다. 핸들러가 `net.Dial` 로 새 소켓을 열면 운영체제가 빈 임시 포트를 하나 줍니다. 고루틴마다 자기 수신 큐를 갖고, 클라이언트는 첫 데이터 블록이 온 그 포트로 ACK 를 보내므로 A 의 ACK 는 A 의 소켓으로만 갑니다. 전송마다 쓰는 이 포트가 RFC 1350 의 TID 입니다.

전송마다 고루틴과 소켓과 포트를 하나씩 쓰므로 비용도 따져 봅니다.

| 하나당 드는 것 | 크기 |
|---|---|
| 고루틴 | 처음엔 스택 몇 KB |
| 소켓 | 파일 디스크립터 1개와 커널 구조체. 수신 버퍼는 데이터가 쌓일 때만 메모리를 씁니다 |
| 포트 | 임시 포트 1개. 리눅스 기본 범위는 32768~60999, 약 2만 8천 개입니다 |

TCP 서버도 `Accept` 로 연결마다 소켓을 하나씩 받으므로 같은 구조입니다. TFTP 는 PXE 부팅처럼 많아야 수십에서 수백 대가 동시에 받는 용도라 한도에 닿을 일이 거의 없습니다.

규모가 아주 커지면 소켓 하나에 읽기 전담 고루틴을 두는 방식도 있습니다. 이 고루틴이 주소를 보고 전송별 채널로 나눠 줍니다.

QUIC 는 패킷마다 연결 ID 가 있어 소켓 하나로 받아도 연결을 가를 수 있습니다. 포트를 바꾸지 않으니 NAT·방화벽도 넘기 쉽습니다.

TCP 의 전용 소켓과 견주면 같은 점과 다른 점이 함께 보입니다.

| | TCP | TFTP(UDP) |
|---|---|---|
| 전용 소켓의 내 쪽 포트 | 같은 포트(예: 80)를 그대로 씁니다 | 새 임시 포트로 옮깁니다 |
| 전송 구분 | 커널이 출발지·목적지 IP 와 포트 네 값으로 구분합니다 | 내 쪽 포트가 달라서 구분됩니다 |
| 연결 수립 | 핸드셰이크가 있고 커널이 순서 번호·창 상태를 관리합니다 | 핸드셰이크가 없고, 신뢰성은 앱이 만듭니다 |

포트를 바꾸는 이 규약 때문에 방화벽은 69번으로 나간 요청의 응답이 낯선 포트에서 돌아오는 것을 따로 알아봐야 합니다. 그래서 리눅스 방화벽에는 TFTP 전용 도우미 모듈(`nf_conntrack_tftp`)이 있습니다.



## 2. 블록 하나를 보내고 ACK 를 받을 때까지 기다린다

> 핸들러는 512바이트 블록을 보내고 ACK 가 올 때까지 대기하며, 6초 데드라인 만료 시 최대 10회까지 같은 블록을 재전송합니다.

### 정지-대기(Stop-and-Wait) 흐름

TFTP 는 가장 단순한 신뢰 전송 모델인 정지-대기(Stop-and-Wait ARQ) 규약을 따릅니다. 송신 측은 한 번에 하나의 패킷만 보내고 수신 측이 잘 받았다는 확인응답 ACK 를 돌려줄 때까지 다음 블록을 보내지 않고 대기합니다.

클라이언트와 서버 사이의 통신 과정을 도식으로 따라가 봅니다.

![TFTP 전송과 정지-대기 재전송](./_assets/06-02.stop-and-wait.svg)

1. 클라이언트가 읽기 요청 RRQ 를 전송합니다.
2. 서버는 1번 블록 DATA 1(512바이트)로 응답합니다.
3. 클라이언트는 수신을 확인하는 ACK 1 을 반환합니다.
4. 서버는 2번 블록 DATA 2 를 전송합니다. 네트워크에서 패킷이 손실되거나 지연되어 응답이 오지 않습니다.
5. 서버의 대기 타이머가 만료(Timeout 6초)됩니다.
6. 서버는 직전에 보냈던 DATA 2 를 다시 전송합니다.
7. 클라이언트가 DATA 2 를 받고 ACK 2 를 회신합니다.
8. 이 왕복이 이어지다가 페이로드가 512바이트 미만인 마지막 블록(DATA 148)을 전송하고 최종 ACK 를 받으면 전송이 종료됩니다. 도식의 'DATA 148'은 서버 로그 "sent 148 blocks"에서 가져온 값이고, 클라이언트 출력 "75352 bytes"(75,352 = 147×512 + 88)와도 맞아떨어집니다.

### 이중 루프로 구현된 handle 제어문

아래 코드는 이 정지-대기 논리를 정교한 이중 레이블 루프로 풀어냅니다.

```go
// handle 메서드의 이중 전송 루프 (server.go, 일부)
func (s Server) handle(clientAddr string, rrq ReadReq) {
	log.Printf("[%s] requested file: %s", clientAddr, rrq.Filename)
	// 클라이언트 고정 UDP 연결
	conn, err := net.Dial("udp", clientAddr)
	if err != nil {
		log.Printf("[%s] dial: %v", clientAddr, err)
		return
	}
	defer func() { _ = conn.Close() }()

	var (
		ackPkt  Ack
		errPkt  Err
		dataPkt = Data{Payload: bytes.NewReader(s.Payload)}
		buf     = make([]byte, DatagramSize)
	)

NEXTPACKET:
	// 다음 블록 진행 루프
	for n := DatagramSize; n == DatagramSize; {
		data, err := dataPkt.MarshalBinary()
		if err != nil {
			log.Printf("[%s] preparing data packet: %v", clientAddr, err)
			return
		}

RETRY:
		// 재전송 루프 (최대 10회)
		for i := s.Retries; i > 0; i-- {
			// 패킷 송신
			n, err = conn.Write(data)
			if err != nil {
				log.Printf("[%s] write: %v", clientAddr, err)
				return
			}

			// 6초 데드라인 설정
			_ = conn.SetReadDeadline(time.Now().Add(s.Timeout))
			_, err = conn.Read(buf)
			if err != nil {
				if nErr, ok := err.(net.Error); ok && nErr.Timeout() {
					// 타임아웃 발생 시 재전송
					continue RETRY
				}
				log.Printf("[%s] waiting for ACK: %v", clientAddr, err)
				return
			}

			switch {
			case ackPkt.UnmarshalBinary(buf) == nil:
				// 블록 번호 일치 확인
				if uint16(ackPkt) == dataPkt.Block {
					// 다음 블록으로 이동
					continue NEXTPACKET
				}
			// 오류 패킷 수신
			case errPkt.UnmarshalBinary(buf) == nil:
				log.Printf("[%s] received error: %v", clientAddr, errPkt.Message)
				return
			default:
				log.Printf("[%s] bad packet", clientAddr)
			}
		}
		// 재시도 소진
		log.Printf("[%s] exhausted retries", clientAddr)
		return
	}
	log.Printf("[%s] sent %d blocks", clientAddr, dataPkt.Block)
}
```

핸들러의 상태 전이도를 통해 각 탈출 및 순환 조건을 한눈에 볼 수 있습니다.

![TFTP 서버 handle 루프 상태 전이](./_assets/06-02.handle-loop.svg)

제어 흐름은 세 갈래로 나뉩니다.

1. **정상 전진**: 수신한 ACK 의 블록 번호가 `dataPkt.Block` 과 일치하면 내부 루프를 벗어나 `continue NEXTPACKET` 을 탑니다. 이때 마지막 블록이어서 전송 바이트 `n` 이 516보다 작았다면 외부 루프 조건 `n == DatagramSize` 가 거짓이 되며 루프 전체를 빠져나와 성공 종료합니다.
2. **손실 복구**: 6초 동안 응답이 없어 `conn.Read` 에서 타임아웃 오류가 발생하면 내부 루프 `continue RETRY` 로 돌아가 같은 데이터를 다시 쏩니다. 번호가 다른 ACK 를 받으면 `switch` 를 빠져나온 재전송 루프가 `i--` 를 합니다. 그리고 다음 바퀴의 `conn.Write(data)` 로 지금 블록을 곧바로 다시 보냅니다. 이 동작은 결함입니다(아래에서 다룹니다). 재시도 횟수 `i` 가 0이 될 때까지 응답을 받지 못하면 전송을 포기하고 빠져나옵니다.
3. **치명적 오류**: 클라이언트가 ERROR 패킷을 보내오면 즉시 함수를 반환하여 세션을 닫습니다.

재시도에 상한을 두는 이유는 클라이언트가 꺼졌거나 망이 끊기면 ACK 가 영원히 오지 않기 때문입니다. 상한이 없으면 고루틴과 소켓이 그 클라이언트를 붙잡고 끝없이 재전송합니다. 이 서버는 6초씩 10번, 약 1분 뒤에 포기합니다.

타임아웃 6초는 RTT 가 1ms 든 150ms 든 같은 고정값입니다. TCP 는 실제 RTT 를 재서 재전송 시간을 맞추고 실패할 때마다 간격을 두 배로 늘립니다([RFC 6298](https://www.rfc-editor.org/rfc/rfc6298)). RFC 1350 은 타임아웃 값을 구현에 맡겼으므로 고정값은 이 구현의 단순한 선택입니다.

`dataPkt.Block` 은 받은 ACK 의 목록이 아니라 지금 보낸 블록 번호 하나입니다. 바깥 루프가 새 블록을 만들 때 `MarshalBinary` 의 `d.Block++` 로 늘고, 재전송은 이미 만든 `data` 바이트를 다시 보내므로 늘지 않습니다. `handle` 의 지역 변수라 전송이 끝나면 사라집니다. 정지-대기라 날아가는 블록이 하나뿐이므로 번호 하나로 충분합니다.

번호가 다른 ACK 에 곧바로 다시 보내는 동작은 왜 결함일까요? 5번 블록이나 그 ACK 가 늦게 도착해 서버가 타임아웃으로 5번을 다시 보냈다고 해 봅니다. 클라이언트는 5번을 두 번 받아 ACK 5 를 두 번 보내고, 서버는 첫 ACK 5 에 6번을 보낸 뒤 두 번째 ACK 5 를 받습니다. 이 ACK 는 이미 지난 블록의 것인데 코드는 지금 블록인 6번을 또 보냅니다.

| 순서 | 서버 | 클라이언트 |
|---|---|---|
| 1 | 두 번째 ACK 5 를 받고 6번을 또 보냅니다 | |
| 2 | | 6번을 두 번 받으므로 ACK 6 도 두 번 보냅니다 |
| 3 | 첫 ACK 6 에 7번을, 두 번째 ACK 6 에 7번을 또 보냅니다 | |
| 4 | 이후 모든 블록이 두 번씩 오갑니다 | |

한 번의 지연이 남은 전송 전체를 두 배로 부풀립니다. 이 현상을 마법사의 제자 증후군(Sorcerer's Apprentice Syndrome)이라 부르며, [RFC 1123 §4.2.3.1](https://www.rfc-editor.org/rfc/rfc1123#section-4.2.3.1)은 중복 ACK 를 받았다고 현재 블록을 다시 보내면 안 된다고 규정합니다. 재전송은 타임아웃 때만 해야 합니다.

고친 재전송 루프는 아래와 같습니다. 바깥 `NEXTPACKET` 루프와 변수 선언은 원래 코드와 같습니다.

```go
RETRY:
	for i := s.Retries; i > 0; i-- {
		n, err = conn.Write(data)
		if err != nil {
			log.Printf("[%s] write: %v", clientAddr, err)
			return
		}

		// 데드라인은 보낼 때 한 번만 건다
		_ = conn.SetReadDeadline(time.Now().Add(s.Timeout))
		for {
			_, err = conn.Read(buf)
			if err != nil {
				if nErr, ok := err.(net.Error); ok && nErr.Timeout() {
					// 타임아웃일 때만 다시 보낸다
					continue RETRY
				}
				log.Printf("[%s] waiting for ACK: %v", clientAddr, err)
				return
			}

			switch {
			case ackPkt.UnmarshalBinary(buf) == nil:
				if uint16(ackPkt) == dataPkt.Block {
					continue NEXTPACKET
				}
				// 지난 블록의 ACK 는 버리고, 다시 보내지 않고 같은 데드라인 안에서 다시 읽는다
			case errPkt.UnmarshalBinary(buf) == nil:
				log.Printf("[%s] received error: %v", clientAddr, errPkt.Message)
				return
			default:
				log.Printf("[%s] bad packet", clientAddr)
			}
		}
	}
```

안쪽 `for` 가 데드라인 안에서 읽기를 반복하므로 지난 ACK 는 재전송도, 재시도 횟수 소모도 일으키지 않습니다. 데드라인을 보낼 때 한 번만 걸었으므로 지난 ACK 가 계속 와도 기다림이 무한히 늘지는 않습니다. 이 코드는 실행으로 확인하지 않았습니다.

### TCP 슬라이딩 윈도와의 대비

이 메커니즘을 TCP 의 신뢰성과 대조해 보면 흥미로운 트레이드오프가 보입니다. [03-01 §3](./03-01.TCP%20세션은%20핸드셰이크로%20열고%20창으로%20속도를%20맞추고%20FIN·RST%20로%20끝난다.md)과 [TII 12-01](../tii_tcp-ip-illustrated/12-01.TCP%20의%20신뢰성은%20재전송·번호·창으로%20만든다.md)에서 다루었듯 TCP 는 슬라이딩 윈도를 이용해 확인응답을 기다리지 않고도 윈도 크기만큼 여러 패킷을 쉼 없이 파이프라인에 밀어 넣습니다.

반면 TFTP 의 정지-대기는 한 번에 한 블록만 보내므로 왕복 시간(RTT)이 긴 네트워크에서는 대역폭이 아무리 넓어도 전송 속도가 극도로 떨어집니다. [CNTD 03-02 신뢰성은 어떻게 만들어지는가](../cntd_computer-networking-top-down/03-02.신뢰성은%20어떻게%20만들어지는가.md)에서 분석한 rdt 3.0 프로토콜과 완전히 동일한 한계를 가집니다. 단순성을 대가로 높은 전송률을 포기한 전형적인 설계입니다.

수치로 보면 한계가 더 분명합니다. 1Gbps 회선에 516바이트를 싣는 시간은 516 × 8 ÷ 10⁹ ≈ 0.004ms 로, RTT 150ms 에 비하면 사실상 0 입니다. 그래서 회선 속도와 무관하게 블록 하나에 RTT 하나가 걸립니다. 속도는 512바이트 ÷ 0.15초 ≈ 초당 3.4KB 로 묶여 1Gbps 의 약 0.003% 만 씁니다.

| 파일 | 블록 수 | 걸리는 시간(RTT 150ms) |
|---|---|---|
| 75,352바이트(이 편의 예시) | 148 | 약 22초 |
| 10MB | 20,480 | 약 51분 |

[04-03](./04-03.TCPConn%20손잡이와%20흔한%20버그%20—%20keepalive·linger·버퍼·zero%20window·CLOSE_WAIT.md)의 BDP 와 같은 이야기입니다. TFTP 는 창이 블록 하나(512바이트)로 묶인 경우입니다.

지난 블록 번호를 걸러 내는 일은 TCP 의 2MSL(TIME_WAIT)과 같은 계열의 문제입니다. 둘 다 늦게 온 중복을 새 것으로 착각하지 않기 위한 장치입니다. 다만 `dataPkt.Block` 은 전송하는 동안만 쓰이고, TIME_WAIT 는 연결을 닫은 뒤에 남습니다.

TFTP 에도 닮은 규칙이 있습니다. RFC 1350 은 마지막 ACK 를 보낸 쪽에게 바로 끝내지 말고 잠시 기다리라고 권합니다(dallying). 마지막 ACK 가 사라져 상대가 마지막 블록을 다시 보내면 ACK 를 한 번 더 보내 주려는 것입니다.



## 3. 받은 파일은 체크섬으로 확인한다

> 서버를 띄워 파일을 다운로드하고, 64비트 연산에 최적화된 SHA512/256 해시를 계산하여 원본과 100% 동일한지 검증합니다.

### 서버 구동과 클라이언트 다운로드

아래 코드는 명령줄에서 서버를 띄우는 실행 프로그램(`tftp.go`)입니다.

```go
// 명령줄 TFTP 서버 구동 (tftp.go, 일부)
package main

import (
	"flag"
	"log"
	"os"

	"github.com/awoodbeck/gnp/ch06/tftp"
)

var (
	address = flag.String("a", "127.0.0.1:69", "listen address")
	payload = flag.String("p", "payload.svg", "file to serve to clients")
)

func main() {
	flag.Parse()
	// 페이로드 로드
	p, err := os.ReadFile(*payload)
	if err != nil {
		log.Fatal(err)
	}
	s := tftp.Server{Payload: p}
	// 리스너 구동
	log.Fatal(s.ListenAndServe(*address))
}
```

파일을 통째로 읽어 페이로드로 준비할 때는 Go 표준 라이브러리의 [`os.ReadFile`](https://pkg.go.dev/os#ReadFile) 을 사용합니다.

포트 69는 1024 미만의 특권 포트(privileged port)이므로 Linux 나 macOS 에서는 루트 권한(`sudo`)이 필요합니다.

Windows 10 환경에서 기본 내장된 TFTP 클라이언트를 사용하여 전송을 테스트합니다. 실행 화면 기록은 다음과 같습니다.

```powershell

```

다른 터미널 창에서 클라이언트를 실행하여 바이너리 모드(`-i`)로 다운로드를 요청합니다.

```powershell

```

서버 콘솔에는 클라이언트 접속과 전송 블록 수가 찍힙니다.

```powershell

```

총 75,352바이트가 전송되었고 블록 수는 148개입니다. 512바이트 블록 147개(75,264바이트)와 마지막 148번째 블록 88바이트가 전송되어 정확히 맞아떨어집니다.

> 책 밖 보강: macOS 나 Linux 환경에서 재현할 때는 터미널에서 `tftp 127.0.0.1` 을 입력해 대화형 프롬프트로 진입한 뒤 `binary` 명령으로 모드를 바꾸고 `get test.svg` 를 실행하면 동일하게 다운로드할 수 있습니다.

### 무결성 검증과 SHA512/256 해시의 선택 이유

다운로드한 `test.svg` 가 서버의 원본 `payload.svg` 와 한 바이트도 틀림없이 같은지 어떻게 확인할까요? 아래는 순수 Go 코드로 작성된 SHA512/256 해시 생성기입니다.

```go
// SHA512/256 체크섬 도구 (sha512-256sum.go, 일부)
package main

import (
	"crypto/sha512"
	"flag"
	"fmt"
	"os"
)

func main() {
	flag.Parse()
	for _, file := range flag.Args() {
		fmt.Printf("%s  %s\n", checksum(file), file)
	}
}

func checksum(file string) string {
	b, err := os.ReadFile(file)
	if err != nil {
		return err.Error()
	}
	// 256비트 해시 생성
	return fmt.Sprintf("%x", sha512.Sum512_256(b))
}
```

해시 함수는 크기가 얼마든 입력을 받아 고정 길이 값을 냅니다. SHA512/256 은 어떤 파일이든 32바이트(16진수 64글자)를 냅니다. 성질은 세 가지입니다. 같은 입력은 언제나 같은 값을 냅니다. 1비트만 달라도 값은 완전히 달라집니다. 같은 값을 내는 다른 두 파일을 찾는 일은 사실상 불가능합니다. 그래서 파일 전체 대신 64글자만 비교하면 됩니다. macOS 에서는 `shasum -a 512256 <파일>` 로 같은 값을 낼 수 있습니다.

UDP 체크섬과 ACK 가 이미 있는데 해시가 왜 또 필요할까요? 체크섬은 손실이 아니라 손상을 확인하고, 손실은 ACK 와 타임아웃이 잡습니다. UDP 체크섬은 16비트라 우연한 손상도 약 6만 5천 번에 한 번은 놓칠 수 있습니다.

체크섬과 ACK 는 데이터그램 하나씩, 오가는 동안만 확인합니다. 그래서 블록을 잘못 이어 붙이거나, 블록 번호가 넘쳐 하나가 빠지거나, 디스크에 쓰다 틀리는 일은 잡지 못합니다. 해시는 완성된 파일 전체를 원본과 비교하므로 이 경로를 한 번에 짚습니다. 이 편이 해시를 쓴 목적도 직접 만든 TFTP 구현이 맞게 동작하는지 검증하는 것입니다.

위조 방지는 조건부입니다. 비교 기준인 해시값을 믿을 수 있는 다른 경로(HTTPS 페이지, 서명 등)로 받아야 위조를 잡을 수 있습니다. 파일을 바꿀 수 있는 공격자는 같은 경로의 해시값도 바꿀 수 있기 때문입니다.

흔히 쓰이는 SHA-256 대신 왜 굳이 SHA512/256 을 사용할까요? 두 가지 명확한 기술적 이유가 있습니다.

1. **64비트 아키텍처 연산 속도**: SHA-256 은 32비트 워드 연산을 기반으로 하지만 SHA-512 는 64비트 워드를 사용합니다. SHA 전용 명령이 없는 64비트 CPU 에서는 64비트 워드로 계산하는 SHA-512 계열이 SHA-256 보다 빠를 수 있습니다. 다만 요즘 CPU 에는 SHA-256 전용 명령(x86 의 SHA 확장, ARMv8 의 암호 확장)이 있어 SHA-256 이 더 빠른 경우가 많습니다.
2. **길이 확장 공격(Length Extension Attack) 방어**: 순수 SHA-512 는 해시 출력 길이가 내부 상태 크기와 같아 뒤에 악의적인 데이터를 덧붙이는 길이 확장 공격에 취약합니다. SHA512/256 은 512비트 계산 결과를 256비트로 잘라내어(truncation) 내부 상태가 외부에 노출되지 않으므로 이 공격에 강합니다. 다만 이 공격은 비밀값을 앞에 붙여 해시하는 인증 코드(H(비밀 ‖ 메시지))에서 문제가 되며, 두 파일을 비교하는 이 용도와는 관계가 없습니다.

두 파일의 체크섬을 대조하면 완벽한 일치를 볼 수 있습니다.

```powershell
C:\Users\User\dev\gnp\ch06>sha512-256sum \Users\User\test.svg
\Users\User\test.svg => 3f5794c522e83b827054183658ce63cb701dc49f4e59335f08b5c79c56873969

C:\Users\User\dev\gnp\ch06>sha512-256sum tftp\tftp\payload.svg
tftp\tftp\payload.svg => 3f5794c522e83b827054183658ce63cb701dc49f4e59335f08b5c79c56873969
```

해시값이 일치함으로써 UDP 가 가진 본질적인 패킷 유실 위험 속에서도 애플리케이션 계층이 구축한 순서 번호와 재전송 메커니즘이 데이터의 완벽한 신뢰 전송을 달성했음이 증명됩니다.

## 정답 (자답 후 펼치기)

> 위 §면접 대비의 질문에 먼저 스스로 답한 뒤 읽으세요.

### 정답 1 — 동시성 확보와 커널 수준의 송수신자 필터링

메인 69번 소켓에서 직접 블록 전송을 수행하면 파일 하나를 다 보낼 때까지 다른 클라이언트의 새로운 연결 요청을 수신할 수 없습니다. 별도 고루틴을 띄우고 `net.Dial("udp", clientAddr)` 로 전용 소켓을 열면 첫째, 공용 69번 포트를 즉시 비워 다중 클라이언트를 동시에 수용할 수 있습니다. 둘째, 표준 TFTP 규약(RFC 1350)에 따라 새로운 임시 포트를 할당해 전송을 격리합니다. 셋째, 커널이 소켓의 수신 대상을 해당 클라이언트로만 고정하므로 매 수신마다 발신자 주소를 대조하는 번거로움 없이 안전하게 `Read` 와 `Write` 를 호출할 수 있습니다.

### 정답 2 — 516바이트 미만 전송과 외부 레이블 루프 조건

TFTP 에서 일반 데이터 패킷은 항상 헤더 4바이트와 페이로드 512바이트를 합쳐 516바이트(`DatagramSize`) 크기를 갖습니다. 파일의 마지막 조각을 전송할 때 `io.CopyN` 은 512바이트 미만을 읽어 `conn.Write` 가 전송한 총 바이트 수 `n` 이 516 미만이 됩니다. 이 마지막 블록에 대해 클라이언트로부터 올바른 ACK 가 도착하면 `continue NEXTPACKET` 을 수행하게 되고, 이때 외부 루프의 지속 조건인 `n == DatagramSize` 가 거짓이 되면서 루프를 정상 탈출합니다.

### 정답 3 — 송신 측 타임아웃 재전송과 수신 측 중복 ACK 응답

클라이언트의 ACK 패킷이 네트워크에서 유실되면 서버는 확인응답을 받지 못한 채 6초 데드라인 만료에 도달합니다. 타임아웃 에러를 감지한 서버는 `RETRY` 레이블을 통해 직전에 보냈던 데이터 블록을 그대로 재전송합니다. 이미 해당 블록을 받았던 클라이언트는 동일한 블록이 다시 도착하더라도 당황하지 않고 해당 블록 번호에 대한 ACK 를 다시 회신하여 서버의 상태를 다음 단계로 전진시킵니다.

### 정답 4 — RTT 지연에 묶이는 파이프라인 부재

TCP 는 슬라이딩 윈도 프로토콜을 사용해 확인응답을 기다리지 않고도 수신 윈도 용량만큼 여러 패킷을 네트워크 파이프라인에 연속해서 쏟아붓습니다. 반면 TFTP 의 정지-대기 방식은 512바이트 블록 하나를 보낼 때마다 반드시 상대방의 왕복 시간(RTT)만큼 대기해야 합니다. 따라서 대역폭이 넓은 초고속 망이라도 지연 시간이 길면 초당 전송할 수 있는 블록 수가 엄격히 제한되어 네트워크 자원을 온전히 활용하지 못합니다.

### 정답 5 — 64비트 워드 연산과 길이 확장 공격에 대한 내성

SHA512/256 은 내부적으로 64비트 워드 연산을 수행하므로 SHA 전용 명령이 없는 64비트 CPU 에서는 32비트 기반의 SHA-256 보다 빠를 수 있습니다. 다만 SHA-256 전용 명령이 있는 CPU 에서는 SHA-256 이 더 빠른 경우가 많습니다. 또한 순수 SHA-512 와 달리 계산 결과의 상위 256비트만 잘라내어 출력하므로 해시 함수의 내부 상태가 외부에 드러나지 않아, 뒤에 임의 데이터를 덧붙이는 길이 확장 공격(Length Extension Attack)에 강합니다. 다만 이 공격은 비밀값을 앞에 붙여 해시하는 인증 코드에서 문제가 되며, 두 파일을 비교하는 이 용도와는 관계가 없습니다.
