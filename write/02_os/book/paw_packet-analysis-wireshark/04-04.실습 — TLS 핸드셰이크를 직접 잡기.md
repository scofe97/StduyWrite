# 실습 — TLS 핸드셰이크를 직접 잡기

---

## 실험실

> OrbStack 리눅스 컨테이너 둘. 2026-09-20 실행. 서버의 버전과 cipher suite 를 마음대로 못박아야 해서 웹 서버 대신 `openssl s_server` 를 씁니다.

공개 사이트에 붙어 캡처하면 조건을 고를 수 없습니다. 어떤 버전으로 붙을지, 어떤 묶음을 고를지가 상대 서버 설정에 달려 있습니다. 그래서 정적 RSA 로 붙여 보거나 일부러 협상을 깨뜨리는 실험을 할 수 없습니다. `s_server` 는 이 조건을 명령줄 인자로 고정할 수 있어 실험 대상이 됩니다.

랩은 저장소 밖 `~/study/paw-lab/04-tls/` 에 있습니다. `compose.yaml`·`Dockerfile`·`make-certs.sh`·`look-tls.sh`·`certs/`·`pcap/` 한 벌입니다.

```bash
cd ~/study/paw-lab/04-tls
./make-certs.sh                  # 자체 CA 하나 + 서버 인증서 둘(a.test, b.test)
docker compose up -d --build     # tls-server, tls-client 두 컨테이너
```

인증서를 두 장 만드는 이유는 묶음 A 의 마지막 단계 때문입니다. 같은 주소와 포트에서 요청한 이름에 따라 다른 인증서가 나가는 것을 보려면 이름이 다른 인증서가 둘 필요합니다. 인증서를 만드는 세 걸음과 각 파일의 역할은 [04-02 §3](./04-02.%EC%9D%B8%EC%A6%9D%EC%84%9C%EC%99%80%20%EB%91%90%20%EC%84%9C%EB%AA%85.md) 이 다룹니다.

### 잡는 쪽과 읽는 쪽을 가릅니다

캡처는 컨테이너 안 `tcpdump` 가 `pcap/` 에 쓰고 읽는 일은 호스트의 `tshark` 가 합니다. 읽을 때는 `./look-tls.sh <파일> [필터]` 를 씁니다. 이 편의 표는 대부분 그 출력입니다.

```bash
# 잡기 — -d 는 셸을 거치지 않으므로 리다이렉션을 쓰려면 sh -c 를 하나 끼웁니다
docker exec -d tls-server sh -c \
  'tcpdump -i eth0 -w /pcap/a1-handshake.pcap "tcp port 4433" 2>/dev/null'

# 읽기 — 핸드셰이크 종류와 레코드 길이를 정렬된 표로 냅니다
./look-tls.sh pcap/a1-handshake.pcap 'tls.handshake.type'
```

### 먼저 알아야 할 함정 넷

이 넷을 모르면 캡처가 비거나 명령이 조용히 실패합니다. 네 가지 모두 실행 중에 부딪혀 고친 것입니다.

`tcpdump` 를 `docker exec -d` 로 띄운 직후에는 아직 장치를 열지 않았습니다. 바로 접속하면 첫 패킷들이 통째로 빠집니다. 접속 전에 2초를 두고, 끝내기 전에도 2~3초를 기다려 마지막 패킷이 파일에 flush 되게 합니다.

```bash
docker exec -d tls-server sh -c 'tcpdump -i eth0 -w /pcap/x.pcap "tcp port 4433" 2>/dev/null'
docker exec tls-client sh -c 'sleep 2; openssl s_client ...'    # 2초 뒤에 접속합니다
sleep 3; docker exec tls-server pkill -f tcpdump                 # 3초 뒤에 멈춥니다
```

`s_server` 와 `s_client` 에는 `-4` 를 붙여 IPv4 로 고정합니다. 붙이지 않으면 IPv6 로 붙어 `eth0` 의 IPv4 필터에 걸리지 않고 캡처가 빈 채로 끝납니다.

OpenSSL 3.0.13 은 기본 보안 수준에서 TLS 1.1 을 아예 내보내지 않습니다. 묶음 C 에서 버전 불일치를 만들려면 클라이언트에 `-cipher "DEFAULT:@SECLEVEL=0"` 을 함께 줘야 제안이 나갑니다. 이것을 빼면 서버가 거절하기 전에 클라이언트가 먼저 포기해서 보고 싶은 Alert 가 선에 나오지 않습니다.

`look-tls.sh` 는 빈 칸을 `-` 로 채웁니다. `column -t` 가 빈 필드를 건너뛰어 뒤 열을 앞으로 당기기 때문입니다. 암호화된 레코드는 핸드셰이크 종류가 비는데 그대로 두면 레코드 길이가 종류 열 밑에 찍혀 엉뚱하게 읽힙니다.

### 이 편에서 쓰는 명령 옵션

`s_server` 는 인증서를 **읽는** 쪽이지 만드는 쪽이 아닙니다. `-cert`·`-key` 에 넘기는 파일은 `make-certs.sh` 가 미리 만들어 둔 것입니다.

| 옵션 | 하는 일 |
|---|---|
| `s_server -cert`·`-key` | 서버가 제시할 인증서와 짝인 개인키를 읽습니다 |
| `s_server -servername`·`-cert2`·`-key2` | 그 이름으로 왔을 때 내보낼 둘째 인증서를 겁니다 |
| `s_server -www` | 붙은 클라이언트에 협상 결과를 HTML 로 돌려줍니다 |
| `s_client -CAfile` | 검증에 쓸 CA 를 알려 주는 입력입니다. 서버에 보내는 값이 아닙니다 |
| `s_client -servername` | ClientHello 에 실을 SNI 를 정합니다 |
| `openssl x509 -in … -noout -text` | 인증서 파일을 사람이 읽는 형태로 풀어 봅니다 |
| `curl --connect-to` | 이름은 그대로 두고 접속할 주소만 바꿉니다 |
| `curl --tls-max`·`--ciphers` | 최대 버전과 제안할 묶음을 고정합니다 |

읽는 쪽 옵션은 둘입니다. `-o uat:rsa_keys:"경로",""` 는 서버 개인키를 물리고, `-o tls.keylog_file:경로` 는 세션 키 로그를 물립니다. 복호화 결과는 `-q -z follow,tls,ascii,0` 으로 스트림 단위로 봅니다.

이 편은 개인키 파일과 키 로그의 실제 값을 싣지 않습니다. 구조를 보일 때는 값을 줄임표로 가립니다.



## 묶음 A · 평문 핸드셰이크 읽기

> TLS 1.2 로 한 번 붙여 협상·인증서·암호화 경계를 눈으로 확인합니다. 네 단계입니다.

### A1. 서버를 띄우고 핸드셰이크를 잡습니다

먼저 예측합니다. 클라이언트가 묶음을 몇 개나 제안할까요? 서버는 그중 몇 번째를 고를까요?

```bash
docker exec -d tls-server sh -c \
  'openssl s_server -4 -accept 4433 -cert /certs/a.test.crt -key /certs/a.test.key -www'
docker exec -d tls-server sh -c \
  'tcpdump -i eth0 -w /pcap/a1-handshake.pcap "tcp port 4433" 2>/dev/null'
docker exec tls-client sh -c \
  'sleep 2; echo | openssl s_client -4 -connect a.test:4433 -servername a.test \
     -CAfile /certs/ca.crt -tls1_2'
sleep 3; docker exec tls-server pkill -f tcpdump
```

`-tls1_2` 를 빼면 OpenSSL 3.0 은 TLS 1.3 으로 붙습니다. 이 묶음은 평문으로 읽히는 1.2 를 보는 자리라 버전을 고정합니다.

볼 곳은 ClientHello 의 제안 목록과 ServerHello 의 선택입니다.

```bash
./look-tls.sh pcap/a1-handshake.pcap 'tls.handshake.type == 1 || tls.handshake.type == 2'
tshark -r pcap/a1-handshake.pcap -Y 'tls.handshake.type==1' \
  -T fields -e tls.handshake.ciphersuite | tr ',' '\n' | wc -l
```

실측은 제안 28줄, 서버 선택 `0xc030` 입니다. 목록의 순서는 전방 비밀성이 있는 묶음이 앞이고 정적 RSA 가 맨 뒤입니다.

서버가 고른 `0xc030` 은 `TLS_ECDHE_RSA_WITH_AES_256_GCM_SHA384` 입니다. 클라이언트가 1순위로 올린 것은 `ECDHE_ECDSA` 계열인데 서버는 그것을 건너뛰었습니다. 서버 인증서가 RSA 키를 담고 있어 ECDSA 로 서명할 수 없기 때문입니다.

> **흔한 예측 실수** — 서버가 목록의 1순위를 고른다고 봅니다. 서버는 자기가 감당할 수 있는 것 중에서 고르며, 인증서의 키 종류가 그 범위를 좁힙니다.

### A2. 서버가 보낸 네 메시지가 한 번에 옵니다

서버의 네 메시지는 각각 따로 도착할지, 한 번에 올지 예측해 봅니다.

```bash
./look-tls.sh pcap/a1-handshake.pcap 'tls.handshake.type'
```

| 프레임 | content_type | handshake.type | record.length |
|---|---|---|---|
| 5 | 22 | 1 | 303 |
| 7 | 22,22,22,22 | 2,11,12,14 | 65,796,300,4 |
| 9 | 22,20,22 | 16 | 37,1,40 |

프레임 7 한 줄에 레코드가 넷 들어 있습니다. ServerHello·Certificate·ServerKeyExchange·ServerHelloDone 이 한 세그먼트로 나갔습니다. 메시지 수를 패킷 수로 세면 안 되는 이유가 여기서 눈에 보입니다.

Certificate 가 796바이트로 가장 크고 ServerKeyExchange 가 300바이트입니다. 후자 안에 x25519 공개값 32바이트와 서명 256바이트가 들어 있습니다.

```bash
tshark -r pcap/a1-handshake.pcap -Y 'tls.handshake.type==12' \
  -T fields -e tls.handshake.server_named_curve -e tls.handshake.sig_hash_alg
# 출력: 0x001d  0x0804   → x25519 · rsa_pss_rsae_sha256
```

`0x001d` 는 ECDHE 에 쓴 타원곡선 그룹 x25519 이고, `0x0804` 는 RSA 공개키 인증서로 만든 RSASSA-PSS 서명(해시 SHA-256)입니다.[^rfc8446-names] 두 값이 무엇을 가리키는지는 [04-02 §1](./04-02.%EC%9D%B8%EC%A6%9D%EC%84%9C%EC%99%80%20%EB%91%90%20%EC%84%9C%EB%AA%85.md) 과 그 심화 학습에 있습니다.

두 서명이 각각 무엇을 보증하는지는 [04-02 §1](./04-02.%EC%9D%B8%EC%A6%9D%EC%84%9C%EC%99%80%20%EB%91%90%20%EC%84%9C%EB%AA%85.md) 이 다룹니다.

> **흔한 예측 실수** — 메시지마다 패킷이 하나씩 온다고 봅니다. 순서 그림의 화살표는 개념적 순서이지 패킷 경계가 아닙니다.

### A3. 암호화가 시작되는 지점을 찾습니다

예측합니다. 프레임 9 에는 레코드가 셋 있는데 핸드셰이크 종류는 몇 개나 읽힐까요?

프레임 9 의 `content_type` 은 `22,20,22` 이고 `handshake.type` 은 `16` 하나뿐입니다. 레코드는 셋인데 종류는 하나만 읽힙니다.

첫 22 는 ClientKeyExchange(16), 20 은 ChangeCipherSpec, 마지막 22 는 Finished 입니다. 셋째 레코드의 종류가 안 읽히는 것은 그 레코드가 이미 암호화됐기 때문입니다. ChangeCipherSpec 자체는 평문이고 그 **다음** 레코드부터 보호가 걸립니다.

> **흔한 예측 실수** — ChangeCipherSpec 부터 암호화된다고 봅니다. 전환을 알리는 그 메시지는 평문이어야 상대가 읽을 수 있습니다.

### A4. SNI 만 바꿔 두 번 붙습니다

예측합니다. 같은 IP 와 포트인데 요청 이름만 바꾸면 무엇이 달라질까요?

```bash
docker exec -d tls-server sh -c \
  'openssl s_server -4 -accept 4433 -cert /certs/a.test.crt -key /certs/a.test.key \
     -servername b.test -cert2 /certs/b.test.crt -key2 /certs/b.test.key -www'

for h in a.test b.test; do
  docker exec tls-client sh -c \
    "echo | openssl s_client -4 -connect a.test:4433 -servername $h \
       -CAfile /certs/ca.crt 2>/dev/null | grep -m1 'subject='"
done
```

```bash
# 출력 — 접속 주소는 같고 인증서만 갈립니다
# a.test → subject=CN = a.test
# b.test → subject=CN = b.test
```

cipher suite 는 둘 다 같고 인증서 주체만 다릅니다. 서버가 인증서를 고르려면 이름을 알아야 하고 그 이름은 암호화가 시작되기 전에 와야 합니다. SNI 가 평문일 수밖에 없는 이유입니다.

> **흔한 예측 실수** — SNI 가 바뀌면 인증 쪽 협상도 바뀐다고 봅니다. 바뀌는 것은 서버가 꺼내는 인증서이고 묶음 선택은 그대로일 수 있습니다.



## 묶음 B · 복호화

> 같은 서버에 키 교환 방식만 바꿔 붙여, 서버 개인키로 열리는 캡처와 열리지 않는 캡처를 가릅니다. 세 단계입니다.

### B5. 정적 RSA 로 붙이면 메시지 하나가 사라집니다

예측합니다. 키 교환을 정적 RSA 로 바꾸면 서버의 메시지 구성이 달라질까요?

```bash
docker exec -d tls-server sh -c \
  'openssl s_server -4 -accept 4433 -cert /certs/a.test.crt -key /certs/a.test.key -www'
docker exec -d tls-server sh -c \
  'tcpdump -i eth0 -w /pcap/b5-static-rsa.pcap "tcp port 4433" 2>/dev/null'
docker exec tls-client sh -c \
  'sleep 2; curl -s --cacert /certs/ca.crt --connect-to a.test:4433:a.test:4433 \
     --tls-max 1.2 --ciphers AES128-SHA https://a.test:4433/ -o /dev/null -w "%{http_code}\n"'
sleep 3; docker exec tls-server pkill -f tcpdump
```

| 프레임 | handshake.type | record.length |
|---|---|---|
| 5 | 1 | 136 |
| 7 | 2,11,14 | 89,796,4 |
| 9 | 16 | 262,1,68 |

서버의 메시지가 `2, 11, 14` 입니다. ServerKeyExchange 에 해당하는 12 가 없습니다. 정적 RSA 는 인증서 안의 공개키를 그대로 키 교환에 쓰므로 새로 보낼 공개값이 없습니다. RFC 5246 §7.4.3 은 이 방식에서 그 메시지를 보내는 것을 아예 금지합니다.[^rfc5246]

ClientKeyExchange 가 262바이트로 커진 것도 같은 이유입니다. 그 안에는 비밀 값 256바이트가 2048비트 RSA 로 잠긴 채 실려 있습니다. ECDHE 로 붙은 A 묶음에서는 같은 메시지가 37바이트였고 x25519 공개값 32바이트만 담았습니다.

> **흔한 예측 실수** — 키 교환과 인증 칸이 나뉘어야 연결마다 새 대칭 키가 생긴다고 봅니다. 정적 RSA 도 매번 새 비밀 값을 만듭니다. 갈리는 것은 그 값이 장기 키로 잠긴 채 선을 지나가느냐입니다([04-03 §1](./04-03.%EC%97%B4%EC%87%A0%EC%99%80%20%EC%8B%A4%ED%8C%A8.md)).

### B6. 서버 개인키로 열어 봅니다

이번에도 먼저 예측합니다. 방금 잡은 정적 RSA 캡처는 서버 개인키만으로 열릴까요?

```bash
tshark -r pcap/b5-static-rsa.pcap \
  -o uat:rsa_keys:'"'"$PWD"'/certs/a.test.key",""' \
  -q -z follow,tls,ascii,0
```

```bash
# 출력 — 요청과 응답이 양방향 모두 평문으로 나옵니다
# Node 0: 192.168.147.3:51228
# Node 1: 192.168.147.2:4433
# 74
# GET / HTTP/1.1
# Host: a.test:4433
# ...
# HTTP/1.0 200 ok
```

요청은 74바이트로 고정이고 응답 길이는 실행할 때마다 달라집니다. `-www` 가 돌려주는 페이지에는 그 연결에서 협상된 묶음 목록이 들어가기 때문입니다.

같은 개인키로 묶음 A 의 ECDHE 캡처를 열면 결과가 비어 있습니다.

```bash
tshark -r pcap/a1-handshake.pcap \
  -o uat:rsa_keys:'"'"$PWD"'/certs/a.test.key",""' \
  -q -z follow,tls,ascii,0
# 출력: Node 0: :0   ← 스트림이 비어 있습니다
```

키가 틀린 것은 아닙니다. 그 키로 풀 대상이 캡처에 없습니다. ECDHE 에서 개인키는 서명에만 쓰이고 세션 키 계산에 관여하지 않습니다. 전방 비밀성은 캡처에서 이렇게 드러납니다.

> **흔한 예측 실수** — 서버 개인키가 있으면 그 서버로 가는 트래픽은 다 열린다고 봅니다. 열리는 것은 키 교환이 정적 RSA 인 연결뿐입니다.

### B7. 키 로그로 ECDHE 캡처를 엽니다

예측합니다. 키 로그 파일 하나를 받아 두면 그 서버의 옛 캡처도 열 수 있을까요?

```bash
docker exec -d tls-server sh -c 'tcpdump -i eth0 -w /pcap/b7-keylog.pcap "tcp port 4433" 2>/dev/null'
docker exec tls-client sh -c \
  'sleep 2; SSLKEYLOGFILE=/pcap/b7-keys.log curl -s --cacert /certs/ca.crt \
     --connect-to a.test:4433:a.test:4433 --tls-max 1.2 https://a.test:4433/ -o /dev/null'
sleep 3; docker exec tls-server pkill -f tcpdump

tshark -r pcap/b7-keylog.pcap -o tls.keylog_file:pcap/b7-keys.log -q -z follow,tls,ascii,0
```

이번에는 ECDHE 인데도 열립니다. 파일 한 줄의 구조를 보면 왜 그런지, 그리고 왜 다른 연결에는 안 통하는지가 같이 드러납니다.

```bash
# 값은 줄여 적었습니다
# CLIENT_RANDOM 4f87d368843b... 9a2c31e0bb7d...
#               └ ClientHello 의 난수      └ master secret
```

첫 값이 색인입니다. ClientHello 에 평문으로 실려 나간 난수와 같은 값입니다. 직접 대조하면 일치합니다.

```bash
awk '{print substr($2,1,16)}' pcap/b7-keys.log
tshark -r pcap/b7-keylog.pcap -Y 'tls.handshake.type==1' \
  -T fields -e tls.handshake.random | cut -c1-16
# 두 출력이 같은 값입니다
```

그래서 이 파일로 묶음 A 의 옛 캡처를 열면 다시 비어 있습니다. 그 연결의 난수에 해당하는 줄이 파일에 없기 때문입니다.

> **흔한 예측 실수** — 키 로그를 한 번 확보하면 그 서버의 통신을 계속 열 수 있다고 봅니다. 로그는 기록된 그 연결만 엽니다. 그래서 복호화가 필요한 통신이 일어나는 시점에 확보해야 합니다.



## 묶음 C · 실패와 진단

> 일부러 협상을 깨뜨려 Alert 를 만들고, 서버가 받아들이는 조건을 밖에서 복원한 뒤, TLS 1.3 에서 보이는 것과 가려지는 것을 가릅니다. 세 단계입니다.

### C8. 조건을 어긋나게 해 Alert 를 만듭니다

예측합니다. 클라이언트가 서버에 없는 묶음만 제안하면 선에 무엇이 나올까요?

```bash
docker exec -d tls-server sh -c \
  'openssl s_server -4 -accept 4433 -cert /certs/a.test.crt -key /certs/a.test.key \
     -www -tls1_2 -cipher AES128-SHA'
docker exec -d tls-server sh -c 'tcpdump -i eth0 -w /pcap/c8-alerts.pcap "tcp port 4433" 2>/dev/null'

# cipher 불일치 — 서버에 없는 묶음만 제안합니다
docker exec tls-client sh -c \
  'sleep 2; echo | openssl s_client -4 -connect a.test:4433 -CAfile /certs/ca.crt \
     -tls1_2 -cipher AES256-SHA'

# 버전 불일치 — SECLEVEL=0 이 없으면 제안 자체가 안 나갑니다
docker exec tls-client sh -c \
  'echo | openssl s_client -4 -connect a.test:4433 -CAfile /certs/ca.crt \
     -tls1_1 -cipher "DEFAULT:@SECLEVEL=0"'
sleep 3; docker exec tls-server pkill -f tcpdump
```

```bash
./look-tls.sh pcap/c8-alerts.pcap 'tls.alert_message'
# 프레임 7   level 2   desc 40   length 2
# 프레임 17  level 2   desc 70   length 2
```

Alert 는 레코드 종류 21 이고 길이가 2바이트입니다. 수준 1바이트와 번호 1바이트가 전부라 화면에서 눈에 잘 안 띕니다. `desc 40` 은 `handshake_failure`, `desc 70` 은 `protocol_version` 이고 클라이언트 쪽 출력에도 같은 번호가 찍힙니다.

성공한 연결과 나란히 두면 차이가 분명합니다. 성공은 ClientHello 뒤에 `2, 11, 12, 14` 가 이어지고 실패는 종류 21 하나로 끝납니다. 종류 2 가 아예 오지 않았다는 사실 자체가 협상이 서지 못했다는 단서입니다.

> **흔한 예측 실수** — 실패하면 에러가 명시적으로 보일 것이라 봅니다. Alert 는 2바이트 레코드 하나라 필터를 걸지 않으면 지나치기 쉽습니다.

### C9. 서버가 받아들이는 조건을 밖에서 복원합니다

예측합니다. 서버 설정을 볼 수 없을 때 지원 목록을 알아내는 일반적인 방법이 있을까요?

서버는 자기 목록을 말해 주는 메시지를 갖고 있지 않습니다. 제안을 받아 하나를 고르거나 거절할 뿐입니다. 그래서 훑는 쪽은 묶음을 하나씩만 제안해 붙여 보고 실패하면 다음으로 넘어가는 일을 반복합니다. 이것이 표준 방법입니다.

```bash
docker exec tls-client sh -c '
  for c in $(openssl ciphers "ALL:@SECLEVEL=0" | tr ":" " "); do
    if echo | openssl s_client -4 -connect a.test:4433 -tls1_2 \
         -cipher "$c" -CAfile /certs/ca.crt >/dev/null 2>&1; then echo "$c"; fi
  done'
```

묶음 140개를 제안해 서버에 숨겨 둔 설정이 그대로 복원됩니다. 위 C8 의 서버를 세 묶음으로 띄워 두고 돌리면 그 셋만 되돌아옵니다. 걸리는 시간은 환경에 따라 다르며 실행할 때마다 달라집니다.

`nmap --script ssl-enum-ciphers` 가 하는 일도 이와 같습니다. 도구는 목록을 알지 못합니다. 하나씩 붙여 보고 되는 것을 모읍니다.

> **흔한 예측 실수** — 하나씩 붙여 보는 방식이 가능은 해도 일반적인 방법은 아닐 것이라 봅니다. 프로토콜에 목록을 묻는 수단이 없어 이 방식이 표준입니다.

### C10. TLS 1.3 에서 무엇이 가려지는지 봅니다

1.3 캡처를 키 없이 열면 핸드셰이크 메시지가 몇 종류나 보일지 예측해 봅니다.

```bash
docker exec -d tls-server sh -c \
  'openssl s_server -4 -accept 4433 -cert /certs/a.test.crt -key /certs/a.test.key -www'
docker exec -d tls-server sh -c 'tcpdump -i eth0 -w /pcap/c10-tls13.pcap "tcp port 4433" 2>/dev/null'
docker exec tls-client sh -c \
  'sleep 2; SSLKEYLOGFILE=/pcap/c10-keys.log curl -s --cacert /certs/ca.crt \
     --connect-to a.test:4433:a.test:4433 https://a.test:4433/ -o /dev/null'
sleep 3; docker exec tls-server pkill -f tcpdump
```

키 없이 열면 종류가 `1` 과 `2` 둘뿐이고 인증서로 검색하면 0건입니다. 같은 캡처에 키 로그를 물리면 프레임 하나에서 다섯이 한꺼번에 드러납니다.

```bash
tshark -r pcap/c10-tls13.pcap -Y 'tls.handshake.type' -T fields -e frame.number -e tls.handshake.type
# 4  1
# 6  2

tshark -r pcap/c10-tls13.pcap -o tls.keylog_file:pcap/c10-keys.log \
  -Y 'tls.handshake.type' -T fields -e frame.number -e tls.handshake.type
# 4   1
# 6   2,8,11,15,20
# 10  4
# 11  4
```

숨어 있던 것이지 오지 않은 것이 아닙니다. 프레임 10·11 의 종류 4 는 `NewSessionTicket` 이고 핸드셰이크가 끝난 뒤에 옵니다.

그렇다고 1.3 이 전부를 가리는 것은 아닙니다. 협상에 필요한 값은 여전히 평문으로 지나갑니다.

| 항목 | 키 없이 | 실측값 |
|---|:---:|---|
| SNI | 보입니다 | `a.test` |
| 고른 cipher suite | 보입니다 | `0x1302` |
| `key_share` 그룹 | 보입니다 | `29` (x25519) |
| ClientHello 레코드 길이 | 보입니다 | 512바이트 |
| 인증서 | 안 보입니다 | 키 로그가 있어야 종류 11 이 드러납니다 |

1.3 의 키 로그는 라벨이 하나가 아닙니다. 방향과 단계마다 따로 기록돼 다섯 종이 들어 있습니다.

```bash
cut -d' ' -f1 pcap/c10-keys.log | sort -u
# CLIENT_HANDSHAKE_TRAFFIC_SECRET · SERVER_HANDSHAKE_TRAFFIC_SECRET
# CLIENT_TRAFFIC_SECRET_0 · SERVER_TRAFFIC_SECRET_0 · EXPORTER_SECRET
```

인증서를 보려면 서버 방향 핸드셰이크 비밀이, 본문을 보려면 traffic secret 이 필요합니다. 1.3 에는 서버 개인키로 여는 길이 없으므로 키 로그가 유일한 경로입니다.

> **흔한 예측 실수** — 1.3 캡처에 인증서가 없다고 봅니다. 왔지만 암호화돼 있고, 키를 물리면 같은 프레임에서 드러납니다.



## 세기 전에 속는 자리 셋

> 위 열 단계에서 실제로 잘못 세거나 놓친 자리입니다.

캡처가 비어 있으면 먼저 `-4` 와 `sleep` 둘을 봅니다. IPv6 로 붙었거나 tcpdump 가 장치를 열기 전에 접속한 것이 대부분입니다. 필터나 명령이 틀린 경우는 그다음입니다.

한 캡처 파일에 연결이 여럿 섞이면 수치가 어긋납니다. ClientHello 의 묶음 개수를 셀 때 파일 전체에서 세면 여러 연결의 합이 나옵니다. `frame.number` 로 한 연결을 고정하고 세야 28 이 나옵니다.

복호화가 됐는데 내용이 비어 보이면 무엇을 보냈는지 돌아봅니다. `echo |` 로 접속하면 개행 하나만 나가므로 스트림이 열려도 볼 것이 없습니다. 요청과 응답을 보려면 `curl` 로 실제 HTTP 요청을 실어야 합니다.



## 남은 것

> 이 랩으로 확인하지 못한 것 셋입니다. 구성상 세울 수 없었거나 범위를 넘는 자리입니다.

이 랩은 서버 쪽 조건만 바꿔 가며 봤습니다. 클라이언트 인증서를 요구하는 상호 인증 구성은 세우지 않았습니다. 그래서 상호 인증에서만 오는 메시지 셋이 실제로 어떻게 찍히는지는 캡처로 확인하지 못했습니다. [04-01 §4](./04-01.TLS%20%ED%95%B8%EB%93%9C%EC%85%B0%EC%9D%B4%ED%81%AC%20%EC%9D%BD%EA%B8%B0.md) 의 그림으로만 두었습니다.

세션 재개도 범위 밖입니다. `NewSessionTicket` 이 오는 것은 C10 에서 봤지만, 그 티켓으로 다시 붙었을 때 핸드셰이크가 얼마나 짧아지는지는 잡지 않았습니다.

ECH 는 랩 구성으로 만들 수 없었습니다. 공개 이름과 내부 이름을 가르려면 DNS 의 HTTPS 레코드까지 세워야 해서 이 편의 컨테이너 둘로는 범위를 넘습니다.
