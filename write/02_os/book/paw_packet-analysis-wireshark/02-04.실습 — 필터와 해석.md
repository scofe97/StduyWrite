# 실습 — 필터와 해석

---

> 앞 세 편의 개념을 명령줄에서 직접 확인하는 실습입니다.

§1 은 1장의 링크 계층을 루프백에서 다시 봅니다. §2~§4 는 02-01·02-02 의 캡처 필터와 디스플레이 필터를 대조하고 §5~§8 은 02-03 의 해석과 재조립, Follow Stream 을 다룹니다. §9 는 같은 02-03 의 IO Graph 와 Conversations 를 숫자로 읽습니다.

## 실험실

> macOS, Wireshark 4.6 계열. 2026-09-14 실행. 1장 실습이 Wi-Fi 에서 남의 기기 이름을 잡아 와 자리를 루프백으로 옮겼습니다.

```bash
# lo0 은 기계 밖으로 안 나가는 가상 인터페이스 — 남의 프레임이 물리적으로 못 들어온다
# 포트 18080 은 Wireshark 가 80·8080 을 비롯한 여러 포트를 이미 HTTP 로 등록해 둬서 피한 번호다
python3 -m http.server 18080 > /dev/null 2>&1 &
curl -sI http://localhost:18080/ | head -2
```

```bash
HTTP/1.0 200 OK
Server: SimpleHTTP/0.6 Python/3.14.4
```



## 1. 루프백의 링크 계층

> 1장에서 본 이더넷 헤더가 여기에는 없습니다.

```bash
# 6초 잡는 사이에 요청 하나를 보낸다
dumpcap -i lo0 -a duration:6 -w ~/lab.pcapng &
sleep 2 && curl -s http://localhost:18080/ -o /dev/null

# 링크 계층 헤더만 뽑아 본다
tshark -r ~/lab.pcapng -c 1 -V | grep -A 3 "^Null/Loopback"
```

```bash
Null/Loopback
    Family: IP (2)
Internet Protocol Version 4, Src: 127.0.0.1, Dst: 127.0.0.1
```

`-V` 전체를 보면 Frame 블록의 `Encapsulation type` 이 `Ethernet (1)` 이 아니라 `NULL/Loopback (15)` 입니다. MAC 자리가 통째로 없고 4바이트에 프로토콜 패밀리 번호만 들어갑니다. `AF_INET` 이 2, macOS 에서 `AF_INET6` 이 30 입니다. 배달할 상대가 없으니 주소가 필요 없습니다.



## 2. 두 필터는 문법이 다릅니다

> 같은 조건인데 표기가 갈립니다.

```bash
# -f 는 캡처 필터, BPF 문법. 커널에 올라가고 통과 못 한 것은 복사조차 안 된다
dumpcap -f "tcp port 18080"

# -Y 는 디스플레이 필터, Wireshark 문법. 파일을 다 읽은 뒤 보여줄 것만 고른다
tshark -Y 'tcp.port==18080'

# 바꿔 쓰면 둘 다 통하지 않는다
# dumpcap -f "tcp.port==80"   → 에러
# tshark  -Y 'port 80'        → 에러
```

두 필터는 거르는 시점이 다릅니다. 캡처 필터는 담기 전에 버립니다(02-01). 디스플레이 필터는 담은 뒤에 보이는 범위만 좁힙니다(02-02). 다음 절은 이 시점 차이가 결과를 어떻게 가르는지 봅니다.



## 3. 캡처 필터로 버린 것은 되살아나지 않습니다

> 같은 디스플레이 필터를 두 파일에 똑같이 겁니다.

§1 에서 필터 없이 뜬 `lab` 에는 HTTP 말고도 NFS 프레임이 섞여 있었습니다. 이 기계의 다른 프로세스가 lo0 로 주고받은 트래픽이고 어느 프로세스인지는 확인하지 않았습니다. 캡처 필터를 걸면 이런 곁 트래픽이 어떻게 되는지를 이 NFS 프레임으로 봅니다.

```bash
# 이번엔 캡처 필터로 18080 만 담는다
dumpcap -i lo0 -a duration:5 -f "tcp port 18080" -w ~/narrow.pcapng &
sleep 1 && curl -s http://localhost:18080/ -o /dev/null

# 같은 -Y 'nfs' 를 두 파일에 건다. narrow 는 결과 없음, lab 은 3건 이상
tshark -r ~/narrow.pcapng -Y 'nfs'
tshark -r ~/lab.pcapng    -Y 'nfs'
```

```bash
narrow: Packets captured: 14   → nfs 0건
lab:    Packets captured: 36   → nfs 3건 이상
```

필터 문법이 틀린 것이 아닙니다. 같은 `-Y 'nfs'` 가 `lab` 에서는 작동합니다. `narrow` 에는 NFS 프레임이 애초에 담기지 않았습니다.



## 4. BPF 는 바이트 자리를 짚어 읽습니다

> 컴파일된 결과를 직접 볼 수 있습니다.

```bash
# -d 가 컴파일된 BPF 명령어를 출력한다
# 인터페이스를 지정하지 않으면 macOS 는 PKTAP 으로 열려 -d 가 실패한다
sudo tcpdump -i en0 -d 'udp port 53'
```

```bash
(000) ldh      [12]
(001) jeq      #0x86dd          jt 2    jf 8
(002) ldb      [20]
(003) jeq      #0x11            jt 4    jf 19
(004) ldh      [54]
(005) jeq      #0x35            jt 18   jf 6
(006) ldh      [56]
(007) jeq      #0x35            jt 18   jf 19
(008) jeq      #0x800           jt 9    jf 19
(009) ldb      [23]
(010) jeq      #0x11            jt 11   jf 19
(011) ldh      [20]
(012) jset     #0x1fff          jt 19   jf 13
(013) ldxb     4*([14]&0xf)
(014) ldh      [x + 14]
(015) jeq      #0x35            jt 18   jf 16
(016) ldh      [x + 16]
(017) jeq      #0x35            jt 18   jf 19
(018) ret      #524288
(019) ret      #0
```

이 출력에 나온 명령은 세 갈래입니다.

- `ld*` — 정해진 자리를 읽습니다 (`ldx*` 는 보조 레지스터 `x` 에 읽습니다)
- `jeq`·`jset` — 비교해 갈라집니다. `jeq` 는 값이 같은지, `jset` 은 지정한 비트가 켜졌는지를 봅니다 (`jt` 는 참일 때, `jf` 는 거짓일 때)
- `ret` — 담을 바이트 수를 답합니다. `ret #0` 이 버림입니다

흐름은 EtherType 에서 두 갈래로 나뉩니다. 001~007 은 IPv6(`0x86dd`) 쪽이고 008 부터가 IPv4(`0x800`) 쪽입니다. `port 53` 은 출발지나 목적지 어느 쪽이든 걸리므로 두 갈래 모두 포트를 두 번 비교합니다.

IPv4 쪽을 따라가면 오프셋이 곧 계층입니다. `[12]` 는 이더넷 헤더의 EtherType 이고 `[23]` 은 IP 헤더의 Protocol 입니다. 011~012 는 단편(fragment)의 뒷조각이면 포트가 없으니 버립니다. `4*([14]&0xf)` 가 가변 길이 IP 헤더를 계산합니다. `[x+14]` 는 IP 헤더를 건너뛴 UDP 출발지 포트이고 `[x+16]` 은 목적지 포트입니다.

판정은 이렇게 패킷 하나 안에서 끝나고 앞 패킷의 상태를 넘겨받지 못합니다. 그래서 재전송처럼 앞뒤 대조가 필요한 판정은 캡처 필터가 아니라 디스플레이 필터의 몫입니다.



## 5. 포트가 빗나가면 휴리스틱이 받습니다

> 비표준 포트인데도 해석이 붙었습니다. 두 번 다 그랬습니다.

```bash
# NFS 프레임의 실제 포트를 필드로 직접 꺼낸다 — Info 열에 안 보인다고 없는 게 아니다
tshark -r ~/lab.pcapng -c 1 -T fields -e tcp.srcport -e tcp.dstport -e frame.protocols

# 18080 은 Wireshark 에 등록되지 않은 번호인데도 HTTP 로 해석된다
tshark -r ~/lab.pcapng -Y 'tcp.port==18080' | sed -n '4p'
```

```bash
56503   50954   null:ip:tcp:rpc:nfs
   28   ::1 → ::1   HTTP 154   GET / HTTP/1.1
```

NFS 는 표준 포트 `2049` 가 아닌 dynamic 범위에서 잡혔고 HTTP 는 `18080` 에서 잡혔습니다. 둘 다 등록된 포트 밖이니 포트 매칭이 아니라 내용의 패턴으로 판단된 것입니다. TCP 는 기본값에서 포트에 등록된 해석기를 먼저 시도하고 휴리스틱을 앞세우는 설정은 꺼져 있습니다.[^tcp-heur]

포트로 맞는 해석기가 없을 때 휴리스틱 해석기가 내용을 보고 해석을 맡습니다. `tshark -G heuristic-decodes` 에는 TCP 위의 `rpc_tcp` 와 `http_tcp` 가 켜진 채 올라 있습니다. RPC 는 헤더 구조가 독특하고 HTTP 는 첫머리가 평문이라 포트를 보지 않아도 알아봅니다.

해석 경로가 셋인 셈입니다. 포트 매칭, 휴리스틱, 사람이 지정하는 Decode As 입니다. 이번 실습은 포트 매칭이 빗나간 자리에서 휴리스틱이 받는 모습만 봤습니다.



## 6. 같은 바이트, 다른 화면

> 해석을 떼고 붙여 봅니다. 파일은 하나입니다.

```bash
# --disable-protocol 로 HTTP 해석을 끈다
tshark -r ~/lab.pcapng --disable-protocol http -Y 'tcp.port==18080' | sed -n '4p;7p;8p'

# -d 로 "이 포트는 이 프로토콜로 읽어라" 를 지정한다
tshark -r ~/lab.pcapng -d tcp.port==18080,http -Y 'tcp.port==18080' | sed -n '4p;7p;8p'
```

```bash
28  TCP   154  61012 → 18080 [PSH, ACK] Seq=1 Ack=1 Len=78
31  TCP   232  18080 → 61012 [PSH, ACK] Seq=1 Ack=79 Len=156
32  TCP  6238  18080 → 61012 [FIN, PSH, ACK] Seq=157 Len=6162

28  HTTP  154  GET / HTTP/1.1
31  TCP   232  HTTP/1.0 200 OK
32  HTTP 6238  HTTP/1.0 200 OK  (text/html)
```

프레임은 한 바이트도 바뀌지 않았습니다. `Len=78` 도 `Seq=1` 도 양쪽에 그대로 있습니다. 해석이 없으면 78바이트가 갔다는 것까지만 알고 붙으면 `GET /` 를 요청했다는 것을 압니다.

비표준 포트에 서비스를 띄웠을 때 잃는 것이 왼쪽 화면입니다.

- Info 열이 쓸모없어집니다
- `http.*` 디스플레이 필터가 안 먹습니다
- Follow HTTP Stream 으로 대화를 복원할 수 없습니다

3-way handshake(25~27)가 양쪽 모두 `TCP` 인 것도 볼 자리입니다. `Len=0` 이라 안쪽에 해석할 내용이 없습니다.



## 7. 재조립은 필드로 확인합니다

> 눈으로 짐작하지 않고 Wireshark 가 적어 둔 명세를 읽습니다.

```bash
# frame.len 은 프레임 전체, tcp.len 은 TCP 가 나른 데이터만
tshark -r ~/lab.pcapng -Y 'tcp.port==18080' -T fields \
  -e frame.number -e frame.len -e tcp.len -e frame.protocols

# 어느 프레임 몇 바이트씩 합쳤는지가 그대로 적혀 있다
tshark -r ~/lab.pcapng -Y 'frame.number==32' -V | grep -A 4 "Reassembled TCP Segments"
```

```bash
31   232   156   null:ipv6:tcp
32  6238  6162   null:ipv6:tcp:http:data-text-lines

[2 Reassembled TCP Segments (6318 bytes): #31(156), #32(6162)]
    [Frame: 31, payload: 0-155 (156 bytes)]
    [Frame: 32, payload: 156-6317 (6162 bytes)]
    [Segment count: 2]
```

31번의 프로토콜 목록에 `http` 가 없습니다. 응답 헤더를 담고 있는데도 HTTP 메시지가 완성되는 32번에서야 HTTP 로 인정됩니다. 재조립 여부는 `tcp.reassembled_in` 필드로 확정하고 추론하지 않습니다. 이 필드는 뒤 프레임을 봐야 채워지므로 `-2` 로 두 번 읽어야 나옵니다.[^tshark-2] 같은 모양으로 다시 뜬 캡처에서 `-2 -T fields -e tcp.reassembled_in` 은 응답 헤더 세그먼트에 본문 세그먼트의 프레임 번호를 돌려주었습니다. `-2` 를 빼면 빈칸이었습니다.

`6238 - 6162 = 76` 은 루프백 4 + IPv6 40 + TCP 32 입니다.



## 8. Follow Stream 은 TCP 를 걷어냅니다

> 쪼개진 세그먼트를 애플리케이션이 본 바이트로 되돌립니다.

```bash
# 스트림 번호를 먼저 찾는다
tshark -r ~/lab.pcapng -Y 'tcp.port==18080' -T fields -e tcp.stream | head -1

# -q 는 패킷 목록을 찍지 말라는 뜻, -z 가 분석 기능을 하나 돌린다
tshark -r ~/lab.pcapng -q -z follow,tcp,ascii,2 | head -20
```

첫 명령이 `2` 를 돌려주어 둘째 명령 끝에 그 번호를 넣었습니다.

```bash
Node 0: [::1]:61012
Node 1: [::1]:18080
78
GET / HTTP/1.1
Host: localhost:18080
        156
HTTP/1.0 200 OK
Content-Length: 6162
        6162
<!DOCTYPE HTML>
```

`Seq`·`Ack`·`Win` 이 없습니다. 애플리케이션 관점의 바이트 스트림을 복원하는 기능이라 TCP 제어 정보를 걷어냅니다. 남은 숫자는 각 방향의 바이트 수이고 들여쓰기가 방향을 나눕니다.



## 9. 숫자로 보는 트래픽

> GUI 의 IO Graph 와 Conversations 를 명령줄로 봅니다. 리듬이 있어야 볼 만해서 1초 간격으로 다섯 번 요청했습니다.

```bash
# 9초 잡는 사이 1초 간격으로 5회 요청
dumpcap -i lo0 -a duration:9 -f "tcp port 18080" -w ~/stat.pcapng &
sleep 2 && for i in 1 2 3 4 5; do curl -s http://localhost:18080/ -o /dev/null; sleep 1; done

# IO Graph 의 숫자 판 — 1초 단위 집계
tshark -r ~/stat.pcapng -q -z io,stat,1

# Conversations — 어느 쌍이 얼마나 주고받았나
tshark -r ~/stat.pcapng -q -z conv,tcp
```

```bash
| Interval | Frames | Bytes |
|  0 <> 1  |     12 |  7430 |
|  1 <> 2  |     12 |  7430 |
|  2 <> 3  |     12 |  7430 |
|  3 <> 4  |     12 |  7430 |
|  4 <> Dur|     12 |  7430 |

::1:53094  <-> ::1:18080    6 6,884 bytes    6 546 bytes   12 7,430 bytes   0.000000000   0.0183
::1:53096  <-> ::1:18080    6 6,884 bytes    6 546 bytes   12 7,430 bytes   1.037073000   0.0017
::1:53098  <-> ::1:18080    6 6,884 bytes    6 546 bytes   12 7,430 bytes   2.058556000   0.0064
::1:53099  <-> ::1:18080    6 6,884 bytes    6 546 bytes   12 7,430 bytes   3.088026000   0.0042
::1:53100  <-> ::1:18080    6 6,884 bytes    6 546 bytes   12 7,430 bytes   4.110289000   0.0014
```

같은 요청을 같은 간격으로 보냈으니 `io,stat` 은 평평합니다. 실제 조사에서는 **이 선이 튀는 구간**을 찾는 것이 목적입니다. 7장의 DoS 탐지가 그 용도입니다.

`conv` 의 단위는 **대화**입니다. `curl` 한 번이 대화 하나라 다섯 줄이 나왔습니다. 왕복 횟수나 RTT 가 아닙니다.

**연결이 다섯으로 갈린 이유는 `curl` 을 다섯 번 따로 실행했기 때문입니다.** curl man page 는 연결 재사용이 한 명령줄에 적은 URL 사이에서만 되고 따로 실행한 curl 사이에서는 안 된다고 적습니다.[^curl-reuse]

서버도 연결을 붙잡지 않습니다. 요청은 `GET / HTTP/1.1` 로 갔는데 파이썬 `http.server` 의 기본 `protocol_version` 이 `HTTP/1.0` 입니다. 1.0 은 keep-alive 가 기본이 아니라 응답 뒤 연결을 닫습니다 — 6절에서 본 `FIN` 이 그것입니다. 서버가 1.1 로 답하더라도 curl 을 따로 실행하는 한 대화는 다섯으로 잡힙니다.

`io,stat` 출력 머리에 찍힌 `Duration: 4.111640 secs`(위 출력에서는 머리를 줄였습니다)는 캡처를 켠 시간이 아니라 **첫 프레임부터 마지막 프레임까지**입니다. 9초를 잡았지만 트래픽이 있었던 구간은 4.11초입니다.

출발지 포트가 매번 다른 것도 눈여겨볼 만합니다. TCP 연결의 식별자는 `(출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트)` 네 쌍인데 여기서는 셋이 같습니다. 출발지 포트가 겹치면 커널이 응답을 어느 연결에 줄지 가릴 수 없어 연결마다 새 번호를 배정합니다. dynamic 범위에서 나오는 이 번호를 ephemeral port 라고 합니다.



## 뒷정리

> 루프백이라 민감정보는 없지만 서버 프로세스가 남습니다.


## 남은 것

> 2장 범위에서 재현하지 못한 축입니다.

이번 회차는 전부 명령줄로 돌렸습니다. 엔진은 같으므로 개념은 같은 것을 봤지만 **2장은 화면 기능을 적지 않게 다루고 그쪽은 통째로 빠졌습니다.**

| 축 | 상태 |
|----|------|
| 네 개 창의 연동 (`02-02` §1) | **못 함** — 명령줄에는 창이 없습니다 |
| 색 규칙 (`02-02` §2) | **못 함** — 화면 전용입니다 |
| IO Graph 의 실제 그래프 (`02-03` §3) | 숫자 판(`-z io,stat`)만 봤습니다 |
| 방화벽 ACL 규칙 생성 (`02-03` §6) | **못 함** — GUI 의 Tools 메뉴 기능입니다 |
| Follow Stream (`02-03` §4) | 명령줄로 했고 GUI 팝업으로는 안 봤습니다 |
| Decode As (`02-03` §1) | `-d` 로 했고 GUI 메뉴로는 안 봤습니다 |

명령줄에서도 남은 것이 셋 있습니다.

- **링 버퍼 동작** — `-b filesize:`·`-b files:` 로 파일이 실제로 갈아 끼워지는 것을 확인하지 않았습니다. 오래 돌릴 시간이 필요합니다.
- **휴리스틱이 실패하는 경우** — Decode As 가 꼭 필요해지는 것은 휴리스틱 해석기가 없는 프로토콜이 비표준 포트에 뜰 때입니다. 이번에는 `--disable-protocol` 로 끄는 대조로 대신했습니다.
- **snaplen 과 이름 해석** — `-s` 로 앞부분만 담았을 때와 `-n` 으로 이름 해석을 껐을 때의 차이를 재지 않았습니다.
