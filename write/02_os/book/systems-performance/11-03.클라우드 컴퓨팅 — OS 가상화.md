# 클라우드 컴퓨팅 — OS 가상화
---
> 이 노트는 11.3 OS 가상화를 다룹니다. 하나의 커널이 격리된 OS 인스턴스(컨테이너)를 만드는 방식, 그 장단점(빠른 부팅·세밀한 공유 vs 커널 경합·관측성 상실), namespace·cgroup 구현, 자원 제어, 그리고 호스트·게스트에서의 관측과 점검 순서를 봅니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 **커널이 하나뿐이라는 사실 하나가 컨테이너의 모든 장점과 모든 단점을 동시에 만든다는 것**입니다.

OS 가상화는 운영체제를 Linux가 *컨테이너* 라 부르는 인스턴스로 나눕니다. 각 컨테이너는 별도 게스트 서버처럼 동작하고 독립적으로 관리·재부팅됩니다.

하드웨어 가상화와의 결정적 차이는 **커널이 하나만 실행된다** 는 점입니다. 커널을 새로 띄우지 않으니 부팅이 밀리초 단위로 끝납니다. 게스트마다 커널이 메모리를 먹지도 않습니다. 호스트에서는 모든 게스트 프로세스가 그대로 보입니다.

같은 사실이 반대쪽도 만듭니다. 커널을 공유하니 커널 자원 경합이 늘어납니다. 게스트는 그 커널을 분석할 수 없습니다. 커널이 패닉하면 모든 게스트가 함께 죽고, 다른 커널 버전을 쓰는 것도 불가능합니다.

이 계보는 Unix의 `chroot` 에서 시작합니다. 프로세스가 보는 최상위 디렉토리를 다른 곳으로 바꿔, 파일 시스템의 한 서브트리에 가두는 명령입니다.

갈래는 둘입니다. Unix 계열이 격리 구획을 먼저 완성했고, Linux는 부품을 따로따로 쌓았습니다.

| 갈래 | 연도 | 기술 |
|------|------|------|
| Unix 계열 | 1998 | FreeBSD jails — 자체 서버처럼 동작하는 격리 구획 |
| Unix 계열 | 2005 | Solaris Zones — 각종 자원 제어 포함 |
| Linux | 2002 | namespace (2.4.19) |
| Linux | 2008 | cgroup (2.6.24) |

Linux는 마지막 둘을 조합해 컨테이너를 만들고, 보통 여기에 seccomp-bpf를 더해 syscall 접근까지 통제합니다.



## 학습 목표

> 이 편을 덮은 뒤 스스로 할 수 있어야 하는 일을 먼저 적어 둡니다.

- 커널이 하나라는 사실에서 장점과 단점을 각각 이끌어 냅니다.
- 커널에 컨테이너 개념이 없는데 컨테이너가 어떻게 만들어지는지 설명합니다.
- 멀티테넌트 경합이 전통 다중 사용자 환경보다 심한 까닭을 댑니다.
- shares 와 bandwidth 값으로 컨테이너가 쓸 CPU 범위를 계산하고, bursting 이 사용자를 오해하게 만드는 까닭을 말합니다.
- 컨테이너 안에서 보이는 전역 통계가 누구 것인지 가리고, 소프트웨어 한계를 먼저 점검해 CPU 가 어떤 한계에 막혔는지 지표로 가리며, 자원 제어용 USE 체크리스트를 짭니다.

![11-03 전체 지도 — 커널 하나가 규정하는 다섯 절](_assets/11-03.chapter-overview.svg)

첫 절이 나머지 전체를 규정합니다. 구현·오버헤드·제어·관측이 모두 "커널이 하나"라는 사실에서 따라 나옵니다.



## 이 문서가 다루지 않는 것

> 앞뒤 편으로 넘긴 주제를 밝혀 둡니다.

- **클라우드 일반 배경** — 11-01이 다룹니다.
- **하드웨어 가상화**(하이퍼바이저·guest exit) — 11-02가 다룹니다.
- **경량 가상화와 세 기술 비교** — 11-04가 다룹니다. 컨테이너의 단점을 푸는 방법이 거기 있습니다.
- **Kubernetes 운영** — 11-01이 개요만 다루고, 이 편은 그 아래 커널 기능을 봅니다.



## 1. 컨테이너의 장단점 — 빠른 공유와 잃는 격리

> 컨테이너는 커널이 하나라 빠른 부팅·메모리 절약·세밀한 자원 공유·호스트의 높은 관측성을 줍니다. 대가는 커널 자원 경합 증가, 게스트의 관측성 상실(커널 분석 불가), 커널 패닉이 모든 게스트에 영향, 커스텀/다른 커널 불가입니다.

장점만 골라 세거나 단점만 골라 세면 컨테이너를 잘못 보게 됩니다. 둘은 같은 뿌리에서 나오기 때문입니다.

커널이 하나라는 점이 하드웨어 VM 대비 장단점을 모두 만듭니다.

| 장점 | 설명 |
|------|------|
| 빠른 초기화 | 보통 밀리초 단위 |
| 메모리 효율 | 게스트가 메모리를 전부 앱에 씀(추가 커널 없음) |
| 통합 파일 시스템 캐시 | 호스트·게스트 이중 캐싱 회피 |
| 세밀한 자원 공유 | cgroup |
| 호스트 관측성↑ | 게스트 프로세스가 직접 보임 |
| 페이지 공유 | 공통 파일을 공유해 캐시 절약·CPU 캐시 적중↑ |
| 실제 CPU | 적응형 뮤텍스 락이 기대는 가정이 그대로 성립 |

| 단점 | 설명 |
|------|------|
| 커널 자원 경합↑ | 락·캐시·버퍼·큐 |
| 게스트 관측성↓ | 커널을 분석할 수 없음 |
| 커널 패닉 | 모든 게스트에 영향 |
| 커스텀 커널 모듈 불가 | |
| 장기 실행 PGO 커널 불가 | 원서 3.5.1의 프로파일 기반 최적화 커널 |
| 다른 커널 버전·종류 불가 | |

> 처음 두 단점을 함께 보면 핵심이 드러납니다 — VM에서 컨테이너로 옮긴 게스트는 *커널 경합 문제를 더 만나면서 동시에 그것을 분석할 능력을 잃습니다*. 그래서 이런 분석을 호스트 운영자에 더 의존하게 됩니다. 모든 단점은 경량 가상화(11-04)가 풀지만, 일부 장점을 대가로 합니다. 비성능 단점으로는 커널 공유로 인한 *약한 보안* 이 있습니다.



## 2. 구현 — namespace와 cgroup

> Linux 커널에 "컨테이너"라는 개념은 없습니다 — 유저 공간 소프트웨어(Docker 등)가 namespace와 cgroup을 조합해 컨테이너를 만듭니다. namespace는 시스템 뷰를 필터링해 격리하고, cgroup은 자원 사용을 제한합니다.

![컨테이너 = namespace + cgroup](_assets/11-03.container-namespace-cgroup.svg)

Linux 커널에는 *컨테이너라는 개념이 없습니다.* namespace와 cgroup이 있을 뿐이고, 유저 공간 소프트웨어가 이 둘을 조합해 "컨테이너"라 부르는 것을 만듭니다.

컨테이너마다 PID 1 프로세스가 있지만 서로 다른 namespace에 속하므로 각각 다른 프로세스입니다.

**namespace** 는 시스템 뷰를 필터링해 컨테이너가 자기 자원만 보고 관리하게 합니다. 격리의 1차 메커니즘입니다.

| namespace | 격리 대상 |
|-----------|----------|
| cgroup | cgroup 가시성 |
| ipc | 프로세스 간 통신 |
| mnt | 파일 시스템 마운트 |
| net | 네트워크 스택(인터페이스·소켓·라우트) |
| pid | 프로세스 가시성(/proc 필터) |
| time | 컨테이너별 시스템 시계 |
| user | 사용자 ID |
| uts | 호스트 정보(uname) |

`lsns`로 현재 namespace를 봅니다.

**cgroup**(control group)은 자원 사용을 제한합니다. v1과 v2가 있고, 책이 쓰인 시점에는 Kubernetes를 비롯한 많은 프로젝트가 아직 v1을 쓰고 있었습니다.

아래는 원서가 드는 cgroup v1 컨트롤러 중 이 편에서 쓰거나 알아 둘 것입니다. 원서 표에는 devices·hugetlb·rdma 도 있습니다. `net_cls` 가 붙이는 **classid** 는 패킷에 다는 클래스 번호이고, qdisc 와 방화벽이 이 번호로 패킷을 골라 처리합니다.

| cgroup v1 | 제한 대상 |
|--------|----------|
| blkio | 블록 I/O(바이트·IOPS) |
| cpu | 공유 기반 CPU |
| cpuacct | 프로세스 묶음의 CPU 사용 계정 — 제한이 아니라 집계 |
| cpuset | CPU·메모리 노드 할당 |
| memory | 프로세스·커널·swap 메모리 |
| net_cls·net_prio | 패킷 classid·인터페이스 우선순위 |
| perf_event | perf 가 cgroup 단위로 프로세스를 관측하게 함 — 제한이 아니라 관측 범위 |
| pids | 생성 프로세스 수 |

cgroup은 컨테이너 간 자원 경합을 제한합니다. 하드 한계는 CPU·메모리처럼 상한을 못 박습니다. 소프트 한계는 CPU·디스크를 공유 기반으로 나눕니다. v2는 계층 기반이라 v1의 여러 단점을 풀었습니다. 원서는 컨테이너 기술이 앞으로 몇 해에 걸쳐 v2로 옮겨 가고 v1은 결국 폐기될 것이라 전망했고, 2019년 Fedora 31 이 이미 v2로 바꿨다고 적습니다.

> **갱신 (2026-09)**: 원서가 전망한 이동은 대부분 진행됐습니다. Kubernetes는 v1.25에서 cgroup v2 지원을 GA로 올렸고, v1.35에서 cgroup v1을 deprecated로 지정했습니다. 지금 kubelet은 기본 설정으로는 cgroup v1 노드에서 뜨지 않습니다(`failCgroupV1` 을 false로 낮춰야 뜹니다). 배포판도 대부분 v2가 기본입니다 — Ubuntu 21.10+, Debian 11+, Fedora 31+, RHEL 9+.[^k8s-cgroups] v2 커널 문서의 컨트롤러 목록에는 `blkio` 대신 `io` 가 있고 `net_cls`·`net_prio` 는 없습니다.[^cgv2] 이 편의 설정 이름은 원서를 따라 v1 기준이므로, v2 노드에서는 이 차이를 감안해 읽습니다.

> 구현의 핵심은 *컨테이너 = namespace(격리) + cgroup(제한)* 의 조합이고, 커널엔 통일된 컨테이너 ID가 없다는 점입니다. 이것이 관측을 복잡하게 만듭니다(§5). 전통 도구가 컨테이너 ID를 모르기 때문입니다. Kubernetes는 여러 컨테이너가 같은 namespace를 공유하는 Pod로 묶어 더 빠른 통신을 가능하게 합니다.



## 3. 오버헤드 — 가벼운 실행과 멀티테넌트 경합

> 컨테이너 실행은 가벼워, 앱 CPU·메모리는 베어메탈 성능을 냅니다(namespace·cgroup에 추가 CPU 오버헤드 없음). 가장 큰 성능 문제는 멀티테넌트 경합 — 컨테이너가 커널·물리 자원 공유를 더 조장하기 때문입니다.

컨테이너 실행 오버헤드는 가벼워야 합니다. 앱 CPU·메모리는 베어메탈 성능을 내되, 파일 시스템·네트워크 경로의 계층 때문에 I/O에 커널 내 추가 호출이 있을 수 있습니다.

- **CPU**: 유저 모드 실행에 직접 오버헤드가 없습니다. namespace와 cgroup 자체에도 추가 CPU 비용이 없습니다. 모든 프로세스가 이미 기본 namespace와 cgroup 안에서 돌고 있기 때문입니다. 다만 Kubernetes 서비스가 수천 개로 늘면 kube-proxy 가 큰 iptables 규칙 집합을 처리하느라 첫 패킷 오버헤드를 겪는데, 원서는 kube-proxy 를 BPF로 대체해 이를 넘을 수 있다고 적습니다.
- **메모리**: 매핑·로드·스토어에 오버헤드가 없습니다. 앱이 할당된 메모리를 전부 씁니다(VM은 게스트마다 커널이 메모리를 씀). 흔한 컨테이너 구성인 **OverlayFS** 는 여러 파일 시스템을 위아래로 겹쳐 하나처럼 보이게 하는 파일 시스템입니다.[^overlayfs] 같은 아래층 파일을 읽는 컨테이너끼리 페이지 캐시를 공유하므로, 공통 라이브러리를 게스트마다 메모리에 따로 올리는 VM보다 메모리를 아낍니다.
- **I/O**: 격리 계층(OverlayFS, bridge 네트워킹)이 오버헤드를 더합니다. 저IOPS 서버(<1000 IOPS)엔 무시할 수준입니다.

가장 큰 문제는 **멀티테넌트 경합** 입니다. 컨테이너가 커널·물리 자원 공유를 더 조장하기 때문입니다. 원서가 드는 경합은 여섯 가지입니다.

| 경합 | 영향 |
|------|------|
| CPU 캐시 | 다른 테넌트가 엔트리를 evict해 적중률↓(컨텍스트 전환 시 L1 flush 가능) |
| TLB 캐시 | 다른 테넌트·전환으로 적중률↓(PCID로 완화 가능) |
| CPU 인터럽트 | 다른 테넌트 디바이스 인터럽트로 실행 중단 |
| 커널 자원 | 버퍼·캐시·큐·락 경합(멀티테넌트가 부하를 자릿수로 늘림) |
| 네트워크 | iptables 컨테이너 네트워킹의 CPU 오버헤드 |
| 시스템 자원 | 다른 테넌트가 쓰는 CPU·디스크·네트워크 인터페이스 경합 |

TLB 행의 **PCID**(Process-Context Identifier)는 페이지 테이블을 바꿀 때 TLB 전체를 비우지 않고 넘어가게 해 주는 CPU 기능입니다.[^pti] 이 기능이 없으면 문맥 전환마다 다른 테넌트가 채운 TLB를 버리고 다시 채워야 합니다.

> 멀티테넌트 경합이 핵심 오버헤드인 까닭은 *전통 다중 사용자 환경보다 훨씬 심하기 때문* 입니다. 한 사례에선 다른 컨테이너의 워크로드가 dcache(경로 이름을 inode로 바꾼 결과를 담는 커널 캐시, 08-01 §3)에 영향을 줘 lstat 지연이 시간이 지나며 서서히 악화됐습니다. 또 다른 사례는 단일 테넌트 VM에서 멀티테넌트 컨테이너로 옮기며 posix_fadvise 호출이 병목이 됐습니다. 표의 마지막 항목(다른 테넌트의 시스템 자원 경합)은 자원 제어로 관리합니다(§4).



## 4. 자원 제어 — CPU shares·bandwidth와 bursting

> 자원 제어는 우선순위(이웃 간 균형)와 한계(소비 상한)로 나뉩니다. CPU는 cpusets(전체 CPU 할당)·shares(유휴 공유, bursting)·bandwidth(상한)로, 메모리는 한계·소프트 한계로, 디스크·네트워크는 blkio·net_prio로 제어합니다.

![bursting 의 함정 — 빌린 성능을 자기 몫으로 착각한다](_assets/11-03.bursting-trap.svg)

자원 제어는 주로 cgroup으로 자원을 공정히 나눠 쓰게 throttle합니다. 크게 둘로 나뉩니다. *우선순위* 는 중요도에 따라 이웃 사이 균형을 잡고, *한계* 는 소비 상한을 겁니다.

CPU 는 세 방식으로 제어합니다.

- **cpusets**: 전체 CPU를 특정 컨테이너에 할당합니다. 중단 없는 일관된 CPU 용량을 주지만, 유휴 용량을 다른 컨테이너가 못 씁니다.
- **shares**: 스케줄러가 유휴 CPU를 나눠 씁니다. 다른 컨테이너의 유휴 CPU를 빌려 더 빨리 도는 것이 *bursting* 입니다.
- **bandwidth**: CPU 사용 상한입니다.

shares 와 bandwidth 는 둘 다 **CFS**(Completely Fair Scheduler)가 제공합니다. 책 시점 Linux 의 일반 스레드 기본 스케줄러입니다(06-02 §6).

> **갱신 (2026-09)**: Linux 는 6.6 부터 일반 스레드 스케줄러를 CFS 에서 EEVDF(Earliest Eligible Virtual Deadline First)로 옮기기 시작했습니다.[^eevdf] 그래서 지금 v2 커널 문서는 이 계층을 CFS 가 아니라 fair-class 스케줄러라 부릅니다.[^cgv2] shares(v2 의 `cpu.weight`)와 bandwidth(`cpu.max`)의 의미는 그대로입니다.

### shares — 공식에서 나오는 최소 보장

"shares 를 10 줬다"는 말만으로는 컨테이너가 CPU 를 얼마나 쓸지 알 수 없습니다. 몫은 그 순간 누가 바쁜지에 따라 달라지기 때문입니다. 원서의 공식은 이렇습니다.

```bash
# 그 순간 CPU 를 원하는 컨테이너들 사이의 몫
컨테이너 CPU = 전체 CPU × 컨테이너 shares / 시스템에서 바쁜 컨테이너의 shares 합
# 모든 컨테이너가 동시에 바쁠 때 (분모가 전체 shares 합이 된다)
컨테이너 CPU = 전체 CPU × 컨테이너 shares / 시스템 전체 shares 합
```

원서의 예를 따라가 봅니다. 여러 컨테이너에 shares 100 을 나눠 줬고, 컨테이너 A 는 10, B 는 30 을 가졌습니다.

| 그 순간 바쁜 컨테이너 | 분모 | A 의 몫 |
|----------------------|------|---------|
| A 와 B 만 | 10 + 30 = 40 | 10/40 = 25% |
| 모든 컨테이너 | 100 | 10/100 = 10% |
| A 만 | 10 | 10/10 = 100% |

마지막 행이 bursting 입니다. 분모가 가장 커지는 경우가 모두 바쁠 때이므로 A 는 어떤 상황에서도 10% 아래로 내려가지 않습니다. 원서가 shares 를 *최소 보장* 이라 부르는 까닭이 여기서 나옵니다. A 가 실제로 받는 몫은 이웃이 얼마나 바쁘냐에 따라 10% 에서 100% 사이를 오갑니다.

### bursting의 함정과 bandwidth 상한

이 범위가 사용자를 속입니다. 사용자가 idle 시스템에서 컨테이너 A 를 테스트해 100% CPU를 얻고 만족했다가, 나중에 다른 컨테이너가 들어오면 최소치 10% 로 떨어집니다. 원서 저자는 이 장면을 실무에서 여러 번 봤다고 적습니다. 사용자는 시스템 문제라 여기고 디버깅을 요청하지만, 시스템은 설계대로 도는 중이고 10배 느린 것이 새 기준입니다. 많은 모니터링 시스템이 bursting 통계를 보여 주지 않아 용량 계획도 함께 틀어집니다.

급락 폭을 줄이는 방법은 bursting 에 천장을 두는 것입니다. 성능 상한도 함께 낮아지는 대가가 있습니다. A 에 bandwidth 를 시스템 CPU 용량의 20% 로 설정하면, shares 가 주는 바닥 10% 와 합쳐져 A 는 10~20% 사이에서 움직입니다. 20% 는 설정값이고 10~20% 는 그 결과로 생기는 운영 범위입니다. 사용자가 테스트에서 보는 최대치가 20% 이므로 이웃이 들어와도 떨어지는 폭은 두 배에 그칩니다.

이 범위에는 원서가 단 전제가 있습니다. 각 컨테이너에 사용 가능한 CPU 를 다 쓸 만큼 바쁜 스레드가 충분해야 합니다. 스레드가 모자라면 컨테이너는 시스템이 정한 한계에 닿기 전에 자기 워크로드 때문에 먼저 CPU 가 막힙니다.

bandwidth 는 보통 CPU 개수 단위로 노출됩니다. 2.5 는 CPU 두 개 반입니다. 커널 설정은 실제로 마이크로초 단위의 period 와 quota 이고, 컨테이너는 period 마다 quota 만큼의 CPU 시간을 받습니다. 그래서 CPU 개수는 quota 를 period 로 나눈 값입니다.

```bash
# 개념 계산 — period 100,000 µs 에 quota 250,000 µs 를 주면
# 250,000 / 100,000 = 2.5  → 매 100 ms 마다 CPU 시간 250 ms, 즉 CPU 2.5 개 분량
```

Kubernetes 사용자에게는 이 두 손잡이가 익숙한 이름으로 나타납니다. Kubernetes 문서는 CPU request 가 경합 시의 가중치로, CPU limit 이 커널이 CPU throttling 으로 강제하는 하드 상한으로 동작한다고 설명합니다.[^k8s-res] shares 와 bandwidth 의 관계가 request 와 limit 에 그대로 옮겨진 셈입니다.

또 다른 대응은 운영자가 일정 기간(예: 며칠) bursting 중인 사용자에게 알려 주는 것입니다. 사용자가 잘못된 성능 기대를 굳히기 전에, shares 가 더 많은 큰 컨테이너로 올려 최소 보장을 높이도록 권할 수 있습니다. CPU 캐시는 Intel CAT로 제어하되, 캐시 접근을 제한하면 성능도 함께 떨어집니다.

### 메모리·디스크·네트워크 제어

메모리 용량은 memory cgroup 으로 제어합니다.

| 항목 | 역할 |
|------|------|
| limit_in_bytes | 하드 한계 — 넘으면 swap(설정 시) 또는 OOM killer |
| soft_limit_in_bytes | best-effort 회수로 소프트 한계 쪽으로 유도 |
| kmem.limit_in_bytes · kmem.tcp.limit_in_bytes | 커널 메모리·TCP 버퍼 메모리 한계. 현행 v1 문서에서 `kmem.limit_in_bytes` 는 deprecated |
| pressure_level | eventfd(2)로 받는 저메모리 알림 |

컨테이너가 쓰지 않는 메모리는 다른 컨테이너의 페이지 캐시로 쓰입니다. 메모리 형태의 bursting 인 셈입니다. swap 한계는 `memory.memsw.limit_in_bytes` 로 겁니다. 이름의 memsw 는 메모리와 swap 을 합친 양이라는 뜻입니다.

페이지 캐시의 계상은 따로 봐 둘 만합니다. Linux 에서 컨테이너가 쓴 파일 시스템 페이지 캐시는 별도 설정 없이 그 컨테이너의 memory cgroup 에 계상됩니다. 파일을 많이 읽는 컨테이너는 앱 힙이 작아도 메모리 한계에 가까워 보일 수 있습니다. swap 을 켰다면 `memory.swappiness` 로 swap 과 페이지 캐시 회수 중 어느 쪽을 먼저 할지 조정합니다.

디스크 I/O 는 blkio cgroup 이 맡습니다. `blkio.weight` 는 CPU shares 처럼 부하 중 디스크 몫을 정하며 **BFQ**(Budget Fair Queueing) I/O 스케줄러와 함께 씁니다. 현행 v1 문서는 이 파일을 `blkio.bfq.weight` 라는 이름으로 적습니다. BFQ 는 가중치에 비례해 디스크를 나누는 스케줄러입니다.[^bfq]

`blkio.throttle.read_bps_device` 계열은 읽기·쓰기의 바이트/초와 IOPS 에 하드 한계를 겁니다.

네트워크 I/O 는 net_prio 가 송신 우선순위를, net_cls 가 classid 태깅을 맡습니다. 실제 셰이핑은 **qdisc**(queueing discipline, 인터페이스 송신 큐의 처리 규칙, 10-02 §4)가 합니다.

원서는 Kubernetes 의 ingress·egress 대역폭 설정이 토큰 버킷 필터(tbf) qdisc 로 구현된다고 예를 듭니다. 실제로는 Kubernetes 가 이 설정을 bandwidth CNI 플러그인에 넘깁니다. 플러그인이 컨테이너 인터페이스의 송수신 양쪽에 tbf qdisc 를 겁니다.[^cni-bw] cgroup 을 거치는 제어가 아니라 인터페이스에 거는 셰이핑입니다.

cgroup 에 BPF 프로그램을 붙여 커스텀 제어나 방화벽을 만들기도 합니다. Cilium 이 그 예입니다.

> 자원 제어의 핵심은 *우선순위와 한계의 조합* 이고, 특히 CPU shares의 bursting이 양날입니다. 효율(유휴 CPU 활용)을 주지만, 모니터링이 bursting 통계를 안 보여 주면 사용자가 잘못된 성능 기대를 갖게 됩니다. 그래서 bandwidth 로 천장을 두거나, bursting 통계를 노출하거나, bursting 중임을 알려 더 큰 컨테이너를 권합니다.



## 5. 관측 — 호스트는 다 보지만 게스트는 헷갈린다

> 호스트는 모든 컨테이너를 직접 보고, 게스트는 자기 프로세스만 보면서 시스템 전역 통계(CPU·디스크)는 호스트 것을 봐 헷갈립니다. 어느 쪽이든 cgroup 한계가 물리 한계보다 먼저 걸리므로 그것부터 확인합니다.

![VM 과 컨테이너에서 관측이 뒤집힌다](_assets/11-03.observability-inversion.svg)

관측은 도구를 어디서 띄우느냐와 보안 설정에 따라 다릅니다.

### 호스트에서 — 컨테이너별로 가르기

호스트에서는 최고 권한으로 하드웨어 자원·파일 시스템·게스트 프로세스·TCP 세션을 다 봅니다. 게스트에 로그인하지 않고도 게스트 프로세스를 분석할 수 있습니다. 흔한 걱정인 noisy neighbor 분석도 한 커널 아래의 여러 프로세스를 보는 전통 분석과 비슷합니다.

차이는 cgroup 이 하드웨어 한계보다 먼저 걸리는 소프트웨어 한계를 더한다는 점입니다. 원서는 여기서 경고를 답니다. 독립 시스템용으로 만든 많은 모니터링 도구는 컨테이너를 모르고 cgroup 한계도 모릅니다. 컨테이너 안에서 돌리면 동작하는 듯 보이지만 물리 자원만 보여 줍니다. 그래서 이미 소프트웨어 한계에 닿은 시스템을 "여유 있음"으로 거짓 보고하거나, 다른 테넌트 때문에 높은 사용률을 내 것처럼 보여 줄 수 있습니다.

커널에 컨테이너 ID가 없어 통계를 컨테이너별로 가르려면 따로 방법이 필요합니다.

| 방법 | 수단 |
|------|------|
| 컨테이너 도구 | `kubectl top` · `docker stats` |
| cgroup 통계 | `/sys/fs/cgroup/.../cpu.stat` 의 nr_throttled · throttled_time |
| namespace 매핑 | `nsenter -t PID -m -p` 로 호스트 도구를 컨테이너에서 실행 |
| BPF 추적 | 커널에서 직접 집계 |

프로세스 namespace 때문에 게스트 PID와 호스트 PID가 다릅니다. `/proc/PID/status` 의 NSpid 는 한 프로세스가 각 namespace 에서 갖는 PID 를 나란히 보여 줍니다. 호스트에서 모든 프로세스의 NSpid 를 훑어 게스트 PID 753 을 찾으면 호스트 PID 가 둘 이상 나올 수 있습니다. 753 이라는 번호가 여러 컨테이너의 pid namespace 에 따로 있을 수 있기 때문입니다. 그래서 확정은 namespace ID 를 대조해서 합니다. 원서의 예에서 게스트 PID 753 과 호스트 PID 4915 는 같은 pid namespace ID 를 가리킵니다.

```bash
# 원서 예 — 게스트와 호스트에서 각자 본 pid namespace 링크
guest# ls -lh /proc/753/ns/pid
... /proc/753/ns/pid -> 'pid:[4026532216]'
host# ls -lh /proc/4915/ns/pid
... /proc/4915/ns/pid -> 'pid:[4026532216]'
```

두 링크의 ID 4026532216 이 같으므로 호스트 PID 4915 가 게스트 PID 753 과 같은 프로세스입니다.

mount namespace 도 같은 문제를 만듭니다. 호스트에서 perf 를 돌리면 보조 심볼 파일을 호스트의 `/tmp/perf-PID.map` 에서 찾습니다. Java 처럼 실행 중에 기계어를 만드는 런타임은 이 파일로 함수 이름을 perf 에 알립니다. 그런데 컨테이너 앱은 그 파일을 컨테이너 안의 `/tmp` 에 씁니다. PID 도 호스트와 다릅니다. 그래서 이 노트가 보기에는 스택에 그 런타임의 함수 이름 대신 주소만 남게 됩니다.

원서는 perf 가 이후 namespace 를 지원하게 됐고, 커널이 `/proc/PID/root` 로 컨테이너의 루트(`/`)를 호스트에서 바로 보여 준다고 적습니다. 호스트에서 `ls /proc/4915/root/tmp` 를 하면 컨테이너 `/tmp` 의 파일이 보입니다.

### BPF 로 컨테이너별로 가르기 — uts nodename

커널에 컨테이너 ID 가 없으니 BPF 로 이벤트를 세면 시스템 전체 합계만 나옵니다. 원서의 forks.bt 는 clone·fork·vfork syscall 을 세어 추적하는 동안 새로 만든 프로세스 590 개를 보고합니다. 어느 컨테이너가 만들었는지는 모릅니다.

원서가 드는 해법은 uts namespace 의 nodename(호스트 이름)을 키로 쓰는 것입니다. 컨테이너 소프트웨어가 보통 이 값을 컨테이너 이름으로 설정해 두기 때문입니다.

코드는 `curtask` 로 시작합니다. `curtask` 는 지금 CPU 에서 도는 태스크의 커널 구조체(`task_struct`)이고, 코드는 거기서 그 태스크의 namespace 묶음(`nsproxy`)을 거쳐 uts namespace 의 nodename 까지 따라갑니다.

```bash
# 원서 forks.bt 의 컨테이너별 판 — #include 세 줄은 생략, 원서에서 세 줄인 probe 목록은 한 줄로 합침
tracepoint:syscalls:sys_enter_clone, tracepoint:syscalls:sys_enter_fork, tracepoint:syscalls:sys_enter_vfork
{
    $task = (struct task_struct *)curtask;
    $nodename = $task->nsproxy->uts_ns->name.nodename;
    @new_processes[$nodename] = count();
}
```

```bash
# 원서의 출력 — 앞의 590 과는 다른 실행이다
@new_processes[ip-10-1-239-218]: 171
@new_processes[efe9f9be6185]: 743
```

`ip-10-1-239-218` 은 호스트이고 `efe9f9be6185` 는 컨테이너입니다. 이 방법에는 조건이 붙습니다. syscall 은 그 syscall 을 부른 프로세스의 문맥에서 돌기 때문에 `curtask` 가 책임 프로세스를 가리킵니다. 디스크 I/O 완료 인터럽트처럼 프로세스와 비동기로 일어나는 이벤트를 추적하면, 그 순간 on-CPU 인 태스크가 원래 요청한 프로세스가 아닐 수 있어 nodename 이 틀립니다.

> **원문 정오 (2026-09 확인)**: 원서는 이 출력을 설명하며 "nodename 6280172ea7b9(컨테이너)가 추적 중 프로세스 252 개를 만들었다"고 적습니다. 바로 위 출력에는 그런 줄이 없고, 컨테이너 줄은 `efe9f9be6185: 743` 입니다. 6280172ea7b9 는 원서가 앞서 `docker ps` 예에 보인 컨테이너 ID 라서 다른 실행의 설명이 남은 것으로 보이며, 이 노트는 출력 쪽 값을 따릅니다.

원서는 커널 컨테이너 ID 의 다른 후보로 cgroup v2 ID 도 들며, BPF 와 bpftrace 가 이미 그 용도로 쓴다고 적습니다.

### cpu.stat 읽기 — 507 period 중 74번

cgroup 통계는 숫자만 있고 해석은 읽는 사람 몫입니다. 원서가 Docker cgroup 에서 읽은 값을 그대로 옮기면 이렇습니다.

```bash
# cd /sys/fs/cgroup/cpu,cpuacct/docker/02a7cf65f82e...
# cat cpuacct.usage
1615816262506
# cat cpu.stat
nr_periods 507
nr_throttled 74
throttled_time 3816445175
```

손으로 풀어 봅니다. `cpuacct.usage` 는 이 cgroup 이 쓴 CPU 시간 합계(나노초)라서 1,615,816,262,506 ns 는 약 1,616 초입니다. `nr_periods` 507 중 `nr_throttled` 74 이므로 bandwidth period 의 74 ÷ 507 ≈ 14.6% 에서 quota 를 다 써 멈췄습니다. `throttled_time` 3,816,445,175 ns 는 멈춰 있던 시간의 합으로 약 3.8 초입니다.

이 값들은 누적치라 한 번 읽어서는 지금 막혀 있는지 모릅니다. 원서가 판정 기준을 "throttled_time 이 늘고 있는가"로 적는 까닭입니다. 간격을 두고 두 번 읽어 증분을 봅니다. 이 throttling 은 bandwidth 한계에 대한 것이고, cpusets 를 쓴다면 mpstat 같은 CPU 별 도구로 할당된 CPU 의 사용률을 봅니다.

> **갱신 (2026-09)**: cgroup v2 에서 상한은 `cpu.max` 파일에 `$MAX $PERIOD` 형식으로 들어가며 기본값은 `max 100000`(상한 없음, period 100 ms)입니다. `cpu.stat` 은 `nr_periods`·`nr_throttled` 와 함께 `throttled_time`(ns) 대신 `throttled_usec`(µs)을 보고합니다.[^cgv2] 위 예를 v2 노드에서 재현하면 단위가 1,000 배 달라집니다.

### CPU throttling 판별 — 다섯 지표

bandwidth 에는 `throttled_time` 이라는 직접 통계가 있습니다. shares 로 제한된 컨테이너에는 그런 통계가 없습니다. 내 컨테이너가 shares 에 막혔는지 호스트 전체가 꽉 찼는지 가리려면 여러 지표를 엮어 추론해야 합니다. 원서 그림 11.13 이 그 판별 흐름이고, 쓰는 지표는 다섯입니다.

| 지표 | 어디서 읽나 |
|------|------------|
| throttled time | cpu cgroup 의 `throttled_time` |
| 비자발적 문맥 전환 | `/proc/PID/status` 의 `nonvoluntary_ctxt_switches` 증가 |
| 호스트 idle CPU | mpstat 의 `%idle`, `/proc/stat` |
| cpuset CPU 100% busy | cpusets 사용 시 mpstat, `/proc/stat` |
| 다른 테넌트 모두 idle | `docker stats` 같은 컨테이너 도구, 또는 top 에 이 컨테이너만 %CPU 를 쓰는지 |

원서가 인용한 원본 흐름도[^gregg17g]는 네 질문을 차례로 던집니다.

1. `throttled_time` 이 늘고 있는가? 늘고 있으면 bandwidth 상한(cap)에 막힌 것입니다. 가장 직접적인 통계라 먼저 봐서 이 경우를 지웁니다.
2. 아니면 `nonvoluntary_ctxt_switches` 가 늘고 있는가? 늘지 않으면 CPU 를 빼앗기고 있지 않으니 throttle 이 아닙니다.
3. 늘고 있다면 호스트에 idle CPU 가 있는가? 있으면 throttle 은 아닌 것으로 보되, 더 파 봅니다.
4. 호스트에 idle 이 없다면 다른 테넌트가 모두 idle 인가? 모두 idle 이면 이 컨테이너 혼자 물리 CPU 를 다 쓰는 것이라 물리 CPU 한계입니다. 다른 테넌트도 바쁘면 shares 에 막힌 것입니다.

다섯 번째 지표인 cpuset 사용률은 cpusets 를 쓰는 컨테이너에서 할당된 CPU 가 100% 인지 보는 데 씁니다. 원서 본문은 이를 지표 목록에 넣지만, 흐름도의 어느 갈림길에 놓는지는 이 텍스트에서 확인할 수 없어 위 네 단계에는 넣지 않았습니다.

흐름의 순서에는 이유가 있습니다. 직접 통계가 있는 cap 을 먼저 지웁니다. 그다음 빼앗김의 증거인 비자발적 전환이 있을 때만 원인을 찾아 들어갑니다. 원서는 다른 자원에도 비슷한 흐름을 만들 수 있다고 적습니다. 이상적인 모니터링 도구라면 이 판정을 대신해 컨테이너마다 어떻게 throttle 되는지 보고해야 한다는 것이 원서의 주문입니다.

### 게스트에서 — 새어 드는 시스템 전역 통계

게스트에서는 보통 자기 프로세스·파일 시스템·네트워크·TCP만 보입니다.

큰 예외가 시스템 전역 통계입니다. CPU와 디스크 통계는 종종 *컨테이너가 아니라 호스트* 것을 보여 줍니다. *완전히 idle한 컨테이너* 에서 iostat을 돌려도 CPU와 디스크가 바쁘게 나오는데, 다른 테넌트의 활동까지 포함한 호스트 통계이기 때문입니다. OS 가상화가 처음이면 "왜 내 컨테이너가 바쁘지?" 하고 헷갈리기 쉽습니다.

그럴 때는 컨테이너 자기 cgroup 의 통계를 두 번 읽어 확인합니다. 원서는 iostat 이 바쁘게 나온 같은 컨테이너에서 블록 I/O 횟수를 10초 간격으로 읽었습니다.

```bash
# 원서 예 — 컨테이너 안에서, 10초 간격으로 두 번(두 번째 출력도 같다)
container# cat /sys/fs/cgroup/blkio/blkio.throttle.io_serviced
259:0 Read 452
259:0 Write 352
[... Sync·Async·Discard 줄 생략]
259:0 Total 804
container# sleep 10
container# cat /sys/fs/cgroup/blkio/blkio.throttle.io_serviced
[... 앞과 같은 줄 생략]
259:0 Total 804
```

Total 이 804 에서 그대로이므로 그 10초 동안 이 컨테이너는 디스크 I/O 를 한 건도 내지 않았습니다. iostat 의 바쁜 디스크는 다른 테넌트의 것입니다. 바이트 수는 `blkio.throttle.io_service_bytes` 가 따로 줍니다.

커널 내부는 보통 보이지 않아 perf·Ftrace·BPF 같은 커널 추적 도구가 대개 동작하지 않습니다.

전통 도구가 컨테이너 안에서 무엇을 보여 주는지는 도구마다 다릅니다.

| 도구 | 컨테이너 안에서 보이는 것 |
|------|----------|
| top | 헤더는 호스트가 섞이고, 프로세스 표는 컨테이너 |
| ps · pidstat · pidstat -d | 컨테이너 프로세스 |
| uptime · free · mpstat · vmstat · iostat | 호스트 |
| sar -n DEV,TCP · tcpdump | 컨테이너 인터페이스 |
| perf | 실패하거나, 허용하면 다른 테넌트까지 프로파일 |
| dmesg | 실패 |

컨테이너를 인지하게 만들지 여부는 *목표* 에 달렸습니다. 격리된 서버를 파는 클라우드 벤더라면 컨테이너 활동만 보여 주는 편이 맞습니다. 자사 클라우드의 패키징 솔루션이라면 호스트 통계를 함께 보여 줘 noisy neighbor를 이해하게 하는 편이 낫습니다.

### 점검 순서 — 소프트웨어 한계를 먼저

앞 장들의 물리 자원 분석법은 호스트 운영자가 그대로 쓰고, 게스트도 위 제약 안에서 일부 씁니다. 게스트는 고수준 자원 사용은 보지만 커널까지 파고들지는 못합니다.

그 위에 하나를 더합니다. 원서는 자원 제어가 거는 클라우드 한계를 호스트 운영자와 게스트 테넌트 모두 확인해야 하고, 그것을 먼저 확인하라고 권합니다. 이런 한계는 걸려 있다면 물리 한계보다 훨씬 먼저 닿으므로 실제로 작동 중일 가능성이 더 높기 때문입니다. top·iostat 처럼 컨테이너 이전에 만들어진 도구는 자원 제어 정보를 기본으로 보여 주지 않아 잊기도 쉽습니다.

| 자원 | 점검 방법 |
|------|----------|
| CPU | 위 판별 흐름. cpusets·bandwidth·shares 를 모두 확인 |
| 메모리 | 현재 사용량을 memory cgroup 한계와 비교 |
| 파일 시스템 용량 | 다른 파일 시스템처럼 df(1) 로 |
| 디스크 I/O | `/sys/fs/cgroup/blkio` 의 throttle 설정과 `blkio.throttle.io_serviced`·`io_service_bytes`. 이 값이 throttle 과 같은 속도로 늘면 throttle 에 막힌 증거. BPF 가 되면 blkthrot(8) 로 확인 |
| 네트워크 I/O | 현재 처리량을 알려진 대역폭 한계와 비교. 한계는 호스트에서만 보일 수 있고, 걸리면 지연이 늘어남 |

이 표가 곧 자원 제어용 USE 체크리스트의 골격입니다. USE 메서드(02-02 §3)가 자원마다 사용률·포화·에러를 보듯, 자원 제어가 있으면 그 제어마다 같은 점검을 합니다. 원서 11.7 연습문제 4번이 바로 이 체크리스트를 명령과 해석까지 붙여 만들어 보라고 요구합니다.

> 관측의 핵심 대비는 *호스트는 다 보고 게스트는 헷갈린다* 입니다. 호스트는 모든 컨테이너를 한 커널에서 동시에 분석(전통 다중 프로세스 분석과 유사)하지만, 게스트는 자기 것만 보이면서도 시스템 전역 통계는 호스트 것이 새어 나옵니다. **11-02 VM과 정반대** 입니다. VM은 게스트가 커널을 다 분석하지만 물리 자원을 못 보고, 컨테이너는 게스트가 커널을 못 보지만 호스트 통계가 새어 나옵니다. 그래서 "관측은 컨테이너가 호스트 운영자에 유리, VM이 엔드유저에 유리"라는 11-04 §4 비교로 이어집니다.



## 학습 점검

> 먼저 답해 본 뒤 아래 정답과 맞춰 봅니다. 1~3 은 본문을 떠올리는 문항이고, 4·5 는 본문에 없는 조건으로 판단하는 문항입니다.

1. 커널이 하나라는 사실에서 나오는 장점 둘을 들고, VM에서 컨테이너로 옮긴 게스트가 커널 경합을 더 만나면서 동시에 분석 능력을 잃는다는 게 무슨 뜻인지 설명해 봅니다. (→ §1)
2. 커널에 컨테이너 개념이 없는데 컨테이너가 어떻게 만들어지는지(namespace + cgroup), 각각의 역할을 떠올려 봅니다. (→ §2)
3. 멀티테넌트 경합이 전통 다중 사용자 환경보다 심한 까닭과, 원서가 드는 여섯 경합 중 자원 제어로 관리하는 항목을 말해 봅니다. (→ §3)
4. 전체 shares 200 인 호스트에서 컨테이너 C 가 shares 40 을 가졌고 bandwidth 를 시스템 CPU 의 30% 로 설정했습니다. C 와 shares 60 짜리 D 만 바쁠 때, 모두 바쁠 때, C 혼자 바쁠 때 C 의 몫을 각각 구하고 운영 범위를 말합니다. 이 컨테이너를 한가한 호스트에서 처음 시험한 사용자가 무엇을 기대하게 되는지도 말해 봅니다. (→ §4)
5. 한 컨테이너의 응답이 느립니다. 이 컨테이너에 관해 차례로 답해 봅니다. (→ §5, 원서 11.7 연습문제 4)
   - (가) 컨테이너 안에서 iostat 을 돌리니 CPU·디스크가 바쁘게 나옵니다. 이 수치를 그대로 믿어도 되는지, 무엇으로 확인하는지 답합니다. VM 게스트였다면 무엇이 달랐을지도 말합니다.
   - (나) 호스트에서 10초 간격으로 두 번 읽으니 `throttled_time` 은 그대로이고 `nonvoluntary_ctxt_switches` 는 크게 늘었습니다. 호스트 mpstat 의 `%idle` 은 0 에 가깝고 `docker stats` 에는 다른 컨테이너 셋이 CPU 를 많이 씁니다. 어떤 throttle 이며 무엇을 권하겠습니까?
   - (다) 같은 점검을 메모리·디스크 I/O 까지 넓혀, 자원 제어용 USE 체크리스트를 명령과 해석을 붙여 짜 봅니다.



## 정답 (자답 후 펼치기)

> 먼저 답한 뒤 읽습니다. 판단 근거와 흔한 오해를 함께 적습니다.

### 정답 1 — 경합은 늘고 분석 수단은 줄어든다

장점부터 보면, 커널을 새로 띄우지 않으니 초기화가 밀리초 단위로 끝나고, 게스트마다 커널이 메모리를 먹지 않아 메모리를 앱에 다 씁니다. 같은 사실이 단점도 만듭니다. 커널을 여러 테넌트가 공유하므로 락·캐시·버퍼·큐 경합이 VM 시절보다 잦아집니다. 동시에 게스트는 그 커널을 분석할 수 없어 perf·BPF 같은 커널 추적 도구를 쓰지 못합니다. 문제가 늘어나는 자리와 분석 능력이 사라지는 자리가 같은 커널이라, 게스트는 이런 분석을 호스트 운영자에게 기대게 됩니다. 대표 오해는 컨테이너가 VM보다 가벼우니 문제도 적다고 보는 것입니다.

### 정답 2 — namespace 는 보이는 것을, cgroup 은 쓰는 양을

namespace 는 PID·네트워크·마운트 등 시스템 뷰를 걸러 컨테이너가 자기 자원만 보게 하고, cgroup 은 CPU·메모리·I/O 사용량에 한계를 겁니다. Docker 같은 유저 공간 소프트웨어가 둘을 묶어 컨테이너라 부릅니다. 대표 오해는 커널에 컨테이너 객체가 있다고 보는 것입니다. 통일된 컨테이너 ID 가 없어 관측 도구가 컨테이너별로 가르기 어렵습니다.

### 정답 3 — 부하가 자릿수로 늘어난다

원서는 멀티테넌트 컨테이너 시스템이 커널 자원의 부하를 10배 이상 늘릴 수 있다고 적습니다. 컨테이너 구조 자체가 커널·물리 자원 공유를 더 부추깁니다. 전통 다중 사용자 환경에도 있던 요인이지만 훨씬 흔해집니다. 원서가 이 표 끝에서 "자원 제어로 관리한다"고 가리킨 것은 마지막 행인 "다른 테넌트의 CPU·디스크·네트워크 인터페이스 경합"입니다. CPU 캐시는 §4 에서 본 Intel CAT 로 따로 제어하고, TLB 경합은 PCID 같은 하드웨어 기능이 완화합니다.

### 정답 4 — 20% 바닥에서 30% 천장까지

C 와 D 만 바쁘면 40 / (40 + 60) = 40%지만 bandwidth 30% 에 걸려 30% 입니다. 모두 바쁘면 40 / 200 = 20% 로, 이것이 shares 가 보장하는 바닥입니다. C 혼자 바쁘면 shares 로는 100% 까지 bursting 할 수 있지만 bandwidth 가 30% 로 자릅니다. 운영 범위는 20~30% 입니다.

한가한 호스트에서 처음 시험한 사용자는 30% 를 자기 몫으로 기대하게 되지만, 이웃이 모두 바빠지면 20% 까지 내려갑니다. bandwidth 가 없었다면 시험에서 100% 를 보고 20% 로 떨어졌을 테니, 상한이 급락 폭을 다섯 배에서 1.5 배로 줄인 셈입니다. 이 범위는 C 에 CPU 를 다 쓸 만큼 바쁜 스레드가 있을 때만 성립합니다. 대표 오해는 첫 경우를 40% 로 답하는 것입니다. shares 공식의 결과는 bandwidth 상한을 넘을 수 없습니다.

### 정답 5 — 누구 통계인지 가리고, 소프트웨어 한계부터

(가) 믿으면 안 됩니다. iostat 이 읽는 CPU·디스크 통계는 컨테이너 것이 아니라 호스트 전체 것이라 다른 테넌트의 활동이 섞입니다.

확인은 컨테이너 자기 cgroup 통계로 합니다. CPU 는 `cpuacct.usage` 를 간격을 두고 두 번 읽어 증분을 봅니다. 디스크는 컨테이너 자기 cgroup 의 `blkio.throttle.io_serviced` 를 같은 방식으로 읽습니다. pidstat -d 같은 프로세스 단위 도구로 내 프로세스의 I/O 도 따로 봅니다.

VM 게스트였다면 자기 커널의 통계를 보므로 게스트 전용으로 정확하고 커널 추적도 되지만, 대신 물리 자원을 못 봅니다.

(나) `throttled_time` 이 늘지 않으니 bandwidth cap 은 아닙니다. 비자발적 문맥 전환이 늘었으니 CPU 를 빼앗기고 있습니다. 호스트에 idle 이 없고 다른 테넌트도 바쁘므로 흐름도의 결론은 shares throttle 입니다. 권할 것은 shares 가 더 많은 큰 컨테이너로 올려 최소 보장을 높이는 것입니다. bandwidth(limit)를 올리는 것은 답이 아닙니다. 막힌 것은 천장이 아니라 바닥 쪽 몫이라 limit 을 올려도 빈 CPU 가 없습니다. 다른 테넌트가 모두 idle 이었다면 결론은 물리 CPU 한계로 바뀝니다.

(다) 아래 표로 짭니다.

| 자원 | 사용률 | 포화 | 해석 |
|------|--------|------|------|
| CPU | `cpuacct.usage` 증분(ns) ÷ (간격(ns) × bandwidth CPU 수) | `cpu.stat` 의 `nr_throttled`·`throttled_time` 증분, 프로세스별 `nonvoluntary_ctxt_switches` | throttled_time 이 늘면 cap. 늘지 않는데 비자발 전환만 늘면 판별 흐름으로 shares·물리를 가림 |
| 메모리 | 현재 사용량 대 `memory.limit_in_bytes` | 한계 근처에서의 회수·swap | 페이지 캐시도 계상되므로 파일 캐시가 한계를 채울 수 있음. 한계를 넘어 OOM killer 가 돌았다면 그것이 이 제어의 에러 |
| 디스크 I/O | `blkio.throttle.io_serviced`·`io_service_bytes` 증분 대 throttle 설정 | 증분이 throttle 값과 같은 속도로 붙어 있음, blkthrot(8) | 붙어 있으면 물리 디스크가 아니라 throttle 에 막힌 것 |

이 표는 원서 11.3.4.4 의 자원별 점검을 USE 의 칸에 맞춰 이 노트가 짠 것이고, CPU 사용률 식도 이 노트의 구성입니다. 원서가 자원 제어별 에러를 따로 적지 않아 에러는 메모리의 OOM killer 만 해석 열에 넣었습니다. 네트워크는 한계가 호스트에서만 보일 수 있어 게스트 체크리스트로는 처리량 대 알려진 한계만 봅니다. 대표 오해는 셋 모두에서 같습니다. 전역 통계와 물리 자원만 보고 판단하는 것입니다. 원서는 자원 제어가 거는 소프트웨어 한계를 먼저 보라고 권합니다.
