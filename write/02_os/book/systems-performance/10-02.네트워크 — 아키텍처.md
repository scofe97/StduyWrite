# 네트워크 — 아키텍처
---
> 이 노트는 원서 10.4 아키텍처를 다룹니다. 프로토콜(IP·TCP·UDP·QUIC)의 성능 특성, 네트워크 하드웨어(인터페이스·컨트롤러·스위치·라우터·방화벽), 그리고 Linux 네트워크 스택(연결 큐·버퍼·GSO/TSO·NAPI·CPU 스케일링·커널 바이패스)을 봅니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 프로토콜·하드웨어·커널 세 층이 각자 다른 오버헤드를 줄이려 애쓰고, 그 장치마다 줄이지 못하고 남기는 비용이 다음 병목이 된다는 것입니다.

10-01 이 개념이었다면 이 노트는 프로토콜과 그 아래 구조입니다. TCP 가 어떻게 높은 RTT 에서도 처리량을 내는지, 하드웨어가 어디서 병목이 되는지, 커널이 패킷을 어떻게 큐잉·분산·오프로드하는지를 봅니다.

세 층을 관통하는 주제는 오버헤드입니다. TCP 는 슬라이딩 윈도로 왕복 대기를 줄이고, 커널은 세그먼테이션 오프로드로 작은 패킷이 스택을 여러 번 지나는 비용을 줄입니다. CPU 스케일링은 한 코어에 몰리는 부하를 흩뜨립니다.

그래서 이 편은 대표 장치 몇 개를 문제 → 작동 방식 → 줄어드는 비용 → 남는 한계 순으로 봅니다. 남는 한계가 다음에 볼 자리이기 때문입니다. 가장 분명한 예가 커널 바이패스입니다. DPDK 처럼 스택을 비켜 가면 빨라지지만 카운터와 트레이싱 이벤트도 함께 비켜 가서 분석이 어려워집니다. XDP 는 커널 안에 남는 방식이라 대가가 다릅니다.



## 학습 목표

> 이 편을 덮은 뒤 스스로 할 수 있어야 하는 일을 먼저 적어 둡니다.

1. fast retransmit·fast recovery·TLP 가 각각 어떤 손실 신호를 쓰는지 구분하고, fast recovery 에 대한 원서 설명과 RFC 5681 의 차이를 설명합니다.
2. SYN 큐와 accept 큐를 구분하고, 각각이 넘칠 때 커널이 무엇을 하며 어떤 카운터와 출력으로 드러나는지 연결합니다.
3. 인터페이스·컨트롤러·버스 중 어디가 먼저 한계에 닿는지 계산합니다.
4. RSS·RPS·RFS·XPS 를 처리 위치·분산 대상·필요 조건으로 비교해 상황에 맞는 것을 고릅니다.
5. DPDK 와 XDP 가 커널 스택과 맺는 관계를 구분하고, 각각이 관측성에서 치르는 대가를 말합니다.

![10-02 전체 지도 — 프로토콜에서 하드웨어, 그 위의 커널로](_assets/10-02.chapter-overview.svg)

프로토콜 → 하드웨어 → 소프트웨어 순으로 내려갑니다. 위 두 층이 무엇을 주는지 본 뒤, 커널이 그 위에서 무슨 일을 더 하는지를 봅니다.

## 1. TCP — 높은 RTT에서도 처리량을 내는 법

> TCP는 슬라이딩 윈도와 버퍼링으로 높은 RTT에서도 처리량을 내고, 혼잡 제어로 안정성을 지킵니다. 손실을 얼마나 빨리 알아채느냐가 재전송 지연을 가릅니다.

왕복에 시간이 걸리는 링크에서 한 번 보내고 ACK 를 기다리면 처리량이 RTT 에 묶입니다. TCP 가 그 묶임을 푸는 방식이 이 절의 내용입니다.

TCP 는 신뢰성 있는 연결의 표준입니다. 성능 면에서 버퍼링과 슬라이딩 윈도로 높은 RTT 에서도 높은 처리량을 내고, 혼잡 제어와 혼잡 윈도로 다양한 네트워크에서 높지만 안정적인 전송률을 유지합니다.

| TCP 성능 기능 | 역할 |
|--------------|------|
| 슬라이딩 윈도 | ACK 전에 윈도 크기만큼 여러 패킷을 보냄. 윈도 크기는 받는 쪽이 광고 |
| 혼잡 회피 | 과전송으로 인한 포화·드롭 방지 |
| slow-start | 작은 혼잡 윈도로 시작해 ACK 를 받으며 키움 |
| SACK | 불연속 구간을 확인해 재전송 수를 줄임 |
| fast retransmit | 중복 ACK 를 신호로 타이머를 기다리지 않고 재전송 |
| fast recovery | 빠른 재전송 뒤 slow-start 로 돌아가지 않고 전송을 이어 감(아래 소절) |
| TCP fast open | SYN 에 데이터를 실어 핸드셰이크를 기다리지 않고 처리 시작 |
| TCP timestamps | RTT 측정용 타임스탬프 |
| TCP SYN cookies | SYN 큐가 찼을 때 요청 상태를 저장하지 않고 연결을 받음(§4) |

3-way 핸드셰이크는 SYN → SYN-ACK → ACK 로 연결을 수립합니다. 클라이언트가 보는 연결 지연은 마지막 ACK 까지이고, 이 사이에 패킷이 드롭되면 타임아웃과 재전송으로 지연이 붙습니다.

### 손실을 빨리 알아채는 법 — fast retransmit·fast recovery·TLP

손실을 타이머로만 알면 재전송 타임아웃(RTO)을 기다려야 합니다. RTO 는 연결의 RTT 로 계산하는데, Linux 는 첫 재전송에서 최소 200 ms 를 기다리고 이후 재전송마다 두 배로 늘립니다.[^tcp-h] RFC 6298 은 RTO 가 1초보다 작으면 1초로 올리라고 권하므로(SHOULD),[^rfc6298] 원서도 Linux 가 이를 어기는 것처럼 보인다고 짚습니다.

타이머를 기다리지 않는 방법이 중복 ACK 입니다. 받는 쪽은 빠진 세그먼트 뒤의 세그먼트가 도착할 때마다 아직 기다리는 번호로 같은 ACK 를 다시 보냅니다. 보내는 쪽은 중복 ACK 셋을 손실 신호로 보고 즉시 재전송합니다(fast retransmit). 그 뒤 새 ACK 가 올 때까지 새 데이터 전송을 이어 가는 것이 fast recovery 입니다.

원서는 fast recovery 가 연결을 되돌려 slow-start 를 수행해 성능을 회복한다고 적습니다. RFC 5681 은 반대로 적습니다. 중복 ACK 가 온다는 것은 세그먼트가 망을 떠나 받는 쪽에 닿고 있다는 뜻이므로 slow start 를 하지 않고, 복구가 끝나면 혼잡 윈도를 줄여 둔 임계값(ssthresh)에 맞춥니다.[^rfc5681-fr] 혼잡 윈도를 1 세그먼트로 되돌리고 slow start 를 다시 하는 것은 타임아웃 쪽입니다.[^rfc5681-to] 원서의 Tahoe 설명(중복 ACK 셋에 cwnd 를 1 MSS 로)이 이 동작과 같습니다.

그래서 줄어드는 비용은 둘입니다. 타이머 대기(Linux 최소 200 ms, RFC 권고 1초)가 대략 한 RTT 로 줄고, 윈도를 1 세그먼트로 되돌리지 않아 처리량이 빨리 돌아옵니다.

남는 한계도 분명합니다. 중복 ACK 는 손실된 세그먼트 뒤에 세그먼트가 더 있어야 생깁니다. 마지막 세그먼트가 사라지면 신호가 없어 타이머로 떨어지는데, TLP(Tail Loss Probe)가 짧은 대기 뒤 세그먼트를 하나 더 보내 손실을 드러나게 합니다. 재전송이 빨라질 뿐 재전송 자체가 없어지지는 않으며, 혼잡 제어 알고리즘은 재전송이 있으면 처리량을 줄입니다.

### 혼잡 제어 알고리즘과 그 밖의 TCP 동작

TCP 에서 가장 큰 성능 레버는 혼잡 제어 알고리즘입니다. 원서는 Reno·Tahoe·CUBIC·BBR·DCTCP 를 듭니다. CUBIC 은 Reno 보다 공격적이고, BBR 은 경로의 RTT 와 대역폭을 모델로 세워 어떤 경로는 극적으로 개선하고 어떤 경로는 악화시킵니다. DCTCP 는 ECN 을 얕은 큐에서 표시하도록 설정된 데이터센터 안에서만 맞습니다.

기본 알고리즘은 커널 빌드 설정이 정하고, `tcp_congestion_control` 로 바꿀 수 있습니다.[^ip-sysctl] 원서와 이 노트의 실험 환경(10-04 §6)에서는 CUBIC 이었습니다. 원서는 Netflix 가 BBR 로 심한 패킷 손실 구간의 처리량을 세 배까지 개선했다는 사례와, Linux 5.6 부터 BPF 로 새 혼잡 제어 알고리즘을 만들 수 있게 됐다는 점도 듭니다.

그 밖에 성능에 영향을 주는 동작이 몇 가지 있습니다.

- Nagle: 작은 패킷을 모아 보내려고 지연시킵니다. 지연 ACK 와 맞물리면 지연이 커질 수 있어 `TCP_NODELAY` 로 끕니다(10-03 §5).
- 지연 ACK: 여러 ACK 를 합치려고 늦춥니다. 원서는 최대 500 ms 로 적는데, RFC 1122 는 0.5초 미만이어야 한다고 정하고(MUST)[^rfc1122] Linux 의 상한은 200 ms 입니다.[^tcp-h]
- SACK·FACK·RACK: 손실 복구를 개선합니다. RACK 은 ACK 순서가 아니라 시간 정보로 손실을 판정합니다.
- 초기 윈도(IW): 연결 초기에 ACK 없이 보내는 양입니다. Linux 기본은 10 세그먼트(IW10)입니다.[^tcp-h]



## 2. TCP 상태·UDP·QUIC — 연결 관리와 대안

> TCP 세션은 상태와 타이머로 전이하며, 먼저 닫은 쪽에 남는 TIME_WAIT 는 잦은 연결에서 포트 고갈을 부를 수 있습니다. UDP는 단순·무상태·무재전송이고, QUIC은 그 위에 신뢰성·혼잡 제어·암호화를 다시 얹은 표준 전송입니다.

![TCP · UDP · QUIC 이 주는 것과 포기하는 것](_assets/10-02.tcp-vs-udp-quic.svg)

TCP 세션은 패킷·소켓 이벤트로 상태를 전이합니다. LISTEN·SYN-SENT·ESTABLISHED·TIME-WAIT·CLOSED 같은 상태가 있고, 성능 분석은 보통 활성 연결인 ESTABLISHED 에 집중합니다.

완전히 닫은 세션은 TIME_WAIT 로 들어갑니다. 늦게 도착한 패킷이 같은 포트를 쓰는 새 연결에 잘못 섞이지 않게 하려는 것입니다. 머무는 시간은 기준마다 다릅니다. 원서는 보통 2분이라 적습니다. RFC 9293 은 2 MSL 을 쓰고 MSL 을 2분으로 잡으므로 4분이 됩니다.[^rfc9293] Linux 는 60초로 고정합니다.[^tcp-h]

이 상태는 먼저 닫은 쪽에 남고, 잦은 연결에서 포트 고갈을 부를 수 있습니다(10-03 §2). TIME_WAIT 가 많아 보일 때 정상인지 읽는 법은 [PAW 03-02 「3. TIME_WAIT — 정상인데 많아 보일 때」](../paw_packet-analysis-wireshark/03-02.TCP%EA%B0%80%20%EC%96%B4%EA%B8%8B%EB%82%A0%20%EB%95%8C.md)가 다룹니다.

**UDP**는 데이터그램이라 부르는 메시지를 보내는 표준입니다. 성능 면의 장점은 셋입니다. 헤더가 작아 단순합니다. 무상태라 연결 오버헤드가 낮습니다. 재전송이 없어 TCP 의 큰 지연을 피합니다.

대가도 분명합니다. 비신뢰적이라 데이터가 누락되거나 순서가 뒤바뀔 수 있고, 혼잡 회피가 없어 네트워크 혼잡에 오히려 기여할 수 있습니다. 주 용도는 DNS 였습니다.

**QUIC**은 HTTP/3 의 기반입니다. Google 이 설계했고, 원서 집필 시점에는 IETF 가 표준화하던 중이었으며 지금은 RFC 9000 이 표준입니다.[^rfc9000] UDP 위에 여러 기능을 다시 얹었습니다.

- 한 연결 안에 여러 스트림을 다중화합니다. 스트림은 순서 있는 바이트열이고, 신뢰 전달과 혼잡 제어에 필요한 피드백을 QUIC 이 스스로 갖춥니다.[^rfc9000]
- 원서는 하위 스트림마다 신뢰성을 끌 수 있다고 적지만, RFC 9000 의 스트림은 모두 순서 있는 신뢰 전달입니다. 신뢰하지 않는 전송은 별도 확장인 DATAGRAM 프레임이 더합니다.[^rfc9221]
- 클라이언트 주소가 바뀌어도 연결 ID 로 연결을 이어 갑니다(연결 이전).
- 패킷 전체를 인증하고 할 수 있는 만큼 암호화합니다.
- 사전 통신이나 설정이 있는 상대와는 0-RTT 로 첫 비행에 데이터를 싣습니다.

원서는 UDP 가 단순하고 혼잡 제어가 없으며 보통 방화벽에 막히지 않는다는 점이 그 위에 자체 혼잡 제어를 얹은 새 프로토콜을 낳았다고 봅니다. RFC 9000 도 기존 시스템과 네트워크에 배포하기 쉽게 하려고 QUIC 패킷을 UDP 데이터그램에 싣는다고 적습니다.[^rfc9000]



## 3. 하드웨어 — 인터페이스·컨트롤러·스위치·방화벽

> 인터페이스는 프레임을 주고받으며 대역폭이 높을수록 지연이 낮고 비싸집니다. 컨트롤러·I/O 버스가 처리량 한계가 될 수 있고, 스위치·라우터·방화벽도 내부 버퍼·CPU가 부하에서 병목이 됩니다.

"NIC 가 10GbE 니까 10Gbit/s 가 나온다"는 기대는 자주 어긋납니다. 인터페이스 뒤에 컨트롤러와 버스가 있고, 그중 가장 좁은 곳이 실제 상한을 정하기 때문입니다.

**인터페이스**는 프레임을 주고받으며 전기·광·무선 신호와 전송 에러를 다룹니다. 이더넷은 1~400GbE 까지 있고, 대역폭이 높을수록 지연이 낮고 비싸서 서버 설계 시 가격과 성능을 저울질합니다. 무선은 신호 약함·간섭으로 성능 문제가 생깁니다.

**컨트롤러(NIC)**는 PCIe 같은 I/O 버스로 시스템에 붙습니다. 컨트롤러와 버스 어느 쪽이든 처리량·IOPS 한계가 될 수 있습니다.

원서의 예로 계산해 봅니다. 듀얼 10GbE NIC 는 한 방향으로 2 × 10 = 20Gbit/s 를 낼 수 있습니다. PCIe Gen2 x4 슬롯은 레인당 4Gbit/s 라 4 × 4 = 16Gbit/s 가 상한입니다. 20 > 16 이므로 두 포트를 동시에 라인 속도로 몰지 못합니다. 컨트롤러 전용 관측 도구는 드물어, 원서는 컨트롤러에 달린 포트들의 처리량을 더해 컨트롤러 사용률을 추정하라고 권합니다.

**스위치·라우터**도 병목이 됩니다.

| 장치 | 역할·병목 |
|------|----------|
| 스위치 | 두 호스트 간 전용 경로(허브의 충돌 문제 해결). 내부 버퍼·CPU가 부하에서 한계 |
| 라우터 | 네트워크 간 패킷 전달(라우팅 테이블). 동적 경로라 순서 뒤바뀜 → TCP 성능 문제 가능 |
| 방화벽 | 인가된 통신만 허용. stateful 이면 연결당 메타데이터로 메모리 부하(DoS·대량 연결 시) |

라우터·스위치는 rate transition(10Gbps → 1Gbps 등)이 일어나는 곳이라 버퍼링이 필요한데, 과버퍼링하면 버퍼블로트(10-01 §4)로 지연이 커집니다. 소스에서 pacing 으로 트래픽을 덜 버스티하게 만드는 것도 완화책입니다.

어느 컴포넌트든 병목이 될 수 있다는 것이 하드웨어 쪽의 교훈입니다. 원서는 BPF 로 commodity 하드웨어에 방화벽·DDoS 방어를 구현하는 추세도 짚습니다(Facebook·Cloudflare·Cilium). 성능·프로그래밍 가능성·비용 때문입니다.



## 4. Linux 네트워크 스택 — 연결 큐·버퍼·세그먼테이션 오프로드

> Linux 스택은 멀티스레드라 인바운드 패킷을 여러 CPU가 처리합니다. TCP 연결은 두 큐(SYN 큐·accept 큐)로 폭주를 흡수하고, 송수신 버퍼로 처리량을 높이며, GSO/TSO/GRO로 패킷당 스택 비용을 줄입니다.

![송신 경로의 버퍼 · 큐 · 오프로드](_assets/10-02.linux-network-stack.svg)

패킷 하나하나가 스택을 통과할 때마다 비용이 듭니다. 초당 수백만 개가 오가면 그 비용이 곧 병목이 되므로, 커널은 여러 층에서 그 횟수를 줄이려 합니다.

Linux 스택은 멀티스레드라 인바운드 패킷을 여러 CPU 가 처리합니다. 패킷은 `struct sk_buff` 로 커널 컴포넌트를 통과합니다.

### 연결 큐가 둘인 까닭

연결 요청은 두 줄에 섭니다. **SYN 큐**는 SYN 을 받았지만 핸드셰이크가 끝나지 않은 요청을, **accept 큐**는 핸드셰이크가 끝나 앱이 `accept()` 로 꺼내 가기를 기다리는 연결을 담습니다. 원서는 둘째 큐를 listen 백로그라 부릅니다. `listen(2)` 의 backlog 인자가 정하는 것이 이 큐의 길이이고, 그 값은 `net.core.somaxconn` 을 넘으면 잘립니다.[^listen2]

![SYN 큐에서 accept 큐를 거쳐 accept() 까지](_assets/10-02.connection-queues.svg)

큐가 둘인 이유는 SYN 플러드 방어입니다. 첫 큐는 가짜일 수 있는 연결의 대기소입니다. 핸드셰이크가 끝난 것만 둘째 큐로 옮깁니다. 첫 큐를 길게 두면 SYN 플러드를 흡수할 수 있고, 저장할 메타데이터를 최소로 줄여 최적화합니다.

어느 큐가 언제 넘치느냐에 따라 커널이 하는 일이 다릅니다. 아래는 기준 커밋의 커널 코드에서 확인한 동작입니다.[^tcp-input][^tcp-minisocks]

| 상황 | 커널이 하는 일 | 오르는 카운터 | 밖에서 보이는 것 |
|---|---|---|---|
| SYN 이 올 때 SYN 큐가 한도를 넘음, SYN cookies 켜짐(기본) | 요청을 저장하지 않고 쿠키를 담은 SYN-ACK 로 응답 | `TCPReqQFullDoCookies` | 연결은 맺어지나 일부 TCP 옵션에 제약 |
| 같은 상황, SYN cookies 꺼짐 | SYN 을 버림 | `TCPReqQFullDrop`·`ListenDrops` | 클라이언트 SYN 재전송 |
| SYN 이 올 때 accept 큐가 이미 참 | SYN 을 버림 | `ListenOverflows`·`ListenDrops` | 클라이언트 SYN 재전송 |
| 마지막 ACK 가 올 때 accept 큐가 참 | ACK 를 버리고 요청을 보류(`tcp_abort_on_overflow=0`) | `ListenOverflows`·`ListenDrops` | 클라이언트는 연결됐다고 보는데 서버는 아직 받지 않음, 서버 SYN-ACK 재전송 |

마지막 줄이 함정입니다. 클라이언트의 `connect()` 는 SYN-ACK 를 받는 순간 끝납니다. 그래서 서버가 연결을 아직 accept 큐에 넣지 못했는데도 클라이언트 쪽은 빨리 붙었다고 기록합니다. 10-04 §6 의 첫 실험에서 accept 큐에 셋만 들어가는데 즉시 성공한 연결이 다섯이었고, 서버의 SYN-ACK 재전송이 다섯 번 기록됐습니다. `tcp_abort_on_overflow` 를 켜면 보류 대신 RST 로 끊습니다. 커널 문서는 이 설정이 클라이언트를 해칠 수 있다고 경고합니다.[^ip-sysctl]

SYN 큐의 한도는 원서 설명과 현행 구현이 갈리는 자리입니다. 원서는 두 큐를 따로 조정한다고 적습니다(10.8). 기준 커밋의 코드는 SYN 큐가 찼는지를 accept 큐와 같은 한도, 곧 listen backlog 를 somaxconn 으로 자른 값과 비교해 판단합니다.[^tcp-input] `tcp_max_syn_backlog` 는 SYN cookies 가 꺼져 있을 때, 큐가 그 값의 3/4 을 넘으면 아직 확인되지 않은 상대의 요청을 먼저 버리는 기준으로 쓰입니다.[^tcp-input] listen(2) 매뉴얼도 SYN cookies 가 켜져 있으면 이 설정이 무시된다고 적습니다.[^listen2]

관측은 두 자리에서 합니다. `ss -lnt` 의 LISTEN 행에서 Recv-Q 는 지금 accept 큐에 든 연결 수, Send-Q 는 그 한도입니다.[^tcp-diag] 카운터 쪽은 `ListenOverflows` 가 accept 큐를, `TCPReqQFull*` 이 SYN 큐를 가리킵니다. `ListenDrops` 는 둘을 모두 포함합니다. 카운터를 나란히 읽는 법은 [패킷이 사라지는 네 자리](../../../troubleshooting/_concepts/%ED%8C%A8%ED%82%B7%EC%9D%B4-%EC%82%AC%EB%9D%BC%EC%A7%80%EB%8A%94-%EB%84%A4-%EC%9E%90%EB%A6%AC.md)의 소절 「SYN 큐와 accept 큐는 카운터가 갈립니다」에 있습니다. 실제 출력은 10-04 §6 에 있습니다.

### SYN cookies — 상태를 저장하지 않고 받는다

SYN 플러드는 위조한 출발지로 SYN 을 쏟아 SYN 큐를 채우고, 진짜 클라이언트가 들어올 자리를 없앱니다. SYN cookies 는 요청 상태를 저장하는 대신 그 상태를 SYN-ACK 의 시퀀스 번호에 담아 보냅니다. 출발지가 위조되지 않았다면 핸드셰이크를 끝내는 ACK 에서 그 번호를 되받아 상태를 복원합니다.[^rfc4987]

줄어드는 비용은 요청마다 드는 메모리입니다. 커널 문서 기준으로 SYN_RECV 요청 하나가 약 304바이트를 씁니다.[^ip-sysctl]

남는 한계는 시퀀스 번호에 다 담지 못하는 정보입니다. 흔한 방식은 일부 TCP 옵션과 맞지 않습니다.[^rfc4987] Linux 는 타임스탬프 옵션이 있으면 창 배율·SACK·ECN 허용 여부를 그 안에 담아 되살립니다.[^syncookies] 커널 문서는 SYN cookies 가 대비책일 뿐이며, 정상 연결이 몰려 쿠키가 나가는 것이라면 다른 설정을 조정해야 한다고 적습니다.[^ip-sysctl]

원서는 쿠키가 클라이언트가 이미 인가됐음을 보여 준다고 적습니다. 쿠키가 보여 주는 것은 그 출발지가 SYN-ACK 를 실제로 받았다는 데까지입니다. 클라이언트가 누구인지 확인하는 인증은 아닙니다.

### 버퍼와 세그먼테이션 오프로드 — 패킷당 스택 비용

송수신 버퍼(10-01 §4)는 크면 처리량이 오르지만 연결당 메모리가 늘어납니다. Linux 는 연결 활동에 따라 버퍼 크기를 동적으로 키우며, 최소·기본·최대를 튜닝할 수 있습니다(10-03 §5).

세그먼테이션 오프로드는 패킷마다 스택을 지나는 비용을 줄입니다. Linux 는 GSO 로 최대 64KB 슈퍼 패킷을 만들어 스택을 한 번만 통과시키고, NIC 에 넘기기 직전에 MSS 크기로 쪼갭니다. NIC·드라이버가 TSO 를 지원하면 쪼개는 일까지 NIC 하드웨어에 맡깁니다. 수신 쪽에서는 GRO 가 반대로 작은 패킷을 모아 한 번에 올립니다.

줄어드는 비용은 바이트당 스택 통과 횟수이고, 남는 한계는 셋입니다. 선 위에는 여전히 MSS 크기 프레임이 나갑니다. NIC 에 넘기기 전에 잡는 캡처에는 MTU 보다 큰 패킷이 찍힙니다. 인터페이스 패킷 카운터가 슈퍼 패킷 하나를 한 개로 세기도 해서, 10-04 §2 의 실측에서는 2Gbit/s 송신 중 초당 패킷이 약 6천인데 TCP 세그먼트는 초당 약 17만이었습니다. 캡처 쪽 해석은 [PAW 01-01](../paw_packet-analysis-wireshark/01-01.%ED%8C%A8%ED%82%B7%20%EB%B6%84%EC%84%9D%EA%B8%B0%EC%99%80%20Wireshark.md)의 소절 「캡처에 남는 프레임은 캡처 지점에서 본 모습입니다」가 풉니다.

> **갱신 (2026-09)**: 64KB라는 상한은 IP 헤더의 length 필드가 16비트여서 생긴 것입니다. 이후 BIG TCP 가 이 한계를 넘겼습니다. IPv6는 RFC 2675의 hop-by-hop 헤더로 32비트 length를 써 훨씬 큰 패킷을 만들 수 있고, IPv4용 경로도 뒤따라 들어왔습니다. 기본은 꺼져 있으므로 64KB가 여전히 기본값이라고 읽으면 됩니다. (출처: [LWN — BIG TCP](https://lwn.net/Articles/884104/)) 이 노트의 실험 환경에서도 `gso_max_size` 는 65536 이었습니다(10-04 §6, 실행 확인).

### 큐잉 규율과 장치 백로그

큐잉 규율(qdisc) 층은 트래픽 분류·스케줄링·셰이핑을 맡고 `tc` 로 설정합니다. 커널 기본은 pfifo_fast 이고 `net.core.default_qdisc` 로 바꿀 수 있습니다.[^net-sysctl] 다중 큐 물리 장치는 루트에 mq 를 두고 그 아래에 이 기본값을 씁니다. lo·veth 같은 가상 장치는 설정과 상관없이 noqueue 입니다.[^net-sysctl] systemd 는 이 값을 fq_codel 로 바꿔 둡니다.[^systemd] 원서도 같은 차이를 짚고, BPF(`BPF_PROG_TYPE_SCHED_CLS/ACT`)가 이 층을 강화해 로드밸런서·방화벽에 쓰인다고 적습니다.

**장치 백로그**는 인터페이스가 커널이 처리하는 속도보다 빨리 받을 때 패킷이 쌓이는 CPU 별 입력 큐이고, 한도는 `net.core.netdev_max_backlog` 입니다.[^net-sysctl] 넘쳐 버린 수는 `/proc/net/softnet_stat` 의 둘째 열에 CPU 마다 쌓입니다.[^softnet] SYN 큐와 accept 큐가 소켓 하나의 줄이라면, 장치 백로그는 패킷이 소켓에 닿기 전에 서는 CPU 의 줄입니다.



## 5. CPU 스케일링·커널 바이패스 — 패킷율을 끌어올리는 법

> 높은 패킷율은 여러 CPU로 패킷을 나눠 처리해 얻습니다. 분산(RSS·RPS·RFS·XPS)과 인터럽트 완화(NAPI)가 커널 안의 방법이고, DPDK는 커널을 비켜 가며, XDP는 커널 안에서 스택 앞단에 프로그램을 붙입니다.

![분산 · 완화 · 앞단 판정 · 우회 네 수위](_assets/10-02.cpu-scaling-bypass.svg)

NIC 하나가 한 CPU 만 깨우면, 나머지 코어가 놀아도 그 한 코어가 100%에 닿아 병목이 됩니다. 패킷율을 올리는 일은 그 쏠림을 푸는 데서 시작합니다.

### 분산 기법은 처리 위치·분산 대상·필요 조건으로 가릅니다

원서가 드는 다섯 기법은 이름이 비슷해 설명을 하나씩 읽으면 뒤섞입니다. 같은 축으로 세우면 차이가 드러납니다. 필요 조건과 기본 상태는 커널 문서 기준입니다.[^scaling]

| 기법 | 처리 위치 | 무엇을 어디로 나누나 | 필요 조건 | 기본 상태 |
|---|---|---|---|---|
| RSS | NIC 하드웨어 | 수신 패킷을 흐름 해시로 여러 수신 큐에, 큐마다 IRQ 를 다른 CPU 로 | 다중 큐 NIC, IRQ affinity(irqbalance 가 덮어쓸 수 있음) | 드라이버가 큐 수를 정함 |
| RPS | 커널 소프트웨어(인터럽트 하반부) | 인터럽트 위 프로토콜 처리를 다른 CPU 의 backlog 로 | `CONFIG_RPS`, 수신 큐별 `rps_cpus` 비트맵, CPU 간 인터럽트 비용 | 꺼짐 |
| RFS | 커널 소프트웨어(RPS 위) | 흐름을 그 흐름을 읽는 앱 스레드의 CPU 로 | `rps_sock_flow_entries` 와 큐별 `rps_flow_cnt` | 꺼짐 |
| Accelerated RFS | NIC 하드웨어 + 드라이버 | RFS 가 고른 CPU 에 맞는 수신 큐로 NIC 가 직접 | `CONFIG_RFS_ACCEL`, NIC·드라이버 지원, ntuple 필터 | NIC 지원에 따름 |
| XPS | 커널(송신 큐 선택) | 송신을 CPU 나 수신 큐에 묶인 송신 큐로 | 다중 송신 큐, 송신 큐별 `xps_cpus`·`xps_rxqs` | 드라이버에 따름 |

고르는 순서는 커널 문서가 권하는 대로입니다. 다중 큐 NIC 가 CPU 마다 수신 큐를 줄 수 있으면 RSS 로 충분하고 RPS 는 대개 불필요합니다. 큐가 CPU 보다 적거나 단일 큐 NIC 면 RPS 를 켜고, 캐시 지역성이 중요하면 RFS 를 더합니다.[^scaling]

분산이 없으면 NIC 가 한 CPU 만 인터럽트해 그 CPU 가 100%에 닿고, mpstat 에서 한 CPU 의 높은 softirq 시간으로 보입니다. 원서는 로드밸런서·프록시(nginx)처럼 인바운드 패킷율이 높은 워크로드에서 특히 그렇다고 적습니다. 반대로 모든 기법이 같은 흐름을 같은 CPU 로 보내므로, 흐름 하나가 트래픽을 독차지하면 기법을 켜도 그 CPU 하나가 찹니다.[^scaling]

### NAPI — 인터럽트를 묶어 처리한다

패킷마다 인터럽트를 받으면 높은 패킷율에서 인터럽트 처리만으로 CPU 를 씁니다. NAPI 는 장치가 인터럽트로 새 이벤트를 알리면 호스트가 NAPI 인스턴스를 예약해 poll 로 여러 이벤트를 한꺼번에 처리하게 합니다. 인터럽트 없이 폴링하는 busy polling 도 됩니다.[^napi] 원서의 표현으로는 저패킷율에서는 인터럽트를 쓰고, 고패킷율에서는 인터럽트를 끄고 폴링해 합칩니다.

줄어드는 비용은 인터럽트 횟수입니다. 남는 한계는 지연과 쏠림입니다. 모아 처리하는 만큼 지연이 붙을 수 있어, 원서는 인터럽트 병합이 처리량을 얻는 대신 지연을 치른다고 적습니다. 처리 자체는 여전히 그 CPU 에서 돌므로 위의 분산 기법과 함께 써야 합니다. 원서는 NAPI 의 다른 기능으로 패킷 스로틀링·인터페이스 스케줄링·`SO_BUSY_POLL` 을 듭니다.

### DPDK 와 XDP 는 스택과 맺는 관계가 다릅니다

둘을 커널 바이패스로 묶어 부르지만, 원서도 XDP(eXpress Data Path)는 스택을 우회하지 않고 기존 스택에 통합되는 경로라고 구분합니다. 관측성에서 치르는 대가가 여기서 갈립니다.

| | DPDK | XDP |
|---|---|---|
| 어디서 도나 | 유저 공간 라이브러리. 대부분 장치는 커널 드라이버에서 떼어 vfio-pci 에 묶어야 함[^dpdk] | 커널 안. 패킷이 일반 스택에 들어가기 전에 eBPF 프로그램이 판정 |
| 패킷의 행방 | 앱이 직접 받고 프로토콜을 스스로 구현 | 패킷마다 PASS(일반 스택으로)·DROP·TX·REDIRECT 중 하나.[^xdp] REDIRECT 로 AF_XDP 소켓에 보내면 유저 공간이 받음[^af-xdp] |
| 커널 관측 | 그 포트는 Linux 가 다루지 않아 커널 카운터·트레이싱이 보지 못함 | PASS 된 패킷은 기존 관측이 그대로 봄. XDP 에서 DROP·REDIRECT 된 패킷은 뒤쪽 스택 카운터에 나타나지 않음 |

원서는 스택을 우회하면 전통 도구가 쓰는 카운터와 트레이싱 이벤트도 함께 우회돼 성능 분석이 어려워진다고 경고합니다. DPDK 가 이 경고에 온전히 해당하고, XDP 는 판정 뒤 스택에서 빠진 패킷에만 해당합니다. 원서는 XDP 쪽 이벤트 소스로 xdp tracepoint 를 드는데, 기준 커밋의 목록은 예외·리다이렉트·송신 묶음을 기록하고 정상 DROP 판정마다 남는 이벤트는 두지 않습니다.[^xdp-tp] 원서는 DPDK 가 이제 XDP 로 받는 기능도 지원한다고 덧붙입니다.

그 밖에 송신 경로에는 pacing·TCP Small Queues·Byte Queue Limits·Earliest Departure Time 같은 알고리즘이 조합돼 성능을 높입니다. TCP 가 보낸 패킷은 NIC 에 닿기 전에 혼잡 제어·TSO·TSQ·pacing·qdisc 를 모두 지날 수 있습니다.



## 학습 점검

> 먼저 답해 본 뒤 아래 정답과 맞춰 봅니다. 1~2 는 본문을 떠올리는 문항이고, 3~6 은 본문에 없는 조건으로 판단하는 문항입니다.

1. TCP 가 높은 RTT 에서도 처리량을 내는 두 축과, 손실을 타이머보다 빨리 알아채는 신호가 무엇인지 설명해 봅니다. (→ §1)
2. SYN cookies 로 받은 연결이 잃을 수 있는 것과, 쿠키가 보증하지 않는 것을 말해 봅니다. (→ §4)
3. 듀얼 25GbE NIC 를 PCIe 레인당 약 8Gbit/s 인 x8 슬롯에 꽂았습니다. 한 방향으로 두 포트를 동시에 라인 속도로 몰 수 있는지 계산해 봅니다. (→ §3)
4. 서버의 `ss -lnt` 에서 LISTEN 행이 Recv-Q 129, Send-Q 128 이고, `nstat` 증분에서 `TcpExtListenOverflows` 는 늘었는데 `TcpExtTCPReqQFullDrop` 은 0 입니다. 어느 큐가 찼는지, 클라이언트에서는 무엇이 보일지, 먼저 고칠 곳이 어디인지 판단해 봅니다. (→ §4)
5. 처리량은 링크의 10%인데 mpstat 에서 CPU 0 하나만 softirq 90%입니다. 무엇을 의심하고, 다음에 어떤 출력을 확인하겠습니까? (→ §5)
6. 한 팀이 "XDP 를 도입하면 DPDK 처럼 커널 도구로는 아무것도 안 보인다"고 걱정합니다. 맞는 부분과 틀린 부분을 가려 봅니다. (→ §5)



## 정답 (자답 후 펼치기)

> 먼저 답한 뒤 읽습니다. 판단 근거와 흔한 오해를 함께 적습니다.

### 정답 1 — 두 축과 손실 신호

버퍼링과 슬라이딩 윈도가 ACK 를 기다리지 않고 여러 세그먼트를 내보내게 해 RTT 의 영향을 줄이고, 혼잡 제어가 안정성을 지킵니다. 손실은 중복 ACK 셋으로 타이머보다 빨리 알아챕니다. 대표 오해는 fast recovery 가 slow-start 로 되돌아간다는 원서 설명을 그대로 외우는 것입니다. RFC 5681 에서 slow start 로 돌아가는 것은 타임아웃 쪽입니다.

### 정답 2 — SYN cookies 의 한계

시퀀스 번호에 다 담지 못한 TCP 옵션을 잃을 수 있습니다. Linux 는 타임스탬프가 있으면 창 배율·SACK·ECN 을 그 안에 담지만, 타임스탬프가 없으면 그 정보가 줄어듭니다. 쿠키는 출발지가 SYN-ACK 를 받았다는 것만 보이고 클라이언트의 신원은 보증하지 않습니다. 대표 오해는 쿠키가 나간다는 사실을 "공격을 막았다"로만 읽는 것입니다. 정상 연결이 몰려 쿠키가 나간다면 큐 설정과 앱의 accept 속도를 먼저 봐야 합니다.

### 정답 3 — 버스 상한

NIC 는 한 방향으로 2 × 25 = 50Gbit/s, 슬롯은 8 × 8 = 64Gbit/s 입니다. 50 < 64 이므로 한 방향으로는 버스가 먼저 막히지 않습니다. 대표 오해는 결론을 여기서 끝내는 것입니다. 이 계산은 레인당 값을 가정했고, 양방향 동시 부하나 버스 프로토콜 오버헤드를 넣으면 여유가 줄 수 있으므로 실측으로 확인합니다.

### 정답 4 — 넘친 큐와 다음 조치

Recv-Q 129 가 한도 128 을 넘었으므로 accept 큐가 찼습니다. `TCPReqQFullDrop` 이 0 이라 SYN 큐 쪽은 아닙니다. 클라이언트에서는 SYN 재전송으로 connect 가 1초 단위로 늦어집니다. 일부는 빨리 붙은 것처럼 보이지만 서버가 아직 받지 않은 상태일 수 있습니다. 먼저 고칠 곳은 앱이 왜 `accept()` 를 제때 못 하는지입니다. backlog 를 늘리는 것은 순간 폭주를 흡수할 뿐입니다. 도착률이 accept 속도를 계속 넘으면 큐는 다시 찹니다. 대표 오해는 `tcp_max_syn_backlog` 부터 올리는 것입니다.

### 정답 5 — CPU 하나에 몰린 softirq

수신 처리가 한 CPU 로 몰렸다고 의심합니다. `/proc/interrupts` 에서 NIC 큐의 IRQ 가 한 CPU 에 몰렸는지, NIC 가 수신 큐를 몇 개 쓰는지, 해시 분배표(`ethtool -x`)가 어떻게 돼 있는지 봅니다. 큐가 하나뿐이면 `rps_cpus` 설정 여부를 확인합니다. 설정이 멀쩡하면 흐름 하나가 트래픽을 독차지하는지 봅니다. `/proc/net/softnet_stat` 의 CPU 별 처리량과 드롭도 함께 봅니다. 대표 오해는 처리량이 낮으니 네트워크는 문제가 아니라고 결론 내는 것입니다. 패킷율과 CPU 가 병목일 수 있습니다.

### 정답 6 — XDP 와 관측

맞는 부분은 XDP 가 DROP 하거나 REDIRECT 한 패킷은 뒤쪽 스택 카운터와 소켓 층 도구에 나타나지 않는다는 것입니다. 틀린 부분은 전부 안 보인다는 것입니다. XDP 는 커널 안에서 돌고 PASS 된 패킷은 일반 스택을 그대로 지나므로 기존 도구가 봅니다. 다만 XDP 가 버린 패킷은 판정마다 남는 tracepoint 가 없으니, 버린 수를 어디서 셀지는 도입 전에 정해 둡니다. 포트를 커널에서 떼어 내는 DPDK 와는 다릅니다. 대표 오해는 둘을 같은 커널 바이패스로 묶는 것입니다.
