# 네트워크 — 방법론·실험·튜닝
---
> 이 노트는 원서 10.5 방법론·10.7 실험·10.8 튜닝을 다룹니다. 네트워크 성능을 어떤 순서로 분석하고(방법론 10종), 어떻게 부하를 걸어 재고(ping·iperf·tc), 어떤 손잡이를 돌리는가(sysctl·소켓 옵션)를 잡습니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 네트워크 분석이 내 호스트를 먼저 확인해 혐의를 좁히고, 실험으로 네트워크를 가린 뒤에야 손잡이를 돌리는 순서라는 것입니다.

10-01·10-02 가 개념과 구조였다면 이 노트는 행동입니다. 네트워크가 의심받을 때 무엇부터 보는지, 호스트 사이 네트워크 건강을 어떻게 실험으로 확인하는지, 원인을 찾았을 때 무엇을 바꾸는지의 순서입니다.

이 순서에는 이유가 있습니다. 네트워크는 모르면 일단 의심받는 자원이라(10-01), 내 인터페이스와 설정을 먼저 확인해야 내 탓이 아니라는 것을 증거로 보일 수 있습니다.

순서 안에서 지킬 규칙이 하나 있습니다. 관찰된 증상과 원인 후보와 원인 확정을 섞지 않습니다. 지표 하나가 움직였다는 것은 후보를 세울 근거이고, 원인이 확정되려면 다른 관측이 같은 후보를 가리키고 조치 뒤 증상이 사라져야 합니다.

튜닝이 마지막인 데도 이유가 있습니다. 네트워크 튜너블은 대개 이미 잘 맞춰져 있고 스택도 워크로드에 동적으로 반응합니다. 그래서 손잡이를 돌리기 전에 불필요한 일을 없애는 편이 이득이 크고, 손잡이마다 그것을 가리키는 관측과 치를 대가를 함께 따집니다.



## 학습 목표

> 이 편을 덮은 뒤 스스로 할 수 있어야 하는 일을 먼저 적어 둡니다.

1. 증상에 따라 먼저 꺼낼 방법론을 고르고, 그 순서의 이유를 댑니다.
2. 관찰된 증상·원인 후보·원인 확정을 구분하고, 재전송 같은 지표 하나로 원인을 확정하지 않습니다.
3. 포트 고갈이 성립하는 조건을 계산하고, TIME_WAIT 대책마다 치르는 대가를 비교합니다.
4. iperf 결과를 애플리케이션 문제에 옮길 수 있는 경우와 없는 경우를 판단합니다.
5. 튜닝 항목마다 변경 근거가 될 관측과 대가를 대고, 시스템 전역 설정과 소켓별 설정 중 범위에 맞는 것을 고릅니다.

![10-03 전체 지도 — 관찰에서 실험으로, 실험에서 튜닝으로](_assets/10-03.chapter-overview.svg)

방법론 → 실험 → 튜닝 순으로 갑니다. 원서가 권하는 시작 순서는 성능 모니터링·USE·정적 성능 튜닝·워크로드 특성화입니다.



## 이 문서가 다루지 않는 것

> 앞뒤 편으로 넘긴 주제를 밝혀 둡니다.

- 지연 6종·버퍼링 같은 기본 개념: 10-01 이 다룹니다.
- TCP 혼잡 제어 알고리즘·커널 스택 구현: 10-02 가 다룹니다.
- 도구별 출력 읽는 법(`ss`·`sar`·`tcpdump` 등): 10-04 가 다룹니다. 출력에서 원인 후보를 좁혀 가는 과정은 10-04 §6 의 실측 사례가 보여 줍니다. 여기서는 어떤 방법론에 어떤 도구가 붙는지까지만 봅니다.



## 1. 방법론 10종 — 무엇부터 보는가

> 원서의 네트워크 분석 방법론은 10가지입니다. 외울 목록이 아니라, 증상에 따라 먼저 꺼낼 방법을 고르는 메뉴로 씁니다.

무엇부터 볼지 정하지 않으면 도구를 아무거나 꺼내게 됩니다. 원서는 아무 단서가 없을 때 성능 모니터링 → USE → 정적 성능 튜닝 → 워크로드 특성화 순으로 시작하라고 권합니다. 증상이 이미 있다면 그 증상이 가리키는 방법부터 씁니다.

### 증상이 먼저 꺼낼 방법을 정합니다

아래 표는 원서의 방법론을 증상별로 다시 묶은 것입니다. 묶는 기준은 이 노트의 판단이고, 각 방법의 내용은 원서를 따릅니다.

| 관찰된 증상 | 먼저 쓸 방법 | 이어서 | 먼저 쓰는 이유 |
|---|---|---|---|
| 무엇이 느린지 모른다 | 성능 모니터링 | USE | 언제부터 어느 자원이 변했는지부터 잡습니다 |
| 처리량이 기대보다 낮다 | 정적 성능 튜닝(설정 점검) | 마이크로벤치마킹, `ss` 의 limited 플래그 | 협상 속도·MTU·부과 한도가 상한을 정하는 경우를 먼저 배제합니다 |
| 일부 요청만 느리다 | 지연 분석(분포·건당) | TCP 분석(재전송) | 원서는 재전송이 지연 이상치의 흔한 원인이라고 적습니다 |
| 새 연결이 가끔 1초씩 늦다 | 지연 분석(연결 지연) | TCP 분석(SYN 재전송·큐 넘침) | 연결 단계의 1초는 SYN 재전송 간격과 맞습니다(10-01 §3) |
| 처리량은 낮은데 CPU 하나가 바쁘다 | USE(CPU 별 softirq·NIC 큐) | 분산 기법 점검(10-02 §5) | 병목이 선이 아니라 패킷율과 CPU 일 수 있습니다 |
| 용량을 계획해야 한다 | 워크로드 특성화 | 성능 모니터링 | 처리량·패킷율·연결율의 추세가 필요합니다 |
| 특정 패킷·헤더를 봐야 한다 | 패킷 스니핑(짧게) | 없음 | 비용이 커 다른 방법으로 답이 안 날 때 꺼냅니다 |

원서의 10종 전체는 이렇습니다. 원서의 이름 "정적 성능 튜닝"은 설정을 바꾸는 일이 아니라 점검하는 일이라 괄호로 적어 둡니다(§5).

| 방법론 | 무엇을 하나 | 유형 |
|--------|-----------|------|
| 도구 메서드 | 가용 도구를 차례로 훑으며 핵심 지표 점검 | 관측 |
| USE | 인터페이스별·방향별 사용률·포화·에러 | 관측 |
| 워크로드 특성화 | 처리량·패킷율·연결율 파악 | 관측·용량계획 |
| 지연 분석 | 여러 지연(이름해석~inter-stack)을 재 원천 좁힘 | 관측 |
| 성능 모니터링 | 처리량·연결·에러·재전송 시계열 | 관측·용량계획 |
| 패킷 스니핑 | 패킷 단위로 헤더·데이터 검사 | 관측 |
| TCP 분석 | 버퍼·백로그·윈도·TIME_WAIT 조사 | 관측 |
| 정적 성능 튜닝(설정 점검) | 인터페이스 속도·MTU·라우팅·방화벽 점검 | 관측·용량계획 |
| 자원 제어 | 대역폭 한계·QoS·지연 주입 | 튜닝 |
| 마이크로벤치마킹 | iperf 등으로 처리량 한계 측정 | 실험 |

### 관찰된 증상·원인 후보·원인 확정을 나눕니다

방법을 고른 뒤에는 결과를 세 층으로 나눠 적습니다.

- 관찰된 증상: 측정으로 본 사실입니다. "이 구간에 `TcpRetransSegs` 가 늘었다", "connect 가 1초 걸렸다" 가 여기 듭니다.
- 원인 후보: 그 증상을 설명할 수 있는 가설입니다. 재전송이 늘었다면 경로 손실, 받는 쪽 드롭, 서버 큐 넘침, 방화벽이 모두 후보입니다.
- 원인 확정: 다른 관측이 후보 하나만 가리키고, 그 원인을 없앤 뒤 같은 부하에서 증상이 사라진 상태입니다.

원서도 이 구분을 요구합니다. TCP 재전송은 네트워크 포화의 지표가 될 수 있지만 서버와 클라이언트 사이 어느 홉의 문제로도 생긴다고 적습니다. 그래서 재전송 하나로 원인을 확정하지 않습니다. 재전송이 어느 상태·어느 목적지에서 났는지와 서버 쪽 카운터를 함께 봅니다. 10-04 §6 의 사례는 후보를 서버의 accept 큐로 좁히는 데까지 가고, 확정은 앱이 왜 늦게 받는지 확인하는 일로 남깁니다.

### USE 메서드 — 인터페이스별·방향별

![USE 를 네트워크에 적용하는 순서](_assets/10-03.use-method-network.svg)

USE 는 빠른 병목·에러 식별의 핵심입니다. 인터페이스별로, 그리고 TX/RX 방향별로 사용률·포화·에러를 봅니다.

셋 중 에러를 먼저 봅니다. 빠르고 해석이 쉽기 때문입니다. 수신 쪽은 체크섬 불량·너무 짧거나 긴 프레임·충돌이, 송신 쪽은 늦은 충돌이 원서가 드는 에러입니다.

사용률은 현재 처리량을 협상 속도로 나눠 방향별로 계산합니다(10-01 §5). 원서는 OS 도구가 이 값을 직접 주지 않는 경우가 많다고 적습니다. sar 의 `%ifutil` 은 링크 속도를 읽을 수 있을 때만 계산되므로, 속도를 모르는 인터페이스에서는 0 이 나옵니다(10-04 §2). 클라우드처럼 대역폭 제한이 걸린 환경은 물리 한도와 함께 부과된 한도로도 봅니다.

포화는 측정이 어렵습니다. 원서는 앱 스레드가 네트워크 송신에서 막힌 시간이나 Linux 의 overruns 같은 커널 통계를 후보로 듭니다. 재전송도 포화 지표가 될 수 있지만, 위에서 본 대로 어느 홉의 문제로도 생기므로 단독으로 쓰지 않습니다.

USE 는 컨트롤러에도 적용됩니다. 컨트롤러 A 에 포트 A0·A1 이 달려 있다면 A 의 처리량은 두 포트 처리량의 합이고, 컨트롤러 한도로 나누면 사용률이 됩니다.

### 워크로드 특성화 — 무엇을 얼마나 나르나

워크로드 특성화의 기본 축은 셋입니다. 인터페이스 처리량은 RX/TX byte/s 로, IOPS 는 RX/TX frame/s 로, TCP 연결율은 active 와 passive 로 봅니다. 원서의 예시는 이 축을 한 문장에 담습니다. "쓰기(TX)가 읽기보다 많고, 쓰기 최대는 초당 200MB·21만 패킷, 읽기 최대는 초당 10MB·7만 패킷, 들어오는 연결은 초당 3,000" 식입니다.

심화 점검에서는 평균 패킷 크기·프로토콜 분해·활성 포트·브로드캐스트와 멀티캐스트율·네트워크를 쓰는 프로세스까지 묻습니다. 원서는 이 과정이 없애도 되는 일을 찾아 가장 큰 개선을 낳기도 한다고 적습니다.



## 2. 지연 분석·TCP 분석 — 원천 좁히기

> 지연 분석은 여러 구간의 지연을 재 진짜 원천을 좁히고, TCP 분석은 버퍼·백로그·윈도·TIME_WAIT를 조사합니다. 포트 고갈은 조건이 맞을 때만 생기는 확장성 문제입니다.

지연 분석은 10-01 의 지연 6종을 더 잘게 나눠 되도록 많이 재 원천을 좁힙니다. 이름 해석·ping·TCP 연결 초기화·첫 바이트·재전송·TIME_WAIT·연결 수명이 그 목록에 들어갑니다. 여기에 syscall 송수신·syscall connect·RTT·인터럽트·inter-stack 지연까지 더합니다.

흔한 문제는 TCP 재전송으로 인한 지연 이상치입니다. 전체 분포를 보거나, 최소 지연 임계값으로 거른 건당 추적으로 식별합니다. 원서는 일부 지연이 부하 중에만 나타나므로 한가한 시스템뿐 아니라 부하 중인 시스템도 재라고 권합니다.

지연 측정은 트레이싱 도구와 소켓 옵션으로 합니다. Linux 의 `SO_TIMESTAMP`(수신 시각)와 `SO_TIMESTAMPING`(건당 타임스탬프)이 전송 지연·RTT·inter-stack 지연을 식별하며, 터널링이 얽힌 복잡한 패킷 지연 분석에 특히 유용합니다.

TCP 분석은 TCP 고유 동작을 조사합니다. 원서의 목록에 어디서 보는지를 붙였습니다.

| 조사 대상 | 보는 것 | 어디서 보나 |
|----------|--------|------------|
| 송수신 버퍼 사용 | 버퍼가 처리량을 막는가 | `ss -m` 의 skmem, `sndbuf_limited` |
| 백로그 큐 사용 | accept 큐가 차오르는가 | `ss -lnt` 의 Recv-Q·Send-Q |
| 백로그가 차서 생긴 커널 드롭 | 호스트 과부하 후보 | `ListenOverflows`·`TCPReqQFull*` |
| 혼잡 윈도 크기 | 보내는 쪽이 망을 추정해 줄였는가 | `ss -i` 의 `cwnd` |
| 수신 윈도 0 광고(zero window) | 받는 쪽 앱이 못 읽는가 | `ss -i` 의 `rwnd_limited`, 캡처의 `win 0` |
| TIME_WAIT 중 받은 SYN | 같은 네 값의 재사용이 부딪히는가 | 아래 소절 |

원서는 zero window 를 "혼잡 윈도 크기, 크기 0 광고 포함"으로 한 줄에 적습니다. zero window 는 받는 쪽이 광고하는 수신 윈도의 일이고, 혼잡 윈도는 보내는 쪽 내부 값이라 광고되지 않습니다(10-01 §4). 받는 쪽 앱을 볼지 망을 볼지가 여기서 갈리므로 둘을 나눠 봅니다.

### 포트 고갈 — 구분할 축이 하나만 남을 때

![연결을 구분하는 축이 하나만 남을 때](_assets/10-03.port-exhaustion.svg)

한 호스트가 같은 목적지 IP·포트로 자주 새 연결을 열고 출발지 IP 도 하나라면, 연결을 구분하는 것은 출발지 ephemeral 포트뿐입니다. 목적지가 다르면 같은 로컬 포트를 다시 쓸 수 있습니다. 커널이 출발지·목적지의 주소와 포트 네 값이 겹치는지로 판단하기 때문입니다.[^hash-connect]

포트는 16비트라 이론상 65,536개지만, Linux 기본 범위는 32768~60999 라 28,232개입니다.[^ip-sysctl] 여기에 TIME_WAIT 가 겹칩니다. Linux 는 먼저 닫은 쪽에 60초 동안 이 상태를 둡니다(10-02 §2).

```bash
# 개념 계산 — 출발지 IP 하나, 목적지 IP·포트 하나, 클라이언트가 먼저 닫는 경우
# 쓸 수 있는 포트 28,232 개 ÷ TIME_WAIT 60 초 ≈ 초당 470 개
# 같은 목적지로 새 연결이 이 속도를 계속 넘으면 포트가 모자라기 시작한다
```

원서는 60초 동안 65,536개를 넘으면 충돌한다고 적는데, 포트 범위 제한을 빼고 센 값입니다. 충돌이 드러나는 모습은 TIME_WAIT 가 어느 쪽에 남느냐에 따라 다릅니다.

- 클라이언트가 먼저 닫을 때: TIME_WAIT 가 클라이언트에 남고, 커널은 그 포트를 새 연결에 주지 않습니다(`tcp_tw_reuse` 가 허용하는 경우 제외). 범위가 바닥나면 connect 가 `EADDRNOTAVAIL` 로 실패합니다.[^connect2]
- 서버가 먼저 닫을 때: TIME_WAIT 가 서버에 남고 클라이언트는 그 포트를 다시 쓸 수 있습니다. 새 SYN 이 서버의 TIME_WAIT 항목과 같은 네 값을 갖게 되는데, 원서는 이것이 옛 연결로 오인되면 거부될 수 있다고 적습니다. Linux 는 새 SYN 의 시퀀스 번호가 더 크거나 타임스탬프가 더 새로우면 받아 줍니다.[^tw-syn] 원서가 대개 잘 처리된다고 쓴 것이 이 동작입니다.

대책은 치르는 대가가 다릅니다. 먼저 검토할 것은 새 연결의 수 자체를 줄이는 것입니다.

| 대책 | 효과 | 대가·조건 |
|---|---|---|
| 연결 재사용(keep-alive·풀) | 새 연결 수 자체를 줄임 | 앱·클라이언트 설정 변경. 가장 먼저 검토 |
| 출발지 IP 추가 | 네 값의 조합을 늘림(원서) | 주소 관리 |
| `ip_local_port_range` 확장 | 쓸 포트 수를 늘림 | 서비스 포트와 겹치지 않게 `ip_local_reserved_ports` 로 비워 둠 |
| `tcp_tw_reuse` | 프로토콜상 안전할 때 TIME_WAIT 소켓을 새 연결에 씀 | 기본 2(loopback 만). 커널 문서는 전문가 조언 없이 바꾸지 말라고 적음[^ip-sysctl] |
| `SO_LINGER` 0초 | 닫을 때 RST 로 끊어 TIME_WAIT 를 남기지 않음 | 보내지 못한 데이터를 버리고 상대는 연결 리셋을 받음. 일반 해법이 아님 |

원서는 짧은 linger 시간의 `SO_LINGER` 를 해법의 하나로 듭니다. linger 시간이 0이 아니면 close 가 전송 완료나 시간 만료까지 기다릴 뿐입니다.[^socket7] 정상 종료를 거치므로 TIME_WAIT 는 그대로 남습니다. 0초일 때만 커널이 연결을 끊고 RST 를 보냅니다.[^tcp-close]

이 노트의 실험 환경에서 먼저 닫는 쪽이 연결 20개씩을 닫아 보았습니다. linger 없음과 1초는 각각 TIME_WAIT 20개를 남겼고, 0초는 하나도 남기지 않으면서 `TcpExtTCPAbortOnData` 가 20 올랐습니다(실행 확인). 원서가 함께 드는 `tcp_tw_recycle` 은 기준 커밋의 커널 문서에 없습니다.[^ip-sysctl]

지연 분석과 TCP 분석은 짝입니다. 지연 분석으로 어디서 시간을 쓰는지 좁히고, TCP 분석으로 TCP 내부의 무엇이 막는지 봅니다.



## 3. 패킷 스니핑 — 마지막 수단의 정밀 도구

> 패킷 스니핑은 패킷 단위로 헤더·데이터를 검사하는 정밀 도구지만, CPU·저장 비용이 커 관측 분석의 마지막 수단입니다. 커널 내 BPF 필터로 원하는 패킷만 골라 오버헤드를 줄입니다.

**패킷 스니핑**은 네트워크에서 패킷을 잡아 프로토콜 헤더·데이터를 패킷 단위로 검사하는 일로, 패킷 캡처라고도 부릅니다. 관측 분석에선 마지막 수단입니다. CPU·저장 오버헤드가 크기 때문입니다. 네트워크 커널 코드는 초당 수백만 패킷을 다루도록 사이클 최적화돼 있어, 추가 오버헤드에 민감합니다.

스니핑은 강력한 만큼 비쌉니다. 그래서 실무에서 쓰려면 비용을 깎는 장치가 먼저 필요합니다. 원서가 드는 장치는 셋입니다.

- 커널 ring buffer: 패킷 데이터를 공유 메모리로 유저 트레이스 도구에 넘깁니다(BPF 와 perf 출력 ring buffer, AF_XDP).
- out-of-band 스니퍼: 스위치의 tap·mirror 포트에 연결한 별도 서버가 잡습니다.
- 커널 내 BPF 필터: 원하는 패킷만 골라 쓰지 않을 패킷을 유저 레벨로 넘기지 않습니다. 필터 표현식은 BPF 바이트코드로 컴파일돼 커널에서 JIT 됩니다.

패킷 캡처 로그는 보통 네 가지를 담습니다. 타임스탬프, 모든 헤더와 페이로드 일부 또는 전체를 포함한 패킷, 패킷 수와 드롭 수 같은 메타데이터, 그리고 인터페이스명입니다. CPU 비용이 커서 과부하 시 이벤트를 드롭하는 능력을 두고, 드롭한 수는 로그에 남깁니다.

패킷 스니핑은 메시지 지연·누락 패킷·프로토콜 헤더 디버깅에 강력하지만 짧게만 씁니다. 가능하면 BPF 기반 도구로 커널 안에서 집계해 패킷을 유저 레벨로 넘기지 않는 편이 낫습니다. 10-04 §3 의 tcplife·tcpretrans 가 패킷 캡처보다 싼 이유가 여기 있습니다.



## 4. 실험 — 네트워크 건강을 능동 측정

> 실험은 ping·traceroute·iperf·netperf·tc로 네트워크를 능동 측정합니다. iperf 결과는 같은 경로의 대량 전송 한도를 알려 줄 뿐이라, 애플리케이션 문제에 옮기려면 조건이 맞아야 합니다.

![네트워크 분석 흐름 — 면죄에서 실험·튜닝까지](_assets/10-03.network-methodology-flow.svg)

관찰만으로는 이 네트워크가 낼 수 있는 최대치를 알 수 없습니다. 지금 트래픽이 적어서 조용한 것인지, 더 밀어도 안 나가는 것인지 구분되지 않기 때문입니다.

실험은 상태를 관찰하는 대신 능동적으로 부하를 걸어 측정합니다.

| 도구 | 측정 |
|------|------|
| ping | ICMP echo 로 연결성·RTT. 커널 타임스탬프(SO_TIMESTAMP)로 정확도↑ |
| traceroute | TTL 을 1씩 늘려 홉별 경로·RTT 노출(방화벽이 ICMP 막으면 `*`) |
| pathchar | traceroute + 홉 간 대역폭(시간 오래 걸림, 잘 안 쓰임) |
| iperf | TCP/UDP 최대 처리량(병렬 모드로 라인 속도까지). 서버·클라이언트 양쪽 실행 |
| netperf | 요청/응답 성능(TCP_RR 로 왕복 지연 측정) |
| tc | 큐잉 규율 선택 + netem 으로 손실·지연 주입(테스트·시뮬레이션) |

**iperf**가 가장 널리 쓰입니다. 분산 애플리케이션의 처리량 문제를 조사할 때 네트워크가 기대 처리량을 낼 수 있는지부터 확인합니다. iperf 는 애플리케이션보다 훨씬 단순해 디버깅이 빠릅니다. 100Gbit/s 같은 빠른 인터페이스는 다중 클라이언트 스레드(`-P`)로 몰아야 최대 대역폭에 닿습니다. 원서는 대역폭 실험에 방화벽 규칙 변경이 필요할 수 있어 보안 팀과 조율하라고도 적습니다.

### iperf 결과를 애플리케이션 문제에 옮길 수 있는 조건

iperf 가 재는 것은 두 호스트 사이 대량 전송의 한도입니다. 그 결과를 애플리케이션 문제에 옮기려면 두 측정이 같은 것을 재야 합니다. 아래 표는 원서의 쓰임새에서 끌어낸 판단 기준입니다.

| 옮길 수 있는 경우 | 옮길 수 없는 경우 |
|---|---|
| 앱과 같은 두 호스트, 같은 경로(NIC·라우팅·중간 장비)를 지남 | 앱 트래픽은 로드밸런서·프록시를 지나는데 iperf 는 두 호스트를 직접 이음 |
| 앱도 연결 몇 개로 큰 데이터를 나름 | 앱은 짧은 요청·응답이 많음. 왕복 지연은 netperf TCP_RR 같은 요청/응답 시험이 맞음 |
| 방향과 병렬도를 앱에 맞춤(`-R`, `-P`) | 앱은 연결을 자주 새로 엶. 연결 수립과 SYN 큐의 비용은 대량 전송 시험에 거의 드러나지 않음 |
| 앱의 병목도 메모리에서 메모리로 보내는 구간에 있음 | 병목이 디스크·파일 시스템에 있음. iperf3 는 그 비용을 넣으려면 `-F` 를 따로 씀[^iperf3] |
| 대역폭 제한 조건이 측정 때와 같음 | 클라우드의 부과 한도가 시간대나 인스턴스마다 다름(원서 10.5.9) |

그래서 iperf 가 기대치를 내면 확정되는 것은 "이 경로는 대량 전송 한도를 막지 않는다" 까지입니다. 앱이 느린 이유는 앱 쪽 측정으로 찾습니다. 반대로 기대치에 못 미치면 앱보다 단순한 마이크로벤치마크로 원인을 좁히고, 네트워크를 원하는 속도로 맞춘 뒤 앱으로 돌아갑니다(원서).

**tc + netem**은 실험용 부하를 주입합니다. 아래는 eth0 에 1% 패킷 손실을 걸었다가 지우는 예로, root(또는 CAP_NET_ADMIN) 권한이 필요합니다. 이 노트의 실험 환경에서 두 명령이 그대로 동작하는 것을 확인했습니다.

```bash
# eth0 의 루트 qdisc 를 netem 으로 바꿔 나가는 패킷의 1% 를 버린다
tc qdisc add dev eth0 root netem loss 1%
# 시험이 끝나면 원래 qdisc 로 되돌린다
tc qdisc del dev eth0 root
```

다른 네트워크를 흉내 내거나 손실 상황에서 앱이 어떻게 동작하는지 시험할 때 씁니다.



## 5. 튜닝 — 어떤 손잡이를 돌리나

> 튜닝은 시스템 전역(sysctl), 소켓별(setsockopt), 설정(점보 프레임·링크 집계)에서 합니다. 기본값이 대개 잘 맞춰져 있어, 바꾸기 전에 그 손잡이를 가리키는 관측이 있어야 하고 대가를 함께 따져야 합니다.

원인을 찾았다면 이제 무엇을 바꿀 차례입니다. 다만 손잡이부터 돌리려는 충동을 먼저 눌러야 합니다. 네트워크 튜너블은 대개 이미 고성능으로 맞춰져 있고 스택도 워크로드에 동적으로 반응합니다. 그래서 튜너블보다 워크로드 이해가 먼저입니다. 불필요한 일을 없애는 편이 이득이 큽니다. 원서는 가용 튜너블이 OS 버전마다 다르므로 아래 값을 출발점으로만 쓰라고 적습니다.

### 점검과 변경은 다른 단계입니다

§1 의 정적 성능 튜닝은 이름과 달리 설정을 바꾸는 일이 아니라 점검하는 일입니다. 원서의 질문 목록도 확인으로 이뤄집니다. 인터페이스가 몇 개이고 몇 개를 쓰는지, 최대 속도와 협상된 속도·듀플렉스, MTU, 튜너블이 기본값에서 바뀌었는지, 경로의 최대 MTU 와 분할 여부, 방화벽과 부과된 대역폭 한도가 여기 듭니다.

그 답에서 문제가 나왔을 때만 이 절의 변경으로 넘어갑니다. 이 노트는 변경을 한 번에 하나씩 하고, 바꾸기 전과 같은 부하에서 같은 지표로 다시 재 효과를 확인하는 것을 원칙으로 둡니다.

### 시스템 전역 튜너블 — 바꿀 근거와 대가

시스템 전역 튜너블은 sysctl 이나 `/proc/sys/net` 으로 보고 바꿉니다. 호스트의 모든 연결(또는 새로 만들어질 연결)에 걸린다는 뜻입니다.

| 튜너블 | 무엇을 정하나 | 바꿀 근거가 되는 관측 | 대가·주의 |
|--------|------------|-------------------|----------|
| `net.core.rmem_max`·`wmem_max` | 앱이 `SO_RCVBUF`·`SO_SNDBUF` 로 요청할 수 있는 버퍼 상한 | 버퍼를 명시하는 앱이 BDP 보다 작게 잘림 | 연결당 메모리. 자동 조정 상한은 아님 |
| `net.ipv4.tcp_rmem`·`tcp_wmem` | 자동 조정의 최소·기본·최대 | 먼 경로에서 `ss` 가 `rwnd_limited`·`sndbuf_limited` 를 보임 | 최소·기본을 올리면 모든 연결이 더 씀(원서) |
| `net.ipv4.tcp_max_syn_backlog` | SYN cookies 가 꺼졌을 때 확인 안 된 요청을 먼저 버리는 기준 | 쿠키가 꺼진 환경에서 `TCPReqQFullDrop` 증가 | 쿠키가 켜진 기본 환경에서는 쓰이지 않음. 쿠키가 나가는 기준은 listen backlog 한도(10-02 §4) |
| `net.core.somaxconn` | listen backlog 상한 | `ListenOverflows` 증가, `ss -lnt` 의 Recv-Q 가 Send-Q 를 넘음 | 앱의 backlog 인자도 함께 올려야 함. 근본은 앱의 accept 속도 |
| `net.core.netdev_max_backlog` | CPU 별 입력 큐 길이 | `/proc/net/softnet_stat` 둘째 열 증가 | 큐가 길면 대기가 길어짐. 원서는 10GbE 에서 10,000 을 예로 듦 |
| `net.ipv4.tcp_congestion_control` | 새 연결의 기본 혼잡 제어 | 손실·지연이 큰 경로에서 처리량이 기대보다 낮음 | 경로마다 결과가 다름(원서의 BBR 사례). 소켓별로도 바꿀 수 있음 |
| `net.core.default_qdisc` | 새로 만드는 qdisc 의 기본 | 송신 큐 지연(버퍼블로트) | 가상 장치는 noqueue 라 무관. 설정 없이 도는 qdisc 만 맞음[^net-sysctl] |
| `net.ipv4.tcp_tw_reuse` | TIME_WAIT 소켓 재사용 | connect 의 `EADDRNOTAVAIL`, TIME_WAIT 수가 포트 범위에 근접 | 기본 2. 문서의 경고(§2) |
| `net.ipv4.ip_local_port_range` | 출발지 포트 범위 | 같은 목적지로의 포트 고갈(§2) | 서비스 포트와 겹치지 않게 예약 |

버퍼 두 줄은 범위가 다릅니다. `rmem_max` 는 앱이 `SO_RCVBUF` 로 요청할 수 있는 상한이고,[^socket7] 자동 조정이 쓰는 상한은 `tcp_rmem` 의 셋째 값입니다. 앱이 `SO_RCVBUF` 를 부르면 그 소켓의 자동 조정이 꺼집니다.[^ip-sysctl]

원서는 `rmem_max`·`wmem_max` 를 16MB 이상으로 두어야 10GbE 를 풀 속도로 쓸 수 있다고 적습니다. 이 수치는 RTT 조건을 달고 읽어야 합니다. 한 연결이 링크를 채우려면 윈도가 대역폭 × RTT(BDP) 이상이어야 하기 때문입니다.

```bash
# 개념 계산 — 10 Gbit/s = 1.25 GB/s 인 링크를 한 연결로 채우는 데 필요한 윈도(BDP)
# RTT 0.2 ms (원서 표 10.1 의 같은 서브넷 10GbE ping) → 1.25 GB/s × 0.0002 s =  250 KB
# RTT 10 ms                                          → 1.25 GB/s × 0.010 s  = 12.5 MB
# RTT 40 ms (원서 표 10.1 의 샌프란시스코~뉴욕 ping)   → 1.25 GB/s × 0.040 s  =   50 MB
# 16 MiB(16,777,216 바이트)가 채울 수 있는 RTT 상한: 16,777,216 ÷ 1,250,000,000 B/s ≈ 13.4 ms
```

16MB(원서 값 16,777,216바이트)는 RTT 가 약 13 ms 이하인 경로에서 한 연결로 10GbE 를 채우는 경우에 맞는 값입니다. 같은 데이터센터라면 훨씬 작은 버퍼로 충분하고, 먼 경로라면 모자랍니다. 버퍼 전부가 윈도로 쓰이지도 않습니다. 커널 문서는 `tcp_rmem` 의 기본값 131072바이트가 초기 창 65535 로 이어진다고 적습니다.[^ip-sysctl]

원서는 Netflix 가 클라우드 인스턴스에서 14개 튜너블만 설정한다고 소개합니다. fq qdisc·bbr 혼잡 제어·버퍼·백로그 등으로, 가능한 전부가 아니라 워크로드에 맞는 일부입니다. 원서는 이것이 그 시점의 예시일 뿐 따라 할 처방이 아니라고 적고, 2020년에 두 값을 바꾸는 것을 검토 중이라고 덧붙입니다.

### 소켓별 옵션 — 그 연결만 바꾼다

소켓별 튜닝은 애플리케이션이 setsockopt 로 소켓을 하나씩 조정하는 방식입니다. 원서는 소스를 고치거나 다시 빌드할 수 있을 때만 쓸 수 있다고 적습니다.

| 옵션 | 역할 | 대가·주의 |
|------|------|----------|
| `SO_SNDBUF`·`SO_RCVBUF` | 그 소켓의 송수신 버퍼 | 커널이 값을 두 배로 잡고 `rmem_max`·`wmem_max` 로 자름.[^socket7] 그 소켓의 자동 조정이 꺼짐 |
| `SO_REUSEPORT` | 여러 프로세스·스레드가 같은 포트에 바인드, 커널이 부하를 나눔 | Linux 3.9 부터(원서) |
| `SO_MAX_PACING_RATE` | 전송 속도 상한(bytes/s) | 원서는 tc-fq(8) 를 참고하라고 적음 |
| `SO_LINGER` | close 가 기다리는 방식 | 0초면 RST 로 끊음(§2). TIME_WAIT 대책으로 쓰지 않음 |
| `TCP_NODELAY` | Nagle 비활성 | 지연이 줄고 패킷이 늘어남 |
| `TCP_CONGESTION` | 그 소켓만의 혼잡 제어 | 시스템 기본과 다른 경로를 쓰는 연결에만 |

범위로 고르면 됩니다. 특정 연결만 다르게 하려면 소켓 옵션을, 호스트의 기본을 바꾸려면 sysctl 을 씁니다. 두 층이 겹치는 자리도 있습니다. 소켓 옵션으로 큰 버퍼를 요청해도 sysctl 상한(`rmem_max`)에서 잘리므로, 한 연결만 크게 하려 해도 상한은 전역에서 올려 둬야 합니다.

설정 쪽으로는 MTU 9,000 의 점보 프레임, 여러 NIC 를 묶는 링크 집계, 방화벽의 IP ToS/DSCP 설정이 있습니다. 점보 프레임은 경로 전체가 지원해야 이득입니다(10-01 §2). 원서는 링크 집계가 스위치 지원과 설정이 있어야 제대로 동작한다고 적습니다. 여러 튜너블을 network-latency·network-throughput 같은 프로파일로 한 번에 설정하는 Tuned Project 같은 자동 튜닝 도구도 있습니다.

2. 패킷 스니핑이 마지막 수단인 까닭과, 커널 내 BPF 필터가 비용을 줄이는 원리를 말해 봅니다. (→ §3)
3. 클라이언트의 `nstat` 증분에서 `TcpExtTCPSynRetrans` 가 `TcpRetransSegs` 와 같은 값만큼 늘었습니다. 원인 후보를 셋 이상 들고, 후보를 가를 확인 카운터나 출력을 고릅니다. (→ §1·§2)
4. 출발지 IP 하나인 배치 서버가 같은 DB(IP·포트 하나)로 초당 600개씩 새 연결을 열고, 매번 DB 보다 먼저 닫습니다. Linux 기본 포트 범위에서 무슨 일이 생기는지와, 대책을 무엇부터 검토할지 판단합니다. (→ §2)
5. iperf3 로 두 서버 사이 9.4Gbit/s 가 나왔는데, 두 서버 사이 REST API 는 요청당 30 ms 가 걸립니다. iperf 결과로 확정할 수 있는 것과 더 재야 할 것을 나눠 봅니다. (→ §4)
6. 한 서비스의 대용량 백업 연결만 수신 버퍼를 크게 하고 나머지 연결은 기본으로 두고 싶습니다. 시스템 전역 설정과 소켓별 설정 중 무엇을 쓰고, 무엇을 함께 확인해야 합니까? (→ §5)



## 정답 (자답 후 펼치기)

> 먼저 답한 뒤 읽습니다. 판단 근거와 흔한 오해를 함께 적습니다.

### 정답 1 — 시작 순서와 내 호스트 먼저

원서는 성능 모니터링·USE·정적 성능 튜닝(설정 점검)·워크로드 특성화 순으로 시작하라고 권합니다. 네트워크는 모르면 먼저 의심받는 자원이라, 내 인터페이스와 설정을 먼저 확인해야 "내 탓이 아니다"를 증거로 보이거나 범위를 좁힐 수 있습니다. 대표 오해는 정적 성능 튜닝을 설정을 바꾸는 단계로 읽는 것입니다.

### 정답 2 — 스니핑의 비용

패킷마다 복사하고 저장하므로 CPU·저장 비용이 크고, 사이클 최적화된 커널 경로에 부담을 줍니다. 커널 내 BPF 필터는 원하는 패킷만 골라 나머지를 유저 레벨로 넘기지 않아 복사량을 줄입니다. 대표 오해는 필터를 걸면 비용이 사라진다는 것입니다. 걸러 낸 패킷의 복사와 저장은 여전히 남습니다.

### 정답 3 — SYN 재전송의 원인 후보

재전송이 모두 SYN 이라는 것은 문제가 연결 수립 단계에 있다는 관찰입니다. 후보는 서버 accept 큐 넘침, 쿠키가 꺼진 서버의 SYN 큐 넘침, 경로 손실, 방화벽의 조용한 드롭, 서버 다운입니다. 서버에서 `ListenOverflows` 가 오르면 accept 큐, `TCPReqQFullDrop` 이 오르면 SYN 큐입니다.

서버의 TCP 카운터가 그대로인데 SYN 만 사라진다면 TCP 층에 닿기 전을 봅니다. 경로나 방화벽이고, 서버 자신의 netfilter 도 여기 듭니다. 재전송의 목적지가 한 곳인지 여럿인지도 가릅니다(10-04 §6). 대표 오해는 원서의 "SYN_SENT 재전송은 과부하 서버" 를 확정으로 읽는 것입니다.

### 정답 4 — 초당 600 연결의 포트 고갈

클라이언트가 먼저 닫으므로 TIME_WAIT 가 배치 서버에 60초 남습니다. 쓸 포트는 28,232개라 초당 약 470개가 한계인데 600을 여니 28,232 ÷ 600 ≈ 47초 만에 범위가 바닥나 connect 가 `EADDRNOTAVAIL` 로 실패합니다. 대책은 연결 풀로 새 연결 수를 줄이는 것부터 검토하고, 그다음 출발지 IP 추가나 포트 범위 확장을 봅니다. `tcp_tw_reuse` 는 문서의 경고를 읽고 조건을 확인한 뒤에만 씁니다. 대표 오해는 `SO_LINGER` 0초로 TIME_WAIT 를 없애는 것입니다. 그 대가로 연결이 RST 로 끊깁니다.

### 정답 5 — iperf 결과의 범위

확정되는 것은 두 서버 사이 경로가 대량 전송을 9.4Gbit/s 까지 막지 않는다는 것입니다. REST 요청 30 ms 의 원인은 아직 모릅니다. 요청마다 새 연결을 여는지, 로드밸런서를 거치는지, 서버 처리 시간이 얼마인지를 재야 합니다. 요청/응답 왕복은 netperf TCP_RR 같은 시험이 맞고, 앱 쪽에서는 연결 지연과 TTFB 를 나눠 잽니다(10-01 §3). 대표 오해는 iperf 가 빠르니 네트워크는 무관하다고 결론 내는 것입니다.

### 정답 6 — 백업 연결만 버퍼를 크게

그 연결에만 `SO_RCVBUF` 를 쓰는 소켓별 설정이 범위에 맞습니다. 함께 확인할 것은 두 가지입니다. 요청한 값이 `rmem_max` 에서 잘리지 않는지, 그리고 그 소켓의 자동 조정이 꺼진다는 점입니다. 필요한 크기는 경로의 BDP 로 정합니다. 대표 오해는 `tcp_rmem` 최댓값을 올리는 것입니다. 그 값은 자동 조정을 쓰는 모든 연결에 걸립니다.
