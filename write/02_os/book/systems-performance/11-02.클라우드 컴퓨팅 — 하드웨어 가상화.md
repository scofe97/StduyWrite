# 클라우드 컴퓨팅 — 하드웨어 가상화
---
> 이 노트는 11.2 하드웨어 가상화를 다룹니다. 하이퍼바이저가 게스트마다 자체 커널을 가진 가상 머신을 만들고 관리하는 방식, 그 성능 오버헤드(특히 guest exit와 I/O), 자원 제어, 그리고 호스트·게스트에서의 관측을 Xen·KVM·Nitro를 예로 봅니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 **가상화 오버헤드가 늘 붙어 있는 세금이 아니라, 게스트가 하이퍼바이저로 빠져나가는 순간에만 생기는 비용이라는 것**입니다.

하드웨어 가상화는 자체 커널을 포함한 전체 OS를 돌리는 가상 머신을 만듭니다. 하이퍼바이저가 그 VM을 생성하고 관리합니다. 옛 Type 1/2 분류 대신 실용적으로 둘로 봅니다. Config A는 베어메탈 위에서 도는 것(Xen), Config B는 호스트 OS가 실행하는 것(KVM)입니다.

성능을 볼 때 중요한 것은 *언제 오버헤드가 생기고 언제 안 생기는지* 입니다. 게스트 애플리케이션은 대개 프로세서에서 직접 실행되므로 CPU-bound 작업은 베어메탈과 거의 같습니다. 비용은 특권 명령이나 하드웨어 접근처럼 하이퍼바이저의 손을 빌려야 하는 순간에 발생합니다.

1998년 VMware의 바이너리 변환 이후의 개선은 한 줄로 이어진 순서가 아닙니다. 프로세서 지원, 패러버추얼라이제이션, 디바이스 하드웨어 지원의 세 갈래가 나란히 진행됐습니다. 연대로 보면 패러버추얼 게스트를 내세운 Xen 의 첫 공개가 2003년으로, AMD-V·VT-x 확장이 나온 2005~2006년보다 먼저입니다. 세 갈래의 공통점은 하이퍼바이저가 끼어드는 순간의 수나 비용을 줄였다는 데 있습니다.



## 학습 목표

> 이 편을 덮은 뒤 스스로 할 수 있어야 하는 일을 먼저 적어 둡니다.

- Config A와 Config B의 차이를 말하고, Nitro 같은 현대 하드웨어 가상화에 어떤 오버헤드가 남는지 설명합니다.
- guest exit가 무엇인지 답하고, `perf kvm stat` 에서 exit 횟수와 시간을 나눠 읽어 게스트 상태를 추론합니다.
- 메모리 매핑이 왜 두 단계인지 말하고, I/O 완화 기술 셋이 성능과 유연성을 어떻게 맞바꾸는지 비교합니다.
- 메모리·CPU 한계가 어떻게 걸리고 게스트 안에서 어떻게 보이는지 설명합니다.
- 호스트와 게스트에서 각각 무엇이 보이고 안 보이는지 구분하고, 게스트에서 지연으로 물리 경합을 추정합니다.

구현에서 시작해 오버헤드가 생기는 자리를 짚고, 제어와 관측으로 넘어갑니다.

## 1. 구현 — VMware·Xen·KVM·Nitro

> 하이퍼바이저 구현은 Config A(베어메탈, Xen)와 Config B(호스트 OS가 실행, KVM)로 나뉩니다. 둘 다 I/O 프록시(QEMU)를 쓸 수 있어 오버헤드가 붙는데, Nitro는 하드웨어 지원으로 프록시를 없애 베어메탈에 가까운 성능을 냅니다.

### 두 구성 — Config A 와 Config B

게스트 커널은 자기가 하드웨어를 직접 만진다고 믿습니다. 그 믿음을 깨지 않으면서 실제 하드웨어를 여럿이 나눠 쓰게 만드는 것이 하이퍼바이저(가상 머신 모니터, VMM)의 일이고, 그 방법이 세대마다 달랐습니다.

원서는 옛 Type 1/2 분류가 더는 딱 맞지 않는다고 봅니다. Type 2가 커널 모듈로 하드웨어에 직접 닿으면서 Type 1에 가까워졌기 때문입니다. 그래서 두 구성으로 나눕니다.

Config A에서는 하이퍼바이저가 프로세서 위에서 직접 돌며 게스트 VM을 담을 도메인을 만듭니다. 그리고 가상 CPU를 실제 CPU에 스케줄링합니다. 0번 특권 도메인이 나머지를 관리합니다. Xen이 대표이고, Xen에서는 이 관리 도메인을 dom0, 게스트 도메인을 domU라 부릅니다.

Config B에서는 호스트 OS 커널이 하이퍼바이저를 실행합니다. 하이퍼바이저는 커널 모듈과 유저 프로세스로 이뤄질 수 있고, 호스트 커널이 VM의 CPU를 다른 프로세스와 함께 스케줄링합니다. KVM이 대표입니다.

두 구성 모두 게스트 I/O를 위해 *I/O 프록시* 를 돌릴 수 있습니다. Xen은 dom0에서, KVM은 호스트 OS에서 QEMU를 띄웁니다. 이 프록시가 I/O 경로에 단계를 하나 더해 오버헤드가 됩니다. 공유 메모리 전송 같은 기법으로 오랫동안 최적화해 왔습니다.

### 바이너리 변환 이후의 세 갈래 개선

1998년 VMware의 하드웨어 하이퍼바이저는 *바이너리 변환* 으로 전체 하드웨어를 가상화했습니다. syscall이나 페이지 테이블 조작 같은 특권 명령을 실행 전에 재작성하고, 나머지 비특권 명령은 프로세서에서 그대로 돌렸습니다. 오버헤드가 컸지만 서버 통합으로 얻는 절감이 더 컸습니다.

이후 개선은 세 갈래로 나란히 진행됐습니다.

| 갈래 | 무엇을 하나 | 원서의 연대·조건 |
|------|-----------|----------------|
| 프로세서 가상화 지원 | 프로세서가 특권 명령과 MMU 가상화를 직접 돕습니다 | AMD-V·Intel VT-x, 2005~2006년 |
| 패러버추얼라이제이션(PV) | 게스트 OS가 하이퍼바이저를 부르는 인터페이스를 써서 호스트 자원을 효율적으로 씁니다 | 게스트 OS 수정 필요. Xen 이 2003년부터 PV 게스트로 고성능을 냄 |
| 디바이스 하드웨어 지원 | 프로세서 밖 장치가 VM 지원을 갖춰 게스트가 하드웨어에 직접 닿습니다 | 네트워크·스토리지용 SR-IOV, 드라이버 지원 필요(ixgbe·ena·nvme 등) |

PV에서 게스트가 하이퍼바이저를 부르는 호출을 하이퍼콜(hypercall)이라 합니다. 예를 들어 타이머 설정은 보통 특권 명령 여러 개라 하이퍼바이저가 하나씩 에뮬레이션해야 하는데, PV 게스트는 이를 하이퍼콜 하나로 끝냅니다. Xen은 하이퍼콜을 multicall로 묶어 더 줄입니다.

SR-IOV(single root I/O virtualization)는 장치가 하드웨어 차원에서 가상화를 제공해, 게스트가 하이퍼바이저나 프록시를 거치지 않고 장치에 직접 접근하게 하는 기술입니다. I/O 경로에서 이것이 무엇을 없애는지는 §3이 봅니다.

현대 Xen은 두 가지를 섞습니다. 먼저 HVM(hardware VM) 모드, 곧 프로세서 가상화 지원으로 수정 없는 게스트를 부팅하는 모드로 띄웁니다. 그 위에서 PV 드라이버를 쓰는 구성이 PVHVM입니다. 여기서 더 나아가 네트워크·스토리지 같은 일부 드라이버를 SR-IOV에 전적으로 맡기기도 합니다.

### 구현 다섯

| 구현 | 성격 |
|------|------|
| VMware ESX | 2001년. 베어메탈 마이크로커널 하이퍼바이저. 엔터프라이즈 서버 통합 |
| Xen | 2003년. Type 1. 패러버추얼 게스트로 고성능. 도메인(dom0이 관리). 옛 EC2 기반 |
| Hyper-V | Windows Server 2008. Type 1. 파티션으로 게스트 실행. Azure |
| KVM | Type 2(커널 모듈). 유저 프로세스 QEMU와 짝지어 완전한 VM 생성. GCE 기반 |
| Nitro | 2017년. KVM 기반 부품 + 프로세서·네트워크·스토리지·인터럽트·타이머에 하드웨어 지원. QEMU 프록시 없음. 베어메탈급 |

> **출처 주의 (2026-09 확인)**: Nitro의 "KVM 기반 · QEMU 없음"은 책의 서술입니다. AWS 공식 문서는 Nitro Hypervisor를 "lightweight hypervisor"로만 소개하고 KVM 기반인지, QEMU를 쓰지 않는지를 명시하지 않습니다. 반박할 근거도 없으니 그대로 두되, AWS가 문서화한 사실이 아니라는 점만 알아 둡니다. (확인: [AWS — Nitro instances](https://docs.aws.amazon.com/ec2/latest/instancetypes/ec2-nitro-instances.html))

> 구현의 핵심 차이는 *I/O 경로의 단계 수* 입니다. Nitro는 하드웨어 지원으로 I/O 프록시라는 추가 단계를 없앱니다. 원서는 최대 성능을 추구하는 대형 클라우드 제공자라면 이 방향을 따를 것으로 전망합니다. 세 갈래 개선이 모두 하이퍼바이저가 끼어드는 순간을 줄이는 쪽이었고, Nitro는 그것을 I/O까지 밀어붙인 구현입니다.



## 2. CPU 오버헤드 — guest exit가 핵심

> 게스트 애플리케이션은 보통 프로세서에서 직접 실행돼 CPU-bound 작업은 베어메탈과 거의 같습니다. 오버헤드는 특권 명령·하드웨어 접근·메모리 매핑 시 하이퍼바이저로의 전환(guest exit)에서 생기며, exit 처리 시간이 곧 CPU 오버헤드입니다.

![두 구성과 guest exit](_assets/11-02.hypervisor-config-guest-exit.svg)

### 특권 명령을 처리하는 세 방식

게스트 애플리케이션은 일반적으로 프로세서에서 *직접 실행* 되어, CPU-bound 작업은 베어메탈과 거의 같은 성능입니다. CPU 오버헤드는 특권 프로세서 호출·하드웨어 접근·메모리 매핑 때, 하이퍼바이저가 어떻게 처리하느냐에 따라 생깁니다.

이 차이를 보려면 보호 링을 먼저 떠올려야 합니다. 프로세서는 대개 링 네 개를 두고, 커널은 가장 특권이 높은 ring 0, 애플리케이션은 ring 3에서 돕니다. 게스트 커널도 자기가 ring 0에 있다고 가정하고 짜였습니다. 처리 방식은 셋입니다.

- **바이너리 변환**: VMM이 ring 0을 차지하고 게스트 커널을 비어 있던 ring 1로 옮깁니다. ring 0을 가정한 게스트 커널 명령은 실행 중에 변환돼 VMM을 부르므로 CPU 오버헤드가 큽니다.
- **패러버추얼라이제이션**: 가상화가 필요한 게스트 명령을 하이퍼콜로 바꿉니다. 게스트 OS를 수정해야 합니다.
- **하드웨어 지원**: VMM이 ring 0보다 아래 특권 수준에서 돕니다. 수정하지 않은 게스트 커널이 특권 명령을 실행하면 프로세서가 제어를 강제로 VMM에 넘기는데, 이것을 trap이라 합니다. VMM이 그 특권을 에뮬레이션해 줍니다.

보통은 하드웨어 지원을 선호하고, 게스트 OS가 지원하면 I/O 같은 일부 워크로드에 PV를 더합니다. 다만 초기 하드웨어 지원이 늘 빨랐던 것은 아닙니다. VMware는 2007년에, 전환 비용이 크고 프로그래밍 모델이 경직된 1세대 하드웨어 지원보다 자사 바이너리 변환이 대부분 상황에서 빠르다고 적었습니다.

### guest exit — 오버헤드가 생기는 순간

핵심 개념이 **guest exit** 입니다. 게스트에게 CPU처럼 보이는 가상 CPU(vCPU)가 게스트 안에서 실행을 멈추고 하이퍼바이저로 빠져나가는 이벤트를 말합니다.

게스트 밖에서 보낸 시간이 곧 하드웨어 가상화의 CPU 오버헤드입니다. exit 처리에 시간을 더 쓸수록 오버헤드가 커집니다. 일부 exit는 호스트 커널에서 바로 처리되지만, 그러지 못하는 것은 커널을 떠나 유저 프로세스(KVM에서는 QEMU)까지 돌아가 *더 큰* 비용을 냅니다.

KVM은 exit 이유마다 핸들러를 둡니다. `handle_halt` 는 idle 스레드의 halt를, `handle_io` 는 I/O 명령을 받습니다. `handle_rdmsr`·`handle_wrmsr` 는 MSR 읽기·쓰기를 받는데, MSR은 x86 CPU의 모델별 레지스터(model-specific register)입니다[^msr]. `handle_cpuid` 같은 것도 있습니다.

가장 흔한 exit 하나가 *halt* 입니다. 커널이 더 할 일을 찾지 못하면 idle 스레드가 halt 명령을 부르고, 프로세서는 인터럽트가 올 때까지 저전력 상태로 쉽니다. 그래서 halt exit 하나는 짧게 끝나지 않고 다음 인터럽트까지 이어집니다. §5에서 이 성질이 출력에 그대로 드러납니다.

> CPU 오버헤드의 핵심 지표는 *guest exit의 빈도와 처리 시간* 입니다. 원서는 exit 수가 적고 그중 halt가 차지하는 비율이 높으면 게스트 CPU가 꽤 idle하다고 읽습니다. 반대로 I/O 명령과 인터럽트 생성·주입이 많으면 가상 NIC·디스크로 I/O 중일 가능성이 큽니다. 이 exit를 분석하면 게스트 내부를 직접 못 봐도 하드웨어 가상화 오버헤드가 테넌트에 미치는 영향을 특성화할 수 있습니다(§5 관측).



## 3. 메모리·I/O 오버헤드 — 매핑 두 단계와 I/O 경로

> 메모리 매핑은 게스트 가상→게스트 물리→호스트 물리 두 단계라, EPT/NPT(하드웨어) 또는 shadow page table로 가속합니다. I/O는 역사적으로 가장 큰 오버헤드였고, 패러버추얼 드라이버로 오버헤드를 줄이고, PCI pass-through로 최고 성능을 얻되 유연성을 잃고, SR-IOV로 그 유연성을 되찾아 왔습니다.

### 메모리 — 매핑 두 단계와 크기

**메모리 매핑** 오버헤드는 변환이 두 단계이기 때문에 생깁니다. 게스트 커널이 게스트 가상 주소를 게스트 물리 주소로 바꾸고, 하이퍼바이저가 다시 그것을 호스트 물리 주소로 바꿉니다.

이 매핑은 TLB에 캐시되므로 이후 접근은 정상 속도입니다. 현대 프로세서는 MMU 가상화를 지원해, TLB에서 빠진 매핑을 하이퍼바이저 호출 없이 하드웨어만으로 되찾습니다. Intel EPT와 AMD NPT가 그것입니다. 지원이 없으면 VMM이 게스트 가상에서 호스트 물리로 바로 잇는 *shadow page table* 을 관리하고, 게스트 실행 중에 페이지 테이블 루트를 담는 CR3 레지스터를 shadow 쪽으로 덮어씁니다.

**메모리 크기** 쪽에도 오버헤드가 있습니다. 게스트마다 자체 커널이 메모리를 조금씩 씁니다. 스토리지 아키텍처는 *이중 캐싱* 을 부르는데, 게스트와 호스트가 같은 데이터를 각자 캐시하는 상황입니다. KVM류에서는 VM마다 QEMU 프로세스가 따로 메모리를 씁니다.

### I/O — 성능과 유연성의 교환

![I/O 경로 — 성능과 유연성의 교환](_assets/11-02.io-path-evolution.svg)

**I/O** 는 역사적으로 가장 큰 오버헤드였습니다. 모든 디바이스 I/O를 하이퍼바이저가 변환해야 했고, 10Gbit/s 같은 고빈도 I/O에서는 건당 작은 오버헤드도 전체 성능을 크게 떨어뜨렸습니다. 하드웨어 쪽에서는 I/O MMU 가상화(AMD-Vi·Intel VT-d)가 이 오버헤드를 없애는 기반이 됐습니다. 완화 기술은 셋입니다.

| 기술 | 동작 | 얻는 것과 잃는 것 |
|------|------|-----------------|
| 패러버추얼 드라이버 | I/O를 합치고 디바이스 인터럽트를 줄임 | 하이퍼바이저 오버헤드↓, 게스트 OS 지원 필요 |
| PCI pass-through | PCI 디바이스를 게스트에 직접 할당 | 원서 기준 최고 성능. 장치를 게스트가 독점해 공유 불가, 라이브 마이그레이션이 복잡 |
| SR-IOV / MR-IOV | 하드웨어 가상화로 장치를 여러 게스트에 나눠 직접 접근 | pass-through 의 유연성 문제를 푸는 기술. Nitro 의 기본 |

표의 순서는 빠르기의 순서가 아닙니다. 원서는 PCI pass-through가 선택지 중 최고 성능을 낸다고 하고, SR-IOV·MR-IOV는 가상화 환경에서 PCI 장치를 *유연하게* 쓰게 하는 기술로 소개합니다. EC2는 이 기술을 네트워크에 먼저, 그다음 스토리지 I/O에 도입했고 Nitro에서는 기본으로 씁니다.

### I/O 경로의 단계 수

Xen·KVM·Nitro의 I/O 경로가 다릅니다. Xen은 dom0과 domU 사이 *device channel*(비동기 공유 메모리 전송)로 도메인 사이의 추가 복사를 피합니다. KVM 개발자들은 2006년에 Xen 같은 특권 게스트 구조와 KVM을 비교해, KVM이 I/O를 절반의 단계(5 대 10)로 처리한다고 보고했습니다. 원서는 이 측정이 패러버추얼라이제이션 없이 이뤄져 대부분의 현대 구성을 반영하지 않는다고 단서를 답니다. Nitro는 하드웨어 지원으로 I/O 프록시를 두지 않아 추가 I/O 단계가 없습니다.

> 메모리·I/O 오버헤드의 공통 주제는 *하드웨어 지원으로 소프트웨어 단계를 없애는 것* 입니다. 메모리는 EPT/NPT로 두 단계 변환을 하드웨어가, I/O는 SR-IOV로 게스트가 하드웨어를 직접 접근합니다. 한편 *멀티테넌트 경합* 도 있습니다. CPU·캐시 공유로 stolen time·캐시 오염이 생기고, 다른 테넌트의 I/O 인터럽트가 실행을 끊을 수도 있습니다. 이는 bursting 을 위해 공유를 권하는 컨테이너에서 VM보다 더 큰 문제입니다(11-03).



## 4. 자원 제어 — vCPU·메모리·I/O 제한

> CPU는 vCPU 수로 거칠게, 하이퍼바이저 스케줄러(Xen credit·KVM cgroup)로 세밀하게 제한합니다. 메모리는 게스트 설정으로 고정하되 balloon 드라이버로 유연성을 더하고, I/O는 호스트 커널 기능(cgroup·qdisc)이나 하드웨어로 제한합니다.

### CPU — vCPU 수와 스케줄러

**CPU** 는 보통 vCPU 단위로 할당되고 하이퍼바이저가 스케줄링합니다. vCPU 수가 CPU 사용을 거칠게 제한하는 셈입니다. 더 세밀한 쿼터는 Xen이 하이퍼바이저 CPU 스케줄러로, KVM이 호스트 OS의 cgroup CPU bandwidth로 부과합니다. Xen 스케줄러는 계보가 있습니다. BVT는 가상 시간을 앞당겨 쓰게 해 저지연을 노렸고, SEDF는 최단 데드라인 우선의 실시간 스케줄링을, credit 기반은 가중치와 상한에 CPU 간 부하 분산을 더했습니다.

> **갱신 (2026-09)**: 지금 기본은 **credit2** 입니다(Xen 4.12부터). 그래서 위 셋은 현재 선택지가 아니라 역사적 계보로 읽는 편이 맞습니다. (출처: [Xen — Credit2 Scheduler](https://xenbits.xen.org/docs/unstable/features/sched_credit2.html))

여기에 한계가 하나 있습니다. *게스트 우선순위를 존중하기 어렵다* 는 점입니다. 게스트 안의 CPU 사용은 하이퍼바이저에게 불투명하므로, 한 게스트의 한가한 로그 데몬이 다른 게스트의 핵심 앱과 같은 우선순위로 취급될 수 있습니다.

Xen에는 I/O가 많은 워크로드가 dom0 CPU를 추가로 먹는 문제가 있습니다. 백엔드 드라이버와 I/O 프록시가 할당보다 많은 CPU를 쓰는데 그 몫이 게스트에 계정되지 않습니다. *격리 드라이버 도메인(IDD)* 으로 I/O 서비스를 떼어 내 따로 계정합니다. CPU 캐시는 Intel CAT로 게스트별 LLC 분할이 가능한데, 캐시를 제한하면 성능도 함께 깎인다는 점은 감안해야 합니다.

게스트 안에서 CPU 한계는 vCPU 수로 보이고, 하이퍼바이저가 가져간 시간은 vmstat 의 steal로 드러납니다(§5).

### 메모리 — 고정 한계와 balloon

**메모리 용량** 은 게스트 설정으로 부과돼 게스트가 정해진 양만 봅니다. 게스트 커널은 그 한계 안에 머물려고 스스로 페이징·스와핑을 합니다. 그래서 게스트 관리자에게 메모리 고갈은 "한계에 걸렸다"는 신호가 아니라 평범한 메모리 부족과 페이징으로 보입니다.

정적 설정에 유연성을 더하려고 VMware가 *balloon 드라이버* 를 만들었습니다. 게스트 안의 balloon 모듈을 "부풀리면" 게스트 메모리를 그만큼 소비합니다. 이때 게스트 커널은 평소의 메모리 관리 루틴(페이징 등)으로 메모리를 비웁니다. 하이퍼바이저는 그렇게 비워진 메모리를 회수해 다른 게스트에 씁니다. 반대로 수축시키면 게스트에 돌려줍니다. Xen과 KVM도 지원합니다.

### 디바이스 I/O — 호스트 기능과 외부 장치

**디바이스 I/O** 는 역사적으로 CPU 제어를 통해 간접적으로 제한했습니다. 네트워크 처리량은 외부 전용 장치를 두거나, KVM류라면 호스트 커널의 cgroup 대역폭·qdisc로 throttle합니다. 게스트 디스크는 호스트가 만든 가상 볼륨으로 주어지며, KVM류에서는 ZFS 볼륨처럼 호스트 OS가 원하는 크기로 만듭니다.

Nitro 같은 하드웨어 지원 하이퍼바이저에서는 하드웨어나 외부 장치가 I/O 한계를 부과합니다. EC2는 외부 시스템으로 네트워크와 EBS I/O를 쿼터에 맞춰 throttle합니다.

> 자원 제어의 핵심은 *KVM류는 호스트 OS 제어를 함께 쓸 수 있다* 는 점입니다. 호스트가 물리 자원을 최종 통제하므로 cgroup·taskset이 하이퍼바이저 제어에 더해 적용됩니다(11-03 OS 가상화 자원 제어 참조). balloon 드라이버가 동작 중이면(게스트 dmesg에서 "balloon" 검색) 그것이 일으킬 성능 문제를 주시합니다.



## 5. 관측 — 호스트는 자원, 게스트는 커널

> 호스트(Xen dom0·KVM)에서는 물리 자원을 게스트별로 관측하지만 게스트 내부(프로세스)는 직접 못 봅니다. 게스트에서는 자체 커널이라 BPF 등 커널 추적 도구가 다 동작하고, vmstat의 steal로 가상화를 인지할 수 있으며, 물리 경합은 지연으로 추정합니다.

관측은 도구를 *어디서 띄우느냐* 에 따라 다릅니다. 호스트에서는 물리 자원을 표준 OS 도구로 보고, 이용률·포화·오류·IOPS·처리량·I/O 유형을 게스트별로 나눠 무거운 게스트를 빨리 찾습니다. 다만 *게스트 내부 프로세스와 그 호출 스택은 직접 못 봅니다.* 보려면 SSH 같은 허가된 수단으로 게스트에 로그인해야 합니다.

### 호스트에서 — xentop 과 qemu 프로세스

Xen은 vCPU가 하이퍼바이저 안에 있어 dom0의 표준 도구에 잡히지 않으므로 `xentop` 을 씁니다. CPU 사용률, 메모리 사용량과 한계, VCPUS, 가상 블록 장치의 VBD_RD·VBD_WR 을 줍니다. 이 가운데 `VBD_OO` 는 막혀서 큐에 쌓인 가상 블록 장치 요청 수라, 원서는 이것을 포화 지표로 적습니다.

KVM은 게스트가 호스트에서 `qemu-system-x86` 프로세스로 보입니다. 이 프로세스에는 vCPU마다 스레드가 있고 I/O 프록시 스레드도 있습니다. top으로 게스트 전체를, pidstat로 vCPU별 사용을 봅니다.

```bash
# 원서 발췌 — KVM 호스트에서 게스트 프로세스(PID 24881)의 스레드별 CPU (시각·UID·CPU 열과 나머지 스레드 생략, 스레드 이름은 원서 본문대로 복원)
host$ pidstat -tp 24881 1
  TGID   TID   %usr %system %guest %wait  %CPU  Command
 24881     -  17.00   17.00 147.00  0.00 181.00  qemu-syst
     - 24897   1.00    3.00  69.00  1.00  73.00  |__CPU 0/KVM
     - 24899   1.00    4.00  79.00  0.00  84.00  |__CPU 1/KVM
```

`CPU 0/KVM`·`CPU 1/KVM` 스레드가 두 vCPU이고 각각 73%·84%를 씁니다. `%guest` 는 그 작업이 가상 프로세서를 돌리며 VM 안에서 보낸 CPU 비율입니다[^pidstat]. 두 vCPU 모두 사용의 대부분이 `%guest` 이므로, 이 게스트는 호스트 쪽 처리보다 게스트 안의 실행에 CPU를 쓰고 있습니다. 어느 QEMU 프로세스가 어느 게스트인지는 `ps -wwfp PID` 로 인자를 보고 `-name` 옵션을 읽어 맞춥니다.

### perf kvm stat — exit 횟수와 시간을 따로 읽습니다

exit 유형은 게스트가 idle 인지, I/O 중인지, 계산 중인지를 알려 줍니다. Linux 에서는 `perf kvm stat` 이 exit 유형별 통계를 줍니다.

```bash
# 원서 발췌 — KVM 호스트, 모든 VM·vCPU의 exit 통계 (8행 중 4행만 옮김)
host# perf kvm stat live
         VM-EXIT  Samples  Samples%   Time%   Min Time    Max Time     Avg time
       MSR_WRITE     1668    68.90%   0.28%    0.67us      31.74us      3.25us
             HLT      466    19.25%  99.63%    2.61us  100512.98us   4160.68us
PREEMPTION_TIMER      112     4.63%   0.03%    2.53us      10.42us      4.71us
  IO_INSTRUCTION       37     1.53%   0.04%    5.36us      84.88us     19.97us
Total Samples:2421, Total events handled time:1946040.48us.
```

`Samples` 는 추적하는 동안 일어난 exit 횟수, `Samples%` 는 그 횟수의 비율, `Time%` 는 exit 처리에 쓴 시간의 비율입니다. 이 출력에서 두 비율은 따로 놉니다. MSR_WRITE는 횟수로는 68.9%로 가장 많지만 한 번에 평균 3.25µs라 시간으로는 0.28%입니다. HLT는 횟수로는 19.25%에 그치지만 한 번에 평균 4.16ms가 걸려 시간의 99.63%를 차지합니다.

HLT가 긴 까닭은 §2에서 본 halt의 성질입니다. vCPU가 idle 상태에 들어가 다음 인터럽트까지 머물기 때문에, 원서도 이 출력에서 가장 긴 exit를 HLT로 짚고 그 이유를 idle 진입으로 설명합니다. 그래서 원서의 "halt 비율이 높으면 idle"이라는 읽기는 *exit 횟수* 에서 HLT가 차지하는 비율을 말합니다.

이 예처럼 idle 이 섞인 게스트에서는 exit 한 번이 다음 인터럽트까지 이어져 HLT 의 시간 비율이 크게 나옵니다. 그래서 시간 비율만 보고 "halt가 많다"고 읽으면 횟수로 본 판단과 어긋날 수 있습니다. CPU-bound 게스트라면 halt 자체가 드물어 시간 비율도 작게 나올 수 있습니다. 횟수로 무엇이 자주 일어나는지, 평균 시간으로 무엇이 한 번에 비싼지를 따로 봅니다.

더 깊이 보려면 `kvm:kvm_exit` 와 `kvm:kvm_entry` tracepoint를 짝지어 exit 이유별 지속 시간을 잽니다. 원서의 `kvmexits.bt` 는 이를 히스토그램으로 보여 주는데, 예시 출력에서 IO_INSTRUCTION exit는 대부분 512µs 아래였고 몇 개가 2~8ms까지 튀었습니다. 호스트에서 CR3 레지스터를 샘플링하면 게스트 안에서 한 프로세스만 도는지(같은 CR3 값), 여러 프로세스를 오가는지(다른 CR3 값)도 추정할 수 있습니다.

### SR-IOV·pass-through 를 쓰면 호스트 iostat 에서 I/O 가 사라집니다

pass-through나 SR-IOV를 쓰면 게스트가 하드웨어에 직접 I/O를 냅니다. 하이퍼바이저의 I/O 경로를 건너뛰므로, 그 경로가 모으던 통계도 함께 사라집니다. 결과적으로 게스트 I/O가 호스트의 iostat 같은 도구에 나타나지 않습니다. 원서가 드는 우회책은 PMC(하드웨어 성능 카운터)의 I/O 관련 카운터로 I/O를 추론하는 것입니다.

Nitro처럼 하드웨어 지원이 기본인 호스트에서도 SR-IOV 때문에 하이퍼바이저에서 장치 I/O를 보기 어려워질 수 있습니다. Amazon이 Nitro에서 하이퍼바이저 관측을 실제로 어떻게 하는지는 공개돼 있지 않습니다.

### 게스트에서 — steal·지연·커널 추적

**게스트에서** 는 가상화된 자원과 그 사용만 보이고, 물리 쪽 문제는 추론해야 합니다. mpstat도 게스트에 할당된 vCPU만 보여 줍니다.

vmstat의 *steal*(`st`) 컬럼은 가상화를 인지하는 드문 통계입니다. 게스트가 쓰지 못한 CPU 시간을 보여 주는데, 원서는 그 시간을 가져간 쪽으로 다른 테넌트만 들지 않습니다. 하이퍼바이저가 *내 게스트의 I/O를 처리* 하느라 쓴 시간일 수도 있고, *인스턴스 유형에 따른 throttle* 일 수도 있습니다. 원서의 예시는 공격적인 CPU 제한 정책을 건 Xen 게스트로, 처음 4초는 90% 넘게 게스트 유저 모드였다가 이후 CPU 시간 대부분이 steal로 넘어갔습니다. 그러니 steal이 높다고 곧 noisy neighbor라고 단정하지 않습니다.

핵심은 **게스트가 자체 전용 커널을 가져 perf·Ftrace·BPF 같은 커널 추적 도구가 다 동작한다** 는 점입니다. root가 전체 커널 접근권을 가지므로 biosnoop 같은 BPF 도구로 가상 디스크 지연까지 봅니다. 사이클 수준 분석에 필요한 PMC는 하이퍼바이저 설정에 따라 게스트에 열리기도 하고 안 열리기도 합니다. Xen은 가상 PMU(vpmu)로 게스트에 PMC를 내줄 수 있습니다.

### 게스트에서 경합을 가르는 순서 — 지연, 크기, 접근 패턴

호스트 관리자는 물리 자원의 병목과 오류를 앞 장들의 방법으로 찾고, 게스트가 한계에 계속 붙어 있는지 확인해 업그레이드를 권할 수 있습니다. 그 이상은 게스트에 로그인하지 않으면 알기 어렵습니다. 그래서 진지한 조사는 게스트 쪽에서 이어집니다.

게스트에서 먼저 바꿔야 할 것은 지표입니다. 디스크와 네트워크 장치가 가상이므로 %busy 같은 사용률은 밑의 실제 장치를 모르면 해석하기 어렵습니다. 대신 지연을 봅니다. 지연은 가상화, 한계, 다른 테넌트가 모두 섞인 결과로 장치가 어떻게 응답하는지를 보여 줍니다. 보이지 않는 한계나 이웃 경합 때문에 자원이 끝까지 쓰이지 않을 수도 있으므로, 한계와 경합은 I/O 지연과 CPU 스케줄링 지연의 증가로 추정합니다. 이 지연은 syscall 층에서도, 게스트 커널에서도 잴 수 있습니다.

원서 저자가 디스크·네트워크 경합을 게스트에서 가를 때 쓰는 순서는 이렇습니다.

1. biosnoop 출력을 기록하고, I/O 순서를 따라가며 지연 이상치가 있는지 찾습니다.
2. 이상치가 I/O 크기로 설명되는지 봅니다. 큰 I/O는 원래 느립니다.
3. 접근 패턴으로 설명되는지 봅니다. 예를 들어 쓰기 flush 뒤에 줄 선 읽기는 느려집니다.
4. 둘 다 아니라면 물리 경합이나 장치 문제일 가능성이 큽니다.

제공자가 다른 테넌트를 알아볼 수 없게 가린 물리 자원 사용 정보를 SNMP나 클라우드 API로 내주면, 게스트 쪽에서 이 추정을 확인할 수 있습니다. 원서는 그런 수단이 있는 것을 이상적이라 봅니다.

> 관측의 핵심 대비는 *호스트는 자원, 게스트는 커널* 입니다. 호스트는 물리 자원을 게스트별로 보지만 게스트 내부는 못 보고, 게스트는 자체 커널이라 커널 추적이 다 되지만 물리 자원은 추론만 합니다. 이것이 컨테이너(11-03)와 다른 점입니다. VM 게스트는 커널 추적 도구가 다 동작하지만, 컨테이너 게스트는 보통 커널을 분석할 수 없습니다. 게스트에서 물리 자원이 안 보여 "noisy neighbor 탓"으로 돌리기 쉬우므로, 지연을 크기·접근 패턴으로 먼저 설명해 보고 남는 것만 경합으로 봅니다.

4. KVM 게스트에서 메모리 한계와 CPU 한계는 각각 어떻게 걸리고, 게스트 관리자에게는 무엇으로 보입니까? 이어서, 어떤 게스트의 vmstat `st` 가 5%에서 60%로 뛰고 `us` 가 그만큼 줄었습니다. 가능한 원인 셋을 대 봅니다. (→ §4·§5)
5. VM 게스트에서 물리 시스템은 얼마나 보입니까? 이어서, 게스트의 biosnoop 로그에서 4KB 읽기 하나가 85ms 걸렸고, 그 직전에 쓰기 flush는 없었으며 주변 4KB 읽기는 1ms 안팎이었습니다. 이 이상치를 어떻게 판정합니까? (→ §5)



## 정답 (자답 후 펼치기)

> 먼저 답한 뒤 읽습니다. 판단 근거와 흔한 오해를 함께 적습니다.

### 정답 1 — 두 구성과 현대 하드웨어 가상화의 오버헤드

Config A는 하이퍼바이저가 프로세서 위에서 직접 돌고 dom0 같은 특권 도메인이 관리합니다. 반면 Config B는 호스트 OS 커널이 하이퍼바이저를 실행합니다. 호스트 커널이 vCPU를 다른 프로세스와 함께 스케줄링합니다. Nitro에서는 CPU-bound 실행이 베어메탈과 거의 같습니다. 프로세서·네트워크·스토리지·인터럽트·타이머에 하드웨어 지원이 있어 I/O 프록시 단계가 사라집니다. 남는 것은 guest exit가 일어나는 순간의 비용, 게스트마다 커널을 두는 메모리 비용, 그리고 다른 테넌트와의 경합입니다. 대표 오해는 "베어메탈급"을 오버헤드 0으로 읽는 것입니다.

### 정답 2 — exit 횟수와 시간

첫 VM은 exit 자체가 적고 그 대부분이 HLT라 원서의 기준대로 꽤 idle 한 게스트입니다. 둘째 VM은 exit가 많고 I/O 명령과 인터럽트가 대부분이라 가상 NIC·디스크로 I/O 중일 가능성이 큽니다. 두 VM 모두 Time%에서 HLT가 큰 것은 halt exit 하나가 다음 인터럽트까지 이어지기 때문입니다. Time%만 봤다면 둘을 똑같이 "halt가 대부분"으로 읽어 I/O 중인 둘째 VM을 놓칩니다. 대표 오해는 Time%가 큰 exit를 곧 비싼 오버헤드로 보는 것입니다.

### 정답 3 — pass-through 와 SR-IOV

원서 기준으로 PCI pass-through가 선택지 중 최고 성능을 냅니다. 대신 장치를 한 게스트가 독점해 여러 테넌트가 나눠 쓸 수 없고 라이브 마이그레이션도 복잡해집니다. SR-IOV는 그 유연성 문제를 풀려고 나온 기술로, 하드웨어 가상화로 장치를 여러 게스트에 나눠 주면서 직접 접근을 유지합니다. 그러니 "SR-IOV가 더 빠르다"가 아니라 "성능을 크게 잃지 않으면서 공유를 되찾았다"가 맞는 설명입니다. 두 방식 모두 게스트 I/O가 하이퍼바이저 경로를 건너뛰므로 호스트 iostat 에 나타나지 않을 수 있고, 운영자는 PMC로 추론해야 합니다.

### 정답 4 — 한계가 걸리는 방식과 steal

메모리 한계는 게스트 설정으로 걸립니다. 게스트는 정해진 양만 봅니다. 고갈되면 게스트 커널이 스스로 페이징·스와핑을 하므로 관리자에게는 평범한 메모리 부족으로 보입니다. balloon 이 부풀면 쓸 수 있는 양이 더 줄어듭니다. CPU 한계는 vCPU 수로 거칠게, 호스트 cgroup CPU bandwidth로 세밀하게 걸리고, 게스트에는 vCPU 수와 steal로 보입니다. steal 이 뛴 원인 후보는 다른 테넌트의 CPU 사용, 하이퍼바이저가 내 게스트의 I/O를 처리하는 데 쓴 시간, 인스턴스 유형에 따른 throttle 셋입니다. 대표 오해는 steal 을 곧 noisy neighbor로 읽는 것입니다.

### 정답 5 — 게스트의 물리 관측과 biosnoop 이상치

게스트에서는 가상 장치와 그 사용만 보이고 물리 자원은 거의 보이지 않습니다. 대신 자체 커널이 있어 perf·Ftrace·BPF 가 모두 동작하므로, 가상 장치의 지연은 자세히 잴 수 있습니다. 이상치는 크기로 설명되지 않습니다. 주변과 같은 4KB이기 때문입니다. 직전에 쓰기 flush가 없어 접근 패턴으로도 설명되지 않습니다. 둘 다 아니므로 원서의 순서대로 물리 경합이나 장치 문제일 가능성이 크다고 판정합니다. 대표 오해는 첫 이상치를 보자마자 이웃 탓으로 돌리는 것입니다. 크기와 패턴을 먼저 배제해야 그 판정에 근거가 생깁니다.
