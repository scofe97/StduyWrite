# 주고받는 일은 결국 몇 개의 명령으로 줄어든다

---

> 7장 노트의 마지막 편으로, 스택 꼭대기인 애플리케이션 계층과 그 위에서 원격 기계를 다루는 명령을 다룹니다. 웹·SSH·파일 전송·원격 마운트·패킷 캡처가 차례로 나옵니다.

## 핵심 요약

> 이 구간이 매달린 생각은 **명세를 알면 도구의 옵션과 실패 메시지가 저절로 설명된다**는 것입니다. URI 의 구조가 `curl` 의 동작을, SSH 의 신뢰 모델이 첫 접속 화면을, `rsync` 의 비교 기준이 두 번째 전송을 설명합니다.

웹의 핵심 구성요소는 셋입니다. 자원의 위치를 가리키는 **URL**, 그 자원과 주고받는 방법인 **HTTP**, 페이지 요소를 정의하는 **HTML** 입니다. 저자는 IETF·W3C 명세를 직접 읽고 무엇이 벌어지는지 이해하려 애쓰라고 강하게 권합니다. 웹을 십 년 가까이 쓰고 만든 뒤인 2006년에야 W3C 활동을 하며 이것을 진지하게 받아들였고 그 보상이 컸다고 적습니다.

이 편의 나머지는 그 위에서 도는 일들입니다. SSH 로 원격 기계에 로그인하고 `scp`·`rsync`·`aws s3` 로 파일을 주고받습니다. NFS·SMB 로 중앙의 저장소를 마운트하고 `tshark` 로 선 위를 지나가는 패킷을 들여다봅니다.



## 학습 목표

> 이 구간을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. URI 한 줄을 다섯 부분으로 가르고, 프래그먼트가 서버로 가지 않는 이유와 그 귀결을 말할 수 있습니다.
2. `curl` 의 종료 코드로 요청이 어느 층에서 끊겼는지 가르고, 그다음 볼 것을 순서대로 댈 수 있습니다.
3. SSH 접속에서 서버와 사용자가 각각 무엇으로 자기를 증명하는지, TOFU 와 CA 서명 방식의 값과 대가를 말할 수 있습니다.
4. 복사·동기화·마운트를 사본의 위치로 가르고, `scp` 와 `rsync` 가 두 번째 전송에서 갈리는 이유를 비교 기준으로 설명할 수 있습니다.
5. 고급 도구들이 스택의 어느 층을 보는지 구분하고, `tshark` 출력 한 줄에서 네 층의 정보를 가려낼 수 있습니다.

아래는 이 문서를 읽는 순서로 이은 지도입니다. 칸마다 절 번호와 그 절이 답하는 물음을 적었습니다. 색이 붙은 칸이 이 노트의 제목이 가리키는 자리입니다.

![7장 마지막 구간의 전체 지도](./_assets/07-03.chapter-overview.svg)



## 이 문서가 다루지 않는 것

> 저자가 스스로 그은 선과, 노트를 나누며 생긴 경계를 함께 적습니다.

- 링크·인터넷 계층 → [첫 노트](./07-01.%EA%B2%B0%EA%B5%AD%EC%9D%80%20%EC%84%A0%EA%B3%BC%20%EA%B3%B5%EA%B8%B0%EB%A5%BC%20%ED%83%80%EA%B3%A0%20%EB%8B%A4%EB%8B%88%EB%8A%94%20%EB%B9%84%ED%8A%B8%EB%8B%A4.md)가 다룹니다
- 전송 계층과 DNS → [둘째 노트](./07-02.%ED%8F%AC%ED%8A%B8%EA%B0%80%20%EC%9E%88%EC%96%B4%EC%95%BC%20%EC%84%9C%EB%B9%84%EC%8A%A4%EB%A5%BC%20%EA%B0%80%EB%A6%AC%ED%82%AC%20%EC%88%98%20%EC%9E%88%EA%B3%A0%20%EC%9D%B4%EB%A6%84%EC%9D%B4%20%EC%9E%88%EC%96%B4%EC%95%BC%20%EC%82%AC%EB%9E%8C%EC%9D%B4%20%EA%B8%B0%EC%96%B5%ED%95%9C%EB%8B%A4.md)가 다룹니다
- JavaScript 와 CSS 와 단일 페이지 앱 → 책의 범위를 넘는다고 저자가 밝힙니다
- DHCP 서버의 설치와 관리, Samba 설정의 상세 → 이름과 `dhcpdump` 만 다룹니다
- 명령의 옵션과 실행 예 → 절마다 링크한 명령 참조 시트가 정본입니다



## 1. 웹의 세 구성요소와 HTTP 세대

> 웹은 URL·HTTP·HTML 셋으로 이루어지고, HTTP 는 세대마다 왕복을 기다리는 방식이 다릅니다. 무엇이 어떤 순서로 오가는지 알면 응답이 늦을 때 어디를 볼지 정해집니다.

`curl` 로 주소 하나를 두드렸는데 응답이 늦습니다. 이름이 늦게 풀렸는지, 앞 요청에 막혔는지, 패킷 하나가 빠져 연결 전체가 섰는지 모르면 어디부터 볼지 막힙니다.

**URL** 은 웹에서 자원의 정체와 위치를 함께 정의합니다. 자원은 정적인 페이지일 수도 있고 내용을 그때그때 만드는 프로세스일 수도 있습니다. 일반 문법은 다음 절의 RFC 3986 이 정합니다.

**HTTP** 는 그 URL 로 접근한 자원과 어떻게 주고받을지를 정하는 애플리케이션 계층 프로토콜입니다. 핵심 개념은 셋입니다. **메서드**는 읽기의 `GET`·쓰기의 `POST` 처럼 CRUD 같은 인터페이스를 정합니다. **자원 명명**은 URL 을 어떻게 짓는지를 정합니다. **상태 코드**는 2xx 성공, 3xx 리다이렉트, 4xx 클라이언트 오류, 5xx 서버 오류입니다.

지금은 메서드·상태 코드 같은 의미를 RFC 9110 이 정합니다. 선 위의 형식은 버전마다 따로라 HTTP/1.1 은 RFC 9112, HTTP/2 는 RFC 9113, HTTP/3 은 RFC 9114 입니다. 넷 다 2022년 6월에 나왔습니다.[^http-rfcs]

**HTML** 은 처음에 W3C 명세였고 지금은 WHATWG 가 관리하는 살아 있는 표준입니다. 헤더나 입력 같은 페이지 요소를 정의합니다.

세 HTTP 세대는 같은 의미를 다른 방식으로 실어 나릅니다. 갈리는 지점은 응답 하나가 늦거나 패킷 하나가 빠졌을 때 나머지가 기다리느냐입니다.

![왕복 대기를 줄이려는 시도 넷 — 세대마다 겹치게 한 것과 남는 병목이 다릅니다](./_assets/07-03.roundtrip-generations.svg)

가장 아래층의 시도는 HTTP 보다 오래됐습니다. TCP 는 ACK 를 기다리지 않고 윈도우 크기만큼 세그먼트를 밀어 넣습니다.

HTTP/1.1 은 1997년의 첫 HTTP/1.1 명세(RFC 2068)부터 파이프라이닝을 두었습니다. 응답을 기다리지 않고 요청을 이어 보내는 방식입니다. 다만 서버가 받은 순서대로 응답해야 해서 앞 응답이 늦으면 뒤가 막힙니다. 그래서 클라이언트는 연결을 여럿 엽니다.[^pipelining]

HTTP/2 는 한 연결 위에서 여러 메시지를 프레임 단위로 섞어 보내 이 막힘을 풀었습니다. 프레임마다 스트림 ID 를 붙였기 때문에 응답 순서가 자유로워졌습니다. 그래도 모두 TCP 한 줄 위라 패킷 하나가 빠지면 그 패킷과 무관한 스트림까지 함께 섭니다.[^h2-hol] HTTP/3 은 그 줄을 스트림마다 따로 신뢰성을 주는 QUIC 으로 바꿨습니다.[^h3-quic]



## 2. URI 한 줄 뜯어보기

> URL 은 URI 의 특수한 경우이고, URI 의 일반형을 알면 주소창의 문자열이 부분마다 누구에게 가는지 보입니다. 특히 `#` 뒤는 서버에 가지 않습니다.

![URI 다섯 부분과 authority 안의 셋](./_assets/07-03.uri-parts.svg)

RFC 3986 은 URI 를 `URI = scheme ":" hier-part [ "?" query ] [ "#" fragment ]` 로 정의합니다. 사용자 정보는 authority 안에 있어 `authority = [ userinfo "@" ] host [ ":" port ]` 입니다.[^rfc3986] 그래서 HTTP URL 은 `http://michaelh:12345678@example.com:4242/this/is/the/way?orisit=really#anchor` 처럼 스킴이 맨 앞에 오고 사용자 정보는 `//` 뒤, 호스트 앞에 붙습니다. 부분은 이렇습니다.

| 부분 | 예 | 뜻 |
|---|---|---|
| scheme | `http` | URL 스킴. 그 뜻을 정의하는 IETF 명세가 따로 있습니다 |
| authority | `michaelh:12345678@example.com:4242` | 계층적 이름 부분. HTTP 에서는 사용자 정보·호스트·포트입니다 |
| path | `/this/is/the/way` | 자원의 세부를 나타내는 스킴별 부분 |
| query | `?orisit=really` | 계층적이지 않은 데이터. 선택입니다 |
| fragment | `#anchor` | 이차 자원. HTML 이면 문서의 한 절입니다. 선택입니다 |

호스트는 DNS FQDN 이거나 IP 주소입니다. `http` 의 기본 포트가 80 이라 `example.com:80` 과 `example.com` 은 같은 곳입니다. `user:password` 형식의 사용자 정보는 처음에 기본 인증에 쓰였지만 RFC 3986 이 이미 폐기된 형식으로 적습니다.[^userinfo] HTTP 라면 HTTPS 위에서 제대로 된 인증 장치를 씁니다.

프래그먼트는 **서버로 전송되지 않습니다.** RFC 3986 에 따르면 프래그먼트는 URI 의 스킴별 처리에 쓰이지 않습니다. 참조를 따라가기 전에 나머지에서 떼어져 사용자 에이전트가 혼자 해석합니다.[^fragment] 그래서 브라우저는 `#` 앞까지만 요청으로 보냅니다. 스프링에서 `@RequestParam` 으로 쿼리는 받는데 프래그먼트는 받을 방법이 없고 서버 접근 로그에도 남지 않는 이유가 이것입니다.



## 3. 서버를 띄우고 curl 로 두드리기

> 흐름을 처음부터 끝까지 흉내 내려면 두드릴 서버가 하나 있어야 합니다. 서버를 띄우고 `curl` 로 요청을 보낸 뒤, 실패했을 때 종료 코드로 어느 층에서 끊겼는지 가르는 법까지 봅니다.

`curl` 을 연습하려는데 두드릴 서버가 없으면 첫걸음부터 막힙니다. 디렉토리 내용만 서비스하는 HTTP 서버는 파이썬이나 `netcat` 으로 쉽게 띄울 수 있습니다.

```bash
# 현재 디렉토리를 그대로 HTTP 로 서비스한다
python3 -m http.server
```

```bash
Serving HTTP on :: port 8000 (http://[::]:8000/) ...
::ffff:127.0.0.1 - - [21/Sep/2021 08:53:53] "GET / HTTP/1.1" 200 -
```

내장 모듈 `http.server` 가 포트 8000 에서 현재 디렉토리를 서비스합니다. 마지막 줄은 루트(`/`)에 대한 요청이 처리됐다는 기록입니다. 그 `200` 이 앞 절의 2xx 범위입니다.

정적 서비스보다 더 나아가려면 저자는 NGINX 같은 제대로 된 웹 서버를 권하며 Docker 로 돌리는 예를 답니다.

```bash
# NGINX 컨테이너로 현재 디렉토리를 정적 서비스한다
docker run --name mywebserver \
    --rm -d \
    -v "$PWD":/usr/share/nginx/html:ro \
    -p 8042:80 \
    nginx:1.21    # --rm 종료 시 삭제, -d 데몬
```

`-v` 는 현재 디렉토리를 NGINX 의 내용 디렉토리로 붙이는 5장의 바인드 마운트입니다. `-p 8042:80` 은 컨테이너 안의 잘 알려진 포트 80 을 호스트의 등록된 구간 포트 8042 로 내줍니다. `$PWD` 는 bash 에서 현재 디렉토리이고 Fish 에서는 `(pwd)` 를 씁니다.

이제 `curl` 로 그 서버를 두드립니다.

```bash
# 방금 띄운 서버를 두드려 본문을 받는다
curl localhost:8000
```

```bash
<!DOCTYPE HTML PUBLIC "-//W3C//DTD HTML 4.01//EN" "http://www.w3.org/TR/html4/strict.dtd">
<html>
<head>
<meta http-equiv="Content-Type" content="text/html; charset=utf-8">
<title>Directory listing for /</title>
</head>
<body>
<h1>Directory listing for /</h1>
<ul>
<li><a href="app.yaml">app.yaml</a></li>
<li><a href="Dockerfile">Dockerfile</a></li>
<li><a href="gh-user-info.sh">gh-user-info.sh</a></li>
...
</ul>
</body>
```

저자가 자주 쓴다고 꼽는 옵션은 일곱입니다. 상세 출력 `-v`, 진행 표시를 끄는 `-s`, 리다이렉트를 따라가는 `-L`, 파일로 저장하는 `-o` 가 있습니다. 최대 대기 시간 `-m`, 헤더만 받는 `-I`, HTTPS 검증을 건너뛰는 `-k` 도 있습니다.

`-I` 는 HEAD 메서드를 보내는데 모든 서버가 모든 경로에서 HEAD 를 지원하지는 않습니다. `-v` 출력에서 `>` 로 시작하는 줄은 `curl` 이 보낸 헤더, `<` 는 받은 헤더, `*` 는 `curl` 이 덧붙인 진행 정보입니다.[^curl-verbose] `curl` 이 없으면 더 제한적이지만 간단한 요청에는 충분한 `wget` 을 씁니다.

### 종료 코드로 끊긴 층 가르기

`-v` 로 파고들기 전에 먼저 할 일은 **어느 층에서 끊겼는지 가르는 것**입니다. `curl` 은 실패할 때마다 다른 종료 코드를 남깁니다. 그 코드가 층을 가리킵니다.

![안 될 때 curl 의 종료 코드가 어느 층인지 가른다](./_assets/07-03.curl-exit-triage.svg)

아래는 이 노트를 쓰며 직접 재 본 셋입니다.

```bash
# 없는 이름을 물어본다 — 이름이 안 풀린다
curl -s -o /dev/null -w '%{http_code}\n' http://no-such-host.invalid/ ; echo "exit=$?"
```

```bash
curl: (6) Could not resolve host: no-such-host.invalid
exit=6
```

```bash
# 살아 있는 기계의 닫힌 포트를 두드린다 — 즉시 거절당한다
curl -s http://127.0.0.1:9 ; echo "exit=$?"
```

```bash
curl: (7) Failed to connect to 127.0.0.1 port 9 after 0 ms: Couldn't connect to server
exit=7
```

```bash
# 대답 없는 주소로 나간다 — 한도까지 기다린다
curl -s -m 6 http://10.255.255.1/ ; echo "exit=$?"
```

```bash
curl: (28) Connection timed out after 6005 milliseconds
exit=28
```

| 종료 코드 | 메시지 | 어디서 끊겼나 | 다음에 볼 것 |
|:--:|---|---|---|
| 6 | Could not resolve host | **이름**. 전송은 시작도 못 했습니다 | `dig`·`/etc/resolv.conf`·검색 도메인 |
| 7 | Failed to connect ... after 0 ms | **포트**. 길은 있고 그 포트만 안 열렸습니다 | 상대에서 `ss -tlnp` |
| 28 | Connection timed out after 6005 ms | **무응답**. 길이 없거나 중간이 삼켰습니다 | 라우팅·방화벽 |

**`0 ms` 와 `6005 ms` 가 둘을 가릅니다.** 즉시 실패했다면 상대가 무언가 **대답한** 것입니다. TCP 로 치면 RST 가 돌아온 셈입니다. 그러려면 패킷이 거기까지 갔다 와야 합니다. 한도를 다 채우고 끝났다면 아무도 대답하지 않은 것입니다. 길이 없었거나 중간의 무엇이 조용히 버렸다는 뜻입니다.

가른 뒤의 순서는 이렇습니다.

1. `curl` 로 **부류**를 가릅니다. 6 인지 7 인지 28 인지.
2. 28 이면 `route -n get <주소>` 로 **길이 있는지** 봅니다. 길이 없으면 라우팅 문제로 끝납니다.
3. 길이 있으면 `ping` 으로 **상대가 살아 있는지** 봅니다.
4. 그래도 모르면 `traceroute` 로 **어디까지 갔는지** 좁힙니다. 멈춘 홉이 범인 근처입니다.

넷이 다 정상인데 연결이 늘어지면 마지막 후보는 **accept 큐 포화**입니다. 아래 「accept 큐 포화와 ss 의 LISTEN 행」이 다룹니다.

### 종료 코드 6 과 dig 의 status

종료 코드 6 을 받았다고 이름이 없다는 뜻은 아닙니다. `curl` 은 리졸버에게서 「못 풀었다」는 결과 하나만 받습니다. 그래서 이름이 정말 없을 때, 리졸버가 조회에 실패했을 때, 리졸버에 닿지도 못했을 때가 모두 6 으로 옵니다. `dig` 는 리졸버가 돌려준 결과 코드를 헤더의 `status:` 에 찍어 셋을 가릅니다.

```bash
# 없는 이름 · 서명 검증에 실패하는 이름 · 대답 없는 리졸버를 차례로 묻는다
dig @1.1.1.1 no-such-host.invalid +noall +comments | grep status

dig @1.1.1.1 dnssec-failed.org +noall +comments | grep status

dig @10.255.255.1 example.com +time=2 +tries=1 | tail -1
```

```bash
;; ->>HEADER<<- opcode: QUERY, status: NXDOMAIN, id: 24577
;; ->>HEADER<<- opcode: QUERY, status: SERVFAIL, id: 24514
;; connection timed out; no servers could be reached
```

| `dig` 가 보인 것 | 뜻 | 다음에 볼 것 |
|---|---|---|
| `status: NXDOMAIN` | 그런 이름이 없습니다. 리졸버는 제 일을 했습니다 | 오타·검색 도메인·레코드 등록 여부 |
| `status: SERVFAIL` | 리졸버가 답을 만들지 못했습니다 | 권한 서버 상태·DNSSEC 서명 |
| `connection timed out` | 리졸버에 닿지 못했습니다 | `/etc/resolv.conf` 의 서버 주소·그쪽으로 가는 길 |

`SERVFAIL` 은 어느 리졸버에 물었느냐에 따라 달라집니다. 2026-10-03 에 `dnssec-failed.org` 를 서명을 검증하는 `1.1.1.1` 에 물으면 `SERVFAIL` 이었습니다. 이 맥의 기본 리졸버에 물으면 `NOERROR` 로 주소가 돌아왔고 `curl` 도 0 으로 끝났습니다. 그래서 `@서버` 로 문제의 기계가 쓰는 바로 그 리졸버를 지정해야 같은 장면을 봅니다.

### TCP 가 붙은 뒤에 끊기는 자리 — TLS 와 응답

6·7·28 은 모두 TCP 연결이 맺어지기 전에 끝나는 실패입니다. 연결이 맺어진 뒤에도 HTTPS 의 TLS 핸드셰이크·인증서 검증과, 그 위의 HTTP 응답이 남습니다. 2026-10-03 에 로컬 서버 셋을 세워 curl 8.7.1 로 이 층의 실패를 재현했습니다. 평문 HTTP, 응답 없이 끊는 소켓, 자체 서명 인증서의 `openssl s_server` 입니다.

```bash
# 평문 HTTP 포트에 https 로 붙는다 — TLS 핸드셰이크가 깨진다
curl -sS https://127.0.0.1:18080/ ; echo "exit=$?"

# 자체 서명 인증서를 내미는 서버에 붙는다 — 인증서 검증이 깨진다
curl -sS -o /dev/null https://localhost:18443/ ; echo "exit=$?"
```

```bash
curl: (35) LibreSSL/3.3.6: error:1404B42E:SSL routines:ST_CONNECT:tlsv1 alert protocol version
exit=35
curl: (60) SSL certificate problem: self signed certificate
exit=60
```

```bash
# -f 없이 404 를 받는다 — 응답이 왔으니 curl 은 성공으로 친다
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:18080/nope ; echo "exit=$?"

# -f 를 켜고 503 을 받는다
curl -sS -f -o /dev/null http://127.0.0.1:18080/boom ; echo "exit=$?"

# 요청을 읽고 아무 말 없이 닫는 서버에 붙는다
curl -sS http://127.0.0.1:18081/ ; echo "exit=$?"

# 자기 자신으로 돌려보내는 주소를 -L 로 따라간다
curl -sS -L --max-redirs 5 -o /dev/null http://127.0.0.1:18080/loop ; echo "exit=$?"
```

```bash
404
exit=0
curl: (22) The requested URL returned error: 503
exit=22
curl: (52) Empty reply from server
exit=52
curl: (47) Maximum (5) redirects followed
exit=47
```

| 종료 코드 | 메시지 | 어디서 끊겼나 | 다음에 볼 것 |
|:--:|---|---|---|
| 35 | SSL connect error | TLS 핸드셰이크. 연결은 됐지만 TLS 로 말이 안 통했습니다 | 포트가 정말 TLS 인지, `openssl s_client -connect` |
| 60 | SSL certificate problem | 인증서 검증. 핸드셰이크는 됐지만 상대를 믿을 근거가 없습니다 | 인증서 체인·만료·이름, 내 CA 목록 |
| 22 | The requested URL returned error | HTTP 응답. 서버가 400 이상을 돌려줬습니다. `-f` 를 켰을 때만 나옵니다 | 상태 코드와 서버 로그 |
| 52 | Empty reply from server | HTTP 응답. 연결은 받고 아무것도 안 보냈습니다 | 앱이 요청 중에 죽었는지, 앞단 프록시 |
| 47 | Maximum (5) redirects followed | HTTP 응답. `-L` 로 따라가다 한도에 걸렸습니다 | `curl -v` 로 `Location` 이 어디를 도는지 |

가장 조심할 줄은 22 입니다. `-f` 가 없으면 404 를 받아도 종료 코드는 0 입니다. 응답이 왔으면 전송은 성공했다고 보는 것이 `curl` 의 기본입니다. man 페이지도 22 를 "This return code only appears if -f, --fail is used." 로 못 박습니다.[^curl-exit] 그래서 스크립트에서 성패를 가를 때는 `-f` 를 켜거나 `-w '%{http_code}'` 로 상태 코드를 따로 받습니다.

35 도 메시지만 보고 짐작하면 틀립니다. 위의 `protocol version` 은 TLS 버전이 맞지 않았다는 뜻이 아닙니다. TLS 를 모르는 평문 서버가 TLS 첫 메시지에 엉뚱한 바이트를 돌려줬다는 뜻입니다.

### accept 큐 포화와 ss 의 LISTEN 행

듣는 소켓에는 큐가 둘 붙습니다. 핸드셰이크가 끝나지 않은 연결이 기다리는 SYN 큐와, 핸드셰이크를 마치고 앱의 `accept()` 를 기다리는 accept 큐입니다. `listen()` 의 backlog 는 뒤쪽의 길이입니다. 앞쪽의 최대 길이는 `/proc/sys/net/ipv4/tcp_max_syn_backlog` 가 따로 정합니다.[^listen-backlog]

연결은 핸드셰이크가 끝나는 순간 이미 `ESTABLISHED` 입니다. `accept()` 는 상태를 바꾸지 않고 그 연결의 파일 디스크립터를 앱에 건넬 뿐입니다. 그래서 앱이 멈춰 `accept()` 를 안 불러도 클라이언트 쪽에서는 연결이 성공한 것으로 보입니다.

accept 큐가 얼마나 찼는지는 `ss -tln` 의 LISTEN 행이 보여 줍니다. 듣는 소켓에 한해 `Recv-Q` 는 큐에 쌓인 연결 수, `Send-Q` 는 backlog 최대치입니다.[^tcp-diag] 두 칸을 읽는 법은 [ss 참조 시트 「소켓 큐 읽기」](../../docs/cmd/net/ss.md#소켓-큐-읽기)에 있습니다. 2026-10-03 에 OrbStack 의 Ubuntu 에서 서버를 띄웠습니다. backlog 3 으로 듣기만 하고 `accept()` 는 부르지 않는 서버입니다. 그 서버에 클라이언트 여섯을 붙여 봤습니다.

```bash
# backlog 3 · accept 안 함 서버에 클라이언트 여섯이 붙은 뒤 듣는 소켓을 본다
ss -tln "sport = :19090"

# 클라이언트 쪽 연결 상태를 센다
ss -tn "dport = :19090" | awk 'NR>1{print $1}' | sort | uniq -c

# 이 상태에서 curl 을 하나 더 보낸다
curl -s -m 5 -o /dev/null http://127.0.0.1:19090/ ; echo "curl exit=$?"
```

```bash
State  Recv-Q Send-Q Local Address:Port  Peer Address:Port
LISTEN 4      3          127.0.0.1:19090      0.0.0.0:*
      4 ESTAB
      2 SYN-SENT
curl exit=28
```

`Recv-Q` 4 가 `Send-Q` 3 을 넘었습니다. 이 실측에서 리눅스는 backlog 보다 하나를 더 받은 뒤에 막았습니다. 그래서 `Recv-Q` 가 `Send-Q` 와 같거나 넘으면 포화로 읽습니다. `accept()` 를 한 번도 안 불렀는데 넷은 `ESTAB` 입니다. 자리를 못 얻은 둘은 `SYN-SENT` 에 머물며 SYN 을 다시 보내고 있었습니다.

포트가 열려 있는데도 `curl` 은 7 이 아니라 28 로 끝났습니다. 큐가 넘칠 때 연결을 리셋하는 `tcp_abort_on_overflow` 는 기본이 꺼져 있습니다(이 기계에서도 `0`).[^abort-overflow] 그래서 커널이 RST 없이 조용히 버리고 밖에서는 아무도 대답하지 않은 것과 같아 보입니다. 28 을 받았는데 길도 상대도 멀쩡하면 상대 기계에서 이 행을 보는 것이 순서의 마지막 칸입니다.



## 4. SSH — 안전하지 않은 망 위에서 안전하게

> SSH 는 서버가 자기를 증명하는 걸음과 사용자가 자기를 증명하는 걸음을 따로 둡니다. 뒤에 나올 파일 전송 도구들이 전부 그 위에 얹힙니다.

원격 서버에 들어가야 하는데 그 사이의 망은 믿을 수 없습니다. 비밀번호가 평문으로 지나가면 중간의 누구나 가로채 그 기계에 들어올 수 있습니다.

SSH 는 안전하지 않은 네트워크 위에서 네트워크 서비스를 안전하게 제공하는 암호학적 프로토콜이고 `telnet` 을 대체합니다. 원격 로그인과 기계 사이의 데이터 이동에 씁니다.

```bash
# 신원 파일을 명시해 원격에 로그인한다
ssh -i ~/.ssh/lml.pem ec2-user@63.32.106.149
```

`-i` 는 비밀번호 대신 쓸 신원 파일(개인 키)입니다. 뒤는 `사용자명@호스트` 형식의 대상입니다. 저자는 키가 기본 위치인 `~/.ssh` 에 있어 생략해도 되지만 명시하는 것이 좋은 관례라고 봅니다. `ssh` 의 옵션과 실행 예는 [ssh 참조 시트](../../docs/cmd/ssh/ssh.md)에 있습니다.

저자가 가장 힘주어 말하는 팁은, SSH 서버를 연다면 **비밀번호 인증을 반드시 끄라**는 것입니다. 사용자는 키 쌍을 만들어 공개 키를 넘깁니다. 서버 관리자는 그것을 `~/.ssh/authorized_keys` 에 더해 키로만 로그인하게 합니다. 서버 쪽 설정은 [sshd 참조 시트 「비밀번호 인증 거절 확인하기」](../../docs/cmd/ssh/sshd%C2%B7sshd_config.md#비밀번호-인증-거절-확인하기)에 있습니다.

나머지 팁은 짧습니다. 의사 tty 를 강제하려면 `ssh -tt` 를 씁니다. 화면이 깨지면 접속 뒤 `export TERM=xterm` 을 칩니다. 세션 타임아웃은 `~/.ssh/config` 의 `ServerAliveInterval`·`ServerAliveCountMax` 로 잡습니다. 키 권한 문제를 배제했는데도 안 되면 `-v`(더 자세히는 `-vvv`)로 띄웁니다.

![서버를 믿는 걸음과 나를 증명하는 걸음은 다르다](./_assets/07-03.ssh-handshake.svg)

### 호스트 키 확인과 TOFU

인증은 양방향입니다. 위 팁은 모두 **사용자가 자기를 증명하는** 이야기이고 그보다 먼저 **서버가 자기를 증명하는** 걸음이 있습니다.

그 걸음은 키 교환 안에 있습니다. 서버는 키 교환 응답에 자기 공개 호스트 키와, 교환 내용의 해시를 호스트 개인 키로 서명한 값을 함께 보냅니다. 클라이언트는 그 키가 정말 그 서버의 키인지 확인하고 서명을 검증합니다.[^kex] 양쪽이 `SSH_MSG_NEWKEYS` 를 보낸 뒤부터 모든 메시지가 새 키로 암호화됩니다.[^newkeys] 사용자 인증은 그 암호화된 채널 위에서 일어납니다. 공개 키 방식이면 사용자의 **개인 키로 만든 서명**을 보냅니다. 서버는 `authorized_keys` 의 공개 키로 검증합니다.[^pubkey]

호스트 키를 확인하려면 클라이언트가 그 서버의 공개 호스트 키를 **미리** 알고 있어야 합니다.[^hostkey] RFC 4251 은 미리 아는 방법으로 둘을 듭니다. 클라이언트가 호스트명과 공개 키의 짝을 로컬 데이터베이스로 들고 있는 방법과, CA 가 그 짝을 인증해 주는 방법입니다. 앞의 것은 중앙 기반도 제삼자의 조율도 필요 없습니다. 대신 짝의 목록을 건사하는 일이 부담이 됩니다.[^trustmodel]

우리가 매일 쓰는 것이 앞의 것입니다. 처음 접속할 때는 확인 없이 호스트 키를 받아 로컬 데이터베이스에 저장합니다. 이후 모든 접속에서는 그 키와 대조합니다.[^tofu] 이 전략에 흔히 붙는 이름이 **TOFU(trust on first use)이고, 그 이름 자체는 RFC 에 나오지 않습니다.** `ssh` 가 첫 접속에서 지문을 보여 주고 `yes` 를 받으면 `~/.ssh/known_hosts` 에 한 줄을 적는 화면이 이것입니다. 다음부터는 조용히 대조하고 다르면 크게 경고합니다. 그 화면은 [ssh 참조 시트 「처음 접속과 호스트 키 확인」](../../docs/cmd/ssh/ssh.md#처음-접속과-호스트-키-확인)에서 재현합니다.

대가는 RFC 가 분명히 적습니다. 이 방식은 수동적인 엿듣기는 막지만 **능동적인 중간자 공격에는 취약해집니다.**[^tofurisk] 취약한 구간은 첫 접속 한 번뿐이지만 그 한 번에 가짜 서버가 끼어들면 뒤의 모든 접속이 가짜 키를 믿습니다.

사람은 그 한 번을 대충 넘깁니다. 지문을 아무 데와도 대조하지 않고 `yes` 를 칩니다. 서버를 재설치해 호스트 키가 바뀌면 **진짜 중간자 공격과 똑같은 경고 화면**이 뜹니다. 대개는 옛 줄을 지우고 다시 `yes` 를 칩니다. 옛 줄을 지우는 `ssh-keygen -R` 은 [ssh-keygen 참조 시트 「known_hosts 정리」](../../docs/cmd/ssh/ssh-keygen%C2%B7ssh-copy-id%C2%B7ssh-agent.md#known_hosts-정리)에 있습니다. 확인 없이 이 명령을 치면 그대로 구멍이 납니다.

제대로 하려면 지문을 **대역 밖에서** 받습니다. RFC 도 지문은 전화나 다른 외부 통신 경로로 쉽게 확인할 수 있다고 적습니다.[^oob] 실무에서는 프로비저닝 로그나 클라우드 콘솔의 시리얼 출력에 찍힌 지문을 받아 화면의 것과 맞춰 봅니다.

### 호스트 키 CA 서명

RFC 4251 이 든 둘째 방법, **CA 가 호스트명과 키의 짝을 인증하는 방식**도 SSH 에 실제로 있습니다. 자체 CA 키로 서버의 호스트 키에 서명하면 클라이언트는 `known_hosts` 에 서버를 한 대씩 적는 대신 CA 공개 키 하나만 믿으면 됩니다.

```bash
# CA 키를 만든다 — 이 하나로 모든 호스트 키에 서명한다
ssh-keygen -t ed25519 -f ssh_host_ca -C "our host CA"

# 서버의 호스트 공개키에 서명해 인증서를 만든다
ssh-keygen -s ssh_host_ca -I db01 -h -n db01.example.com -V +52w ssh_host_ed25519_key.pub

# 클라이언트는 CA 공개키 하나만 알면 된다 (~/.ssh/known_hosts 한 줄)
# @cert-authority *.example.com ssh-ed25519 AAAA...
```

`-h` 는 사용자 인증서 대신 호스트 인증서를 만들라는 뜻입니다. `-I` 는 인증서의 신원 이름입니다.[^hostcert] `known_hosts` 의 `@cert-authority` 표지는 그 줄이 CA 키라는 뜻입니다.[^cert-authority]

- 값은 사이에 한 겹을 두어 아래를 갈아 끼울 수 있게 된 것입니다. 앞 편의 CNAME 과 같은 모양입니다. 서버를 재설치해도 CA 가 서명해 주면 클라이언트는 아무것도 안 고칩니다. 「재설치했더니 중간자 공격과 같은 화면이 뜬다」는 문제가 사라집니다.
- 대가는 CA 키가 단일 실패 지점이 된다는 것입니다. 그 키가 새면 조직의 모든 서버를 위조할 수 있습니다. 그래서 서버가 수천 대인 조직이 이 방식을 씁니다. 몇 대뿐이면 TOFU 가 더 쌉니다. 어느 쪽을 쓸지는 **대수가 정합니다.**

### 키 준비와 접속 설정

키로 접속하려면 `ssh` 앞뒤에 명령이 몇 개 더 필요합니다. `ssh-keygen` 이 키 쌍을 만들고 `ssh-copy-id` 가 공개 키를 원격의 `authorized_keys` 에 붙입니다. 손으로 붙이다 파일 권한을 틀려 로그인이 안 되는 사고를 줄여 줍니다. 개인 키에 암호구를 걸었다면 `ssh-agent` 가 한 번 푼 키를 들고 있어 접속마다 묻지 않게 합니다. 셋의 실행 예는 [ssh-keygen·ssh-copy-id·ssh-agent 참조 시트](../../docs/cmd/ssh/ssh-keygen%C2%B7ssh-copy-id%C2%B7ssh-agent.md)에 있습니다.

`~/.ssh/config` 는 긴 접속 명령을 `ssh db` 같은 별칭 하나로 줄입니다. 그중 `ProxyJump` 는 사설 대역에 있어 바깥에서 닿지 않는 기계에 경유 서버를 지나 한 번의 명령으로 들어가게 합니다. 앞 편의 사설 IP 대역이 이 설정을 필요하게 만듭니다. 별칭은 [ssh 참조 시트 「config 로 접속 이름 만들기」](../../docs/cmd/ssh/ssh.md#config-로-접속-이름-만들기), 경유는 [「점프 호스트 거치기」](../../docs/cmd/ssh/ssh.md#점프-호스트-거치기)가 다룹니다.

SSH 는 사람이 직접 쓰는 도구이면서 다음 절의 파일 전송 도구 안에서 재료로도 쓰입니다.



## 5. 파일을 옮기는 세 가지 길

> 로컬에서 클라우드의 서버로, 혹은 옆 기계로 파일을 옮기는 일은 아주 흔합니다. 한 번 옮기느냐 반복해서 맞추느냐, 원격 서버냐 객체 저장소냐에 따라 도구가 갈리고, 같은 SSH 위의 `scp` 와 `rsync` 도 두 번째 전송에서 갈립니다.

빌드 결과물 하나를 서버에 올릴 때와 데이터 디렉토리를 매일 백업할 때 같은 명령을 쓰면 백업 쪽은 매번 전부 다시 보내느라 시간을 못 아낍니다.

![무엇을 옮기느냐가 도구를 정한다](./_assets/07-03.file-transfer.svg)

**`scp`** 는 secure copy 의 줄임이고 SSH 위에서 동작합니다. 그래서 비밀번호나, 더 낫게는 키 기반 인증이 먼저 갖춰져 있어야 합니다. 실행 예는 [scp·sftp 참조 시트](../../docs/cmd/ssh/scp%C2%B7sftp.md#파일-하나-올리고-내려받기)에 있습니다.

```bash
# 파일 하나를 원격의 홈으로 복사한다
scp copyme ec2-user@63.32.106.149:/home/ec2-user/
```

```bash
copyme                        100%    0     0.0KB/s   00:00
```

**`rsync`** 도 기본은 SSH 위입니다. 더해지거나 바뀐 파일만 복사할 수 있어 디렉토리를 반복해서 맞추거나 백업할 때 씁니다. 목적지는 `user@host:` 형식입니다.

```bash
# 디렉토리를 원격과 맞춘다 — 아카이브·진행 표시·압축
rsync -avz ~/data/ mh9@63.32.106.149:
```

```bash
building file list ... done
./
example.txt

sent 155 bytes  received 48 bytes  135.33 bytes/sec
total size is 10  speedup is 0.05
```

`-a` 는 재귀(`-r`)를 포함한 아카이브 모드로 속성을 보존합니다. `-v` 는 진행을 보이고 `-z` 는 압축합니다. 무엇을 할지 확신이 없으면 실제로 바꾸지 않고 계획만 보이는 `--dry-run` 을 함께 씁니다.

**호스트 뒤의 콜론을 빠뜨리면** `rsync` 는 아무 불평 없이 그 인자를 로컬 경로로 읽습니다. 파일은 원격이 아니라 로컬의 `user@example.com/` 같은 디렉토리에 남습니다. 이 함정은 [rsync 참조 시트 「호스트 뒤 콜론을 빼면」](../../docs/cmd/file/rsync.md#호스트-뒤-콜론을-빼면)에서 재현합니다. 원본 끝 슬래시가 복사 위치를 바꾸는 더 흔한 함정은 [「끝 슬래시 한 글자가 바꾸는 대상」](../../docs/cmd/file/rsync.md#끝-슬래시-한-글자가-바꾸는-대상)에 있습니다.

**`aws s3 sync`** 는 Amazon S3 버킷에서 받을 때 씁니다.

```bash
# 공개 S3 버킷의 내용을 현재 디렉토리로 받는다
aws s3 sync \
    s3://commoncrawl/contrib/c4corpus/CC-MAIN-2016-07/ \
    . \
    --no-sign-request
```

목적지의 점 하나가 현재 디렉토리입니다. `--no-sign-request` 는 공개 버킷이라 인증을 건너뛰라는 뜻입니다. 이 디렉토리에는 8GB 가 넘는 데이터가 있어 대역폭이 아깝지 않을 때만 해 볼 만합니다.

### FTP 와 SFTP 는 다른 프로토콜

FTP(RFC 959)는 아직 쓰이지만 저자는 더는 권하지 않습니다. 안전하지 않고 위의 더 나은 대안이 있기 때문입니다. FTP 는 `scp`·`rsync` 와 달리 SSH 위가 아니라 **자기 규격을 따로 가진 별개의 프로토콜**입니다. 제어 연결에는 **포트 21** 을 씁니다. 파일을 받는 명령이 `RETR`, 보내는 명령이 `STOR` 이고 데이터는 따로 여는 데이터 연결로 흐릅니다.[^ftp] 자격증명과 내용이 **평문으로** 지나가는 것이 안전하지 않다는 말의 실체입니다.

**SFTP 는 FTP 가 아닙니다.** SSH 위에서 도는 별개의 것이라 포트도 22 이고 규격도 다릅니다. man page 가 `ftp(1)` 과 비슷하다고 적는 것은 쓰는 느낌이 닮았다는 뜻입니다.[^sftp] 진짜 FTP 를 TLS 로 감싼 쪽은 **FTPS** 이고 RFC 4217 이 정의합니다.[^ftps]

### 두 번째 전송에서 갈린다

`rsync` 가 무엇을 근거로 「바뀌었다」고 판단하는지가 실무에서 자주 문제가 됩니다.

![두 번째로 보낼 때 무엇이 달라지는가](./_assets/07-03.transfer-second-run.svg)

첫 전송은 둘이 같습니다. 받는 쪽에 아무것도 없으니 전부 보냅니다. 갈리는 것은 두 번째입니다. `scp` 는 비교라는 개념이 없어 **매번 통째로** 다시 보냅니다. `rsync` 는 양쪽을 견주어 보낼 필요가 있는 것만 보냅니다. 기본 비교는 **quick check** 라 부르는 방식으로, 크기나 최종 수정 시각이 달라진 파일을 찾고 둘 다 그대로면 건너뜁니다.[^quickcheck]

`rsync` 는 「지난번에 어디까지 보냈다」를 기억하지 않습니다. 기준 시점을 저장하지 않고 **매번 양쪽의 현재 상태를 견줍니다.** 그래서 중간에 다른 방법으로 파일이 바뀌어도 다음 실행이 알아차리고 받는 쪽에서 파일을 지워도 다시 채웁니다.

비교 방식은 셋이고 각각 값과 대가가 다릅니다.

| 비교 방식 | 무엇을 보는가 | 놓치는 것 | 대가 |
|---|---|---|---|
| quick check (기본) | 크기 + 최종 수정 시각 | 시각을 건드리지 않은 변경 | 거의 없음. 메타데이터만 읽습니다 |
| `-c` (`--checksum`) | 크기가 같은 파일의 체크섬 | 없음 | 양쪽이 파일 전체를 읽어야 합니다 |
| `--size-only` | 크기만 | 크기가 같은 모든 변경 | 가장 쌉니다 |

`-c` 는 크기가 맞는 파일마다 체크섬을 비교하도록 바꿉니다. 체크섬을 만드는 비용은 양쪽이 다 치릅니다.[^checksum] 보낼 것이 없어도 전 파일을 읽어야 하므로 네트워크를 아끼려고 디스크를 쓰는 맞바꿈입니다. 그래서 평소에는 기본값을 씁니다. `-c` 는 수정 시각을 보존하면서 내용을 바꾸는 도구가 파이프라인에 있을 때만 켭니다. 두 경우를 `-i` 출력으로 재현한 것이 [rsync 참조 시트 「바뀐 파일만 보내는 기준과 -c」](../../docs/cmd/file/rsync.md#바뀐-파일만-보내는-기준과--c)입니다.



## 6. 중앙의 저장소를 내 트리에 붙이기

> 같은 파일을 여러 기계에서 써야 할 때 매번 복사해 오는 대신 중앙의 한 곳을 그대로 마운트할 수 있습니다. 복사·동기화와는 사본이 어디에 있느냐가 달라, 오프라인과 동시 쓰기에서 다르게 움직입니다.

NFS 는 네트워크로 중앙의 한 곳에서 파일을 공유하는, 널리 지원되고 널리 쓰이는 방법입니다. 1980년대 초 Sun Microsystems 가 처음 개발했고 RFC 7530 등을 거치며 여러 차례 갱신됐습니다. 보통 클라우드 제공자나 중앙 IT 가 NFS 서버를 관리하므로 할 일은 `nfs-common` 같은 클라이언트 패키지를 설치하는 것뿐입니다.

```bash
# 원격 호스트의 디렉토리를 내 트리에 붙인다
sudo mount nfs.example.com:/source_dir /opt/target_mount_dir
```

이 명령은 5장의 `mount` 그대로입니다. 붙일 것과 트리 안의 자리, 입력 둘을 받습니다. 붙일 것이 로컬 블록 장치가 아니라 원격 호스트의 디렉토리라는 점만 다릅니다. 5장에서 VFS 가 추상화하는 네 갈래 중 7장으로 미뤘던 네트워크 파일시스템이 여기입니다.

AWS·Azure 를 비롯한 클라우드가 NFS 를 서비스로 제공합니다. 저장 공간을 많이 쓰는 앱에 로컬 저장 장치처럼 느껴지는 넉넉한 공간을 주고 미디어 앱이라면 NAS 구성이 더 낫다고 저자는 덧붙입니다. 윈도우 기계와 공유하려면 1980년대 IBM 이 처음 개발한 SMB 를 씁니다. 마이크로소프트 쪽 후속이 CIFS 입니다. 리눅스에서는 보통 표준 윈도우 상호운용 프로그램 모음인 Samba 로 합니다.

### 복사·동기화·마운트의 사본 위치

![사본이 어디에 있느냐가 세 모델을 가른다](./_assets/07-03.copy-sync-mount.svg)

`scp` 는 **사본을 만듭니다.** 옮기고 나면 양쪽에 하나씩 있고 그때부터 둘은 남남입니다. `rsync` 도 사본을 만들되 실행할 때마다 원본에 맞춥니다. 마운트에는 **사본이 아예 없습니다.** 그 디렉토리를 읽을 때마다 바이트가 네트워크를 건너옵니다. 용량을 차지하지 않고 언제나 최신인 대신 접근 하나하나가 왕복입니다.

이 차이가 오프라인에서 드러납니다. 사본이 있는 쪽은 망이 끊겨도 로컬 파일을 그대로 읽습니다. 마운트는 그 디렉토리가 통째로 멈춰 `ls` 한 번에 셸이 붙잡힙니다. 구글 드라이브 같은 동기화 폴더에 익숙하면 NFS 에서 놀라는 자리입니다.

NFS 서버를 세우지 않고 마운트하는 방법도 있습니다. `sshfs` 가 FUSE 로 원격 디렉토리를 붙이므로 §4 의 SSH 접속을 그대로 씁니다.

```bash
# SSH 접속 하나로 원격 디렉토리를 내 트리에 붙인다 — 서버 쪽에 따로 세울 것이 없다
sshfs ec2-user@63.32.106.149:/home/ec2-user /mnt/remote

# 다 쓰면 떼어 낸다
fusermount -u /mnt/remote
```

### NFS 의 close-to-open 과 동시 쓰기

여러 클라이언트가 같은 파일을 볼 때 NFS 가 주는 보장의 이름이 **close-to-open** 입니다. RFC 8881 에 따르면 파일을 **닫을 때** 수정된 데이터가 전부 서버로 쓰입니다. 이후에 그 파일을 **열 때** 변경 속성을 캐시된 값과 견주어 달라졌는지 봅니다.[^cto]

뒤집어 읽으면 보장의 경계가 보입니다. 쓴 쪽이 아직 닫지 않았으면 읽는 쪽은 그 내용을 못 봅니다. 두 클라이언트가 같은 파일을 동시에 열어 두고 주고받는 일은 이 보장 밖입니다.

속성 캐시가 또 다른 층입니다. 리눅스 클라이언트는 크기나 수정 시각을 일반 파일은 최소 3초·최대 60초, 디렉토리는 최소 30초 동안 들고 있습니다.[^accache] `ls -l` 이 방금 바뀐 크기를 안 보여 주는 일이 여기서 나옵니다. 락은 있지만 강제가 아니라 nfs(5) 도 분별 있게 쓰라고 **권할** 뿐입니다.[^nfslock] 앱이 락을 걸지 않으면 마지막에 쓴 쪽이 이깁니다.

그래서 관례가 단순합니다. **읽기 공유는 마음껏 하고 쓰기는 한쪽으로 몰거나 파일을 나눕니다.** 여러 파드가 같은 볼륨에 로그를 쌓는다면 파일 이름에 파드 이름을 넣는 식입니다.



## 7. 층마다 하나씩 있는 고급 도구들

> 연결은 되는데 무엇이 오가는지 직접 봐야 할 때가 있습니다. 저자가 고급으로 묶은 도구들은 보통 사용자의 범위를 넘지만, 각각 스택의 어느 층을 보는지 알면 어떤 증상에 무엇을 꺼낼지 고를 수 있습니다.

![고급 도구가 각각 스택의 어느 층을 보는가](./_assets/07-03.advanced-tools.svg)

DHCP 와 NTP 는 UDP 위에서 돌지만 그 자체는 애플리케이션 계층 프로토콜입니다. UDP 를 쓴다는 사실이 그것을 전송 계층으로 만들지는 않습니다. 아래는 같은 도구들을 **하는 일**로 다시 묶은 것이라 `dhcpdump` 처럼 도식에서는 프로토콜의 층에, 여기서는 캡처 도구로 놓이는 것이 있습니다.

### 등록 정보 조회 — whois · geoiplookup

이 둘은 선 위의 트래픽이 아니라 **누군가 등록해 둔 장부**를 조회합니다. `whois` 는 whois 디렉토리 서비스의 클라이언트로, 도메인의 등록과 사용자 정보를 묻습니다. 등록기관에 돈을 내면 그 정보를 비공개로 할 수 있습니다.

```bash
# 도메인 뒤에 누가 있는지 등록 정보를 묻는다
whois ietf.org
```

```bash
% IANA WHOIS server
refer:        whois.pir.org
domain:       ORG
organisation: Public Interest Registry (PIR)
address:      Reston, VA 20190
address:      United States
...
```

`geoiplookup` 은 IP 를 지리적 영역에 대응시킵니다. 주소 하나를 들고 누군가 정리해 둔 표를 찾아본다는 점이 `whois` 와 같습니다.

### 주소·시간 프로토콜 — DHCP · NTP

**DHCP** 는 호스트에 IP 주소를 자동으로 배정하는 클라이언트-서버 프로토콜이라 네트워크 장치를 손으로 설정할 필요를 없앱니다. 서버 운영은 범위 밖이고 `dhcpdump` 로 DHCP 패킷을 훑어봅니다. 로컬 네트워크의 어떤 장치가 주소를 얻으러 들어와야 보이므로 조금 기다려야 할 수 있습니다.

```bash
# 이 인터페이스를 지나가는 DHCP 패킷만 찍어 낸다
sudo dhcpdump -i wlp1s0
```

```bash
  TIME: 2021-09-19 17:26:24.115
    IP: 0.0.0.0 (88:cb:87:c9:19:92) > 255.255.255.255 (ff:ff:ff:ff:ff:ff)
    OP: 1 (BOOTPREQUEST)
 HTYPE: 1 (Ethernet)
  HLEN: 6
OPTION:  50 (  4) Request IP address     192.168.178.42
OPTION:  51 (  4) IP address leasetime   7776000 (12w6d)
OPTION:  12 ( 15) Host name              MichaelminiiPad
```

보내는 쪽 IP 가 `0.0.0.0` 인 것은 아직 주소가 없기 때문입니다. 받는 쪽 `255.255.255.255` 는 브로드캐스트이고 괄호 안이 링크 계층의 MAC 주소입니다. 아직 IP 가 없는 기계가 IP 를 달라고 말하는 방법이 이것뿐이라는 사실이 화면에 그대로 드러납니다.

**NTP** 는 네트워크로 컴퓨터의 시계를 맞추는 프로토콜입니다.

```bash
# 이 기계가 아는 NTP 피어를 상태와 함께 본다
ntpq -p
```

```bash
     remote          refid       st t when poll reach  delay  offset  jit
============================================================================
 0.ubuntu.pool.n .POOL.          16 p    -   64     0  0.000   0.000   0
 ntp17.kashra-se 90.187.148.77    2 u    7   64     1 27.482  -3.451   2
 golem.canonical 17.253.34.123    2 u   13   64     1 20.338   0.057   0
...
```

`-p` 는 이 기계가 아는 피어 목록을 상태와 함께 보입니다. 마지막 열 `jit` 는 지터(jitter) 열이 지면 폭에서 잘린 것입니다. 보통 NTP 는 `systemd` 같은 데몬이 뒤에서 관리하므로 손으로 질의할 일은 드뭅니다. 6장에서 `systemd` 가 네트워크 시간 동기화까지 맡는 관리자가 됐다고 읽은 대목과 이어집니다.

### 패킷 캡처 — tshark · tcpdump

이 부류는 프로토콜을 해석하기 전에 **지나가는 것을 그대로 찍어 냅니다.** 모두 `-i <인터페이스>` 로 어디에 붙을지를 먼저 정합니다. 앞의 `dhcpdump` 도 man page 가 「DHCP 패킷 덤퍼」라 부르는 이 부류입니다.[^dhcpdump] `tcpdump` 와 다른 점은 한 프로토콜만 걸러 보인다는 것뿐입니다.

**`tshark` 와 `wireshark`** 는 스택을 가로지르는 패킷을 정확히 보는 저수준 분석 도구입니다. 앞의 것이 명령줄, 뒤의 것이 GUI 입니다.

```bash
# 이 인터페이스의 TCP 패킷을 실시간으로 본다
sudo tshark -i wlp1s0 tcp
```

```bash
Capturing on 'wlp1s0'
    1 0.000000000 192.168.178.40 → 34.196.251.55 TCP 66 47618 → 443
    [ACK] Seq=1 Ack=1 Win=501 Len=0 TSval=3796364053 TSecr=153122458
    8 7.712741925 192.168.178.40 → 185.199.109.153 HTTP 146 GET / HTTP/1.1
    9 7.776535946 185.199.109.153 → 192.168.178.40 TCP 66 80 → 42000 [ACK]
   10 7.878721682 185.199.109.153 → 192.168.178.40 TCP 2946 HTTP/1.1 200 OK
...
```

다른 세션에서 `curl` 을 쳐서 HTTP 세션을 일으킨 결과가 여덟 번째 줄부터입니다. 덜 강력하지만 더 널리 있는 `tcpdump` 로도 같은 일을 할 수 있습니다. 이 출력이 7장 전체의 요약입니다. `192.168.178.40` 은 RFC 1918 사설 대역이고 `→` 양쪽이 인터넷 계층의 주소입니다. `47618 → 443` 이 전송 계층의 포트 짝입니다. 애플리케이션 계층은 `GET / HTTP/1.1` 입니다. 첫 편의 「결국 선을 타고 공기를 가르는 비트」를 한 화면에서 확인하는 자리입니다.

### 스트림 잇기 — socat · 터널

마지막 묶음은 데이터가 흐를 길을 새로 놓습니다. **`socat`** 은 양방향 바이트 스트림 둘을 세우고 그 끝점 사이에 데이터를 옮깁니다. **터널**은 VPN 이나 다른 사이트 간 네트워킹의 쓰기 쉬운 대안이고 inlets 같은 도구가 그것을 해 줍니다. **BitTorrent** 는 파일을 토런트라는 꾸러미로 묶어 개인 간에 나누는 시스템입니다. 앞의 세 묶음은 이미 있는 길을 들여다보는 도구였습니다. 이 셋은 길 자체를 만듭니다. §4 의 `ProxyJump` 도 같은 부류인데 SSH 가 그 기능을 자기 안에 들고 있을 뿐입니다.

## 적용 관점

> Spring 으로 자바를 쓰다가 컨테이너와 쿠버네티스로 넘어온 사람에게 이 구간이 어디에서 되돌아오는지를 적습니다.

**인그레스 규칙이 URI 의 부분들로 쓰여 있습니다.** `host` 가 authority 의 호스트명이고 `path` 가 path 입니다. 경로를 어떻게 맞출지는 `pathType` 이 정합니다. 쿼리는 계층적이지 않은 데이터라 경로 기반 라우팅의 대상이 아닙니다.

**컨테이너 안에서 `curl` 로 진단하는 순서가 §3 그대로입니다.** `curl -sv http://서비스이름:포트/actuator/health` 한 줄이 DNS 해석과 연결과 HTTP 응답을 한 번에 확인합니다. 실패하면 종료 코드와 `-v` 출력이 어느 층에서 멈췄는지 가리킵니다.

**`-m` 옵션이 프로브 설정과 같은 생각입니다.** `livenessProbe` 의 `timeoutSeconds` 가 하는 일이 `curl -m` 이 하는 일입니다. 기다릴 최대 시간을 정하지 않으면 죽은 것과 느린 것을 구분할 수 없습니다.

**NFS 가 `ReadWriteMany` 볼륨의 대표 구현입니다.** 블록 저장 장치는 노드 하나에만 붙어 `ReadWriteOnce` 입니다. NFS 는 여러 노드가 동시에 마운트할 수 있습니다. 다만 §6 의 close-to-open 이 그대로 적용됩니다. 그래서 여러 노드가 붙을 수 있다고 아무렇게나 써도 되는 것은 아닙니다.

**`aws s3 sync` 는 초기화 컨테이너의 흔한 쓰임새입니다.** 앱 컨테이너가 뜨기 전에 데이터를 `emptyDir` 같은 공유 볼륨으로 내려받는 패턴입니다.

**클러스터에서는 `tshark` 대신 사이드카나 `kubectl debug` 를 씁니다.** 파드의 네트워크 네임스페이스에 들어가 같은 캡처를 합니다. 6장의 `nsenter` 가 그 아래에서 하는 일입니다.

## 정답 (자답 후 펼치기)

> 위 질문 11개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — 사용자 정보의 자리

**authority 안**에 있고 호스트 앞에 옵니다. RFC 3986 의 정의가 `authority = [ userinfo "@" ] host [ ":" port ]` 입니다. authority 는 스킴 뒤에 오므로 전체 순서는 `스킴://사용자정보@호스트:포트/경로` 입니다. `user:password` 형식 자체는 폐기됐으므로 HTTPS 위의 제대로 된 인증을 씁니다.

### 정답 2 — 포트 80 의 생략

`http` 스킴의 **기본 포트가 80** 이기 때문입니다. 명시하지 않으면 그 기본값이 쓰이므로 두 표기가 같은 곳을 가리킵니다. 같은 이유로 `https` 는 443 이 기본이고 둘 다 잘 알려진 포트 구간(0~1023)에 있습니다.

### 정답 3 — 콜론을 빠뜨리면

`rsync` 가 **아무 불평 없이 그 인자를 로컬 경로로 해석**합니다. 명령은 정상적으로 끝나지만 파일은 원격이 아니라 로컬의 `user@example.com/` 같은 하위 디렉토리에 남습니다. 종료 코드가 0 이라 스크립트도 실패를 알아채지 못합니다.

### 정답 4 — NFS 마운트와 로컬 마운트

명령의 구조는 **같습니다**. `mount` 는 붙일 것과 트리 안의 자리, 입력 둘을 받습니다. 다른 것은 붙일 대상뿐이라 로컬 블록 장치 대신 `nfs.example.com:/source_dir` 처럼 원격 호스트의 디렉토리를 줍니다. 그 차이를 VFS 가 흡수합니다. 드라이버가 네트워크 연산을 포함하는 네트워크 파일시스템 갈래가 이것입니다.

### 정답 5 — tshark 한 줄 읽기

층마다 다른 자리를 봅니다. `192.168.178.40 → 185.199.109.153` 이 **인터넷 계층**의 출발지·목적지 IP 입니다. `47618 → 443` 이나 `80 → 42000` 이 **전송 계층**의 포트 짝이고 `[ACK]`·`Seq`·`Win` 이 TCP 헤더 필드입니다. `GET / HTTP/1.1` 이나 `HTTP/1.1 200 OK` 는 **애플리케이션 계층**입니다. **링크 계층**의 인터페이스는 캡처할 때 지정한 `-i wlp1s0` 입니다.

### 정답 6 — 첫 접속의 지문 확인

**서버가 자기를 증명하는 걸음**입니다. 서버는 키 교환에서 호스트 키와 서명을 보냅니다. 클라이언트는 그 키가 정말 그 서버의 것인지 확인해야 합니다. 처음에는 알 방법이 없으므로 지문을 보이고 사람에게 묻습니다. `yes` 를 치면 키가 `~/.ssh/known_hosts` 에 저장되고 이후 모든 접속에서 대조합니다. 흔히 TOFU 라 부르는 이 전략을 RFC 4251 이 서술합니다.

**취약한 구간은 첫 접속 한 번입니다.** RFC 도 수동적인 엿듣기는 막지만 능동적인 중간자 공격에는 취약하다고 적습니다. 그래서 지문은 프로비저닝 로그나 콘솔처럼 대역 밖에서 받아 대조합니다.

### 정답 7 — 두 번째 rsync

**바뀐 것만** 전송됩니다. 근거는 기본값인 **quick check** 로, 크기나 최종 수정 시각이 달라진 파일을 찾습니다. 기준 시점을 기억하지 않고 매번 양쪽의 현재 상태를 견주므로 받는 쪽에서 지운 파일도 다시 채웁니다. `-c` 를 켜면 크기가 같은 파일의 체크섬까지 견주어 시각을 건드리지 않은 변경도 잡습니다. 대신 양쪽이 파일 전체를 읽어야 합니다. `scp` 에는 이런 비교가 없어 두 번째에도 통째로 보냅니다.

### 정답 8 — 동시에 쓸 때 NFS 가 보장하는 것

**close-to-open 뿐입니다.** 쓴 쪽이 파일을 **닫으면** 수정된 데이터가 서버로 쓰입니다. 읽는 쪽은 그 파일을 **열 때** 변경 여부를 확인합니다. 아직 닫히지 않은 내용은 못 봅니다. 크기·수정 시각 같은 속성은 몇 초에서 수십 초 캐시됩니다. 락은 강제가 아니라 앱이 쓰지 않으면 마지막에 쓴 쪽이 이깁니다. 그래서 읽기 공유는 마음껏 하고 쓰기는 한쪽으로 몰거나 파일을 나눕니다.

### 정답 9 — 프래그먼트와 서버 요청

서버는 **`GET /docs?q=1`** 까지만 받고 `#intro` 는 가지 않습니다. RFC 3986 에 따라 프래그먼트는 참조를 따라가기 전에 나머지에서 떼어져 사용자 에이전트가 혼자 해석하기 때문입니다. 그래서 스프링에서 쿼리는 `@RequestParam` 으로 받지만 프래그먼트는 받을 방법이 없고 서버 접근 로그에도 남지 않습니다.

### 정답 10 — exit 7 과 0 ms

**패킷이 상대까지 갔다 왔다는 뜻입니다.** 즉시 거절당하려면 누군가 대답해야 합니다. TCP 로 치면 RST 가 돌아온 셈입니다. 이름도 풀렸고 길도 있고 기계도 살아 있는데 **그 포트만 안 열린** 것입니다. 다음에는 상대에서 `ss -tlnp` 로 그 포트를 듣는 소켓이 있는지 봅니다. 대비되는 것이 `exit 28` 입니다. 한도를 채우고 끝났다면 아무도 대답하지 않은 것이라 `route -n get` → `ping` → `traceroute` 순으로 좁힙니다. 넷이 다 멀쩡하면 상대의 accept 큐를 봅니다.

### 정답 11 — 서버가 수천 대일 때

**호스트 키에 CA 서명을 씁니다.** 자체 CA 키로 각 서버의 호스트 공개 키에 서명하면 클라이언트는 `known_hosts` 에 `@cert-authority` 줄로 **CA 공개 키 하나만** 믿으면 됩니다. RFC 4251 이 든 신뢰 모델 둘 중 뒤의 것입니다. 서버를 재설치해 호스트 키가 바뀌어도 클라이언트는 아무것도 안 고칩니다. **대가는 CA 키가 단일 실패 지점이 된다는 것**이라 그 키가 새면 모든 서버를 위조할 수 있습니다. 몇 대뿐이면 TOFU 가 더 쌉니다.
