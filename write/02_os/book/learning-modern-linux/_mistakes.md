# learning-modern-linux 오답 노트

> 복습 회차에서 quality ≤ 3 인 질문을 박제한다. 같은 패턴이 3회 이상 반복되면 원본 챕터 본문 보강 트리거.

## 2026-09-08 — 07-01 Q1: 각 층이 알아야 하는 범위

- **자기 답**: "IP → 출발지/목적지 IP, TCP → 출발지/목적지 포트" — 각 층의 헤더 필드를 나열
- **정답**: 각 층은 **바로 위와 바로 아래 층만** 알고 그것과 통신할 수 있으면 된다 (원본 §2 의 두 규칙 중 첫째)
- **원인 추정**: 질문 축을 "무엇을 담나"로 읽음. 추상 규칙 자리에서 구체 필드로 내려감
- **재방문 트리거**: 2026-09-11 회차 2

## 2026-09-08 — 07-01 Q2: 층 분리로 무엇을 얻는가

- **자기 답**: "계층 간 분리가 된다" — 규칙 재진술. 반사실("없었다면") 절반 미답
- **정답**: **교체 가능성.** TCP→QUIC, 이더넷→WiFi 로 갈아 끼워도 다른 층 코드가 안 바뀐다 (원본 §2)
- **원인 추정**: 이득을 사례로 환산하지 못함. "없었다면?" 뒷절반을 습관적으로 빠뜨림
- **재방문 트리거**: 2026-09-11 회차 2

## 2026-09-08 — 07-01 Q4: 맞은 답을 뒤집음 (방향 오류)

- **자기 답**: `/25` 로 정답을 낸 뒤 스스로 `/23` 으로 정정
- **정답**: `/25` 가 맞다. 노드 수 = 2^(노드 조각 − 클러스터 대역) 이므로 `/23`=128, `/24`=256, `/25`=512. **prefix 숫자가 커질수록 조각이 작아지고, 조각이 작아야 개수가 는다**
- **원인 추정**: 2026-09-06 의 방향 뒤집기 4건과 같은 패턴. 관계는 아는데 화살표가 돈다
- **재방문 트리거**: 2026-09-11 회차 2

## 2026-09-08 — 07-02 Q3: TCP 체크섬이 IP 를 쓰는 이유와 대가

- **자기 답**: "체크섬이 IP 헤더 값으로 만드는 값이라 참조하는 것 같다" — 왜·대가 둘 다 미답
- **정답**: 체크섬 계산에 **의사 헤더**를 붙여 출발지·목적지 IP 를 포함시킨다. 이유는 RFC 9293 의 「잘못 배달된 세그먼트로부터 연결을 보호」. 대가는 **계층 위반** — NAT 이 IP 를 바꾸면 TCP 체크섬 재계산, IPv6 로 가면 의사 헤더 모양이 바뀐다 (원본 §2)
- **원인 추정**: IP 헤더 체크섬과 TCP 체크섬을 섞음. 07-01 §2 의 계층 규칙을 못 세워 그 예외도 예외로 안 보임
- **재방문 트리거**: 2026-09-11 회차 2

## 2026-09-08 — 07-02 Q5: ARP 캐시와 conntrack 이 담는 것 (2연속)

- **자기 답**: "ARP 에는 시간, conntrack 은 홉" — 담기는 내용 대신 만료 조건으로 답함
- **정답**: **ARP 캐시(`ip neigh`)는 IP→MAC 대응**(L2/L3 경계), **conntrack 은 진행 중인 연결의 상태**(5-tuple + 상태, L4) (원본 §7)
- **원인 추정**: 2026-09-06 회차에서 두 표를 맞바꿔 놓은 데 이어 **2연속**. conntrack 이 5-tuple 을 든다는 것은 같은 회차 Q1 의 답이었고 채점에서 명시했는데도 30분 만에 흘렀다 — 단기 노출로는 안 붙는 항목
- **재방문 트리거**: 2026-09-11 회차 2 의 **첫 문항**

## 2026-09-08 — 07-03 Q1: HTTP 요청·응답 첫 줄의 구성

- **자기 답**: "URI로 되어 있는 거 아냐?" — 셋 중 하나만, 응답 쪽은 미답
- **정답**: 요청은 **메서드 + 경로 + 버전**(`GET / HTTP/1.1`), 응답은 **버전 + 상태 코드 + 이유 구절**(`HTTP/1.1 200 OK`). 응답에 메서드·경로가 없는 것은 같은 연결로 돌아온 답이라 클라이언트가 이미 알기 때문 (원본 §1)
- **원인 추정**: 이 편의 출발점이자 원본 §1 첫 코드 블록인데 형태가 안 남았다. 구성·구조를 묻는 문항에서 반복 실패
- **재방문 트리거**: 2026-09-09 회차 2

## 2026-09-08 — 07-03 Q4: rsync 의 판정 축

- **자기 답**: "re 로 시작하는 명령, 각 파일의 해시를 보고 변경점만 가져온다"
- **정답**: `rsync`. **기본은 크기 + 수정 시각**이고 해시 비교는 `-c` 를 줘야 한다. 한계 둘 — mtime 을 보존한 내용 변경을 놓치고, `touch` 만 해도 전송 대상이 된다. `-c` 는 확실하나 양쪽이 전 파일을 읽어야 해 느리다 (원본 §5)
- **원인 추정**: 기본값과 옵션을 맞바꿈. 도구는 알지만 무엇을 근거로 판정하는지가 비어 있어 한계도 못 도출
- **재방문 트리거**: 2026-09-09 회차 2

## 2026-09-08 — 07-03 Q5: RST 즉답의 첫 의심 (방향 오류)

- **자기 답**: "RST 가 바로 오는 건 직접적으로 거부했다는 거니 방화벽 이슈"
- **정답**: RST 는 **도달했고 호스트도 살아 있다**는 증거다. 첫 의심은 **서비스 기동과 포트 번호**. 방화벽은 대개 조용히 버린다(DROP). 다만 `--reject-with tcp-reset` 이면 방화벽도 RST 를 위장하므로, 응답의 **출발지 IP** 로 갈린다 (원본 §3, 그리고 networking-and-kubernetes 02-05 §정답 2)
- **원인 추정**: "거부 = 막혔다"로 읽음. RST 를 나쁜 소식으로 보는 감각 — 실은 상대가 대답했다는 좋은 소식
- **재방문 트리거**: 2026-09-09 회차 2

## 2026-09-09 — 07-03 회차 2 Q1: curl 종료 코드 6·7·28

- **자기 답**: "타임아웃, DNS 에러 이런 거였던 것 같다" — 코드와 층의 대응 미도달, **연결 거부(7)** 누락
- **정답**: 6=이름(전송 시작도 못 함) · 7=포트(길은 있고 그 포트만 안 열림) · 28=무응답(길이 없거나 중간이 삼킴) (원본 §3)
- **원인 추정**: 셋이 서로 다른 층을 가리킨다는 구조는 있으나 항목이 안 붙음. 회차 1 과 같은 축 — 논리는 나오고 항목은 안 나온다
- **재방문 트리거**: 2026-09-10 회차 3

## 2026-09-09 — 07-03 회차 2 Q4: accept 큐 포화 (위치 오류)

- **자기 답**: "중간 라우트가 큐에 너무 많이 쌓여서 처리가 느리다"
- **정답**: **목적지 호스트 커널의 accept 큐**다. 앱이 `accept()` 를 제때 못 불러 대기 줄이 차면 커널이 새 연결을 떨어뜨린다. 앞의 넷이 전부 정상으로 보이는 **애플리케이션 문제**라 사다리 맨 끝에 둔다 (원본 §3)
- **원인 추정**: 큐라는 개념은 잡았으나 위치를 중간 장비로 잡음. 방향 뒤집기와 결이 같되 축이 "어디"
- **재방문 트리거**: 2026-09-10 회차 3

## 2026-09-09 — 07-03 회차 2 Q5: curl -I 의 HEAD 단서

- **자기 답**: 미답
- **정답**: **모든 HTTP 서버가 어느 경로에 대해서든 HEAD 를 지원하지는 않는다.** `-I` 가 405·501 을 받으면 서버 장애로 오독하기 쉬운데 GET 은 200 이 오는 경우가 있다. 확인하려던 것과 실제로 잰 것이 다르다 (원본 §3)
- **원인 추정**: 옵션의 편의(본문 안 받음)만 남고 그 편의가 **다른 메서드를 쓴다**는 대가가 안 남음
- **재방문 트리거**: 2026-09-10 회차 3

## 2026-09-10 — 07-03 회차 3 Q1: 종료 코드는 나왔으나 "다음 명령"이 안 나옴

- **자기 답**: "6(도메인 조회 실패), 7(거부), 28(타임아웃)" — 코드 셋과 층은 전부 회상. 회차 2 에서 빠졌던 **7 = 연결 거부**가 자력으로 나옴
- **정답**: 코드마다 다음에 칠 명령이 붙는다 — 6 → `dig`·`/etc/resolv.conf`·검색 도메인, 7 → 상대에서 `ss -tlnp`, 28 → `route -n get <주소>` 로 길 확인 → `ping` 으로 생존 확인 → `traceroute` 로 좁히기 (원본 §3)
- **원인 추정**: 분류는 섰는데 **분류 다음의 행동**이 안 붙음. 표의 셋째 열(「다음에 볼 것」)이 회상 대상에서 통째로 빠져 있다
- **재방문 트리거**: 2026-09-24 회차 4

## 2026-09-10 — 07-03 회차 3 Q2: ss LISTEN 행의 두 칸 (원문 밖 문항)

- **자기 답**: "LISTEN 은 아직 연결되기 전이고, Recv-Q 가 백로그 최대 크기였던 것 같다. Send-Q 는 모르겠다" — **두 칸이 뒤집힘**
- **정답**: `LISTEN` 행에서 `Recv-Q` 는 accept 큐에 **지금 쌓인 수**, `Send-Q` 는 backlog **최대치**. 둘이 같으면 포화이고 고칠 곳은 **앱**(워커가 `accept()` 로 꺼내 가는 속도가 못 따라감). backlog 를 키우는 것은 미봉
- **⚠️ 문항 설계 오류**: 이 두 칸은 `07-03` 어디에도 없다. §3 은 「accept 큐 포화를 의심합니다」 한 문장뿐이고 `Recv-Q` 는 `07-02` 의 `ss -ulp` 출력 예시에 설명 없이 찍혀 있을 뿐이다. **회차 2 정답 4 가 이 표에 「원본 §3」 을 단 것은 잘못된 출처 표기**다. 학습자 축이 아니므로 노트 보강 뒤 재출제한다
- **원문 범위에서 미달한 것**: accept 큐 포화라는 이름 · 앱이 `accept()` 를 못 부르는 것이 원인 · 그래서 사다리 맨 끝
- **재방문 트리거**: README `보강 후보` 반영 후

## 2026-09-10 — 07-03 회차 3: 학습자가 되물어 드러난 노트 결손 넷

박제 성격이 다르다. 인출 실패가 아니라 **학습자가 노트에 없는 자리를 정확히 겨눈 질문**이다. 전부 원문 밖이라 답은 man page 대조가 필요하다.

- **6 번은 DNS 서버 무응답인가, 이름을 못 찾은 것인가** → `curl` 은 리졸버 실패라는 사실만 받으므로 `NXDOMAIN`·`SERVFAIL`·서버 무응답을 **6 하나로 뭉갠다.** 노트가 「다음에 볼 것: `dig`」 라고 적은 이유가 이것인데 그 셋이 갈린다는 서술이 없다
- **`Send-Q` 는 고정이고 `Recv-Q` 만 움직이는가** → 그렇다. 앱이 다시 `listen()` 하지 않는 한 `Send-Q` 는 안 변하고, 둘이 같아지는 순간이 포화다
- **`accept()` 를 불러야 `ESTABLISHED` 가 되는가** → **아니다.** 3-way 가 끝나는 순간 이미 `ESTABLISHED` 이고 `accept()` 는 앱에게 fd 를 건넬 뿐이다. 그래서 앱이 멈춰도 클라이언트에는 연결이 성공한 것으로 보이고 「연결은 되는데 응답이 없다」 증상이 된다
- **backlog 는 어느 큐인가** → 리눅스에서는 **accept 큐의 한도**다. SYN 큐는 `net.ipv4.tcp_max_syn_backlog` 가 따로 정하고 `listen()` 인자는 `net.core.somaxconn` 이 천장이다. BSD 에서 backlog 하나가 두 큐를 덮던 이름이 남았다
- **재방문 트리거**: 보강 반영 후 2026-09-24 회차 4
