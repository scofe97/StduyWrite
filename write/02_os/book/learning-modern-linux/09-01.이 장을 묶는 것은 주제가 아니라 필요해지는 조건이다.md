# 이 장을 묶는 것은 주제가 아니라 필요해지는 조건이다

---

> 이 책의 마지막 장입니다. 저자 스스로 잡탕이라 부르는 구간이고, 다섯 주제를 잇는 것은 내용이 아니라 각각이 언제 필요해지는가입니다.

## 핵심 요약

> 이 장이 매달린 생각은 여기 있는 것들은 쓸 일이 생겨야 필요해진다는 것입니다. 저자가 서두에서 직접 그렇게 적습니다.

이 장의 주제들이 공통으로 갖는 것은, 대부분 구체적인 용례가 머릿속에 있거나 업무 환경이 요구할 때에만 의미가 있다는 점이라고 저자는 씁니다. 그래서 이 노트의 일도 각 주제를 남김없이 설명하는 것이 아니라, 그것이 필요해지는 조건을 함께 적는 것입니다.

다섯 주제 중 둘은 앞 장들의 연장입니다. 프로세스 사이 통신은 3장의 파이프와 7장의 소켓을 한 기계 안으로 좁힌 것입니다. 인증은 4장의 접근 제어에서 인증 부분만 떼어 낸 것입니다. 나머지 셋인 가상 머신, 현대 배포판, 아직 주류가 아닌 것들은 새 이야기입니다.

운영에서 가장 자주 손에 닿는 것은 시그널입니다. 서비스 중지가 90초를 끌거나 컨테이너가 137 로 끝났다는 알림은 모두 시그널로 읽어야 풀립니다. 그래서 이 노트는 시그널을 따로 한 절로 떼어 배치와 번호, 보내는 도구, 종료 순서와 종료 코드, 정지와 재개까지 Debian 12 컨테이너에서 직접 돌린 출력으로 확인합니다. 시그널 핸들러는 기본 동작을 대체하므로 핸들러를 단 프로세스는 스스로 끝내야 합니다.

인증 절에는 로그인할 때 자원 한도를 거는 `pam_limits` 를 더했습니다. 한도는 로그인마다 새로 걸리고 이미 돌고 있는 프로세스에는 소급되지 않는다는 것이 그 절의 요점입니다.



## 학습 목표

> 이 장을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. 시그널의 세 가지 배치를 말하고, 핸들러가 기본 동작과 어떤 관계인지와 핸들할 수 없는 둘을 댈 수 있습니다.
2. 종료 코드 128+n 을 시그널 이름으로 읽고, `systemctl stop` 이 `SIGTERM` 에서 `SIGKILL` 까지 가는 순서를 설명할 수 있습니다.
3. 명명 파이프를 만들어 두 프로세스를 붙이고, 그것이 왜 막히는지 설명할 수 있습니다.
4. 가상화 스택을 아래에서 위로 쌓아 설명하고, 내 기계가 KVM 을 쓸 수 있는지 확인할 수 있습니다.
5. Kerberos 의 네 걸음과 운영상 제약을 설명하고, `limits.conf` 의 한도가 언제 누구에게 걸리는지 판단할 수 있습니다.

아래는 이 문서 전체를 읽는 순서로 이은 지도입니다. 칸마다 절 번호와 그 절이 언제 필요해지는지를 적었습니다.

## 이 문서가 다루지 않는 것

> 저자가 스스로 그은 선을 옮깁니다.

- IPC 전반 → 저자가 파이프와 소켓과 공유 메모리까지 긴 목록이 있다고만 밝히고, 잘 자리 잡고 널리 쓰이는 셋만 고릅니다
- 도메인 소켓의 프로그래밍 → 보통 프로그램에서 쓰는 것이라 하고, 명령줄에서는 `socat` 으로 만져 보라고만 적습니다
- KVM 위에서 실제로 VM 을 띄우는 절차 → 이 장은 스택의 구성과 가용성 확인까지입니다
- 데스크톱 배포판·임베디드·클라우드 IDE 의 실습 → 저자가 소개 수준으로만 다룹니다



## 1. 시그널, 번호 하나로 오는 알림

> 돌고 있는 프로세스에 멈춰라, 끝내라, 다시 읽어라 같은 사건을 알리는 가장 짧은 길이 시그널입니다. 번호 하나만 가고 데이터는 따라가지 않습니다.

서비스를 내렸는데 프로세스가 한참 버티다 강제로 죽었다는 로그를 받으면, 무슨 일이 있었는지 시그널을 모르고는 읽을 수 없습니다. 컨테이너가 종료 코드 137 로 끝났다는 알림도, `kill` 을 보냈는데 프로세스가 꿈쩍하지 않는 일도 마찬가지입니다.

저자는 프로세스 사이 통신 절을 시그널로 엽니다. 리눅스에는 파이프에서 소켓, 공유 메모리까지 IPC 선택지가 긴 목록으로 있습니다. 저자는 그것이 하는 일을 셋으로 적습니다. 프로세스끼리의 통신, 활동의 동기화, 데이터 공유입니다. 그중 시그널은 데이터를 나르지 않고 사건만 알립니다. 데이터를 나르는 둘은 §2 가 다룹니다.

### 시그널 — 커널이 프로세스를 두드리는 방법

시그널은 원래 커널이 유저 공간 프로세스에 특정 사건을 알리려고 만들어졌습니다. 프로세스로 보내는 비동기 알림이라고 생각하면 된다고 저자는 적습니다.

시그널이 도착했을 때 프로세스가 어떻게 할지를 배치(disposition)라 부릅니다. `signal(7)` 은 프로세스가 셋 중 하나를 고른다고 적습니다. 기본 동작을 수행하거나, 무시하거나, 핸들러로 잡는 것입니다.[^signal] 셋은 서로를 대체합니다. 핸들러를 단 시그널은 기본 동작이 일어나지 않고, 핸들러가 끝나면 프로세스는 하던 일로 돌아갑니다.

예외가 둘 있습니다. `SIGKILL` 과 `SIGSTOP` 은 잡을 수도 막을 수도 무시할 수도 없습니다.[^signal] 어떤 배치를 걸어 두었든 이 둘이 오면 커널이 기본 동작을 그대로 실행합니다.

배치는 스레드가 아니라 프로세스의 속성입니다. 다중 스레드 프로그램에서 한 시그널의 배치는 모든 스레드에 같습니다.[^signal] `fork` 로 만든 자식은 부모의 배치 사본을 물려받습니다. `execve` 로 다른 프로그램을 실행하면 핸들러로 잡던 시그널은 기본 동작으로 되돌아가고, 무시하던 시그널은 무시한 채 남습니다.[^signal] 셸 스크립트의 `trap` 핸들러가 그 스크립트가 실행한 프로그램으로 따라가지 않는 반면, `nohup` 이 건 무시는 따라가는 이유가 이것입니다.

프로세스에 시그널을 보내는 전형적인 방법이 `kill` 명령입니다. 이름이 좀 이상한 것은 기본 동작이 프로세스를 종료시키는 것이기 때문이라고 저자가 덧붙입니다.

```bash
while true ; do sleep 1 ; done &
ps
kill 17030
```

```bash
[1] 17030
  PID TTY          TIME CMD
16939 pts/2    00:00:00 bash
17030 pts/2    00:00:00 bash
17041 pts/2    00:00:00 sleep
17045 pts/2    00:00:00 ps
[1]+  Terminated              while true; do sleep 1; done
```

셸의 작업 제어가 우리 프로그램이 작업 ID 1 번으로 배경에서 돈다는 것과 그 PID 를 알려 줍니다. `ps` 에서 PID 17030 의 이름이 `sleep` 이 아니라 `bash` 인 점을 눈여겨봅니다. 반복문 전체가 서브셸로 떴고 우리가 죽일 대상이 그 서브셸입니다. `sleep` 은 PID 17041 로 그 아래에서 도는 별개의 프로세스이며 회차마다 새로 뜹니다. `kill` 은 기본으로 `SIGTERM` 을 보내고, 핸들러를 등록하지 않았으므로 기본 동작대로 종료됩니다.

핸들러를 다는 쪽은 `trap` 입니다. 셸 환경에서 커스텀 핸들러를 정의하게 해 줍니다.

```bash
trap "echo kthxbye" SIGINT ; while true ; do sleep 1 ; done
```

```bash
^Ckthxbye
```

Ctrl+C 를 누르면 `SIGINT` 의 핸들러가 `kthxbye` 를 찍습니다. 핸들러가 기본 동작인 종료를 대체했으므로 반복문은 그 뒤에도 계속 돕니다. 프롬프트로 돌아가려면 핸들러 안에서 `exit` 를 부르거나 다른 시그널로 끝내야 합니다.

배치 셋을 같은 반복문에 하나씩 걸고 `SIGTERM` 을 보내 비교하면 차이가 종료 상태로 드러납니다. Debian 12 컨테이너(bash 5.2.15)에서 아래 줄들을 스크립트 `/tmp/rerun.sh` 로 돌린 결과입니다.

```bash
# notrap.sh  : while true; do sleep 1; done
# trap.sh    : trap 'echo TERM 받음, 정리 후 종료; exit 0' TERM 를 앞에 둠
# ign.sh     : trap '' TERM 를 앞에 둠
./notrap.sh & p=$!; sleep 0.5; kill $p; wait $p; echo "exit=$?"
./trap.sh   & p=$!; sleep 0.5; kill $p; wait $p; echo "exit=$?"
./ign.sh    & p=$!; sleep 0.5; kill $p; sleep 1.2; kill -0 $p && echo "TERM 뒤에도 살아 있음"
kill -KILL $p; wait $p; echo "exit=$?"
```

```bash
exit=143
TERM 받음, 정리 후 종료
exit=0
TERM 뒤에도 살아 있음
/tmp/rerun.sh: line 11:  4324 Killed                  ./ign.sh
exit=137
```

기본 동작에 맡긴 쪽은 143 으로 끝났습니다. 핸들러를 단 쪽은 핸들러가 직접 `exit 0` 을 불렀기에 0 으로 끝났습니다. 그 `exit` 가 없었다면 핸들러를 실행한 뒤 반복문으로 돌아갔을 것입니다. 무시하는 쪽은 `SIGTERM` 을 받고도 살아 있다가 `SIGKILL` 에 137 로 끝났습니다. `trap "echo caught" KILL` 은 오류 없이 받아들여지지만, 그 셸에 `SIGKILL` 을 보내면 핸들러를 거치지 않고 137 로 죽습니다.

![SIGTERM 하나가 배치 셋을 거쳐 서로 다른 종료 상태로 끝난다](./_assets/09-01.signals.svg)

### 번호와 기본 동작

로그에 `status=9/KILL` 이 찍히거나 설정에 `KillSignal=SIGQUIT` 가 보이면 번호와 이름을 오갈 수 있어야 합니다. bash 의 내장 `kill -l` 이 그 표를 보입니다.

```bash
kill -l
#  1) SIGHUP	 2) SIGINT	 3) SIGQUIT	 4) SIGILL	 5) SIGTRAP
#  6) SIGABRT	 7) SIGBUS	 8) SIGFPE	 9) SIGKILL	10) SIGUSR1
# 11) SIGSEGV	12) SIGUSR2	13) SIGPIPE	14) SIGALRM	15) SIGTERM
# 16) SIGSTKFLT	17) SIGCHLD	18) SIGCONT	19) SIGSTOP	20) SIGTSTP
# 21) SIGTTIN	22) SIGTTOU	23) SIGURG	24) SIGXCPU	25) SIGXFSZ
# 26) SIGVTALRM	27) SIGPROF	28) SIGWINCH	29) SIGIO	30) SIGPWR
# 31) SIGSYS	34) SIGRTMIN	35) SIGRTMIN+1	36) SIGRTMIN+2	37) SIGRTMIN+3
# ...
# 63) SIGRTMAX-1	64) SIGRTMAX
kill -l 143   # TERM
kill -l TERM  # 15
```

`kill -l` 에 숫자를 주면 이름을 돌려줍니다. bash 는 그 숫자를 시그널 번호로도, 시그널로 죽은 프로세스의 종료 상태로도 받아들이기 때문에 143 을 넣어도 `TERM` 이 나옵니다.[^bashkill] 번호는 아키텍처마다 다를 수 있습니다. 아래 번호는 x86 과 ARM 의 것이고 Alpha·SPARC·MIPS·PARISC 에는 다른 번호를 쓰는 시그널이 있습니다.[^signal] 스크립트와 설정에는 번호 대신 이름을 쓰는 편이 안전합니다.

기본 동작 칸의 Term 은 종료, Core 는 종료와 코어 덤프, Ign 은 무시, Stop 은 정지, Cont 는 재개입니다. 기본 동작은 모두 `signal(7)` 의 표에서 옮겼습니다.[^signal]

| 번호 | 이름 | 기본 동작 | 언제 오고 무엇에 쓰나 |
|------|------|-----------|----------------------|
| 1 | `SIGHUP` | Term | 제어 터미널이 끊기거나 제어 프로세스가 죽을 때. nginx 같은 데몬은 설정을 다시 읽는 신호로 씁니다[^nginx] |
| 2 | `SIGINT` | Term | 터미널에서 Ctrl+C |
| 3 | `SIGQUIT` | Core | 터미널에서 Ctrl+\\. JVM 은 이 시그널에 스레드 덤프를 찍고 계속 돕니다[^jdk] |
| 6 | `SIGABRT` | Core | 프로그램이 `abort(3)` 를 부를 때 |
| 9 | `SIGKILL` | Term | 잡을 수도 막을 수도 무시할 수도 없는 종료 |
| 10, 12 | `SIGUSR1`, `SIGUSR2` | Term | 뜻이 정해지지 않은 둘. 프로그램마다 용도를 정합니다(아래) |
| 11 | `SIGSEGV` | Core | 잘못된 메모리 참조 |
| 13 | `SIGPIPE` | Term | 읽는 쪽이 없는 파이프에 쓸 때 |
| 14 | `SIGALRM` | Term | `alarm(2)` 타이머가 다 될 때. `timeout` 이 내부에서 씁니다 |
| 15 | `SIGTERM` | Term | `kill` 과 `systemctl stop` 이 기본으로 보내는 종료 요청 |
| 17 | `SIGCHLD` | Ign | 자식이 멈추거나 끝날 때 |
| 18 | `SIGCONT` | Cont | 멈춘 프로세스를 이어 돌릴 때 |
| 19 | `SIGSTOP` | Stop | 잡을 수 없는 정지 |
| 20 | `SIGTSTP` | Stop | 터미널에서 Ctrl+Z. 잡을 수 있습니다 |
| 24 | `SIGXCPU` | Core | CPU 시간 한도(`setrlimit(2)`)를 넘을 때 |
| 25 | `SIGXFSZ` | Core | 파일 크기 한도를 넘을 때 |
| 28 | `SIGWINCH` | Ign | 터미널 창 크기가 바뀔 때 |
| 34~64 | `SIGRTMIN`~`SIGRTMAX` | Term | 실시간 시그널. 미리 정한 뜻이 없습니다 |

`SIGUSR1` 과 `SIGUSR2` 는 양쪽이 의미에 합의하기만 하면 프로세스끼리 비동기 알림을 주고받는 데 쓸 수 있다고 저자가 적습니다. 실제로 프로그램마다 뜻이 다릅니다. nginx 는 `USR1` 에 로그 파일을 다시 열고 `USR2` 에 실행 파일을 갈아 끼웁니다.[^nginx] HAProxy 에서 `SIGUSR1` 은 리스닝 포트만 놓고 남은 연결을 끝까지 처리한 뒤 나가는 얌전한 중지이고, `SIGTERM` 은 연결을 모두 끊고 곧바로 나가는 강제 중지입니다.[^haproxy] GNU `dd` 는 `USR1` 을 받으면 지금까지의 입출력 통계를 표준 오류에 찍고 복사를 이어 갑니다.[^dd]

```bash
dd if=/dev/zero of=/dev/null bs=1M count=200000 & p=$!; sleep 1; kill -USR1 $p
# 26068+0 records in
# 26068+0 records out
# 27334279168 bytes (27 GB, 25 GiB) copied, 1.00066 s, 27.3 GB/s
# dd: warning: partial read (266240 bytes); suggest iflag=fullblock
```

마지막 경고는 시그널이 읽기를 끊어 짧은 읽기가 생긴 흔적입니다. GNU 매뉴얼도 진행률을 주기적으로 받을 때는 `iflag=fullblock` 을 함께 쓰라고 권합니다.[^dd]

로그 교체가 `USR1` 을 쓰는 대표 자리입니다. nginx 문서의 절차는 로그 파일 이름을 먼저 바꾼 뒤 마스터 프로세스에 `USR1` 을 보내는 것이고, 그러면 마스터가 열려 있던 로그 파일을 모두 다시 엽니다.[^nginx] `logrotate` 설정의 `postrotate` 스크립트는 교체가 끝난 뒤 한 번 실행되므로,[^logrotate] 거기에 `kill -USR1 "$(cat /run/nginx.pid)"` 같은 줄을 둡니다.

기본 동작이 Core 라도 코어 파일이 반드시 생기지는 않습니다. 코어 덤프 크기 한도(`RLIMIT_CORE`)가 0 이면 만들지 않는 등 `core(5)` 가 꼽는 조건이 여럿입니다.[^core] `SIGSEGV` 를 잡지 않은 채 죽은 프로세스는 x86 커널이 `comm[pid]: segfault at 주소 ip … sp … error …` 형식의 줄을 커널 로그에 남기므로 `journalctl -k` 에서 찾을 수 있습니다.[^segv]

자원 한도에서 오는 둘은 직접 일으켜 볼 수 있습니다. `ulimit -f` 의 단위는 1024 바이트입니다.

```bash
( ulimit -St 1; while :; do :; done ); echo "exit=$?"
# /tmp/rerun.sh: line 13:  4329 CPU time limit exceeded ( ulimit -St 1; while :; do ...
# exit=152
( ulimit -f 1; dd if=/dev/zero of=/tmp/big bs=1024 count=100 2>/dev/null ); echo "exit=$?"
# /tmp/rerun.sh: line 14:  4331 File size limit exceededdd if=/dev/zero of=/tmp/big ...
# exit=153
stat -c '%s %n' /tmp/big  # 1024 /tmp/big
```

CPU 를 1초 넘게 쓴 반복문은 `SIGXCPU`(24)로, 1024 바이트를 넘겨 쓰려던 `dd` 는 `SIGXFSZ`(25)로 죽었고 파일은 한도에서 멈췄습니다. `SIGPIPE` 는 `yes | head -n1` 처럼 읽는 쪽이 먼저 끝날 때 생기며, 3장 노트의 [파이프라인 절](./03-01.%EC%85%B8%EC%9D%98%20%EC%8B%A4%EC%B2%B4%EB%8A%94%20%EC%8A%A4%ED%8A%B8%EB%A6%BC%EA%B3%BC%20%EB%B3%80%EC%88%98%EC%99%80%20%EC%A2%85%EB%A3%8C%20%EC%83%81%ED%83%9C%EB%8B%A4.md#파이프라인이-실제로-이어지는-방식)이 `PIPESTATUS` 의 `141 0` 으로 보입니다.

실시간 시그널은 표준 시그널과 두 가지가 다릅니다. 같은 시그널이 여러 번 오면 표준 시그널은 한 건만 대기하지만 실시간 시그널은 큐에 쌓입니다.[^signal]

그리고 `SIGRTMIN` 의 번호가 고정되어 있지 않습니다. 커널은 32 부터 64 까지 33개를 두지만 glibc 가 앞의 둘이나 셋을 내부에 쓰므로 `SIGRTMIN` 은 34 나 35 가 됩니다.[^signal] 위 출력에서 33 다음이 비고 34 가 `SIGRTMIN` 인 것이 그 결과입니다. 그래서 실시간 시그널은 `SIGRTMIN+n` 으로 적습니다. systemd 의 PID 1 은 `SIGRTMIN+0` 을 받으면 `default.target` 으로, `SIGRTMIN+1` 이면 rescue 모드로, `SIGRTMIN+3` 이면 halt 로 들어갑니다.[^systemd1]

### 시그널을 보내는 세 도구 — kill·pkill·timeout

PID 를 일일이 찾지 않고 이름이나 사용자로 보내고 싶거나, 명령에 시간 제한을 걸고 싶을 때 쓰는 도구가 다릅니다.

| 도구 | 기본 시그널 | 대상을 고르는 법 |
|------|------------|-----------------|
| `kill PID` | `SIGTERM` | PID. 음수 PID 는 그 프로세스 그룹 전체입니다[^kill] |
| `pkill 패턴` | `SIGTERM` | 프로세스 이름에 패턴을 맞춥니다. `-f` 는 명령행 전체, `-u` 는 유효 사용자, `-U` 는 실제 사용자, `-t` 는 제어 터미널이며 조건을 함께 주면 모두 맞아야 합니다[^pgrep] |
| `timeout 시간 명령` | `SIGTERM` | 자기가 띄운 명령. 시간이 다 되면 보냅니다[^timeout] |

`pkill` 은 보내기 전에 같은 조건의 `pgrep -a` 로 대상을 먼저 보는 습관이 안전합니다. `-f` 가 명령행 전체를 보기 때문에 엉뚱한 프로세스까지 걸리기 쉽습니다. 이름을 `worker` 로 바꿔 띄운 `sleep 505` 하나를 찾는 실험입니다.

```bash
bash -c "exec -a worker sleep 505" & sleep 0.3; pgrep -a 505; echo "rc=$?"
# rc=1
bash -c 'bash -c "exec -a worker sleep 505" & sleep 0.3; pgrep -af "sleep 505|505"; pkill -f "^worker"'
# 4468 bash -c bash -c "exec -a worker sleep 505" & sleep 0.3; pgrep -af "sleep 505|505"; pkill -f "^worker"
# 4473 worker 505
```

이름에만 맞추면 아무것도 걸리지 않아 종료 상태 1 이 나옵니다. `-f` 로 바꾸면 목표인 4473 뿐 아니라 이 실험을 돌린 셸 4468 도 걸립니다. 그 셸의 명령행 안에 패턴 문자열이 들어 있기 때문입니다. 같은 패턴으로 `pkill -f` 를 보냈다면 자기를 부른 스크립트를 죽였을 것입니다. `pkill` 의 종료 상태는 하나 이상 맞고 시그널을 보냈으면 0, 맞는 것이 없으면 1 입니다.[^pgrep]

`timeout` 은 종료 상태로 무슨 일이 있었는지를 알립니다.

```bash
timeout 1 sleep 10; echo "exit=$?"                    # exit=124
timeout -s KILL 1 sleep 10; echo "exit=$?"            # exit=137
timeout -k 1 1 ./ign.sh; echo "exit=$?"               # exit=137
timeout --preserve-status 1 sleep 10; echo "exit=$?"  # exit=143
```

시간이 다 되면 `SIGTERM` 을 보내고 124 로 끝납니다. `-s` 로 보낼 시그널을 바꾸면 `SIGKILL` 의 128+9 인 137 이 나옵니다. `-k 1` 은 첫 시그널을 보내고도 1초 뒤에 살아 있으면 `SIGKILL` 을 보내라는 뜻이라, `SIGTERM` 을 무시하는 `ign.sh` 도 137 로 끝났습니다. `--preserve-status` 는 124 대신 명령 자신의 종료 상태를 돌려줍니다.[^timeout]

시간을 재는 방법은 표의 `SIGALRM` 입니다. coreutils 9.1 의 `timeout` 은 만료되면 자기에게 `SIGALRM` 이 오도록 타이머를 겁니다. 그 시그널을 받은 순간 자식에게 정한 시그널을 보냅니다.[^timeoutc]

### 종료 코드 128+n 과 systemctl stop 의 순서

컨테이너나 서비스가 137 이나 143 으로 끝났다는 보고를 받으면 먼저 128 을 빼 봅니다. bash 는 시그널 n 으로 죽은 명령의 종료 상태를 128+n 으로 매기며, 그 규칙과 다른 종료 상태의 뜻은 3장 노트의 [종료 상태 절](./03-01.%EC%85%B8%EC%9D%98%20%EC%8B%A4%EC%B2%B4%EB%8A%94%20%EC%8A%A4%ED%8A%B8%EB%A6%BC%EA%B3%BC%20%EB%B3%80%EC%88%98%EC%99%80%20%EC%A2%85%EB%A3%8C%20%EC%83%81%ED%83%9C%EB%8B%A4.md#4-숫자로-알리는-종료-상태)이 다룹니다. 아래는 `sleep 30 &` 에 시그널을 하나씩 보내고 `wait` 로 받은 값입니다.

| 종료 상태 | 시그널 | 흔히 보는 자리 |
|-----------|--------|---------------|
| 129 | `SIGHUP`(1) | 터미널이 끊긴 세션의 잡 |
| 130 | `SIGINT`(2) | Ctrl+C 로 끊은 명령 |
| 131 | `SIGQUIT`(3) | Ctrl+\\ |
| 134 | `SIGABRT`(6) | `abort(3)` 로 끝난 프로그램 |
| 137 | `SIGKILL`(9) | 유예 시간을 넘긴 종료, `timeout -s KILL` |
| 139 | `SIGSEGV`(11) | 잘못된 메모리 참조 |
| 141 | `SIGPIPE`(13) | 읽는 쪽이 먼저 끝난 파이프라인 |
| 142 | `SIGALRM`(14) | 잡지 않은 타이머 |
| 143 | `SIGTERM`(15) | 핸들러 없이 받은 종료 요청 |
| 152, 153 | `SIGXCPU`(24), `SIGXFSZ`(25) | CPU 시간·파일 크기 한도 초과 |

137 은 대개 누군가 기다리다 못해 `SIGKILL` 을 보냈다는 뜻입니다. 그 순서를 systemd 의 `systemctl stop` 이 가장 분명하게 보입니다. 아래 단계는 `systemd.kill(5)` 과 `systemd.service(5)` 에서 옮겼고, 기본값은 Debian 12 의 systemd 252 에서 `systemctl show` 로 확인했습니다.

| 순서 | systemd 가 하는 일 | 정하는 설정과 기본값 |
|------|-------------------|---------------------|
| 1 | `ExecStop=` 명령이 있으면 먼저 실행합니다 | `ExecStop=`, 없으면 건너뜁니다[^sdservice] |
| 2 | 남은 프로세스에 종료 시그널을 보내고 곧바로 `SIGCONT` 를 보냅니다 | `KillSignal=`, 기본 `SIGTERM`(15)[^sdkill] |
| 3 | 서비스가 스스로 끝나기를 기다립니다 | `TimeoutStopSec=`, 기본은 `DefaultTimeoutStopSec=` 의 90초[^sdservice] |
| 4 | 시간이 다 되면 강제로 끝냅니다 | `FinalKillSignal=`, 기본 `SIGKILL`(9) |
| - | 2와 4의 대상은 유닛의 cgroup 에 남은 모든 프로세스입니다 | `KillMode=`, 기본 `control-group`[^sdkill] |

2단계에서 `SIGCONT` 를 함께 보내는 것은 멈춰 있던 프로세스도 종료 시그널을 받아 깨끗이 끝날 수 있게 하려는 것입니다.[^sdkill] 그 이유는 다음 절의 정지 실험이 보입니다.

`SIGTERM` 을 잡고 무시하는 서비스에 `TimeoutStopSec=3` 을 주고 멈춘 기록입니다. 같은 방식으로 띄우되 `SIGTERM` 에 `exit 0` 하는 서비스는 0.005초 만에 `Result=success` 로 멈췄습니다.

```bash
systemctl stop stubborn
journalctl -u stubborn -o short-precise
# 05:08:01.131827 stubborn.sh[1262]: TERM 받음, 무시
# 05:08:04.249285 systemd[1]: stubborn.service: State 'stop-sigterm' timed out. Killing.
# 05:08:04.249325 systemd[1]: stubborn.service: Killing process 1262 (stubborn.sh) with signal SIGKILL.
# 05:08:04.249399 systemd[1]: stubborn.service: Killing process 1283 (sleep) with signal SIGKILL.
# 05:08:04.250047 systemd[1]: stubborn.service: Main process exited, code=killed, status=9/KILL
# 05:08:04.250065 systemd[1]: stubborn.service: Failed with result 'timeout'.
systemctl show stubborn -p Result -p ExecMainStatus
# Result=timeout
# ExecMainStatus=9
```

`SIGTERM` 을 받은 지 3.1초 뒤에 `stop-sigterm` 단계가 시간을 넘겼습니다. 그러자 systemd 가 주 프로세스 1262 와 그 자식 `sleep` 1283 에 함께 `SIGKILL` 을 보냈습니다. 자식까지 죽은 것이 `KillMode=control-group` 의 효과입니다. 유닛 설정이 없었다면 같은 일이 90초 뒤에 일어났을 것입니다. 서비스 중지가 꼭 90초씩 걸린다면 그 서비스가 `SIGTERM` 에 끝나지 않는다는 뜻입니다.

![systemctl stop 이 SIGTERM 에서 SIGKILL 까지 가는 3초](./_assets/09-01.stop-sequence.svg)

쿠버네티스가 파드를 내릴 때도 `SIGTERM` 을 보내고 유예 시간 뒤 `SIGKILL` 을 보내는 같은 모양을 따릅니다. 그 흐름은 [Kubernetes in Action 노트의 종료 단계](../../../08_cloud/book/kubernetes-in-action/06-03.lifecycle%20hook%EA%B3%BC%20Pod%20%EC%83%9D%EC%95%A0%EC%A3%BC%EA%B8%B0%20%EC%A0%84%EC%B2%B4.md#6-종료-단계--prestop-hook에서-sigterm까지)가 다룹니다.

### 멈춤과 재개 — STOP·TSTP·CONT

프로세스가 살아 있는데 CPU 도 쓰지 않고 `kill` 도 먹지 않는 것처럼 보이면 `ps` 의 `STAT` 열부터 봅니다. `T` 면 멈춘 상태입니다.

```bash
sleep 300 & p=$!
ps -o pid,stat,cmd -p $p
#     PID STAT CMD
#    4334 S    sleep 300
kill -STOP $p; ps -o pid,stat,cmd --no-headers -p $p; grep ^State /proc/$p/status
#    4334 T    sleep 300
# State:	T (stopped)
kill -TERM $p; ps -o pid,stat,cmd --no-headers -p $p; grep -E '^(SigPnd|ShdPnd)' /proc/$p/status
#    4334 T    sleep 300
# SigPnd:	0000000000000000
# ShdPnd:	0000000000004000
kill -CONT $p; wait $p; echo "exit=$?"  # exit=143
```

멈춘 프로세스에 `SIGTERM` 을 보내도 그대로 `T` 입니다. 시그널이 사라진 것은 아닙니다. 프로세스 전체가 받을 대기 시그널을 담는 `ShdPnd` 에 `0x4000` 이 섰습니다.[^proc] 0 부터 센 14번 비트이고, 비트 n-1 이 시그널 n 이므로 `SIGTERM`(15)입니다. `SIGCONT` 로 깨우자 기다리던 `SIGTERM` 이 전달되어 143 으로 끝났습니다. systemd 가 종료 시그널 뒤에 `SIGCONT` 를 붙여 보내는 이유가 이것입니다.

`SIGSTOP` 과 `SIGTSTP` 는 둘 다 기본 동작이 정지이지만 잡을 수 있느냐가 다릅니다. Ctrl+Z 가 보내는 `SIGTSTP` 는 핸들러로 잡을 수 있습니다.

```bash
cat tstp.sh
# trap "echo TSTP 받았지만 멈추지 않음" TSTP
# for i in 1 2 3; do sleep 1; done
# echo 끝까지 실행
./tstp.sh & p=$!; sleep 0.5; kill -TSTP $p; wait $p; echo "exit=$?"
# TSTP 받았지만 멈추지 않음
# 끝까지 실행
# exit=0
```

편집기처럼 멈추기 전에 화면을 정리해야 하는 프로그램이 `SIGTSTP` 를 잡는 이유가 이것입니다. 반대로 `SIGSTOP` 은 프로그램이 어떻게 짜였든 멈춥니다. 셸의 `fg` 와 `bg` 가 잡을 멈추고 이어 돌리는 흐름은 3장 노트의 [잡의 상태를 옮기는 명령](./03-01.%EC%85%B8%EC%9D%98%20%EC%8B%A4%EC%B2%B4%EB%8A%94%20%EC%8A%A4%ED%8A%B8%EB%A6%BC%EA%B3%BC%20%EB%B3%80%EC%88%98%EC%99%80%20%EC%A2%85%EB%A3%8C%20%EC%83%81%ED%83%9C%EB%8B%A4.md#잡의-상태를-옮기는-명령)이 다룹니다.

![STAT 이 S 에서 T 로 갔다가 CONT 에 깨어 143 으로 끝나는 길](./_assets/09-01.stop-cont.svg)

### /proc/PID/status 로 배치 읽기

이 프로세스가 `SIGTERM` 을 잡고 있는지, 무시하고 있는지를 소스 없이 알아야 할 때가 있습니다. `/proc/PID/status` 의 `SigBlk`·`SigIgn`·`SigCgt` 가 막고 있는 시그널, 무시하는 시그널, 잡는 시그널을 16진 마스크로 보입니다.[^proc]

```bash
bash -c 'grep -E "^Sig(Ign|Cgt)" /proc/$$/status
         trap "" TERM; trap : USR1 HUP
         grep -E "^Sig(Ign|Cgt)" /proc/$$/status'
# SigIgn:	0000000200000004
# SigCgt:	0000000000010002
# SigIgn:	0000000200004004
# SigCgt:	0000000000010203
```

같은 셸에서 `trap` 을 걸기 전과 뒤를 찍었습니다. `SigIgn` 에는 `0x4000` 이 더해졌습니다. 14번 비트, 곧 `trap "" TERM` 으로 무시하게 된 15번 `SIGTERM` 입니다. `SigCgt` 는 `0x10002` 에서 `0x10203` 으로 바뀌었습니다. 0번과 9번 비트가 더해졌고 각각 1번 `SIGHUP` 과 10번 `SIGUSR1` 입니다. 처음부터 서 있던 1번과 16번 비트는 bash 가 스스로 잡는 2번 `SIGINT` 와 17번 `SIGCHLD` 입니다.

`SigIgn` 의 33번 비트(`0x200000000`, 시그널 34)는 이 셸이 건 것이 아닙니다. 같은 비트가 컨테이너의 PID 1 에도 서 있으니, 컨테이너를 띄운 쪽이 무시를 걸었고 무시가 `execve` 를 지나도 남는다는 규칙대로 물려받은 것입니다. `nohup` 도 같은 규칙을 씁니다. 같은 셸에서 `sleep 100 &` 의 `SigIgn` 은 `0000000200000006` 이고 `nohup sleep 100 &` 은 `0000000200000007` 이어서, 0번 비트인 `SIGHUP` 하나만 다릅니다.

![SigCgt 0x10203 을 비트로 풀면 잡는 시그널 넷이 나온다](./_assets/09-01.sigmask.svg)

### 세션 단위로 끝내기 — loginctl 과 pkill -t

SSH 로 들어온 사용자가 남긴 프로세스를 정리할 때는 PID 를 하나씩 찾지 않고 세션이나 터미널 단위로 끝냅니다. 세션과 제어 터미널의 개념은 3장 노트의 [세션과 제어 터미널](./03-01.%EC%85%B8%EC%9D%98%20%EC%8B%A4%EC%B2%B4%EB%8A%94%20%EC%8A%A4%ED%8A%B8%EB%A6%BC%EA%B3%BC%20%EB%B3%80%EC%88%98%EC%99%80%20%EC%A2%85%EB%A3%8C%20%EC%83%81%ED%83%9C%EB%8B%A4.md#세션과-제어-터미널)이 다룹니다. systemd 를 쓰는 시스템에서는 `systemd-logind` 가 로그인마다 세션을 만들고 `loginctl` 로 다룹니다.

```bash
loginctl list-sessions
# SESSION  UID USER SEAT TTY
#      10 1000 bob       pts/1
#       9 1000 bob       pts/0
loginctl session-status 9
# 9 - bob (1000)
# 	  Leader: 1304 (sshd)
# 	     TTY: pts/0
# 	 Service: sshd; type tty; class user
# 	    Unit: session-9.scope
# 		  ├─1304 "sshd: bob [priv]"
# 		  ├─1323 "sshd: bob@pts/0"
# 		  └─1325 sleep 901
loginctl terminate-session 9; loginctl list-sessions
# SESSION  UID USER SEAT TTY
#      10 1000 bob       pts/1
pgrep -t pts/1 -a                       # 1326 sleep 900
pkill -t pts/1; loginctl list-sessions  # No sessions.
```

`session-status` 는 세션의 리더와 터미널, 그리고 세션에 속한 프로세스를 `session-9.scope` 라는 유닛 아래 나무로 보입니다. `terminate-session` 은 그 세션의 프로세스를 모두 죽이고 세션에 붙은 자원을 거둡니다.[^loginctl] `pkill -t pts/1` 은 제어 터미널이 `pts/1` 인 프로세스에 `SIGTERM` 을 보냅니다. 터미널 이름은 `/dev/` 없이 적습니다.[^pgrep] 여기서는 원격 명령 `sleep 900` 이 죽자 SSH 연결이 끝나 세션 10 도 사라졌습니다.



## 2. 데이터를 나르는 명명 파이프와 도메인 소켓

> 네트워크 없이 같은 기계의 프로세스에게 데이터를 넘기려면, 방향과 받는 쪽의 수에 따라 도구가 달라집니다.

같은 기계에 있는 두 프로그램을 붙이려다 보면 대뜸 TCP 소켓을 여는 손버릇이 나옵니다. 네트워크를 거칠 이유가 없는데도 그렇습니다. 데이터를 한쪽으로만 흘리면 되는지, 주고받아야 하는지에 따라 훨씬 가벼운 길이 이미 있습니다. 실제로 쓰이는 예를 저자가 하나 듭니다. Docker 데몬이 컨테이너를 관리할 때 설정 가능한 소켓을 씁니다. 6장에서 본 컨테이너 런타임이 여기 다시 나옵니다.

### 명명 파이프 — 프로세스보다 오래 사는 이름

3장에서 파이프(`|`)로 한 프로세스의 표준 출력을 다른 프로세스의 표준 입력에 이어 데이터를 넘기는 것을 봤습니다. 그것을 이름 없는 파이프라고 부릅니다. 여기서 한 걸음 나아간 것이 명명 파이프로, 사용자 정의 이름을 붙일 수 있는 파이프입니다. 이름 없는 파이프와 같은 점부터 저자가 적습니다. 보통의 파일 입출력으로 다루며 먼저 들어간 것이 먼저 나옵니다. 다른 점은 수명입니다. 명명 파이프의 수명은 그것을 쓰는 프로세스에 묶이지 않습니다. 기술적으로는 파이프를 감싼 껍데기이며 `pipefs` 라는 가짜 파일시스템을 씁니다. 5장에서 본 그 부류입니다.

```bash
mkfifo examplepipe
ls -l examplepipe
```

```bash
prw-rw-r-- 1 mh9 mh9 0 Oct  2 14:04 examplepipe
```

권한 문자열의 첫 글자가 `p` 인 것이 명명 파이프라는 표시입니다. 크기가 `0` 인 것은 FIFO 특수 파일이 파일시스템에 내용을 갖지 않기 때문입니다. 파일시스템의 항목은 프로세스가 이름으로 파이프에 닿게 해 주는 기준점 노릇만 하고, 데이터는 커널 안에서 넘어갑니다.[^fifo] 이제 발행 쪽과 소비 쪽을 하나씩 붙입니다.

```bash
while true ; do echo "x" > examplepipe ; sleep 5 ; done &
while true ; do cat < examplepipe ; sleep 5 ; done &
```

```bash
[1] 19628
[2] 19636
x
x
...
```

저자가 붙인 주의가 하나 있습니다. 다른 프로세스가 `examplepipe` 에서 읽지 않는 한 파이프가 막히고 더 쓸 수 없다는 것입니다. 터미널에 `x` 가 대략 5초마다 나타나는 것은 PID 19636 인 프로세스가 `cat` 으로 읽어 갈 수 있을 때마다 나오기 때문입니다.

![이름이 붙은 파이프는 프로세스보다 오래 산다](./_assets/09-01.named-pipe.svg)

막히는 자리를 직접 재어 볼 수 있습니다.

```bash
mkfifo p1
timeout 2 bash -c "echo x > p1"; echo "종료상태=$?"
```

```bash
종료상태=124
```

`124` 는 §1 에서 본 대로 `timeout` 이 시간이 다 되어 끝냈다는 뜻입니다. 읽는 쪽을 하나 붙이고 같은 명령을 다시 치면 곧바로 `0` 으로 끝납니다. `fifo(7)` 이 그 이유를 적습니다. FIFO 는 데이터가 오가려면 읽는 쪽과 쓰는 쪽 양끝이 모두 열려야 하고, 보통은 다른 쪽이 열릴 때까지 열기 자체가 막힙니다.[^fifo]

한계도 저자가 바로 짚습니다. 보통 파일처럼 보이고 그렇게 다뤄지지만 방향이 하나이고 소비자도 하나뿐입니다. 여러 프로세스가 같은 FIFO 를 읽기로 열 수는 있습니다.[^fifo] 그러나 소비자 둘을 붙이고 여섯 줄을 흘려 보내면 두 쪽이 받은 줄을 합쳐 늘 여섯이고 같은 줄이 두 번 나오지 않습니다. 데이터가 복제되지 않는다는 뜻입니다.

어느 쪽이 어느 줄을 받을지는 정해져 있지 않습니다. 같은 스크립트를 여섯 번 돌리니 매번 여섯 줄이 한쪽으로 몰렸는데 몰리는 쪽이 회차마다 바뀌었고, 다른 환경에서는 두 쪽에 나뉘어 들어갔습니다. 분배 방식을 설계의 근거로 삼으면 안 됩니다. 여럿에게 같은 내용을 보내야 한다면 파이프가 아닌 다른 것을 씁니다.

### 유닉스 도메인 소켓 — 양방향과 여러 소비자

7장에서 네트워크 맥락의 소켓을 봤습니다. 한 기계 안에서만 동작하는 다른 종류의 소켓도 있고, 그중 하나가 유닉스 도메인 소켓입니다.

저자의 정의로는 양방향이고 다방향인 통신 종단점입니다. 소비자를 여럿 둘 수 있다는 뜻입니다. 앞 절의 두 한계가 여기서 풀리며, 저자가 시그널과 파이프 다음에 이것을 놓은 이유가 그것입니다.

| 갈래 | 저자가 적은 것 |
|------|---------------|
| `SOCK_STREAM` | 스트림 지향 |
| `SOCK_DGRAM` | 데이터그램 지향 |
| `SOCK_SEQPACKET` | 순서 있는 패킷 |

주소 지정은 파일시스템 경로 이름으로 합니다. IP 주소와 포트 대신 단순한 파일 경로면 충분합니다. 7장에서 포트가 기계 안의 서비스를 가리키는 번호였다면, 여기서는 그 역할을 경로가 대신합니다.

보통은 프로그램 안에서 도메인 소켓을 쓰게 된다고 저자가 적습니다. 다만 시스템을 진단하다가 명령줄에서 소켓과 직접 주고받아야 하는 상황을 만날 수 있고, 그때 쓸 도구로 `socat` 을 듭니다. 8장에서 양방향 바이트 스트림을 세우는 도구로 이미 나온 이름입니다.

이 절의 서두에서 저자가 든 예, 곧 Docker 데몬이 컨테이너를 관리하며 쓰는 소켓이 바로 유닉스 도메인 소켓입니다. 파일 경로로 주소를 지정한다는 성질이 `/var/run/docker.sock` 이라는 경로로 그대로 드러납니다. 컨테이너에 그 경로를 마운트해 주면 컨테이너 안에서 호스트의 Docker 를 부릴 수 있게 되는 것도, 주소가 포트가 아니라 파일이기 때문입니다.



## 3. 컨테이너보다 강한 격리, 가상 머신

> 컨테이너가 있는데 왜 아직 VM 을 쓰는가 하는 물음에, 저자는 격리의 세기가 다르다고 답합니다.

![아래에서 위로 — CPU 가 받쳐야 커널이 하이퍼바이저가 된다](./_assets/09-01.vm-stack.svg)

컨테이너로 충분할 것 같은 자리에서도 공용 클라우드는 여전히 VM 을 나눠 줍니다. 저자가 서두에서 그 대비를 분명히 합니다. 6장에서 본 컨테이너는 애플리케이션 수준의 의존성 관리에 좋고, VM 은 워크로드에 강한 격리를 준다는 것입니다. 둘은 같은 문제의 두 답이 아니라 다른 문제의 답입니다. VM 을 만나는 자리도 적어 둡니다. 공용 클라우드 맥락에서 가장 자주 만나고 일반적으로는 데이터 센터에서 만납니다. 로컬에서 쓰는 것도 쓸모가 있다고 덧붙이는데, 시험용이거나 분산 시스템을 흉내 낼 때입니다.

위 도식이 저자가 밑에서부터라고 밝힌 순서입니다. 맨 아래 CPU 가 하드웨어 가상화를 지원해야 합니다. 그 위에 리눅스 커널 안의 KVM 이 있습니다. 유저 공간에는 VMM 과 게스트 커널과 게스트 프로세스가 놓입니다. VMM 은 VM 을 관리하고 QEMU 나 Firecracker 처럼 가상 장치를 흉내 냅니다. `libvirt` 도 있는데 VMM 을 표준화하려는 일반 API 를 노출하는 라이브러리입니다. 저자는 그것을 그림에 따로 그리지 않고 VMM 덩어리의 일부로 보라고 적습니다.

격리의 뜻은 이렇습니다. 호스트 커널 위에서 네이티브로 도는 프로세스들은 게스트 프로세스와 격리됩니다. 대체로 호스트의 물리 CPU 와 메모리는 게스트의 활동에 영향받지 않습니다. VM 에 호스트 시스템 접근을 특별히 주지 않았다면, VM 안에서 공격이 일어나도 호스트 커널과 프로세스는 무사합니다. 저자가 여기에 단서를 답니다. 실무에서는 예외가 있을 수 있고, rowhammer 나 Meltdown 과 Spectre 가 그 예라는 것입니다. 격리가 설계상의 보장이지 물리적 보장이 아니라는 뜻입니다.

### KVM — 하이퍼바이저가 된 커널

KVM 은 가상화 확장을 지원하는 x86 하드웨어를 위한 리눅스 고유의 가상화 해법입니다. AMD-V 나 Intel VT 가 그 확장입니다. 커널 모듈은 두 부분입니다. 핵심 모듈 `kvm.ko` 와 CPU 아키텍처별 모듈 `kvm-intel.ko` 또는 `kvm-amd.ko` 입니다. 여기서 저자가 짚는 한 문장이 이 절의 핵심입니다. KVM 에서는 리눅스 커널이 곧 하이퍼바이저이고 무거운 일의 대부분을 커널이 맡습니다. 그 위에 입출력 가상화를 가능하게 하는 Virtio 같은 드라이버가 붙습니다.

요즘 하드웨어는 대개 가상화를 지원하고 KVM 도 이미 있지만, 내 시스템이 쓸 수 있는지 확인하는 방법을 저자가 둘로 보입니다.

```bash
grep 'svm\|vmx' /proc/cpuinfo
lsmod | grep kvm
```

```bash
flags        : fpu vme de pse tsc msr pae mce cx8 apic sep mtrr pge mca
pat pse36 clflush dts acpi mmx fxsr sse sse2 ss ht tm pbe syscall nx pdpe1
... ds_cpl vmx tm2 ssse3 sdbg cx16 xtpr pdcm sse4_1 sse4_2 x2apic movbe popcnt
...
kvm_intel   253952  0
kvm         659456  1 kvm_intel
```

첫 명령은 CPU 정보에서 `svm` 이나 `vmx` 를 찾습니다. CPU 마다 보고하므로 코어가 여덟이면 같은 `flags` 덩어리가 여덟 번 나온다고 저자가 덧붙입니다. 위 출력에 `vmx` 가 있으니 하드웨어 보조 가상화는 문제가 없습니다.

두 번째 명령은 KVM 커널 모듈이 올라와 있는지 봅니다. `kvm_intel` 모듈이 올라와 있으니 KVM 을 쓸 준비가 끝났습니다. `lsmod` 의 셋째 열은 그 모듈을 쓰고 있는 것의 수이고, 이어지는 이름은 누가 쓰는지입니다. 그래서 `kvm` 행의 `1 kvm_intel` 은 `kvm` 을 쓰는 것이 하나이며 그것이 `kvm_intel` 이라는 뜻입니다. `kvm_intel` 행의 `0` 은 아직 쓰는 것이 없다는 뜻이고 VM 을 띄우면 올라갑니다. 핵심 모듈과 아키텍처별 모듈이 얹힌 모양이 이 두 줄에 그대로 보입니다.

### Firecracker — HTTP 로 다루는 microVM

Firecracker 는 KVM 인스턴스를 관리할 수 있는 VMM 입니다. Rust 로 쓰였고 Amazon Web Services 에서 주로 서버리스 제품을 위해 개발했습니다. AWS Lambda 와 AWS Fargate 가 그 제품입니다. 설계 목표는 같은 물리 기계에서 여러 테넌트의 워크로드를 안전하게 돌리는 것입니다. Firecracker VMM 이 관리하는 것을 microVM 이라 부릅니다. 호스트에 HTTP API 를 드러내어 microVM 을 띄우고 조회하고 멈출 수 있게 합니다.

장치를 다루는 방식도 적어 둡니다. 네트워크 인터페이스는 호스트의 TUN/TAP 장치로 흉내 냅니다. 블록 장치는 호스트의 파일이 뒤를 받치며 Virtio 장치를 지원합니다.

보안과 관측 쪽에도 앞 장들의 이름이 돌아옵니다. Firecracker 는 기본으로 seccomp 필터를 써서 자신이 쓸 수 있는 호스트 시스템 콜을 제한합니다. 4장에서 본 그 seccomp 입니다. cgroups 도 함께 쓸 수 있습니다. 관측 쪽에서는 Firecracker 에서 로그와 메트릭을 모을 수 있는데, 그 통로가 §2 의 명명 파이프입니다.



## 4. 고치지 않고 새로 만드는 현대 배포판

> 기계 한 대를 손보는 일과 수백 대를 손보는 일은 다른 문제이고, 그 차이가 배포판의 설계를 바꿨습니다.

![컨테이너 중심 배포판 넷 중 둘은 한 뿌리에서 갈렸다](./_assets/09-01.distro-lineage.svg)

컨테이너가 늘면서 호스트 운영체제의 역할이 바뀌었다고 저자가 적습니다. 컨테이너 맥락에서 전통적인 패키지 관리자는 다른 역할을 맡습니다. 대부분의 베이스 컨테이너 이미지는 특정 리눅스 배포판에서 만들어집니다. 그 안의 의존성은 `.deb` 나 `.rpm` 으로 채워집니다. 애플리케이션 수준 의존성은 그 위에서 컨테이너 이미지가 통째로 쌉니다. 그다음이 이 절의 논지입니다. 시스템을 조금씩 고쳐 나가는 일이 큰 도전이 된다는 것인데 규모가 커질수록 특히 그렇습니다. 기계 무리를 관리해야 할 때가 그런 경우입니다.

그래서 현대 배포판의 초점이 점점 불변성으로 옮겨 갑니다. 설정이나 코드에 어떤 변경이든 생기면 그것이 새 산출물을 만들게 한다는 발상입니다. 보안 문제를 고치는 패치나 새 기능을 생각하면 됩니다. 새로 만들어진 컨테이너 이미지가 뜨는 것이지 돌고 있는 시스템을 바꾸는 것이 아닙니다. 저자가 "현대 배포판" 이라 말할 때의 뜻도 못 박습니다. 컨테이너 중심이며 불변성과 자동 업그레이드를 앞세운 배포판입니다. 자동 업그레이드는 Chrome 이 개척했다고 덧붙입니다.

전통 배포판도 나쁠 것이 없다고 먼저 적어 둡니다. 필요와 취향에 따라 설치부터 패치까지 전부 직접 챙기며 완전히 통제하는 쪽과, 대부분의 일을 배포판이 대신해 주는 완전 관리형 사이에서 고르면 됩니다.

| 배포판 | 누가 | 앱을 올리는 방식 | 특징 |
|--------|------|-----------------|------|
| RHCOS | Red Hat | 컨테이너 | 단독으로 쓰라고 만든 것이 아니라 OpenShift Container Platform 안에서 씁니다 |
| Flatcar Container Linux | Kinvolk GmbH, 지금은 Microsoft | 컨테이너 | Nebraska 로 자동 업그레이드하고 Ignition 으로 부팅 장치를 세밀하게 제어합니다 |
| Bottlerocket | AWS | OCI 이미지 | `dm-verity` 기반의 대체로 읽기 전용인 무결성 검사 파일시스템을 씁니다 |
| RancherOS | Rancher, 지금은 SUSE | Docker 컨테이너 | Docker 를 둘 돌립니다. 첫 프로세스로 뜨는 시스템 Docker 와 앱을 만드는 사용자 Docker 입니다 |

넷 가운데 패키지 관리자를 두지 않는다고 저자가 적은 것은 셋입니다. CoreOS Linux 가 처음부터 그랬습니다. Flatcar 는 그 전통을 이어 모든 것을 컨테이너로 돌립니다. Bottlerocket 은 패키지 관리자 대신 OCI 이미지 기반 모델로 업그레이드와 롤백을 합니다. RHCOS 와 RancherOS 를 두고는 패키지 관리자를 언급하지 않으므로, 넷 모두 그렇다고 넘겨짚지 않습니다. Bottlerocket 에 저자가 붙인 접근 이야기도 옮길 만합니다. 접근해서 제어하려면 별도의 `containerd` 인스턴스에서 도는 제어 컨테이너를 씁니다. SSH 로도 되지만 권장하지는 않는다고 적습니다.

계보에서 갈림목은 Container Linux 하나입니다. 2013년 CoreOS 라는 신생 기업이 CoreOS Linux 를 내놓았고 나중에 Container Linux 로 이름을 바꿨습니다. 주요 기능은 시스템 업데이트를 위한 이중 파티션 구조와 패키지 관리자의 부재였습니다. 그 생태계에서 나온 도구 중 지금도 쓰이는 것으로 저자는 `etcd` 를 꼽습니다. 설정 작업을 위한 `/etc` 디렉터리의 분산 버전이라 생각하면 된다고 설명합니다.

Red Hat 은 CoreOS 를 인수한 뒤 CoreOS Linux 를 자사의 Project Atomic 과 합치겠다고 밝혔고, 그 합병이 RHCOS 로 이어졌습니다. 그 발표 조금 뒤에 독일 스타트업 Kinvolk GmbH 가 Container Linux 를 포크했습니다. Flatcar Container Linux 라는 새 이름으로 개발을 이어 가겠다는 발표였습니다.



## 5. 인증을 프로그램 밖으로 빼는 두 방법

> 프로그램마다 인증을 따로 짜면 인증 방식이 바뀔 때마다 모든 프로그램을 고쳐야 합니다.

![믿을 수 없는 망 위에서 서로의 신원을 증명하는 네 걸음](./_assets/09-01.kerberos.svg)

인증 코드를 프로그램 안에 직접 짜 두면 인증 방식이 바뀌는 날 프로그램을 전부 다시 건드려야 합니다. LDAP 을 붙이라는 요구가 오면 어디를 고쳐야 할지부터 세어 보게 됩니다.

4장에서 접근 제어 장치를 여럿 봤습니다. 인증은 사용자의 신원을 확인하는 일이고 어떤 종류의 인가에도 앞서는 전제 조건이라는 구분도 거기서 세웠습니다. 이 절은 그중 인증 쪽에서 널리 쓰이는 도구 둘을 짧게 다루고, 같은 PAM 위에서 로그인마다 자원 한도를 거는 모듈 하나를 더합니다.

### Kerberos — 티켓과 세션 키로 도는 네 걸음

Kerberos 는 매사추세츠 공과대학교가 1980년대에 개발한 인증 모음입니다. 오늘날에는 2005년 7월의 RFC 4120 과 관련 IETF 문서에 형식적으로 규정되어 있습니다. RFC 4120 은 앞선 RFC 1510 을 대체했습니다.[^rfc4120] 핵심 발상을 저자가 한 문장으로 적습니다. 우리는 대개 안전하지 않은 망을 상대하지만, 클라이언트와 서비스가 서로에게 신원을 증명할 안전한 방법을 원한다는 것입니다.

위 도식의 네 걸음이 저자가 번호로 적은 그대로입니다.

1. 클라이언트가 Key Distribution Center 라는 Kerberos 구성요소에 특정 서비스에 쓸 자격증명을 요청합니다.
2. KDC 가 그 서비스용 티켓과 임시 암호화 키를 함께 내줍니다. 그 임시 키가 세션 키입니다.
3. 클라이언트가 티켓을 서비스에 건넵니다. 티켓 안에는 클라이언트의 신원과 세션 키의 사본이 들어 있습니다.
4. 클라이언트와 서비스가 나눠 가진 세션 키로 클라이언트를 인증합니다. 선택적으로 서비스도 같은 키로 인증할 수 있습니다.

저자가 과제도 둘 듭니다. KDC 가 중심 역할을 맡는다는 점이 단일 장애점이 되고, 시간 요구가 엄격해 클라이언트와 서버가 NTP 로 시계를 맞춰야 합니다. 7장에서 NTP 를 애플리케이션 계층 프로토콜로 본 것이 여기서 운영 조건으로 돌아옵니다.

시간 요구가 어디서 오는지는 규격에 있습니다. RFC 4120 은 인증이 서버의 현재 시각에 기반하므로 시계가 느슨하게 동기화되어 있어야 한다고 적습니다.[^rfc4120] 서버의 시각과 클라이언트가 보낸 인증자 안의 시각이 허용 오차보다 벌어지면 서버는 `KRB_AP_ERR_SKEW` 오류를 돌려줍니다. 오류 번호는 37 이고 이름은 "Clock skew too great" 입니다. 규격은 허용 오차의 예로 5분을 듭니다. MIT krb5 의 `clockskew` 설정 기본값도 300초입니다.[^krb5] 비밀번호가 맞는데도 인증이 거절되고 이 오류가 보이면 두 기계의 시계부터 비교합니다.

NTP 는 그 조건을 채우는 흔한 수단입니다. 총평도 균형이 잡혀 있습니다. 운영하고 관리하기가 간단하지는 않지만 Kerberos 는 기업과 클라우드 제공자에서 널리 쓰이고 지원됩니다.

### PAM — 프로그램 밖에서 갈아 끼우는 인증

역사적으로 프로그램은 사용자 인증 과정을 스스로 관리했습니다. PAM 과 함께 구체적인 인증 방식과 무관하게 프로그램을 개발하는 유연한 길이 리눅스에 들어왔다고 저자는 적습니다. Linux-PAM 의 문서는 그 뿌리로 1995년 10월의 DCE-RFC 86.0 을 들며 그 제안을 낸 Sun Microsystems 에 감사를 표합니다.[^pam] 구조는 모듈식입니다. 개발자에게는 PAM 과 연결할 강력한 라이브러리를 주며 시스템 관리자에게는 서로 다른 모듈을 꽂아 넣을 수 있게 합니다.

| 모듈 | 하는 일 |
|------|--------|
| `pam_localuser` | 사용자가 `/etc/passwd` 에 있을 것을 요구합니다 |
| `pam_keyinit` | 세션 키링을 위한 것입니다 |
| `pam_krb5` | Kerberos 5 의 비밀번호 기반 검사를 위한 것입니다 |

마지막 줄이 앞 절과 이어집니다. Kerberos 를 쓰기로 했다면 프로그램을 고치는 것이 아니라 PAM 설정에 모듈 하나를 꽂는 것으로 끝납니다. 그것이 인증을 프로그램 밖으로 뺀다는 말의 실제 모습입니다.

### pam_limits — 로그인할 때 거는 자원 한도

`limits.conf` 에서 열 수 있는 파일 수를 올렸는데 돌고 있는 서비스의 한도가 그대로인 일이 흔합니다. 한도를 거는 것이 PAM 모듈이고, 그 모듈은 로그인할 때만 돌기 때문입니다.

`pam_limits` 는 PAM 의 session 단계에만 끼는 모듈입니다. 세션을 열 때 `/etc/security/limits.conf` 를 읽고 이어서 `/etc/security/limits.d/*.conf` 를 C 로케일의 이름순으로 읽으며, 효과는 파일들을 그 순서로 이어 붙인 것과 같습니다.[^pamlimits] Debian 12 에서는 `/etc/pam.d/login`, `/etc/pam.d/su`, `/etc/pam.d/runuser` 에 `session required pam_limits.so` 줄이 있습니다. 그래서 `su` 로 사용자를 바꿀 때도 한도가 다시 걸립니다.

한 줄은 `<domain> <type> <item> <value>` 넷으로 이루어집니다.[^limits]

| 칸 | 쓸 수 있는 값 |
|----|--------------|
| domain | 사용자 이름, `@그룹`, 모두를 뜻하는 `*`, uid 범위 `1000:2000`, gid 범위 `@500:600`. `%` 는 `maxlogins` 에만 씁니다 |
| type | `soft`(지금 적용되는 값), `hard`(soft 를 올릴 수 있는 상한), `-`(둘 다) |
| item | `nofile`(열린 파일 수), `nproc`(프로세스 수), `core`, `fsize`, `cpu`(분), `memlock`, `as`, `maxlogins` 등 |

같은 항목을 여러 줄이 말하면 어느 줄이 이길지는 두 규칙이 정합니다. 사용자 한 사람을 지목한 줄은 그룹이나 `*` 줄보다 우선합니다.[^limits] 같은 우선순위끼리는 나중에 읽힌 줄이 이깁니다. 그리고 `*` 와 그룹 줄은 root 에 걸리지 않으므로 root 에 한도를 주려면 `root` 라고 이름을 적어야 합니다.[^limits] Debian 12 컨테이너에서 `limits.d` 에 `10-a.conf` 와 `20-b.conf` 두 파일을 놓고 `su alice -c 'ulimit -Sn'` 으로 확인했습니다. 이름순이라 `10-a.conf` 가 먼저 읽힙니다.

| `10-a.conf` | `20-b.conf` | 결과 |
|-------------|-------------|------|
| `alice soft nofile 2048` | `alice soft nofile 4096` | 4096. 같은 사용자 줄이라 나중 파일이 이깁니다 |
| `alice soft nofile 2048` | `* soft nofile 4096` | 2048. 나중에 읽혀도 `*` 는 사용자 줄을 못 이깁니다 |
| `* soft nofile 2048` | `alice soft nofile 4096` 과 `* soft nofile 3000` | 4096 |
| 없음 | `* - nofile 5000` | alice 는 soft·hard 5000, root 는 그대로 1024·1048576 |
| 없음 | `* - nofile 5000` 과 `root - nofile 6000` | root 도 6000·6000 |

![limits 파일을 읽는 순서와 이기는 줄](./_assets/09-01.pam-limits.svg)

한도는 로그인마다 새로 걸리고 소급되지 않습니다. `limits.conf(5)` 는 한도가 전역이나 영구가 아니라 그 세션 동안만 있다고 적습니다.[^limits] 파일을 바꾸기 전에 띄운 alice 의 `sleep` 은 바꾼 뒤에도 `/proc/PID/limits` 가 `Max open files 1024 1048576` 그대로였습니다. 같은 컨테이너에서 PAM 을 거치지 않은 `docker exec` 셸은 `ulimit -Sn` 이 20480 이었습니다.

systemd 가 띄운 서비스도 로그인을 거치지 않습니다. 유닛에 `PAMName=` 을 주지 않으면 서비스 프로세스에는 PAM 세션이 열리지 않습니다.[^sdexec] 그래서 서비스의 한도는 `limits.conf` 가 아니라 유닛의 `LimitNOFILE=` 같은 설정이 정합니다. Debian 12 의 기본 서비스는 `systemctl show` 로 `LimitNOFILE=1048576`, `LimitNOFILESoft=1024` 였습니다.

배포판이 기본으로 넣어 두는 파일도 있습니다. CentOS 7 의 `pam-1.1.8` 패키지는 `/etc/security/limits.d/20-nproc.conf` 에 `* soft nproc 4096` 과 `root soft nproc unlimited` 두 줄을 둡니다. 같은 확인에서 Rocky Linux 8.9 와 9.3 컨테이너 이미지에는 그 파일이 없었습니다. 한도가 어디서 왔는지 모를 때는 `limits.d` 를 이름순으로 훑는 것이 첫 순서입니다.



## 6. 아직 주류가 아닌 것들

> 저자가 집필 시점에 주류가 아니라고 명시한 구간입니다. 지금 배울 것이 아니라 지켜볼 것으로 읽는 편이 맞습니다.

리눅스에서 다음에 크게 바뀔 자리가 어디인지 궁금할 때 볼 구간입니다. 이 절의 항목들이 공통으로 갖는 것은 집필 시점에 아직 주류에 들어오지 않았다는 점이라고 저자가 먼저 밝힙니다. 앞으로의 전개가 궁금하거나 리눅스에 아직 성장 여지가 큰 곳이 어디인지 궁금하다면 읽어 보라는 조건도 함께 답니다.

NixOS 는 소스 기반 배포판이고 패키지 관리와 시스템 설정에 함수형 접근을 취하며 업그레이드의 롤백도 그렇게 다룹니다. 함수형이라 부르는 이유를 저자가 밝히는데, 산출물이 불변성에 기반하기 때문입니다. Nix 패키지 관리자가 커널부터 시스템 패키지와 앱까지 운영체제 전체를 빌드합니다. 그리고 다중 사용자 패키지 관리와 같은 패키지의 여러 버전 설치를 허용합니다. 한 가지 대가도 적혀 있습니다. 대부분의 다른 배포판과 달리 NixOS 는 5장에서 본 표준 파일시스템 배치를 따르지 않습니다.

시스템 프로그램이 `/usr/bin` 이나 `/usr/lib` 에 있고 설정이 대개 `/etc` 에 있는 그 배치입니다. 다 받아들이고 싶지 않다면 Nix 패키지 관리자만 따로 쓸 수도 있으며 CI 파이프라인에 특히 쓸모가 있다고 덧붙입니다.

데스크톱 리눅스 쪽에서는 구조를 짚습니다. 유닉스 전통대로 GUI 부분이 나머지 운영체제와 분리되어 있습니다. 보통 X 윈도 관리자가 디스플레이 관리자의 도움을 받아 창 관리부터 스타일과 렌더링까지 GUI 책임을 맡습니다. 그 위에 아이콘과 위젯과 툴바 같은 데스크톱 경험을 구현하는 데스크톱 환경이 앉는데, KDE 나 MATE 가 그 예입니다. 저자가 촉매로 꼽는 것은 뜻밖의 방향입니다. Windows 11 이 그래픽 리눅스 앱을 기본으로 돌릴 수 있게 되면서 유인과 채택이 바뀔지도 모른다는 것입니다.

임베디드 시스템은 자동차부터 라우터 같은 네트워크 장비, 냉장고 같은 스마트 홈 기기, 미디어 기기와 스마트 TV 까지 넓은 분야입니다. 적은 돈으로 구할 수 있는 범용 플랫폼으로 저자는 라즈베리 파이를 듭니다. Debian 기반의 Raspberry Pi OS 를 갖고 있으며 microSD 카드로 다른 배포판도 간단히 설치할 수 있습니다. 범용 입출력 핀이 여럿 있어 브레드보드로 외부 센서와 회로를 붙이기 쉽고, 파이썬 같은 것으로 하드웨어를 프로그래밍하며 전자 회로를 배울 수 있습니다.

클라우드 IDE 는 최근 몇 년간 크게 진전했습니다. IDE 와 Git 과 여러 프로그래밍 언어를 리눅스 환경에 묶은 상용 제품이 나올 정도가 되었습니다. IDE 는 대개 Visual Studio Code 입니다. 개발자에게 필요한 것은 웹 브라우저와 네트워크 접근뿐입니다. 코드를 클라우드에서 편집하고 시험하고 돌립니다. 저자가 꼽은 두 예는 Gitpod 과 Codespaces 입니다. 앞의 것은 관리형으로도 오픈 소스 자체 호스팅으로도 쓸 수 있으며 뒤의 것은 GitHub 에 깊이 통합되어 있습니다.

## 적용 관점

> 저자는 Spring 도 자바도 다루지 않습니다. 아래는 이 장의 원칙을 그 문맥에 옮겨 본 것입니다.

컨테이너의 종료는 시그널로 옵니다. 오케스트레이터가 파드를 내릴 때 보내는 것이 `SIGTERM` 이고, 유예 시간이 지나면 `SIGKILL` 입니다. §1 의 핸들러 실험이 여기서 실무 규칙이 됩니다. 종료 훅을 달았다고 프로세스가 알아서 끝나지 않으므로 정리 작업을 마친 뒤 실제로 종료하는 경로가 있어야 합니다. `SIGKILL` 은 잡을 수 없으니 유예 시간 안에 끝내는 것이 유일한 방법입니다. 종료 코드 137 은 그 시간을 넘겼다는 기록입니다.

JVM 이 멈춘 것 같을 때 `SIGQUIT` 은 프로세스를 죽이지 않고 스레드 덤프를 받는 통로입니다. `kill -QUIT PID` 를 보내면 HotSpot 이 덤프를 표준 출력에 찍으므로, 컨테이너라면 그 로그에서 찾습니다.[^jdk]

애플리케이션 이미지는 고치지 말고 새로 만듭니다. §4 의 불변성이 배포판이 아니라 애플리케이션 층에도 그대로 적용됩니다. 돌고 있는 컨테이너에 들어가 설정 파일을 고치면 다음 재배포에서 사라지고, 왜 두 인스턴스가 다르게 도는지 아무도 설명할 수 없게 됩니다. 변경은 이미지 태그를 바꾸는 것으로 표현합니다.

인증은 애플리케이션 밖으로 뺄수록 바꾸기 쉽습니다. PAM 이 유닉스에서 한 일을 Spring Security 의 인증 공급자 추상이 애플리케이션 안에서 합니다. 인증 방식이 바뀔 때 고치는 자리를 한 곳으로 모아 두는 것이 두 설계의 공통 목적입니다.

로컬에서 분산 시스템을 흉내 낼 때 VM 과 컨테이너를 가립니다. 저자가 로컬 VM 의 쓸모로 든 것이 시험과 분산 시스템 흉내입니다. 커널 수준의 동작을 보아야 하거나 노드마다 다른 커널이 필요하면 VM 이고, 애플리케이션 사이의 통신만 보면 되면 컨테이너로 충분합니다.

`/var/run/docker.sock` 을 마운트하는 일의 무게는 §2 에서 나옵니다. Testcontainers 로 통합 테스트를 돌리려면 그 경로를 컨테이너에 넘겨야 합니다. 도메인 소켓의 주소가 파일 경로라는 성질 덕분에 마운트 한 줄로 되는 것입니다. 같은 이유로 그 소켓을 얻은 쪽은 호스트의 Docker 를 사실상 전부 부릴 수 있고, 그 사이를 막는 것은 파일 권한뿐입니다.

## 정답 (자답 후 펼치기)

1. 기본 동작은 일어나지 않습니다. 핸들러가 기본 동작을 대체하고, 핸들러가 끝나면 프로세스는 하던 일로 돌아갑니다. `signal(7)` 은 프로세스가 기본 동작, 무시, 핸들러 셋 중 하나를 고른다고 적습니다. 실험에서도 핸들러 없는 반복문은 `SIGTERM` 에 143 으로 끝났고, 핸들러에서 `exit 0` 을 부른 쪽은 0 으로 끝났습니다.

2. `SIGKILL` 과 `SIGSTOP` 입니다. 잡을 수도 막을 수도 무시할 수도 없습니다. 운영에서 뜻하는 바는 두 방향입니다. 확실히 죽이거나 멈춰야 할 때 쓸 수 있는 마지막 수단이라는 것과, `SIGKILL` 을 받은 프로세스는 정리 작업을 할 기회가 전혀 없다는 것입니다.

3. 137 은 128+9 이므로 `SIGKILL` 로 죽었다는 뜻이고, 대개 유예 시간 안에 끝나지 않아 강제로 끝났다는 기록입니다. 143 은 128+15 인 `SIGTERM` 으로, 종료 요청을 받고 핸들러 없이 기본 동작대로 끝났다는 뜻입니다. 앞의 것은 정리 기회가 없었고 뒤의 것은 시그널이 온 순간 곧바로 끝났습니다.

4. systemd 는 `SIGTERM` 과 `SIGCONT` 를 보낸 뒤 `TimeoutStopSec=` 만큼 기다리고, 기본값은 `DefaultTimeoutStopSec=` 의 90초입니다. 그 안에 끝나지 않으면 cgroup 에 남은 프로세스 모두에 `SIGKILL` 을 보내고 결과를 `timeout` 으로 남깁니다. 서비스가 `SIGTERM` 을 잡고 끝내지 않거나 무시하는 것이므로, 핸들러가 정리 뒤 종료하게 고치는 것이 먼저입니다. 정리에 시간이 정말 필요하다면 `TimeoutStopSec=` 을 그만큼 잡습니다.

5. `T` 는 멈춘 상태이고, 멈춘 프로세스에 보낸 `SIGTERM` 은 사라지지 않고 대기합니다. `/proc/PID/status` 의 `ShdPnd` 에 해당 비트가 섭니다. `kill -CONT` 로 깨우면 대기하던 시그널이 전달되어 끝납니다. systemd 가 종료 시그널 뒤에 `SIGCONT` 를 보내는 것도 이 때문입니다. `SIGKILL` 로 끝내는 방법도 있지만 정리 기회가 없어집니다.

6. 수명입니다. 이름 없는 파이프는 그것을 쓰는 프로세스에 수명이 묶이지만 명명 파이프는 묶이지 않습니다. 파일시스템에 항목이 남아 있어 양쪽 프로세스가 죽어도 그대로 있습니다. 이름이 있어 서로 모르는 프로세스끼리 붙을 수 있다는 것도 여기서 나옵니다.

7. 읽는 쪽이 없는 것을 의심합니다. `fifo(7)` 은 FIFO 가 데이터를 넘기려면 양끝이 모두 열려야 하고 보통은 다른 쪽이 열릴 때까지 열기 자체가 막힌다고 적습니다. 저자도 같은 주의를 답니다. 다른 프로세스가 읽지 않는 한 파이프가 막혀 더 쓸 수 없습니다.

8. 목적이 다릅니다. 저자의 대비로는 컨테이너가 애플리케이션 수준의 의존성 관리에 좋고 VM 은 워크로드에 강한 격리를 줍니다. 격리의 뜻은 호스트의 물리 CPU 와 메모리가 게스트의 활동에 대체로 영향받지 않는다는 것이며, VM 안에서 공격이 나도 호스트는 무사합니다. 다만 rowhammer 나 Meltdown 과 Spectre 같은 예외가 실무에 있습니다.

9. 리눅스 커널 자신입니다. KVM 에서는 커널이 하이퍼바이저이고 무거운 일의 대부분을 맡습니다. 커널 모듈은 핵심 모듈 `kvm.ko` 와 아키텍처별 모듈 `kvm-intel.ko` 또는 `kvm-amd.ko` 로 나뉩니다.

10. 설정이나 코드의 어떤 변경이든 돌고 있는 시스템을 바꾸는 대신 새 산출물을 만들게 하는 것입니다. 규모에서 중요해지는 이유는 조금씩 고쳐 나가는 방식이 기계 무리를 관리할 때 무너지기 때문입니다. 기계마다 고쳐 온 이력이 달라지면 같은 상태를 보장할 수 없습니다.

11. KDC 가 중심 역할을 맡아 단일 장애점이 된다는 것과, 시간 요구가 엄격하다는 것입니다. RFC 4120 은 시계가 느슨하게 동기화되어 있을 것을 요구하고, 서버 시각과 인증자 안의 클라이언트 시각이 허용 오차보다 벌어지면 `KRB_AP_ERR_SKEW`("Clock skew too great")로 거절합니다. MIT krb5 의 허용 오차 기본값은 300초입니다. 그래서 비밀번호가 맞는데도 인증이 거절되면 시계를 먼저 봅니다. 실무에서는 NTP 로 시계를 맞춥니다.

12. `pam_limits` 는 PAM 세션을 열 때, 곧 로그인이나 `su` 를 할 때만 한도를 걸고, 이미 돌고 있는 프로세스에는 소급하지 않습니다. systemd 가 띄운 서비스는 `PAMName=` 이 없으면 PAM 세션을 거치지 않으므로 `limits.conf` 가 아예 닿지 않습니다. 서비스는 유닛의 `LimitNOFILE=` 로 한도를 정하고 다시 시작해야 합니다.
