# mail-system

---

> 메일 발송 코드를 짜다 보면 "그 메일은 지금 누구 손에 있나?"에 답하지 못해 막힙니다. 이 시리즈는 인터넷 메일이 왜 지금 모양이 되었는지를 역사, 역할, 배달, 보안, 신뢰, 실제 서비스, 서버 소프트웨어, 앱 발송 방식의 아홉 편으로 나눠 설명합니다.

메일 발송 코드를 운영하거나 메일 서버 설정을 들여다보다 보면 같은 질문 세 가지에서 자주 막힙니다.

메일을 넘기려고 받는 서버와 보관하려고 받는 서버는 어떻게 다른가, MX 를 조회하면 왜 보내는 서버를 알 수 없는가, EHLO 응답의 `AUTH` 는 로그인을 요구한다는 뜻인가 하는 질문입니다.

세 질문은 어느 메일 서버 환경에서나 똑같이 생깁니다. 이 시리즈는 특정 설정 대신 표준(RFC)과 공개 자료로 원리를 세웁니다. 마지막 04-03편에서는 앱이 메일을 보내는 세 갈래로 연결합니다.

## 다른 문서와의 경계

> 같은 개념을 두 곳에서 길게 설명하지 않도록, 입문과 로드맵은 기존 문서에 맡깁니다.

SMTP 대화의 흐름과 기본 명령, 봉투와 헤더의 차이는 [메일과 이름은 어떻게 찾아가는가](../../book/cntd_computer-networking-top-down/02-03.메일과%20이름은%20어떻게%20찾아가는가.md)가 입문으로 다룹니다. 이 시리즈는 그 위에서 "왜 그렇게 생겼나"와 앱 밖의 메일 시스템 구조를 다룹니다.

네트워크 전체에서 메일이 어느 자리에 있는지는 [네트워크 개발 키워드](../../network-keywords.md) 1단계 표의 메일 관련 행이 보여 줍니다.



## 이 폴더의 규칙

> 이 시리즈는 공개 저장소의 학습 문서이므로 회사 정보를 넣지 않습니다.

회사 이름, 사내 호스트, 사내 IP, 사람 이름은 쓰지 않습니다. 예시 도메인은 `example.com` 같은 예약 도메인을 씁니다. Gmail·네이버·Microsoft 365 의 호스트 값은 공개 DNS 와 공식 도움말에서 가져온 것이고 조회한 날짜를 함께 적습니다.

근거는 RFC 원문과 각 서비스의 공식 문서입니다. 조사 단계에서 모은 인용은 원문과 기계 대조를 거쳤고 원문과 맞지 않는 인용은 다시 확인하기 전에는 본문에 쓰지 않았습니다.
