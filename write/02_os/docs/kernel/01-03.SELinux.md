# SELinux

---

> SELinux 는 파일 권한(rwx)을 통과한 요청에 한 번 더 걸리는 리눅스의 강제 접근 통제입니다. 소유자가 풀 수 없는 규칙을 프로세스의 타입과 파일의 타입 사이에 걸어 둡니다.



## 학습 목표

이 문서를 읽고 나면:

1. 파일 권한만으로는 막지 못하는 사고와 SELinux 가 그것을 막는 방식을 설명할 수 있습니다.
2. 시스템 콜에서 임의 통제와 강제 통제가 검사되는 순서를 설명할 수 있습니다.
3. 라벨(`user:role:type:level`)에서 어느 칸이 판정에 가장 크게 쓰이는지 짚을 수 있습니다.
4. 파일·프로세스·포트의 라벨이 각각 어디에 저장되는지 말할 수 있습니다.
5. enforcing·permissive·disabled 의 차이와 설정 위치를 설명할 수 있습니다.
6. 접근 거절을 만났을 때 라벨·boolean·포트·정책 모듈 중 무엇을 고칠지 가르는 순서를 설명할 수 있습니다.

이 문서는 임의·강제 통제의 개념을 [OSTEP 55장 노트](../../book/ostep_operating-systems-three-easy-pieces/43-02.%EA%B6%8C%ED%95%9C%EC%9D%80%20%EB%88%84%EA%B0%80%20%EC%A0%95%ED%95%98%EB%8A%94%EA%B0%80%20%E2%80%94%20%EC%9E%84%EC%9D%98%C2%B7%EA%B0%95%EC%A0%9C%20%EC%A0%91%EA%B7%BC%20%ED%86%B5%EC%A0%9C%EC%99%80%20%EC%97%AD%ED%95%A0%20%EA%B8%B0%EB%B0%98%20%ED%86%B5%EC%A0%9C%2C%20setuid%20%EA%B6%8C%ED%95%9C%20%EC%83%81%EC%8A%B9.md)에 맡기고 리눅스의 구현만 다룹니다. 명령 사용법은 [모드](../cmd/security/getenforce%C2%B7setenforce%C2%B7sestatus.md)·[라벨과 boolean](../cmd/security/semanage%C2%B7restorecon%C2%B7setsebool.md)·[감사 로그](../cmd/security/ausearch%C2%B7audit2why%C2%B7audit2allow.md) 시트가 정본입니다.



## 1. 소유자 재량으로 못 막는 사고

> 파일 권한은 프로세스가 실행한 사용자의 권한을 통째로 물려받으므로, 웹 서버가 뚫리면 그 사용자가 읽을 수 있는 모든 파일이 열립니다.

웹 서버 프로세스를 사용자 `apache` 로 돌린다고 해 봅시다. 이 프로세스가 침해되면 공격자는 `apache` 가 읽을 수 있는 모든 파일을 읽습니다. 소유자 재량의 파일 권한은 "누구의 프로세스인가"만 보고, 그 프로세스가 무슨 일을 하는 프로그램인지는 보지 않기 때문입니다. 웹 서버가 `/home` 의 개인 파일을 읽을 이유는 없지만 권한 비트는 이를 막지 못합니다.

이런 상황이 임의 접근 통제의 한계입니다. 해법은 사용자와 별개로 프로세스마다 "이 프로세스가 할 수 있는 일의 범위"를 정해 두고, 그 범위를 소유자가 바꿀 수 없게 하는 것입니다. 이 방식이 강제 접근 통제이고 리눅스에서 가장 널리 쓰이는 구현이 SELinux 입니다.[^dac]



## 2. 커널이 판정 자리에 거는 훅

> SELinux 는 커널이 판정을 내리는 자리마다 LSM 이 뚫어 둔 훅에서 호출되며, 파일 권한 검사가 통과한 뒤에만 실행됩니다.

### LSM 이 하는 일

LSM(Linux Security Modules)은 보안 모듈을 커널에 끼워 넣는 틀입니다. 커널 서비스의 여러 곳에 훅과 보안 정보를 담을 자리를 마련해 두고, 모듈이 그 훅에서 추가 검사를 합니다. LSM 은 보안 서비스를 직접 제공하지 않고 훅과 구조체만 제공합니다. SELinux 말고 AppArmor·SMACK·TOMOYO 도 같은 틀 위에 있습니다.[^lsm]

### DAC 다음에 MAC

파일을 여는 길목은 커널의 `inode_permission()` 입니다. 이 함수는 먼저 소유자·그룹·나머지 비트(또는 ACL)를 보는 `do_inode_permission()` 으로 임의 통제를 검사합니다. 거기서 거절하면 바로 돌아가고, 통과했을 때만 마지막 줄에서 LSM 훅 `security_inode_permission()` 을 호출합니다. 아래는 v6.12 소스에서 이 순서만 뽑은 것입니다.[^order]

```c
retval = do_inode_permission(idmap, inode, mask);   /* rwx 비트·ACL */
if (retval)
	return retval;

retval = devcgroup_inode_permission(inode, mask);
if (retval)
	return retval;

return security_inode_permission(inode, mask);      /* LSM 훅 → SELinux */
```

그래서 SELinux 는 권한을 더 줄 수는 없고 줄이기만 합니다. 파일 권한이 허락해도 SELinux 가 거절하면 접근이 막히고, 파일 권한이 거절하면 이 길목에서는 SELinux 가 호출되지 않습니다. 이 때문에 `rwx` 가 맞는데도 `Permission denied` 가 나면 SELinux 를 의심하게 됩니다.

| 단계 | 검사 | 거절하면 |
|------|------|----------|
| 1 | 임의 통제(rwx·ACL) | 그 자리에서 `EACCES`, SELinux 는 호출되지 않음 |
| 2 | 강제 통제(SELinux 정책) | 접근 거절, AVC 메시지를 감사 로그에 남김 |



## 3. 라벨은 사용자·역할·타입·레벨

> 모든 프로세스와 객체는 `user:role:type:level` 형식의 라벨을 가지며, 판정은 대부분 그중 타입 칸으로 합니다.

SELinux 는 모든 프로세스(주체)와 객체에 보안 컨텍스트를 붙입니다. 이 컨텍스트가 곧 라벨이고 형식은 아래와 같습니다. 앞 세 칸은 항상 있고 레벨(MCS·MLS 범위)은 정책이 지원할 때만 붙습니다.[^sc]

```bash
# user : role : type : level
# system_u:system_r:httpd_t:s0     ← 프로세스 라벨의 예
# system_u:object_r:httpd_sys_content_t:s0  ← 파일 라벨의 예
```

세 칸의 쓰임은 다음과 같습니다. 이 SELinux 사용자는 리눅스 사용자 ID 와 다른 것이고 설정 파일로 대응됩니다. 역할은 그 사용자가 쓸 수 있는 타입 집합을 이어 줍니다([역할 기반 통제](../../book/ostep_operating-systems-three-easy-pieces/43-02.%EA%B6%8C%ED%95%9C%EC%9D%80%20%EB%88%84%EA%B0%80%20%EC%A0%95%ED%95%98%EB%8A%94%EA%B0%80%20%E2%80%94%20%EC%9E%84%EC%9D%98%C2%B7%EA%B0%95%EC%A0%9C%20%EC%A0%91%EA%B7%BC%20%ED%86%B5%EC%A0%9C%EC%99%80%20%EC%97%AD%ED%95%A0%20%EA%B8%B0%EB%B0%98%20%ED%86%B5%EC%A0%9C%2C%20setuid%20%EA%B6%8C%ED%95%9C%20%EC%83%81%EC%8A%B9.md#2-%EC%A7%81%EB%AC%B4%EB%A1%9C-%EB%AC%B6%EB%8A%94-%EA%B6%8C%ED%95%9C--%EC%97%AD%ED%95%A0-%EA%B8%B0%EB%B0%98-%ED%86%B5%EC%A0%9C%EC%99%80-%ED%83%80%EC%9E%85-%EA%B0%95%EC%A0%9C)에서 말한 역할). 타입은 판정에 가장 크게 쓰입니다. 프로세스에 붙은 타입을 **도메인**이라고 부르고, 파일에 붙은 타입을 그냥 **타입**이라고 부릅니다. 정책은 "도메인 `httpd_t` 는 타입 `httpd_sys_content_t` 파일을 읽을 수 있다" 같은 규칙으로 쓰이고 이를 타입 강제라고 합니다.

Rocky Linux 9 에 정책 패키지만 설치해 보면 이 규칙이 실제로 어떻게 생겼는지 볼 수 있습니다. `sesearch` 로 `httpd_t` 가 `httpd_sys_content_t` 파일에 대해 가진 허용 규칙을 뽑은 결과입니다. 이 명령은 컨테이너에서 SELinux 를 켜지 않고도 정책 파일만 읽어 동작합니다.

```bash
sesearch --allow -s httpd_t -t httpd_sys_content_t -c file
```

```bash
allow domain file_type:file map; [ domain_can_mmap_files ]:True
allow httpd_t httpd_content_type:file { getattr ioctl lock map open read };
allow httpd_t httpdcontent:file { append create getattr ioctl link lock open read rename setattr unlink watch watch_reads write }; [ ( httpd_builtin_scripting && httpd_unified && httpd_enable_cgi ) ]:True
allow httpd_t httpdcontent:file { execute execute_no_trans getattr ioctl map open read }; [ ( httpd_builtin_scripting && httpd_unified && httpd_enable_cgi ) ]:True
```

두 번째 줄이 읽기 허용이고, 뒤쪽 줄처럼 끝에 `[ boolean ]:True` 가 붙은 규칙은 그 boolean 이 켜져 있을 때만 유효합니다. `httpd_t` 에 `user_home_t`(홈 디렉터리 파일) 읽기 규칙이 따로 없으면 홈 디렉터리 파일은 읽지 못합니다.



## 4. 라벨은 어디에 저장되는가

> 파일 라벨은 파일 시스템의 확장 속성에, 프로세스 라벨은 커널의 프로세스 자격 구조에, 포트 라벨은 정책에 있습니다.

| 대상 | 저장 위치 | 확인하는 곳 |
|------|-----------|-------------|
| 파일 | 확장 속성 `security.selinux` | `ls -Z`, `getfattr -n security.selinux` |
| 프로세스 | 커널의 프로세스 자격(cred) 안 보안 구조 | `ps -Z`, `/proc/<pid>/attr/current` |
| 네트워크 포트 | 정책의 포트 규칙(디스크 파일 아님) | `semanage port -l` |
| 새 파일의 기본 라벨 | 정책의 경로 규칙 | `semanage fcontext -l`, `matchpathcon` |

파일 라벨은 파일 시스템이 확장 속성을 지원해야 붙습니다. 프로세스 라벨은 `struct task_security_struct` 에 담기고 커널이 프로세스의 자격(cred)에서 꺼내 씁니다.[^cred] 포트에는 파일이 없으므로 정책 안의 "포트 번호 범위 → 타입" 규칙이 라벨 역할을 합니다. Rocky Linux 9 의 정책에서 http 와 ssh 포트 규칙을 뽑으면 아래와 같습니다.

```bash
semanage port -l | grep -E "^http_port_t|^ssh_port_t"
```

```bash
http_port_t                    tcp      80, 81, 443, 488, 8008, 8009, 8443, 9000
ssh_port_t                     tcp      22
```

그래서 웹 서버를 8888 번 포트에서 돌리려 하면 `httpd_t` 가 `unreserved_port_t` 에 `name_bind` 하는 것이 거절됩니다. 포트를 `http_port_t` 로 등록하는 것이 해법입니다(§6).

새로 만드는 파일의 기본 라벨은 정책의 경로 규칙이 정합니다. `matchpathcon` 은 경로가 가져야 할 라벨을 정책에서 찾아 줍니다.

```bash
matchpathcon /var/www/html/index.html /etc/shadow
```

```bash
/var/www/html/index.html	system_u:object_r:httpd_sys_content_t:s0
/etc/shadow	system_u:object_r:shadow_t:s0
```

> 이 실습 컨테이너에서는 SELinux 가 꺼져 있어서 파일에 실제 라벨을 붙인 `ls -Z` 출력은 재현하지 못했습니다. `ls -Z` 는 `?` 를 찍었고 `setfattr -n security.selinux` 는 `Operation not permitted` 였습니다. 파일에 붙은 라벨의 모습은 SELinux Notebook 의 예(`unconfined_u:object_r:user_home:s0`)로 대신합니다.



## 5. 정책과 모드

> 정책은 어떤 도메인이 무엇을 할 수 있는지의 규칙 모음이고, 모드는 그 규칙을 집행할지를 정합니다.

### targeted 정책

리눅스 배포판의 기본 정책은 `targeted` 입니다. 이 정책에서는 대부분의 사용자 프로세스가 제약 없는 `unconfined` 도메인에서 돌고, 웹 서버나 DNS 서버 같은 특정 서비스만 자기 전용 도메인에 갇힙니다. 정책 이름은 `/etc/selinux/config` 의 `SELINUXTYPE` 로 정합니다.[^cfg] `mls` 같은 다른 정책도 설치할 수 있지만 한 번에 하나만 활성입니다.

### 세 가지 모드

모드는 `/etc/selinux/config` 의 `SELINUX` 값으로 정합니다. 세 값의 뜻은 다음과 같습니다.

```bash
# SELINUX=enforcing    정책을 집행한다. 거절하고 감사 로그에 남긴다
# SELINUX=permissive   집행하지 않는다. 허락하되 거절했을 일을 감사 로그에 남긴다
# SELINUX=disabled     정책을 올리지 않는다
```

permissive 는 정책을 만들거나 문제를 찾을 때 쓰입니다. 이 모드에서는 enforcing 일 때 첫 거절에서 멈추던 동작이 계속 진행됩니다. 그래서 enforcing 과 다른 거절 집합이 나올 수 있습니다. 실행 중에 enforcing 과 permissive 를 바꾸는 명령이 `setenforce` 입니다. Rocky Linux 9 컨테이너(SELinux 꺼짐)에서 이 명령들은 이렇게 답합니다.

```bash
getenforce
sestatus
setenforce 0
```

```bash
Disabled
SELinux status:                 disabled
setenforce: SELinux is disabled
```

`setenforce` 는 enforcing 과 permissive 만 오갑니다. disabled 와 사이를 오가려면 재부팅이 필요합니다.

### disabled 대신 커널 인자

`SELINUX=disabled` 로 완전히 끄는 것은 이제 권장하지 않습니다. selinux(8) 은 이 값이 커널 버전과 설정에 따라 SELinux 를 완전히 끄지 못할 수 있다고 적고, 올바르게 끄려면 부팅 인자 `selinux=0` 을 쓰라고 합니다. 그 경우 설정 파일의 값과 무관하게 SELinux 가 꺼집니다.[^cfg]

### 도메인 하나만 permissive 로

SELinux 전체를 끄지 않고 도메인 하나만 허락·감사 상태로 둘 수 있습니다. `semanage permissive -a httpd_t` 는 `httpd_t` 도메인만 permissive 로 만듭니다. 나머지는 enforcing 으로 남습니다. 이 방법은 새 서비스의 거절을 수집할 때 SELinux 를 통째로 끄는 것보다 안전합니다.



## 6. 거절을 읽고 고치는 순서

> 거절은 감사 로그에 AVC 메시지로 남고, 원인에 따라 라벨·boolean·포트·정책 모듈 중 하나를 고칩니다.

### AVC 한 줄 읽기

거절이 나면 감사 로그(`/var/log/audit/audit.log`)에 `type=AVC` 줄이 남습니다. 이 줄에서 읽을 것은 세 가지입니다. 어떤 도메인이(`scontext`), 어떤 타입의 객체에(`tcontext`), 어떤 종류(`tclass`)의 어떤 동작을(`{ read }`) 했는지입니다. 아래 두 줄은 실제 서버에서 받은 로그가 아니라 설명을 위해 직접 만든 AVC 입니다. 형식은 `ausearch` 가 읽는 감사 로그와 같습니다.

```bash
type=AVC msg=audit(1700000000.123:100): avc:  denied  { read } for  pid=1234 comm="httpd" name="index.html" dev="sda1" ino=5678 scontext=system_u:system_r:httpd_t:s0 tcontext=unconfined_u:object_r:user_home_t:s0 tclass=file permissive=0
type=AVC msg=audit(1700000001.123:101): avc:  denied  { name_bind } for  pid=1235 comm="httpd" src=8888 scontext=system_u:system_r:httpd_t:s0 tcontext=system_u:object_r:unreserved_port_t:s0 tclass=tcp_socket permissive=0
```

### audit2why 의 원인 판정

`audit2why` 는 AVC 가 어떤 원인인지 설명합니다. 정책 파일 경로를 `-p` 로 줘야 하고, Rocky Linux 9 에서는 `/etc/selinux/targeted/policy/policy.33` 입니다. 위 두 줄을 넣은 결과입니다.

```bash
audit2why -p /etc/selinux/targeted/policy/policy.33 -i /tmp/avc.log
```

```bash
type=AVC msg=audit(1700000000.123:100): avc:  denied  { read } for  pid=1234 comm="httpd" ...

	Was caused by:
	The boolean httpd_read_user_content was set incorrectly. 
	Description:
	Allow httpd to read user content

	Allow access by executing:
	# setsebool -P httpd_read_user_content 1
type=AVC msg=audit(1700000001.123:101): avc:  denied  { name_bind } for  pid=1235 comm="httpd" ...

	Was caused by:
	The boolean nis_enabled was set incorrectly. 
	Description:
	Allow nis to enabled

	Allow access by executing:
	# setsebool -P nis_enabled 1
```

첫 AVC 는 boolean 으로 풀립니다. 둘째 AVC 는 `nis_enabled` 를 켜라고 나오지만 웹 서버가 8888 번에 바인딩하는 문제의 올바른 해법은 아닙니다. `audit2why` 는 정책 안에서 이 거절을 풀 수 있는 boolean 을 찾을 뿐 의도를 모르기 때문입니다. 이 경우 포트를 `http_port_t` 로 등록하는 편이 맞습니다.

### 무엇을 고칠지 가르는 표

```bash
# 증상                                 원인 후보             고치는 곳
# 파일을 못 읽음, 위치를 옮겼다         파일 라벨이 어긋남     restorecon / semanage fcontext
# 서비스 기능이 정책 기본값에 막힘       boolean 이 꺼져 있음   setsebool -P
# 표준이 아닌 포트에서 서비스를 못 띄움   포트가 타입에 없음     semanage port -a
# 위로도 안 풀림                       정책 규칙이 없음       audit2allow 로 모듈 작성
```

경로 규칙을 로컬에 더하는 명령과 그 결과는 다음과 같습니다. `/srv/web` 아래를 웹 콘텐츠로 라벨링하는 규칙을 더하고 `matchpathcon` 으로 확인합니다.

```bash
semanage fcontext -a -t httpd_sys_content_t "/srv/web(/.*)?"
semanage fcontext -l -C
matchpathcon /srv/web/index.html
```

```bash
SELinux fcontext                                   type               Context

/srv/web(/.*)?                                     all files          system_u:object_r:httpd_sys_content_t:s0 
/srv/web/index.html	system_u:object_r:httpd_sys_content_t:s0
```

이 규칙은 정책에 로컬 규칙만 더할 뿐 파일에 라벨을 바로 붙이지 않습니다. 실제 파일 라벨을 규칙에 맞게 되돌리는 것이 `restorecon` 입니다. 파일에 이미 라벨이 있으면 `restorecon` 은 타입 칸만 고치고, 사용자·역할·레벨까지 바꾸려면 `-F` 를 줍니다.[^restorecon]

### 정책 모듈은 마지막 수단

위 표의 앞 세 칸으로 풀리지 않을 때 `audit2allow` 가 AVC 에서 허용 규칙을 만들고 `-M` 은 설치할 모듈을 만듭니다.

```bash
audit2allow -p /etc/selinux/targeted/policy/policy.33 -i /tmp/avc.log
```

```bash
#============= httpd_t ==============

#!!!! This avc can be allowed using the boolean 'nis_enabled'
allow httpd_t unreserved_port_t:tcp_socket name_bind;

#!!!! This avc can be allowed using the boolean 'httpd_read_user_content'
allow httpd_t user_home_t:file read;
```

`#!!!!` 주석이 붙은 줄은 boolean 으로 풀 수 있다는 표시입니다. 이런 줄을 그대로 모듈로 설치하면 의도보다 넓은 권한을 영구히 허락하게 되므로, 로그를 보지 않고 `audit2allow -M` 결과를 곧바로 설치하지 않습니다.



## 7. 파일을 옮길 때 라벨이 따라가는 방식

> 복사하면 새 파일이 대상 디렉터리의 라벨을 받고, 이동하면 원래 라벨을 그대로 가져갑니다.

SELinux 는 라벨을 파일의 확장 속성으로 들고 있으므로 같은 파일 시스템 안에서 `mv` 는 파일을 새로 만들지 않고 이름만 바꿔 라벨이 따라갑니다. `cp` 는 새 파일을 만들어 대상 디렉터리의 라벨을 받습니다. SELinux Notebook 의 예로 보면, 타입이 `in_queue_t` 인 디렉터리에 복사한 파일은 `in_queue_t` 가 되고 이동한 파일은 원래의 `unconfined_t` 로 남습니다.[^cpmv]

```bash
# 복사: 대상 디렉터리의 라벨을 받음 (SELinux Notebook 의 예)
# -rw-r--r-- root root unconfined_u:object_r:in_queue_t copied-file
# 이동: 원래 라벨이 남음
# -rw-r--r-- root root unconfined_u:object_r:unconfined_t moved-file
```

웹 콘텐츠를 홈 디렉터리에서 `mv` 로 `/var/www/html` 에 옮기면 `user_home_t` 라벨이 따라가서 `httpd_t` 가 읽지 못합니다. 이럴 때 `restorecon` 으로 경로 규칙에 맞는 라벨을 되돌립니다.



## 결정 치트시트

> 이 문서의 판단 기준은 아래 표와 같습니다.

| 상황 | 판단 | 근거 |
|------|------|------|
| rwx 가 맞는데 `Permission denied` 가 난다 | SELinux 거절을 의심하고 AVC 를 본다 | 임의 통제를 통과한 뒤에 SELinux 가 호출된다 |
| 새 서비스의 거절을 모으고 싶다 | 도메인만 permissive 로 둔다 | 전체를 끄지 않고 감사 기록은 남는다 |
| 파일을 다른 곳에서 옮겨 왔다 | `restorecon` 으로 라벨을 되돌린다 | `mv` 는 원래 라벨을 가져간다 |
| 표준이 아닌 포트에서 서비스가 안 뜬다 | `semanage port -a` 로 포트 타입을 추가한다 | 포트 라벨은 정책의 규칙이다 |
| `audit2why` 가 boolean 을 권한다 | 의도에 맞을 때만 켠다 | 도구는 의도를 모르고 풀 수 있는 boolean 만 찾는다 |
| SELinux 를 완전히 끄려 한다 | 부팅 인자 `selinux=0` 을 쓴다 | `SELINUX=disabled` 는 권장하지 않는다 |
