# 포트와 소켓 — 고갈·점유·포워딩·레이트 리밋

---

> 네트워크 장애의 상당수는 회선이 아니라 소켓 상태에서 답이 나옵니다. `ss`가 보여 주는 LISTEN·ESTABLISHED·TIME_WAIT 세 상태가 각각 다른 종류의 문제를 가리킵니다.

앞의 03장이 포트 하나를 두고 벌어진 충돌이었다면, 이 문서는 포트를 자원으로 보고 그 자원이 모자라거나 잘못 쓰이는 상황을 다룹니다.

다섯 사례를 소켓 상태 순서로 배치했습니다. 무엇이 듣고 있는지 본 다음 몇 개가 연결돼 있는지 보고, 끝난 연결이 자리를 붙들고 있는지 봅니다. 그다음 두 사례는 그렇게 파악한 상태를 바꾸는 쪽입니다.



## 소켓 상태가 문제의 종류를 알려 줍니다

> "연결이 안 된다"는 신고 하나에 원인은 여럿입니다. 어느 상태의 소켓이 비정상적으로 많은지가 원인을 가릅니다.

네트워크 문제를 만나면 `ping`이나 `curl`부터 쳐 보게 됩니다. 그런데 이 둘은 되거나 안 되거나만 알려 줄 뿐, 왜 안 되는지는 말해 주지 않습니다.

`ss -s` 한 줄이 훨씬 많은 것을 알려 줍니다. 상태별 소켓 개수가 나오고, 어느 상태가 비정상적으로 부풀었는지가 곧 가설이 됩니다. 연결이 많은 것과 끝난 연결이 안 치워지는 것은 전혀 다른 문제입니다.

| 소켓 상태 | 많으면 의미하는 것 | 사례 |
|-----------|--------------------|------|
| LISTEN | 의도하지 않은 서비스가 떠 있을 수 있다 | 사례 1 |
| ESTABLISHED | 한 프로세스가 연결을 과도하게 열고 있다 | 사례 2 |
| TIME_WAIT | 끝난 연결이 임시 포트를 붙들어 고갈시킨다 | 사례 3 |



## 사례 1 — 감사에서 모르는 포트가 나왔습니다

> `ss -tlnp`는 지금 이 서버가 외부에 무엇을 열어 두었는지 보여 줍니다. 실행 사용자와 경로가 정상 배포물인지를 가릅니다.

보안 감사에서 8000번대 포트에 비인가 애플리케이션이 수신 대기 중인 것이 발견됐습니다.

```bash
LISTEN  0  128  0.0.0.0:8080  0.0.0.0:*  users:(("node",pid=5678,fd=3))
LISTEN  0  128  0.0.0.0:8443  0.0.0.0:*  users:(("python3",pid=6789,fd=4))
LISTEN  0  128  0.0.0.0:8888  0.0.0.0:*  users:(("ruby",pid=7890,fd=5))
LISTEN  0  128  0.0.0.0:9000  0.0.0.0:*  users:(("java",pid=8901,fd=6))
```

```bash
deploy    5678  1.2  3.4  456780  34560 ?  Sl  Mar02  2:30 node /tmp/test-server.js
nobody    6789  0.5  1.2  234560  12340 ?  S   Mar03  0:45 python3 -m http.server 8443
deploy    7890  0.8  2.1  345670  21230 ?  Sl  Mar03  1:15 ruby sinatra-app.rb
nobody    8901  2.1  4.5  567890  45670 ?  Sl  Mar01  8:30 java -jar unknown-service.jar
```

네 프로세스 모두 바인딩 주소가 `0.0.0.0`입니다. 이 값은 모든 네트워크 인터페이스에서 받는다는 뜻이라, 방화벽이 없으면 외부에서 바로 닿습니다. `127.0.0.1`로 떠 있었다면 위험도가 크게 달랐을 겁니다.

무엇이 수상한지는 실행 정보가 알려 줍니다. `/tmp`에서 실행된 테스트 서버, `python3 -m http.server` 같은 간이 서버, 이름이 `unknown-service.jar`인 프로세스가 나란히 있습니다. 정상 배포물이라면 배포 경로와 서비스 이름이 있어야 합니다.

이런 프로세스는 대개 악의보다 방치에서 생깁니다. 테스트로 띄우고 잊은 것들이 몇 달째 외부에 포트를 열어 두고 있는 상태입니다.

### 조치

```bash
# 수신 중인 소켓 전수 확인
ss -tlnp

# 종료 전에 무엇이었는지 기록으로 남긴다
ss -tlnp > listening_audit.txt
ps -p 5678,6789,7890,8901 -o pid,user,lstart,args >> listening_audit.txt

# 확인된 비인가 프로세스 종료
kill 5678 6789 7890 8901

# 정리 확인
ss -tlnp | grep -E ':(8[0-9]{3}|9000)'
```

정리보다 중요한 것은 다시 생기지 않게 하는 쪽입니다. 방화벽을 허용 목록 방식으로 운영하면 이런 프로세스가 떠도 외부에 노출되지 않습니다.

주기적인 감사를 예약 작업으로 돌려 두면 발견 시점이 몇 달에서 하루로 줄어듭니다. 출력이 이전과 달라졌을 때만 알림을 보내는 형태가 실용적입니다.



## 사례 2 — 한 프로세스가 연결 1만 개를 열고 있습니다

> 연결 수는 프로세스별로 묶어 세야 의미가 생깁니다. 전체 숫자만 보면 정상인지 아닌지 판단할 기준이 없습니다.

네트워크 지연이 보고됐습니다. 특정 애플리케이션이 과도한 TCP 연결을 만들고 있는 것으로 의심되지만 근거가 필요합니다.

```bash
Total: 12456
TCP:   12100 (estab 11800, closed 120, orphaned 5, timewait 120)
```

```bash
  11650 users:(("crawler",pid=4567,fd=...))
    85 users:(("nginx",pid=1234,fd=...))
    42 users:(("postgres",pid=2345,fd=...))
    15 users:(("sshd",pid=3456,fd=...))
```

```bash
Recv-Q  Send-Q  Local Address:Port    Peer Address:Port
0       0       192.168.1.50:45231    203.0.113.10:80
0       0       192.168.1.50:45232    203.0.113.10:80
0       0       192.168.1.50:45233    203.0.113.11:80
```

ESTABLISHED가 11,800개인데 그중 11,650개가 `crawler` 하나입니다. 98.7%가 한 프로세스에서 나왔으므로 나머지를 볼 필요가 없습니다.

세 번째 출력이 성격을 확정해 줍니다. 로컬 포트가 45231부터 연속으로 올라가고 목적지가 모두 80번 포트입니다. 서버가 요청을 받는 것이 아니라 스스로 바깥으로 연결을 여는 아웃바운드 패턴입니다.

이 상황이 지연을 만드는 경로는 두 갈래입니다. 연결마다 파일 디스크립터와 커널 메모리를 쓰므로 자원이 마르고, 아웃바운드 연결마다 임시 포트를 하나씩 쓰므로 다음 사례의 고갈로 이어집니다.

### 조치

```bash
# 상태별 요약으로 어느 상태가 부풀었는지 본다
ss -s

# 프로세스별 연결 수로 묶어 센다
ss -tnp | grep -oE 'pid=[0-9]+' | sort | uniq -c | sort -rn | head

# 조사용으로 현재 연결을 통째로 남긴다
ss -tnpa > active_tcp.txt

# 확인 후 해당 프로세스 종료
kill 4567
```

종료는 응급 조치일 뿐입니다. 크롤러나 스크래퍼에는 동시 연결 수 상한을 애플리케이션 설정으로 걸어야 하고, 그것이 없으면 재시작하는 순간 같은 상태로 돌아갑니다.

시스템 쪽에서도 한 겹 막을 수 있습니다. `limits.conf`의 `nofile`은 프로세스가 열 수 있는 파일 디스크립터 수를 제한하는데, 소켓도 파일 디스크립터라 이 상한에 함께 걸립니다.



## 사례 3 — 포트가 남아 있는데 연결을 못 만듭니다

> `Cannot assign requested address`는 임시 포트가 바닥났다는 뜻입니다. 끝난 연결이 TIME_WAIT으로 자리를 붙들고 있는 상태입니다.

스크래퍼 서비스가 연속으로 요청을 보내는데 연결 실패가 잦습니다. 네트워크는 정상이고 원격 서버도 살아 있습니다.

```bash
Mar 04 10:15:01 server scraper[3456]: HTTP Status: 000 - Connection failed to https://example.com
Mar 04 10:15:02 server scraper[3456]: Error: Cannot assign requested address
```

```bash
Total: 65432
TCP:   64890 (estab 245, closed 62100, orphaned 0, timewait 62100)
```

```bash
net.ipv4.ip_local_port_range = 32768    60999
```

에러 문자열이 원인을 좁혀 줍니다. `Connection refused`가 아니라 `Cannot assign requested address`라는 것은 상대에게 닿기도 전에 커널이 출발지 포트를 못 골랐다는 뜻입니다.

숫자가 그것을 확인해 줍니다. 임시 포트 범위가 32768부터 60999까지라 28,232개인데 TIME_WAIT 소켓이 62,100개입니다. 쓸 수 있는 포트보다 붙들려 있는 소켓이 두 배 넘게 많습니다.

TIME_WAIT은 버그가 아니라 설계입니다. 연결을 먼저 닫은 쪽은 늦게 도착한 패킷이 다음 연결에 섞이지 않도록 일정 시간 그 포트를 비워 두는데, 초당 수백 개씩 연결을 여닫으면 이 유예 기간이 자원 부족으로 나타납니다.

### 조치

```bash
# 임시 포트 범위를 넓힌다
sysctl -w net.ipv4.ip_local_port_range="1024 65535"

# 나가는 연결에 한해 TIME_WAIT 소켓 재사용을 허용한다
sysctl -w net.ipv4.tcp_tw_reuse=1

# 영구 적용
echo "net.ipv4.ip_local_port_range = 1024 65535" >> /etc/sysctl.conf
echo "net.ipv4.tcp_tw_reuse = 1" >> /etc/sysctl.conf
sysctl -p
```

`tcp_tw_reuse`는 나가는 연결에만 적용되므로 클라이언트 쪽에서는 안전한 선택입니다. 이름이 비슷한 `tcp_tw_recycle`은 NAT 뒤의 클라이언트를 끊어 버리는 문제가 있어 커널 4.12에서 제거됐습니다.

두 설정 모두 시간을 벌어 줄 뿐입니다. 진짜 해결은 연결을 덜 만드는 것이고, HTTP Keep-Alive와 커넥션 풀을 쓰면 요청 수백 건이 연결 몇 개를 재사용합니다.



## 사례 4 — 앱을 못 건드리는데 포트를 하나 더 열어야 합니다

> `iptables`의 `REDIRECT`는 커널이 목적지 포트를 바꿔 줍니다. 애플리케이션은 자기가 어느 포트로 요청받았는지 모릅니다.

Java 애플리케이션이 8080에서 돌고 있는데 8081로도 접근할 수 있어야 합니다. 설정 변경과 재시작은 불가능한 상황입니다.

```bash
LISTEN  0  128  127.0.0.1:8080  0.0.0.0:*  users:(("java",pid=1234,fd=5))
```

```bash
curl: (7) Failed to connect to 127.0.0.1 port 8081: Connection refused
```

```bash
Chain PREROUTING (policy ACCEPT)
target     prot opt source               destination

Chain OUTPUT (policy ACCEPT)
target     prot opt source               destination
```

8081번에는 아무도 바인딩돼 있지 않고 NAT 테이블도 비어 있으니 거절이 나는 것이 당연합니다. 애플리케이션을 못 건드린다면 남은 방법은 커널이 목적지를 바꿔 주는 것입니다.

여기서 체인을 두 개 걸어야 하는 이유를 알아 둘 필요가 있습니다. `PREROUTING`은 바깥에서 들어온 패킷을 처리하고, 같은 호스트 안에서 자기 자신에게 보낸 패킷은 이 체인을 지나지 않습니다. 로컬에서 `curl`로 확인하려면 `OUTPUT` 체인에도 같은 규칙이 필요합니다.

이 사실을 모르면 규칙을 걸어 놓고 로컬에서 테스트하다 "안 된다"는 결론을 내리게 됩니다.

### 조치

```bash
# 외부에서 들어오는 패킷
iptables -t nat -A PREROUTING -p tcp --dport 8081 -j REDIRECT --to-port 8080

# 같은 호스트 안에서 나가는 패킷
iptables -t nat -A OUTPUT -p tcp -d 127.0.0.1 --dport 8081 -j REDIRECT --to-port 8080

# 동작 확인과 규칙 확인
curl http://127.0.0.1:8081/health
iptables -t nat -L -n

# 재부팅 후에도 유지
iptables-save > /etc/iptables/rules.v4
```

`REDIRECT`는 같은 호스트 안에서만 동작합니다. 다른 서버로 넘기려면 `DNAT`과 `MASQUERADE`를 조합하고 `net.ipv4.ip_forward`를 켜야 하는데, 그 지점부터는 리버스 프록시를 두는 편이 관리하기 쉽습니다.

`iptables` 규칙은 저장하지 않으면 재부팅과 함께 사라진다는 점도 기억해 둡니다. "어제는 됐는데 오늘 안 된다"의 흔한 원인입니다.



## 사례 5 — 특정 클라이언트가 트래픽을 몰아넣습니다

> 레이트 리밋은 로그에서 값을 뽑아 정합니다. 다만 뽑은 값의 단위를 확인하지 않으면 제한이 사실상 없는 것과 같아집니다.

특정 클라이언트의 과도한 요청으로 성능 문제가 생기는데 제한 설정이 전혀 없습니다.

```bash
203.0.113.10 - - [04/Mar/2026:10:00:01 +0000] "GET /api/data HTTP/1.1" 200 1234
203.0.113.25 - - [04/Mar/2026:10:00:01 +0000] "GET /api/data HTTP/1.1" 200 1234
198.51.100.5 - - [04/Mar/2026:10:00:02 +0000] "POST /api/login HTTP/1.1" 200 890
```

```bash
   4523 203.0.113.10
   3891 198.51.100.5
   3456 203.0.113.25
    234 10.0.0.50
     89 10.0.0.51
```

```nginx
http {
    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend;
        }
    }
}
```

상위 세 IP가 4,523건, 3,891건, 3,456건으로 나머지보다 한 자릿수 이상 많습니다. 제한 대상이 명확하다는 점까지는 로그가 답을 줍니다.

문제는 이 숫자를 제한값으로 옮기는 단계입니다. 원본 문제는 세 IP 합계를 셋으로 나눈 뒤 0.8을 곱해 `3165r/s`를 제시하는데, 이 계산은 단위가 맞지 않습니다. 4,523은 로그 파일 전체 기간의 누적 건수이지 초당 요청 수가 아닙니다. 로그가 한 시간 분량이라면 실제 초당 요청은 1.3건 남짓이고, 그런 트래픽에 `3165r/s` 제한을 걸면 아무것도 걸리지 않습니다.

제한값은 건수가 아니라 비율로 뽑아야 합니다. 로그의 시각 필드로 초당 요청 수를 직접 세고, 정상 클라이언트의 최대치를 넘되 공격 클라이언트는 걸리는 지점을 고릅니다.

### 조치

```bash
# 요청이 몰린 출발지 확인
awk '{print $1}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -3

# 초당 요청 수를 실제로 센다. 제한값의 단위는 여기서 나온다
awk '{print $4}' /var/log/nginx/access.log | sort | uniq -c | sort -rn | head -5

# 한 IP 의 초당 최댓값
awk '$1=="203.0.113.10" {print $4}' /var/log/nginx/access.log | uniq -c | sort -rn | head -3
```

```nginx
http {
    # rate 는 위에서 실측한 초당 요청 수를 기준으로 잡는다
    limit_req_zone $binary_remote_addr zone=app_limit:10m rate=20r/s;

    server {
        listen 80;
        server_name example.com;

        location / {
            limit_req zone=app_limit burst=50 nodelay;
            limit_req_status 429;
            proxy_pass http://backend;
        }
    }
}
```

```bash
nginx -t && systemctl reload nginx
```

`zone=app_limit:10m`은 출발지별 상태를 담을 공유 메모리 크기입니다. `burst`는 순간적으로 몰린 요청을 잠시 받아 주는 버퍼이고, `nodelay`를 붙이면 버퍼 안의 요청을 지연 없이 바로 처리합니다.

`limit_req_status 429`를 함께 두는 것을 권합니다. 기본값은 503이라 클라이언트 입장에서 서버 장애와 구분되지 않고, 429는 "너무 많이 보냈다"는 의미를 정확히 전달합니다.



## 다섯 사례를 관통하는 것

> 포트는 65,535개뿐인 유한 자원이고, 소켓은 그 자원을 상태로 관리합니다. 다섯 사례는 이 유한함이 드러나는 다섯 지점입니다.

`ss`의 상태 열 하나가 진단의 절반을 끝냅니다. LISTEN이 많으면 열어 둔 것을 의심하고, ESTABLISHED가 많으면 만드는 쪽을 의심하고, TIME_WAIT이 많으면 닫는 속도를 의심합니다. 세 가지를 나눠 보는 것만으로 후보가 크게 줄어듭니다.

조치의 층위가 다르다는 점도 반복됩니다. 사례 3의 커널 파라미터와 사례 5의 nginx 설정은 각각 커널과 애플리케이션에서 같은 문제를 다르게 막습니다. 어느 층에서 막을지는 그 층이 그 정보를 가지고 있는지로 정합니다.

마지막으로 사례 5가 남기는 교훈을 따로 적어 둡니다. 로그에서 뽑은 숫자를 설정값으로 옮길 때 단위를 확인하지 않으면, 설정은 들어갔지만 아무 효과가 없는 상태가 됩니다. 제한을 걸었다는 사실보다 그 값이 실제로 걸리는 값인지가 중요합니다.
