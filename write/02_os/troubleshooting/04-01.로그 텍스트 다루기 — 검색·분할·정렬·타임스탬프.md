# 로그 텍스트 다루기 — 검색·분할·정렬·타임스탬프

---

> 장애 조사에서 로그를 읽는 시간보다 로그를 읽을 수 있는 상태로 만드는 시간이 더 깁니다. 이 문서는 그 준비 작업을 다섯 갈래로 나눠 봅니다.

앞의 로그 문서가 용량 관점이었다면, 이 문서는 그 안에 쓰인 내용을 다루는 쪽입니다.

로그 파일은 조사할 때 그대로 쓸 수 있는 형태로 오지 않습니다. 너무 커서 열리지 않거나, 여러 파일에 흩어져 있거나, 순서가 섞여 있거나, 시간이 아예 안 찍혀 있습니다. 다섯 사례가 그 네 가지 불편과 그것을 만든 원인 하나를 각각 맡습니다.



## 읽을 수 있는 상태로 만드는 네 가지 준비

> 로그 분석의 앞단은 늘 같은 순서입니다. 왜 커졌는지 알아내고, 흩어진 것을 찾고, 큰 것을 쪼개고, 순서를 맞춥니다.

장애가 나면 로그부터 열게 됩니다. 그런데 열자마자 분석에 들어가는 일은 드뭅니다. 파일이 2GB라 에디터가 멈추거나, 어느 애플리케이션이 낸 로그인지 알 수 없습니다.

이 준비 작업들은 각각 다른 도구를 쓰지만 목적이 하나로 이어집니다. 사람이 눈으로 읽을 수 있는 크기와 순서로 데이터를 바꾸는 것입니다. 도구를 외우기보다 어떤 불편에 어떤 도구가 붙는지를 짝으로 익히는 편이 실전에서 빠릅니다.

| 불편 | 도구 | 사례 |
|------|------|------|
| 파일이 왜 이렇게 빨리 커지는지 모른다 | `lsof`, `tail` | 사례 1 |
| 어느 파일에 있는지 모른다 | `grep -r --include` | 사례 2 |
| 파일이 너무 커서 안 열린다 | `split -l` | 사례 3 |
| 순서가 섞여 인과를 못 읽는다 | `sort -k` | 사례 4 |
| 시간이 안 찍혀 있다 | `ts`, `awk strftime` | 사례 5 |



## 사례 1 — 로그 파일이 5분에 3GB씩 커집니다

> `lsof`는 파일을 쓰는 프로세스를 알려 주지만, 그것이 원인 프로세스는 아닙니다. syslog 구조에서는 한 단계 더 들어가야 합니다.

`/var/log/messages`가 비정상적으로 빠르게 커져 몇 시간이면 디스크가 소진될 상황입니다.

```bash
-rw-r--r-- 1 root root 12G Mar 04 10:00 /var/log/messages
-rw-r--r-- 1 root root 15G Mar 04 10:05 /var/log/messages
```

```bash
COMMAND    PID  USER   FD   TYPE DEVICE  SIZE/OFF     NODE NAME
rsyslogd  1234  root    7w   REG  253,1  15G      131074 /var/log/messages
```

```bash
Mar  4 10:05:01 server app[5678]: DEBUG: Processing item 982341 - cache check
Mar  4 10:05:01 server app[5678]: DEBUG: Processing item 982342 - cache check
Mar  4 10:05:01 server app[5678]: DEBUG: Processing item 982343 - cache check
```

`lsof`가 지목한 것은 `rsyslogd`입니다. 그런데 여기서 멈추면 안 됩니다. `rsyslogd`는 syslog로 들어온 메시지를 파일에 적는 중계자이지 메시지를 만든 쪽이 아닙니다.

진짜 원인은 파일 안에 적혀 있습니다. `tail`로 보면 `app[5678]`이 DEBUG 레벨 메시지를 초당 수천 건씩 보내고 있고, 대괄호 안의 숫자가 그 프로세스의 PID입니다. 로그를 쓰는 쪽과 로그를 만드는 쪽이 다르다는 구조를 알아야 이 한 걸음을 더 갈 수 있습니다.

원인은 결국 프로덕션에 켜진 DEBUG 레벨입니다. 디스크를 비워도 레벨이 그대로면 5분 뒤 같은 속도로 다시 찹니다.

### 조치

```bash
# 파일을 쓰는 프로세스 확인
lsof /var/log/messages

# 로그 내용에서 원인 프로세스를 특정하고 기록을 남긴다
tail -50 /var/log/messages > excessive_log_process.txt
ps -p 5678 -o pid,user,comm >> excessive_log_process.txt

# 즉시 공간 회수
truncate -s 0 /var/log/messages
```

애플리케이션 설정에서 로그 레벨을 `info` 이상으로 되돌리는 것이 진짜 수정입니다. 디버깅 때문에 잠시 켰다면 끝난 뒤 되돌리는 단계를 절차에 넣어 둡니다.

rsyslog 쪽에서도 방어할 수 있습니다. `imjournal`의 rate limit 설정으로 초당 수용량을 제한하면 한 애플리케이션이 폭주해도 디스크가 몇 분 만에 차는 일은 막힙니다.



## 사례 2 — 어느 애플리케이션이 에러를 냈는지 모릅니다

> `grep -r`에 `--include`를 붙이면 검색 범위를 확장자로 좁힐 수 있습니다. 압축 파일과 바이너리를 훑는 낭비가 사라집니다.

여러 애플리케이션이 `/var/log` 아래에 각자 로그를 남기는 서버에서 장애가 났습니다. 어느 쪽에서 에러가 났는지 빠르게 확인해야 합니다.

```bash
/var/log/
├── apache2/
│   ├── access.log
│   └── error.log
├── application.log
├── mysql/
│   └── error.log
├── nginx/
│   ├── access.log
│   └── error.log
└── syslog
```

```bash
[Thu Mar 04 10:23:45] ERROR: Connection timeout to database server
2026-03-04 10:23:46 ERROR: Unable to write to cache directory
2026-03-04T10:23:45Z ERROR: InnoDB: Cannot allocate memory for buffer pool
```

디렉터리를 하나씩 들어가며 확인하는 방식은 파일이 늘어날수록 무너집니다. 재귀 검색이 필요한 이유입니다.

`--include="*.log"`가 중요한 이유는 속도만이 아닙니다. `/var/log` 아래에는 로테이션된 `.gz`와 journald의 바이너리 파일이 섞여 있어서, 확장자를 안 좁히면 결과에 읽을 수 없는 매칭이 끼어듭니다.

결과를 보면 세 애플리케이션이 같은 시각에 각각 다른 에러를 냈습니다. 파일명이 함께 나오므로 어느 계층에서 시작된 장애인지 추정할 실마리가 생깁니다.

### 조치

```bash
# .log 파일에서만 재귀 검색, 파일명과 함께 저장
grep -r "ERROR" /var/log/ --include="*.log" > error_logs.txt
```

```bash
# 상황별로 붙이는 옵션
grep -rn "ERROR" /var/log/ --include="*.log"    # 줄 번호까지
grep -ri "error" /var/log/ --include="*.log"    # 대소문자 무시
grep -rc "ERROR" /var/log/ --include="*.log"    # 파일별 건수만
```

파일이 많고 크면 `ripgrep`이 훨씬 빠릅니다. 기본으로 `.gitignore`와 바이너리를 걸러 주므로 옵션도 덜 붙습니다.

다만 이 방식은 한 서버 안에서만 통합니다. 서버가 여러 대면 같은 명령을 대수만큼 반복해야 하므로, 그 지점이 중앙 집중 로그 수집을 도입할 시점입니다.



## 사례 3 — 파일이 커서 에디터로 열리지 않습니다

> `split -l`은 줄 수 기준으로 나누므로 로그 한 줄이 잘리지 않습니다. 바이트 기준으로 나누면 경계에서 줄이 끊깁니다.

장애 조사를 위해 받은 접근 로그가 2.5GB입니다. 에디터로 열리지 않고 분석 도구도 버티지 못합니다.

```bash
-rw-r--r-- 1 root root 2.5G Mar 04 10:00 /var/log/app/access.log
```

```bash
375000 /var/log/app/access.log
```

```bash
2026-03-04 08:00:01 192.168.1.100 GET /api/users 200 45ms
2026-03-04 08:00:01 192.168.1.101 POST /api/login 401 12ms
2026-03-04 08:00:02 192.168.1.102 GET /api/products 200 89ms
```

로그를 나눌 때 `-b`가 아니라 `-l`을 쓰는 이유가 있습니다. 바이트 기준으로 자르면 조각 경계에서 한 줄이 두 파일에 걸쳐 잘리고, 그 줄은 어느 쪽에서도 온전히 검색되지 않습니다.

줄 수 기준으로 나누면 모든 조각이 그 자체로 유효한 로그 파일이 됩니다. 조각마다 따로 `grep`을 걸 수 있고 여러 사람이 나눠 볼 수도 있습니다.

나눈 뒤에는 총 줄 수를 대조해 유실이 없는지 확인합니다. 이 한 단계가 "조각 하나를 빠뜨린 채 분석했다"는 사고를 막아 줍니다.

### 조치

```bash
mkdir -p /tmp/log_parts

# 10만 줄 단위로 분할
split -l 100000 /var/log/app/access.log /tmp/log_parts/access_part_

# 원본과 조각의 총 줄 수를 대조
wc -l /var/log/app/access.log
cat /tmp/log_parts/access_part_* | wc -l
```

```bash
# 상황에 맞는 분할 기준
# -l 100000            줄 수 기준, 로그에 적합
# -n 4                 개수를 지정해 균등 분할
# --numeric-suffixes   접미사를 aa 대신 00 으로
```

분할 자체가 목적인 경우는 드뭅니다. 조각을 만든 뒤 병렬로 검색하는 것이 실제 목적이므로, `xargs -P`와 묶어 코어 수만큼 동시에 돌리면 조사 시간이 크게 줄어듭니다.

한편 시간 범위를 먼저 좁힐 수 있으면 분할이 아예 필요 없습니다. `head`와 `tail`로 파일의 시작과 끝 시각을 확인하고 필요한 구간만 뽑아내는 편이 더 빠릅니다.



## 사례 4 — 합쳐 놓은 로그의 순서가 섞였습니다

> 로그 타임스탬프가 `YYYY-MM-DD HH:MM:SS` 형식이면 사전순 정렬이 곧 시간순 정렬입니다. 별도 변환이 필요 없습니다.

서버 네 대의 로그를 한 파일로 합쳤는데 수집 순서대로 붙어 시간순이 뒤섞였습니다. 타임라인을 못 읽는 상태입니다.

```bash
2026-03-04 14:23:45 api02 POST /users/create 201
2026-03-04 14:22:10 cache01 CACHE_MISS key=session_abc
2026-03-04 14:22:55 api01 GET /products/list 200
2026-03-04 14:22:10 db02 INSERT INTO orders VALUES (...)
2026-03-04 14:24:12 cache01 CACHE_SET key=user_profile
2026-03-04 14:21:30 api01 GET /health 200
2026-03-04 14:23:45 db02 SELECT * FROM users WHERE id=42
```

이 형식이 다루기 쉬운 이유는 자릿수가 고정돼 있기 때문입니다. 월이 한 자리로 찍히거나 시간이 12시간제로 적혀 있으면 문자열 순서와 시간 순서가 어긋나지만, ISO 형태는 둘이 일치합니다.

`-k1,2`는 첫 번째와 두 번째 필드, 즉 날짜와 시각을 정렬 키로 씁니다. 여기에 `-k3,3`으로 호스트명을 2차 키로 주면 같은 초에 일어난 이벤트가 호스트별로 묶여 읽기 편해집니다.

정렬 결과를 인과로 읽을 때는 전제를 하나 확인해야 합니다. 서버들의 시계가 맞아 있어야 이 타임라인이 의미를 가집니다.

### 조치

```bash
# 날짜와 시각으로 1차 정렬, 호스트명으로 2차 정렬
sort -k1,2 -k3,3 /tmp/app_combined.log > /tmp/app_sorted.log
```

```bash
2026-03-04 14:21:30 api01 GET /health 200
2026-03-04 14:22:10 cache01 CACHE_MISS key=session_abc
2026-03-04 14:22:10 db02 INSERT INTO orders VALUES (...)
2026-03-04 14:22:55 api01 GET /products/list 200
2026-03-04 14:23:45 api02 POST /users/create 201
2026-03-04 14:23:45 db02 SELECT * FROM users WHERE id=42
2026-03-04 14:24:12 cache01 CACHE_SET key=user_profile
```

서버 간 시계가 어긋나 있으면 정렬된 순서가 실제 인과와 다를 수 있습니다. NTP 동기화 여부는 타임라인 분석의 전제 조건이라, 결론을 내기 전에 확인해 두는 편이 안전합니다.

로그 형식이 서버마다 다르면 `sort`만으로는 부족합니다. 그 지점부터는 파싱과 색인을 해 주는 Loki 같은 도구의 영역입니다.



## 사례 5 — 로그에 시간이 안 찍혀 있습니다

> 애플리케이션이 시간을 안 찍으면 파이프에서 붙일 수 있습니다. 다만 그 시간은 발생 시각이 아니라 도착 시각입니다.

수동으로 띄운 서비스의 출력에 타임스탬프가 없어 이벤트 순서와 간격을 분석하기 어렵습니다.

```bash
Application started
Processing request #1234
Database connection established
Cache warming completed
```

```bash
Application started - 2026-03-04 15:30:45
Processing request #1234 - 2026-03-04 15:30:46
Database connection established - 2026-03-04 15:30:47
Cache warming completed - 2026-03-04 15:30:48
```

표준 출력으로 로그를 내면서 시간을 안 찍는 프로그램이 생각보다 많습니다. 컨테이너 환경에서는 런타임이 시간을 붙여 주기 때문에 애플리케이션이 생략하는 경우도 흔합니다.

파이프 중간에서 한 줄씩 읽어 시간을 붙이는 방식으로 해결할 수 있습니다. 다만 여기서 찍히는 시간은 그 줄이 파이프에 도착한 시각이지 이벤트가 발생한 시각이 아닙니다. 버퍼링이 있으면 여러 줄이 같은 시각으로 몰려 찍힙니다.

그래서 이 방법은 대략의 순서와 간격을 보려는 용도입니다. 정확한 발생 시각이 필요하면 애플리케이션이 직접 찍게 만들어야 합니다.

### 조치

```bash
# moreutils 의 ts 가 가장 간단하다
./my-service | ts '%Y-%m-%d %H:%M:%S'

# ts 가 없는 환경에서는 셸 루프로 대체
./my-service | while IFS= read -r line; do
  echo "$line - $(date '+%Y-%m-%d %H:%M:%S')"
done
```

```bash
# 재사용할 스크립트로 남긴다
cat > /usr/local/bin/timestamp.sh << 'EOF'
#!/bin/bash
while IFS= read -r line; do
  echo "$line - $(date '+%Y-%m-%d %H:%M:%S')"
done
EOF
chmod +x /usr/local/bin/timestamp.sh
```

systemd로 관리되는 서비스라면 이 작업이 필요 없습니다. journald가 받은 줄마다 시각을 기록하므로 `journalctl -u <서비스>`로 바로 확인됩니다.

근본적으로는 애플리케이션이 구조화된 형태로 로그를 내는 편이 낫습니다. 시각과 레벨과 메시지가 필드로 분리돼 있으면 이 문서의 사례 2와 사례 4가 함께 쉬워집니다.



## 다섯 사례를 관통하는 것

> 다섯 도구는 모두 로그를 사람이 읽을 수 있는 형태로 바꿉니다. 그리고 다섯 중 넷은 애플리케이션이 처음부터 잘 찍었으면 필요 없는 작업입니다.

`grep`·`split`·`sort`·`ts`는 이미 만들어진 로그를 뒤에서 손보는 도구입니다. 반대로 말하면 로그가 잘 설계돼 있으면 이 작업들이 대부분 사라집니다. 레벨이 적절하면 사례 1이, 중앙 수집이 있으면 사례 2와 사례 3이, 구조화된 형식이면 사례 4와 사례 5가 필요 없습니다.

조사 중에 반복되는 습관도 하나 있습니다. 결과를 파일로 남기는 것입니다. 사례 1의 `excessive_log_process.txt`와 사례 2의 `error_logs.txt`가 그 예이고, 장애 대응은 대개 여러 사람이 이어 붙이는 작업이라 화면에만 남은 결과는 곧 사라집니다.

마지막으로 도구의 한계를 함께 기억해 둡니다. `sort`는 시계가 맞다는 전제 위에서만 옳고, 파이프 타임스탬프는 도착 시각일 뿐입니다. 도구가 만들어 준 결과를 사실로 읽기 전에 그 전제가 성립하는지를 봐야 합니다.
