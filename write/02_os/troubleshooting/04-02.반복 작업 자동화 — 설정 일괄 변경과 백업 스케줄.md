# 반복 작업 자동화 — 설정 일괄 변경과 백업 스케줄

---

> 손으로 반복하던 일을 스크립트로 옮기면 실수는 줄지만 실수의 크기는 커집니다. 그래서 자동화의 절반은 되돌릴 방법을 먼저 마련하는 일입니다.

앞 문서들이 이미 벌어진 일을 조사하는 쪽이었다면, 이 문서는 사람이 반복하던 작업을 기계에 넘기는 쪽입니다.

두 사례가 자동화의 두 얼굴을 보여 줍니다. 하나는 한 번에 여러 파일을 고치는 일이고, 다른 하나는 매일 같은 시각에 도는 일을 만드는 것입니다. 전자는 되돌릴 준비가, 후자는 정리할 준비가 핵심입니다.



## 자동화 전에 되돌릴 길을 만듭니다

> 사람이 열 파일을 손으로 고치면 실수는 한 파일에서 납니다. 스크립트가 고치면 실수는 열 파일 전부에서 납니다.

자동화의 이점은 분명합니다. 파일을 빠뜨리지 않고 오타가 섞이지 않습니다. 그런데 같은 이유로 잘못된 명령도 빠짐없이 정확하게 적용됩니다.

특히 `sed -i`처럼 파일을 그 자리에서 바꾸는 명령은 되돌리기가 어렵습니다. 원본이 남지 않으므로 무엇을 바꿨는지조차 확인할 수 없습니다.

그래서 순서를 고정합니다. 대상 확인, 백업, 변경, 검증 네 단계입니다. 이 중 백업과 검증을 빼면 그때부터 자동화는 위험한 도박이 됩니다.

| 단계 | 목적 | 대표 명령 |
|------|------|-----------|
| 대상 확인 | 무엇이 바뀔지 눈으로 본다 | `find ... -name "*.conf"` |
| 백업 | 되돌릴 길을 만든다 | `find ... -exec cp {} {}.bak \;` |
| 변경 | 실제 수정 | `sed -i -e ... {}` |
| 검증 | 의도대로 됐는지 대조 | `grep -H`, `diff` |



## 사례 1 — 환경 세 곳의 설정을 같이 바꿔야 합니다

> 손으로 고치면 세 파일 중 하나를 빠뜨립니다. 자동화의 이점은 속도가 아니라 누락이 없다는 데 있습니다.

가용 영역 설정을 단일 구성에서 멀티 구성으로 바꿔야 합니다. 같은 내용의 설정 파일이 환경별로 흩어져 있습니다.

```bash
/etc/app/envs/staging/app.conf
/etc/app/envs/dev/app.conf
/etc/app/envs/prod/app.conf
```

```ini
region = "us-east-1"
availability_zone = "us-east-1a"
multi_az = false
instance_type = "t3.medium"
```

```ini
availability_zone = "us-east-1a,us-east-1b"
multi_az = true
```

바꿀 것은 두 줄이고 파일은 세 개입니다. 손으로 해도 되는 규모처럼 보이지만, 이런 작업에서 사고는 대개 "prod만 빠뜨렸다"는 형태로 납니다. 환경마다 결과가 달라지면 원인을 찾기까지 오래 걸립니다.

`find`로 대상을 모으고 `sed -i`로 고치면 누락이 사라집니다. `-e`를 두 번 써서 두 치환을 한 번의 실행에 담으면 파일을 두 번 여는 낭비도 없습니다.

여기서 백업이 특히 중요한 이유가 있습니다. 치환 패턴이 한 글자라도 틀리면 아무 파일도 안 바뀌거나 엉뚱한 줄이 바뀌는데, 둘 다 실행 시점에는 에러 없이 조용히 지나갑니다.

### 조치

```bash
# 대상 확인
find /etc/app/envs -name "*.conf" -type f

# 되돌릴 길부터 만든다
find /etc/app/envs -name "*.conf" -exec cp {} {}.bak \;

# 두 치환을 한 번에 적용
find /etc/app/envs -name "*.conf" -exec sed -i \
  -e 's/multi_az = false/multi_az = true/' \
  -e 's/availability_zone = "us-east-1a"/availability_zone = "us-east-1a,us-east-1b"/' \
  {} \;

# 파일명과 함께 결과를 확인해 누락을 찾는다
find /etc/app/envs -name "*.conf" -exec grep -H "multi_az\|availability_zone" {} \;

# 한 파일은 변경 전후를 직접 대조
diff /etc/app/envs/prod/app.conf.bak /etc/app/envs/prod/app.conf
```

`grep -H`가 파일명을 함께 찍어 주는 덕분에 세 파일이 모두 바뀌었는지 한눈에 보입니다. 검증 없이 넘어가면 안 바뀐 파일이 다음 배포 때 드러납니다.

macOS에서 같은 명령을 쓸 때는 주의할 점이 있습니다. BSD `sed`는 `-i` 뒤에 백업 확장자를 반드시 요구하므로 `sed -i ''` 형태로 빈 문자열을 명시해야 합니다.

더 근본적으로는 이런 설정을 Ansible이나 Terraform 같은 도구로 관리하는 편이 낫습니다. 변경이 코드로 남으면 버전 관리와 되돌리기가 백업 파일보다 훨씬 안전해집니다.



## 사례 2 — 백업을 매번 손으로 돌리고 있습니다

> 백업 자동화는 만드는 쪽보다 지우는 쪽이 어렵습니다. 보존 정책이 없으면 백업이 디스크를 채웁니다.

설정 파일이 실수로 바뀌거나 지워지는 사고가 반복되는데 자동 백업 체계가 없습니다. 매번 손으로 복구하는 중입니다.

```bash
ls: cannot access '/usr/local/bin/backup_etc.sh': No such file or directory
```

```bash
no crontab for root
```

요구 사항은 여섯 가지입니다.

- 스크립트는 `/usr/local/bin/backup_etc.sh`에 둔다
- 백업 저장 경로를 인자로 받는다
- 인자 없이 실행하면 에러를 내고 종료한다
- 아카이브 이름은 `etc-backup-YYYY-MM-DD.tar.gz` 형식이다
- 7일 이상 지난 백업은 자동으로 지운다
- 매일 새벽 2시에 실행한다

세 번째와 다섯 번째가 이 요구 사항의 핵심입니다. 인자 검사가 없으면 경로가 빈 채로 실행돼 엉뚱한 자리에 파일이 생기고, 보존 정책이 없으면 백업 자체가 디스크를 채우는 원인이 됩니다.

앞 문서에서 본 디스크 포화 사례의 상당수가 이렇게 만들어집니다. 백업을 만드는 부분만 짜고 지우는 부분을 안 짜면, 몇 달 뒤 `/backups`가 파티션에서 가장 큰 디렉터리가 됩니다.

### 조치

```bash
mkdir -p /backups/etc

cat > /usr/local/bin/backup_etc.sh << 'SCRIPT'
#!/bin/bash
set -u
BACKUP_DIR="$1"

# 인자가 없으면 즉시 종료한다. 빈 경로로 진행하는 것이 가장 위험하다
if [ -z "${BACKUP_DIR:-}" ]; then
  echo "Error: backup directory path required" >&2
  echo "Usage: $0 <backup-directory>" >&2
  exit 1
fi

mkdir -p "$BACKUP_DIR"

FILENAME="etc-backup-$(date +%Y-%m-%d).tar.gz"
tar -czf "${BACKUP_DIR}/${FILENAME}" /etc 2>/dev/null

# 보존 정책 — 만드는 것과 같은 스크립트 안에 둔다
find "$BACKUP_DIR" -name "etc-backup-*.tar.gz" -mtime +7 -delete

echo "Backup completed: ${BACKUP_DIR}/${FILENAME}"
SCRIPT

chmod +x /usr/local/bin/backup_etc.sh

# 예약 등록 전에 손으로 한 번 돌려 본다
/usr/local/bin/backup_etc.sh /backups/etc/
ls -lh /backups/etc/

# 기존 항목을 보존하면서 예약에 추가
(crontab -l 2>/dev/null; echo "0 2 * * * /usr/local/bin/backup_etc.sh /backups/etc/") | crontab -
crontab -l
```

`crontab -e` 대신 위와 같은 형태를 쓰는 이유는 기존 항목을 지우지 않기 위해서입니다. `crontab -` 는 표준 입력의 내용으로 전체를 덮어쓰므로, 앞에 `crontab -l`을 붙여 기존 목록을 함께 흘려보내야 합니다.

보존 정책을 백업 스크립트 안에 두는 것도 의도적입니다. 별도 정리 작업으로 분리하면 그 작업만 조용히 멈췄을 때 아무도 눈치채지 못합니다.

예약 작업은 실패해도 조용하다는 점을 늘 염두에 둡니다. 성공과 실패를 로그로 남기고 모니터링으로 보내는 단계까지 가야 "백업이 있다"는 말을 신뢰할 수 있습니다.



## 두 사례를 관통하는 것

> 자동화의 위험은 명령이 틀렸을 때가 아니라 틀렸는데도 성공한 것처럼 보일 때 생깁니다. 검증 단계가 그 간극을 메웁니다.

`sed`의 치환 패턴이 안 맞아도 명령은 성공하고, 예약 작업이 실패해도 화면에는 아무것도 안 뜹니다. 두 사례의 공통된 위험은 실패가 조용하다는 점입니다.

그래서 두 사례 모두 마지막에 검증이 붙습니다. `grep -H`로 파일마다 결과를 확인하는 것과 예약 등록 전에 스크립트를 손으로 한 번 돌려 보는 것이 같은 역할을 합니다.

되돌릴 길과 지울 길을 함께 준비하는 것도 반복됩니다. 설정 변경에는 `.bak`이 그 역할을 하고 백업에는 `-mtime +7 -delete`가 그 역할을 합니다. 만드는 코드만 있고 되돌리거나 정리하는 코드가 없는 자동화는 반쪽입니다.
