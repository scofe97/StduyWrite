# 로그가 디스크를 먹는 방식 — 급증 추적과 용량 산정

---

> 로그로 디스크가 터지는 사고는 대부분 로테이션이 없거나, 있어도 파티션 크기와 맞지 않아 생깁니다. 어느 쪽인지는 `logrotate` 설정 디렉터리와 마운트 지점을 같이 봐야 갈립니다.

앞 문서가 "디스크가 찼다"의 세 갈래를 갈랐다면, 이 문서는 그중 가장 흔한 갈래인 로그 하나를 끝까지 따라갑니다.

로그는 다른 파일과 성질이 다릅니다. 사람이 만들지 않고 서비스가 초당 수백 줄씩 스스로 만들며, 아무도 지우라고 말해 주지 않으면 영원히 자랍니다. 그래서 로그 사고는 "누가 채웠나"보다 "왜 아무도 안 비웠나"를 묻는 편이 빠릅니다.



## 로그 용량 사고의 세 가지 실패 지점

> 로그가 파티션을 채우는 경로는 셋입니다. 로테이션 설정이 아예 없거나, 있어도 파티션보다 크게 잡혔거나, 얼마나 쌓였는지 아무도 재지 않은 경우입니다.

로그 사고를 만나면 대개 `df`부터 칩니다. 그런데 `df`는 지금 얼마나 찼는지만 알려 주고, 왜 그 지경이 됐는지는 말해 주지 않습니다. 원인은 설정 파일 쪽에 있습니다.

세 실패 지점은 서로 다른 곳에서 드러납니다. 설정 누락은 `/etc/logrotate.d/` 목록에서, 크기 불일치는 `df`와 `mount`를 나란히 놓을 때, 계측 부재는 애초에 아무도 세어 본 적이 없다는 사실에서 보입니다.

| 실패 지점 | 어디서 드러나나 | 이 문서의 사례 |
|-----------|-----------------|----------------|
| 로테이션 설정 자체가 없음 | `ls /etc/logrotate.d/`에 그 앱이 빠져 있음 | 사례 2 |
| 로테이션은 있지만 파티션보다 큼 | `df`의 마운트 지점이 `/`가 아님 | 사례 1 |
| 얼마나 쌓였는지 안 재고 있음 | 정리 계획을 세울 근거가 없음 | 사례 3 |



## 사례 1 — 루트는 55GB 남았는데 로그가 안 쌓입니다

> `/var/log`가 별도 파티션이면 루트의 여유 공간은 아무 도움이 되지 않습니다. 마운트 지점을 보지 않으면 이 사실이 안 보입니다.

로테이션이 동작하지 않고 새 로그도 기록되지 않습니다. 애플리케이션은 정상 실행 중입니다.

```bash
logrotate: error: failed to rename /var/log/app.log to /var/log/app.log.1: No space left on device
logrotate: error: failed to create new /var/log/app.log: No space left on device
```

```bash
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1       100G   45G   55G  45% /
/dev/sdb1        10G  9.8G  200M  98% /var/log
tmpfs           3.9G     0  3.9G   0% /dev/shm
```

```bash
/dev/sdb1 on /var/log type ext4 (rw,relatime)
```

```bash
-rw-r--r-- 1 root   root   4.2G Mar 01 09:00 app.log
-rw-r--r-- 1 root   root   3.1G Feb 28 23:59 app.log.1
-rw-r--r-- 1 root   root   2.0G Feb 27 23:59 app.log.2.gz
-rw-r--r-- 1 syslog syslog  24K Mar 01 09:01 syslog
```

에러 메시지가 정확히 짚어 줍니다. 로테이션은 이름을 바꾸고 새 파일을 만드는 작업인데, 둘 다 공간이 없어 실패했습니다.

여기서 함정은 `df`의 첫 줄입니다. 루트에 55GB가 남아 있어 "공간이 없다"는 말이 틀린 것처럼 보입니다. 하지만 `/var/log`는 `/dev/sdb1`이라는 10GB 파티션에 따로 마운트되어 있고, 파일시스템이 다르면 루트의 여유는 이쪽으로 넘어오지 않습니다.

문제의 본질은 보관 정책과 파티션 크기의 불일치입니다. 현재 로그 하나가 4.2GB인데 그것을 세 세대까지 남기면 10GB 파티션으로는 절대 감당할 수 없습니다.

### 조치

```bash
# 가장 오래된 세대를 지워 당장 숨 쉴 공간을 만든다
rm /var/log/app.log.2.gz
truncate -s 0 /var/log/app.log

# 보관 세대와 파일 크기 상한을 파티션에 맞게 다시 잡는다
cat > /etc/logrotate.d/app << 'EOF'
/var/log/app.log {
    daily
    rotate 3
    compress
    delaycompress
    maxsize 1G
    copytruncate
    missingok
    notifempty
}
EOF

# 여유 확인
df -h /var/log
```

`maxsize 1G`가 핵심입니다. 이 옵션이 없으면 로테이션은 하루에 한 번만 돌아 그사이 파일이 4GB까지 자랄 수 있습니다. 크기 상한을 함께 걸어야 파티션 용량을 넘기기 전에 로테이션이 먼저 개입합니다.

파티션 자체가 작다고 판단되면 LVM 환경에서 `lvextend` 뒤 `resize2fs`로 온라인 확장이 가능합니다. 다만 확장은 보관 정책을 정리한 다음의 선택지이지 첫 번째 대응이 아닙니다.



## 사례 2 — 로테이션 설정에 그 앱만 빠져 있습니다

> 시스템 패키지는 설치할 때 로테이션 설정을 같이 깔아 줍니다. 직접 만든 애플리케이션은 아무도 깔아 주지 않습니다.

`/var` 사용률이 92%에 도달했고 계속 오르는 중입니다. 어느 파일이 먹고 있는지, 그 파일을 누가 열고 있는지, 로테이션이 걸려 있는지를 한 번에 봅니다.

```bash
45G     /var/log
12G     /var/lib
2.5G    /var/cache
320M    /var/spool
```

```bash
/var/log/mysql/mysql-slow.log     2.3G
/var/log/nginx/access.log         1.3G
/var/log/myapp/app.log           38G
/var/log/syslog.1                655M
```

```bash
COMMAND   PID   USER   FD   TYPE DEVICE SIZE/OFF    NODE NAME
java     2341   app    1w   REG  253,1  38G     131074 /var/log/myapp/app.log
java     2341   app    2w   REG  253,1  38G     131074 /var/log/myapp/app.log
```

```bash
apt  dpkg  mysql-server  nginx  rsyslog
```

`app.log` 하나가 38GB입니다. `lsof`를 보면 `java` 프로세스가 이 파일을 표준 출력과 표준 에러 양쪽으로 열어 두고 있어, 파일을 지워도 프로세스가 끝날 때까지 블록이 반납되지 않습니다.

결정적인 단서는 마지막 출력입니다. `/etc/logrotate.d/`에 `mysql-server`와 `nginx`는 있는데 `myapp`이 없습니다. 패키지 매니저로 설치한 미들웨어는 로테이션 설정을 함께 배포하지만, 직접 만든 애플리케이션은 배포 파이프라인에 그 단계를 넣지 않으면 아무도 넣어 주지 않습니다.

즉 이 사고의 원인은 로그가 많아서가 아니라 로그를 줄이는 장치가 처음부터 없어서입니다. 용량을 비워도 설정을 만들지 않으면 며칠 안에 같은 상태로 돌아옵니다.

### 조치

```bash
# 프로세스가 잡고 있으므로 내용만 비워 즉시 회수한다
truncate -s 0 /var/log/myapp/app.log
df -h /

# 빠져 있던 로테이션 설정을 만든다
cat > /etc/logrotate.d/myapp << 'EOF'
/var/log/myapp/*.log {
    daily
    rotate 7
    compress
    delaycompress
    maxsize 500M
    copytruncate
    missingok
    notifempty
}
EOF

# 실제로 돌리지 않고 동작만 시뮬레이션해 본다
logrotate -d /etc/logrotate.d/myapp

# 같이 커진 다른 로그도 정리
truncate -s 0 /var/log/mysql/mysql-slow.log
```

`copytruncate`는 원본을 복사한 뒤 원본을 0으로 자르는 방식이라 프로세스를 재시작하지 않아도 됩니다. 애플리케이션이 열어 둔 파일 디스크립터가 그대로 유효하기 때문입니다. 대신 복사와 절단 사이에 쓰인 몇 줄이 유실될 수 있어, 무중단이 더 중요한 환경에서 고르는 선택지입니다.

이미 지워졌는데 공간이 안 도는 상황이 의심되면 `lsof +L1`으로 링크 수가 0인 채 열려 있는 파일을 찾을 수 있습니다.



## 사례 3 — 정리하려는데 무엇을 정리할지 모릅니다

> 정리 계획에는 숫자가 필요합니다. `find`의 `-size`와 `-mtime`이 그 숫자를 만들어 줍니다.

`/var` 사용량이 꾸준히 늘어 정리 계획을 세워야 합니다. 여러 애플리케이션이 각자의 하위 디렉터리에 로그를 쌓고 있습니다.

```bash
28G     /var/log/
5.2G    /var/lib/
1.8G    /var/cache/
120M    /var/spool/
```

```bash
/var/log/syslog.log
/var/log/nginx/access.log
/var/log/mysql/slow-query.log
/var/log/app/application.log
/var/log/app/debug.log
/var/log/apache2/access.log
```

앞의 두 사례와 달리 여기에는 고칠 장애가 없습니다. 지금 급한 불은 없지만 추세가 나쁘고, 어디부터 손댈지 정하려면 근거가 필요한 상황입니다.

이때 필요한 것은 전체 개수와 대용량 파일 개수 두 숫자입니다. 전체 개수는 관리 대상의 규모를 알려 주고, 대용량 파일 개수는 그중 실제로 효과가 있을 정리 대상을 좁혀 줍니다. 작은 파일 천 개를 지우는 것보다 큰 파일 다섯 개를 정리하는 편이 대개 이득입니다.

### 조치

```bash
# 관리 대상 전체 규모
find /var -name "*.log" -type f | wc -l

# 정리 효과가 있을 대용량 파일 규모
find /var -name "*.log" -type f -size +512k | wc -l

# 정리 후보를 크기 역순으로 실제 목록화
find /var -name "*.log" -type f -size +512k -exec ls -lh {} \; | sort -k5 -rh
```

```bash
# 자주 쓰는 조건
# -size +512k        512KB 초과
# -mtime +30         마지막 수정이 30일 이전
# -exec ... {} \;    검색된 파일마다 명령 실행
```

정기 정리를 자동화할 때는 `find /var/log -name "*.log" -mtime +30 -delete`를 예약 작업에 걸어 둡니다. 다만 `-delete`를 붙이기 전에 같은 조건을 `-print`로 한 번 돌려 대상 목록을 눈으로 확인하는 습관이 안전합니다.

현재 쓰이는 로그는 로테이션이 맡고, 오래된 아카이브는 `find`가 맡는 이중 구성이 실무에서 가장 무난합니다.



## 세 사례를 관통하는 것

> 로그 사고의 진짜 원인은 언제나 설정 쪽에 있습니다. 용량을 비우는 명령은 증상 완화이고, 로테이션 설정이 치료입니다.

세 사례의 응급 조치는 서로 닮았습니다. `truncate`로 비우거나 오래된 세대를 지우면 몇 초 만에 서비스가 살아납니다. 그런데 그것으로 끝낸 서버가 왜 며칠 뒤 같은 자리로 돌아오는지는 설명되지 않습니다.

`rm`이 아니라 `truncate`를 쓰는 이유도 반복해서 나옵니다. 프로세스가 파일을 열고 있으면 디렉터리 엔트리를 지워도 inode와 블록은 살아 있습니다. 이 성질은 로그 파일에서 특히 자주 부딪힙니다. 로그는 서비스가 계속 열어 두는 파일이기 때문입니다.

마지막으로, 새 애플리케이션을 배포할 때 로테이션 설정을 함께 배포하는지 확인하는 항목 하나가 사례 2 전체를 막습니다. 사고를 겪고 나서 만드는 설정과 배포할 때 같이 넣는 설정은 내용이 같지만 비용이 다릅니다.
