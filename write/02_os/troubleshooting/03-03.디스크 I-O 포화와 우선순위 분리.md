# 디스크 I/O 포화와 우선순위 분리

---

> CPU와 메모리가 멀쩡한데 서버가 느리면 남은 후보는 디스크입니다. 그리고 디스크 경합은 대개 백업이 데이터베이스와 같은 우선순위로 도는 데서 생깁니다.

두 사례는 사실상 같은 상황을 두 단계로 나눈 것입니다. 앞은 포화를 만든 프로세스를 찾는 단계이고, 뒤는 찾은 뒤에 정책을 세우는 단계입니다.

같은 화면을 두 번 보는 셈이지만 묻는 질문이 다릅니다. 처음에는 "누가 먹고 있나"를 묻고, 그다음에는 "누가 먼저여야 하나"를 묻습니다.



## I/O 포화는 사용률과 점유자를 함께 봅니다

> `iostat`의 `%util`이 장치가 얼마나 바쁜지를 알려 주고, `iotop`이 그 바쁨을 만든 프로세스를 지목합니다. 둘 중 하나만 보면 진단이 반쪽입니다.

CPU와 메모리가 정상인데 응답이 느리면 디스크를 의심합니다. 그런데 디스크는 CPU와 달리 "사용률"이라는 말이 직관적으로 안 맞습니다.

`%util`은 장치에 요청이 하나라도 걸려 있던 시간의 비율입니다. 그래서 이 값이 99.8%라는 것은 디스크가 거의 쉬지 않았다는 뜻이지, 대역폭을 다 썼다는 뜻은 아닙니다. 그래도 판정에는 충분합니다. 쉬지 않는 장치 앞에서 프로세스들이 줄을 서고, 그 대기가 곧 응답 지연이 됩니다.

값이 높다는 사실만으로는 고칠 수 없으므로 점유자를 함께 봐야 합니다. `iotop`이 프로세스별 읽기와 쓰기, 그리고 I/O를 기다린 시간 비율을 보여 줍니다.

| 도구 | 답하는 질문 | 눈여겨볼 열 |
|------|-------------|-------------|
| `iostat -x 1` | 장치가 포화인가 | `%util`, `r/s`, `w/s` |
| `iotop -o -b -n 1` | 누가 만들고 있나 | `DISK READ`, `DISK WRITE`, `IO>` |
| `ionice -p <PID>` | 그 프로세스의 우선순위는 | 클래스와 우선순위 값 |



## 사례 1 — 디스크가 쉬지 않고 사용자 접근이 느립니다

> 백업이 데이터베이스와 같은 우선순위로 돌면 디스크는 둘을 공평하게 나눠 줍니다. 공평함이 문제인 상황입니다.

간헐적인 지연과 타임아웃이 발생합니다. CPU와 메모리는 정상인데 디스크 I/O만 비정상적으로 높고, 어느 프로세스가 만든 부하인지는 이 사실만으로 알 수 없습니다.

```bash
Total DISK READ:      125.43 M/s | Total DISK WRITE:      89.32 M/s

  TID  PRIO  USER      DISK READ  DISK WRITE  SWAPIN     IO>    COMMAND
 5678  be/4  backup     98.45 M/s   67.23 M/s  0.00 %  95.32 % rsync /data /backup
 3421  be/4  postgres   15.23 M/s   12.45 M/s  0.00 %  18.45 % postgres: vacuum
 8234  be/4  appuser     8.45 M/s    3.21 M/s  0.00 %  12.10 % /usr/bin/log-processor
```

```bash
Device   r/s     w/s   rkB/s    wkB/s  %util
sda    2450.0  1890.0 128440.0  91320.0  99.8
```

`%util` 99.8%로 장치는 사실상 포화입니다. `iotop`을 보면 `rsync` 하나가 읽기 98.45MB/s와 쓰기 67.23MB/s로 전체의 대부분을 차지하고 있습니다.

여기서 봐야 할 열이 `PRIO`입니다. 세 프로세스가 전부 `be/4`, 즉 Best-effort 클래스의 기본 우선순위입니다. 커널의 I/O 스케줄러 입장에서 백업과 데이터베이스는 동등한 요청자이므로 요청을 순서대로 공평하게 처리합니다.

문제의 성격이 여기서 드러납니다. 디스크가 느린 것도 아니고 백업이 잘못 만들어진 것도 아닙니다. 중요도가 다른 작업에 같은 우선순위를 준 설정이 원인입니다.

### 조치

```bash
# 점유자와 우선순위를 함께 확인
iotop -o -b -n 1

# 비핵심 작업을 idle 클래스로 내린다
ionice -c 3 -p 5678
ionice -c 3 -p 8234

# 반영 확인
ionice -p 5678
iotop -o -b -n 1
```

```bash
# I/O 클래스
# -c 1  Realtime     최우선, 다른 요청을 굶길 수 있어 신중히
# -c 2  Best-effort  기본값, 안에서 0(높음)~7(낮음) 우선순위
# -c 3  Idle         다른 요청이 없을 때만 디스크를 쓴다
```

`idle` 클래스는 이름 그대로 디스크가 한가할 때만 요청을 흘려보냅니다. 백업은 몇 분 늦어져도 되지만 데이터베이스 응답은 늦으면 안 되므로, 이 비대칭을 그대로 설정에 옮기는 것입니다.

주의할 점은 `ionice`가 모든 상황에서 통하지는 않는다는 것입니다. 클래스 구분은 I/O 스케줄러가 지원해야 의미가 있고, 쓰기가 페이지 캐시를 거쳐 나중에 반영되는 경로에서는 효과가 흐려집니다.



## 사례 2 — 어느 작업이 먼저여야 하는지 정하지 않았습니다

> 우선순위 분리는 사고가 났을 때 내리는 조치가 아니라 미리 정해 두는 정책입니다. 핵심은 기본값을 유지하고 배치만 내립니다.

사용자들이 파일 접근이 느리다고 보고합니다. 백업과 로그 프로세서가 데이터베이스와 같은 우선순위로 돌면서 쿼리 응답이 밀리고 있습니다.

```bash
Total DISK READ:      45.67 M/s | Total DISK WRITE:     123.45 M/s

  TID  PRIO  USER      DISK READ  DISK WRITE  SWAPIN     IO>    COMMAND
 5678  be/4  backup     2.34 M/s   98.76 M/s  0.00 %  72.10 % rsync /data /backup
 3421  be/4  postgres  15.23 M/s   12.45 M/s  0.00 %  18.45 % postgres: vacuum
 8234  be/4  appuser    8.45 M/s    3.21 M/s  0.00 %  12.34 % /usr/bin/log-processor
```

```bash
best-effort: prio 4
```

앞 사례와 같은 구성인데 이번에는 쓰기 쪽이 몰려 있습니다. `rsync`가 전체 쓰기 123.45MB/s 중 98.76MB/s를 차지해 80%에 가깝습니다.

조치도 같지만 관점이 다릅니다. 앞에서는 지금 터진 것을 껐다면, 여기서는 어느 작업이 어느 클래스에 속하는지를 미리 정합니다. 정책이 서면 사고 대응이 아니라 배포 설정의 문제가 됩니다.

기준은 단순합니다. 사용자 요청 경로에 있는 것은 기본 클래스를 유지하고, 사람이 기다리지 않는 배치 작업은 idle로 내립니다. 핵심 서비스를 realtime으로 올리는 방향은 권하지 않습니다. realtime은 다른 요청을 굶길 수 있어 위험이 큽니다.

### 조치

```bash
# 비핵심 작업만 idle 로 내리고 핵심 서비스는 건드리지 않는다
ionice -c 3 -p 5678
ionice -c 3 -p 8234

# 세 프로세스의 클래스를 확인
ionice -p 5678
ionice -p 8234
ionice -p 3421
```

```bash
# 처음부터 낮게 띄우는 것이 정책의 실체다
0 2 * * * ionice -c 3 nice -n 10 /usr/local/bin/backup.sh
```

예약 작업 한 줄에 `ionice`와 `nice`를 함께 붙이는 것이 실무의 기본형입니다. 배치는 CPU와 디스크 양쪽에서 양보해야 하고, 둘 중 하나만 낮추면 다른 쪽에서 다시 경합합니다.

더 강한 보장이 필요하면 cgroup v2의 `io.weight`으로 그룹 단위 대역폭 비율을 지정할 수 있습니다. `ionice`가 프로세스 하나의 순서를 정한다면 `io.weight`은 그룹의 몫 자체를 정합니다.



## 두 사례를 관통하는 것

> I/O 문제의 답은 대개 장치를 바꾸는 것이 아니라 순서를 정하는 것입니다. 그리고 그 순서는 사고 전에 정해 두는 편이 훨씬 쌉니다.

두 사례가 보여 주는 것은 같은 명령의 두 가지 쓰임입니다. `ionice -c 3`은 사고 중에는 응급 조치이고 예약 작업 안에서는 정책입니다. 명령은 같지만 언제 실행되느냐가 가치를 완전히 바꿉니다.

진단 쪽에서도 짝이 반복됩니다. `iostat`이 장치가 포화인지를 판정하고 `iotop`이 점유자를 지목하는 구조는 CPU에서 로드 평균과 `ps`가 하는 일과 같습니다. 자원이 달라도 총량 판정과 점유자 특정이라는 두 단계는 그대로입니다.

마지막으로 이 문서의 조치가 디스크를 빠르게 만들지 않는다는 점을 기억해 둡니다. 총 처리량은 그대로이고 누가 먼저 쓰는지만 바뀝니다. 총량이 정말 모자란다면 우선순위로는 풀리지 않고 장치나 구조를 바꿔야 합니다.
