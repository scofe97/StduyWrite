# 자원 병목 — CPU 우선순위와 메모리 누수

---

> "서버가 느리다"는 신고에는 CPU 부족, 우선순위 배분, 메모리 고갈이 뒤섞여 있습니다. 로드 평균 세 숫자를 먼저 읽으면 어느 쪽인지가 대체로 갈립니다.

앞 문서가 범인을 특정하는 법이었다면, 이 문서는 특정한 뒤에 무엇을 조절할지에 관한 것입니다.

느리다는 증상은 자원이 모자랄 때도 나고, 자원은 있는데 엉뚱한 프로세스가 먼저 가져갈 때도 납니다. 두 경우의 조치가 완전히 다르기 때문에, 조치를 고르기 전에 어느 쪽인지 먼저 판정해야 합니다.



## 느리다는 신고를 숫자로 바꿉니다

> 로드 평균은 CPU 사용률이 아니라 실행을 기다리는 큐 길이입니다. 코어 수와 나란히 놓아야 의미가 생깁니다.

"서버가 느립니다"는 관측이 아니라 인상입니다. 그 인상만으로는 어디를 손봐야 할지 알 수 없습니다. 관측 가능한 숫자로 바꿔야 합니다.

가장 싼 숫자가 로드 평균입니다. `uptime` 한 줄이면 1분·5분·15분 세 값이 나옵니다. 세 값의 대소 관계가 부하의 방향을 알려 줍니다. 1분이 크면 지금 막 시작된 부하이고 15분이 크면 오래된 상태입니다.

주의할 점은 이 값이 CPU 사용률이 아니라는 것입니다. 로드 평균은 실행 중이거나 실행을 기다리는 프로세스 수이고, 리눅스에서는 디스크 응답을 기다리는 프로세스까지 포함됩니다. 그래서 로드가 높아도 CPU는 놀고 있을 수 있습니다.

| 관측 | 명령 | 판단 기준 |
|------|------|-----------|
| 부하의 크기와 방향 | `uptime` | 세 값의 대소로 추세를 읽는다 |
| 판단 기준선 | `nproc` | 15분 로드가 코어 수를 넘으면 과부하 |
| CPU 인지 I/O 인지 | `vmstat 1 5` | `wa` 열이 크면 병목은 디스크 쪽 |



## 사례 1 — 로드가 높은데 과부하인지 아닌지 모르겠습니다

> 로드 평균 하나만으로는 판정이 안 됩니다. 코어 수로 나눠야 비로소 기준선이 생깁니다.

서버 안정성 점검 보고서를 쓰려면 가동 시간과 부하를 기록해야 합니다. 그런데 로드 3.85라는 값이 높은 것인지 낮은 것인지 판단할 기준이 없습니다.

```bash
 10:37:22 up 2 days, 5:37, 3 users, load average: 3.85, 2.10, 0.45
```

```bash
4
```

기준선은 코어 수입니다. 로드 평균이 코어 수와 같으면 모든 코어가 정확히 차 있고 대기 큐가 비어 있는 상태이며, 그보다 크면 기다리는 프로세스가 생겼다는 뜻입니다.

이 서버는 4코어이고 15분 로드가 0.45이므로 장기적으로는 한가합니다. 다만 1분 3.85, 5분 2.10, 15분 0.45로 최근으로 올수록 커지고 있어 부하가 방금 붙기 시작한 상태입니다. 지금 조치할 대상은 아니지만 몇 분 뒤 다시 봐야 할 서버입니다.

### 조치

```bash
# 가동 시간과 15분 로드를 기록으로 남긴다
uptime | awk -F'load average: ' '{print $2}' | awk -F', ' '{print $3}'

# 코어 수와 나란히 놓고 판정한다
echo "cores=$(nproc) load15=$(cut -d, -f3 /proc/loadavg | tr -d ' ')"
```

```bash
# 4코어 기준 해석
# 4.0 미만   여유 있음
# 4.0 근처   모든 코어가 차 있는 한계점
# 4.0 초과   대기 큐 발생, 응답 지연이 나타남
```

로드가 높게 나왔을 때 CPU 탓으로 단정하지 않는 것이 중요합니다. `vmstat 1 5`의 `wa` 열이 크면 프로세스들이 디스크를 기다리는 중이므로, CPU를 늘려도 아무것도 나아지지 않습니다.

모니터링에서는 로드 자체보다 `load / nproc` 비율로 알림을 거는 편이 낫습니다. 코어 수가 다른 서버들을 같은 기준으로 볼 수 있기 때문입니다.



## 사례 2 — 배치 작업이 사용자 요청을 밀어냅니다

> 배치를 멈출 수 없다면 순서를 바꿉니다. `renice` 한 줄로 같은 CPU를 다른 순서로 쓰게 만들 수 있습니다.

피크 시간대에 사용자 대면 서비스의 응답이 느려졌습니다. 배치 작업이 CPU를 85% 넘게 쓰고 있지만 이 작업을 중단할 수는 없습니다.

```bash
top - 14:35:22 up 5 days, 3:20, 2 users, load average: 4.82, 4.15, 3.67

  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM   TIME+ COMMAND
 5432 devops    20   0 2048576 256840  12340 R  85.3  12.4   8:23 data-processor
 1234 www-data  20   0  892340 125600  45670 S  12.1   6.1  45:12 nginx
 2345 postgres  20   0 1245680 345200  67890 S   8.5  16.8  32:45 postgres
```

```bash
  PID USER      NI COMMAND
 5432 devops     0 data-processor
```

`NI` 열을 보면 `data-processor`의 nice 값이 0입니다. nginx와 postgres도 같은 0이라, 스케줄러 입장에서는 셋이 동등한 권리를 가진 프로세스입니다. 그래서 배치가 CPU를 잡으면 웹 요청이 그 뒤에 줄을 섭니다.

문제의 성격이 여기서 갈립니다. CPU가 모자란 것이 아니라 배분 순서가 잘못된 것입니다. 코어를 늘려도 우선순위가 같으면 배치가 또 앞자리를 차지합니다.

nice 값은 -20부터 19까지이고 클수록 양보합니다. 값을 올려 두면 CPU가 한가할 때는 배치가 그대로 다 쓰고, 요청이 몰릴 때만 뒤로 물러납니다.

### 조치

```bash
# 현재 우선순위 확인
ps -o pid,user,ni,comm -p 5432

# 배치의 우선순위를 낮춘다
renice 10 -p 5432

# 반영 확인
ps -o pid,user,ni,comm -p 5432
```

```bash
# 처음부터 낮게 띄우는 편이 낫다
nice -n 10 /usr/local/bin/batch-job.sh
```

예약 작업에 등록할 때부터 `nice`를 붙여 두면 이 상황 자체가 생기지 않습니다. `renice`는 이미 벌어진 뒤의 응급 조치입니다.

더 강한 보장이 필요하면 cgroup으로 CPU 사용률 상한을 직접 걸 수 있습니다. nice는 경합할 때의 순서를 정할 뿐이고 상한을 정하지는 않기 때문입니다.



## 사례 3 — 워커 하나만 CPU를 다 씁니다

> 같은 이름의 프로세스가 여럿일 때는 개별 PID의 편차를 봅니다. 하나만 튀면 그 워커가 처리 중인 요청이 원인입니다.

웹 서버가 느려지고 사용자에게 타임아웃이 발생합니다. nginx 워커가 여럿 떠 있는데 그중 하나가 이상한 것으로 의심됩니다.

```bash
USER       PID   %CPU  %MEM    VSZ    RSS TTY  STAT START   TIME COMMAND
nginx     12345  92.3   4.1 245678  42340 ?    R    08:15  45:12 nginx: worker process
python3   22310  45.7   6.2 567890 123450 ?    S    07:00  32:45 python3 app.py
nginx     12346  15.4   2.8 245678  28560 ?    S    08:15   8:23 nginx: worker process
nginx     12347   1.2   1.0 245678  10240 ?    S    08:15   0:45 nginx: worker process
nginx     12340   0.0   0.5 245678   5120 ?    Ss   08:15   0:02 nginx: master process
```

```nginx
worker_processes auto;
worker_connections 1024;
```

세 워커의 CPU가 92.3%, 15.4%, 1.2%로 크게 벌어져 있습니다. 워커는 같은 설정으로 같은 시각에 뜬 형제들이라 부하가 비슷해야 정상인데, 하나만 60배 넘게 쓰고 있습니다.

편차 자체가 단서입니다. 설정이 문제라면 세 워커가 고르게 높아야 합니다. 하나만 튄다는 것은 그 워커가 잡고 있는 특정 연결이나 요청이 원인이라는 뜻이고, 무한 루프나 거대한 파일 처리가 흔한 정체입니다.

nginx의 구조 덕분에 조치는 간단합니다. master가 워커를 관리하므로 문제 워커를 종료하면 새 워커가 곧바로 올라옵니다.

### 조치

```bash
# 같은 사용자의 프로세스를 CPU 역순으로 본다
ps -u nginx -o pid,%cpu,%mem,comm --sort=-%cpu | head -5

# 그 워커가 무엇을 붙들고 있는지 살핀다
ls -l /proc/12345/fd | wc -l
cat /proc/12345/status

# graceful 하게 워커만 종료, master 가 새로 띄운다
kill -QUIT 12345

# 서비스 정상 확인
systemctl status nginx
curl -I http://localhost
```

`SIGQUIT`을 쓰는 이유는 nginx 워커가 이 시그널을 처리 중인 연결을 마무리한 뒤 종료하라는 뜻으로 받기 때문입니다. `SIGKILL`을 쓰면 그 워커가 붙들고 있던 연결이 즉시 끊깁니다.

같은 워커가 반복해서 튄다면 종료로 끝내지 말고 `strace -p <PID>`로 어떤 시스템 콜에 머무는지 확인하는 편이 낫습니다. 재시작은 증상만 지우기 때문입니다.



## 사례 4 — 메모리가 조금씩 줄다가 서비스가 죽습니다

> 누수는 한 시점의 값이 아니라 시간에 따른 기울기로 판정합니다. `dmesg`의 OOM 기록이 그 기울기의 결말입니다.

Node.js 서비스가 몇 시간마다 느려지다 결국 종료됩니다. CPU와 디스크는 정상인데 가용 메모리만 점점 줄어들어 원인을 못 찾고 있습니다.

```bash
              total        used        free      shared  buff/cache   available
Mem:           7.8G        7.1G        120M        45M        580M        350M
Swap:          2.0G        1.8G        200M
```

```bash
USER       PID  %CPU  %MEM    VSZ     RSS  TTY  STAT START   TIME COMMAND
node      3421   2.1  78.5 1845320 6289560  ?    Sl   Mar01  12:34 node /app/server.js
postgres  2100   1.5   8.2  645320  656280  ?    Ss   Mar01   8:45 postgres: main
redis     2200   0.8   3.1  125680  248540  ?    Ssl  Mar01   4:12 redis-server
```

```bash
[285432.123456] Out of memory: Killed process 2987 (node) total-vm:1823456kB, anon-rss:6145280kB
[285432.123457] oom_kill_process: 1 callbacks suppressed
```

`free -h`에서 봐야 할 열은 `free`가 아니라 `available`입니다. `free`가 120MB로 작아 보여도 `buff/cache`는 필요하면 회수되므로, 실제로 쓸 수 있는 양은 350MB라는 `available` 값입니다. 그 값도 이미 위험합니다.

`node` 프로세스의 RSS가 6.2GB로 물리 메모리의 78.5%입니다. 결정적인 근거는 `dmesg`입니다. 같은 이름의 프로세스가 과거에도 OOM Killer에게 종료된 기록이 있어, 이번이 처음이 아니라 반복되는 패턴임을 알 수 있습니다.

한 번의 큰 할당과 누수는 이 기록에서 갈립니다. 재시작 뒤 RSS가 다시 서서히 오른다면 누수이고, 특정 요청에서만 튄다면 그 요청의 처리 방식 문제입니다.

### 조치

```bash
# 메모리 사용 상위 프로세스
ps -o pid,user,rss,vsz,comm --sort=-rss | head -5

# 즉시 조치 — 서비스 재시작으로 메모리 회수
systemctl restart node-app
free -h

# OOM 이력 확인
dmesg | grep -i "out of memory"
```

```bash
# 재발 방지 — 힙 상한을 애플리케이션과 cgroup 양쪽에 건다
# ExecStart=/usr/bin/node --max-old-space-size=2048 /app/server.js
# MemoryMax=3G
```

`--max-old-space-size`는 런타임이 스스로 GC를 돌리도록 압박하는 상한이고, systemd의 `MemoryMax`는 커널이 강제하는 상한입니다. 둘을 함께 걸면 애플리케이션이 먼저 정리를 시도하고 그래도 넘치면 그 서비스만 제한됩니다.

상한이 없으면 누수가 있는 프로세스 하나가 서버 전체를 끌어내립니다. OOM Killer는 점수 계산으로 대상을 고르므로, 반드시 누수 프로세스가 죽는다는 보장도 없습니다.



## 네 사례를 관통하는 것

> 자원 문제는 총량과 배분 두 축으로 갈립니다. 총량이 문제면 늘리거나 줄이고, 배분이 문제면 우선순위와 상한으로 순서를 다시 정합니다.

사례 2와 사례 4가 대비를 잘 보여 줍니다. 배치가 서비스를 밀어낸 것은 CPU 총량이 아니라 배분의 문제였습니다. Node.js가 죽은 것은 메모리 총량의 문제였습니다. 전자는 `renice`로 순서를 바꿔 해결되고 후자는 상한을 걸어 피해 범위를 가둡니다.

판정 순서도 반복됩니다. 먼저 숫자를 기준선과 나란히 놓습니다. 그다음 같은 종류의 프로세스끼리 편차를 보고 마지막에 시간에 따른 추세를 봅니다. 사례 1이 기준선, 사례 3이 편차, 사례 4가 추세를 각각 맡습니다.

마지막으로 네 사례 모두 응급 조치와 재발 방지가 서로 다른 층에 있습니다. `renice`·`kill`·`restart`는 지금을 넘기는 명령이고, `nice` 기본값·`limits.conf`·`MemoryMax`는 다음에 같은 일이 생기지 않게 하는 설정입니다.
