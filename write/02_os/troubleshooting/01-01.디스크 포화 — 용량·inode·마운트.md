# 디스크 포화 — 용량·inode·마운트

---

> `No space left on device`는 한 문장이지만 뒤에 선 원인은 셋으로 갈립니다. 블록이 찼는지, inode가 먼저 떨어졌는지, 애초에 쓸 파티션이 붙지 않았는지를 가르는 것이 진단의 시작입니다.

디스크 문제는 대개 같은 얼굴로 찾아옵니다. 새 로그가 쌓이지 않거나 배포 스크립트가 실패하고, 심하면 `touch` 한 번도 거부됩니다. 증상만 보면 하나인데 손을 대야 할 곳은 전혀 다릅니다.

세 사례를 한 문서에 묶은 이유가 여기 있습니다. 증상이 겹치는 만큼 첫 명령을 잘못 고르면 엉뚱한 곳을 파게 되고, `df -h`만 보고 "여유 있는데 왜 안 되지"에서 멈추는 일이 실제로 자주 생깁니다.



## 신호는 하나, 갈래는 셋

> 같은 에러를 받고도 봐야 할 명령이 다릅니다. `df -h`·`df -i`·`lsblk` 세 개를 순서대로 치는 것이 갈래를 가르는 가장 싼 방법입니다.

파일을 못 만든다는 커널의 응답은 하나뿐입니다. 커널은 "블록이 없다"와 "inode가 없다"를 같은 `ENOSPC`로 돌려주고, 마운트가 없는 경로에 쓰는 것도 결국 다른 파일시스템의 용량을 먹습니다. 에러 메시지가 원인을 구분해 주지 않으니 사람이 세 축을 직접 확인해야 합니다.

확인 순서는 비용이 싼 것부터 잡습니다. 세 명령 모두 읽기 전용이고 1초 안에 끝나므로, 가설을 세우기 전에 셋 다 찍어 두는 편이 빠릅니다.

| 확인할 축 | 명령 | 이 값이 이상하면 |
|-----------|------|------------------|
| 블록 사용률 | `df -h` | 파일이 실제로 용량을 먹었습니다 (사례 1) |
| inode 사용률 | `df -i` | 작은 파일이 개수로 고갈시켰습니다 (사례 2) |
| 블록 장치와 마운트 상태 | `lsblk`, `blkid` | 쓸 수 있는 디스크가 아직 붙지 않았습니다 (사례 3) |



## 사례 1 — 로그 하나가 루트 파티션을 다 먹었습니다

> 루트가 100%인데 `/data`는 23%입니다. 파티션 단위로 갈라 보면 범인은 대개 한 파일입니다.

운영 중인 웹 서버에서 새 로그 파일이 생성되지 않고 배포 스크립트도 실패하기 시작했습니다. 서버에 붙어 확인한 상태는 이렇습니다.

```bash
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   50G     0 100% /
tmpfs           3.9G     0  3.9G   0% /dev/shm
/dev/sda2       200G   45G  155G  23% /data
```

```bash
4.0K    /var/account
45G     /var/log
12K     /var/mail
1.2G    /var/cache
320M    /var/lib
```

```bash
-rw-r--r-- 1 root root  12K Feb 10 09:00 syslog
-rw-r--r-- 1 root root  42G Feb 10 09:01 app-debug.log
-rw-r--r-- 1 root root 2.8G Feb 10 08:55 app-error.log
-rw-r--r-- 1 root root  56K Feb 10 09:00 kern.log
```

찬 것은 루트 파티션 하나이고 `/data`는 멀쩡합니다. `du`로 한 단계씩 좁히면 `/var/log`가 45GB를 쥐고 있고, 그중 `app-debug.log` 한 파일이 42GB입니다. 프로덕션에서 디버그 로그 레벨이 켜진 채 방치되어 로그가 무한히 쌓인 결과입니다.

여기서 `rm`을 쓰면 용량이 바로 안 돌아옵니다. 애플리케이션이 그 파일을 열어 둔 상태라 디렉터리 엔트리만 사라지고 블록은 프로세스가 파일 핸들을 놓을 때까지 잡혀 있습니다. `truncate`는 같은 inode의 크기를 0으로 만들어 그 자리에서 공간을 돌려줍니다.

### 조치

```bash
# 어느 파일이 큰지 크기 역순으로 확인
ls -lhS /var/log | head -5

# 프로세스가 열어 둔 파일이므로 rm 대신 내용만 비운다
truncate -s 0 /var/log/app-debug.log

# 회수된 용량 확인
df -h /

# 재발 방지 — 로그 로테이션 등록
cat > /etc/logrotate.d/app << 'EOF'
/var/log/app-*.log {
    daily
    rotate 7
    compress
    missingok
    notifempty
    copytruncate
}
EOF
```

애플리케이션 설정의 로그 레벨을 `info` 이상으로 되돌리는 것이 진짜 수정입니다. `truncate`는 지금 당장 서비스를 살리는 응급 조치일 뿐이고, 레벨을 그대로 두면 며칠 뒤 같은 자리에서 다시 터집니다.



## 사례 2 — 여유 공간이 있는데 파일이 안 만들어집니다

> `df -h`가 64%인데 `touch`가 거부됩니다. 이때 봐야 할 것은 용량이 아니라 개수입니다.

`touch /tmp/test.txt`가 `No space left on device`로 실패하는데, 용량을 보면 18GB가 남아 있습니다.

```bash
Filesystem      Size  Used Avail Use% Mounted on
/dev/sda1        50G   32G   18G  64% /
/dev/sdb1        10G  2.0G  8.0G  20% /data
```

```bash
Filesystem       Inodes   IUsed   IFree IUse% Mounted on
/dev/sda1       6553600 6553600       0  100% /
/dev/sdb1       3276800  125000 3151800    4% /data
```

`df -h`는 블록 사용량을, `df -i`는 inode 사용량을 보여줍니다. 루트의 블록은 64%로 여유가 있지만 inode는 655만 개를 전부 써서 100%입니다.

inode는 파일마다 하나씩 붙는 메타데이터 구조체입니다. ext4는 이 개수를 포맷 시점에 고정하므로, 파일 하나하나가 아무리 작아도 개수가 상한에 닿으면 새 파일을 만들 수 없습니다. 메일 큐, 세션 파일, 캐시 조각처럼 작은 파일을 대량으로 만드는 쪽이 늘 용의자입니다.

### 조치

```bash
# 디렉터리별 파일 개수로 소비처를 좁힌다
for dir in /var/spool /tmp /var/lib /var/cache; do
  echo "$(find $dir -type f 2>/dev/null | wc -l) $dir"
done | sort -rn | head -5

# 확인된 디렉터리의 누적 파일 정리 (예: 메일 큐)
rm -rf /var/spool/postfix/maildrop/*

# inode 회수 확인
df -i /
```

`df -h`만 보는 습관이 이 장애를 늦게 발견하게 만듭니다. 모니터링에 inode 사용률 알림을 블록 사용률과 나란히 두고, 세션·큐 디렉터리는 정기 정리 작업을 걸어 두는 편이 안전합니다.



## 사례 3 — 디스크는 꽂혔는데 쓸 수가 없습니다

> `lsblk`에 보이는 파티션이 곧 쓸 수 있는 파티션은 아닙니다. `blkid`의 `TYPE`이 비어 있으면 포맷부터 해야 합니다.

데이터 디스크가 부족해 물리 디스크를 추가했는데, 서버에서는 아직 쓸 수 없는 상태입니다.

```bash
NAME    MAJ:MIN RM  SIZE RO TYPE MOUNTPOINT
sda       8:0    0   50G  0 disk
├─sda1    8:1    0   49G  0 part /
└─sda2    8:2    0    1G  0 part [SWAP]
sdb       8:16   0   20G  0 disk
└─sdb1    8:17   0   20G  0 part
```

```bash
/dev/sda1: UUID="a1b2c3d4" TYPE="ext4" PARTUUID="abc-001"
/dev/sda2: UUID="e5f6a7b8" TYPE="swap" PARTUUID="abc-002"
/dev/sdb1: PARTUUID="def-001"
```

`/dev/sdb1`은 20GB 파티션으로 잡혀 있지만 마운트 포인트가 비어 있습니다. 결정적인 단서는 `blkid` 쪽입니다. `sda1`과 `sda2`에는 `TYPE`과 `UUID`가 붙어 있는데 `sdb1`에는 `PARTUUID`만 있습니다.

`TYPE`이 없다는 것은 파티션 위에 파일시스템이 아직 만들어지지 않았다는 뜻입니다. 커널은 마운트할 때 슈퍼블록을 읽어 파일시스템 종류를 판별하므로, 포맷하지 않은 파티션은 마운트 자체가 실패합니다. 순서는 포맷이 먼저이고 마운트가 나중입니다.

### 조치

```bash
# ext4 파일시스템 생성, 레이블로 용도를 남긴다
mkfs.ext4 -L data_extra /dev/sdb1

# 마운트 지점 준비와 마운트
mkdir -p /mnt/data
mount /dev/sdb1 /mnt/data

# 붙었는지 확인
df -h /mnt/data

# 재부팅 후에도 붙도록 fstab 등록 — 장치 경로가 아니라 UUID로 적는다
echo "UUID=$(blkid -s UUID -o value /dev/sdb1) /mnt/data ext4 defaults,nofail 0 2" >> /etc/fstab

# fstab 문법 검증
mount -a
```

`fstab`에 `/dev/sdb1` 같은 장치 경로를 적으면 디스크를 추가하거나 뺄 때 이름이 밀려 엉뚱한 장치가 마운트됩니다. UUID는 파일시스템에 새겨지므로 순서가 바뀌어도 그대로입니다. `nofail`을 함께 붙이면 그 디스크가 없을 때 부팅이 멈추는 사고를 막아 줍니다.



## 세 사례를 관통하는 것

> 세 사례 모두 "어느 자원이 상한에 닿았는가"를 묻습니다. 자원의 이름이 블록·inode·마운트로 다를 뿐입니다.

디스크는 하나의 숫자가 아니라 여러 개의 상한을 동시에 가진 자원입니다. 용량이 하나이고 inode가 다른 하나이며, 그 둘을 담을 파일시스템이 붙어 있는지가 또 다른 하나입니다. `df -h` 하나만 외우고 있으면 셋 중 하나만 볼 수 있습니다.

조치 쪽에도 공통 교훈이 있습니다. 세 사례의 응급 조치는 모두 몇 초 만에 끝나지만, 그중 어느 것도 재발을 막지 않습니다. 로그 레벨, 정기 정리, `fstab` 등록이 각각의 진짜 수정이고 그것을 함께 하지 않으면 같은 사례가 다음 주에 그대로 돌아옵니다.
