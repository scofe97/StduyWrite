# 패킷 캡처와 손실 진단

---

> "네트워크 문제입니다"라는 말은 대개 검증되지 않은 가정입니다. 패킷을 직접 보거나 구간을 나눠 재면 그 가정이 참인지 몇 분 안에 갈립니다.

두 사례 모두 네트워크가 의심받는 상황에서 시작합니다. 그런데 결론은 한쪽이 애플리케이션 문제, 다른 한쪽이 진짜 네트워크 문제로 갈립니다.

이 갈림을 만드는 것은 도구가 아니라 측정 설계입니다. 어디까지 왔는지를 보거나 어느 구간에서 잃는지를 재면, 책임 소재가 추측이 아니라 관측으로 정해집니다.



## 어디까지 왔는지를 먼저 정합니다

> 네트워크 문제와 애플리케이션 문제를 가르는 기준은 하나입니다. 요청이 서버 프로세스까지 닿았는가.

장애 대응에서 가장 소모적인 순간은 팀 사이에 책임이 오갈 때입니다. 클라이언트는 보냈다고 하고 서버는 못 받았다고 하는데, 양쪽 다 자기 로그만 보고 있으면 대화가 진전되지 않습니다.

이 교착을 푸는 방법은 중간을 직접 보는 것입니다. `tcpdump`는 커널이 인터페이스에서 주고받은 패킷을 그대로 보여 주므로, 애플리케이션 로그가 비어 있어도 요청이 도착했는지를 판정할 수 있습니다.

손실이 의심될 때는 접근이 다릅니다. 한 지점을 보는 대신 구간을 나눠 각각 재고, 어느 구간부터 나빠지는지로 범위를 좁힙니다.

| 묻는 것 | 방법 | 판정 근거 |
|---------|------|-----------|
| 요청이 서버까지 왔나 | `tcpdump`로 캡처 | handshake 와 요청 payload 가 보이는가 |
| 응답을 보냈나 | 같은 캡처에서 응답 패킷 확인 | `HTTP/1.1` 로 시작하는 패킷이 있는가 |
| 어느 구간에서 잃나 | 구간별 `ping`, `mtr` | 손실률이 어느 목적지부터 올라가는가 |



## 사례 1 — 클라이언트는 보냈다는데 서버 로그가 비어 있습니다

> 캡처에 요청 payload 가 보이면 네트워크는 혐의를 벗습니다. 그다음 볼 곳은 응답 패킷의 부재입니다.

웹 서비스에 요청이 도달하지 않는 것으로 의심됩니다. 서비스 로그에는 기록이 없는데 클라이언트는 보냈다고 합니다.

```bash
(요청 기록 없음)
```

```bash
LISTEN  0  511  0.0.0.0:80  0.0.0.0:*  users:(("nginx",pid=1234,fd=6))
```

```bash
12:14:03.100001 IP 192.168.1.23.49832 > 192.168.1.50.80: Flags [S], seq 34823901, win 64240, length 0
12:14:03.100025 IP 192.168.1.50.80 > 192.168.1.23.49832: Flags [S.], seq 91234001, ack 34823902, win 65160, length 0
12:14:03.100104 IP 192.168.1.23.49832 > 192.168.1.50.80: Flags [.], ack 1, win 64240, length 0
12:14:03.100310 IP 192.168.1.23.49832 > 192.168.1.50.80: Flags [P.], seq 1:83, ack 1, win 64240, length 82: HTTP: GET / HTTP/1.1
12:14:03.100322 IP 192.168.1.50.80 > 192.168.1.23.49832: Flags [.], ack 83, win 65024, length 0
12:14:08.101991 IP 192.168.1.23.49832 > 192.168.1.50.80: Flags [F.], seq 83, ack 1, win 64240, length 0
```

```bash
2026/03/17 12:14:08 [error] 1234#1234: *104 upstream timed out (110: Connection timed out) while reading response header from upstream, client: 192.168.1.23, server: _, request: "GET / HTTP/1.1", upstream: "http://127.0.0.1:8080/"
```

캡처를 위에서부터 읽으면 이야기가 그대로 보입니다. `[S]`, `[S.]`, `[.]` 세 줄이 3-way handshake이므로 TCP 연결은 정상적으로 맺어졌습니다. 네 번째 줄의 `[P.]`에 `GET / HTTP/1.1`이 실려 있어 요청 본문까지 서버에 도착했습니다.

다섯 번째 줄이 결정적입니다. 서버가 `ack 83`으로 요청을 잘 받았다고 응답했습니다. 여기까지 왔다면 네트워크 경로에는 문제가 없습니다.

그런데 그 뒤로 응답 패킷이 없습니다. 5초 뒤 클라이언트가 `[F.]`로 연결을 닫을 때까지 서버는 아무것도 보내지 않았습니다. nginx 에러 로그가 그 침묵의 이유를 설명합니다. 8080번의 업스트림이 응답하지 않아 nginx도 클라이언트에게 줄 것이 없었던 것입니다.

즉 "요청이 도달하지 않았다"는 처음의 가설은 틀렸습니다. 요청은 도달했고 응답이 못 만들어졌습니다. 조사 방향이 네트워크에서 업스트림 애플리케이션으로 완전히 바뀝니다.

### 조치

```bash
# 재현하면서 캡처한다. 파일로 남겨야 다시 볼 수 있다
tcpdump -i eth0 -nn host 192.168.1.23 and port 80 -c 20 -w /tmp/http_traffic.pcap

# 다른 터미널에서 요청을 보낸다
curl -v http://192.168.1.50/

# handshake 와 요청 도달 여부 확인
tcpdump -r /tmp/http_traffic.pcap -nn -A

# 응답 패킷이 있는지만 따로 확인
tcpdump -r /tmp/http_traffic.pcap -nn -A | grep 'HTTP/1\.'

# 업스트림을 직접 두드려 본다
ss -tlnp | grep :8080
curl -v http://127.0.0.1:8080/
```

```bash
# 자주 쓰는 옵션
# -i eth0        캡처할 인터페이스
# -nn            주소와 포트를 이름으로 바꾸지 않는다
# -A             payload 를 ASCII 로 보여 준다
# -c 20          20개만 잡고 종료
# -w / -r        파일로 저장 / 파일에서 읽기
```

`-nn`을 붙이는 이유는 출력이 깔끔해지기 때문만이 아닙니다. 이름 역조회를 하지 않으므로 DNS가 느린 환경에서 캡처가 멈추지 않고, 조사 중에 불필요한 질의를 만들지도 않습니다.

프로덕션에서 캡처할 때는 범위를 좁히는 것이 중요합니다. `host`와 `port` 필터로 대상 트래픽만 잡고 `-c`로 개수를 제한하면 디스크와 부하가 함께 줄어듭니다. payload에는 인증 헤더 같은 민감 정보가 그대로 들어 있으므로 보관 기간도 짧게 잡습니다.



## 사례 2 — 간헐적으로 타임아웃이 납니다

> 손실은 목적지 하나로 재면 알 수 없습니다. 가까운 곳부터 먼 곳까지 나눠 재야 어느 구간이 나쁜지 드러납니다.

사용자들이 간헐적인 타임아웃을 보고합니다. 손실이 로컬에서 나는지 상위 구간에서 나는지 판단할 근거가 없습니다.

```bash
default via 192.168.1.1 dev eth0
```

```bash
5 packets transmitted, 5 received, 0% packet loss, time 4006ms
rtt min/avg/max/mdev = 1.150/1.224/1.310/0.057 ms
```

```bash
5 packets transmitted, 5 received, 0% packet loss, time 4005ms
rtt min/avg/max/mdev = 14.900/15.500/16.200/0.466 ms
```

```bash
5 packets transmitted, 3 received, 40% packet loss, time 4008ms
rtt min/avg/max/mdev = 82.300/88.700/95.100/5.232 ms
```

세 측정을 나란히 놓으면 구간이 갈립니다. 게이트웨이까지는 손실 0%에 1.2ms, 공인 DNS까지도 손실 0%에 15.5ms, 그런데 외부 목적지에서 40%가 사라집니다.

이 배치가 진단의 핵심입니다. 가까운 구간이 깨끗하다는 사실이 로컬 네트워크와 상위 회선을 후보에서 제거해 주고, 남은 구간으로 범위가 좁혀집니다. 목적지 하나만 찍어 봤다면 "네트워크가 나쁘다"까지밖에 말할 수 없습니다.

다만 `ping` 결과를 그대로 결론으로 삼는 데는 주의가 필요합니다. 중간 라우터가 ICMP를 낮은 우선순위로 처리하거나 제한하는 경우가 흔해서, 실제 TCP 트래픽은 멀쩡한데 `ping`만 나쁘게 나올 수 있습니다.

### 조치

```bash
# 기준점이 될 게이트웨이를 확인
ip route | grep default

# 구간을 나눠 재고 결과를 남긴다
{
  echo "=== gateway ==="
  ping -c 5 192.168.1.1 | tail -2
  echo "=== upstream dns ==="
  ping -c 5 8.8.8.8 | tail -2
  echo "=== internet ==="
  ping -c 5 google.com | tail -2
} > network_diagnostics.txt

# 홉별 손실률을 본다
mtr -rw -c 20 google.com
```

`mtr`은 `ping`과 `traceroute`를 합친 도구라 홉마다 손실률과 지연을 함께 보여 줍니다. 어느 라우터부터 나빠지는지가 한 화면에 나오므로 구간별 `ping`보다 해상도가 높습니다.

읽을 때 흔한 함정이 하나 있습니다. 중간 홉에서만 손실이 나고 마지막 홉이 깨끗하면 그 중간 라우터의 ICMP 제한일 가능성이 큽니다. 진짜 손실이라면 그 지점 이후의 모든 홉에서 손실이 이어집니다.

외부 구간 문제로 판정되면 자기 서버에서 할 수 있는 조치는 없습니다. 대신 `mtr` 결과를 근거로 회선 사업자에게 알리는 것이 다음 단계이고, 그때 구간별 측정 기록이 그대로 근거 자료가 됩니다.



## 두 사례를 관통하는 것

> 두 사례 모두 "네트워크 문제"라는 신고에서 시작해 서로 다른 결론에 닿습니다. 결론을 가른 것은 측정을 어디서 끊었느냐입니다.

사례 1은 한 지점을 깊게 봤고 사례 2는 여러 지점을 얕게 봤습니다. 전자는 패킷 내용까지 들여다봐야 애플리케이션과 네트워크를 가를 수 있었고, 후자는 구간을 나눠야 범위를 좁힐 수 있었습니다. 어느 방식이 맞는지는 증상이 한 요청에서 재현되는지 간헐적인지로 정합니다.

두 사례가 함께 알려 주는 것은 도구의 한계입니다. `tcpdump`는 그 인터페이스를 지난 것만 보여 주고 `ping`은 ICMP만 잽니다. 도구가 안 보여 준 것을 "없다"로 읽으면 틀린 결론에 닿습니다.

마지막으로 두 사례 다 결과를 파일로 남깁니다. `pcap` 파일과 구간별 측정 기록은 다른 팀이나 회선 사업자와 이야기할 때 그대로 근거가 되고, 그 근거가 있으면 책임을 두고 오가는 대화가 짧아집니다.
