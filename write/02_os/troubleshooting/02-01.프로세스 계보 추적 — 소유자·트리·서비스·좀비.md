# 프로세스 계보 추적 — 소유자·트리·서비스·좀비

---

> 프로세스가 많다는 사실만으로는 아무것도 못 고칩니다. `ps`의 집계 축을 사용자·부모·상태·서비스로 바꿔 가며 범위를 좁히는 것이 추적의 전부입니다.

`top`을 열면 수백 줄이 흐릅니다. 그 안에서 손봐야 할 것을 고르는 일은 눈으로 하는 게 아니라 집계 축을 바꿔 가며 하는 일입니다.

이 문서의 다섯 사례는 축이 다섯 번 바뀝니다. 사용자로 묶었다가 부모로 묶고 상태로 거른 다음, 서비스 유닛으로 되짚어 마지막에는 실행 파일 경로까지 내려갑니다. 축을 바꿀 때마다 후보가 수백에서 하나로 줄어드는 과정을 따라가는 것이 이 문서의 목적입니다.



## 축을 바꿔 가며 좁힙니다

> `ps`는 한 줄에 한 프로세스를 보여 주는 도구가 아니라, 원하는 필드로 묶어 세는 도구입니다. 어느 필드로 묶느냐가 곧 어떤 가설을 검증하느냐입니다.

프로세스가 많은 서버에서 `ps aux`를 그냥 치면 답이 안 나옵니다. 500줄을 눈으로 읽어도 "많다"는 인상만 남고, 어느 한 줄이 원인인지는 드러나지 않습니다.

풀어야 할 문제는 목록을 보는 것이 아니라 후보를 좁히는 것입니다. `ps -eo <필드>`로 원하는 축만 뽑고 `sort | uniq -c`로 세면, 한쪽으로 쏠린 값이 곧 가설이 됩니다.

각 축이 답하는 질문은 다릅니다. 아래 표는 이 문서 다섯 사례가 각각 어느 축에서 답을 찾았는지를 정리한 것입니다.

| 집계 축 | 답하는 질문 | 명령 | 사례 |
|---------|-------------|------|------|
| 사용자 | 누가 자원을 독점하나 | `ps -eo user --no-headers \| sort \| uniq -c \| sort -rn` | 사례 1 |
| 부모 PID | 어느 프로세스가 계속 낳고 있나 | `ps -eo ppid --no-headers \| sort \| uniq -c \| sort -rn` | 사례 2 |
| 상태 | 죽었는데 안 사라진 것이 있나 | `ps -eo stat \| grep Z` | 사례 3 |
| 서비스 유닛 | 이 PID는 누가 띄웠나 | `systemctl status <PID>` | 사례 4 |
| 실행 경로와 시작 시각 | 어디서 언제 올라온 바이너리인가 | `ps -eo pid,user,lstart,comm --sort=-start_time` | 사례 5 |



## 사례 1 — 한 사용자가 프로세스 156개를 쥐고 있습니다

> 공유 서버의 자원 문제는 대개 한 계정으로 수렴합니다. 사용자 축으로 세는 명령 한 줄이면 드러납니다.

여러 팀이 함께 쓰는 서버에서 자원 사용률이 전반적으로 올라갔습니다. 특정 사용자가 지나치게 많은 프로세스를 띄운 것으로 의심되지만 근거가 없습니다.

```bash
USER       PID  %CPU  %MEM    VSZ    RSS TTY  STAT START   TIME COMMAND
root         1   0.0   0.1  16924   3240 ?    Ss   Mar01   0:05 /sbin/init
qa-team   3001   5.2   2.1  45678  12340 ?    S    09:00   1:23 pytest runner
qa-team   3002   4.8   2.0  45678  11890 ?    S    09:00   1:20 pytest runner
dev-team  4001   2.1   1.5  34567   8900 ?    S    08:30   0:45 node dev-server
ops-team  5001   0.5   0.8  23456   5600 ?    S    07:00   0:12 ansible-playbook
```

```bash
    156 qa-team
     23 root
     12 dev-team
      8 ops-team
      4 www-data
```

`ps aux` 원본만 보면 어느 팀이 많은지 감이 안 옵니다. 사용자 필드만 뽑아 세는 순간 `qa-team`이 156개로 나머지 전부를 합친 것보다 많다는 사실이 한 줄로 드러납니다.

병렬 테스트 러너가 동시 실행 수 제한 없이 프로세스를 늘린 결과입니다. 프로세스 하나하나는 무겁지 않아도 156개가 모이면 CPU와 프로세스 테이블을 함께 잠식해, 같은 서버를 쓰는 다른 팀의 작업까지 느려집니다.

### 조치

```bash
# 사용자 축으로 집계해 쏠린 계정을 찾는다
ps -eo user --no-headers | sort | uniq -c | sort -rn

# 그 계정 안에서 무엇이 많은지 본다
ps -u qa-team -o pid,%cpu,%mem,comm --sort=-%cpu

# 해당 패턴의 프로세스만 골라 종료
pkill -u qa-team -f "pytest runner"

# 재발 방지 — 계정별 프로세스 수 상한
echo "qa-team hard nproc 50" >> /etc/security/limits.conf
```

`limits.conf`의 `nproc`은 커널이 강제하는 상한이라 스크립트가 실수로 폭주해도 그 선에서 막힙니다. 더 세밀한 제어가 필요하면 cgroup v2로 계정이나 그룹 단위의 CPU와 메모리까지 함께 묶는 방법이 있습니다.



## 사례 2 — 부모 하나가 자식 187개를 낳고 있습니다

> 프로세스 수가 이상하면 부모 PID로 묶어 봅니다. 한 PID에 몰려 있으면 원인은 그 프로세스 하나입니다.

시스템 자원이 비정상적으로 큰 프로세스 트리에 잡아먹히고 있습니다. 어느 부모가 문제인지부터 특정해야 합니다.

```bash
312
```

```bash
    187 159
     23 1
     12 120
      8 2
      5 345
```

```bash
spawn_workers.sh(159)─┬─sleep(209)
                      ├─spawn_workers.sh(190)───sleep(220)
                      ├─spawn_workers.sh(191)───sleep(221)
                      ├─spawn_workers.sh(192)───sleep(222)
                      ├─spawn_workers.sh(193)───sleep(223)
```

전체 프로세스가 312개인데 그중 187개의 부모가 PID 159 하나입니다. 전체의 60%가 한 뿌리에서 나왔다는 뜻이라, 그 뿌리만 처리하면 문제의 대부분이 정리됩니다.

`pstree`로 내려가 보면 `spawn_workers.sh`가 자기 자신을 다시 fork 하면서 각 자식이 `sleep`을 하나씩 붙들고 있습니다. 워커 스크립트에 동시 실행 수 상한이 없어서 생긴 구조입니다.

여기서 자식을 하나씩 죽이는 것은 소용이 없습니다. 부모가 살아 있는 한 계속 새로 만들기 때문에, 프로세스 그룹 전체를 한 번에 정리해야 합니다.

### 조치

```bash
# 부모 PID로 묶어 세서 뿌리를 찾는다
ps -eo ppid --no-headers | sort | uniq -c | sort -rn | head -5

# 트리 구조를 인자까지 포함해 기록으로 남긴다
pstree -ap 159 > process_tree_report.txt

# 프로세스 그룹 전체를 한 번에 종료
kill -- -$(ps -o pgid= -p 159 | tr -d ' ')

# 정리 확인
pstree -p 159 2>/dev/null || echo "process tree cleared"
```

`kill -- -<PGID>` 형태에서 PID 앞의 빼기 부호가 "프로세스 그룹 전체"를 뜻합니다. 부모와 자식이 같은 그룹에 있으므로 이 한 줄로 트리가 통째로 정리되고, 자식이 새로 생길 틈도 남지 않습니다.

종료 전에 `pstree -ap`를 파일로 남기는 단계를 빼지 않는 편이 좋습니다. 죽이고 나면 무엇이 어떤 인자로 돌고 있었는지 확인할 방법이 사라집니다.



## 사례 3 — 죽은 프로세스가 사라지지 않습니다

> 좀비는 자원을 거의 안 쓰지만 프로세스 테이블 슬롯을 차지합니다. 좀비를 죽이는 게 아니라 부모를 손봐야 사라집니다.

배포한 것도 없는데 프로세스 수가 계속 늘고, 새 프로세스를 만들 수 없다는 에러가 간헐적으로 납니다.

```bash
top - 15:30:22 up 12 days, 7:45, 3 users, load average: 2.15, 1.98, 1.87
Tasks: 487 total, 2 running, 340 sleeping, 0 stopped, 145 zombie
```

```bash
devops    8234  0.0  0.0      0     0 ?  Z    14:20  0:00 [worker.sh] <defunct>
devops    8235  0.0  0.0      0     0 ?  Z    14:20  0:00 [worker.sh] <defunct>
devops    8236  0.0  0.0      0     0 ?  Z    14:21  0:00 [worker.sh] <defunct>
```

```bash
  PID  PPID STAT COMMAND
 8234  7100    Z worker.sh
```

```bash
  PID USER     COMMAND
 7100 devops   batch-manager
```

좀비가 145개이고 `RSS`와 `%CPU`가 전부 0입니다. 자원을 안 쓰는데도 문제가 되는 이유는 프로세스 테이블의 슬롯 때문입니다. 슬롯이 차면 새 프로세스를 만들 수 없고, 그것이 간헐적인 에러의 정체입니다.

좀비는 실행이 끝났지만 종료 상태를 아무도 수거하지 않은 프로세스입니다. 자식이 끝나면 커널은 종료 코드를 남겨 두고 부모가 `wait()`로 가져가기를 기다리는데, 부모가 그 호출을 하지 않으면 그 자리가 계속 남습니다.

그래서 좀비에게 `kill`을 보내도 아무 일이 일어나지 않습니다. 이미 죽은 프로세스라 받을 주체가 없습니다. `ps`로 PPID를 확인하면 145개 전부의 부모가 7100번 `batch-manager` 하나입니다.

### 조치

```bash
# 좀비 개수 확인
ps aux | awk '$8 ~ /Z/ {count++} END {print "zombies:", count+0}'

# 좀비의 부모를 확인한다
ps -o pid,ppid,stat,comm -p 8234

# 부모를 종료하면 좀비가 init 으로 넘어가 정리된다
kill 7100

# 정리 확인
ps aux | grep -c "[d]efunct"
```

부모를 종료하면 남은 좀비는 PID 1로 인계되고, init 계열 프로세스는 인계받은 자식을 즉시 수거하도록 만들어져 있어 그 시점에 사라집니다.

다만 이것도 응급 조치입니다. 진짜 수정은 `batch-manager` 쪽에서 자식 종료를 처리하는 것입니다. `SIGCHLD` 핸들러에서 `wait()`를 호출하거나 그 시그널을 무시하도록 설정하면 커널이 자식을 자동으로 수거합니다.



## 사례 4 — 이 PID가 어느 서비스인지 모릅니다

> `systemctl status <PID>`는 PID를 유닛으로 되짚어 줍니다. cgroup 계층이 그 연결을 이미 갖고 있기 때문입니다.

`top`에서 CPU를 95% 쓰는 PID 4567을 찾았는데, 이 프로세스가 어느 서비스 소속이고 누가 띄웠는지 알 수 없습니다.

```bash
  PID USER      PR  NI    VIRT    RES    SHR S  %CPU  %MEM   TIME+ COMMAND
 4567 www-data  20   0  892340 125600  45670 R  95.2   6.1  85:12 nginx
```

```bash
● nginx.service - A high performance web server and reverse proxy server
     Active: active (running) since Mon 2026-03-02 14:00:00 UTC; 2 days ago
   Main PID: 4565 (nginx)
     CGroup: /system.slice/nginx.service
             ├─4565 nginx: master process /usr/sbin/nginx
             ├─4567 nginx: worker process
             ├─4568 nginx: worker process
             └─4569 nginx: worker process
```

```bash
Mar 04 10:00:01 server nginx[4567]: *12345 upstream timed out (110: Connection timed out)
Mar 04 10:00:02 server nginx[4567]: *12346 upstream timed out (110: Connection timed out)
Mar 04 10:00:04 server nginx[4567]: *12348 upstream timed out (110: Connection timed out)
```

`systemctl status`에 유닛 이름 대신 PID를 넘길 수 있다는 점이 이 사례의 핵심입니다. systemd는 서비스마다 cgroup을 만들고 그 아래에 프로세스를 넣으므로, PID 하나만 있으면 소속 유닛을 역으로 찾아냅니다.

유닛을 알면 그다음은 로그입니다. `journalctl -u`로 그 유닛만 보면 `upstream timed out`이 반복되고 있습니다. 백엔드가 응답하지 않아 워커가 연결을 붙든 채 시간을 흘려보내는 상태이고, 그것이 CPU 95%의 정체입니다.

즉 nginx 자체는 원인이 아니라 피해자입니다. 프로세스만 보고 nginx를 재시작하면 잠시 나아졌다가 같은 상태로 돌아갑니다.

### 조치

```bash
# PID 로 유닛 역추적
systemctl status 4567

# 그 유닛의 최근 로그만 본다
journalctl -u nginx.service --no-pager -n 20

# 지목된 업스트림이 살아 있는지 직접 확인
curl -I http://127.0.0.1:3000/health

# 타임아웃을 조정한 뒤 설정 문법 검사와 무중단 반영
nginx -t && systemctl reload nginx
```

```bash
# 유닛 대신 cgroup 파일로도 같은 정보를 얻는다
cat /proc/4567/cgroup
```

`proxy_connect_timeout`과 `proxy_read_timeout`을 짧게 잡으면 죽은 업스트림을 오래 붙들지 않아 워커가 빨리 풀립니다. 다만 이것은 피해를 줄이는 설정이고, 업스트림이 왜 응답하지 않는지는 그쪽에서 따로 봐야 합니다.



## 사례 5 — 배포한 적 없는 프로세스가 CPU를 다 씁니다

> 시작 시각 역순 정렬은 "언제부터 이상해졌나"에 바로 답합니다. 실행 파일 경로까지 보면 정상 배포물인지가 갈립니다.

배포가 없었는데 로드 평균이 급격히 올랐습니다. 무엇이 언제부터 올라왔는지 모르는 상태이므로, 최근 시작된 프로세스부터 훑어야 합니다.

```bash
 16:37:45 up 15 days, 4:22, 3 users, load average: 8.45, 3.21, 1.15
```

```bash
  PID USER     STARTED                         COMMAND
 8236 deploy   Wed Mar  4 16:37:15 2026        crypto-worker
 8235 deploy   Wed Mar  4 16:37:12 2026        crypto-worker
 8234 deploy   Wed Mar  4 16:37:10 2026        crypto-worker
 8233 deploy   Wed Mar  4 16:36:58 2026        bash
 7890 root     Wed Mar  4 16:30:00 2026        cron
```

```bash
deploy    8234  99.0  2.1 456780 34560 ?  R  16:37  1:23 /tmp/.hidden/crypto-worker --threads=4
deploy    8235  99.0  2.1 456780 34560 ?  R  16:37  1:20 /tmp/.hidden/crypto-worker --threads=4
deploy    8236  99.0  2.1 456780 34560 ?  R  16:37  1:18 /tmp/.hidden/crypto-worker --threads=4
```

로드 평균 세 값의 순서부터 읽습니다. 1분 8.45, 5분 3.21, 15분 1.15로 최근으로 올수록 커지므로 부하가 방금 시작됐다는 뜻입니다. 그러면 시작 시각 역순으로 정렬한 목록의 위쪽에 원인이 있습니다.

`crypto-worker` 세 개가 각각 CPU를 99% 쓰고 있고, 실행 경로가 `/tmp/.hidden/`입니다. 정상 배포물이라면 있을 수 없는 자리입니다. `/tmp`는 아무나 쓸 수 있고 점으로 시작하는 디렉터리는 기본 목록에 안 보이므로, 둘이 겹치면 숨기려는 의도로 읽는 것이 맞습니다.

바로 위에 같은 계정의 `bash`가 몇 초 먼저 떠 있다는 점도 함께 봅니다. 셸 세션이 먼저 열리고 그 아래에서 워커가 실행된 흐름이라, `deploy` 계정의 자격 증명이 유출됐을 가능성을 전제로 대응해야 합니다.

### 조치

```bash
# 죽이기 전에 증거를 남긴다
ps -eo pid,ppid,user,lstart,args -p 8233,8234,8235,8236 > incident_ps.txt
ls -la /tmp/.hidden/ >> incident_ps.txt

# 워커와 그것을 띄운 셸 세션을 함께 종료
kill -9 8234 8235 8236 8233

# 실행 파일 제거
rm -rf /tmp/.hidden/

# 계정을 잠그고 접속 이력을 확인
passwd -l deploy
last deploy
```

증거 보존이 첫 단계인 이유는 종료한 뒤에는 인자와 부모 관계를 되살릴 수 없기 때문입니다. 침해 대응에서 가장 아쉬운 순간이 대개 "급해서 먼저 죽였다"입니다.

재발 방지는 두 갈래입니다. 서비스 계정의 로그인 셸을 `/usr/sbin/nologin`으로 막고, `/tmp`를 `noexec`로 마운트하면 이 경로로 들어오는 실행 파일 기반 공격이 상당 부분 차단됩니다.



## 다섯 사례를 관통하는 것

> 다섯 사례 모두 "어느 축으로 묶어야 쏠림이 보이는가"라는 같은 질문을 다르게 풀었습니다. 축을 못 고르면 목록만 길어집니다.

프로세스 추적에서 실력 차이는 `ps` 옵션을 얼마나 아느냐가 아니라 어떤 가설을 먼저 세우느냐에서 납니다. 사용자가 의심되면 사용자로 묶습니다. 폭증이 의심되면 부모로 묶고 최근 변화가 의심되면 시작 시각으로 정렬합니다. 같은 데이터를 다른 축으로 볼 뿐인데 답이 나오는 속도가 크게 달라집니다.

조치 쪽에도 공통점이 있습니다. 다섯 중 넷은 `kill` 한 줄로 증상이 사라지지만, 그 한 줄이 원인을 없애 주는 경우는 하나도 없습니다. 좀비는 부모 코드가, 폭주는 동시 실행 상한이, 독점은 `nproc` 제한이, 타임아웃은 업스트림이 각각 진짜 수정입니다.

마지막으로 죽이기 전에 남기는 습관이 반복해서 등장합니다. `pstree -ap`든 `ps -eo args`든, 종료 뒤에는 다시 얻을 수 없는 정보를 파일로 먼저 빼 두는 몇 초가 사후 분석 전체를 좌우합니다.
