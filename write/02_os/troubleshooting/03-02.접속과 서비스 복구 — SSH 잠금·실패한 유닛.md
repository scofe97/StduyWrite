# 접속과 서비스 복구 — SSH 잠금·실패한 유닛

---

> 서버에 못 들어가는 문제와 서비스가 계속 죽는 문제는 성격이 다르지만, 둘 다 답이 설정 파일 한 곳에 있습니다. `sshd_config`와 유닛 파일이 각각 그 자리입니다.

앞 문서가 서비스를 못 띄우는 문제였다면, 이 문서는 사람이 서버에 못 들어가는 문제와 서비스가 죽은 뒤를 다룹니다.

두 사례를 함께 두는 이유는 대응의 성격이 같기 때문입니다. 둘 다 손으로 반복하던 일을 설정으로 옮기는 작업이고, 설정값을 잘못 잡으면 그 자체가 다음 사고가 됩니다.



## 반복되는 실패는 설정으로 옮깁니다

> 로그가 같은 줄을 반복하고 있다면 사람이 손으로 대응할 문제가 아닙니다. 어떤 값이 그 반복을 만들고 있는지를 찾습니다.

장애 대응에서 가장 지치는 순간은 같은 조치를 반복할 때입니다. 접속이 안 될 때마다 비밀번호를 다시 묻고, 서비스가 죽을 때마다 손으로 다시 띄우는 식입니다.

이런 반복에는 대개 임계값이 하나 숨어 있습니다. 인증 시도 횟수 상한이거나 재시작 횟수 상한이고, 그 값이 현실과 맞지 않아 반복이 생깁니다. 그래서 확인할 곳은 로그가 아니라 설정 파일입니다.

두 사례가 다루는 설정과 그 값이 만드는 결과는 아래와 같습니다.

| 사례 | 설정 | 값이 낮으면 | 값이 높으면 |
|------|------|-------------|-------------|
| SSH 인증 | `MaxAuthTries` | 정상 사용자가 조기에 끊긴다 | 무차별 대입 공격에 시간을 준다 |
| 서비스 복구 | `StartLimitBurst` | 일시적 장애에도 복구를 포기한다 | 고장난 서비스가 무한히 재시도한다 |



## 사례 1 — 비밀번호가 맞는데 접속이 끊깁니다

> `MaxAuthTries`는 세션당 인증 시도 횟수입니다. 이 값이 낮으면 오타 몇 번에 연결이 먼저 끊깁니다.

개발자 계정이 SSH로 서버에 들어갈 수 없습니다. 비밀번호는 맞다고 하는데 로그인 과정에서 연결이 반복해서 종료됩니다.

```bash
dev@server's password:
Permission denied, please try again.
dev@server's password:
Permission denied, please try again.
dev@server's password:
dev@server: Permission denied (publickey,password).
```

```bash
Mar  4 09:12:01 server sshd[2201]: Failed password for dev from 10.0.0.5 port 5432 ssh2
Mar  4 09:12:05 server sshd[2201]: Failed password for dev from 10.0.0.5 port 5432 ssh2
Mar  4 09:12:08 server sshd[2201]: Failed password for dev from 10.0.0.5 port 5432 ssh2
Mar  4 09:12:12 server sshd[2201]: Failed password for dev from 10.0.0.5 port 5433 ssh2
Mar  4 09:12:18 server sshd[2201]: error: maximum authentication attempts exceeded for dev from 10.0.0.5 port 5433 ssh2 [preauth]
```

```bash
MaxAuthTries 3
PermitRootLogin no
PasswordAuthentication yes
```

로그의 마지막 줄이 정답을 그대로 적어 줍니다. `maximum authentication attempts exceeded`는 비밀번호가 틀렸다는 말이 아니라 시도 횟수가 상한에 닿았다는 말입니다.

`MaxAuthTries 3`이 그 상한입니다. 주의할 점은 이 값이 계정 잠금이 아니라 한 연결 안에서 허용하는 인증 시도 수라는 것입니다. 클라이언트가 공개키를 먼저 제시하면 그 시도도 횟수에 포함되므로, 실제로 비밀번호를 칠 기회는 3회보다 적습니다.

그래서 이 상황은 계정이 잠긴 것도 아니고 서버가 고장난 것도 아닙니다. 상한이 실제 사용 방식보다 빡빡해서 정상 사용자가 먼저 걸리는 상태입니다.

### 조치

```bash
# 오늘 이 계정의 인증 실패 건수를 세어 규모를 확인
grep "$(date '+%b %e')" /var/log/auth.log | grep -c "Failed password for dev"

# 상한을 실사용에 맞게 조정
sed -i 's/^MaxAuthTries 3/MaxAuthTries 6/' /etc/ssh/sshd_config

# 문법을 먼저 검사한 뒤 반영한다
sshd -t && systemctl restart sshd
```

`sshd -t`를 빼지 않는 것이 중요합니다. 설정에 오타가 있는 채로 `sshd`를 재시작하면 데몬이 뜨지 않고, 원격 서버라면 그 순간 들어갈 길이 사라집니다.

값을 올리는 것은 편의를 위한 타협이라는 점도 분명히 해 둡니다. 상한을 높이면 무차별 대입 공격에 그만큼 여지를 주므로, `fail2ban` 같은 출발지 단위 차단과 함께 쓰는 것이 안전합니다. 근본적으로는 키 인증으로 옮겨 비밀번호 인증 자체를 없애는 편이 낫습니다.



## 사례 2 — 죽는 서비스를 손으로 다시 띄우고 있습니다

> 자동 재시작만 켜면 고장난 서비스가 영원히 재시도합니다. 재시도 상한을 함께 걸어야 실패가 실패로 드러납니다.

헬스 체크 스크립트가 주기적으로 비정상 종료되는데 매번 사람이 다시 실행하고 있습니다. systemd에 등록된 유닛도 없습니다.

```bash
Checking application health...
Error: Application endpoint not responding
Exit code: 1
```

```bash
Unit check_app.service could not be found.
```

요구 사항은 네 가지입니다.

- 실패하면 자동으로 다시 띄운다
- 재시작 사이에 5초를 쉰다
- 60초 안에 3회를 넘기면 재시도를 포기한다
- 부팅할 때 함께 올라온다

여기서 놓치기 쉬운 것이 세 번째입니다. `Restart=on-failure`만 넣으면 systemd는 고장난 서비스를 무한히 다시 띄웁니다. 프로세스가 계속 뜨고 죽으면서 로그만 쌓이고, 모니터링에는 "가끔 살아 있는" 상태로 보여 장애를 늦게 발견합니다.

재시도 상한은 그래서 편의 기능이 아니라 관측 장치입니다. 상한에 걸린 유닛은 `failed` 상태로 멈추므로, 그 상태가 곧 사람이 봐야 한다는 신호가 됩니다.

### 조치

```bash
cat > /etc/systemd/system/check_app.service << 'EOF'
[Unit]
Description=Application Health Check Service
After=network.target
StartLimitIntervalSec=60
StartLimitBurst=3

[Service]
Type=simple
ExecStart=/usr/local/bin/check_app.sh
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target
EOF

# 유닛 파일을 읽히고 부팅 등록과 기동을 한다
systemctl daemon-reload
systemctl enable --now check_app.service

# 상한에 걸렸는지 상태와 로그로 확인
systemctl status check_app.service
journalctl -u check_app.service --no-pager -n 20
```

```bash
# 값의 의미
# Restart=on-failure         종료 코드가 0이 아닐 때만 다시 띄운다
# RestartSec=5               다시 띄우기 전 5초 대기
# StartLimitIntervalSec=60   상한을 세는 시간 창
# StartLimitBurst=3          그 창 안에서 허용하는 재시작 횟수
```

`StartLimitIntervalSec`과 `StartLimitBurst`가 `[Unit]` 구역에 있다는 점을 눈여겨봅니다. 재시작 정책 자체는 `[Service]`에 있지만 그 상한은 유닛 수준의 값이라, 자리를 잘못 두면 조용히 무시됩니다.

상한에 걸려 멈춘 유닛은 고친 뒤에 `systemctl reset-failed check_app.service`로 카운터를 비워야 다시 시작됩니다. 이 단계를 모르면 "고쳤는데도 안 뜬다"에서 시간을 씁니다.



## 두 사례를 관통하는 것

> 두 설정 모두 상한값이고, 낮으면 정상 동작을 막고 높으면 위험을 키웁니다. 기본값을 그대로 두는 것도 하나의 선택입니다.

`MaxAuthTries`와 `StartLimitBurst`는 다른 소프트웨어의 값이지만 성격이 같습니다. 둘 다 "몇 번까지 봐줄 것인가"를 정하고, 그 숫자 하나가 정상 사용자의 경험과 공격자의 여지를 동시에 움직입니다.

값을 조정할 때 근거를 남기는 습관이 필요한 이유가 여기 있습니다. 사례 1에서 3을 6으로 올린 것은 실패 건수를 세어 본 뒤의 결정이었고, 사례 2에서 3회를 고른 것은 요구 사항에 적힌 값이었습니다. 근거 없이 올린 숫자는 다음 사람이 되돌릴 수도 유지할 수도 없습니다.

설정을 바꾼 뒤 검증하는 순서도 공통입니다. `sshd -t`와 `systemctl status`가 각각 그 역할을 하고, 원격 서버에서는 이 검증을 건너뛴 대가가 접속 불가로 돌아옵니다.
