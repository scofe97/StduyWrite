# 라우팅과 DNS — 경로 추가·수정과 이름 해석

---

> 목적지에 못 닿는 이유는 크게 둘입니다. 어디로 보낼지 모르거나, 이름을 주소로 바꾸지 못하거나. 커널이 돌려주는 에러 문구가 둘을 갈라 줍니다.

앞 문서가 소켓 자원의 문제였다면 여기는 목적지를 찾는 단계의 문제입니다.

세 사례가 순서대로 이어집니다. 경로가 아예 없는 경우, 경로는 있는데 틀린 경우, 그리고 경로 이전에 이름을 못 바꾸는 경우입니다. 셋 다 애플리케이션이 아니라 커널과 resolver 설정에서 답이 나옵니다.



## 에러 문구가 계층을 알려 줍니다

> `Network is unreachable`, `Connection refused`, `Could not resolve host`는 각각 다른 계층에서 나옵니다. 문구를 구분하면 확인할 곳이 하나로 좁혀집니다.

연결이 안 될 때 원인을 찾는 가장 빠른 길은 에러 문구를 정확히 읽는 것입니다. 세 문구가 자주 뒤섞여 쓰이지만 나오는 자리가 서로 다릅니다.

`Network is unreachable`은 커널이 라우팅 테이블에서 목적지로 갈 경로를 못 찾았을 때 나옵니다. 패킷이 나가지도 못한 상태이므로 방화벽이나 상대 서버는 후보에서 빠집니다.

`Could not resolve host`는 그보다 앞 단계입니다. 이름을 주소로 바꾸는 데 실패했으므로 라우팅은 시도조차 되지 않았습니다.

| 에러 문구 | 실패한 단계 | 확인할 곳 |
|-----------|-------------|-----------|
| `Could not resolve host` | 이름 해석 | `/etc/hosts`, `/etc/resolv.conf`, `dig` |
| `Network is unreachable` | 경로 선택 | `ip route` |
| 손실률만 높고 응답은 옴 | 경로는 있으나 잘못됨 | `ip route`, `traceroute` |
| `Connection refused` | 상대 포트 | 상대 서버의 `ss -tlnp` |



## 사례 1 — 목적지로 가는 경로가 없습니다

> `Network is unreachable`은 패킷이 나가지 못했다는 뜻입니다. 상대를 의심하기 전에 자기 라우팅 테이블을 봅니다.

원격 서브넷 `10.20.0.0/16`에 접근해야 하는데 통신이 되지 않습니다. 영구 설정을 바꾸지 않고 임시로 길을 내야 합니다.

```bash
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.50
172.16.0.0/16 via 192.168.1.254 dev eth0
```

```bash
connect: Network is unreachable
```

```bash
1: lo: <LOOPBACK,UP> mtu 65536
2: eth0: <BROADCAST,MULTICAST,UP> mtu 1500
3: veth0: <BROADCAST,MULTICAST,UP> mtu 1500
```

라우팅 테이블에 기본 경로가 있는데도 `unreachable`이 나는 점이 처음에는 이상해 보입니다. 기본 경로가 있으면 모든 목적지가 그리로 가야 할 것 같기 때문입니다.

실제로는 그렇게 동작합니다. 다만 이 에러는 목적지가 사설 대역이고 그 대역에 명시적 경로가 필요한 구성에서 나옵니다. `172.16.0.0/16`에는 별도 경로가 잡혀 있는데 `10.20.0.0/16`에는 없다는 대비가 그 사실을 보여 줍니다.

커널의 경로 선택은 가장 긴 프리픽스를 우선합니다. 그래서 특정 대역에 전용 게이트웨이가 있는 환경에서는 대역마다 경로를 명시해야 하고, 빠진 대역이 곧 닿지 않는 대역이 됩니다.

### 조치

```bash
# 해당 대역의 경로가 있는지 먼저 확인
ip route | grep 10.20

# 임시 경로 추가
ip route add 10.20.0.0/16 via 192.168.1.1 dev veth0

# 추가 확인과 연결 테스트
ip route | grep 10.20
ping -c 3 10.20.1.100
```

```bash
# 점검이 끝나면 되돌린다
ip route del 10.20.0.0/16 via 192.168.1.1 dev veth0
```

`ip route add`로 넣은 경로는 커널 메모리에만 있어 재부팅과 함께 사라집니다. 점검이나 임시 우회에는 적합하지만, 계속 필요한 경로라면 배포판의 네트워크 설정에 넣어야 합니다.

이 휘발성은 장점이기도 합니다. 잘못 넣어도 재부팅하면 원래대로 돌아오므로, 운영 중인 서버에서 경로를 시험해 볼 때 비교적 안전합니다.



## 사례 2 — 경로는 있는데 엉뚱한 인터페이스로 나갑니다

> 손실률 80%는 경로가 없을 때의 모습이 아닙니다. 일부가 도달한다는 것은 잘못된 경로로도 어떻게든 흘러간다는 뜻입니다.

인터페이스가 둘인 서버에서 `10.10.0.0/16` 통신에 패킷 손실이 발생합니다. 라우팅이 잘못된 인터페이스를 쓰는 것으로 의심됩니다.

```bash
default via 192.168.1.1 dev eth0
192.168.1.0/24 dev eth0 proto kernel scope link src 192.168.1.50
192.168.100.0/24 dev eth1 proto kernel scope link src 192.168.100.50
10.10.0.0/16 via 192.168.50.1 dev eth0
```

```bash
5 packets transmitted, 1 received, 80% packet loss, time 4020ms
rtt min/avg/max/mdev = 245.123/245.123/245.123/0.000 ms
```

```bash
eth0: 192.168.1.0/24    → 인터넷/일반 트래픽
eth1: 192.168.100.0/24  → 내부 네트워크 (10.10.0.0/16 접근 가능)
올바른 게이트웨이: 192.168.100.1 (eth1 경유)
```

증상의 모양이 앞 사례와 다릅니다. 경로가 없으면 즉시 `unreachable`이 나지만, 여기서는 다섯 중 하나가 도달하고 응답 시간도 245ms로 유난히 깁니다.

이 조합이 "경로가 틀렸다"의 전형적인 모습입니다. 패킷이 `eth0`으로 나가 우회 경로를 타고 돌아 들어오면서 대부분 중간에 버려지고 일부만 겨우 도달합니다. 응답 시간이 긴 것도 먼 길을 돌았기 때문입니다.

테이블을 보면 `10.10.0.0/16`이 `192.168.50.1`을 거쳐 `eth0`으로 나가게 돼 있습니다. 그런데 그 게이트웨이 주소는 어느 인터페이스의 대역에도 속하지 않습니다. 구성상 이 대역은 `eth1`과 `192.168.100.1`을 써야 합니다.

### 조치

```bash
# 현재 경로 확인
ip route | grep 10.10

# 한 번에 교체한다. del 과 add 사이에 통신이 끊기지 않는다
ip route replace 10.10.0.0/16 via 192.168.100.1 dev eth1

# 확인과 테스트
ip route | grep 10.10
ping -c 5 10.10.1.100
```

```bash
# 실제 경로를 눈으로 확인한다
traceroute 10.10.1.100
```

`del` 뒤에 `add`를 하는 방식보다 `replace`가 안전합니다. 두 명령 사이의 짧은 순간에 경로가 없는 상태가 생기고, 원격에서 작업 중이라면 그 틈에 자기 세션이 끊길 수 있습니다.

수정 후에는 `ping`만으로 만족하지 말고 `traceroute`로 실제 경유지를 확인하는 편이 좋습니다. 응답이 온다는 사실과 의도한 경로로 간다는 사실은 다릅니다.



## 사례 3 — 이름을 주소로 바꾸지 못합니다

> DNS 서버 수정에 시간이 걸릴 때 `/etc/hosts`가 즉시 통하는 우회로입니다. 다만 서버 대수만큼 관리 부담이 늘어납니다.

내부 도메인 `example.local`이 일부 서버에서 해석되지 않아 서비스 간 통신이 실패합니다. DNS 서버 수정에는 시간이 걸리는 상황입니다.

```bash
;; QUESTION SECTION:
;example.local.                 IN      A

;; ANSWER SECTION:
(응답 없음)

;; Query time: 50 msec
;; SERVER: 192.168.1.1#53(192.168.1.1)
```

```bash
curl: (6) Could not resolve host: example.local
```

```bash
IPv4: 198.51.100.42
IPv6: 2001:db8:85a3::8a2e:370:7334
```

`dig` 결과를 읽을 때 두 가지를 함께 봅니다. 응답 섹션이 비어 있다는 사실과, 질의가 실제로 `192.168.1.1`까지 갔다가 50ms 만에 돌아왔다는 사실입니다.

이 조합은 DNS 서버에 닿지 못한 것이 아니라 닿았는데 레코드가 없다는 뜻입니다. resolver 설정이 잘못됐다면 질의가 타임아웃되거나 다른 서버로 갔을 것입니다. 원인은 DNS 서버의 존 데이터 쪽에 있습니다.

A 레코드와 AAAA 레코드가 모두 비어 있다는 점도 확인해 둡니다. 한쪽만 없으면 IPv6 우선 동작 때문에 간헐적으로 실패하는 다른 종류의 문제가 되지만, 여기서는 둘 다 없어 해석 자체가 불가능합니다.

### 조치

```bash
# 두 레코드를 모두 확인한다
dig example.local A +short
dig example.local AAAA +short

# 즉시 조치 — 로컬 이름 해석에 직접 등록
echo "198.51.100.42 example.local" >> /etc/hosts
echo "2001:db8:85a3::8a2e:370:7334 example.local" >> /etc/hosts

# 해석 확인은 dig 가 아니라 getent 로 한다
getent hosts example.local
curl -I http://example.local/api/health
```

```bash
# DNS 서버가 고쳐지면 임시 항목을 걷어낸다
sed -i '/example.local/d' /etc/hosts
```

확인에 `dig` 대신 `getent`를 쓰는 이유가 있습니다. `dig`는 DNS 서버에 직접 물어보므로 `/etc/hosts`를 보지 않습니다. 애플리케이션이 실제로 거치는 경로는 glibc의 이름 해석 계층이고, `getent`가 그 경로를 그대로 씁니다.

우선순위는 `/etc/nsswitch.conf`의 `hosts:` 줄이 정합니다. 보통 `files dns` 순서라 `/etc/hosts`가 DNS보다 먼저 조회되고, 그래서 이 우회가 즉시 통합니다.

다만 이것은 그 서버 한 대에만 적용되는 임시 조치입니다. 서버가 늘면 어느 장비에 어떤 항목이 남았는지 추적하기 어려워지므로, DNS 서버를 고친 뒤 반드시 걷어내는 단계까지가 한 세트입니다.



## 세 사례를 관통하는 것

> 셋 다 애플리케이션은 멀쩡합니다. 커널의 라우팅 테이블과 시스템의 이름 해석 설정이라는 서버 바깥의 두 층에서 답이 나옵니다.

에러 문구를 정확히 읽는 것이 세 사례의 공통 출발점입니다. `unreachable`과 `Could not resolve host`는 각각 다른 계층의 실패이고, 손실률이 높지만 일부는 통하는 상태는 또 다른 신호입니다. 문구를 뭉뚱그려 "안 된다"로 받으면 확인할 곳이 열 배로 늘어납니다.

임시 조치와 영구 설정을 구분하는 것도 반복됩니다. `ip route add`와 `/etc/hosts` 항목은 둘 다 그 자리에서 통하지만 둘 다 관리되지 않는 상태를 남깁니다. 전자는 재부팅으로 사라지고 후자는 사라지지 않아서 더 위험합니다.

마지막으로 확인 도구를 실제 경로에 맞추는 습관이 필요합니다. 이름 해석은 `dig`가 아니라 `getent`로, 경로는 `ping`이 아니라 `traceroute`로 확인해야 애플리케이션이 겪는 것과 같은 것을 봅니다.
