# 파일 정리와 백업 — 빈 디렉터리·재귀 백업·크기 분할

---

> 흩어진 파일을 다루는 일은 대개 `find`로 대상을 고르고 `-exec`로 처리하는 두 단계로 끝납니다. 사고는 대상을 확인하지 않고 바로 처리 단계로 넘어갈 때 납니다.

앞의 두 문서가 디스크가 터진 뒤의 대응이었다면, 이 문서는 터지기 전에 파일을 정리하고 옮기는 일상 작업입니다.

세 사례는 목적이 다 다릅니다. 하나는 지우는 일이고 하나는 복사하는 일이며 나머지 하나는 쪼개는 일입니다. 그런데 셋 다 "여러 디렉터리에 흩어진 대상을 조건으로 골라 같은 처리를 반복한다"는 뼈대를 공유하기 때문에 한 자리에 둡니다.



## 대상 선택과 처리를 분리합니다

> `find`를 쓸 때 가장 값싼 안전장치는 처리 명령을 붙이기 전에 같은 조건을 한 번 먼저 출력해 보는 것입니다.

`find`는 조건이 틀려도 경고하지 않습니다. `-type d`를 빠뜨리거나 경로를 한 단계 위로 잡아도 명령은 그대로 성공하고, 지우려던 것보다 훨씬 많은 것이 사라집니다.

그래서 이 문서의 세 사례는 모두 같은 두 단계를 밟습니다. 먼저 조건만으로 목록을 뽑아 눈으로 확인하고, 그다음에 그 조건에 처리 명령을 붙입니다. 단계를 나누는 데 드는 비용은 명령 한 줄뿐입니다. 막아 주는 사고는 복구할 수 없는 삭제입니다.

| 단계 | 하는 일 | 형태 |
|------|---------|------|
| 대상 선택 | 조건에 맞는 것만 목록으로 뽑는다 | `find <경로> <조건>` |
| 확인 | 목록이 의도와 같은지 눈으로 본다 | 위 명령의 출력을 읽는다 |
| 처리 | 확인된 조건에 명령을 붙인다 | `-delete` 또는 `-exec ... {} \;` |



## 사례 1 — 빈 디렉터리만 골라 지웁니다

> `-empty`는 내용이 없는 것만 고릅니다. 파일이 하나라도 있으면 대상에서 빠지므로 살아 있는 작업 디렉터리를 건드리지 않습니다.

`/tmp`에 이전 실행이 남긴 빈 디렉터리가 쌓여 있습니다. 파일이 든 디렉터리는 그대로 두고 빈 것만 정리해야 합니다.

```bash
drwxr-xr-x  2 root   root   4096 Feb 15 build_cache/
drwxr-xr-x  2 deploy deploy 4096 Feb 20 session_temp_1234/
drwxr-xr-x  2 root   root   4096 Feb 22 extract_workspace/
drwxr-xr-x  2 app    app    4096 Feb 25 app_tmp_5678/
drwxr-xr-x  3 dev    dev    4096 Mar 01 active_project/
-rw-r--r--  1 dev    dev    8192 Mar 01 active_project/data.csv
```

```bash
/tmp/build_cache
/tmp/session_temp_1234
/tmp/extract_workspace
/tmp/app_tmp_5678
```

빈 디렉터리는 넷이고 `active_project/`는 `data.csv`를 갖고 있어 대상에서 빠집니다. 이 구분을 사람이 눈으로 하려면 디렉터리마다 들어가 봐야 하지만, `-empty`는 그 판단을 커널이 이미 아는 정보로 대신해 줍니다.

`-delete`를 붙일 때 알아 둘 성질이 하나 있습니다. `-delete`는 `-depth`를 암묵적으로 켜서 깊은 곳부터 지웁니다. 그래서 빈 디렉터리 안에 빈 디렉터리가 든 중첩 구조도 안쪽부터 차례로 정리됩니다.

### 조치

```bash
# 먼저 대상만 확인한다
find /tmp -type d -empty

# 확인된 조건에 삭제를 붙인다
find /tmp -type d -empty -delete

# 남은 것이 없는지 같은 조건으로 재확인
find /tmp -type d -empty
```

```bash
# -delete 대신 rmdir 를 쓰면 비어 있지 않은 디렉터리에서 실패해 한 겹 더 안전하다
find /tmp -type d -empty -exec rmdir {} +
```

정기 정리를 자동화하려면 `systemd-tmpfiles`가 표준적인 선택입니다. `/etc/tmpfiles.d/`에 규칙을 두면 부팅 시점과 주기적으로 임시 파일을 정리해 줍니다.



## 사례 2 — 흩어진 파일마다 백업본을 만듭니다

> `-exec cp {} {}.bak \;`는 검색된 각 파일의 원래 자리에 복사본을 남깁니다. `{}`가 파일 경로로 치환되므로 디렉터리 구조를 따로 계산할 필요가 없습니다.

스키마 마이그레이션 전에 `/opt/data/` 하위에 흩어진 `.db` 파일을 모두 백업해야 합니다. 원본은 그대로 두고 옆에 `.db.bak`을 만드는 것이 목표입니다.

```bash
/opt/data/apps/inventory.db
/opt/data/logs/session.db
/opt/data/config/settings.db
```

```bash
/opt/data/apps/inventory.db
/opt/data/apps/inventory.db.bak
/opt/data/logs/session.db
/opt/data/logs/session.db.bak
/opt/data/config/settings.db
/opt/data/config/settings.db.bak
```

파일이 서브디렉터리 세 곳에 나뉘어 있어 한 디렉터리에서 `cp *.db` 로는 처리되지 않습니다. 각 파일을 원래 자리에 두고 이름만 늘려야 하므로, 검색 결과를 그대로 인자로 받는 `-exec`가 맞는 도구입니다.

`{}`는 검색된 경로 전체로 치환됩니다. 그래서 `{}.bak`은 같은 디렉터리에 같은 이름 뒤에 확장자만 붙은 경로가 되고, 파일이 몇 단계 깊이에 있든 계산이 필요 없습니다.

### 조치

```bash
# 대상 확인
find /opt/data -name "*.db" -type f

# 각 파일 옆에 복사본 생성, 권한과 타임스탬프까지 보존
find /opt/data -name "*.db" -type f -exec cp -p {} {}.bak \;

# 원본과 백업이 짝을 이루는지 확인
find /opt/data -name "*.db*" -type f | sort
```

`cp` 대신 `cp -p`를 쓰는 이유는 복원 시점에 권한과 소유자가 달라지면 애플리케이션이 파일을 열지 못하기 때문입니다. 백업은 내용뿐 아니라 접근 조건까지 되돌릴 수 있어야 의미가 있습니다.

다만 데이터베이스 파일은 이 방식의 한계가 분명합니다. 서비스가 켜진 채 복사하면 쓰기 도중의 상태가 그대로 찍혀 무결성이 깨질 수 있습니다. SQLite의 `.backup`이나 PostgreSQL의 `pg_dump`처럼 일관된 스냅숏을 보장하는 전용 도구가 있으면 그쪽이 우선입니다.



## 사례 3 — 업로드 제한에 걸리는 파일을 쪼갭니다

> `split -b`는 바이트 단위로 나눕니다. 나눈 조각은 `cat`으로 순서대로 이어 붙이면 원본과 바이트 단위로 같아집니다.

애플리케이션이 외부 서비스로 파일을 올리는데 최대 크기가 1MB입니다. 일부 파일이 이 제한을 넘어 업로드가 실패합니다.

```bash
ERROR: Upload failed - /tmp/app/uploads/video.mp4 (3.2MB) exceeds 1MB limit
ERROR: Upload failed - /tmp/app/data/archive.tar.gz (2.5MB) exceeds 1MB limit
```

```bash
/tmp/app/uploads/:
-rw-r--r-- 1 app app 3.2M Mar 04 video.mp4
-rw-r--r-- 1 app app 512K Mar 04 photo.jpg

/tmp/app/data/:
-rw-r--r-- 1 app app 2.5M Mar 04 archive.tar.gz
-rw-r--r-- 1 app app 800K Mar 04 report.csv
```

제한을 넘는 것은 두 파일이고 나머지 둘은 문제가 없습니다. 대상을 크기 조건으로 고를 수 있으므로 사람이 목록을 손으로 관리할 필요가 없습니다.

`split`은 내용을 해석하지 않고 바이트 위치로만 자릅니다. 동영상이든 압축 파일이든 상관없이 나뉘고, 받는 쪽에서 같은 순서로 이어 붙이면 원본이 그대로 복원됩니다. 조각 이름이 `aa`, `ab`, `ac` 순으로 붙는 것도 사전순 정렬이 곧 원래 순서가 되도록 만든 설계입니다.

### 조치

```bash
# 제한을 넘는 파일만 확인
find /tmp/app -type f -size +1M

# 각 파일을 1MB 조각으로 나눈다
find /tmp/app -type f -size +1M -exec sh -c 'split -b 1m "$1" "${1}.part_"' _ {} \;

# 결과 확인
ls -lh /tmp/app/uploads/
```

```bash
video.mp4          3.2M   원본
video.mp4.part_aa  1.0M
video.mp4.part_ab  1.0M
video.mp4.part_ac  1.0M
video.mp4.part_ad  0.2M
```

```bash
# 받는 쪽에서 복원하고 원본과 같은지 확인
cat /tmp/app/uploads/video.mp4.part_* > restored.mp4
md5sum /tmp/app/uploads/video.mp4 restored.mp4
```

복원 뒤 체크섬을 비교하는 단계를 빼지 않는 것이 좋습니다. 조각 하나가 전송 중 빠져도 `cat`은 조용히 성공하고, 손상은 파일을 실제로 열어 볼 때에야 드러납니다.

한편 이 방식은 우회책이라는 점도 분명히 해 둡니다. 대용량 전송이 반복되는 경로라면 S3 멀티파트 업로드나 `rsync`처럼 분할과 재전송을 프로토콜 차원에서 지원하는 도구로 옮기는 편이 낫습니다.



## 세 사례를 관통하는 것

> 셋 다 `find`로 대상을 고르고 `-exec`나 `-delete`로 처리합니다. 실력 차이는 조건을 얼마나 좁게 쓰느냐에서 납니다.

같은 명령이 정리도 하고 백업도 하고 분할도 합니다. 달라지는 것은 조건과 뒤에 붙는 처리뿐입니다. `-empty`, `-name "*.db"`, `-size +1M`이 각각 대상을 정하고 `-delete`, `cp`, `split`이 그 대상에 무엇을 할지 정합니다.

조건을 넓게 잡는 실수가 가장 비쌉니다. 경로를 한 단계 위로 잡거나 `-type` 을 빠뜨리면 명령은 그대로 성공하면서 의도보다 많은 대상을 처리합니다. 처리 단계를 붙이기 전에 조건만으로 한 번 출력해 보는 습관이 이 실수를 대부분 막아 줍니다.

`-exec ... {} \;`와 `-exec ... {} +`의 차이도 알아 두면 좋습니다. 앞의 것은 파일마다 명령을 한 번씩 실행하고, 뒤의 것은 여러 파일을 한 번에 넘깁니다. 파일 수가 많으면 뒤쪽이 훨씬 빠르지만, `{}`를 두 번 쓰는 사례 2 같은 형태에는 앞쪽만 쓸 수 있습니다.
