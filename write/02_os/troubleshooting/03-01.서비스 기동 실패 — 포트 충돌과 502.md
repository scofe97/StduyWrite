# 서비스 기동 실패 — 포트 충돌과 502

---

> 502는 프록시가 뒤를 못 찾았다는 뜻이지 프록시가 고장 났다는 뜻이 아닙니다. 두 사례 모두 원인은 앱이 포트에 붙지 못한 데 있습니다.

502 Bad Gateway를 보면 nginx 설정부터 열어 보게 됩니다. 그런데 이 두 사례에서 nginx 설정에는 아무 문제가 없습니다.

원인은 한 단계 뒤에 있습니다. 백엔드가 뜨지 못했고, 뜨지 못한 이유는 쓰려던 포트를 다른 프로세스가 이미 쥐고 있었기 때문입니다. 앞뒤를 잇는 이 연결을 놓치면 프록시 설정만 몇 번씩 고치게 됩니다.



## 502를 만나면 뒤부터 확인합니다

> 프록시는 자기가 받은 요청을 그대로 전달했을 뿐입니다. 확인 순서는 프록시 설정이 아니라 업스트림의 생사입니다.

502는 nginx가 만드는 응답이지만 nginx의 상태를 말해 주지는 않습니다. 프록시가 업스트림에 연결을 시도했고 그 시도가 실패했다는 사실만 알려 줍니다.

그래서 설정 파일을 먼저 열면 순서가 어긋납니다. `proxy_pass`가 가리키는 주소가 맞는지 확인하는 일도 결국 그 주소에 무언가 떠 있는지를 봐야 끝나므로, 업스트림 생사부터 보는 편이 빠릅니다.

확인은 세 단계면 충분합니다. 먼저 프록시 에러 로그에서 실패 이유를 읽습니다. 그다음 그 포트에 무엇이 붙어 있는지 보고 마지막으로 붙어 있어야 할 서비스의 상태를 봅니다.

| 단계 | 명령 | 읽는 것 |
|------|------|---------|
| 실패 이유 | `tail /var/log/nginx/error.log` | `Connection refused` 인가 `timed out` 인가 |
| 포트 점유 | `ss -tlnp \| grep :<포트>` | 아무도 없는가, 엉뚱한 프로세스가 있는가 |
| 서비스 상태 | `systemctl status <서비스>` | 죽었다면 종료 코드와 마지막 로그 |



## 사례 1 — 프록시는 멀쩡한데 502가 납니다

> `Connection refused`는 그 주소에 아무도 듣고 있지 않다는 뜻입니다. 방화벽 차단이라면 거절이 아니라 타임아웃으로 나타납니다.

리버스 프록시 뒤에 백엔드를 둔 구성에서 웹 접속이 502로 떨어집니다. 설정은 최근에 건드린 적이 없습니다.

```nginx
server {
    listen 80;
    server_name example.com;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
    }
}
```

```bash
2024/01/15 10:23:45 [error] 1234#0: *1 connect() failed (111: Connection refused) while connecting to upstream, client: 192.168.1.100, server: example.com, upstream: "http://127.0.0.1:3000/"
2024/01/15 10:23:46 [error] 1234#0: *2 connect() failed (111: Connection refused) while connecting to upstream, client: 192.168.1.101, server: example.com, upstream: "http://127.0.0.1:3000/api/health"
```

```bash
● app.service - Node.js Application
     Loaded: loaded (/etc/systemd/system/app.service.conf; enabled)
     Active: failed (Result: exit-code) since Mon 2024-01-15 10:20:00 UTC
    Process: 5678 ExecStart=/usr/bin/node /opt/app/server.js (code=exited, status=1/FAILURE)

Jan 15 10:20:00 web-server node[5678]: Error: listen EADDRINUSE: address already in use :::3000
Jan 15 10:20:00 web-server systemd[1]: app.service: Main process exited, code=exited, status=1/FAILURE
```

에러 번호 111이 핵심입니다. `Connection refused`는 패킷이 목적지에 닿았는데 그 포트에서 듣는 소켓이 없어 커널이 즉시 거절했다는 뜻입니다. 방화벽이 막았다면 응답 없이 타임아웃이 나므로, 이 구분만으로 네트워크 문제를 후보에서 뺄 수 있습니다.

`systemctl status`가 나머지를 채워 줍니다. 앱은 `EADDRINUSE`로 시작에 실패했고, 그래서 3000번에 아무도 붙어 있지 않으며, 그 결과 프록시가 거절당했습니다. 세 사실이 한 줄로 이어집니다.

즉 502는 결과이지 원인이 아닙니다. 고칠 자리는 프록시가 아니라 앱이 포트를 못 잡은 이유입니다.

### 조치

```bash
# 그 포트를 누가 쥐고 있는지 확인
ss -tlnp | grep :3000

# 확인된 프로세스를 정리한 뒤 앱을 다시 띄운다
kill <PID>
systemctl restart app

# 앞뒤 양쪽에서 확인
systemctl status app
curl -I http://127.0.0.1:3000/api/health
```

`Restart=on-failure`와 `RestartSec=5`를 유닛에 넣어 두면 이런 실패에서 자동으로 복구를 시도합니다. 다만 포트를 쥔 프로세스가 그대로 살아 있으면 재시도도 계속 실패하므로, 자동 재시작은 근본 해결이 아니라 시간을 벌어 주는 장치입니다.

애플리케이션 쪽에서는 `SIGTERM`을 받았을 때 소켓을 닫고 나가는 종료 처리를 구현해야 합니다. 비정상 종료가 포트를 남기는 것이 이 사고의 반복 원인입니다.



## 사례 2 — 시작하자마자 종료됩니다

> `bind(): Address already in use`는 앱의 버그가 아니라 환경의 상태입니다. 누가 그 포트를 쥐고 있는지부터 봅니다.

애플리케이션 서버를 시작하면 즉시 에러를 내고 종료됩니다. 어제까지 정상이었고 설정을 바꾼 적도 없습니다.

```bash
Starting application server...
Error: bind(): Address already in use (port 8080)
Server failed to start. Exiting.
```

```bash
LISTEN  0  128  0.0.0.0:8080  0.0.0.0:*  users:(("python3",pid=4521,fd=3))
```

```bash
nobody    4521  0.1  1.2  45678  12340 ?  S  Feb28  2:15  python3 -m http.server 8080
```

`ss -tlnp`가 곧바로 답을 줍니다. 8080번을 `python3 -m http.server`가 듣고 있고, 시작 시각이 2월 28일이라 며칠째 살아 있습니다. 테스트로 띄운 간이 서버가 종료되지 않고 남은 전형적인 모습입니다.

앞 사례와 같은 원인이 다른 각도에서 보입니다. 사례 1에서는 앱의 실패가 프록시의 502로 드러났고, 여기서는 앱을 직접 띄우다 같은 실패를 눈으로 봅니다. 관측 지점만 다를 뿐 커널이 거절하는 지점은 같습니다.

`ss` 옵션 네 글자의 뜻을 알아 두면 이 확인이 빨라집니다. `t`는 TCP, `l`은 듣고 있는 소켓만, `n`은 포트를 이름으로 바꾸지 않기, `p`는 프로세스 정보 표시입니다.

### 조치

```bash
# 포트 점유자 확인, 둘 중 편한 쪽을 쓴다
ss -tlnp | grep :8080
lsof -i :8080

# 점유 프로세스 종료
kill 4521

# 포트가 비었는지 확인한 뒤 기동
ss -tlnp | grep :8080
./server.sh start
```

systemd로 관리한다면 `ExecStartPre`에 포트 확인을 넣어 기동 전에 걸러낼 수 있습니다. 실패 원인을 앱 로그가 아니라 유닛 로그에서 명확하게 볼 수 있다는 이점도 함께 얻습니다.

애플리케이션이 재시작 직후에만 실패한다면 원인이 다를 수 있습니다. 이전 연결이 `TIME_WAIT`으로 남아 바인딩을 막는 경우인데, 이때는 `SO_REUSEADDR` 소켓 옵션이 정답입니다.



## 두 사례를 관통하는 것

> 두 사례의 진짜 원인은 하나입니다. 포트는 한 번에 한 프로세스만 쥘 수 있고, 그 사실을 프록시는 502로, 앱은 기동 실패로 각각 보고합니다.

같은 원인이 관측 지점에 따라 다른 얼굴로 나타난다는 점이 이 문서의 핵심입니다. 502만 보고 nginx 설정을 고치면 문제가 풀리지 않습니다. 에러 로그의 `Connection refused` 한 줄을 읽어야 곧바로 뒤쪽으로 넘어갑니다.

에러 문자열이 원인을 좁혀 준다는 점도 반복됩니다. `Connection refused`는 아무도 안 듣는 상태, `timed out`은 응답이 없는 상태, `EADDRINUSE`는 이미 누가 쥔 상태를 각각 가리킵니다. 셋을 구분하면 확인할 곳이 절반으로 줄어듭니다.

마지막으로 재발 방지의 방향이 같습니다. 종료 시 소켓을 확실히 닫는 처리와 기동 전 포트 점검 두 가지가 이 계열 사고의 대부분을 막습니다.
