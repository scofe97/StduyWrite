# Repo·프로젝트·워크트리 — 작업 공간을 가르는 법
---
> 격리는 ADE 세 축 중 첫째이고, ORCA는 그것을 git 워크트리로 구현합니다. 발명한 개념이 아니라 원래 있던 기능이라 평소 쓰던 git 명령이 그대로 통합니다. 다만 무엇이 남고 무엇이 사라지는지는 정확히 알아야 합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. git 워크트리가 브랜치 전환과 무엇이 다른지 설명하고, ORCA가 그 위에 무엇을 얹었는지 댈 수 있습니다.
2. 작업을 워크트리로 나눌지 말지를 기준을 들어 판단할 수 있습니다.
3. `worktree rm`이 무엇을 막고 무엇을 막지 않는지 표로 재현하고, 삭제 전 확인 절차를 실행할 수 있습니다.
4. Repo와 프로젝트·호스트 셋업의 관계를 알고, 언제 `project` 명령이 필요한지 판단할 수 있습니다.

에이전트에게 지시를 보내고 결과를 회수하는 일은 [02-02](02-02.터미널과 에이전트 운전 — 지시·대기·완료 판정.md)에서 다룹니다.



## 1. 워크트리는 git의 기능입니다

> 브랜치 전환은 폴더 하나의 내용을 통째로 바꿉니다. 워크트리는 브랜치마다 폴더를 따로 두되 저장소는 하나를 공유합니다.

![브랜치 전환과 워크트리의 차이 — 폴더 하나 대 폴더 여럿](_assets/02-01-worktree-vs-switch.svg)

`git switch`로 브랜치를 바꾸면 같은 폴더의 파일 내용이 바뀝니다. 폴더가 하나라서 생기는 제약이 몇 가지 있습니다. `feature/login`을 작업하면서 `main`의 테스트를 동시에 돌릴 수 없고, 두 브랜치의 실행 결과를 나란히 비교할 수도 없습니다.

git 워크트리는 하나의 저장소에서 브랜치마다 별도 폴더를 만드는 기능입니다.

```bash
git worktree add ../my-app-login feature/login
```

두 폴더는 같은 `.git`을 공유하므로 커밋 이력이 하나로 이어집니다. 저장소는 하나이고 작업 폴더가 여럿인 구조입니다.

ORCA는 이 구조를 작업 관리의 뼈대로 쓰기로 결정했을 뿐입니다. 그래서 ORCA가 만든 작업 공간에 평소 쓰던 git 명령이 그대로 통하고, ORCA를 지워도 브랜치와 커밋은 남습니다.

다만 git 워크트리만으로는 에이전트를 여럿 돌리기에 부족합니다. 폴더는 나뉘었지만 관리가 없기 때문입니다. ORCA는 각 워크트리에 터미널 세션, 에이전트 상태, 읽음 표시, 부모-자식 관계, 이슈·PR 링크, 코멘트, 브라우저 탭 스코프를 붙입니다.

실측한 v1.4.188에서 워크트리 하나를 만들어 응답을 보면 필드가 40개입니다. git이 아는 것은 `path`·`head`·`branch`·`isMainWorktree` 정도이고 나머지는 ORCA가 관리하는 정보입니다. **워크트리는 git 폴더에 ORCA의 작업 메타데이터를 얹은 것**입니다.



## 2. 만들면 어디에 무엇이 생기는가

> 명령 한 줄이 폴더와 브랜치와 터미널을 동시에 만듭니다. 원본 폴더는 건드려지지 않습니다.

![worktree create 한 줄이 만드는 폴더·브랜치·터미널](_assets/02-01-create-effects.svg)

가장 짧은 형태입니다.

```bash
orca worktree create --repo id:<repoId> --name demo-a --json
```

이 한 줄이 만든 것을 실측으로 확인하면 이렇습니다.

```bash
# 응답
path:   $HOME/orca/workspaces/orca-practice/demo-a
branch: refs/heads/demo-a
isMainWorktree: false

# git 쪽
git worktree list
# ~/orca-practice                            1f87868 [main]
# ~/orca/workspaces/orca-practice/demo-a     1f87868 [demo-a]
```

읽어 낼 규칙이 넷 있습니다.

**폴더는 정해진 자리에 만들어집니다.** 원본 프로젝트 폴더 옆이 아니라 홈 디렉터리 아래입니다. 프로젝트 폴더를 깨끗하게 유지하려는 선택인데, 대신 원본과 멀리 떨어져 있어 처음에는 헷갈립니다. 원서의 Windows 경로와 형태는 같고 구분자만 다릅니다.

**브랜치 이름이 워크트리 이름과 같습니다.** `--name`이 폴더 이름과 브랜치 이름을 동시에 정합니다. 그래서 워크트리 이름을 브랜치 규칙에 맞춰 짓는 편이 좋습니다.

**원본 폴더도 워크트리입니다.** 목록에 원본이 함께 나오고 `isMainWorktree: true`로 구분됩니다.

**터미널이 하나 자동으로 붙습니다.** `--agent`를 주지 않아도 그렇습니다. 빈 워크트리를 만들었다고 생각했는데 `connected: true`인 셸이 이미 있는 것이 정상입니다.

에이전트를 넣을 생각이면 처음부터 한 번에 하는 편이 낫습니다. 워크트리를 먼저 만들고 나중에 에이전트를 띄우면 쓰지 않는 셸 터미널이 하나 더 남기 때문입니다.

```bash
orca worktree create --repo id:<repoId> --name first-task \
  --agent claude --prompt "src/calc.py 에 power 함수를 추가하고 테스트로 확인해 주세요" --json
```

워크트리를 만들어도 앱 화면은 전환되지 않습니다. 스크립트로 여러 개를 만들 때 화면이 튀지 않게 한 설계이고, 바로 보려면 `--activate`를 줍니다. `--agent`를 주면 자동으로 전환됩니다.



## 3. 언제 나누고 언제 나누지 않는가

> 한 워크트리는 한 개의 완결된 작업이고 한 개의 브랜치이며 하나의 PR입니다. PR 하나로 올릴 만한 크기가 워크트리 하나의 크기입니다.

![워크트리를 나눌 때와 나누지 않을 때의 기준](_assets/02-01-split-criteria.svg)

나눠야 하는 쪽부터 봅니다. 에이전트를 둘 이상 동시에 돌린다면 파일 충돌을 막기 위해 필수입니다. 실패해도 되는 실험을 할 때, 같은 작업을 다른 방식으로 두 번 시켜 비교할 때, 리뷰 대기 중인 작업을 건드리지 않고 다른 일을 시작할 때도 나눕니다.

반대로 굳이 나누지 않아도 되는 쪽이 있습니다. 한 줄 수정처럼 즉시 끝나는 일은 워크트리를 만들고 정리하는 비용이 더 큽니다. 여러 파일에 걸쳐 있어도 하나의 논리적 작업이면 워크트리는 하나입니다. 읽기만 하는 조사 작업은 파일을 안 고치니 충돌이 없습니다.

**워크트리는 무료가 아닙니다.** 비용이 세 갈래로 붙습니다.

- 디스크 — 프로젝트 파일이 별도 폴더에 체크아웃됩니다. 저장소 데이터는 공유합니다.
- 메모리 — 워크트리마다 터미널 세션이 붙고, 에이전트가 붙으면 수백 MB를 씁니다.
- 시간 — 설정 스크립트가 있으면 워크트리를 만들 때마다 실행됩니다.

원서는 에이전트가 붙은 세션 하나가 446MB를 쓰는 경우를 봤다고 적었습니다. 워크트리 열 개에 에이전트를 다 붙이면 메모리가 금방 바닥납니다. 끝난 워크트리를 지우는 습관이 필요한 이유입니다.



## 4. `rm`이 막는 것과 막지 않는 것

> 미커밋 변경만 막습니다. 그리고 가장 위험한 것은 막지 않는 쪽에 있습니다.

![파일 상태별로 삭제가 막히는지와 삭제 후 남는지](_assets/02-01-rm-safety.svg)

깨끗한 워크트리는 바로 지워집니다. 막히는 경우는 커밋하지 않은 변경 하나입니다. 실측에서 재현한 오류는 이랬습니다.

```bash
orca worktree rm --worktree "path:$HOME/orca/workspaces/orca-practice/demo-a" --json
# "code": "runtime_error"
# "message": "Failed to delete worktree at .../demo-a. ?? result.txt"
```

어떤 파일이 남아 있는지까지 알려 줍니다. 원서 예시는 수정된 파일(`M src/calc.py`)이었고 이쪽은 추적되지 않는 새 파일(`?? result.txt`)이었는데, 둘 다 막습니다.

여기서 놓치기 쉬운 것이 있습니다. `git reset --hard HEAD`나 `git restore`는 **git이 알고 있는 파일만** 되돌립니다. 에이전트가 새로 만든 파일은 그대로 남고, 그러면 삭제가 계속 막힙니다. `git clean -fd`까지 해야 정리됩니다.

**가장 위험한 것은 `.gitignore`에 걸린 파일입니다.** 삭제를 막아 주지도 않고 어디에도 보이지 않은 채 워크트리와 함께 사라집니다. 이 노트에서 직접 재현했습니다.[^gitignore]

```bash
# result.txt 를 .gitignore 에 넣어 둔 상태
git status --short          # 아무것도 안 나옴
orca worktree rm --worktree "path:.../probe-links" --json
# {"removed": true, "preservedBranch": {...}}   ← --force 없이 통과
ls .../probe-links/result.txt
# No such file or directory
```

에이전트에게 완료 신호로 `DONE.txt`를 만들게 하거나 테스트 결과를 `result.txt`로 남기게 했다면, 그 파일이 무시 목록에 있는지 확인하세요. 지우기 전에 다른 경로로 복사해야 합니다.

`--force`는 미커밋 변경 검사만 건너뜁니다. 실측에서 `--force`를 준 삭제는 살아 있는 터미널이 있어도 통과했습니다.

원서는 v1.4.154에 두 번째 안전장치가 있었다고 기록해 두었습니다. 에이전트 TUI가 살아 있으면 `Failed to physically stop every PTY` 오류로 거부됐고, `--force`로도 빠져나오기 어려웠다고 합니다. v1.4.176에서 그 검사가 없어졌고 v1.4.188에서도 없습니다. **안전장치가 하나 줄었다는 뜻이므로, 끝났는지 확인하고 지우는 책임은 사람에게 넘어왔습니다.**

정리 순서는 이렇습니다.

```bash
git status --short          # 무엇이 있는지 본다
git clean -nd               # 지워질 새 파일을 미리 본다
# 남길 것은 커밋, 버릴 것은 git reset --hard HEAD + git clean -fd
orca worktree rm --worktree "path:<경로>" --json
```



## 5. 삭제해도 브랜치가 남는 조건

> 커밋한 것만 남습니다. 그리고 남길 것이 없으면 브랜치도 함께 정리됩니다.

<!-- no-diagram: 앞 절 도식이 파일 상태별 생존 여부를 이미 보이고, 이 절은 그 표의 한 줄을 조건으로 좁히는 서술이라 새로 그릴 형태가 없습니다. -->

원서는 삭제 응답에 보존된 브랜치가 함께 온다고 적었습니다. 실측에서도 그랬습니다.

```bash
orca worktree rm --worktree "path:.../demo-b" --force --json
# {"removed": true,
#  "preservedBranch": {"branchName": "demo-b", "head": "0abe84ff..."}}
```

그 브랜치를 확인하면 커밋이 그대로 살아 있습니다. 워크트리 폴더만 사라진 것입니다.

여기에 조건이 하나 더 있다는 것을 통제 실험으로 확인했습니다. **그 브랜치에 고유한 커밋이 없으면 브랜치까지 정리됩니다.** 워크트리를 만들자마자 아무 커밋 없이 지운 경우 응답에 `preservedBranch`가 없었고 `git branch --list`에서도 사라졌습니다. 같은 절차를 커밋 하나를 얹고 반복하니 보존됐습니다.

두 실험의 차이는 커밋 유무 하나였습니다. 남길 것이 있으면 남기고 없으면 정리하는, 합리적인 동작입니다. 다만 "브랜치는 항상 남는다"고 외우면 첫 번째 경우에 당황하게 됩니다.



## 6. Repo와 프로젝트는 다른 층입니다

> 한 기기에서만 일한다면 `repo add` 하나로 끝납니다. `project` 명령 일곱 개는 여러 기기에서 같은 프로젝트를 다룰 때를 위한 것입니다.

![프로젝트·호스트 셋업·Repo 세 층의 관계](_assets/02-01-project-layers.svg)

`repo add`로 등록을 끝냈는데도 명령 출력에 `projectId`나 `projectHostSetupId` 같은 필드가 계속 등장합니다. 세 층으로 나뉘어 있기 때문입니다.

프로젝트는 일감의 논리적 이름이고 하나입니다. 호스트 셋업은 특정 기기에서의 실제 위치이고 기기마다 하나입니다. Repo는 그 기기의 실제 폴더이고 셋업마다 하나입니다.

중요한 것은 **이 셋이 이미 만들어져 있다**는 점입니다. `repo add`를 한 번 실행하면 프로젝트와 셋업이 함께 생깁니다. 프로젝트 id는 `repo:<repoId>` 형태로 자동 생성되고, 셋업에는 `setupMethod: "legacy-repo"`가 붙습니다. 단순 Repo 등록으로 만들어진 셋업이라는 표시입니다.

`project` 명령이 필요한 경우는 셋입니다. 같은 프로젝트를 두 기기에서 다룰 때, 원격 기기에 아직 클론이 없을 때, 셋업 정보가 어긋났을 때입니다. 셋 다 원격 런타임과 함께 쓰는 상황이라 [05-01](05-01.운영과 권한 경계 — 환경 레시피·원격 런타임·보안.md)과 함께 보는 편이 좋습니다.

워크트리의 부모 관계에도 자동 추론이 걸려 있습니다. 프로젝트 폴더 안에서 `worktree create`를 실행하면 `capture.source`가 `cwd-context`, `confidence`가 `inferred`인 정보가 붙습니다. 명령을 실행한 곳을 부모 작업 공간으로 추측한 것입니다. 의도와 다르면 `--parent-worktree`로 명시하거나 `--no-parent`로 끊습니다.

`--no-parent`는 목록 표시에만 영향을 줍니다. 브랜치가 어디서 갈라지는지는 `--base-branch`가 정합니다.



## 면접에서 받을 만한 질문

1. 에이전트가 만든 결과가 마음에 들지 않아 워크트리를 지우려는데 삭제가 막힙니다. 어떤 순서로 처리합니까?
2. 워크트리를 지웠는데 브랜치가 안 보입니다. 커밋이 사라진 것입니까?
3. 워크트리 격리가 있으니 에이전트를 스무 개까지 늘려도 됩니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 새 파일까지 정리해야 풀립니다

`git status --short`로 무엇이 남았는지 먼저 봅니다. 수정된 파일(`M`)은 `git reset --hard HEAD`로 되돌아가지만, 추적되지 않는 새 파일(`??`)은 그대로 남아 삭제를 계속 막습니다. `git clean -nd`로 지워질 목록을 확인한 뒤 `git clean -fd`로 정리합니다. `--force`로 우회할 수도 있지만, 그전에 `.gitignore`에 걸린 산출물이 있는지 확인해야 합니다. 그 파일들은 경고 없이 함께 사라집니다.

### 정답 2 — 그 브랜치에 고유 커밋이 있었는지를 봅니다

커밋한 내용은 사라지지 않습니다. 브랜치가 안 보인다면 그 워크트리에서 커밋을 하나도 하지 않았을 가능성이 큽니다. 원본과 같은 지점이라 남길 것이 없으면 ORCA가 브랜치까지 정리합니다. 커밋이 있었다면 삭제 응답에 `preservedBranch`가 함께 오고 브랜치는 남습니다.

### 정답 3 — 자원이 먼저 바닥납니다

격리는 파일 충돌만 막습니다. 워크트리마다 프로젝트 파일이 체크아웃되어 디스크를 쓰고, 터미널 세션이 붙어 메모리를 씁니다. 에이전트가 붙은 세션 하나가 수백 MB를 쓰므로 열 개만 넘어도 부담이 큽니다. 포트나 데이터베이스처럼 공용으로 쓰는 자원은 여전히 겹칩니다. 동시 개수는 격리가 아니라 자원과 사람이 확인할 수 있는 양이 정합니다.
