# 실패와 복구 — 거짓 성공과 개입 신호
---
> 이 편을 관통하는 문장이 하나 있습니다. **`ok: true`는 "요청을 접수했다"는 뜻이지 "그렇게 됐다"는 뜻이 아닙니다.** 그리고 반대도 성립합니다 — 오류를 받아도 실제로는 됐을 수 있습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 응답이 아니라 상태로 확인하는 습관을 명령별로 대응시켜 적용할 수 있습니다.
2. 오류 응답을 받았을 때 재시도 전에 무엇을 확인해야 하는지 설명할 수 있습니다.
3. 진단 3단 콤보로 어느 층이 문제인지 좁힐 수 있습니다.
4. 멈춘 에이전트를 판별하는 재료를 대고, 자기 환경에서 그 수치를 직접 재는 방법을 실행할 수 있습니다.

되돌리기 절차의 상세와 개입 신호 목록은 원서 유료 편의 본론이라 이 노트에서 다루지 않습니다.



## 1. 성공 응답을 믿지 마세요

> 실측으로 확인된 "거짓 성공"이 여럿입니다. 대응은 하나뿐입니다 — 응답이 아니라 상태를 봅니다.

![응답과 실제가 어긋나는 명령들과 대신 확인할 상태](_assets/05-02-false-success.svg)

원서가 12장 미리보기에 공개한 목록입니다. 전부 성공 응답을 돌려주면서 실제로는 그 일이 일어나지 않았습니다.

| 명령 | 응답 | 실제 |
|------|------|------|
| `terminal stop` | `{"stopped": 1}` | 에이전트 TUI 프로세스는 살아남음 |
| `terminal send --text "/exit" --enter` | `ok: true` | 프로세스 안 죽음 |
| `terminal close --tab` | `{"ptyKilled": true}` | 곧바로 다시 생김 |
| `click --element <ref>` | `{"clicked": "e4"}` | 클릭 이벤트 미전달 |
| `cookie delete --name <이름>` | `{"cleared": true}` | 이름과 무관하게 전부 삭제 |

앞 편들에서 이 중 둘을 v1.4.188에서 다시 밟았습니다. **클릭은 고쳐졌고 쿠키는 그대로였습니다.** 목록이 버전마다 바뀐다는 뜻이고, 그래서 목록을 외우는 것보다 습관을 들이는 쪽이 낫습니다.

| 확인하려는 것 | 응답 대신 볼 것 |
|--------------|----------------|
| 터미널이 죽었는가 | `worktree ps`의 `live:` 숫자 |
| 워크트리가 지워졌는가 | `worktree list`에 없는지 |
| 클릭이 먹었는가 | 다시 `snapshot`을 떠서 화면 변화 |
| 파일이 바뀌었는가 | `git status --short` |

이 대응이 앞 편들에서 반복해 나온 원칙과 같습니다. [02-02](02-02.터미널과 에이전트 운전 — 지시·대기·완료 판정.md)에서 완료를 신호가 아니라 결과물로 판정했고, [04-01](04-01.내장 브라우저 자동화 — 스냅샷으로 보고 나서 누른다.md)에서 조작 결과를 다시 스냅샷으로 확인했습니다. **같은 습관이 도구 전체에 걸쳐 필요합니다.**



## 2. 오류 응답도 믿지 마세요

> 방향이 반대인 어긋남도 있습니다. `runtime_unavailable`을 받고 실패한 줄 알았는데 이미 처리돼 있는 경우입니다.

![성공 응답과 오류 응답이 각각 어느 방향으로 어긋나는가](_assets/05-02-both-directions.svg)

원서가 워크트리 셋을 연달아 지우다 셋 다 재시작하라는 오류를 받았는데, 목록을 확인하니 **셋 다 실제로는 지워져 있었다**고 기록했습니다.

| 받은 것 | 실제 | 해야 할 일 |
|---------|------|-----------|
| `ok: true` | 안 됐을 수 있다 | 상태 확인 |
| `runtime_unavailable` | 됐을 수 있다 | 상태 확인 후 재시도 결정 |

실패했다고 믿고 같은 명령을 반복하면 이미 처리된 작업을 다시 시도하다 엉뚱한 오류를 만납니다. **양쪽 모두에서 결론이 같습니다.** 응답의 방향과 무관하게 상태를 한 번 확인합니다.

브라우저 쪽에서 이 오류를 만나면 앱을 재시작하기 전에 두 가지를 봐야 한다는 것을 [04-01](04-01.내장 브라우저 자동화 — 스냅샷으로 보고 나서 누른다.md)에서 확인했습니다. 스냅샷을 먼저 찍었는지, `--json`을 붙였는지입니다. `orca status --json`을 실행해 보면 대개 `ready`입니다.



## 3. 진단은 층을 좁히는 일입니다

> 부품이 나뉘어 있으니 어느 부품이 문제인지 좁혀 가면 됩니다. 세 명령이면 대부분 좁혀집니다.

![진단 3단 콤보와 각 단계에서 읽는 값](_assets/05-02-triage.svg)

무슨 문제든 이 셋으로 시작합니다.

```bash
orca status --json          # 어느 층이 준비되지 않았나
orca worktree ps            # 어떤 작업이 살아 있나
orca terminal list --json   # 어떤 터미널이 붙어 있나
```

첫 번째가 [01-02](01-02.ORCA의 구성 — 앱·런타임·CLI·워크트리.md)의 3층 모델을 진단 관점에서 쓰는 것입니다. 앱 창이 없으면 `app`, 거의 모든 명령이 실패하면 `runtime`, 워크트리·태스크 명령이 빈 결과를 주면 `graph`를 의심합니다. **브라우저 명령만 실패한다면 런타임 문제가 아닐 가능성이 높습니다.**

두 번째의 값어치는 `preview`에 있습니다. 각 워크트리의 마지막 출력 줄을 보여 주므로 워크트리 열 개 중 어느 것이 멈춰 있는지 스크롤 한 번으로 보입니다.

| 읽은 값 | 뜻 |
|---------|-----|
| `live:0 pty:no` | 터미널이 없음 — 에이전트가 죽었거나 시작 못 함 |
| `live:1` + `preview`가 프롬프트 | 셸만 있고 에이전트는 없음 |
| `preview`가 질문 화면 | 사람 입력을 기다리는 중 |
| `preview`가 몇 분 전과 같음 | 멈춤 의심 |

세 번째에서는 `lastOutputAt`을 봅니다. 밀리초 타임스탬프라 현재 시각과 비교하면 몇 분째 조용한지 계산됩니다. 완료 판정의 재료이자 멈춤 판정의 재료입니다.

에이전트가 반응 없을 때 가장 흔한 원인은 폴더 신뢰 확인입니다. `preview`에 질문 문구가 보이면 그것입니다.



## 4. 자원 수치는 자기 환경에서 재야 합니다

> 원서 수치를 그대로 인용하면 틀립니다. 구조는 같고 값은 환경마다 다릅니다.

![diagnostics memory 응답 구조와 이 맥북에서 잰 값](_assets/05-02-memory.svg)

앱이 무거워졌을 때 씁니다.

```bash
orca diagnostics memory --json
```

응답 구조는 원서 서술과 같았습니다. 최상위에 `app`·`totalMemory`·`totalCpu`·`collectedAt`·`host`·`worktrees`가 오고 **단위는 바이트**입니다. 워크트리마다 세션 목록이 붙고 각 세션에 `pid`가 있어서, 특정 세션이 자원을 먹고 있으면 OS 도구에서 그 프로세스를 찾을 수 있습니다.

**값은 크게 달랐습니다.** 이 맥북에서 잰 결과입니다.[^mem]

| 대상 | 이 맥북 | 원서 (Windows) |
|------|---------|----------------|
| 앱 전체 | 411MB | 890MB (다른 시점 713MB) |
| 세션 네 개 | 1 · 46 · 81 · 94MB | 에이전트 446MB · 셸 8MB |

원서는 에이전트 세션과 셸 세션의 차이가 50배가 넘는다고 적었는데 여기서는 그 비율이 나오지 않았습니다. OS도 다르고 그때 돌던 에이전트와 작업 내용도 다릅니다. **방향은 같습니다** — 에이전트가 붙은 세션이 셸보다 훨씬 무겁고, 세션 수가 곧 메모리입니다.

그래서 이 절의 결론은 수치가 아니라 습관입니다. 워크트리를 몇 개까지 늘릴지는 남의 수치가 아니라 **자기 환경에서 잰 값**으로 정합니다. 앱 하단 상태바의 자원 표시가 이 정보의 요약이므로, 거기서 먼저 보고 자세히 봐야 할 때 이 명령을 씁니다.

여기서 원서 안의 어긋남이 하나 드러납니다.

> **원문 정오**: 09-4는 이 수치를 근거로 "`--max-concurrent`가 왜 필수 안전장치인지"를 설명합니다. 그런데 같은 책 05-4는 자동 코디네이터 루프가 은퇴하면서 `--max-concurrent` 같은 자동 상한이 사라졌다고 적었습니다. v1.4.188의 스키마를 훑어 보면 이 플래그는 `orchestration coordinator-start` 하나에만 남아 있고, 그 명령은 호출하면 `orchestration_migration_required`를 돌려주는 은퇴 스텁입니다. **자동 상한은 실질적으로 없고, 동시 실행 수는 직접 세야 합니다.**



## 5. 꼬인 상태를 푸는 순서

> 각 장에서 흩어져 나온 정리 문제가 여기서 한 절차로 모입니다. 순서를 지키는 것이 핵심입니다.

![워크트리가 안 지워질 때 밟는 세 단계](_assets/05-02-cleanup.svg)

워크트리가 지워지지 않을 때의 순서입니다.

```bash
git status --short     # 미커밋 변경이 있는가 — 있으면 커밋 또는 되돌리기
orca worktree ps       # 에이전트가 아직 일하고 있지는 않은가
orca worktree rm --worktree "path:<경로>" --json
```

두 번째 단계의 의미가 버전에 따라 바뀌었습니다. 예전에는 살아 있는 터미널이 삭제를 막았지만 지금은 막지 않습니다. **안전장치가 하나 줄었다는 뜻이므로, 끝났는지 확인하는 책임이 사람에게 넘어왔습니다.** 돌고 있는 워크트리를 지우면 하던 일이 사라집니다.

자동화가 만든 워크트리가 쌓이는 것도 같은 절차로 정리하되, 근본 대책은 사전 검사로 불필요한 실행을 줄이는 쪽입니다.

오케스트레이션 상태가 지저분할 때 **`orchestration reset --all`을 쓰지 않습니다.** 조회는 Run 단위로 나뉘지만 초기화는 로컬 데이터베이스 전체를 지웁니다. 화면에 안 보이는 다른 Run까지 사라집니다. 정리는 태스크를 하나씩 닫는 것으로 합니다.

```bash
orca orchestration task-update --id <task_id> --status completed --from <핸들> --json
```

여기에 한 줄 덧붙일 것이 있습니다. **끝나지 않은 태스크를 완료로 위조하지 않습니다.** 의존이 걸린 후속 태스크가 전제 없이 열립니다. 포기하는 경우라면 그것을 그대로 기록하는 편이 낫습니다.



## 6. 보고할 때 모으고 지울 것

> 재현 정보를 모으는 것과 개인·조직 정보를 지우는 것이 한 세트입니다.

<!-- no-diagram: 모을 항목과 지울 항목을 나열하는 절이고, 노출 경로는 앞 편의 도식이 이미 보입니다. -->

버그로 보이는 문제를 만났을 때 모을 것은 여섯입니다. 버전과 세 층 상태, 실패한 명령 전문과 응답, 당시 워크트리 상황, 터미널 상황, 자원 문제로 보이면 메모리 상황, 그리고 재현 절차입니다.

지울 것은 [05-01](05-01.운영과 권한 경계 — 환경 레시피·원격 런타임·보안.md)에서 다룬 목록과 같습니다. 다른 프로젝트 경로, 원격 연결 정보와 페어링 코드, 사용자 이름이 든 경로, 티켓·저장소 식별자입니다.

이 노트를 만들며 실행한 명령에서도 매번 무관한 프로젝트가 함께 나왔습니다. 출력을 그대로 붙여넣지 않는 것이 규칙입니다.

버전이 달라 이 노트와 동작이 어긋나면 확인 순서는 원서가 정한 그대로입니다.

1. `orca status --json` 으로 내 버전을 확인합니다.
2. `orca agent-context --json` 에서 그 명령의 사용법을 직접 봅니다.
3. `orca skills get <주제>` 로 설치본 기준 가이드를 읽습니다.

**이 셋은 버전과 무관하게 정답을 알려 줍니다.**



## 면접에서 받을 만한 질문

1. `orca worktree rm`이 `runtime_unavailable`을 돌려줬습니다. 바로 다시 실행해도 됩니까?
2. 에이전트가 30분째 조용합니다. 멈춘 것인지 어떻게 판별합니까?
3. 오케스트레이션 상태가 지저분해서 초기화하려 합니다. 무엇을 조심해야 합니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 먼저 목록을 확인합니다

오류 응답이 실패를 뜻하지 않는 경우가 있습니다. 원서 실측에서 이 오류를 세 번 연속 받았는데 셋 다 실제로는 지워져 있었습니다. 실패했다고 믿고 같은 명령을 반복하면 이미 처리된 작업을 다시 시도하다 다른 오류를 만납니다. `worktree list`나 `worktree ps`로 상태를 확인한 뒤 재시도 여부를 정합니다.

### 정답 2 — 상태를 여러 재료로 겹쳐 봅니다

`worktree ps`의 `preview`가 몇 분 전과 같은지 봅니다. `terminal list`의 `lastOutputAt`을 현재 시각과 비교해 조용한 시간을 계산합니다. `preview`에 질문 문구가 있으면 멈춘 것이 아니라 사람 입력을 기다리는 것입니다. 자원 쪽이 의심되면 메모리 진단으로 그 세션이 실제로 무엇을 쓰고 있는지 봅니다. 어느 하나로 단정하지 않고 겹쳐 보는 것이 요령입니다.

### 정답 3 — 초기화의 범위가 조회의 범위와 다릅니다

조회는 Run 단위로 나뉘어 있어 자기 작업만 보입니다. 반면 `reset --all` 은 로컬 오케스트레이션 데이터베이스 전체를 지워서 화면에 보이지 않는 다른 Run 의 상태까지 사라집니다. 정리는 태스크를 하나씩 완료로 바꾸는 것으로 합니다. 끝나지 않은 태스크를 완료로 위조하면 후속 태스크가 전제 없이 열립니다.
