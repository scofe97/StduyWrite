# ADE란 무엇인가 — IDE에서 ADE까지
---
> ADE는 Agentic Development Environment의 줄임말입니다. IDE에 AI를 얹은 물건처럼 들리지만 출발점이 다릅니다. 에이전트를 하나 쓸 때는 없던 문제가 둘로 늘리는 순간 세 가지 생기는데, ADE는 그 셋에 하나씩 대응하려고 만들어진 도구 범주입니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. IDE·AI 코딩 도구·ADE가 무엇을 중심에 두는 도구인지 한 문장씩으로 구분할 수 있습니다.
2. 에이전트를 둘 이상 돌릴 때 무너지는 세 가지를 대고, 각각이 왜 터미널 탭을 늘려서는 해결되지 않는지 설명할 수 있습니다.
3. 격리·관측·조율이 각각 어떤 실패에 대응하는 개념인지 짝지을 수 있습니다.
4. ADE에서 CLI가 왜 선택 사항이 아닌지, 그 판단이 도구 설계에 어떻게 드러나는지 근거를 들어 말할 수 있습니다.

ORCA의 설치와 개별 명령 사용법은 다루지 않습니다. 그쪽은 [부록 06-01](06-01.부록 — macOS 실측 환경과 설치 경로.md)과 [부록 06-02](06-02.부록 — orca CLI 명령 지도 v1.4.188.md)에 있습니다. 이 편은 "왜 이런 모양의 도구가 생겼는가"만 봅니다.



## 1. 도구의 중심이 세 번 옮겨갔습니다

> 편집기에서 대화로, 대화에서 작업 관리로 무게가 옮겨갔습니다. 셋 다 편집기를 갖고 있지만 화면의 가장 좋은 자리를 무엇에 내주는지가 다릅니다.

![편집기·대화·작업 관리로 옮겨간 도구의 무게중심](_assets/01-01-tool-generations.svg)

IDE의 중심은 편집기였습니다. 자동 완성, 리팩터링, 디버거는 모두 사람이 코드를 더 잘 쓰게 만드는 기능입니다. 사람이 코드를 쓰고 도구는 그 쓰기를 편하게 돕습니다.

AI 코딩 도구의 중심은 대화입니다. 사람이 요청하고 모델이 코드를 내놓습니다. 이때도 일하는 주체는 하나이고, 사람은 그 하나를 옆에서 지켜봅니다. Copilot과 Cursor, Claude Code가 모두 이 자리에 있습니다.

ADE의 중심은 작업 관리입니다. 편집기도 대화창도 여전히 있지만 주인공이 아닙니다. 화면에서 가장 좋은 자리를 차지하는 것은 "지금 몇 개의 일이 어떤 상태로 돌아가고 있는가"입니다. ORCA의 왼쪽 사이드바가 파일 트리가 아니라 작업 현황판인 이유가 여기 있습니다.

이 구분은 기능 목록으로는 잘 드러나지 않습니다. 셋 다 파일을 열고 고칠 수 있기 때문입니다. 구분이 드러나는 곳은 화면 배치와 기본 단위입니다.

- IDE의 기본 단위는 **파일**입니다.
- AI 코딩 도구의 기본 단위는 **대화**입니다.
- ADE의 기본 단위는 **작업**입니다.



## 2. 에이전트가 둘이 되는 순간 세 가지가 무너집니다

> 하나일 때는 아무 문제가 없습니다. 둘로 늘리면 작업 공간·상태·순서가 동시에 무너지고, 셋 다 터미널 탭을 더 여는 것으로는 풀리지 않습니다.

<!-- no-diagram: 세 실패가 서로 인과나 순서로 이어지지 않고 병렬로 나열되는 절이라 그릴 형태가 없습니다. 셋이 무엇에 대응되는지는 3절 도식이 보입니다. -->

코딩 에이전트를 하나만 쓸 때는 문제가 없습니다. 폴더 하나에서 에이전트 하나가 일하고, 사람이 그 화면을 보고 있으니까요.

**작업 공간이 충돌합니다.** 같은 폴더에서 에이전트 둘이 같은 파일을 고치면 결과가 뒤섞입니다. A가 고친 줄을 B가 다시 고치고, A는 자기가 방금 쓴 내용이 사라진 것을 모릅니다. 테스트를 돌려도 누구의 코드가 실패했는지 알 수 없습니다. 터미널 탭을 두 개 여는 것으로는 해결되지 않습니다. 탭이 달라도 파일은 하나이기 때문입니다.

**상태가 보이지 않습니다.** 에이전트는 몇 분씩 조용히 일합니다. 터미널 탭이 다섯 개면 다섯 개를 번갈아 눌러 봐야 하고, 그중 하나가 20분 전에 사람에게 뭔가 물어보고 멈춰 있어도 다른 탭을 보고 있었다면 모릅니다. 무엇이 돌고 있고 무엇이 끝났고 무엇이 막혀 있는지를 한눈에 보는 화면이 없다는 문제입니다.

**순서를 강제할 수 없습니다.** 구현 다음에 리뷰가 돌아야 하고 그 결과에 따라 사람이 승인해야 하는 작업이 있습니다. 이걸 사람이 손으로 이어 붙이면 사람이 자리를 비우는 동안 파이프라인 전체가 멈춥니다. "A 다음에 B를 시작하고 C 지점에서는 사람에게 물어라"를 도구가 알아야 하는 문제입니다.

셋을 묶는 공통점이 있습니다. 전부 **일이 여러 개일 때만 생기는 문제**이고, 편집기를 아무리 좋게 만들어도 줄어들지 않습니다. IDE의 개선 축과 방향이 다릅니다.



## 3. 격리·관측·조율 — 무너진 셋에 하나씩 대응합니다

> 세 실패에 세 개념이 하나씩 붙습니다. ORCA에서 이 셋은 각각 git 워크트리, 터미널 읽기와 상태 훅, 태스크 의존 관계로 구현됩니다.

![세 실패에 격리·관측·조율이 하나씩 대응하는 매핑](_assets/01-01-three-axes.svg)

**격리**는 작업 공간 충돌에 대응합니다. 새 작업을 시작하면 ORCA는 원본 폴더를 건드리지 않고 별도 폴더에 작업 공간을 만듭니다. git의 워크트리 기능을 그대로 쓰기 때문에 폴더가 다르고 브랜치도 다릅니다.

이 격리가 파일 충돌만 막는다는 점은 짚어 둘 필요가 있습니다. 포트나 데이터베이스처럼 공용으로 쓰는 자원은 여전히 겹치고, 보안 경계도 아닙니다. 워크트리는 실수를 되돌리기 쉽게 만드는 장치이지 신뢰할 수 없는 코드를 가두는 상자가 아닙니다.

**관측**은 상태가 안 보이는 문제에 대응합니다. 각 작업 공간에 터미널이 붙고 ORCA가 그 출력을 읽어 상태를 표시합니다. 여기에 더해 에이전트의 설정 파일에 상태 보고용 훅을 심어, 무슨 말을 했고 몇 분째 돌고 있는지까지 목록에 띄웁니다.

훅을 심는다는 것은 ORCA가 여러분의 `~/.claude/settings.json` 같은 파일에 손을 댄다는 뜻입니다. 불편하면 끌 수 있고, 끄면 진행 표시가 빈약해지는 대신 나머지 기능은 그대로 동작합니다.

**조율**은 순서 문제에 대응합니다. 작업을 태스크로 등록하고 의존 관계를 걸어 두면 지금 시작할 수 있는 일만 골라 줍니다. 사람 판단이 필요한 지점에는 결정 게이트를 세워 파이프라인을 멈춰 둘 수 있습니다.

세 축의 비중은 같지 않습니다. 격리는 에이전트를 하나만 써도 값을 하고, 관측은 둘부터, 조율은 셋 이상에서 값을 합니다. 그래서 ORCA를 처음 붙일 때는 격리만 써도 손해가 아닙니다.



## 4. CLI가 부가 기능이 아니라 유일한 통로입니다

> 에이전트는 마우스를 쓰지 않습니다. 그래서 ADE에서 CLI는 고급 사용자용 편의가 아니라 에이전트가 도구를 조작하는 단 하나의 경로입니다.

![사람과 에이전트가 같은 CLI를 통해 런타임에 닿는 경로](_assets/01-01-cli-path.svg)

ORCA의 명령은 200개를 넘습니다. 이 노트를 쓰며 확인한 설치본은 **232개**였습니다.[^cmdcount] 원서 기준인 v1.4.176에서는 223개, 그 앞 v1.4.154에서는 206개였으니 버전마다 늘고 있습니다.

명령이 이렇게 많은 이유를 "기능이 많아서"로만 읽으면 절반만 맞습니다. 나머지 절반은 **에이전트에게 시키려면 명령이어야 하기 때문**입니다. 클릭 순서는 에이전트에게 넘길 수 없습니다.

이 판단이 가장 잘 드러나는 명령이 `orca agent-context --json`입니다. 자기 명령 사용법 전체를 기계가 읽을 형태로 뱉어 내는 명령이고, 사람이 읽으라고 만든 것이 아닙니다. 에이전트에게 "이걸 읽고 ORCA를 조작해"라고 넘기기 위한 출력입니다.

```bash
orca agent-context --json | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['commandCount'])"
# 232
```

여기서 따라오는 결론이 하나 있습니다. ORCA에서 CLI를 익히는 것은 자신이 쓰기 위해서이기도 하지만, 에이전트에게 시킬 수 있게 되기 위해서이기도 합니다. 뒤로 갈수록 후자의 비중이 커집니다.

같은 설계가 문서에도 적용돼 있습니다. `orca skills list`는 설치된 버전과 짝이 맞는 가이드 문서를 돌려줍니다. 실측한 v1.4.188에는 8종이 들어 있었습니다.

```bash
orca skills list
# orca-cli · orchestration · computer-use · orca-emulator
# orca-emulator-android · orca-linear · linear-tickets · orca-per-workspace-env
```

웹 문서를 찾아 헤매다 버전이 어긋나는 사고를 구조적으로 막는 배치입니다.



## 5. ADE가 아닌 것 세 가지

> 이름 때문에 생기는 오해를 먼저 걷어 냅니다. ADE는 IDE의 대체재도 아니고 AI 모델도 아니며, 에이전트를 하나만 쓴다면 없어도 됩니다.

<!-- no-diagram: 서로 관계가 없는 세 가지 부정을 나열하는 절이라 도식으로 만들 형태가 없습니다. -->

**IDE를 대체하지 않습니다.** ORCA에도 파일 탐색기와 편집기가 있지만, 대규모 리팩터링이나 단계 디버깅은 여전히 기존 IDE가 낫습니다. ORCA의 파일 보기는 에이전트가 무엇을 고쳤는지 확인하는 용도에 가깝습니다.

**AI 모델이 아닙니다.** ORCA는 모델을 품고 있지 않고 API 키를 받는 절차도 없습니다. 여러분이 이미 쓰는 에이전트를 터미널에 띄워 주는 것이 전부라, 명령줄에서 안 되는 것은 ORCA에서도 안 됩니다. 뒤집으면 에이전트를 바꿔도 ORCA 사용법은 바뀌지 않습니다.

**에이전트 하나만 쓴다면 필요하지 않을 수 있습니다.** ORCA의 가치는 병렬성과 자동화에서 나옵니다. 다만 하나만 쓸 때도 워크트리 격리와 예약 실행은 그 자체로 쓸모가 있어서, 도입 판단이 전부 아니면 전무는 아닙니다.



## 6. 이 노트가 무엇을 확인했는가

> 원서는 페이지마다 실측인지 문서 대조인지를 배지로 밝힙니다. 이 노트는 거기에 한 층을 더해, 원서 서술 중 무엇을 우리 설치본에서 다시 확인했는지까지 나눕니다.

<!-- no-diagram: 근거 등급의 정의와 대응 관계는 표로 읽는 편이 정확하고, 그릴 만한 흐름이나 계층이 없습니다. -->

원서는 「ORCA 따라하기」(이창근)이고 Claude Code로 집필했다고 밝히고 있습니다. 그래서 페이지마다 `[검증]`과 `[참고]` 배지로 직접 실행한 것과 문서만 대조한 것을 나눠 두었습니다. 수집한 59페이지 중 `[검증]`이 46건, `[참고]`가 9건이었습니다.

기술서에서 가장 위험한 것은 문서를 읽고 정리한 내용을 직접 해 본 내용처럼 쓰는 일입니다. 원서가 그 선을 그어 둔 만큼, 이 노트도 같은 선을 유지하되 한 칸을 더 나눕니다.

| 등급 | 뜻 | 이 노트의 표기 |
|------|-----|--------------|
| 실행 | 이 맥북 설치본(v1.4.188)에서 직접 실행해 확인 | 출력·오류 메시지를 그대로 인용 |
| 스키마 | `orca agent-context --json` 으로 존재와 플래그만 대조 | "스키마 기준" 명시 |
| 원서 | 원서 서술만 있고 이쪽에서 확인하지 못함 | "원서 기준·미실측" 명시 |

세 번째 등급이 필요한 이유는 실측 환경이 다르기 때문입니다. 원서는 Windows 11에서 썼고 이 노트는 macOS arm64에서 확인했습니다. 원서가 macOS 전용이라 못 했다고 밝힌 iOS 시뮬레이터는 이쪽에서 확인할 수 있고, 반대로 Windows 전용 경로는 이쪽에서 확인할 수 없습니다.

버전도 다릅니다. 원서 대부분이 v1.4.176 기준이고 설치본은 v1.4.188입니다. 열두 버전 차이지만 명령이 223개에서 232개로 늘었고, 뒤 편들에서 보겠지만 동작이 바뀐 곳도 있습니다. 그래서 이 노트는 원서와 갈리는 지점을 감추지 않고 그때마다 적습니다.



## 면접에서 받을 만한 질문

1. AI 코딩 도구를 이미 쓰고 있는데 ADE가 따로 필요한 이유가 무엇입니까? 터미널 탭을 여러 개 여는 것과 무엇이 다릅니까?
2. ORCA의 워크트리 격리를 "샌드박스"라고 설명해도 됩니까?
3. ORCA의 CLI 명령이 200개가 넘는 것을 두고 "기능이 과하다"고 볼 수 있습니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 탭은 화면을 나눌 뿐 파일을 나누지 않습니다

에이전트를 둘로 늘리면 작업 공간·상태·순서 세 가지가 동시에 무너집니다. 터미널 탭을 늘리는 것은 셋 중 어느 것도 풀지 못합니다. 탭이 달라도 파일은 하나라 충돌은 그대로입니다. 탭이 늘수록 상태를 보려면 더 많이 눌러 봐야 합니다. 탭 사이에 순서를 강제할 장치도 없습니다. ADE는 이 셋에 각각 격리·관측·조율로 대응합니다.

### 정답 2 — 파일 충돌만 막고 보안 경계는 아닙니다

워크트리는 폴더와 브랜치를 나눠 에이전트끼리 같은 파일을 덮어쓰지 못하게 합니다. 그러나 포트나 데이터베이스 같은 공용 자원은 여전히 겹치고, 프로세스나 파일시스템 권한을 가두지 않습니다. 실패해도 원본이 안전하다는 뜻이지 신뢰할 수 없는 코드를 안전하게 돌린다는 뜻이 아닙니다.

### 정답 3 — 명령 수는 자동화 가능 범위의 다른 이름입니다

에이전트는 마우스를 쓰지 않으므로, 도구에서 명령으로 노출되지 않은 기능은 에이전트가 쓸 수 없습니다. ADE에서 CLI 표면적은 곧 위임 가능한 작업의 범위입니다. `orca agent-context --json`이 명령 스키마 전체를 기계가 읽을 형태로 뱉는다는 사실이 그 의도를 드러냅니다. 다만 사람이 다 외울 필요는 없고, 영역별 묶음만 알면 됩니다.
