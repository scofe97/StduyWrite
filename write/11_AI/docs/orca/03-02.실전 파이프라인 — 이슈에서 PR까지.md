# 실전 파이프라인 — 이슈에서 PR까지
---
> 앞 편의 모델을 실제 파이프라인으로 세웁니다. 구현과 리뷰를 다른 세션에 맡기는 이유, 워크트리를 몇 개로 할지 정하는 기준, 그리고 게이트 이후에 빼먹기 쉬운 한 단계를 다룹니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 구현과 리뷰를 분리하는 이유를 설명하고, 그 구성에서 워크트리를 몇 개로 할지 기준을 들어 정할 수 있습니다.
2. `dispatch --inject`가 워커에게 무엇을 넣어 주는지 알고, 그것이 왜 완료 판정 문제를 없애는지 말할 수 있습니다.
3. 게이트를 해결한 뒤에 남은 단계를 빠짐없이 세고, 한 단계를 빼면 무엇이 무너지는지 설명할 수 있습니다.
4. 조회와 소비를 갈라 쓰는 습관의 이유를 자기 버전에서 확인하고 적용할 수 있습니다.

파이프라인을 예약 실행으로 옮기는 일은 [04-02](04-02.화면 밖 자동화 — 컴퓨터 유즈·에뮬레이터·예약 실행.md)에서 다룹니다.



## 1. 구현과 리뷰를 왜 나누는가

> 같은 에이전트에게 구현하고 스스로 리뷰하라고 하면 자기 코드를 관대하게 봅니다. 별도 세션은 결과만 보고 판단합니다.

![한 세션이 자기 코드를 리뷰할 때와 별도 세션이 결과만 볼 때의 차이](_assets/03-02-why-split.svg)

원서가 이 판단을 한 문장으로 적어 두었습니다. 같은 세션은 자기가 왜 그렇게 짰는지를 알고 있어서 그 이유가 리뷰의 편에 섭니다. 별도 세션의 에이전트는 그 맥락이 없으니 결과만 봅니다.

사람 팀에서 작성자와 리뷰어를 나누는 것과 같은 이유이고, 에이전트에서는 비용이 훨씬 쌉니다. 세션을 하나 더 띄우는 것이 전부입니다.

여기서 따라오는 결정이 워크트리 개수입니다. 기준은 **에이전트 수가 아니라 쓰는 에이전트 수**입니다.

| 구성 | 언제 | 근거 |
|------|------|------|
| 워크트리 1개 + 터미널 여럿 | 쓰는 워커가 하나뿐일 때 | 리뷰어가 구현 결과를 그대로 봅니다 |
| 워크트리 여럿 | 쓰는 워커가 둘 이상일 때 | 같은 파일을 동시에 고치면 결과가 뒤섞입니다 |

구현·리뷰 2단은 첫 번째에 해당합니다. 구현만 쓰고 리뷰는 읽으므로 한 워크트리를 공유해도 충돌하지 않습니다.

여기에 프롬프트로 걸어야 하는 조건이 하나 있습니다. **리뷰어에게 "고치지 말라"고 명시해야 합니다.** 리뷰어가 친절하게 고치기 시작하면 쓰는 워커가 둘이 되어 전제가 깨집니다. 원서가 관찰 포인트에서 이것을 핵심으로 꼽았습니다.

문서화 워커를 붙일 때도 같은 계산이 필요합니다. 문서 워커는 읽기 전용이 아니라 파일을 씁니다. 같은 워크트리에 둘 거면 수정 범위를 `docs/` 아래로 못박아 구현 워커와 겹치지 않게 해야 합니다.



## 2. 순서는 사람이 아니라 데이터가 강제합니다

> `--deps`를 걸어 두면 리뷰가 `pending`으로 잠깁니다. 아직 시키면 안 된다는 것을 사람이 기억할 필요가 없습니다.

![구현·리뷰 2단 파이프라인의 태스크 상태 전이](_assets/03-02-two-stage.svg)

구성은 단순합니다. 구현 워커와 함께 워크트리를 만들고, 리뷰 워커와 코디네이터 자리를 같은 워크트리에 추가합니다.

```bash
orca worktree create --repo id:<repoId> --name pipeline-task --agent claude --json
orca terminal create --worktree "path:<경로>" --title "REVIEWER" --command "claude" --json
orca terminal create --worktree "path:<경로>" --title "COORD" --json
```

`COORD`에는 에이전트를 띄우지 않습니다. 오케스트레이션 명령의 `--from`에 넘길 주소가 필요할 뿐이기 때문입니다. **코디네이터를 사람이 맡을 때의 요령**입니다.

`--title`을 반드시 줍니다. 핸들만으로는 목록에서 누가 누구인지 구분되지 않습니다.

그다음 Run을 만들고 태스크 둘을 정의합니다. 리뷰는 구현에 의존하게 겁니다.

```bash
orca orchestration run-create --objective "factorial 구현과 리뷰" --from <코디핸들> --json
orca orchestration task-create --task-title "구현" --spec "..." --from <코디핸들> --json
orca orchestration task-create --task-title "리뷰" --spec "..." \
  --deps '["<구현task>"]' --from <코디핸들> --json
```

리뷰 프롬프트에는 장치 셋을 넣습니다.

- "코드를 수정하지 말라" — 쓰는 워커가 둘이 되는 것을 막습니다.
- "발견한 문제를 `REVIEW.md` 에 정리하라" — 완료 판정과 결과 회수를 겸합니다.
- "사람이 판단해야 할 사항은 별도로 표시하라" — 게이트의 재료가 됩니다.

이 셋이 앞 편에서 본 지시의 네 덩어리 중 경계와 진행 규칙에 해당합니다. 파이프라인 설계가 곧 프롬프트 설계라는 것이 여기서 드러납니다.



## 3. `--inject`가 보고 규약을 대신 넣어 줍니다

> 워커가 완료를 어떻게 알릴지는 지시에 적지 않습니다. 배분할 때 ORCA가 핸들과 태스크 id가 채워진 규약 블록을 통째로 주입합니다.

![dispatch 가 워커 프롬프트 앞에 붙이는 규약 블록의 구성](_assets/03-02-preamble.svg)

배분 전에 무엇이 들어갈지 먼저 볼 수 있습니다.

```bash
orca orchestration dispatch --task <task_id> --to <워커핸들> --from <코디핸들> \
  --dry-run --return-preamble --json
```

실측한 v1.4.188의 `preamble`은 **4,648자**였습니다.[^preamble] 그 안에 들어 있는 것을 보면 이 기능의 성격이 드러납니다.

- 코디네이터 핸들과 자기 태스크 id가 값으로 채워진 상태로 들어옵니다.
- `worker_done`을 **정확히 한 번** 보내되 `--outcome succeeded|failed`를 반드시 붙이라고 못박습니다. 실패를 산문으로만 남기거나 조용히 끝내지 말라고 적혀 있습니다.
- `--body`는 세 문장 요약이어야 합니다. 코디네이터가 본문을 먼저 읽고 필요할 때만 산출물을 연다는 이유까지 적혀 있습니다.
- 작업 중에는 5분마다 `heartbeat`를 보내라고 합니다. 코디네이터가 "생각 중"과 "멈춤"을 구분하는 근거입니다.
- `taskId`와 `dispatchId`를 **둘 다** 실으라고 합니다. 실패한 재시도에서 뒤늦게 온 보고가 현재 배분을 완료 처리하지 못하게 막는 장치입니다.
- 사람에게 물을 때는 에이전트 자체의 질문 UI를 쓰지 말고 `orchestration ask`를 쓰라고 금지 규칙으로 적어 둡니다. 로컬 TUI 프롬프트는 코디네이터가 볼 수도 답할 수도 없어 세션이 영원히 멈추기 때문입니다.
- `worker_done` 이후에는 대기 상태로 돌아가 폴링 루프를 돌리지 말라고 합니다. 대신 터미널은 닫지 말라고 하는데, 코디네이터가 새 배분으로 다시 부를 수 있기 때문입니다.

이 목록을 읽고 나면 원서 05-5의 서술 하나가 앞뒤로 어긋나 보입니다.

> **원문 정오**: 05-5 본문은 "`spec`에 완료 보고 명령을 적지 않는 것이 요령"이라고 하면서 태스크 id가 아직 없어 순환에 걸린다고 설명합니다. 그런데 같은 페이지의 관찰 포인트 6은 "spec에 완료 보고 명령을 적어 준 것이 핵심이었습니다"라고 반대로 적었습니다. 실측한 `preamble`을 보면 본문 쪽이 맞습니다. 보고 규약은 `--inject`가 넣습니다.

앞 편에서 완료 판정에 애를 먹은 것과 대비됩니다. 거기서는 `tui-idle`을 폴링하며 결과물을 확인해야 했는데, 여기서는 워커가 직접 알립니다.

```bash
orca orchestration check --terminal <코디핸들> --wait \
  --types worker_done,escalation --timeout-ms 900000 --json
```

**오케스트레이션을 배우는 가장 실용적인 이유가 이것입니다.** 완료 판정이 추측에서 수신으로 바뀝니다.

받은 메시지는 `subject`로 성공과 실패를 가릅니다. 제목이 `Failed:`로 시작하면 실패 보고이므로 태스크를 완료로 닫으면 안 됩니다. 워커가 여럿이면 `worker_done`도 여럿 오는데 순서가 보낸 순서와 같다는 보장이 없으니, `task_id`를 보고 해당 태스크만 닫습니다.



## 4. 게이트 이후에 빼먹기 쉬운 단계

> 승인을 보내는 것은 새 작업을 시작시킨 것이지 끝낸 것이 아닙니다. 여기서 멈추면 승인 도장만 찍은 셈이 됩니다.

![게이트 해결부터 커밋까지 남은 여섯 단계](_assets/03-02-after-gate.svg)

리뷰어가 사람 판단이 필요하다고 표시한 항목을 게이트로 올립니다.

```bash
orca orchestration gate-create --task <리뷰task> \
  --question "factorial 을 재귀로 구현했습니다. 큰 입력에서 스택 초과 위험이 있는데 어떻게 할까요?" \
  --options '["반복문으로 변경","입력 상한 추가","현재 유지"]' --from <코디핸들> --json

orca orchestration gate-list --status pending --from <코디핸들> --json
orca orchestration gate-resolve --id <gate_id> --resolution "입력 상한 추가" --from <코디핸들> --json
```

게이트를 만들면 그 태스크가 `blocked`가 되고 해결하면 `ready`로 돌아옵니다. **그 태스크만 멈춥니다.** 사람의 판단이 파이프라인 전체를 정지시키지 않도록 설계된 것입니다.

여기서 원서가 두 페이지에 걸쳐 강조하는 지점이 나옵니다. 결정을 구현 워커에게 전달한 뒤에 해야 할 일이 넷 더 남았습니다.

1. 두 번째 `worker_done`을 기다립니다. 추가 지시는 새 작업을 시작시킨 것입니다.
2. 테스트를 직접 확인합니다.
3. **리뷰를 다시 돌립니다.** 리뷰어는 처음 결과만 봤고 추가 변경분은 아직 못 봤습니다.
4. 리뷰 완료를 받고 나서 커밋합니다.

한 단계라도 빼면 게이트를 둔 의미가 없어집니다. 사람이 판단하려고 멈춘 것인데 판단 이후의 결과를 아무도 확인하지 않으면 검증 고리가 끊깁니다.

워커 터미널을 재사용할 수 있다는 점이 이 흐름을 쉽게 만듭니다. `worker_done` 이후에도 셸을 종료하지 않는 것이 규약이라, 같은 터미널에 추가 지시를 넣으면 됩니다.



## 5. 조회와 소비를 가릅니다

> 구경하려고 부른 명령이 대기 중인 쪽의 메시지를 먹을 수 있습니다. 다만 어느 명령이 먹는지는 버전에 따라 다릅니다.

<!-- no-diagram: 앞 편의 delivery·ack 도식이 같은 메커니즘을 이미 보이고, 이 절은 그것을 파이프라인 상황에 적용하는 주의사항이라 새로 그릴 형태가 없습니다. -->

기다리는 동안 진행 상황을 보고 싶을 때가 있습니다. 원서는 이때 `inbox`를 쓰고 `check`를 쓰지 말라고 강하게 권합니다. `check`의 기본이 읽음 처리라 대기 중인 `check --wait`이 그 메시지를 못 받기 때문입니다.

```bash
orca orchestration inbox --limit 10 --json
orca worktree ps --limit 5
```

앞 편에서 확인했듯 **v1.4.188에서는 이 위험이 사라졌습니다.** `check`가 배치를 재전달만 하고 `--ack`를 줘야 소비됩니다. 그래도 습관은 그대로 두는 편이 낫습니다. 조회용 명령과 소비용 명령을 가르는 것은 버전과 무관하게 옳고, 팀이 여러 버전을 섞어 쓰는 상황에서 특히 그렇습니다.

`worktree ps`를 함께 보는 것이 실전에서 유용합니다. 오케스트레이션 상태는 태스크가 어디까지 갔는지를 알려 주고, `worktree ps`의 `preview`는 각 워커의 마지막 출력 줄을 보여 줍니다. **둘이 어긋나면 그 자리가 문제입니다.**

정리는 태스크를 하나씩 완료로 바꾸는 것으로 합니다. `orchestration reset --all`은 조회 범위와 달리 로컬 데이터베이스 전체를 지우므로 쓰지 않습니다.



## 6. 이 구성을 어디까지 늘릴 수 있는가

> 읽는 워커는 싸고 쓰는 워커는 비쌉니다. 늘릴 때는 그 축으로 셉니다.

![읽는 워커와 쓰는 워커를 늘릴 때 드는 비용의 차이](_assets/03-02-scaling.svg)

가장 실용적인 확장은 **관점별 리뷰어**입니다. 보안·성능·가독성 워커 셋을 병렬로 붙여도 전부 읽기 작업이라 워크트리를 공유할 수 있습니다. 사람 리뷰어를 여럿 부르는 것보다 훨씬 쌉니다.

테스트 워커를 하나 더 붙이는 것도 같습니다. 구현에 의존하는 태스크를 하나 더 만들어 리뷰와 병렬로 두면 됩니다.

반대로 쓰는 워커를 늘리면 워크트리를 나누고 병합 절차를 설계해야 합니다. 여기서부터 비용이 급해집니다.

**자동 상한이 없다는 점을 기억해야 합니다.** 워커 하나가 워크트리 하나와 에이전트 세션 하나를 쓰고, 원서 실측에서는 세션 하나가 446MB를 썼습니다. 태스크 스무 개에 워커를 한꺼번에 붙이면 메모리와 모델 사용량이 함께 폭발합니다.

확인은 두 명령으로 합니다.

```bash
orca orchestration worker-list --json
orca diagnostics memory --json
```

앞엣것으로 워커 수를, 뒤엣것으로 실제 메모리를 봅니다. 자동 안전장치가 사라진 자리를 이 확인이 대신합니다. 둘셋으로 시작해 여유를 보고 올리는 편이 안전합니다.



## 면접에서 받을 만한 질문

1. 구현 워커와 리뷰 워커를 같은 워크트리에 두어도 됩니까?
2. 워커에게 "끝나면 이렇게 보고하라"는 지시를 태스크 명세에 적어야 합니까?
3. 게이트를 해결하고 구현 워커에게 결정을 전달했습니다. 이제 커밋해도 됩니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 쓰는 워커가 하나뿐이면 됩니다

기준은 에이전트 수가 아니라 쓰는 에이전트 수입니다. 구현만 파일을 고치고 리뷰는 읽기만 한다면 한 워크트리를 공유해도 충돌하지 않고, 오히려 리뷰어가 구현 결과를 그대로 볼 수 있어 유리합니다. 다만 리뷰 프롬프트에 "코드를 수정하지 말라"를 명시해야 합니다. 리뷰어가 고치기 시작하면 쓰는 워커가 둘이 되어 전제가 깨집니다.

### 정답 2 — 적지 않습니다. 배분이 넣어 줍니다

보고 명령에는 태스크 id가 들어가야 하는데 그 id는 태스크를 만들어야 나옵니다. 명세에 적으려면 아직 없는 값을 적어야 하는 순환에 걸립니다. `dispatch --inject`가 핸들과 태스크 id가 채워진 규약 블록을 워커 프롬프트 앞에 붙여 줍니다. 무엇이 들어갈지는 `--dry-run --return-preamble`로 미리 볼 수 있습니다.

### 정답 3 — 네 단계가 남았습니다

결정을 전달한 것은 새 작업을 시작시킨 것입니다. 네 단계가 남습니다.

1. 두 번째 `worker_done` 을 기다립니다.
2. 테스트를 직접 확인합니다.
3. 리뷰를 다시 돌려 추가 변경분을 검토받습니다.
4. 그 완료를 받은 뒤에 커밋합니다.

여기서 멈추면 사람이 판단하려고 세운 게이트가 승인 도장으로만 남습니다.
