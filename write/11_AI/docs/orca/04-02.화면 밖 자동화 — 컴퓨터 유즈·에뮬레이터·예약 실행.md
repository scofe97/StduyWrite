# 화면 밖 자동화 — 컴퓨터 유즈·에뮬레이터·예약 실행
---
> 브라우저 밖에도 확인해야 할 화면이 있고, 사람이 시켜야만 도는 것도 아닙니다. 데스크톱 앱과 모바일 화면을 읽는 방법, 그리고 에이전트가 스스로 시작하는 예약 실행을 다룹니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 컴퓨터 유즈와 브라우저 자동화 중 어느 것을 쓸지 대상으로 가를 수 있습니다.
2. 플랫폼별 지원 범위를 먼저 조회하는 습관을 들이고, 승인 상태가 어떻게 표시되는지 읽을 수 있습니다.
3. 자동화 응답의 필드를 읽어 그 자동화가 언제 어떻게 돌지 예측할 수 있습니다.
4. 자동화에 맡겨도 되는 작업과 맡기면 안 되는 작업을 하나의 기준으로 가를 수 있습니다.

원격 런타임과 권한 경계 전반은 [05-01](05-01.운영과 권한 경계 — 환경 레시피·원격 런타임·보안.md)에서 다룹니다.



## 1. 브라우저로 닿을 수 없는 곳을 위한 도구

> 원리는 브라우저와 같습니다. 접근성 트리를 읽고 번호로 조작합니다. 다만 웹 페이지라면 브라우저 명령이 항상 낫습니다.

![대상에 따라 브라우저 명령과 컴퓨터 유즈를 가르는 기준](_assets/04-02-which-tool.svg)

컴퓨터 유즈는 데스크톱 앱을 읽고 조작하는 기능입니다. 화면을 이미지로 보고 좌표를 찍는 방식이 아니라 OS가 주는 UI 구조 정보를 씁니다. 앞 편의 스냅샷과 같은 발상입니다.

가르는 기준은 **대상이 무엇인가**입니다. ORCA 내장 브라우저의 웹 페이지라면 브라우저 명령을 씁니다. 스냅샷이 짧고 조작이 정확하며 네트워크와 콘솔까지 볼 수 있습니다. 일반 데스크톱 앱, 외부 브라우저 창, ORCA 앱 자신의 UI는 컴퓨터 유즈입니다.

솔직하게 말하면 컴퓨터 유즈는 활용도가 낮습니다. 그래도 쓸모가 분명한 자리가 있습니다. 데스크톱 앱을 만들고 있을 때, 특정 창이 떠 있는지 같은 앱 상태를 읽어 판단해야 할 때, 웹으로 대체할 수 없는 GUI 단계가 자동화에 끼어 있을 때입니다.

응답 크기에 주의할 점이 하나 있습니다. `get-app-state`는 스크린샷을 base64로 함께 싣습니다. 원서 실측에서 200KB였던 응답이 `--no-screenshot`을 붙이니 9KB로 줄었습니다. **트리만 필요하면 반드시 붙입니다.** 에이전트에게 넘길 때 스무 배 차이입니다.



## 2. 지원 범위를 먼저 조회합니다

> 플랫폼마다 되는 것이 다릅니다. 설계하기 전에 무엇이 지원되는지부터 봅니다.

![플랫폼별 지원 범위와 승인 상태 표시의 차이](_assets/04-02-capabilities.svg)

```bash
orca computer capabilities --json
```

이 맥북에서 확인한 결과는 `platform: darwin`이었고, 동작(클릭·타이핑·키·단축키·붙여넣기·스크롤·드래그·값 설정·접근성 액션) 아홉 가지가 모두 지원됐습니다. 반면 **창 포커스 이동과 메뉴·다이얼로그·독·메뉴바 접근은 지원되지 않았습니다.**

여기서 원서 서술을 하나 보완할 수 있습니다. 원서는 이 제약을 Windows 프로바이더의 한계로 설명했는데, **darwin에서도 같은 값이었습니다.** 플랫폼 한정 제약이 아닙니다. 파일 메뉴를 열어 항목을 고르는 자동화는 어느 쪽에서도 어렵습니다.

승인 상태는 플랫폼에 따라 다르게 표시됩니다. 원서는 macOS 쪽을 미실측으로 남겼는데, 그 자리가 이렇게 채워집니다.[^perm]

```bash
orca computer permissions --json
# platform: "darwin"
# helperAppPath: "/Applications/Orca.app/Contents/Resources/Orca Computer Use.app"
# permissions: [{accessibility: "not-granted"}, {screenshots: "not-granted"}]
# nextStep: "Grant Accessibility to Orca Computer Use, then retry get-app-state."
```

Windows의 `unsupported`와 `nextStep: null`은 "승인할 항목 자체가 없다"는 뜻이었습니다. macOS의 `not-granted`와 실행 가능한 `nextStep`은 "아직 승인하지 않았다"는 뜻입니다. **같은 필드를 다른 의미로 읽어야 합니다.**

승인 주체가 ORCA 본체가 아니라 **별도 헬퍼 앱**이라는 점도 눈에 띕니다. 시스템 설정에서 찾을 이름이 다릅니다.

승인 전 상태에서 화면을 읽어 보면 조용히 틀린 답을 주지 않고 명확히 거부합니다.

```bash
orca computer get-app-state --app "Orca" --no-screenshot --json
# "code": "permission_denied"
# "message": "Accessibility permission is required for Orca Computer Use. ..."
```

반면 `list-apps`는 승인 없이도 동작했습니다. 앱 열거와 화면 읽기의 권한 경계가 다릅니다.

원서가 Windows에서 두 번 재현했다는 함정도 확인해 봤습니다. 이름으로 앱을 지정했더니 창 제목에 "orca"가 든 다른 편집기가 잡혔다는 사례입니다. **이 맥북에서는 재현되지 않았고** 정확한 번들 id로 해석됐습니다. 시도 한 번이라 macOS가 안전하다고 일반화하지는 않겠습니다. 세 단계로 좁히는 것이 여전히 정석입니다.

```bash
orca computer list-apps --json                                    # pid 확인
orca computer list-windows --app pid:<PID> --json                 # 창 id 확인
orca computer get-app-state --app pid:<PID> --window-id <창id> --no-screenshot --json
```

**출력에 실려 나오는 것을 조심해야 합니다.** 실측 중 앱 목록에 개인·사내 앱 이름이 그대로 나왔습니다. 창 제목에는 열어 둔 파일명이 들어 있었습니다. 이 노트에 옮기지 않은 이유이며, 버그 리포트에 붙일 때도 지워야 하는 항목입니다.

모바일 쪽은 플랫폼 방향이 반대입니다. iOS 시뮬레이터 중계 도구가 macOS 전용이라 **원서가 Windows에서 확인하지 못한 영역**입니다. Android 쪽은 양쪽에서 동작하고, 붙어 있는 기기가 없으면 오류가 아니라 빈 배열이 돌아옵니다. 이 맥북에서도 그랬습니다.



## 3. 예약 실행은 응답에 동작이 다 적혀 있습니다

> 만들고 나면 응답 필드가 그 자동화가 언제 어떻게 돌지를 그대로 알려 줍니다. 만든 직후 확인하는 습관이 스케줄 실수를 대부분 잡습니다.

![automations create 응답에서 읽어야 할 다섯 필드](_assets/04-02-automation-fields.svg)

이 장부터는 사람이 시키지 않아도 에이전트가 시작합니다. 정해진 시각에 워크트리를 만들고 에이전트를 띄워 프롬프트를 주는 예약 작업입니다.

```bash
orca automations create --name "아침 점검" --trigger "0 7 * * *" \
  --prompt "저장소 상태를 점검하고 요약해 주세요" --provider claude --repo id:<repoId> --json
```

**플래그 이름이 `--cron`이 아니라 `--trigger`입니다.** 원서 본문은 cron 표현식을 다루면서 `--trigger`로 적었는데, 이 자리에서 `--cron`을 넣으면 `Unknown flag`로 거부됩니다. 값으로는 프리셋(`daily` 등), 다섯 칸 cron, RRULE 문자열을 받습니다.

만든 뒤 응답에서 다섯 필드를 봅니다.[^auto]

**`workspaceMode: "new_per_run"`** — 실행마다 새 워크트리를 만듭니다. 격리가 자동화에도 적용된 것이라, 어제 실행이 오늘에 영향을 주지 않습니다. 대신 방치하면 워크트리가 쌓입니다.

**`timezone`** — 명시하지 않으면 OS 설정을 따릅니다. 이 맥북에서는 `Asia/Seoul`이 자동으로 채워졌습니다. cron의 "7시"가 어느 시간대인지를 이 값이 정합니다.

**`nextRunAt`** — 다음 실행 시각을 미리 계산해 둡니다. 밀리초 타임스탬프라 그대로는 안 읽히지만, 사람 시각으로 바꿔 보면 표현식이 의도대로 해석됐는지 즉시 확인됩니다. `0 7 * * *`로 만든 자동화는 다음 날 07:00 KST가 잡혔습니다. **만든 직후 이 값을 확인하는 것이 스케줄 실수를 가장 많이 잡습니다.**

**`missedRunGraceMinutes: 720`** — PC가 꺼져 있어 놓친 실행을 12시간 안에 한 번 만회합니다. 아침 자동화를 노트북을 닫아 놓쳤어도 저녁에 켜면 그때 한 번 돕니다. 사흘 쉬었다고 세 번 몰아 하지는 않습니다.

**`rrule`** — 준 표현식이 그대로 저장됩니다. `dtstart`와 함께 보면 스케줄러가 무엇을 기준으로 계산했는지 알 수 있습니다.

자동화가 이상하게 굴 때는 지우지 말고 먼저 끕니다. `--disabled`로 멈추면 설정과 실행 이력이 남아 원인을 찾을 수 있습니다.



## 4. 사전 검사는 출력이 아니라 종료 코드로 판정합니다

> 변경이 없는 날 에이전트를 띄우지 않으려고 조건을 거는데, 그 조건이 항상 통과하는 함정이 있습니다.

![출력이 비어도 성공으로 끝나는 명령과 종료 코드를 바꿔 준 명령의 대비](_assets/04-02-precheck.svg)

`--precheck`는 실행 전에 명령을 돌려 조건을 확인합니다. 판정 기준이 **출력이 아니라 종료 코드**라는 점이 함정의 출발입니다.

```bash
git log --since=midnight --oneline
echo $?          # 오늘 커밋이 없어 출력이 비어도 → 0
```

출력이 비어 있어도 명령 자체는 성공했으므로 0으로 끝납니다. 이걸 그대로 `--precheck`에 넣으면 조건이 **항상 통과**해 아무것도 걸러내지 못합니다.

출력이 없을 때 실패하도록 한 단계를 덧붙입니다. 원서는 Windows 기준으로 `findstr . >nul`을 적었고, macOS와 리눅스에서는 `grep -q .`가 같은 역할을 합니다.

```bash
orca automations create --name "변경 있을 때만 리뷰" --trigger "0 18 * * 1-5" \
  --prompt "오늘 변경분을 리뷰해 주세요." --provider claude --repo id:<repoId> \
  --precheck "git log --since=midnight --oneline | grep -q ." --json
```

여기에 검증 방법의 함정이 하나 더 붙습니다. 사전 검사가 잘 도는지 확인하려고 즉시 실행을 걸면 **그 방법으로는 확인되지 않습니다.** 원서 실측에서 조건이 실패해야 하는 상태로 수동 실행을 걸었는데 그대로 실행됐고 `precheckResult`는 끝까지 `null`이었습니다. 사전 검사는 예약된 시각에 스케줄러가 실행할 때만 평가되는 것으로 보입니다.

그래서 검증을 두 단계로 나눕니다.

1. 명령이 의도대로 0과 1을 내는지 **셸에서 직접 실행**해 `echo $?`로 확인합니다.
2. 자동화가 실제로 걸러내는지는 예약 시각이 지난 뒤 실행 이력의 `precheckResult`로 확인합니다.

첫 번째를 먼저 해야 합니다. 종료 코드가 틀린 명령을 넣어 두면 다음 날 아침까지 모르고, 그때는 이미 하루치 실행이 낭비된 뒤입니다.



## 5. 자동화에 맡길 것과 맡기지 말 것

> 기준은 하나입니다. 잘못 실행되면 되돌릴 수 있는가. 자동화의 무서운 점은 실수가 정기적으로 반복된다는 것입니다.

![되돌릴 수 있는지로 가르는 자동화 적합성](_assets/04-02-what-to-automate.svg)

어울리는 쪽은 결과가 정보이고 틀려도 피해가 없는 작업입니다. 상태 요약, 의존성·취약점 확인, 문서 갱신, 테스트 실행과 보고, 로그 분류가 여기 듭니다.

안 어울리는 쪽은 되돌리기 비용이 큰 작업입니다. 코드를 고쳐 커밋하고 푸시하는 일, 배포, 외부로 메시지 보내기, 데이터 삭제입니다. 한 번의 실수로 끝나지 않고 매일 같은 시각에 반복된다는 점이 특히 나쁩니다.

**`workspaceMode: new_per_run`이 안전장치 역할을 합니다.** 에이전트가 새 워크트리에서만 작업하므로 결과가 그 워크트리에 갇혀 있습니다. 이 성질을 활용하면 대부분의 위험이 사라집니다 — **자동화 프롬프트에 "커밋해 주세요"를 넣지 않는 것**만으로 충분합니다.

여기서 앞 편들과 이어지는 지점이 하나 있습니다. 자동화가 만든 워크트리에는 커밋되지 않은 결과물이 남고, 그것을 회수하지 않은 채 워크트리를 지우면 사라집니다. 산출물을 파일로 남기게 했다면 그 파일이 무시 목록에 걸려 있는지 확인해야 합니다.

정리 부담도 같은 자리에서 생깁니다. 실행마다 워크트리가 하나씩 쌓이므로 주기적으로 치워야 하고, `--precheck`로 불필요한 실행을 막는 것이 그 부담을 줄이는 가장 쉬운 방법입니다.



## 면접에서 받을 만한 질문

1. 웹 애플리케이션의 화면을 검증하려는데 컴퓨터 유즈와 브라우저 명령 중 무엇을 씁니까?
2. 매일 아침 저장소를 점검하는 자동화를 만들었습니다. 만든 직후 무엇을 확인해야 합니까?
3. 자동화가 코드를 고쳐 커밋까지 하게 해도 됩니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 웹 페이지라면 브라우저 명령입니다

컴퓨터 유즈는 브라우저로 닿을 수 없는 곳을 위한 도구입니다. 웹 페이지는 브라우저 명령의 스냅샷이 훨씬 짧고 조작이 정확하며 네트워크와 콘솔까지 관측할 수 있습니다. 컴퓨터 유즈를 쓰는 경우는 일반 데스크톱 앱, 외부 브라우저 창, ORCA 앱 자신의 UI, 웹뷰 기반 앱입니다.

### 정답 2 — `nextRunAt`을 사람 시각으로 바꿔 봅니다

cron 표현식을 잘못 써서 엉뚱한 시각에 잡히는 일이 흔하고, 그것을 가장 확실하게 잡아 주는 필드가 `nextRunAt`입니다. 함께 `timezone`도 봅니다. 명시하지 않으면 OS 설정을 따르므로, 팀이 여러 시간대에 있으면 의도와 달라질 수 있습니다. 사전 검사를 걸었다면 그 명령의 종료 코드를 셸에서 먼저 확인합니다.

### 정답 3 — 되돌릴 수 있는지로 판단합니다

되돌릴 수 없는 일은 자동화하지 않습니다. 자동화의 실수는 정기적으로 반복되기 때문입니다. 다만 ORCA는 실행마다 새 워크트리를 만들어 결과를 가둬 두므로, 프롬프트에 커밋을 시키지 않으면 결과가 그 워크트리 밖으로 나가지 않습니다. 사람이 그 워크트리를 열어 확인한 뒤 반영하는 구성이 안전합니다.
