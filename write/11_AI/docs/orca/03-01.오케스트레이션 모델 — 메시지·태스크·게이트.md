# 오케스트레이션 모델 — 메시지·태스크·게이트
---
> ADE 세 축 중 마지막입니다. 태스크는 무엇을, 메시지는 어떻게 주고받는지, 게이트는 언제 멈추는지를 담당합니다. 명령을 외우기 전에 이 모델을 잡으면 나머지는 따라옵니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 코디네이터와 워커의 별 모양 구조가 왜 관리하기 쉬운지 설명할 수 있습니다.
2. 태스크 DAG로 순서를 표현하고 `--ready`가 무엇을 걸러 주는지 실행 결과로 말할 수 있습니다.
3. 메시지 타입 여덟 개의 방향과 뜻을 대고, 타입이 정해져 있는 것이 왜 장점인지 설명할 수 있습니다.
4. 오케스트레이션을 쓸 때와 워크트리만으로 충분할 때를 가를 수 있습니다.

여러 워커를 실제로 물려 돌리는 예제는 [03-02](03-02.실전 파이프라인 — 이슈에서 PR까지.md)에서 다룹니다.



## 1. 모든 소통이 코디네이터를 거칩니다

> 워커끼리 직접 말하게 두면 대화 경로가 폭발해 아무도 전체를 모르게 됩니다. 별 모양이 관리하기 가장 쉬운 형태이고 ORCA의 명령도 그 전제 위에 있습니다.

![코디네이터를 중심에 둔 별 모양과 워커끼리 직접 말하는 그물 모양의 대비](_assets/03-01-star-topology.svg)

코디네이터는 전체를 보는 쪽입니다. 태스크를 만들어 누구에게 줄지 정하고, 완료 보고를 받아 막힌 것을 풀어 줍니다.

워커는 받은 일만 합니다. 다른 워커가 무엇을 하는지 모르고 코디네이터에게만 말합니다.

이 구분이 실용적인 이유는 경로의 수에 있습니다. 워커 n개가 서로 직접 말하면 경로가 n(n−1)/2로 늘지만, 별 모양이면 n개입니다. 워커 다섯이면 열 갈래와 다섯 갈래의 차이입니다.

다른 구조가 불가능하지는 않습니다. 코디네이터를 계층으로 쌓거나 공유 게시판을 두거나 이벤트를 뿌릴 수도 있습니다. 다만 그런 구조는 상태를 추적할 장치를 직접 만들어야 합니다.

코디네이터는 사람일 수도 있고 에이전트일 수도 있습니다. 그리고 **이 명령들은 원래 에이전트가 쓰도록 설계됐습니다.** 에이전트는 자기가 어느 터미널인지 환경 변수로 알고 있어서 `--from`을 줄 필요가 없습니다.

여기서 원서가 잡아낸 위험이 하나 있습니다. v1.4.154에서는 바깥 셸에서 보낸 메시지를 `no_active_sender_terminal`로 거부했는데, v1.4.176부터는 거부하지 않고 **살아 있는 터미널 중 하나를 알아서 발신자로 고릅니다.** 오류가 안 나니 알아채기도 어렵습니다.

그래서 바깥에서 명령을 칠 때는 `--from <핸들>`을 항상 명시합니다. 이 편의 실측도 전부 그렇게 했습니다.



## 2. 태스크·메시지·게이트 세 요소

> 태스크는 무엇을, 메시지는 어떻게 주고받는지, 게이트는 언제 멈추는지를 담당합니다. 식별자 형태가 셋 다 다릅니다.

![태스크·메시지·게이트가 각각 담당하는 축](_assets/03-01-three-elements.svg)

**태스크를 만들기 전에 Run이 필요합니다.** v1.4.176부터 생긴 제약이고 v1.4.188에서도 그렇습니다. 준비 없이 실행하면 `run_required`로 거부됩니다.

```bash
orca orchestration run-create --objective "ORCA 학습 노트용 오케스트레이션 실측" --from <핸들> --json
# { "run": { "id": "run_5921853c62d2", "objective": "...", "coordinator_handle": "term_..." } }
```

Run은 태스크와 메시지를 담는 묶음이자 받은 편지함입니다. 스케줄링은 하지 않습니다. 그 뒤 태스크를 만들면 `task_` 접두의 식별자와 함께 `spec`·`status`·`deps`가 붙습니다.

게이트는 태스크에 붙어 사람의 결정을 기다립니다. 실측에서 만든 게이트는 이렇게 돌아왔습니다.

```bash
orca orchestration gate-create --task <task_id> --question "이 구현을 머지할까요?" \
  --options '["merge","revise"]' --from <핸들> --json
# { "gate": { "id": "gate_609bc0cdc12a", "task_id": "task_...",
#             "options": "[\"merge\",\"revise\"]", "status": "pending" } }
```

여기서 눈에 띄는 것이 `options` 값입니다. 배열이 아니라 **JSON 문자열**로 저장됩니다. 뒤에서 볼 `deps`와 같은 방식이라, 스크립트로 다룰 때 한 번 더 파싱해야 합니다.

게이트를 해결하는 명령에는 함정이 하나 있습니다. 다른 게이트 명령은 `--task`를 쓰는데 이것만 `--id`입니다.

```bash
orca orchestration gate-resolve --gate <gate_id> --resolution merge --from <핸들> --json
# "message": "Unknown flag --gate for command: orchestration gate-resolve"
# "validFlags": ["environment","from","help","id","json","pairing-code","resolution","retry-request"]
```

오류 응답이 정답을 알려 줍니다. `--id`로 바꿔 실행하면 `status: "resolved"`와 함께 고른 답이 기록됩니다.



## 3. 태스크 DAG가 순서를 표현합니다

> 의존 관계를 걸면 "지금 시작할 수 있는 일"만 골라 줍니다. 선후 관계만 있고 고리가 없는 작업 순서표입니다.

![의존 관계에 따라 ready와 pending으로 갈리는 태스크 그래프](_assets/03-01-task-dag.svg)

의존 관계 없이 만든 태스크는 곧바로 `ready`가 되고, 앞 태스크에 의존하게 만든 태스크는 `pending`으로 대기합니다. 실측한 그대로입니다.

```bash
orca orchestration task-create --spec "calc.py 에 power 함수 추가" --task-title "구현" --from <핸들> --json
# task_b8c2efd6a92c

orca orchestration task-create --spec "구현 결과 리뷰" --task-title "리뷰" \
  --deps '["task_b8c2efd6a92c"]' --from <핸들> --json

orca orchestration task-list --ready --brief --run <run_id> --json
# [("task_b8c2efd6a92c", "구현", "ready")]      ← 리뷰는 빠집니다
```

의존이 걸린 리뷰 태스크가 `--ready` 목록에서 빠집니다. 코디네이터가 매번 "무엇을 시작할 수 있나"를 계산하지 않아도 되는 이유입니다.

이런 그래프를 DAG라고 부릅니다. 방향이 있고 순환하지 않는다는 뜻인데, 쉽게 말하면 선후 관계만 있고 뱅뱅 도는 고리가 없는 작업 순서표입니다. 구현이 끝나면 리뷰와 테스트가 동시에 시작될 수 있고, 둘 다 끝나야 문서화가 시작되는 관계를 `--deps`로 적습니다.

**`deps` 값이 배열이 아니라 JSON 문자열입니다.**

```bash
# task 응답에서
deps = '["task_b8c2efd6a92c"]'    # 파이썬 타입: str
```

배열로 바로 접근하려 하면 실패합니다. 게이트의 `options`도 같은 방식이니, 오케스트레이션 응답에서 배열처럼 보이는 값은 일단 문자열을 의심하는 편이 안전합니다.



## 4. 메시지 타입 여덟 개가 어휘입니다

> `--type`에 아무 값이나 넣을 수 없습니다. 타입이 정해져 있어야 코디네이터가 자동으로 판정할 수 있습니다.

![메시지 타입 여덟 개의 방향과 뜻](_assets/03-01-message-types.svg)

여덟 개뿐이고 각각 방향이 정해져 있습니다. `dispatch`만 코디네이터에서 워커로 가고, 나머지는 대체로 워커에서 코디네이터로 갑니다. `handoff`는 소유권을 넘기는 것이라 워커끼리도 갑니다.

타입이 정해져 있는 것이 장점인 이유는 자동 판정 때문입니다. 코디네이터가 `worker_done`만 세면 몇 개가 끝났는지 알 수 있고, `heartbeat`가 끊긴 워커를 멈춤으로 판정할 수 있습니다. 자유 형식 텍스트로는 이런 계산이 불가능합니다.

**잘못된 값을 주면 목록을 알려 주지 않습니다.** 원서가 v1.4.176에서 관찰한 변화가 v1.4.188에도 그대로입니다.

```bash
orca orchestration send --subject "테스트" --type bogus_type --to run:<run_id> --from <핸들> --json
# { "code": "invalid_argument", "message": "Invalid input" }     ← data 는 null
```

v1.4.154에서는 여덟 개 목록을 그대로 뱉어 줬다고 합니다. 친절함이 줄었으니 목록을 손에 들고 있어야 합니다.

여덟 개가 모두 유효한지는 하나씩 보내 확인했습니다. 타입 자체는 전부 통과하고, 거부된 셋은 타입이 아니라 조건 때문이었습니다.[^types]

| 타입 | 실측 결과 |
|------|----------|
| `status` · `heartbeat` · `handoff` · `merge_ready` · `dispatch` | 그대로 발송 |
| `worker_done` | `--outcome succeeded\|failed` 를 요구 |
| `escalation` · `decision_gate` | 활성 Dispatch 가 있어야 함 |

`worker_done`과 `heartbeat`는 그룹 주소로 보낼 수 없고, `--to`를 생략하면 그 배분이 속한 Run의 우편함으로 갑니다.



## 5. 메시지를 읽는 것과 소비하는 것

> 원서는 `check`의 기본 동작이 읽음 처리라고 경고합니다. v1.4.188에서는 그렇지 않았습니다. 명시적인 확인이 있어야 소비됩니다.

![delivery 배치를 재전달하다가 ack 로 소비하는 흐름](_assets/03-01-delivery-ack.svg)

원서 05-2는 "파이프라인이 이유 없이 멈췄다면 십중팔구 누군가 `check`로 메시지를 먹었다"고 적고, 조회는 `inbox`로 소비는 `check`로 역할을 나누라고 권합니다. **v1.4.188에서는 이 경고가 성립하지 않습니다.**

메시지 일곱 개를 Run 우편함에 보내 두고 순서대로 확인했습니다.[^ack]

```bash
orca orchestration check --terminal <핸들> --peek --json   # count 7
orca orchestration check --terminal <핸들> --json          # count 7 · replayed: true
orca orchestration check --terminal <핸들> --peek --json   # count 7   ← 그대로
```

기본 `check`를 부른 뒤에도 개수가 줄지 않았습니다. 응답을 보면 이유가 있습니다.

```bash
deliveryId: "delivery_d75dacbf5113"
replayed:   true
acknowledged: null
```

같은 배치를 계속 재전달하고 있고, 소비하려면 그 배치를 명시적으로 확인해야 합니다.

```bash
orca orchestration check --terminal <핸들> --ack delivery_d75dacbf5113 --json
# acknowledged: "delivery_d75dacbf5113",  count: 0
orca orchestration check --terminal <핸들> --peek --json
# count: 0
```

읽음 처리가 자동에서 명시적 확인으로 바뀐 셈입니다. 명령 사용법에도 그렇게 적혀 있습니다.

- 기본은 묶인 Run 의 가장 오래된 미확인 배치를 돌려줍니다.
- `--ack` 가 이전 배치를 확인합니다.
- `--peek` 은 읽지 않은 것만 표시 없이 보여 줍니다.

**이 변화의 방향이 중요합니다.** 조회했다는 이유로 메시지가 사라지지 않으므로, 워커가 중간에 죽어도 배치가 남아 다시 전달됩니다. 대신 확인을 빠뜨리면 같은 배치를 영원히 다시 받게 됩니다.



## 6. 언제 쓰고 언제 안 써도 되는가

> 병렬로 돌리는 것만이 목적이면 워크트리로 충분합니다. 오케스트레이션은 서로 물려 있는 작업에 필요합니다.

![작업 관계에 따라 워크트리·태스크·메시지·게이트 중 무엇이 필요한지](_assets/03-01-when-to-use.svg)

솔직하게 정리하면 오케스트레이션은 배우는 비용이 있고 항상 필요하지 않습니다.

에이전트 하나로 끝나는 일은 앞 편의 방식으로 충분합니다. 에이전트 둘이 서로 무관한 일을 한다면 워크트리만 나누면 됩니다. **병렬 실행 자체는 격리가 주는 것이지 조율이 주는 것이 아닙니다.**

조율이 필요한 것은 관계가 있을 때입니다. 순서가 있으면 태스크 DAG, 결과를 주고받아야 하면 메시지, 사람 승인이 중간에 필요하면 게이트입니다.

자동 코디네이터 루프를 기대했다면 조정이 필요합니다. 원서는 v1.4.176에서 네 명령이 은퇴했다고 기록했는데, v1.4.188에서는 처리가 두 갈래로 갈렸습니다.[^retired]

| 명령 | v1.4.188 |
|------|----------|
| `orchestration run` · `run-stop` | 스키마에서 아예 사라짐 |
| `coordinator-start` · `coordinator-stop` | 목록에는 있으나 호출하면 `orchestration_migration_required` |

은퇴 스텁의 응답이 친절합니다. `effectsApplied: false`로 아무 일도 하지 않았음을 밝히고, `nextCommandArgs`로 읽어야 할 가이드까지 알려 줍니다.

설계 철학이 바뀐 것입니다. 태스크를 쪼개고 워커를 배치하고 동시 실행 수를 제한하는 일이 전부 사람이나 에이전트 쪽으로 넘어왔습니다. 공식 가이드의 표현대로 ORCA는 워커를 스케줄링하지 않고 충돌을 추론하지 않습니다.

편해 보이던 자동화가 사라진 대신 무슨 일이 벌어지는지가 눈에 보이게 됐습니다. 대가는 **자동 상한이 없다**는 점입니다. 워커 하나가 워크트리 하나와 에이전트 세션 하나를 쓰므로, 태스크 스무 개에 워커를 한꺼번에 붙이면 메모리와 사용량이 함께 폭발합니다. 두셋으로 시작해 여유를 보고 올리는 편이 안전합니다.

`orchestration reset --all`은 쓰지 않습니다. 조회는 Run 단위로 좁혀졌지만 이 명령의 파괴 범위는 로컬 데이터베이스 전체라, 다른 작업의 상태까지 지웁니다. 정리는 태스크를 하나씩 `completed`로 바꾸는 것으로 합니다. 이 노트의 실측도 그렇게 정리했습니다.



## 면접에서 받을 만한 질문

1. 에이전트 셋을 동시에 돌리려고 합니다. 오케스트레이션 명령을 배워야 합니까?
2. 코디네이터가 워커의 완료를 어떻게 자동으로 셉니까? 자유 형식 보고로는 왜 안 됩니까?
3. 파이프라인이 이유 없이 멈춘 것 같습니다. 메시지를 확인하려는데 어떤 명령을 씁니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 관계가 없으면 워크트리로 충분합니다

셋이 서로 무관한 일을 한다면 워크트리 셋을 만들어 각각 에이전트를 붙이면 끝입니다. 병렬 실행은 격리가 주는 것입니다. 오케스트레이션이 필요한 경우는 관계가 있을 때입니다. A가 끝나야 B가 시작되면 태스크 DAG, 결과를 주고받아야 하면 메시지, 중간에 사람 승인이 필요하면 게이트입니다.

### 정답 2 — 타입이 정해져 있어서 셀 수 있습니다

메시지 타입이 여덟 개로 고정돼 있습니다. 코디네이터는 `worker_done`의 개수만 세면 몇 개가 끝났는지 알 수 있고, `heartbeat`가 도착하는 간격을 보면 멈춘 워커를 판정할 수 있습니다. 자유 형식 텍스트라면 매번 내용을 해석해야 하고 그 해석 자체가 불확실합니다. 어휘를 제한하는 것이 자동 판정의 전제입니다.

### 정답 3 — 버전에 따라 답이 다릅니다

원서 기준(v1.4.176)에서는 조회에 `inbox`를, 소비에 `check`를 쓰고, 굳이 `check`로 봐야 하면 `--peek`을 붙이라고 권합니다. `check`의 기본이 읽음 처리였기 때문입니다. v1.4.188에서는 `check`가 배치를 재전달만 하고 `--ack <deliveryId>`를 줘야 소비됩니다. 자기 설치본에서 `--peek`을 두 번 불러 개수가 그대로인지 확인하면 어느 쪽인지 바로 알 수 있습니다.
