# ORCA의 구성 — 앱·런타임·CLI·워크트리
---
> ORCA는 앱 하나로 보이지만 안에 부품이 넷 있습니다. 화면과 처리부가 갈려 있고 CLI는 화면을 거치지 않습니다. 이 구조를 알면 "앱이 안 돌고 있다"는 오류가 떴는데 상태는 정상인 상황을 스스로 설명할 수 있습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 앱·런타임·CLI·워크트리가 각각 무엇을 맡는지 구분하고, 화면 없이 런타임만 띄우는 것이 왜 가능한지 설명할 수 있습니다.
2. `orca status`의 세 층을 읽고 어느 층이 준비되지 않아 명령이 실패했는지 짚을 수 있습니다.
3. Repo·워크트리·터미널의 개수 관계를 대고, ORCA 워크트리가 git 워크트리와 같은 것임을 확인하는 명령을 댈 수 있습니다.
4. CLI 응답 형태와 셀렉터 표기를 읽고, 오류 응답만으로 옳은 플래그를 찾아낼 수 있습니다.

개별 명령의 사용법은 다루지 않습니다. 명령 지도는 [부록 06-02](06-02.부록 — orca CLI 명령 지도 v1.4.188.md)에 있습니다.



## 1. 화면과 처리부가 나뉘어 있습니다

> 앱은 창을 그리고 런타임은 실제 처리를 합니다. CLI는 화면을 거치지 않고 런타임에 직접 말을 겁니다. 이 분리가 헤드리스 실행과 원격 페어링을 가능하게 만듭니다.

![앱·런타임·CLI·번들 엔진의 관계와 두 진입 경로](_assets/01-02-components.svg)

**데스크톱 앱**은 Electron으로 만들어졌습니다. 이 사실이 실제로 의미를 갖는 지점이 하나 있습니다. 앱 안에 완전한 브라우저가 들어 있다는 점입니다. 그래서 나중에 다룰 내장 브라우저 자동화는 별도 프로그램이 아니라 앱의 일부이고, Playwright를 따로 깔 필요가 없습니다.

**런타임**은 명령을 받아 실제로 처리하는 부분입니다. 워크트리를 만들고 터미널 프로세스를 띄우고 브라우저를 조작하고 태스크 상태를 보관합니다. CLI가 말을 거는 상대가 이 런타임입니다.

런타임은 자기 식별자를 갖습니다. 모든 CLI 응답의 `_meta.runtimeId`에 같은 값이 실려 오는데, 로컬과 원격 런타임을 함께 쓸 때 지금 어디에 말을 걸었는지 확인하는 용도입니다. 앱을 다시 켜면 이 값이 바뀝니다.

**번들 엔진**은 런타임이 필요할 때 불러 쓰는 별도 실행 파일입니다. 브라우저 자동화 엔진, 데스크톱 제어 프로바이더, 원격 중계가 설치본에 함께 들어옵니다. 브라우저 자동화가 왜 추가 설치 없이 되는지의 답이 여기 있습니다.

이 분리 덕분에 두 가지가 가능해집니다. 앱 창을 열지 않고 런타임만 띄울 수 있고(`orca serve`), 다른 기기의 런타임에 붙어 쓸 수 있습니다.



## 2. 상태는 세 층이 순서대로 켜집니다

> `app` → `runtime` → `graph` 순으로 준비됩니다. 명령이 이상하게 동작하면 어느 층까지 켜졌는지부터 봅니다.

![app·runtime·graph 세 층과 각 층이 준비되지 않았을 때의 증상](_assets/01-02-status-layers.svg)

문제가 생겼을 때 가장 먼저 실행할 명령입니다.

```bash
orca status --json
```

이 노트를 쓰며 확인한 정상 상태는 이랬습니다.[^status]

```bash
appRunning: true
runtimeState: ready
graphState: ready
```

세 층은 각각 다른 것을 뜻합니다. `app`은 데스크톱 앱 프로세스가 떠 있는가, `runtime`은 명령을 받아 처리할 내부 서버가 응답하는가, `graph`는 작업 상태를 담은 내부 저장소가 준비됐는가입니다.

여기서 초심자가 놀라는 값이 하나 있습니다. 앱을 켜지 않은 상태의 `runtime.state`가 `stale_bootstrap`입니다. "stale"이라는 단어 때문에 고장 난 것처럼 보이지만, 예전 부트스트랩 정보만 남아 있고 지금은 안 돌고 있다는 뜻입니다.

`graph.state`가 `ready`가 아니면 워크트리·태스크 명령이 실패하거나 빈 결과를 돌려줍니다. 명령이 조용히 빈 배열을 줄 때 이 값을 먼저 보는 습관이 진단을 크게 줄입니다.

앱을 켜는 방법이 둘인데 자동화에서는 차이가 생깁니다. 아이콘으로 켜면 창이 떠도 잠깐은 CLI 명령이 실패할 수 있습니다. `orca open`은 런타임이 응답할 수 있게 된 뒤에 제어권을 넘겨줍니다. 스크립트 첫 줄에 넣기 좋은 쪽은 후자입니다.



## 3. Repo · 워크트리 · 터미널의 관계

> Repo 하나에 워크트리가 여러 개 붙고, 워크트리 하나에 터미널이 하나 이상 붙습니다. 이 세 층이 ORCA에서 "작업"을 세는 단위입니다.

![Repo 하나에서 워크트리가 갈리고 각 워크트리에 터미널이 붙는 구조](_assets/01-02-repo-tree.svg)

용어 셋의 관계를 먼저 정리합니다. Repo는 ORCA에 등록한 저장소이고 프로젝트마다 하나입니다. 워크트리는 그 저장소에서 파생된 독립 작업 폴더이자 브랜치이고 작업마다 하나입니다. 터미널은 워크트리 안에서 도는 셸이나 에이전트 세션입니다.

여기서 확인해 둘 사실이 있습니다. **ORCA가 만든 작업 공간은 진짜 git 워크트리입니다.** 실측한 v1.4.188에서 워크트리를 하나 만든 뒤 git으로 확인하면 그대로 보입니다.

```bash
orca worktree create --repo id:<repoId> --name demo-a --json
cd ~/orca-practice && git worktree list
# ~/orca-practice                              1f87868 [main]
# ~/orca/workspaces/orca-practice/demo-a       1f87868 [demo-a]
```

브랜치도 워크트리 이름과 같게 자동 생성됩니다. ORCA만 아는 특수한 개념이 아니라서, 평소 쓰는 git 명령을 그대로 쓸 수 있고 ORCA를 지워도 브랜치와 커밋은 남습니다.

워크트리 폴더의 위치는 원서가 적은 Windows 경로와 형태가 같았습니다. 원서는 `%USERPROFILE%\orca\workspaces\<프로젝트>\<워크트리>`라고 적었는데, 이 맥북에서는 `$HOME/orca/workspaces/<프로젝트>/<워크트리>`였습니다. 구분자만 다릅니다.

터미널에 관해 원서가 적어 둔 사실 하나도 그대로였습니다. `--agent`를 주지 않아도 터미널 하나가 자동으로 만들어집니다. 위 명령으로 워크트리만 만든 직후 터미널 목록을 보면 `connected: true`인 셸이 이미 붙어 있습니다.



## 4. CLI는 얇습니다 — 오해를 부르는 오류 메시지

> CLI에는 처리 로직이 거의 없습니다. 런타임이 응답하지 않으면 CLI가 아무리 멀쩡해도 할 수 있는 일이 없고, 그 상황을 CLI는 "앱이 없다"로 표현합니다.

<!-- no-diagram: 오류 메시지 하나를 어떻게 읽을 것인가를 다루는 절이라 그릴 구조가 없습니다. 부품 관계는 1절 도식이 이미 보입니다. -->

CLI가 하는 일은 단순합니다. 준 명령을 런타임이 이해하는 요청으로 바꿔 보내고 응답을 돌려줍니다. 그래서 응답 형태가 명령 종류와 무관하게 일정합니다.

```bash
{ "id": "...", "ok": true,  "result": { ... }, "_meta": { "runtimeId": "..." } }
{ "id": "...", "ok": false, "error":  { "code": "...", "message": "..." } }
```

`ok` 필드만 보면 성공 여부를 알 수 있어서 조건 분기가 쉽습니다. 그래서 거의 모든 명령에 `--json`을 붙이는 습관을 권합니다. 텍스트 출력은 보기 좋게 정리되면서 일부 정보가 생략되고, 뒤에서 볼 것처럼 텍스트 경로에만 결함이 있는 명령도 있습니다.

원서가 실측 중에 만났다는 오류가 이 구조를 잘 보여 줍니다.

```bash
The Orca runtime closed the connection before responding. Restart Orca and try again.
Orca is not running. Run 'orca open' first.
```

앱이 안 돌고 있다는 말이지만 바로 뒤에 `orca status`를 실행하면 `ready`였다고 합니다. CLI와 런타임 사이의 연결 하나가 끊긴 것을 CLI가 "앱이 없다"로 해석한 것입니다. 부품이 나뉘어 있다는 사실을 알면 이 메시지에 속아 앱을 재시작하지 않게 됩니다.

오류가 친절한 쪽도 있습니다. 플래그 이름을 틀리면 무엇을 써야 하는지 알려 줍니다. 실제로 틀리게 실행해 본 결과입니다.

```bash
orca orchestration gate-resolve --gate <id> --resolution merge --json
# "code": "invalid_argument"
# "message": "Unknown flag --gate for command: orchestration gate-resolve"
# "validFlags": ["environment","from","help","id","json","pairing-code","resolution","retry-request"]
```

옵션이 기억나지 않으면 일부러 틀리게 실행하는 편이 도움말을 뒤지는 것보다 빠릅니다. 다만 이 친절이 모든 명령에 걸려 있지는 않습니다. 잘못된 메시지 타입을 주는 경우처럼 목록 없이 `Invalid input`만 돌아오는 자리도 있습니다.



## 5. 명령 232개를 읽는 법

> 다 외울 필요가 없습니다. 영역별로 묶여 있고, 어느 영역이 두꺼운지가 이 도구의 성격을 그대로 드러냅니다.

![v1.4.188 명령 232개의 영역별 분포](_assets/01-02-command-mix.svg)

`orca agent-context --json`이 정확한 수를 알려 줍니다. 이 설치본은 232개였고 최상위 명령 그룹은 69개였습니다.

분포에서 두 가지가 눈에 띕니다.

**브라우저 계열이 77개로 전체의 33%입니다.** 스냅샷·클릭·입력은 물론이고 쿠키, 네트워크 가로채기, 콘솔 로그, 기기 에뮬레이션, 스토리지까지 있습니다. ORCA가 "코드를 고치는 일"과 "화면에서 확인하는 일"을 한 세트로 본다는 뜻입니다.

**이슈 연동이 27개로 터미널(11개)보다 두껍습니다.** 티켓 읽기, 상태 이동, PR 링크 붙이기, 하위 티켓 만들기까지 들어 있습니다. 티켓에서 시작해 PR로 끝나는 흐름을 통째로 다루려는 설계입니다.

오케스트레이션은 29개인데, 이 숫자에 버전 이야기가 하나 들어 있습니다. 원서 기준인 v1.4.176에서는 16개였습니다. 그 16개가 그대로 남은 위에 `run-*` 5개와 `worker-*` 8개가 얹혀 29개가 됐습니다.[^orch] 원서 소개글이 "Run·워커 명령으로 교체됐다"고 적은 변화가 이것입니다.



## 6. 실행할 때마다 달라지는 값과 셀렉터

> 식별자는 실행마다 새로 생깁니다. 문서의 값을 복사해 쓰면 동작하지 않고, 대상을 고를 때는 셀렉터 표기를 씁니다.

<!-- no-diagram: 표기 규약을 나열하는 절이라 도식으로 만들 형태가 없습니다. -->

`repoId`, 터미널 핸들, 페이지 id는 모두 실행할 때마다 달라집니다. 명령을 실행해 나온 값을 그대로 다음 명령에 넣어야 합니다.

워크트리나 터미널처럼 여러 개가 있는 대상은 셀렉터로 고릅니다. 형식이 통일돼 있습니다.

| 셀렉터 | 의미 | 예 |
|--------|------|-----|
| `active` | 지금 활성 대상 | `--worktree active` |
| `id:<값>` | 식별자로 지정 | `--repo id:bd032ebc-...` |
| `path:<경로>` | 경로로 지정 | `--worktree path:$HOME/orca/workspaces/my-app/task-1` |
| `name:<이름>` | 이름으로 지정 | `--repo name:my-app` |
| `branch:<브랜치>` | 브랜치로 지정 | `--worktree branch:feature/login` |

경로에 공백이 있으면 셀렉터 전체를 따옴표로 감쌉니다.

응답에서 값을 꺼낼 때 주의할 곳이 하나 있습니다. `terminal create`의 핸들은 `result.terminal.handle`이지 `result.handle`이 아닙니다. 이 노트를 쓰며 여기서 한 번 걸렸는데, 잘못 꺼낸 빈 값을 넘기니 모든 후속 명령이 `terminal_handle_stale`을 돌려줬습니다. 존재한 적 없는 핸들도 같은 코드를 주기 때문에, 이 오류만으로는 "터미널이 죽었다"와 "그런 핸들이 없다"를 구분할 수 없습니다.

응답 구조가 궁금하면 추측하지 말고 스키마를 봅니다.

```bash
orca agent-context --json | python3 -m json.tool | grep -A6 '"command": "terminal create"'
```



## 면접에서 받을 만한 질문

1. ORCA에서 명령이 실패했는데 `orca status`는 정상입니다. 어디를 봐야 합니까?
2. ORCA를 지우면 에이전트가 만든 작업 결과도 사라집니까?
3. ORCA CLI에 처리 로직이 거의 없다는 설계가 사용자에게 주는 실질적인 이점은 무엇입니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 세 층 중 어디까지 켜졌는지부터 봅니다

`orca status`가 전부 `ready`인데 명령이 실패한다면 두 가지를 봅니다. 첫째로 `graph.state`가 `ready`인지 다시 확인합니다. 이 층이 준비되지 않으면 워크트리·태스크 명령이 오류 대신 빈 결과를 줍니다. 둘째로 CLI와 런타임 사이의 개별 연결이 끊긴 경우가 있습니다. 이때 CLI는 "Orca is not running"이라고 말하지만 앱을 재시작할 필요는 없습니다.

### 정답 2 — 브랜치와 커밋은 git 쪽에 남습니다

ORCA의 워크트리는 진짜 git 워크트리이고 브랜치는 저장소 안에 만들어집니다. `git worktree list`로 확인할 수 있고, ORCA를 지워도 브랜치와 커밋은 저장소에 남습니다. 다만 워크트리를 지우는 시점의 동작은 조건에 따라 갈리므로 그 자리는 따로 확인해야 합니다.

### 정답 3 — 자동화와 원격 실행이 같은 표면을 씁니다

CLI가 얇다는 것은 모든 기능이 런타임 쪽에 있다는 뜻입니다. 그래서 화면 없이 런타임만 띄우거나 다른 기기의 런타임에 붙어도 명령 표면이 똑같습니다. 로컬에서 만든 스크립트를 원격 런타임에 그대로 쓸 수 있는 이유가 이 구조입니다. 대가는 런타임이 죽으면 CLI가 할 수 있는 일이 없다는 점입니다.
