# 터미널과 에이전트 운전 — 지시·대기·완료 판정
---
> 무인 자동화의 성패는 대개 "작업이 끝났다는 것을 어떻게 아는가"에서 갈립니다. ORCA가 주는 대기 조건은 둘뿐이고 둘 다 완료를 보장하지 않습니다. 완료는 신호가 아니라 결과물로 판정해야 합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 터미널 핸들을 안정적으로 얻는 세 가지 방법을 대고, 스크립트에 핸들을 하드코딩하면 안 되는 이유를 설명할 수 있습니다.
2. `--for exit`과 `--for tui-idle`이 각각 언제 성립하고 언제 성립하지 않는지 대조 실험 결과로 말할 수 있습니다.
3. 완료 판정을 결과물 기준으로 설계하고, 출력과 완료 신호를 동시에 얻는 패턴을 쓸 수 있습니다.
4. 편차를 줄이는 지시의 네 덩어리 구조를 적용해 프롬프트를 작성할 수 있습니다.

여러 에이전트 사이의 메시지와 태스크 조율은 [03-01](03-01.오케스트레이션 모델 — 메시지·태스크·게이트.md)에서 다룹니다. 이 편은 에이전트 하나를 운전하는 기본기입니다.



## 1. 핸들이 모든 명령의 입구입니다

> 에이전트는 터미널 안에서 도는 프로세스입니다. 터미널을 다루는 능력이 곧 에이전트를 다루는 능력이고, 그 입구가 핸들입니다.

![워크트리 생성 방식에 따라 핸들을 얻는 세 경로](_assets/02-02-handle-paths.svg)

핸들을 얻는 방법이 만든 방식에 따라 갈립니다. `worktree create --agent`를 쓰면 응답의 `agentTerminalHandle`에서 바로 나옵니다. 에이전트 없이 워크트리만 만들면 응답에 터미널 정보가 없어서 `terminal list`로 따로 조회해야 합니다. `terminal create`로 만들면 `result.terminal.handle`에 있습니다.

마지막 경로에서 한 번 걸렸습니다. `result.handle`이 아니라 **`result.terminal.handle`**입니다. 잘못 꺼낸 빈 값을 넘겼더니 모든 후속 명령이 `terminal_handle_stale`을 돌려줬는데, 존재한 적 없는 핸들도 같은 코드를 주기 때문에 한동안 "터미널이 죽었다"로 오해했습니다.

터미널 응답에는 식별자가 넷 나옵니다. `handle`은 세션이고 거의 모든 명령이 이것을 씁니다. `tabId`는 탭, `paneKey`는 탭 안의 분할 창, `ptyId`는 실제 프로세스입니다. **`handle`만 챙기면 됩니다.** 나머지는 필요할 때 다시 조회할 수 있습니다.

핸들은 실행할 때마다 새로 생기고 앱을 재시작하면 전부 바뀝니다. 스크립트에 박아 두면 다음 실행에서 깨지므로 세 가지 중 하나를 씁니다.

- 만들면서 받은 값을 변수에 담아 바로 이어 씁니다. 가장 안전합니다.
- `--title`을 정해 두고 `terminal list`에서 그 제목으로 찾습니다. 역할 기반 스크립트에 맞습니다.
- `--worktree`로 범위를 좁힙니다. 후보가 하나뿐인 경우가 많습니다.

`terminal read`와 `terminal list`는 `--terminal`을 생략하면 현재 활성 터미널을 씁니다. 사람이 직접 칠 때는 편하지만 스크립트에서는 "지금 활성"이 무엇인지 불확실하니 명시하는 편이 좋습니다.



## 2. 보내기 전에 읽습니다

> Enter는 "지금 화면에 떠 있는 것이 무엇이든 기본 선택으로 확정하라"는 뜻입니다. 무엇이 떠 있는지 모르고 보내면 엉뚱한 것을 승인합니다.

![읽고 판별한 뒤에 보내는 3단 절차](_assets/02-02-read-before-send.svg)

입력은 `terminal send`로 보냅니다. `--text`에 문자열을, `--enter`로 Enter를 붙이고, `--interrupt`로 Ctrl+C 상당을 보냅니다.

빈 텍스트에 Enter만 보내는 형태가 실전에서 자주 쓰입니다. 기본 선택지가 이미 지정된 프롬프트를 통과시킬 때입니다.

```bash
orca terminal send --terminal <핸들> --text "" --enter --json
# { "send": { "accepted": true, "bytesWritten": 1 } }
```

대표적인 자리가 코딩 에이전트의 폴더 신뢰 확인입니다. 워크트리는 매번 새 경로에 만들어지므로 새 워크트리마다 이 질문을 다시 받습니다. 다만 원서는 v1.4.176 재실측에서 **신뢰 확인이 뜨지 않고 곧바로 작업을 시작한 경우**를 기록해 두었습니다. 이미 승인한 상위 경로 아래라면 다시 묻지 않는 것으로 보입니다.

그래서 절차를 화면에 따라 갈라야 합니다.

| 읽어 본 화면 | 할 일 |
|--------------|-------|
| 신뢰 확인이 떠 있다 | Enter로 통과 |
| 이미 작업을 시작했다 | 아무것도 보내지 않습니다 |
| 예상하지 못한 다른 질문이다 | 멈추고 사람을 부릅니다 |

작업이 이미 시작된 터미널에 Enter를 보내면 위험합니다. 에이전트가 무언가를 묻고 있을 때 그 질문에 기본값으로 답해 버립니다.

스크립트에도 같은 절차를 넣습니다.

1. `terminal read` 로 마지막 화면을 읽습니다.
2. 기대한 확인 문구가 들어 있는지 봅니다.
3. 맞으면 Enter, 아니면 멈추고 사람을 부릅니다.

한 줄이 늘어날 뿐입니다.

TUI에 보낼 때 주의할 것이 셋 더 있습니다. 에이전트가 뜨기 전에 보낸 입력은 초기화 중에 묻힙니다. 여러 줄 텍스트는 줄바꿈이 Enter로 해석돼 여러 번 제출될 수 있으니 한 줄로 만들거나 파일로 넘깁니다. `--interrupt`는 작업을 멈추지만 TUI를 종료시키지는 못합니다.



## 3. 대기 조건은 둘뿐이고 둘 다 완료가 아닙니다

> `exit`은 프로세스 종료, `tui-idle`은 화면 정지입니다. 어느 쪽도 "일이 끝났다"를 뜻하지 않습니다.

![대상과 조건의 조합별 대기 성립 여부](_assets/02-02-wait-matrix.svg)

조합을 직접 돌려 확인했습니다. 원서가 v1.4.176에서 만든 표와 같은 실험을 v1.4.188에서 다시 밟은 것입니다.[^wait]

**일반 셸에 `tui-idle`을 걸면 타임아웃입니다.** 셸은 TUI가 아니라 이 조건이 성립하지 않습니다. 12초를 기다려 `code: "timeout"`을 받았습니다.

**`--command`로 준 명령이 끝나도 셸은 살아 있습니다.** 명령이 끝나면 프롬프트로 돌아올 뿐이라 `exit` 조건도 만족되지 않습니다. 여기서도 타임아웃이 났습니다.

명령이 끝날 때 터미널까지 종료시키려면 종료를 이어 붙여야 하는데, **여기서 원서와 갈립니다.** 원서는 Windows 명령 프롬프트 기준으로 `<명령> & exit`을 적었습니다. 그 표기를 zsh에 그대로 쓰면 이렇게 됩니다.

```bash
orca terminal create --worktree <셀렉터> --command "sleep 4 && echo DONE > slow.txt & exit" --json
orca terminal wait --terminal <핸들> --for exit --timeout-ms 20000 --json
# { "ok": false, "error": { "code": "timeout" } }   ← 20초 타임아웃
```

그런데 파일은 만들어져 있었습니다. 터미널을 읽어 보니 원인이 그대로 적혀 있었습니다.

```bash
orca terminal read --terminal <핸들> --limit 30 --json
# [1] 86843
# zsh: you have running jobs.
# [1]  + 86843 done       echo DONE > slow.txt
```

zsh에서 `&`는 백그라운드 실행이고, 실행 중인 작업이 있으면 첫 `exit`을 거부합니다. **일은 됐는데 완료 신호만 오지 않는 상태**가 만들어집니다. macOS에서는 `; exit`을 씁니다.

```bash
orca terminal create --worktree <셀렉터> --command "sleep 4 && echo DONE > ok.txt; exit" --json
orca terminal wait --terminal <핸들> --for exit --timeout-ms 20000 --json
# satisfied: true, exitCode: 0, 경과 5초
```

**`tui-idle`이 만족돼도 작업은 끝나지 않았을 수 있습니다.** 원서는 v1.4.154에서 에이전트가 아직 생각 중(`Synthesizing…`)일 때 이 조건이 만족된 사례를 기록했고, v1.4.176에서 두 번 다시 돌렸을 때는 재현되지 않았다고 밝혔습니다. 여기서 얻을 결론은 "이 조건이 항상 거짓말한다"가 아닙니다. **`tui-idle`은 화면 상태를 알려 주도록 설계된 신호이고 작업 완료를 보장하도록 설계된 것이 아닙니다.** 버전에 따라 정확도가 달라지는 신호에 판정을 걸지 않는 편이 안전합니다.



## 4. 완료는 결과물로 판정합니다

> 신호를 폴링 도구로 쓰고 판정은 결과물로 합니다. 가장 튼튼한 결과물은 에이전트에게 만들게 한 완료 파일입니다.

![신호로 폴링하고 결과물로 판정하는 루프](_assets/02-02-completion-loop.svg)

에이전트 작업의 권장 패턴입니다.

```bash
# 1. 지시와 함께 워크트리 생성
orca worktree create --repo id:<repoId> --name task-1 --agent claude \
  --prompt "... 끝나면 DONE.txt 에 세 줄 요약을 써 주세요" --json

# 2. 화면을 읽고 필요할 때만 Enter
orca terminal read --terminal <핸들> --limit 20 --json

# 3. 짧게 기다리고 결과물을 본다 — 반복
orca terminal wait --terminal <핸들> --for tui-idle --timeout-ms 30000 --json
git status --short
```

`tui-idle`을 짧은 간격의 폴링 도구로 쓰고 판정은 다른 재료로 합니다. 파일 변경은 `git status --short`나 `git diff --stat`으로, 테스트 통과는 에이전트에게 돌리게 한 출력으로, 마무리 보고는 `terminal read`로 봅니다.

가장 튼튼한 것은 마지막 재료입니다. 프롬프트에 "끝나면 `DONE.txt`에 요약을 써 주세요"를 넣으면 판정이 "파일이 있는가"로 단순해집니다.

셸 명령이라면 `exit`으로 판정하는 편이 정확합니다. `exitCode`까지 받으므로 성공과 실패가 갈립니다. **다만 여기에 큰 함정이 있습니다.**

```bash
orca terminal read --terminal <핸들> --cursor 0 --limit 200 --json
# status: exited
# returnedLineCount: 0
# tail: []
```

`--cursor 0`으로 처음부터 읽어도 빈 결과였습니다. **터미널이 종료되면 출력 버퍼가 사라집니다.** 완료 신호를 정확히 받는 방식과 출력을 확보하는 방식이 서로 배타적인 셈입니다.

둘을 함께 얻으려면 출력을 파일로 남깁니다.

```bash
orca terminal create --worktree <셀렉터> \
  --command "python3 -m pytest -q > result.txt 2>&1; exit" --json
orca terminal wait --terminal <핸들> --for exit --timeout-ms 60000 --json
# 그 뒤 워크트리 폴더의 result.txt 를 읽습니다
```

`2>&1`을 붙여 오류 출력까지 담습니다. 그리고 **이 파일을 `.gitignore`에 넣을 때는 대가를 알아야 합니다.** 무시 목록에 있으면 `worktree rm`의 미커밋 변경 검사에 걸리지 않아 편하지만, 워크트리를 지울 때 경고 없이 함께 사라집니다.

타임아웃은 실패가 아니라 정상 흐름의 일부로 취급합니다. 긴 한 번보다 짧은 여러 번이 낫습니다. **같은 프롬프트를 다시 보내는 재시도는 위험합니다.** 절반쯤 작업한 에이전트가 같은 지시를 또 받으면 중복 작업을 하거나 자기 결과를 되돌립니다. 애매한 상태를 수습하기보다 워크트리를 지우고 새로 만드는 편이 낫습니다. 버리는 비용이 싸다는 것이 격리의 값어치입니다.



## 5. 지시는 네 덩어리로 씁니다

> 어제 되던 지시가 오늘 다른 결과를 내는 이유는 대개 지시가 검증 가능하지 않기 때문입니다. 목표·완료 조건·경계·진행 규칙 넷을 나눠 적습니다.

![지시의 네 덩어리와 각각이 막는 사고](_assets/02-02-prompt-blocks.svg)

원서 11장 미리보기가 템플릿 전문을 공개해 두었습니다. 구조는 이렇습니다.

```bash
[목표]
src/calc.py 의 divide 함수가 0으로 나눌 때 None 을 반환하도록 고쳐 주세요.

[완료 조건]
- python -m pytest -q 가 전부 통과
- 0으로 나누는 경우를 검증하는 테스트가 tests/ 에 존재

[경계]
- 기존 테스트 파일의 기존 케이스는 수정하지 마세요 (추가만)
- 새 라이브러리를 추가하지 마세요
- 워크트리 바깥 경로는 건드리지 마세요

[진행 규칙]
- 의미 있는 단위마다 커밋해 주세요
- 막히면 추측하지 말고 BLOCKED.txt 에 이유를 적고 멈춰 주세요
- 끝나면 DONE.txt 에 세 줄 요약을 써 주세요
```

각 덩어리가 막는 사고가 다릅니다.

- 완료 조건이 없으면 매번 결과가 달라집니다.
- 경계가 없으면 시키지 않은 파일이 바뀝니다.
- 진행 규칙이 없으면 복구 지점이 남지 않고 완료를 판정할 수 없습니다.

앞 절의 완료 판정과 이 구조가 맞물린다는 점을 보세요. `DONE.txt`를 만들게 하는 것은 진행 규칙이고, 그 파일의 존재가 판정 재료가 됩니다. **완료 조건을 프롬프트에 적는 것과 완료를 기계로 판정하는 것이 같은 설계의 앞뒷면입니다.**

목표만 갈아 끼우면 다른 작업에 그대로 재사용됩니다. 여기서 한 걸음 더 나가면 반복되는 규칙을 지시가 아니라 파일에 두게 되고, 그러면 위 템플릿이 목표 두 줄로 줄어듭니다. 그 방법은 유료 편의 본론이라 이 노트에서는 다루지 않습니다.



## 6. 정리와 종료의 함정

> `close`와 `stop`은 대상이 다릅니다. 그리고 정리하려고 `stop`을 먼저 부르는 습관이 오히려 문제를 만든 시기가 있었습니다.

<!-- no-diagram: 두 명령의 대상 차이는 한 줄 표로 충분하고, 그 위에 얹히는 것은 버전별 주의사항이라 그릴 구조가 없습니다. -->

`terminal close`는 창 하나를 닫고 `--tab`을 주면 탭 전체를 닫습니다. `terminal stop`은 워크트리의 모든 터미널을 일괄 정지시킵니다.

원서는 v1.4.154에서 `stop`이 만든 나쁜 상태를 기록해 두었습니다. 에이전트 TUI가 도는 워크트리에 `stop`을 실행했을 때의 관측입니다.

- 응답은 `{"stopped": 1}` 로 성공
- `terminal list` 에는 여전히 `connected: true`
- 탭 레코드는 이미 지워져 `close --tab` 이 `tab_not_found`
- `worktree rm` 은 PTY 오류로 막힘

CLI로 손댈 수 없는 상태가 만들어진 것입니다.

v1.4.176에서 이 문제가 고쳐졌고, 앞 편에서 확인했듯 v1.4.188에서도 살아 있는 터미널이 삭제를 막지 않습니다. 그래도 원칙은 남습니다. **워크트리를 지울 생각이면 굳이 `stop`을 먼저 부르지 않습니다.** 셸이라면 `worktree rm`이 알아서 정리합니다.

에이전트를 확실히 종료하려면 앱에서 탭을 직접 닫는 것이 가장 확실합니다. `--interrupt`는 작업을 멈출 뿐 TUI를 종료시키지 못합니다.



## 면접에서 받을 만한 질문

1. 무인 스크립트에서 에이전트 작업의 완료를 어떻게 판정하겠습니까? `wait --for tui-idle`로 충분합니까?
2. 셸 명령을 돌리고 그 출력을 확보하려는데, `--for exit`으로 완료를 받으면 출력이 비어 있습니다. 어떻게 해결합니까?
3. 에이전트가 30분째 응답이 없습니다. 같은 프롬프트를 다시 보내도 됩니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 신호는 폴링, 판정은 결과물로

`tui-idle`은 화면 갱신이 멈췄다는 신호이지 작업 완료 신호가 아닙니다. 버전에 따라 작업 중에도 만족된 사례가 보고돼 있습니다. 이 조건은 짧은 타임아웃으로 폴링하는 데 쓰고, 판정은 결과물로 합니다. 가장 튼튼한 것은 프롬프트에서 만들게 한 완료 파일의 존재이고, `git status --short`와 테스트 통과 여부를 함께 봅니다.

### 정답 2 — 출력을 파일로 남깁니다

터미널이 종료되면 출력 버퍼가 사라져서 `--cursor 0`으로 읽어도 빈 결과가 옵니다. 완료 신호와 출력을 동시에 얻으려면 명령에서 출력을 파일로 돌리고 `2>&1`로 오류까지 담습니다. macOS에서 종료를 이어 붙일 때는 `& exit`이 아니라 `; exit`을 써야 합니다. `&`는 백그라운드라 zsh가 첫 `exit`을 거부합니다.

### 정답 3 — 재시도 대신 버리고 다시 만듭니다

절반쯤 작업한 에이전트가 같은 지시를 또 받으면 중복 작업을 하거나 자기 결과를 되돌립니다. 먼저 `terminal read`로 화면을 읽어 무엇을 기다리는지 확인합니다. 승인 대기라면 그 화면을 보고 답하고, 원인을 모르겠으면 워크트리를 지우고 새로 만듭니다. 격리의 값어치가 버리는 비용이 싸다는 데 있습니다.
