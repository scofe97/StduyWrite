# 내장 브라우저 자동화 — 스냅샷으로 보고 나서 누른다
---
> 명령의 3분의 1이 브라우저에 몰려 있는 이유는 ORCA가 코드 수정과 화면 확인을 한 세트로 보기 때문입니다. 선택자를 맞히는 대신 화면을 먼저 읽고 그 안에서 고르는 방식이라, 에이전트가 쓰기에 자연스럽습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 스냅샷 기반 조작이 선택자 방식과 무엇이 다르고 왜 에이전트에게 맞는지 설명할 수 있습니다.
2. ref가 언제 유효하고 언제 무효가 되는지 판단해 불필요한 재스냅샷을 줄일 수 있습니다.
3. 브라우저 명령의 `runtime_unavailable` 오류를 앱 문제로 오해하지 않고 원인을 짚을 수 있습니다.
4. 원서가 공개한 결함들을 자기 설치본에서 다시 확인하는 절차를 실행할 수 있습니다.

데스크톱 앱과 모바일 화면 조작은 [04-02](04-02.화면 밖 자동화 — 컴퓨터 유즈·에뮬레이터·예약 실행.md)에서 다룹니다.



## 1. 선택자를 맞히는 대신 화면을 먼저 읽습니다

> 사람은 개발자 도구를 열어 선택자를 확인하지만 에이전트는 그럴 수 없습니다. 순서를 뒤집어 화면에 무엇이 있는지 먼저 받습니다.

![선택자 방식과 스냅샷 방식의 순서 대비](_assets/04-01-snapshot-vs-selector.svg)

선택자 방식의 문제는 화면을 모르는 상태에서 이름을 맞혀야 한다는 점입니다. `#login-button`이 실제로 있는지는 열어 봐야 압니다.

스냅샷 방식은 읽고 → 고르고 → 다시 읽는 순환입니다. 조작한 뒤 다시 읽으면 그 결과가 같은 형식으로 돌아오므로, 검증에 별도 도구가 필요 없습니다.

이 순환이 에이전트에게 자연스러운 이유가 하나 더 있습니다. **스냅샷이 HTML이 아니라 접근성 트리**라 짧습니다. 계측용으로 만든 로그인 페이지를 찍어 보면 이렇습니다.[^snap]

```bash
orca snapshot --json
```

```bash
- form
  - heading "my-app 로그인" [level=1, ref=e1]
  - LabelText
    - StaticText "아이디 "
    - textbox "아이디" [ref=e4]
  - button "로그인" [ref=e2]
  - combobox "요금제" [expanded=false, ref=e3]: free
  - status
  - StaticText "clicks=0"
```

`div`나 `span` 같은 껍데기가 빠지고 역할과 이름만 남습니다. 화면 낭독기가 보는 구조와 같습니다. 같은 페이지의 HTML보다 훨씬 짧아 에이전트에게 넘길 때 토큰을 아낍니다.

응답은 두 형태로 같은 정보를 줍니다. `refs`는 `e1` → `{name, role}` 맵이라 기계가 쓰기 좋고, `snapshot`은 트리 텍스트라 읽기 좋습니다.

`e1`·`e2` 같은 값을 ref라고 부르고 이 번호로 조작합니다.



## 2. 조작하고 다시 읽으면 검증이 끝납니다

> 입력값과 상태 변화가 다음 스냅샷의 트리에 그대로 반영됩니다. "성공 메시지가 떴는가"를 별도 명령 없이 확인할 수 있습니다.

![조작 후 스냅샷에 반영되는 값·마스킹·상태 영역](_assets/04-01-verify-loop.svg)

조작 명령은 ref를 받습니다.

```bash
orca fill  --element e4 --value "demo"  --json   # { "filled": "e4" }
orca click --element e2                  --json   # { "clicked": "e2" }
```

다시 스냅샷을 찍으면 세 가지가 확인됩니다. 입력란에 값이 들어갔고, **비밀번호는 마스킹돼 평문이 실리지 않으며**, `status` 영역에 결과 메시지가 나타납니다.

두 번째가 보안 면에서 반갑습니다. 에이전트가 스냅샷을 읽어도 비밀번호를 알 수 없습니다. 다만 입력에 쓴 명령줄에는 값이 그대로 남으므로, 그쪽 로그를 남길 때는 주의가 필요합니다.

세 번째가 검증의 핵심입니다. 픽셀을 비교하거나 별도 단언 도구를 붙이지 않아도, 스냅샷 텍스트에 기대한 문구가 있는지만 보면 됩니다. 폰트나 렌더링 차이로 인한 오탐이 없어서 회귀 점검에는 오히려 이쪽이 안정적입니다.

`fill`이 안 먹는 커스텀 입력란이 있습니다. 그때는 포커스를 준 뒤 삽입합니다.

```bash
orca focus --element e4 --json
orca inserttext --text "demo" --json
```



## 3. ref가 언제 무효가 되는가

> 값만 바뀌는 조작에서는 유지됩니다. 페이지가 이동하거나 구조가 크게 바뀌면 무효가 됩니다.

![ref 가 유지되는 조작과 무효가 되는 조작](_assets/04-01-ref-lifetime.svg)

매번 재스냅샷할 필요는 없습니다. 입력하고 클릭해도 페이지 이동이 없으면 ref가 그대로 유효합니다. 반대로 `goto`나 링크 클릭으로 이동하면, 탭을 전환하면, 모달이 열려 구조가 바뀌면 무효가 됩니다.

ref는 **탭 단위**로 부여됩니다. 탭 A의 `e2`와 탭 B의 `e2`는 다른 요소입니다.

무효해지면 `browser_stale_ref`가 나므로 그때 다시 찍으면 됩니다.

ref를 모른 채 역할이나 텍스트로 찾아 바로 조작할 수도 있습니다.

```bash
orca find --locator role --value button --action click --json
```

이름이 `find`라 찾기만 할 것 같지만 **찾아서 바로 조작하는** 명령이라 `--action`이 필수입니다. 빼면 `Missing required --action`으로 거부됩니다. 요소가 수백 개인 페이지에서 특정 버튼 하나만 필요할 때 스냅샷보다 빠릅니다.



## 4. "런타임이 끊겼다"는 오류를 믿지 마세요

> 스냅샷을 찍지 않고 요소를 건드리면 앱을 재시작하라는 메시지가 나옵니다. 재시작할 필요가 없습니다.

<!-- no-diagram: 오류 메시지 하나를 어떻게 읽을지 다루는 절이라 그릴 구조가 없습니다. 원인과 대처는 아래 두 줄 점검이 전부입니다. -->

새 탭을 열고 스냅샷 없이 바로 요소를 읽으려 하면 이렇게 나옵니다.

```bash
orca get --element e1 --what text --json
# "code": "runtime_unavailable"
# "message": "The Orca runtime closed the connection before responding. Restart Orca and try again."
```

실제 원인은 **그 탭에 ref가 아직 만들어지지 않은 것**입니다. `e1`이 어느 요소인지 ORCA가 모르는 상태인데, 메시지는 런타임 문제라고 안내합니다. [01-02](01-02.ORCA의 구성 — 앱·런타임·CLI·워크트리.md)에서 본 것과 같은 패턴입니다.

브라우저 명령에서 이 오류를 만나면 앱을 의심하기 전에 두 가지를 봅니다.

1. `--json`을 붙였는가
2. `snapshot`을 먼저 찍었는가

`orca status --json`을 실행해 보면 대개 `ready`입니다.

나머지 오류는 회복 절차가 단순합니다.

| 오류 | 대처 |
|------|------|
| `browser_no_tab` | `tab create --url <주소>` |
| `browser_stale_ref` | `snapshot` 다시 찍고 재시도 |
| `browser_tab_not_found` | `tab list`로 pageId 확인 |



## 5. 원서가 공개한 결함을 다시 확인했습니다

> 원서는 `orca click`이 성공을 반환하면서 이벤트를 전달하지 않는다고 공개 편에 정오까지 실었습니다. v1.4.188에서는 재현되지 않았습니다.

![원서가 공개한 브라우저 결함 넷의 v1.4.188 재현 여부](_assets/04-01-defect-recheck.svg)

원서는 v1.4.163부터 v1.4.176까지 `orca click`이 깨져 있다고 밝히고, 06장 실습이 그대로는 동작하지 않는다는 경고를 머리말에 달았습니다. 버튼에 카운터를 심어 계측한 결과 클릭 이벤트가 도달하지 않았다는 서술입니다.

같은 계측을 v1.4.188에서 다시 했습니다. 버튼에 클릭 카운터를 붙인 페이지를 만들고 채운 뒤 눌렀습니다.

```bash
orca fill  --element e4 --value "demo"     --json   # { "filled": "e4" }
orca fill  --element e5 --value "demo1234" --json   # { "filled": "e5" }
orca click --element e2                     --json   # { "clicked": "e2" }

orca eval --expression "'clicks=' + window.__clicks + ' | ' + document.getElementById('status').textContent" --json
# "clicks=1 | 로그인 성공: demo"
```

**카운터가 1로 올랐고 상태 영역도 갱신됐습니다.** 원서의 대표 정오가 해소된 것입니다.[^click]

나머지 셋은 그대로였습니다.

**`cookie delete`는 이름을 줘도 전부 지웁니다.** 쿠키 세 개를 심고 하나만 지정해 지웠는데 셋 다 사라졌습니다. 응답이 `{"deleted": ...}`가 아니라 `{"cleared": true}`인 것이 힌트입니다. 로그아웃 시뮬레이션에는 그대로 쓸 만하지만, 세션을 살린 채 특정 쿠키만 지우려면 다른 방법이 필요합니다.

**`intercept`는 요청을 가로채지 않습니다.** 모든 패턴을 걸고 `{"routed": "*"}`를 받은 뒤 페이지를 다시 불렀는데 정상 로드됐습니다. `intercept list`와 `network`가 같은 건수를 돌려주는 것도 원서 관찰과 같았습니다. 덧붙이면 v1.4.188의 `intercept`에는 `enable`·`disable`·`list`만 있고 `add`는 없습니다.

**창이 가려지면 `screenshot`이 실패합니다.** `CDP error (Page.captureScreenshot): Screenshot timed out`이 났고, 같은 조건에서 `pdf`는 성공했습니다. **무인 자동화는 정의상 창이 앞에 없는 상태**이므로 증거 수집을 스크린샷에 의존하면 깨집니다.

이 셋을 합치면 증거 체계의 구성이 정해집니다. 스크린샷 대신 **PDF와 스냅샷 텍스트**를 씁니다. 텍스트 비교는 폰트 차이로 인한 오탐이 없어 회귀 점검에 오히려 안정적입니다.

여기서 얻는 교훈이 하나 더 있습니다. 원서가 결함을 감추지 않고 우회와 함께 실었기 때문에, 독자는 자기 버전에서 그것이 아직 살아 있는지 확인할 수 있었습니다. **정오를 공개한 문서가 정오가 없다고 주장하는 문서보다 오래 쓸모 있습니다.**



## 6. 이 노트를 만들 때 실제로 쓴 방식

> 원서 59페이지를 수집한 것이 ORCA 브라우저였습니다. 이 편의 내용이 그대로 쓰인 사례입니다.

<!-- no-diagram: 수집 절차의 단계 관계는 1절 도식의 읽기·고르기 순환과 같고, 여기서는 그 순환이 실제로 어디에 쓰였는지를 밝히는 짧은 서술이라 새로 그릴 형태가 없습니다. -->

원서는 Cloudflare 뒤에 있습니다. `curl`과 일반 HTTP 클라이언트는 403으로 막혔습니다. ORCA의 내장 브라우저는 통과했습니다.

```bash
orca tab create --url "https://wikidocs.net/385916" --json
orca goto --url "https://wikidocs.net/<페이지id>" --json
orca eval --expression "<본문을 마크다운으로 바꾸는 JS>" --json
```

`eval`이 문자열을 표준 출력으로 돌려주므로 셸 루프에 넣어 59페이지를 파일로 받았습니다. 브라우저 자동화 명령이 "코드를 고치고 화면으로 확인하는 고리"만을 위한 것이 아니라, **사람이 손으로 못 하는 수집 작업**에도 그대로 쓰인다는 뜻입니다.

한 가지 주의를 함께 적습니다. 남의 사이트를 자동으로 훑는 일은 그 사이트의 이용 약관과 부하를 함께 봐야 합니다. 이 노트는 공개된 페이지를 사람이 읽는 속도로(요청 사이 간격을 두고) 한 번 수집했고, 수집한 원문을 재배포하지 않았습니다.



## 면접에서 받을 만한 질문

1. 브라우저 자동화에서 CSS 선택자 대신 접근성 트리를 쓰면 무엇이 좋습니까?
2. 조작할 때마다 스냅샷을 다시 찍어야 합니까?
3. 무인 회귀 점검의 증거를 스크린샷으로 남기려 합니다. 괜찮습니까?



## 정답 (자답 후 펼치기)

### 정답 1 — 화면을 모르는 쪽이 먼저 읽을 수 있습니다

선택자는 화면 구조를 이미 아는 사람이 쓰는 방식입니다. 에이전트는 개발자 도구를 열 수 없으므로 이름을 맞혀야 합니다. 접근성 트리는 화면에 무엇이 있는지를 역할과 이름으로 먼저 돌려주므로, 읽고 고르는 순서가 됩니다. 부수 효과로 트리가 HTML보다 훨씬 짧아 토큰을 아끼고, 조작 결과가 같은 형식으로 반영되어 검증에 별도 도구가 필요 없습니다.

### 정답 2 — 값만 바뀌면 유지됩니다

입력하고 클릭해도 페이지 이동이 없으면 ref는 그대로 유효합니다. 페이지 이동, 탭 전환, 모달처럼 구조가 크게 바뀌는 경우에만 무효가 되고, 그때는 `browser_stale_ref` 오류가 알려 줍니다. ref는 탭 단위라 다른 탭의 같은 번호는 다른 요소입니다.

### 정답 3 — 무인 상태에서는 깨집니다

`screenshot`은 브라우저 탭이 보이지 않으면 실패합니다. 무인 자동화는 정의상 창이 앞에 없는 상태이므로 증거가 남지 않습니다. 같은 조건에서 `pdf`는 성공하므로 PDF와 스냅샷 텍스트를 조합해 남깁니다. 텍스트 비교는 폰트나 렌더링 차이로 인한 오탐이 없어 회귀 점검에 더 안정적입니다.
