## 요점

한 줄: 백엔드 장애 메커니즘 10편을 런타임(JVM·OS), 네트워크·캐시 경계, DB 동시성·저장 엔진 세 층으로 묶어 프록시·B+Tree·격리 수준·락 선택·연쇄 장애를 짚습니다.

- 묶음 구성: 10편을 런타임(JVM·OS), 네트워크·캐시 경계, DB 동시성·저장 엔진 세 층으로 나눕니다.
- 프록시: Spring Boot 는 기본으로 CGLIB 클래스 프록시를 만듭니다. 그래서 `final` 클래스·메서드와 내부 호출(`this.inner()`)에는 `@Transactional` 이 걸리지 않습니다.
- B+Tree: 비교 횟수가 아니라 디스크 페이지 읽기 횟수를 줄이려고 트리를 낮게 유지합니다. 인덱스를 늘리면 쓰기와 페이지 분할 비용이 붙습니다.
- 격리 수준: READ COMMITTED 는 같은 SELECT 가 다른 값을 볼 수 있습니다. InnoDB 기본값 REPEATABLE READ 는 동시 쓰기가 몰리면 Gap Lock 경합과 데드락으로 처리량이 떨어진다고 합니다.
- 원문의 권고: 트래픽이 크면 격리 수준을 READ COMMITTED 로 낮추고, 꼭 필요한 경합 지점만 분산 락이나 명시적 행 락으로 막으라고 합니다.
- 락 선택: 우열이 아니라 충돌 빈도로 고릅니다. 충돌이 드문 수정은 낙관적 락, 선착순처럼 한 행에 몰리는 핫스팟은 비관적 락이 낫다고 합니다.
- 원문 사례: 선착순 100명에 낙관적 락과 재시도를 쓰자 쿼리가 5,000번 실행됐다고 적습니다.
- 연쇄 장애: 캐시 동시 만료 → 커넥션 풀 고갈 → 클라이언트 타임아웃과 재시도 → 서버는 포기된 쿼리를 계속 실행하는 고리로 설명합니다.
- 대응 셋: TTL 에 무작위 오프셋, 남은 시간을 `Statement.setQueryTimeout` 과 하위 호출에 전달, `connectionTimeout` 을 짧게 해 빨리 실패하기입니다.
- 커넥션 풀: `maxLifetime` 을 DB `wait_timeout` 보다 짧게 두고 `leakDetectionThreshold` 로 누수를 찾으라고 합니다.
- 타임아웃: 클라이언트 타임아웃은 연결을 포기할 뿐 서버 작업을 취소하지 않습니다. 결제 같은 부작용 작업에는 멱등성 키와 상태 조회 복구가 필요합니다.
- 실행 모델: I/O 위주는 코루틴, CPU 위주는 OS 스레드·병렬 처리, 격리가 필요하면 프로세스를 고릅니다.
- 코루틴 주의: suspend 지점 없이 CPU 를 오래 쓰면 캐리어 스레드가 막혀 다른 코루틴이 굶습니다. CPU 작업은 `Dispatchers.Default` 같은 별도 풀로 뺍니다.
- 스레드 안전성: 스택이냐 힙이냐가 아니라 공유하느냐가 안전성을 정한다고 정리합니다.
- 찾을 키워드: 가상 스레드는 `pinning`, `JEP 491` 입니다. 나머지는 `consistent read`, `locking read`, `Request Coalescing`, `Redisson` 입니다.

## 자료와 실습

- 자료:
  - [Spring Framework Reference — Transaction Management & AOP Proxies](https://docs.spring.io/spring-framework/reference/data-access/transaction.html): `@Transactional` 프록시 동작 원리, Self-invocation 한계, 전파 속성 공식 명세입니다.
  - [MySQL 8.4 Reference Manual — InnoDB Locking and Transaction Model](https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-transaction-model.html): 격리 수준별 잠금(Record Lock, Gap Lock, Next-Key Lock) 및 MVCC 동작 공식 문서입니다.
  - [HikariCP 공식 문서](https://github.com/brettwooldridge/HikariCP): `maxLifetime`, `connectionTimeout`, `leakDetectionThreshold` 권장 설정 가이드입니다.
  - [OpenJDK JEP 444 — Virtual Threads](https://openjdk.org/jeps/444): Java 21 가상 스레드의 Heap 기반 Continuation 스택 구조와 플랫폼 스레드 마운트·언마운트 설계 명세입니다.
  - 『데이터 중심 애플리케이션 설계』: B+Tree 페이지 읽기 비용, 격리 수준별 이상 현상, 클라이언트 타임아웃과 유령 작업을 다룹니다. 리포트는 3장(저장소와 검색)·7장(트랜잭션)·8장(분산 시스템의 골칫거리)을 권합니다. 정독 노트는 2판 기준 저장이 [04-03](../../05_data/book/designing-data-intensive-applications/04-03.B-tree와 LSM 비교.md) 입니다. 트랜잭션은 [08-01](../../05_data/book/designing-data-intensive-applications/08-01.ACID와 트랜잭션 개요.md) 입니다. 분산 시스템은 [09-01](../../05_data/book/designing-data-intensive-applications/09-01.부분 실패와 비신뢰 네트워크.md) 입니다.
  - 『Real MySQL 8.0』 1권 5장(트랜잭션과 잠금)·8장(인덱스): B+Tree 인덱스의 쓰기 비용과 복합 인덱스 컬럼 순서, InnoDB `REPEATABLE READ` 의 갭 락 동작을 실무 쿼리 실행 계획과 연결합니다.
  - 『Java Concurrency in Practice』 1~3장(스레드 안전성과 객체 공유)·10장(활동성 위험: 데드락): 지역 변수(Stack)와 객체 필드(Heap)의 동시성 안전성 차이 및 스레드 풀 크기 산정 원리를 다룹니다. 가상 스레드는 JEP 444 문서로 보완을 권합니다.
  - [AWS Builders' Library — Timeouts, retries, and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/): 타임아웃 설정, 재시도 폭풍 방지, 지수 백오프와 Jitter 를 다룬 아키텍처 아티클입니다.
  - 코드: HikariCP `pool/HikariPool.java`(`getConnection`, `evictConnection`)와 `pool/ProxyConnection.java`(`close()` 풀 반납)를 봅니다. spring-framework `spring-tx/.../TransactionInterceptor.java` 의 `invokeWithinTransaction` 을 봅니다. postgres `src/backend/access/nbtree/`(B+Tree 탐색과 분할)와 `src/backend/storage/lmgr/`(락 매니저)도 봅니다.
- 실습:
  - Level 1: Spring `@Transactional` 의 Self-Invocation 실패 재현 및 HikariCP `leakDetectionThreshold` 경고 로그를 확인합니다. 동일 클래스 내 비-트랜잭션 `outer()`에서 `this.inner()`로 호출해 `getCurrentTransactionName()`으로 프록시 우회를 확인합니다. `leak-detection-threshold=2000` 설정 뒤 `close()` 없이 3초 대기해 누수 스택 트레이스를 확인합니다.
  - Level 2: 재고 100개 차감 시나리오에서 `@Version` 낙관적 락(재시도 포함)과 비관적 락(`PESSIMISTIC_WRITE`)의 완료 시간과 쿼리 수를 500명 동시 요청으로 비교합니다. 캐시에 `TTL = baseTTL + Random(-10%, +10%)`을 적용하고 `CompletableFuture` 맵 기반 요청 병합(Request Coalescing)을 구현합니다.
  - Level 3: `X-Request-Deadline` 헤더의 남은 시간을 파싱해 1.5초 경과 시 쿼리와 외부 API 호출 전에 중단하는 인터셉터를 구현합니다. 결제 승인 API 에 `Idempotency-Key` 테이블과 상태 조회 복구를 두고, 카오스 테스트(외부 지연 10초)에서 정상 조회 응답 시간이 유지되는지 검증합니다.



## 경고

- ⚠ 영상 수·출처 표시: 원문은 "10개 영상" 이라고 하지만 분석 대상에는 9개 주제가 있습니다. 출처 표시(` `)도 비어 있어 주장을 영상과 맞댈 수 없습니다.
- ⚠ Gap Lock 범위: "REPEATABLE READ 는 Gap Lock 으로 팬텀을 막는다" 는 잠그는 읽기·쓰기에 해당합니다. 일반 SELECT 는 잠금 없이 MVCC 스냅샷으로 읽습니다(확인하지 않음).
- ⚠ 일반화: "격리 수준을 READ COMMITTED 로 낮추는 것이 표준 패턴" 은 원문의 일반화입니다. 정합성 책임을 애플리케이션으로 옮기는 결정이라 도메인마다 다릅니다.
- ⚠ 수치: "100명 처리에 5,000번 쿼리", "OS 스레드 스택 약 1MB" 는 원문 수치입니다. 스택 기본 크기는 OS·JVM 설정(`-Xss`)에 따라 다릅니다.
- ⚠ `maxLifetime` 여유: "wait_timeout 보다 30초~1분 짧게" 는 원문 수치입니다. HikariCP 문서의 권장 문구와 대조하지 않았습니다.
- ⚠ 가상 스레드 스택: "스택 프레임을 Heap 에 적재" 는 언마운트됐을 때의 이야기입니다. 실행 중에는 캐리어 스레드 위에서 돕니다(확인하지 않음, [JEP 444](https://openjdk.org/jeps/444)).
- ⚠ 책 장 번호: 원문은 DDIA 3·7·8장(저장·트랜잭션·분산 시스템의 골칫거리)을 듭니다. 노트로 정리한 2판에서는 4·8·9장입니다. 저장은 [04-03](../../05_data/book/designing-data-intensive-applications/04-03.B-tree와 LSM 비교.md) 입니다. 트랜잭션은 [08-01](../../05_data/book/designing-data-intensive-applications/08-01.ACID와 트랜잭션 개요.md) 입니다. 분산 시스템은 [09-01](../../05_data/book/designing-data-intensive-applications/09-01.부분 실패와 비신뢰 네트워크.md) 입니다.
- ⚠ 도서 연식: 『Java Concurrency in Practice』 는 2006년 책이라 가상 스레드는 JEP 444 로 보완해야 한다고 원문도 적었습니다.
