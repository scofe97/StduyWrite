## 요점

한 줄: 빌드마다 비는 Docker 캐시를 프로젝트별 EBS 볼륨 N개를 돌려 쓰는 풀로 살리고, Docker 29 의 containerd image store 기본값이 낸 쓰기 폭증을 overlay2 고정으로 푼 사례입니다.

- 문제: 사내 플랫폼은 Argo Workflows 로 빌드마다 새 컨테이너를 띄웁니다. 깨끗하고 확장하기 쉽지만 `/var/lib/docker` 가 매번 비어 빌드 캐시가 사라집니다.
- Remote Cache 실패: S3·ECR 로 캐시를 압축·전송하는 방식은 작은 프로젝트에서는 빠릅니다. 캐시가 큰 무거운 프로젝트에서는 압축·해제와 전송 비용이 아낀 빌드 시간보다 커서 오히려 느려졌습니다.
- V1: 프로젝트마다 EBS 볼륨 하나를 동적 프로비저닝해 빌드 컨테이너의 `/var/lib/docker` 에 붙였습니다. 로컬 빌드처럼 디렉터리를 그대로 남기니 압축·전송이 없어집니다. 발표는 전사 평균 30% 이상, 최대 91% 단축이라고 했습니다.
- V1 한계: EBS 는 Pod 하나에만 붙고, Docker 데몬 둘이 같은 `/var/lib/docker` 를 함께 쓸 수도 없습니다. 같은 프로젝트에서 빌드가 겹치면 먼저 시작한 빌드만 캐시를 쓰고 나머지는 처음부터 빌드합니다.
- 버린 대안: 일반 스냅샷 복원은 블록을 S3 에서 늦게 읽어 첫 I/O 가 느립니다. Volume Initialization 은 오래 걸리고, FSR 은 빠르지만 비싸고 한도가 있습니다.
- V2: 커밋 20번 중 19번은 아래쪽 의존성 레이어가 바뀌지 않는다는 통계를 근거로, 프로젝트마다 볼륨 N개를 두고 돌려 씁니다. 최신이 아닌 캐시를 써도 대부분 맞습니다. 발표는 캐시 미스 30회 → 11회, V1 대비 평균 16% 추가 단축이라고 했습니다.
- 트러블슈팅: V2 뒤 가벼운 프로젝트의 빌드 시간 중앙값이 오르고 EBS 쓰기가 최대 500배 늘었습니다. 원인은 Docker 29 가 빈 데이터 디렉터리에서는 containerd image store 를 기본으로 쓰는 동작이었습니다. 새로 만든 빈 볼륨마다 이 모드로 시작했고, 빌드 결과를 언팩하는 쓰기가 늘었습니다.
- 해결: `daemon.json` 에 `"features": {"containerd-snapshotter": false}` 를 두어 graph driver(overlay2)로 고정했습니다.
- 관측 교훈: 평균은 무거운 프로젝트의 큰 개선에 가려 다수의 작은 프로젝트가 느려진 것을 숨깁니다. 중앙값·백분위수와 디스크 쓰기 지표를 함께 봐야 합니다.
- Dockerfile 패턴: `go.mod`·`go.sum` 을 먼저 복사해 의존성을 받고 소스는 나중에 복사합니다. `RUN --mount=type=cache` 로 `/go/pkg/mod` 와 빌드 캐시를 남깁니다.
- 찾을 키워드: `buildkit cache mount sharing=locked`, `containerd-snapshotter false`, `EBS volume initialization`, `buildkitd daemon pool` 입니다.

  - 『Kubernetes in Action』 2판: 리포트는 6장(볼륨)·16장(고급 스케줄링)을 권합니다. 동적 PVC 마운트를 통한 캐시 영속화와 AZ 종속성을 다룹니다. [정독 노트](../../08_cloud/book/kubernetes-in-action/README.md) 에서 볼륨은 09-01 입니다. PV·PVC 와 동적 프로비저닝은 [10-01.PV·PVC·StorageClass와 동적 프로비저닝](../../08_cloud/book/kubernetes-in-action/10-01.PV·PVC·StorageClass와 동적 프로비저닝.md) 입니다.
  - 『Continuous Delivery』: 리포트는 1~3장(배포 파이프라인과 빌드 자동화)과 13장(인프라 및 환경 관리)을 권합니다. 빌드 파이프라인 피드백 루프 단축과 상태 오염 방지 원칙입니다.
  - 코드: [moby/buildkit](https://github.com/moby/buildkit) 의 `cache/manager.go`(로컬 캐시 메타데이터 DB 인덱싱)와 `executor/oci/`(`--mount=type=cache` 바인딩)를 봅니다. [docker/buildx](https://github.com/docker/buildx) 의 `build/build.go`·`driver/`(캐시 파이프라인)를 봅니다. [argoproj/argo-workflows](https://github.com/argoproj/argo-workflows) 의 `workflow/controller/operator.go`(PVC 마운트와 생명주기 관리)도 봅니다.
- 실습:
  - Level 1: BuildKit Cache Mount 와 레이어 무효화 차이를 검증합니다. 의존성 파일(`package.json` 또는 `go.mod`)을 1줄 수정하고 일반 빌드와 `--mount=type=cache` 적용 빌드의 소요 시간을 `time docker build` 로 비교합니다. 함정은 구버전 환경에서 `--mount` 문법 에러가 날 수 있어 `DOCKER_BUILDKIT=1` 환경변수를 켜야 한다는 점입니다. 완료: 의존성 레이어가 무효화되더라도 재다운로드 없이 캐시 디렉터리에서 복원되는 로그(`CACHED`)를 확인합니다.
  - Level 2: `overlay2` 와 containerd image store 의 I/O 를 비교합니다. 동일한 이미지를 빌드하며 `/etc/docker/daemon.json` 의 `"containerd-snapshotter"` 를 `false` 와 `true` 로 두고 `iostat -xm 1` 로 쓰기량과 `unpacking` 로그를 비교합니다. 완료: `containerd-snapshotter: true` 환경에서 이미지 패킹과 언패킹으로 디스크 쓰기 I/O 와 지연이 추가로 생김을 수치로 입증합니다.
  - Level 3: 쿠버네티스 환경에서 LRU 기반 PVC 캐시 풀 스케줄러를 구현합니다. Go 와 `client-go` 로 유휴 PVC 를 조회하고 `last-used-timestamp` 어노테이션 기준으로 가장 최근에 사용된 볼륨을 골라 Job 매니페스트를 만듭니다. 함정은 동시 빌드 요청 때 같은 유휴 PVC 를 중복 선택하는 경쟁 상태로, `resourceVersion` 기반 낙관적 락을 적용해야 합니다. 완료: 3개 빌드가 서로 다른 PVC 를 충돌 없이 마운트하고 4번째 빌드는 먼저 끝난 첫 번째 PVC 를 재사용함을 검증합니다.



## 경고

- ⚠ 원문은 볼륨 선택을 "가장 최근에 사용된 볼륨부터 고르는 LRU"라고 부릅니다. 가장 최근에 쓴 것을 고르는 것은 MRU 이고, LRU 는 가장 오래 안 쓴 것을 고르는 정책입니다. 이름과 동작이 반대입니다.
- ⚠ 원문은 FSR 을 "메모리 기반 프리로딩, 계정당 기본 20개"라고 설명합니다. 이전 요약은 공식 문서로 FSR 이 완전 초기화 볼륨을 만드는 기능이고 한도는 리전당 5개라고 확인했습니다. — 확인됨: [EBS Fast Snapshot Restore](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-fast-snapshot-restore.html) ([인프라 발표 5편 요약](2026-10-10_당근_빌더_밋업_2026_인프라_발표_5편.md) 경고)
- ⚠ Docker 29 새 설치의 기본 저장소가 containerd image store 라는 점은 확인됐습니다. "OCI 로 패킹했다가 다시 언패킹한다"는 세부 동작과 500배라는 수치는 발표·원문 설명이고 확인하지 않았습니다. — 확인됨(기본값 부분만): [containerd image store](https://docs.docker.com/engine/storage/containerd/)
- ⚠ 원문은 containerd image store 가 런타임 노드의 Lazy Pulling 에 유리하다고 합니다. Lazy Pulling 은 stargz·SOCI 같은 별도 snapshotter 가 하는 일이라 기본 설정만으로 생기지 않습니다. 확인하지 않았습니다.
- ⚠ 원문 `daemon.json` 예시의 `max-concurrent-uploads`·로그 옵션은 발표와 관계없는 원문 추가입니다. 발표의 해결은 `containerd-snapshotter: false` 하나입니다.
- ⚠ 대안 비교표(Docker Build Cloud "완벽 지원", 비용 평가 등)는 출처가 없는 원문 평가입니다.
- ⚠ Kaniko 는 원 저장소가 2025-06-03 보관됐고 chainguard 포크가 이어 갑니다. 원문은 이 사실 없이 대안으로 비교합니다. — 확인됨: [kubernetes-patterns 30-01](../../08_cloud/book/kubernetes-patterns/30-01.Image Builder — 클러스터 안에서 이미지를 빌드하기.md) (2026-11-14 확인 기록)
- ⚠ 원문은 『Kubernetes in Action』 2판 추천 범위를 6장(볼륨)·16장(고급 스케줄링)으로 적었습니다. 지금 노트 기준으로 볼륨은 9장, PV·PVC 는 10장입니다.
- ⚠ 『Continuous Delivery』 13장 범위는 확인하지 않았습니다.
- ⚠ 성과 수치(30%·91%·16%·64%, 미스 30 → 11회, 커밋 19/20)는 발표 수치이고 원문 영상과 대조하지 않았습니다.
