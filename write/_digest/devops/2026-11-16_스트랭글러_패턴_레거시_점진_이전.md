## 요점

한 줄: 15년 된 쇼핑몰 모놀리스를 한 번에 다시 짜는 빅뱅 재작성 대신, 기능 단위로 트래픽을 옮겨 옛 시스템이 스스로 불필요해지게 하라는 영상입니다.

- 순서: 코드를 고치기 전에 라우팅 계층부터 세워 트래픽 제어권을 잡습니다. 그다음 상품 검색처럼 경계가 뚜렷한 기능부터 떼고, 주문·결제는 뒤로 미룹니다.
- 가역성: 문제가 나면 몇 달 작업을 되돌리는 대신 라우팅 규칙 하나를 옛 시스템으로 돌립니다.
- 끝내기: 트래픽을 100% → 80% → 0% 로 줄여 옛 시스템이 아무 일도 하지 않게 된 뒤에 끕니다.
- 가장 큰 실패: 30~50% 만 옮기고 멈추면 두 아키텍처의 모니터링·배포·디버깅을 계속 떠안는다고 경고합니다.
- 쓰지 않을 때: 시스템이 작거나, 점검 시간에 끄고 일괄 이관할 수 있거나, 끝까지 옮길 인력이 없으면 단순 교체가 낫다고 합니다.
- 데이터: 데이터 계획 없이 코드만 옮기지 말라고 합니다. 리포트는 앱의 이중 쓰기 대신 CDC 로 옛 DB 의 로그를 복제하라고 보완합니다.
- 찾을 키워드: `Parallel Run`, `Event Interception`, `Kubernetes Gateway API`, `Database-per-Service` 입니다.

## 자료와 실습

- 자료:
  - [Fowler 「Strangler Fig Application」](https://martinfowler.com/bliki/StranglerFigApplication.html): 패턴의 원전입니다.
  - [Azure Strangler Fig pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/strangler-fig): 적용 절차와 주의점입니다.
  - [AWS Prescriptive Guidance](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/strangler-fig.html): 프록시로 경로를 옮기는 구현 예시입니다.
  - 『Monolith to Microservices』 3·4장: 모놀리스를 쪼개는 패턴과 데이터베이스 분리입니다.
  - Evans 『Domain-Driven Design』 14장: 모델 무결성과 Context Map, 충돌 방지 계층입니다.
  - 『Designing Data-Intensive Applications』 5·11장(1판 기준): 복제와 CDC 입니다. 정독 노트 [DDIA 2판](../../05_data/book/designing-data-intensive-applications/README.md) 에서는 6·12장입니다.
  - [Fowler 「Patterns of Legacy Displacement」](https://martinfowler.com/articles/patterns-legacy-displacement/): 점진 이전 패턴 모음입니다.
  - [Shopify 「Deconstructing the Monolith」](https://shopify.engineering/deconstructing-monolith-designing-software-maximizes-developer-productivity): 모듈러 모놀리스로 간 실제 사례입니다.
  - 코드: envoy `api/envoy/config/route/v3/route_components.proto`(`WeightedCluster`·`RequestMirrorPolicy`)와 Debezium 커넥터를 봅니다. istio `pilot/pkg/networking/core/v1alpha3/route/` 도 봅니다.
- 실습:
  - Level 1: NGINX 로 `/search` 만 새 서비스로 돌립니다. 완료: 설정을 되돌려 5초 안에 옛 경로로 롤백됩니다.
  - Level 2: Envoy 가중치로 10% → 100% 카나리를 걸고 미러링으로 새 서비스를 미리 시험합니다. 함정은 미러된 요청의 부수 효과(중복 쓰기)입니다. 완료: Grafana 에 옛·새 서비스 트래픽이 반대 곡선으로 보입니다.
  - Level 3: PostgreSQL → Debezium → Kafka 로 상품 데이터를 복제하고 소유권을 넘깁니다. 함정은 초기 스냅샷과 스트림 사이의 순서입니다. 완료: 새 서비스가 유일한 원본이 됩니다.



## 경고

- ⚠ 다크 런치와 미러링: 리포트는 응답을 버리는 복제를 "다크 런칭" 으로 부릅니다. 노트의 istio 5장은 헤더로 고른 실사용자에게 보내는 다크 런치와 응답을 버리는 미러링을 따로 다룹니다.
- ⚠ 롤백 범위: "라우팅 규칙 하나로 초 단위 롤백" 은 새 서비스가 아직 데이터를 소유하지 않을 때만 맞습니다. 쓰기 소유권을 넘긴 뒤에는 새 저장소의 데이터를 옛 쪽으로 되돌려야 합니다.
- ⚠ 미러링 부수 효과: 복제한 요청이 새 시스템에서 주문 생성·결제 호출을 일으킬 수 있어, 쓰기 경로에는 그대로 쓰지 못합니다. 리포트 Level 2 에도 같은 주의가 있습니다.
- ⚠ 원전 연도: 원문은 Fowler 글을 "2004 / Updated" 로 적습니다. 처음 이름은 Strangler Application 이었고 뒤에 Strangler Fig Application 으로 바꿨다고 알려져 있습니다(확인하지 않음).
- ⚠ 책 장 번호: 원문은 DDIA 5·11장(복제·스트림 처리)을 듭니다. 노트로 정리한 2판에서는 6·12장이고, CDC 는 위 DDIA 12-02 입니다.
- ⚠ 리포트 보완: ACL·Outbox·Saga·CDC 는 영상이 아니라 리포트가 덧붙인 "심층 보완" 입니다. 소스 경로(Envoy proto, Istio pilot)도 확인하지 않았습니다.
