## 요점

한 줄: SBOM 은 소프트웨어에 무엇이 들었는지 적은 구성 목록이고 SLSA 는 그 소프트웨어가 믿을 만한 과정으로 만들어졌는지 증명하는 체계라서, 둘은 경쟁하지 않고 서명·어드미션 컨트롤과 묶여 하나의 공급망 보안을 이룹니다.

- SBOM: 의존 라이브러리와 버전을 표준 형식으로 적은 목록입니다. `jackson-databind` 에 CVE 가 나면 어느 서비스·이미지가 어떤 버전을 직접·간접으로 쓰는지 바로 찾습니다.
- SBOM 표준: SPDX(Linux Foundation, 라이선스·컴포넌트 정보)와 CycloneDX(OWASP, 보안·공급망 분석)가 있습니다. 생성 도구는 Syft·Trivy 입니다.
- SLSA 가 막는 것: 소스에 악성 코드가 들어가거나, CI 가 뚫려 결과물이 바뀌거나, 소스와 다른 결과물이 배포되거나, 레지스트리에 악성 이미지가 올라가는 경우입니다. CI 자동화만으로는 결과물의 신뢰가 보장되지 않습니다.
- Provenance: 어떤 저장소·ref 에서, 어떤 빌더가, 어떤 실행(`invocationId`)으로 만들었고 산출물 SHA-256 이 무엇인지 적은 출처 증명입니다(`buildDefinition`·`runDetails`·`subject`).
- SLSA Build 트랙: L1 은 provenance 생성, L2 는 인증된 빌드 플랫폼에서 생성, L3 는 빌드 플랫폼 강화와 빌드 격리입니다. SLSA 에는 Build 말고 Source 트랙도 있습니다.
- 네 용어 구분:
  - SBOM 은 구성 요소를, provenance 는 빌드 출처를 설명합니다.
  - 서명은 산출물·증명이 서명 뒤 바뀌지 않았음을 검증합니다.
  - attestation 은 어떤 사실을 검증 가능하게 주장한 증명 자료입니다.
- 파이프라인: 소스 → 빌드(Syft·Trivy 로 SBOM, SLSA·in-toto 로 provenance) → Cosign·Sigstore 서명 → 레지스트리(Harbor·ECR) → Kubernetes 어드미션 컨트롤에서 검증 실패 시 배포 차단입니다.
- 학습 순서:
  - SBOM(SPDX·CycloneDX·Syft) → 취약점 스캔(CVE·CVSS·Grype·Trivy) → 서명(Cosign·Sigstore) 순으로 갑니다.
  - 이어서 provenance(SLSA·in-toto) → 어드미션 컨트롤(Kyverno·OPA Gatekeeper) → 공급망 공격(dependency confusion·typosquatting·빌드 변조)입니다.
- 출발 질문: 배포한 이미지가 의도한 소스 코드로 만들어졌음을 어떻게 증명할까입니다.

## 자료와 실습

- 자료:
  - [SLSA](https://slsa.dev/): Build·Source 트랙과 레벨별 요구, provenance 형식의 정본입니다.
  - [CycloneDX](https://www.cyclonedx.org/)·[SPDX](https://spdx.dev/): 두 SBOM 표준의 명세입니다.
  - [Sigstore](https://docs.sigstore.dev/): Cosign 키리스 서명과 투명성 로그입니다.
  - [in-toto](https://in-toto.io/): 공급망 단계별 attestation 형식입니다.
- 실습:
  - 프로젝트: Secure Image Pipeline 입니다.
  - 1~4단계: Spring Boot 나 Go 앱을 이미지로 빌드하고 Syft 로 SBOM 을 만든 뒤 Trivy 로 CVE 를 검사합니다.
  - 5~8단계: Cosign 서명과 SLSA provenance 를 만들어 Harbor 에 이미지와 함께 저장합니다. 완료: Kubernetes 어드미션 정책이 검증되지 않은 이미지 배포를 막습니다.



## 경고

- ⚠ SLSA 레벨 판본: 리포트는 v1.0 Build 트랙 L1~L3 로 설명합니다. [배포 전략](../../07_devops/book/cicd_cicd-patterns/06-01.Deployment Strategies for Structural Patterns.md) 노트는 L0~L3 와 "호스팅된 빌드 서비스" 로 적어 판본이 다릅니다. 레벨별 요구는 [SLSA 명세](https://slsa.dev/)와 대조하지 않았습니다.
- ⚠ Source 트랙: 리포트는 SLSA 에 Source 트랙이 있다고만 적습니다. 그 트랙의 정식 판본과 레벨은 확인하지 않았습니다.
- ⚠ provenance 예시: 리포트 스스로 "개념 설명용 축약형" 이라고 밝힙니다. `buildType: jenkins-build` 같은 값은 실제 형식이 아닙니다.
- ⚠ 표준 성격: SPDX 는 라이선스, CycloneDX 는 보안이라는 구분은 출발점의 차이를 단순화한 말입니다. 두 형식 모두 지금 다루는 범위를 확인하지 않았습니다.
- ⚠ 링크 정리: 공식 자료 링크 끝의 유입 추적 매개변수를 뗐습니다.
