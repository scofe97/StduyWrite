## 요점

한 줄: 캐싱은 컴퓨터를 빠르게 하는 기술이 아니라 불필요한 반복 작업을 피하는 설계이고, DB 는 여전히 유일한 원본(Source of Truth)이라고 봅니다.

- 비유: 도서관 사서가 지하 서고(DB)의 책을 책상(캐시)에 올려 두고 다음 사람에게 바로 답합니다. 책상이 좁아 무엇을 내릴지 정하는 것이 축출입니다.
- 사용자 반응: 느린 앱은 어느 정도 참지만 틀린 데이터(옛 가격, 이미 팔린 좌석)를 보여 주는 앱은 떠난다고 강조합니다.
- TTL 과 무효화: TTL 은 단순하지만 만료 전까지 옛 값이 보이고, 무효화는 정확하지만 쓰기 경로가 복잡해집니다. 데이터마다 오차 허용 범위로 고르라고 합니다.
- 고르는 기준: 게시글·추천 목록은 짧은 TTL 로 둡니다. 잔여 좌석·계좌 잔액·특가 재고는 즉시 무효화합니다.
- 다층 캐시: 아마존 홈페이지 요청이 Browser → CDN → Redis → DB 로 내려가고, 뒤따르는 요청은 앞 계층에서 끝나는 흐름을 따라갑니다.
- 장애 3패턴(리포트 보완): Stampede 는 락이나 확률적 조기 갱신으로 막습니다. Penetration 은 Null 캐싱·Bloom Filter 로, Avalanche 는 TTL Jitter 로 막습니다.
- 운영(리포트 보완): `maxmemory` 와 `maxmemory-policy` 를 정하지 않으면 메모리가 찼을 때 쓰기 오류가 난다고 합니다.
- 찾을 키워드: `maxmemory-samples`, `stale-while-revalidate`, `singleflight`, `XFetch`, `Redlock` 입니다.

## 자료와 실습

- 자료:
  - [Redis eviction](https://redis.io/docs/latest/develop/reference/eviction/): `maxmemory` 정책과 근사 LRU·LFU 동작을 확인합니다.
  - [MDN HTTP caching](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching): `Cache-Control`·검증 헤더·`stale-while-revalidate` 를 봅니다.
  - [AWS Database Caching Strategies Using Redis](https://docs.aws.amazon.com/whitepapers/latest/database-caching-strategies-using-redis/welcome.html): Cache-Aside·Write-Through 같은 전략을 비교합니다.
  - 『Designing Data-Intensive Applications』 5·11장(1판 기준): 복제 지연과 스트림 기반 캐시 무효화입니다. 정독 노트 [DDIA 2판](../../05_data/book/designing-data-intensive-applications/README.md) 에서는 6·12장입니다.
  - 『System Design Interview』 1·5장: 규모 확장의 캐시 층과 안정 해시입니다. 정독 노트 [system-design](../../03_architecture/book/system-design/README.md) 이 있습니다.
  - 『High Performance Browser Networking』 1~2장·11장: 지연의 물리 한계와 HTTP 캐시입니다. 웹 판이 [hpbn.co](https://hpbn.co/) 에 있습니다.
  - [Scaling Memcache at Facebook (NSDI 2013)](https://www.usenix.org/conference/nsdi13/technical-sessions/presentation/nishtala): 대규모 캐시에서 stale set 과 몰림을 막는 사례입니다.
  - [Cloudflare 「What is caching?」](https://www.cloudflare.com/learning/cdn/what-is-caching/): CDN 캐시 입문 글입니다.
  - 코드: caffeine `BoundedLocalCache.java`(W-TinyLFU)와 redis `src/evict.c`·`src/expire.c`(근사 LRU·만료)를 봅니다. mcrouter `mcrouter/routes/`(라우팅)도 봅니다.
- 실습:
  - Level 1: 해시맵과 이중 연결 리스트로 LRU + TTL 캐시를 직접 구현합니다. 완료: get·put 이 O(1) 이고 적중률을 시험으로 확인합니다.
  - Level 2: Cache-Aside 에서 갱신과 조회가 겹치는 경합을 k6 로 재현합니다. 완료: 커밋 뒤 삭제(afterCommit)와 짧은 TTL 로 DB·캐시 불일치가 0% 가 됩니다.
  - Level 3: 인기 키가 만료될 때의 Stampede 를 재현하고 singleflight·2계층 캐시를 붙입니다. 완료: 동시 요청에도 DB 쿼리가 1건이고 P99 가 90% 줄어듭니다.



## 경고

- ⚠ 100ms 와 매출 1%: 아마존 사례는 널리 인용되지만 공식 자료가 아니라 전 직원의 발표·회고에서 나온 수치입니다(확인하지 않음).
- ⚠ 커밋 뒤 삭제의 한계: 커밋 뒤에 지워도, 커밋 전 옛 값을 읽은 요청이 늦게 `SET` 하면 옛 값이 남습니다. 리포트의 "불일치 0% 수렴" 은 짧은 TTL 같은 안전망을 함께 둔다는 가정입니다.
- ⚠ 장애 패턴 이름: Penetration·Avalanche 는 주로 중국어권 글에서 쓰는 이름이라, 글마다 정의가 조금씩 다릅니다.
- ⚠ 표본 수: Redis 근사 LRU 가 기본 5개 키를 표본으로 뽑는다는 설명(`maxmemory-samples`)은 원문 설명입니다. 실행 중인 Redis 버전 문서와 대조하지 않았습니다.
- ⚠ 단일 스레드: 리포트는 Redis 를 단일 스레드 이벤트 루프로 소개합니다. Redis 6 부터는 네트워크 I/O 를 별도 스레드로 나눌 수 있고, 명령 실행만 한 스레드입니다.
- ⚠ 책 장 번호: 원문은 DDIA 5·11장(복제·스트림 처리)을 듭니다. 노트로 정리한 2판에서는 6·12장입니다. 복제 지연은 [DDIA 06-03](../../05_data/book/designing-data-intensive-applications/06-03.복제 지연 문제와 일관성 보장.md) 입니다.
- ⚠ 자막 교정: 원문이 자동 자막의 `cash` 를 `cache` 로, `Reddius`·`radius` 를 `Redis` 로 고쳤습니다. 장애 3패턴·Spring 코드·CDC 는 영상이 아니라 리포트가 덧붙인 내용입니다.
