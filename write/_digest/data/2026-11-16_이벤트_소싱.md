## 요점

한 줄: 현재 상태를 덮어쓰는 CRUD 대신 이미 일어난 불변 이벤트의 순서를 진실로 삼고 상태는 재생으로 만들며, 재생 비용·스키마 진화·조회·분산 순서라는 네 비용을 감수할 만큼 이력이 값진 도메인에만 쓰라고 봅니다.

- 문제: CRUD 는 `Order 42` 의 상태를 `Placed` → `Paid` → `Shipped` → `Cancelled` 로 한 행에 덮어써 마지막 상태만 남깁니다. "어떻게 여기까지 왔나" 를 데이터로 증명하지 못합니다.
- 멘탈 모델: 은행 원장입니다. 잔액 120 대신 `+100`·`-30`·`+50` 거래를 적고 합산해 잔액을 냅니다.
- Command 와 Event: Command(`PayOrder`)는 거절될 수 있는 요청입니다. Event(`OrderPaid`)는 검증을 통과해 이미 일어난 과거형 사실이라 고치거나 지우지 않습니다. 잘못 기록했으면 바로잡는 새 이벤트를 덧붙입니다.
- Event Store 와 브로커: Event Store 는 "무슨 일이 어떤 순서로 있었나" 를, 브로커는 "이 메시지를 누구에게 보낼까" 를 맡습니다. 브로커로 이벤트를 발행한다고 이벤트 소싱이 되지는 않습니다.
- 재생: 빈 상태에서 이벤트를 차례로 적용(fold)해 현재 상태를 냅니다. 특정 시각까지만 재생하면 그 시점 상태가 나오고, 운영 이벤트를 테스트 환경에서 재생해 버그를 재현합니다.
- 네 비용과 해법:
  - 긴 스트림 재생은 스냅샷으로 줄입니다. 스냅샷은 캐시일 뿐 진실이 아닙니다.
  - 옛 스키마(`OrderPaid v1 {orderId, amount}`)는 읽을 때 새 형식으로 바꾸는 upcaster 로 다룹니다.
  - 다차원 조회는 CQRS 프로젝션(읽기 모델)으로 풉니다. 새 분석 서비스는 과거 이벤트 전체를 재생해 만듭니다.
  - 순서는 전역이 아니라 같은 aggregate 스트림 안에서만 보장하고, 서비스 사이 결과적 일관성을 받아들입니다.
- 흔한 오해(대본): 이벤트 소싱은 Kafka·마이크로서비스·CQRS 와 같지 않습니다. 모놀리스의 RDB 테이블 하나로도 구현하는 영속화 패턴입니다.
- 실무 보완(리포트): Event Store 저장과 브로커 발행 사이 원자성은 Transactional Outbox 나 CDC 로 맞춥니다. 재시작한 컨슈머가 중복 지급하지 않게 멱등 처리를 둡니다.
- 도입 기준: "상태 변경의 역사 자체가 비즈니스 가치인가" 입니다. 원장·결제·주문 생명주기·감사 추적에는 맞고, 프로필·설정·CMS 초안에는 CRUD 가 낫습니다.

## 자료와 실습

- 자료:
  - [Martin Fowler Event Sourcing](https://martinfowler.com/eaaDev/EventSourcing.html): 패턴의 원전입니다.
  - [Azure Event Sourcing pattern](https://learn.microsoft.com/en-us/azure/architecture/patterns/event-sourcing): 적용 기준과 주의점입니다.
  - [Kurrent 문서](https://docs.kurrent.io/): 이벤트 저장소의 스트림·구독 개념입니다.
  - 『Designing Data-Intensive Applications』 11장(1판 기준): 스트림과 이벤트 로그입니다. 정독 노트 [DDIA 2판](../../05_data/book/designing-data-intensive-applications/README.md) 에서는 3장(03-06)·12장입니다.
  - 『Implementing Domain-Driven Design』 8·10장·부록 A: 도메인 이벤트, Aggregate, 이벤트 소싱 구현입니다.
  - Greg Young 『Versioning in an Event Sourced System』: 이벤트 스키마 버전 관리입니다.
  - [event-driven.io](https://event-driven.io/): 이벤트 소싱 실무 글 모음입니다.
  - 코드: [EventSourcing.NetCore](https://github.com/oskardudycz/EventSourcing.NetCore) `Sample/EventSourcing.Sample/` 은 프레임워크 없이 원리를 보입니다. [marten](https://github.com/JasperFx/marten) `src/Marten/Events/` 는 PostgreSQL 을 이벤트 저장소로 씁니다.
  - 코드: [AxonFramework](https://github.com/AxonFramework/AxonFramework) 는 `EventSourcingRepository` 의 스냅샷과 upcaster 체인을 봅니다.
- 실습:
  - Level 1: 인메모리 주문 aggregate 와 `replay(events, untilTimestamp)` 를 짭니다. 함정은 apply 안의 현재 시각·난수 같은 비결정 코드입니다. 완료: Given-When-Then 시험 5개 이상이 통과합니다.
  - Level 2: PostgreSQL `events` 테이블에 `(stream_id, stream_version)` 유니크 인덱스로 낙관적 동시성을 겁니다. 함정은 동시 쓰기에서 나는 동시성 예외 처리입니다. 완료: 읽기 모델을 비운 뒤 재생으로 100% 복구합니다.
  - Level 3: 100건마다 스냅샷, v1→v2 upcaster, `processed_events` 멱등 컨슈머를 넣습니다. 함정은 스냅샷 형식 변경이라 `schema_version` 이 다르면 처음부터 재생합니다. 완료: 이벤트 5만 건 스트림 로드가 P99 20 ms 이하입니다.



## 경고

- ⚠ Kafka 를 Event Store 로: 리포트는 Event Store 와 브로커를 다른 역할로 나눕니다. 반면 [Event Sourcing](../../04_messaging/07_CQRS_EventSourcing/01-02.Event Sourcing.md) 노트는 Kafka·Redpanda 토픽이 Event Store 로 적합한 이유를 적습니다. 어느 조건에서 둘이 맞는지 대조하지 않았습니다.
- ⚠ "100% 동일한 버그 재현": 리포트 자체가 Level 1 에서 `apply()` 안 `now()`·외부 호출이 재생 결과를 바꾼다고 적습니다. 재현은 재생이 결정적일 때만 성립합니다.
- ⚠ 리포트 보완: Outbox·CDC·멱등 컨슈머는 대본이 아니라 리포트가 덧붙인 내용입니다(리포트 4-1 이 밝힘). upcaster·약한 스키마도 대본이 이름을 댔는지 확인하지 않았습니다.
- ⚠ DDIA 장 번호: 리포트는 1판 11장(스트림 처리)을 가리킵니다. 정독 노트는 2판 기준이라 이벤트 소싱이 3장(03-06), 데이터베이스와 스트림이 12장(12-02)에 있습니다.
- ⚠ 도서 정보: IDDD 의 장 번호, Greg Young 책의 출판 연도·분량·무료 여부는 확인하지 않았습니다.
- ⚠ EventStoreDB 와 Kurrent: 리포트는 EventStoreDB 문서를 Kurrent 주소로 링크합니다. 이름이 바뀐 시점과 범위는 확인하지 않았습니다.
- ⚠ 오픈소스 경로: `Sample/EventSourcing.Sample/`, Axon 의 `eventsourcing/src/main/java/…` 경로는 확인하지 않았습니다. Axon 은 메이저 버전마다 모듈 배치가 다를 수 있습니다.
- ⚠ 실습 목표값: Level 3 의 "5만 건 스트림 P99 20ms 이하" 는 리포트가 정한 목표로, 측정 근거가 없습니다.
- ⚠ 자막 교정과 링크: 자동 자막의 `canled`→cancelled, `100us 30`→100 - 30, `cues`→queues 를 리포트가 고쳤습니다. Greg Young 강연 링크는 YouTube 검색 결과라 넣지 않았습니다.
- ⚠ 링크 정리: 강연 영상 검색 링크는 버렸습니다.
