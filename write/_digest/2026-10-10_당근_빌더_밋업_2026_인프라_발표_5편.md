## 요점

- 노드 오토스케일링 제약과 해결: Cluster Autoscaler는 다중 AZ 환경에서 특정 가용영역 확장을 보장하지 못합니다. Karpenter는 Pod 자원 요구에 맞춰 EC2를 직접 프로비저닝하여 이 문제를 해소합니다.
- 프로비저닝 전환 후 운영 맞물림: PDB `maxUnavailable`이 5%로 낮으면 노드 회수가 차단됩니다. 빠른 프로비저닝 환경에서는 롤링 배포 시 노드 급증을 막기 위해 `maxSurge`를 낮춰야 합니다.
- CI 빌드 캐시 볼륨 풀 운영: 상태 없는 CI 러너의 캐시 손실을 막기 위해 BuildKit 캐시를 담은 EBS 볼륨 여러 장을 교대로 재사용합니다. 의존성 층이 유지되므로 이전 캐시로도 높은 히트율을 얻습니다.
- Docker 29 스토리지 변경 대응: 신규 설치 시 containerd image store가 기본 활성화되어 압축 해제 쓰기 부하가 늘어납니다. 데몬 설정을 통해 기존 graph driver(overlay2)로 되돌려 빌드 시간을 단축합니다.
- eBPF 커널 이벤트 기반 사후 추적: 간헐적 장애 후 복구되는 문제를 해결하기 위해 eBPF로 커널 이벤트를 BPF 맵에 상시 누적하고 경보 시 스냅샷으로 추출합니다.
- 앱과 사이드카 재시도 중복 장애: 앱의 즉각적 RST와 사이드카의 SYN 재전송이 겹쳐 NAT 소스 포트가 고갈되고 외부 차단이 발생했습니다. 서킷 브레이커를 도입해 비정상 연결 생성을 차단합니다.
- 관측 플랫폼과 ReAct 에이전트: 노드 수명과 Pod 이벤트를 단일 타임라인에 겹쳐 원인을 파악합니다. 진단 에이전트가 ReAct 루프로 관측 도구를 병렬 호출해 장애 분석 시간을 1~2분으로 단축합니다.
- 프록시 기반 Elasticsearch 무중단 이전: Go 프록시 뒤에서 쓰기 복제, 읽기 섀도잉, 점진적 응답 전환을 차례로 수행합니다. 전 과정에서 섀도잉 100%를 유지해 OS 파일시스템 캐시를 웜 상태로 보존합니다.



## 경고

- ⚠ 상시 스택 수집 오버헤드 과장: 요약은 상시 스택 수집이 심각한 오버헤드를 유발한다고 적었으나 실제로는 상시 이벤트를 BPF 맵에 누적하다가 경보 시 추출합니다 (원문 53줄). — 미확인: 발표 설계 내용이라 공식 문서 대상 아님
- ⚠ 백로그 큐와 소스 포트 혼동: 요약은 SYN 전송이 둘을 동시 고갈시킨다 했으나 백로그는 수신 서버 자원이고 소스 포트는 송신 NAT 자원입니다 (원문 55줄). — 확인됨: [Linux ip-sysctl](https://raw.githubusercontent.com/torvalds/linux/v6.6/Documentation/networking/ip-sysctl.rst)
- ⚠ 발표 수치의 원문 미확인: 월 15,000달러 절감이나 빌드 시간 62% 단축 같은 성과 수치는 작성 주체 미상의 요약 자료 기준으로 실제 원문 검증이 없습니다 (원문 59줄). — 미확인: 발표 성과 수치라 공식 문서로 검증 불가
- ⚠ Karpenter의 Instance LB 불가 단정: 요약은 ASG 부재로 Instance 유형이 불가하다 했으나 컨트롤러가 인스턴스를 직접 등록할 수 있어 절반만 맞습니다 (원문 118줄). — 확인됨: [AWS LB Controller TargetGroupBinding](https://kubernetes-sigs.github.io/aws-load-balancer-controller/v2.8/guide/targetgroupbinding/targetgroupbinding/)
- ⚠ Fast Snapshot Restore(FSR) 오류: 요약은 메모리 상주 및 계정당 20개라 했으나 완전 초기화 볼륨 생성 기능이며 한도는 리전당 5개입니다 (원문 134줄). — 확인됨: [EBS Fast Snapshot Restore](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-fast-snapshot-restore.html)
- ⚠ 검색 엔진 cold start 주원인 왜곡: 요약은 cold start를 쿼리·세그먼트 캐시 부재로만 설명했으나 공식 문서상 검색 성능을 좌우하는 핵심은 OS 파일시스템 캐시입니다 (원문 245줄). — 확인됨: [Elasticsearch 검색 속도 튜닝](https://www.elastic.co/guide/en/elasticsearch/reference/8.15/tune-for-search-speed.html)
- 확인됨: Cluster Autoscaler는 ASG의 원하는 용량만 조정하므로 다중 AZ 배포 시 특정 AZ 노드 확장을 보장하지 못합니다 ([Cluster Autoscaler FAQ](https://github.com/kubernetes/autoscaler/blob/master/cluster-autoscaler/FAQ.md)).
- 확인됨: Karpenter의 인스턴스 프로비저닝 리소스 v1 공식 명칭은 EC2NodeClass입니다 ([Karpenter NodePools](https://karpenter.sh/docs/concepts/nodepools/)).
- 확인됨: Karpenter 컨트롤러는 축출 루프를 방지하기 위해 관리형 노드 그룹이나 Fargate에 격리 배포해야 합니다 ([Karpenter 시작 가이드](https://karpenter.sh/docs/getting-started/getting-started-with-karpenter/)).
- 확인됨: AWS Load Balancer Controller는 Pod IP를 직접 등록하는 ip 모드와 EC2 인스턴스를 등록하는 instance 모드를 지원합니다 ([AWS LB Controller 어노테이션](https://kubernetes-sigs.github.io/aws-load-balancer-controller/latest/guide/ingress/annotations/)).
- 확인됨: EBS 스냅샷에서 생성된 볼륨은 초기 읽기 시 S3 다운로드 지연이 발생하며 볼륨 초기화 속도는 초당 100~300 MiB입니다 ([EBS 볼륨 초기화](https://docs.aws.amazon.com/ebs/latest/userguide/initalize-volume.html)).
- 확인됨: Fast Snapshot Restore(FSR)는 스냅샷에서 완전히 초기화된 EBS 볼륨을 즉시 복원하는 기능입니다 ([EBS Fast Snapshot Restore](https://docs.aws.amazon.com/ebs/latest/userguide/ebs-fast-snapshot-restore.html)).
- 확인됨: Docker Engine 29 신규 설치본은 기본 저장소를 containerd image store로 전환해 언팩 스냅샷 쓰기 부하를 유발합니다 ([Docker Engine 29 릴리스](https://www.docker.com/blog/docker-engine-version-29/), [containerd 스토리지](https://docs.docker.com/engine/storage/containerd/)).
- 확인됨: Docker 데몬 설정(`daemon.json`)에서 `containerd-snapshotter: false`로 기존 graph driver(overlay2) 복구가 가능합니다 ([Mirantis Docker 29 문서](https://docs.mirantis.com/mcr/29/ref-arch/containerd-image-store.html)).
- 확인됨: AWS NAT 게이트웨이는 고유 목적지당 최대 55,000개의 동시 연결을 지원하며 소진 시 `ErrorPortAllocation`이 발생합니다 ([AWS NAT 게이트웨이 지표](https://docs.aws.amazon.com/vpc/latest/userguide/metrics-dimensions-nat-gateway.html), [NAT 게이트웨이 기초](https://docs.aws.amazon.com/vpc/latest/userguide/nat-gateway-basics.html)).
- 확인됨: eBPF 프로그램 실행 통계 수집 커널 파라미터는 `kernel.bpf_stats_enabled`이며 실행 시 약간의 성능 부하를 유발합니다 ([Linux Kernel Sysctl 문서](https://docs.kernel.org/admin-guide/sysctl/kernel.html)).
- 확인됨: Envoy 액세스 로그에서 NC는 라우트 대상 클러스터 부재, UH는 건강한 엔드포인트 부재, UF는 upstream 연결 실패를 의미합니다 ([Envoy 액세스 로그 명세](https://www.envoyproxy.io/docs/envoy/v1.20.0/configuration/observability/access_log/usage)).
- 확인됨: Istio traffic mirroring은 응답을 기다리지 않고 요청을 비동기 복제하여 전달합니다 ([Istio 미러링 작업](https://istio.io/latest/docs/tasks/traffic-management/mirroring/)).
- 확인됨: Elasticsearch 검색 최적화는 쿼리 캐시 이전에 가용 RAM의 절반 이상을 OS 파일시스템 캐시에 할당하는 것이 기본입니다 ([Elasticsearch 검색 속도 최적화](https://www.elastic.co/docs/deploy-manage/production-guidance/optimize-performance/search-speed)).
- 확인됨: ReAct 프레임워크는 언어 모델이 추론(Reasoning)과 도구 실행(Acting)을 교차 반복하는 자율 문제 해결 기법입니다 ([ReAct 논문 arXiv:2210.03629](https://arxiv.org/abs/2210.03629)).
