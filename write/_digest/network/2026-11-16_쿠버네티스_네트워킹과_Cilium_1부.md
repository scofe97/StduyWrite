## 요점

한 줄: 쿠버네티스 네트워킹의 네 통신 문제가 커널(netns·veth·라우팅·iptables)에서 풀리는 방식을 보이고, Cilium 이 eBPF 와 라벨 Identity 로 iptables 병목과 IP 기반 보안을 대신한다고 봅니다.

- 출발점: 쿠버네티스는 CNI 구현을 내장하지 않고, 모든 Pod 가 NAT 없이 고유 IP 로 통신해야 한다는 모델만 정합니다.
- 네 문제: 같은 Pod 의 컨테이너는 netns 를 공유해 `localhost` 로 닿습니다. Pod 사이는 veth·브리지와 노드별 Pod CIDR 라우팅으로, 서비스는 ClusterIP DNAT 로 잇습니다. 외부와는 SNAT(Masquerade)·LoadBalancer·Ingress 로 오갑니다.
- 규모 병목(대본): 5,000노드·2,000서비스·서비스당 Pod 10개면 워커 노드마다 iptables 규칙이 20,000개 넘게 생긴다고 합니다.
- 진화 3단계: iptables 는 체인을 차례로 대조하고 확률로 백엔드를 고릅니다. IPVS 는 ipset 해시로 서비스를 찾고 RR·Least Connection 을 줍니다. Cilium 은 BPF 해시 맵을 조회하고 iptables 체인을 없앱니다.
- 데모: kind 의 기본 CNI 는 kindnet, kube-proxy 기본 모드는 iptables 입니다. `disableDefaultCNI: true`·`kubeProxyMode: "none"` 으로 만들면 노드가 `NotReady` 이고, Cilium 을 kube-proxy 대체 모드로 깔면 서비스 라우팅과 `cilium endpoint list` 가 동작합니다.
- Identity: `pod-template-hash` 같은 휘발성 라벨은 빼고 라벨 조합으로 숫자 ID 를 줍니다. 그래서 같은 라벨의 복제본은 한 ID 를 함께 씁니다.
- 트레이드오프(리포트 보완): iptables 는 익숙한 도구로 디버깅되고 옛 커널에서도 돕니다. Cilium 은 `cilium monitor`·`hubble observe` 같은 전용 CLI 와 최신 커널이 필요합니다.
- 다음 편(Part 2) 예고: L3~L7 정책, Hubble, Cilium Service Mesh, Cluster Mesh 입니다.
- 찾을 키워드: `nftables` 프록시 모드, `Geneve`, `XDP`, `BGP Control Plane`, `Cluster Mesh` 입니다.

## 자료와 실습

- 자료:
  - [Cilium kube-proxy free](https://docs.cilium.io/en/stable/network/kubernetes/kubeproxy-free/): kube-proxy 없이 eBPF 로 Service 를 처리하는 설정입니다.
  - [Kubernetes Virtual IPs and Service Proxies](https://kubernetes.io/docs/reference/networking/virtual-ips/): iptables·IPVS 모드의 공식 설명입니다.
  - [CNI Specification](https://www.cni.dev/docs/spec/): 플러그인이 지킬 ADD·DEL 계약입니다.
  - 『Learning eBPF』 1~3장·8장: eBPF 기초와 네트워킹입니다. 정독 노트 [learning-ebpf](../../02_os/book/learning-ebpf/README.md) 가 있습니다.
  - 『Networking and Kubernetes』 2·4·5장: Linux 네트워킹, Kubernetes 네트워킹, Service 입니다. 정독 노트 [networking-and-kubernetes](../../08_cloud/book/networking-and-kubernetes/README.md) 가 있습니다.
  - 『Systems Performance』 2판 10·15장: 네트워크 성능과 BPF 도구입니다. 정독 노트 [systems-performance](../../02_os/book/systems-performance/README.md) 가 있습니다.
  - [Cracking kubernetes node proxy](https://arthurchiao.art/blog/cracking-k8s-node-proxy/): 노드 프록시 방식을 직접 짜며 비교하는 글입니다.
  - 코드: containernetworking/plugins `plugins/main/bridge/bridge.go`(`cmdAdd`)와 kind `images/kindnetd/cmd/kindnetd/` 를 봅니다. cilium `bpf/bpf_sock.c`·`pkg/identity/` 도 봅니다.
- 실습:
  - Level 1: kind 에서 iptables 와 IPVS 모드의 NAT 규칙 수를 비교합니다. 함정은 kind 노드에 `ipset`·`ipvsadm` 을 따로 깔아야 한다는 점입니다. 완료: 두 모드의 NAT 규칙 줄 수를 나란히 셉니다.
  - Level 2: kube-proxy 없는 kind 에 Cilium 을 깝니다. 함정은 `k8sServiceHost`·`k8sServicePort` 를 꼭 지정해야 한다는 점입니다. 완료: `cilium status` 가 OK 이고 같은 라벨의 파드가 같은 Identity 를 씁니다.
  - Level 3: L7 규칙이 든 `CiliumNetworkPolicy` 를 겁니다. 함정은 L7 처리를 Envoy 로 돌리면서 생기는 지연입니다. 완료: `hubble observe` 에 Identity 별 FORWARDED·DROPPED 가 보입니다.



## 경고

- ⚠ 유저스페이스 왕복: 영상은 iptables 가 유저스페이스에서 처리한다는 취지로 말합니다. 실제로 Netfilter 의 패킷 대조는 커널 안에서 돕니다. 비용은 사용자 공간 도구가 규칙 전체를 다시 쓰는 갱신과 긴 체인 순회에서 나며, 리포트도 이렇게 교정합니다.
- ⚠ O(1) 표현: 리포트는 IPVS 와 Cilium 을 모두 O(1) 로 적습니다. 위 표에 링크한 networking-and-kubernetes 02-03 의 비교표는 BPF 맵 조회 비용이 맵 유형에 따라 다르다고 적습니다.
- ⚠ 규칙 수: "노드당 20,000개 이상" 은 서비스 2,000 × Pod 10 에서 나온 대략값입니다. 실제 수는 포트 수와 체인 구성에 따라 달라집니다.
- ⚠ Helm 값: 영상의 `kubeProxyReplacement=strict` 는 옛 값입니다. 리포트는 v1.14 부터 `true` 로 바뀌었다고 적습니다(확인하지 않음).
- ⚠ 커널 버전: "5.10 이상, 권장 5.15+" 는 리포트 값입니다. 기능마다 요구 커널이 달라서 Cilium 문서의 요구 사항 표와 대조하지 않았습니다.
- ⚠ 리포트 보완: ENI IPAM·Maglev·커널 요구·트레이드오프 표·L7 정책 실습은 영상이 아니라 리포트가 덧붙인 내용입니다. 정책과 Hubble 은 영상 말미에 Part 2 범위로 예고만 합니다.
- ⚠ 자막 교정: 원문이 자동 자막의 `cider`·`cedar` 를 CIDR 로, `cube proxy`·`Q proxy` 를 kube-proxy 로 고쳤습니다. Thomas Graf 발표 링크는 YouTube 검색 결과라 특정 발표를 가리키지 않아 넣지 않았습니다.
- ⚠ 링크 정리: 강연 영상 검색 링크는 버렸습니다.
