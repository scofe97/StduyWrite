## 요점

한 줄: 코드는 정상인데 컴포넌트 경계(타이머·신뢰·계약·인프라 수명)의 암묵적 가정이 어긋나 프로덕션 장애가 난다고 봅니다.

- 502: 새벽처럼 한산할 때 서버(Gunicorn 2초, Node.js 5초)가 먼저 연결을 닫습니다. ALB(60초)는 그 연결에 요청을 보내고, 그래서 502 가 납니다.
- 502 대응: 서버 keep-alive 를 LB idle timeout 보다 길게 둡니다(ALB 60초 → 서버 65초). Node.js 는 `headersTimeout` 도 `keepAliveTimeout` 보다 크게 잡으라고 합니다.
- 재시도: 고정 간격 3회 재시도는 트래픽을 3배로 불려, 외부가 복구된 직후 양쪽을 다시 쓰러뜨린다고 합니다.
- 재시도 대응: 백오프와 Jitter 는 시점만 흩고 총량은 줄이지 못합니다. 총량은 Circuit Breaker 와 Retry Budget 으로 막습니다.
- 커넥션 풀: DB 작업 10ms 에 외부 응답 2~3초가 붙으면, 풀 10개가 금방 마르고 새 요청은 `connectionTimeout`(30초)까지 기다린다고 합니다.
- 커넥션 대응: 외부 호출을 트랜잭션 밖으로 빼서 짧은 트랜잭션 둘로 나눕니다. 깨진 원자성은 상태 머신·멱등성 키·대사로 메웁니다.
- XFF: 앞단이 위조 헤더 뒤에 실제 IP 를 덧붙이면, 맨 왼쪽 값을 클라이언트 IP 로 읽는 앱이 속습니다.
- XFF 대응: `RemoteIpValve`·Envoy `xff_num_trusted_hops` 처럼 믿는 홉만 거슬러 읽습니다. 관리자 보호는 IP 가 아니라 토큰·이상 탐지로 하라고 권합니다.
- 메일: 개발 환경의 내부 메일 서버는 없는 주소에 `550` 을 바로 돌려주지만, 운영의 대형 메일 서버는 `250` 을 주고 나중에 반송한다고 합니다.
- 메일 대응: 발송 예외에 기대지 말고 Return-Path·Webhook(SES·SNS 등) 반송 파이프라인을 둡니다. 없는 주소로 계속 보내면 발신 평판이 떨어집니다.
- API 호환: 필드 하나 추가가 `kotlinx.serialization` 기본 설정 앱만 깨뜨렸다고 합니다. 계약에 "모르는 필드는 무시" 를 적고, 강제 업데이트가 어려우면 버저닝을 함께 씁니다.
- 인증서: `certbot -q` 크론이 조용히 실패했고 만료 알림 메일도 오지 않았다고 합니다. 관리형 인증서(ACM)나 서버 밖 감시(UptimeRobot 등)를 권합니다.
- 찾을 키워드: 프록시 헤더는 `server.forward-headers-strategy`, `internal-proxies` 입니다. 나머지는 `FAIL_ON_UNKNOWN_PROPERTIES`, `Synthetic Monitoring`, `Adaptive Concurrency`, `Load Shedding` 입니다.

## 자료와 실습

- 자료:
  - [ALB 문제 해결 (AWS 문서)](https://docs.aws.amazon.com/elasticloadbalancing/latest/application/load-balancer-troubleshooting.html): ALB/NLB 와 타겟 서버 간 Keep-Alive Timeout 설정 권고 가이드입니다.
  - [Timeouts, retries, and backoff with jitter (AWS Builders' Library)](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/): 분산 환경의 재시도 폭풍과 지수 백오프, Jitter 와 Retry Budget 아키텍처 원전입니다.
  - [RFC 5321](https://datatracker.ietf.org/doc/html/rfc5321): SMTP `RCPT TO` 응답 코드(`250`, `550`)와 비동기 DSN 표준 명세입니다.
  - [Ending Expiration Notification Emails (Let's Encrypt 공지)](https://letsencrypt.org/2025/01/22/ending-expiration-emails): 만료 알림 이메일 서비스 종료 배경과 외부 모니터링 권고 공지입니다.
  - [Handling Overload (Google SRE Book 21장)](https://sre.google/sre-book/handling-overload/): 재시도 비율 상한(Retry Budget)과 부하 제어 실무 사례입니다.
  - [Tolerant Reader](https://martinfowler.com/bliki/TolerantReader.html): API 스키마 확장 때 소비자가 모르는 필드를 무시해야 하는 설계 원칙 아티클입니다.
  - 『Release It! 2판』 4장(연쇄 장애와 커넥션 풀 안티패턴)·5장(안정성 패턴): 연쇄 장애와 커넥션 풀 고갈을 막는 방어적 아키텍처 패턴입니다.
  - 『Designing Data-Intensive Applications』: 원문은 4장·8장·9장을 권합니다. 2판 기준 인코딩 정독 노트는 [DDIA 05-01](../../05_data/book/designing-data-intensive-applications/05-01.인코딩과 호환성 기초.md) 입니다. 부분 실패는 [DDIA 09-01](../../05_data/book/designing-data-intensive-applications/09-01.부분 실패와 비신뢰 네트워크.md) 입니다.
  - 『High Performance Browser Networking』 2장·4장·11장: TCP 소켓 생명주기와 Keep-Alive, TLS 핸드셰이크입니다. 온라인 공개판은 [High Performance Browser Networking](https://hpbn.co/) 입니다.
  - 코드: `brettwooldridge/HikariCP` 의 `HikariPool.java`(`getConnection()` 대기 루프)를 봅니다. `resilience4j/resilience4j` 의 `CircuitBreakerStateMachine.java`·`IntervalFunction.java`(상태 전이와 Jitter)를 봅니다. `envoyproxy/envoy` 의 `conn_manager_utility.cc`·`retry_state_impl.cc`(신뢰 홉 계산과 재시도 예산)도 봅니다.
- 실습:
  - Level 1: Nginx(60초)와 백엔드(2초)로 Keep-Alive Timeout 역전 `502 Bad Gateway` 를 재현하고 해결합니다. 함정은 단순 저부하에서는 타이밍이 겹치지 않아 백엔드 타임아웃 직전에 요청을 집중시켜야 하는 점입니다. 완료: `tcpdump` 로 `RST` 와 502 로그를 확보하고 백엔드 타임아웃을 65초로 늘려 에러율 0%를 검증합니다.
  - Level 2: Spring Boot 와 HikariCP, WireMock 2초 지연으로 트랜잭션 내 외부 호출 시 커넥션 풀 고갈을 재현합니다. 함정은 트랜잭션 분리 뒤 결제 API 타임아웃 때 유령 결제가 발생할 수 있는 점입니다. 완료: 단일 트랜잭션 대비 트랜잭션 분리 시 커넥션 점유 시간이 10ms 대로 줄어드는 비교 리포트를 작성합니다.
  - Level 3: 30초 장애 뒤 복구되는 Mock 결제 서버로 재시도 폭풍을 시뮬레이션하고 Resilience4j Circuit Breaker 와 Jitter 로 보호합니다. 함정은 Jitter 없이 백오프만 두면 동일 시점 실패 요청들이 계속 함께 몰리는 점입니다. 완료: 고정 재시도 환경의 10분 연쇄 장애를 재현하고, Jitter 와 Circuit Breaker 로 복구 즉시 정상화됨을 검증합니다.



## 경고

- ⚠ NLB 수치: 원문은 NLB TCP idle timeout 을 "350초 고정" 으로 적습니다. AWS 는 2024년부터 이 값을 바꿀 수 있게 했다고 알려져 있습니다(확인하지 않음).
- ⚠ 대형 메일 서버: "Gmail 등은 계정 열거 방지로 항상 `250 OK`" 는 과장일 수 있습니다. Gmail 은 없는 주소에 `RCPT TO` 단계에서 `550 5.1.1` 을 주는 경우가 많습니다(확인하지 않음).
- ⚠ Jackson 기본값: 원문은 `FAIL_ON_UNKNOWN_PROPERTIES` 를 "false 로 유지" 하라고 적습니다. 순수 Jackson `ObjectMapper` 의 기본값은 `true` 입니다. Spring Boot 가 만드는 `ObjectMapper` 는 이를 끕니다.
- ⚠ 만료 메일 종료: Let's Encrypt 가 만료 알림 메일을 끝낸 것은 사실입니다. 2025년 1월 공지하고 2025년 6월에 멈췄습니다(공지 날짜는 위 링크 주소로 확인).
- ⚠ SRE 장 번호: 원문은 21장을 "Cascading Failures & Retry Budgets" 로 묶습니다. 21장은 과부하 처리(Retry Budget 포함)이고, 연쇄 장애는 22장 「Addressing Cascading Failures」 입니다.
- ⚠ 계산값: "처리량 300배 급감" 은 3초를 10ms 로 나눈 AI 계산입니다. 영상 수치가 아닐 수 있습니다.
- ⚠ 책 장 번호: 원문은 DDIA 4·8·9장(부호화·분산 시스템의 골칫거리·일관성과 합의)을 듭니다. 노트로 정리한 2판에서는 5·9·10장입니다. 인코딩은 [DDIA 05-01](../../05_data/book/designing-data-intensive-applications/05-01.인코딩과 호환성 기초.md) 입니다.
- ⚠ 링크 상태: Spring Boot 프록시 문서 링크는 검색 결과 주소로 감싸져 있어 넣지 않았습니다. 출처 표시도 비어 있어 주장을 영상과 맞댈 수 없습니다.
