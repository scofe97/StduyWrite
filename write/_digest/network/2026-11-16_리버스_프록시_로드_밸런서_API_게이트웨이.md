## 요점

한 줄: Reverse Proxy·Load Balancer·API Gateway 는 고르는 제품이 아니라 요청 경로에서 맡는 역할이고, Nginx·HAProxy·Traefik·Kong 하나가 설정에 따라 여러 역할을 겸한다고 봅니다.

- 1단계 보안 노출: 원본 IP 가 드러난 서버 앞에 Reverse Proxy 를 둡니다. 질문은 "이 요청을 어느 서버로 넘길까" 입니다.
- 격리의 실체: 프록시는 통제된 정문일 뿐이고, 원본 직접 접근을 막는 것은 방화벽·사설망 규칙이라고 짚습니다.
- 2단계 과부하: 1만 명이 몰려 한 인스턴스가 죽으면 Load Balancer 로 복제본에 나눕니다. 질문은 "어느 건강한 인스턴스로 보낼까" 입니다.
- 3단계 MSA 복잡도: 서비스를 나누자 클라이언트가 주소를 다 알아야 하고 인증·제한·로깅이 서비스마다 중복됐습니다. API Gateway 의 질문은 "어느 서비스로 보내고 어떤 정책을 걸까" 입니다.
- 면접 포인트: "Nginx 는 프록시인가 LB 인가" 에는 제품명이 아니라 그 자리의 역할로 답하라고 합니다.
- 인가 책임: 게이트웨이가 인증을 맡아도 각 서비스는 여전히 자기 권한을 검사해야 한다고 경고합니다.
- 프록시 체인(리포트 보완): CDN·WAF → 외부 LB → 게이트웨이 → 내부 LB·사이드카 순서가 흔하며, 정답 다이어그램은 없다고 합니다.
- 찾을 키워드: `proxy_cache_valid`, `auth_request`, `PROXY protocol`, `Connection Draining`, `BOLA` 입니다.

## 자료와 실습

- 자료:
  - [NGINX reverse proxy](https://docs.nginx.com/nginx/admin-guide/web-server/reverse-proxy/): `proxy_pass`·헤더 전달·버퍼링 설정입니다.
  - [Envoy architecture overview](https://www.envoyproxy.io/docs/envoy/latest/intro/arch_overview/arch_overview): 리스너·클러스터·필터 체인 구조입니다.
  - [How Elastic Load Balancing works](https://docs.aws.amazon.com/elasticloadbalancing/latest/userguide/how-elastic-load-balancing-works.html): 관리형 LB 의 영역 간 분산과 헬스 체크입니다.
  - [RFC 7239](https://datatracker.ietf.org/doc/html/rfc7239): `Forwarded` 헤더 표준입니다.
  - 『System Design Interview』 1·4장: 규모 확장과 처리율 제한입니다. 정독 노트 [system-design](../../03_architecture/book/system-design/README.md) 이 있습니다.
  - 『Designing Data-Intensive Applications』 1·8장(1판 기준): 신뢰성과 부분 실패입니다. 정독 노트 [DDIA 2판](../../05_data/book/designing-data-intensive-applications/README.md) 에서는 2·9장입니다.
  - 『마이크로서비스 패턴』 8·11장: API 게이트웨이 패턴과 보안입니다.
  - [Cloudflare 「What is a reverse proxy?」](https://www.cloudflare.com/learning/cdn/glossary/reverse-proxy/): 입문 글입니다.
  - 코드: traefik `pkg/server/router/`·`pkg/middlewares/` 와 kong `kong/plugins/rate-limiting/`·`kong/plugins/jwt/` 를 봅니다. envoy `source/common/router/`·`source/common/upstream/` 도 봅니다.
- 실습:
  - Level 1: Docker Compose + Nginx 하나로 리버스 프록시·LB·게이트웨이 세 역할을 나눕니다. 함정은 기본 60초 타임아웃이라 `proxy_connect_timeout 2s`·`max_fails` 를 조정합니다. 완료: 백엔드에 직접 닿지 못하고 Nginx 로만 닿습니다.
  - Level 2: Go `httputil.ReverseProxy` 로 헬스 체크가 든 LB 를 만듭니다. 함정은 백엔드 상태를 여러 고루틴이 고치는 데이터 경쟁이라 atomic 을 씁니다. 완료: `-race` 가 깨끗하고 죽은 백엔드가 자동으로 빠졌다 돌아옵니다.
  - Level 3: k6 부하 중 롤링 배포에 graceful shutdown 을 넣습니다. 완료: k6 결과가 `http_req_failed: 0.00%` 입니다.



## 경고

- ⚠ 질문 구분: 리포트는 Reverse Proxy 의 질문을 "어느 서버로" 로 적습니다. 그러면 LB 의 "어느 인스턴스로" 와 겹치므로, 영상의 구분은 원본 은닉·단일 진입점 쪽으로 읽는 편이 맞습니다.
- ⚠ 헬스 체크 설정: 예제의 `max_fails`·`fail_timeout` 은 실제 요청 실패를 세는 수동 검사입니다. 오픈소스 Nginx 에는 주기적으로 찔러 보는 능동 `health_check` 가 없고 NGINX Plus 기능입니다(확인하지 않음).
- ⚠ L4 속도: "마이크로초 단위·커널 수준 포워딩" 은 구현마다 다릅니다. AWS NLB 같은 관리형 장비의 내부 구현은 공개 수치로 확인하지 않았습니다.
- ⚠ TLS 종료 뒤 평문: 내부를 평문 HTTP 로 두는 구성은 내부망 침투에 약합니다. 리포트도 서비스 사이에는 mTLS 를 권합니다.
- ⚠ 책 장 번호: 원문은 DDIA 1·8장(신뢰성·분산 시스템의 골칫거리)을 듭니다. 노트로 정리한 2판에서는 2·9장이고, 부분 실패는 [DDIA 09-01](../../05_data/book/designing-data-intensive-applications/09-01.부분 실패와 비신뢰 네트워크.md) 입니다.
- ⚠ 리포트 보완: 마이크로 캐싱·Graceful Shutdown·`X-Forwarded-For` 처리·Nginx 설정 예제는 영상이 아니라 리포트가 덧붙인 내용입니다.
