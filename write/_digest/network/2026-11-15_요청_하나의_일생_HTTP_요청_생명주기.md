## 요점

한 줄: 코드가 모두 정상 실행돼도 비즈니스 결과(중복 결제·주문 누락·5분 대기)는 실패할 수 있으니, 요청이 지나는 모든 구간의 지연과 타임아웃을 통제하라는 강의입니다.

- 로컬과 운영의 차이 셋: 동시 요청과 풀 경합, 지연·유실이 흔한 외부 네트워크, Primary·Replica 복제 지연입니다.
- 네트워크 비용: 외부 도메인 요청은 첫 바이트까지 약 1초였고 서버 처리는 약 0.23초였다고 합니다. `localhost` 는 전체 0.02초라 개발자가 이 비용을 못 느낍니다.
- 중복 결제: "주문 확인 중" 이 10~20초 이어지면 사용자가 다시 누릅니다. 첫 요청이 PG 응답을 기다리는 사이 두 번째 요청도 처리돼 결제가 두 번 됩니다.
- 중복 대응: 버튼 비활성화로는 막지 못합니다. 서버가 `Idempotency-Key` 를 Redis 나 DB 유니크 제약으로 검사해야 합니다.
- Guard 쿼리: 풀 10개 × 쿼리 20ms 면 상한이 초당 500건입니다. Guard 에서 DB 를 한 번 더 읽으면 요청당 쿼리가 둘이 돼 250건으로 떨어진다고 합니다.
- Guard 대응: 인증 검사는 JWT 서명 검증이나 캐시로 끝내고, 계정 정지 같은 예외만 Redis 블랙리스트로 확인하라고 권합니다.
- 외부 대기: 응답하지 않는 가짜 PG 를 `fetch` 로 부르자 클라이언트는 5초에 끊겼는데 서버는 약 5분간 연결과 메모리를 붙들었다고 합니다.
- 외부 대기 결과: 초당 500건이면 5분에 15만 건이 쌓여 메뉴 조회 같은 무관한 API 까지 죽는다고 합니다.
- 핵심 문장(원문): 평소 응답 속도는 가장 느린 구간이 정하지만, 최악의 응답 속도는 타임아웃이 없는 구간이 정한다고 정리합니다.
- 외부 호출 대응: 연결·응답 타임아웃을 모두 명시하고 `AbortSignal.timeout()` 을 겁니다. 결제 타임아웃이면 재시도 전에 상태 조회로 먼저 확인하고 대사 큐에 넣습니다.
- 풀 크기 공식(원문): 서버당 풀 크기는 (DB 의 안전한 최대 커넥션 − 관리 여유분) ÷ 오토스케일 최대 서버 수 이하로 잡으라고 합니다.
- 복제 지연 대응: 결제 직후 조회처럼 최신값이 필요한 읽기는 Primary 로 보냅니다. 또는 쓰기 뒤 몇 초간만 Primary 로 읽는 세션 단위 고정을 씁니다.
- 찾을 키워드: `connectTimeout`, `undici Agent`, `RDS Proxy`, `OpenTelemetry`, `Tail Latency` 입니다.

- 실습:
  - Level 1: `curl -w` 로 단일 HTTP 요청의 DNS, TCP, TLS, TTFB 시간을 정량적으로 측정합니다. 함정은 연속 요청 때 OS DNS 캐시 때문에 `time_namelookup` 이 급격히 줄어드는 점입니다. 완료: 구간별 시간 차분을 계산해 순수 백엔드 서버 처리 시간을 도출합니다.
  - Level 2: 무응답 Mock PG 와 커넥션 풀 5개로 Guard DB 조회 및 타임아웃 부재 시의 연쇄 장애를 재현합니다. 함정은 부하 중 서버 CPU 가 10% 미만인데 모든 API 가 타임아웃되는 유령 병목 현상입니다. 완료: `AbortSignal.timeout(2000)` 으로 타임아웃을 걸어 PG 장애 때도 메뉴 조회 API 가 50ms 이내로 응답하도록 격리합니다.
  - Level 3: Redis 분산 락과 `Idempotency-Key` 를 활용한 결제 파이프라인과 대사 워커를 구현합니다. 함정은 동일 멱등 키의 0.01초 간격 동시 요청이 서로 다른 서버 인스턴스로 라우팅되는 경합 조건입니다. 완료: 동일 키로 10개 요청을 동시 발송했을 때 결제 호출이 1회만 실행되고 나머지는 중복 결제 없이 처리됩니다.



## 경고

- ⚠ `curl -w` 수치: 시간 변수는 요청 시작부터의 누적값입니다. 그래서 "TCP 0.5초" 는 TCP 구간만의 값이 아니고, 구간 시간은 앞 값과의 차이(약 0.25초)입니다.
- ⚠ 계산값: "500 → 250 RPS" 는 두 쿼리가 차례로 20ms 씩 걸린다는 가정입니다. "15만 건" 은 500 × 300초 계산이고, 그 전에 OOM 이 나는지는 메모리 크기에 달려 있습니다.
- ⚠ 기본값 출처: undici 의 `headersTimeout`·`bodyTimeout` 기본값이 300초라는 주장은 원문 설명입니다. 실행 중인 Node.js 버전의 문서와 대조하지 않았습니다.
- ⚠ 0-RTT: 원문은 HTTP/3 를 "0-RTT" 로 소개합니다. 0-RTT 는 이전 연결을 재개할 때만 되고, 재전송 공격 위험이 있어 결제 같은 비멱등 요청에는 쓰지 않습니다.
- ⚠ 책 장 번호: 원문은 DDIA 5·8장(복제·분산 시스템의 골칫거리)을 듭니다. 노트로 정리한 2판에서는 6·9장입니다. 부분 실패는 [DDIA 09-01](../../05_data/book/designing-data-intensive-applications/09-01.부분 실패와 비신뢰 네트워크.md) 입니다.
- ⚠ 소스 경로: PgBouncer 의 `src/pooler.c` 는 연결 수락을 맡는 파일입니다. 클라이언트와 서버 연결을 묶는 로직이 거기 있다는 원문 설명은 확인하지 않았습니다.
- ⚠ 자막 교정: 원문이 `Akka example` 을 `fetch`·Axios 예제로, `curl-w` 를 `curl -w` 로 고쳤습니다. 강의는 Node.js·NestJS 기준이라 Spring 노트와 바로 맞물리지는 않습니다.
