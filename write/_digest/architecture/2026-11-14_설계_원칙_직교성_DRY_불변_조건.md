## 요점

한 줄: Facade·직교성·Delete Ruthlessly·DRY 로 복잡성을 어디서 줄이고 무엇을 남길지 가르고, Invariant 는 그 상태를 가진 객체 안에서 강제하라고 봅니다.

- 앞 다섯 편은 "복잡성을 어디서 줄이고 무엇은 남기는가"를 다루고, 여섯째 편은 Invariant 를 보안 문서화로 넓힙니다.
- Facade 줄이기: 책임 없이 호출만 넘기는 Facade 는 간접 참조(indirection)만 늘립니다. 하위 시스템의 복잡성을 숨기거나 트랜잭션을 조율하는 Facade 는 남깁니다. 지울 대상은 추상화 자체가 아니라 책임 없는 추상화입니다.
- 직교성 판별 질문은 "이 기능을 다른 구현체로 바꿔도 다른 기능 코드를 고치지 않는가?"입니다.
- 둘은 같은 방향이 아닙니다. Facade 를 걷어낸 뒤 모듈끼리 서로의 내부에 직접 닿으면 직교성은 오히려 나빠집니다.
- Delete Ruthlessly: 줄일 것은 코드 줄 수가 아니라 시스템을 이해하려고 알아야 할 개념 수입니다. 장애 격리·보안·테스트 가능성을 주는 계층은 지울 대상이 아닙니다.
- DRY: 같은 `age >= 18` 이라도 가입 정책과 관리자 정책처럼 서로 다른 규칙이면 합치지 않습니다. 정책이 갈라지는 순간 공통 메서드가 둘 다 깨뜨립니다.
- Invariant 는 그 상태를 가진 객체 안에서 강제합니다(`Account.withdraw()`, `Order.cancel()`). 외부가 상태 필드를 직접 바꾸지 못하게 하면 같은 상태의 규칙이 여러 서비스에 흩어지는 상태 파편화를 막습니다.
- 원칙 지도: 복잡성 감소(KISS·YAGNI·Delete Ruthlessly), 중복·책임(DRY·관심사 분리·높은 응집도), 독립성·경계(직교성·낮은 결합도·정보 은닉·상속보다 조합), 정확성(Invariant·SSOT)으로 묶습니다.
- 원칙끼리 충돌합니다. DRY 를 과하게 쓰면 다른 정책이 한 모듈에 묶여 직교성이 떨어지고, 직교성을 과하게 쫓으면 작은 기능까지 모듈로 갈라져 복잡해집니다.
- 보안 문서 세 가지: Invariant(무엇을 지켜야 하는가), Trust Boundary(누가 누구를 믿는가), ADR(왜 이렇게 정했는가)입니다. 셋을 같은 틀로 남겨 개발팀과 보안팀이 같은 말로 설계를 검토하게 합니다.
- Narrow Facade 는 `createOrder()`·`cancelOrder()` 처럼 외부 인터페이스를 좁게 둡니다. Narrow Waist(여러 구현과 소비자 사이에 두는 작고 안정된 공통 계층)와 이어지지만 같은 용어는 아닙니다.
- 셋을 코드 주석에 몰아 쓰지 않습니다. 주석은 시간이 지나면 실제 정책과 어긋납니다. 실행 로직은 코드, Invariant 는 도메인 로직과 테스트, Trust Boundary 는 보안 설계 문서와 집행 코드, ADR 은 Git 에 둡니다.
- 문서는 구현을 대신하지 않습니다. Invariant 는 코드·DB 제약 조건·테스트로, Trust Boundary 는 인증·인가·입력 검증·네트워크 정책으로 실제로 강제합니다.
- 문서 항목: Invariant 문서는 ID·규칙·적용 범위·강제 위치·검증 방법·위반 시 처리를 적습니다. Trust Boundary 문서는 출발·도착 지점·신뢰 수준·인증·인가·위협·방어를 적습니다. ADR 은 Status·Context·Decision·Alternatives·Consequences·Security Impact 를 적고, 왜 다른 대안이 아닌지가 핵심입니다.
- 내부 네트워크에 있다는 이유로 믿지 않습니다. Kubernetes 에서는 NetworkPolicy·mesh mTLS·SPIFFE/SPIRE·JWT 검증·RBAC·Workload Identity 를 함께 봅니다.
- 진행 순서: 요구사항 분석 → Trust Boundary 정의 → Invariant 정의 → ADR 기록 → 구현·PR(Invariant 테스트와 경계 검증 포함) → 보안팀 리뷰입니다.
- 찾을 키워드: 설계 원칙은 `DRY knowledge duplication`, `orthogonality Pragmatic Programmer`, `deep module`, `pass-through method` 입니다. 구조는 `Functional Core Imperative Shell`, `narrow waist architecture` 입니다. 보안은 `trust boundary data flow diagram`, `STRIDE threat modeling`, `OWASP ASVS` 입니다.

## 자료와 실습

- 자료:
  - 『The Pragmatic Programmer』: DRY, 직교성, 자동화, 실용적인 개발 원칙을 연결해서 이해하기 좋습니다.
  - 『A Philosophy of Software Design』: 복잡성, 모듈 깊이, 정보 은닉, 추상화의 적절한 경계를 깊이 있게 다룹니다. 불필요한 계층과 인터페이스가 어떻게 시스템 복잡성을 키우는지 이해하는 데 좋은 책입니다.
  - 『Clean Architecture』: 의존성 방향, 경계, 정책과 세부 구현의 분리를 공부하기 좋습니다. 개념 노트는 [클린 아키텍처](../../03_architecture/02_application/01-02.클린 아키텍처.md) 입니다.



## 경고

- ⚠ DRY 예시가 편마다 엇갈립니다. 「설계 원칙 지도」 편은 `isAdult()` 추출을 DRY 의 좋은 예로 들고, 「DRY 와 Invariant」 편은 같은 추출이 정책이 갈리면 위험하다고 합니다. 기준은 코드 모양이 아니라 "같은 지식인가"입니다.
- ⚠ KISS 예시(덧셈에 Factory·Strategy·Registry 를 들이지 말라)는 실제로 아무도 그렇게 하지 않는 과장된 예라 판단 기준으로 쓰기 어렵습니다.
- ⚠ Delete Ruthlessly 는 DRY·YAGNI 처럼 출처가 정해진 원칙 이름이 아니고, 원문도 "사고방식"이라고 부릅니다. 원문은 출처를 밝히지 않았습니다.
- ⚠ 「직교성이 높은 구조」 예시는 기능마다 Port 를 두는 모양입니다. 포트를 늘리는 것은 계층을 하나 더하는 일이라 「Facade 줄이기」와 부딪칠 수 있습니다. 원문도 두 방향이 늘 같지는 않다고 적었습니다.
- ⚠ "Narrow Facade" 는 정해진 용어가 아닙니다. 원문도 "이해할 수 있습니다"라며 뜻을 추정해 풀었고, 이 말이 처음 나온 출처는 밝히지 않았습니다.
- ⚠ "Security-Aware Architecture Documentation" 은 원문이 붙인 이름이고, 이런 이름의 방법론이 따로 있지는 않습니다.
- ⚠ ADR 형식: 원문은 "일반적으로" 이 형식을 쓴다고 했지만 Alternatives·Security Impact 절의 유무는 템플릿마다 다릅니다. 키워드 `Nygard ADR template`, `MADR`.
- ⚠ 디렉터리 예시는 Invariant 문서를 `docs/security/invariants/` 아래에 둡니다. 주문·잔액 같은 비즈니스 불변식까지 보안 폴더에 두는 모양이라, 위치는 팀 규칙에 따라 달라질 수 있습니다.
