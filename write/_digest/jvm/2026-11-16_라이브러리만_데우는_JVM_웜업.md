## 요점

한 줄: 배포 직후 지연을 줄이려고 실제 API 를 미리 호출하던 웜업을 버리고, 앱 안에서 자기 자신을 호출해 Jackson·WebClient·DB 드라이버 같은 라이브러리 코드 경로만 JIT 컴파일시킨 뒤 readiness 를 여는 방식입니다.

- 출발 문제: 새 파드는 바이트코드를 인터프리터로 돌리다가 자주 도는 메서드만 C1·C2 로 컴파일합니다. 그래서 배포 직후 첫 요청들이 느립니다.
- API 호출식 웜업의 부작용:
  - 서비스 N 개가 의존 서비스 M 개를 부르면 웜업 트래픽이 N×M 으로 불어납니다.
  - HPA 가 웜업 부하를 실제 부하로 보고 파드를 늘리고, 웜업 요청이 로그·지표를 더럽힙니다.
  - API 가 바뀔 때마다 웜업 시나리오도 고쳐야 합니다.
- 바꾼 방식: 공통 라이브러리 층만 데웁니다. 코드를 세 층(웜업 실행기·대상 라이브러리별 웜업·readiness 연결)으로 나눴습니다.
- 내부 호출 웜업: `LocalWarmup` 이 WebClient 로 같은 앱의 `WarmupController` 를 2만 번 부릅니다. 직렬화·역직렬화와 HTTP 클라이언트·서버 경로가 함께 데워집니다.
- 저장소 웜업: MySQL·Mongo 는 읽기 200번, Redis 는 읽기·쓰기 200번을 보냅니다.
- readiness 연결: `ApplicationReadyEvent` 뒤에 웜업을 돌리고, 끝나면 readiness 를 UP 으로 바꿔 트래픽을 받습니다.
- 측정: jcmd 와 JFR 로 컴파일·인라이닝 이벤트를 봤습니다. 호출 5,000회 언저리부터 C2 컴파일 수가 가파르게 늘었다고 합니다.
- 결과(발표 주장): 배포 직후 응답이 400 ms 에서 170 ms 로, 웜업을 포함한 기동이 41초에서 27초로 줄었습니다.
- 남은 선택: 라이브러리만으로 부족한 서비스는 핵심 API 1~2개만 함께 데우는 혼합 방식을 씁니다.

## 자료와 실습

- 자료:
  - [HotSpot 성능 향상 문서 (JDK 21)](https://docs.oracle.com/en/java/javase/21/vm/java-hotspot-virtual-machine-performance-enhancements.html): tiered compilation·Code Cache 기본값을 확인합니다.
  - [JFR API (JDK 21)](https://docs.oracle.com/en/java/javase/21/jfapi/): 컴파일 이벤트를 코드로 읽어 웜업 효과를 재는 데 씁니다.
  - [Spring Boot Kubernetes 프로브](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.kubernetes-probes): readiness 그룹과 `AvailabilityChangeEvent` 동작을 확인합니다. 정독 노트는 [Health Probe](../../08_cloud/book/kubernetes-patterns/04-01.Health Probe — 앱이 자기 건강을 플랫폼에 알리기.md) 입니다.
  - 『Java Performance』 2판 3~4장: 도구와 JIT 컴파일러를 다룹니다. 정독 노트 [jpf_java-performance](../../01_language/book/jpf_java-performance/README.md) 가 있습니다.
  - 『Optimizing Java』 9~10장: 코드 실행과 JIT 컴파일을 깊게 봅니다.
  - 『Release It!』 2판 1부: 기동 직후 장애와 안정성 패턴을 다룹니다.
  - [JVM Anatomy Quarks](https://shipilev.net/jvm/anatomy-quarks/): 인라이닝·컴파일 세부를 짧은 글로 봅니다.
  - [Project Leyden](https://openjdk.org/projects/leyden/): 웜업을 기동 전으로 옮기려는 OpenJDK 프로젝트입니다.
  - 코드: jmh `LoopBenchmarkHandler.java`(반복 측정 루프)와 spring-boot `availability/`(readiness 상태 전이)를 봅니다. openjdk `compilationPolicy.cpp`·`opto/bytecodeInfo.cpp`(컴파일 정책과 인라이닝 판단)도 봅니다.
- 실습:
  - Level 1: 호출 횟수를 바꿔 가며 Jackson 메서드의 Tier 4 컴파일 수를 셉니다. JMH·`-XX:+PrintCompilation` 을 씁니다. 함정은 결과를 버려 생기는 죽은 코드 제거입니다. 완료: 호출 수가 늘수록 Tier 4 컴파일 수가 오르는 것을 표로 보입니다.
  - Level 2: Spring Boot 에 `LocalWarmup` 과 readiness 게이트를 넣고 k6 로 배포 직후 지연을 잽니다. 함정은 임시 포트 고갈과 커넥션 풀 `PoolAcquireTimeoutException` 입니다. 완료: 배포 직후 P99 가 웜업 전보다 50% 줄어듭니다.
  - Level 3: 다형 DTO 로 megamorphic 을 일부러 만들고, Code Cache 사용률 80% 에서 웜업을 멈추는 보호 장치를 넣어 kind 에서 Blue-Green 으로 배포합니다. 완료: Grafana 에 웜업 유무별 지연과 Code Cache 곡선이 나란히 보입니다.



## 경고

- ⚠ 코드 골격: `LocalWarmup`·`WarmupController` 와 세 층 구조의 코드는 리포트가 발표를 바탕으로 다시 짠 예시입니다. 발표 원본 코드가 아닙니다.
- ⚠ 수치: 400 ms → 170 ms, 41초 → 27초, "5,000회부터 급증", "JFR 오버헤드 1% 미만" 은 발표·리포트 주장입니다. 측정 조건(JDK 버전, CPU 제한)을 확인하지 않았습니다.
- ⚠ DB 웜업 횟수: 읽기 200번은 C2 컴파일 임곗값보다 한참 적습니다. 이 웜업이 JIT 보다는 커넥션 풀·드라이버 초기화를 데우는 것인지 확인해야 합니다.
- ⚠ readiness 시점: Spring Boot 는 `ApplicationReadyEvent` 무렵 readiness 를 기본으로 `ACCEPTING_TRAFFIC` 으로 바꿉니다. 웜업이 끝날 때까지 `REFUSING_TRAFFIC` 으로 붙잡는 코드가 필요한지 공식 문서로 확인하지 않았습니다.
- ⚠ 자막 교정: 리포트가 "MTTC" 같은 자동 자막 오인식을 고쳐 적었습니다. 고친 용어가 발표 원문과 같은지는 대조하지 않았습니다.
- ⚠ 자료 제목: 리포트는 HotSpot 성능 향상 문서를 "GC & Compiler Tuning" 이라는 제목으로 걸었습니다. URL 이 가리키는 실제 문서 제목과 다릅니다.
- ⚠ 이름: 발표 회사·발표자 이름은 뺐습니다.
