## 요점

한 줄: 리눅스는 어렵지 않고 잘못된 순서로 배울 뿐이니, 명령어보다 실행 흐름(셸 → 권한 검사 → 프로세스 생성 → I/O·로그)을 먼저 잡으라는 영상입니다.

- 명령 하나의 일생: 셸이 `PATH` 에서 실행 파일을 찾고 `fork()` 와 `execve()` 를 부릅니다. 커널이 권한을 검사하고 메모리를 붙인 뒤, 결과를 FD 1 로 내보냅니다.
- 오류 구분: `command not found` 는 셸이 `PATH` 에서 파일을 못 찾은 것입니다. `Permission denied` 는 파일은 찾았지만 커널이 `execve()`·`open()` 단계에서 권한 비트로 막은 것입니다.
- CI 실패 원인: 로컬에서 되던 스크립트가 `cron`·`systemd`·CI 러너에서 실패하는 주원인은 비대화형 셸의 `PATH` 가 다르기 때문이라고 합니다. 그래서 유닛 파일 `ExecStart` 에는 절대 경로를 적습니다.
- 가상 파일시스템: `/proc`·`/sys` 는 디스크가 아니라 커널 메모리를 파일 트리로 보여 줍니다. `node_exporter`·cAdvisor 도 `/proc` 와 `/sys/fs/cgroup` 을 읽어 지표를 모은다고 합니다.
- 컨테이너의 정체: 컨테이너는 VM 이 아니라 호스트 커널을 함께 쓰는 프로세스이고, 그래서 호스트 `ps aux` 에 보입니다. namespace 는 보이는 범위를, cgroup 은 쓸 수 있는 양을 정합니다.
- 연결 사례: Pod 의 `resources.limits.memory` 는 컨테이너 cgroup 의 `memory.max` 로 내려간다고 합니다. 넘으면 OOM Killer 가 프로세스를 끝내 `OOMKilled` 가 됩니다.
- 격리의 한계: 커널을 같이 쓰므로 커널 취약점 하나가 호스트 전체로 번질 수 있습니다. 믿을 수 없는 코드는 gVisor 나 Firecracker 로 한 겹 더 감싸라고 권합니다.
- 디스크 장애: 로그 파일을 `rm` 해도 프로세스가 FD 를 쥐고 있으면 공간이 돌아오지 않습니다. `/proc/<pid>/fd` 에서 `(deleted)` 를 찾아 재시작하거나 크기를 0 으로 비웁니다.
- 자가 복구: 유닛 파일에 `Restart=on-failure`, `RestartSec=3s`, `LimitNOFILE=65535` 를 두어 OS 수준의 1차 복원력을 얻으라고 합니다. 전용 계정(`User=appuser`)으로 띄우는 것도 함께 권합니다.
- 찾을 키워드: 커널 경계는 `io_uring`, `Kernel Bypass`, `DPDK` 입니다. 운영은 `ulimit`, `AmbientCapabilities`, `eBPF` 입니다.

  - 『How Linux Works 3판』 1~9장: 커널, `/dev`·`/proc`·`/sys`, 권한, 프로세스, `systemd`, 네트워킹의 기초 구조를 다룹니다.
  - 『The Linux Programming Interface』: 리포트는 3~5장(파일 I/O)·24~27장(프로세스)·44장(파이프)을 권합니다. [정독 노트](../../02_os/book/tlpi_the-linux-programming-interface/README.md) 가 있습니다. 프로세스 생성은 [06-01.프로세스는 프로그램에 커널이 자원을 붙인 것이다](../../02_os/book/tlpi_the-linux-programming-interface/06-01.프로세스는 프로그램에 커널이 자원을 붙인 것이다.md) 입니다.
  - 『Systems Performance』 2판: 리포트는 2장(방법론)·6장(CPU)·7장(메모리)·10장(네트워크)을 권합니다. 커널 메트릭과 프로파일링 기반 병목 진단입니다. [정독 노트](../../02_os/book/systems-performance/README.md) 에서는 02-0x·06-0x·07-0x·10-0x 편입니다.
  - 코드: [lizrice/containers-from-scratch](https://github.com/lizrice/containers-from-scratch) 의 `main.go`(`syscall.Clone`, `chroot`)를 봅니다. [opencontainers/runc](https://github.com/opencontainers/runc) 의 `libcontainer/nsenter/` 를 봅니다. [systemd/systemd](https://github.com/systemd/systemd) 의 `src/core/service.c` 도 봅니다.
- 실습:
  - Level 1: `/proc` 가상 파일시스템과 파이프 및 `strace` 시스템 콜 추적을 실험합니다. `sleep 300 &` 의 PID 로 `/proc/<pid>/status`·`fd` 를 조회하고 `strace` 로 `ls` 시스템 콜을 관찰합니다. 함정은 컨테이너 안에서 `ptrace: Operation not permitted` 로 막힐 수 있어 `--cap-add=SYS_PTRACE` 가 필요한 점입니다. 완료: `execve()` 호출과 FD 1 출력을 시스템 콜 로그로 설명합니다.
  - Level 2: `systemd` 서비스 구성과 `journalctl` 로그 및 권한 격리를 실습합니다. 전용 유저(`appuser`)로 HTTP 서버를 `Restart=always` 서비스로 등록하고 `kill -9` 로 프로세스를 종료해 자동 복구를 확인합니다. 함정은 1024 미만 특권 포트 바인딩에 `AmbientCapabilities=CAP_NET_BIND_SERVICE` 가 필요한 점입니다. 완료: 3초 안에 새 PID 로 서비스가 복구되고 모든 이벤트가 `journalctl` 에 남습니다.
  - Level 3: Go 로 `namespaces` 와 `cgroups v2` 기반 미니 컨테이너를 만듭니다. `CLONE_NEWUTS`·`CLONE_NEWPID`·`CLONE_NEWNS` 로 자식 프로세스를 띄우고 rootfs 에서 `chroot` 와 `/proc` 마운트 뒤 `memory.max` 로 50MB 를 제한합니다. 함정은 `/proc` 마운트 때 `MS_PRIVATE` 전파 설정을 빠뜨리면 호스트 마운트 테이블이 오염되는 점입니다. 완료: 100MB 할당 테스트 때 호스트 중단 없이 해당 컨테이너만 OOM 종료됨을 검증합니다.



## 경고

- ⚠ 컨텍스트 스위칭 표현: 원문은 시스템 콜 비용을 "User Mode → Kernel Mode 컨텍스트 스위칭" 이라고 적습니다. 정확히는 같은 프로세스 안의 모드 전환이고, 프로세스를 바꾸는 컨텍스트 스위치와는 다릅니다.
- ⚠ Ring 표현: Ring 0·Ring 3 은 x86 용어입니다. ARM 은 예외 수준(EL0·EL1)이라고 부릅니다.
- ⚠ 소켓과 파일: 원문은 소켓이 `/dev` 에 나타나지 않으니 "모든 것이 파일은 아니다" 라고 적습니다. 소켓도 FD 이고 `/proc/<pid>/fd` 에 `socket:[inode]` 로 보입니다.
- ⚠ `truncate` 대상: 이미 지운 파일은 경로가 없어 `truncate -s 0 <경로>` 로 비울 수 없습니다. `/proc/<pid>/fd/<N>` 을 대상으로 하거나, 애초에 지우기 전에 비워야 합니다.
- ⚠ 출처 표시: `[cite: 1]` 이 모든 문장에 붙어 있지만 자막 한 파일만 가리킵니다. 그래서 어느 주장이 영상에 있고 어느 것이 AI 보충인지 가를 수 없습니다.
- ⚠ 책 장 번호: TLPI 3~5·24~27·44장, Systems Performance 2·6·7·10장 추천은 목차와 대조하지 않았습니다. 『How Linux Works 3판』(2021) 범위도 확인하지 않았습니다.
- ⚠ 자료 링크: Liz Rice 「Containers From Scratch」 강연은 링크가 없습니다. 코드 저장소만 원문 표에 있습니다.
- ⚠ 실습 계산: Level 3 의 "50MB 상한에 100MB 할당 → 그 프로세스만 OOM" 은 swap 이 꺼져 있다는 전제입니다. `memory.swap.max` 가 열려 있으면 swap 으로 밀려날 수 있습니다(확인하지 않음).
