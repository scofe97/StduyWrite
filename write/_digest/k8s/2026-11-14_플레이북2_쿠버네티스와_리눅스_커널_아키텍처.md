# 쿠버네티스와 리눅스 커널 아키텍처 분석 — AI 요약

> 출처: Gemini · 2026-11-14 · [플레이북] 2. 쿠버네티스와 리눅스 커널 아키텍처 분석 · 분야: k8s-keywords · 미검증

## 요점

한 줄: `kubelet`·`containerd`·`kube-proxy` 는 시스템 콜로 커널을 부리는 유저스페이스 데몬이고, 자원 한도는 cgroups 로, ClusterIP 는 `br_netfilter`·iptables DNAT 로 커널이 집행한다는 내용입니다.

- 쿠버네티스는 목표 상태를 선언하고, 프로세스 격리·자원 통제·패킷 라우팅·강제 종료는 호스트 커널이 집행함
- 컨테이너는 VM 이 아니라 호스트 커널을 공유하는 프로세스라서, 시스템 콜과 자원 접근을 통제해야 탈출을 막음
- 파드 생성 흐름: `kubelet` → CRI(gRPC) → `containerd` → OCI → `runc` 가 `unshare()`·`clone()` 으로 네임스페이스를 만들고 cgroup 파일에 `write()` 로 상한을 기록함
- `requests.cpu` 는 `cpu.weight`, `limits.cpu` 는 `cpu.max`, `limits.memory` 는 `memory.max` 로 전달됨
- CPU 는 압축 가능 자원이라 한도를 넘으면 쓰로틀링으로 느려지고, 메모리는 압축 불가라 넘으면 OOM Killer 가 `SIGKILL`(종료 코드 137)로 죽임
- 멀티스레드 런타임(JVM·Go·Node.js)에 `limits.cpu` 를 낮게 두면 짧은 버스트에도 쿼터가 바닥나 꼬리 지연(Tail Latency)이 치솟음
- 운영 패턴으로 `memory.requests == limits` 는 노드 OOM 을 줄이고, `limits.cpu` 는 크게 잡거나 지연 민감 서비스는 `requests` 만 둠
- `/proc`·`/sys` 는 디스크 블록이 0바이트인 가상 파일이고, VFS 가 `read()` 를 가로채 커널 RAM 의 상태를 텍스트로 만들어 줌
- `MiB`(1024 기반)와 `MB`(1000 기반)는 약 4.8% 차이이고, `MemAvailable` 은 kubelet 축출 판단의 기준으로 소개됨
- 4 GiB DIMM 의 `MemTotal` 이 약 3.74 GiB 로 보이는 것은 부팅 때 커널 코드·데이터·예약 영역이 빠지기 때문임
- L2 브리지를 지나는 패킷은 기본으로 iptables 를 안 거치므로, `br_netfilter` 와 `bridge-nf-call-iptables=1` 이 있어야 ClusterIP 가 파드 IP 로 DNAT 됨
- 노드 부트스트랩 전제는 `overlay`·`br_netfilter` 모듈 적재와 `ip_forward=1` 임
- 서비스·파드가 수천 개로 늘면 iptables 순차 탐색(O(N))이 병목이라, IPVS 나 eBPF 기반 Cilium 으로 옮김
- 파드는 `securityContext` 에 seccomp `RuntimeDefault`, 권한 상승 금지, non-root 를 명시함
- 너무 엄격한 커스텀 seccomp 는 `futex`·`epoll_ctl` 까지 막아 기동을 깨뜨림

## 경고

- ⚠ "Kubernetes v1.35에서 cgroup v1이 공식 제거되어 cgroup v2가 필수가 됨" — 제거가 아니라 v1.35 에서 cgroup v1 이 deprecated 되었습니다. kubelet 은 cgroup v1 노드에서 기본으로 시작하지 않으며 failCgroupV1 을 false 로 두면 계속 쓸 수 있습니다 (원문 33줄). — 확인됨: [Kubernetes cgroups v1.35](https://raw.githubusercontent.com/kubernetes/website/release-1.35/content/en/docs/concepts/architecture/cgroups.md). 같은 줄의 "v1.25 에서 cgroup v2 GA" 는 확인됨: [cgroups.md](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/architecture/cgroups.md) 가 v1.25 stable 로 표기합니다.
- ⚠ "Kubernetes 1.28+부터 NodeSwap이 베타/정식 도입됨" (원문 54줄) — NodeSwap 은 1.28 에 beta, 1.30 에 기본 켜짐, 1.34 에 stable 이 되었습니다. 원문 주장은 대체로 맞고 「정식」은 1.34 부터입니다. — 확인됨: [NodeSwap 기능 게이트 v1.34](https://raw.githubusercontent.com/kubernetes/website/release-1.34/content/en/docs/reference/command-line-tools-reference/feature-gates/NodeSwap.md)
- ⚠ "실무에서는 memory.requests == memory.limits 로 설정하여 노드 단위 OOM 을 방지" (원문 53줄) — 하나의 운영 패턴이고, Burstable 오버커밋 환경도 널리 쓰입니다. — 미확인: 운영 설계 의견입니다.
- ⚠ "kubeadm init preflight 에서 ip_forward 나 bridge-nf-call-iptables 에러가 난다" — 현재 kubeadm preflight 는 `ip_forward` 만 확인합니다. 컨테이너 런타임 문서도 `ip_forward` 만 필수 sysctl 로 적습니다 (원문 60줄). — 확인됨: [kubeadm checks.go](https://raw.githubusercontent.com/kubernetes/kubernetes/master/cmd/kubeadm/app/preflight/checks.go) 에 `ip_forward` 경로만 있고 `bridge-nf` 문자열은 없으며, [container-runtimes.md](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/setup/production-environment/container-runtimes.md) 도 같습니다. `br_netfilter` 가 CNI 에 따라 필요한 것은 별개입니다. kubeadm 1.26 까지는 preflight 가 `bridge-nf-call-iptables` 도 검사했고, 1.27 부터 빠졌습니다.
- ⚠ "MemAvailable 이 Kubelet Eviction 기준" — kubelet 의 `memory.available` 은 `capacity[memory] - workingSet` 으로 cgroupfs 에서 계산합니다. `free -m` 이나 `/proc/meminfo` 의 `MemAvailable` 과 다릅니다 (원문 26줄). — 확인됨: [node-pressure-eviction.md](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/scheduling-eviction/node-pressure-eviction.md)
- ⚠ "seccomp 는 허용되지 않은 시스템 콜을 SIGSYS 로 즉시 차단" (원문 77줄) — 동작은 필터의 기본 동작에 달렸습니다. KILL 계열은 SIGSYS 로 죽이고 TRAP 은 SIGSYS 를 보내며, ERRNO 계열은 오류만 돌려줍니다. containerd 의 RuntimeDefault 는 기본 동작이 ERRNO 라서 막힌 호출이 SIGSYS 로 끝나지 않습니다. — 확인됨: [seccomp(2)](https://man7.org/linux/man-pages/man2/seccomp.2.html), [seccomp_default.go](https://raw.githubusercontent.com/containerd/containerd/main/contrib/seccomp/seccomp_default.go)
- ⚠ "시스템 콜 약 460여 개" (원문 41줄) — 아키텍처와 커널 버전에 따라 다릅니다. x86_64 `syscall_64.tbl`(master)의 64비트 항목은 386행, 진입점이 있는 것은 370개, 가장 큰 번호는 472 입니다. 460여 개는 번호 범위에 가까운 수입니다. — 확인됨: kernel.org master `arch/x86/entry/syscalls/syscall_64.tbl`
- ⚠ "`clone()`·`unshare()` 가 `task_struct` 에 독립된 `nsproxy` 를 할당" (원문 72줄) — `task_struct` 는 `struct nsproxy *nsproxy` 를 가집니다. `clone()` 은 `copy_namespaces()`, `unshare()` 는 `unshare_nsproxy_namespaces()` 로 새 nsproxy 를 만들고, `CLONE_NEW*` 플래그가 없으면 부모 것을 공유합니다. — 확인됨: [sched.h](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/include/linux/sched.h), [nsproxy.c](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/kernel/nsproxy.c)
- ⚠ "MemTotal 이 줄어든 이유는 약 260 MiB 의 예약 메모리" (원문 34줄) — 4 GiB 와 3,920,000 KiB 의 차이는 약 268 MiB 이고 원문 수치는 어림값입니다. — 확인됨: 원문 수치로 직접 계산한 값이며 예약 영역의 구성은 미확인입니다.
