## 요점

한 줄: DevOps 엔지니어 4명이 온프레미스 클러스터 16개를 운영하면서, 노드가 부팅 때 스스로 클러스터에 합류하게 바꾸고 서비스 생성·배포·회수를 개발자 셀프 서비스와 메트릭 기반 알림으로 넘겨 반복 운영 작업을 걷어 낸 발표입니다.

- 문제는 두 층으로 나눴습니다. 클러스터 층(노드 조인·OS·K8s 업그레이드)과 서비스 라이프사이클 층(생성·배포·종료)입니다.
- Kubespray 의 한계:
  - Ansible 이 대상 노드 전체를 여러 번 돌며 사전 조건을 검사해서, 노드 조인 작업 하나에 30분이 걸렸습니다.
  - K8s 업그레이드는 마이너 버전 하나씩 올려야 해서 버전당 2시간, 여러 버전이면 6~12시간이 걸렸습니다.
- 자가 조인(Self-Join) 설계 원칙:
  - 사람이 손대지 않고 조인됩니다.
  - 조인 장치가 고장 나도 다른 플랫폼을 또 디버깅하지 않게 단순하게 만듭니다.
  - 구성 변경 이력을 Git 으로 추적합니다.
  - 이 원칙 때문에 Ansible AWX API 호출을 버리고, 셸 스크립트와 `git-sync` 에 로컬 캐시 폴백을 붙였습니다.
- 자가 조인 3단계:
  - 노드가 호스트명 규칙으로 자기 클러스터를 알아내고, DNS SRV 레코드로 API 서버 주소를 얻습니다.
  - 클러스터 버전과 노드 타입에 맞는 구성 파일을 받습니다.
  - 스케줄링을 막은 상태로 `kubeadm join` 한 뒤 검증이 끝나면 풀고 결과를 알립니다.
- 업그레이드: 노드를 제자리에서 고치지 않고 새 버전 노드 그룹을 띄워 롤링 교체합니다. 리포트는 OS 커널 업그레이드가 30분에서 2분으로, K8s 업그레이드가 버전당 2시간에서 30분으로 줄었다고 적습니다.
- 셀프 서비스:
  - 개발자가 UI 에서 언어·통신 방식을 고르면 파이프라인 YAML 이 생성되고 GitHub PR 이 열립니다. DevOps 는 리뷰 후 머지만 합니다.
  - 배치(CronJob)는 리소스·타임아웃·스케줄·`concurrencyPolicy`·알림 채널을 UI 에서 고칩니다. 공통 이미지 태그 일괄 갱신도 UI 로 넘겼습니다.
  - 운영에 바로 닿는 변경이라 같은 서비스 담당 동료의 승인을 거쳐야 반영됩니다.
- 회수 자동화:
  - 카나리 배포 후 2일 안에 블루/그린 전환이 없으면 담당 개발자에게 알립니다. 구버전과 신버전 Pod 가 함께 자원을 잡기 때문입니다.
  - 미사용 API 는 Istio(Envoy) 요청 메트릭, 컨슈머는 Spring Actuator 와 Kafka 브로커 메트릭, 배치는 `kube_cronjob_spec_suspend` 로 찾습니다. 매주 알림을 보냅니다.
  - `suspend` 배치는 삭제 대상·단발성 대기·실수로 꺼짐 중 무엇인지 개발자에게 확인받습니다.
  - 리포트는 서비스 80개를 지워 1,280 Core 와 1,280GB 메모리를 줄였다고 적습니다.

## 자료와 실습

- 자료:
  - [Version Skew Policy](https://kubernetes.io/releases/version-skew-policy/) — 공식 문서, 컨트롤 플레인과 노드 버전 차이 규칙과 kubeadm 업그레이드 절차를 봅니다.
  - [Istio Standard Metrics](https://istio.io/latest/docs/reference/config/metrics/) — 공식 문서, `istio_requests_total` 의 `reporter`·`source_workload`·`destination_service` 라벨 명세입니다.
  - [kube-state-metrics CronJob Metrics](https://github.com/kubernetes/kube-state-metrics/blob/main/docs/metrics/workload/cronjob-metrics.md) — `spec.suspend` 가 메트릭으로 나오는 매핑입니다.
  - 『Site Reliability Engineering』 5장(Toil 제거)·6장(모니터링)·7장(자동화의 진화) — 무엇을 자동화하고 무엇을 셀프 서비스로 넘길지 판단 기준을 줍니다. [무료 공개판](https://sre.google/sre-book/table-of-contents/)이 있습니다.
  - 『Team Topologies』 플랫폼 팀과 X-as-a-Service 상호작용 부분 — 티켓을 받아 대신 YAML 을 짜던 팀이 셀프 서비스 플랫폼으로 바뀌는 조직 맥락입니다.
  - 『Kubernetes: Up and Running』 3판 Deployments·Jobs·CronJob 장 — taint 와 배포 전략의 자원 점유를 봅니다. [정독 노트](../../08_cloud/book/kubernetes-up-and-running/README.md)가 있습니다.
  - [kubernetes/git-sync](https://github.com/kubernetes/git-sync) — 새 커밋을 임시 디렉터리에 받은 뒤 심볼릭 링크를 바꿔 원자적으로 동기화하는 구조를 봅니다.
  - [backstage/backstage](https://github.com/backstage/backstage) `plugins/scaffolder-backend/` — 폼 입력을 템플릿에 넣어 PR 을 여는 Software Templates 구현입니다.
  - [kubernetes/kubernetes](https://github.com/kubernetes/kubernetes) `cmd/kubeadm/app/cmd/join.go` — `kubeadm join` 의 TLS 부트스트랩과 노드 등록입니다.
- 실습:
  - Level 1 DNS SRV 디스커버리와 git-sync 캐시: dnsmasq 나 CoreDNS 에 `_k8s-api._tcp` SRV 를 넣고 `dig` 로 호스트명을 파싱합니다. git-sync 컨테이너로 버전별 설정 디렉터리를 받고 네트워크를 끊어도 읽히는지 봅니다. 완료: 호스트명만 넣으면 클러스터 엔드포인트와 설정 경로가 나옵니다.
  - Level 2 PR 을 여는 셀프 서비스 생성기: FastAPI·Jinja2 로 폼 입력에서 Deployment·Service·파이프라인 YAML 을 만들고 GitHub API 로 브랜치와 PR 을 엽니다. `CODEOWNERS` 로 리뷰어를 정합니다. 함정: 같은 서비스 이름으로 PR 이 겹치므로 브랜치 이름에 해시를 붙이고 열린 PR 을 먼저 확인합니다. 완료: 제출 후 5초 안에 매니페스트가 든 PR URL 이 돌아옵니다.
  - Level 3 미사용 워크로드·방치 카나리 탐지 봇: Prometheus HTTP API 로 7일간 요청이 없는 서비스, `kube_cronjob_spec_suspend == 1` 인 배치, 48시간 넘은 `-canary` Deployment 를 고릅니다. 결과는 `owner-team` 라벨의 Slack 채널로 보냅니다. 완료: 트래픽 없는 더미 Deployment 와 `suspend: true` CronJob 을 정확히 잡아냅니다.



## 경고

- ⚠ 성과 수치: "30분 → 2분", "버전당 2시간 → 30분", "서비스 80개, 1,280 Core·1,280GB" 는 자막을 리포트가 옮긴 값입니다. 발표 영상과 대조하지 않았습니다. 표의 "주당 평균 N개" 는 리포트가 값을 채우지 못한 자리입니다.
- ⚠ `--register-schedulable=false`: 자막의 오인식을 리포트가 이 이름으로 고쳤습니다. 이 이름은 kubelet 의 옛 플래그이고 `kubeadm join` 의 옵션이 아닙니다. 실제로는 kubelet `--register-with-taints` 나 조인 뒤 cordon 일 수 있으니 [kubelet 문서](https://kubernetes.io/docs/reference/command-line-tools-reference/kubelet/)로 확인해야 합니다.
- ⚠ 업그레이드 제약의 주체: 리포트는 마이너 버전 하나씩 올리는 제약을 Kubespray 탓으로 적습니다. [클러스터 업그레이드](../../08_cloud/docs/kubernetes/operations/클러스터 업그레이드·ETCD 백업·복구.md) 노트는 kubeadm 과 Version Skew Policy 를 근거로 듭니다. 새 노드 투입으로 줄어드는 것은 노드 쪽 시간입니다.
- ⚠ "트래픽이 없으면 시계열 푸시가 멈춘다": Prometheus 는 카운터를 긁어 가며, Pod 가 살아 있으면 값이 그대로 남습니다. `No Data` 가 언제 나는지는 Istio 의 메트릭 만료 설정에 달려 있어 확인이 필요합니다.
- ⚠ 리포트가 덧붙인 것: Pull 방식의 SPOF 분석, Prometheus 스크랩·헬스 체크 필터링, Cluster API·Karpenter·Kubecost 확장은 발표가 아니라 리포트의 의견입니다.
- ⚠ 책 범위: 『Team Topologies』 는 3부 구성이라 리포트의 "4부" 는 맞지 않습니다. 『Kubernetes: Up and Running』 3판의 장 번호(10장 Deployments, 13장 Jobs)도 정독 노트(12장 Jobs)와 다릅니다.
- ⚠ 코드 경로: git-sync `pkg/sync/`, kubeadm `phases/kubeletfinalize/` 가 리포트 설명대로의 역할인지 저장소에서 확인하지 않았습니다.
- ⚠ 자막 교정: 리포트가 오인식(`데보스`→DevOps, `기 싱크`→git-sync 등)을 고쳤다고 밝힙니다. 발표자 이름과 회사 이름은 뺐습니다.
