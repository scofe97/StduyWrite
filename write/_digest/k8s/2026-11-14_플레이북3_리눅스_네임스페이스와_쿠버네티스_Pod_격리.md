# 리눅스 네임스페이스와 쿠버네티스 Pod 격리 아키텍처 분석 — AI 요약

> 출처: Gemini · 2026-11-14 · [플레이북] 3. 리눅스 네임스페이스와 쿠버네티스 Pod 격리 아키텍처 분석 · 분야: k8s-keywords · 미검증

## 요점

한 줄: 컨테이너는 커널 객체가 아니라 Namespace·cgroups·OverlayFS 의 조합이고, Pod 는 pause 컨테이너가 쥔 공유 네임스페이스 위에 컨테이너별 격리를 얹은 구조라는 내용입니다.

- 컨테이너 본질: 커널에 `struct container` 는 없고 `task_struct` 만 있음. Docker·containerd·`unshare` 모두 `clone()`/`unshare()` 에 `CLONE_NEW*` 를 넘기는 유저 도구임
- 커널 경로: `sys_clone` → `copy_process` → `copy_namespaces` → `create_new_namespaces`(`kernel/nsproxy.c`). 새 네임스페이스마다 고유 inode 번호가 붙음
- 이름 혼동: 쿠버네티스 Namespace(`default`·`kube-system`)는 API 오브젝트를 묶는 폴더이고, 리눅스 Namespace 는 커널의 시야 격리라 서로 다른 개념임
- 네임스페이스는 8종(Mount·PID·Network·IPC·UTS·User·cgroup·Time)이고 쿠버네티스는 Time 을 뺀 7종을 씀. Mount 는 2002년 첫 도입이라 플래그가 `CLONE_NEWNS` 로 남음
- PID Namespace 3특성: 호스트 PID 와 내부 PID 가 공존하는 이중 매핑(`struct pid` 다중 레벨), 호스트는 내부를 보지만 반대는 못 보는 일방 통행, PID 1 종료 시 전체 소멸
- PID 1 이 죽으면 커널이 `zap_pid_ns_processes()` 로 내부 프로세스 전부에 `SIGKILL` 을 보냄. PID 1 은 좀비 수거(`wait()`)와 시그널 전달도 맡아야 함
- PID 1 함정: `ENTRYPOINT sh -c "java -jar ..."` 로 셸이 PID 1 이면 `SIGTERM` 이 자식에 안 가고 좀비가 쌓임. `exec` 로 앱을 PID 1 로 두거나 `tini`·`dumb-init` 을 앞세움
- `unshare --pid` 만 하고 `/proc` 을 다시 마운트하지 않으면 `ps` 가 호스트 `/proc` 을 읽어 호스트 프로세스를 그대로 보임. `ps` 는 시스템 콜이 아니라 `/proc` 파싱이라서 PID 와 Mount 네임스페이스는 함께 써야 함
- pause 컨테이너: 네임스페이스는 안에 프로세스가 없으면 커널이 지우므로, `RunPodSandbox` 단계에서 pause 를 먼저 띄워 Network·IPC·UTS 를 붙잡아 둠. 앱 컨테이너가 재시작해도 Pod IP 가 유지되는 이유임
- Pod 2-3-2 구조: 호스트 보호 2개(User·cgroup), Pod 공유 3개(Network·IPC·UTS), 컨테이너 개별 2개(PID·Mount)로 배치함
- 2-3-2 의 효과: 한 Pod 안에서 `localhost` 통신·같은 호스트명·공유 메모리를 쓰고, `ps`·`/` 는 컨테이너별로 따로 가짐
- 사이드카 효과: 같은 Pod 의 Envoy·로그 수집기가 `127.0.0.1` 과 `/dev/shm` 으로 곧바로 통신함. IPC 공유는 같은 RAM 을 두 주소 공간에 매핑(zero-copy)하고 세마포어로 동기화함
- CNI 주체 변화: 1.24 에서 dockershim 이 빠진 뒤 kubelet 은 containerd 에 `RunPodSandbox` 만 보내고, containerd 가 pause 생성과 CNI 호출(veth 연결·IP 할당)을 맡음
- 런타임 분리: containerd 와 runc 사이의 `containerd-shim-runc-v2` 가 부모로 남아, containerd 를 재시작해도 Pod 의 네임스페이스와 stdio 가 유지됨
- 무침습 노드 진단: 도구 없는 Distroless·Alpine 컨테이너는 `crictl inspect` 로 호스트 PID 를 얻고 `/proc/<PID>/ns/*` inode 를 비교해 격리를 확인함
- `nsenter -t <PID> -n` 으로 호스트의 `ss`·`tcpdump` 를 그 컨테이너 네트워크 공간에서 실행함
- 호스트 침해 통제: `hostPID: true` 는 호스트 초기 PID 네임스페이스(inode 4026531836)에 합류해 `kubelet`·`containerd` 를 `kill` 할 수 있음
- 통제 방법: PSA 로 막고, 모니터링 에이전트 같은 예외는 전용 namespace 에만 허용함
- 비특권 root: `hostUsers: false` 는 컨테이너 root(UID 0)를 `/proc/<pid>/uid_map` 으로 호스트 비특권 UID(예: 100000)에 매핑해 탈출 피해를 줄임
- 한계와 대안: 컨테이너는 호스트 커널 시스템 콜을 직접 호출하므로 커널 취약점(Dirty COW·Dirty Pipe)에 약함. gVisor(Sentry 가 시스템 콜 가로채기, I/O 느림)와 Kata·Firecracker(Pod 마다 경량 커널)가 대안임
- 학습 순서: 프로세스·시그널·`/proc` → Namespace → cgroups v2·OverlayFS → runc·containerd·pause → Seccomp·gVisor·eBPF
- 역할 구분: Namespace 가 시야를, cgroups 가 사용량을, Seccomp·Capabilities 가 시스템 콜 권한을 제한함

## 자료와 실습

- 자료:
  - [namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html) 와 pid_namespaces(7)·network_namespaces(7)·user_namespaces(7): `CLONE_NEW*`, `/proc/<pid>/ns/`, `setns()`·`unshare()` 의 1차 레퍼런스입니다. 가장 먼저 읽을 자료입니다.
  - 커널 소스 [kernel/nsproxy.c](https://github.com/torvalds/linux/blob/master/kernel/nsproxy.c) 와 `kernel/pid_namespace.c`: `copy_namespaces()`·`create_new_namespaces()` 와 PID 1 사망 시 `zap_pid_ns_processes()` 를 봅니다. 노트는 [나머지 namespace와 호스트에서 본 컨테이너](../../08_cloud/book/container-security/04-02.나머지 namespace와 호스트에서 본 컨테이너.md) 입니다.
  - [Pod Security Standards](https://kubernetes.io/docs/concepts/security/pod-security-standards/): `hostPID`·`hostNetwork`·`hostIPC` 공유의 위협과 Baseline·Restricted 차단 기준입니다. 노트는 [파드 보안 설정 강제하기](../../08_cloud/book/cks-study-guide/05-01.파드 보안 설정 강제하기 — securityContext·Pod Security Admission·Gatekeeper.md) 입니다.
  - 『Container Security』(Liz Rice) 2·4·5장: 시스템 콜·권한, 격리, VM 과 컨테이너를 다룹니다. 초급~중급이며 컨테이너가 네임스페이스·cgroups·파일시스템의 조합임을 코드로 보여 줍니다. 노트는 [정독 인덱스](../../08_cloud/book/container-security/README.md) 입니다.
  - 『The Linux Programming Interface』 24~27장(프로세스 생명주기·시그널)과 47~48장(System V 세마포어·공유 메모리): `clone()`·`SIGCHLD`·`waitpid` 의 저수준 계약을 봅니다. 중급~고급이고, 최신 User·cgroup·Time 네임스페이스는 man7.org 로 보완합니다. 노트는 [정독 인덱스](../../02_os/book/tlpi_the-linux-programming-interface/README.md) 입니다.
  - 『Kubernetes in Action』 2판 2~3장: Pod 가 왜 네임스페이스를 공유하는 컨테이너 묶음인지 설계 패턴으로 봅니다. 가까운 노트는 [02-03](../../08_cloud/book/kubernetes-in-action/02-03.네임스페이스와 cgroup으로 보는 컨테이너 격리.md) 입니다.
  - [lizrice/containers-from-scratch](https://github.com/lizrice/containers-from-scratch): Go `main.go` 가 `CLONE_NEWUTS|CLONE_NEWPID|CLONE_NEWNS` 로 자식 프로세스를 띄우고 `/proc` 을 마운트합니다. 초급~중급입니다.
  - [kubernetes `build/pause/linux/pause.c`](https://github.com/kubernetes/kubernetes/blob/master/build/pause/linux/pause.c): 60여 줄 C 로 `sigreap` 좀비 수거와 `for(;;) pause();` 대기를 구현한 인프라 앵커입니다.
  - [runc `libcontainer/nsenter/nsexec.c`](https://github.com/opencontainers/runc/blob/main/libcontainer/nsenter/nsexec.c): Go 런타임이 뜨기 전 C 생성자 단계에서 `clone()`·`setns()` 로 네임스페이스를 옮깁니다. 고급입니다.
- 실습:
  - Level 1: `sudo unshare --pid --mount --uts --net --fork /bin/bash` 뒤 `mount --make-rprivate /` 와 `mount -t proc proc /proc` 을 적용합니다. 격리 셸에서 호스트 프로세스가 안 보임(`kill -0 <호스트PID>` 실패)을 봅니다. 호스트에서 `nsenter -t <격리_bash_PID> -u -p hostname` 으로 일방 통행을 보고, `exit` 뒤 `lsns -t pid` 에서 inode 가 사라지는지 확인합니다. 완료는 호스트 PID 와 내부 PID 1 을 한 프로세스로 대응시키고 `exit` 뒤 네임스페이스가 사라진 출력을 남기는 것입니다. 함정은 `/proc` 을 다시 마운트하지 않으면 `ps` 가 호스트 목록을 그대로 보인다는 점입니다.
  - Level 2: `ip netns add pod-a`·`pod-b` 와 `ip link add veth-a type veth peer name veth-b` 로 가상 케이블을 만들어 각 네임스페이스에 `eth0` 으로 넣고 `up` 합니다. `10.200.1.1/24`·`10.200.1.2/24` 를 주고 `curl` 통신을 성공시켜 CNI 의 개통 원리를 익힙니다. 완료는 양쪽 `curl` 이 성공하고 `ip link` 에서 veth 쌍이 보이는 것입니다.
  - Level 3: Go `exec.Command("/proc/self/exe", "child", ...)` 와 `SysProcAttr.Cloneflags`(`CLONE_NEWPID|NEWUTS|NEWNS|NEWIPC|NEWNET`)로 자식을 띄웁니다. 자식에서 `syscall.Sethostname`, Alpine minirootfs 의 `pivot_root`, `/proc` 마운트를 구현해 mini-runc 를 만듭니다. 완료는 격리 셸에서 `hostname` 이 바뀌고 `ps` 가 PID 1 부터 보이는 것입니다.



## 경고

- ⚠ "Time Namespace는 현재 runc 및 Kubernetes에서 사용하지 않음" — runc 는 OCI 명세에 따라 Time 네임스페이스를 지원하므로 runc 미지원 단정은 공식 기능과 다릅니다 (원문 66줄). — 확인됨: [runc v1.2.0 CHANGELOG](https://raw.githubusercontent.com/opencontainers/runc/v1.2.0/CHANGELOG.md). Time 은 Linux 5.6 부터라는 점도 [namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html) 로 확인됨 쿠버네티스 미사용 부분은 맞습니다. CRI `NamespaceOption` 에 Time 필드가 없습니다.
- ⚠ "Kubernetes 기본 설정에서 /dev/shm 크기는 항상 64MB" (원문 51줄) — 기본 64MB 는 containerd·CRI-O 모두 맞습니다. 「항상」이 과장이고, CRI-O 는 `shm-size.crio.io` annotation 으로 바꿀 수 있습니다. — 확인됨: [containerd helpers_linux.go](https://raw.githubusercontent.com/containerd/containerd/v2.1.0/internal/cri/server/podsandbox/helpers_linux.go) 의 `defaultShmSize`, [CRI-O sandbox.go](https://raw.githubusercontent.com/cri-o/cri-o/main/internal/lib/sandbox/sandbox.go) 의 `DefaultShmSize`, [CRI-O annotations.go](https://raw.githubusercontent.com/cri-o/cri-o/main/pkg/annotations/v2/annotations.go)
- ⚠ "Kubernetes 1.30+에서 hostUsers: false로 User NS 격리 활성화" — 1.30 은 beta 지만 기본 꺼짐이라 feature gate 를 켜야 했습니다 (원문 186·193줄). 기본 켜짐은 1.33(beta), GA 는 1.36 이고, 커널 idmapped mounts 와 볼륨 파일시스템 지원 제약이 따릅니다. — 확인됨: [kubernetes v1.36.0 kube_features.go](https://raw.githubusercontent.com/kubernetes/kubernetes/v1.36.0/pkg/features/kube_features.go) 제약은 [User Namespaces 문서](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/workloads/pods/user-namespaces.md) 에 있습니다.
- ⚠ "2-3-2: User·cgroup 은 호스트 보호, PID·Mount 는 컨테이너 개별" (원문 47·70~72줄) — 쉬운 모델일 뿐 CRI 와 어긋납니다. CRI 에서 User 는 Pod 단위(POD·NODE)이고 기본(`hostUsers: true`)은 호스트 것을 씁니다. cgroup 은 출시된 CRI(v0.36, K8s 1.36)에 필드가 없어 런타임 기본값을 따르고, 컨테이너 단위(CONTAINER·NODE) 선택은 2026-09 master 에 들어온 KEP-5714 필드입니다. PID 는 기본 컨테이너별이지만 `shareProcessNamespace` 로 Pod 공유가 됩니다. Mount 는 `NamespaceOption` 에 없고, UTS 는 Network 를 따라 Pod 단위로 공유됩니다. — 확인됨: [cri-api api.proto](https://raw.githubusercontent.com/kubernetes/cri-api/master/pkg/apis/runtime/v1/api.proto), [containerd spec_opts.go](https://raw.githubusercontent.com/containerd/containerd/v2.1.0/internal/cri/opts/spec_opts.go) 328줄
- ⚠ "pause 가 좀비 프로세스를 수거하고 네임스페이스를 유지" (원문 46·67줄) — pause 는 `sigreap` 으로 자기 PID 네임스페이스의 좀비를 거둡니다. 기본 Pod 에서 pause 는 샌드박스 전용 PID 네임스페이스의 PID 1 이고, 앱 컨테이너의 좀비는 각 컨테이너의 PID 1 이 거둡니다. pause 가 앱 프로세스의 좀비까지 거두는 것은 `shareProcessNamespace: true` 일 때뿐입니다. — 확인됨: [pause.c](https://raw.githubusercontent.com/kubernetes/kubernetes/master/build/pause/linux/pause.c) 의 `getpid() != 1` 경고, [containerd sandbox_run_linux.go](https://raw.githubusercontent.com/containerd/containerd/v2.1.0/internal/cri/server/podsandbox/sandbox_run_linux.go) 는 NODE 일 때만 PID 네임스페이스를 뺍니다. [Share Process Namespace](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/tasks/configure-pod-container/share-process-namespace.md)
- ⚠ "pause 가 Network 네임스페이스를 붙잡아 앱 재시작에도 Pod IP 유지" (원문 46·49줄) — 과장입니다. containerd 는 pause 를 띄우기 전에 netns 를 직접 만들고 `/var/run/netns` 에 bind mount 로 고정한 뒤 pause 를 그 안에 넣습니다. 네임스페이스는 bind mount·열린 fd 가 있으면 프로세스가 없어도 남습니다. — 확인됨: [containerd sandbox_run.go](https://raw.githubusercontent.com/containerd/containerd/v2.1.0/internal/cri/server/sandbox_run.go) 의 `netns.NewNetNS`, [namespaces(7)](https://man7.org/linux/man-pages/man7/namespaces.7.html) 「Namespace lifetime」
- ⚠ "PSA restricted 프로파일로 hostPID 를 원천 차단" — `hostPID`·`hostNetwork`·`hostIPC` 는 Baseline 부터 금지이고 Restricted 는 Baseline 을 포함합니다 (원문 38·172~173줄). — 확인됨: [Pod Security Standards](https://raw.githubusercontent.com/kubernetes/website/main/content/en/docs/concepts/security/pod-security-standards.md)
- ⚠ Level 1 의 `mount --make-rprivate /` 단계 (원문 259줄) — util-linux 2.27 부터 `unshare` 가 새 마운트 네임스페이스를 기본 private 으로 바꿔 대개 생략해도 됩니다. `--propagation unchanged` 를 줬을 때만 shared 전파 위험이 있습니다. — 확인됨: [unshare(1)](https://raw.githubusercontent.com/util-linux/util-linux/v2.40/sys-utils/unshare.1.adoc)
- ⚠ "호스트 PID 네임스페이스 inode 4026531836" (원문 16줄) — 확인됨: `PID_NS_INIT_INO = 0xEFFFFFFC` 가 4026531836 입니다. [nsfs.h](https://git.kernel.org/pub/scm/linux/kernel/git/torvalds/linux.git/plain/include/uapi/linux/nsfs.h)

- ⚠ "`sh -c \"java -jar app.jar\"` 형태면 sh 가 PID 1 이라 SIGTERM 을 전달하지 못함" (원문 41줄) — 셸 구현에 따라 단일 명령은 앱이 PID 1 이 되기도 해서 일괄 단정은 어렵습니다. 실측으로 확인했습니다. dash 0.5.12(Debian 12·Ubuntu 24.04)는 `sh -c "sleep 5"` 에서 sh 가 PID 1 로 남고, Rocky 9 의 sh(bash)는 단일 명령을 exec 해 앱이 PID 1 이 됩니다. 명령이 둘 이상이면 셋 다 sh 가 PID 1 입니다.
