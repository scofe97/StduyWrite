## 요점

한 줄: cgroup v2 가 Pod 의 `requests`·`limits` 를 CPU 는 throttling, 메모리는 OOM kill 로 강제하므로, 평균 사용률이 아니라 `cpu.stat`·QoS 점수로 봐야 한다는 내용입니다.

- namespace 가 "무엇을 보는가"를 가른다면 cgroup 은 "얼마나 쓰는가"를 커널이 강제합니다. Pod 의 `requests`·`limits` 는 kubelet → containerd → runc 를 거쳐 `/sys/fs/cgroup` 의 `cpu.max`·`cpu.weight`·`memory.max` 같은 파일 값이 됩니다.
- CPU 는 압축 가능 자원이라 한도를 넘으면 throttling 으로 다음 주기까지 멈춥니다. 메모리는 비압축 자원이라 회수에 실패하면 cgroup OOM killer 가 SIGKILL 을 보내고 종료 코드는 137 입니다.
- `cpu.max` 는 주기(기본 100ms)당 쓸 수 있는 CPU 시간입니다. `1000m` 은 코어 하나를 독점한다는 뜻이 아닙니다. 8개 스레드가 동시에 일하면 12.5ms 만에 쿼터를 다 쓰고 남은 87.5ms 동안 멈춥니다.
- 평균 CPU 사용률(`kubectl top`)로는 throttling 이 보이지 않습니다. `cpu.stat` 의 `nr_throttled`·`throttled_usec`, 또는 `container_cpu_cfs_throttled_periods_total` 을 봅니다.
- Endowus 사례: 6GB Pod 에 `-XX:MaxRAMPercentage=80` 을 줬고, 힙이 4.37GB 일 때 OOMKilled 가 반복됐습니다. NMT 로 따라가 보니 Akka 메일박스·Netty 버퍼 같은 off-heap 과 대시보드에 안 잡히는 `JImageReader` 등이 더해져 `memory.max` 를 넘었습니다. 힙 비율을 50~70% 로 내리고 메일박스 상한을 줄여 해결했습니다.
- QoS 와 `oom_score_adj`: BestEffort 1000, Burstable 2~999(메모리 요청 비율로 계산), Guaranteed -997, kubelet 같은 시스템 데몬 -999 입니다. 노드 메모리가 부족하면 점수가 높은 쪽부터 죽습니다.
- 원문은 `limits.cpu` 를 빼고 `requests.cpu` 만 두는 운영을 권합니다. 대신 CPU limit 이 없으면 Guaranteed 가 될 수 없어 Burstable 로 내려갑니다.
- 대본 정정: 영상의 `cpu.shares` 는 cgroup v1 이름이고 v2 에서는 `cpu.weight`(기본 100, 범위 1~10000)입니다. Burstable 1% 요청의 점수는 999 가 아니라 990 입니다. 커널 6.6 부터 CFS 는 EEVDF 로 바뀌었지만 `cpu.max` 기반 throttling 은 그대로입니다.
- 찾을 키워드: `EEVDF scheduler 6.6`, `runc cgroup fs2`, `systemd cgroup driver`, `CPU Manager static policy`, `Kyverno require requests limits` 입니다.

## 자료와 실습

- 자료:
  - [Control Group v2 (Linux 커널 문서)](https://docs.kernel.org/admin-guide/cgroup-v2.html): `memory.min`·`memory.max`·`cpu.max`·`cpu.weight` 등 cgroup v2 가상 파일시스템 인터페이스와 회수 알고리즘의 1차 명세입니다. 정독 노트는 [cgroup v2](../../02_os/docs/kernel/01-01.cgroup v2.md) 입니다.
  - [Resource Management for Pods and Containers (Kubernetes 문서)](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/): `requests`·`limits` 가 cgroup 값으로 매핑되는 규칙과 QoS 등급별 계산 가이드입니다.
  - [Pod Quality of Service Classes (Kubernetes 문서)](https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/): QoS 판별 조건과 `oom_score_adj` 산출 공식 명세입니다.
  - [OOMKilled: At Least For Now](https://endowus.com/insights/oomkilled-at-least-for-now): JVM 힙 외 Akka 메일박스·Netty 버퍼·`JImageReader` 추적 과정이 담긴 포스트모템입니다. 관련 노트는 [힙 밖에서 쌓이는 메모리](../../troubleshooting/_concepts/runtime-힙-밖에서-쌓이는-메모리.md) 입니다.
  - [Resource Requests and Limits](https://cloud.google.com/blog/products/containers-kubernetes/kubernetes-best-practices-resource-requests-and-limits): `limits.cpu` 설정 시 발생하는 throttling 문제와 `requests.cpu` 설계 가이드입니다.
  - [cgroups(7)](https://man7.org/linux/man-pages/man7/cgroups.7.html): `/sys/fs/cgroup` 및 `/proc/[pid]/oom_score_adj` 커널 사양 매뉴얼입니다. `proc(5)` 도 함께 봅니다.
  - 『Systems Performance』 2판: 리포트는 6장(CPU)·7장(메모리)·11장(클라우드와 컨테이너)을 권합니다. 정독 노트는 [systems-performance](../../02_os/book/systems-performance/README.md) 의 06-02·07-04·11-03 편입니다.
  - 『Container Security』: 리포트는 2장(시스템 콜과 권한)·4장(컨테이너 격리 메커니즘)을 권합니다. 정독 노트는 [container-security](../../08_cloud/book/container-security/README.md) 의 02-01·03-01 편입니다.
  - 『Kubernetes in Action』 2판: Pod 컴퓨팅 리소스와 QoS 클래스를 다룹니다. 정독 노트는 [kubernetes-in-action](../../08_cloud/book/kubernetes-in-action/README.md) 의 02-03 편입니다.
  - 코드: [containers-from-scratch](https://github.com/lizrice/containers-from-scratch) `main.go` 의 `cg()` 함수(cgroup 디렉터리 생성과 자원 제한)를 봅니다. runc `libcontainer/cgroups/fs2/` 의 `memory.go`·`cpu.go` 와 kubernetes `pkg/apis/core/helper/qos/qos.go`·`pkg/kubelet/qos/policy.go` 도 봅니다.
- 실습:
  - Level 1: 순수 Linux `/sys/fs/cgroup` 가상 파일시스템에 디렉터리를 만들고 Bash 와 Python 으로 CPU throttling 과 OOM kill 을 검증합니다. 함정은 부모 cgroup 의 `cgroup.subtree_control` 에 `+cpu +memory` 가 없으면 하위에 `cpu.max` 나 `memory.max` 파일이 생기지 않는 것입니다. 완료: `memory.events` 의 `oom_kill` 증가와 `dmesg -T` 의 OOM 메시지를 확인하고 프로세스 종료 코드가 137 인지 확인합니다.
  - Level 2: 메모리 한도 256MiB 에 `-Xmx128m` 으로 실행되는 Java 앱에서 `ByteBuffer.allocateDirect` 로 off-heap OOM 을 재현하고 `jcmd` NMT 로 진단합니다. 함정은 `-XX:MaxDirectMemorySize` 를 주지 않으면 힙 크기만큼 다이렉트 메모리를 허용해 컨테이너 한도를 쉽게 넘기는 것입니다. 완료: `MaxRAMPercentage=60.0` 과 `-XX:MaxDirectMemorySize` 설정으로 동일 부하에서 `OOMKilled` 없이 안정적으로 동작하도록 개선합니다.
  - Level 3: Go 로 `/sys/fs/cgroup/kubepods.slice` 하위를 탐색해 `cpu.stat` 과 `memory.current`·`memory.pressure`(PSI)를 읽는 throttling·OOM 위험 감지 데몬을 만듭니다. 함정은 Pod 생성·삭제 때 cgroup 디렉터리가 동적으로 사라지므로 파일 읽기 때 `os.ErrNotExist` 에러를 우아하게 처리해야 하는 것입니다. 완료: BestEffort·Burstable·Guaranteed Pod 에 부하를 가할 때 데몬이 QoS 점수와 throttling 비율을 탐지해 Prometheus 메트릭으로 노출합니다.



## 경고

- ⚠ 원문 흐름도는 runc 가 `memory.min` 에 requests 값을 쓴다고 그립니다. 기본 설정에서 kubelet 은 `memory.min`·`memory.low` 를 쓰지 않고, 따로 켰을 때만 씁니다. — 확인됨: [Pod QoS 문서](https://kubernetes.io/docs/concepts/workloads/pods/pod-qos/) ([kubernetes-in-action 02-03](../../08_cloud/book/kubernetes-in-action/02-03.네임스페이스와 cgroup으로 보는 컨테이너 격리.md) 각주에 2026-11-04 조회 기록)
- ⚠ 원문은 `memory.max` 가 "RSS 전체(RSS + Page Cache)"를 본다고 씁니다. RSS 는 page cache 를 포함하지 않는 다른 지표이고, cgroup 은 익명 페이지·파일 페이지·커널 메모리를 따로 셉니다. 또 원문은 "커널 슬랩이 격리되지 않는다"고 하지만 cgroup v2 는 커널 메모리도 기본으로 셉니다. 두 말이 서로 어긋납니다.
- ⚠ "Google·Datadog·Zalando 는 `limits.cpu` 를 아예 설정하지 않는다"는 출처가 없습니다. CPU limit 제거는 노이즈 이웃과 QoS 강등을 함께 따지는 논쟁 주제입니다.
- ⚠ 종료 코드 137 은 SIGKILL 을 받았다는 뜻일 뿐입니다. cgroup OOM killer 말고 kubelet 축출·사람의 `kill -9` 로도 같은 값이 나옵니다.
- ⚠ 원문이 적은 Endowus 글 URL(`endowus.com/insights/oomkilled-at-least-for-now`)과 제목·연도는 확인하지 않았습니다. 기존 노트는 `build.endowus.com/oomkilled/` 와 Medium `endowus-tech` 글을 인용합니다.
- ⚠ "힙을 50~70% 로 보수적으로" 는 한 사례의 결론입니다. 원문도 힙을 줄이면 GC 가 잦아져 CPU 사용과 throttling 이 늘 수 있다고 적었습니다.
- ⚠ runc 의 cgroup 코드 위치 `libcontainer/cgroups/fs2/` 는 버전에 따라 별도 저장소로 옮겨졌을 수 있습니다. 확인하지 않았습니다.
- ⚠ 원문은 『Container Security』 추천 범위를 2·4장으로 적었습니다. cgroup 은 3장입니다([container-security 03-01](../../08_cloud/book/container-security/03-01.Control Group — 자원을 제한해 굶기기를 막다.md)).
- ⚠ 『Kubernetes in Action』 2판에서 QoS 를 다루는 장 번호는 원문도 적지 않았습니다. 지금 노트는 18장까지 있습니다.
