## 요점

한 줄: Service 는 트래픽을 받는 프로세스가 아니라 kube-proxy 가 각 노드의 nat 테이블에 쓴 규칙 묶음이고, 커널 상태 테이블(conntrack)이 어긋나면 지표가 모두 정상이어도 서비스가 멈춘다고 봅니다.

- 질의 출발: 앱이 `getaddrinfo()` 를 부르면 `/etc/resolv.conf` 의 ClusterIP `10.96.0.10:53` 으로 패킷이 나갑니다.
- 커널 경로: PREROUTING → KUBE-SERVICES → KUBE-SVC-\* → KUBE-SEP-\* DNAT 를 지나 conntrack 에 기록되고, L2 또는 L3 로 전달됩니다.
- 확률 분산: 엔드포인트 3개면 `--probability 0.3333`, 남은 것 중 `0.50`, 마지막 `1.00` 으로 고릅니다. 부하나 연결 수는 보지 않으므로 L7 제어는 Ingress·Service Mesh 몫이라고 합니다.
- conntrack 이 필요한 이유: DNAT 로 바꾼 목적지를 기록해 두어야 응답의 출발지를 다시 ClusterIP 로 되돌릴 수 있습니다.
- 사례(원문 기준): CoreDNS 컨테이너 하나가 OOMKilled(Exit 137)된 뒤 5초 만에 같은 Pod IP 로 재시작했습니다. 그런데 클러스터 전체에 `read udp ...:53: i/o timeout` 이 계속 났습니다.
- 맞물린 조건 넷: CoreDNS OOMKilled 와 kube-proxy 가 지우지 않은 stale UDP conntrack 이 먼저입니다. 여기에 Istio 사이드카의 30초 주기 같은 출발지 포트 DNS 갱신과 UDP conntrack 120초 타이머 갱신이 겹쳤습니다.
- 원문의 교훈: CPU·메모리·Pod `Running` 이 모두 정상이어도 커널 상태 테이블이 어긋나면 서비스가 멈춥니다. 장애는 계층마다 다른 기본값(120초 > 30초)이 만날 때 난다고 합니다.
- 대응(원문): NodeLocal DNSCache(`169.254.20.10`, raw 테이블 `NOTRACK`)와 kube-proxy 의 stale UDP conntrack 정리 기능입니다.
- 진단 명령(체인·항목 조회): `iptables -t nat -L KUBE-SERVICES -n`, `conntrack -L -p udp --dport 53` 입니다.
- 진단 명령(복구·캡처): `conntrack -D -p udp --dport 53 --reply-src <IP>`, `tcpdump -i any -nn -e "udp port 53"` 입니다.
- 상시 관측: 노드에 매번 들어가는 대신 Cilium Hubble 이나 node_exporter 의 `node_nf_conntrack_entries` 를 수집하라고 권합니다.
- 찾을 키워드: conntrack 은 `nf_conntrack_udp_timeout_stream`, `conntrack reconciler`, `--conntrack-tcp-be-liberal` 입니다. iptables 모드는 `KUBE-MARK-MASQ`, `MinimizeIPTablesRestore` 입니다.

  - [A Deep Dive into Iptables and Netfilter Architecture](https://www.digitalocean.com/community/tutorials/a-deep-dive-into-iptables-and-netfilter-architecture): PREROUTING·OUTPUT·POSTROUTING 과 nat·filter 테이블 순서를 정리한 아티클입니다.
  - [Cracking Kubernetes Node Proxy (aka kube-proxy)](https://arthurchiao.art/blog/cracking-k8s-node-proxy/): kube-proxy 가 만드는 `KUBE-SVC`·`KUBE-SEP` 같은 체인을 실제 규칙 덤프로 해부한 블로그 글입니다.
  - 『Networking and Kubernetes』: 리포트는 2장(Linux 네트워킹)·4장(Kubernetes 네트워킹과 CNI)·5장(Service 와 kube-proxy)을 권합니다. 정독 노트는 [networking-and-kubernetes](../../08_cloud/book/networking-and-kubernetes/README.md) 의 02-02·02-03·04-02 편입니다.
  - 『The TCP/IP Guide』: IP 주소·CIDR 서브넷팅, ARP, TCP/UDP 파트에서 패킷 헤더와 상태 머신 기초를 다룹니다.

  - 코드: [metallb](https://github.com/metallb/metallb) 의 `speaker/layer2_controller.go`(가상 IP ARP 응답)를 봅니다. coredns 의 `plugin/kubernetes/` 와 kubernetes `pkg/proxy/iptables/proxier.go`·`pkg/proxy/conntrack/` 도 봅니다.
- 실습:
  - Level 1: Docker·Kubernetes 없이 순수 리눅스 명령어로 `ip netns`·veth pair·브리지(`br0`)와 iptables DNAT 로 가상 ClusterIP 로드밸런싱을 구축합니다. 함정은 `net.ipv4.ip_forward=1` 이 꺼져 있거나 `FORWARD` 체인 기본 정책이 DROP 이면 네임스페이스 간 패킷이 차단되는 것입니다. 완료: 가상 IP `10.96.0.100` 호출 시 백엔드 HTTP 응답이 정상 반환되고 `conntrack -L` 에 양방향 NAT 매핑이 기록됨을 증명합니다.
  - Level 2: 출발지 포트를 고정한 UDP 클라이언트로 가상 IP 에 질의를 보내며 백엔드 강제 종료 후 stale conntrack 블랙홀을 재현합니다. 함정은 일반 소켓이 임시 포트를 임의 할당하므로 장애를 재현하려면 클라이언트의 로컬 포트를 반드시 고정해야 하는 것입니다. 완료: 120초 타이머가 매 요청마다 초기화되는 패킷 유실을 관찰하고 `conntrack -D` 로 항목을 지워 새 서버로 즉시 복구합니다.
  - Level 3: Go 와 Netlink 소켓으로 conntrack 테이블을 스캔하고 종료된 백엔드의 고아 UDP 항목을 지우는 자동 리컨사일러를 만듭니다. 함정은 Netlink 소켓 조작을 위해 `CAP_NET_ADMIN` 권한이 필요하고 테이블 스캔 시 CPU 스파이크 방지 배칭이 필요한 것입니다. 완료: 백엔드 종료 후 1초 이내에 stale 엔트리를 지워 후속 DNS 질의 타임아웃을 0건으로 유지하고 Prometheus 메트릭으로 노출합니다.



## 경고

- ⚠ IPVS 위상: 원문은 IPVS 를 eBPF 와 함께 "현대 프로덕션 표준" 으로 적습니다. 공식 문서는 IPVS 모드를 deprecated 로 표시합니다. 기본 비활성화는 v1.40, 제거는 v1.43 이고, 대체로 nftables 모드를 권합니다(확인됨, [Virtual IPs and Service Proxies](https://kubernetes.io/docs/reference/networking/virtual-ips/)).
- ⚠ 빠진 모드: 원문 비교표에는 nftables 가 없습니다. 공식 문서는 Linux 프록시 모드로 iptables·ipvs·nftables 셋을 들고, 기본값은 지금 iptables 이며 앞으로 nftables 로 바뀐다고 적습니다(확인됨, 위 문서).
- ⚠ 고친 버전: "kube-proxy 의 UDP conntrack 정리 기능이 Kubernetes 1.32 에 반영됐다" 는 확인하지 않았습니다. 비슷한 race 사례는 이슈 #126468 로 [트러블슈팅 노트](../../troubleshooting/os/2026-09-22_저절로 풀리지 않는 일부 Pod 의 DNS 타임아웃.md)에 있습니다.
- ⚠ 사례 출처: "Cisco ThousandEyes 2025년 9월 발표" 는 원문이 자막에서 고친 이름입니다. 원문 링크는 블로그 첫 화면뿐이라 발표 원본을 확인하지 않았습니다.
- ⚠ UDP 타이머: 원문은 UDP conntrack 기본값을 120초 하나로 적습니다. 커널에는 응답 전 수명과 양방향 이후 수명(`udp_timeout_stream`) 두 값이 있습니다. 두 값은 [networking-and-kubernetes 02-02](../../08_cloud/book/networking-and-kubernetes/02-02.커널이 패킷을 판정하는 층 — Netfilter·Conntrack·라우팅.md)에 정리돼 있습니다.
- ⚠ 게이트웨이 주소: "다른 대역은 목적지 MAC 이 게이트웨이 `169.254.1.1` 로 설정된다" 는 Calico 의 방식입니다. CNI 마다 다르므로 일반 규칙으로 읽으면 안 됩니다.
- ⚠ 포트 사슬: "NodePort → port → targetPort → containerPort 4단계" 에서 containerPort 는 정보용 선언입니다. 실제 DNAT 목적지는 targetPort 입니다.
- ⚠ 수치: "NodeLocal DNSCache 로 DNS 응답이 수 ms 이하로 준다", "Istio 사이드카가 30초마다 같은 포트로 갱신한다" 는 원문 수치이고 출처가 없습니다.
- ⚠ 책 장 매핑: 원문은 『Networking and Kubernetes』 5장을 "Service 와 kube-proxy iptables/IPVS" 로 소개합니다. 노트 기준으로 iptables·IPVS 는 [2장](../../08_cloud/book/networking-and-kubernetes/02-03.iptables·IPVS·eBPF — kube-proxy를 이해하는 세 기술.md)에 있습니다. kube-proxy 는 [4장](../../08_cloud/book/networking-and-kubernetes/04-02.CNI와 kube-proxy — Pod 네트워크의 배선공과 로드밸런서.md)에 있습니다.
- ⚠ 도서 표기: 원문은 『BPF Performance Tools』(Brendan Gregg)와 『Learning eBPF』(Liz Rice)를 한 항목에 묶고 출판 정보를 하나로 적었습니다. 두 권은 다른 책입니다.
- ⚠ 도서 연식: 『The TCP/IP Guide』 는 2005년 책이라 오버레이·eBPF 는 따로 보완해야 한다고 원문도 적었습니다.
