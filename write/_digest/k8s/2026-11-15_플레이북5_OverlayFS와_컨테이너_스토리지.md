## 요점

한 줄: OverlayFS 는 읽기 전용 레이어 위에 쓰기 층을 겹친 파일 단위 CoW 라서, 쓰기가 많은 디렉터리는 볼륨으로 빼라는 내용입니다.

- 영상의 큰 틀: 컨테이너는 Namespace·cgroup·OverlayFS 세 기능으로 만들고, 이 편은 파일시스템 층인 OverlayFS 를 다룹니다.
- 구조: lowerdir(읽기 전용 레이어 여러 장) 위에 upperdir(쓰기 층)을 겹치고, workdir 에서 원자적 교체를 준비한 뒤 merged 로 보여 줍니다.
- 읽기·쓰기·삭제 비용이 다릅니다. 읽기는 하위 층을 그대로 읽고, 쓰기는 파일 전체를 copy_up 한 뒤 고치며, 삭제는 Whiteout 으로 가립니다.
- 원문은 OverlayFS 를 파일 단위 CoW 로, ZFS·Btrfs 를 블록 단위 CoW 로 대비합니다. 큰 파일 하나에 조금씩 덧붙이는 패턴(SQLite·로그 append)에 약합니다.
- 쓰기가 많은 디렉터리는 PersistentVolume 이나 emptyDir 로 빼서 OverlayFS 쓰기 층을 우회하라고 권합니다.
- containerd 는 레이어 폴더를 SHA-256 해시가 아닌 짧은 정수 ID 로 만듭니다. 원문은 그 이유를 마운트 옵션 문자열의 1페이지 한계로 설명합니다.
- 스냅샷 디렉터리는 `/var/lib/containerd/io.containerd.snapshotter.v1.overlayfs/snapshots/` 입니다. Committed 와 Active 의 점유를 나눠 보면 DiskPressure 원인을 가를 수 있다고 합니다.
- Netflix 사례: Docker 에서 containerd 와 User Namespace(idmap)로 옮겼습니다. 그 뒤 50레이어 컨테이너 100개를 동시에 띄우자 mount/umount 가 약 20,200번 일어났습니다.
- 그 결과 96 vCPU 의 r5.metal 노드가 mount_lock 스핀 대기로 30초 넘게 멈췄고, Flame Graph 에서 `path_init` 병목을 찾았습니다.
- 우회와 해결: 먼저 CCX 구조인 m7a·m7i 인스턴스로 옮겨 견뎠습니다. 그다음 recursive bind mount 로 마운트 호출을 약 600번(약 33배 감소)으로 줄였습니다.
- 하드웨어 요인 셋: NUMA 인터커넥트, SMT 의 물리 코어 공유, 단일 LLC 의 캐시 일관성 트래픽입니다.
- 원문의 교훈: 락 종류를 바꾸기보다 작업을 묶어 락을 잡는 횟수를 줄이는 것(배칭)이 근본 해법이라고 합니다.
- 찾을 키워드: `metacopy`, `redirect_dir`, `copy_mount_options`, `open_tree`, `MOUNT_ATTR_IDMAP` 입니다.

## 자료와 실습

- 자료:
  - [Overlay Filesystem (Linux 커널 문서)](https://docs.kernel.org/filesystems/overlayfs.html): `lowerdir`·`upperdir`·`workdir` 규칙과 Whiteout(`c 0,0`), `metacopy` 최적화 옵션 명세입니다.
  - [Mount Metrics: Scaling Containers on Modern CPUs](https://netflixtechblog.com/mount-metrics-scaling-containers-on-modern-cpus-2878c8b19c53): idmap 마운트 폭발과 `mount_lock` 스핀락 병목을 Flame Graph 로 분석한 포스트모템입니다. 정독 노트는 [OverlayFS와 idmapped mount](../../02_os/docs/kernel/OverlayFS 와 idmapped mount — Netflix 사례.md) 입니다.
  - [containerd Snapshotters Documentation](https://github.com/containerd/containerd/tree/main/docs/snapshotters): containerd 가 overlayfs 스냅샷터와 bbolt 메타데이터로 레이어를 관리하는 공식 문서입니다.
  - [Idmapped Mounts in the Linux Kernel (LWN.net)](https://lwn.net/Articles/837566/): idmap 마운트와 `AT_RECURSIVE` 기능 도입 배경과 VFS 변경 사항을 다룬 아티클입니다.
  - [mount_setattr(2)](https://man7.org/linux/man-pages/man2/mount_setattr.2.html): idmap 마운트와 `AT_RECURSIVE` 플래그의 시스템 콜 명세입니다.
  - [CPU Flame Graphs & Linux Performance](https://www.brendangregg.com/flamegraphs.html): 커널 스핀락 병목과 호출 스택을 시각화하는 해석 가이드입니다.
  - 『Systems Performance』 2판: 리포트는 2장(방법론)·6장(CPU와 캐시/NUMA)·8장(파일시스템)을 권합니다. 정독 노트는 [systems-performance](../../02_os/book/systems-performance/README.md) 의 06-02·08-02 편입니다.
  - 『Container Security』: 리포트는 3장(컨테이너 격리)·4장(가상화 vs 컨테이너)·6장(보안과 User Namespace)을 권합니다. 정독 노트는 [container-security](../../08_cloud/book/container-security/README.md) 의 04-02·06-01 편입니다.
  - 『Operating Systems: Three Easy Pieces』: 28장(락과 스핀락 vs 슬립락)과 40장(파일시스템 구현)에서 동시성과 원자적 rename 원리를 다룹니다([OSTEP 무료 웹판](https://pages.cs.wisc.edu/~remzi/OSTEP/)).
  - 코드: [moby](https://github.com/moby/moby) 의 `overlay.go`(콜론 문자열 조립)를 봅니다. containerd 의 `overlay.go`·`bolt.go` 와 linux `fs/overlayfs/` 의 `copy_up.c`·`dir.c` 도 봅니다.
- 실습:
  - Level 1: 순수 리눅스 `mount -t overlay` 로 `lower`·`upper`·`work`·`merged` 4개 영역을 조립하고 파일 수정 시 CoW 와 삭제 시 `c 0,0` 장치 생성을 검증합니다. 함정은 마운트 상태에서 디렉터리를 지우려 하면 `Device or resource busy` 에러가 나는 것입니다. 완료: `lower` 원본이 보존된 채 `merged` 에만 변경이 반영되고 `umount` 로 정리합니다.
  - Level 2: 64자리 해시 디렉터리 35개를 콜론으로 이어 붙여 4,096바이트 초과 `lowerdir` 옵션으로 `mount -t overlay` 가 `EINVAL` 로 실패함을 재현합니다. 함정은 커맨드라인 길이(`ARG_MAX`)가 아니라 `mount(2)` 커널의 `PAGE_SIZE` 한계임을 `strace` 로 가르는 것입니다. 완료: 짧은 정수 ID 경로로 치환해 마운트에 성공하고 `strace` 로 반환값을 대조합니다.
  - Level 3: 50개 레이어 이미지와 3개 레이어 이미지로 각각 50개 컨테이너를 동시 기동하며 `perf record -g -a` 로 `do_mount`·`path_init` 커널 함수 점유율을 측정합니다. 함정은 호스트 커널 심볼 프로파일링을 위해 루트 권한과 `kernel.perf_event_paranoid` 설정이 필요한 것입니다. 완료: Flame Graph 로 레이어 수 최적화가 커널 마운트 락 경합을 줄이는 효과를 비교합니다.



## 경고

- ⚠ 커널 버전: 원문은 "Linux 6.3 에서 AT_RECURSIVE idmap 이 도입됐다"고 적습니다. man page 는 `mount_setattr()` 와 `AT_RECURSIVE` 가 Linux 5.12 에 처음 나왔다고 적습니다. 6.3 에서 무엇이 더해졌는지는 확인하지 않았습니다(5.12 부분 확인됨, [mount_setattr(2)](https://man7.org/linux/man-pages/man2/mount_setattr.2.html)).
- ⚠ 읽기 비용 0: "읽기는 Zero-cost" 는 과장입니다. 여러 층을 거치는 이름 조회 비용이 있고, 커널 문서의 metacopy 를 켜면 소유권·권한 변경은 데이터 없이 메타데이터만 copy_up 합니다(metacopy 확인됨, [OverlayFS 커널 문서](https://docs.kernel.org/filesystems/overlayfs.html)).
- ⚠ Whiteout 형식: 원문은 `c 0,0` 문자 장치만 적습니다. 커널 문서는 `trusted.overlay.whiteout` xattr 를 단 크기 0 파일도 whiteout 으로 인정합니다(확인됨, [OverlayFS 커널 문서](https://docs.kernel.org/filesystems/overlayfs.html)).
- ⚠ 락 종류: 원문은 mount_lock 을 스핀락이라고 단정합니다. 커널 소스에서는 seqlock 으로 선언된 것으로 알려져 있어, 쓰는 쪽만 스핀락을 잡는지 확인이 필요합니다(이번에 소스 조회 실패).
- ⚠ 수치: 20,200번 → 600번(33배), "마운트 갱신은 1μs 이내", "문맥 교환은 수십 μs" 는 원문 수치입니다. Netflix 글 원문과 대조하지 않았습니다(블로그 접근 403).
- ⚠ 사례 날짜: 자막의 "2015년 11월" 을 원문이 2023년 11월 Netflix TechBlog 글로 고쳤습니다. 이 날짜는 확인하지 않았습니다.
- ⚠ containerd 정수 ID 이유: "마운트 옵션 1페이지 한계 때문" 이라는 설명은 원문 해석입니다. containerd 문서나 커밋으로 확인하지 않았습니다.
- ⚠ 모호한 권고: "자주 변경되는 레이어를 하단에 배치" 는 Dockerfile 아래쪽(나중 레이어)인지 이미지 스택 아래쪽인지 모호합니다. 빌드 캐시 관점에서는 자주 바뀌는 명령을 Dockerfile 뒤쪽에 둡니다.
- ⚠ 추측: "스핀락 대신 mutex 였으면 처리량이 더 느려졌을 것" 은 원문 추론이고 측정이 없습니다.
- ⚠ 책 장 번호: 원문은 Container Security 6장을 User Namespace 장으로 소개합니다. 6장은 이미지 장이고 user namespace 는 4장입니다(노트로 확인함, [container-security 04-02](../../08_cloud/book/container-security/04-02.나머지%20namespace와%20호스트에서%20본%20컨테이너.md), [06-01](../../08_cloud/book/container-security/06-01.컨테이너%20이미지%20해부%20—%20두%20부분과%20층과%20식별자.md)).
- ⚠ 링크 버전: containerd snapshotter README 링크는 `main` 브랜치를 가리켜 내용이 바뀔 수 있습니다.
