## 학습 목표 (원본 §학습목표 인용)

OSI 7계층과 TCP/IP 4계층이 왜 다르게 잘렸는지를, 계층을 나눠서 얻은 것과 잃은 것으로 설명할 수 있는 상태.

이 목표 한 줄이 본 복습의 *기준점*. 5개 질문 모두 이 목표의 한 축을 검증한다.

### Q1. 정의 — 한 줄로 답할 수 있는가

**질문**: OSI 모델을 한 문장으로 정의하라. **실무 표준을 TCP/IP 에 내줬는데도** 왜 아직 가르치는가.

**자기 답** (보고 답하지 말 것):

```
(여기에 자기 답 작성)
```

<details>
<summary>정답 보기 (먼저 자기 답 적은 뒤)</summary>

두 시스템 간 네트워크 통신의 책임을 **7개 계층으로 나눈 개념 프레임워크**다.

실무 표준은 TCP/IP 에 내줬지만 **계층별 책임을 구분하는 용어 체계**가 유용해 계속 쓴다. "L4 로드밸런싱", "L7 라우팅" 같은 실무 용어와 Kubernetes 추상화가 모두 OSI 계층 *번호*를 쓴다.

반대로 TCP/IP 계층은 번호가 아니라 **이름**으로 불린다(Application·Transport·Internet·Link). "L3" 라고 하면 OSI 번호를 빌려 쓰는 것이다 — 원본 §4.
</details>

**점수 (0~5)**: **3** (채점: Claude — 7계층·설명용 존속까지 도달. 정의에서 "통신의 책임" 누락, 존속 근거를 "이론"으로 뭉개 L4/L7 현역 용어 체계 논지 미도달)
*점수 기준: 0=완전 못 답함, 1=틀린 답, 2=부분 답+큰 누락, 3=핵심 맞음+세부 누락, 4=정확하지만 머뭇, 5=막힘 없이 정확*

### Q2. 동기 — 왜 이 개념이 등장했는가

**질문**: NCP 는 왜 TCP/IP 로 대체됐는가. 그리고 RFC 791 의 **IP 분리가 얻은 것**은 무엇인가.

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

NCP 는 **네트워크의 다양성과 규모를 감당하지 못해** 대체됐다.

원래 TCP 하나가 신뢰성과 전달을 **모두** 맡고 있었다. 1981년 RFC 791 이 **주소 지정·전달을 IP 로 떼어 내** 각 프로토콜의 책임을 단순화했다.

결과는 역할 분담이다 — **전달은 IP 가 최선을 다하되 보장하지 않고, 신뢰성은 양 끝단의 TCP 가 책임진다.** 보장을 양 끝으로 밀어냈기 때문에 중간 장비가 연결 상태를 안 들어도 되고, 그것이 규모를 낸다 — 원본 §1·§3.
</details>

**점수 (0~5)**: **2** (채점: Claude — 모듈성 직관은 있으나 몰락 원인을 유지보수로 잡아 확장성·다양성 축을 놓침. IP 분리 후 책임 분담 미답. **NCP 몰락과 OSI 패배를 한 줄기로 묶는 오해 재발** — 2026-08-15 §3 보강이 겨눈 바로 그 지점)

---

### Q3. 메커니즘 — 그림 없이 말로 흐름을 설명할 수 있는가

**질문**: 캡슐화가 계층 모델에서 **실제로 하는 일**은 무엇인가. PDU 이름이 계층마다 어떻게 바뀌는지도 답하라.

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

위 계층의 데이터 앞뒤에 자기 계층의 **헤더(와 푸터)를 붙이는** 일이다.

송신 측은 **내려가며 붙이고** 수신 측은 **올라가며 벗긴다.** 그래서 각 계층은 다른 계층의 *내용*을 몰라도 자기 일을 한다 — 이 무지가 곧 계층을 나눈 이득이다.

PDU 는 `Data → Segment(TCP)·Datagram(UDP) → Packet → Frame → Bit` 로 바뀐다 — 원본 §2.
</details>

**점수 (0~5)**: **2** (채점: Claude — 헤더를 붙이며 내려간다까지 도달. 수신 측 역방향 해제와 "계층은 안쪽을 몰라도 된다"는 이득 누락, PDU 5개 중 Frame 1개만 회상)

### Q4. 적용 — 실무 시나리오에 응용할 수 있는가

**질문**: 라우터는 왜 **Internet 계층까지만** 구현하는가. "신뢰성은 양 끝" 과 이어서 답하라. (Phase 4 빈틈)

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

**end-to-end 원칙** 때문이다.

라우터가 할 일은 다음 홉으로 넘기는 것뿐이고, 그 판단에는 IP 헤더의 목적지 주소면 족하다. Transport 헤더를 열어 볼 이유가 없다.

더 중요한 것은 **열지 말아야 한다**는 쪽이다. 신뢰성을 양 끝이 책임지므로 중간은 연결 상태를 들 필요가 없고, 들지 않기 때문에 백본 라우터 한 대를 수백만 연결이 지나가도 견딘다. 중간이 상태를 들기 시작하면 그 확장성이 무너진다.

IP 가 `best-effort` 인 것은 게을러서가 아니라 **보장을 양 끝으로 밀어낸 설계 선택**이다 — 원본 §3·§4.
</details>

**점수 (0~5)**: **3** (채점: Claude — "전달만 하면 되니 L3까지"·"핸드셰이크를 라우터마다 안 함" 도달. 힌트를 줬음에도 무상태성이 확장성을 만든다는 강한 이유와 end-to-end 원칙 명명 미도달)

---

### Q5. 함정 — 흔한 실수 패턴을 진단할 수 있는가

**질문**: **NCP 의 몰락과 OSI 의 패배는 같은 사건인가?** 둘을 한 사건으로 묶으면 어떤 오해가 생기는지로 답하라. (Phase 4 빈틈 — 실제로 이렇게 오해했던 자리)

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

**다른 사건이다.** 둘을 묶으면 "**OSI 는 안 쪼갠 쪽**" 이라는 정반대 오해가 생긴다.

NCP 는 **안 쪼개서** 밀려났다. 신뢰성과 전달을 한 프로토콜이 다 맡아 다양성·규모를 감당하지 못했고, TCP/IP 가 그것을 IP 와 TCP 로 갈라 이겼다.

OSI 는 반대다. **더 잘게 쪼갠 쪽**이었다(7계층). 진 이유는 안 쪼개서가 아니라 표준화가 느리고 구현이 무거웠던 것이며, TCP/IP 가 이미 돌아가는 코드로 현장을 차지한 뒤였다. CLNP 같은 OSI 네트워크 계층 프로토콜이 실제로 있었다.

정리하면 **NCP 는 덜 쪼개서 졌고, OSI 는 더 쪼갰는데도 졌다.** 계층을 나누는 것 자체가 승패를 정하지 않는다 — 원본 §3.
</details>

**점수 (0~5)**: **2** (채점: Claude — Q2 채점에서 이미 교정한 내용이라 깨끗한 인출 아님. "다른 사건"·NCP 확장성은 도달, 묶었을 때 생기는 오해 자체와 "돌아가는 코드가 이겼다" 요인 미도달)
