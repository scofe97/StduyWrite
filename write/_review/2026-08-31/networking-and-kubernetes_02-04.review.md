## 학습 목표 (원본 §학습목표 인용)

읽어서 아는 것과 만들어서 아는 것 사이의 간격을 좁히는 것. 네임스페이스 둘을 veth 쌍으로 브리지에 물리고, 포워딩과 MASQUERADE 를 얹어 밖으로 내보내는 경로를 손으로 짓는다.

이 목표 한 줄이 본 복습의 *기준점*. 5개 질문 모두 이 목표의 한 축을 검증한다.

**질문**: `veth` 는 왜 **항상 쌍**으로 만들어지는가. 만들자마자 두 끝이 어디에 있는지도 함께 답하라.

**자기 답** (보고 답하지 말 것):

```
(여기에 자기 답 작성)
```

<details>
<summary>정답 보기 (먼저 자기 답 적은 뒤)</summary>

**터널의 양 끝**이기 때문이다. 한쪽에 쓴 패킷이 즉시 반대쪽에서 수신되는 구조라, 끝이 하나면 성립하지 않는다.

`ip link add veth1 type veth peer name veth1-br` 를 치면 **두 끝이 다 기본 네임스페이스에 생긴다.** 그다음 `ip link set veth1 netns ns1` 로 **안쪽 끝만 옮긴다.** 경계를 넘는 것은 이 한 줄이다.

안쪽 끝은 네임스페이스에 네트워크를 공급하고, 바깥쪽 끝은 브리지에 물려 호스트와 잇는다 — 원본 §2.
</details>

### Q2. 동기 — 왜 이 개념이 등장했는가

**질문**: 네임스페이스 안의 프로세스를 **밖으로 내보내려면** 무엇이 필요한가. 실습에서 세 번 실패하며 드러난 세 가지로 답하라.

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

세 곳에 하나씩 필요하다.

1. **나갈 길** — 네임스페이스 안의 기본 경로(`ip route add default via 10.10.1.1`). 없으면 `Network is unreachable`.
2. **중계 허가** — 중계 호스트의 `net.ipv4.ip_forward=1`. 없으면 패킷이 호스트에서 멈춘다.
3. **돌아올 길** — 상대가 사설 대역으로 돌아올 경로를 알아야 한다. 없으면 요청은 가는데 응답이 안 온다.

실패 문구가 각각 다른 계층을 가리켰다는 것이 이 절의 논점이다. **실패 메시지는 실패가 아니라 좌표다** — 원본 §3·§4.
</details>

### Q3. 메커니즘 — 그림 없이 말로 흐름을 설명할 수 있는가

**질문**: `ip_forward=1` 을 켜면 패킷의 무엇이 바뀌고 무엇이 그대로인가. 장치를 지날 때마다 무엇이 달라지는지로 답하라.

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

**IP 는 그대로 가고 MAC 만 홉마다 바뀐다.** 그리고 TTL 이 하나씩 준다.

중계 호스트는 라우팅 테이블에서 다음 홉을 찾고, ARP 로 그 홉의 MAC 을 얻어 **겉봉(L2 헤더)만 새로 쓴다.** 속의 IP 헤더는 출발지·목적지 그대로다. 그래서 상대는 사설 주소 `10.10.1.11` 을 그대로 본다.

브리지는 여기서 아무것도 안 바꾼다 — **스위치이지 홉이 아니다.** MASQUERADE 를 걸어야 비로소 POSTROUTING 한 칸에서 출발지 IP 가 노드 주소로 바뀐다 — 원본 §3·§5.
</details>

**자가 점수 (0~5)**: __

### Q4. 적용 — 실무 시나리오에 응용할 수 있는가

**질문**: `MASQUERADE` 를 걸면 conntrack 엔트리의 **두 줄 중 어느 줄이 바뀌는가.** 나머지 줄은 왜 남아 있어야 하는가.

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

엔트리는 **원본 튜플**과 **응답 튜플** 두 줄을 갖는다. NAT 는 **응답 튜플만** 바꾼다.

원본 줄은 `src=10.10.1.11 dst=192.168.139.238` 그대로 남는다. 그게 있어야 돌아온 패킷을 **원래 보낸 쪽으로 되돌릴** 수 있다. 원본을 지우면 응답을 누구에게 줘야 할지 잃는다.

NAT 가 없을 때는 응답 줄이 원본을 그냥 뒤집은 값이지만, NAT 가 걸리면 그 대칭이 깨진다. **응답 줄이 원본의 뒤집기가 아니게 되는 순간**을 보는 것이 이 절이다 — 원본 §5.
</details>

**자가 점수 (0~5)**: __

### Q5. 함정 — 흔한 실수 패턴을 진단할 수 있는가

**질문**: `ping` 을 두 번 쳤는데 nat 규칙 카운터는 `pkts 1` 이었다. 왜인가. 그러면 두 번째 패킷은 MASQUERADE 가 안 걸리는가.

**자기 답**:

```
(여기에 자기 답 작성)
```

<details>
<summary>정답</summary>

**규칙은 연결의 첫 패킷에서만 발화**하기 때문이다. 카운터가 1 인 것은 규칙을 훑은 것이 한 번이라는 뜻이다.

하지만 **변환은 두 패킷 모두에 적용된다.** 첫 패킷이 규칙을 훑을 때 만들어진 conntrack 엔트리가 이후 패킷을 대신 변환한다. 규칙을 다시 안 볼 뿐 변환이 빠지는 것이 아니다.

이 구조가 kube-proxy 로 이어진다. 확률 사다리도 **첫 패킷에서 한 번만** 백엔드를 고른다. 매번 다시 골랐다면 같은 연결의 패킷들이 매번 다른 백엔드로 흩어졌을 것이다 — 원본 §5.
</details>

**자가 점수 (0~5)**: __
