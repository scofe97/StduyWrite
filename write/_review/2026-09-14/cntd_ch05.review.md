## Q&A 7문제

### Q1. 정의 — 두 제어 모델을 가르는 핵심 구분 (05-01 §1)

**질문**: 05-01 §1 은 전달 표에 값을 누가 채우는가를 라우터마다 제어와 논리적 중앙 제어로 가른다. 원문이 이 둘을 가르는 **핵심 구분(key distinction)** 이라고 못 박은 것은 무엇인가?

**자기 답**:

```
라우터에서 직접 테이블을 채우고 평가하느냐, 혹은 컨트롤러 같은 중앙제어장치가 만들고
라우터는 전송만 하느냐의 차이로 알고 있습니다.
```

되묻기 1(컨트롤러 존재가 갈림길이 아니라면 라우터 안쪽은 무엇이 다른가) → "달라질 게 있는가"로 되물음.
되묻기 2(그 조각들 **사이**에는 무엇이 오가는가) → "CA 는 컨트롤러하고만 통신하는 것 아닌가" 로 도달.

**점수 (0~5)**: **2** (채점: AI — 첫 자답은 "누가 계산하느냐"라는 일반 구분에 머물렀고, CA 사이에 대화가 없다는 지점에는 되묻기 2회 끝에 닿았다)

---

### Q2. 동기 — AS 안과 밖에 다른 프로토콜을 쓰는 이유 (05-02 §1)

**질문**: AS 안에서 쓰던 프로토콜을 AS 사이까지 늘려 쓰면 될 텐데, 원문은 그러지 않는 이유를 셋으로 답한다. 셋이 무엇인가?

**자기 답**:

```
정확히는 모르겠다. iBGP, eBGP 로 쪼개진 것만 안다.
```

되묻기 1(주인이 다르다는 사실이 경로 고르기에 무엇을 끌어들이나) → "다른 AS 를 끌어들인다" 로 빗나감.
되묻기 2(더 짧은 길을 알면서 안 보내는 일이 왜 생기나) → "AS 는 TCP 로 통신하니 제대로 된 거리를 몰라서" 로 빗나감.

**점수 (0~5)**: **1** (채점: AI — 되묻기 2회에도 정책에 닿지 못했다. "거리를 모른다"가 세 번째 이유의 절반과 스쳤으나 인과가 거꾸로였다)

---

### Q3. 메커니즘 A — count-to-infinity 의 첫 걸음 (05-01 §5)

**질문**: `c(y,x)` 가 4 에서 60 으로 오른다. `c(y,z)=1` 이고 변화 직전 z 는 y 에게 `D_z(x)=5` 라고 말해 두었다. y 가 새로 내놓는 `D_y(x)` 는 얼마이고 그 값이 왜 틀렸는가?

**자기 답**:

```
6 이고, 틀린 이유는 D_z(x)=5 가 거쳐 가는 경우에 5 인데 이제는 거쳐 가서 저 값이 안 나오기 때문.
```

되묻기 없음.

**점수 (0~5)**: **4** (채점: AI — 첫 자답에 값과 메커니즘을 모두 맞혔다. 다만 5 를 만든 경유지가 z 가 아니라 **y** 라는 자리가 문장에서 흐렸다)

---

### Q4. 메커니즘 B — NEXT-HOP 이 다리인 이유 (05-02 §4)

**질문**: 1b 는 iBGP 로 `AS2 AS3 x` 를 받는다. 전달 표에 적어야 하는 것은 `(접두어, 인터페이스 번호)` 인데 AS 번호 목록에서는 인터페이스가 나오지 않는다. 1b 는 무엇을 함께 받아 그 빈칸을 채우는가?

**자기 답**:

```
모르겠음 → (되묻기 후) 게이트웨이 주소를 알려줘야 하는 거 아냐?
```

되묻기 1(OSPF 에게 무엇을 건네면 "어느 인터페이스로"가 나오는가) → 도달.

**점수 (0~5)**: **3** (채점: AI — 되묻기 1회로 NEXT-HOP 에 도달했다. 다만 그것이 **이웃 AS 의** 게이트웨이 주소라는 점, 그리고 그 서브넷이 내 AS 에 붙어 있어야 성립한다는 조건은 나오지 않았다)

---

### Q5. 적용 — 상황형: 링크가 끊겼는데 닿지도 않은 스위치의 표가 바뀐다 (05-03 §4)

**질문**: SDN 망에서 s1-s2 링크가 끊겼다. 잠시 뒤 흐름 표를 보니 s1·s2 만이 아니라 **s4** 의 표도 바뀌어 있다. s4 는 끊어진 링크에 닿아 있지도 않다. 무슨 일이 일어난 것이고, 같은 사건을 OSPF 로 겪었다면 무엇이 달랐겠는가?

**자기 답**:

```
모르겠음 → (되묻기 후) 직행이 없어졌으니 다른 곳으로 가야겠지 → 모르겠는데
```

되묻기 1(s1 이 s2 로 보내던 패킷은 이제 어디를 거치나), 되묻기 2(그 스위치는 누구한테서 알게 되나) 모두 실패.

**점수 (0~5)**: **0** (채점: AI — 첫 자답과 되묻기 두 번 모두 내용에 닿지 못했다. 우회로 위에 s4 가 있다는 사실도, 컨트롤러가 한 곳에서 계산해 셋을 한꺼번에 고친다는 조율 모델도 나오지 않았다)

---

### Q6. 진단 — 상황형: TTL 이 한 화면에서 두 가지를 말한다 (05-04 §2)

**질문**: 아래 셋을 읽어라. 같은 패킷인데 3 이 1 로 찍힌 이유는 무엇이고, 그 **1** 은 무엇을 알려 주는가? 봉투의 **253** 은 무엇을 알려 주는가?

```
내가 내보낸 탐침 : ttl 3   , id 47851
인용된 그 원본   : ttl 1   , id 47851
봉투(ICMP 자신)  : ttl 253
```

**자기 답**:

```
(1차) 인용되었다는 의미가 무엇인가? 문제가 다소 생략된 것 같음
   → 출제자 책임. "인용" 정의와 tcpdump 출력 형태를 보강해 재출제
(2차) 홉을 지날 때마다 -1 이 됩니다. 1 로 돌아온 걸 보면 홉을 2번 거쳐서 목적지 호스트에 도착
(3차) 최대 TTL 은 라우터마다 다르니 각각 256, 64 로 두었을 때 앞에서는 3번, 공유기는 직행
```

되묻기 1(홉마다 TTL 은 어떻게 되고 인용은 언제의 상태인가) → 인용 쪽 절반 도달.
되묻기 2(253 과 64 를 나란히 놓으면) → 봉투 쪽 도달.

**점수 (0~5)**: **2** (채점: AI — 되묻기 2회로 도달. 출발값을 256 으로 잡아 홉 수가 하나 어긋났고, TTL 3 짜리 탐침이 목적지에 닿았다고 읽은 것도 어긋남)

> **덧붙여 나온 좋은 질문**: "64 가 바로 직행인지 128 에서 64번을 간 건지 어떻게 아는가?" — 단정할 수 없고 추론이라는 답을 스스로 요구한 자리다. 흔한 초기값(64·128·255) 중 관측값 이상인 가장 가까운 것을 출발값으로 잡는 방법은 **원문 밖 보충**이다.

### Q7. 함정 — 상황형: 애니캐스트로 파일을 받는 도중 경로가 바뀐다 (05-02 §5)

**질문**: 애니캐스트 주소의 서버에서 큰 파일을 받는 도중에 BGP 경로가 바뀌면 무슨 일이 벌어지는가? DNS 는 왜 같은 문제를 겪지 않는가?

**자기 답**:

```
큰 파일을 받는 도중 BGP 경로가 바뀌면 통신 경로가 다운받는 도중 바뀌는 문제가 발생한다.
DNS 는 워낙 가볍고 재시도할 일이 없어 큰 문제 없다?
```

되묻기 1(LA 기계는 무엇을 갖고 있지 않아서 문제인가) → "도쿄의 라우팅 정보가 없다" 로 빗나감.
되묻기 2(TCP 연결은 어디에 존재하는가) → "양 끝 호스트에 존재" 로 전제에는 도달, 결론(맞는 소켓이 없어 리셋)에는 미도달.

**점수 (0~5)**: **2** (채점: AI — 되묻기 2회로 전제까지. 첫 자답은 "경로가 바뀌면 경로가 바뀐다"로 순환했고 DNS 쪽 이유도 「가볍다」로 빗나갔다)

> 일곱 문항에 *먼저 자답한 뒤* 읽습니다. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 (05-01 §1)

핵심 구분은 **CA 끼리는 서로 이야기하지 않고 전달 표 계산에 끼어들지도 않는다**는 점이다. 갈림길은 컨트롤러의 존재가 아니다.

- 라우터마다 제어: 라우터마다 라우팅 컴포넌트가 있고 그 컴포넌트들이 **서로 이야기해** 자기 전달 표를 계산한다. 라우터가 판단 주체다.
- 논리적 중앙 제어: CA 가 하는 일은 컨트롤러와 이야기하고 시키는 대로 하는 것뿐이다. 라우터는 실행 장치다.

같은 절이 "논리적"은 하나의 상자가 아니라 **하나처럼 보이는 서비스**를 뜻한다고 덧붙인다.

### 정답 2 (05-02 §1 「안과 밖에 서로 다른 프로토콜을 쓰는 이유」)

1. **정책** — AS 사이에서는 정책이 지배한다. 특정 AS 를 지나지 않게 하거나 통과 트래픽을 통제하는 일이 중요하다. AS 안에서는 모두가 명목상 같은 관리 아래 있어 정책의 비중이 훨씬 작다.
2. **규모** — AS 사이 라우팅에서는 확장성이 결정적이다. AS 안에서는 덜 문제인데, ISP 가 너무 커지면 AS 둘로 쪼개면 되기 때문이다. §2 의 OSPF 영역도 같은 처방이다.
3. **성능** — AS 사이는 정책 중심이라 경로 품질이 부차적이다. **AS 사이에는 AS 홉 수 말고는 비용이라는 개념 자체가 없다.** AS 안에서는 정책 걱정이 적으니 성능에 집중할 수 있다.

§6 이 정책의 손잡이를 둘로 정리한다 — **무엇을 광고할지**(짧은 길이라도 광고하지 않으면 후보조차 되지 못한다)와 **받은 경로 중 무엇을 고를지**(규칙 1 이 로컬 선호도).

### 정답 3 (05-01 §5)

`D_y(x) = min{ c(y,x)+0, c(y,z)+D_z(x) } = min{ 60+0, 1+5 } = 6`.

틀린 이유는 z 가 말해 준 5 가 **y 자신을 거쳐 가는 값**이기 때문이다. 변화 전 `D_z(x) = min{50, 1+4} = 5` 는 `z → y → x` 경로다. y 가 아는 것은 자기 직통이 60 이라는 것과 z 가 마지막으로 5 라고 말했다는 것뿐이라, y 는 z 를 거쳐 가기로 하는데 정작 z 는 y 를 거쳐 간다. 라우팅 루프이고 원문은 블랙홀에 비유한다. 이후 둘이 번갈아 **2 씩** 오르고, z 가 y 를 거치는 비용을 50 보다 크게 계산할 때 끝난다(원문의 44회).

### 정답 4 (05-02 §4 「NEXT-HOP 이 다리인 이유」)

함께 받는 속성이 **NEXT-HOP** — AS-PATH 를 시작하는 라우터 인터페이스의 IP 주소다. 이 경로라면 AS2 의 게이트웨이 2a 쪽 주소이고, 내 AS 밖 주소지만 **그 주소를 담은 서브넷은 내 AS 에 직접 붙어 있다.**

1. iBGP: `x 는 AS2 AS3 로, NEXT-HOP 10.0.0.2`
2. OSPF: `10.0.0.0/30 은 1c 에 붙어 있다`
3. 1b 가 NEXT-HOP 을 들고 OSPF 쪽에서 그 주소가 든 서브넷을 찾는다
4. 전달 표 한 줄 `(x, I)`

**BGP 는 어느 출구로 나가는지를, OSPF 는 그 출구까지 어떻게 가는지를 답한다.** (`10.0.0.0/30` 과 `I` 는 노트의 읽기 — 원문은 "2a 의 가장 왼쪽 인터페이스 주소"라고만 적는다.)

### 정답 5 (05-03 §4 「링크 하나가 끊어지면」)

**s4 는 우회로 `s1-s4-s2` 위에 있다.** 그래서 s1 이 s2 로 보내는 패킷을 나르게 되고 표가 바뀐다. s3 는 우회로를 지나지 않아 그대로다.

여섯 걸음: s1 이 OpenFlow **port-status** 로 컨트롤러에 알림 → 링크 상태 관리자가 DB 갱신 → **미리 등록해 둔** 라우팅 앱이 알림 수신 → 새 최소 비용 경로 계산 → 흐름 표 관리자와 협의 → OpenFlow 로 **s1·s2·s4 를 한꺼번에** 갱신.

앞 편과 다른 점 둘: 다익스트라가 패킷 스위치 **밖의 별도 앱**으로 돈다. 스위치는 서로가 아니라 **컨트롤러에게만** 알린다. 이 편 핵심 요약의 한 문장이 **조율이 프로토콜의 수렴이 아니라 한 곳의 계산이 된다**이다.

딸려 오는 차이: 방식을 바꾸려면 SDN 은 제어 앱 소프트웨어만, 라우터별 제어는 여러 공급자에게서 산 **모든 라우터의 소프트웨어**를 바꿔야 했다.

(원문 정오도 이 자리다. 원문은 s1·s3·s4 가 영향받고 s2 는 그대로라 적었는데 이름 둘이 자리를 바꿨다. 실제는 s1·s2·s4.)

### 정답 6 (05-04 §2 「TTL 이 두 자리에서 거리를 말합니다」)

**인용된 TTL 1** — 인용은 그 라우터에 **도착했을 때의 상태**다. 3 으로 출발해 `3 → 2 → 1` 로 깎였고 세 번째 라우터가 1 을 받아 0 으로 만들고 버리면서 받은 그대로 인용했다. 그러니 인용된 TTL 은 **"얼마나 남았나"가 아니라 "얼마나 왔나"** 를 거꾸로 알려 준다.

**봉투의 253** — `255` 에서 출발해 두 홉을 지난 값이다. 그 라우터가 나에게서 두 홉 거리라는 뜻이다. 공유기는 바로 옆이라 출발값 64 가 그대로 도착했다.

인용 안의 TTL 은 **내 패킷이 간 거리**를, 봉투의 TTL 은 **답이 온 거리**를 가리킨다. 돌아오는 길이 가는 길과 다를 수 있어 둘을 같은 것으로 읽으면 안 된다.

### 정답 7 (05-02 §5 「상태가 있으면 깨질 수 있습니다」)

1. 바뀌기 전: 라우터가 도쿄 쪽을 최선으로 골라 TCP 연결이 도쿄에 닿는다. **이 연결의 상태, 곧 소켓은 도쿄에만 생긴다.**
2. 바뀌는 순간: BGP 라우팅이 바뀌어 LA 쪽 광고가 최선이 된다. 목적지 주소는 그대로라 사용자는 알 수 없다.
3. 바뀐 뒤: 같은 연결의 다음 세그먼트가 LA 에 도착한다. 연결은 양 끝 호스트의 메모리에만 있으므로 LA 는 그 상태를 나눠 갖지 않는다.
4. 리셋: 맞는 소켓이 없다는 이유로 RST 가 돌아온다.

반드시 그렇게 되지는 않는다 — 같은 인스턴스로 갈 수도, 조용히 버려져 재전송 시간 초과로 끝날 수도, 인스턴스끼리 상태를 나눠 갖는 설계도 있다. 다만 **어느 쪽이든 종단이 감당해야 할 일이 생긴다.**

DNS 가 쓸 수 있는 이유는 가벼워서가 아니라 **질의 하나가 응답 하나로 끝나 어느 인스턴스가 받아도 상관없기** 때문이다. RFC 7766 이 DNS 구현의 TCP 지원을 요구하므로 TCP 를 쓰는 동안에는 DNS 도 같은 제약 아래 놓인다. **애니캐스트와 어긋나는 것은 프로토콜 이름이 아니라 연결 상태를 드느냐다.**

CDN 은 대신 DNS 재지향(YouTube)이나 클라우드 소프트웨어의 직접 지정(Netflix)을 쓴다. 둘 다 고르는 일을 연결을 맺기 **전에** 끝낸다.
