## 학습 목표 (원본 §학습목표 통합)

3장 다섯 편을 읽고 나면 — 트랜스포트가 IP 위에 무엇을 더하는지 말하고, 세그먼트를 소켓에 넣는 키가 UDP 와 TCP 에서 어떻게 갈리는지 설명하고,
신뢰적 전송을 rdt 의 가정 제거로 쌓아 GBN 과 SR 의 차이를 대고, TCP 가 번호를 세고 타이머를 잡는 방식과 빠른 재전송의 조건을 말하고,
흐름 제어와 연결 관리의 함정(영 창 교착·SYN 플러드)을 짚고, 혼잡 제어의 세 국면과 손실 신호별 반응을 그림 없이 풀 수 있다.


## Q&A 7문제

> 축 배분: 정의 1 · 동기 1 · 메커니즘 2 · 적용 1 · 진단 1 · 함정 1. 문항 5~7 은 상황형.

### Q1. 정의 — 도착한 세그먼트를 어느 소켓에 넣나 (03-01 §4)

**질문**: 서버가 UDP 5000 과 TCP 80 을 열어 두었고 클라이언트 A·B 가 동시에 보낸다. UDP 쪽 둘은 같은 소켓 하나로, TCP 쪽 둘은 서로 다른 소켓으로 들어간다. 두 프로토콜은 각각 헤더의 어떤 값들을 보는가?

**자기 답**:

```
TCP 는 목적지/출발 IP 와 포트 4개를 보고 소켓에 넣고,
UDP 는 최소 정보? (뭐였는지 기억은 안 남) 라서 단일 소켓으로 가능했던 것 같음
```

되묻기 1(A·B 양쪽을 한 소켓이 받았다면 그 키에 무엇이 들어 있을 수 없나) → "목적지의 IP 와 포트만 쓰면 되려나?" 로 도달.

**점수 (0~5)**: **3** (채점: AI — TCP 4튜플은 첫 자답에 정확, UDP 2튜플은 되묻기 1회)

---

### Q2. 동기 — 링크 계층이 검사하는데 왜 또 검사하나 (03-01 §6)

**질문**: 이더넷은 프레임마다 CRC 로 오류를 검사한다. 그런데 UDP 는 체크섬을 또 둔다. 원문이 드는 이유 둘은 무엇인가?

**자기 답**:

```
링크에서 체크섬 검사 진행 → 전송계층에서 한번 더?
(전송계층에서만 하는 게 아니었나? CRC 는 라우터에서 체크섬을 빠르게 하기 위한 기술로만 이해했었음)
```

전제 보강(검사 장치가 계층마다 따로 있고 링크 CRC 는 한 링크 구간만 덮는다) 후 되묻기 1(양 끝은 잡는데 링크 CRC 가 놓치는 자리 둘) → "링크 체크섬은 링크 헤더의 값?(맥주소?) 이고 전송계층은 IP·PORT 에 대한 전체 검사 아닐까? (사실 잘 모르겠음)" 로 미도달.

**점수 (0~5)**: **1** (채점: AI — 두 이유 모두 미도달. **링크 CRC 의 범위를 "링크 헤더만"으로 잘못 알고 있었다** — 실제로는 프레임 전체를 덮되 한 홉만 유효하다)

---

### Q3. 메커니즘 A — 하나만 사라졌을 때 GBN 과 SR (03-02 §3·§4)

**질문**: 창 4로 1·2·3·4 를 보냈는데 3만 사라지고 4는 도착했다. (가) GBN 에서 수신자는 4를 어떻게 하고 타임아웃 뒤 송신자는 무엇을 보내나. (나) SR 이면 무엇이 달라지나.

**자기 답**:

```
(가) 3번이 누락되었으니 4번을 ACK3 으로 바꾸어서 3번을 다시 요청하게 함 (4번은 받는 쪽에서 버퍼로 보관)
(나) 몰루?
```

되묻기 1(GBN 이라는 이름이 말하는 재전송 범위 / 수신자도 버퍼링한다면 SR 과의 차이는) → "누락된 번호로 되돌아간다는 의미" 까지.
되묻기 2(4번을 버렸다면 다시 보내야 하나, 타임아웃 한 번에 나가는 패킷은 몇 개인가) → "누락된 것부터 다시 보냄, 3·4 이니 2개" 로 도달. (나)는 끝까지 미도달.

**점수 (0~5)**: **2** (채점: AI — (가) 되묻기 2회, (나) 미도달. 다만 "4를 버퍼에 보관"은 **노트의 읽기와 맞는 답**이었다 — 규격은 폐기이고 구현은 흔히 버퍼링한다. `ACK 3` 표기도 TCP 방식으로는 맞다)

---

### Q4. 메커니즘 B (부재) — 신호가 오지 않으면 (03-03 §5)

**질문**: (가) 중복 ACK 가 왜 손실 신호가 되고 하필 셋인가. (나) 마지막 세그먼트가 사라지면 빠른 재전송이 되는가, 안 된다면 무엇이 없어서인가.

**자기 답**:

```
(가) TCP 는 GBN 과 SR 양쪽을 취했다. 수신자 측에서 앞의 값이 누락되었다면 이후 받은 값은 버퍼에 저장하고
     누락된 걸 중복으로 응답해 주기 때문이다. (왜 3개인지는 잘 모르겠음, 전송이 느려 재전송할 수도 있어서 그런 것 같음)
(나) 마지막 세그먼트는 ACK 를 받을 수 없습니다. 이때는 빠른 재전송을 못하고 타임아웃으로 재전송합니다
```

되묻기 없음.

**점수 (0~5)**: **4** (채점: AI — 둘 다 첫 자답에 도달. "셋"의 이유는 짐작에 머물렀으나 가리킨 축(지연·재정렬)이 맞았다)

---

### Q5. 적용 — 상황형: SYN 이 쏟아질 때 (03-04 §3)

**질문**: SYN 을 초당 수만 개 받고 정상 클라이언트가 연결을 못 맺는다. (가) 무엇이 차 있나, 세 번의 악수 중 어느 단계에서 서버가 무엇을 잡나. (나) SYN 쿠키는 무엇을 **하지 않음**으로써 막고, 정상 연결은 어떻게 살리나.

**자기 답**:

```
(가) 무언가 꽉 차 있어서 못 했단 건 윈도우(버퍼)가 꽉 차서 버려졌기에 그런 것 같습니다.
     그런데 보통 SYN 보낼 때 본인 윈도우의 남은 공간을 알려주지 않는가?
(나) SYN 쿠키? 쿠키가 왜 나오지? 연결 살리는 건 버퍼 비워지면 뭔가 조치를 해주겠지?
```

되묻기 1(SYN-ACK 를 보내는 순간 서버가 만들어 둬야 하는 것과 그것을 얼마나 오래 들고 있나) → "출발지·목적지 IP·포트의 소켓 정보가 있어야겠지, 안 오면 기본 타임아웃으로 사라짐" 으로 (가) 도달.
되묻기 2(ACK 에 서버의 초기 순서 번호가 되돌아온다 — 기억하지 않고 검산할 방법은) → "없습니다, 기억하지 못하면 판단할 수 없습니다" 로 미도달.

**점수 (0~5)**: **2** (채점: AI — (가) 되묻기 1회, (나) 되묻기 2회에도 미도달. **"반쯤 열린 연결"이라는 상태 자체가 없었다**)

---

### Q6. 진단 — 상황형: 혼잡 창 기록 읽기 (03-05 §2)

**질문**: `1 2 4 8 16 32 → 16 17 18 19 … 24 → 1 2 4` 라는 왕복별 `cwnd` 기록에서 (가) 두 구간의 국면과 증가 방식, (나) 사건 A·B 가 각각 무엇이고 반응이 왜 다른가.

**자기 답**:

```
혼잡 임계점이라 1씩 늘어납니다, 32에서 임계점을 넘어섰고, 24도 마찬가지
```

되묻기 1(두 구간의 왕복당 증가량 차이 / 손실을 아는 두 길 중 어느 쪽이 A·B 인가) → "2배로 증가하는 부분과 1씩 증가, B 아닐까요? cwnd 가 뭔지 잘 기억 안 나는데 송신 버퍼에 있어야 할 내용인가요?" — `cwnd` 정의 보강(송신 측이 스스로 정하는 한도, `rwnd` 와 둘 중 작은 쪽).
되묻기 2(중복 ACK 는 길이 살아 있다는 뜻, 타임아웃은 아무 소식도 없는 것 — 어느 쪽이 더 나쁜 소식인가) → "타임아웃이 더 나쁜 소식. 창을 반으로 줄인 건 유실이고 1부터는 타임아웃" 으로 도달.

**점수 (0~5)**: **2** (채점: AI — (가) 증가 방식은 되묻기 1회로 갈랐으나 국면 이름(느린 시작·혼잡 회피)은 안 나옴, (나) 되묻기 2회)

> **출제 쪽 단순화**: 제시한 기록은 중복 ACK 에서 창을 정확히 절반으로 줄였다. 원문의 Reno 는 **절반에 3 MSS 를 더한다**(빠른 회복). 다음 회차에서는 19 로 내는 편이 정확하다.

### Q7. 함정 — 상황형: 창이 0이 된 뒤 (03-04 §1)

**질문**: `rwnd = 0` 광고 뒤 수신 앱이 버퍼를 비웠는데 수신 쪽은 보낼 데이터가 없다. (가) 무엇이 깨지나. (나) TCP 는 무엇을 더해 막고, UDP 에는 왜 이 문제가 없나.

**자기 답**:

```
(가) rwnd 수신 버퍼가 비워져도 보내는 측이 이를 알지 못하고 대기합니다 — 즉 영원히 못 보냄
(나) 윈도우 크기 0을 받으면 주기적으로 확인을 보냅니다. UDP 는 혼잡 제어를 전송 계층에서 하지 않기 때문에 그렇습니다
```

되묻기 없음.

**점수 (0~5)**: **4** (채점: AI — 교착과 처방을 첫 자답에 정확히 짚었다. UDP 쪽 이유만 한 칸 어긋났다 — 혼잡 제어가 아니라 **흐름 제어**를 제공하지 않아서다)

## 정답 (자답 후 펼치기)

> 일곱 문항에 *먼저 자답한 뒤* 읽는다.

### 정답 1 (03-01 §4)

**UDP 소켓은 2튜플** — 목적지 IP 와 목적지 포트로 완전히 식별된다. 출발지가 누구든 목적지만 같으면 같은 소켓이다. **TCP 소켓은 4튜플** — 출발지 IP·출발지 포트·목적지 IP·목적지 포트다. 예외는 **연결 수립 요청(첫 SYN)** 뿐이고, 그것만 출발지가 빈 듣는 소켓(`*:80`)으로 간다. 아파치가 포트 80 하나로 버티는 근거가 이 4튜플이다.

### 정답 2 (03-01 §6)

1. **모든 링크가 오류 검사를 한다는 보장이 없다.** 경로 중 한 구간이 오류 검사 없는 링크 계층 프로토콜을 쓸 수 있다.
2. **링크를 제대로 건너도 라우터 메모리에 놓여 있는 동안 비트 오류가 생길 수 있다.**

그래서 종단 간 오류 검출은 트랜스포트가 해야 한다. **종단 간 원칙**의 사례이고, 원문의 인용은 "낮은 층에 놓인 기능은 높은 층에서 그것을 제공하는 비용에 비해 중복이거나 값이 거의 없을 수 있다" 이다. 노트의 읽기가 그림을 덧붙인다 — 라우터는 프레임을 통째로 넘기지 않고 **새 프레임을 만들어 새 CRC 를 붙이므로**, 검사와 재계산 사이에 뒤집힌 비트는 정상 도장을 받는다(RFC 3385). 이더넷 CRC 는 **프레임 전체**를 덮되 **한 링크만** 유효하고, IP 헤더 체크섬은 헤더만 덮고 **홉마다 다시 계산**된다. IPv6 는 라우터를 빠르게 하려고 그 칸을 아예 뺐다(04-04 §1).

### 정답 3 (03-02 §3·§4)

GBN 수신자는 순서대로 온 것만 올리고, **그 밖의 경우에는 버리고 가장 최근에 순서대로 받은 패킷의 ACK 를 다시 보낸다**(여기서는 `ACK 2`). 송신자는 타임아웃에 **미확인 패킷 전부**(3·4) 를 다시 보내며 타이머는 하나다. SR 은 **개별 확인 응답**을 쓰고 순서 밖 4를 **버퍼에 두었다가** 3이 오면 묶어 올린다. 타이머는 미확인 패킷마다 두고 **그 패킷만** 다시 보낸다. 대가는 수신자 복잡도이고, 두 창이 늘 일치하지는 않는다. 실제 TCP 는 누적 ACK(GBN)와 순서 밖 버퍼링·선택적 재전송(SR)을 섞은 혼종이다.

### 정답 4 (03-03 §5 · 03-02 §1)

받는 쪽은 구멍을 발견하면 **마지막으로 순서대로 받은 바이트의 ACK 를 다시 보낸다**(암묵적 NAK). 셋을 세는 이유는 중복 ACK 가 손실 말고도 생기기 때문이다 — RFC 5681 이 원인을 손실·**망의 순서 바꿈**·복제 셋으로 세고, 가운데 것에 "어떤 경로에서는 드문 일이 아니다" 를 단다. 하나·둘로 자르면 단순 재정렬에 멀쩡한 데이터를 다시 보낸다. 중복 ACK 는 **받는 쪽이 도착 즉시** 만들고 타임아웃은 **보내는 쪽 시계**가 만들어, 서로 무관하다.

마지막 세그먼트가 사라지면 **뒤따를 세그먼트가 없어 중복 ACK 를 만들 계기가 없다.** 남는 것은 타임아웃뿐이고, 그래서 타임아웃은 느려도 없앨 수 없는 최후의 수단이다.

### 정답 5 (03-04 §3)

서버는 SYN 을 받으면 **연결 변수와 버퍼를 할당하고** SYN-ACK 를 보낸 뒤 ACK 를 기다리며, 오지 않으면 **1분 이상 지나서야** 반쯤 열린 연결을 정리한다. 공격자는 세 번째 단계를 완성하지 않는 SYN 을 쏟아부어 그 자리를 고갈시킨다.

**SYN 쿠키**는 반쯤 열린 연결을 만들지 않는다. 출발지·목적지 IP 와 포트, **서버만 아는 비밀 수**로 해시를 계산해 초기 순서 번호로 삼아 SYN-ACK 를 보내고 **아무 상태도 저장하지 않는다.** ACK 가 오면 **같은 해시를 다시 계산**해 확인 번호와 맞춰 보고, 맞을 때만 소켓을 만든다. ACK 가 없으면 가짜 SYN 은 아무 해도 끼치지 않는다. 핵심은 **기억하는 대신 다시 계산할 수 있게 만든 설계**다.

### 정답 6 (03-05 §2)

왕복 1~5 는 **느린 시작** — 확인마다 1 MSS 씩 늘어 **왕복마다 두 배**다. 7~14 는 **혼잡 회피** — 들어올 때 이미 지난 혼잡 지점의 절반이라 **왕복마다 1 MSS** 만 늘린다. 사건 A 는 **중복 ACK 셋**이라 창을 절반으로(원문의 Reno 는 절반+3 MSS), 사건 B 는 **타임아웃**이라 `cwnd` 를 1 MSS 로 되돌리고 느린 시작부터 다시 한다. 어느 쪽이든 `ssthresh` 는 그때 `cwnd` 의 절반이다. 중복 ACK 는 **망이 아직 일부를 나르고 있다는 뜻**이라 덜 극단적으로 대응하며, 이 구분을 넣은 것이 **Reno**(Tahoe 는 둘 다 1로 잘랐다)다. 가산 증가와 승산 감소가 **AIMD** 이고 톱니를 만든다.

### 정답 7 (03-04 §1)

`rwnd = 0` 이고 받는 쪽이 보낼 데이터도 없을 때, 애플리케이션이 버퍼를 비워도 **TCP 는 보낼 데이터나 보낼 확인 응답이 있을 때만 세그먼트를 보내므로** 새 `rwnd` 가 전달되지 않는다. 송신자는 영영 막힌다. 처방은 창이 0일 때 **송신자가 한 바이트짜리 세그먼트를 계속 보내는 것**이고, 받는 쪽의 확인 응답에 0 이 아닌 `rwnd` 가 실려 온다. 뿌리는 **TCP 가 상태 변화를 스스로 알리지 않는다**는 데 있고, 같은 모양의 처방이 킵얼라이브·하트비트에서 반복된다. UDP 는 **흐름 제어를 제공하지 않아** 창도 교착도 없고, 대신 버퍼가 넘치면 세그먼트가 버려진다.
