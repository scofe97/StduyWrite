앞 두 편과 같은 지형이 반복된다. **정의·구성 문항(Q1)은 1 점, 메커니즘·적용(Q3·Q4)은 2~3 점, 상황 판단(Q5 가)은 맞힌다.** 사흘째 같은 모양이라 개별 편의 문제가 아니라 **인출 형식의 문제**로 본다 — 상황을 주면 나오고, 구성을 물으면 안 나온다.

**방향 뒤집기 3건째.** Q5(나)에서 RST 의 첫 의심을 방화벽으로 잡았다. RST 는 도달·생존의 증거이므로 서비스 기동이 먼저다. 07-01 Q4(`/25`→`/23`), 07-03 Q2 의 스트림 ID 인과, 여기까지 오늘만 셋이다.

**세션 중 자발적 연결이 늘었다.** TCP HOL blocking → HTTP/3 QUIC, SNI 의 닭·달걀, 02-05 실습의 DROP/REJECT 를 스스로 끌어와 물었다. 채점 점수와 별개로 기록해 둔다 — 질문의 질이 올라간 회차다.


## 정답 (자답 후 펼치기)

> 다섯 문항에 *먼저 자답한 뒤* 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.
> 정답을 문항 옆이 아니라 파일 끝에 모은 것은 Typora 가 raw HTML 접힘을 지원하지 않기 때문입니다 — 접기로는 가려지지 않습니다.

### 정답 1

**요청** — 메서드 + 경로 + 버전 (`GET / HTTP/1.1`). **응답** — 버전 + 상태 코드 + 이유 구절 (`HTTP/1.1 200 OK`). 응답에 메서드와 경로가 없는 것은 같은 연결로 돌아온 답이라 클라이언트가 이미 알기 때문이다.

### 정답 2

**배달에는 이름이 필요 없지만 답을 고르는 데는 필요하기 때문이다.** 한 IP 에 사이트가 여럿 얹히면 서버는 어느 것을 줄지 정해야 하는데 그건 배달 문제가 아니라 애플리케이션 문제다. HTTP/1.0 에는 `Host` 가 없어 IP 하나에 사이트 하나였고, HTTP/1.1 이 필수로 만들면서 가상 호스팅이 가능해졌다. HTTPS 면 그 줄이 암호화 안쪽이라 TLS 핸드셰이크 앞에 이름을 한 번 더 평문으로 싣는다(SNI).

### 정답 3

**TOFU**(Trust On First Use). ① 서버가 호스트 키의 공개키를 내민다 ② 보증할 CA 가 없으니 클라이언트가 사용자에게 지문을 보이고 묻는다 ③ `yes` 하면 `~/.ssh/known_hosts` 에 **공개키 원본**을 적는다 ④ 다음부터는 그 기록과 대조하고 다르면 경고한다. `ssh-keygen -l` 이 보여 주는 `SHA256:...` 는 파일에 없고 그 자리에서 공개키를 해시해 만든 **지문**이다.

### 정답 4

**rsync 가 양쪽을 비교해 바뀐 것만 보낸다.** 기본은 크기 + 수정 시각이고 `-c` 를 주면 체크섬으로 비교한다. 파일 단위를 넘어 **바뀐 블록만** 보내기도 한다. 한계는 둘 — mtime 비교는 **시각을 안 건드리고 내용만 바꾼 변경을 놓치고**, 반대로 `touch` 만 해도 전송 대상이 된다(2026-09-07 실습에서 직접 반증). 체크섬 비교는 확실하지만 양쪽이 전 파일을 읽어야 해 느리다. rsync 는 기준 시점을 기억하지 않고 **매번 양쪽을 새로 비교**한다.

### 정답 5

**`SYN` 재전송만** = 패킷이 못 갔거나 갔는데 조용히 버려졌다. 경로·VPN·방화벽 `DROP` 을 의심한다. **`RST` 즉시** = 도달했고 호스트도 살아 있다. 그 포트에 듣는 게 없을 뿐이라 서비스 기동과 포트 번호를 의심한다. `curl` 종료 코드로도 갈린다 — 6 은 이름 해석 실패, 7 은 연결 거부(0ms), 28 은 타임아웃. **`RST` 는 나쁜 소식이 아니라 상대가 대답했다는 좋은 소식이다.** 그리고 마운트를 동기화로 오해하는 것도 흔한 함정이다 — 마운트는 사본이 없어 매 접근이 네트워크 왕복이고 오프라인이면 디렉토리가 통째로 멈춘다.
