### 정답 1

HTTP 와 HTTPS 모두 **`nodePort` → `port` → `targetPort`** 세 단계로 흐른다.

- HTTP: 노드 `nodePort` 30080 → cluster IP `port` 80 → 파드 `targetPort` 8080
- HTTPS: 노드 30443 → cluster IP 443 → 파드 8443

외부 클라이언트는 노드 IP:30080 으로, 내부 클라이언트는 cluster IP:80 으로 접속하고 둘 다 최종적으로 파드 8080 에 닿는다. `nodePort` 를 비우면 쿠버네티스가 **30000~32767** 범위에서 자동 배정한다 — 원본 §정답 1.

### 정답 2

LoadBalancer 는 내부적으로 **NodePort 처럼 node port 를 열고** 그 앞에 실제 로드밸런서를 프로비저닝한다. 로드밸런서가 건강한 노드의 node port 로 트래픽을 넘기므로 죽은 노드를 피하고 고른 분산을 얻는다.

지원하지 않는 클러스터(애드온 없는 베어메탈)에서 만들면 Service 는 생성되지만 **EXTERNAL-IP 가 `<pending>`** 에 머문다. 이때는 node port 로만 접근된다 — 원본 §정답 2.

### 정답 3

노드 A(`172.18.0.4`)로 들어온 패킷이 노드 B 의 파드(`10.244.2.9`)로 갈 때 노드 A 의 커널이 두 필드를 바꾼다.

- **목적지** `172.18.0.4:30080` → `10.244.2.9:8080` (DNAT) — **두 정책 모두** 한다. 안 바꾸면 패킷이 파드에 닿지 못한다.
- **출발지** 클라이언트 IP → `172.18.0.4` (SNAT) — **Cluster 만** 한다. 응답이 반드시 노드 A 로 되돌아와야 하므로 출발지를 자기 주소로 위조한다.

Local 에서 일어나지 않는 것은 **출발지 변환(SNAT)** 이다. 자기 노드 위 파드로만 넘기니 응답 경로가 어긋날 일이 없어 위조할 이유가 없다.

주의 — 목적지가 **cluster IP 를 거치지 않는다.** cluster IP 와 node port 는 같은 파드 목록을 가리키는 두 입구이므로, node port 로 들어온 패킷은 곧바로 파드 주소로 바뀐다 — 원본 §정답 3.

**곁가지**: "다른 노드의 파드로 넘길 수 있는가"를 정하는 것은 Service 타입이 아니라 `externalTrafficPolicy` 다. 로드밸런서는 **어느 노드로 보낼지**만 고르고, 도착한 노드의 커널이 **어느 파드로 넘길지**를 고른다 — 원본 §정답 4.

### 정답 4

로드밸런서는 노드 **셋 모두**에 균등하게 나누므로 A·B·C 가 각 33개를 받는다. Local 이라 각 노드는 자기 위 파드로만 넘긴다.

- 노드 A 의 33개를 파드 3개가 나눠 각 **11개**
- 노드 B 의 33개를 파드 1개가 전부 받아 **33개**
- 노드 C 의 33개는 넘길 파드가 없고 남의 노드로도 못 넘기니 **버려진다**(타임아웃)

파드당 부하가 11 대 33 으로 **3배** 어긋난다. 로드밸런서는 노드 단위로 공평했지만 파드 단위로는 불공평해졌다 — 원본 §정답 5.

### 정답 5

노드 C 가 503 을 응답해 분배 대상에서 빠지고 A·B 가 **50개씩** 받는다. 노드 A 의 파드 3개는 각 **16.7개**, 노드 B 의 파드 1개는 **50개**다.

유실은 사라졌지만 **불균등은 그대로 남는다** — 16.7 대 50 으로 여전히 3배다. 이 장치는 "파드 없는 노드로 간 요청이 죽는다"만 풀고 불균등은 풀지 못한다.

불균등의 뿌리는 로드밸런서가 **노드 단위**로 나누는데 노드마다 파드 수가 다르다는 데 있다. 그래서 노드별 파드 수를 고르게 맞춰야 줄어든다 — `DaemonSet` 이나 `topologySpreadConstraints` 가 그 수단이다 — 원본 §정답 6.
