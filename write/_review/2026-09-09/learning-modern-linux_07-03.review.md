## 학습 목표 (원본 §진입 인용)

주고받는 일을 몇 개의 명령으로 줄이되, **안 될 때 어느 층에서 끊겼는지 가를 수 있는** 상태.

## Q&A 5문제

### Q1. 정의 — curl 종료 코드 셋

**질문**: `curl` 이 실패할 때 남기는 종료 코드 **6 · 7 · 28** 은 각각 어느 층에서 끊긴 것인가.

**점수 (0~5)**: **2** (채점: Claude — 양 끝 둘(이름·타임아웃)은 회상. 가운데 **연결 거부**(7) 누락, 코드와 층의 대응 미도달)

---

### Q2. 동기 — 0 ms 와 6005 ms

**질문**: `7` 은 `after 0 ms`, `28` 은 `after 6005 ms` 로 끝난다. 이 차이가 무엇을 알려 주며 왜 진단의 갈림길이 되는가.

**점수 (0~5)**: **4** (채점: Claude — "즉각 거부 vs 타임아웃 대기"를 자력으로 갈랐고, `0 ms` 가 문자 그대로 0 이 아닌 이유까지 되물어 정확히 좁혔다. 2026-09-08 Q5 에서 RST 첫 의심을 방화벽으로 뒤집었던 자리를 오늘 바로 세웠다)

---

### Q3. 메커니즘 — TOFU 말고 CA 를 쓰는 길

**질문**: SSH 에서 CA 를 쓰면 무엇이 달라지며 TOFU 의 어떤 문제를 푸는가.

**점수 (0~5)**: **4** (채점: Claude — "미리 인증된 상태로 오니 확인이 필요 없다"·"최초 등록의 사용자 판단 의존을 없앤다" 둘 다 정확. 대가(CA 키가 단일 실패 지점, 대수가 선택을 정한다) 미도달)

---

### Q4. 적용 — 사다리 맨 끝의 후보

**질문**: 길도 멀쩡하고 포트도 열려 있는데 연결이 늘어진다. 무엇을 의심하며 왜 사다리의 **맨 끝**에 두는가.

**점수 (0~5)**: **2** (채점: Claude — "큐가 쌓여 느리다"는 방향은 맞으나 위치를 **중간 라우터**로 잡음. 실제는 목적지 호스트 커널의 **accept 큐**이고 원인은 앱이 `accept()` 를 제때 못 부르는 것. 네트워크가 아니라 애플리케이션 문제라 맨 끝인 이유도 미도달)

---

### Q5. 함정 — curl -I 의 단서

**질문**: `curl -I` 로 서버 생존을 확인하려 한다. 원본이 단 단서는 무엇이며 그걸 모르면 어떤 오진을 하는가.

**점수 (0~5)**: **0** (채점: Claude — 미답)

### 4. 회차 소견 (2026-09-09)

**양극화가 뚜렷하다.** Q2·Q3 는 4 점인데 Q1·Q4·Q5 는 2·2·0 이다. 갈리는 선이 회차 1 과 같다 — **논리를 물으면 나오고 항목을 물으면 안 나온다.**

### 정답 1

| 종료 코드 | 메시지 | 어디서 끊겼나 | 다음에 볼 것 |
|:--:|---|---|---|
| 6 | Could not resolve host | **이름**. 전송은 시작도 못 했다 | `dig`·`/etc/resolv.conf`·검색 도메인 |
| 7 | Failed to connect … after 0 ms | **포트**. 길은 있고 그 포트만 안 열렸다 | 상대에서 `ss -tlnp` |
| 28 | Connection timed out after 6005 ms | **무응답**. 길이 없거나 중간이 삼켰다 | 라우팅·방화벽 |

숫자 자체가 아니라 **셋이 서로 다른 층을 가리킨다**는 것이 값이다 — 원본 §3.

### 정답 2

**즉시 실패했다는 것은 상대가 무언가 대답했다는 뜻이다.** TCP 로 치면 RST 가 돌아온 것이고, 그러려면 패킷이 거기까지 갔다 와야 한다. 반대로 한도를 다 채우고 끝났다면 아무도 대답하지 않은 것이라, 길이 없거나 중간의 무엇이 조용히 버린 것이다.

`0 ms` 는 문자 그대로 0 이 아니라 루프백이라 반올림된 값이다. 갈라 주는 것은 숫자가 아니라 **왕복 한 번 만에 끝났느냐, 한도를 다 채웠느냐** — 원본 §3.

### 정답 3

`ssh-keygen -s` 로 자체 CA 키를 두고 서버의 호스트 키에 서명하면, 클라이언트는 **CA 공개키 하나만 믿으면 된다.** `known_hosts` 에 서버를 한 대씩 적을 필요가 없다.

값과 대가가 CNAME 과 같은 모양이다 — **사이에 한 겹을 두어 아래를 갈아 끼울 수 있게 된 것.** 서버를 재설치해도 CA 가 서명하면 클라이언트는 아무것도 안 고친다. 대가는 **CA 키가 단일 실패 지점**이 되는 것이라, 서버가 수천 대면 CA 가 싸고 몇 대뿐이면 TOFU 가 싸다. **대수가 정한다** — 원본 §4.

### 정답 4

**accept 큐 포화**다. 앱이 `accept()` 를 제때 못 불러 대기 줄이 차면 커널이 새 연결을 떨어뜨린다.

`LISTEN` 소켓에는 큐가 둘 딸려 있다 — SYN 큐(3-way 진행 중)와 accept 큐(완성됐고 앱이 꺼내 가길 대기). `ss` 의 `LISTEN` 행에서 `Recv-Q` 가 accept 큐에 쌓인 수, `Send-Q` 가 backlog 최대치다(ESTAB 행과 뜻이 다른 재활용 칸이다).

**맨 끝에 두는 이유**는 앞의 넷(이름·포트·경로·상대 생존)이 전부 정상으로 보이기 때문이다. 네트워크가 아니라 **애플리케이션 문제**라 앞을 지우지 않고 여기부터 보면 엉뚱한 데를 판다 — 원본 §3.

### 정답 5

**모든 HTTP 서버가 어느 경로에 대해서든 HEAD 메서드를 지원하지는 않는다.**

`-I` 로 두드려 `405`·`501` 이 오거나 응답이 없으면 "서버가 죽었다"고 읽기 쉬운데, 같은 URL 에 GET 을 걸면 `200` 이 오는 경우가 있다. **확인하려던 것(GET 이 되는가)과 실제로 잰 것(HEAD 가 되는가)이 다르다** — 원본 §3.
