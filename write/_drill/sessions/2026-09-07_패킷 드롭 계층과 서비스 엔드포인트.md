# 트러블슈팅 드릴 — 패킷 드롭 계층과 서비스 엔드포인트

---

> 첫 회차 기록입니다. 지면 2문항을 풀어 점수 2와 3을 받았습니다. 두 문항 모두 원인의 방향은 잡았고 "어디를 어떻게 보는가"에서 막혔습니다.

## 오늘의 회차

> 계층 A와 B에서 한 문항씩 뽑았습니다. 소요는 대화 포함 약 한 시간이고, 지면만이면 25분 분량입니다.

| 문항 | 계층 | 점수 | 막힌 지점 |
|------|------|------|----------|
| D1 실패율 0.3%가 사라지지 않는 서버 | A 리눅스 호스트 | 2 | 패킷이 지나는 층마다 카운터가 있다는 것을 몰랐습니다 |
| D2 Pod 로는 되고 이름으로는 안 되는 호출 | B 쿠버네티스 | 3 | EndpointSlice 를 스스로 떠올리지 못했습니다 |

두 문항의 성격이 달랐습니다. D1은 아예 후보를 못 세워 "모름"으로 두 칸을 비웠고, D2는 후보를 세웠다가 반증 앞에서 스스로 지웠습니다. 후자가 진단에서 더 중요한 동작이라 점수가 높습니다.



## D1 — 실패율 0.3%가 사라지지 않는 서버

> 로그가 비어 있는데 클라이언트만 실패를 본다면, 요청이 애플리케이션에 닿기 *전에* 사라진 것입니다. 그래서 수사는 위가 아니라 아래에서 시작합니다.

![패킷이 사라질 수 있는 층](../_assets/2026-09-07.drop-layers.svg)

증상은 이랬습니다. 실패율이 0.3% 안팎으로 꾸준합니다. 클라이언트는 타임아웃을 보고하는데 애플리케이션 로그에는 예외가 없습니다. 같은 랙의 동일 구성 서버 두 대는 멀쩡합니다.

제가 세운 가설은 "네트워크 이슈이니 패킷을 봐야 하나"였고 무엇을 볼지는 몰랐습니다. 확인 명령과 처방은 비웠습니다.

답은 도식의 다섯 층을 아래에서 위로 훑는 것입니다. 층마다 넘치면 버리고, 버릴 때마다 커널이 숫자를 세어 둡니다. 어느 층의 숫자가 늘고 있는지가 곧 어디서 사라졌는지입니다.

힌트를 받고 나서 "처리량이 느리면 저장 공간이 차고 꽉 차면 DROP 된다"까지는 스스로 세웠습니다. 이름과 명령만 몰랐던 셈입니다.

### DROP 과 REJECT 는 증상이 다릅니다

처음에 저는 타임아웃의 원인을 `iptables` 하나로만 잡았습니다. 여기서 갈라야 할 것이 있습니다.

REJECT 는 RST 나 ICMP 로 거부를 알려주므로 클라이언트가 **즉시 실패**를 봅니다. 타임아웃은 아무 말 없이 사라졌을 때만 납니다. 그러니 "타임아웃이다"라는 사실은 규칙이 막았다는 뜻이 아니라 **조용히 버려졌다**는 뜻입니다.

간헐적이라는 것도 단서였습니다. 상시 DROP 이면 100% 실패해야 하는데 99.7% 는 성공합니다. 규칙이 아니라 **무언가가 가끔 넘친다**는 신호입니다.



## 카운터는 총량이 아니라 증가분으로 읽습니다

> 91일 가동 서버에서 총량만 보면 91일치 정상 오차를 문제로 읽게 됩니다. 간격을 두고 두 번 재야 지금 늘고 있는 것이 보입니다.

회차 중에 `/proc/net/softnet_stat` 을 두 번 찍었더니 이 원리가 그대로 드러났습니다.

| CPU 0 | 처음 | 잠시 뒤 | 증가 |
|---|---|---|---|
| processed | 2,495,160 | 2,506,564 | +11,404 |
| dropped | 0 | 0 | 0 |
| time_squeeze | 4,816 | 4,840 | +24 |

패킷을 만 개 넘게 더 처리하는 동안 버린 것은 0 입니다. 총량 `4,816` 만 봤다면 큰 숫자로 보였을 것입니다.

`dropped` 와 `time_squeeze` 도 뜻이 다릅니다. `dropped` 는 큐가 꽉 차서 **버렸다**는 것이고, `time_squeeze` 는 한 번에 처리할 몫을 다 쓰고 물러났을 뿐 **버리지는 않았다**는 것입니다. 후자는 "바빴다"는 신호이지 장애가 아닙니다.

### 읽는 법을 몰랐던 출력들

`uptime` 은 다섯 가지를 한 줄에 보여줍니다. 현재 시각, 가동 시간, 접속자 수, 그리고 1분과 5분과 15분의 부하 평균입니다.

`load average` 는 퍼센트가 아니라 **개수**입니다. 실행 가능 상태로 줄 서 있는 프로세스의 평균 수라, 코어 수와 나란히 놓아야 뜻이 생깁니다. 8코어에서 `0.82` 는 약 10% 이지 82% 가 아닙니다.

리눅스에만 있는 함정이 하나 더 있습니다. 이 값은 CPU 대기만 세지 않고 **디스크 I/O 대기까지 함께 셉니다.** 그래서 CPU가 놀아도 디스크가 느리면 부하 평균이 치솟습니다.

`ip -s link` 의 RX 와 TX 는 수신과 송신입니다. 네 칸을 갈라 읽습니다.

- **errors**: 체크섬이나 프레임이 망가진 패킷
- **dropped**: 받았지만 버린 것
- **missed**: NIC 가 아예 못 받은 것으로, 링 버퍼 넘침의 직접 지표입니다
- **mcast**: 멀티캐스트

### 컨테이너 안에서는 물리 NIC 를 못 봅니다

실습 중에 `eth0@if8` 과 `link-netnsid 0` 이 찍혔습니다. veth 페어의 한쪽이라는 표시이고, 반대쪽 끝은 호스트의 8번 인터페이스에 꽂혀 있습니다.

그래서 `ethtool -S` 결과가 `peer_ifindex` 로 시작하고 `xdp_` 와 `pp_` 통계만 나왔습니다. **링 버퍼는 물리 NIC 의 것이라 컨테이너 안에서는 보이지 않습니다.** 보려면 노드로 나가야 합니다.



## 톰캣의 세 상한은 서로 다른 구간을 셉니다

> accept 큐 100 과 max-connections 8192 와 스레드 200 이 동시에 성립하는 이유입니다. 셋이 같은 것을 세지 않기 때문입니다.

![톰캣 연결 하나의 수명](../_assets/2026-09-07.tomcat-connection-life.svg)

"대기 줄이 100인데 어떻게 8192개를 무느냐"가 회차 중 나온 질문이었습니다. 답은 **대기 줄이 저장소가 아니라 통과 지점**이라는 데 있습니다. 톰캣이 계속 꺼내가므로 평소엔 거의 비어 있고, 꺼내가는 속도보다 들어오는 속도가 빠른 순간에만 찹니다.

8192가 말이 되는 것은 keep-alive 때문입니다. 연결은 살아 있지만 대부분은 요청을 안 보내고 쉬고 있습니다. 도식에서 강조한 유휴 상태가 그 자리이고, 이 상태의 연결은 목록을 차지하되 스레드는 쓰지 않습니다.

| 설정 | 정체 | 기본값 |
|---|---|---|
| `server.tomcat.accept-count` | 대기 줄(backlog) | 100 |
| `server.tomcat.threads.max` | 처리 스레드 | 200 |
| `server.tomcat.max-connections` | 물고 있는 연결 | 8192 |

`net.core.somaxconn` 은 그 위의 커널 상한입니다. 앱이 1000을 요청해도 커널이 128이면 128로 잘립니다. 앱 설정만 올리고 커널을 안 올리면 조용히 무시되는 함정이 여기 있습니다. 이 장비에서 재 보니 4096이라 `accept-count` 100은 잘리지 않습니다.

그래서 조치가 둘로 갈립니다. 큐를 늘리는 것은 **시간을 버는 일**이고, 원인 제거는 **앱이 왜 못 꺼내가는지**를 고치는 쪽입니다. 스레드 풀이 꽉 찼거나 GC 가 멈췄거나 블로킹 I/O 에 물려 있으면 초당 수십 건에도 큐가 찹니다.



## D2 — Pod 로는 되고 이름으로는 안 되는 호출

> Pod IP 직접 호출이 성공했다는 사실 하나가 후보 여럿을 한꺼번에 지웁니다. 그러면 남는 것은 이름으로 부를 때만 지나는 두 관문입니다.

![이름이 Pod 에 닿기까지](../_assets/2026-09-07.service-name-path.svg)

증상은 Pod 가 Running 이고 Ready 인데, Pod IP 로는 응답이 오고 Service 이름으로는 타임아웃이 나는 것이었습니다.

제 첫 가설은 NetworkPolicy 였습니다. 근거로 "Pod IP 와 ClusterIP 가 다르다"를 들었는데 **이건 원래 다른 대역이라 필터링의 증거가 아닙니다.**

그런데 되물음을 받고 나서 스스로 지웠습니다. NetworkPolicy 는 Pod 의 인터페이스에서 평가되는데, Service 로 온 패킷도 노드에서 이미 Pod IP 로 바뀐 뒤 도착합니다. 두 경로가 도착 시점에는 구분되지 않으므로, Pod IP 호출이 성공했다면 정책은 막고 있지 않습니다.

**후보 하나를 실험 없이 지운 것**이 이 문항의 성과입니다.

### 답은 EndpointSlice 가 비었는지였습니다

Service 는 `selector` 에 적힌 라벨로 자기 뒤에 세울 Pod 를 고릅니다. 그 라벨이 Pod 의 실제 라벨과 어긋나면 아무도 안 걸리고, 목록은 빈 채로 남습니다. Pod 가 멀쩡히 Running 인데도 말입니다.

```bash
kubectl get endpoints payment
kubectl get svc payment -o jsonpath='{.spec.selector}'
kubectl get pod payment-7d4b9c6f8-x2klm --show-labels
```

목록이 비면 노드에는 만들 규칙이 없습니다. 바꿔칠 대상이 없으니 패킷은 갈 곳을 잃고, 클라이언트는 타임아웃을 봅니다.

원인은 두 갈래입니다. 라벨 불일치가 첫째이고, `targetPort` 가 컨테이너 포트와 다른 경우가 둘째입니다. 후자는 항목이 잡히고도 연결이 안 되므로 증상이 미묘하게 다릅니다.

응급 조치는 라벨을 맞춰 붙이는 것입니다. 재발 방지는 매니페스트에서 Service 의 `selector` 와 Deployment 의 라벨을 **같은 값에서 끌어오게** 만드는 것입니다. 손으로 두 곳에 같은 문자열을 적는 한 언젠가 어긋납니다.



## 주소를 정하는 주체가 다릅니다

> Pod IP 와 ClusterIP 는 대역도 다르고 정하는 주체도 다릅니다. 한 줄로 줄이면 Service IP 는 중앙이, Pod IP 는 노드가 정합니다.

| | 대역 정의 | 개별 IP 할당 |
|---|---|---|
| Service | kube-apiserver 플래그 | kube-apiserver 가 직접 |
| Pod | controller-manager 플래그 또는 CNI 설정 | CNI 의 IPAM |

Service 를 만들면 apiserver 가 그 자리에서 주소를 찍어 오브젝트에 박습니다. Pod IP 는 다릅니다. 노드가 서브넷을 배정받고 그 안에서 CNI 가 골라 꽂은 다음, 결과를 `status.podIP` 에 보고할 뿐입니다.

ClusterIP 는 **어느 인터페이스에도 붙어 있지 않습니다.** `ip addr` 로 찾아도 없고 라우팅 테이블에도 없습니다. 노드의 iptables 규칙이나 IPVS 테이블 안에만 존재하는 이름표라서 "가상"입니다.

### CNI 가 Service 까지 맡지는 않습니다

CNI 는 Pod 네트워크를 만드는 역할이고, Service 처리는 원래 kube-proxy 몫입니다. Cilium 이 특이한 쪽입니다.

| CNI | Service 처리 | NetworkPolicy |
|---|---|---|
| Flannel | kube-proxy | 미지원 |
| Calico | kube-proxy 또는 자체 eBPF | iptables 또는 eBPF |
| Cilium | 자체 eBPF (kube-proxy 대체) | eBPF |

### 이름을 푸는 경로는 파일 둘이 나눠 갖습니다

`/etc/nsswitch.conf` 는 **어떤 순서로 물을지**를 정하고, `/etc/resolv.conf` 는 **DNS 로 물을 때 어디에 어떻게**를 정합니다. `/etc/hosts` 는 로컬 DNS 가 아니라 정적 파일이라 DNS 프로토콜을 쓰지 않습니다.

그래서 `getent hosts` 와 `dig` 는 보는 것이 다릅니다. `dig` 는 DNS 서버에 직접 묻고, `getent` 는 앱이 실제로 겪는 경로를 그대로 탑니다. "DNS 서버는 잘 답하는데 앱은 못 찾는" 상황을 잡을 때 후자가 정확합니다.



## 오답으로 남긴 것

> 점수 3 이하 문항을 [오답 노트](../_mistakes.md) 로 옮겼습니다. 무엇을 틀렸는지보다 왜 그 방향으로 갔는지를 남깁니다.

D1은 **후보를 세울 재료 자체가 없었습니다.** 패킷이 여러 층을 지나고 층마다 버릴 수 있다는 그림이 머릿속에 없으니, "네트워크 문제"라는 큰 덩어리에서 더 내려가지 못했습니다.

D2는 **배제를 하지 않고 가설을 세웠습니다.** NetworkPolicy 를 의심할 때 "그렇다면 Pod IP 호출은 어떻게 성공했나"를 자문했다면 첫 답에서 지웠을 것입니다. 가설 칸에 배제 근거를 함께 적으라는 규칙이 정확히 이 지점을 겨냥합니다.

두 문항 다 점수가 3 이하라 오답 노트에 올렸고, D1은 2점이므로 사흘 뒤인 2026-09-10에 같은 계층의 비슷한 문항으로 다시 나옵니다.



## 다음에 볼 것

> 오늘 열렸다가 닫지 않은 갈래입니다. 다음 회차의 출제 후보이기도 합니다.

- `conntrack` 은 첫 패킷부터 추적을 시작하고 UDP 도 추적합니다. 그 테이블이 차면 어떤 증상이 나오는지
- Pod 의 `resolv.conf` 에 박히는 `ndots:5` 와 `search` 도메인이 짧은 이름 하나를 몇 번 질의하게 만드는지
- `time_squeeze` 가 계속 늘면 언제 `dropped` 로 번지는지
