# 레지스트리 복제와 프록시 캐시 — Push·Pull Replication 과 Proxy Cache 선택 기준

---

> Harbor 에서 레지스트리 간 이미지를 옮기거나 외부 이미지를 캐시할 때는 **Replication(Push·Pull)** 과 **Proxy Cache** 를 목적에 따라 구분해야 합니다. 내부 환경 승격·DR 동기화는 Replication 이 맡고, 외부 레지스트리 rate limit 회피와 대역폭 절감은 Proxy Cache 가 맡습니다.

근거는 Harbor 2.14.0 공식 문서입니다. 참고한 블로그 글의 UI 절차와 복제 모드는 2.14.0 공식 명세로 교차 확인했습니다.[^blog-34][^harbor-rep]

실제 Harbor 클러스터에 접속해 UI 조작이나 전송 속도를 실측하지는 않았습니다. 모든 동작 규칙과 기본값은 Harbor 2.14.0 공식 문서 문장에 따랐습니다.



## 학습 목표와 범위

> 읽고 나면 상황에 맞춰 Push 복제, Pull 복제, Proxy Cache, 오프라인 반입 넷 중 하나를 고르고, 설정 시 빠지기 쉬운 제약을 짚을 수 있습니다.

1. Push-based 와 Pull-based Replication 이 연결 방향과 트리거 조건에서 어떻게 다른지 설명할 수 있습니다.
2. Proxy Cache 가 Docker Hub 의 pull 횟수 제한을 피하는 `HEAD` 검증 절차와 `push` 불가 제약을 설명할 수 있습니다.
3. 멀티 리전 DR, 외부 공개 이미지 캐시, 완전 폐쇄망 반입 각각에 알맞은 전송 경로를 선택할 수 있습니다.

레지스트리의 `/v2/` 토큰 인증과 `docker save`·`skopeo` 오프라인 반입 절차 자체는 [레지스트리 통신과 오프라인 반입](../container/03-03.레지스트리%20통신과%20오프라인%20반입.md) 이 맡습니다. Harbor 의 컴포넌트와 로봇 계정 개요는 [Harbor 개요](../../../../_archive/08_cloud/kubernetes/11_devtools/11-04.Harbor.md) 에 있습니다.



## 1. 단일 레지스트리를 넘어야 하는 상황

> 레지스트리 하나만 두면 외부 이미지 pull 제한, 리전 장애 시 배포 중단, 환경 격리 경계가 한꺼번에 부딪힙니다.

쿠버네티스 클러스터가 늘어나고 외부 공개 이미지 의존이 커지면 단일 Harbor 인스턴스로는 세 가지 문제가 생깁니다.

1. **외부 pull rate limit 초과**: 노드 여러 대가 같은 공개 이미지를 동시에 받으면 Docker Hub 요청 한도에 걸려 파드가 `ImagePullBackOff` 에 빠집니다.
2. **가용성과 재해 복구**: 주 Harbor 서버가 내려가거나 리전 간 회선이 느려지면 새 파드 스케줄링과 롤백이 함께 멈춥니다.
3. **환경 간 이미지 승격**: 개발 레지스트리에 올린 이미지를 검증한 뒤 운영 레지스트리나 클라우드 저장소로 넘겨야 합니다.

이 세 문제를 하나의 기능으로 풀려고 하면 설계가 어긋납니다. 외부 이미지를 캐시할 때 Replication 을 쓰면 안 쓰는 태그까지 전부 복제되어 스토리지가 낭비됩니다. 반대로 사내 빌드 이미지를 Proxy Cache 프로젝트에 올리려 하면 `push` 자체가 막혀 실패합니다.



## 2. Replication 모드와 트리거

> 원격에 이미지가 없거나 로컬 변경을 즉시 반영하지 못하면 환경 간 배포가 어긋납니다. Replication 은 이미지·Helm 차트·Cosign 서명을 Push 또는 Pull 모드로 동기화합니다.

먼저 `Administration > Registries` 에서 대상 레지스트리 **Endpoint** 를 등록하고 연결 테스트를 통과해야 합니다.[^harbor-ep] 대상 네임스페이스가 원격에 없으면 Harbor 가 자동으로 새로 만듭니다.[^harbor-rep]

![Harbor Replication Push·Pull 과 Proxy Cache 의 구조 비교](./_assets/레지스트리%20복제·프록시%20캐시.replication-modes.svg)

위 그림은 세 방식이 누가 연결을 열고 아티팩트를 어느 방향으로 옮기는지를 나란히 놓은 것입니다. 상단 두 줄인 Push 와 Pull 은 `jobservice` 가 연결을 여는 방향만 다를 뿐 같은 규칙 엔진을 씁니다.

### Push-based 와 Pull-based 의 차이

- **Push-based**: 로컬 Harbor 가 원본, 원격 레지스트리가 대상입니다. 로컬 변경이 생기면 `jobservice` 가 원격으로 밀어내며 원격 프로젝트 쓰기 권한이 필요합니다.[^harbor-ep][^harbor-rule]
- **Pull-based**: 원격 레지스트리가 원본, 로컬 Harbor 가 대상입니다. 로컬 `jobservice` 가 원격에서 당겨 오며 원격의 읽기 권한만 있으면 됩니다.[^harbor-rule]

방화벽이나 NAT 뒤 클러스터가 중앙 메인 Harbor 를 바라보는 구조에서는 Pull 모드가 유리합니다. 메인 Harbor 가 수많은 엣지에 일일이 접속해 밀어내지 않고, 각 엣지가 자기 일정에 맞춰 가져가기 때문입니다.

### 트리거 3종과 삭제·경로 옵션

복제 규칙을 실행하는 트리거는 세 가지입니다.[^harbor-rule]

1. **Manual**: 관리자가 UI 에서 `Replicate` 를 눌러 즉시 실행합니다.
2. **Scheduled**: cron 표현식으로 정해진 주기마다 실행합니다.
3. **Event Based**: 로컬 프로젝트에 새 리소스가 push 되거나 태그가 다시 붙을(retag) 때 즉시 실행됩니다.[^harbor-rule]

`Manual` 과 `Scheduled` 에서는 로컬 이미지를 지워도 원격 이미지가 지워지지 않습니다.[^harbor-rule] 원격 삭제까지 맞추려면 `Event Based` 에서 `Delete remote resources when locally deleted` 옵션을 켜야 합니다.[^harbor-rule] 단, 아티팩트의 라벨을 바꾸는 작업은 복제 이벤트를 일으키지 않습니다.[^harbor-rule]

대상 경로 계층을 줄이는 `Destination Flattening` 옵션도 있습니다.[^harbor-rule] Harbor v2.3.0 이후 기본값은 왼쪽 1단계를 떼어 내는 `Flattening 1 level` 입니다.[^harbor-rule] 예를 들어 `a/b/c/d/img` 를 복제하면 대상 네임스페이스 아래 `b/c/d/img` 로 저장됩니다.

Harbor 끼리 대용량 아티팩트를 복제할 때는 `Copy by chunk` 옵션을 켤 수 있습니다.[^harbor-rule] 기본 청크 크기는 10MB 입니다. 이 크기는 `jobservice` 환경변수 `REPLICATION_CHUNK_SIZE`(바이트 단위)로 조절합니다.[^harbor-rule]



## 3. Proxy Cache 의 온디맨드 캐싱 흐름

> 미리 전체를 복제하면 쓰지 않는 태그까지 디스크를 채우고 pull 한도를 소모합니다. Proxy Cache 는 클라이언트 pull 시점에만 업스트림을 조회하며 `HEAD` 로 무과금 검증을 수행합니다.

**Proxy Cache** 는 일반 Harbor 프로젝트가 아니라 전용 프록시 프로젝트로 만듭니다.[^harbor-proxy] 클라이언트가 `<Harbor 주소>/<프록시 프로젝트>/<원본 경로>` 로 pull 하면 아래 네 갈래로 동작합니다.

![Harbor Proxy Cache 의 pull 판정과 push 차단 순서](./_assets/레지스트리%20복제·프록시%20캐시.proxy-cache-flow.svg)

위 시퀀스에서 핵심 동작은 **CASE 2** 와 **CASE 4** 입니다.

1. **캐시 미스 (CASE 1)**: 로컬에 없으면 Harbor 가 업스트림에서 이미지를 내려받습니다. 받은 이미지는 로컬에 저장한 뒤 클라이언트에 반환합니다.[^harbor-proxy]
2. **캐시 히트 (CASE 2)**: 이미 캐시된 이미지를 다시 요청하면 Harbor 는 업스트림에 `HEAD` 요청만 보냅니다.[^harbor-proxy] Harbor v2.1.1 이후 이 `HEAD` 확인은 Docker Hub 의 pull rate limit 횟수를 깎지 않습니다.[^harbor-proxy]
3. **업스트림 단절 (CASE 3)**: 업스트림 레지스트리에 닿지 않으면 로컬 캐시 이미지를 그대로 내어 줍니다.[^harbor-proxy] 단, 업스트림에서 이미지 자체가 지워진 경우에는 제공하지 않습니다.[^harbor-proxy]
4. **직접 push 차단 (CASE 4)**: Proxy Cache 프로젝트는 pull 전용입니다. 따라서 클라이언트가 이 프로젝트로 직접 `docker push` 하는 요청은 거부됩니다.[^harbor-proxy]

새 Proxy Cache 프로젝트를 만들면 기본적으로 **7일 보존 정책(tag retention)** 이 자동 생성됩니다.[^harbor-proxy] 오래 안 쓰는 외부 이미지가 디스크를 계속 채우지 않게 하려는 기본값입니다.



## 4. 세 전송 방식의 비교와 선택

> 목적이 다른데도 예비 Harbor 에 복제와 캐시를 한꺼번에 섞으면 장애 복구와 저장소 정책이 충돌합니다. 2026년 운영 기준으로는 외부 캐시와 내부 승격·DR 동기화를 분리합니다.

2024년 전후 사례에서는 예비 Harbor 를 두고 Replication 과 Proxy Cache 를 묶어 HA 대안처럼 쓰기도 했습니다.[^blog-34] 그러나 목적과 제약이 다르므로 아래 기준으로 나누는 편이 안전합니다.

| 구분 | Push Replication | Pull Replication | Proxy Cache | 오프라인 반입(`skopeo`) |
|---|---|---|---|---|
| 동작 시점 | push·retag 이벤트, cron, 수동 | cron, 수동 | 클라이언트 `pull` 시 온디맨드 | 작업자 반입 시 수동·스크립트 |
| 직접 `push` 가능 여부 | 가능(원본 프로젝트) | 가능(원본 프로젝트) | **불가(읽기 전용)** | 내부 레지스트리에 별도 `push` |
| 필요한 네트워크 방향 | 원본 → 대상 아웃바운드 | 대상 → 원본 아웃바운드 | Harbor → 업스트림 아웃바운드 | 물리 단절(이동 매체) |
| Docker Hub rate limit | 필터 대상 전체 pull 발생 | 필터 대상 전체 pull 발생 | `HEAD` 확인으로 최소화 | 반입 횟수만큼만 발생 |
| 주 용도 | Dev→Prod 승격, 멀티 리전 DR | 엣지·지사 Harbor 동기화 | 외부 공개·벤더 이미지 캐싱 | 완전 폐쇄망(Air-gap) |

2026년 기준 레지스트리 복제·운영에서 함께 챙겨야 할 실무 기준은 세 가지입니다.

- **OCI 아티팩트와 서명 동반 복제**: Harbor 2.14 Replication 은 이미지뿐 아니라 Helm 차트와 Cosign 서명을 함께 복제합니다.[^harbor-rep] `Resource` 필터를 `all` 로 두어야 운영 클러스터의 서명 검증이 깨지지 않습니다.
- **불변 태그와 digest 고정**: 같은 태그에 새 이미지를 덮어쓰면 `Override` 설정에 따라 원본과 대상이 엇갈릴 수 있습니다. [이미지 구조와 digest](../container/03-01.이미지%20구조와%20digest.md) 의 Tag Immutability 를 켜고 `@sha256:` digest 로 배포를 고정합니다.
- **완전 폐쇄망과의 경계**: Proxy Cache 와 Replication 은 모두 소스 레지스트리에 네트워크가 닿아야 합니다. 외부 접속이 막힌 폐쇄망은 [이미지 pull과 폐쇄망 반입](../../../../08_cloud/docs/kubernetes/architecture/이미지%20pull·폐쇄망%20반입.md) 의 `skopeo copy --all --preserve-digests` 경로를 씁니다.



## 5. 한계와 운영 시 주의사항

> 버전 간 API 불일치, Proxy Cache 엔드포인트의 권한 과다 노출, 대역폭 제한 중 작업 중단 지연을 미리 확인해야 합니다.

설정하기 전에 공식 문서가 명시한 네 가지 함정을 짚고 넘어갑니다.

- **Harbor 버전 호환성**: API 변경 때문에 서로 다른 버전의 Harbor 간 Replication 은 지원되지 않습니다.[^harbor-rep] 특히 OCI 매니페스트 리스트 지원이 바뀐 v1.x 와 v2.0+ 사이는 복제가 불가능합니다.[^harbor-rule]
- **Proxy Cache 의 권한 전파 위험**: Proxy Cache 프로젝트는 Endpoint 계정이 접근할 수 있는 업스트림의 모든 이미지를 pull 합니다.[^harbor-proxy] 그 결과 프로젝트 권한이 있는 사용자는 Endpoint 계정이 볼 수 있는 업스트림 비공개 이미지까지 끌어갈 수 있습니다.[^harbor-proxy]
- **대역폭 제한과 jobservice 점유**: 대역폭 상한을 너무 낮게 잡고 작업을 중지하면 `jobservice` 워커가 바로 풀리지 않는 알려진 이슈(#15708)가 있습니다.[^harbor-rule] `jobservice` 파드당 기본 동시 실행 수는 10개입니다.[^harbor-rule]
- **고가용성 대체 불가**: Replication 은 비동기 복제라서 네트워크 상태에 따라 지연이 생깁니다.[^harbor-rep] 무중단 HA 가 목적이면 PostgreSQL·Redis·스토리지를 외부화해 Harbor 자체를 다중화해야 합니다.[^harbor-arch]



## 6. 관련 실습

> 이 문서는 Harbor 2.14.0 공식 문서 대조만으로 작성했으며, 라이브 Harbor 인스턴스를 띄워 UI 설정이나 복제 전송을 실행하지는 않았습니다.

실습 환경에서 확인하려면 Harbor 두 대를 띄운 뒤 두 가지를 검증합니다. 첫째, `Event Based` Push 규칙을 걸고 이미지를 `push`·`retag` 한 뒤 실행 로그와 대상의 `Flattening` 경로를 봅니다. 둘째, Proxy Cache 프로젝트를 만들고 첫 `pull` 과 재요청 시 업스트림 접근 기록을 비교해 `HEAD` 무과금 동작을 확인합니다.



## 결정 치트시트

> 목적과 네트워크 경계에 따라 선택하는 기준 요약입니다.

| 상황 | 선택 | 이유 |
|---|---|---|
| 사내 클러스터에서 Docker Hub·GHCR 이미지 pull 제한 회피 | Proxy Cache | 요청 시점만 캐시하고 재요청 시 `HEAD` 로 pull 횟수 미소모 |
| CI 가 올린 사내 이미지를 DR Harbor 나 ECR 로 즉시 배포 | Push Replication (`Event Based`) | push·retag 즉시 송신하며 삭제 전파 옵션 지원 |
| 본사 메인 Harbor 에서 다수 지사·엣지 Harbor 로 주기 동기화 | Pull Replication (`Scheduled`) | 엣지가 읽기 권한만으로 자기 일정에 맞춰 수집 |
| 컨테이너 내부에서 `docker push` 도 함께 받아야 하는 저장소 | 일반 프로젝트 + Replication | Proxy Cache 는 직접 `push` 를 차단함 |
| 외부망과 물리적으로 완전히 단절된 폐쇄망 클러스터 | `skopeo copy --all --preserve-digests` | Harbor 간 온라인 복제·캐시 연결 자체가 성립하지 않음 |



## 면접 질문

> 위 내용을 근거와 함께 말로 설명할 수 있는지 확인하는 질문입니다.

1. Docker Hub 에서 같은 이미지를 반복해서 `pull` 할 때, Harbor Proxy Cache 가 rate limit 소모를 피하는 원리는 무엇입니까?
2. 사내 다중 리전이나 DR 환경에서 Push Replication 과 Pull Replication 은 각각 어느 쪽에 더 유리합니까?
3. Proxy Cache 프로젝트를 일반 Harbor 프로젝트와 섞어 쓰거나 내부 CI push 대상 저장소로 쓰지 못하는 이유는 무엇입니까?
4. Harbor `Event Based` Replication 에서 이미지 push 외에 어떤 동작이 복제를 일으키고, 어떤 변경은 일으키지 않습니까?



## 정답 (자답 후 펼치기)

> 위 면접 질문 4개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — `HEAD` 매니페스트 확인
클라이언트가 이미 캐시된 이미지를 다시 요청하면, Harbor v2.1.1 이후 Proxy Cache 는 업스트림에 레이어 `GET` 대신 매니페스트 `HEAD` 요청만 보내 변경 여부를 확인합니다. Docker Hub 정책상 `HEAD` 요청은 pull rate limit 횟수를 차감하지 않으므로, 이미지가 바뀌지 않았을 때 횟수 소모 없이 로컬 캐시를 반환할 수 있습니다.

### 정답 2 — 연결 주체와 권한 경계
CI 가 올린 산출물을 즉시 운영·DR 레지스트리로 넘겨야 하거나 원격 삭제까지 동기화해야 할 때는 `Event Based` 트리거를 지원하는 Push Replication 이 맞습니다. 반대로 다수의 원격·엣지 클러스터가 중앙 메인 Harbor 에서 이미지를 받아 가는 구조에서는, 원격이 읽기 권한만으로 자기 주기에 맞춰 가져가는 Pull Replication 이 메인 Harbor 의 연결·송신 부담을 줄입니다.

### 정답 3 — 읽기 전용 제약과 7일 보존 정책
Proxy Cache 프로젝트는 업스트림 레지스트리의 대리 캐시 역할만 맡도록 설계돼 있어 직접 `docker push` 하는 기능이 막혀 있습니다. 또한 기본으로 7일 태그 보존 정책이 붙기 때문에 사내 빌드 산출물을 영구 보관하는 원본 저장소로 쓸 수 없습니다.

### 정답 4 — 이벤트 트리거 범위
`Event Based` 복제는 아티팩트 **push**, **retag**, 그리고 `Delete remote resources when locally deleted` 옵션을 켰을 때의 **delete** 에서만 발동합니다. 반면 아티팩트에 **라벨(label)을 붙이거나 바꾸는 작업** 은 복제 이벤트를 일으키지 않습니다.
