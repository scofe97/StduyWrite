# Web API 구조

> 공식 문서의 Web API 페이지는 한 장뿐이고 엔드포인트 목록이 없습니다. 실제 레퍼런스는 인스턴스 안에 있습니다. 이 편은 로컬 인스턴스에서 전수로 뜬 카탈로그를 근거로 구조를 정리합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 엔드포인트 목록을 어디서 얻어야 하는지 알고 그 방법을 실행할 수 있습니다.
2. 인증 방식 두 가지를 대고 각각 언제 쓰는지 설명할 수 있습니다.
3. POST 요청에서 쿼리 문자열 대신 폼 데이터를 써야 하는 이유를 말할 수 있습니다.
4. v2 API 가 어떤 위치에 있는지 판단할 수 있습니다.



## 1. 카탈로그는 인스턴스가 갖고 있습니다

> 공식 문서에는 엔드포인트 목록이 없습니다. 인스턴스의 `/api/webservices/list` 가 전수 목록입니다.

Web API 를 다루려 할 때 처음 부딪히는 문제가 있습니다. 공식 문서의 Web API 페이지는 "인스턴스 안에 문서화돼 있으니 상단 도움말 버튼을 누르라"고 안내할 뿐 목록을 싣지 않습니다.

그래서 목록은 인스턴스에서 떠야 합니다. 로컬 인스턴스에서 전수로 뜨면 이 규모입니다.

| 항목 | 실측 |
|---|---:|
| 네임스페이스 | **39** |
| 액션 | **229** |

액션이 많은 네임스페이스 상위는 이렇습니다.

| 네임스페이스 | 액션 | 성격 |
|---|---:|---|
| `api/alm_settings` | 23 | DevOps 플랫폼 설정 |
| `api/qualityprofiles` | 21 | 프로파일 관리 |
| `api/qualitygates` | 21 | 게이트와 조건 |
| `api/permissions` | 17 | 권한과 템플릿 |
| `api/issues` | 14 | 이슈 조회·수정 |
| `api/system` | 10 | 시스템 상태·관리 |

CI 통합에서 실제로 쓰는 것은 훨씬 좁습니다.

| 네임스페이스 | 액션 | 쓰임 |
|---|---:|---|
| `api/ce` | 4 | 분석 작업 상태 조회 |
| `api/qualitygates` | 21 | 게이트 판정 조회 |
| `api/webhooks` | 6 | 웹훅 등록과 전달 이력 |
| `api/user_tokens` | 3 | 토큰 발급·폐기 |
| `api/measures` | 3 | 지표 값 조회 |

카탈로그를 뜨면 각 액션의 파라미터와 `deprecatedSince` 표시까지 함께 옵니다. 문서를 뒤지는 것보다 이쪽이 정확합니다. 인스턴스 버전에 실제로 존재하는 것만 나오기 때문입니다.

한 가지 주의할 점이 있습니다. **`/api/webservices/list` 자체가 인증을 요구합니다.** 익명으로 호출하면 401 이 돌아옵니다. 반면 `/api/system/status` 는 익명으로도 200 을 줍니다. 어떤 엔드포인트가 인증을 요구하는지는 일관된 규칙이 아니라 엔드포인트마다 다릅니다.



## 2. 인증은 Bearer 가 기본입니다

> 토큰을 `Authorization: Bearer` 헤더로 보냅니다. 그것이 안 되는 소수의 엔드포인트만 passcode 를 씁니다.

공식 문서가 권장하는 방식은 **bearer 스킴**입니다.

```bash
curl --request GET \
  --url 'http://localhost:9000/api/measures/component?component=demo-app&metricKeys=ncloc' \
  --header 'Authorization: Bearer <token>'
```

두 번째 방식은 **X-Sonar-Passcode** 입니다. bearer 를 쓸 수 없는 엔드포인트에 씁니다. 문서가 예로 드는 것이 `monitoring/metrics` 입니다. passcode 는 `sonar.properties` 의 `sonar.web.systemPasscode` 나 환경 변수 `SONAR_WEB_SYSTEMPASSCODE` 로 정합니다.

토큰으로 API 를 호출할 때 응답에 유용한 헤더가 하나 붙습니다.

```bash
SonarQube-Authentication-Token-Expiration: 2026-09-20T00:00:00+0000
```

토큰 만료일을 알려 주므로 외부 도구가 만료를 추적해 미리 회전할 수 있습니다. 다만 실측해 보면 이 헤더는 **조건부**입니다.

| 조건 | 헤더 |
|---|---|
| 인증이 필요한 엔드포인트 + 만료일이 있는 토큰 | 나옴 |
| 인증이 필요한 엔드포인트 + 만료일이 없는 토큰 | 안 나옴 |
| 익명으로도 되는 엔드포인트 | 안 나옴 |

만료일 없이 토큰을 만들면 이 헤더로 회전 시점을 추적할 수 없습니다. 자동 회전을 설계한다면 토큰 발급 시 `expirationDate` 를 반드시 넣어야 합니다.



## 3. POST 는 폼 데이터로 보냅니다

> 쿼리 문자열에 파라미터를 실으면 안전하게 전달되지 않습니다. 기본 Content-Type 은 form-urlencoded 입니다.

공식 문서가 명시합니다. POST 요청에는 폼 데이터 파라미터를 쓰기를 강력히 권장하며, URI 쿼리 파라미터를 쓰면 그 파라미터가 안전하게 전달되지 않습니다.

엔드포인트 명세가 특정 `Content-Type` 을 요구하지 않는 한 기본값은 이것입니다.

```bash
Content-Type: application/x-www-form-urlencoded
```

`curl` 과 Python `requests` 를 포함한 대부분의 도구가 이 값을 기본으로 씁니다. 그래서 `curl -d` 로 보내면 별도 설정 없이 맞습니다.

실무에서 이 규칙이 걸리는 자리가 토큰 발급입니다. 토큰 이름이나 프로젝트 키를 쿼리 문자열에 실으면 서버 접근 로그에 그대로 남습니다. 발급된 토큰 자체는 응답 본문에 오지만, 요청 파라미터가 로그에 남는 것만으로도 정보가 새 나갑니다.



## 4. v2 API 가 자리를 넓히는 중입니다

> 기존 엔드포인트가 하나씩 폐기되면서 v2 로 대체됩니다. 지금은 둘이 공존합니다.

공식 문서가 한 줄로 예고합니다. Web API V2 가 기존 Web API 를 점진적으로 대체하며, 엔드포인트가 폐기되고 교체되는 방식으로 진행됩니다.

로컬 인스턴스에서 확인하면 실제로 살아 있습니다.

| 경로 | 응답 |
|---|---|
| `/api/v2/analysis/version` | `200` — 본문에 `26.1.0.118079` |
| `/api/v2/system/liveness` | `204` |
| `/api/v2/` | `404` |

v2 는 루트 인덱스를 주지 않으므로 `/api/v2/` 로 목록을 얻을 수 없습니다. 어떤 v2 엔드포인트가 있는지는 인스턴스 내장 문서에서 확인해야 합니다.

당장의 판단은 이렇습니다. 지금 스크립트를 짠다면 v1 을 쓰되 카탈로그에서 `deprecatedSince` 가 붙은 액션은 피합니다. 카탈로그를 뜨면 이 표시가 함께 오므로 폐기 예정인 것을 미리 걸러낼 수 있습니다.

실측하면 229개 액션 중 25개가 이미 폐기 표시를 달고 있고, 쏠림이 뚜렷합니다.

| 네임스페이스 | 폐기 / 전체 |
|---|---:|
| `api/user_groups` | **7 / 7** |
| `api/users` | 8 / 9 |
| `api/alm_integrations` | 5 / 12 |
| `api/qualityprofiles` | 3 / 21 |
| `api/system` | 1 / 10 |
| `api/issues` | 1 / 14 |

사용자와 그룹 관리 쪽이 거의 전부 넘어갔습니다. `api/user_groups` 는 7개가 하나도 남김없이 폐기 표시라 사실상 v2 로 이전이 끝난 영역입니다. 이런 네임스페이스를 v1 으로 새로 짜면 다음 LTA 에서 깨질 확률이 높습니다.



## 면접에서 받을 만한 질문

1. SonarQube 의 엔드포인트 목록을 어디서 얻겠습니까. 공식 문서로 충분합니까.
2. 토큰 만료를 자동으로 추적하려면 무엇을 해야 합니까.
3. `POST /api/user_tokens/generate` 를 쿼리 문자열로 호출하면 무엇이 문제입니까.

> 3개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 3개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 인스턴스가 카탈로그를 갖고 있음

공식 문서로는 부족합니다. Web API 페이지는 한 장이고 엔드포인트 목록을 싣지 않으며 "인스턴스 안에 문서화돼 있다"고 안내할 뿐입니다.

목록은 인스턴스의 `/api/webservices/list` 에서 뜹니다. 로컬 실측으로는 네임스페이스 39개에 액션 229개였습니다. 이 응답에는 각 액션의 파라미터와 `deprecatedSince` 표시까지 함께 오므로 문서보다 정확합니다. 인스턴스 버전에 실제로 존재하는 것만 나오기 때문입니다.

호출 자체에 인증이 필요합니다. 익명으로 부르면 401 입니다.

### 정답 2 — 발급할 때 만료일을 넣어야 함

응답의 `SonarQube-Authentication-Token-Expiration` 헤더로 추적합니다. 다만 이 헤더는 조건부라서 만료일이 **있는** 토큰으로 **인증이 필요한** 엔드포인트를 호출할 때만 나옵니다.

따라서 자동 회전을 설계하려면 토큰을 발급할 때 `expirationDate` 를 반드시 넣어야 합니다. 만료일 없이 만든 토큰은 이 헤더가 아예 붙지 않아 회전 시점을 알 수 없습니다.

### 정답 3 — 파라미터가 접근 로그에 남음

공식 문서가 POST 에는 폼 데이터를 쓰라고 권장하며, URI 쿼리 파라미터를 쓰면 안전하게 전달되지 않는다고 명시합니다.

토큰 발급의 경우 이름과 프로젝트 키가 서버 접근 로그에 그대로 남습니다. 발급된 토큰 값 자체는 응답 본문에 오므로 로그에 남지 않지만, 어떤 토큰이 어느 프로젝트용으로 언제 만들어졌는지가 노출됩니다.

기본 `Content-Type` 은 `application/x-www-form-urlencoded` 이고 `curl -d` 나 Python `requests` 는 이 값을 기본으로 쓰므로 별도 설정이 필요 없습니다.
