# Rule과 Quality Profile

> 규칙은 언어별로 묶여 프로파일이 되고, 분석기는 프로파일에 켜진 규칙만 적용합니다. 내장 프로파일은 고칠 수 없으므로 팀 규칙은 상속으로 만듭니다. 상속을 쓰면 새 규칙이 자동으로 따라오고, 쓰지 않으면 프로파일이 그 자리에 얼어붙습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 내장 프로파일을 왜 직접 고칠 수 없는지, 그러면 어떻게 하는지 설명할 수 있습니다.
2. 상속을 걸었을 때 부모의 변경이 자식에 어떻게 반영되는지 규칙을 댈 수 있습니다.
3. 자식에서 규칙을 끄거나 심각도를 바꿨을 때 상태가 어떻게 표시되는지 말할 수 있습니다.
4. 상속을 쓰지 않은 커스텀 프로파일이 시간이 지나면 어떻게 되는지 판단할 수 있습니다.



## 1. 프로파일은 언어마다 한 벌씩 있습니다

> 한 언어에 여러 프로파일을 둘 수 있고 그중 하나가 기본입니다. 내장 프로파일 `Sonar way` 는 읽기 전용입니다.

프로파일은 언어에 묶입니다. 특정 언어가 지원하는 규칙 집합 위에서, 그중 어떤 규칙을 켤지를 정한 것이 프로파일입니다.

한 언어에 프로파일을 여러 개 둘 수 있고 그중 하나가 기본 프로파일입니다. 프로젝트가 프로파일을 명시하지 않으면 기본 프로파일로 분석합니다.

설치 시점에 언어마다 `Sonar way` 라는 내장 프로파일이 제공되며 **편집할 수 없습니다.** 로컬 인스턴스에서 세어 보면 내장 프로파일이 27개이고 전부 `Sonar way` 라는 같은 이름을 씁니다. 이름이 같아도 언어가 다르므로 서로 다른 프로파일입니다.

| 언어 | `Sonar way` 활성 규칙 |
|---|---:|
| java | 537 |
| ts | 394 |
| js | 381 |
| cs | 321 |
| py | 306 |

내장 프로파일은 대부분의 프로젝트에 두루 맞도록 설계됐지만 **출발점으로만 의도된 것**입니다. 팀 사정에 맞추려면 커스텀 프로파일을 만듭니다.



## 2. 상속이 곧 유지보수 전략입니다

> 자식은 부모의 활성 규칙을 물려받고, 부모가 바뀌면 자동으로 따라옵니다. 이것이 새 규칙을 놓치지 않는 유일한 장치입니다.

커스텀 프로파일을 만드는 방법은 둘입니다. 빈 프로파일에서 규칙을 하나씩 켜는 방법과, 내장 프로파일을 부모로 두고 상속받는 방법입니다.

로컬 인스턴스에서 두 번째를 실제로 해봤습니다. `team-java` 라는 빈 커스텀 프로파일을 만들고 부모를 `Sonar way` 로 지정하니 활성 규칙이 곧바로 **537개**가 됐습니다. 부모와 같은 수입니다.

상속을 쓰면 다음 셋이 자동으로 따라옵니다.

- 새로 구현된 규칙
- 규칙 설정의 변경
- 폐기된 규칙의 비활성화

세 번째가 특히 중요합니다. SonarQube 를 업그레이드하면 규칙 집합과 내장 프로파일이 함께 갱신되는데, 상속을 걸어 두지 않은 커스텀 프로파일은 이 갱신을 받지 못합니다. 만든 시점의 규칙 목록에 그대로 멈춰 있습니다. 몇 번의 업그레이드가 지나면 그 프로파일은 최신 규칙을 하나도 모르는 상태가 됩니다.

계층도 만들 수 있습니다. 부모의 변경은 모든 하위 자식에 반영됩니다. 다만 자식은 항상 커스텀 프로파일이어야 합니다. 내장 프로파일은 자식이 될 수 없습니다.



## 3. 자식에서 무엇을 바꿀 수 있습니까

> 규칙을 켜고 끄고, 심각도와 파라미터를 바꿀 수 있습니다. 바꾼 규칙은 재정의 상태로 표시됩니다.

자식 프로파일에서 할 수 있는 일은 셋입니다. 꺼져 있는 규칙을 켜기, 켜져 있는 규칙을 끄기, 그리고 심각도나 파라미터를 부모와 다르게 바꾸기입니다. 세 번째의 경우 그 규칙은 **재정의(overridden)** 상태가 됩니다.

로컬에서 확인한 결과입니다. `team-java` 에서 규칙 하나를 끄고 다른 규칙 하나의 심각도를 바꾼 뒤 상태를 조회했습니다.

| 규칙 | 부모 `Sonar way` | 자식 `team-java` |
|---|---|---|
| `java:S1192` | `CRITICAL` · `inherit=NONE` | `BLOCKER` · **`inherit=OVERRIDES`** |
| `java:S1118` | `MAJOR` · 활성 | 비활성 |

규칙을 하나 끄자 활성 규칙 수가 537 에서 536 으로 줄었습니다. 재정의한 규칙은 `OVERRIDES` 로 표시되어 부모와 다르다는 사실이 목록에서 바로 보입니다.

재정의의 효과는 그 프로파일 안에만 머뭅니다. 규칙 자체의 권장 심각도는 바뀌지 않습니다. 다른 프로파일이 같은 규칙을 쓰고 있어도 영향이 없습니다.

부모의 변경이 자식에 반영되는 방식에도 규칙이 있습니다. 부모에서 규칙을 켜거나 끄면 자식에서의 상태와 무관하게 반영됩니다. 반면 파라미터 변경은 **자식이 그 규칙을 재정의하지 않았을 때만** 반영됩니다. 재정의한 규칙은 자식의 값을 지킵니다.



## 4. 프로파일을 갈아 끼우면 결과가 달라집니다

> 같은 코드라도 프로파일이 다르면 이슈가 다릅니다. 수치를 비교하기 전에 프로파일부터 맞춥니다.

[01-01](01-01.정적 분석이 푸는 결함.md) 에서 Java 규칙 695개 중 537개만 `Sonar way` 에 켜져 있다고 했습니다. 나머지 158개는 존재하지만 기본으로는 적용되지 않습니다.

따라서 이슈 수는 코드만의 함수가 아닙니다. 두 프로젝트의 이슈 수를 비교하거나, 같은 프로젝트의 이슈가 갑자기 늘었다고 판단하기 전에 프로파일이 같은지 확인해야 합니다. 프로파일을 바꾸거나 서버를 업그레이드해 내장 프로파일이 갱신되면 코드가 그대로여도 숫자가 움직입니다.

이것이 [01-01](01-01.정적 분석이 푸는 결함.md) 에서 본 이슈 백데이팅과 이어집니다. 새 규칙이 프로파일에 추가되어 오래된 코드에서 이슈가 새로 발견되면, 서버는 그 이슈를 분석일이 아니라 해당 줄이 마지막으로 바뀐 날짜로 잡습니다. 그렇게 하지 않으면 프로파일을 갱신할 때마다 오래된 코드의 이슈가 전부 새 코드로 몰려 Quality Gate 가 무너집니다.



## 면접에서 받을 만한 질문

1. 커스텀 프로파일을 상속 없이 만들면 시간이 지나 어떻게 됩니까.
2. 자식에서 규칙 하나의 심각도를 바꾸면 `OVERRIDES` 로 표시됩니다. 이후 부모가 그 규칙의 파라미터를 바꾸면 자식에 반영됩니까.

> 2개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 2개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 만든 시점에 얼어붙음

만든 시점의 규칙 목록에 멈춥니다. 상속을 걸면 새로 구현된 규칙, 규칙 설정 변경, 폐기된 규칙의 비활성화가 자동으로 따라오는데 상속이 없으면 이 갱신을 받지 못합니다.

업그레이드를 몇 번 지나면 그 프로파일은 최신 규칙을 하나도 모르는 상태가 됩니다. 실측에서는 빈 커스텀 프로파일에 부모를 `Sonar way` 로 지정하자 활성 규칙이 곧바로 537개가 됐습니다.

### 정답 2 — 재정의한 규칙은 자식 값을 지킴

반영되지 않습니다. 부모의 파라미터 변경은 자식이 그 규칙을 재정의하지 않았을 때만 반영됩니다.

반면 규칙의 활성·비활성은 다릅니다. 부모에서 규칙을 켜거나 끄면 자식에서의 상태와 무관하게 반영됩니다. 재정의가 지켜 주는 것은 심각도와 파라미터이지 존재 여부가 아닙니다.
