# Quality Gate

> Quality Gate 는 "이 프로젝트를 릴리스해도 되는가"라는 질문 하나에 답합니다. 조건 집합을 코드에 대고 재서 통과와 실패를 냅니다. 26.1 의 기본 게이트는 조건 네 개이고, 작은 변경에는 일부 조건을 건너뛰는 장치가 기본으로 켜져 있습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 게이트 조건이 무엇으로 구성되는지 세 요소를 댈 수 있습니다.
2. 내장 게이트 `Sonar way` 의 네 조건을 지표 이름으로 말할 수 있습니다.
3. 브랜치 분석과 Pull Request 분석에서 적용되는 조건이 어떻게 다른지 설명할 수 있습니다.
4. fudge factor 가 무엇을 언제 건너뛰는지, 왜 필요한지 판단할 수 있습니다.



## 1. 조건은 지표·연산자·기준값 셋으로 이뤄집니다

> 게이트는 분석에서 계산된 지표에 조건을 겁니다. 조건 하나라도 걸리면 게이트가 실패합니다.

Quality Gate 는 분석 중 계산된 지표에 대한 조건 집합입니다. 조건 하나하나는 새 코드 또는 전체 코드 중 한쪽에 적용되며, **조건 중 하나라도 충족되면 게이트가 실패합니다.**

조건 하나는 셋의 조합입니다.

- **지표**: 무엇을 재는가
- **비교 연산자**: 어떻게 재는가
- **기준값**: 어디서부터 실패인가

예를 들어 지표가 Blocker 이슈, 연산자가 초과, 기준값이 0 이면 "Blocker 이슈가 없어야 한다"가 됩니다.

쓸 수 있는 지표는 보안·유지보수성·신뢰성 이슈의 통계와 등급, 테스트 커버리지, 순환 복잡도와 인지 복잡도, 검토된 Security Hotspot 통계, 중복 줄과 블록, 코드 크기 통계입니다.

한 가지 예외가 있습니다. 테스트 코드의 품질도 게이트에 영향을 주지만 측정 범위가 좁습니다. MQR 모드에서는 유지보수성과 신뢰성 지표로만 재고, 중복과 보안 이슈는 테스트 코드에서 측정하지 않습니다.



## 2. Sonar way 의 네 조건

> 내장 게이트는 새 코드에만 조건을 겁니다. 실측한 네 조건이 Clean as You Code 를 그대로 구현합니다.

각 프로젝트에는 게이트가 하나씩 배정되고, 명시적으로 지정하지 않은 프로젝트에는 기본 게이트가 적용됩니다. 로컬 인스턴스에서 조회하면 이렇습니다.

| 게이트 | 내장 | 기본 | CaYC 준수 |
|---|---|---|---|
| `Sonar way` | 예 | 예 | `compliant` |

조건 네 개를 지표 이름 그대로 뽑으면 이렇습니다.

| 지표 | 연산자 | 기준값 | 뜻 |
|---|---|---|---|
| `new_violations` | `>` | 0 | 새 이슈가 없어야 합니다 |
| `new_security_hotspots_reviewed` | `<` | 100 | 새 Hotspot 이 모두 검토돼야 합니다 |
| `new_coverage` | `<` | 80 | 새 코드 커버리지가 80% 이상이어야 합니다 |
| `new_duplicated_lines_density` | `>` | 3 | 새 코드 중복이 3% 이하여야 합니다 |

지표 이름이 전부 `new_` 로 시작합니다. 전체 코드에 대한 조건이 하나도 없습니다. [01-03](01-03.Clean as You Code와 MQR.md) 에서 본 Clean as You Code 가 게이트 정의에 그대로 박혀 있는 것입니다. 오래된 코드베이스에 붙여도 첫날부터 실패하지 않는 이유가 여기 있습니다.

`Sonar way` 는 Sonar 가 제공하며 **읽기 전용**입니다. 기준을 바꾸려면 커스텀 게이트를 만듭니다.

새 이슈를 막는 조건은 두 가지 방식으로 표현할 수 있습니다. 이슈 수가 0을 넘으면 실패로 하거나, 신뢰성·보안·유지보수성 등급이 A 보다 나쁘면 실패로 하는 방식입니다. 등급 방식은 약간의 기술 부채가 새어 들어오는 것을 허용하므로, 새 코드를 완전히 깨끗하게 두려면 이슈 수 조건이 확실합니다.



## 3. 브랜치와 Pull Request 는 적용 범위가 다릅니다

> 브랜치는 전체 코드 조건까지 보고, Pull Request 는 새 코드 조건만 봅니다.

같은 프로젝트에는 같은 게이트 정의가 쓰이지만 계산 방식이 갈립니다.

**브랜치 분석**에서는 전체 코드 조건과 새 코드 조건이 모두 적용됩니다. 무엇이 새 코드인지는 그 브랜치에 적용되는 New Code 정의가 정합니다.

**Pull Request 분석**에서는 새 코드 조건만 적용됩니다. 여기서 새 코드는 대상 브랜치와 비교해 바뀐 코드입니다.

이 차이가 실무에서 혼선을 만듭니다. PR 에서는 통과했는데 병합 후 대상 브랜치 분석에서 실패하는 경우입니다. PR 이 보지 않던 전체 코드 조건이 병합 후에 적용되기 때문입니다. 커스텀 게이트에 전체 코드 조건을 넣었다면 이 현상을 예상해야 합니다.

`Sonar way` 를 그대로 쓰면 전체 코드 조건이 없으므로 이 문제가 생기지 않습니다.



## 4. 작은 변경에는 일부 조건을 건너뜁니다

> 새 줄이 20줄 미만이면 중복과 커버리지 조건을 적용하지 않습니다. 기본으로 켜져 있습니다.

한 줄짜리 수정에 커버리지 80% 를 요구하면 어떻게 될까요. 그 한 줄에 테스트가 없으면 커버리지는 0% 이고 게이트는 실패합니다. 오타 하나 고치는 PR 이 품질 기준 미달로 막히는 셈입니다.

이것을 막는 장치가 **fudge factor** 입니다. 동작은 둘입니다.

- 새 줄 수가 20 미만이면 **중복 조건을 무시합니다**
- 커버리지가 필요한 새 줄 수가 20 미만이면 **커버리지 조건을 무시합니다**

작은 변경에서 사소한 문제가 게이트 전체를 좌우하는 것을 피하려는 장치입니다.

로컬 인스턴스에서 설정 정의를 조회하면 키와 기본값이 나옵니다.

| 설정 키 | 기본값 | 이름 |
|---|---|---|
| `sonar.qualitygate.ignoreSmallChanges` | `true` | Ignore duplication and coverage on small changes |

전역 설정이며 모든 새 프로젝트에 적용됩니다. 프로젝트 관리자가 프로젝트 단위로 덮어쓸 수 있습니다.

한 가지 짚어둘 것이 있습니다. fudge factor 는 **중복과 커버리지에만** 적용됩니다. 새 이슈 조건과 Hotspot 검토 조건은 변경 크기와 무관하게 그대로 적용됩니다. 한 줄을 고쳤어도 그 한 줄에 이슈가 있으면 게이트는 실패합니다.



## 면접에서 받을 만한 질문

1. `Sonar way` 의 네 조건이 전부 새 코드 지표인 것이 왜 중요합니까.
2. 한 줄짜리 오타 수정 PR 이 커버리지 미달로 막히지 않는 이유는 무엇입니까. 이 장치의 적용 범위는 어디까지입니까.

> 2개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 2개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — Clean as You Code 가 게이트에 박힘

지표 이름이 전부 `new_` 로 시작하고 전체 코드 조건이 하나도 없습니다. `new_violations`, `new_security_hotspots_reviewed`, `new_coverage`, `new_duplicated_lines_density` 넷입니다.

오래된 코드베이스에 붙여도 첫날부터 실패하지 않는 이유가 여기 있습니다. 병합 후 동작에도 영향을 줍니다. 전체 코드 조건이 없으므로 PR 에서 통과한 코드가 병합 후 대상 브랜치 분석에서 갑자기 실패하는 일이 생기지 않습니다.

### 정답 2 — fudge factor 는 중복·커버리지에만

fudge factor 때문입니다. 새 줄 수가 20 미만이면 중복 조건을, 커버리지가 필요한 새 줄 수가 20 미만이면 커버리지 조건을 무시합니다. 설정 키는 `sonar.qualitygate.ignoreSmallChanges` 이고 기본값은 `true` 입니다.

적용 범위가 좁다는 점이 중요합니다. 이 장치는 중복과 커버리지에만 적용되고 새 이슈 조건과 Hotspot 검토 조건은 변경 크기와 무관하게 그대로 적용됩니다. 한 줄을 고쳤어도 그 줄에 이슈가 있으면 게이트는 실패합니다.
