# 인증과 토큰

> 토큰은 세 종류이고 접두어로 구분됩니다. CI 에 어떤 것을 주느냐가 곧 사고가 났을 때의 피해 범위를 정합니다. 만료일을 넣지 않으면 회전을 자동화할 수단도 사라집니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 토큰 세 종류를 대고 접두어로 구분할 수 있습니다.
2. CI 파이프라인에 어떤 토큰을 주는 것이 최소 권한인지 판단할 수 있습니다.
3. 만료일이 회전 자동화에 왜 필요한지 설명할 수 있습니다.
4. 토큰이 유출됐을 때 무엇을 할 수 있는지 말할 수 있습니다.



## 1. 세 종류가 접두어로 갈립니다

> User, Global Analysis, Project Analysis 셋입니다. 접두어를 보면 어느 종류인지 바로 알 수 있습니다.

로컬 인스턴스에서 세 종류를 각각 발급해 보면 접두어가 다릅니다.

| 종류 | 접두어 | 길이 | 할 수 있는 일 |
|---|---|---:|---|
| **User** | `squ_` | 44 | 그 사용자가 가진 모든 권한. API 조회·관리 포함 |
| **Global Analysis** | `sqa_` | 44 | 모든 프로젝트에 분석 결과 업로드 |
| **Project Analysis** | `sqp_` | 44 | 지정한 한 프로젝트에만 분석 결과 업로드 |

접두어가 있다는 사실 자체가 실무에서 쓸모 있습니다. 로그나 설정 파일에서 `sqp_` 로 시작하는 문자열을 발견하면 그것이 프로젝트 한정 분석 토큰임을 즉시 알 수 있습니다. 시크릿 스캐너에 패턴을 등록하기도 쉽습니다.

권한 범위가 넓은 순서는 User → Global Analysis → Project Analysis 입니다. User 토큰은 발급한 사람의 권한을 그대로 물려받으므로, 관리자가 만든 User 토큰이 유출되면 관리자 권한이 유출된 것과 같습니다.



## 2. CI 에는 가장 좁은 것을 줍니다

> 프로젝트 하나만 분석하는 파이프라인에는 Project Analysis Token 이 맞습니다.

파이프라인이 하는 일은 분석 결과를 올리는 것 하나입니다. 그 일에 필요한 최소 권한이 Project Analysis Token 입니다.

그런데 실무에서는 Global Analysis Token 을 쓰는 경우가 흔합니다. 이유가 있습니다. 프로젝트가 수십 개면 토큰도 수십 개가 되고, 새 프로젝트가 생길 때마다 토큰을 만들어 크레덴셜에 넣어야 합니다. 관리 비용이 실제로 듭니다.

판단 기준은 사고 시 피해 범위입니다.

- **Project Analysis Token**: 유출되면 그 프로젝트에 가짜 분석 결과를 올릴 수 있습니다
- **Global Analysis Token**: 유출되면 **모든 프로젝트**에 올릴 수 있습니다
- **User Token**: 유출되면 그 사용자가 할 수 있는 일을 전부 할 수 있습니다. 관리자 계정이면 설정 변경과 권한 부여까지 포함됩니다

CI 크레덴셜은 빌드 로그에 실수로 찍히거나, 포크된 저장소의 파이프라인에 노출되거나, 에이전트가 침해되면 새 나갑니다. 그 확률이 0 이 아니므로 범위를 좁혀 두는 편이 낫습니다.

**User 토큰을 CI 에 주는 것은 피합니다.** 분석에 필요 없는 권한이 딸려 오기 때문입니다. Web API 로 설정을 읽거나 바꾸는 스크립트가 따로 필요하다면 그 용도의 전용 계정을 만들어 필요한 권한만 부여하고, 그 계정의 User 토큰을 씁니다.



## 3. 만료일이 없으면 회전을 자동화할 수 없습니다

> 응답 헤더로 만료를 추적할 수 있는데, 그 헤더는 만료일이 있는 토큰에만 붙습니다.

[04-02](04-02.Web%20API%20구조.md) 에서 본 헤더가 여기서 의미를 갖습니다.

```bash
SonarQube-Authentication-Token-Expiration: 2026-09-20T00:00:00+0000
```

이 헤더가 있으면 외부 도구가 만료를 미리 감지해 회전할 수 있습니다. 그런데 실측하면 조건부입니다.

| 조건 | 헤더 |
|---|---|
| 인증이 필요한 엔드포인트 + 만료일이 있는 토큰 | 나옴 |
| 인증이 필요한 엔드포인트 + 만료일이 없는 토큰 | **안 나옴** |
| 익명으로도 되는 엔드포인트 | 안 나옴 |

만료일 없이 만든 토큰은 이 신호를 주지 않습니다. 회전 시점을 알 방법이 없으니 사람이 달력에 적어 두는 수밖에 없고, 그렇게 관리되는 토큰은 대개 잊힙니다.

토큰을 발급할 때 `expirationDate` 를 넣는 습관이 그래서 중요합니다.

```bash
curl -X POST -H "Authorization: Bearer <admin-token>" \
  -d "name=ci-pipeline&type=PROJECT_ANALYSIS_TOKEN&projectKey=demo-app&expirationDate=2026-09-20" \
  http://localhost:9000/api/user_tokens/generate
```

Enterprise Edition 부터는 시스템 차원에서 최대 수명을 강제할 수 있습니다. 관리자가 최대 수명을 정하면 이후 발급되는 토큰은 그 값과 사용자가 정한 값 중 **먼저 오는 쪽**에서 만료됩니다. 다만 이 설정은 기존 토큰에는 영향을 주지 않습니다. Community Build 에는 이 강제 장치가 없으므로 발급 절차 쪽에서 규율을 세워야 합니다.



## 4. 유출됐을 때 할 수 있는 일

> 폐기가 유일한 조치입니다. 토큰 값은 발급 시점에만 보이므로 사후에 확인할 수 없습니다.

토큰 값은 발급 응답에 한 번만 나옵니다. 이후에는 목록에서 이름과 종류와 생성일만 볼 수 있고 값은 볼 수 없습니다. 그래서 "이 토큰이 그 토큰인가"를 값으로 대조할 수 없습니다.

유출이 의심되면 이름으로 찾아 폐기합니다.

```bash
curl -X POST -H "Authorization: Bearer <admin-token>" \
  -d "name=ci-pipeline" \
  http://localhost:9000/api/user_tokens/revoke
```

시스템 관리자는 다른 사용자를 대신해 User 토큰을 발급할 수 있고, 어떤 토큰이든 폐기할 수 있습니다. 유출 대응에서 이 권한이 쓰입니다.

폐기 후에는 파이프라인 쪽 크레덴셜도 함께 갱신해야 합니다. 폐기만 하고 새 토큰을 넣지 않으면 다음 분석이 인증 실패로 떨어집니다. 순서를 지키려면 새 토큰을 먼저 만들어 크레덴셜을 갱신하고, 그다음에 옛 토큰을 폐기합니다.

토큰에 이름을 잘 붙이는 일이 여기서 값을 합니다. `token1` 같은 이름은 어느 파이프라인이 쓰는지 알 수 없어 폐기 결정을 못 내립니다. `jenkins-demo-app` 처럼 소비자와 대상을 담으면 유출 시 무엇을 갱신해야 하는지 바로 보입니다.



## 면접에서 받을 만한 질문

1. CI 파이프라인에 줄 토큰으로 세 종류 중 무엇을 고르겠습니까. 근거는 무엇입니까.
2. 토큰 만료를 자동으로 감지해 회전하는 구조를 만들려면 발급 단계에서 무엇을 해야 합니까.
3. 토큰이 유출된 것 같은데 어느 토큰인지 확실하지 않습니다. 값을 대조해 찾을 수 있습니까.

> 3개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 3개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 피해 범위로 고름

프로젝트 하나만 분석하는 파이프라인이면 Project Analysis Token(`sqp_`)이 최소 권한입니다.

근거는 유출 시 피해 범위입니다.

- Project Analysis Token(`sqp_`): 그 프로젝트에만 가짜 결과를 올릴 수 있습니다
- Global Analysis Token(`sqa_`): 모든 프로젝트에 올릴 수 있습니다
- User Token(`squ_`): 발급자의 권한을 그대로 물려받습니다. 관리자 토큰이면 설정 변경까지 가능합니다

다만 프로젝트가 수십 개면 토큰 관리 비용이 실제로 들어 Global 을 쓰는 선택도 있습니다. 그 경우에도 **User 토큰을 CI 에 주는 것은 피합니다.** 분석에 불필요한 권한이 딸려 오기 때문입니다.

### 정답 2 — 발급 시 expirationDate 를 넣음

`expirationDate` 를 넣어 발급해야 합니다. 그래야 API 응답에 `SonarQube-Authentication-Token-Expiration` 헤더가 붙어 외부 도구가 만료를 추적할 수 있습니다.

이 헤더는 조건부입니다. 만료일이 있는 토큰으로 인증이 필요한 엔드포인트를 호출할 때만 나옵니다. 만료일 없이 만든 토큰은 이 신호를 아예 주지 않아 회전 시점을 알 수단이 없습니다.

Enterprise Edition 이면 시스템 차원에서 최대 수명을 강제할 수 있지만 Community Build 에는 그 장치가 없으므로 발급 절차 쪽에서 규율을 세워야 합니다.

### 정답 3 — 값으로는 못 찾음

찾을 수 없습니다. 토큰 값은 발급 응답에 한 번만 나오고 이후에는 이름과 종류와 생성일만 조회됩니다.

그래서 이름 짓기가 사후 대응을 좌우합니다. `token1` 같은 이름은 어느 파이프라인이 쓰는지 알 수 없어 폐기 결정을 못 내립니다. `jenkins-demo-app` 처럼 소비자와 대상을 담아 두면 무엇을 갱신해야 하는지 바로 보입니다.

폐기 순서도 중요합니다. 새 토큰을 먼저 만들어 크레덴셜을 갱신한 뒤 옛 토큰을 폐기해야 다음 분석이 인증 실패로 떨어지지 않습니다.
