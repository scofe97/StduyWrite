# Webhook

> 웹훅은 서버가 CI 에게 "처리가 끝났다"고 알리는 유일한 경로입니다. 전달은 최선 노력이라 재시도가 없고, 페이로드에는 작업 상태와 게이트 판정이 다른 필드로 들어 있습니다. 이 구분을 놓치면 실패를 성공으로 읽습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 페이로드에서 작업 상태와 게이트 판정이 어떻게 다른 필드인지 설명할 수 있습니다.
2. 전달 실패의 판정 기준과 재시도 정책을 말할 수 있습니다.
3. HMAC 서명으로 페이로드를 검증하는 구조를 설명할 수 있습니다.
4. 전역 웹훅과 프로젝트 웹훅이 함께 있을 때 무엇이 실행되는지 판단할 수 있습니다.



## 1. 페이로드에는 두 개의 상태가 있습니다

> 최상위 `status` 는 분석 작업의 처리 결과이고, `qualityGate.status` 는 판정입니다. 둘은 독립적입니다.

로컬 인스턴스에서 실제 전달된 페이로드를 뜨면 구조가 이렇습니다.

```bash
serverUrl                              http://localhost:9000
taskId                                 0c71d532-1298-4a1e-a28f-dccc702ca792
status                                 SUCCESS
analysedAt                             2026-08-21T07:09:34+0000
project.key                            demo-app
project.url                            http://localhost:9000/dashboard?id=demo-app
branch.name                            main
branch.type                            BRANCH
branch.isMain                          true
qualityGate.name                       Sonar way
qualityGate.status                     ERROR
qualityGate.conditions[]               (4개)
properties.sonar.analysis.detectedscm  undetected
```

여기서 놓치기 쉬운 것이 최상위 `status` 와 `qualityGate.status` 의 차이입니다. 위 예시는 **작업은 성공했고 게이트는 실패한** 상태입니다.

- `status`: Compute Engine 이 리포트를 처리한 결과입니다. `SUCCESS` 는 계산이 끝났다는 뜻입니다
- `qualityGate.status`: 계산된 값으로 조건을 재서 나온 판정입니다

웹훅을 직접 받아 처리하는 코드를 짤 때 최상위 `status` 만 보고 성공으로 처리하면 게이트 실패를 놓칩니다. 반대로 `status` 가 `FAILED` 면 게이트 판정 자체가 없습니다. 계산이 안 끝났기 때문입니다.

`taskId` 가 [04-01](04-01.Jenkins%20연계.md) 에서 본 그 값입니다. `withSonarQubeEnv` 가 컨텍스트에 붙인 taskId 와 같은 값이라 Jenkins 가 "내가 기다리던 그 분석"임을 식별합니다.

`serverUrl` 과 `project.url` 은 서버에 설정된 기준 URL 을 씁니다. 실측 환경에서 Jenkins 는 `http://sq-server:9000` 으로 접속하지만 페이로드의 URL 은 `http://localhost:9000` 입니다. 사람이 클릭할 주소와 컨테이너가 통신할 주소가 다를 수 있다는 뜻이고, 이 값은 `sonar.core.serverBaseURL` 이 정합니다.

`properties` 에 담긴 `detectedscm` 과 `detectedci` 도 눈여겨볼 만합니다. 실측에서 둘 다 `undetected` 로 나왔는데, 작업 공간에 git 저장소 없이 파일만 복사해 분석했기 때문입니다. [01-02](01-02.서버%20구성%20요소와%20분석%20흐름.md) 에서 말한 SCM 메타데이터 부재가 여기에 그대로 드러납니다.



## 2. 전달은 최선 노력입니다

> 10초 안에 응답이 없으면 실패로 기록되고, 서버는 재시도하지 않습니다.

전달 정책이 세 줄로 정리됩니다.

- URL 이 **10초** 안에 응답하지 않으면 전달 실패로 표시됩니다
- SonarQube 는 **실패한 전달을 재시도하지 않습니다**
- 응답 기록은 **30일** 뒤 정리됩니다

재시도가 없다는 점이 설계에 영향을 줍니다. 웹훅을 받는 쪽이 잠깐 내려가 있으면 그 분석의 통보는 영영 오지 않습니다. 공식 문서는 자동 재전달이 필요하면 Web API 로 직접 구현하라고 안내합니다.

[04-01](04-01.Jenkins%20연계.md) 에서 본 `waitForQualityGate` 의 경쟁 상태 대비가 이 맥락에서 이해됩니다. 스텝이 시작하거나 재시작할 때 서버에 직접 한 번 물어봅니다. 웹훅을 놓쳤더라도 그때 이미 끝난 작업이면 결과를 얻을 수 있습니다. 다만 이것은 스텝이 시작하는 시점의 한 번뿐이라, 기다리는 동안 도착해야 할 웹훅이 유실되면 타임아웃까지 갑니다.

전달 이력은 API 로 조회합니다. 실측에서 분석 세 번에 전달 세 건이 남았습니다.

| 시각 | 성공 | HTTP | 소요 |
|---|---|---|---|
| 07:11:21 | true | 200 | 322ms |
| 07:06:58 | true | 200 | 201ms |
| 07:04:25 | true | 200 | 332ms |

`api/webhooks/deliveries` 로 목록을, `api/webhooks/delivery` 로 개별 페이로드를 봅니다. 전달이 아예 없으면 웹훅 미등록이고, 있는데 실패면 URL 이나 네트워크 문제입니다. 이 둘을 구분하는 것이 [04-01](04-01.Jenkins%20연계.md) 에서 본 "파이프라인이 멈춘다" 증상의 진단 첫 단계입니다.



## 3. 서명으로 발신자를 확인합니다

> 시크릿을 설정하면 페이로드마다 HMAC-SHA256 서명이 헤더로 붙습니다.

웹훅을 받는 서버는 그 요청이 정말 SonarQube 에서 온 것인지 알아야 합니다. 주소만 알면 누구나 가짜 요청을 보낼 수 있기 때문입니다.

시크릿을 설정하면 서버가 요청 본문의 HMAC 서명을 계산해 헤더에 담습니다.

```bash
X-Sonar-Webhook-HMAC-SHA256: <소문자 16진수 digest>
```

받는 쪽은 같은 시크릿으로 본문의 HMAC 을 계산해 헤더 값과 비교합니다. 일치하면 SonarQube 가 보낸 것입니다.

Jenkins 는 이것을 설정으로 지원합니다. 전역으로는 SonarQube 서버 설정의 Advanced 에 Webhook Secret 을 등록하고, 프로젝트 단위로 덮어쓰려면 스텝에 넘깁니다.

```bash
waitForQualityGate(webhookSecretId: 'yourSecretID')
```

기본 인증도 지원합니다. 웹훅 URL 에 `https://myLogin:myPassword@my_server/foo` 형태로 자격 증명을 담는 방식입니다. 다만 URL 에 비밀번호가 들어가므로 로그 노출 위험이 있어 HMAC 쪽이 낫습니다.



## 4. 전역과 프로젝트 웹훅은 함께 실행됩니다

> 프로젝트 웹훅이 전역 웹훅을 대체하지 않습니다. 양쪽 모두 실행됩니다.

이 규칙이 직관과 어긋나 사고를 만듭니다. 보통 설정은 좁은 범위가 넓은 범위를 덮는데 웹훅은 그렇지 않습니다.

- 전역 수준에는 최대 **10개**까지 등록할 수 있습니다
- 전역 웹훅은 프로젝트 웹훅으로 **대체되지 않습니다**
- 양쪽 수준의 **모든 웹훅이 실행됩니다**

그래서 전역에 Jenkins 웹훅을 걸어 둔 상태에서 프로젝트에 또 걸면 같은 통보가 두 번 갑니다. 받는 쪽이 멱등하지 않으면 중복 처리가 일어납니다.

[04-01](04-01.Jenkins%20연계.md) 의 문서도 이 점을 활용합니다. 프로젝트마다 웹훅을 만들 필요 없이 전역에 하나만 두면 모든 프로젝트의 분석이 Jenkins 로 통보됩니다. 프로젝트 수가 많을 때 관리 비용이 줄어드는 대신, 관계없는 프로젝트의 통보까지 받게 되므로 받는 쪽에서 `project.key` 로 걸러야 합니다.



## 면접에서 받을 만한 질문

1. 웹훅 페이로드의 최상위 `status` 가 `SUCCESS` 입니다. 게이트를 통과했다고 봐도 됩니까.
2. 웹훅을 받는 서버가 배포 중이라 1분간 응답하지 못했습니다. 그동안의 통보는 어떻게 됩니까.
3. 전역에 Jenkins 웹훅이 있는데 프로젝트에도 같은 URL 로 하나 더 걸면 어떻게 됩니까.

> 3개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 3개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 두 상태는 독립적임

아닙니다. 최상위 `status` 는 Compute Engine 이 리포트를 처리한 결과이고, 판정은 `qualityGate.status` 라는 별도 필드에 있습니다.

실측 페이로드가 정확히 그 조합이었습니다. `status` 는 `SUCCESS` 인데 `qualityGate.status` 는 `ERROR` 였습니다. 계산은 정상적으로 끝났고 그 결과가 조건을 어긴 상태입니다.

웹훅을 직접 받아 처리한다면 두 필드를 다 봐야 합니다. `status` 가 `FAILED` 면 계산 자체가 안 끝난 것이라 게이트 판정이 아예 없습니다.

### 정답 2 — 유실되고 재시도는 없음

그 통보는 영영 오지 않습니다. URL 이 10초 안에 응답하지 않으면 전달 실패로 기록되고, **SonarQube 는 재시도하지 않습니다.**

자동 재전달이 필요하면 Web API 로 직접 구현해야 한다고 공식 문서가 안내합니다. 전달 이력은 `api/webhooks/deliveries` 로 조회할 수 있고 기록은 30일 뒤 정리됩니다.

Jenkins 의 `waitForQualityGate` 는 스텝이 시작하거나 재시작할 때 서버에 한 번 직접 물어보는 대비를 갖고 있습니다. 다만 그 한 번뿐이라 기다리는 동안 유실되면 타임아웃까지 갑니다.

### 정답 3 — 두 번 갑니다

같은 통보가 두 번 전달됩니다. 프로젝트 웹훅이 전역 웹훅을 대체하지 않고 **양쪽 모두 실행되기** 때문입니다.

일반적인 설정은 좁은 범위가 넓은 범위를 덮지만 웹훅은 그렇지 않습니다. 받는 쪽이 멱등하지 않으면 중복 처리가 일어납니다.

전역에 하나만 두는 편이 관리에 유리합니다. 프로젝트마다 만들 필요가 없어지는 대신 관계없는 프로젝트의 통보까지 오므로 받는 쪽에서 `project.key` 로 걸러야 합니다.
