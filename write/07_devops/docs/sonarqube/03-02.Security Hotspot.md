# Security Hotspot

> Hotspot 은 고쳐야 할 결함이 아니라 사람이 봐야 할 자리입니다. 도구가 위험 여부를 단정할 수 없는 코드를 표시해 두는 장치이고, 그래서 이슈와 다른 상태와 다른 우선순위 체계를 갖습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. Hotspot 과 보안 이슈의 차이를 한 문장으로 설명할 수 있습니다.
2. Hotspot 의 네 가지 상태를 대고 각각이 무엇을 뜻하는지 말할 수 있습니다.
3. 검토 우선순위가 무엇을 근거로 매겨지는지 설명할 수 있습니다.
4. 모드에 따라 화면 용어가 어떻게 달라지는지 판단할 수 있습니다.



## 1. 검토가 필요하냐가 갈림길입니다

> 보안 이슈는 이미 문제가 확인된 것이고 Hotspot 은 위험할 수도 있는 코드입니다. 차이는 고치기 전에 사람의 판단이 필요한지입니다.

둘의 차이를 공식 문서는 **검토의 필요성**으로 정의합니다.

- **Security Hotspot**: 보안에 민감한 코드가 표시되지만 애플리케이션 전체 보안에는 영향이 없을 수도 있습니다. 고칠 필요가 있는지는 개발자가 코드를 검토해 판단합니다
- **보안 이슈**: 애플리케이션 보안에 영향을 주는 문제가 발견된 것이고 즉시 고쳐야 합니다

문서가 드는 예가 이해를 돕습니다. 쿠키에 secure 플래그를 권고하는 규칙이 있습니다. 이 규칙이 걸린 코드에 검토가 필요한 이유는 둘입니다. 중간자 공격을 막는 주된 보호 장치는 HTTPS 이고 secure 플래그는 네트워크 보안이 실패했을 때를 위한 추가 보호일 뿐입니다. 게다가 그 쿠키가 추적용이라 HTTPS 가 아닌 사이트에도 보내도록 **의도된** 것일 수 있습니다.

같은 코드가 어떤 서비스에서는 문제이고 다른 서비스에서는 설계입니다. 도구는 그 차이를 모릅니다.

이 관점은 심층 방어(Defense in depth)와 이어집니다. 보호 계층을 여러 겹 두어 공격을 받아도 견디게 만드는 발상입니다. Hotspot 을 고칠수록 그 겹이 두꺼워집니다.

[01-01](01-01.정적%20분석이%20푸는%20결함.md) 에서 센 대로 Java 규칙 695개 중 `SECURITY_HOTSPOT` 타입은 39개이고, 이 39개는 소프트웨어 품질 영향이 하나도 매겨져 있지 않은 규칙과 정확히 일치했습니다. 판정 전에는 영향을 정할 수 없기 때문입니다.



## 2. 네 가지 상태

> To review 로 시작해 Acknowledged·Fixed·Safe 중 하나로 갑니다. 이슈의 상태와 겹치지 않습니다.

Hotspot 은 전용 라이프사이클을 갖습니다.

- **To review**: 새 Hotspot 의 기본 상태입니다. 보고됐고 확인이 필요합니다
- **Acknowledged**: 검토는 했고 조치가 진행 중이거나 다음 단계를 정하는 중입니다
- **Fixed**: 검토 후 수정을 적용했습니다
- **Safe**: 검토 후 변경이 필요 없다고 판단했습니다. 더 적절한 다른 보호 장치가 이미 있는 경우입니다

Acknowledged 가 있다는 점이 이슈와 다릅니다. 이슈에는 "봤고 판단은 보류"에 해당하는 상태가 없습니다. Hotspot 은 검토 자체가 목적이라 그 중간 단계를 상태로 인정합니다.

[02-04](02-04.Quality%20Gate.md) 에서 본 `Sonar way` 의 조건 하나가 여기 걸립니다. `new_security_hotspots_reviewed` 가 100 미만이면 게이트가 실패합니다. 즉 **새 코드의 Hotspot 은 전부 검토를 마쳐야** 통과합니다. 고치라는 것이 아니라 판단하라는 요구입니다. Safe 로 판정해도 검토는 끝난 것이므로 게이트는 통과합니다.



## 3. 우선순위는 표준이 정합니다

> 검토 우선순위는 규칙이 속한 보안 카테고리로 정해지고, 그 카테고리의 순위는 OWASP Top 10 과 CWE Top 25 를 따릅니다.

Hotspot 이 검출되면 검토 우선순위에 따라 높은 것부터 목록에 놓입니다. 우선순위가 높은 것이 실제로 보안 조치가 필요한 코드일 가능성이 큽니다.

우선순위는 각 보안 규칙의 **보안 카테고리**로 정해집니다. OWASP Top 10 과 CWE Top 25 에서 높은 순위에 있는 카테고리의 규칙은 높은 우선순위를 받고, 그 목록에 없거나 낮은 순위인 카테고리는 Medium 이나 Low 가 됩니다.

근거가 외부 표준이라는 점이 실무에서 유용합니다. "왜 이걸 먼저 봐야 하느냐"는 질문에 도구의 판단이 아니라 업계 표준을 댈 수 있습니다.

검토할 때 볼 것은 셋입니다.

- **위험 이해**: 언제 왜 조치가 필요한지 판단합니다
- **보호 장치 확인**: 어떤 장치가 이미 있고 무엇이 빠졌는지 봅니다
- **영향 판단**: 전체 보안에 미치는 영향을 기준으로 조치를 정합니다

권장 보안 코딩 관행이 Hotspot 페이지에 함께 표시됩니다.



## 4. 모드에 따라 용어가 바뀝니다

> 같은 대상을 Standard Experience 는 Security Vulnerability 로, MQR 모드는 Security 로 부릅니다.

인스턴스 설정에 따라 화면에 다른 용어가 나옵니다.

| 대상 | Standard Experience | MQR 모드 |
|---|---|---|
| 보안 이슈 | Security Vulnerability | Security |
| 검토 대상 | Security Hotspot | Security Hotspot |

Hotspot 은 두 모드에서 이름이 같지만 보안 이슈 쪽은 다릅니다. [01-03](01-03.Clean%20as%20You%20Code와%20MQR.md) 에서 본 심각도 어휘 차이와 같은 성질의 문제입니다. 사내 문서나 대시보드가 "Vulnerability 0건" 같은 문구를 쓰고 있다면 모드를 바꿀 때 그 문구가 가리키는 대상이 사라집니다.

[01-01](01-01.정적%20분석이%20푸는%20결함.md) 의 실측 표를 다시 보면 이 관계가 숫자로 드러납니다. Standard 의 `VULNERABILITY` 는 32개이고 MQR 의 보안 품질에 연결된 규칙은 38개입니다. 이름만 바뀐 것이 아니라 세는 방식이 달라 숫자도 어긋납니다.



## 면접에서 받을 만한 질문

1. 같은 코드에 걸린 규칙인데 어떤 프로젝트에서는 고쳐야 하고 어떤 프로젝트에서는 두어도 됩니다. SonarQube 는 이런 규칙을 어떻게 취급합니까.
2. `Sonar way` 게이트를 통과하려면 새 코드의 Hotspot 을 전부 고쳐야 합니까.
3. Hotspot 의 검토 우선순위는 무엇을 근거로 매겨집니까.

> 3개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 3개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 이슈가 아니라 Hotspot 으로 표시

Security Hotspot 으로 표시합니다. 보안에 민감하지만 애플리케이션 전체 보안에 영향이 있는지는 맥락에 달린 코드이기 때문입니다.

쿠키 secure 플래그가 예입니다. HTTPS 가 주된 보호 장치라 이 플래그는 추가 보호일 뿐이고, 추적용 쿠키라면 HTTPS 가 아닌 곳에도 보내도록 의도된 것일 수 있습니다. 도구는 그 의도를 모르므로 "고쳐야 할 결함"이라 단정하지 않고 "사람이 볼 자리"로 넘깁니다.

그래서 Hotspot 규칙에는 소프트웨어 품질 영향이 매겨져 있지 않습니다. 영향은 사람이 판정한 뒤에야 정해집니다.

### 정답 2 — 고치는 것이 아니라 검토하는 것

아닙니다. 조건은 `new_security_hotspots_reviewed` 가 100% 미만이면 실패입니다. 요구하는 것은 수정이 아니라 **검토 완료**입니다.

검토 후 Safe 로 판정해도 검토는 끝난 것이므로 게이트는 통과합니다. 더 적절한 다른 보호 장치가 이미 있다고 판단한 경우가 여기 해당합니다. 통과하지 못하는 것은 To review 로 남아 있는 Hotspot 이 있을 때입니다.

### 정답 3 — OWASP Top 10 과 CWE Top 25

각 보안 규칙이 속한 보안 카테고리로 정해집니다. 그 카테고리가 OWASP Top 10 과 CWE Top 25 에서 높은 순위이면 높은 우선순위를 받고, 목록에 없거나 낮은 순위이면 Medium 이나 Low 가 됩니다.

근거가 도구 내부 판단이 아니라 외부 표준이라는 점이 실무에서 쓸모 있습니다. 검토 순서를 정할 때 업계 표준을 근거로 댈 수 있습니다.
