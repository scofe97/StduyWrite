# 분석 한 번의 흐름

> 스캐너를 실행하면 분석이 끝난 것이 아닙니다. 스캐너는 리포트를 올리고 빠지며, 실제 계산은 서버의 Compute Engine 이 큐에서 꺼내 처리합니다. 이 비동기 경계를 모르면 "분석은 성공했는데 결과가 안 보인다"는 상황을 해석하지 못합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 스캐너가 끝나는 시점과 결과가 보이는 시점이 왜 다른지 설명할 수 있습니다.
2. 분석 파라미터가 어디에 적히고 무엇이 무엇을 덮는지 순서를 댈 수 있습니다.
3. 배경 작업이 밀렸을 때 무엇을 확인해야 하는지 말할 수 있습니다.
4. 스캐너 캐시가 첫 분석과 이후 분석의 시간을 어떻게 가르는지 설명할 수 있습니다.



## 1. 스캐너가 끝나도 분석은 안 끝났습니다

> 스캐너는 리포트를 서버에 올리고 종료합니다. 계산은 그다음에 서버에서 비동기로 일어납니다.

[01-02](01-02.서버 구성 요소와 분석 흐름.md) 에서 봤듯 데이터베이스에는 리포트 작업 큐가 있습니다. 스캐너가 채우고 Compute Engine 이 꺼내 씁니다. 이 구조가 뜻하는 바가 있습니다.

스캐너 프로세스가 성공으로 끝났다는 것은 **리포트 업로드까지 성공했다**는 뜻이지 결과가 반영됐다는 뜻이 아닙니다. 업로드 직후 프로젝트 페이지를 열면 이전 분석 결과가 그대로 보입니다. Compute Engine 이 큐에서 그 리포트를 꺼내 처리를 마쳐야 새 결과가 나타납니다.

이 시차가 실무에서 두 가지 오해를 만듭니다.

하나는 "분석이 성공했는데 Quality Gate 가 이전 값"이라는 상황입니다. 파이프라인이 스캐너 종료 직후 곧바로 게이트를 조회하면 아직 계산 전 값을 읽습니다. 그래서 Jenkins 통합에는 대기 장치가 따로 있습니다. 이 부분은 4장에서 다룹니다.

다른 하나는 "스캐너 로그에는 에러가 없는데 결과가 안 보인다"는 상황입니다. 이때 봐야 할 곳은 스캐너 로그가 아니라 서버의 배경 작업 목록입니다.



## 2. 배경 작업으로 실패를 확인합니다

> Compute Engine 의 처리 결과는 `api/ce` 로 조회합니다. 스캐너가 성공해도 여기서 실패할 수 있습니다.

서버는 Compute Engine 작업을 조회하는 엔드포인트를 제공합니다. 로컬 인스턴스에서 세어 보면 `api/ce` 네임스페이스에 액션이 4개 있습니다.

| 액션 | 쓰임 |
|---|---|
| `activity` | 최근 작업 목록. 실패한 작업을 여기서 찾습니다 |
| `activity_status` | 대기·처리 중·실패 건수 요약 |
| `component` | 특정 프로젝트의 현재·최근 작업 |
| `task` | 작업 하나의 상세. 스캐너 로그가 아닌 서버 쪽 실패 사유가 여기 있습니다 |

작업 상태는 대기(`PENDING`), 처리 중(`IN_PROGRESS`), 성공(`SUCCESS`), 실패(`FAILED`)로 옮겨 갑니다. `activity_status` 의 대기 건수가 계속 쌓이면 Compute Engine 이 유입 속도를 못 따라가는 것이고, 이때는 워커 수나 서버 자원을 봅니다.

스캐너는 성공했는데 배경 작업이 실패하는 경우가 있습니다. 리포트 자체는 올라갔지만 서버가 처리하다 실패한 상황입니다. 같은 프로젝트 키를 다른 브랜치 설정으로 올렸거나, 참조하는 Quality Profile 이 사라졌거나, 데이터베이스 제약을 건드린 경우입니다. 이 사유는 스캐너 로그 어디에도 없습니다.



## 3. 파라미터는 여러 곳에 적히고 순서대로 덮입니다

> 같은 설정을 여러 곳에 적을 수 있습니다. 무엇이 무엇을 이기는지 모르면 "분명히 설정했는데 안 먹는다"가 됩니다.

분석 파라미터는 한 곳에만 적는 것이 아닙니다. 서버 UI 의 전역 설정, 프로젝트 설정, 프로젝트 루트의 `sonar-project.properties`, 빌드 스크립트, 그리고 스캐너 명령의 커맨드라인 인자까지 여러 층이 있습니다.[^params]

우선순위는 **분석 시점에 가까운 쪽이 이깁니다.** 커맨드라인 인자가 가장 강하고, 서버 UI 의 전역 설정이 가장 약합니다. 그래서 CI 에서 `-Dsonar.projectKey=...` 로 넘긴 값은 파일에 무엇이 적혀 있든 그것을 덮습니다.

여기서 흔한 사고가 나옵니다. 서버 UI 에서 제외 경로를 설정했는데 적용되지 않는 경우, 대개는 파이프라인이 같은 키를 커맨드라인으로 다시 넘기고 있습니다. UI 만 보면 원인을 못 찾습니다.

일부 파라미터는 아예 UI 에서 설정할 수 없습니다. `sonar.projectVersion` 처럼 분석마다 값이 달라져야 하는 것들입니다. 이것은 [01-03](01-03.Clean as You Code와 MQR.md) 에서 본 Previous version 기준의 New Code 판정과 직결됩니다. 버전을 안 넘기면 새 코드 구간이 갱신되지 않습니다.



## 4. 첫 분석이 느린 이유

> 스캐너는 엔진과 분석기를 캐시에 둡니다. 캐시가 비면 매번 내려받습니다.

[01-02](01-02.서버 구성 요소와 분석 흐름.md) 4절에서 스캐너가 엔진과 언어 분석기를 분석 시점에 내려받는다고 했습니다. 받은 것은 스캐너 캐시에 저장되고, 다음 분석은 캐시를 먼저 확인합니다.

문제는 캐시가 유지되지 않는 환경입니다. 매 빌드마다 새 컨테이너를 띄우는 파이프라인이 그렇습니다. 컨테이너가 사라지면 캐시도 사라지므로 모든 분석이 "첫 분석"이 됩니다. 엔진과 분석기를 매번 받는 시간이 그대로 빌드 시간에 얹힙니다.

해결은 캐시 디렉터리를 빌드 사이에 살려 두는 것입니다. Jenkins 라면 워크스페이스 밖의 고정 경로에 두거나 볼륨으로 마운트합니다. Kubernetes 에이전트라면 PVC 를 붙입니다.

받는 양은 프로젝트가 쓰는 언어에 달렸습니다. 스캐너 엔진이 코드를 훑어 언어를 식별한 뒤 필요한 분석기만 받기 때문에, 단일 언어 프로젝트는 다언어 프로젝트보다 적게 받습니다.

## 면접에서 받을 만한 질문

1. 스캐너가 성공으로 끝났는데 프로젝트 페이지에 이전 결과가 보입니다. 무엇을 의심하고 어디를 봅니까.
2. 서버 UI 에서 제외 경로를 설정했는데 적용되지 않습니다. 왜입니까.
3. 매 빌드마다 새 컨테이너를 띄우는 파이프라인이 느립니다. 스캐너 쪽 원인은 무엇입니까.

> 3개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 3개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 업로드 성공과 처리 완료는 다름

스캐너 성공은 리포트 업로드까지 성공했다는 뜻이지 결과가 반영됐다는 뜻이 아닙니다. Compute Engine 이 큐에서 그 리포트를 꺼내 처리를 마쳐야 새 결과가 나타납니다.

확인할 곳은 스캐너 로그가 아니라 서버의 배경 작업입니다. `api/ce` 의 `activity` 로 실패한 작업을 찾고 `task` 로 실패 사유를 봅니다. 서버 쪽 실패 사유는 스캐너 로그 어디에도 없습니다.

### 정답 2 — 분석 시점에 가까운 쪽이 이김

분석 파라미터는 여러 층에 적힐 수 있고 분석 시점에 가까운 쪽이 이깁니다. 커맨드라인 인자가 가장 강하고 서버 UI 의 전역 설정이 가장 약합니다.

파이프라인이 같은 키를 커맨드라인으로 다시 넘기고 있다면 UI 설정은 덮입니다. UI 만 보고 있으면 원인을 찾지 못합니다.

### 정답 3 — 캐시가 매번 비워짐

스캐너는 엔진과 언어 분석기를 분석 시점에 서버에서 받아 캐시에 둡니다. 컨테이너가 사라지면 캐시도 사라지므로 모든 분석이 첫 분석이 되고 받는 시간이 매번 빌드 시간에 얹힙니다.

캐시 디렉터리를 빌드 사이에 살려 두면 줄어듭니다. Jenkins 라면 워크스페이스 밖 고정 경로나 볼륨, Kubernetes 에이전트라면 PVC 를 씁니다.
