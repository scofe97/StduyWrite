# Coverage와 Duplication

> 커버리지는 SonarQube 가 재는 것이 아니라 외부 도구가 만든 리포트를 읽어 들이는 값입니다. 중복은 반대로 SonarQube 가 직접 탐지하며, 언어에 따라 임계가 다릅니다. 둘 다 Quality Gate 조건이므로 계산 방식을 알아야 숫자를 해석할 수 있습니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. `coverage` 와 `line_coverage` 와 `branch_coverage` 가 무엇을 다르게 재는지 설명할 수 있습니다.
2. 커버리지 값이 0 으로 나올 때 어디를 봐야 하는지 판단할 수 있습니다.
3. 중복으로 판정되는 임계가 Java 와 다른 언어에서 어떻게 다른지 댈 수 있습니다.
4. 중복 탐지가 무엇을 무시하는지, 지원하지 않는 언어가 무엇인지 말할 수 있습니다.



## 1. 커버리지 지표는 셋입니다

> 줄만 보는 값, 조건만 보는 값, 둘을 섞은 값이 따로 있습니다. Quality Gate 가 쓰는 것은 섞은 값입니다.

로컬 인스턴스에서 지표를 세면 전체 149개 중 Coverage 도메인이 21개입니다. 이 중 핵심은 셋입니다.

**Line coverage** 는 한 줄이 테스트 중에 실행됐는지만 봅니다.

```bash
line_coverage = LC / EL
# LC = 커버된 줄 = lines_to_cover - uncovered_lines
# EL = 실행 가능한 줄 수 (lines_to_cover)
```

**Condition coverage** 는 불리언 식이 있는 줄에서 각 조건이 참과 거짓 **양쪽으로** 평가됐는지 봅니다.

```bash
branch_coverage = (CT + CF) / (2 * B)
# CT = 한 번이라도 참으로 평가된 조건 수
# CF = 한 번이라도 거짓으로 평가된 조건 수
# B  = 전체 조건 수
```

**Coverage** 는 둘을 섞은 값이고, Quality Gate 의 `new_coverage` 가 쓰는 것이 이 계열입니다.

```bash
coverage = (CT + LC) / (B + EL)
```

분모는 조건 수와 실행 가능한 줄 수를 더한 것이고 분자는 참으로 평가된 조건 수와 커버된 줄 수를 더한 것입니다.

빈 줄과 주석만 있는 줄은 `lines_to_cover` 에 들어가지 않습니다. 이 지표는 "무엇이 가능한가"를 세는 것이지 "무엇이 남았는가"를 세는 것이 아닙니다. 남은 것은 `uncovered_lines` 가 셉니다.



## 2. 커버리지는 SonarQube 가 재지 않습니다

> 값은 외부 테스트 도구가 만든 리포트에서 옵니다. 0 으로 나오면 대개 리포트가 안 넘어간 것입니다.

여기서 자주 어긋나는 지점이 있습니다. SonarQube 는 테스트를 실행하지 않습니다. JaCoCo 같은 커버리지 도구가 만든 리포트를 분석 시점에 읽어 들일 뿐입니다.

따라서 커버리지가 0% 로 나올 때 의심할 순서가 정해집니다.

1. 테스트가 실제로 돌았는가
2. 커버리지 리포트 파일이 생성됐는가
3. 그 파일 경로를 스캐너가 알고 있는가

세 번째가 가장 흔한 원인입니다.

[02-02](02-02.분석%20한%20번의%20흐름.md) 3절에서 본 파라미터 우선순위가 여기서 걸립니다. 리포트 경로를 서버 UI 에 설정했는데 파이프라인이 같은 키를 커맨드라인으로 덮고 있으면 경로가 어긋납니다.

빌드 순서도 중요합니다. 테스트가 리포트를 만든 **뒤에** 스캐너가 돌아야 합니다. 순서가 뒤집히면 스캐너는 이전 빌드의 리포트를 읽거나 아무것도 못 읽습니다.

[02-04](02-04.Quality%20Gate.md) 4절의 fudge factor 를 여기서 다시 짚어둘 만합니다. 커버리지가 필요한 새 줄이 20 미만이면 커버리지 조건이 무시됩니다. 작은 PR 이 커버리지 0% 인데도 통과하는 것은 리포트가 잘 넘어갔다는 뜻이 아닐 수 있습니다.

테스트 코드 자체의 품질도 게이트에 반영되지만 범위가 좁습니다. MQR 모드에서는 유지보수성과 신뢰성 지표로만 재고, **중복과 보안 이슈는 테스트 코드에서 측정하지 않습니다.**



## 3. 중복 임계는 언어에 따라 다릅니다

> Java 는 문장 10개, 다른 언어는 토큰 100개 이상이 기준입니다. 세는 단위 자체가 다릅니다.

중복은 SonarQube 가 직접 탐지합니다. 블록 하나가 중복으로 판정되는 기준이 언어에 따라 갈립니다.

| 대상 | 기준 |
|---|---|
| **Java** | 연속된 중복 **문장 10개** 이상. 토큰 수와 줄 수는 보지 않습니다 |
| 그 밖의 언어 | 연속된 중복 **토큰 100개** 이상이고, 아래 줄 수 이상에 걸쳐 있을 것 |
| — COBOL | 30줄 |
| — ABAP | 20줄 |
| — 나머지 | 10줄 |

Java 만 문장 단위로 세는 것이 눈에 띕니다. 다른 언어는 토큰과 줄 수를 함께 보는데 Java 는 문장 수 하나만 봅니다. 그래서 같은 양의 중복이라도 언어에 따라 판정이 갈릴 수 있습니다.

탐지할 때 **들여쓰기 차이와 문자열 리터럴 차이는 무시합니다.** 같은 구조를 복사해 문자열만 바꾼 코드도 중복으로 잡힌다는 뜻입니다. 테스트 코드에서 같은 골격을 반복하며 기대값만 바꾸는 패턴이 중복으로 걸리는 이유가 여기 있습니다.

지원하지 않는 언어도 있습니다. Terraform 같은 IaC 계열과 CSS 는 중복 탐지가 되지 않습니다. 이 언어들로만 이뤄진 프로젝트는 중복 지표가 비어 있습니다.



## 4. 밀도로 재기 때문에 분모가 중요합니다

> 중복 조건은 개수가 아니라 비율입니다. 코드가 늘면 같은 중복이라도 밀도는 떨어집니다.

Quality Gate 가 쓰는 `new_duplicated_lines_density` 는 비율입니다.

```bash
duplicated_lines_density = duplicated_lines / lines * 100
```

분자는 중복에 관여한 줄 수이고 분모는 전체 줄 수입니다. 이 성질 때문에 같은 중복 코드가 있어도 프로젝트가 커지면 밀도가 내려갑니다. 반대로 작은 변경에서는 몇 줄만 중복돼도 밀도가 크게 튑니다.

이것이 [02-04](02-04.Quality%20Gate.md) 의 fudge factor 가 중복 조건도 함께 건너뛰는 이유입니다. 새 줄이 20 미만일 때 중복 조건을 무시하지 않으면, 세 줄짜리 변경에서 두 줄이 기존 코드와 같기만 해도 밀도가 66% 가 되어 3% 기준을 훌쩍 넘습니다.

관련 지표도 함께 봅니다. `duplicated_lines` 는 중복에 관여한 줄 수, `duplicated_blocks` 는 중복 블록 수, `duplicated_files` 는 중복이 있는 파일 수입니다. 밀도만 보면 어디가 문제인지 모르므로 블록 수와 파일 수를 함께 보는 편이 실제 조치에 가깝습니다.



## 면접에서 받을 만한 질문

1. 테스트를 분명히 돌렸는데 SonarQube 의 커버리지가 0% 입니다. 어떤 순서로 확인하겠습니까.
2. `coverage` 와 `branch_coverage` 는 무엇을 다르게 셉니까.
3. 세 줄짜리 PR 인데 두 줄이 기존 코드와 같습니다. 중복 밀도 조건에 걸립니까.

> 3개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 3개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — SonarQube 는 테스트를 돌리지 않음

커버리지 값은 SonarQube 가 재는 것이 아니라 JaCoCo 같은 외부 도구가 만든 리포트를 읽어 들인 것입니다. 그래서 확인 순서가 정해집니다.

먼저 테스트가 실제로 실행됐는지 봅니다. 다음으로 커버리지 리포트 파일이 생성됐는지 확인합니다. 마지막으로 그 파일 경로를 스캐너가 알고 있는지 봅니다. 세 번째가 가장 흔한 원인입니다.

빌드 순서도 봐야 합니다. 테스트가 리포트를 만든 뒤에 스캐너가 돌아야 하며, 순서가 뒤집히면 이전 빌드의 리포트를 읽거나 아무것도 못 읽습니다. 파라미터를 UI 와 커맨드라인 양쪽에 적어 두었다면 커맨드라인이 이깁니다.

### 정답 2 — 조건을 양쪽으로 보느냐

`branch_coverage` 는 불리언 식의 각 조건이 참과 **거짓 양쪽으로** 평가됐는지를 봅니다. `(CT + CF) / (2 * B)` 로, 분모에 2를 곱하는 이유가 조건 하나마다 참·거짓 두 경우를 세기 때문입니다.

`coverage` 는 줄과 조건을 섞은 값입니다. `(CT + LC) / (B + EL)` 로 계산하며 Quality Gate 의 `new_coverage` 가 이 계열입니다. `line_coverage` 는 조건을 보지 않고 줄이 실행됐는지만 봅니다.

세 값이 다르게 나오는 것이 정상입니다. 조건 분기가 많은 코드일수록 `line_coverage` 는 높고 `branch_coverage` 는 낮게 나옵니다.

### 정답 3 — fudge factor 가 막아 줌

걸리지 않습니다. 새 줄 수가 20 미만이면 중복 조건이 무시되기 때문입니다.

이 장치가 없으면 세 줄 중 두 줄이 중복일 때 밀도가 66% 가 되어 `Sonar way` 의 3% 기준을 훌쩍 넘깁니다. 중복 지표가 개수가 아니라 `duplicated_lines / lines * 100` 이라는 비율이라 분모가 작을 때 값이 크게 튀는 성질 때문입니다.

다만 이 면제는 중복과 커버리지에만 적용됩니다. 그 두 줄에 이슈가 있으면 `new_violations` 조건은 그대로 걸립니다.
