# Scanner 종류와 선택

> 스캐너는 빌드 시스템에 맞춰 고릅니다. 고르고 나면 CI 호스트에 어떤 Java 가 필요한지가 따라오는데, 여기서 오해가 자주 생깁니다. 스캐너가 요구하는 Java 버전은 스캐너 자신이 돌 런타임이지 분석 대상 코드의 버전이 아닙니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 빌드 시스템을 보고 어떤 스캐너를 쓸지 고를 수 있습니다.
2. CLI 로 대체할 수 없는 언어가 무엇이며 왜 그런지 설명할 수 있습니다.
3. JRE 자동 프로비저닝이 무엇을 자동화하는지, 껐을 때 무엇이 달라지는지 말할 수 있습니다.
4. Java 17 지원 종료가 어디까지 영향을 주는지 판단할 수 있습니다.



## 1. 빌드 시스템이 스캐너를 정합니다

> 스캐너는 취향으로 고르지 않습니다. 빌드 시스템이 이미 정답을 가지고 있습니다.

공식 선택표는 이렇습니다.[^req]

| 빌드 시스템 | 스캐너 |
|---|---|
| Maven | SonarScanner for Maven |
| Gradle | SonarScanner for Gradle |
| MSBuild 또는 .NET CLI | SonarScanner for .NET |
| NPM | SonarScanner for NPM |
| Python | SonarScanner for Python |
| 그 밖의 모든 프로젝트 | SonarScanner CLI |

빌드 도구에 붙는 스캐너를 쓰는 이유는 빌드가 이미 아는 정보를 다시 알려주지 않아도 되기 때문입니다. 소스 경로, 컴파일된 클래스 위치, 테스트 소스, 의존성 목록을 빌드 스크립트가 이미 가지고 있습니다. CLI 를 쓰면 이것을 `sonar-project.properties` 에 손으로 다시 적어야 하고, 빌드 설정이 바뀔 때마다 두 곳을 맞춰야 합니다.

한 가지는 선택이 아니라 제약입니다. **C# 과 VB.NET 은 SonarScanner for .NET 이 필요하고 CLI 로는 분석할 수 없습니다.** 다른 언어는 CLI 로 우회가 가능하지만 이 둘은 안 됩니다.

지원 운영체제는 넷입니다.

- Linux: x64, AArch64
- Windows: x64
- macOS: x64, AArch64
- IBM z/OS: 별도 요구사항 있음

Apple Silicon 이 AArch64 로 목록에 있어 로컬 실습에 제약이 없습니다.



## 2. 서버 버전이 스캐너 최소 버전을 정합니다

> 서버와 스캐너는 짝이 있습니다. 오래된 스캐너로 새 서버에 올리면 분석이 거부됩니다.

2026.1 LTA 기준 최소 스캐너 버전입니다.[^req]

| 스캐너 | 2026.1 LTA | 9.9 LTA |
|---|---|---|
| SonarScanner CLI | 8.0.1 | 4.8 |
| Jenkins extension | 2.18 | 2.15 |
| SonarScanner for Maven | 5.5.0.6356 | 3.9.1.2184 |
| SonarScanner for Gradle | 7.2.2.6593 | 3.5.0.2730 |
| SonarScanner for .NET | 11.0.0.126294 | 5.11 |
| SonarScanner for NPM | 4.3.0 | 3.7.0 |
| SonarScanner for Python | 1.3.0.4086 | 없음 |

9.9 LTA 와 비교하면 간격이 큽니다. Gradle 스캐너는 3.5 에서 7.2 로, .NET 스캐너는 5.11 에서 11.0 으로 올라갔습니다. 서버를 9.9 에서 2026.1 로 올리는 업그레이드는 서버만 올려서는 끝나지 않고, 각 파이프라인의 스캐너 버전도 함께 올려야 한다는 뜻입니다. Python 스캐너는 9.9 시절에 아예 없었습니다.



## 3. JRE 는 스캐너가 알아서 받아 옵니다

> 자동 프로비저닝이 켜져 있으면 스캐너가 필요한 JRE 를 서버에서 내려받습니다. CI 호스트의 Java 를 맞출 필요가 없습니다.

스캐너 엔진은 Java 로 돌기 때문에 JRE 가 필요합니다. 그런데 그 JRE 를 CI 호스트가 준비할 필요가 없습니다. **JRE 자동 프로비저닝**이 켜져 있으면 스캐너가 분석 시점에 서버에서 알맞은 JRE 를 받아 씁니다.[^jre]

지원 시작 버전은 스캐너마다 다릅니다.

| 스캐너 | 자동 프로비저닝 지원 시작 |
|---|---|
| SonarScanner CLI | 6.0 |
| SonarScanner for .NET | 7.0 |
| SonarScanner for NPM | 4.0 |
| SonarScanner for Maven | 5.0 |
| SonarScanner for Gradle | 6.0 |

지원하는 스캐너에서는 기본으로 켜져 있습니다. 껐을 때와 켰을 때 CI 호스트에 필요한 Java 가 이렇게 갈립니다.

| 스캐너 | 켰을 때 | 껐을 때 |
|---|---|---|
| Maven · Gradle | Java 11 | Java 21 (17 은 deprecated) |
| CLI | Java 11 (7.2 이상) | Java 21 (17 은 deprecated) |
| .NET · NPM · Python | 불필요 | Java 21 (17 은 deprecated) |

끄는 경우가 있습니다. 사내에서 인증한 Java 버전만 쓰도록 통제하는 환경이라면 자동 다운로드가 정책에 어긋납니다. 이때는 `sonar.scanner.skipJreProvisioning` 파라미터로 끄고 직접 Java 를 지정합니다.



## 4. Java 17 지원 종료는 어디까지 영향을 줍니까

> 스캐너 자신이 돌 런타임에만 해당합니다. 분석 대상 코드의 Java 버전과는 무관합니다.

공식 문서의 문장을 그대로 옮기면 이렇습니다. Java 17 은 스캐너 런타임으로서 지원이 종료되며, SonarQube Server 2026.3 까지 지원되고 **2026.4(2026년 7월)부터 Java 21 이 필요합니다.** 같은 시점부터 Community Build 와 Cloud 에서는 Java 21 만 지원합니다.[^req]

여기서 두 가지를 구분해야 합니다.

첫째, **이 요구는 스캐너가 돌아가는 Java 버전에 대한 것입니다.** 공식 문서가 못 박습니다. JRE 요구사항은 스캐너 자신이 실행되는 Java 버전만 가리키며, 스캐너가 분석할 수 있는 Java 버전을 제한하지 않습니다. Corretto 17 로 빌드하는 프로젝트를 Java 21 스캐너가 분석하는 것은 문제가 없습니다.

둘째, **자동 프로비저닝을 쓰면 할 일이 없습니다.** 공식 문서가 "no action is required" 라고 적습니다. Java 요구사항을 스캐너가 알아서 관리하기 때문입니다. 조치가 필요한 쪽은 자동 프로비저닝을 껐거나 스캐너가 지원하지 않는 경우입니다.

정리하면 Java 17 종료를 걱정해야 하는 조건은 좁습니다. 자동 프로비저닝을 끈 파이프라인이면서 CI 호스트에 Java 17 만 있는 경우입니다. 기본 설정을 쓰고 있다면 서버를 2026.4 로 올려도 파이프라인은 그대로 돕니다.

<https://docs.sonarsource.com/sonarqube-server/2026.1/analyzing-source-code/scanners/scanner-environment/general-requirements>

[^jre]: SonarQube Server 2026.1 — JRE 자동 프로비저닝 지원 스캐너와 비활성화 방법.

## 면접에서 받을 만한 질문

1. Gradle 프로젝트에 CLI 스캐너를 쓰면 무엇이 번거로워집니까. 번거로움으로 끝나지 않는 경우도 있습니까.
2. 사내 정책상 Java 21 을 아직 못 올립니다. 2026.4 이후 분석이 막힙니까.

> 2개 질문에 *먼저 스스로 답해 보세요.* 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 2개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다.

### 정답 1 — 빌드가 아는 정보를 다시 적어야 함

소스 경로, 컴파일된 클래스 위치, 테스트 소스, 의존성 목록을 `sonar-project.properties` 에 손으로 적어야 하고 빌드 설정이 바뀔 때마다 두 곳을 맞춰야 합니다.

번거로움으로 끝나지 않는 경우가 하나 있습니다. C# 과 VB.NET 은 SonarScanner for .NET 이 필요하며 CLI 로는 분석할 수 없습니다. 이쪽은 선택이 아니라 제약입니다.

### 정답 2 — 스캐너 런타임과 분석 대상은 별개

기본 설정이라면 막히지 않습니다. 두 가지를 구분해야 합니다.

첫째, Java 요구는 스캐너 자신이 돌아가는 런타임에 대한 것이고 분석 대상 코드의 Java 버전을 제한하지 않습니다. Corretto 17 로 빌드하는 프로젝트를 Java 21 스캐너가 분석하는 데 문제가 없습니다.

둘째, JRE 자동 프로비저닝이 켜져 있으면 스캐너가 필요한 JRE 를 서버에서 받아 씁니다. 조치가 필요한 조건은 자동 프로비저닝을 껐거나 스캐너가 지원하지 않는 경우로 좁습니다.
