# REST API 로 빌드를 부르고 추적하기

---

> 외부 서비스는 API Token 으로 인증하면 crumb 없이 Jenkins 를 호출하고, 큐 아이템 URL 을 폴링해 빌드 번호를 얻습니다. 빌드 종료는 `building` 이 false 인지로 보고 `input` 승인 대기는 `wfapi` 로 알아봅니다.

## 학습 목표

> 이 편을 읽고 나면 외부 시스템에서 Jenkins API 를 안전하게 연동하는 핵심 흐름을 스스로 설명할 수 있습니다.

1. UI 경로와 API 엔드포인트의 대응 관계를 설명할 수 있습니다. `tree` 로 응답을 줄이는 이유도 말할 수 있습니다.
2. API Token 요청이 CSRF crumb 검사에서 제외되는 이유를 공격의 전제로 설명할 수 있습니다.
3. 트리거 직후 빌드 번호 대신 큐 아이템 URL 이 반환되는 이유와 빌드 번호를 얻는 경로를 설명할 수 있습니다.
4. 빌드 종료 판정에서 `building` 과 `result` 의 차이를 구분할 수 있습니다. 승인 대기(`PAUSED_PENDING_INPUT`)를 알아보는 방법도 설명할 수 있습니다.
5. 빌드 트리거가 멱등하지 않다는 점을 이해합니다. 재시도 때 중복 빌드가 생기는 조건과 각 방어 수단이 막는 범위를 설명할 수 있습니다.



## 1. 리소스 기반 URL 과 tree 제어

> Jenkins API 는 UI 경로 뒤에 `/api/json` 을 붙여 부릅니다. 응답은 대상 객체를 뿌리로 한 서브트리라서 폴링에서는 `tree` 로 필요한 필드만 받아 줄입니다.

외부 서비스가 Jenkins 와 연동하려면 화면 대신 호출할 인터페이스가 필요합니다. Jenkins 는 모든 기능을 받는 단일 진입점을 두지 않습니다. 대상 객체의 URL 아래 `.../api/` 에 그 객체의 기능을 둡니다.[^remote-api] 화면에서 보던 잡 URL 이 `/job/my-job/` 이라면 JSON 은 `/job/my-job/api/json` 에서 받습니다.

문제는 응답의 크기입니다. Jenkins 가 내부에 가진 데이터 모델은 큰 트리입니다. API 호출 한 번은 그 일부인 서브트리를 돌려줍니다. 서브트리는 호출한 객체를 뿌리로 하며 일정한 깊이에서 잘립니다. `depth` 를 키우면 잘리는 지점이 늦어져 더 많은 데이터가 옵니다. 큰 값의 응답은 작은 값의 응답을 모두 포함합니다.[^remote-api] 한 번의 호출로 하위 객체까지 보고 싶을 때 쓰는 수단입니다.

폴링은 반대 방향의 요구를 가집니다. 같은 값을 주기적으로 묻는데 필요한 필드는 몇 개뿐입니다. 이때는 `tree` 로 받을 필드를 직접 적어 응답을 줄입니다. `?tree=name,lastBuild[number,result]` 는 잡 이름과 마지막 빌드의 번호와 결과만 돌려 달라는 요청입니다. 응답이 작을수록 반복 호출이 Controller 에 주는 부담도 줄어듭니다.



## 2. API Token 과 CSRF crumb 면제

> 브라우저 세션으로 상태를 바꾸는 POST 는 CSRF 방어용 crumb 이 필요합니다. API Token 으로 인증한 요청은 CSRF 보호에서 제외되어 crumb 없이 트리거를 호출할 수 있습니다.

브라우저 세션으로 상태를 바꾸는 요청은 CSRF(Cross-Site Request Forgery) 공격에 노출됩니다. 로그인된 브라우저는 사용자가 모르는 다른 사이트의 폼 요청에도 세션 쿠키를 자동으로 싣기 때문입니다. Jenkins 는 빌드 실행이나 설정 변경처럼 내용을 바꾸는 요청에 crumb 이라는 토큰을 요구합니다.[^csrf-protect]

기본 crumb 발급기는 crumb 에 사용자 이름, 웹 세션 ID, Jenkins 인스턴스 고유의 salt 를 담습니다. 이 정보가 모두 맞아야 검증을 통과합니다.[^csrf-protect] 그래서 사용자 이름과 비밀번호로 인증하는 스크립트는 번거로운 절차를 밟습니다. 먼저 `/crumbIssuer/api` 로 crumb 을 요청합니다. 응답의 `Set-Cookie` 로 받은 세션 쿠키도 기억합니다. 이후 요청마다 crumb 과 그 세션 쿠키를 함께 보냅니다.[^csrf-protect]

반면 사용자 이름과 API Token 으로 인증한 요청은 CSRF 보호에서 제외됩니다.[^csrf-protect] 공식 문서도 crumb 대신 API Token 을 권합니다.[^remote-api] 스크립트에 실제 비밀번호를 두는 방식은 유출 위험과 비밀번호 재사용 문제 때문에 권하지 않습니다.[^scripted-clients]

제외되는 이유는 공식 문서에 적혀 있지 않습니다. 아래는 공격의 전제에서 풀어 본 설명입니다. CSRF 는 브라우저가 쿠키를 자동으로 보내는 동작에 기대는 공격입니다. API Token 은 클라이언트가 HTTP Basic 인증 헤더에 직접 담아야 전달됩니다.[^scripted-clients] 브라우저가 알아서 붙여 주지 않으니 다른 사이트가 사용자 몰래 토큰 인증 요청을 만들 수 없습니다.

API Token 은 비밀번호보다 다루기도 쉽습니다.[^token-blog]

- 토큰을 여러 개 만들 수 있습니다. 새거나 잊은 토큰만 골라 폐기할 수 있습니다.
- 토큰에 이름을 붙여 어디서 쓰는지 구분할 수 있습니다.
- 토큰별 사용 이력을 추적할 수 있습니다.

다만 Basic 헤더는 암호화되지 않은 채 전달됩니다. 전송 구간을 보호하는 HTTPS 가 필수 전제입니다.



## 3. 큐 아이템에서 빌드 번호까지

> 빌드 트리거 POST 는 빌드 번호 대신 큐 아이템 URL 을 돌려줍니다. 빌드 번호는 Executor 스레드가 빌드 객체를 만든 뒤에야 생겨서 큐 아이템의 `executable` 이 채워지기를 폴링으로 기다립니다.

외부 서비스가 `POST /job/{name}/build` 나 `/buildWithParameters` 를 부르면 HTTP 201 응답이 돌아옵니다. `Location` 헤더에는 `/queue/item/{id}/` 형태의 큐 아이템 URL 이 담깁니다. 이 응답이 만들어지는 과정은 [Stapler 와 URL 이 doBuild 에 닿는 길](02-01.Stapler%20와%20URL%20이%20doBuild%20에%20닿는%20길.md) §3 에 있습니다.

이 시점에는 빌드 번호가 아직 없습니다. 요청은 대기 큐에 들어갔을 뿐입니다. 번호는 Executor 스레드가 일을 받아 빌드 객체를 만들 때 정해집니다. 큐 대기표인 `queueId` 와 `buildNumber` 가 각각 어디서 발급되는지는 [Queue 상태 전이와 Executor 로 가는 길](02-02.Queue%20상태%20전이와%20Executor%20로%20가는%20길.md) §4 에 있습니다.

그래서 외부 서비스는 큐 아이템을 폴링해 번호를 확보합니다.

1. `Location` 헤더에서 큐 아이템 id 를 꺼냅니다.
2. `GET /queue/item/{id}/api/json?tree=executable[number,url]` 로 폴링합니다.
3. 아이템이 큐를 떠나고 빌드 객체가 만들어지면 `executable` 이 채워집니다. 그 안의 `number` 가 빌드 번호입니다.
4. 번호를 얻은 뒤에 `/job/{name}/{number}/api/json` 으로 빌드 상태를 추적합니다.

`executable` 은 큐를 떠난 아이템(`LeftItem`)이 가진 값입니다.[^left-executable] 아이템은 큐를 떠난 직후 빌드 객체가 만들어지기 전의 짧은 틈이 있어 `executable` 이 아직 비어 있을 수 있습니다. 그러니 값이 채워질 때까지 계속 폴링합니다.

큐를 떠난 아이템의 기록은 5분 동안만 보관됩니다. 폴링 간격이 이보다 길어지면 아이템이 조회되지 않아 빌드 번호를 놓칩니다. 이 보관 시간의 근거는 [Queue 상태 전이와 Executor 로 가는 길](02-02.Queue%20상태%20전이와%20Executor%20로%20가는%20길.md) §1 에 있습니다.



## 4. 완료 판정과 building·result

> 빌드가 끝났는지는 `building` 이 false 인지로 보고, 결과는 그때 `result` 로 읽습니다. 실행 중에도 `result` 에 중간 값이 있을 수 있어서 null 여부로 종료를 판정하면 안 됩니다.

빌드 번호를 얻었다면 이제 빌드가 끝났는지 알아야 합니다. 그런데 `building`, `inProgress`, `result` 세 필드의 의미를 섞으면 진행 중인 빌드를 끝난 것으로 오판합니다. 코어 빌드 API 는 이 필드들로 종료 여부와 결과를 알려 줍니다.

`building` 은 빌드의 주된 실행이 끝나기 전까지 true 입니다. 주된 실행이 끝나 후처리 단계로 넘어가면 false 가 됩니다. `inProgress` 는 후처리가 끝나야 false 가 됩니다. 그래서 `building` 이 false 여도 후처리가 아직 남아 있을 수 있습니다.[^run-state]

`result` 는 빌드의 판정 문자열입니다. 값은 `SUCCESS`, `UNSTABLE`, `FAILURE`, `NOT_BUILT`, `ABORTED` 다섯 가지입니다.[^result] 실행 중에도 이 값이 정해질 수 있습니다. 소스는 `result` 가 실행 단계에서 바뀔 수 있다고 적습니다. 값은 더 나쁜 쪽으로만 바뀝니다.[^run-state] 주된 실행이 끝나면 최종 값이 정해지고 그 뒤에 `building` 이 false 가 됩니다.[^run-state]

정리하면 `result` 가 null 이 아니라는 것은 종료를 뜻하지 않습니다. 반대로 실행 중 `result` 가 null 일 수 있다고 해서 null 을 실패로 처리해서도 안 됩니다. 순서는 하나입니다. `building == false` 로 종료를 먼저 확인합니다. 그때의 `result` 를 판정에 씁니다.

폴링은 `?tree=building,result` 로 필요한 필드만 요청합니다. 폴링 간격은 Controller 부하를 고려해 정합니다. 무한 폴링에 빠지지 않도록 클라이언트에 최대 대기 시간도 둡니다.



## 5. 승인 대기와 wfapi

> 파이프라인이 `input` 스텝에서 멈춰도 코어 API 는 `building: true` 로만 보입니다. 승인 대기는 `wfapi` 의 `PAUSED_PENDING_INPUT` 으로 알아봅니다.

배포 파이프라인은 운영 배포 직전에 사람의 승인을 받는 `input` 스텝을 자주 둡니다. 이 스텝에 들어가면 파이프라인은 외부 신호가 올 때까지 멈춥니다.

이때 코어 빌드 API 만 보면 문제가 생깁니다. 빌드는 끝나지 않았으므로 `building` 은 true 입니다. 코어 API 의 필드 어디에도 입력 대기를 가리키는 값이 없습니다. 그래서 작업이 도는 중인지 승인을 기다리며 멈춘 것인지 구분할 수 없습니다.

Pipeline REST API 플러그인이 제공하는 `wfapi` 는 이 구분을 줍니다. `GET /job/{name}/{number}/wfapi/describe` 는 런 전체와 스테이지별 `status` 를 돌려줍니다. 입력을 기다리는 런과 스테이지의 `status` 는 `PAUSED_PENDING_INPUT` 입니다.[^pipeline-rest] 이 상태의 런은 `pendingInputActions` 링크도 가집니다. 이 링크의 `wfapi/pendingInputActions` 는 대기 중인 입력마다 `proceedUrl` 과 `abortUrl` 을 줍니다.[^pipeline-rest]

외부 서비스는 이 신호로 사용자 화면에 승인 버튼을 띄웁니다. 승인 결과는 받은 `proceedUrl` 이나 `abortUrl` 에 POST 합니다. 문서의 예시 URL 은 `/job/{name}/{number}/input/{inputId}/proceedEmpty` 형태입니다.[^pipeline-rest] 입력 id 는 `input` 스텝마다 달라서 URL 을 직접 조립하기보다 응답에서 받는 편이 낫습니다. `wfapi` 의 나머지는 [stage 상태와 로그를 가져오는 wfapi](08-02.stage%20상태와%20로그를%20가져오는%20wfapi.md) 에서 다룹니다.

승인 대기 중인 파이프라인이 Agent 슬롯을 계속 쥐면 다른 빌드가 시작하지 못합니다. `input` 스텝을 `node` 블록 밖으로 빼서 슬롯 점유를 막는 원리는 [병렬·승인·재시도와 실행기 점유](03-02.병렬·승인·재시도와%20실행기%20점유.md) §2 에 있습니다.



## 6. 멱등성 부재와 중복 트리거 방어

> 빌드 트리거 POST 는 멱등하지 않습니다. 응답을 못 받고 재시도하면 중복 빌드가 생길 수 있고 방어 수단마다 막는 범위가 달라 조합해서 씁니다.

같은 요청을 여러 번 보내도 서버 상태가 한 번 보낸 것과 같은 성질을 멱등성(idempotency)이라고 합니다. HTTP GET 조회는 멱등하지만 Jenkins 의 `POST /build` 와 `/buildWithParameters` 는 그렇지 않습니다.

외부 서비스가 트리거를 호출했는데 네트워크 지연으로 응답을 받지 못했다고 가정합니다. 요청이 Jenkins 에 닿았는지 알 수 없는 상태에서 같은 POST 를 다시 보내면 빌드가 두 번 돌 수 있습니다.

다만 재시도가 항상 두 빌드가 되는 것은 아닙니다. 같은 작업이 아직 큐에 있으면 Jenkins 는 새 아이템을 만들지 않고 기존 아이템에 요청을 합쳐 같은 큐 아이템 URL 을 돌려줍니다. 파라미터가 다른 요청은 별도 아이템이 됩니다. 이 동작은 [Queue 상태 전이와 Executor 로 가는 길](02-02.Queue%20상태%20전이와%20Executor%20로%20가는%20길.md) §4 에 있습니다. 그러니 첫 요청이 이미 큐를 떠났다면 합쳐질 아이템이 없습니다. 재시도는 새 아이템이 되어 두 번째 빌드로 이어집니다.

이 위험을 줄이는 수단은 세 가지입니다. 각각 막는 범위가 다릅니다.

첫째, 파이프라인에 `options { disableConcurrentBuilds() }` 를 둡니다. 같은 파이프라인의 실행을 동시에 허용하지 않는 옵션입니다. 이미 실행 중이면 새 빌드는 큐에서 기다립니다.[^pipeline-syntax] 중복 빌드를 없애는 것이 아니라 한 번에 하나씩 돌도록 직렬화할 뿐입니다. 두 번째 빌드는 앞 빌드가 끝나면 그대로 실행됩니다. 배포 충돌은 막아도 낭비는 막지 못합니다.

둘째, 트리거 직전에 대상 잡의 상태를 조회합니다. `?tree=inQueue,lastBuild[building]` 로 잡의 `api/json` 을 읽습니다.[^job-inqueue] `inQueue` 나 `lastBuild.building` 이 true 면 새 요청을 보내지 않습니다. 다만 조회와 트리거는 원자적이지 않습니다. 두 호출 사이에 다른 요청이 끼어들 수 있어 낭비를 줄이는 보조 수단입니다.

셋째, 요청 ID 나 커밋 SHA 같은 고유 식별자를 파라미터로 넘깁니다. 파이프라인 시작 단계에서 같은 식별자로 이미 시작한 빌드가 있는지 검사합니다. 있으면 바로 끝냅니다. 식별자가 다르면 큐 아이템이 합쳐지지 않으므로 이 검사는 파이프라인 쪽에서 직접 구현해야 합니다.

## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 다섯 개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — API Token 의 crumb 제외 이유

공식 문서는 API Token 요청이 CSRF 보호에서 제외된다는 사실만 적습니다. 이유는 공격의 전제에서 풀 수 있습니다. CSRF 공격은 로그인한 브라우저가 세션 쿠키를 자동으로 요청에 싣는 동작에 기댑니다. 그래서 쿠키 인증 환경에서는 브라우저가 모르는 crumb 을 요구해 위조 요청을 막습니다. API Token 은 클라이언트가 `Authorization` 헤더에 직접 담아야만 전달되고 브라우저가 자동으로 붙이지 않습니다. 위조 요청이 성립하는 전제가 없으므로 검사를 제외해도 위험이 늘지 않습니다.

### 정답 2 — 큐 아이템 URL 과 빌드 번호

트리거는 빌드를 즉시 실행하지 않고 먼저 대기 큐에 넣습니다. 대기 시간 동안에는 아직 빌드 객체가 없습니다. 응답에 담을 수 있는 값은 큐에 들어올 때 발급된 대기표뿐입니다. 그것이 `Location` 헤더의 큐 아이템 URL 입니다. 빌드 번호는 Executor 스레드가 아이템을 받아 빌드 객체를 만들 때 작업별 카운터로 발급됩니다. 따라서 큐 아이템 API 를 폴링해 `executable.number` 가 채워졌을 때 번호를 얻습니다.

### 정답 3 — 완료 판정과 결과 검사

`building` 은 빌드의 주된 실행이 끝나기 전까지 true 입니다. `result` 는 판정 문자열인데, 실행 중에도 중간 값이 정해질 수 있고 null 일 수도 있습니다. 그래서 값만으로는 종료 여부를 알 수 없습니다.

먼저 `building == false` 로 종료를 확인합니다. 그다음 `result` 가 `SUCCESS`, `UNSTABLE`, `FAILURE`, `NOT_BUILT`, `ABORTED` 중 무엇인지 읽습니다. `result` 가 null 이라고 실패로 처리하면 정상적으로 돌고 있는 빌드를 실패로 오판합니다.

### 정답 4 — wfapi 와 승인 대기 상태

코어 Build API 는 파이프라인이 입력을 기다리며 멈춰 있어도 빌드가 끝나지 않았으므로 `building: true` 로 응답합니다. 입력 대기를 가리키는 필드가 없어서 도는 중인지 멈춘 것인지 구분하지 못합니다. `wfapi/describe` 는 런과 스테이지별 `status` 를 줍니다. 입력 대기 중이면 `PAUSED_PENDING_INPUT` 입니다. 외부 서비스는 이 값을 감지하고 `pendingInputActions` 에서 받은 `proceedUrl` 이나 `abortUrl` 로 승인 또는 거절을 전달합니다.

### 정답 5 — 멱등성 부재와 중복 트리거 방어

트리거 POST 는 호출마다 요청을 큐에 넣으므로 멱등하지 않습니다. 같은 작업이 아직 큐에 있으면 요청이 합쳐집니다. 그러나 첫 요청이 큐를 떠났거나 파라미터가 다르면 합쳐지지 않아 빌드가 두 번 돕니다. `disableConcurrentBuilds()` 는 같은 파이프라인이 동시에 도는 것만 막습니다. 두 번째 빌드는 큐에서 기다렸다가 앞 빌드가 끝나면 실행되므로 중복 빌드 자체는 막지 못합니다. 낭비까지 줄이려면 트리거 전에 `inQueue` 와 `building` 을 조회하거나 파이프라인 시작 단계에서 고유 식별자를 검사합니다.
