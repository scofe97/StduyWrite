# 인증·인가와 시크릿

---

> Jenkins 보안은 신원을 확인하는 Security Realm 과 권한을 검사하는 Authorization Strategy 로 나뉩니다. 시크릿은 Scope 로 노출 범위를 정하고, 로그 마스킹은 값이 일치할 때만 가리므로 우회 경로를 알고 막아야 합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. Security Realm 과 Authorization Strategy 가 분리된 이유를 계정 인프라와 권한 수명의 차이로 설명할 수 있습니다.
2. Matrix 보안과 Role-Based Strategy 의 차이를 비교하고 Item Roles 정규식으로 최소 권한을 설계할 수 있습니다.
3. Credentials 의 Scope 가 노출 범위를 정하는 방식과 Domain 이 보안 장치가 아닌 이유를 설명할 수 있습니다.
4. 빌드 로그 마스킹이 우회되는 세 가지 경로를 분석하고 스크립트 작성 시 주의점을 제시할 수 있습니다.
5. 단일 관리자 API 토큰이 유발하는 세 가지 운영 부채를 설명하고 용도별 서비스 계정 분리 방안을 세울 수 있습니다.



## 1. 인증과 인가를 나눈 이유

> Security Realm 은 신원을 확인하고 Authorization Strategy 는 그 신원이 무엇을 할 수 있는지 결정합니다. 두 축을 따로 설정하므로 계정 인프라가 바뀌어도 권한 설정을 다시 쓰지 않아도 됩니다.

사용자 정보와 세부 권한이 한 설정에 묶여 있으면 계정 체계가 바뀔 때마다 많은 잡의 권한을 다시 써야 합니다. 사내 디렉터리를 Jenkins 자체 데이터베이스에서 LDAP 이나 SAML 기반 SSO 로 옮기다가 프로젝트 권한까지 깨지면 이전이 멈춥니다.

Jenkins 는 접근 통제를 두 설정으로 나눕니다.[^sec-overview]

### 인증과 인가의 생애주기 분리

Security Realm 은 사용자 정보를 어디서 가져와 누구인지 확인할지 정합니다. Jenkins 내장 사용자 데이터베이스를 쓸 수 있습니다. LDAP 이나 SAML·OIDC 기반 SSO 같은 외부 신원 제공자(IdP)에 인증을 위임할 수도 있습니다. LDAP 과 SAML 기능은 별도 플러그인이므로 설치돼 있지 않을 수 있습니다.

Authorization Strategy 는 로그인한 사용자가 어떤 자원에 어떤 작업을 할 수 있는지 정합니다.

외부 IdP 를 쓰는 환경에서 인증 쪽은 조직 전체의 정책을 따르므로 바뀌는 일이 드뭅니다. 반면 인가 규칙은 팀이 생기고 담당자가 바뀔 때마다 고쳐야 합니다. 바뀌는 주기와 관리 주체가 다르므로 두 설정을 나누어 두는 편이 변화에 유연합니다.

### Controller 에서 빌드를 돌릴 때의 위험

인증과 인가는 Controller 에서 이루어집니다. 그런데 빌드를 Controller 자신(built-in node)에서 돌리면 문제가 생깁니다. built-in node 에서 도는 빌드는 Jenkins 프로세스와 같은 수준으로 파일시스템에 접근합니다.[^controller-isolation] 빌드 스크립트가 JENKINS_HOME 을 읽을 수 있으면 권한 설정은 의미를 잃습니다.

빌드 내용은 관리자보다 덜 신뢰되는 사람들이 정합니다. Job/Configure 권한을 가진 사용자, 빌드 스크립트 작성자, 빌드 중 실행되는 코드 작성자가 그들입니다. 그래서 built-in node 의 executor 수를 0 으로 두고 빌드를 Agent 로 보내는 것이 첫 조치입니다. 이때 빌드를 받을 Agent 나 클라우드가 따로 있어야 빌드가 시작됩니다.

Agent 로 보내도 끝이 아닙니다. Controller 와 Agent 는 하나의 분산 프로세스처럼 동작해서 Agent 가 Controller 에 정보나 명령 실행을 요청할 수 있습니다. 탈취된 Agent 가 이를 악용하지 못하게 막는 장치가 Agent → Controller Access Control 이고, 문서는 이를 끄지 말라고 권합니다.



## 2. 권한 모델과 최소 권한

> Jenkins 는 전역 매트릭스, 프로젝트별 매트릭스, 역할 기반 전략을 고를 수 있게 합니다. 어느 쪽이든 권한 모델은 화면과 API 접근을 가를 뿐이고 빌드 안에서 실행되는 명령까지 막지는 못합니다.

모든 사용자에게 전역 관리자나 넓은 실행 권한을 주면 한 계정이 탈취되거나 스크립트를 잘못 써도 피해가 전체로 번집니다. 그래서 작업에 꼭 필요한 권한만 나누어 줍니다.

### 인가 전략 비교

Jenkins 코어가 주는 선택지와 플러그인이 더하는 선택지는 아래와 같습니다.[^sec-overview]

| 인가 전략 | 권한을 정하는 단위 | 특징 |
|---|---|---|
| Anyone can do anything | 없음 | 익명 사용자까지 모든 권한. 로컬 테스트에만 씁니다. |
| Logged-in users can do anything | 로그인 여부 | 로그인한 모두가 전체 권한. 로그인을 강제하므로 사용자별 감사 추적이 남습니다. |
| Matrix-based security | 사용자·그룹 × 권한 | 권한은 합집합으로 더해집니다. |
| Project-based Matrix | 위 매트릭스 + 프로젝트별 ACL | 프로젝트 설정 화면에서 ACL 을 따로 정의하고 전역 설정과 합산합니다. |
| Role-Based Strategy | 역할(전역·항목·에이전트) | 역할을 먼저 만들고 사용자나 그룹에 배정합니다. 플러그인입니다. |

Matrix 는 열 하나가 코어나 플러그인이 제공하는 권한 하나라서 표가 넓어집니다. 행은 사용자나 그룹이고, 한 사용자의 권한은 본인과 소속 그룹, `authenticated`, `anonymous` 에 준 권한의 합입니다. 이 합집합 규칙 때문에 한 행에서 권한을 빼도 다른 행에서 받은 권한은 남습니다.

Role-Based Strategy 플러그인은 전역 역할, 항목 역할, 에이전트 역할을 제공합니다.[^role-strategy] 전역 역할이 준 권한은 항목 역할이 무엇을 정하든 모든 항목에 적용됩니다. 예를 들어 전역 역할에 `Job/Read` 를 주면 그 역할은 모든 잡을 읽습니다. 그래서 최소 권한은 전역 역할을 좁게 두고 항목 역할로 범위를 열어 가야 설계됩니다.

### Item Roles 정규식과 최소 권한

Item Roles 와 Agent Roles 는 정규식 패턴으로 대상을 고릅니다. 패턴은 항목의 전체 이름에 대해 맞춥니다. 대소문자를 가리며 가리지 않으려면 `(?i)` 를 붙입니다.[^role-strategy]

잡 이름 규칙을 정해 두면 새 잡이 패턴에 맞는 순간 같은 권한이 적용됩니다. 예를 들어 배포 자동화 계정에는 `deploy-.*` 패턴의 항목 역할에만 `Job/Build` 와 `Job/Read` 를 줍니다. 그러면 다른 잡의 설정과 소스에는 닿지 못합니다.

폴더 안의 잡에 접근하려면 폴더 자체도 접근할 수 있어야 합니다. 폴더와 잡을 한 패턴으로 묶을 수 있으나 권한이 다르면 역할을 둘로 나눕니다.

일반 개발자에게는 `Overall/Read`, `Job/Read`, `Job/Build` 만 줍니다. 설정과 삭제 권한은 뺍니다. 파이프라인 변경은 Jenkinsfile 에 대한 코드 리뷰로 통제하는 편이 안전합니다. 문서에 따르면 Jenkinsfile 은 커밋 권한이 없는 사용자가 고칠 수 없습니다. 단 Pipeline 신뢰 설정이 알맞을 때입니다.[^securing-builds]

### 권한 모델이 막지 못하는 것

권한 모델은 사용자가 화면과 API 로 무엇을 할 수 있는지를 정합니다. 빌드가 돌기 시작한 뒤 그 안에서 실행되는 명령은 별개의 문제입니다. 그 명령을 정하는 사람은 Job/Configure 권한자, 빌드 스크립트 작성자, 코드 작성자입니다.[^controller-isolation]

그래서 `Job/Build` 만 가진 개발자라도 저장소에 커밋한 스크립트가 Agent 에서 돌면서 내부망 호출이나 파일 탐색을 시도할 수 있습니다. 권한 모델이 이를 막지 못합니다.

문서가 제시하는 대책은 빌드를 서로 격리하는 것입니다. 빌드마다 새 Agent 를 만드는 클라우드 제공자를 씁니다. 또는 Job Restrictions 플러그인으로 특정 잡이 도는 노드를 제한합니다.[^securing-builds] 파이프라인 안의 Groovy 가 도는 곳과 그 제한은 [Groovy 는 Jenkins 어디서 도는가](05-01.Groovy%20는%20Jenkins%20어디서%20도는가.md)에서 다룹니다.



## 3. 시크릿의 Scope 와 Domain

> Credentials 의 Scope 는 시크릿을 어느 범위에서 쓸 수 있는지 정하고 Domain 은 선택 목록을 서비스별로 거릅니다. 시크릿 값은 Controller 에 암호화되어 보관되고 파이프라인은 ID 로만 참조합니다.

소스 코드나 Jenkinsfile 에 비밀번호와 토큰을 평문으로 쓰면 저장소 이력과 빌드 로그로 샙니다. Jenkins 는 시크릿을 Credentials 저장소에 두고 파이프라인에는 ID 만 남기게 합니다. 값은 Controller 에 암호화되어 있고 파이프라인은 ID 로만 다룹니다. 그래서 사용자가 실제 값을 볼 일이 줄어듭니다.[^using-credentials]

### Scope 가 정하는 노출 범위

Scope 는 그 크레덴셜이 어느 맥락(root, 폴더, 잡 등)에서 보이는지 정합니다.[^credentials-plugin]

- `GLOBAL`: 기본값입니다. 연결된 맥락과 그 아래 모든 자식 맥락에서 보입니다. 잡이 일반적으로 쓰는 저장소 토큰이나 레지스트리 비밀번호에 씁니다.
- `SYSTEM`: Jenkins 시스템과 백그라운드 작업이 쓰는 용도입니다. Agent 연결용 SSH 키가 대표 예입니다. root 맥락에서만 보입니다.
- `USER`: 사용자별 저장소에만 있고, 그 사용자의 권한으로 도는 작업에서만 보입니다.

Authorize Project 플러그인이 없으면 잡은 시스템 권한으로 돌고 `GLOBAL` Scope 크레덴셜에만 접근합니다. 그래서 일반 파이프라인은 `SYSTEM` 크레덴셜을 읽지 못하고, 인프라 SSH 키를 스크립트가 빼 가지 못하게 하는 방어선이 됩니다.

반대로 조심할 점이 있습니다. Jenkins 의 `GLOBAL` Scope 크레덴셜은 시스템의 어떤 잡에서도 접근할 수 있습니다.[^credentials-faq] `GLOBAL` 은 "전역으로 공개" 에 가깝습니다. 노출을 줄이려면 폴더 같은 하위 맥락에 크레덴셜을 두어 그 아래에서만 보이게 해야 합니다.

### Domain 의 역할과 한계

Domain 은 크레덴셜에 서비스 정보를 붙여 UI 에서 올바른 크레덴셜을 고르기 쉽게 하는 장치입니다. 같은 사용자 이름과 비밀번호 종류가 여러 서비스에 있을 때 어느 서비스용인지 구분할 수 있습니다.

서비스 URL 을 입력하면 그 주소와 맞지 않는 Domain 의 크레덴셜은 목록에서 빠집니다. 다만 공식 문서는 "맞지 않는 것을 제외한다" 와 "맞는 것만 포함한다" 가 다르다고 강조합니다. 기본 Domain(global)에는 조건이 없어서 어떤 요청에도 항상 목록에 나타납니다.

공식 문서는 Domain 이 크레덴셜이 엉뚱한 서비스에 쓰이는 것을 막으려는 기능이 아니라고 밝힙니다. 접근을 제한하는 기능도 아닙니다. 따라서 기본 Domain 에 모든 시크릿을 모아 두면 노출은 그대로이고 선택 목록만 길어집니다. 시크릿의 접근 범위는 Scope 와 크레덴셜을 둔 맥락, 그리고 권한으로 좁혀야 합니다.[^credentials-plugin]

### 저장과 빌드에서의 사용

Jenkins 기본 저장소는 크레덴셜 값을 암호화해 Controller 의 JENKINS_HOME 에 둡니다. 암호화 키도 같은 JENKINS_HOME 에 있습니다. Jenkins JVM 은 이 둘을 모두 읽을 수 있어야 합니다.[^credentials-plugin] 그래서 Controller 파일시스템을 읽을 수 있는 사람은 시크릿을 복호화할 수 있습니다.[^credentials-faq] 더 민감한 시크릿에는 외부 크레덴셜 저장소 플러그인을 쓰라고 문서는 권합니다.

빌드에서는 크레덴셜을 환경변수에 바인딩해서 씁니다. `environment` 블록의 `credentials('id')` 는 사용자 이름·비밀번호 종류에서 `_USR`, `_PSW` 접미사 변수를 만듭니다. 파일 형태의 크레덴셜은 임시 파일 경로가 변수에 담깁니다.[^pipeline-cred]



## 4. 마스킹이 우회되는 경로

> 빌드 로그 마스킹은 바인딩한 시크릿 값이 로그에 나오면 가리는 장치입니다. 값이 달라지거나 로그 밖으로 나가는 경로는 가려 주지 않습니다.

Credentials Binding 으로 바인딩한 시크릿은 빌드 로그에서 자동으로 마스킹됩니다.[^cred-binding] 별표가 찍힌 로그를 보고 시크릿이 안전하다고 믿으면 사고를 막지 못합니다. 마스킹은 보안 경계가 아니라 실수로 찍히는 값을 가려 주는 장치입니다.

### 값 변형과 마스킹

마스킹은 시크릿 값이 로그에 그대로 나왔을 때 작동합니다. 값이 바뀌어서 나오면 가리지 못합니다. 공식 문서의 예가 이를 보여 줍니다. 시크릿이 `sec%ret` 일 때 Windows `bat` 는 `%` 를 지우고 `secret` 을 출력합니다. 한 글자가 달라서 마스킹되지 않습니다.[^pipeline-cred]

같은 원리로 시크릿을 base64 로 바꾸거나 일부만 잘라 출력해도 원래 값과 달라서 마스킹되지 않을 수 있습니다. 공식 문서에 이 두 경우의 예는 없고, 위 예에서 따라 나오는 추론입니다.

### Groovy 큰따옴표 보간

가장 흔한 실수는 시크릿을 Groovy 큰따옴표 문자열에 넣는 것입니다. `sh "curl -H 'Token: ${MY_TOKEN}' ..."` 처럼 쓰는 경우입니다. Groovy 가 명령을 Agent 로 보내기 전에 `${MY_TOKEN}` 을 값으로 바꿉니다. 그러면 시크릿이 프로세스 인자에 들어가 `ps` 같은 프로세스 목록에 노출됩니다.[^pipeline-cred]

작은따옴표로 쓰면 Groovy 가 건드리지 않고 셸이 환경변수를 확장합니다. `sh 'curl -H "Token: $MY_TOKEN" ...'` 가 그 형태입니다. 문서는 시크릿에 Groovy 보간을 쓰지 말라고 말합니다. 위 `sec%ret` 사례도 보간으로 값이 바뀐 경우였습니다.

### 로그 밖으로 나가는 시크릿

로그 출력을 막아도 스크립트가 시크릿을 외부로 보내면 마스킹은 소용이 없습니다. 빌드 스크립트가 환경변수를 외부 서버로 보내는 요청을 담고 있으면 시크릿은 콘솔 로그를 거치지 않고 나갑니다.

그래서 마스킹에 기대지 않는 방어가 필요합니다. 일반적인 방어책으로 Agent 의 나가는 트래픽을 방화벽 등으로 허용된 대상에만 제한합니다. 장기 비밀번호 대신 유효 기간이 짧은 토큰을 쓰면 새어도 피해 기간이 짧습니다. 이 두 가지는 Jenkins 문서의 설명이 아니라 일반 방어 원칙입니다.



## 5. 관리자 토큰이 남기는 빚

> 자동화 초기에 단일 관리자 토큰을 쓰면 유출 시 전체 장악, 감사 추적 불가, 권한 회수 불가능의 세 부채가 남습니다. 처음부터 기능별 서비스 계정을 두면 피해 범위가 계정 권한으로 좁혀집니다.

외부 시스템이 Jenkins REST API 를 호출할 때 관리자 계정의 API Token 하나를 돌려쓰는 경우가 흔합니다. 초기 연동은 편하지만 나중에 권한을 줄이지 못하는 빚으로 남습니다.

스크립트 클라이언트는 사용자 이름과 API Token 으로 HTTP Basic 인증을 합니다. 비밀번호를 쓸 수도 있으나 노출 위험과 재사용 때문에 권장하지 않습니다.[^api-tokens] 그 토큰이 가진 권한은 그 계정의 권한입니다. 관리자 토큰이면 관리자 권한이 그대로 따라갑니다.

### 단일 관리자 토큰이 만드는 세 가지 빚

첫 부채는 유출 시 파급력입니다. 관리자 토큰(`Overall/Administer`)이 노출되면 공격자는 인스턴스 설정과 잡과 크레덴셜까지 관리자로서 건드립니다.

둘째 부채는 감사 추적의 마비입니다. 모든 호출이 같은 관리자 이름으로 남으므로 이상한 동작이 있어도 호출한 주체를 가릴 수 없습니다. 문서도 로그인을 강제하는 이유로 사용자별 감사 추적을 듭니다.[^sec-overview]

셋째 부채는 권한 회수의 교착입니다. 많은 외부 서비스가 관리자 토큰에 의존하면 권한을 줄일 때 어느 서비스가 깨질지 알 수 없어 줄이기를 포기하게 됩니다.

### 용도별 서비스 계정 분리

해결은 용도마다 서비스 계정을 만들고 최소 권한만 주는 것입니다.

- 빌드 트리거 전용 계정: 대상 잡에 `Job/Build` 와 `Job/Read` 만 줍니다.
- 상태 수집 전용 계정: 모니터링에 필요한 `Overall/Read` 와 `Job/Read` 만 줍니다.
- 관리자 계정: 일상 연동에서 빼고 비상 유지보수에만 사람이 직접 씁니다.

계정마다 따로 토큰을 쓰면 한 토큰이 새도 그 계정의 권한 범위로 피해가 막힙니다. 서비스를 바꿀 때도 그 계정만 정리하면 됩니다. 전체 잡이 아니라 `deploy-.*` 같은 패턴에 대한 권한만 줄 수 있다는 점에서 2절의 Item Roles 와 맞물립니다.

## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 다섯 개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — 인증·인가 분리와 Controller 격리

Security Realm 은 사용자 신원을 확인하고 Authorization Strategy 는 자원별 권한을 정합니다. 둘을 나누면 계정 시스템을 LDAP 이나 SAML 로 바꿔도 권한 설정을 유지할 수 있습니다. 조직이 개편되면 인증은 그대로 두고 권한만 조정할 수 있습니다.

built-in node 에서 도는 빌드는 Jenkins 프로세스와 같은 수준으로 Controller 파일시스템에 접근합니다. 빌드 내용은 관리자보다 덜 신뢰되는 사람이 정하므로, built-in node 의 executor 를 0 으로 두고 빌드를 Agent 로 보내야 합니다. 이때 Agent → Controller Access Control 은 끄지 말아야 합니다.

### 정답 2 — Item Roles 와 권한 모델의 한계

Item Roles 는 정규식으로 잡 이름을 골라 역할을 줍니다. 자동화 계정이 자기 담당 잡에만 `Job/Build` 를 갖게 할 수 있고, 새 잡이 패턴에 맞으면 같은 권한이 적용됩니다. 전역 역할의 권한은 항목 역할과 무관하게 모든 항목에 적용되므로 전역 역할은 좁게 둡니다.

그러나 권한 모델은 화면과 API 접근만 가릅니다. 빌드가 시작되면 그 안의 명령은 Job/Configure 권한자와 스크립트·코드 작성자가 정하므로, 스크립트가 Agent 에서 내부망 접근이나 파일 조작을 시도할 수 있습니다. 대책은 빌드를 격리하는 것입니다. 빌드마다 새 Agent 를 만들거나 Job Restrictions 로 노드를 제한합니다.

### 정답 3 — Scope 와 Domain

Scope 는 크레덴셜이 어느 맥락에서 보이는지 정합니다. `GLOBAL` 은 연결된 맥락과 그 아래에서 보이고 시스템의 어떤 잡에서도 접근할 수 있습니다. `SYSTEM` 은 root 맥락에서만 보여서 일반 파이프라인은 읽지 못합니다. Agent 연결용 SSH 키를 `SYSTEM` 으로 두는 이유입니다.

Domain 은 크레덴셜에 서비스 정보를 붙여 UI 에서 올바른 것을 고르게 돕는 장치입니다. 맞지 않는 Domain 만 목록에서 빼고 기본 Domain 은 항상 나타납니다. 공식 문서는 Domain 이 접근을 제한하지 않는다고 밝히므로 접근 통제는 Scope 와 맥락과 권한으로 해야 합니다.

### 정답 4 — 로그 마스킹 원리와 우회 경로

마스킹은 Credentials Binding 으로 바인딩한 시크릿 값이 로그에 그대로 나오면 가리는 필터입니다. 값이 달라지면 가리지 못합니다.

우회 경로는 세 가지입니다. 첫째, Groovy 큰따옴표 보간으로 시크릿이 명령 문자열에 먼저 들어가 `ps` 같은 프로세스 목록에 노출되고, 보간으로 값이 바뀌면 마스킹도 되지 않습니다. 둘째, base64 인코딩이나 부분 출력으로 값이 달라지는 경우입니다. 셋째, 로그를 거치지 않고 시크릿을 외부 네트워크로 보내는 경우입니다.

대책은 작은따옴표로 셸이 환경변수를 확장하게 하는 것입니다. 일반 방어책으로 Agent 의 나가는 트래픽을 제한하고 수명이 짧은 토큰을 씁니다.

### 정답 5 — 관리자 토큰의 부채와 서비스 계정 분리

단일 관리자 토큰은 세 부채를 만듭니다. 첫째, 하나가 새면 인스턴스 전체가 관리자 권한으로 노출됩니다. 둘째, 모든 호출이 같은 관리자 이름으로 남아 호출 주체를 가릴 수 없습니다. 셋째, 많은 서비스가 관리자 권한에 묶여 권한을 줄이거나 바꾸기 어려워집니다.

해결은 빌드 트리거용, 모니터링용 같은 기능별 서비스 계정을 만들고 최소 권한만 주는 것입니다. 계정마다 API Token 을 따로 쓰면 유출 피해가 그 계정의 권한으로 좁혀지고 호출 주체도 구분됩니다.
