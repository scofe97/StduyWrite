# Shared Library

---

> Jenkinsfile 을 여러 저장소에 복사해 두면 변경 증폭과 구성 드리프트가 발생합니다. Shared Library 는 공통 파이프라인 로직을 별도 Git 저장소로 추출해 단일 지점에서 관리하고, Trusted 전역 등록과 Untrusted Sandbox 로 권한 경계를 나눕니다.

## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 설명하고 판단할 수 있습니다.

1. Jenkinsfile 복붙 방식이 초래하는 변경 증폭과 구성 드리프트를 Shared Library 로 해결하는 방식을 설명할 수 있습니다.
2. `vars/`, `src/`, `resources/` 세 디렉토리의 역할과 클래스패스·DSL 호출 가능 여부를 비교할 수 있습니다.
3. Explicit, Implicit, Dynamic 로딩 방식의 차이와 브랜치·태그·커밋 해시 기반 버전 고정의 운영 효과를 판단할 수 있습니다.
4. Global Trusted 라이브러리와 Folder-level Untrusted 라이브러리의 Sandbox 적용 여부와 보안 신뢰 경계를 설명할 수 있습니다.
5. `call(Map config)` 설계 패턴과 `Serializable` 인터페이스 구현 필요성, 그리고 `@NonCPS` 분리 경계를 설명할 수 있습니다.



## 1. Jenkinsfile 복붙과 드리프트 문제

> 마이크로서비스마다 동일한 파이프라인 코드를 복사해 두면 로직 변경 시 모든 저장소를 수정해야 하고 저장소별 설정이 어긋납니다. Shared Library 는 공통 로직을 독립된 저장소로 모아 한 번의 수정으로 모든 파이프라인에 반영합니다.

마이크로서비스 아키텍처를 도입한 조직에서는 수십 개 이상의 서비스가 유사한 빌드, 검증, 배포 단계를 거칩니다. 이때 동일한 파이프라인 코드를 각 저장소의 Jenkinsfile 에 복사해 붙여넣으면 세 가지 운영 문제가 발생합니다.

첫째는 변경 증폭(Change Amplification)입니다. 보안 점검 도구나 컨테이너 레지스트리 주소가 바뀌면 수십 개 저장소의 Jenkinsfile 을 일일이 수정해야 합니다. 100개 서비스라면 100개의 풀 리퀘스트를 열어야 합니다.

둘째는 구성 드리프트(Configuration Drift)입니다. 시간이 흐르며 특정 팀이 임의로 단계를 수정하거나 최신 설정을 누락합니다. 그 결과 저장소마다 파이프라인 로직이 조금씩 달라지는 불일치가 일어납니다.

셋째는 거버넌스 부재입니다. 보안 스캔이나 코드 품질 검사를 중앙에서 강제할 수 없습니다. 일부 서비스가 필수 검증을 건너뛰어도 이를 감지하기 어렵습니다.

Shared Library 는 이 문제를 공통 로직의 중앙화로 해결합니다.[^shared-libraries] 공통 파이프라인 코드를 별도의 독립된 Git 저장소에 둡니다. 개별 Jenkinsfile 은 해당 라이브러리를 호출하는 몇 줄의 선언문만 남깁니다.

```groovy
@Library('my-shared-lib@v1.2.0') _

standardPipeline(
    serviceName: 'order-api',
    deployTarget: 'production'
)
```

수백 줄의 파이프라인 정의가 단 몇 줄로 줄어듭니다. 도구 교체나 공통 정책 변경은 라이브러리 저장소의 한 커밋으로 전체 서비스에 일괄 반영됩니다.



## 2. 세 디렉토리의 역할 분담

> Shared Library 는 세 디렉토리로 역할을 분리합니다. `vars/` 는 파이프라인 전역 함수, `src/` 는 순수 비즈니스 로직 클래스, `resources/` 는 외부 정적 파일을 보관합니다.

Shared Library 저장소는 Jenkins 가 인식하는 표준 디렉토리 구조를 따라야 합니다.[^shared-lib-dirs] 각 디렉토리는 클래스패스 로딩 여부와 파이프라인 DSL 접근 권한이 서로 다릅니다.

`vars/` 디렉토리는 파이프라인에서 변수처럼 쓰는 스크립트를 담습니다. 파일 이름(basename)이 곧 파이프라인의 전역 변수 이름입니다. `vars/log.groovy` 에 `def info(message)` 가 있으면 파이프라인에서 `log.info "hello"` 로 부릅니다. 파일에 `call()` 메서드를 두면 변수 자체를 `sayHello 'Joe'` 처럼 step 모양으로 호출할 수 있습니다.

이 스크립트 안에서는 `sh`, `stage`, `echo` 같은 Pipeline step 을 그대로 호출합니다. 다만 전역 변수에 상태를 저장하면 안 됩니다. 컨트롤러가 재기동하면 그 상태가 사라지기 때문입니다. 그래서 전역 변수는 함수 모음(stateless)으로만 씁니다.[^shared-lib-dirs]

`src/` 디렉토리는 표준 Java 소스 디렉토리 구조를 따르는 Groovy 소스 파일을 담습니다. 이 디렉토리는 파이프라인을 실행할 때 클래스패스에 추가됩니다. 그래서 `import com.example.ConfigHelper` 형태로 불러와 사용합니다. 복잡한 로직이나 유틸리티를 클래스로 구성할 때 씁니다.

단, `src/` 클래스는 `sh` 같은 step 을 직접 호출할 수 없습니다. step 이 필요하면 파이프라인 스크립트의 `this` 를 생성자나 메서드 인자로 넘겨 그 객체로 호출합니다. `vars/` 와 `src/` 의 Groovy 소스는 둘 다 Scripted Pipeline 과 같은 CPS 변환을 거칩니다. CPS 변환은 5절에서 다룹니다.

`resources/` 디렉토리는 Groovy 가 아닌 파일을 보관합니다. 파이프라인에서는 `libraryResource` step 으로 이 파일을 문자열로 읽습니다. 공식 문서의 예는 JSON 파일입니다. 읽은 문자열은 API 인자로 넘기거나 `writeFile` 로 워크스페이스에 저장합니다. 이 기능은 외부 라이브러리에서만 지원됩니다.[^shared-lib-dirs]

| 디렉토리 | 저장 내용 | 접근 방식 | Pipeline DSL 직접 호출 | 주 용도 |
|---|---|---|---|---|
| `vars/` | 전역 변수 스크립트 | 파일명이 변수 이름 (`call()` 이면 step 모양) | 가능 | 파이프라인 흐름 제어, 알림, 빌드 단계 |
| `src/` | 일반 Groovy 클래스 | `import` 문 선언 후 객체 생성 | 직접은 불가능 (`this` 전달 필요) | 순수 로직, 설정 검증 |
| `resources/` | Groovy 가 아닌 파일 | `libraryResource` step 호출 | 해당 없음 | JSON 같은 정적 데이터 |

`vars/` 를 진입점으로 두고, 그 안에서 필요에 따라 `src/` 클래스를 쓰거나 `resources/` 파일을 읽는 구성이 흔합니다. 이 구성은 공식 문서의 규칙이 아니라 위 역할 분담에서 나오는 관례입니다.



## 3. 로딩 방식과 버전 고정 전략

> 라이브러리는 Jenkinsfile 에 직접 선언하거나 전역 설정으로 자동 로딩할 수 있습니다. 안정적인 운영을 위해서는 가변 브랜치 대신 태그나 커밋 해시로 버전을 고정해야 합니다.

라이브러리를 파이프라인에 불러오는 방법은 세 가지입니다. 각각 라이브러리가 준비되는 시점이 다릅니다.[^library-loading]

첫째는 `@Library` 어노테이션입니다. Jenkinsfile 에 `@Library('lib-name') _` 를 적습니다. 라이브러리는 스크립트가 실행을 시작하기 전, 컴파일 단계에서 해석되고 로드됩니다. 그래서 `src/` 클래스를 `import` 하거나 타입 선언에 쓸 수 있습니다. 어떤 라이브러리를 쓰는지 Jenkinsfile 에 그대로 드러납니다. 뒤의 밑줄(`_`)은 어노테이션을 붙일 자리를 채우는 기호입니다. `vars/` 의 전역 변수만 쓸 때 `import` 문 대신 이 기호에 어노테이션을 답니다.

둘째는 암시적 로딩입니다. 라이브러리 설정에서 "Load implicitly" 를 켜면 어노테이션 없이도 모든 파이프라인이 그 라이브러리의 클래스와 전역 변수를 바로 씁니다. 공통 라이브러리를 모든 곳에 깔 때 편합니다. 반면 Jenkinsfile 만 읽어서는 이 라이브러리가 어디서 왔는지 알 수 없습니다.

셋째는 `library` step 입니다. 빌드 도중 `library 'lib-name@version'` 으로 불러옵니다. 일반 step 이라서 버전 문자열을 변수로 계산할 수 있습니다. 예를 들어 `library "my-shared-library@$BRANCH_NAME"` 은 멀티브랜치 Jenkinsfile 과 같은 브랜치를 씁니다.

이 시점에는 스크립트가 이미 컴파일된 뒤입니다. 그래서 `vars/` 의 전역 변수는 바로 쓰지만 `src/` 클래스는 `import` 할 수 없습니다. 반환값에서 전체 클래스 이름으로 접근해야 하고 타입 검사도 받지 못합니다. 이미 암시적으로 로드된 라이브러리의 버전은 이 step 으로 바꿀 수 없습니다. 같은 이름의 라이브러리는 두 번 로드되지 않기 때문입니다.

버전은 `@` 뒤에 적습니다. Git 이라면 브랜치, 태그, 커밋 해시가 모두 됩니다. 버전을 생략하면 라이브러리 설정의 "Default version" 이 쓰입니다. 이 값이 비어 있으면 Jenkinsfile 이 버전을 반드시 적어야 합니다. 설정에서 "Allow default version to be overridden" 를 켜야 `@Library` 가 기본 버전을 덮어쓸 수 있습니다. 반대로 설정에 버전을 박아 두면 스크립트가 다른 버전을 고르지 못하게 막을 수 있습니다.

프로덕션에서는 브랜치 대신 태그나 커밋 해시로 버전을 고정하는 편이 안전합니다. 브랜치는 계속 움직입니다. 모든 파이프라인이 `@main` 을 가리키면 호환성을 깨는 변경이 머지된 직후 실행되는 빌드가 모두 그 변경을 받습니다. 태그나 커밋 해시는 가리키는 코드가 고정되므로 라이브러리가 갱신돼도 기존 파이프라인은 그대로입니다. 단 태그는 다시 옮길 수 있어서, 완전한 불변을 원하면 커밋 해시를 씁니다. 각 팀은 준비된 때에 버전을 올립니다.



## 4. Trusted 라이브러리와 Sandbox 경계

> 전역 설정(Global Trusted Pipeline Libraries)에서 trusted 로 표시한 라이브러리는 Sandbox 없이 모든 API 를 호출합니다. 폴더에 등록한 라이브러리는 항상 untrusted 라서 Groovy Sandbox 안에서만 실행됩니다.

공유 라이브러리가 컨트롤러 안의 모든 API 를 호출할 수 있다고 해 봅시다. 그러면 악의적인 코드나 실수가 Jenkins 전체를 위협합니다. Jenkins 는 라이브러리를 등록하는 위치와 등록자의 권한에 따라 trusted 여부를 나누어 이 위험을 통제합니다.[^shared-libraries]

Global Trusted Pipeline Libraries(Manage Jenkins » System)에서는 라이브러리를 trusted 로 표시할 수 있습니다. trusted 라이브러리는 Java 와 Groovy 의 메서드를 제한 없이 호출합니다. Jenkins 내부 API 와 플러그인, 서드파티 라이브러리도 마찬가지입니다. 안전하지 않은 API 를 감싸 모든 파이프라인이 쓸 수 있는 안전한 래퍼를 만들 때 이 권한을 씁니다.

따라서 이 저장소에 커밋을 push 할 수 있는 사람은 Jenkins 에 무제한 접근할 수 있습니다. 공식 문서도 이 점을 경고합니다. 저장소의 쓰기 권한과 리뷰 절차를 컨트롤러 관리자 수준으로 통제해야 하는 이유가 여기에 있습니다. trusted 로 등록하는 데에는 Overall/RunScripts 권한이 필요합니다. Overall/Manage 권한만 있으면 전역 라이브러리도 untrusted 로만 등록할 수 있습니다.

폴더에 등록한 라이브러리는 항상 untrusted 입니다. 해당 폴더와 하위 폴더의 파이프라인에만 범위가 한정됩니다. untrusted 라이브러리는 일반 파이프라인 스크립트와 똑같이 Groovy Sandbox 안에서 실행됩니다. Sandbox 가 막는 호출은 승인 절차를 거쳐야 합니다. 이 절차는 [Groovy 는 Jenkins 어디서 도는가](05-01.Groovy%20는%20Jenkins%20어디서%20도는가.md)에서 다룹니다.

정리하면 경계는 라이브러리의 등록 위치(전역 또는 폴더)와 등록자의 권한에 있습니다. 한 팀이 자기 폴더에 둔 라이브러리는 Sandbox 에 묶여 있어 컨트롤러 전체를 건드리지 못합니다.



## 5. Step 함수 설계와 직렬화 실패

> `vars/` 함수는 `call(Map config)` 형태로 작성해 확장성과 조기 검증을 확보합니다. 또한 파이프라인 상태 영속화 과정에서 직렬화 실패를 막으려면 `Serializable` 구현과 `@NonCPS` 분리 규칙을 준수해야 합니다.

`vars/` 의 함수를 설계할 때는 위치 기반 파라미터 대신 `call(Map config = [:])` 형태의 Map 인자 패턴을 권장합니다.

```groovy
def call(Map config = [:]) {
    def serviceName = config.serviceName ?: error("serviceName 은 필수 값입니다.")
    def tag = config.tag ?: env.BUILD_NUMBER

    stage('Build') {
        sh "docker build -t ${serviceName}:${tag} ."
    }
}
```

이 패턴은 인자의 순서 혼동을 없애고 가독성을 높입니다. 새로운 옵션이 추가되어도 기존 호출부가 깨지지 않습니다. 또한 엘비스 연산자(`?:`)를 이용하면 필수 파라미터 누락을 함수가 호출되는 첫 줄에서 잡아낼 수 있습니다. 배포 단계까지 간 뒤에야 실패하는 지연 실패를 방지합니다. 이 예는 Scripted 방식으로 Jenkinsfile 최상위에서 호출하는 경우입니다. Declarative Pipeline 에서 전역 변수의 메서드(`log.info` 같은 형태)를 부르려면 `script` 블록 안에 넣어야 합니다.

라이브러리 코드에서 흔히 마주치는 런타임 오류는 `NotSerializableException` 입니다. 원인은 Pipeline 의 실행 방식에 있습니다. Pipeline 스크립트는 CPS(continuation-passing style) 변환을 거쳐 실행됩니다. 이 변환 덕분에 실행 상태를 빌드 디렉토리의 `program.dat` 에 저장합니다. 그래서 Jenkins 가 재기동한 뒤에도 이어서 실행합니다.[^cps-mismatches] 저장 대상에는 파이프라인 변수에 담긴 객체가 포함됩니다. 직렬화할 수 없는 객체를 변수에 담아 둔 채 저장 시점이 오면 이 예외가 납니다.[^serializable-practice]

그래서 상태를 가지는 `src/` 클래스는 `Serializable` 을 구현해야 합니다.[^shared-lib-dirs] 공식 문서가 든 이유는, 그래야 이 클래스를 쓰는 파이프라인이 중단됐다가 다시 이어질 수 있기 때문입니다. 직렬화할 수 없는 객체는 변수에 오래 들고 있지 않는 쪽이 안전합니다. 예를 들어 `java.util.regex.Matcher` 는 `Serializable` 이 아니므로 변수에 담은 채 step 을 넘기면 위험합니다. 이런 객체를 다루는 계산은 `@NonCPS` 메서드 안에서 끝내고 직렬화 가능한 결과만 돌려주는 방식이 널리 쓰입니다.

`@NonCPS` 는 메서드 하나를 CPS 변환에서 빼 일반 Groovy 로 실행하게 하는 어노테이션입니다. 이 메서드에는 두 가지 제약이 있습니다.

첫째, 안에서 Pipeline step 이나 CPS 변환된 메서드를 호출할 수 없습니다. CPS 변환이 안 된 코드는 변환된 코드를 부를 수 없기 때문입니다.[^cps-mismatches] 둘째, 직렬화할 수 없는 객체는 지역 변수로만 쓰는 편이 맞습니다. 인자나 반환값으로 넘기거나 저장하지 않습니다.[^noncps-readme]

## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 다섯 개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — 복붙 문제와 중앙화

파이프라인 코드를 복사해 관리하면 도구 교체 시 수십 개 저장소를 모두 고쳐야 하는 변경 증폭과, 저장소별로 설정이 달라지는 구성 드리프트가 발생합니다.

Shared Library 는 공통 로직을 별도 Git 저장소로 추출해 단일 지점에서 관리합니다. 개별 Jenkinsfile 은 함수 호출만 남기므로, 중앙 라이브러리의 한 번의 수정으로 조직 전체 파이프라인을 일괄 갱신하고 표준 정책을 강제할 수 있습니다.

### 정답 2 — 세 디렉토리와 DSL 경계

`vars/` 는 파일명이 곧 전역 변수 이름이 되는 스크립트입니다. `call()` 을 두면 step 처럼 호출됩니다. 안에서 Pipeline step 을 직접 호출해 파이프라인 흐름을 제어합니다.

`src/` 는 표준 Java 소스 구조를 따르는 Groovy 클래스로 클래스패스에 추가되며 복잡한 로직을 클래스로 묶습니다. step 을 직접 호출할 수 없어서 `this` 를 넘겨받아야 합니다. `resources/` 는 `libraryResource` step 으로 문자열로 읽는 Groovy 가 아닌 파일을 보관하며, 외부 라이브러리에서만 지원됩니다.

### 정답 3 — 버전 고정과 장애 격리

브랜치(`@main`)는 계속 움직이므로, 호환성이 깨지는 변경이 머지되면 그 뒤 실행되는 모든 빌드가 그 변경을 받아 함께 실패할 수 있습니다.

태그나 커밋 해시로 고정하면 라이브러리가 갱신돼도 기존 파이프라인은 같은 코드를 실행합니다. 태그는 옮길 수 있으므로 완전한 고정은 커밋 해시입니다. 새 버전을 검증한 뒤 각 팀이 자기 속도로 버전을 올립니다.

### 정답 4 — Trusted 와 Sandbox

전역 설정(Global Trusted Pipeline Libraries)에서 trusted 로 표시한 라이브러리는 Groovy Sandbox 없이 Java, Groovy, Jenkins 내부 API, 플러그인의 메서드를 제한 없이 호출합니다. 그래서 이 저장소에 push 할 수 있는 사람은 Jenkins 에 무제한 접근할 수 있고, 저장소 쓰기 권한이 곧 보안 경계입니다.

반면 Folder 단위 라이브러리는 항상 untrusted 라서 일반 파이프라인과 같은 Sandbox 제약 아래에서 실행됩니다. 그래서 팀 단위 라이브러리가 컨트롤러 전체를 건드리지 못합니다.

### 정답 5 — CPS 직렬화 실패와 NonCPS 분리

Pipeline 은 CPS 변환 덕분에 실행 상태를 `program.dat` 에 저장하고 재기동 뒤 이어 갑니다. 그래서 상태를 가지는 `src/` 클래스는 `Serializable` 을 구현해야 합니다. 직렬화할 수 없는 객체를 변수에 담아 두면 `NotSerializableException` 이 납니다.

`Matcher` 처럼 직렬화할 수 없는 객체를 다루는 계산은 `@NonCPS` 메서드 안에서 끝내고 직렬화 가능한 결과만 돌려줍니다. `@NonCPS` 안에서는 Pipeline step 이나 CPS 변환된 메서드를 호출할 수 없습니다.
