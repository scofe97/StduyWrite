# 설정을 코드로 관리하는 JCasC

---

> Jenkins UI 로 수정한 설정은 변경 이력 없이 디스크 XML 파일에 흩어져 재현할 수 없습니다. JCasC 는 시스템 설정을 YAML 로 선언해 Java 객체에 매핑하며 reload 시점에 선언한 속성을 다시 적용합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. UI 설정이 다른 서버에서 재현되지 않는 원인과 설정 표류 문제를 설명할 수 있습니다.
2. `jenkins.yaml` 이 Java 객체로 매핑되는 과정과 reload 때 선언한 속성과 선언하지 않은 속성이 어떻게 다뤄지는지 설명할 수 있습니다.
3. Secret Source 와 Strict Secret Resolution 으로 시크릿을 안전하게 주입하는 원리를 설명할 수 있습니다.
4. 플러그인 설치와 JCasC 설정 사이의 순서 의존성, 다중 YAML 합성 제약을 설명할 수 있습니다.
5. JCasC 가 책임지는 시스템 영역과 다루지 않는 런타임 상태의 경계를 구분할 수 있습니다.



## 1. UI 설정의 비재현성과 형상 드리프트

> 웹 화면에서 클릭으로 바꾼 설정은 변경 사유가 남지 않아 서버 장애 시 복구하기 어렵습니다. JCasC 는 시스템 설정을 코드 파일로 관리해 버전 추적과 같은 환경 재현을 돕습니다.

Controller 를 새로 배포할 때 이전과 같은 설정으로 복구하지 못하면 파이프라인이 멈춥니다. 관리자가 웹 UI 에서 조작한 설정은 메모리에 적재된 뒤 `$JENKINS_HOME` 아래 `config.xml` 파일에 흩어져 저장됩니다. 누가 언제 어떤 이유로 옵션을 바꿨는지 기록이 남지 않으므로 새 서버에 같은 구성을 손으로 재현하기 어렵습니다.

이 수동 관리 방식은 개발 환경과 운영 환경의 설정이 서로 어긋나는 형상 드리프트를 일으킵니다. 옵션 하나만 달라도 운영 환경에서만 빌드가 실패할 수 있습니다.

JCasC(Jenkins Configuration as Code) 플러그인은 이 문제를 선언형 YAML 파일로 풉니다. Controller 전체 설정을 사람이 읽는 YAML 텍스트로 정의합니다.[^jcasc-doc] 이 파일을 Git 에 커밋하면 코드 리뷰와 이력 추적, 롤백을 Git 이 맡습니다.



## 2. YAML 적용 메커니즘과 reload 동작

> JCasC 는 YAML 트리를 파싱해 Descriptor 의 속성에 주입합니다. reload 는 재시작 없이 YAML 에 선언된 속성만 다시 설정하고 선언하지 않은 속성은 건드리지 않습니다.

웹 UI 에서 설정을 수동으로 바꾸면 변경 사항을 다른 서버에 똑같이 적용하기 어렵습니다. JCasC 는 `CASC_JENKINS_CONFIG` 환경변수가 가리키는 파일이나 디렉토리에서 YAML 을 읽어 시스템 설정을 코드로 적용합니다.[^jcasc-repo]

플러그인이 설치되면 Jenkins 코어의 확장 포인트 모델에 따라 컴포넌트별 Descriptor 가 등록됩니다. JCasC 의 `Configurator` 는 각 대상 클래스의 속성(setter 와 필드)을 탐색합니다. 이를 통해 YAML 의 계층형 키와 값을 Java 객체에 매핑합니다.

`jenkins.yaml` 의 대표적인 루트 키는 아래 네 가지입니다. 이 밖의 루트 키는 설치한 플러그인이 더합니다.

- `jenkins`: Controller 의 시스템 설정, 보안 영역(Security Realm), 인가 전략, 실행자 수를 정의합니다.
- `tool`: JDK, Maven, Gradle 같은 빌드 도구의 설치 경로와 자동 설치 규칙을 지정합니다.
- `unclassified`: 코어에 속하지 않는 개별 플러그인의 글로벌 옵션(GitLab, Slack, SonarQube 등)을 설정합니다.
- `credentials`: 시스템 자격증명 저장소에 등록할 시크릿 항목을 선언합니다.

설정이 바뀔 때마다 Jenkins Controller 를 재시작하면 실행 중이던 빌드가 중단됩니다. JCasC 는 재시작 없이 새 설정을 적용하는 reload 기능을 제공합니다.

reload 는 UI 의 reload 메뉴, Jenkins CLI, HTTP POST 로 호출합니다. HTTP 는 관리자 인증을 쓰는 `POST /configuration-as-code/reload` 가 기본입니다. 토큰 방식은 `/reload-configuration-as-code/` 에 `casc-reload-token` 파라미터를 붙여 호출합니다. 이 방식은 기본이 꺼져 있고 `CASC_RELOAD_TOKEN` 으로 토큰을 정하면 켜집니다.[^jcasc-reload] reload 가 호출되면 JCasC 는 YAML 을 다시 파싱해 선언된 속성을 객체에 새 값으로 설정합니다.

이때 적용 단위를 이해해야 합니다. JCasC 는 YAML 에 선언된 속성에만 새 값을 설정합니다. 선언하지 않은 속성은 건드리지 않습니다. 운영자가 UI 에서 바꾼 값이 YAML 에도 선언되어 있다면 reload 때 YAML 값으로 되돌아갑니다. YAML 에 없는 속성은 UI 변경분이 그대로 남습니다. 또 YAML 에서 항목을 지워도 Jenkins 에서 그 설정이 지워지지는 않습니다. 따라서 시스템을 온전히 재현하려면 관리할 설정을 YAML 에 빠짐없이 적어야 합니다.

다중 YAML 파일을 사용할 때도 주의가 필요합니다. `CASC_JENKINS_CONFIG` 에 디렉토리를 지정하면 하위의 YAML 파일을 모두 찾아 하나로 합성합니다.

기본 병합 전략은 `errorOnConflict` 입니다. 두 파일이 같은 설정 값을 겹쳐 정의하면 충돌로 보고 `ConfiguratorException` 을 던집니다.[^jcasc-multi] 파일은 서로 보완해야 하며 덮어쓸 수 없기 때문에 읽는 순서는 결과에 영향이 없습니다. 파일을 나눌 때는 루트 키(`jenkins`, `tool`, `credentials`, `unclassified`) 단위로 역할을 분리해 충돌을 방지합니다. `CASC_MERGE_STRATEGY=override` 를 지정하면 읽는 순서대로 덮어쓰는 전략으로 바꿀 수 있습니다.



## 3. 시크릿 외부화와 엄격 해석 모드

> 비밀값을 Git 에 평문으로 두지 않도록 JCasC 는 외부 시크릿 소스와 변수 치환을 지원합니다. 변수를 해석하지 못하면 기본적으로 빈 문자열이 되므로 운영 환경에서는 엄격 모드를 켜 두는 편이 안전합니다.

관리자 비밀번호나 Git 접근 토큰 같은 민감 정보를 `jenkins.yaml` 파일에 평문으로 적으면 Git 이력에 영구히 남아 유출 위험이 커집니다. JCasC 는 평문 대신 `${VAR}` 형식의 변수 치환 문법을 지원해 파일 밖에서 값을 주입하도록 만듭니다.[^jcasc-secrets]

JCasC 는 여러 외부 시크릿 소스를 해석할 수 있습니다:

- 환경변수: 프로세스 환경에 값을 넣으면 `${이름}` 이 그 값으로 바뀝니다.
- 파일 및 볼륨 마운트: Docker Secrets 나 Kubernetes Secret 을 `/run/secrets/` 아래 파일로 마운트합니다. 그러면 파일 이름이 변수 이름이 됩니다. 기준 폴더는 `SECRETS` 환경변수로 바꿉니다.
- 외부 시크릿 관리 서비스: HashiCorp Vault 같은 외부 저장소를 SecretSource 플러그인으로 연결합니다. 값은 그 저장소에서 받아옵니다.

변수에는 값을 가공하는 헬퍼도 쓸 수 있습니다. `${readFile:/path/file}` 은 파일 본문을 읽고 `${base64:...}` 는 인코딩하며 `${trim:...}` 은 앞뒤 공백을 지웁니다. 헬퍼는 `${trim:${readFile:/secret/file.txt}}` 처럼 중첩할 수 있습니다. `readFile` 은 파일 끝의 공백 문자까지 그대로 읽으므로 비밀번호 파일에는 `trim` 을 함께 씁니다. 변수에 기본값이 필요하면 `${VAR:-기본값}` 으로 씁니다.

가장 조심할 동작은 변수를 해석하지 못했을 때입니다. 기본 동작은 경고 로그를 남기고 그 변수를 빈 문자열로 바꾸는 것입니다. 외부 시크릿 저장소가 잠시 응답하지 않으면 자격증명이 빈 값으로 덮어써진 채 reload 가 성공할 수 있습니다.

이를 막는 설정이 Strict Secret Resolution 입니다. 환경변수 `CASC_STRICT_SECRET_RESOLUTION=true` 나 시스템 속성 `-Dcasc.strict.secret.resolution=true` 로 켭니다. 켜면 기본값(`:-`)이 없는 변수가 해석되지 않을 때 reload 를 통째로 중단합니다. 이전의 정상 설정은 그대로 남습니다.[^jcasc-secrets] 잘못된 설정이 조용히 적용되는 대신 바로 실패하므로 운영 환경에서는 켜 두는 편이 안전합니다.



## 4. GitOps 배포와 3계층 순서 의존성

> JCasC 는 인프라와 플러그인이 준비된 뒤에야 정상 동작하는 3계층 순서 의존성을 갖습니다. 플러그인 목록과 JCasC 설정을 같은 커밋으로 묶어야 플러그인과 YAML 키의 불일치를 막을 수 있습니다.

Jenkins 를 코드로 온전히 배포하려면 설정 파일 하나만으로는 부족합니다. 인프라 프로비저닝, 플러그인 설치, 시스템 설정 적용이 순서대로 이어져야 완전한 자동화가 완성됩니다.

배포는 아래 세 계층의 순서 의존성을 따릅니다:

1. 1계층 인프라: Terraform 이나 클라우드 템플릿으로 VM, 네트워크, 스토리지 볼륨을 프로비저닝합니다.
2. 2계층 바이너리와 플러그인: Helm 차트나 패키지 매니저가 Jenkins 코어와 `plugins.txt` 에 명시된 플러그인 목록을 설치합니다.
3. 3계층 시스템 설정: JCasC 가 `jenkins.yaml` 을 읽어 전역 옵션과 자격증명을 구성합니다.

이 순서가 중요한 이유는 YAML 에서 쓸 수 있는 키가 설치된 플러그인에 달려 있기 때문입니다. JCasC 는 설치된 플러그인의 Descriptor 를 바탕으로 YAML 키를 해석합니다. 필요한 플러그인이 없거나 버전이 달라 속성이 바뀌면 JCasC 는 그 키를 인식하지 못하고 `ConfiguratorException` 을 던집니다. 이 예외가 Jenkins 기동 중에 나면 기동이 실패하고 reload 중에 나면 그 reload 가 실패합니다. 따라서 `plugins.txt` 와 `jenkins.yaml` 은 분리하지 않고 항상 같은 Git 커밋 안에서 함께 관리해야 합니다.

Kubernetes 에서 Helm 차트로 Jenkins 를 운영하면 JCasC 설정은 차트 값 `controller.JCasC.configScripts` 로 넣습니다. 변경이 반영되는 방식은 sidecar 자동 reload 를 켰는지에 따라 갈립니다. sidecar 는 Controller Pod 안에 함께 뜨는 보조 컨테이너입니다. 설정 키는 `controller.sidecars.configAutoReload.enabled` 입니다. 아래 표의 오른쪽 열이 이를 켠 경우입니다.[^helm-readme]

| 비교 항목 | 기본 (auto-reload 꺼짐) | auto-reload 켬 |
|---|---|---|
| 설정 반영 경로 | `helm upgrade` 로 새 Pod 생성 | sidecar 가 `configScripts` 변경을 감지해 파일을 복사하고 reload 를 호출 |
| 적용 시점 | 새 Pod 가 시작할 때 | Pod 를 유지한 채 즉시 |
| 추가 조건 | 없음 | ConfigMap 을 watch 할 RBAC 설정 필요 |

설정 변경이 잦다면 auto-reload 를 켜서 Pod 재시작 없이 반영할 수 있습니다. 이때도 값의 출처는 Git 에 둔 `values.yaml` 입니다. 적용 경로만 Pod 재시작 대신 reload 로 바뀝니다. 차트와 JCasC 의 역할 분담은 [Kubernetes 편](07-01.Kubernetes%20에%20Jenkins%20를%20올리는%20이유와%20방법.md)에서 다룹니다.



## 5. JCasC의 책임 범위와 한계

> JCasC 는 전역 시스템 형상을 다루며 개별 파이프라인 로직이나 런타임 빌드 이력은 관리하지 않습니다. 데이터와 코드의 역할을 분리해야 올바른 백업 및 복구 전략을 세울 수 있습니다.

JCasC 를 도입하면 Jenkins 의 모든 상태가 YAML 하나로 관리된다고 오해하기 쉽습니다. 그러나 JCasC 는 시스템 레벨의 전역 설정(Descriptor)을 담당할 뿐, 빌드 실행 중에 생기는 데이터는 다루지 않습니다. 개별 작업의 정의도 JCasC 본래의 일이 아닙니다.

JCasC 로 관리할 수 있는 영역과 관리할 수 없는 영역의 경계는 명확합니다:

- JCasC 책임 영역: 시스템 메시지, 실행자 수, 인증 영역, 인가 전략, 자격증명, 에이전트 템플릿, 전역 도구 경로입니다.
- JCasC 범위 밖 영역: 과거 빌드 번호와 로그, 아티팩트, 큐 대기 상태, 개별 작업 정의, 파이프라인 스크립트입니다. 첫 Job 을 만들어야 하면 Job DSL 플러그인에 위임하는 `jobs` 루트 키로 seed job 을 선언할 수 있습니다.[^jcasc-seed]

특히 파이프라인 로직은 JCasC 가 아니라 각 애플리케이션 저장소의 `Jenkinsfile` 로 관리하는 것이 원칙입니다. Jenkins 시스템 전체를 코드로 다루려면 여러 도구의 책임 분담을 조합해야 합니다.

| 관리 계층 | 담당 도구 | 형상의 진실 원천(SSOT) |
|---|---|---|
| 클라우드 인프라 | Terraform | Git 저장소의 `.tf` 코드 |
| 애플리케이션 설치 | Helm | Helm Chart 및 `values.yaml` |
| 전역 시스템 설정 | JCasC | Git 저장소의 `jenkins.yaml` |
| CI/CD 파이프라인 | Pipeline as Code | 저장소별 `Jenkinsfile` |
| 빌드 이력과 영속 데이터 | Persistent Volume | 스토리지 볼륨 및 스냅샷 백업 |

재해 복구 시나리오를 설계할 때는 복합 전략이 필요합니다. JCasC 로 시스템 구성을 복원하고 영속 볼륨 백업으로 과거 빌드 기록을 살립니다. 파이프라인은 SCM 연동으로 다시 등록합니다.



## 면접에서 받을 만한 질문

1. 웹 UI 에서 직접 바꾼 Jenkins 설정이 재현성을 해치는 이유와 JCasC 가 이를 해결하는 방식을 설명해 보세요?
2. JCasC 의 reload 가 호출되었을 때 YAML 에 선언한 속성과 선언하지 않은 속성이 각각 어떻게 처리되는지 설명해 보세요?
3. 다중 YAML 파일 분할 시 `ConfiguratorException` 이 발생하는 원인과 이를 방지하는 파일 분리 원칙은 무엇입니까?
4. JCasC 에서 `CASC_STRICT_SECRET_RESOLUTION` 을 운영 환경에서 켜 두는 편이 안전한 이유를 설명해 보세요?
5. JCasC 가 관리하는 설정 영역과 관리하지 못하는 런타임 데이터 영역의 경계를 구분해 설명해 보세요?

> 다섯 질문에 먼저 스스로 답해 보세요. 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 다섯 개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — UI 설정의 비재현성과 JCasC

UI 로 조작한 설정은 `$JENKINS_HOME` 아래 개별 `config.xml` 파일에 기록되어 변경 이력과 감사 추적이 불가능합니다. 새 인스턴스를 띄우면 수동으로 다시 클릭해야 하므로 복구 시간이 길어지고 환경 간 설정 드리프트가 발생합니다. JCasC 는 시스템 설정을 `jenkins.yaml` 로 단일 코드화하여 Git 버전 관리, 리뷰, 신속한 동일 환경 재현을 가능하게 만듭니다.

### 정답 2 — reload 동작과 선언한 속성만 적용

reload 가 호출되면 JCasC 는 YAML 을 다시 파싱해 해당 컴포넌트의 속성에 새 값을 설정합니다. YAML 에 선언된 속성은 UI 에서 바꾼 값이 있어도 YAML 값으로 되돌아갑니다. YAML 에 없는 속성은 건드리지 않으므로 UI 변경분이 남습니다. YAML 에서 항목을 지워도 Jenkins 에서 지워지지 않습니다. 그래서 일관성을 유지하려면 관리할 설정을 빠짐없이 선언해야 합니다.

### 정답 3 — 다중 YAML 합성 제약과 루트 키 분리

기본 병합 전략 `errorOnConflict` 에서 다중 YAML 파일은 서로 보완해야 하며 덮어쓸 수 없습니다. 서로 다른 파일이 같은 설정 값을 겹쳐 정의하면 충돌로 보고 `ConfiguratorException` 을 던집니다. 이를 방지하려면 `jenkins`, `tool`, `unclassified`, `credentials` 처럼 루트 키 단위로 파일을 분리해 키 중복을 구조적으로 차단해야 합니다.

### 정답 4 — 엄격 해석 모드와 빈 비밀번호 방지

JCasC 의 기본 동작은 해결되지 않은 `${VAR}` 변수를 경고 로그만 남기고 빈 문자열로 대체하는 것입니다. 그러면 시크릿 저장소 장애 같은 일시적 실패가 자격증명을 빈 값으로 덮어쓴 채 reload 를 성공시킬 수 있습니다. `CASC_STRICT_SECRET_RESOLUTION=true` 를 켜면 기본값이 없는 미해결 변수가 있을 때 reload 전체가 중단되고 이전 설정이 유지됩니다.

### 정답 5 — JCasC 책임 범위와 런타임 데이터 경계

JCasC 는 시스템 전역 구성(보안 영역, 인가 전략, 실행자, 도구, 클라우드 에이전트 템플릿, 공용 자격증명)을 책임집니다. 반면 빌드 번호, 콘솔 로그, 아티팩트 같은 빌드 런타임 데이터와 개별 파이프라인 로직은 관리하지 않습니다. 파이프라인 로직은 저장소의 `Jenkinsfile` 로, 과거 빌드 데이터는 영속 볼륨 스토리지 백업으로 분리해 관리해야 합니다.
