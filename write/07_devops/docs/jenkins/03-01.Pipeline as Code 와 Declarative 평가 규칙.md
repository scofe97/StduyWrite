# Pipeline as Code 와 Declarative 평가 규칙

---

> 빌드 파이프라인을 코드로 관리하면 변경 추적과 복구가 쉬워지고 선언적 DSL 은 정해진 구조를 강제합니다. 이 편은 Freestyle 의 한계, Declarative 와 Scripted 의 평가 차이, 블록 우선순위, Job 정의 위치와 이름공간 격리 원리를 다룹니다.

## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. Freestyle 과 Pipeline as Code 의 차이를 변경 추적과 재현성 축에서 비교할 수 있습니다.
2. Declarative 가 강제하는 구조와 `script` 블록의 관리 기준을 설명할 수 있습니다.
3. 최상위와 stage 에 선언한 `agent`·`environment` 의 적용 범위와 `post` 조건의 실행 순서를 예측할 수 있습니다.
4. SCM 과 인라인 Job 정의의 차이와 Folder 플러그인이 이름 충돌을 푸는 원리를 설명할 수 있습니다.
5. 빠른 실패 원칙에 따라 CI 스테이지 순서를 설계하고 품질 게이트의 위치를 판단할 수 있습니다.



## 1. Freestyle 한계와 코드화

> 웹 UI 클릭으로 빌드를 구성하는 Freestyle 은 팀 규모가 커질수록 변경 추적과 복구가 어려워집니다. 파이프라인을 코드로 정의해 애플리케이션 저장소에 두면 수명주기와 리뷰를 일치시킬 수 있습니다.

초기 Jenkins 는 웹 화면에서 마우스 클릭으로 빌드 단계와 셸 명령을 구성했습니다. 프로젝트 수가 적을 때는 직관적이지만 팀 규모가 커지면 한계에 부딪힙니다.

UI 에서 직접 설정을 바꾸면 누가 언제 어떤 이유로 설정을 고쳤는지 Git 커밋 히스토리가 남지 않습니다. 위험한 변경을 PR(Pull Request)로 사전에 검토할 수도 없습니다. 서버 장애나 컨트롤러 교체 시에도 수십 개 Job 의 웹 UI 설정을 하나씩 다시 입력해야 하므로 복구 시간이 길어집니다. 환경마다 별도 Job 을 만들어 관리하다 보면 설정이 어긋나는 문제가 생깁니다.

| 비교 항목 | Freestyle Job | Pipeline as Code |
|---|---|---|
| 변경 추적 | UI 변경 이력이 없어 추적 불가 | Git 커밋 히스토리로 저자·시점·이유 기록 |
| 코드 리뷰 | 설정 변경에 대한 PR 검토 불가 | Jenkinsfile 변경을 코드와 동일하게 리뷰 |
| 장애 복구 | 서버 장애 시 UI 수동 재설정 필요 | Jenkinsfile 이 저장소에 남아 있어 본문을 잃지 않음 |
| 환경 일관성 | 환경별 Job 수동 복제로 설정 불일치 | 단일 파일에서 매개변수 기반 환경 분기 |

Pipeline as Code 는 파이프라인 전체를 `Jenkinsfile` 로 정의하는 방식입니다.[^pipeline-syntax] 애플리케이션 코드 저장소 루트에 함께 두고 관리합니다.

파이프라인을 애플리케이션 코드와 같은 저장소에 두면 둘의 수명주기가 일치합니다. 새 기능 브랜치에서 새로운 빌드 도구나 테스트 단계가 필요하면 해당 브랜치의 Jenkinsfile 만 수정하면 됩니다. 메인 브랜치에는 영향이 없습니다. 기능 머지 시 파이프라인도 함께 승격됩니다. 잘못된 변경이 발생해도 `git revert` 로 파이프라인을 이전 상태로 되돌릴 수 있습니다.



## 2. Declarative 와 script 경계

> Declarative 는 구조가 정해진 DSL 이고 Scripted 는 Groovy 를 거의 그대로 씁니다. 그래서 `script` 블록은 꼭 필요한 곳에만 씁니다.

Jenkins Pipeline 엔진은 Declarative 와 Scripted 라는 두 가지 문법을 제공합니다.[^pipeline-syntax] 둘은 같은 런타임 위에서 돌지만 검증 시점과 에러 처리 방식이 다릅니다.

Declarative 는 `pipeline {}` 블록을 최상위로 쓰는 선언적 DSL 입니다.[^declarative-validation] DSL(Domain-Specific Language)은 한 가지 용도에 맞춰 문법을 좁힌 언어입니다. 유효한 Declarative 는 `pipeline` 블록 안에 `agent` 와 `stages` 를 둡니다. 각 stage 에 실행 내용을 적어야 합니다.[^jenkinsfile] 이 구조를 어기면 유효한 파이프라인이 아닙니다.

정해진 틀이 있어서 어디에 무엇이 있는지 예측할 수 있습니다. 환경 변수·파라미터·`post` 같은 반복 요소는 지시문으로 선언합니다.

Scripted Pipeline 은 `node {}` 블록 안에서 실행되는 Groovy 스크립트입니다.[^pipeline-syntax] 공식 문서는 Groovy 가 제공하는 기능 대부분을 쓸 수 있는 범용 DSL 이라고 설명합니다. 위에서 아래로 순서대로 실행되므로 `if/else`, `try-catch-finally` 로 흐름과 오류를 직접 다룹니다. 구조가 자유로운 만큼 어디서 무엇을 할지는 작성자가 정합니다.

Scripted 는 한 가지 제약을 알아야 합니다. 실행 중인 파이프라인이 컨트롤러 재시작에서 살아남게(durability) 하려고 데이터를 컨트롤러로 직렬화합니다. 그래서 `collection.each { }` 같은 일부 Groovy 관용구는 온전히 지원되지 않습니다.[^pipeline-syntax]

| 비교 항목 | Declarative Pipeline | Scripted Pipeline |
|---|---|---|
| 문법 형태 | 구조화된 DSL (`pipeline {}`) | Groovy 기반 범용 DSL (`node {}`) |
| 구조 | `agent`·`stages`·`steps` 가 필수인 정해진 틀 | 틀이 없고 Groovy 흐름 제어로 구성 |
| 에러 핸들링 | `post {}` 블록으로 선언적 처리 | `try-catch-finally` 직접 작성 |
| 파라미터·환경 변수 | `parameters`·`environment` 지시문 | `properties` step·`withEnv` step |

Declarative 안에서 동적 분기나 복잡한 Groovy 코드가 필요한 경우 `script {}` 블록을 씁니다. 예를 들어 런타임 API 응답에 따라 동적으로 병렬 실행 맵을 구성해야 할 때는 Declarative 정적 문법으로 표현하기 어렵습니다.

하지만 `script` 블록을 남용하면 Declarative 의 장점인 사전 검증과 가독성이 사라집니다. `script` 의 경계는 아래 세 신호로 판단합니다. 숫자 기준은 공식 문서에 없으니 팀이 정합니다.

- 반복: 같은 `script` 패턴이 둘 이상의 Jenkinsfile 에서 반복되면 Shared Library 의 전역 함수로 추출합니다.
- 선언적 대체: 단순 환경 변수 선언이나 브랜치 분기를 script 로 풀고 있다면 `environment` 나 `when` 지시문으로 되돌립니다.
- 크기: `script` 블록이 stage 의 `steps` 본문을 차지할 만큼 커지면, 그 stage 는 사실상 Scripted 이므로 구조를 다시 봅니다.



## 3. 블록 평가 순서와 agent 종류

> 파이프라인 블록은 최상위 지시문 등록, stage 진입과 `when` 평가, steps 실행, post 후처리 순으로 동작합니다. `agent` 는 최상위와 stage 에 둘 수 있고 종류에 따라 호스트 직접 사용부터 Pod 까지 실행 환경이 갈립니다.

Declarative 의 기본 골격은 `pipeline` → `stages` → `stage` → `steps` 순으로 중첩됩니다.[^jenkinsfile] stage 하나는 `steps`, `stages`, `parallel`, `matrix` 중 정확히 하나를 가져야 합니다.[^pipeline-syntax] 일반적인 흐름은 다음과 같습니다.

1. 최상위 지시문 평가: `options`, `triggers`, 최상위 `environment`, `parameters` 를 등록합니다.
2. stage 진입과 조건 평가: `stages` 안의 각 `stage` 로 진입합니다. `when` 조건은 기본적으로 그 stage 의 `agent` 에 들어간 뒤에 평가됩니다. `when` 안에 `beforeAgent true` 를 주면 조건을 먼저 평가합니다. 참일 때만 agent 에 들어가므로 건너뛸 stage 가 Executor 슬롯을 잡지 않습니다.[^pipeline-syntax]
3. 작업 실행: `steps` 블록 안의 step 명령들이 차례로 실행됩니다. `steps` 는 stage 에서 step 이 실제로 실행되는 자리입니다. 중첩 stage 를 쓰면 `stages`, 병렬이면 `parallel` 이 그 자리를 대신합니다.
4. 후처리 평가: stage 레벨의 작업이 끝나면 stage `post` 가 돕니다. 모든 stage 가 완료되면 최상위 `post` 가 돕니다.

`environment` 는 선언한 위치에 따라 모든 step 에 적용되거나 그 stage 의 step 에만 적용됩니다.[^pipeline-syntax] 최상위 값은 파이프라인 전체의 기본 환경입니다. stage 안에 둔 값은 그 stage 범위에서만 쓰입니다.

`agent` 도 둘 위치가 두 곳입니다. 최상위 `agent any` 가 있어도 stage 에 별도 `agent` 를 두면 그 stage 는 지정한 agent 에서 실행됩니다. 최상위에 `agent none` 을 두면 파이프라인 전체에 agent 를 할당하지 않습니다. 이때는 모든 stage 가 자기 `agent` 를 직접 선언해야 합니다.[^pipeline-syntax] 사용자 입력을 기다리는 승인 단계처럼 일을 하지 않는 stage 가 빈 agent 슬롯을 붙잡는 낭비를 이 방식으로 피합니다. `tools` 도 `agent none` 이면 무시됩니다.

`post` 블록의 조건 지시문은 작성 순서와 상관없이 공식 문서가 정한 순서로 평가됩니다.

순서는 `always`, `changed`, `fixed`, `regression`, `aborted` 다음에 `failure`, `success`, `unstable`, `unsuccessful`, 마지막이 `cleanup` 입니다.[^pipeline-syntax]

```groovy
post {
    always { echo 'always 가 가장 먼저' }
    failure { echo 'Build failed' }
    cleanup { cleanWs() }
}
```

`always` 는 결과와 무관하게 먼저 실행됩니다. `cleanup` 은 다른 post 조건을 모두 평가한 뒤 결과와 무관하게 마지막에 실행됩니다.[^pipeline-syntax] 그래서 작업 공간을 비우는 `cleanWs()` 는 `always` 가 아니라 `cleanup` 에 둡니다. `always` 에 두면 뒤에 오는 `failure`·`success` 블록이 이미 지워진 작업 공간에서 돕니다. 거기서 산출물을 읽으려 하면 실패합니다. 반대로 `success` 에만 두면 실패한 빌드의 산출물이 디스크에 남습니다.

`agent` 선언은 stage 가 어디서 어떤 환경으로 실행되는지 정합니다.[^pipeline-syntax]

| 유형 | 실행 환경 | 특징 |
|---|---|---|
| `any` / `label` | 호스트 직접 실행 | Agent 호스트에서 그대로 실행, 빌드 도구가 미리 설치되어 있어야 함 |
| `none` | 해당 없음 | 최상위 Agent 를 잡지 않고 각 stage 로 할당을 위임 |
| `docker` / `dockerfile` | 컨테이너 | 컨테이너 안에서 실행해 빌드 도구 환경을 호스트와 분리, `dockerfile` 은 SCM 에서 읽은 Jenkinsfile 이어야 함 |
| `kubernetes` | Pod | 클러스터의 Pod 안에서 실행, Pod 템플릿은 블록 안에 정의, SCM 에서 읽은 Jenkinsfile 이어야 함 |



## 4. SCM 과 인라인 및 Folder 격리

> 파이프라인 코드는 config.xml 의 definition 클래스에 따라 SCM 추적형과 인라인 스크립트형으로 갈립니다. Folder 플러그인은 full name 계층으로 전역 이름 충돌을 풉니다.

파이프라인 코드는 어디에 저장되느냐에 따라 SCM 방식과 인라인 방식으로 갈립니다. SCM(Source Code Management)은 Git 같은 소스 저장소를 가리키는 Jenkins 용어입니다. Declarative 와 Scripted 어느 쪽이든 둘 다 쓸 수 있습니다.[^getting-started]

Jenkins 는 Job 설정을 컨트롤러 디스크의 `config.xml` 파일로 저장합니다. 파이프라인 코드가 어디 있는지는 Job 이 가진 definition 클래스가 결정합니다.

- SCM 방식 (`CpsScmFlowDefinition`): SCM 설정과 `Jenkinsfile` 경로(`scriptPath`)만 Job 에 둡니다.[^cps-scm] 본문은 저장소에 있어 변경 이력과 PR 리뷰를 Git 이 맡습니다.
- 인라인 방식 (`CpsFlowDefinition`): 스크립트 문자열과 `sandbox` 여부를 Job 자체에 담습니다.[^cps-flow] 공식 문서는 이 방식의 Jenkinsfile 을 Jenkins 가 자기 홈 디렉터리에 저장한다고 설명합니다.[^getting-started] 저장소가 없으니 변경 이력과 PR 리뷰도 없습니다. 코드로 관리한다는 목적과 어긋나서, 공식 문서는 Jenkinsfile 을 소스 관리에 두는 쪽을 모범 사례로 봅니다.[^jenkinsfile]

`sandbox` 는 인라인 스크립트가 Jenkins 내부 API 를 직접 호출하지 못하게 막는 Groovy 샌드박스를 켤지 정하는 값입니다. 샌드박스를 끄고 실행하는 스크립트는 내부 API 를 직접 부를 수 있어서 관리자만 승인할 수 있습니다.[^workflow-cps]

폴더가 없으면 모든 Job 이 한 이름공간에 놓여 Job 이름이 시스템 전체에서 유일해야 합니다. 조직이 커져 두 팀이 똑같이 `deploy` 라는 Job 을 만들려고 하면 이름이 충돌합니다. 이를 피하려고 `team-a-deploy`, `team-b-deploy` 처럼 이름에 접두사를 붙여야 합니다.

Folder 플러그인은 이 문제를 full name 계층으로 해결합니다.[^folder-plugin]

핵심 클래스 `AbstractFolder` 는 `TopLevelItem` 이면서 자식을 담는 `ItemGroup` 도 구현합니다.[^abstract-folder] 폴더가 그 자체로 항목이고 자식의 부모도 되므로, 폴더 안에 폴더를 중첩할 수 있습니다.

```pseudocode
TEAM-A/
  └─ STG/
       └─ deploy    → full name: TEAM-A/STG/deploy
TEAM-B/
  └─ STG/
       └─ deploy    → full name: TEAM-B/STG/deploy
```

Job 은 부모 폴더 안에서만 이름이 유일하면 됩니다. 시스템 전체에서는 경로를 포함한 `full name` 으로 구분됩니다. 두 팀이 같은 `deploy` 라는 이름을 써도 full name 이 다르므로 이름이 충돌하지 않습니다.

폴더는 이름공간 말고도 폴더 단위 크레덴셜 저장소 같은 범위 경계를 줍니다. Folder 플러그인 변경 이력에 Credentials 플러그인의 폴더 기반 저장소를 쓰도록 맞춘 항목이 있습니다.[^folder-plugin] Multibranch Pipeline 의 `MultiBranchProject` 도 `ComputedFolder` 를 거쳐 `AbstractFolder` 를 상속합니다. 브랜치별 Job 을 자식으로 두는 폴더의 한 종류입니다.[^multibranch]

계층마다 `/job/` 세그먼트가 반복됩니다. `TEAM-A/STG/deploy` 의 경로는 `/job/TEAM-A/job/STG/job/deploy/api/json` 이 됩니다.



## 5. 빠른 실패를 위한 스테이지 순서 기준

> CI 파이프라인은 비용이 적고 실패율이 높은 검증을 앞세우는 빠른 실패 원칙으로 순서를 잡습니다. 무거운 이미지 빌드 전에 정적 분석과 품질 게이트를 통과해야 합니다.

CI 파이프라인을 설계할 때 스테이지 순서를 결정하는 핵심 기준은 빠른 실패(Fast Fail)입니다. 실패할 빌드라면 가장 적은 시간과 컴퓨팅 자원을 쓴 이른 시점에 멈춰야 피드백 루프가 빨라집니다.

이 문서가 쓰는 기준 순서는 다음과 같습니다. 공식 문서가 정한 표준이 아니라 이 원칙을 적용한 예입니다.

1. Clone: 소스코드 체크아웃 (모든 검증의 전제 조건)
2. Unit Test: 단위 테스트 실행 (가장 빠르고 빈번한 결함 검출)
3. SCA: 정적 코드 분석과 보안 취약점 스캔
4. Quality Gate: 정적 분석 결과가 기준을 충족하는지 판정
5. Build: 컨테이너 이미지 또는 배포용 바이너리 패키징

단위 테스트가 빌드 앞에 오는 이유는 컴파일과 단위 테스트가 깨진 코드에 무거운 패키징 자원을 투입할 이유가 없기 때문입니다.

정적 분석(SCA)과 Quality Gate 는 Build 앞에 둡니다. 기준을 넘지 못한 코드가 이미지로 만들어져 저장소에 올라간 뒤에 게이트가 막으면, 이미 올라간 산출물을 치우는 비용이 듭니다. 이미지 빌드·배포 절차 자체는 이 편이 다루지 않습니다.

Quality Gate 는 정적 분석 결과를 평가하는 체크포인트이므로 반드시 SCA 분석 단계 뒤에 위치해야 합니다.

## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 다섯 개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — 코드화 이점과 수명주기

Freestyle 은 UI 직접 변경으로 인해 변경 이력 추적과 PR 사전 리뷰가 어렵습니다. Pipeline as Code 는 Jenkinsfile 을 애플리케이션 코드와 같은 저장소에 관리하여 변경 히스토리를 보존하고 브랜치별 격리와 PR 리뷰를 가능하게 합니다.

Freestyle 은 UI 로 바꾸므로 설정이 코드와 따로 놉니다. Pipeline as Code 는 Jenkinsfile 을 애플리케이션 코드와 같은 브랜치에 두어 기능 브랜치마다 파이프라인을 따로 고치고 머지 때 함께 승격합니다.

### 정답 2 — 구조와 script 블록 관리 기준

Declarative 는 `pipeline` 블록 아래 `agent`·`stages`·`steps` 가 필수인 정해진 틀을 따라야 유효합니다. Scripted 는 Groovy 흐름 제어로 구성하고 오류도 `try-catch-finally` 로 직접 다룹니다.

`script` 블록 남용은 세 가지 신호로 봅니다. 둘 이상의 파이프라인에서 비슷한 script 가 반복되면 Shared Library 로 뺍니다. 단순 변수나 조건 분기는 `environment`·`when` 으로 되돌립니다. script 가 stage 본문을 차지할 만큼 크면 구조를 다시 봅니다.

### 정답 3 — 적용 범위와 post 평가 순서

`environment` 는 최상위에 두면 전체 step 에, stage 안에 두면 그 stage 의 step 에 적용됩니다. `agent` 는 stage 에 따로 두면 그 stage 만 지정한 agent 에서 돕니다. 최상위에 `agent none` 을 두면 stage 마다 `agent` 를 선언해야 합니다. 승인 대기 같은 stage 가 agent 슬롯을 잡지 않습니다.

`post` 조건은 `always`, `changed`, `fixed`, `regression`, `aborted`, `failure`, `success`, `unstable`, `unsuccessful`, `cleanup` 순으로 평가됩니다. `cleanWs()` 는 마지막에 돌고 결과와 무관한 `cleanup` 에 둡니다. `always` 는 가장 먼저 돌아, 그 뒤 조건 블록이 지워진 작업 공간에서 실행되기 때문입니다.

### 정답 4 — Job 정의 위치와 Folder 이름공간

SCM 방식(`CpsScmFlowDefinition`)은 Job 에 SCM 과 Jenkinsfile 경로만 두고 본문은 저장소에서 가져오므로 이력 추적과 PR 리뷰를 Git 이 맡습니다. 인라인 방식(`CpsFlowDefinition`)은 스크립트 문자열을 Job 안에 두므로 저장소 이력이 없습니다. 인라인은 `sandbox` 값으로 Groovy 의 내부 API 직접 호출을 막을지 정합니다.

폴더가 없으면 Job 이름이 전역에서 유일해야 합니다. `AbstractFolder` 는 `TopLevelItem` 이면서 `ItemGroup` 이라 폴더 중첩이 됩니다. Job 은 경로를 포함한 `full name` 으로 구분되므로 짧은 이름이 같아도 충돌하지 않습니다.

### 정답 5 — 빠른 실패와 게이트 배치

CI 파이프라인은 빠른 실패 원칙에 따라 비용이 적고 자주 실패하는 검증을 앞에 둡니다. 단위 테스트와 정적 분석, Quality Gate 를 통과하지 못한 코드가 무거운 이미지 빌드로 넘어가면 빌드 자원이 낭비됩니다.

게이트가 이미지 빌드 뒤에 있으면 기준 미달 산출물이 이미 만들어져 저장소에 올라간 뒤라 치우는 비용이 듭니다. 그래서 Quality Gate 는 Build 앞에 둡니다. 이 순서는 공식 규칙이 아니라 원칙을 적용한 설계입니다.
