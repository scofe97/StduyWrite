# Kubernetes 에 Jenkins 를 올리는 이유와 방법

---

> VM 기반 Jenkins 의 설정 표류와 유휴 비용 문제를 Kubernetes 동적 Agent 로 줄이는 원리를 짚습니다. Helm 차트와 JCasC 의 역할 분담, Kubernetes Plugin 의 Pod 생성 흐름, 빌드 캐시와 Pod 격리 기준을 다룹니다.

## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 설명하고 판단할 수 있습니다.

1. VM 기반 정적 Agent 의 설정 표류(Configuration Drift)와 유휴 비용 문제를 설명할 수 있습니다.
2. Helm 차트가 맡는 오브젝트 배포와 JCasC 가 맡는 Jenkins 내부 설정의 경계를 구분할 수 있습니다.
3. Kubernetes Plugin 이 Pod Agent 를 만들고 Controller 에 연결하는 흐름을 설명할 수 있습니다.
4. 캐시 볼륨의 접근 모드(RWO·RWX)가 동시 빌드에 주는 제약과 Pod 격리 원칙을 제시할 수 있습니다.
5. 팀의 파이프라인 규모와 요구 조건에 따라 VM 과 Kubernetes 중 하나를 고를 수 있습니다.



## 1. VM Jenkins 의 한계와 유휴 비용

> 상시 켜 둔 VM Agent 는 빌드가 없을 때도 비용이 들고 수동 변경으로 머신마다 달라집니다. 빌드마다 이미지에서 Pod 를 새로 만들면 두 문제를 함께 줄입니다.

전통적인 Jenkins 환경에서는 Agent VM 을 상시 켜 두고 빌드를 돌렸습니다. 이 방식은 빌드가 없는 심야나 주말에도 VM 자원을 점유해 유휴 비용이 듭니다.

더 큰 문제는 시간이 지날수록 머신 상태가 어긋나는 설정 표류(Configuration Drift)입니다. 누군가 한 Agent 에 도구를 수동으로 설치하거나 패치하면 머신 사이의 환경이 달라집니다. 같은 파이프라인이 머신에 따라 성공하거나 실패하는 이유가 여기서 나옵니다.

Kubernetes 에 올리는 핵심 동기는 빌드 환경을 고정 설비에서 일회용 Pod 로 바꾸는 데 있습니다. 빌드가 시작될 때 정해 둔 이미지로 Pod 를 띄우고, 빌드가 끝나면 Pod 를 지웁니다. 이 모델은 [정적 Agent 와 동적 Agent](01-02.정적%20Agent%20와%20동적%20Agent.md) 의 동적 Agent 를 Kubernetes 위에서 구현한 것입니다.

| 비교 항목 | VM 기반 정적 Agent | Kubernetes Pod Agent |
|---|---|---|
| 유휴 자원 점유 | 빌드가 없어도 VM 이 계속 떠 있음 | Pod 는 빌드 요청 때 생기고 끝나면 지워짐 |
| 환경 일관성 | 수동 패치와 설치가 쌓여 머신마다 달라짐 | 이미지로 정의해 빌드마다 같은 출발선 |
| 잔여물 | 이전 빌드의 파일·프로세스가 남을 수 있음 | Pod 를 지우면 Pod 안 `emptyDir` 도 사라짐 |

이 표에는 두 가지 전제가 붙습니다. 첫째, Pod 를 지워도 Pod 를 담는 클러스터 노드를 줄이지 않으면 노드 비용은 그대로 남습니다. 둘째, 캐시 볼륨처럼 일부러 남기는 저장소는 빌드 사이에 상태를 이어 줍니다(§4).



## 2. Helm 차트와 JCasC 의 역할 분담

> Helm 은 Controller 를 Kubernetes 오브젝트로 배포하고, JCasC 는 Jenkins 안의 설정을 코드로 선언합니다. 공식 차트는 값 일부를 JCasC 로 렌더링해 주므로 두 계층의 경계를 알아야 합니다.

Jenkins 를 Kubernetes 에 올릴 때는 두 종류의 설정이 있습니다. 하나는 StatefulSet·Service·PVC 같은 Kubernetes 오브젝트입니다. 다른 하나는 Jenkins 가 시작할 때 읽는 클라우드·보안·시스템 설정입니다. 둘을 섞어 손으로 관리하면 재현이 어렵습니다.

공식 Jenkins Helm 차트는 앞의 것을 만듭니다.[^helm-values] Controller 는 StatefulSet 으로 배포합니다. 여기에 `JENKINS_HOME` 용 PVC(`persistence`), Agent 접속 Service, Ingress, RBAC 가 따라옵니다. Agent 접속 Service 는 `controller.agentListenerPort`(기본 50000)로 열립니다.

차트의 `controller.numExecutors` 기본값은 0 입니다.[^helm-values] Executor 가 0 이면 Controller 자신(built-in node)에서는 빌드가 돌지 않습니다. 공식 문서에 따르면 built-in node 의 빌드는 Jenkins 프로세스와 같은 수준으로 Controller 파일시스템에 접근합니다.[^isolation] `JENKINS_HOME` 에 시크릿 파일이 있으므로 빌드를 Agent Pod 로 보내 이 접근을 끊습니다.

뒤의 것, 곧 Jenkins 안의 설정은 JCasC(Jenkins Configuration as Code) 플러그인이 YAML 로 읽습니다. 차트는 `controller.JCasC.configScripts` 의 키마다 설정 파일을 만듭니다. Jenkins 가 시작할 때 JCasC 플러그인이 그 파일을 처리합니다.[^helm-readme]

경계가 헷갈리는 지점은 Kubernetes cloud 설정입니다. 차트는 `controller.JCasC.defaultConfig`(기본 true)로 Kubernetes cloud 용 JCasC 를 직접 만듭니다. `agent.containerCap`(기본 10)과 `agent.jenkinsTunnel` 같은 값이 거기에 채워집니다.[^helm-helpers] 그래서 cloud 를 새로 선언하는 `configScripts` 를 따로 쓰기보다 `agent.*` 값을 바꾸는 편이 겹치지 않습니다. `configScripts` 는 차트 값으로 닿지 않는 설정을 넣는 자리입니다.

```yaml
controller:
  numExecutors: 0          # 차트 기본값
  JCasC:
    configScripts:
      system-message: |    # 키는 설정 파일 이름이 됨
        jenkins:
          systemMessage: "Managed as code"
persistence:
  size: "20Gi"             # JENKINS_HOME PVC
agent:
  containerCap: 20         # 클러스터 전체 Agent Pod 상한 (차트 기본 10)
```

정리하면 오브젝트의 모양은 Helm 값이, Jenkins 안의 동작은 JCasC 가 정합니다. 차트 값 일부는 JCasC 로 번역되어 들어가므로 최종 설정은 두 곳의 합입니다.



## 3. 동적 Pod Agent 생성 흐름

> 빌드가 실행기를 요구하면 Kubernetes Plugin 이 PodTemplate 으로 Pod 를 만들고, Pod 안의 inbound agent 가 Controller 에 먼저 연결합니다. 배정과 정리의 상세 규칙은 앞선 편에서 다룹니다.

빌드가 몰려 라벨에 맞는 Executor 가 모자라면 큐의 빌드는 기다려야 합니다. 이때 Kubernetes Plugin 이 새 Pod 를 계획합니다. 큐 아이템이 Executor 를 찾는 과정과 `containerCap` 같은 상한은 [Executor 배정과 동적 Pod](02-03.Executor%20배정과%20동적%20Pod.md) 에서 다뤘습니다. 이 절은 Pod 가 뜨고 연결되는 흐름만 짚습니다.

1. Pod 생성 요청: Plugin 이 PodTemplate 으로 Pod 명세를 만들어 Kubernetes API 서버에 보냅니다.
2. 스케줄링과 기동: Kubernetes 스케줄러가 노드를 골라 이미지를 받고 컨테이너를 실행합니다.
3. Agent 컨테이너: Pod 안에는 Jenkins Agent 를 돌리는 컨테이너가 반드시 하나 있습니다. 템플릿에 따로 지정하지 않으면 이름이 `jnlp` 인 inbound-agent 컨테이너를 Plugin 이 만듭니다.[^k8s-readme]
4. Controller 로 역연결: Agent 가 Controller 에 먼저 연결합니다. 기본은 Agent 용 TCP 포트(차트 기본 50000)입니다. WebSocket 을 켜면 HTTP(S)로 연결합니다.[^k8s-readme] 연결되면 Executor 가 생겨 큐의 빌드를 받습니다.
5. 단계 실행: Controller 가 연결된 Agent 로 파이프라인 단계를 보내 실행합니다.
6. Pod 정리: 빌드가 끝나면 `podRetention` 정책에 따라 Pod 를 지우거나 남깁니다. 정책별 동작과 지워지지 않은 Pod 의 정리는 [podRetention·Garbage Collection](02-04.podRetention·Garbage%20Collection.md) 에서 다룹니다.

연결 방향이 중요합니다. Controller 가 Pod 에 들어가는 것이 아니라 Pod 안의 Agent 가 Controller 로 나옵니다. 그래서 Agent 용 포트나 HTTP(S) 경로가 Agent Pod 에서 닿아야 합니다. §4 의 NetworkPolicy 도 이 길을 열어 두어야 합니다.

PodTemplate 은 컨테이너를 여러 개 둘 수 있습니다. 빌드 도구를 컨테이너별로 나눠 두고 파이프라인에서 `container('maven')` 처럼 명령을 보낼 컨테이너를 고릅니다.[^k8s-readme] 워크스페이스 볼륨의 기본은 `emptyDir` 이므로 같은 Pod 의 컨테이너들이 작업 디렉터리를 공유합니다.[^k8s-readme] 한 컨테이너의 컴파일 결과를 다른 컨테이너가 복사 없이 읽는 이유가 이것입니다.



## 4. 빌드 캐시 관리와 Pod 보안

> `emptyDir` 워크스페이스는 Pod 와 함께 사라지므로 의존성을 매번 다시 받습니다. 캐시 볼륨은 접근 모드에 따라 동시 빌드가 제한되며, 임의 코드를 도는 Agent Pod 는 권한과 네트워크로 격리해야 합니다.

### 빌드 캐시와 접근 모드

동적 Pod 은 빌드가 끝나면 지워지고 기본 워크스페이스인 `emptyDir` 도 함께 사라집니다. Maven 이나 Gradle 의 의존성 캐시도 같이 없어지므로 매 빌드가 원격 저장소에서 의존성을 다시 받아 빌드 시간이 늘어납니다.

이를 줄이려면 캐시 디렉터리에 PVC 를 마운트합니다. Kubernetes Plugin 은 기존 PVC 를 볼륨으로 붙이는 방식을 지원합니다.[^k8s-readme] 이때 PVC 의 접근 모드가 동시 빌드 수를 제한합니다.

- `ReadWriteOnce`(RWO): 볼륨을 한 노드에서만 읽고 쓰기로 마운트할 수 있습니다. 같은 노드에서 도는 Pod 여럿은 같은 볼륨을 쓸 수 있습니다.[^pv-modes]
- `ReadWriteMany`(RWX): 여러 노드에서 읽고 쓰기로 마운트할 수 있습니다.[^pv-modes]

동시 빌드가 여러 노드에 흩어지는 클러스터에서 RWO 캐시 하나를 쓰면, 다른 노드에 뜬 Pod 는 그 볼륨을 마운트하지 못해 기동이 막힙니다. 이를 피하려고 RWX 를 쓰면 여러 Pod 가 같은 캐시 디렉터리에 동시에 씁니다. 이 동시 쓰기를 견디는지는 빌드 도구와 스토리지의 잠금 지원에 달려 있으므로, 쓰기를 공유하지 않는 구조가 더 안전합니다.

그 구조의 예가 Gradle 의 읽기 전용 의존성 캐시입니다. 기존 캐시를 복사해 만든 디렉터리를 `GRADLE_RO_DEP_CACHE` 로 가리킵니다. Gradle 은 이를 읽기 전용으로 참조하고 새로 받는 의존성은 Pod 로컬 캐시에 씁니다.[^gradle-ro] 공식 문서는 이 기능이 incubating 이고 읽기 전용 캐시는 읽기 전용 권한으로 마운트하라고 적습니다. 도구마다 같은 기능이 있는지는 따로 확인해야 합니다. 이미지 빌드 도구와 레이어 캐시는 [컨테이너 아티팩트](../artifact/container/) 에서 다룹니다.

### Pod 격리 세 가지

Agent Pod 은 개발자 코드와 외부 라이브러리의 스크립트를 실행하므로 클러스터 침해의 통로가 될 수 있습니다. 세 가지 격리를 함께 적용합니다.

첫째, Agent Pod 의 ServiceAccount 에 권한을 주지 않습니다. Kubernetes Plugin 의 보안 모델은 신뢰할 수 없는 쪽이 Agent 네임스페이스를 읽기만 하는 것도 막아야 한다고 요구합니다. Pod 를 볼 수 있으면 Agent 로 가장해 Controller 에 붙을 정보를 모을 수 있기 때문입니다. 그래서 Agent Pod 은 자기 네임스페이스 권한이 있는 ServiceAccount 로 돌면 안 됩니다.[^k8s-security]

Agent 가 API 서버를 부를 필요가 없다면 토큰 자동 마운트도 끕니다. `automountServiceAccountToken: false` 는 ServiceAccount 와 Pod 명세 어느 쪽에나 둘 수 있습니다. 둘 다 있으면 Pod 명세가 우선합니다.[^sa-automount] 차트의 `serviceAccountAgent.automountServiceAccountToken` 은 기본이 true 입니다. 끄려면 값을 바꿔야 합니다.[^helm-values]

둘째, Controller 의 Role 을 Agent 를 만들 수 있는 최소로 둡니다. 차트가 만드는 Role 은 Agent 네임스페이스 안에서 다섯 리소스만 다룹니다. `pods`, `pods/exec`, `pods/log`, `persistentvolumeclaims`, `events` 입니다.[^helm-rbac] Secret 읽기 권한은 `rbac.readSecrets` 를 켤 때만 별도 Role 로 붙습니다.[^helm-rbac]

셋째, NetworkPolicy 로 Agent Pod 의 통신 범위를 좁힙니다. 차트의 `networkPolicy.enabled` 기본값은 false 입니다. 켜면 Controller 에 접속할 수 있는 Agent Pod 를 라벨로 제한합니다.[^helm-values] Agent 의 아웃바운드를 Controller 와 필요한 저장소·레지스트리로 좁히는 것은 설계 선택입니다. NetworkPolicy 는 이를 집행하는 네트워크 플러그인이 있어야 효력이 있으므로 클러스터가 지원하는지 먼저 확인합니다.[^np]



## 5. VM 과 Kubernetes 선택 기준

> 부하가 몰리고 서비스마다 도구 버전이 다르면 Kubernetes 동적 Agent 가 유리합니다. 환경이 고정되고 Kubernetes 운영 경험이 부족하면 VM 정적 Agent 가 단순합니다.

Kubernetes 위의 Jenkins 가 언제나 정답은 아닙니다. 워크로드의 모양과 팀의 운영 역량이 선택을 가릅니다.

| 판단 축 | VM 정적 Agent | Kubernetes 동적 Agent |
|---|---|---|
| 빌드 부하 패턴 | 시간대 편차가 적고 예측 가능 | 특정 시간대나 배포 주기에 몰림 |
| 도구 환경 다양성 | 단일·소수 스택 | 서비스마다 JDK·Node 버전이 다름 |
| 운영 역량 | 일반 Linux 서버 운영 지식 | Kubernetes 오브젝트·스토리지·네트워크 지식 필요 |
| 컨테이너로 담기 어려운 빌드 | macOS 빌드처럼 Linux 컨테이너로 못 도는 환경은 별도 노드 필요 | 컨테이너로 담을 수 있는 워크로드 |
| 초기 구성 | VM 준비만으로 시작 | Helm 값, JCasC, 스토리지 설계에 투자 |

이미 Kubernetes 클러스터를 운영하고 서비스마다 런타임이 다르다면 동적 Agent 가 맞습니다. 유휴 Pod 가 없고 빌드 환경이 이미지로 고정되기 때문입니다. 다만 비용은 노드를 함께 줄일 때 내려갑니다.

반대로 파이프라인이 적고 스택이 하나로 고정된 팀은 VM 으로 단순하게 시작하는 편이 낫습니다. Kubernetes 운영 경험이 없는 채로 올리면 Helm·스토리지·네트워크 문제를 Jenkins 문제와 함께 풀어야 합니다.



## 면접에서 받을 만한 질문

1. VM 기반 Jenkins 와 Kubernetes 기반 Jenkins 의 핵심 차이를 유휴 비용과 설정 표류 관점에서 설명해 보세요.
2. Helm 차트와 JCasC 는 Jenkins on Kubernetes 배포에서 각각 무엇을 맡으며, 차트 값과 JCasC 가 겹치는 곳은 어디입니까?
3. Kubernetes Plugin 이 동적 Agent Pod 을 만들고 Controller 와 연결을 맺는 과정을 설명해 보세요. 연결은 어느 쪽이 먼저 맺습니까?
4. 빌드 캐시를 PVC 로 공유할 때 RWO 와 RWX 는 동시 빌드에 어떤 제약을 줍니까?
5. Agent Pod 의 ServiceAccount 권한과 토큰 마운트를 제한해야 하는 이유는 무엇입니까?



## 정답 (자답 후 펼치기)

> 위 면접 질문 5개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — 유휴 비용과 설정 표류

VM Agent 는 빌드가 없는 시간에도 켜져 있어 유휴 비용이 들고, 수동 변경이 쌓여 머신마다 환경이 달라집니다.

Kubernetes 에서는 빌드 때만 Pod 를 만들고 끝나면 지웁니다. 이미지로 환경을 정의하므로 빌드마다 같은 출발선에서 시작합니다. 다만 Pod 를 담는 노드를 줄이지 않으면 노드 비용은 남습니다.

### 정답 2 — Helm 과 JCasC 의 경계

Helm 은 StatefulSet, PVC, Service, Ingress, RBAC 같은 Kubernetes 오브젝트를 배포합니다. JCasC 는 Jenkins 가 시작할 때 읽는 내부 설정을 YAML 로 선언합니다.

겹치는 곳은 Kubernetes cloud 설정입니다. 차트가 `agent.*` 값으로 cloud 용 JCasC 를 직접 만들기 때문에, `containerCap` 같은 값은 차트 값으로 바꾸고 차트가 닿지 않는 설정만 `configScripts` 에 둡니다.

### 정답 3 — 동적 Pod 생성과 연결

빌드가 실행기를 기다리고 맞는 Executor 가 없으면 Kubernetes Plugin 이 PodTemplate 으로 Pod 생성을 API 서버에 요청합니다. 스케줄러가 Pod 를 노드에 올리면 Pod 안의 Agent 컨테이너(기본 이름 `jnlp`)가 기동합니다.

연결은 Agent 가 Controller 로 먼저 맺습니다. 기본은 Agent 용 TCP 포트이고 WebSocket 이면 HTTP(S)입니다. 연결된 Executor 에서 단계가 실행되고, 끝나면 `podRetention` 정책에 따라 Pod 가 정리됩니다.

### 정답 4 — RWO 와 RWX 의 제약

`emptyDir` 워크스페이스는 Pod 와 함께 사라지므로 캐시를 남기려면 PVC 를 붙입니다. RWO 볼륨은 한 노드에서만 마운트되므로 동시 빌드가 여러 노드로 흩어지면 다른 노드의 Pod 가 볼륨을 못 붙입니다.

RWX 는 여러 노드에서 마운트되지만 여러 Pod 가 같은 디렉터리에 동시에 씁니다. 이를 견디는지는 도구와 스토리지에 달려 있으므로, Gradle 의 읽기 전용 의존성 캐시처럼 공유는 읽기만 하고 쓰기는 Pod 로컬에 두는 구조가 안전합니다.

### 정답 5 — ServiceAccount 권한과 토큰

Agent Pod 은 임의의 빌드 스크립트를 실행합니다. 이 Pod 가 자기 네임스페이스 권한이 있는 ServiceAccount 로 돌면 침해된 빌드가 그 권한을 씁니다. Kubernetes Plugin 도 Agent Pod 이 그런 ServiceAccount 로 돌면 안 된다고 요구합니다.

API 서버를 부를 필요가 없으면 `automountServiceAccountToken: false` 로 토큰 파일이 Pod 에 들어가지 않게 합니다. Controller 쪽 Role 도 Agent 네임스페이스의 Pod 관리에 필요한 권한만 두어 피해 범위를 줄입니다.
