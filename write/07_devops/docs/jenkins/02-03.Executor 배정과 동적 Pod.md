# Executor 배정과 동적 Pod

---

> 빈 Executor 가 있다고 바로 일을 받지는 않습니다. 큐는 후보마다 자격 검사를 돌린 뒤 일관 해시로 하나를 고르고, Kubernetes 환경에서는 그 Executor 자체가 큐를 보고 만들어집니다.

## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. 빈 Executor 가 후보에서 빠지는 검사를 `JobOffer.getCauseOfBlockage` 의 순서대로 말할 수 있습니다.
2. 기본 배정 전략이 일관 해시인 이유와 해시 키, 가중치를 설명할 수 있습니다.
3. 배정 결정이 한 번에 하나씩만 일어나는 근거를 소스로 말하고 외부 디스패처와 비교할 수 있습니다.
4. Kubernetes 플러그인이 큐를 보고 Pod 를 만드는 경로와 코어의 기본 전략이 다른 점을 설명할 수 있습니다.
5. 동적 Pod 환경에서 유휴 Executor 수가 0 인 것이 정상인 이유와 대기 원인을 읽는 법을 설명할 수 있습니다.



## 1. 후보 Executor 를 거르는 검사

> 빈 Executor 가 있어도 모든 작업을 받을 수는 없습니다. 라벨, 권한, 플러그인 거부, 노드 상태 가운데 하나라도 걸리면 그 Executor 는 후보에서 빠집니다.

`maintain()` 은 일을 기다리는 Executor 마다 `JobOffer` 를 만듭니다. 그리고 실행 후보 아이템마다 이 제안을 하나씩 검사합니다.

큐 전체의 단계는 [Queue 상태 전이와 Executor 로 가는 길](02-02.Queue%20상태%20전이와%20Executor%20로%20가는%20길.md) §2 에 있습니다. 여기서는 검사 하나를 들여다봅니다.

```java
// Queue.java — JobOffer.getCauseOfBlockage (로그·예외 처리 생략)
Node node = getNode();
if (node == null) return /* 노드가 설정에서 지워짐 */;
CauseOfBlockage reason = node.canTake(item);
if (reason != null) return reason;
for (QueueTaskDispatcher d : QueueTaskDispatcher.all()) {
    reason = d.canTake(node, item);
    if (reason != null) return reason;
}
if (workUnit != null) return /* 슬롯이 이미 쓰이는 중 */;
if (executor.getOwner().isOffline()) return new CauseOfBlockage.BecauseNodeIsOffline(node);
if (!executor.getOwner().isAcceptingTasks()) // Node.canTake (above) does not consider RetentionStrategy.isAcceptingTasks
    return new CauseOfBlockage.BecauseNodeIsNotAcceptingTasks(node);
return null;
```

검사는 위에서부터 차례로 돌고 처음 걸린 이유를 돌려줍니다.[^job-offer]

- 노드 존재: 설정에서 지워진 노드의 Executor 는 받지 않습니다.
- `Node.canTake`: 작업이 요구한 라벨을 노드가 가졌는지 봅니다. 라벨 없는 작업은 `EXCLUSIVE` 모드 노드에 가지 못합니다. 작업을 실행할 사용자에게 그 노드의 빌드 권한이 있는지, 노드 속성(`NodeProperty`)이 막지 않는지도 봅니다.[^node-cantake]
- `QueueTaskDispatcher`: 플러그인이 배정을 거부하는 확장 지점입니다. 큐는 이 응답을 기억하지 않고 매번 다시 묻습니다.[^dispatcher] 그래서 준비되면 null 만 돌려주면 되어 일시적인 차단을 쉽게 만들 수 있지만 판단은 빨라야 합니다.
- 노드 상태: 슬롯이 이미 쓰이는 중인지, 노드가 오프라인인지 봅니다. 마지막으로 `RetentionStrategy` 가 새 작업을 받는지 확인합니다. 코드 주석대로 앞의 `Node.canTake` 는 이 조건을 보지 않기 때문입니다.[^accepting]

거부 이유는 `CauseOfBlockage` 객체로 남습니다. 맞는 Executor 를 하나도 못 찾은 아이템은 이 이유들을 붙인 채 `buildables` 에 남습니다.[^transient-cause] 큐 아이템 API 의 `why` 필드가 사람이 읽을 대기 이유를 보여 줍니다.[^why]



## 2. 일관 해시와 워크스페이스 캐시

> 후보가 여럿이면 같은 작업은 되도록 같은 노드로 보냅니다. 그 노드에 남은 워크스페이스를 다시 쓰기 위해서입니다.

빌드는 Agent 의 워크스페이스에 체크아웃과 의존성 캐시를 남깁니다. 같은 작업이 매번 다른 노드로 가면 이 캐시를 쓰지 못하고 처음부터 받습니다.

검사를 통과한 후보는 `MappingWorksheet` 에 담겨 `LoadBalancer` 로 넘어갑니다. 기본 구현은 `LoadBalancer.CONSISTENT_HASH` 입니다.[^consistent-hash]

```java
// LoadBalancer.java — CONSISTENT_HASH 의 핵심 (발췌)
ConsistentHash<ExecutorChunk> hash = new ConsistentHash<>(ExecutorChunk::getName);
List<ExecutorChunk> chunks = ws.works(i).applicableExecutorChunks();
for (ExecutorChunk ec : chunks) {
    toAdd.put(ec, ec.size() * 100);   // 후보 Executor 가 많은 노드일수록 가중치가 큼
}
// ...
key = task.getAffinityKey();          // 기본값: 작업의 전체 이름
for (ExecutorChunk ec : hashes.get(i).list(key)) { /* 링 순서대로 배정 시도 */ }
```

`ExecutorChunk` 는 한 노드에 속한 후보 Executor 묶음입니다. 해시 링에는 노드 단위로 점이 찍히고 후보 Executor 가 많은 노드일수록 점이 많습니다. 키는 `getAffinityKey()` 이며 기본값은 작업의 전체 이름입니다.[^affinity-key] 같은 작업은 매번 같은 키로 링을 돌므로 같은 후보 집합이면 같은 노드부터 시도합니다.

해시 링은 배정할 때마다 그 순간의 후보만으로 새로 만듭니다. 그래서 선호 노드가 바쁘면 링에 아예 없고 링 위의 다음 노드가 일을 받습니다. 노드 하나가 늘거나 줄어도 다른 작업들의 선호 노드는 대부분 그대로입니다. 일관 해시가 바뀐 노드 근처의 키만 옮기기 때문입니다.

아래 표는 같은 알고리즘을 쓰는 분산 캐시(Memcached 클라이언트 같은)와 쓰임새를 비교합니다.

| 비교 항목 | Jenkins 기본 배정 | 분산 캐시의 일관 해시 |
|---|---|---|
| 링에 오르는 것 | 지금 비어 있는 후보 노드 | 데이터를 맡은 모든 노드 |
| 키가 다른 노드로 가면 | 워크스페이스 캐시를 못 씀 (느려짐) | 데이터를 못 찾음 (조회 실패) |
| 역할 | 선호를 주는 최적화 | 데이터 위치를 정하는 규칙 |



## 3. 배정은 큐의 락 안에서만

> 배정 결정은 큐의 락을 쥔 스레드 하나만 내립니다. 그래서 두 작업이 같은 Executor 를 동시에 차지하는 경쟁이 생기지 않습니다.

빈 Executor 하나를 두 결정자가 동시에 보고 서로 다른 빌드를 넣으면 실행이 충돌합니다. 이 경쟁을 막으려면 배정을 한 번에 하나씩만 해야 합니다.

`LoadBalancer` javadoc 은 `map()` 을 부르는 스레드가 항상 `Queue` 의 락을 쥐고 있다고 적습니다.[^lb-lock] 후보 수집, 자격 검사, `map()` 호출은 모두 `maintain()` 안에서 일어납니다. 그리고 `maintain()` 은 큐의 단일 락을 잡습니다. 그 락의 구조는 [Queue 상태 전이와 Executor 로 가는 길](02-02.Queue%20상태%20전이와%20Executor%20로%20가는%20길.md) §2 에서 다뤘습니다.

이 보장은 한 JVM 안의 락에서 옵니다. Jenkins 앞에 여러 인스턴스로 된 별도 디스패처를 두고 그 디스패처가 직접 배정을 정한다면, 같은 보장을 공유 저장소의 락으로 다시 만들어야 합니다.

큐는 쌓이는 개수에도 상한을 두지 않습니다. `scheduleInternal` 은 중복만 확인합니다. 큐 길이를 보고 요청을 거절하는 코드는 없습니다.[^no-limit] 외부 서비스가 빌드를 쏟아 넣을 수 있다면 큐 길이를 보고 요청을 멈추는 장치는 호출 측에 둬야 합니다.



## 4. 큐를 보고 Pod 를 만드는 길

> Kubernetes 플러그인 환경에서는 Executor 가 미리 있지 않습니다. 큐에 일이 쌓이면 Pod 를 만들고 Pod 의 Agent 가 연결된 뒤에야 위의 배정이 일어납니다.

모니터링 화면에서 유휴 상태의 Executor 총량이 0 으로 나오면 장애로 보기 쉽습니다. 정적 Agent 는 빌드가 없어도 슬롯이 떠 있지만 동적 Pod 환경에서는 빌드가 없으면 Pod 도 없습니다. 이때 0 은 정상입니다.

노드를 새로 만들지 판단하는 일은 코어의 `NodeProvisioner` 가 맡습니다. 이 클래스는 `LoadStatistics` 의 부하 통계를 보고 `Cloud` 에 새 노드를 요청합니다.[^node-provisioner] 기본 전략은 일시적인 급증에 과하게 반응하지 않으려고 지금 값과 지수 이동 평균 가운데 보수적인 값을 씁니다.[^standard-strategy] 그래서 큐에 일이 들어와도 노드 요청이 조금 늦게 나갈 수 있습니다.

Kubernetes 플러그인은 이 지연을 줄이는 `NoDelayProvisionerStrategy` 를 더 높은 순서(ordinal 100)로 등록합니다. javadoc 은 작업이 큐에 들어오면 곧바로 새 노드를 만든다고 적습니다. Kubernetes Agent 는 빨리 만들고 없앨 수 있어 기다릴 필요가 없다는 것이 이유입니다.[^no-delay] 이 전략은 시스템 속성 `io.jenkins.plugins.kubernetes.disableNoDelayProvisioning` 으로 끕니다.

요청을 받은 `KubernetesCloud.provision` 은 Pod 템플릿마다 Executor 1개짜리 노드를 계획합니다.[^k8s-provision] 계획할 때마다 `KubernetesProvisioningLimits` 가 상한 두 개를 확인합니다. 클라우드 전체의 `containerCap` 과 템플릿별 `instanceCap` 입니다.[^k8s-limits] `containerCap` 을 설정하지 않으면 상한은 `Integer.MAX_VALUE` 입니다.[^container-cap] 상한에 닿으면 새 Pod 계획이 멈추고 남은 아이템은 맞는 Executor 가 없는 채로 큐에 남습니다.

Pod 가 뜨고 그 안의 Agent 가 Controller 에 연결되면 Executor 가 생깁니다. 다음 `maintain()` 이 이 Executor 를 후보로 모아 §1 과 §2 의 배정을 진행합니다. 빌드가 끝난 Pod 가 얼마나 남는지는 `idleMinutes` 같은 설정이 정합니다. 이 설정은 [정적 Agent 와 동적 Agent](01-02.정적%20Agent%20와%20동적%20Agent.md) §2 에서 다뤘습니다.

| 비교 항목 | 정적 Agent | Kubernetes 동적 Pod |
|---|---|---|
| Executor 가 생기는 때 | Agent 를 연결할 때 미리 | 큐에 일이 쌓인 뒤 Pod 가 연결될 때 |
| 유휴 시 Executor 수 | 설정한 슬롯 수 | 0 일 수 있음 (정상) |
| 대기 원인 | 맞는 슬롯이 모두 바쁨 | Pod 기동·연결 대기, 또는 `containerCap` 도달 |
| 동시 실행 상한 | 노드 수 × 노드별 슬롯 수 | `containerCap`, `instanceCap` |

큐 길이만으로는 두 대기를 구분할 수 없습니다. Pod 가 뜨는 중인지, 상한에 걸려 Pod 를 더 만들지 못하는지에 따라 할 일이 다릅니다. 그래서 큐 아이템의 `why` 와 현재 Pod 수를 함께 봐야 합니다.



## 면접에서 받을 만한 질문

1. 빈 Executor 가 있는데도 빌드가 그 Executor 로 가지 않는 이유를 검사 순서대로 설명해 보세요.
2. 플러그인이 특정 노드로의 배정을 잠시 막고 싶다면 어떤 확장 지점을 쓰며, 큐는 그 응답을 어떻게 다룹니까?
3. 기본 배정 전략이 라운드로빈이 아니라 일관 해시인 이유는 무엇이며, 해시 키와 가중치는 무엇입니까?
4. Kubernetes 플러그인 환경에서 큐에 빌드가 들어온 뒤 Pod 가 생기고 배정되기까지의 경로를 설명해 보세요.
5. 동적 Pod 환경에서 큐 대기가 길어졌을 때, Pod 기동 지연과 `containerCap` 도달을 어떻게 구분합니까?

> 다섯 질문에 먼저 스스로 답해 보세요. 자답이 끝나면 아래 §정답 (자답 후 펼치기) 으로 내려갑니다.



## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 다섯 개에 먼저 자답한 뒤 아래를 읽으세요.

### 정답 1 — JobOffer 의 검사 순서

`JobOffer.getCauseOfBlockage` 는 먼저 노드가 남아 있는지 봅니다. 이어 `Node.canTake` 가 라벨, `EXCLUSIVE` 모드, 빌드 권한, 노드 속성을 검사합니다. 그다음 `QueueTaskDispatcher` 들에게 묻고, 마지막으로 슬롯 사용 여부와 오프라인, `RetentionStrategy` 의 작업 수락 여부를 봅니다. 하나라도 걸리면 그 이유가 `CauseOfBlockage` 로 남습니다.

### 정답 2 — QueueTaskDispatcher

`QueueTaskDispatcher` 를 구현해 등록합니다. 큐는 응답을 캐시하지 않고 `maintain()` 이 돌 때마다 다시 묻습니다. 그래서 막을 동안 이유를 돌려주다가 준비되면 null 을 돌려주면 됩니다. 대신 자주 불리므로 판단이 빨라야 합니다.

### 정답 3 — 일관 해시의 키와 가중치

같은 작업을 같은 노드로 보내 워크스페이스 캐시를 다시 쓰기 위해서입니다. 키는 `getAffinityKey()` 로, 기본값은 작업의 전체 이름입니다. 링에는 지금 후보인 노드만 오르고, 후보 Executor 수에 100 을 곱한 값이 가중치입니다. 선호 노드가 바쁘면 링의 다음 노드가 받으므로 잃는 것은 캐시 재사용뿐입니다.

### 정답 4 — 프로비저닝에서 배정까지

큐에 일이 들어오면 `NoDelayProvisionerStrategy` 가 기다리지 않고 `KubernetesCloud` 에 노드를 요청합니다. 클라우드는 상한을 확인하고 Executor 1개짜리 Pod 를 계획합니다. Pod 의 Agent 가 Controller 에 연결되면 Executor 가 생기고 다음 `maintain()` 이 그 Executor 를 후보로 삼아 일반 배정을 진행합니다.

### 정답 5 — 대기 원인 구분

큐 길이만으로는 구분되지 않습니다. 현재 Pod 수가 `containerCap` 에 닿았는지 확인하고 큐 아이템의 `why` 필드로 대기 이유를 함께 봅니다. Pod 수가 상한보다 작은데 대기가 길면 Pod 기동이나 Agent 연결이 늦은 것입니다.
