## 2. 오답 상세 해설 (20문항)

### 섹션 1 — DevOps 기본

#### 1번. DevOps의 핵심 목적 (제출 D → 정답 **B**)

**왜 B인가.** DevOps의 정의 자체를 묻는 문제다. 핵심은 개발(Dev)과 운영(Ops)을 하나의 흐름으로 잇는 것 — 개발·테스트·배포·운영을 자동화하고 두 팀의 협업을 강화하는 것이다.

**왜 D가 틀렸나.** D(운영을 전담 조직으로 몰아 개발자와 분리)와 A(책임 완전 분리)는 정확히 DevOps가 깨부수려는 대상이다. 전통적으로 개발팀은 "코드 던지면 끝", 운영팀은 "받아서 굴리기"로 벽(silo)이 있었고, 이 벽 때문에 장애와 배포 지연이 생겼다. DevOps는 이 벽을 없애는 운동이라 D는 정반대 답이다. "운영을 전담화한다"는 얼핏 효율적으로 들리지만 DevOps 맥락에선 사일로 강화 = 안티패턴이다.

**연결.** 9번 "You build it, you run it"(당신이 만들었으면 당신이 굴린다)과 정반대 개념이다. 두 문항을 짝으로 기억한다.

#### 5번. shift-left의 의미 (제출 D → 정답 **B**)

**개념부터.** 파이프라인을 왼쪽(개발 초기) → 오른쪽(운영 배포)으로 흐르는 수평선이라고 본다.

```
[코딩] → [빌드] → [테스트] → [배포] → [운영]
 왼쪽 ───────────────────────────────→ 오른쪽
```

전통 방식은 보안 검사·테스트·품질 검사를 오른쪽(배포 직전이나 운영 후)에서 했다. 문제는 그때 버그를 발견하면 이미 손볼 게 많아 수정 비용이 크다는 것이다. **shift-left는 이 검사들을 왼쪽(개발 초기)으로 당기는 것**이다. 코딩하는 순간부터 정적 분석·보안 스캔·테스트를 돌려 결함을 일찍 잡는다. 일찍 잡을수록 싸게 고친다.

**왜 D가 틀렸나.** D(테스트를 운영 배포 이후로 미룸)는 정확히 반대 방향, 즉 shift-right에 가깝다. 이름 그대로 "왼쪽으로 당긴다"만 기억하면 헷갈리지 않는다.

**연결.** shift-left = 검사를 앞당김(예방). shift-right = 운영 환경에서 관찰·실험(카나리·프로덕션 모니터링). 둘 다 유효하지만 방향이 반대다. 10번 "피드백 루프를 짧게"와 같은 철학이고, 97·98번 SAST/DAST가 shift-left의 실제 보안 도구다.

### 섹션 2 — Git·브랜치

#### 13번. trunk-based development (제출 C → 정답 **B**)

**개념부터.** trunk는 나무의 몸통(줄기) — Git에서는 `main`/`master` 브랜치를 뜻한다. 가지(branch)가 아니라 몸통이다. **trunk-based development(TBD)** 는 긴 가지를 만들지 않고 몸통(main)에 아주 작은 단위로 매우 자주 통합하는 전략이다. 하루에도 여러 번 main에 머지하고, 브랜치를 쓰더라도 수명이 몇 시간~하루로 아주 짧다.

**왜 이렇게 하나.** 15번(장기 feature branch의 위험)에서 본 그 이유다. 브랜치가 오래 살수록 main과 벌어져 병합 충돌·통합 리스크가 커지니까, 아예 자주 합쳐서 그 격차가 쌓일 틈을 안 준다. 이게 CI(Continuous **Integration**, 지속적 "통합")의 원래 정신과 정확히 맞닿는다.

**왜 C가 틀렸나.** C(배포용 브랜치를 연 1회만 생성)는 통합을 극도로 미루는 방식이라 TBD 철학과 정반대다. D(리뷰를 두지 않는다)도 흔한 오해인데, TBD도 리뷰를 한다 — 단지 작은 PR을 빠르게 리뷰할 뿐이다.

| | feature branch 전략 | trunk-based development |
|---|---|---|
| 브랜치 수명 | 길 수 있음(기능 완성까지) | 매우 짧음(몇 시간~하루) |
| main 통합 빈도 | 드물게 | 매우 자주(하루 여러 번) |
| 위험 | 오래되면 충돌·통합 리스크↑ (15번) | 통합 격차가 안 쌓임 |
| 장점 | 기능 단위 독립 개발·리뷰 (14번) | 빠른 피드백, CI 정신에 부합 |

### 섹션 4 — 빌드·테스트·품질

#### 33번. flaky test의 의미 (제출 A → 정답 **B**)

**개념부터.** flaky는 "잘 부스러지는, 변덕스러운"이라는 뜻이다. **flaky test는 코드를 하나도 안 바꿨는데도 어떤 때는 통과(green), 어떤 때는 실패(red)하는 불안정한 테스트**다.

**왜 A가 틀렸나.** A(항상 성공하도록 고정된 테스트)는 정반대다. flaky의 핵심은 결과가 "고정"이 아니라 "왔다갔다"라는 것이다.

**왜 생기나.** 테스트가 불확실한 것에 의존할 때다.
- 시간·순서: `sleep(100)` 후 결과를 보는데 가끔 100ms로 부족
- 실행 순서: 테스트 A가 남긴 데이터에 테스트 B가 의존
- 외부 자원: 네트워크·실제 DB·랜덤 값

이 변덕을 없애는 작업을 flaky test hardening(단단하게 만들기)이라 한다.

#### 34번. flaky test를 방치하면 안 되는 이유 (제출 C → 정답 **D**)

**왜 D인가.** 33번과 한 세트다. flaky test를 내버려두면 CI 신뢰도가 떨어지고 진짜 실패를 무시하게 된다. 메커니즘이 중요하다 — 테스트가 자꾸 이유 없이 빨간불이 뜨면 개발자들은 "아 또 flaky네, 그냥 재실행하자"를 학습한다. 이 습관이 들면 어느 날 진짜 버그로 빨간불이 떠도 "또 flaky겠지" 하고 무시한다. **양치기 소년 효과**다. CI의 존재 이유(문제를 빨리 알려주는 것)가 무력화된다.

**왜 C가 틀렸나.** C(코드 리뷰 절차가 불필요해진다)는 flaky와 아무 인과관계가 없다.

**연결.** 29번(retry 주의점)에서 본 "재시도가 비결정적 실패를 숨기지 않도록"이 바로 이 얘기다. flaky를 retry로 덮으면 원인이 가려진다. 34번과 29번을 연결해서 기억한다. 91번 alert fatigue와도 같은 심리 구조(둔감화)다.

#### 36번. contract test가 유용한 경우 (제출 A → 정답 **C**)

**개념부터.** contract(계약) test는 서비스 간 API "계약"이 지켜지는지 검증하는 테스트다. MSA(마이크로서비스)에서 특히 중요하다.

상황을 그리면 — 주문 서비스(consumer)가 결제 서비스(provider)의 API를 호출한다. 계약은 "결제 API는 `{amount, currency}`를 받아 `{status, txId}`를 준다" 같은 약속이다. 어느 날 결제팀이 응답 필드명을 `txId`→`transactionId`로 바꾸면 주문 서비스가 깨진다. 그런데 각자 단위 테스트만 돌리면 이 깨짐을 못 잡는다 — 두 서비스가 따로 놀기 때문이다. contract test는 이 약속이 깨졌는지를 양쪽에서 자동으로 검증한다. 대표 도구는 Pact, Spring Cloud Contract다.

**왜 A가 틀렸나.** A(UI 색상·폰트 검증)는 시각적 회귀 테스트(visual regression) 쪽이라 무관하다.

| | integration test (35번) | contract test (36번) |
|---|---|---|
| 검증 대상 | 컴포넌트들이 실제로 같이 돌 때의 흐름 | 서비스 간 API "약속(스키마)"의 준수 |
| 실행 방식 | 실제 의존 서비스를 띄워야 함(무겁다) | 계약 문서 기준으로 각자 독립 검증(가볍다) |
| MSA에서 강점 | 통합 확인 | 상대 서비스 없이도 계약 깨짐 감지 |

#### 37번. 빌드 캐시의 장점 (제출 C → 정답 **A**)

**왜 A인가.** 빌드 캐시는 이전 빌드에서 이미 한 작업 중 변경되지 않은 부분을 재사용해 빌드 시간을 줄이는 것이다. 예를 들어 Gradle/Maven이 안 바뀐 모듈은 재컴파일하지 않고, Docker가 안 바뀐 레이어를 캐시에서 가져온다(44번 multi-stage build, 이미지 레이어와 연결). 소스 100개 중 1개만 고쳤으면 나머지 99개를 다시 빌드할 이유가 없다.

**왜 C가 틀렸나.** C(운영 장애를 로그에서 숨긴다)는 캐시와 전혀 무관하다. 애초에 "숨긴다/삭제한다" 류의 보기는 이 퀴즈에서 거의 항상 오답이다 — 관찰 가능성·추적성을 해치는 행위라서다. 이 패턴을 소거 기준으로 삼는다.

#### 38번. reproducible build의 의미 (제출 A → 정답 **D**)

**개념부터.** reproducible(재현 가능한) build는 같은 소스·같은 환경에서 빌드하면 언제 누가 하든 바이트 단위로 동일한 산출물이 나오는 빌드다.

**왜 A가 틀렸나.** A(실행할 때마다 다른 산출물이 나온다)는 정확히 반대 — 그건 "재현 불가능한" 빌드다.

**왜 중요한가.**
- 신뢰: 내가 빌드한 것과 CI가 빌드한 것이 같다고 보장 → "내 컴퓨터에선 됐는데" 문제 제거
- 보안(공급망): 소스에서 나온 바이너리가 정말 그 소스에서 나온 게 맞는지 검증 가능 → 100번 provenance, SLSA와 직결
- 방해 요소: 빌드에 타임스탬프·랜덤 값·절대 경로가 섞이면 매번 달라져 재현성이 깨진다. 그래서 이런 걸 제거한다.

**연결.** 39번 dependency lock file(의존성 버전 고정)이 재현성을 만드는 핵심 수단이다 — 버전이 고정돼야 매번 같은 산출물이 나온다. 38·39번을 "재현성" 한 묶음으로, 그리고 100번 provenance의 기술적 토대로 기억한다.

### 섹션 5 — Docker

#### 50번. `.dockerignore`의 목적 (제출 C → 정답 **D**)

**먼저 빌드 컨텍스트 개념.** `docker build .` 을 실행하면 Docker는 그 `.`(현재 디렉터리)의 모든 파일을 통째로 Docker 데몬에 먼저 전송한다. 이 전송되는 파일 묶음이 빌드 컨텍스트(build context)다. 문제는 이 폴더에 이미지에 들어갈 필요 없는 것들이 섞여 있다는 것이다 — `.git/`(버전 이력 전체, 수백 MB일 수도), `node_modules/`, 빌드 산출물, `.env`·키 파일 같은 민감 정보, 로컬 로그·임시 파일.

**왜 D인가.** `.dockerignore`는 `.gitignore`와 똑같은 방식으로 이 빌드 컨텍스트에서 제외할 파일 목록을 적는 파일이다. 효과는 두 가지 — 전송량이 줄어 빌드가 빨라지고, 이미지에 쓸데없는/민감한 파일이 안 들어간다(`.env` 실수 포함 방지).

**왜 C가 틀렸나.** C(운영 DB를 자동 백업)는 완전히 무관하다. "`.gitignore`의 Docker 버전"이라고 기억하면 안 헷갈린다.

**연결.** 45번(이미지에 secret을 넣지 마라)과 이어진다. `.env`를 `.dockerignore`에 넣으면 실수로 `COPY . .` 해도 secret이 이미지에 안 들어간다.

> **참고 — 45번 심화(정답은 맞혔지만 원리 정리).** 이미지에 secret을 넣으면 안 되는 이유의 핵심은 "이미지 레이어는 지워도 안 지워진다"는 성질이다. Docker 이미지는 여러 겹의 레이어를 쌓은 구조이고, 각 명령(`COPY`·`RUN`)이 한 겹씩 만든다. 앞 레이어에서 secret을 복사한 뒤 뒷 레이어에서 `rm`으로 지워도 앞 레이어에는 그대로 남아 `docker history`로 노출된다. 그래서 secret은 이미지에 굽지 않고 실행 시점에 주입한다(환경 변수·볼륨·K8s Secret·BuildKit `--secret`). 27번의 "secret은 secret store로" 원칙의 컨테이너 버전이다.

### 섹션 9 — Observability·SRE

> 이 섹션이 이번 퀴즈에서 가장 낯설었다. 먼저 큰 그림을 세우고 개별 문항으로 들어간다.

**관측성 3신호 (82번에서 맞힌 뼈대).** OpenTelemetry의 세 신호는 Logs·Metrics·Traces다.
- **Log(85번)**: 개별 사건 기록. "14:03 결제 실패, userId=5"
- **Metric(84번)**: 수치 시계열. CPU 80%, 요청 200/s, 에러율 2%
- **Trace(83번)**: 요청 하나가 여러 서비스를 거친 경로·지연

그 위에 **SRE(Site Reliability Engineering)** 가 "얼마나 안정적이어야 하는가"를 숫자로 정의하는 용어 4형제를 얹는다: SLI → SLO → Error Budget → MTTR. 이게 87~95의 핵심이다.

#### 87번. USE 지표 (제출 A → 정답 **D**)

**왜 D인가.** 86번 RED는 맞혔다 — **R**ate(요청률), **E**rrors(에러 수), **D**uration(응답 시간)으로 서비스(요청을 받는 것)를 볼 때 쓴다(사용자 관점). 87번 USE는 그 짝으로 자원(서버·디스크·CPU)을 볼 때 쓴다 — **U**tilization(사용률), **S**aturation(포화도, 대기열이 쌓인 정도), **E**rrors(에러).

**왜 A가 틀렸나.** A(User, Session, Event)는 U·S·E로 시작하는 단어를 억지로 붙인 함정이다.

| | RED (86번) | USE (87번) |
|---|---|---|
| 대상 | 서비스(요청 흐름)를 밖에서 | 자원(머신)을 안에서 |
| 구성 | Rate · Errors · Duration | Utilization · Saturation · Errors |
| 관점 | 사용자가 겪는 것 | 시스템이 겪는 것 |

> 둘 다 세 번째가 Errors인 것도 기억 포인트.

#### 89번. SLO의 의미 (미응답 → 정답 **B**) · 90번. Error Budget (미응답 → 정답 **C**)

이 둘은 88번 SLI와 한 몸이라 같이 본다. 예로 "응답 시간"을 든다.

- **SLI** (Service Level **Indicator**, 지표): 실제로 측정한 값. "지난 30일간 요청의 99.2%가 300ms 안에 응답했다." → 현실의 측정치. (88번, 맞힘)
- **SLO** (Service Level **Objective**, 목표): 그 SLI에 대해 우리가 세운 목표. "요청의 99.9%는 300ms 안에 응답해야 한다." → 목표 수준. (89번)
- **Error Budget** (오류 예산): SLO가 99.9%라면 나머지 0.1%는 실패해도 되는 허용 여유분. (90번)

**Error Budget이 왜 중요한가.** "실패 0%"는 불가능하고 오히려 혁신을 막는다. 그래서 SRE는 "0.1%까지는 실패해도 된다"고 예산처럼 할당한다. 예산이 남으면 마음껏 새 기능을 배포하고(위험 감수 OK), 예산을 다 쓰면(장애가 많았으면) 배포를 멈추고 안정화에 집중한다. 이게 개발팀(빨리 배포하고 싶음)과 운영팀(안정성 지키고 싶음)의 갈등을 숫자 하나로 중재한다. 그래서 90번 보기 B("어떤 상황에서도 배포 금지")가 오답이다 — Error Budget은 배포를 금지하는 게 아니라 예산 안에서는 허용하는 개념이다.

**혼동 주의 — SLA.** SL**I**/SL**O**는 흔히 **SLA**(Agreement, 계약)와 섞인다. SLA는 고객과의 법적 계약(어기면 배상)이다. 88번 보기 B(위반 시 벌금)가 바로 SLA를 가리키는 함정이었다.

> 순서: **SLI(측정) → SLO(내부 목표) → SLA(외부 계약, 보통 SLO보다 느슨).** Error Budget = 1 − SLO.

#### 91번. Alert fatigue의 원인 (제출 A → 정답 **D**)

**왜 D인가.** alert fatigue(알림 피로)는 중요하지 않은 알림이 너무 많이 와서 정작 중요한 알림을 놓치게 되는 현상이다. 하루에 알림이 500개 오면 사람은 다 무시하게 되고 그 속에 묻힌 진짜 장애 알림을 놓친다.

**왜 A가 틀렸나.** A(알림이 전혀 안 온다)는 정반대다. fatigue는 "너무 많아서" 생긴다.

**연결.** 34번의 flaky test → 실제 실패를 무시와 정확히 같은 심리 구조(둔감화)다. 해법은 92번(맞힘)의 "증상 기반, 조치가 필요한 알림만"이다. "CPU 1% 올랐다"가 아니라 "사용자가 결제를 못 한다" 수준의 행동이 필요한 것만 알린다.

#### 93번. MTTR의 의미 (미응답 → 정답 **B**)

**왜 B인가.** 약어를 풀면 바로 답이다. MTTR = Mean Time To Recovery(또는 Repair), 평균 복구 시간. 장애가 터진 뒤 정상으로 돌아오기까지 걸린 평균 시간이다.

**연결 — DORA 4대 지표.** 이건 SRE 용어이자 DORA 4대 지표 중 하나다(퀴즈 도입부에 나온 그 DORA).
1. Deployment Frequency — 얼마나 자주 배포하나 (속도)
2. Lead Time for Changes — 커밋부터 배포까지 걸리는 시간 (속도)
3. Change Failure Rate — 배포 중 장애를 낸 비율 (안정성)
4. MTTR — 장애 복구까지 평균 시간 (안정성) ← 93번

앞 2개는 "얼마나 빠른가", 뒤 2개는 "얼마나 안정적인가"다. 좋은 팀은 넷 다 좋다(6번에서 맞힌 "속도와 안정성이 함께 개선").

#### 94번. postmortem의 목적 (미응답 → 정답 **C**) · 95번. blameless culture (미응답 → 정답 **D**)

**postmortem(94번).** 원래 "부검"이라는 뜻인데, IT에서는 장애가 끝난 뒤 원인을 분석하고 재발 방지책을 도출하는 사후 회고 문서/회의다. 장애 → 복구 → "왜 일어났나? 어떻게 하면 다시 안 일어나나?"를 타임라인·근본 원인·재발 방지 액션으로 기록한다.

**blameless culture(95번).** 장애가 났을 때 "누가 잘못했냐"로 개인을 비난하지 않고 "시스템의 어떤 허점이 이 실수를 가능하게 했나"에 집중하는 문화다. 사람을 비난하면 다음부터 사람들이 장애를 숨긴다 — "내가 터뜨렸다고 하면 혼나니까 조용히 덮자." 그러면 원인을 못 배우고 같은 장애가 반복된다. 반대로 비난하지 않으면 사람들이 솔직하게 말하고 팀은 "그게 가능했던 시스템 구조가 문제였네"라고 배운다.

**두 문항은 한 세트.** postmortem을 비난 없이(blameless) 해야 사람들이 진실을 말하고 진짜 학습이 일어난다. 2번(빠른 피드백·지속적 개선), 10번(피드백 루프)에서 맞힌 DevOps 문화의 정점이다. 94번 보기(책임자 지목·은폐), 95번 보기(분석 생략·기록 안 남김)가 전부 이 문화의 반대라 오답이다.

### 섹션 10 — DevSecOps

> 전부 약어 첫 글자가 뜻이다. 9번 섹션과 같은 약점(약어 해석)이 반복됐다.

#### 97번. SAST (미응답 → 정답 **B**) · 98번. DAST (미응답 → 정답 **C**)

이 둘은 항상 짝으로 나오고 서로 바꿔치기로 헷갈리게 한다. 5번에서 본 shift-left의 실제 보안 도구들이다.

- **SAST** = **S**tatic **A**pplication **S**ecurity **T**esting (정적 분석). 코드를 실행하지 않고 소스/바이너리를 들여다보며 취약점을 찾는다(97번=B). 31번의 정적 분석(static analysis)의 보안 버전이다. SQL 인젝션 가능한 코드, 하드코딩된 비밀번호 같은 걸 소스에서 잡는다. 대표 도구: SonarQube, Checkmarx, Semgrep. 개발 초기(왼쪽)에 돌린다 — 코드만 있으면 되니까.
- **DAST** = **D**ynamic **A**pplication **S**ecurity **T**esting (동적 분석). 실제로 실행 중인 앱을 밖에서 공격해보며 취약점을 찾는다(98번=C). 실행되는 앱에 실제 요청을 던져 반응을 본다(해커처럼). 대표 도구: OWASP ZAP, Burp Suite. 앱이 떠 있어야(오른쪽) 돌린다.

| | SAST (97번) | DAST (98번) |
|---|---|---|
| 뜻 | **S**tatic (정적) | **D**ynamic (동적) |
| 대상 | 소스 코드 (안 돌림) | 실행 중인 앱 (돌림) |
| 관점 | 코드 내부를 봄 (white-box) | 밖에서 공격 (black-box) |
| 비유 | 설계도 검토 | 실제로 문을 흔들어봄 |

> 암기: **S**tatic = **S**ource(코드), **D**ynamic = 실행 중(**D**oing). 첫 글자가 곧 뜻이다.

#### 99번. SBOM의 목적 (미응답 → 정답 **D**)

**개념부터.** SBOM = **S**oftware **B**ill **O**f **M**aterials, "소프트웨어 자재 명세서"다. 제조업의 부품 목록표(BOM)에서 온 개념이다. 자동차에 "이 부품, 저 부품이 들어갔다"는 명세서가 있듯, 내 소프트웨어에 어떤 라이브러리·구성요소가 어떤 버전으로 들어갔는지를 목록으로 관리하는 것이다.

**왜 중요한가.** 2021년 Log4Shell 사건을 떠올리면 된다. Log4j라는 로깅 라이브러리에서 치명적 취약점이 터졌을 때, 회사들이 가장 먼저 부딪힌 질문이 "우리 시스템 중에 Log4j 쓰는 게 뭐가 있지?"였다. SBOM이 있으면 목록만 검색해서 1분 만에 영향받는 시스템을 찾는다. 없으면 수백 개 서비스를 일일이 뒤져야 한다.

**연결.** 39번의 dependency lock file(의존성 버전 고정)과 이어진다 — lock file이 "무엇을 어떤 버전으로 쓰는지"를 고정하고, SBOM은 그걸 보안 추적용 명세로 뽑아낸 것이다.

#### 100번. provenance가 중요한 이유 (미응답 → 정답 **A**)

**개념부터.** provenance는 "출처, 유래"라는 뜻이다(미술품의 "이 그림이 어디서 왔고 누가 소유했는지 내력"이 정확히 provenance다). 소프트웨어에서는 이 artifact(빌드 산출물)가 어떤 소스 코드에서, 어떤 빌드 과정을 거쳐, 누가 만들었는지의 검증 가능한 내력이다.

**왜 중요한가.** 공급망 공격(supply chain attack)을 막기 위해서다. 공격자가 빌드 과정에 몰래 악성코드를 끼워넣었다면? provenance가 있으면 "이 바이너리는 정말 그 git 커밋에서, 그 CI 파이프라인으로 만들어진 게 맞다"를 증명할 수 있다. 위변조를 잡아낸다.

**연결.** 38번의 reproducible build(같은 소스 → 같은 산출물)가 provenance의 기술적 토대다 — 재현 가능해야 "정말 이 소스에서 나왔다"를 검증할 수 있다. 퀴즈 도입부의 SLSA(공급망 무결성 프레임워크)가 바로 이 provenance를 표준화한 것이다.

## 3. 약점 집중 정리 — 암기 카드

### 관측성 3신호

| 신호 | 무엇 | 예 |
|------|------|-----|
| **Log** | 개별 사건 기록 | "14:03 결제 실패 userId=5" |
| **Metric** | 수치 시계열 | CPU 80%, 요청 200/s |
| **Trace** | 요청의 서비스 간 경로·지연 | 주문→결제→DB 400ms |

### RED ↔ USE

| | RED | USE |
|---|---|---|
| 본다 | 서비스(요청 흐름) | 자원(머신) |
| 구성 | **R**ate · **E**rrors · **D**uration | **U**tilization · **S**aturation · **E**rrors |

> 둘 다 Errors로 끝난다. RED=밖(사용자), USE=안(시스템).

### SRE 안정성 용어 사슬

```
SLI (측정한 값)  →  SLO (목표)  →  Error Budget (1 − SLO, 허용 실패분)
                                         │
                              SLA (외부 고객 계약, SLO보다 느슨, 어기면 배상)
```

- **SLI** = Indicator(지표, 현실) · **SLO** = Objective(목표, 내부) · **SLA** = Agreement(계약, 외부)
- Error Budget이 개발(속도)과 운영(안정성)의 갈등을 숫자로 중재한다.

### DORA 4지표

| 축 | 지표 |
|----|------|
| 속도 | Deployment Frequency · Lead Time for Changes |
| 안정성 | Change Failure Rate · **MTTR**(평균 복구 시간) |

> 좋은 팀은 넷 다 좋다. 속도와 안정성은 상충이 아니다.

### 보안 테스트 (전부 첫 글자 = 뜻)

| 약어 | 풀이 | 한 줄 |
|------|------|-------|
| **SAST** | **S**tatic App Security Testing | 코드 안 돌리고 소스 검사 (개발 초기) |
| **DAST** | **D**ynamic App Security Testing | 실행 중인 앱을 밖에서 공격 |
| **SBOM** | **S**oftware **B**ill **O**f **M**aterials | 구성요소·의존성 부품 명세서 (Log4Shell 대응) |
| **provenance** | 출처·유래 | 산출물이 어디서 어떻게 만들어졌는지 검증 가능한 내력 |

> 이 모두가 **96번 DevSecOps**(보안을 파이프라인 전체에 통합) + **5번 shift-left**(보안을 앞으로 당김)의 구현이다.

### 문화·습관 (둔감화를 경계하라)

- **flaky test 방치(34)** → "또 flaky겠지" → 진짜 실패 무시
- **alert fatigue(91)** → 알림 홍수 → 진짜 알림 놓침
- 둘의 해법: 노이즈를 줄여 신호를 살린다(flaky 고치기 / 증상 기반 알림).
- **postmortem + blameless(94·95)**: 비난하면 장애를 숨긴다. 비난 없이 원인을 배워야 재발을 막는다.
