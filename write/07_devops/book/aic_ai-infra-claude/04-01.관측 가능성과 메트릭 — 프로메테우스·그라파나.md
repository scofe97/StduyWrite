# 관측 가능성과 메트릭 — 프로메테우스·그라파나
---
> **관측 가능성이 메트릭·로그·트레이스 3요소로 이루어지고 4장이 그중 메트릭·로그에 알림을 더한다는 지도를 그릴 수 있고, 프로메테우스의 Pull 수집·PromQL·ServiceMonitor와 kube-prometheus-stack 한 차트로 5종이 설치되는 구조를 설명할 수 있으며, e2-medium 노드에 맞춰 Helm values로 리소스를 줄여 설치하고 15개 타깃 수집을 확인하는 흐름까지 답할 수 있다.**



## 📌 핵심 요약

> "Pod는 Running인데 서비스가 안 된다"는 새벽 연락에 답하려면 데이터가 필요합니다. 4장 전반부는 그 첫 축 — 메트릭 수집(프로메테우스)과 시각화(그라파나) — 를 Helm 차트 하나로 세웁니다.

3장에서 GitOps와 CI/CD 파이프라인을 완성했지만 서비스가 지금 잘 돌아가고 있는지 알 수 없습니다. 어느 날 새벽 '서비스가 안 됩니다'라는 연락이 오면 — Pod는 Running인데 CPU가 100%인지, 메모리가 부족한지, 어디서 에러가 나는지 아무것도 모릅니다. 4장은 클로드 코드에게 '모니터링 구축해줘'라고 말하는 것에서 시작해 메트릭·로그·알림을 한 번에 구축합니다.

## 🎯 학습 목표

> 이 절을 읽고 나면 다음 세 가지를 할 수 있습니다.

1. 관측 가능성 3요소(메트릭·로그·트레이스)가 각각 어떤 질문에 답하는 데이터인지 구분할 수 있습니다.
2. Push와 Pull 수집의 차이, node-exporter와 kube-state-metrics의 역할 분담, Prometheus가 StatefulSet인 이유를 설명할 수 있습니다.
3. kube-prometheus-stack을 values 파일로 리소스를 줄여 설치하고, targets API와 PromQL로 수집을 검증할 수 있습니다.



## 1. 관측 가능성이란

> 메트릭은 '무엇이 잘못됐는지', 로그는 '왜 잘못됐는지', 트레이스는 '어디서 느려졌는지'에 답하는 데이터입니다.

관측 가능성(observability)은 세 요소로 이루어집니다.

- 메트릭(metrics)은 숫자입니다 — 'CPU 90%, 초당 요청 500개, 에러율 2%'. 지금 상태가 정상인지 비정상인지 판단하는 데이터입니다.
- 로그(logs)는 텍스트입니다 — 'connection refused at line 42, timeout after 30s'. 무엇이 잘못되었는지 원인을 찾는 데이터입니다.
- 트레이스(traces)는 흐름입니다 — 하나의 요청이 어떤 서비스를 거쳐 어디서 느려졌는지를 추적하는 데이터입니다.

4장에서는 메트릭과 로그를 구축하고 여기에 알림(alerting)을 더합니다. 트레이스는 서비스 간 호출이 생기는 8장에서 추가합니다. 책은 노트로 네 번째 요소인 프로파일(profiles)도 소개합니다 — CPU·메모리를 어떤 함수가 얼마나 쓰는지 코드 수준에서 보여주는 축으로 Pyroscope가 대표적이며, 책에서는 다루지 않지만 성능 병목을 깊이 파고들 때 유용합니다.



## 2. 도구 선택 — 프로메테우스 + 그라파나

> Pull 수집·PromQL·ServiceMonitor가 프로메테우스의 세 기둥이고, kube-prometheus-stack 한 차트가 5종을 한 번에 설치합니다.

"클러스터에서 뭐가 돌아가고 있는지 어떻게 알 수 있어?"라고 물으면 클로드 코드가 **Prometheus + Grafana**를 추천합니다.

Prometheus가 하는 일은 세 가지입니다:

- **Pull 기반 수집** — 30초마다 각 Pod의 `/metrics` 엔드포인트를 직접 조회합니다.[^scrape-interval]
- **PromQL** — 시계열 데이터 전용 쿼리 언어입니다. `rate(http_requests_total[5m])`이면 최근 5분간 초당 요청 수를 뜻합니다.
- **ServiceMonitor CRD** — 어떤 Service를 scrape할지 선언적으로 정의합니다.

Grafana는 그 데이터를 대시보드로 시각화하고, 나중에 Loki(로그)·Tempo(트레이스)도 같은 화면에서 통합 확인합니다. kube-prometheus-stack Helm 차트를 쓰면 Prometheus·Grafana·Alertmanager·node-exporter·kube-state-metrics가 한 번에 설치되며, 쿠버네티스 모니터링의 사실상 표준입니다.

Push vs Pull의 차이가 첫 관문입니다. Push는 각 앱이 모니터링 서버에 데이터를 보내는 방식입니다. 앱마다 전송 코드를 넣어야 하고, 수집 서버 주소를 앱이 알아야 하며, 서버가 죽으면 그동안의 데이터가 유실됩니다. Pull은 반대로 Prometheus가 주기적으로 '너 지금 어때?'라고 각 Pod에 묻는 방식입니다. 앱은 `/metrics` 엔드포인트에 현재 상태만 노출하면 되고, 능동적으로 보낼 필요가 없습니다. 새 Pod가 뜨면 Prometheus가 자동으로 발견해 수집을 시작하고, 모니터링 서버가 잠시 죽어도 앱은 아무 영향을 받지 않습니다.

화살표 방향이 핵심입니다. Push는 화살표가 앱에서 서버로 향해 앱이 능동적으로 데이터를 밀어야 하고, 그래서 앱마다 전송 코드와 서버 주소가 박힙니다. Pull은 화살표가 Prometheus에서 앱으로 향해, 앱은 문 앞에 `/metrics`만 걸어 두면 됩니다. 새 Pod가 떠도 앱을 고칠 필요 없이 Prometheus가 알아서 발견해 긁어 갑니다.

수집기 두 종의 역할 분담도 짚어 둡니다. node-exporter는 노드(VM) 수준의 하드웨어 지표(CPU·메모리·디스크 I/O)를 담당합니다. 모든 노드에 정확히 1개씩 있어야 하므로 DaemonSet으로 배포됩니다. Deployment가 '아무 노드에나 N개'라면, DaemonSet은 '모든 노드에 1개씩'입니다. kube-state-metrics는 쿠버네티스 API의 오브젝트 상태를 숫자로 변환합니다 — 'Pod가 몇 개야?', 'replica 3인데 실제 3개 떠 있어?', '이 Pod는 왜 Pending이야?' 같은 질문에 답하는 데이터입니다.

네 컴포넌트의 관계를 한 줄로 요약하면 이렇습니다:

- node-exporter → 하드웨어("이 노드 CPU가 90%야")
- kube-state-metrics → 쿠버네티스("이 Pod가 CrashLoopBackOff야")
- Prometheus → 위 둘을 수집·저장
- Grafana → 저장된 데이터를 시각화

대안 비교에서는 Notiflex 환경(e2-medium×2, 4GB) 판단이 결정적입니다.

| 구분 | Prometheus + Grafana | Datadog | Google Cloud Monitoring | CloudWatch |
|------|---------------------|---------|------------------------|------------|
| 추천도 | ★★★ | ★★ | ★★ | ★ |
| 비용 | 무료 | 호스트당 $15+/월 | 무료 티어(제한적) | AWS 전용 |
| 설치 | Helm 차트 한 줄 | 에이전트 설치 | GKE 자동 통합 | GKE 불편 |
| 커스텀 대시보드 | 무제한(Grafana) | 무제한 | 제한적 | 제한적 |
| 통합 | Loki·Tempo 연결 | 자체 APM 포함 | GCP 제한 | AWS 제한 |

학습 환경에서 SaaS 비용을 쓸 이유가 없고(Prometheus는 CPU 100m·Memory 256Mi면 충분), 더 중요한 근거는 통합성입니다 — 4.3에서 Loki를 추가하면 Grafana에서 로그를, 8.2에서 Tempo를 추가하면 트레이스를 같은 대시보드에서 봅니다. 장기 저장이 필요해지면 Thanos나 Cortex를 Prometheus 앞에 두고 오브젝트 스토리지(S3·GCS)에 백업하는 구조로 확장하되, 지금은 24시간 retention으로 충분합니다.



## 3. 설치 — Helm values로 리소스 다이어트

> 기본값은 프로덕션용으로 넉넉하게 잡혀 있어, e2-medium 노드에 맞게 values 파일로 CPU·메모리를 줄여 설치합니다.

values 파일은 Helm 설치 시 기본값을 덮어쓰는 설정 파일입니다. 책이 작성한 `helm-values/kube-prometheus.yaml`은 컴포넌트별 requests를 낮춥니다:

```yaml
# helm-values/kube-prometheus.yaml — 책 §4.2.3 실습본
prometheus:
  prometheusSpec:
    resources:
      requests:
        cpu: 100m
        memory: 256Mi
    retention: 24h        # 24시간 지난 메트릭은 자동 삭제 — 디스크 절약
    storageSpec: {}
grafana:
  resources:
    requests:
      cpu: 50m
      memory: 128Mi
  adminPassword: notiflex-grafana
alertmanager:
  alertmanagerSpec:
    resources:
      requests:
        cpu: 25m
        memory: 64Mi
prometheusOperator:
  resources:
    requests:
      cpu: 25m
      memory: 64Mi
kubeStateMetrics:
  resources:
    requests:
      cpu: 10m
      memory: 32Mi
nodeExporter:
  resources:
    requests:
      cpu: 10m
      memory: 32Mi
```

retention 24h는 학습용 디스크 절약 설정이고, 프로덕션은 보통 15~30일, 그 이상은 Thanos를 씁니다.

"Helm이 왜 필요해? `kubectl apply -f`로는 안 돼?"라는 질문에 대한 답이 이 절의 백미입니다. 할 수는 있습니다. 다만 kube-prometheus-stack은 50개가 넘는 리소스(CRD·Deployment·Service·ConfigMap·ServiceMonitor·PrometheusRule)에 YAML 수천 줄입니다. 그 수천 줄 사이에서 'Prometheus 메모리를 256Mi로 바꾸고 싶다'는 한 줄 요구를 정확히 찾아 수정하는 것은 유지보수가 사실상 불가능합니다. Helm은 이 복잡한 YAML 묶음을 차트(chart)라는 패키지로 만들고, 사용자가 건드리고 싶은 값만 values 파일로 덮어씁니다. 그래서 `helm install ... -f my-values.yaml` 한 줄로 끝납니다.

설치는 네 명령입니다:

```bash
# monitoring 네임스페이스에 kube-prometheus-stack 설치 — 책 §4.2.3
kubectl create namespace monitoring
helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install kube-prometheus prometheus-community/kube-prometheus-stack \
    -n monitoring -f helm-values/kube-prometheus.yaml
```

60초 뒤 Pod 7개가 모두 Running입니다. 각각의 역할은 다음과 같습니다:

- `prometheus-...-prometheus-0` — 수집 엔진
- `grafana` — 대시보드 UI
- `alertmanager-...-0` — 알림 라우팅 (4.4에서 설정)
- `kube-prome-operator` — PrometheusRule·ServiceMonitor CRD 관리
- `kube-state-metrics` — 쿠버네티스 오브젝트 상태 수집
- `node-exporter` ×2 — 노드 하드웨어 수집 (DaemonSet이라 노드 2개에 각 1개)

Prometheus가 StatefulSet인 이유도 여기서 나옵니다. Deployment는 Pod 이름이 랜덤이고 죽으면 새 이름으로 생기지만, StatefulSet은 고정 이름(`prometheus-0`)에 고정 저장소(PVC)가 연결됩니다. 수집한 메트릭을 디스크에 저장하므로, 재시작에도 데이터가 날아가면 안 되기 때문입니다.



## 4. 그라파나 접속과 메트릭 확인

> 대시보드는 이미 20개 이상 만들어져 있고, 뒤에서 Prometheus가 15개 타깃을 수집 중인 것을 API로 확인합니다.

`kubectl port-forward svc/kube-prometheus-grafana -n monitoring 3000:80 &` 후 `http://localhost:3000`에 admin / notiflex-grafana(values에서 설정한 값)로 로그인합니다. kube-prometheus-stack이 설치 시 자동으로 만든 기본 대시보드가 20개 이상 들어 있어, 대부분의 K8s 모니터링 시나리오를 이미 커버합니다:

- Kubernetes/Compute Resources/Cluster — 클러스터 전체 CPU·메모리
- Kubernetes/Compute Resources/Namespace — 네임스페이스별 Pod 자원
- Node Exporter/Nodes — 노드별 시스템 메트릭

Prometheus 쪽 검증은 API로 합니다 — `port-forward svc/prometheus-operated 9090:9090` 후 `curl .../api/v1/targets | jq '.data.activeTargets | length'`가 15, `query?query=up`의 결과도 15로, 15개 타깃 모두 정상 scrape 중입니다. 수집된 데이터는 PromQL로 조회합니다. Grafana 대시보드의 그래프도 내부적으로는 이 PromQL을 실행한 결과입니다.

> **복습 실습 메모: 타깃 수는 환경마다 다릅니다.** 책은 15개지만 우리 GKE 클러스터에서 `up`을 질의하면 18개가 나왔습니다. 노드 2개짜리 job(kubelet은 노드당 `/metrics`·`/cadvisor`·`/probes` 세 경로, node-exporter는 노드당 1개)이 인스턴스 단위로 세지기 때문입니다. 그래서 노드 수·쿠버네티스 배포판에 따라 총계가 달라집니다. 숫자 자체보다 `up == 0`으로 DOWN만 걸러 보는 게 실무 감각에 가깝습니다. 18개 중 coredns 2개가 걸렸습니다. 이 `up == 0` 한 줄이 4.4 PrometheusRule에서 `for: 5m`을 붙여 '5분 이상 DOWN이면 알려라'로 자라는 알람 조건의 원형입니다.

- `rate(container_cpu_usage_seconds_total{namespace="notiflex"}[5m])` — Notiflex Pod의 초당 CPU 사용률
- `container_memory_working_set_bytes{namespace="notiflex"}` — 메모리 사용량
- `kube_pod_status_phase{namespace="notiflex"}` — Pod 상태

마무리로 `helm-values/kube-prometheus.yaml`을 커밋합니다("feat: add Prometheus + Grafana monitoring stack"). monitoring 네임스페이스가 새로 생겨 Prometheus(30초 간격 수집)·Grafana·Alertmanager(4.4 예정)·kube-state-metrics·node-exporter×2가 argocd·notiflex 네임스페이스와 나란히 서게 됐습니다.



## 🔍 심화 학습

> 3요소 프레임의 원전과 Operator 패턴의 의미를 보강합니다. 책 밖 조사 내용입니다.

### "3 pillars"의 원전 — Peter Bourgon (2017)

메트릭·로그·트레이스 3요소 프레임은 Peter Bourgon이 2017년 2월 블로그 글 "Metrics, tracing, and logging"에서 정리해 업계 표준 어휘가 된 것입니다. 원전의 구분 기준은 책 설명보다 한 층 정밀합니다. 메트릭은 집계 가능(aggregatable)한 원자 데이터, 로그는 이산 이벤트(discrete events), 트레이스는 요청 범위(request-scoped) 데이터라는 속성으로 가릅니다. '숫자/텍스트/흐름'이라는 책의 직관적 구분을 면접에서 한 단계 깊게 말하고 싶을 때 이 속성 축을 쓰면 됩니다.

모니터링과 관측 가능성의 개념 구분, 그리고 Golden Signals·RED·USE 같은 시그널 모델은 이 저장소의 [06_observability 01-01 모니터링](../../../../06_observability/01_Foundations/01-01.모니터링.md)과 [01-03 시그널 모델](../../../../06_observability/01_Foundations/01-03.시그널%20모델%20—%20Golden%20Signals,%20RED,%20USE.md)이 정본이므로 그쪽으로 위임합니다.

### Prometheus Operator — 모니터링 설정도 선언형으로

kube-prometheus-stack의 실체는 Prometheus Operator입니다. Prometheus 원본은 scrape 대상과 알림 규칙을 자체 설정 파일(prometheus.yml)로 관리하는데, Operator는 그 두 가지를 각각 다른 CRD로 끌어올립니다. '무엇을 수집할지'(scrape 대상)는 ServiceMonitor·PodMonitor가, '무엇을 경보할지'(알림·기록 규칙)는 PrometheusRule이 맡습니다 — 두 CRD의 역할은 겹치지 않습니다. 그 덕분에 수집 대상과 알림 규칙이 모두 YAML 리소스가 되어 깃에 커밋되고 ArgoCD가 관리할 수 있게 됩니다. 3장에서 만든 GitOps 체계에 모니터링 설정이 자연스럽게 올라타는 구조입니다. 4.4의 PrometheusRule이 바로 이 알림 규칙 CRD 위에 서 있습니다.

### 차트 하나에 5종이 묶인 이유

kube-prometheus-stack 차트는 Prometheus Operator + Prometheus + Alertmanager + Grafana + 수집기(node-exporter·kube-state-metrics)에 기본 대시보드·알림 규칙 세트까지 포함한 배포판입니다. 컴포넌트를 따로 깔면 서로 연결(데이터소스 등록·룰 발견 라벨)을 수동으로 맞춰야 하는데, 차트가 그 배선을 다 해 둔 것입니다 — 4.4에서 만날 `release: kube-prometheus` 라벨 규칙이 그 배선의 한 예입니다. 공식 차트 저장소는 [prometheus-community/helm-charts](https://github.com/prometheus-community/helm-charts/tree/main/charts/kube-prometheus-stack)입니다.

### 주의할 점

- ⚠️ retention 24h는 학습용 설정입니다 — 장애 회고는 며칠 뒤에 하게 되므로 프로덕션은 15~30일 + 장기 보관은 Thanos 계열로 잡아야 합니다.
- ⚠️ adminPassword를 values 파일에 평문으로 두는 것도 학습용 타협입니다 — 이 파일이 깃에 커밋되므로 실무라면 Secret 참조로 바꿔야 합니다.
- ⚠️ Helm 설치분은 ArgoCD 관리 밖입니다 — 이 장 시점에서는 helm install이 직접 실행이므로, 클러스터 재생성 시 values 파일이 깃에 있다는 것이 복구의 근거가 됩니다.
- ⚠️ 복습 실습에서 확인한 함정: 타깃이 `DOWN`이라고 반드시 장애는 아닙니다. GKE 클러스터에서 targets 페이지를 열면 coredns 타깃 2개가 `connection refused`로 DOWN이었습니다. 그런데 DNS 기능은 멀쩡했습니다. GKE의 kube-dns가 메트릭 포트 `9153`을 기본으로 열지 않아 scrape만 실패한 것입니다. 무엇이 DOWN인지를 봐야 심각도가 갈립니다. node-exporter가 DOWN이면 진짜 노드 신호지만 GKE coredns의 DOWN은 알려진 메트릭 미노출입니다.
- ⚠️ 복습 실습에서 확인한 경계: `up{namespace="notiflex"}`를 질의하면 빈 결과가 나옵니다. 우리 앱은 `/health`·`/id`·`/version`만 노출하고 `/metrics`가 없습니다. 그래서 Prometheus의 타깃으로 등록조차 되지 않았습니다. 이 빈 결과는 DOWN(값 0)과 다릅니다 — DOWN은 '긁으려다 실패', 빈 결과는 '긁을 대상에 아예 없음'입니다. 앱을 관측 대상에 넣으려면 client 라이브러리로 `/metrics`를 노출하고 ServiceMonitor로 등록하는 계측(instrumentation)이 필요합니다. 이 계측은 4장 범위 밖입니다.

## ☕ Spring 앱 개발 관점

> 이 절의 마지막 함정 — "우리 앱은 `/metrics`가 없어 타깃 등록조차 안 됐다" — 은 사실 Spring 앱에서 가장 쉽게 풀리는 지점입니다. 책은 Go 앱(Notiflex)이라 계측을 4장 범위 밖으로 미뤘지만, Spring Boot라면 의존성 하나로 이 절 안에서 관측 대상이 됩니다. 책에 없는 내용이라 공식 문서(Spring Boot Actuator)로 보강합니다.

Prometheus의 Pull 모델에서 앱이 해야 할 일은 단 하나, `/metrics` 엔드포인트를 여는 것입니다. Go 앱은 client 라이브러리를 붙이고 핸들러를 직접 등록해야 하지만, Spring Boot는 Micrometer가 이미 그 자리에 들어가 있습니다. Actuator와 Prometheus registry 의존성만 추가하면 `/actuator/prometheus`가 열리고, JVM 힙·GC·스레드 풀·HTTP 요청 지연 같은 지표가 별도 코드 없이 자동으로 수집됩니다.

```gradle
// build.gradle — 이 둘만 있으면 /actuator/prometheus가 열립니다
implementation 'org.springframework.boot:spring-boot-starter-actuator'
implementation 'io.micrometer:micrometer-registry-prometheus'
```

Actuator 엔드포인트는 기본적으로 `/actuator/health`·`/actuator/info` 정도만 노출되므로, prometheus 엔드포인트를 밖으로 꺼내려면 노출 목록에 넣어 줍니다:

```yaml
# application.yml — prometheus 엔드포인트를 웹으로 노출
management:
  endpoints:
    web:
      exposure:
        include: health, info, prometheus
```

이제 남은 일은 이 절 본문의 계측 경로 그대로입니다 — Prometheus가 이 앱을 긁도록 ServiceMonitor를 하나 만들어 대상 Service를 라벨로 지정하면 됩니다. 그러면 §4의 `up{namespace="notiflex"}` 빈 결과가 값 있는 결과로 바뀌고, 앱이 관측 대상 목록에 정식으로 올라섭니다. 즉 이 노트가 "4장 범위 밖"이라 미뤄 둔 계측이, Spring에서는 의존성 2줄 + 노출 설정 1줄 + ServiceMonitor 1개로 끝납니다.

한 가지 주의는 노출 범위입니다. `/actuator/prometheus`에는 앱 내부 지표가 그대로 담기므로, 클러스터 안에서만 접근되도록 두고 외부에 열지 않는 편이 안전합니다. `include: "*"`로 모든 엔드포인트를 여는 예제가 흔하지만, 실무에서는 필요한 엔드포인트만 골라 노출합니다.

## 정답 (자답 후 펼치기)

### 정답 1 — 관측 가능성 3요소

메트릭은 숫자로 '무엇이 잘못됐는지'(CPU 90%·에러율 2%), 로그는 텍스트로 '왜 잘못됐는지'(connection refused), 트레이스는 흐름으로 '어디서 느려졌는지'를 알려 줍니다. 4장은 앞의 둘(메트릭·로그)에 알림(alerting)을 더하고, 트레이스는 서비스 간 호출이 생기는 8장에서 추가합니다.

### 정답 2 — 왜 Prometheus인가

학습 환경에서 SaaS 비용을 쓸 이유가 없고(Prometheus는 CPU 100m·메모리 256Mi로 충분), 더 중요한 근거는 통합성입니다. Grafana 한 화면에서 뒤에 붙일 Loki(로그)·Tempo(트레이스)까지 함께 봅니다. Pull 방식이라 앱은 `/metrics`만 노출하면 되고, 새 Pod가 떠도 Prometheus가 자동 발견해 수집하며, 모니터링 서버 장애가 앱에 영향을 주지 않습니다.

### 정답 3 — 수집기 두 종의 역할

node-exporter는 노드(VM) 하드웨어(CPU·메모리·디스크 I/O)를 수집하므로 모든 노드에 정확히 1개씩 있어야 해서 DaemonSet입니다. kube-state-metrics는 쿠버네티스 API의 오브젝트 상태('replica 3인데 실제 몇 개 떠 있나')를 숫자로 변환하는 단일 서비스라 아무 노드에 1개만 뜨면 되어 Deployment입니다.

### 정답 4 — Prometheus가 StatefulSet인 이유

수집한 메트릭을 디스크(PVC)에 저장하므로 재시작에도 데이터가 날아가면 안 됩니다. Deployment는 Pod 이름이 랜덤이고 죽으면 새 이름으로 생기지만, StatefulSet은 고정 이름(`prometheus-0`)에 고정 저장소가 1:1로 연결됩니다.

### 정답 5 — 설치 검증

Grafana에 접속해 자동 생성된 기본 대시보드가 뜨는지 보고, Prometheus의 `/api/v1/targets`로 scrape 대상 수(책 기준 15개)를 확인한 뒤, PromQL `up`으로 각 타깃이 정상인지(`up == 0`이면 DOWN) 조회합니다. 숫자 자체보다 `up == 0`으로 DOWN만 걸러 보는 게 실무 감각에 가깝습니다.

### 정답 빈칸 — ①`retention` ②`requests` ③`adminPassword`

`retention: 24h`는 24시간 지난 메트릭을 자동 삭제해 디스크를 아끼는 학습용 설정이고(프로덕션은 15~30일), `resources.requests`는 각 컴포넌트의 CPU·메모리 하한을 낮춰 작은 노드에 욱여넣는 다이어트 필드입니다. `adminPassword`를 values에 평문으로 두는 것은 이 파일이 깃에 커밋되므로 실무라면 Secret 참조로 바꿔야 할 학습용 타협입니다.
