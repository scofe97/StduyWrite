# 오답노트 — 내가 틀린 키워드 상세

> `01-AI엔지니어링-100문항.md`(2026-07-06~07 풀이, 98/100)에서 실제로 틀렸거나, 찍어서 맞았지만 개념을 몰라 다시 배운 키워드를 따로 뺀 문서입니다.
> 원본의 한 줄 표는 시험 직전 스캔용이고, 이 문서는 **"왜 헷갈렸는지"와 "어떻게 구분하는지"를 문장으로 풀어** 개념 자체를 다시 세우는 용도입니다.
> 시험 대비 함정 소거법은 원본 문서 하단 "전체 함정 패턴 요약"을 그대로 두었으니 그쪽을 봅니다.

---

## 1. 실제로 틀린 문항 (2개)

100문항 중 이 둘만 실제로 틀렸습니다. 나머지는 맞혔지만, 두 문항 모두 "개념을 반대로 기억"하거나 "범위를 헷갈린" 전형적인 함정이라 뿌리부터 다시 정리합니다.

### 1-1. temperature (4번)

제가 고른 답은 A(결정적·반복적)였고 정답은 D(다양성·창의성)였습니다. temperature를 **올리면** 응답이 더 결정적으로 변한다고 거꾸로 외운 것이 원인입니다.

temperature는 모델이 다음 토큰을 고를 때 참고하는 **확률 분포의 모양을 조절하는 값**입니다. 값을 올리면 분포가 평탄해집니다. 평탄해진다는 말은, 원래 확률이 낮아 잘 안 뽑히던 토큰까지 뽑힐 여지가 생긴다는 뜻입니다. 그래서 응답이 더 다양하고 창의적으로 흔들립니다. 반대로 값을 낮추면 분포가 뾰족해져서, 가장 확률 높은 토큰이 거의 항상 뽑힙니다. 그 결과 응답이 결정적이고 반복적이 됩니다.

헷갈리지 않으려면 "온도가 높으면 분자가 활발하게 튄다 → 응답도 활발하게 튄다(다양)"로 물리적 온도에 빗대어 기억합니다. 온도 ↑ = 다양·창의, 온도 ↓ = 결정적·일관. 이 방향만 붙잡으면 됩니다.

한 가지 더 주의할 점은, temperature는 컨텍스트 윈도우 크기나 토큰 개수, safety filter와는 **아무 관계가 없다**는 것입니다. 오답 선택지가 "context window를 확장한다", "토큰 수를 제한한다"처럼 엉뚱한 영역을 끌어오면 그 자체로 걸러낼 수 있습니다.

### 1-2. MCP의 세 프리미티브 (72번)

제가 고른 답은 B("로그 파일만")였고 정답은 A(tools·resources·prompts)였습니다. 두 가지가 겹쳐서 틀렸습니다. 하나는 **"~만"이라는 범위 한정 함정**에 걸린 것이고, 다른 하나는 **MCP 서버 전체가 노출하는 것(3종)과 그중 하나인 resource를 혼동**한 것입니다.

MCP 서버는 세 가지 프리미티브를 노출합니다. **tools**는 모델이 호출하는 행동(함수)이고 부수효과가 있을 수 있습니다. **resources**는 모델이 읽는 데이터로 파일·DB 레코드·위키 페이지 같은 것입니다. **prompts**는 재사용 가능한 프롬프트 템플릿입니다. "로그 파일"이나 "캐시 키", "환경 변수"처럼 하나로 좁힌 선택지는 이 셋 중 어디에도 정확히 대응하지 않으므로 오답입니다.

이 문항에서 배운 교훈은 두 개입니다. 첫째, 선택지가 "~만"으로 범위를 좁히면 대개 오답입니다. 실제로는 여러 요소가 있는데 하나로 축소했기 때문입니다. 둘째, "서버가 노출하는 것 전체"를 묻는지 "그중 하나의 정의"를 묻는지 문두를 정확히 읽어야 합니다. tools·resources·prompts는 서버 레벨의 3종 세트이고, resource는 그 안의 한 갈래입니다.

## 2. 찍어서 맞았거나 몰라서 물어본 개념 (재학습)

아래는 정답은 맞혔지만 확신이 없어 다시 확인한 개념들입니다. 시험장에서 "이건 확실히 안다"고 말할 수 있을 때까지 문장으로 풀어 둡니다. 주제별로 묶었습니다.

### 2-1. 샘플링·디코딩 파라미터

**top-p (nucleus sampling)** 는 확률이 높은 토큰부터 차례로 누적해서, 누적 확률이 임계값 p에 닿을 때까지의 토큰만 후보로 남기고 그 안에서 샘플링하는 방식입니다. 확률 분포의 긴 꼬리(거의 안 나오는 헛소리 토큰)를 잘라내는 효과가 있습니다. "뷔페에서 상위 90%까지만 담는다"고 기억하면 됩니다. temperature가 분포의 **모양**을 조절한다면, top-p는 후보 **집합의 크기**를 조절한다는 점에서 다릅니다.

### 2-2. 학습·정렬 단계

**instruction tuning** 은 (지시, 이상적인 응답) 쌍을 모아 모델을 추가로 학습시켜, 사람의 명령을 더 잘 따르게 만드는 단계입니다. 사전학습만 마친 모델은 다음 토큰 예측은 잘해도 "요약해줘" 같은 지시를 얌전히 따르지는 못하는데, 이 단계가 그 간극을 메웁니다.

**RLHF (Reinforcement Learning from Human Feedback)** 는 사람이 여러 응답을 놓고 어느 쪽이 더 나은지 비교한 선호 데이터로 보상 모델을 만들고, 그 보상을 최대화하도록 강화학습으로 모델을 정렬하는 단계입니다. 전체 순서는 **사전학습 → instruction tuning → RLHF**입니다. 이 순서를 함께 외워두면 각 단계의 목적이 뒤섞이지 않습니다.

### 2-3. 모델 능력·형태

**reasoning** 은 여러 단계를 논리로 밟아 답에 이르는 능력입니다. 복잡한 코드 분석, 수학 문제, 설계 검토처럼 한 번에 답이 안 나오는 작업에서 이 능력이 갈립니다.

**멀티모달(multi-modal)** 은 텍스트뿐 아니라 이미지·오디오·영상 같은 여러 입력 양식을 한 모델에서 함께 다루는 것입니다. modal(양식)에 multi(여럿)가 붙은 말로 기억합니다. 다만 텍스트만 다루는 RAG처럼 다른 양식이 필요 없는 작업에는 굳이 멀티모달 모델을 쓸 이유가 없습니다.

**tokenizer** 는 텍스트를 토큰 단위로 쪼개는 도구입니다. 이것이 바뀌면 같은 문장이라도 토큰 개수가 달라지므로, 비용·최대 출력 길이·컨텍스트 한도를 전부 다시 계산해야 합니다.

### 2-4. 모델 선택·라우팅 전략

**모델 라우팅** 은 요청의 특성(난이도·비용·지연 요구)을 보고 어떤 모델로 보낼지 정하는 로직입니다. 규칙 기반(가벼운 작업은 haiku, 표준은 sonnet, 어려운 건 opus), 분류기 기반, escalation 방식 등이 있습니다.

**fast + fallback** 은 먼저 빠르고 싼 모델로 처리해 보고, 실패하거나 신뢰도가 낮으면 상위 모델로 넘기는 구조입니다. 대부분의 쉬운 요청을 저비용으로 처리하므로 평균 비용과 지연이 내려갑니다. 다만 환각이 사라지거나 보안 검사가 불필요해지는 것은 아닙니다.

### 2-5. 프롬프트·추론 다루기

**chain-of-thought (CoT)** 는 최종 답을 내기 전에 중간 추론 과정을 거치게 하는 기법입니다. 품질을 위해 추론은 활용하되, 운영 환경에서는 그 과정을 통째로 노출하기보다 결론과 근거, 검증 결과만 정제해 보여주는 편이 안전하고 유용합니다.

**role prompting** 은 "너는 10년차 엔지니어다"처럼 역할을 부여하는 방식입니다. 응답의 스타일과 톤을 유도할 수는 있지만, 그것만으로 실제 능력이나 권한, 정확성이 보장되지는 않습니다. 역할은 분위기이지 검증 장치가 아니라는 점을 분명히 해야 합니다.

### 2-6. 평가·회귀

**golden dataset** 은 정답 또는 채점 기준이 확정된 기준 문제집입니다. 프롬프트나 모델을 바꿨을 때 품질이 올랐는지 내렸는지를 재는 잣대 역할을 합니다.

**regression test** 는 무언가를 고친 뒤, 이전에 잘 되던 케이스가 퇴보하지 않았는지 확인하는 검사입니다. golden dataset과 짝을 이뤄, 골든셋을 기준으로 회귀 여부를 판정합니다.

### 2-7. 컨텍스트·메모리

**context rot** 는 컨텍스트가 길어질수록 핵심 정보가 묻혀 정확도가 떨어지는 현상입니다. 1M 토큰짜리 큰 컨텍스트를 쓰더라도 발생한다는 점이 핵심입니다. 크다고 무조건 좋은 게 아닙니다.

**summarization memory** 는 오래된 대화를 요약해 저장하는 방식입니다. 토큰을 아끼는 대신 세부 정보가 누락되거나 왜곡될 위험을 감수합니다. Claude Code의 `/compact`가 바로 이 방식에 해당합니다.

**progressive disclosure** 는 필요할 때 필요한 만큼만 정보를 공개하는 원칙입니다. 스킬이나 도구 스키마를 처음부터 다 넣지 않고 지연 로드해서, 토큰 낭비와 도구 오선택을 줄입니다. "접이식 매뉴얼"처럼 펼칠 때만 펼치는 그림으로 기억합니다.

### 2-8. RAG·검색

**RAG (Retrieval-Augmented Generation)** 는 질문으로 관련 문서를 검색해 컨텍스트에 주입하고, 그 근거로 답을 생성하는 방식입니다. 모델의 고정된 학습 지식 한계를 검색으로 보완합니다. "오픈북 시험"에 빗대면 자연스럽습니다.

**벡터 검색** 은 텍스트를 벡터로 바꿔 의미가 가까운 것끼리 찾는 방식입니다. 키워드 검색과 달리 "개"와 "강아지"처럼 표현은 달라도 의미가 가까우면 잡아냅니다.

**cosine similarity** 는 두 벡터가 이루는 방향(사잇각)의 유사성을 재는 척도입니다. 벡터의 크기 차이에는 둔감하고 방향만 봅니다.

**hybrid search** 는 정확한 일치에 강한 키워드 검색과 의미 유사에 강한 벡터 검색을 함께 써서 검색 recall을 높이는 방식입니다.

**reranker** 는 1차 검색으로 넓게 뽑은 후보를 질문과의 정밀한 관련성 기준으로 다시 정렬하는 단계입니다. "넓게 뽑고 정밀하게 추린다"는 2단계 그림으로 기억합니다.

**chunk size** 는 RAG에서 문서를 자르는 조각의 크기입니다. 너무 크면 한 조각에 무관한 내용이 섞여 임베딩이 흐려지고 토큰이 낭비되며, 너무 작으면 문맥이 끊겨 의미 파악이 어려워집니다. "완결된 의미 단위"에 맞추는 것이 좋습니다.

**citation** 은 답변이 어느 문서에 근거했는지 출처를 표기하는 것입니다. 근거를 추적하고 검증할 수 있게 해 신뢰도를 높입니다. "논문 각주"와 같은 역할입니다.

**freshness** 는 문서의 최신성입니다. 낡은 문서가 검색되면 이미 폐기된 정책이나 구버전 정보를 근거로 삼아 틀린 답이 나올 수 있습니다. "상한 우유"처럼, 오래됐다고 더 정확한 게 아니라 오히려 해가 됩니다.

**임베딩 모델 교체** 시에는 벡터 공간 자체가 달라지므로, 기존 인덱스를 새 모델로 전부 재생성해야 합니다. "자를 바꾸면 치수를 다시 재야 한다"로 기억합니다.

**grounded answer** 는 검색된 근거 문서에 발을 붙인 답변, 즉 지어내지 않은 답변입니다. 환각의 반대말로 이해하면 됩니다.

### 2-9. 도구 호출·에이전트

**function calling (tool use)** 은 모델이 어떤 함수를 어떤 인자로 부를지 구조화해 **제안**하고, 실제 실행은 애플리케이션이 맡는 방식입니다. 모델이 직접 함수를 실행하는 것이 아니라는 점이 핵심입니다.

**tool description** 은 도구 설명문으로, 모델이 언제 어느 도구를 써야 할지 판단하는 거의 유일한 단서입니다. "공구함의 라벨"처럼, 라벨이 부실하면 엉뚱한 공구를 집습니다.

**ReAct** 는 Reasoning과 Acting을 번갈아 반복하는 에이전트 패턴입니다. 생각하고(추론) → 행동하고(도구 호출) → 관찰한(결과) 것을 다시 추론에 반영하며 문제를 풉니다. 프론트엔드 라이브러리 React와는 이름만 같고 아무 관계가 없습니다.

**idempotency key (멱등 키)** 는 같은 요청을 여러 번 보내도 결제·배포·티켓 생성 같은 작업이 중복 실행되지 않도록 보장하는 키입니다. 재시도가 필요하면서 부작용이 있는 작업에 필수입니다.

**agent memory 정책** 은 무엇을 남기고(사용자 선호·누적 학습) 무엇을 지울지(개인정보·일회성 값)를 정책으로 구분하는 것입니다. MEMORY.md가 이 정책이 실제로 구현된 물건입니다.

**destructive action** 은 되돌릴 수 없는 작업(삭제·배포·결제)입니다. dry-run, 사용자 확인, 권한 검증, 감사 로그의 네 겹으로 방어합니다.

### 2-10. MCP·운영·보안

**MCP Gateway / Proxy** 는 여러 MCP 서버 앞단에 두는 중앙 관문입니다. 라우팅·인증·로깅·정책 적용을 한곳에 모아 일관되게 처리합니다.

**guardrail** 은 입력·출력·도구 실행을 정책 기준으로 검증하고 차단하는 안전 울타리입니다.

**tracing** 은 응답이 어떤 프롬프트·모델·도구·문서·비용 경로를 거쳐 나왔는지 추적하는 것입니다. 비결정적인 에이전트를 디버깅하고 감사하는 데 필요합니다.

**LLM-as-a-judge** 는 모델로 다른 모델의 출력을 채점하는 방식입니다. 단, 심판 모델도 틀릴 수 있으므로 rubric(채점 기준), 사람 검수, 다중 평가로 보정해야 합니다.

**red teaming** 은 배포 전에 일부러 공격적인 입력이나 시나리오를 넣어 취약점을 찾는 활동입니다. 모의 해킹과 같은 개념입니다.

**rate limit 대응** 은 요청 한도에 걸렸을 때 backoff를 두고 재시도하거나, 큐에 쌓거나, fallback으로 넘기는 방식입니다. 무한 즉시 재시도는 서버를 더 압박하므로 금물입니다.

## 3. 이 오답들이 공통으로 가르쳐 준 것

두 문항을 틀리고 여러 개념을 다시 본 뒤 남은 교훈은 세 가지로 좁혀집니다.

첫째, **두 개념의 설명을 서로 뒤바꾼 선택지**를 조심해야 합니다. temperature의 ↑↓가 대표적입니다. 방향을 물리적 비유(온도 높으면 활발)로 못 박아 두면 흔들리지 않습니다.

둘째, **"~만"으로 범위를 좁힌 선택지**는 대체로 오답입니다. MCP 프리미티브 문항이 그랬습니다. 실제로는 여러 요소가 있는데 하나로 축소했기 때문입니다.

셋째, **문두가 무엇을 묻는지 정확히 읽어야** 합니다. "서버 전체가 노출하는 것"과 "그중 하나의 정의"는 답이 다릅니다. 부정형("아닌 것/나쁜 것")까지 포함해, 문제를 끝까지 읽는 습관이 이 두 실점을 막는 가장 확실한 방법이었습니다.
