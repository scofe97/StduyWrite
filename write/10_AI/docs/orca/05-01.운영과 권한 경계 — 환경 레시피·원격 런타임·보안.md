# 운영과 권한 경계 — 환경 레시피·원격 런타임·보안
---
> 이 편의 중심 문장은 하나입니다. **워크트리는 보안 경계가 아닙니다.** 코드 변경이 섞이지 않게 할 뿐 프로세스가 무엇을 할 수 있는지는 전혀 제한하지 않습니다. 무엇이 실제로 범위를 좁히는지 구분해야 합니다.

## 학습 목표

> 이 편을 읽고 나면 아래 네 가지를 스스로 해낼 수 있습니다.

1. 워크트리가 막아 주는 것과 막아 주지 않는 것을 나눠 대고, 그것이 왜 샌드박스가 아닌지 설명할 수 있습니다.
2. 실제로 경계 역할을 하는 장치 넷을 구분하고, 각각이 무엇을 언제 통제하는지 말할 수 있습니다.
3. 명령 출력에 함께 나오는 정보를 알고 공유 전에 지울 항목을 짚을 수 있습니다.
4. 일회용 실행 환경이 필요한 시점을 판단할 수 있습니다.

명령이 성공을 반환하면서 아무 일도 하지 않는 상황의 대처는 [05-02](05-02.실패와 복구 — 거짓 성공과 개입 신호.md)에서 다룹니다.



## 1. 에이전트는 확인 없이 실행됩니다

> `--agent`로 에이전트를 띄우면 파일 수정과 명령 실행 전 확인 절차가 전부 생략된 상태로 시작합니다. 버그가 아니라 설계입니다.

<!-- no-diagram: 명령 한 줄이 어떤 플래그로 실행되는가라는 사실 하나를 다루는 절이라 그릴 구조가 없습니다. 그 결과가 무엇을 뜻하는지는 다음 절 도식이 보입니다. -->

ORCA가 실제로 터미널에 입력하는 명령에는 권한 확인을 건너뛰는 플래그가 붙어 있습니다. 매번 사람이 확인해야 하면 에이전트 열 개를 병렬로 돌리는 일이 불가능하기 때문입니다.

ORCA는 이 확인 절차를 워크트리 격리로 대체한다고 설명합니다. 에이전트는 자기 워크트리에서 일하고 결과는 사람이 커밋 전에 검토합니다.

**여기서 한 걸음 더 들어가야 합니다.** 그 대체가 어디까지 유효한지가 다음 절의 내용이고, 이 편에서 가장 중요한 부분입니다.



## 2. 워크트리는 보안 경계가 아닙니다

> 격리라고 부르지만 그것은 코드 변경의 격리이지 프로세스의 격리가 아닙니다. 워크트리는 프로세스가 무엇을 할 수 있는지를 전혀 제한하지 않습니다.

![워크트리가 막아 주는 것과 막아 주지 않는 것](_assets/05-01-not-a-sandbox.svg)

워크트리는 git의 기능입니다. 같은 저장소에 작업 폴더를 여러 개 두는 것이 전부입니다. 막아 주는 것은 다른 워크트리의 파일을 실수로 덮어쓰는 일과 브랜치가 섞이는 일입니다.

막아 주지 않는 것이 훨씬 많습니다. 워크트리 밖 파일을 읽고 쓰는 일, 환경 변수를 읽는 일, 네트워크 통신, 외부 서비스 조작, 다른 프로그램 실행이 전부 그대로 가능합니다.

권한 확인을 끈 에이전트는 **여러분 계정이 할 수 있는 일을 전부 할 수 있습니다.** 홈 디렉터리의 자격증명 파일을 읽을 수 있습니다. 인터넷에 무언가를 보낼 수 있습니다. 상위 경로로 올라가 다른 프로젝트를 고칠 수도 있습니다.

이 편의 앞 편들에서 워크트리를 계속 격리라고 불렀는데, 그 말을 샌드박스로 읽으면 안 됩니다. [02-01](02-01.Repo·프로젝트·워크트리 — 작업 공간을 가르는 법.md)에서도 짚었듯 워크트리가 주는 것은 **실수를 되돌리기 쉽게 만드는 성질**이지 신뢰할 수 없는 코드를 가두는 상자가 아닙니다.

실제로 경계 역할을 하는 것은 따로 있습니다.

| 장치 | 무엇을 제한하나 | 언제 작동하나 |
|------|----------------|--------------|
| 일회용 실행 환경 (컨테이너·VM) | 파일 시스템과 네트워크 전체 | 프로세스가 도는 내내 |
| 네트워크 이그레스 제한 | 밖으로 나가는 통신 | 프로세스가 도는 내내 |
| 최소 권한·짧은 수명 자격증명 | 유출됐을 때의 피해 범위 | 유출 이후 |
| 커밋 전 사람 검토 · 결정 게이트 | 결과가 반영되는 시점 | 작업이 끝난 뒤 |

**이 표에 워크트리가 없다는 점이 요지입니다.** 그리고 아래 두 줄과 위 두 줄이 통제하는 시점이 다릅니다. 프로세스 자체를 가두는 것은 일회용 환경뿐이고, 검토와 게이트는 결과가 반영되는 시점만 통제합니다.



## 3. 비밀정보는 위치를 바꿔도 소용없습니다

> 파일에서 환경 변수로 옮기는 것은 위치만 바꾸는 것입니다. 효과가 있는 것은 유출됐을 때 피해가 작은 자격증명을 쓰는 쪽입니다.

![비밀정보를 다루는 방법별 실효성](_assets/05-01-secrets.svg)

에이전트는 워크트리 안의 모든 파일을 읽습니다. `.env` 에 실제 키가 들어 있으면 그것을 읽어 프롬프트에 인용하거나 로그에 남길 수 있습니다.

**워크트리는 원본 폴더의 파일을 그대로 갖습니다.** 원본에 키가 있으면 워크트리에도 있습니다. 워크트리를 나눈다고 비밀정보가 격리되지는 않습니다.

"환경 변수에 넣으면 되지 않나"도 답이 아닙니다. 앞 절에서 본 대로 권한 확인을 끈 에이전트는 자기 프로세스의 환경 변수를 그대로 읽습니다. 파일에서 환경 변수로 옮기는 것은 접근을 막는 것이 아니라 위치를 바꾸는 것입니다.

실제로 효과가 있는 것은 세 가지입니다. 수명이 짧아 곧 만료되는 토큰, 저장소 하나나 읽기 전용처럼 범위가 좁은 토큰, 값을 직접 넘기지 않고 필요할 때만 대신 호출해 주는 중계입니다.

브라우저 쪽에도 같은 오해가 있습니다. 스냅샷에서 비밀번호가 마스킹되는 것은 **그다음 화면에서 한 번 더 노출되는 것**을 줄여 줄 뿐입니다. 값 자체가 감춰지지는 않습니다.

| 경로 | 비밀번호가 보이나 |
|------|------------------|
| `snapshot` 출력 | 마스킹됨 |
| `fill --value` 에 넣은 명령줄 | 그대로 보임 |
| 셸 이력 | 그대로 남음 |
| 에이전트에게 준 프롬프트 | 그대로 보임 |

에이전트가 그 명령을 직접 만들었다면 값을 이미 알고 있습니다. 실제 계정 정보를 명령줄이나 프롬프트에 넣지 않는 것이 답이고, 테스트 계정만 로그인한 별도 브라우저 프로필을 쓰는 편이 낫습니다.



## 4. 명령 출력에는 의도하지 않은 것이 함께 나옵니다

> 조회 명령 하나가 등록한 모든 프로젝트의 경로와 다른 작업의 상태를 함께 보여 줍니다. 공유 전에 가공해야 합니다.

![조회 명령별로 함께 노출되는 정보](_assets/05-01-output-leak.svg)

이 노트를 쓰며 계속 마주친 문제입니다. 워크트리 현황을 보려고 실행한 명령 하나에 이 저장소와 무관한 프로젝트의 워크트리 네 개가 함께 나왔습니다. 컴퓨터 유즈의 앱 목록에는 개인·사내 앱 이름이 그대로 실렸고, 창 제목에는 열어 둔 파일명이 들어 있었습니다.

| 명령 | 함께 나오는 것 |
|------|---------------|
| `repo list` | 등록한 **모든** 프로젝트의 경로, 원격 연결 id |
| `worktree ps` | 다른 프로젝트의 워크트리 경로와 터미널 마지막 줄 |
| `diagnostics memory` | 모든 워크트리 경로, 세션 PID |
| `orchestration inbox` · `task-list` | 그 우편함·Run의 메시지와 태스크 명세 |
| `computer get-app-state` | 화면에 보이는 모든 것 |

오케스트레이션 쪽은 나아졌습니다. 조회가 Run 단위로 나뉘어 다른 프로젝트의 태스크가 함께 쏟아지지는 않습니다. 다만 `--from`을 빠뜨리면 ORCA가 임의의 터미널을 골라 그 우편함을 보여 주므로, **어느 범위를 보고 있는지 모른 채 출력을 공유하는 상황**은 여전히 생깁니다.

이 노트도 같은 규칙을 지켰습니다. 홈 경로는 전부 치환했고, 실행 중이던 앱 이름과 파일명은 옮기지 않았습니다. 버그 리포트를 올릴 때도 같은 항목을 지웁니다.

원격 연결 쪽에는 항목이 하나 더 있습니다. **페어링 코드는 비밀정보입니다.** 코드를 가진 사람은 여러분의 런타임에 붙어 터미널을 열 수 있고, 그 터미널의 에이전트는 확인 절차 없이 움직입니다. 페어링 코드는 그 기기에서 명령을 실행할 수 있는 권한과 같으므로 SSH 키와 같은 급으로 다룹니다.



## 5. ORCA가 내 설정 파일에 손을 댑니다

> 사이드바의 실시간 진행 표시는 각 에이전트의 설정 파일에 심은 훅이 만들어 냅니다. 나쁜 동작은 아니지만 알고 써야 하는 동작입니다.

![아는 에이전트 14종 중 이 맥북에서 훅이 설치된 여섯](_assets/05-01-agent-hooks.svg)

ORCA는 화면을 훔쳐보는 것이 아니라 에이전트의 설정 파일에 상태 보고용 훅을 심습니다. 이 맥북에서 상태를 조회해 봤습니다.[^hooks]

```bash
orca agent hooks status --json
```

아는 에이전트가 14종이고, 그중 여섯에 훅이 실제로 들어가 있었습니다. `managedHooksPresent: true`로 표시되는 항목입니다. 여기에 **Claude Code의 `~/.claude/settings.json`이 포함됩니다.**

내 도구의 설정 파일에 다른 프로그램이 손을 대는 것이 불편할 수 있습니다. 판단은 사용자의 몫이고 끄는 방법이 있습니다.

```bash
orca agent hooks status --json   # 지금 어디에 들어가 있는지 확인
orca agent hooks off --json      # 비활성화 + 설치된 훅 제거
```

끄면 사이드바의 실시간 진행 표시가 빈약해지지만 워크트리·터미널·자동화는 그대로 동작합니다.

이 사실을 이 편에 둔 이유가 있습니다. 앞 절들이 "에이전트가 무엇을 할 수 있는가"를 다뤘다면, 이것은 **도구 자체가 무엇을 하는가**입니다. 둘 다 알아야 경계를 설계할 수 있습니다.



## 6. 일회용 환경이 필요해지는 시점

> 워크트리로 부족한 순간이 옵니다. 다만 대부분의 독자에게는 아직 필요 없고, 필요해지는 조건이 분명합니다.

![워크트리로 충분한 구간과 일회용 환경이 필요한 구간](_assets/05-01-when-sandbox.svg)

작업마다 일회용 실행 환경을 만들고 끝나면 버리는 기능이 있습니다. 클라우드 샌드박스, VM, 로컬 컨테이너를 씁니다.

**ORCA는 여기서 얇은 껍데기입니다.** 공식 가이드가 선을 그어 두었습니다. ORCA는 절차를 순서대로 안내하고 준비 상태를 감지하고 스크립트 골격을 만들어 줍니다. 클라우드 계정을 만들거나 요금제를 고르거나 돈이 드는 작업을 승인 없이 실행하지는 않습니다. 계정과 비용은 사용자 것입니다.

레시피는 저장소 루트의 설정 파일에 적고 생성·중단·재개·삭제 네 스크립트를 연결합니다. 레시피가 저장소에 들어가므로 팀원이 클론하면 같은 환경 정의를 갖게 됩니다.

만든 레시피는 돈이 들지 않는 검사부터 돌립니다.

```bash
orca vm recipe doctor <레시피id> --json
```

이 명령의 응답 형태가 **다른 명령과 다릅니다.** 다른 명령은 결과를 `result` 안에 담는데 이것은 최상위에 그대로 돌려줍니다. 이 맥북에서도 그랬습니다.[^doctor]

```bash
# 다른 명령
{ "id": "...", "ok": true, "result": { ... }, "_meta": { ... } }

# vm recipe doctor
{ "recipeId": "default", "repoPath": "...", "ok": false, "checks": [ ... ] }
```

스크립트에서 `result`를 꺼내려다 빈 값을 받고 당황하기 쉬운 자리입니다.

응답의 `checks[].remediation`이 무엇을 하면 되는지까지 알려 줍니다. 오류를 알려 주는 데서 멈추지 않는 설계이고, 이것이 시키는 대로 하나씩 채워 나가는 것이 레시피 만들기의 정석 흐름입니다.

판단 기준은 단순합니다. 개인 PC에서 에이전트 두셋을 돌리는 단계라면 워크트리 격리로 충분합니다. 에이전트가 전역 환경을 오염시키거나, 팀이 같은 환경을 공유해야 하거나, 클라우드에서 대량으로 돌리는 단계가 되면 필요합니다.

**신뢰할 수 없는 코드를 다룰 때는 선택이 아니라 필수입니다.** 앞 절들에서 본 이유 때문입니다. 저장소 안의 파일이 에이전트에게 지시를 심을 수 있고, 워크트리는 그것을 막지 못합니다.

## 정답 (자답 후 펼치기)

### 정답 1 — 코드 변경의 격리이지 프로세스의 격리가 아닙니다

워크트리는 같은 저장소에 작업 폴더를 여러 개 두는 git 기능입니다. 다른 워크트리의 파일을 덮어쓰는 일과 브랜치가 섞이는 일을 막아 줄 뿐, 프로세스가 무엇을 할 수 있는지는 전혀 제한하지 않습니다. 권한 확인을 끈 에이전트는 워크트리 밖 파일을 읽고 쓰고 네트워크로 통신할 수 있습니다. 프로세스를 실제로 가두는 것은 컨테이너나 VM 같은 일회용 환경뿐입니다.

### 정답 2 — 위치만 바뀝니다

에이전트는 자기 프로세스의 환경 변수를 그대로 읽습니다. 파일에서 환경 변수로 옮기는 것은 접근을 막는 조치가 아닙니다. 효과가 있는 것은 유출됐을 때 피해가 작은 자격증명을 쓰는 쪽입니다. 수명이 짧은 토큰, 저장소 하나나 읽기 전용으로 범위를 좁힌 토큰, 값을 직접 넘기지 않는 중계가 그 방법입니다.

### 정답 3 — 다른 프로젝트 정보가 함께 나옵니다

조회 명령 하나가 등록한 모든 프로젝트의 경로와 다른 작업의 워크트리·터미널 상태를 함께 보여 줍니다. 원격 연결 id와 페어링 코드가 섞이면 그 자체가 실행 권한 유출입니다.

공유 전에 세 가지를 처리합니다.

1. 홈 경로와 식별자를 치환합니다.
2. 무관한 프로젝트 항목을 지웁니다.
3. 페어링 코드는 절대 붙이지 않습니다.
