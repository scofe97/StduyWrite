# 세션 세 층 — 메인·저장소·작업 운영 규칙
---
> 저장소 두 개에 기능 여러 개를 Claude 세션으로 나눠 맡길 때, 어느 창에서 채팅하고 창끼리 무엇을 주고받을지 정한 기록입니다. 창 사이 연결은 `herdr agent prompt` 한 줄과 상태 파일 하나로 합니다.



## 핵심 요약

> 채팅은 메인과 저장소 두 곳에서 하고, 작업 창은 리뷰·확인 창·긴 논의 때만 찾아갑니다. 다른 창이 보낸 글은 승인이 아니라는 규칙을 연결과 함께 둡니다.

세 층은 메인, 저장소, 작업입니다. 메인은 저장소를 가로지르는 결정과 현황을 맡습니다. 저장소는 기능을 열고 닫습니다. 작업은 기능 하나를 구현해 MR 까지 엽니다. 위로 올라가는 소식은 두 갈래입니다. 하나는 상태 파일에 남기는 기록이고 다른 하나는 위 창 입력창에 넣는 한 줄 보고입니다. Claude 세션은 입력이 와야 움직입니다. 그래서 기록만 있고 보고가 없으면 위 창은 물어보기 전까지 모릅니다.

| 하고 싶은 일 | 어디서 |
|------|------|
| 범위·설계를 정하거나 바꾸기, 문서 지시, 짧은 승인 전달 | 메인 |
| 기능 시작, 병합 뒤 정리, 기준 브랜치 최신화, 저장소 질문 | 저장소 |
| 코드 리뷰, 학습형 리뷰, push·MR | 작업 (직접 찾아감) |
| 확인 창에 멈춘 세션에 답하기 | 그 창 (직접 찾아감) |
| 다른 창에 글 보내기 | `herdr agent prompt <이름> "<글>"` |



## 이 문서의 기준

> herdr 0.9.3 의 명령과, 그 위에 직접 만든 스킬 두 개를 기준으로 했습니다. 층 구조와 상태 파일은 herdr 기능이 아니라 스킬이 정한 약속입니다.

herdr 가 제공하는 것은 workspace·탭·창, git worktree 를 여는 명령, 창마다 떠 있는 에이전트를 부르는 `herdr agent` 명령까지입니다. 그 위의 구조는 스킬 두 개가 만듭니다. herdr-project 는 저장소와 기능마다 workspace 를 열고 닫는 스크립트입니다. herdr-relay 는 다른 창에 에이전트를 띄우고 결과를 회수하는 스크립트이고, 상태 파일을 지켜보는 `fleet-watch.sh` 도 여기에 있습니다.

그래서 아래 내용 중 `herdr` 로 시작하는 명령의 동작은 herdr 설명서(`herdr --skill`)와 도움말로 확인한 사실입니다. 층 이름, 상태 파일 형식, 보고 머리표는 이 환경에서 정한 규칙입니다.



## 세 층으로 나누는 이유와 각 층이 하는 일

> 기능마다 worktree 와 workspace 를 따로 두면 에이전트끼리 같은 파일을 건드리지 않습니다. 대신 누가 무엇을 아는지가 흩어지므로 층마다 맡을 일을 정해 둡니다.

**worktree** 는 한 git 저장소에서 브랜치마다 작업 폴더를 따로 꺼내 두는 기능입니다. 기능 하나에 worktree 하나를 주면, 두 에이전트가 같은 폴더의 같은 파일을 동시에 고치는 사고가 없습니다. herdr 는 worktree 하나를 workspace 하나로 열어 사이드바에 저장소별로 묶어 보여 줍니다.

| 층 | herdr | git | 하는 일 |
|---|---|---|---|
| 메인 | 묶음마다 workspace 하나 | 없음 (스킬 저장소 폴더에서 뜸) | 저장소를 가로지르는 결정, 설계 문서 작성, 현황, 사용자 결정 전달 |
| 저장소 | 저장소마다 workspace 하나 | 본 checkout, 늘 기준 브랜치(`dev`) | 기능 시작, 병합 확인 뒤 정리, 기준 브랜치 최신화, 저장소 질문 |
| 작업 | 기능마다 worktree workspace 하나 | 기능 브랜치의 worktree | 구현, 테스트, 학습형 리뷰, 로컬 커밋, push·MR |
| 세부 작업 | 작업이나 메인 workspace 의 다른 탭 | 같은 폴더 | 문서 본문·도식처럼 따로 맡길 일 |

저장소 층의 본 checkout 을 기준 브랜치에 두는 데는 이유가 있습니다. 본 checkout 이 기능 브랜치에 가 있으면 herdr 사이드바가 다른 기능들을 그 브랜치 아래에 묶어 보여 줘서 구조가 흐려집니다. 저장소 창에서 코드를 고치지 않는 것도 같은 이유입니다. 기준 브랜치 폴더가 더러워지면 다음 기능이 그 위에서 시작합니다.

창 이름은 사람이 찾기 쉽게 정했습니다. 저장소 창은 `be-main`·`fe-main`, 작업 창은 workspace 이름(브랜치에서 `feature/` 를 뺀 값)과 같습니다. 이동도 이름으로 합니다. `ctrl+b` → `g` 를 누르고 이름이나 브랜치를 검색합니다.



## 채팅은 어디서 치는가

> 거의 모든 대화는 메인에서 하고, 저장소에 걸린 일만 저장소 창에서 합니다. 작업 창은 눈으로 봐야 하거나 직접 답해야 할 때만 찾아갑니다.

메인에서 하는 말은 대개 이렇습니다. "나 기다리는 곳 알려 줘", "fe 메일 화면 범위 정하자", "이력에 기간 필터 넣기로 해", "메일은 테스트 다시 돌리고 커밋만". 마지막처럼 다른 창에 줄 짧은 답은 메인이 그 창에 대신 전달합니다. 저장소 창에서는 "비밀번호 재설정 기능 시작해", "메일 병합됐어, 정리해" 처럼 저장소에 걸린 일을 시킵니다.

작업 창에 직접 가야 하는 경우는 넷입니다.

- 코드 리뷰: reviewr 는 그 기능 workspace 에서 diff 를 보고 코멘트를 다는 도구입니다. 코멘트는 그 창의 Claude 에게 바로 갑니다([herdr-reviewr](01-03.herdr-reviewr.md)).
- 확인 창에 멈춘 세션: 선택지나 권한 확인 창이 떠 있으면 다른 창에서 글을 보낼 수 없습니다(아래 절).
- 학습형 리뷰: 설명과 퀴즈를 주고받는 긴 대화라 중계하면 맥락이 빠집니다.
- 길어지는 구현 논의: 메인을 거치면 한 번 오갈 때마다 요약이 끼어듭니다.

어느 창이 나를 기다리는지는 두 가지로 압니다. 메인에 "기다리는 곳"을 물으면 모든 창의 마지막 화면을 읽어 정리합니다. herdr 알림이 왔다면 `ctrl+b` → `o` 로 그 창에 바로 갑니다.



## 다른 창에 글 보내기 · herdr agent prompt

> 창 사이 전달은 `herdr agent prompt` 한 명령으로 합니다. 받는 창의 입력창에 글을 붙이고 Enter 까지 치므로, 받는 Claude 에게는 사람이 친 글과 똑같이 보입니다.

```bash
herdr agent prompt be-main "[보고 ← common-mail-outbox-20261008] 메일 기능 MR 열림 / 상태 파일 ~/claude/.omc/fleet/mail-outbox.md"
```

명령의 동작(확인 창에 멈춘 창은 거부, `--wait` 로 답 기다리기, 답 읽기)과 직접 해 보는 예시 세 가지는 [CLI reference](01-01.CLI%20reference.md)에 모았습니다. 이 문서에는 운영에 필요한 약속만 둡니다.

이름으로 부르려면 창마다 herdr 에이전트 이름을 붙여야 합니다. 이 환경에서는 메인을 `main`, 저장소 창을 `be-main`·`fe-main`, 작업 창을 workspace 이름과 같게 붙였습니다. 이름은 창이 아니라 그 안의 에이전트에 붙어서, 에이전트를 다시 띄우면 사라집니다. 다시 띄운 뒤에는 `herdr agent rename <창 ID> <이름>` 으로 다시 붙입니다.

규칙은 창마다 길게 붙여 넣지 않았습니다. 한 파일(`~/claude/.omc/herdr-project/session-protocol.md`)에 적고, 창마다 그 파일을 읽으라는 한 줄과 그 창의 이름만 보냈습니다. 여섯 창(메인 하나, 저장소 둘, 작업 셋)이 모두 "규칙 확인" 이라고 답했습니다.



## 위로 올리는 길 · 상태 파일과 한 줄 보고

> Claude 세션은 다른 창을 주기적으로 들여다보지 않습니다. 그래서 작업이 끝나면 상태 파일에 기록하고, 위 창에 한 줄 보고를 보내 깨웁니다.

**상태 파일** 은 기능마다 하나씩 있는 `~/claude/.omc/fleet/<기능>.md` 입니다. 첫 줄은 `STATUS: working|done|blocked|mr-open (이유)` 이고, 그 아래 `## 진행` 에 끝낸 단위를, `## LESSONS` 에 다음 세션이 알아야 할 교훈을 적습니다. 메인에서 "fleet 현황"이라고 하면 `status.sh` 가 이 파일들의 첫 줄을 모아 표로 보여 줍니다.

기록만으로는 위 창이 깨어나지 않습니다. Claude 세션이 움직이는 때는 입력이 들어올 때와 자기가 백그라운드로 걸어 둔 명령이 끝날 때뿐입니다. 그래서 작업 창은 MR 을 열었을 때나 사용자가 "올려"라고 할 때 저장소 창에 한 줄을 보냅니다. 저장소 창은 사용자가 "메인에 올려"라고 할 때 메인에 한 줄을 보냅니다. 보고가 거부되더라도 기록은 남으므로 메인 현황표에서는 보입니다.

감시 스크립트로 깨우는 방법도 있지만 조건이 있습니다. `fleet-watch.sh` 를 백그라운드로 걸어 두면 상태 첫 줄이 done·partial·blocked 로 바뀔 때 끝나면서 건 세션을 깨웁니다. 그런데 이 스크립트는 저장소를 가리지 않고 모든 기능을 보고, 이미 본 변화를 `.seen` 파일 하나에 같이 적습니다. 그래서 메인과 저장소가 동시에 걸면 먼저 본 쪽만 깨고 다른 쪽은 놓칩니다. 지금은 한 곳에서만 걸 수 있습니다.

처음에는 이 길이 끊겨 있었습니다. 기능을 여는 스크립트(`feature-start.sh`)는 작업 창의 Claude 를 아무 지시 없이 띄웁니다. 그러니 작업 창들은 상태 파일을 고쳐야 한다는 것을 몰랐고, 일을 끝내도 첫 줄이 바뀌지 않았습니다. 규칙 공지를 보낸 뒤에야 이어졌습니다. 앞으로 여는 작업 창에도 적용하려면 스크립트가 띄울 때 첫 지시로 규칙 파일을 넘겨야 합니다.



## 다른 창이 보낸 글은 승인이 아닙니다

> 받는 Claude 는 다른 창이 보낸 글을 사용자 입력으로 받아들입니다. 그래서 보고에 머리표를 붙이고, 승인은 사람에게서만 받는다는 규칙을 모든 창에 둡니다.

작업 창이 "push 해도 됨"이라고 보내면, 저장소 창은 그 글을 사용자가 승인한 것으로 읽을 수 있습니다. 화면만으로는 누가 쳤는지 구분되지 않기 때문입니다. 그래서 보내는 글 앞에 출처를 밝힙니다.

| 머리표 | 뜻 |
|---|---|
| `[보고 ← <보낸 창 이름>]` | 일이 끝났거나 상태가 바뀌었다는 알림 |
| `[메인 지시 ← main]` | 메인이 결정을 전하는 지시 |
| `[사용자 승인 전달 ← main]` | 사용자가 메인에서 승인한 것을 메인이 전달 |

커밋·push·MR·정리의 승인으로 인정하는 것은 두 가지뿐입니다. 사용자가 그 창에 직접 친 승인과, `[사용자 승인 전달 ← main]` 머리표가 붙은 글입니다. 보고를 받은 저장소 창은 상태 파일을 읽어 확인하고 사용자에게 알리기만 합니다. 받은 보고로 push 나 정리를 시작하지 않습니다.

보내는 쪽에도 약속이 둘 있습니다. 하나는 길이입니다. 글은 한 줄 요약과 파일 경로로 짧게 쓰고, 자세한 내용은 상태 파일이나 보고서에 둡니다. 다른 하나는 보내는 때입니다. 받는 창에서 사람이 글을 치는 중이면 붙여 넣은 글이 섞여 함께 전송될 수 있습니다. 그래서 일이 끝났거나 요청받았을 때만 보냅니다.



## push·MR 은 작업 창이 엽니다

> 스킬의 처음 설계는 저장소 창이 push·MR 을 맡는 것이었습니다. 리뷰와 학습형 리뷰를 작업 창에서 하므로, 마지막 확인과 MR 까지 같은 창에서 끝내도록 바꿨습니다.

처음 설계에서 작업 창은 로컬 커밋까지만 하고, push·MR·정리는 저장소 창이 사용자 승인을 받아 했습니다. 원격 작업은 사내망과 승인이 필요하니 한 곳에 모으려는 뜻이었습니다.

바꾼 이유는 리뷰가 작업 창에서 일어나기 때문입니다. reviewr 로 보는 diff, 학습형 리뷰, 테스트가 모두 작업 창에서 일어납니다. 거기서 끝난 판단을 저장소 창으로 넘겨 push 를 다시 시키면 한 단계가 늘어납니다.

이것이 기술적으로 꼭 필요한 선택은 아닙니다. worktree 들은 한 저장소의 브랜치와 커밋을 함께 쓰므로, 저장소 창에서도 `git diff dev...feature/<기능>` 으로 기능 브랜치를 보고 `git -C <worktree> push` 로 올릴 수 있습니다. 작업 창으로 옮긴 것은 흐름을 줄이려는 선택입니다. 대가로 원격 작업이 기능 수만큼 여러 창에 흩어지고, 작업 창마다 사내망과 승인이 필요합니다.

MR 은 GitLab push 옵션으로 push 와 함께 열 수 있습니다. 서버가 이 옵션을 허용하는지는 아직 확인하지 않았습니다. 이 맥에는 `glab` 이 없어서 CLI 로 MR 을 따로 만들 수는 없고, 옵션이 막혀 있으면 GitLab 웹에서 엽니다.

```bash
git push -u origin feature/<기능> -o merge_request.create -o merge_request.target=dev
```

스킬 문서에는 아직 "push·MR 은 저장소"라고 적혀 있습니다. 그래서 규칙 파일 첫 줄에 이 파일이 스킬보다 우선한다고 적고, 각 창에 보낸 공지에도 같은 말을 넣었습니다.



## 기능 하나가 흐르는 길 · be 와 fe 를 함께 만들 때

> be 에 메일 발송을, fe 에 메일 관리 화면을 만든다고 하면 결정은 메인에, 구현과 MR 은 각 작업 창에, 열고 닫는 일은 저장소 창에 갑니다.

1. 시작: 메인에서 범위를 정합니다. fe 화면 범위가 정해지지 않았다면 이것이 첫 결정입니다. 기능 workspace 는 저장소 창에서 "기능 시작해"로 엽니다. 스크립트가 브랜치·worktree·workspace·작업 Claude·상태 파일을 한 번에 만듭니다.
2. 설계 문서: 메인이 API 계약 문서, 결정 로그, 오픈 이슈를 씁니다. 설계 문서는 git 밖(로컬 전용) 폴더에 있어서 두 세션이 같은 파일을 고치면 병합 없이 서로 덮어씁니다. 그래서 쓰는 창을 메인 하나로 정했습니다.
3. 구현: be 작업 창이 구현하고, fe 작업 창은 계약 문서를 보고 화면을 만듭니다. 같은 맥이라 fe 창은 be 가 아직 push 하기 전에도 be worktree 의 DTO 를 경로로 읽을 수 있습니다.
4. 설계가 바뀔 때: 발견한 작업 창은 다른 저장소 코드를 고치지 않고 `STATUS: blocked (설계 변경 필요: 무엇)` 로 멈춥니다. 메인이 사용자와 정해 결정 로그와 계약 문서를 고친 뒤, 영향받는 작업 창마다 한 줄로 전합니다. 순서는 be 먼저, fe 나중입니다.
5. 학습형 리뷰: 각 작업 창에 직접 가서 diff 를 옆에 두고 설명과 퀴즈로 진행합니다. 결과 문서는 설계 문서 폴더의 학습 폴더에 남깁니다.
6. 완료와 MR: 학습형 리뷰, 전체 테스트, 로컬 커밋이 끝나면 작업 창이 `STATUS: done` 으로 바꾸고 push·MR 여부를 묻습니다. 승인 뒤 MR 을 열고 `mr-open` 으로 바꾼 다음 저장소 창에 한 줄 보고를 보냅니다. 순서는 be 먼저입니다. fe 화면이 be API 에 기대기 때문입니다.
7. 병합과 정리: 병합은 GitLab 에서 일어나 이 맥이 저절로 알 수 없습니다. 저장소 창에 "병합됐어"라고 알리면 `feature-close.sh` 가 fetch 로 병합을 확인한 뒤 workspace·worktree·브랜치를 정리합니다.
8. 다음 기능: 저장소 창에서 기준 브랜치를 받고 다음 기능을 엽니다. 다음 기능이 앞 기능 코드에 기대지 않으면 병합을 기다릴 필요가 없습니다.



## worktree 를 옮긴 뒤 workspace 를 다시 여는 절차

> `git worktree move` 로 폴더를 옮겨도 herdr workspace 는 옛 경로를 계속 들고 있습니다. workspace 이름을 바꿔도 경로는 그대로라서, worktree 로 새로 열고 옛 workspace 를 닫아야 합니다.

에이전트 세션이 작업 도중 worktree 폴더 이름을 브랜치 이름에 맞춰 옮긴 적이 있습니다. 그 뒤 그 workspace 의 에이전트 창, 보조 에이전트 창, reviewr 가 전부 엉뚱한 폴더(`~/claude`)에서 돌고 있었습니다. reviewr 는 메일 작업의 diff 대신 그 폴더 저장소의 diff 를 보여 줬습니다. herdr 가 기억하는 경로와 git 이 아는 경로를 나란히 보면 어긋남이 바로 드러납니다.

```bash
herdr workspace get <workspace ID> | jq -r '.result.workspace.worktree.checkout_path'
git -C <원 저장소> worktree list
```

`herdr workspace rename` 은 표시 이름만 바꿉니다. 경로를 바로잡는 명령은 없어서 아래 순서로 옮겼습니다.

1. 옛 에이전트 세션에게 인계 노트를 쓰게 합니다. 에이전트 세션의 작업 폴더는 띄울 때 정해져서 대화 안에서 바꿀 수 없으므로, 새 폴더에서 새 세션을 띄워야 합니다.
2. 올바른 경로로 worktree workspace 를 새로 엽니다. 이름은 다른 worktree 처럼 브랜치에서 `feature/` 를 뺀 값으로 맞췄습니다.
3. 새로 열린 첫 창에서 에이전트를 띄우고 인계 노트를 읽게 합니다. reviewr 는 2번에서 새 경로로 저절로 열립니다.
4. 새 세션이 상태를 확인하면 옛 workspace 를 닫습니다.

```bash
herdr worktree open --workspace <원 저장소 workspace ID> \
  --path <새 worktree 경로> --label <브랜치 이름> --no-focus
herdr pane run <새 창 ID> "<에이전트 실행 명령>"
herdr workspace close <옛 workspace ID>
```

`--workspace` 를 빼고 다른 저장소의 창에서 `worktree open` 을 부르면 `worktree_not_found` 로 실패합니다. 기준 저장소를 호출한 창의 저장소로 잡기 때문입니다. 원 저장소의 workspace ID 를 넘기면 해결됩니다. `workspace close` 는 창만 닫고 worktree 폴더와 커밋하지 않은 변경은 건드리지 않습니다. 닫은 뒤 변경 파일 수가 그대로인지 `git status --porcelain -uall` 로 세어 확인했습니다.

상태 파일(`~/claude/.omc/fleet/<기능>.json`)의 `worktree`·`workspace`·`branch`·`child` 값도 옛 값으로 남습니다. 고치지 않으면 정리 스크립트(`feature-close.sh`)가 worktree 를 못 찾습니다. 값을 고친 뒤 `status.sh` 와 `feature-close.sh <기능> --plan` 으로 새 경로를 찾는지 확인했습니다. 새 창의 에이전트는 아래 절의 옵션으로 띄웁니다.



## 실제로 해 보며 고친 것

> 구조를 실제 세션에 적용하자 다섯 군데가 어긋나 있었습니다. 모두 "자동으로 이어질 것"이라고 가정한 자리였습니다.

- worktree 를 옮긴 뒤의 workspace: `git worktree move` 뒤에도 herdr workspace 가 옛 경로를 들고 있었습니다. 상태 파일의 `worktree`·`workspace`·`branch` 값도 옛 값이라 정리 스크립트가 worktree 를 못 찾았습니다. workspace 를 새로 열고 상태 파일 값을 고친 뒤 `feature-close.sh <기능> --plan` 으로 확인했습니다. 절차는 아래 절에 있습니다.
- 맨 런처로 띄운 작업 Claude: 새 창에서 계정 런처만으로 Claude 를 띄웠더니 스킬 저장소의 스킬·규칙·계정별 메모리를 보지 못했습니다. 스크립트가 띄울 때와 같은 옵션으로 다시 띄웠습니다.
- 상태 파일 규칙 미전달: 앞 절에서 말한 대로 작업 창들이 규칙을 몰라 위로 가는 길이 끊겨 있었습니다.
- 이름 없는 창: 저장소 창과 메인 창에 herdr 에이전트 이름이 없어 창 ID 로만 부를 수 있었습니다.
- 계정마다 다른 메모리: 메인과 나머지 창이 다른 계정으로 떠 있어 메모리 폴더가 다릅니다. 한쪽에서 "기억해"라고 한 것이 다른 쪽에 보이지 않습니다. 작업 창이 LESSONS 에 적고, 메인이 확인해 메모리에 옮기는 것으로 정했습니다.

작업 Claude 를 띄우는 옵션은 아래와 같습니다. 스킬 저장소를 `--add-dir` 로 열면 스킬이 보이고, 환경 변수가 있어야 그 저장소의 CLAUDE.md 와 규칙까지 읽습니다. `RELAY_DEPTH=1` 은 이 창이 메인이 아니라는 표시라, 사용량 승인 같은 메인 전용 일을 거부하게 합니다.

```bash
cd <worktree> && export RELAY_DEPTH=1 CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1
<계정 런처> --add-dir ~/claude --settings '{"autoMemoryDirectory":"<계정 설정 폴더>/projects/-Users-<사용자>-claude/memory"}' -n <이름>
herdr agent rename <창 ID> <이름>
```



## 아직 확인하지 않은 것

> 아래 넷은 동작을 직접 보지 못했습니다. 쓰기 전에 한 번씩 시험해야 합니다.

- GitLab 서버가 push 옵션(`merge_request.create`)을 허용하는지 확인하지 않았습니다. 이 맥에서 사내 GitLab 에 접속되지 않는 시간에 정리했기 때문입니다.
- 받는 창에서 사람이 글을 치는 중에 보고가 들어오면 실제로 어떻게 섞이는지 시험하지 않았습니다.
- 저장소 창 두 곳에는 `RELAY_DEPTH` 가 없습니다. 스크립트가 생기기 전에 띄운 창이라, 설계와 달리 메인 전용 일(사용량 승인)도 할 수 있는 상태입니다.
- 병합을 자동으로 알아채는 장치는 없습니다. GitLab 을 fetch 해야 알 수 있고, 그것도 사내망에서만 됩니다.
