# MCP
---
> 외부 도구와 실시간 데이터 소스를 안전하게 연결하는 표준 프로토콜의 동작 원리를 다룹니다. 도구 검색, 범위 분리, 컨텍스트 최적화, 코드 실행 패턴까지 실제 운영에 필요한 설정을 정리합니다.



## 핵심 요약

> MCP 는 외부 서비스의 실시간 데이터를 조회하고 조작하기 위한 개방형 연결 표준입니다.

대형 언어 모델은 학습 시점 이후의 최신 정보를 알지 못하며 외부 인프라에 직접 접근할 수도 없습니다. **MCP**(Model Context Protocol, 모델과 외부 도구를 잇는 개방형 프로토콜)는 외부 도구를 일관되게 연결하는 규격입니다. 정적 지침을 담는 메모리나 작업 절차를 감싸는 스킬과 달리 데이터베이스 조회나 이슈 생성 같은 동적 상호작용을 실시간으로 처리합니다.

도구가 늘어날수록 도구 명세가 모델 컨텍스트를 과도하게 차지하는 문제가 발생합니다. Claude Code 는 도구를 필요할 때만 불러오는 도구 검색 기능과 설명 길이 상한, 자동 백그라운드 전환으로 자원을 아낍니다. 수백 개 이상의 대규모 도구를 운영할 때는 도구를 직접 호출하는 대신 코드를 작성해 실행하는 패턴으로 토큰 소모를 크게 줄일 수 있습니다.

| 하고 싶은 일 | 쓸 것 |
|------|------|
| 외부 서비스 실시간 연동 및 동적 데이터 조회 | MCP 프로토콜 연결 |
| 팀 저장소에 공유할 프로젝트 도구 등록 | 프로젝트 스코프 (`.mcp.json`) |
| 모든 프로젝트에서 쓸 개인 도구 등록 | 사용자 스코프 (`~/.claude.json`) |
| 웹에서 쓰던 도구를 CLI 세션에 즉시 연동 | Claude.ai MCP 커넥터 |
| 도구 명세로 인한 컨텍스트 낭비 방지 | 동적 도구 검색 (`ENABLE_TOOL_SEARCH`) |
| 특정 도구를 검색 없이 항상 컨텍스트에 유지 | 서버 설정 내 `"alwaysLoad": true` |
| 긴 도구 실행으로 인한 대화 차단 방지 | 자동 백그라운드 전환 (`CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS`) |
| Claude 를 외부 앱의 MCP 도구로 제공 | `claude mcp serve` |
| 대규모 도구 환경에서 토큰 소모 최소화 | 샌드박스 기반 코드 실행 패턴 |
| 연결 상태 및 오류 코드 점검 | `claude mcp list` 및 `/mcp` |

## MCP 가 푸는 문제

> 정적 지식에 갇힌 모델에게 외부 시스템과 실시간으로 소통하는 표준 통로를 열어 줍니다.

대형 언어 모델은 사전에 학습된 데이터에 의존하므로 현재 시점의 실시간 정보를 알지 못합니다. 소스 코드 저장소의 최근 풀 리퀘스트나 실시간 결제 내역, 프로덕션 데이터베이스 상태를 확인하려면 외부 시스템과의 통신이 필수적입니다. 서비스마다 API 규격과 인증 체계가 다르면 도구를 연동할 때마다 별도의 결합 코드를 작성해야 하는 번거로움이 생깁니다.

### 실시간 외부 상태와의 단절

전통적인 프롬프트 엔지니어링은 사용자가 필요한 정보를 직접 복사해 입력창에 붙여넣는 방식으로 작동했습니다. 이 방식은 데이터가 조금만 바뀌어도 매번 사람이 개입해야 하므로 자동화가 끊깁니다.

MCP 는 클라이언트와 서버 구조로 이 문제를 해결합니다. Claude Code 는 클라이언트 역할을 맡습니다. GitHub 나 PostgreSQL 같은 외부 서비스 앞단에는 MCP 서버가 위치합니다. Claude Code 가 표준화된 JSON-RPC 요청을 보내면 MCP 서버가 이를 해석해 외부 API 를 호출하고 결과를 표준 규격으로 반환합니다.

### 메모리와 스킬과의 경계

에이전트 확장을 도입할 때 메모리, 스킬, MCP 의 역할 구분이 모호해지기 쉽습니다. 세 기능은 데이터의 수명과 변경 주기에 따라 명확히 갈립니다.

메모리는 사용자 선호도나 코딩 규칙처럼 자주 바뀌지 않는 정적 지식을 파일에 기록해 영속화합니다. 스킬은 반복되는 업무 절차나 스크립트 실행 지침을 프롬프트와 로컬 명령으로 감싼 절차 지식입니다. 반면 MCP 는 끊임없이 변하는 외부 시스템의 실시간 상태를 읽고 조작하는 통신 규약입니다. 아키텍처 원칙은 메모리에 보관합니다. 배포 파이프라인 지침은 스킬로 정의하고, 실시간 이슈 목록은 MCP 로 조회하는 방식이 자연스럽습니다.

### 표준 통신 아키텍처와 생태계

MCP 생태계는 다양한 표준 서버를 중심으로 빠르게 확장되고 있습니다. 파일시스템 서버는 로컬 디렉터리의 읽기와 쓰기를 담당하고 GitHub 서버는 커밋과 풀 리퀘스트를 관리합니다. 데이터베이스 서버는 SQL 쿼리를 실행하며 Slack 서버는 팀 채널로 메시지를 전송합니다.

모든 서버가 표준 프로토콜을 따르므로 Claude Code 는 개별 서비스의 전송 계층 세부 사항을 알 필요가 없습니다. 도구 이름과 파라미터 규격만 파악하면 단일한 인터페이스 안에서 복수의 서비스를 조합해 복잡한 작업을 수행할 수 있습니다.



## 서버 추가와 범위

> 도구의 사용 목적과 공유 대상에 따라 올바른 전송 방식과 스코프를 선택해야 보안 위험을 막을 수 있습니다.

외부 도구를 무작정 연결하면 민감한 API 토큰이 노출되거나 불필요한 도구가 다른 작업 공간까지 오염시키는 문제가 발생합니다. 팀원과 함께 쓰는 도구인지 개인 전용 도구인지에 따라 설정 위치를 엄격히 분리해야 합니다.

### 네 가지 전송 프로토콜

Claude Code 는 MCP 서버와 통신하기 위해 네 가지 전송 프로토콜을 지원합니다.

가장 권장되는 방식은 HTTP 전송입니다. 원격 서버와 통신할 때 안정적이며 OAuth 2.0 인증을 자연스럽게 지원합니다. CLI 명령으로 간편하게 등록할 수 있습니다.

```bash
claude mcp add --transport http notion https://mcp.notion.com/mcp
```

로컬 환경에서 Node.js 나 바이너리 형태로 실행되는 도구에는 표준 입출력(stdio) 전송을 사용합니다. 실행 시점에 프로세스를 생성해 표준 입출력 스트림으로 통신합니다.

```bash
claude mcp add --transport stdio database -- npx -y @bytebase/dbhub --dsn "${DATABASE_URL}"
```

과거에 쓰이던 SSE(Server-Sent Events) 전송은 하위 호환성을 위해 유지되지만 현재는 HTTP 전송으로 대체되는 추세입니다.

마지막으로 WebSocket(`ws`) 전송은 원격 서버가 클라이언트 요청 없이도 이벤트를 푸시해야 하는 지속적인 양방향 연결에 적합합니다. 다만 WebSocket 은 OAuth 흐름을 지원하지 않으며 오직 헤더 인증만 가능합니다. CLI 플래그가 없으므로 설정 파일이나 `add-json` 명령으로 등록해야 합니다. v2.1.285부터는 `claude mcp list` 에서 WebSocket 서버의 URL 과 상태가 정상적으로 출력됩니다.

### 세션 작업 디렉터리와 인증 수명주기

stdio 전송으로 실행되는 서버는 v2.1.139부터 저장소 루트의 절대 경로가 담긴 `CLAUDE_PROJECT_DIR` 환경 변수를 자동으로 주입받습니다. 프로젝트 `.mcp.json` 에서는 `${CLAUDE_PROJECT_DIR:-.}` 문법으로 프로젝트 기준 상대 경로를 안전하게 참조할 수 있습니다. v2.1.163부터는 세션 식별자인 `CLAUDE_CODE_SESSION_ID` 도 함께 전달되어 세션 재개 시에도 동일한 맥락을 유지합니다.

v2.1.203부터 MCP 서버는 `roots/list` 요청을 통해 Claude Code 가 바라보는 모든 작업 디렉터리를 감지합니다. 디렉터리가 추가되면 `notifications/roots/list_changed` 알림이 서버로 전달됩니다. 또한 stdio 서버에는 30분의 유휴 타임아웃이 적용됩니다.

인증 측면에서는 OAuth 2.0 흐름을 내장 지원하여 토큰을 시스템 키체인에 안전하게 보관합니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> v2.1.193부터는 시작 시 로그인이 필요한 서버 목록을 안내합니다. `headersHelper` 가 등록된 환경에서는 401이나 403 오류가 발생할 때 자동으로 헬퍼를 다시 실행해 자격 증명을 갱신합니다. 단 v2.1.238부터 신뢰하지 않는 작업 공간에서는 프로젝트 레벨의 `headersHelper` 실행이 차단되며 환경 변수 상속도 제한됩니다.

### 설정 스코프와 우선순위

Claude Code 는 MCP 설정을 세 가지 기본 스코프로 나누어 관리합니다.

로컬 스코프(`--scope local`)는 기본값이며 현재 사용자의 현재 프로젝트에만 적용됩니다. 설정 내용은 `~/.claude.json` 내부의 프로젝트별 경로 아래에 저장되므로 버전 관리 시스템에 들어가지 않습니다.

프로젝트 스코프(`--scope project`)는 프로젝트 루트의 `.mcp.json` 파일에 저장됩니다. 저장소에 커밋되어 팀원 전체가 같은 도구 설정을 공유할 수 있습니다. 보안을 위해 다른 팀원이 해당 도구를 처음 실행할 때 승인 대화상자가 나타납니다.

사용자 스코프(`--scope user`)는 `~/.claude.json` 의 최상위에 저장됩니다. 머신 내의 모든 프로젝트 세션에서 해당 도구를 공통으로 불러올 수 있습니다.

```bash
# 팀원과 공유하는 프로젝트 스코프 등록
claude mcp add --scope project --transport http github https://api.githubcopilot.com/mcp/

# 모든 프로젝트에서 사용할 개인 도구 등록
claude mcp add --scope user --transport stdio memory -- npx @modelcontextprotocol/server-memory
```

동일한 이름의 서버가 여러 스코프에 중복 정의되어 있으면 로컬 스코프가 가장 높은 우선순위를 가집니다. 사용자 정의 설정을 프로젝트 기본값으로 덮어쓰거나 로컬 전용 설정으로 임시 변경할 때 유용합니다.

### 환경 변수 치환과 CLI 관리 명령

설정 파일에 민감한 API 키나 비밀번호를 직접 적으면 보안 사고가 발생합니다. `command`, `args`, `env`, `url`, `headers` 필드는 `${VAR}` 및 `${VAR:-default}` 문법으로 런타임 환경 변수를 치환합니다.

```json
{
  "mcpServers": {
    "api-server": {
      "type": "http",
      "url": "${API_BASE_URL:-https://api.example.com}/mcp",
      "headers": {
        "Authorization": "Bearer ${API_KEY}"
      }
    }
  }
}
```

CLI 를 통해 등록된 서버를 직관적으로 관리할 수 있습니다.

```bash
# 등록된 서버 목록 및 상태 확인
claude mcp list

# 특정 서버의 상세 설정 조회
claude mcp get github

# 서버 제거
claude mcp remove github

# 비대화형 환경에서 OAuth 로그인 수행 (v2.1.186+)
claude mcp login github --no-browser
```

### 엔터프라이즈 관리형 MCP

기업 환경에서는 중앙 IT 관리자가 보안 정책에 따라 사용 가능한 MCP 서버를 강제해야 합니다. 관리형 설정 파일인 `managed-mcp.json` 을 시스템 전역 디렉터리에 배치하면 일반 사용자가 임의로 삭제할 수 없는 전역 도구를 배포할 수 있습니다.

macOS 는 `/Library/Application Support/ClaudeCode/managed-mcp.json` 경로를 씁니다. Linux 와 WSL 은 `/etc/claude-code/managed-mcp.json` 에 둡니다. Windows 는 `C:\Program Files\ClaudeCode\managed-mcp.json` 경로에 배치합니다. 누구나 읽을 수 있는 파일이므로 평문 인증 정보를 넣어서는 안 됩니다.

도구 필터링은 관리형 설정의 `allowedMcpServers` 와 `deniedMcpServers` 키로 처리합니다. 대상 지정에는 `serverUrl`, `serverCommand`, `serverName` 키를 씁니다. 허용 목록과 차단 목록이 충돌하면 항상 차단 규칙이 우선합니다.

### 플러그인과 서브에이전트 한정 서버

도구의 사용 범위를 특정 기능이나 에이전트로 좁힐 수도 있습니다.

플러그인은 자체 루트에 `.mcp.json` 을 두거나 `plugin.json` 매니페스트 내부에 MCP 서버를 선언할 수 있습니다. 이때 `${CLAUDE_PLUGIN_ROOT}` 변수를 사용하여 플러그인 설치 경로 기준의 상대 경로를 참조합니다.

서브에이전트 마크다운 정의의 프론트매터에는 `mcpServers:` 키를 사용해 특정 에이전트만 사용할 MCP 서버를 인라인으로 선언할 수 있습니다. 이렇게 등록된 서버는 해당 서브에이전트의 실행 컨텍스트에만 격리되어 로드되며, 상위 메인 세션이나 다른 형제 에이전트의 컨텍스트를 침범하지 않습니다.



## 도구가 컨텍스트에 실리는 방식

> 수많은 도구 정의와 방대한 반환값으로 인한 컨텍스트 고갈을 막기 위해 다양한 방어 기제를 둡니다.

MCP 서버를 여러 개 등록하면 도구 명세만으로도 컨텍스트 윈도우가 고갈됩니다. 도구 설명이 컨텍스트 창을 메우면 정작 모델이 추론에 사용할 공간이 부족해지고, 응답 지연과 비용 상승이 발생합니다. Claude Code 는 도구를 메모리에 적재하는 시점과 크기를 정밀하게 통제합니다.

### 온디맨드 도구 검색과 예외 설정

Claude Code 는 기본적으로 **도구 검색**(Tool Search, 컨텍스트 낭비를 막기 위해 도구 명세를 지연 적재하는 기능)을 활성화합니다. 모든 도구 명세를 처음부터 모델에 전달하지 않고, 모델이 필요로 할 때 온디맨드로 탐색하여 로드합니다.

환경 변수 `ENABLE_TOOL_SEARCH` 로 동작 방식을 조정할 수 있습니다.

| 설정값 | 동작 방식 |
|------|------|
| 미설정 (기본값) | 모든 MCP 도구를 지연 적재하여 필요할 때만 탐색 |
| `auto` | 도구 정의가 컨텍스트 윈도우의 10% 에 도달할 때까지 사전 로드 후 전환 |
| `auto:<N>` | 사용자 지정 비율(예: `auto:5`)에 도달하면 지연 적재로 전환 |
| `true` | 모든 도구를 강제로 지연 적재 |
| `false` | 도구 검색을 끄고 모든 도구 설명을 처음에 전부 전송 |

매 턴마다 반드시 사용해야 하는 핵심 도구는 도구 검색을 우회할 수 있습니다. 서버 설정에 `"alwaysLoad": true` 를 부여하면 지연 적재 대상에서 빠져 항상 즉시 사용 가능한 상태로 유지됩니다. 반대로 서버 제작자가 사전 로드로 지정한 도구라도 `"alwaysLoad": false` 를 주면 강제로 도구 검색 뒤로 숨길 수 있습니다.

### 동적 도구 갱신과 설명 길이 상한

세션 실행 중에 MCP 서버가 도구를 추가하거나 수정할 수 있습니다. Claude Code 는 `list_changed` 알림을 지원하므로 재연결 없이도 바뀐 도구 목록을 즉시 반영합니다.

지나치게 장황한 도구 설명으로 인한 토큰 낭비를 막기 위해 길이 상한도 적용됩니다. v2.1.296 기준 사전 로드되는 도구 설명과 서버 지시문은 기본 4,096자로 잘립니다. 도구 검색을 통해 동적으로 로드되는 도구 설명은 최대 16,384자까지 허용됩니다. 필요한 경우 `CLAUDE_CODE_MAX_MCP_DESCRIPTION_LENGTH` 환경 변수로 이 값을 재정의할 수 있습니다. 중요한 파라미터나 핵심 지침은 설명의 앞부분에 작성하는 것이 안전합니다.

### 서버 중복 제거와 출력 토큰 한도

동일한 이름의 도구 서버가 전역, 프로젝트, 로컬에 흩어져 있으면 로컬 스코프 설정을 기준으로 중복이 제거됩니다. 의도치 않게 동일 도구가 중복 등록되어 컨텍스트를 두 배로 낭비하는 현상을 방지합니다.

도구 실행 결과로 돌아오는 출력 데이터의 크기에도 엄격한 제한이 있습니다.

| 단계 | 기준치 | 동작 |
|------|------|------|
| 경고 단계 | 10,000 토큰 | 출력이 크다는 경고 메시지 출력 |
| 기본 상한 | 25,000 토큰 | 본문 대신 파일로 저장하고 해당 파일 경로만 컨텍스트에 전달 |
| 디스크 보관 | 50,000 글자 | 5만 글자를 초과하는 결과물은 자동으로 디스크에 영속화 |

최대 출력 토큰 제한은 `MAX_MCP_OUTPUT_TOKENS` 환경 변수를 통해 필요에 따라 상향할 수 있습니다.

### 장기 실행 도구 자동 백그라운드 전환

복잡한 데이터베이스 집계나 대규모 파일 동기화 작업은 실행 시간이 수 분 이상 걸릴 수 있습니다. 이전 버전에서는 도구가 끝날 때까지 전체 세션이 차단되어 사용자가 다른 입력을 할 수 없었습니다.

v2.1.212부터는 2분 이상 실행되는 도구 호출을 자동으로 백그라운드로 전환합니다. 메인 세션의 차단이 풀리므로 사용자는 다른 대화를 이어갈 수 있으며, 도구 실행이 완료되면 비동기적으로 결과를 수신합니다. 이 대기 시간 임계치는 `CLAUDE_CODE_MCP_AUTO_BACKGROUND_MS` 환경 변수로 밀리초 단위 조절이 가능합니다.



## 도구 밖의 표면

> 함수 호출 방식 외에도 슬래시 명령, 리소스 인라인 참조, 대화형 UI 확장을 제공합니다.

외부 시스템과의 연동을 오직 백그라운드 함수 호출로만 제한하면 복잡한 작업 흐름에서 사용자가 개입하기 어렵습니다. 도구가 요구하는 민감한 파라미터를 사용자가 직접 대화창에서 입력하거나, 조회된 대량의 데이터를 시각적으로 즉시 확인하지 못하면 불필요한 질의응답이 반복됩니다.

### 슬래시 명령 프롬프트

MCP 서버는 재사용 가능한 프롬프트 템플릿을 노출할 수 있습니다. Claude Code 는 이를 감지하여 세션 내의 슬래시 명령 형태로 자동 등록합니다.

명령 이름은 `/mcp__<server>__<prompt>` 형식을 따릅니다. 예를 들어 `github` 서버가 `review` 프롬프트를 제공하면, 사용자는 `/mcp__github__review` 로 정형화된 코드 리뷰를 즉시 시작할 수 있습니다.

### 골뱅이 멘션을 통한 인라인 리소스

외부 문서나 데이터베이스 스키마를 대화 도중에 즉시 인용해야 할 때가 있습니다. MCP 리소스 기능을 활용하면 `@` 멘션 문법으로 외부 리소스를 프롬프트에 직접 인라인으로 포함할 수 있습니다.

```markdown
@database:postgres://mydb/users 스키마를 참고해서 회원 가입 쿼리를 작성해 주세요.
```

이 문법을 사용하면 모델이 별도의 도구 호출 과정을 거치지 않고도 지정된 리소스의 최신 내용을 프롬프트 컨텍스트에 즉시 삽입해 처리합니다.

### 대화형 UI 확장을 위한 MCP Apps

전통적인 도구 결과는 터미널에 평문 텍스트나 JSON 형태로만 반환되었습니다. 대규모 테이블이나 복잡한 차트를 텍스트로 확인하는 것은 가독성이 떨어집니다.

공식 MCP 확장 규격인 MCP Apps 는 도구 호출 결과로 대화형 UI 컴포넌트를 반환할 수 있게 해 줍니다. 대화창을 벗어나지 않고도 리치 대시보드, 인터랙티브 폼, 데이터 시각화 결과물을 인라인으로 렌더링하여 확인할 수 있습니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 -->

### 구조화된 입력 요청을 돕는 Elicitation

v2.1.76부터 지원되는 MCP Elicitation 은 도구 실행 도중에 사용자에게 구조화된 입력을 역으로 요청하는 기능입니다.

파괴적인 데이터베이스 변경 전에 확인 대화상자를 띄울 수 있습니다. 여러 선택지 중 하나를 고르게 하거나 필수 필드를 입력받을 수도 있습니다. 일방적인 도구 호출을 넘어 양방향 상호작용이 가능해집니다.



## Claude 를 MCP 서버로

> Claude Code 자체를 MCP 서버로 띄워 다른 애플리케이션이나 외부 에이전트의 도구로 연결할 수 있습니다.

Claude Code 의 파일 탐색, 코드 수정, 명령 실행 능력을 외부 시스템에서 호출하고 싶지만 연결 프로토콜이 표준화되지 않으면 연동 작업이 막힙니다. 독립된 에디터나 자체 제작한 오케스트레이터가 Claude Code 를 하위 작업 도구로 활용해야 하는 상황이 대표적입니다.

### 표준 stdio 서버 구동

Claude Code 는 자체적으로 MCP 서버 역할을 수행할 수 있는 구동 명령을 내장하고 있습니다.

```bash
claude mcp serve
```

이 명령을 실행하면 Claude Code 가 표준 입출력 스트림 기반의 MCP 서버로 대기합니다. 외부 도구나 다른 개발 환경은 표준 MCP 프로토콜 규격에 맞춰 이 프로세스와 통신할 수 있습니다.

### 다중 에이전트 오케스트레이션 연동

이 기능은 복수의 에이전트가 협업하는 환경에서 특히 빛을 발합니다. 예를 들어 상위 오케스트레이션 Claude 세션에 하위 Claude 인스턴스를 도구로 등록할 수 있습니다.

```bash
claude mcp add --transport stdio claude-agent -- claude mcp serve
```

상위 에이전트는 복잡한 코드 분석이나 리팩토링 작업을 `claude-agent` 도구 호출로 위임합니다. 하위 Claude 프로세스가 독립된 환경에서 작업을 수행하고 결과만 상위 세션에 돌려주므로 역할이 깔끔하게 분리됩니다.



## 컨텍스트 팽창과 코드 실행

> 도구를 직접 호출하는 대신 코드를 작성해 실행함으로써 수만 토큰의 낭비를 원천 차단합니다.

생태계 확장에 따라 수십 개 이상의 서버를 붙이는 대규모 환경이 등장했습니다. 하지만 이 규모에서는 **컨텍스트 팽창**(context bloat, 도구 명세와 중간 데이터가 컨텍스트 창을 채우는 현상)이 발생해 효율이 급격히 떨어집니다.

### 대규모 도구 환경의 두 가지 토큰 낭비

컨텍스트 팽창은 크게 두 가지 경로에서 발생합니다.

첫째는 도구 정의 자체의 과부하입니다. 수백 개의 도구 스키마를 사전에 로드하면 사용자의 본 질문을 읽기도 전에 수십만 토큰이 소모됩니다.

둘째는 중간 데이터의 불필요한 모델 통과입니다. 예를 들어 Google Drive 에서 회의 녹취록을 읽어 Salesforce 에 업데이트하는 작업을 가정해 봅시다. 기존 도구 호출 방식에서는 수만 토큰에 달하는 녹취록 원문이 모델의 컨텍스트 창으로 들어온 뒤 다시 업데이트 도구의 인자로 모델을 거쳐 나갑니다. 대용량 데이터가 모델의 컨텍스트를 두 번이나 가로지르며 막대한 토큰을 낭비합니다.

### 코드 API 변환과 샌드박스 실행

Anthropic 엔지니어링 팀은 이 문제의 해결책으로 도구를 직접 호출하는 대신 코드를 작성해 실행하는 방식을 제시했습니다.

모든 MCP 도구를 파일시스템 형태의 타입화된 TypeScript 함수로 노출합니다. 에이전트는 도구를 직접 호출하지 않고 이 함수들을 가져다 쓰는 오케스트레이션 코드를 작성합니다. 작성된 코드는 격리된 샌드박스 환경에서 실행됩니다.

```typescript
import * as gdrive from './servers/google-drive';
import * as salesforce from './servers/salesforce';

// 중간 데이터는 샌드박스 메모리에만 머물며 모델 컨텍스트를 거치지 않습니다
const transcript = (await gdrive.getDocument({ documentId: 'meeting-123' })).content;

await salesforce.updateRecord({
  objectType: 'SalesMeeting',
  recordId: 'rec-456',
  data: { Notes: transcript }
});
```

이 패턴을 적용하면 약 15만 토큰에 달하던 컨텍스트 소모량이 필요한 도구 정의만 읽어 들이는 약 2,000 토큰 수준으로 급감합니다. 토큰 소모를 98% 이상 절감하는 효과를 거둘 수 있습니다.

### 코드 실행 도입의 효과와 트레이드오프

코드 실행 패턴은 토큰 절약 외에도 명확한 장점을 제공합니다.

에이전트가 필요한 도구 파일만 탐색해 읽어 들이므로 도구 정의의 점진적 공개가 가능합니다. 만 건의 데이터베이스 행을 가져와도 샌드박스 내부에서 필터링한 뒤 최종 5건만 모델에 넘길 수 있습니다. 또한 루프나 예외 처리 같은 제어 흐름이 코드 안에서 해결되므로 모델과의 불필요한 왕복 턴이 사라집니다. 민감한 개인정보가 모델 컨텍스트에 기록되지 않아 보안성도 높아집니다.

다만 코드를 안전하게 격리 실행할 샌드박스 인프라와 자원 제한, 로깅 체계를 추가로 구축해야 하는 운영상의 부담이 따릅니다. 도구가 서너 개에 불과한 환경이라면 전통적인 직접 호출 방식이 단순하며, 수십 개 이상의 대규모 연동에서 비로소 코드 실행 방식의 가치가 드러납니다.

### MCPorter 도구 합성 런타임

MCPorter 는 대규모 MCP 도구를 TypeScript 코드로 손쉽게 합성할 수 있도록 돕는 런타임이자 CLI 도구입니다.

로컬 환경이나 에디터 설정에 있는 MCP 서버를 자동으로 발견합니다. `mcporter emit-ts` 로 타입 정의를 생성하고, `createServerProxy()` 로 도구를 직관적인 메서드로 다룹니다. 불필요한 도구 스키마를 숨기고 코드로 도구를 엮어내는 작업을 실무에 즉시 적용할 수 있도록 돕습니다.



## 운영 팁과 문제 해결

> 연결 장애와 인증 실패의 원인을 체계적으로 추적하고 최소 권한 원칙을 지켜야 안전합니다.

실제 개발 환경에서 MCP 서버를 운용하다 보면 인증이 풀리거나 도구가 표시되지 않는 다양한 문제에 직면합니다. 문제를 진단하는 표준 순서와 보안 예방책을 익혀 두어야 장애 시간을 줄일 수 있습니다.

### 최소 권한과 보안 수칙

MCP 서버는 로컬 파일시스템과 원격 인프라에 직접 접근하므로 보안에 각별히 유의해야 합니다.

모든 자격 증명은 설정 파일에 직접 적지 말고 반드시 환경 변수로 관리해야 합니다. 데이터베이스 MCP 도구는 기본적으로 임의의 SQL 을 실행할 수 있는 위험이 있습니다. 실수로 인한 데이터 삭제를 방지하려면 `SELECT` 권한만 부여된 읽기 전용 데이터베이스 계정을 생성해 연결해야 합니다.

```sql
CREATE ROLE claude_readonly LOGIN PASSWORD 'change-me';
GRANT CONNECT ON DATABASE mydb TO claude_readonly;
GRANT USAGE ON SCHEMA public TO claude_readonly;
GRANT SELECT ON ALL TABLES IN SCHEMA public TO claude_readonly;
```

DBHub 도구를 사용할 때는 `dbhub.toml` 설정 파일에서 `readonly = true` 옵션을 켜 두는 조치도 병행해야 안전합니다.

### 연결 오류 상태 코드 진단

서버 연결에 실패했을 때는 임의로 설정을 고치기 전에 상태부터 확인해야 합니다. v2.1.219부터 `claude mcp list` 및 `/mcp` 명령은 실패한 서버 옆에 HTTP 상태 코드와 오류 본문을 함께 출력합니다.

- `401` 또는 `403`: 인증 정보가 잘못되었거나 만료되었습니다. `claude mcp login <name>` 명령으로 재인증을 수행합니다.
- `404`: 엔드포인트 URL 이 잘못되었습니다. URL 끝에 `/mcp` 나 `/sse` 경로가 누락되었는지 점검합니다.
- `5xx` 또는 타임아웃: 원격 서버 프로세스가 다운되었거나 네트워크 방화벽에 차단된 상태입니다.

### 환경 변수 공백과 헤드리스 누락 점검

자주 발생하면서도 찾기 힘든 오류 원인 중 하나는 환경 변수 앞뒤의 공백 문자입니다. 토큰을 복사해 붙여넣는 과정에서 개행 문자나 공백이 섞여 들어가면 인증 헤더가 유효하지 않게 처리되어 401 오류가 발생합니다. v2.1.219부터는 공백이 감지되면 경고를 띄워 주지만, 의심스러울 때는 공백 여부를 터미널에서 직접 확인하는 것이 좋습니다.

```bash
printf '[%s]\n' "$GITHUB_PERSONAL_ACCESS_TOKEN"
```

헤드리스 실행에서 검증에 실패한 서버는 에러로 중단되지 않고 건너뜁니다. v2.1.219부터는 누락된 서버를 `mcp_server_errors` 필드로 기록하므로, 실행 결과 로그를 확인해 도구 누락 여부를 검증해야 합니다.

### 라이프사이클 수정 사항과 대응

과거 버전에서 빈번하게 보고되었던 수명주기 문제들은 최근 업데이트를 통해 상당 부분 개선되었습니다.

v2.1.136에서는 대화창을 초기화하는 `/clear` 명령을 실행해도 등록된 MCP 서버가 유지되도록 수정되었습니다. 이전에는 에디터 확장이나 SDK 환경에서 `/clear` 후 서버가 사라져 전체 세션을 재시작해야 했습니다.

또한 여러 개의 OAuth 서버가 동시에 토큰 갱신을 시도할 때 경쟁 상태로 인해 리프레시 토큰이 유실되던 문제도 v2.1.136에서 해결되었습니다. 아침마다 모든 도구의 인증을 다시 수행해야 했던 불편함이 사라졌으므로 다중 OAuth 서버를 운용한다면 해당 버전 이상으로 환경을 유지하는 것이 권장됩니다.
