# Planning Mode·Extended Thinking·Auto Mode·Permission Modes·Sandboxing
---
> 코드 수정을 잠그고 계획을 세우는 방법부터 깊은 추론, 안전 분류기 기반 자율 실행, 6단계 권한 모드, 운영체제 수준 샌드박스 격리까지 에이전트 안전 장치 전반을 정리합니다.



## 핵심 요약

> 코드를 고치기 전에 계획을 검토하고, 깊은 추론으로 설계를 다듬으며, 안전 분류기와 샌드박스로 실행 위험을 통제합니다.

Claude Code 의 고급 제어 기능들은 모델이 성급하게 코드를 고치지 않도록 안전망을 제공합니다. 에이전트가 복잡한 저장소에서 작업을 단독으로 진행하면 잘못된 설계나 파괴적인 셸 명령으로 시스템이 손상될 위험이 있습니다. 이 문제를 해결하기 위해 시스템은 사전 계획 수립, 심층 사고, 안전 심사, 권한 단계 분리, 운영체제 격리라는 5단계 방어 체계를 갖추고 있습니다.

계획 모드는 모든 쓰기 작업을 잠그고 전체 작업 순서를 먼저 검토하도록 유도합니다. 확장된 생각 기능은 모델이 여러 대안과 엣지 케이스를 사전에 따지도록 만듭니다. 자동 모드는 배경 분류기를 통해 유해한 작업을 자동으로 차단하면서도 안전한 반복 작업은 승인 대기 없이 진행합니다. 권한 모드는 상황에 맞춰 질문 빈도와 허용 범위를 조절합니다. 샌드박스는 운영체제 격리를 통해 허가되지 않은 파일 변경과 네트워크 유출을 원천 차단합니다.

| 하고 싶은 일 | 쓸 기능과 설정 |
|---|---|
| 변경 전에 계획부터 검토하고 승인하기 | `/plan`, `--permission-mode plan` |
| 아키텍처와 트레이드오프 깊게 따지기 | `--effort high`, 프롬프트 `ultrathink` |
| 안전 검사를 거쳐 작업 자동 승인하기 | `--permission-mode auto` |
| 파일 수정만 자동 승인하고 명령은 확인하기 | `--permission-mode acceptEdits` |
| 파일과 네트워크 접근을 OS 수준에서 가두기 | `/sandbox`, `~/.claude/settings.json` 의 `sandbox` |
| 민감한 API 키 유출 없이 도구 실행하기 | `sandbox.credentials` 의 `mode: "mask"` |

## Planning Mode

> 계획 모드는 모든 파일 수정을 잠그고 구현 계획을 먼저 작성하여 사용자의 승인을 받도록 만듭니다.

복잡한 요구사항을 접한 에이전트는 성급하게 코드를 수정하다가 구조를 망치기 쉽습니다. 계획 모드는 코드를 고치기 전에 설계와 단계별 작업 순서를 먼저 정리하도록 강제하는 안전장치입니다.

### 구현 계획과 실행의 분리

작업을 계획 단계와 구현 단계로 엄격하게 나누는 것이 **계획 모드**(Planning Mode, 쓰기를 잠그고 계획 수립에 집중하는 동작 모드)입니다. 첫 번째 단계에서 Claude 는 프로젝트의 파일 구조와 코드를 읽고 분석하여 상세한 구현 계획을 세웁니다. 두 번째 단계에서는 사용자가 계획을 검토하고 승인한 뒤에만 실제 구현 작업을 시작합니다.

이 모드는 여러 파일을 함께 고치는 대규모 리팩터링이나 신규 기능 개발, 데이터베이스 스키마 마이그레이션처럼 구조적 영향이 큰 작업에 적합합니다. 반면 단순한 오타 수정이나 단일 파일의 사소한 변경, 빠른 정보 조회 작업에는 적합하지 않습니다. 그런 단순 작업에 계획 모드를 적용하면 계획 수립과 검토에 불필요한 시간과 토큰이 소모되기 때문입니다.

### 계획 모드의 쓰기 차단과 셸 명령 위임

계획 모드가 활성화되면 모든 파일 쓰기 작업이 전면 차단됩니다. 원문 기준 v2.1.136 버전부터 계획 모드의 파일 쓰기 차단은 무조건적으로 적용됩니다. 이전에는 `permissions.allow` 에 특정 파일 수정 규칙이 있으면 쓰기가 허용되기도 했습니다. 하지만 v2.1.136 버전에서 이 우회 통로가 완전히 차단되었습니다. 따라서 파일 수정이 필요한 단계에 도달하면 반드시 계획 모드를 종료해야 합니다.

반면 계획 수립에 필요한 정보 수집용 셸 명령은 유연하게 처리됩니다. 원문 기준 v2.1.218 버전부터 `useAutoModeDuringPlan` 설정이 켜져 있으면 대화형 질문을 줄입니다. 배경 안전 분류기가 계획 수립용 셸 명령을 직접 심사합니다. 승인된 안전한 조회 명령은 사용자 개입 없이 바로 실행되며 거절된 명령만 차단됩니다. 이때도 파일 쓰기 차단 정책은 흔들림 없이 유지됩니다.

### 계획 모드 진입과 설정

계획 모드는 다양한 경로로 실행할 수 있습니다. 대화 중에는 슬래시 명령 `/plan` 뒤에 작업 내용을 입력하여 즉시 계획 수립을 시작할 수 있습니다. 터미널에서 세션을 시작할 때는 CLI 실행 옵션으로 `--permission-mode plan` 을 넘깁니다.

```bash
# 슬래시 명령으로 계획 수립 시작
/plan 사용자 인증 시스템 구현

# CLI 실행 플래그로 계획 모드 진입
claude --permission-mode plan
```

계획 모드를 프로젝트나 사용자 환경의 기본값으로 지정할 수도 있습니다. 설정 파일의 `permissions.defaultMode` 키를 `"plan"` 으로 설정하면 모든 세션이 계획 모드로 시작됩니다.

```json
{
  "permissions": {
    "defaultMode": "plan"
  }
}
```

실행 중인 대화창에서는 단축키 `Shift + Tab` 을 눌러 권한 모드를 순환 전환할 수 있습니다. 윈도우 환경에서 터미널 가상 터미널 모드가 꺼져 있을 때는 `Alt + M` 키로 전환합니다. 또한 수립 중인 계획을 외부 텍스트 편집기에서 세밀하게 고치고 싶다면 `Ctrl + G` 키를 눌러 에디터를 띄울 수 있습니다.

v2.1.111 버전부터는 생성된 계획 파일이 무작위 단어 대신 프롬프트 내용에 맞춘 이름으로 저장됩니다. 덕분에 나중에 계획 파일을 다시 찾거나 재사용하기 수월해졌습니다. 모델 설정에서는 `opusplan` 이라는 모델 별칭을 사용할 수 있습니다. 이 별칭을 지정하면 계획 수립에는 Opus 모델을 씁니다. 승인 후 실제 코드 구현에는 Sonnet 모델을 배정하여 속도와 비용 효율을 높입니다.

```bash
claude --model opusplan "신규 API 설계 및 구현"
```

### 계획 검토와 승인에 따른 동작 전환

계획 모드에서 Claude 는 구현 단계와 파일 변경 목록, 예상 소요 시간을 정리한 계획서를 출력합니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> 계획서 끝에는 사용자에게 진행 여부를 묻는 확인 질문이 나타납니다.

사용자는 계획을 그대로 승인(`yes`)하거나 승인하지 않고 계획 단계에 머무를(`no`) 수 있습니다. 특정 단계를 건너뛰거나 순서를 바꾸고 싶다면 계획 수정을 요청할 수도 있습니다. 사용자가 수정을 요구하면 Claude 는 계획서를 갱신하여 다시 보여줍니다. 최종적으로 계획을 승인하면 세션은 실행 단계로 넘어가며 계획에 적힌 순서대로 파일 변경을 순차적으로 수행합니다.

## Extended Thinking

> 생각 깊이를 늘려 엣지 케이스와 대안을 검토하며 복잡한 아키텍처 설계와 리팩터링을 수행합니다.

단순한 질문에는 빠른 응답이 유리하지만 설계 판단이나 버그 추적에는 깊은 사고가 필요합니다. 확장된 생각 기능은 모델이 답변을 내놓기 전에 내부적으로 충분한 추론 과정을 거치도록 만듭니다.

### 단계적 추론의 필요성과 가치

답하기 전에 문제를 체계적으로 검토하게 하는 기능이 **확장된 생각**(Extended Thinking, 내부 추론 토큰을 할당하여 단계적으로 사고하는 기능)입니다. 모델은 주어진 제약 조건을 분석하고 여러 가지 구현 접근법을 나열하며 각 접근법의 장단점과 엣지 케이스를 사전에 평가합니다.

이 과정은 초기 토큰 소모와 응답 지연을 발생시키지만 잘못된 구조 결정으로 인한 재작업 비용을 줄여줍니다. 마이크로서비스 도입 여부 결정이나 대규모 동시성 제어 구조 설계처럼 한 번 결정하면 되돌리기 어려운 작업에서 높은 가치를 발휘합니다. 반면 정형화된 코드 작성이나 단순 API 조회에서는 비용 대비 이점이 적으므로 필요한 상황에만 깊이를 높이는 판단이 필요합니다.

### 생각 깊이 설정과 조절 수단

생각 깊이는 CLI 실행 옵션과 환경 변수, 세션 내부 명령으로 유연하게 조절할 수 있습니다. 터미널 명령 뒤에 `--effort` 옵션을 붙이거나 대화 세션 안에서 `/effort` 명령을 실행하여 추론 수준을 지정합니다.

```bash
# 실행 옵션으로 추론 수준 지정
claude --effort high "분산 트랜잭션 아키텍처 검토"

# 환경 변수로 기본 노력 수준 지정
export CLAUDE_CODE_EFFORT_LEVEL=high

# 고정 생각 토큰 예산 지정 (Opus 4.6·Sonnet 4.6 에서 적응형 추론을 끈 경우만)
export MAX_THINKING_TOKENS=16000
```

단축키로는 macOS 에서 `Option + T`, 윈도우와 리눅스에서 `Alt + T` 를 눌러 생각 모드를 켜거나 끌 수 있습니다. 추론 과정을 자세히 살펴보고 싶다면 `Ctrl + O` 키를 눌러 상세 모드를 활성화합니다. 또한 프롬프트 안에 `ultrathink` 라는 단어를 포함하면 모델이 스스로 깊은 추론 모드로 전환하여 답변을 구성합니다.

노력 수준은 `low`, `medium`, `high`, `xhigh`, `max` 단계로 나뉩니다. 세부적인 모델별 적용 단계와 우선순위 결정 규칙은 `./01-01.CLI reference.md` 에 정리되어 있습니다. 원문 기준 Opus 5.5, Sonnet 5.5 등 최신 모델군에서는 생각 기능을 끌 수 없습니다. 기본 노력 수준은 `medium` 입니다.

추가로 `/effort` 슬라이더에는 **울트라코드**(Ultracode, 동적 워크플로를 조율하는 오케스트레이션 기능) 토글이 포함되어 있습니다. 이는 모델 자체의 추론 토큰 수준이 아니라 에이전트의 전체 워크플로 진행 방식을 제어하는 기능입니다. 원문 기준 v2.1.284 버전부터는 울트라코드를 켜더라도 `xhigh` 추론 단계가 강제되지 않고 사용자가 설정한 노력 수준이 그대로 유지됩니다.

### 안전 분류기 플래그와 자동 폴백

Opus 5 모델에서는 서비스 장애 대응용 모델 폴백과 별개로 안전 분류기 기반의 카테고리별 자동 폴백이 동작합니다. 원문 기준 v2.1.219 버전 이상에서 지원되는 이 동작은 사용자의 요청 유형에 따라 다른 방식으로 반응합니다.

사이버보안 관련 내용으로 감지된 요청은 Opus 4.8 모델로 전환되어 조용히 다시 실행됩니다. 반면 생물학 관련 위험으로 감지된 요청은 Opus 5 자체 분류기에 의해 즉시 거절되며 대체 모델로의 전환도 지원되지 않습니다. 따라서 모의 해킹이나 보안 점검 작업을 수행할 때는 모델 전환이 조용히 일어날 수 있음을 염두에 두어야 합니다.

이러한 자동 전환을 원하지 않는다면 설정 파일에서 `switchModelsOnFlag` 설정을 `false` 로 지정할 수 있습니다. 이 값을 끄면 모델이 임의로 바뀌지 않고 작업이 일시 중지되며, 프롬프트를 고칠 것인지 모델을 전환할 것인지 묻는 선택창이 나타납니다.

```json
{
  "switchModelsOnFlag": false
}
```

## Auto Mode

> 배경 안전 분류기가 위험한 시스템 명령을 차단하고 안전한 로컬 작업을 자동으로 승인합니다.

반복적인 작업마다 확인 질문에 답하는 일은 개발 흐름을 끊고 자동화를 방해합니다. 자동 모드는 배경 분류기를 활용하여 일상적인 작업은 자동으로 통과시키고 파괴적인 작업만 선별 차단합니다.

### 배경 안전 분류기의 동작 원리

승인 피로를 줄이면서 안전을 유지하려고 만든 권한 모드가 **자동 모드**(Auto Mode, 배경 분류기로 위험 명령을 심사하는 권한 모드)입니다. 작업이 요청되면 배경에 상주하는 안전 분류기가 명령의 위험도를 즉시 평가합니다.

동작 판정은 정해진 네 단계 순서를 거쳐 이루어집니다. 가장 먼저 사용자가 설정한 명시적 허용 및 거부 규칙(`allow`, `deny`)을 대조합니다. 두 번째로 일반 파일 읽기와 프로젝트 내부 파일 수정 작업은 안전한 작업으로 분류되어 즉시 자동 승인됩니다. 세 번째로 셸 실행이나 외부 통신 같은 잠재적 위험 작업은 배경 분류기로 넘어가 위험성을 심사받습니다. 마지막으로 분류기 차단이 3회 연속 또는 누적 20회에 이르면 사용자에게 확인 질문을 띄우는 폴백 단계로 전환됩니다.

### 지원 환경과 요구 조건

자동 모드는 모든 요금제에서 사용할 수 있지만 모델과 인프라에 따른 제약이 존재합니다. 엔터프라이즈 요금제나 Claude API 직접 연동 계정에서는 원문 기준 v2.1.278 버전부터 서버 측 분류기 검사가 무료로 제공됩니다. 그러나 서버 측 검사가 닿지 않는 세션(요청을 바꾸는 LLM 게이트웨이 등)에서는 분류기 심사 과정에서 추가적인 추론 토큰 비용이 발생합니다.

모델 측면에서는 Claude Opus 4.6 이상, Sonnet 4.6 이상, Haiku 5.5 등 최신 세대 모델이 필요합니다. Sonnet 4.5 나 Haiku 4.5 같은 이전 세대 구형 모델은 자동 모드를 지원하지 않습니다. 클라우드 인프라의 경우 Bedrock, Vertex AI, Foundry 환경에서도 지원됩니다. 원문 기준 v2.1.207 버전부터 별도 변수 없이 기본 활성화되었습니다.

### 기본 허용 작업과 기본 차단 작업

자동 모드는 개발 생산성과 안전의 균형을 맞추기 위해 기본 허용 목록과 기본 차단 목록을 명확히 구분합니다.

프로젝트 내부의 소스 코드 읽기와 쓰기는 자동으로 허용됩니다. `package.json` 등에 명시된 의존성 패키지 설치(`npm install`, `pip install`)도 자동 승인 대상입니다. 기술 문서를 확인하기 위한 읽기 전용 HTTP 요청이나 현재 작업 중인 기능 브랜치로의 git push 작업도 승인 질문 없이 진행됩니다.

반면 시스템 손상이나 데이터 유실을 일으킬 수 있는 명령은 기본적으로 차단됩니다. 원격 스크립트를 셸에서 직접 실행하는 명령(`curl | bash`)이나 API 키 등 자격 증명을 외부로 보내는 행위는 금지됩니다. 운영 배포 명령과 대규모 디렉토리 삭제(`rm -rf`), 클라우드 IAM 권한 변경, 메인 브랜치 강제 푸시(`git push --force origin main`)도 모두 차단 대상에 포함됩니다.

사용자가 세션에서 직접 요구하지 않은 파괴적 명령은 분류기가 거부합니다. 원문 기준 v2.1.183 버전부터 `git reset --hard`, `git clean -fd`, `terraform destroy` 등이 이에 해당합니다.

### 규칙 확장과 엄격한 제어

자동 모드의 동작 방식은 명령어와 설정 파일을 통해 세밀하게 조정할 수 있습니다. `claude auto-mode defaults` 명령은 내장된 기본 규칙을 JSON 형식으로 보여줍니다. 설정을 원래대로 되돌리려면 `claude auto-mode reset` 명령을 실행합니다.

```bash
# 기본 자동 모드 규칙 확인
claude auto-mode defaults

# 기본 규칙으로 재설정
claude auto-mode reset --yes
```

규칙을 확장할 때는 내장 규칙을 덮어쓰지 않도록 주의해야 합니다. 원문 기준 v2.1.118 버전부터는 설정 배열 안에 `"$defaults"` 토큰을 넣을 수 있습니다. `autoMode.allow` 나 `autoMode.soft_deny` 에 이를 지정합니다. 이 토큰을 사용하면 기존에 제공되는 안전 규칙을 유지하면서 조직 고유의 허용 규칙이나 차단 규칙을 뒤에 추가할 수 있습니다.

```json
{
  "autoMode": {
    "allow": ["$defaults", "Listing pull requests with gh pr list is allowed"],
    "soft_deny": ["$defaults", "Never run kubectl delete against any cluster"]
  }
}
```

어떠한 상황에서도 절대 실행되어서는 안 되는 명령이 있다면 `autoMode.hard_deny` 설정을 사용합니다. 원문 기준 v2.1.136 버전부터 지원되는 이 설정은 분류기의 의도 추론을 거치지 않고 해당 명령을 무조건 차단합니다. 또한 모든 셸 명령을 하나도 빠짐없이 분류기 심사에 맡기고 싶다면 `autoMode.classifyAllShell` 설정을 `true` 로 지정합니다.

```json
{
  "autoMode": {
    "hard_deny": ["$defaults", "Never run rm -rf on the filesystem root", "Never force-push to protected branches"],
    "classifyAllShell": true
  }
}
```

분류기가 판단을 내리지 못하고 차단이 반복되면 세션은 안전을 위해 사용자에게 직접 묻는 방식으로 전환됩니다. 단일 세션 안에서 분류기 차단이 3회 연속 발생하거나 누적 20회에 도달하면 대화형 확인 창이 나타나며 최종 제어권을 사용자에게 넘깁니다.

### 분류기 없는 보수적 권한 스크립트 구성

배경 분류기의 추가 토큰 비용이나 응답 지연이 부담스럽다면 정적 권한 규칙을 구성하여 유사한 안전 환경을 만들 수 있습니다. 원문 보조 자료인 `setup-auto-mode-permissions.py` 스크립트는 이러한 정적 권한 구성을 자동화해 주는 도구입니다.

이 스크립트는 `~/.claude/settings.json` 파일에 읽기 전용 도구와 안전한 검사용 셸 명령만을 기초 규칙으로 등록합니다. 이후 필요에 따라 옵션 플래그로 권한을 넓힙니다. 파일 수정(`--include-edits`), 테스트(`--include-tests`), git 쓰기(`--include-git-write`) 등을 선택적으로 추가합니다. 분류기 모델 호출 없이도 명시적인 허용 목록 방식으로 안전한 작업 공간을 구축할 수 있습니다.

```bash
# 기본 안전 규칙 등록 미리보기
python3 setup-auto-mode-permissions.py --dry-run

# 편집과 테스트 권한을 포함하여 등록
python3 setup-auto-mode-permissions.py --include-edits --include-tests
```

## Permission Modes

> 수동 확인부터 완전 자동화까지 6단계 권한 모드로 에이전트의 자율 범위를 조절합니다.

작업의 성격과 실행 환경에 따라 필요한 자율성의 정도는 다릅니다. 권한 모드는 Claude 가 사용자의 명시적 허락 없이 수행할 수 있는 작업의 경계를 규정합니다.

### 6가지 권한 모드의 체계와 차이

Claude Code 는 총 6가지의 권한 모드를 지원합니다. 가장 엄격한 수동 확인부터 완전히 제한을 푸는 위험한 모드까지 상황에 맞춰 유연하게 선택할 수 있습니다.

원문 기준 v2.1.200 버전에서 기존의 `default` 모드는 **수동 모드**(manual, 파일 읽기만 자동 허용하고 수정과 명령 실행은 매번 확인하는 모드)로 이름이 변경되었습니다. 설정값(훅과 SDK 가 쓰는 값)은 여전히 `default` 이고, `manual` 은 같은 모드를 가리키는 별칭으로 함께 받습니다.

각 권한 모드는 파일 읽기, 파일 수정, 셸 명령 실행, 안전 심사 여부에서 명확한 차이를 보입니다.

| 권한 모드 | 파일 읽기 | 파일 수정 | 셸 명령 실행 | 안전 분류기 심사 | 주요 특징 및 권장 작업 |
|---|---|---|---|---|---|
| `manual` | 자동 허용 | 확인 질문 | 확인 질문 | 미사용 | 구 default 모드. 모든 주요 변경을 사람이 직접 확인하는 짝 프로그래밍 |
| `acceptEdits` | 자동 허용 | 자동 허용 | 확인 질문 | 미사용 | 린트 수정이나 코드 서식 정리처럼 파일 편집만 대량으로 발생할 때 사용 |
| `plan` | 자동 허용 | 전면 차단 | 분류기 심사 | 심사 사용 | 조사 및 설계 전용. 쓰기 작업이 완벽히 잠긴 상태로 코드 분석과 계획 수립 |
| `auto` | 자동 허용 | 자동 허용 | 분류기 심사 | 심사 사용 | 위험 명령은 차단하고 안전한 명령은 자동 승인하는 일상적 자율 개발 |
| `bypassPermissions` | 자동 허용 | 자동 허용 | 자동 허용 | 미사용 | 확인 없이 모든 동작 즉시 실행. 완전히 격리된 일회성 컨테이너 전용 |
| `dontAsk` | 허용 목록만 | 허용 목록만 | 허용 목록만 | 미사용 | 사전 등록된 도구만 실행하고 나머지는 확인 없이 즉시 거절하는 폐쇄 모드 |

### 모드 전환 방식과 기본값 정책

권한 모드는 세션 안에서 단축키 `Shift + Tab` 을 눌러 순환 전환할 수 있습니다. 전환 순서는 `manual` 에서 시작하여 `acceptEdits`, `plan` 을 거쳐 사용 가능한 경우 `bypassPermissions` 와 `auto` 로 이어집니다. 단, 사전 승인 목록만 실행하는 `dontAsk` 모드는 작업 흐름이 완전히 차단될 수 있으므로 단축키 순환 목록에서 제외되어 있습니다.

터미널에서 세션을 시작할 때는 `--permission-mode` 옵션으로 모드를 지정하거나 설정 파일의 `permissions.defaultMode` 키에 원하는 모드를 적어 둡니다.

```bash
# 수동 모드로 시작
claude --permission-mode manual

# 파일 수정 자동 승인 모드로 시작
claude --permission-mode acceptEdits
```

세션이 시작될 때 적용되는 기본 모드 정책은 버전에 따라 크게 변화했습니다. 원문 기준 v2.1.284 버전부터 대화형 터미널 세션은 권한 모드가 명시되지 않았을 때 `auto` 모드로 자동 시작됩니다. 다만 자동 모드를 지원하지 않는 환경이거나 설정 파일에 다른 기본값이 적혀 있다면 `manual` 모드로 시작합니다. 반면 배치 처리나 CI/CD 파이프라인에서 실행되는 `claude -p` 비대화형 세션은 안전을 위해 `manual` 모드로 시작하므로, 자율 실행이 필요하다면 `--permission-mode auto` 를 명시적으로 전달해야 합니다.

### 안전을 위한 예외 차단 규칙

파일 수정을 자동으로 승인하는 모드라 하더라도 시스템 핵심 파일에 대해서는 예외적인 보호 규칙이 작동합니다.

원문 기준 v2.1.160 버전부터는 `acceptEdits` 모드에서도 시스템 민감 파일 수정 시 승인 질문을 강제로 띄웁니다. 셸 초기화 파일(`.zshenv`, `.bash_login` 등)이나 코드 실행 설정 파일(`.npmrc`, `.devcontainer/` 등)이 대표적입니다. 이러한 파일이 오염되면 임의 스크립트가 백그라운드에서 실행될 위험이 있기 때문입니다.

모든 권한 확인을 건너뛰는 `bypassPermissions` 모드(`--dangerously-skip-permissions` 플래그) 역시 최소한의 안전장치를 둡니다. 원문 기준 v2.1.281 버전부터는 극단적인 파괴 명령(`rm -rf /` 등) 감지 시 2분간 사용자 입력을 대기합니다. 2분 동안 응답이 없으면 명령이 자동 거절되어 무인 세션이 폭주하는 참사를 방지합니다.

윈도우 운영체제 환경에서의 셸 지원도 개선되었습니다. Git Bash 가 설치되어 있지 않더라도 PowerShell 7 환경을 자동으로 감지하여 셸 도구로 활용합니다. 원문 기준 v2.1.143 버전부터 클라우드 공급자 환경에서 PowerShell 도구가 기본 활성화됩니다. 필요한 경우 실행 정책을 우회하여 정상 동작을 보장합니다.

## Sandboxing

> 운영체제 수준의 프로세스 격리로 허용되지 않은 파일 접근과 네트워크 연결을 차단합니다.

권한 모드가 애플리케이션 계층에서의 정책이라면 샌드박스는 운영체제 커널 계층에서의 물리적 장벽입니다. 에이전트가 실행하는 프로세스 자체를 가두어 잠재적 보안 사고를 방지합니다.

### 권한 규칙과 운영체제 샌드박스의 차이

권한 규칙만으로 막지 못하는 접근은 **샌드박스**(Sandboxing, OS 격리로 파일과 네트워크를 통제하는 기술)가 막습니다. 샌드박스는 애플리케이션 권한 규칙을 보완합니다. 권한 모드가 Claude 의 의도를 심사하는 방어선이라면, 샌드박스는 커널 수준에서 접근을 차단합니다. macOS 의 Seatbelt 나 Linux 의 Bubblewrap 기술이 이에 쓰입니다.

에이전트가 임의로 실행한 스크립트가 우회 기법을 쓰거나 예상치 못한 서브프로세스를 띄우더라도 커널 수준에서 파일 쓰기와 네트워크 호출이 가로막힙니다. 이러한 이중 방어 체계(Defense in Depth)를 통해 개발 머신의 민감한 개인 정보와 프로젝트 외부 파일이 안전하게 보호됩니다.

### 샌드박스 활성화와 설정 구조

샌드박스는 대화 세션 안에서 슬래시 명령 `/sandbox` 를 입력하여 켤 수 있습니다. 이 명령을 실행하면 프로젝트의 로컬 설정 파일인 `.claude/settings.local.json` 에 설정이 기록됩니다. 모든 프로젝트에 전역 적용하려면 `~/.claude/settings.json` 에 `"sandbox": { "enabled": true }` 를 선언합니다.

```json
{
  "sandbox": {
    "enabled": true,
    "failIfUnavailable": true,
    "filesystem": {
      "allowWrite": ["/Users/me/project"],
      "allowRead": ["/Users/me/project", "/usr/local/lib"],
      "denyRead": ["/Users/me/.ssh", "/Users/me/.aws"]
    }
  }
}
```

CLI 실행 시에는 독립적인 `--sandbox` 플래그가 존재하지 않으므로 `--settings` 옵션을 통해 JSON 문자열로 설정을 전달해야 합니다.

네트워크 격리 설정에서는 도메인 허용 및 차단 목록을 유연하게 구성할 수 있습니다. `allowedDomains` 에 와일드카드를 주더라도 특정 호스트를 막을 수 있습니다. 원문 기준 v2.1.113 버전부터 지원되는 `deniedDomains` 설정으로 위험 호스트를 차단합니다. 또한 `strictAllowlist` 설정을 켜면 비인가 호스트로의 연결 시도 시 확인 질문을 생략하고 즉시 연결을 끊어버립니다.

```json
{
  "sandbox": {
    "network": {
      "allowedDomains": ["*.example.com"],
      "deniedDomains": ["evil.example.com"],
      "strictAllowlist": true
    }
  }
}
```

리눅스와 WSL 환경에서는 `sandbox.bwrapPath` 등으로 커스텀 바이너리 경로를 직접 지정합니다. 파일 격리가 도구 호환성을 깨뜨릴 때는 네트워크 격리만 유지할 수 있습니다. 원문 기준 v2.1.216 버전의 `sandbox.filesystem.disabled` 설정을 활용합니다.

### 자격 증명 마스킹과 보안 프록시

샌드박스 내부에서 빌드나 테스트 명령을 수행하다 보면 클라우드 자격 증명이나 비공개 패키지 토큰이 필요한 경우가 많습니다. 이전에는 자격 증명 파일 읽기를 거부하면 관련 빌드 명령이 실패할 수밖에 없었습니다.

원문 기준 v2.1.221 및 v2.1.224 버전에 추가된 **자격 증명 마스킹**(Credential Masking, 가짜 값을 제공하고 전송 시 치환하는 기술)이 이 딜레마를 해결합니다. 샌드박스 내부의 프로세스는 `mode: "mask"` 로 지정된 자격 증명 파일의 가짜 사본(sentinel)을 읽습니다. 그리고 프로세스가 외부 네트워크로 요청을 내보낼 때 샌드박스 보안 프록시가 가짜 값을 가로채 실제 비밀값으로 실시간 치환합니다.

```json
{
  "sandbox": {
    "network": {
      "tlsTerminate": {}
    },
    "credentials": {
      "files": [
        {
          "path": "~/.aws/credentials",
          "mode": "mask"
        }
      ]
    }
  }
}
```

이 메커니즘은 구조화된 환경 변수 내부의 특정 필드만 골라 마스킹하거나, JWT 토큰을 디코딩하여 특정 클레임만 숨기는 고급 기능을 제공합니다. 심지어 AWS SigV4 서명처럼 인증 키가 변경되면 요청 서명이 깨지는 프로토콜을 위해 프록시가 실제 키로 서명을 재계산해 주는 기능도 포함되어 있습니다.

이 기능을 안전하게 사용하기 위해서는 두 가지 제약을 기억해야 합니다. 첫째로 프록시가 네트워크 패킷 내부를 들여다보고 값을 치환해야 하므로 `sandbox.network.tlsTerminate` 설정이 반드시 켜져 있어야 합니다. 둘째로 파일 마스킹 기능은 리눅스와 WSL 환경에서만 완벽히 동작하며 macOS 환경에서는 거부 방식으로 대체됩니다. 또한 악의적인 저장소가 설정을 변조하여 인증 정보를 탈취하지 못하도록 사용자 설정 범위에서만 이 기능이 활성화됩니다.

## 신뢰와 권한 범위

> 외부 저장소의 설정이 로컬 머신의 권한을 임의로 확장하지 못하도록 사용자 범위로 제한합니다.

오픈소스 프로젝트나 검증되지 않은 외부 저장소를 클론하여 에이전트를 실행할 때는 심각한 보안 위험이 따릅니다. 저장소 안에 심어진 설정 파일이 사용자의 시스템 권한을 임의로 넓히거나 보안 제약을 해제할 수 있기 때문입니다.

### 저장소 신뢰와 격리 원칙

Claude Code 는 외부 저장소의 설정이 호스트 머신의 보안 정책을 침해하지 못하도록 엄격한 신뢰 격리 원칙을 적용합니다. 처음 방문하는 디렉토리에서 세션을 시작할 때 나타나는 폴더 신뢰 확인창과 외부 CLAUDE.md 임포트 승인 대화창은 이러한 방어의 출발점입니다. 신뢰 승인 상태를 저장하는 구체적인 설정 키와 동작 구조는 `./01-01.CLI reference.md` 에 정리되어 있습니다.

클론된 저장소 안의 `.claude/settings.json` 은 안전한 환경 설정만 바꿀 수 있습니다. 보안에 직접적인 영향을 미치는 핵심 설정들은 프로젝트 단위 설정 파일에서 완전히 무시됩니다.

### 중첩 저장소 신뢰 분리

원문 기준 v2.1.232 버전부터는 중첩된 저장소에 대한 신뢰 상속이 차단되었습니다. 상위 모노레포 디렉토리를 사용자가 이미 신뢰했다고 하더라도, 그 내부에 포함된 git 서브모듈이나 서브 저장소는 부모 디렉토리의 신뢰를 물려받지 않습니다.

예를 들어 승인된 프로젝트 안에서 벤더 코드가 담긴 서브모듈을 작업할 때가 있습니다. Claude Code 는 서브모듈 디렉토리에 진입하는 순간 독립적인 신뢰 질문을 다시 띄웁니다. 이를 통해 제3자가 악의적인 코드를 서브모듈 형태로 심어두고 상위 저장소의 신뢰 권한을 악용하는 공급망 공격을 차단합니다.

### 사용자 스코프 전용 설정 패턴

최근 릴리스는 권한 확장 가능성이 있는 설정을 **사용자 스코프 전용**(User-scope only, 사용자 홈이나 관리자 설정에서만 제어 가능한 속성)으로 묶어둡니다.

`sandbox.ripgrep` 설정은 원문 기준 v2.1.232 버전부터 사용자 설정과 관리자 설정, CLI 옵션으로만 지정할 수 있습니다. 저장소 내부 설정 파일로 임의의 악성 바이너리를 지정하여 실행시키는 행위를 방지하기 위함입니다. 원격 제어 자동 시작 기능 역시 원문 기준 v2.1.222 버전부터 저장소 로컬 설정으로는 켤 수 없으며 사용자가 직접 `/config` 에서 켜야 합니다.

앞서 살펴본 자격 증명 마스킹 설정과 파일 격리 해제 설정(`sandbox.filesystem.disabled`) 또한 오직 사용자 스코프에서만 활성화됩니다. 저장소에 체크인된 파일이 로컬 머신의 보안 방벽을 허무는 일은 구조적으로 불가능합니다.
