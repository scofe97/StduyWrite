# Background Tasks·Monitor·Scheduled Tasks·Headless Mode
---
> 오래 걸리는 셸 작업과 로그 감시를 백그라운드로 넘겨 대화 흐름을 유지하고, 예약 실행과 비대화형 모드로 자동화 파이프라인을 구축하는 방법을 다룹니다.



## 핵심 요약

> 긴 작업을 대기 없이 백그라운드로 넘기고, 이벤트 기반 감시와 비대화형 실행으로 개발 자동화를 완성합니다.

인공지능 도구와 협업할 때 전체 테스트 실행이나 빌드처럼 긴 시간이 걸리는 작업을 만나면 대화가 멈추기 쉽습니다. Claude Code는 이러한 대기 시간을 없애기 위해 명령을 뒤로 보내는 비동기 처리 체계를 갖추고 있습니다. 사용자는 작업을 기다리는 동안에도 다른 모듈의 리팩터링이나 기능 구현을 계속해서 이어갈 수 있습니다.

단순 실행을 넘어 로그 변화를 감지하는 도구와 대규모 작업을 병렬로 쪼개는 워크플로 엔진도 지원합니다. 정기적인 상태 확인이 필요할 때는 주기적 루프나 클라우드 예약 기능을 걸어 둘 수 있습니다. 파이프라인이나 스크립트에 연동할 때는 비대화형 헤드리스 모드를 적용하여 사람의 개입 없이 결과물을 생성합니다.

| 하고 싶은 일 | 쓸 것 |
|------|------|
| 실행 중인 긴 셸 명령을 백그라운드로 전환 | 단축키 `Ctrl+B` |
| 백그라운드 작업과 에이전트 목록 확인 | 명령어 `/tasks` (별칭 `/bashes`) |
| 백그라운드 작업 기능 전체 끄기 | 환경 변수 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` |
| 파일이나 로그의 이벤트 즉시 감시 | Monitor 도구 (`grep --line-buffered` 파이프) |
| 대규모 다중 서브에이전트 조율 실행 | 동적 워크플로 및 `/effort ultracode` |
| 워크플로 실행 진행 상황 확인 | 명령어 `/workflows` |
| 일정 주기마다 프롬프트 반복 실행 | 명령어 `/loop <간격> <프롬프트>` |
| 특정 시점에 단발성 알림 실행 | 프롬프트에 `remind me at <시각>` 입력 |
| 세션 종료 후에도 도는 클라우드 예약 작업 | 명령어 `/schedule <주기> <프롬프트>` |
| 지속적 통합 환경에서 비대화형 실행 | `claude -p "<프롬프트>"` |
| 구조화된 JSON 결과물 생성 강제 | `claude -p --output-format json --json-schema '<스키마>'` |
| 사용자 설정을 모두 끈 문제 해결 모드 | `claude --safe-mode` |

## Background Tasks

> 오래 걸리는 셸 명령을 백그라운드로 전환하여 대화 흐름을 끊지 않고 다음 작업을 진행합니다.

<!-- 도식 후보: sequence · 백그라운드 작업 실행부터 대화 병행 및 완료 통지 수신 흐름 · 원문 09-advanced-features/README.md:54-73 -->

수백 개의 단위 테스트를 실행하거나 컨테이너 이미지를 빌드하는 작업은 수 분 이상 걸립니다. 이러한 명령을 대화창에서 동기식으로 실행하면 처리가 끝날 때까지 새로운 프롬프트를 입력할 수 없습니다. 작업을 기다리느라 개발 흐름이 끊기고 전체 생산성이 떨어집니다.

Claude Code는 이러한 지연을 해소하기 위해 **백그라운드 작업**(background tasks, 대화를 차단하지 않고 백그라운드에서 비동기로 실행되는 작업)을 제공합니다. 오래 걸리는 명령을 별도의 비동기 프로세스로 떼어 내어 실행하므로 사용자는 대기 시간 없이 즉시 다른 작업으로 넘어갈 수 있습니다.

### 백그라운드 작업 대상과 실행 방식

백그라운드로 돌리기 적합한 작업은 완료까지 긴 시간이 필요하면서도 대화창에 즉각적인 상호작용을 요구하지 않는 작업들입니다. 원문에서는 다음과 같은 작업을 대표적인 대상으로 꼽습니다.

- 대규모 테스트 스위트 실행
- 프로젝트 전체 빌드 프로세스
- 데이터베이스 마이그레이션 적용
- 배포 스크립트 실행
- 정적 분석 및 린트 도구 실행

백그라운드 작업은 자연어 요청으로 시작할 수 있습니다. 사용자가 테스트를 백그라운드로 실행해 달라고 요청하면 모델은 별도의 작업 식별자를 부여하고 프로세스를 백그라운드로 보냅니다. 작업이 백그라운드에서 도는 동안 대화창에는 즉시 다음 입력을 받는 프롬프트가 열립니다.

### 대화 병행과 완료 통지

백그라운드 작업이 돌고 있는 동안 사용자는 모델에게 완전히 다른 작업을 지시할 수 있습니다. 예를 들어 전체 테스트가 백그라운드에서 돌아가는 동안 인증 모듈의 코드를 리팩터링하거나 새로운 API 규격을 작성하도록 요청할 수 있습니다.

작업이 백그라운드에서 끝나면 모델이 알림 메시지를 화면에 띄웁니다. 실행 결과 요약과 성공 여부 및 실패한 항목의 개수가 대화창에 보고됩니다. 작업 식별자를 바탕으로 출력 상세 내용을 확인하거나 추가 조치를 이어갈 수 있습니다.

### 작업 관리와 단축키 제어

실행 중인 명령을 백그라운드로 보내고 상태를 확인하는 제어 수단도 제공됩니다. 터미널에서 포그라운드로 실행 중인 Bash 명령이나 에이전트 작업은 키보드 단축키 `Ctrl+B`를 눌러 즉시 백그라운드로 전환할 수 있습니다.

현재 돌고 있는 작업 목록을 확인하거나 중단할 때는 `/tasks` 명령어를 입력합니다. 이 명령어는 별칭으로 `/bashes`를 지원합니다. 화면에 실행 중인 셸 명령과 서브에이전트 목록이 표시되며, 완료된 서브에이전트 내역도 함께 나타납니다. 특정 항목을 선택하여 표준 출력을 확인하거나 실행을 중지할 수 있습니다. 세부 하위 명령어는 따로 없으며 이 뷰에서 모든 조작을 수행합니다.

### 환경 변수와 세션별 제한시간

백그라운드 작업은 별도의 설정 파일 블록 대신 환경 변수로 동작을 제어합니다. 전체 백그라운드 기능을 완전히 비활성화하고 싶다면 환경 변수를 설정합니다.

```bash
export CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1
```

동시에 실행할 수 있는 에이전트의 개수는 백그라운드 작업 설정이 아니라 서브에이전트 환경 변수로 관리합니다. 동시 실행 개수를 지정하는 변수는 `CLAUDE_CODE_MAX_CONCURRENT_SUBAGENTS`이며 기본값은 20개입니다.

백그라운드로 실행되는 Bash 및 PowerShell 명령에는 세션 유형에 따라 실행 시간 제약이 적용됩니다. 원문 v2.1.288 기준에 따르면 비대화형 환경에서 시작된 백그라운드 명령은 제한시간에 도달하면 자동으로 중단됩니다. 적용 대상은 비대화형 `-p` 실행, Agent SDK 세션, 지속적 통합(CI) 환경, 클라우드 세션입니다.

기본 제한시간은 30분이며 최대 2시간까지 연장할 수 있습니다. 작업이 중단되면 모델에게 알림이 전달됩니다. 일반 대화형 터미널이나 데스크톱 앱 및 VS Code 확장 프로그램 세션에서는 이러한 시간 제약이 적용되지 않습니다. 이전 버전인 v2.1.285부터 v2.1.287까지는 모든 세션에 시간 제약이 일괄 적용되었으나 이후 버전에서 인터랙티브 세션의 제약이 완화되었습니다.



## Monitor Tool

> 이벤트 스트림을 실시간 감시하여 불필요한 토큰 낭비 없이 상태 변화에 즉각 대응합니다.

<!-- 도식 후보: flowchart · Monitor 도구의 이벤트 스트림 감시와 세션 기상 흐름 · 원문 09-advanced-features/README.md:126-162 -->

서버 프로세스를 띄우거나 긴 배치 작업을 수행할 때는 특정 로그 메시지가 출력되는 순간을 기다려야 할 때가 많습니다. 기존 방식대로 주기적인 루프를 돌며 상태를 확인하면 변경 사항이 없는데도 매번 API를 호출하게 됩니다. 이러한 방식은 토큰을 크게 소모하고 발견 시점도 지연됩니다.

Claude Code는 원문 v2.1.98 버전부터 **모니터 도구**(monitor tool, 명령의 표준 출력을 주시하다가 특정 이벤트가 발생할 때 세션을 깨우는 기능)를 지원합니다. 모니터 도구는 백그라운드 명령의 표준 출력을 구독하고 있다가 일치하는 이벤트가 발생하는 즉시 세션을 깨웁니다.

### 폴링 방식과의 차이점

주기적으로 상태를 확인하는 폴링 방식은 대기 상태에서도 매 주기마다 API 왕복 호출을 발생시킵니다. 루프를 짧게 잡으면 토큰 비용이 급증하고, 길게 잡으면 이벤트 발생 후 인지할 때까지 지연이 발생합니다.

모니터 도구는 이벤트가 발생하기 전까지 아무런 API 호출을 일으키지 않습니다. 조용한 상태에서는 토큰 소모량이 0입니다. 그러다가 표준 출력에 일치하는 로그 라인이 나타나는 순간 지체 없이 세션을 깨워 후속 작업을 진행합니다. 몇 분 이상 지속되는 관찰 작업에서는 폴링에 비해 비용과 반응 속도 모두에서 유리합니다.

### 두 가지 감시 패턴

원문에서는 모니터 도구를 활용하는 일반적인 패턴으로 두 가지 접근 방식을 제시합니다.

첫 번째는 연속적인 로그 출력을 실시간으로 걸러내는 스트림 필터 패턴입니다. 계속해서 표준 출력을 내보내는 장기 실행 명령에 필터를 붙여 감시합니다.

```bash
tail -f /var/log/app.log | grep --line-buffered "ERROR"
```

두 번째는 자체적인 이벤트 스트림이 없는 대상을 위한 폴링 후 방출 필터 패턴입니다. 외부 API나 데이터베이스처럼 스트림 출력을 지원하지 않는 대상을 셸 스크립트 루프로 검사하되, 변경 사항이 감지되었을 때만 표준 출력을 한 줄 출력합니다.

```bash
last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
while true; do
  gh api "repos/owner/repo/issues/123/comments?since=$last" || true
  last=$(date -u +%Y-%m-%dT%H:%M:%SZ)
  sleep 30
done
```

스크립트 내부에서는 주기를 두고 확인하지만 외부로 출력을 내보내지 않으므로 모델 세션은 깨어나지 않습니다. 새로운 댓글이 등록되어 표준 출력이 발생하는 순간에만 모니터가 이를 감지하여 모델을 깨웁니다.

### 버퍼링 함정과 데드라인 제약

모니터 도구를 설정할 때 반드시 주의해야 하는 기술적 함정이 있습니다. 파이프로 출력을 넘길 때 `grep` 명령어를 사용할 경우 반드시 `--line-buffered` 옵션을 붙여야 합니다.

일반적인 `grep`은 표준 출력이 터미널이 아닐 때 출력을 4KB 단위로 버퍼링합니다. 로그 양이 적은 환경에서는 4KB 버퍼가 찰 때까지 수 분 이상 출력이 전달되지 않습니다. 이벤트가 이미 발생했는데도 모델이 깨어나지 않는 현상은 대부분 이 옵션이 누락되어 발생합니다.

```bash
# 올바른 사용 예시
tail -F server.log | grep --line-buffered -E "ERROR|FATAL"
```

또한 원문 v2.1.271 버전부터 모든 모니터 감시 작업에 데드라인 제약이 도입되었습니다. 무한정 대기하는 모니터는 더 이상 허용되지 않습니다. 일반 대화 세션에서는 최대 30분, 단일 프롬프트 비대화형 `-p` 실행에서는 최대 10분의 제한시간이 적용됩니다. 데드라인이 만료되면 모델에게 알림이 전달되며 모델은 필요에 따라 감시를 다시 걸 수 있습니다.



## Dynamic Workflows

> 수십에서 수백 개의 서브에이전트를 결정론적 스크립트로 엮어 단일 컨텍스트의 한계를 넘는 대규모 작업을 수행합니다.

<!-- 도식 후보: tree · Dynamic Workflows의 스크립트 기반 다중 서브에이전트 분기 및 결과 취합 구조 · 원문 09-advanced-features/README.md:165-187 -->

복잡한 프로젝트 전반을 감사하거나 대규모 리팩터링을 진행할 때는 단일 모델의 컨텍스트 창 크기가 한계에 부딪힙니다. 여러 서브에이전트를 띄우더라도 모델의 자율적인 판단에만 조율을 맡기면 작업 순서가 어긋나거나 누락이 발생하기 쉽습니다.

Claude Code는 원문 v2.1.154 버전부터 **동적 워크플로**(dynamic workflows, 결정론적 스크립트에 따라 수십에서 수백 개의 서브에이전트를 조율하는 기능)를 제공합니다. 스크립트에 분기 조건과 병렬 파이프라인 단계를 명시하여 수많은 에이전트를 일관성 있게 지휘합니다.

### 서브에이전트와의 구조적 차이

일반적인 서브에이전트는 메인 세션이 필요할 때마다 임베딩하여 호출하는 독립적인 작업 단위입니다. 개별 에이전트는 하나의 컨텍스트 창 안에서 동작하며 다음 행동의 결정은 모델의 추론에 의존합니다.

반면 동적 워크플로는 여러 단계를 거치는 오케스트레이션 과정을 스크립트 형태로 명시합니다. 작업을 여러 에이전트에게 확산시키고 각 결과를 다시 취합하는 파이프라인이 결정론적으로 정의됩니다. 개별 에이전트의 컨텍스트 한계를 넘어서는 거대한 작업을 체계적으로 나누어 실행할 수 있습니다.

### 도입 기준과 규모 가이드라인

동적 워크플로는 모든 작업에 무조건 적용하는 만능 도구가 아닙니다. 이미 구조를 잘 알고 있는 단순한 수정 작업은 단일 에이전트로 처리하는 편이 빠르고 경제적입니다. 원문에서는 다음과 같은 상황에서 워크플로 도입을 권장합니다.

- 종합적인 코드 검토: 여러 디렉터리와 다양한 검증 관점을 병렬로 전수 조사할 때
- 신뢰도 확보: 서로 다른 관점의 독립적인 분석 결과를 모으고 상호 검증할 때
- 컨텍스트 초과 작업: 대규모 라이브러리 전환이나 방대한 코드베이스 탐색처럼 단일 창에 담을 수 없을 때

원문 v2.1.219 버전부터 동적 워크플로는 기본 크기 가이드라인을 제공합니다. 기본값은 중간 크기이며, 도입 당시 15개 미만이던 목표 에이전트 수가 v2.1.271 에서 10개 미만으로 낮아졌습니다. 원문 v2.1.271 버전부터 프로 요금제로 로그인한 환경에서는 기본값이 소형 크기로 지정됩니다. 워크플로 크기는 `/config` 메뉴의 Dynamic workflow size 항목에서 변경하거나 설정 파일의 `workflowSizeGuideline` 키로 조정할 수 있습니다.

### 실행과 울트라코드 토글

동적 워크플로는 사용자가 Claude에게 특정 작업을 워크플로 형태로 진행해 달라고 요청하여 시작할 수 있습니다. 예를 들어 특정 소스 폴더 전체를 검토하는 워크플로를 지시하면 모델이 직접 조율 스크립트를 작성하여 백그라운드에서 구동합니다. 진행 중인 워크플로와 완료된 작업 상태는 `/workflows` 명령어로 실시간 확인할 수 있습니다.

동적 워크플로를 기본 방식으로 사용하도록 켜는 장치로 **울트라코드**(ultracode, 동적 워크플로를 기본 작업 방식으로 활성화하는 토글)가 제공됩니다. 슬래시 명령어 `/effort` 입력 후 탭 키를 눌러 슬라이더에서 토글하거나 `/effort ultracode on` 명령어로 켤 수 있습니다.

원문 v2.1.284 버전부터 이 토글을 켜더라도 세션의 기존 노력 수준이 유지됩니다. 이전 버전에서는 토글 시 노력 수준이 `xhigh`로 강제 변경되었으나 현재는 기존 단계를 그대로 유지합니다. CLI 실행 옵션 `--effort ultracode`나 Agent SDK의 `effortLevel: "ultracode"` 설정을 사용할 때는 여전히 `xhigh` 수준이 지정됩니다.

원문 v2.1.160 버전부터 워크플로를 기동하는 핵심 키워드는 `ultracode`로 고정되었습니다. 단순히 `workflow`라는 단어만으로는 구동되지 않습니다. 모든 세션에 걸쳐 기본으로 적용하려면 설정 파일에 `ultracode: true` 키를 지정합니다.



## Scheduled Tasks

> 세션 내 반복 실행이나 단발성 알림을 등록하고, 클라우드 인프라를 통해 지속적인 정기 작업을 위임합니다.

<!-- 도식 후보: state · 로컬 세션 스케줄과 클라우드 스케줄 작업의 생명주기 및 만료 상태 전이 · 원문 09-advanced-features/README.md:191-250 -->

개발 작업을 진행하다 보면 30분 뒤에 배포 상태를 확인해야 하거나, 특정 시간 간격으로 테스트를 다시 돌려야 하는 경우가 생깁니다. 매번 시계를 보며 수동으로 명령을 입력하면 번거롭고 시점을 놓치기 쉽습니다.

Claude Code는 v2.1.71 버전부터 **예약 작업**(scheduled tasks, 정해진 시간 간격이나 특정 시점에 프롬프트를 자동으로 실행하는 기능)을 지원합니다. 이 기능은 공식 블로그에서 루틴이라는 명칭으로 소개되기도 했으나 CLI 인터페이스에서는 `/schedule` 명령어를 그대로 사용합니다.

### 반복 루프와 단발성 알림

대화창에서 주기적인 반복 작업을 걸 때는 `/loop` 명령어를 사용합니다. 시간 간격을 명시하거나 자연어로 실행 주기를 지정할 수 있습니다.

```bash
# 명시적 간격 지정
/loop 5m check if the deployment finished

# 자연어 표현 지정
/loop check build status every 30 minutes
```

정밀한 주기 제어가 필요하다면 표준 5개 필드로 구성된 크론 표현식도 사용할 수 있습니다.

미래의 특정 시점에 한 번만 실행되는 단발성 알림도 등록할 수 있습니다. 대화창에 자연어로 시점을 지정하여 작업을 예약합니다.

```markdown
remind me at 3pm to push the release branch
in 45 minutes, run the integration tests
```

### 도구 인터페이스와 세션 생명주기

예약 작업은 내부적으로 전용 도구를 통해 관리됩니다. 도구 목록과 역할은 아래와 같습니다.

- `CronCreate`: 새로운 예약 작업을 생성합니다.
- `CronList`: 등록된 예약 작업 목록을 조회합니다. 원문 v2.1.136 버전부터 예약된 프롬프트 본문과 수식어가 함께 표시되어 등록 내용을 바로 점검할 수 있습니다.
- `CronDelete`: 등록된 예약 작업을 삭제합니다.

로컬에서 생성된 예약 작업은 현재 대화 세션에 종속됩니다. 세션이 종료되면 예약 작업도 멈추며, `--resume` 이나 `--continue` 로 세션을 다시 열 때 만료되지 않은 작업만 복원됩니다. 세부적인 동작 제한과 특성은 다음과 같습니다.

- 세션당 최대 50개까지 예약 작업을 등록할 수 있습니다.
- 반복 작업은 등록 후 7일이 지나면 자동으로 만료됩니다.
- Claude Code가 실행 중일 때만 동작하며, 프로그램이 닫혀 있던 시간 동안 놓친 실행은 소급 실행되지 않습니다.
- 반복 작업에는 다음 실행까지 간격의 최대 절반(최대 30분)만큼 늦게 시작하는 실행 분산 지터가 적용됩니다. 5분 주기 작업만 예외입니다.
- 정각이나 30분에 잡힌 단발성 알림은 최대 90초 일찍 실행됩니다.
- 전체 예약 기능을 끄려면 환경 변수 `export CLAUDE_CODE_DISABLE_CRON=1`을 선언합니다.

### 클라우드 예약 작업과 계정 조건

로컬 세션이 닫힌 뒤에도 정기 작업을 유지하려면 클라우드 인프라에서 실행되는 클라우드 예약 작업을 등록해야 합니다. `/schedule` 명령어를 사용하면 개발 서버가 꺼져 있어도 클라우드 환경에서 지정된 시간에 프롬프트가 실행됩니다.

```bash
/schedule daily at 9am run the test suite and report failures
```

다만 원문 v2.1.139 기준에 따르면 클라우드 `/schedule` 기능은 환경 변수에 API 키가 설정되어 있을 경우 자동으로 비활성화됩니다. `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `apiKeyHelper` 중 하나라도 설정되어 있다면 유료 계정으로 로그인되어 있더라도 클라우드 스케줄 기능을 사용할 수 없습니다. 클라우드 예약 작업을 쓰려면 API 키 환경 변수를 해제하고 Pro·Max·Team·Enterprise 요금제의 claude.ai 로그인 상태로 전환해야 합니다. 로컬에서 도는 `CronCreate` 도구는 이 제약과 무관하게 동작합니다.



## Headless Mode

> 프롬프트 입력창 없이 단발 명령으로 Claude Code를 실행하여 지속적 통합 파이프라인과 셸 스크립트에 통합합니다.

소프트웨어 개발 파이프라인에서는 사람이 터미널에 앉아 프롬프트를 입력할 수 없는 환경이 자주 발생합니다. Git 커밋이 들어왔을 때 자동으로 코드 리뷰를 수행하거나, 빌드 실패 로그를 분석하여 이슈를 등록하는 작업이 대표적입니다.

Claude Code는 비대화형 자동화를 위해 **헤드리스 모드**(headless mode, 대화형 프롬프트 없이 단발성 명령으로 실행하는 비대화형 모드)를 제공합니다. 이전 플래그였던 `--headless`는 인쇄 모드 플래그인 `-p`로 대체되었습니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> 기본적인 CLI 옵션 목록은 [01-01 편](./01-01.CLI%20reference.md)을 참고하시기 바랍니다.

### 비대화형 실행과 파이프 연동

`-p` 플래그를 붙여 실행하면 대화창을 열지 않고 넘겨받은 프롬프트만 수행한 뒤 결과를 표준 출력으로 반환합니다. 셸 파이프를 통해 다른 프로그램의 출력을 직접 넘겨받을 수도 있습니다.

```bash
# 특정 프롬프트 단발 실행
claude -p "Run all tests"

# 로그 파일 내용을 파이프로 전달하여 분석
cat error.log | claude -p "Analyze these errors"
```

파이프라인 연동 시에는 후속 스크립트가 결과를 쉽게 해석할 수 있도록 구조화된 출력 형식을 지정하는 것이 유리합니다.

### 자동화 파이프라인 필수 제어 옵션

사람이 대화창 앞에 없는 환경에서는 실행 비용과 반복 횟수를 제어하는 안전장치가 필수적입니다. Claude Code는 자동화 환경을 위한 전용 플래그를 지원합니다.

- 턴 수 제한: `--max-turns <수치>` 플래그로 모델의 자율 도구 호출 횟수를 제한합니다. 무한 루프에 빠져 API 비용이 과도하게 청구되는 사고를 예방합니다.
- 구조화 출력: `--output-format json` 플래그로 출력 형식을 JSON으로 지정합니다.
- 스키마 검증: `--json-schema '<JSON 규격>'` 플래그를 함께 주면 모델이 반환하는 JSON의 필드 규격을 강제할 수 있습니다.
- 세션 기록 미저장: `--no-session-persistence` 플래그를 주면 일회성 자동화 실행 내역이 로컬 세션 목록에 쌓이지 않습니다.

비대화형 실행에서는 권한 승인 질문에 답할 사람이 없습니다. 따라서 수정 작업을 수행해야 한다면 사전 설정 파일이나 플래그를 통해 권한 모드를 미리 지정해 두어야 합니다.

권한 정책과 샌드박스 설정의 세부 사항은 [05-02 편](./05-02.Planning%20Mode%C2%B7Extended%20Thinking%C2%B7Auto%20Mode%C2%B7Permission%20Modes%C2%B7Sandboxing.md) 문서를 참고하시기 바랍니다.

### 깃허브 액션 연동 구성

지속적 통합 환경인 깃허브 액션에서 풀 리퀘스트를 검토하는 워크플로 예시는 아래와 같습니다.

```yaml
# .github/workflows/code-review.yml
name: AI Code Review

on: [pull_request]

jobs:
  review:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install Claude Code
        run: npm install -g @anthropic-ai/claude-code

      - name: Run Claude Code Review
        env:
          ANTHROPIC_API_KEY: ${{ secrets.ANTHROPIC_API_KEY }}
        run: |
          claude -p --output-format json \
            --max-turns 3 \
            "Review this PR for code quality, security, and test coverage. Output JSON" > review.json
```

생성된 JSON 분석 결과는 이후 단계의 액션 스크립트로 전달되어 풀 리퀘스트에 댓글로 자동 게시될 수 있습니다.

### 안전 모드를 통한 환경 격리

자동화 스크립트가 알 수 없는 이유로 실패할 때는 프로젝트에 등록된 플러그인이나 훅 스크립트가 문제를 일으켰을 가능성을 의심해 보아야 합니다. Claude Code는 모든 사용자 정의 구성을 배제하고 순수 기본 상태로 구동하는 **안전 모드**(safe mode, 사용자 정의 설정을 모두 끄고 순수 기본 상태로 실행하는 문제 해결 모드)를 제공합니다.

`--safe-mode` 플래그를 붙이거나 환경 변수 `CLAUDE_CODE_SAFE_MODE=1`을 선언하고 실행하면 프로젝트의 CLAUDE.md 파일, 플러그인, 스킬, 훅, MCP 서버 설정이 모두 비활성화됩니다. 자동화 장애가 발생했을 때 문제가 사용자 환경 설정에 있는지 도구 자체에 있는지 원인을 분리하는 데 유용합니다.
