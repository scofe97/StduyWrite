# Plugins
---
> 슬래시 명령, 스킬, 서브에이전트, MCP 서버, 훅을 하나의 단위로 묶어 배포하고 관리하는 플러그인 시스템을 다룹니다. 개별 도구를 수동으로 관리하던 방식과의 차이점부터 매니페스트 구조, 마켓플레이스 유통, 보안 정책까지 정리합니다.



## 핵심 요약

> 개별 폴더에 흩어져 관리되던 여러 확장 기능을 단일 명령으로 설치하고 공유할 수 있게 묶어 주는 단위가 플러그인입니다. 명령 충돌 방지 네임스페이스와 버전 관리, 조직 차원의 보안 격리를 제공합니다.

새 프로젝트마다 필요한 명령과 도구를 수동으로 설정하면 팀원 간 환경 차이가 벌어집니다. **플러그인**(plugin, 독립된 기능 모음을 한 번에 배포하는 단위)은 확장 요소를 단일 패키지로 묶어 이 문제를 해결합니다. 전용 매니페스트로 버전과 종속성을 관리하며 마켓플레이스를 거쳐 설치합니다.

사용자는 이름만으로 원하는 도구를 내려받고, 관리자는 허용 목록으로 외부 스크립트 실행을 통제합니다. 개발 중에는 로컬 경로를 지정해 변경 사항을 즉시 시험할 수 있습니다.

| 하고 싶은 일 | 쓸 것 |
|------|------|
| 복수 확장 기능을 한 번에 설치 | `claude plugin install <이름>@<마켓플레이스>` |
| 마켓플레이스 없이 로컬에서 바로 시험 | `claude --plugin-dir <경로>` |
| 설치된 플러그인 구성 요소와 토큰 비용 확인 | `claude plugin details <이름>` |
| 변경 사항 세션에 즉시 반영 | `/reload-plugins` |
| 고유 식별자 기반 영속 데이터 저장 | `${CLAUDE_PLUGIN_DATA}` |
| 버전 태그 생성 및 배포 준비 | `claude plugin tag <경로>` |
| 고립된 자동 설치 의존성 정리 | `claude plugin prune` |
| 관리자 차원의 안전한 마켓플레이스 제한 | `strictKnownMarketplaces` |



## 이 문서의 기준

> 원문 커밋 188f468과 Claude Code 2.1.302 기준 기술 문서를 바탕으로 정리했습니다. 이후 공식 문서와 설치본 2.1.310 으로 사실을 대조해 고쳤습니다.

새 버전을 사용할 때 옵션이 동작하지 않거나 세부 동작이 어긋나면 기준 버전을 먼저 확인해야 합니다. 본문은 원문 커밋 188f468과 Claude Code 2.1.302 버전까지의 공개 문서를 바탕으로 작성했습니다. 2026-10-26 에 별도 검증 창이 공식 문서(code.claude.com/docs)와 설치본 2.1.310 으로 사실을 대조해 틀린 곳을 고쳤고, 찾지 못한 사실에는 `확인 필요` 주석을 남겼습니다.



## 플러그인이 푸는 문제

> 개별 파일 복사에 의존하던 개발 환경 설정을 표준화된 패키지로 묶어 배포와 버전 관리를 단순화합니다. 명령어 충돌을 방지하는 네임스페이스와 자동 설정 주입을 제공합니다.

여러 프로젝트를 오가며 작업하다 보면 이전에 유용하게 썼던 도구 설정을 다른 저장소로 다시 복사해야 하는 번거로움이 생깁니다. 파일 단위로 복사하는 방식은 설정 파일 위치나 환경 변수가 어긋나기 쉽습니다.

특히 **스킬**(skill, 작업 지침과 도구 모음)과 **서브에이전트**(subagent, 보조 에이전트)를 따로 두면 설정이 흩어집니다.

여기에 사건에 맞춰 동작하는 **훅**(hook, 자동 실행 명령)까지 더해지면 버전 관리가 더욱 어려워집니다.

### 개별 설정 복사의 한계

수동 설정 방식에서는 슬래시 명령과 서브에이전트 정의를 각자 복사해야 합니다. 여기에 MCP 서버와 훅 스크립트 권한까지 더해지면 초기 설정에 많은 시간이 들어갑니다.

팀원이 각자 설정하면 도구 누락이나 경로 오타로 동작 결과가 달라집니다. 최신 스크립트를 공유하더라도 팀원이 덮어쓰지 않으면 기능 격차가 누적됩니다.

### 플러그인 패키징의 이점

플러그인은 개별 확장 요소를 하나의 디렉터리로 묶고 매니페스트를 부여합니다. 단일 명령 한 줄로 모든 명령, 에이전트, 도구 연결이 즉시 구성됩니다.

| 항목 | 단독 개별 설정 | 플러그인 패키지 |
|------|------|------|
| 설치 방식 | 개별 파일 수동 복사 | 단일 명령 설치 |
| 초기 구성 시간 | 15분 이상 소요 | 수분 이내 완료 <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> |
| 컴포넌트 결합 | 개별 단일 파일 | 다중 요소 통합 |
| 버전 추적 | 수동 확인 | 시맨틱 버전 자동화 |
| 팀 공유 | 저장소 설정 직접 전달 | 고유 식별자 공유 |
| 의존성 관리 | 미지원 | 패키지 간 종속 선언 지원 |
| 유통 채널 | 개별 깃 저장소 | 마켓플레이스 카탈로그 |

도구 배포 시 실행 권한과 환경 변수 안내를 패키지로 함께 묶어 전달할 수 있습니다. 프로젝트마다 설정 스크립트를 다시 작성할 필요 없이 완성된 워크플로를 재현할 수 있습니다.

### 플러그인 전환 기준

모든 작업을 플러그인으로 만들 필요는 없습니다. 개인 환경에서 쓰는 단순 프롬프트나 단일 스크립트는 단독 스킬이나 단독 명령으로 두는 편이 가볍습니다.

반대로 팀 전체가 공유할 워크플로나 복합 파이프라인은 플러그인으로 승격할 가치가 충분합니다. 중앙에서 버전을 올렸을 때 사용자에게 자동 전파되어야 하는 도구도 마찬가지입니다.

### 명령어 네임스페이스와 호출 방식

단독 명령은 `/review`처럼 루트에 직접 등록되므로 도구 간 이름 충돌이 발생하기 쉽습니다. 플러그인은 각 명령 앞에 식별자를 접두사로 붙여 충돌을 방지합니다.

예를 들어 `pr-review` 플러그인의 `check` 명령은 정규 형태인 `/pr-review:check`로 등록됩니다. 원문 기준 v2.1.136부터는 공백을 둔 `/pr-review check` 호출도 정규 콜론 형태로 자동 해석됩니다. 스크립트에서는 명확한 식별을 위해 콜론 표기를 사용하는 것이 안전합니다.



## 구조와 로딩

> 플러그인은 매니페스트 파일과 역할별 서브 디렉터리로 구성됩니다. 세션이 시작되거나 설치될 때 정해진 순서에 따라 컴포넌트를 추출하고 등록합니다.

플러그인을 구성할 때 디렉터리 위치나 형식이 어긋나면 세션이 컴포넌트를 올바르게 인식하지 못합니다. 매니페스트를 중심으로 스킬, 서브에이전트, 훅, 언어 서버 정의가 정해진 규격에 맞춰 배치되어야 합니다.

### 디렉터리 구성과 매니페스트

모든 플러그인의 진입점은 `.claude-plugin/plugin.json` 파일입니다. 이 매니페스트는 패키지의 신원 정보와 진입 경로를 기술합니다.

```json
{
  "name": "my-first-plugin",
  "description": "Greeting and workflow helper",
  "version": "1.0.0",
  "author": {
    "name": "Your Name"
  },
  "homepage": "https://example.com",
  "repository": "https://github.com/user/repo",
  "license": "MIT"
}
```

매니페스트에는 패키지 식별 정보 외에도 다양한 구성 요소의 대체 경로를 지정할 수 있습니다.

| 필드 | 타입 | 설명 |
|------|------|------|
| `workflows` | 문자열 또는 배열 | 기본 `workflows/` 대신 사용할 워크플로 스크립트 경로 |
| `outputStyles` | 문자열 또는 배열 | 커스텀 출력 스타일 파일 또는 디렉터리 경로 |
| `lspServers` | 문자열, 배열 또는 객체 | 코드 인텔리전스를 제공하는 언어 서버 설정 |
| `channels` | 배열 | 외부 메시지 주입을 위한 채널 선언 |
| `dependencies` | 배열 | 필요한 다른 플러그인 목록과 버전 조건 |
| `keywords` | 배열 | 마켓플레이스 검색과 탐색에 쓰이는 키워드 |
| `metadata` | 객체 | Claude Code 가 읽지 않는 자유 형식의 추가 데이터 |
| `experimental.monitors` | 문자열 또는 배열 | 자동 시작되는 백그라운드 모니터 구성 |

### 컴포넌트별 배치 규칙

플러그인 루트 아래에는 기능별 디렉터리가 표준 위치에 자리합니다.

```pseudocode
my-plugin/
├── .claude-plugin/
│   └── plugin.json         # 패키지 매니페스트
├── skills/review-tool/
│   └── SKILL.md            # 스킬 정의
├── agents/
│   └── security-analyst.md # 서브에이전트 정의
├── hooks/
│   └── hooks.json          # 이벤트 핸들러
├── .mcp.json               # MCP 서버 설정
├── .lsp.json               # 언어 서버 설정
├── bin/                    # 보조 실행 바이너리
└── settings.json           # 플러그인 기본 설정
```

과거의 `commands/` 디렉터리도 호환을 위해 계속 동작합니다. 다만 공식 가이드는 신규 플러그인 작성 시 `skills/` 디렉터리 사용을 권장합니다.

원문 기준 v2.1.142부터는 `skills/` 하위 폴더 없이 루트에 단일 `SKILL.md`만 배치하는 단독 스킬 플러그인 패턴도 지원합니다. 이 경우 플러그인 자체가 하나의 스킬로 인식됩니다.

원문 기준 v2.1.136부터는 `plugin.json`에 `skills` 필드를 선언해도 디스크의 `skills/` 디렉터리가 가려지지 않습니다. 두 위치의 스킬이 병합되어 로드됩니다.

### 언어 서버 연동 설정

플러그인은 실시간 코드 분석과 탐색을 지원하기 위해 **언어 서버**(LSP, 코드 진단과 심볼 탐색을 제공하는 프로토콜)를 함께 패키징할 수 있습니다. 편집 직후 진단 결과 수집, 함수 정의로 이동, 심볼 목록 조회가 가능해집니다.

설정은 루트의 `.lsp.json` 파일에 두거나 매니페스트의 `lspServers` 키에 직접 선언합니다.

| 설정 필드 | 필수 여부 | 설명 |
|------|------|------|
| `command` | 필수 | PATH 상에 존재하는 언어 서버 실행 바이너리 |
| `extensionToLanguage` | 필수 | 파일 확장자와 언어 식별자 매핑 |
| `args` | 선택 | 언어 서버 구동 인자 목록 |
| `transport` | 선택 | 통신 방식 지정 (`stdio` 또는 `socket`) |
| `env` | 선택 | 서버 프로세스에 전달할 환경 변수 |
| `restartOnCrash` | 선택 | 프로세스 비정상 종료 시 자동 재시작 여부 |

파이썬을 위한 `pyright` 설정은 아래와 같이 작성합니다.

```json
{
  "python": {
    "command": "pyright-langserver",
    "args": ["--stdio"],
    "extensionToLanguage": {
      ".py": "python",
      ".pyi": "python"
    }
  }
}
```

### PATH 우선순위와 실행 파일

플러그인 루트의 `bin/` 디렉터리에 실행 파일(`chmod +x`)을 배치하면 세션 `PATH` 뒤쪽에 해당 경로가 자동으로 추가됩니다.

이 경로는 사용자의 기존 `PATH` 뒤쪽에 덧붙습니다. 따라서 시스템 명령어를 가로채지 못하도록 보호됩니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> 등록된 유틸리티는 세션 내부 Bash 도구에서 상대 경로 없이 파일 이름만으로 호출할 수 있습니다. 원문 기준 v2.1.302부터는 윈도우 환경의 PowerShell 도구에서도 동일하게 인식됩니다.

### 로딩 순서와 자동 로딩

플러그인이 로드될 때 Claude Code는 먼저 매니페스트를 검증하고 각 서브 디렉터리에서 컴포넌트를 추출합니다. 스킬, 에이전트, MCP 서버, 훅이 차례대로 등록되어 세션 도구로 편입됩니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 -->

원문 기준 v2.1.157부터는 `~/.claude/skills/<name>/`에 두면 마켓플레이스 없이 `<name>@skills-dir`로 자동 로드됩니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> 원격 세션의 경우 v2.1.179에서 로딩 성능이 개선되어 접속 직후 빠르게 도구를 사용할 수 있습니다.



## 옵션·데이터·설정

> 플러그인은 사용자가 값을 입력할 수 있는 설정 창구와 세션 간 유지되는 전용 저장소를 제공합니다. 모드를 통해 인터페이스를 확장하거나 설정을 인라인으로 주입할 수 있습니다.

단순한 도구 실행을 넘어 사용자 환경에 맞춘 옵션 제어와 영속 상태 관리가 필요할 때 플러그인의 부가 설정 기능을 사용합니다.

### 사용자 설정과 민감 정보 관리

원문 기준 v2.1.83부터 플러그인 매니페스트에 `userConfig` 객체를 정의하여 사용자 입력 옵션을 선언할 수 있습니다.

```json
{
  "name": "deploy-helper",
  "version": "1.0.0",
  "userConfig": {
    "apiKey": {
      "type": "string",
      "title": "API Key",
      "description": "배포 서비스 접근 토큰",
      "sensitive": true
    },
    "region": {
      "type": "string",
      "title": "Target Region",
      "description": "클라우드 리전",
      "default": "ap-northeast-2"
    }
  }
}
```

`sensitive: true`로 지정된 항목은 일반 텍스트 설정 파일에 노출되지 않고 macOS 키체인(다른 플랫폼은 보호된 자격 증명 파일)에 안전하게 보관됩니다.

설치 시점에는 `--config key=value` 플래그로 옵션 값을 즉시 넘길 수 있습니다. 원문 기준 v2.1.285부터는 번들링된 `.mcpb` 확장 서버 설정도 `<server>.<key>=<value>` 문법으로 한 번에 넘길 수 있습니다. 현재 설정 상태는 `claude plugin configure <name>@<marketplace>` 명령으로 확인합니다.

### 플러그인 영속 데이터

원문 기준 v2.1.78부터 플러그인은 `${CLAUDE_PLUGIN_DATA}` 환경 변수를 통해 플러그인 전용 영속 저장 디렉터리에 접근할 수 있습니다.

이 경로는 `~/.claude/plugins/data/<id>/` 위치에 식별자별로 분리되어 생성됩니다. 세션이 종료되거나 플러그인이 업데이트되더라도 데이터가 보존되므로 로컬 캐시나 경량 데이터베이스를 저장하기에 적합합니다.

저장된 데이터는 사용자가 플러그인을 최종 삭제할 때 함께 정리됩니다. 만약 데이터를 보존하고 싶다면 삭제 명령 실행 시 `--keep-data` 플래그를 전달해야 합니다.

### 백그라운드 모니터 등록

원문 기준 v2.1.105부터 플러그인은 백그라운드 모니터를 등록해 외부 로그나 이벤트를 실시간으로 감시할 수 있습니다. 매니페스트의 `experimental.monitors` 배열이나 `monitors/monitors.json` 파일에 정의합니다.

```json
{
  "name": "server-watcher",
  "version": "1.0.0",
  "experimental": {
    "monitors": [
      {
        "name": "error-log",
        "command": "tail -f /var/log/app-error.log",
        "description": "에러 로그 감시",
        "when": "always"
      }
    ]
  }
}
```

모니터의 `when` 속성은 두 가지를 받습니다. `"always"`는 세션 시작 시 구동되며, `"on-skill-invoke:<skill>"`은 해당 스킬 첫 호출 시 시작됩니다. 모니터는 내부 모니터 도구를 거쳐 표준 출력 라인을 이벤트 스트림으로 전달합니다.

### 인라인 플러그인 정의

원문 기준 v2.1.80부터 별도의 외부 저장소 없이 설정 파일 내에 플러그인을 직접 인라인으로 선언할 수 있습니다.

```json
{
  "extraKnownMarketplaces": {
    "internal-tools": {
      "source": {
        "source": "settings",
        "name": "internal-tools",
        "plugins": [
          {
            "name": "code-checker",
            "source": { "source": "github", "repo": "company/code-checker" }
          }
        ]
      }
    }
  }
}
```

`source: "settings"` 방식을 쓸 때는 반드시 GitHub나 npm 같은 완전한 원격 주소를 명시해야 합니다. 상대 경로는 기준이 될 저장소가 없어 거부됩니다.

### 인터페이스를 바꾸는 모드

원문 기준 v2.1.287부터 **모드**(mod, 사용자 화면과 동작 방식을 확장하는 자바스크립트 모듈)가 도입되었습니다. Claude Code 화면과 상호작용을 변경하는 확장 플러그인입니다. 터미널 CLI 환경뿐 아니라 데스크톱 앱과 VS Code 확장 프로그램에서도 동작합니다.

| 모드가 할 수 있는 작업 | 구체적인 쓰임새 |
|------|------|
| 패널 및 배너 렌더링 | 대화창 옆에 보조 패널을 띄우거나 프롬프트 상단에 상태 배너 표시 |
| 즉각 실행 명령어 등록 | 모델 턴 소비 없이 자바스크립트 함수를 즉시 실행하는 슬래시 명령 등록 |
| 도구 호출 제어 | 도구 실행 전에 사용자 확인 창을 띄우거나 입력을 수정해 응답 반환 |
| 이벤트 가로채기 | 프롬프트 입력과 도구 호출 횟수를 집계해 스피너 옆에 상태 출력 |
| 모드 전용 API 호출 | 자체 API를 거쳐 파일 입출력, 프로세스 실행, 네트워크 요청 수행 |

모드는 자바스크립트나 타입스크립트 훅 모듈로 작성됩니다. 모드 작성은 내장 `plugin-authoring` 스킬을 활용할 수 있으며 `claude plugin validate`로 사전 문법 검사를 수행합니다. 원문 기준 v2.1.299부터 v2.1.301에 걸쳐 텍스트 크기와 굵기, 방향 제어, 다중 행 입력 필드 등 다양한 UI 컴포넌트 속성이 추가되었습니다. 관리자는 보안을 위해 `allowManagedModsOnly` 설정으로 승인된 모드만 실행되도록 제한할 수 있습니다.

### 기본 환경 설정 적용

플러그인은 배포 패키지 안에 `settings.json` 파일을 담아 권장 기본 설정을 함께 배포할 수 있습니다.

```json
{
  "agent": "security-analyst"
}
```

보안과 일관성을 위해 플러그인의 `settings.json`에서는 오직 `agent`와 `subagentStatusLine` 두 키만 효력을 갖습니다. 그 외의 설정 키는 무시됩니다. `agent` 키에 특정 서브에이전트 이름을 지정하면 해당 에이전트가 메인 실행 스레드를 맡게 됩니다.



## 마켓플레이스와 설치 수명

> 플러그인은 마켓플레이스 카탈로그를 거쳐 배포되며 다양한 원격 소스에서 설치됩니다. 수명 주기 전반에 걸쳐 의존성 검사와 캐시 무결성이 유지됩니다.

외부에서 개발된 도구를 가져올 때 출처를 일일이 확인하지 않으면 버전 충돌이나 의존성 누락이 발생하기 쉽습니다. 마켓플레이스는 여러 플러그인의 메타데이터와 다운로드 위치를 모아 체계적으로 유통하는 카탈로그입니다.

### 마켓플레이스 카탈로그 구조

플러그인을 찾아 설치하는 출발점은 **마켓플레이스**(marketplace, 플러그인을 유통하는 저장소 목록)입니다. 마켓플레이스는 여러 플러그인의 메타데이터와 다운로드 위치를 모아 둔 카탈로그입니다.

공식 카탈로그인 `anthropics/claude-plugins-official`은 첫 실행 시 자동으로 등록됩니다. 안전성 검증을 거친 서드파티 플러그인이 모인 `anthropics/claude-plugins-community`는 사용자가 필요할 때 직접 추가할 수 있습니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 -->

```bash
# 커뮤니티 마켓플레이스 등록
/plugin marketplace add anthropics/claude-plugins-community

# 커뮤니티 카탈로그에서 플러그인 설치
/plugin install <plugin-name>@claude-community
```

원문 기준 v2.1.205부터 `first-party-plugins`(공식 등급)와 `healthcare`(커뮤니티 등급)는 예약된 이름입니다. <!-- 확인 필요: 공식 문서·설치본에서 찾지 못함 --> 일반 커스텀 마켓플레이스 이름으로 쓸 수 없습니다.

카탈로그 설정은 `.claude-plugin/marketplace.json` 형식으로 정의됩니다.

```json
{
  "name": "team-marketplace",
  "owner": { "name": "platform-team" },
  "plugins": [
    {
      "name": "code-review",
      "source": { "source": "github", "repo": "org/code-review", "ref": "v1.2.0" },
      "description": "PR 자동 검토 도구",
      "version": "1.2.0"
    }
  ]
}
```

카탈로그 최상위에는 플러그인 이름 변경에 대응하기 위한 `renames` 필드(v2.1.193+)를 둘 수 있습니다. 이전 이름을 새 이름으로 매핑해 두면 사용자가 기존 이름으로 호출해도 자연스럽게 새 버전으로 마이그레이션됩니다.

### 다양한 플러그인 소스 유형

마켓플레이스 항목은 다양한 저장소 유형을 소스로 지정할 수 있습니다.

| 소스 유형 | 선언 형식 | 비고 |
|------|------|------|
| 상대 경로 | `"./plugins/my-plugin"` | 로컬 모노레포 내부 경로 |
| GitHub | `{ "source": "github", "repo": "owner/repo" }` | `ref` 및 `sha` 지정 지원 |
| Git URL | `{ "source": "url", "url": "https://..." }` | 일반 깃 저장소 주소 |
| Git 하위 디렉터리 | `{ "source": "git-subdir", "url": "...", "path": "..." }` | 대형 저장소 내 특정 패키지 지정 |
| npm | `{ "source": "npm", "package": "@org/plugin" }` | npm 레지스트리 패키지 |
| 아카이브 | `{ "source": "archive", "url": "...", "sha256": "..." }` | v2.1.224+, HTTPS 압축 파일 직다운로드 |
| 로컬 명령 | `{ "source": "command", "command": "..." }` | v2.1.229+, 외부 툴이 디렉터리 경로 반환 |

깃랩 저장소도 v2.1.232부터 정규 지원되며 전체 HTTPS URL 형태로 지정해야 합니다. 비공개 토큰 유출 방지 마스킹도 함께 적용됩니다.

원문 기준 v2.1.238부터는 `headersHelper` 속성을 지정할 수 있습니다. 인증 토큰 발급 도구를 호출해 HTTP 헤더를 동적으로 생성하므로 설정 파일에 시크릿을 남기지 않고도 비공개 저장소와 통신할 수 있습니다.

원문 기준 v2.1.239부터 웹 환경인 claude.ai에서 동기화된 플러그인은 `<name>@synced` 이름으로 들어옵니다. 이는 로컬 설치 플러그인과 충돌하지 않고 공존합니다.

### 아카이브와 외부 명령 소스

아카이브 소스는 깃 복제 과정 없이 순수 HTTPS 주소에서 zip 파일을 내려받아 설치합니다. 크기는 최대 256MiB로 제한됩니다.

내부 루프백이나 클라우드 메타데이터 주소로의 접근(SSRF)을 차단하기 위해 리다이렉트가 발생하는 모든 홉마다 대상 호스트 검증을 엄격하게 수행합니다. 매니페스트에 기재된 `sha256` 해시가 일치하지 않으면 무결성 오류를 내며 설치가 중단됩니다.

외부 명령 소스는 사내 패키지 관리자가 설치 위치를 계산해 줄 때 사용됩니다. 지정된 명령은 반드시 표준 출력에 한 줄로 플러그인 루트 디렉터리의 절대 경로를 출력하고 종료 코드 0으로 끝나야 합니다. `mode` 속성을 `"link"`로 설정하면 심볼릭 링크를 생성하여 로컬 소스 수정 사항이 실시간으로 반영됩니다.

### 설치와 활성화 지연 판정

플러그인 설치는 대화형 인터페이스(`/plugin install`)와 터미널 CLI(`claude plugin install`) 모두 지원합니다. 원문 기준 v2.1.275부터는 미등록 마켓플레이스라도 `--marketplace <source>` 옵션으로 등록과 설치를 한 번에 끝낼 수 있습니다. 셸의 `claude plugin install` 에는 이 옵션이 v2.1.292에 들어왔습니다.

설치 완료 후 즉시 사용 가능한지 여부는 출력 요약 메시지를 통해 판정합니다.

| 출력 안내 문구 | 상태 및 의미 | 조치 방법 |
|------|------|------|
| `Plugin is now active.` | 즉시 활성화 완료 | 추가 작업 없이 바로 사용 |
| `Run /reload-plugins to apply.` | 설치 완료되었으나 대기 상태 | 대화창에서 `/reload-plugins` 실행 |

원문 기준 v2.1.221 이전에는 모든 설치 후 세션을 재시작하거나 수동으로 리로드해야 했습니다. 최신 버전에서는 프롬프트 캐시를 깨뜨리지 않는 조건이라면 설치 즉시 활성화됩니다. 이미 진행 중인 긴 대화 맥락이 있어서 캐시 보존이 필요한 경우에는 활성화를 보류하므로 안내에 따라 `/reload-plugins`를 입력하면 됩니다.

### 의존성 관리와 정리

플러그인은 매니페스트에 다른 플러그인에 대한 의존성을 선언할 수 있습니다.

원문 기준 v2.1.143부터는 의존성 제약이 엄격하게 강제됩니다. 다른 활성 플러그인이 의존하고 있는 플러그인은 비활성화(`disable`)할 수 없습니다. 반대로 부모 플러그인을 활성화(`enable`)하면 종속된 플러그인들도 연쇄적으로 활성화됩니다.

부모 플러그인 삭제 후 남은 고립 의존성은 `claude plugin prune`(별칭 `autoremove`)으로 일괄 정리할 수 있습니다. 플러그인 삭제 시점에 `claude plugin uninstall <name> --prune` 플래그를 넘기면 삭제와 고립 의존성 정리를 한 번에 처리합니다.

### 컨텍스트 토큰 비용 투영

플러그인을 많이 추가하면 항상 주입되는 시스템 프롬프트와 툴 명세로 인해 턴당 소비되는 컨텍스트 토큰이 늘어납니다.

원문 기준 v2.1.139부터 `claude plugin details <name>` 명령으로 컴포넌트 목록과 턴당 예상 토큰 비용을 확인할 수 있습니다.

```pseudocode
pr-review 1.0.0
Component inventory
  Skills (2)  check, start      Hooks (3)  (harness-only — no model context cost)
  MCP servers (1)  github  (tool schemas resolved at runtime; not counted)      LSP servers (0)
Projected token cost
  Always-on:   ~1,250 tok   added to every session
```

원문 기준 v2.1.143부터는 마켓플레이스 목록에서 플러그인을 고르면 상세 창의 `Context cost` 절로 설치 전 토큰 부하를 가늠할 수 있습니다. 이 절은 `Every turn:` 과 `When invoked:` 두 줄로 이루어지며 공식 마켓플레이스 플러그인에만 나타납니다.

### 자동 갱신과 주기 제어

Claude Code는 대화형 세션에서 첫 메시지를 보낸 뒤 최대 10분 안의 무작위 시점에 마켓플레이스 인덱스와 설치된 플러그인의 최신 버전을 확인해 자동 업데이트를 수행합니다.

공식 마켓플레이스는 기본적으로 자동 갱신이 켜져 있으며 서드파티 및 로컬 마켓플레이스는 기본적으로 꺼져 있습니다. 자동 갱신 동작은 환경 변수로 세밀하게 제어할 수 있습니다.

| 환경 변수 조합 | 동작 방식 |
|------|------|
| `DISABLE_AUTOUPDATER=1` | Claude Code 자체 및 모든 플러그인 자동 업데이트 중단 |
| `DISABLE_AUTOUPDATER=1` + `FORCE_AUTOUPDATE_PLUGINS=1` | 본체 업데이트는 끄고 플러그인 자동 업데이트만 유지 |
| `CLAUDE_CODE_PLUGIN_PREFER_HTTPS=1` | v2.1.141+, SSH 키가 없는 CI 환경을 위해 깃 클론 시 HTTPS 강제 |



## 만들고 시험하고 배포하기

> 플러그인은 전용 초기화 명령으로 틀을 잡고 로컬 플래그로 즉시 시험합니다. 평가 도구로 기능 안정성을 확인한 뒤 태그를 발행해 배포합니다.

새로 만든 플러그인을 원격 저장소에 바로 배포했다가 파일 누락이나 문법 오류가 생기면 배포 버전을 다시 올려야 하는 문제가 발생합니다. 로컬 디렉터리와 아카이브를 세션에 직접 마운트하여 실시간으로 동작을 점검한 뒤 검증을 거쳐 배포해야 합니다.

### 플러그인 초기화와 스캐폴딩

새 플러그인을 만들 때는 CLI 스캐폴딩 도구를 사용합니다.

```bash
claude plugin init my-plugin
claude plugin init my-plugin --with skills agents hooks mcp lsp
```

`--with` 플래그를 사용하면 필요한 컴포넌트 폴더와 템플릿 파일이 함께 생성됩니다. 기존 디렉터리를 덮어써야 할 때는 `-f` 또는 `--force` 플래그를 덧붙입니다.

### 로컬 디렉터리와 아카이브 시험

개발 중인 플러그인을 테스트할 때는 마켓플레이스에 배포할 필요 없이 실행 옵션으로 로컬 폴더를 전달합니다.

```bash
claude --plugin-dir ./my-plugin --plugin-dir ./second-plugin
claude --plugin-dir ./my-plugin.zip
claude --plugin-url https://example.com/builds/my-plugin-dev.zip
```

세션 내부에서 코드를 수정한 뒤에는 `/reload-plugins` 명령을 실행해 재시작 없이 변경 사항을 즉시 반영할 수 있습니다.

### 구조 검증과 평가 도구

배포 전에는 패키지 유효성 검사 명령을 실행해 디렉터리 참조 오류나 JSON 문법 오류를 점검합니다.

```bash
claude plugin validate ./my-plugin
claude plugin validate ./my-plugin --strict --json
```

원문 기준 v2.1.281부터는 내장된 `.mcp.json` 명세의 유효성을 함께 검증합니다. v2.1.283부터는 매니페스트가 가리키는 파일 경로가 플러그인 디렉터리 외부를 참조하고 있거나 누락되었을 경우 검증 실패를 발생시킵니다.

원문 기준 v2.1.269부터 `claude plugin eval` 명령으로 스킬과 에이전트의 테스트를 돌려 평가 점수를 매길 수 있습니다. Git 2.31 이상이 필요하며 `--disallow-tools` 플래그를 통해 불필요한 기본 도구 개입을 차단한 상태에서 정밀한 측정을 진행할 수 있습니다.

### 릴리스 태깅과 배포 절차

검증이 끝난 플러그인은 Git 태그를 생성해 배포 버전을 확정합니다.

```bash
# 버전 태그 생성 (경로 지정)
claude plugin tag ./my-plugin

# 생성과 동시에 원격 저장소로 푸시
claude plugin tag ./my-plugin --push
```

`claude plugin tag` 명령은 버전 문자열 대신 플러그인 **경로**를 인자로 받습니다. 매니페스트와 카탈로그의 버전 일치 여부를 대조한 뒤 `{name}--v{version}` 형식의 릴리스 태그를 생성합니다.

태그를 발행한 뒤에는 `marketplace.json`에 해당 태그나 커밋 해시를 등록하고 PR을 제출하여 카탈로그에 반영합니다.

### 컴포넌트 연계 워크플로

실제 배포되는 플러그인은 훅, MCP, 서브에이전트가 긴밀하게 맞물려 돌아갑니다. 풀 리퀘스트 검토 플러그인을 예로 들면 아래와 같은 흐름으로 동작합니다.

사용자가 대화창에서 `/pr-review:start` 명령을 입력하면 사전 검증 훅이 Git 작업 트리 상태를 점검합니다. 이어서 GitHub MCP 서버가 변경된 diff와 커밋 내역을 가져옵니다.

수집된 코드 정보는 보안 전문 서브에이전트와 테스트 점검 서브에이전트에게 각각 병렬로 전달됩니다. 서브에이전트 분석이 완료되면 최종 결과가 종합 요약 보고서 형태로 사용자 화면에 출력됩니다.



## 보안과 관리 설정

> 플러그인은 로컬 셸 명령과 외부 연결을 수행할 수 있으므로 보안 통제가 필수적입니다. 안전한 아카이브 검증과 조직 단위 정책 설정을 통해 악성 코드 유입을 차단합니다.

외부에서 제작된 플러그인을 설치하는 것은 검증되지 않은 바이너리를 로컬 환경에서 실행하는 것과 다름없습니다.

### 플러그인 실행 시 위험 요소

플러그인은 다양한 방식으로 시스템 자원에 접근합니다. 훅 스크립트는 도구 실행 전후에 임의의 셸 명령을 실행할 수 있습니다. `bin/` 디렉터리에 포함된 파일은 세션의 실행 경로에 추가됩니다.

또한 백그라운드 MCP 서버는 독립 프로세스로 떠서 로컬 포트를 점유하거나 원격 서버와 통신할 수 있습니다. 따라서 출처가 불분명한 마켓플레이스나 개인 저장소의 플러그인을 무분별하게 설치하면 보안 취약점에 노출될 위험이 큽니다.

### 서브에이전트 권한 제약

Claude Code는 플러그인 내부 서브에이전트가 시스템 권한을 임의로 상향하는 것을 막기 위해 엄격한 차단 규칙을 적용합니다. 플러그인에 정의된 서브에이전트 마크다운 파일의 프론트매터에서는 아래 키들이 완전히 무시됩니다.

- `hooks`: 개별 서브에이전트가 임의의 이벤트 핸들러를 등록할 수 없습니다.
- `mcpServers`: 서브에이전트 단위로 독자적인 외부 MCP 서버를 띄울 수 없습니다.
- `permissionMode`: 전체 세션의 권한 정책 모델을 서브에이전트가 재정의할 수 없습니다.
- `initialPrompt`: 서브에이전트 구동 시 첫 프롬프트를 자동으로 주입할 수 없습니다.

모든 훅과 MCP 서버는 패키지 루트 레벨에서 투명하게 명시되어야 하며 개별 에이전트 뒤에 숨겨진 채 동작할 수 없습니다.

### 네트워크와 아카이브 검증

원격 아카이브 소스로부터 zip 파일을 내려받을 때는 다중 계층의 네트워크 안전장치가 가동됩니다. 모든 요청은 오직 안전한 HTTPS 프로토콜만 허용됩니다.

리다이렉트 시 매 홉마다 대상 IP를 재검사합니다. 링크 로컬 주소, 로컬 호스트, 클라우드 메타데이터(169.254.169.254 등) 접근을 사전에 차단합니다. 파일 크기는 256MiB를 넘을 수 없으며 SHA-256 체크섬이 불일치하면 설치가 즉시 중단됩니다.

### 조직 차원의 관리자 정책

기업 환경에서는 중앙 관리자 정책 파일을 통해 사용자가 설치할 수 있는 플러그인과 마켓플레이스 범위를 통제할 수 있습니다.

| 관리자 설정 키 | 역할 및 제약 내용 |
|------|------|
| `strictKnownMarketplaces` | 허용된 마켓플레이스 목록을 강제하는 엄격 모드 (별칭 `allowedMarketplaces`) |
| `blockedMarketplaces` | 특정 마켓플레이스를 차단하는 블랙리스트 (호스트 및 경로 정규식 패턴 지원) |
| `enabledPlugins` | 특정 플러그인을 기본 활성화하거나 `false`로 지정해 전역 설치 및 노출 차단 |
| `allowedChannelPlugins` | 세션 내부로 메시지를 보낼 수 있는 채널 플러그인 허용 목록 |
| `disableCommandPluginSources` | 임의 셸 명령을 실행해 경로를 계산하는 `command` 소스 형식 전역 차단 |
| `allowManagedModsOnly` | 사내 공인 모드 및 내장 모드 외의 외부 모드 훅 실행 차단 |

원문 기준 v2.1.223부터 `strictKnownMarketplaces`와 `blockedMarketplaces`에 `"owner/*"` 와일드카드를 지원합니다. 특정 조직 산하 카탈로그를 한 번에 허용하거나 차단할 수 있습니다. 원문 기준 v2.1.117부터 마켓플레이스 통제 규칙은 설치, 갱신, 자동 업데이트 등 모든 수명 주기 단계에서 매번 재검증됩니다.



## 운영 팁과 문제 해결

> 플러그인을 안정적으로 유지하려면 명확한 책임 분리와 주기적인 점검이 필요합니다. 장애 발생 시 진단 도구를 활용해 병목과 오류 지점을 추적합니다.

플러그인 운영 과정에서 자주 발생하는 오류 유형과 권장 대응 절차를 정리합니다.

### 플러그인 설계 권장 사항

플러그인은 명확한 단일 목적을 갖도록 응집도 높게 설계해야 합니다. 서로 관련 없는 도구들을 하나의 큰 패키지에 몰아넣으면 불필요한 의존성으로 인해 설치가 무거워지고 토큰 비용이 낭비됩니다.

비밀번호나 API 토큰 같은 민감한 자격 증명은 절대 코드나 매니페스트에 직접 하드코딩해서는 안 됩니다. 반드시 `userConfig`의 `sensitive: true` 옵션이나 환경 변수를 통해 런타임에 주입받아야 합니다.

### 설치와 컴포넌트 누락 점검

플러그인을 설치했으나 명령어가 목록에 나타나지 않거나 컴포넌트가 로드되지 않을 때는 단계별 확인이 필요합니다.

먼저 `claude --version`으로 현재 실행 중인 CLI 버전이 플러그인 요구 사항을 만족하는지 확인합니다. 이어서 `claude plugin list` 명령을 통해 해당 플러그인이 실제로 활성화 상태인지 점검합니다.

설치 직후라면 설치 요약의 마지막 줄을 확인하여 `Run /reload-plugins to apply.` 메시지가 떠 있는지 살펴봅니다. 해당 메시지가 보인다면 대화창에서 `/reload-plugins`를 입력하여 구성을 갱신해야 합니다.

구성 요소가 올바르게 인식되었는지는 `claude plugin details <name>` 명령으로 인벤토리를 출력해 확인합니다. 선언된 스킬이나 에이전트 경로에 오타가 있거나 실행 권한이 누락된 경우 인벤토리에서 누락 항목을 식별할 수 있습니다.

### 외부 연동과 권한 장애 해결

MCP 서버 연결이 실패하는 경우 `/mcp` 명령으로 연결 상태를 점검하고 필수 환경 변수가 세션에 전달되었는지 확인합니다.

훅 스크립트가 실행되지 않는 문제는 주로 실행 권한 누락에서 비롯됩니다. 스크립트 파일에 `chmod +x` 권한이 부여되어 있는지 확인하고 `hooks.json`의 이벤트 매처 문법이 올바른지 점검합니다.

아카이브 다운로드가 실패할 때는 주소가 HTTPS인지 확인합니다. 서버 파일의 체크섬이 매니페스트의 `sha256` 해시와 일치하는지도 검증해야 합니다.
