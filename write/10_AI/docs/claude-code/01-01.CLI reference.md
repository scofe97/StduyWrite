# CLI reference
---
> Claude Code 를 여러 창·여러 계정·여러 워크트리로 나눠 띄우면서 쓰거나 새로 알게 된 실행 옵션을 모았습니다. 도움말에 한 줄로만 나오거나 아예 나오지 않는 동작을 실측 결과와 함께 적습니다.



## 핵심 요약

> 다른 폴더에서 띄운 세션이 내 설정을 그대로 보게 하려면 옵션 셋과 환경 변수 하나가 함께 필요합니다. 신뢰 질문은 옵션으로 넘길 수 없습니다.

스킬 저장소 밖의 워크트리에서 Claude Code 를 띄우면 그 세션은 스킬 저장소의 스킬·규칙·메모리를 모릅니다. `--add-dir` 은 스킬·명령·서브에이전트 정의까지만 열어 줍니다. CLAUDE.md 는 환경 변수 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 이 있어야 읽고, 메모리 폴더는 `--settings` 에 JSON 으로 넘겨야 바뀝니다. 처음 보는 폴더에서 뜨는 신뢰 질문 두 개는 옵션이 없어서 설정 파일에 승인값을 미리 적어 둡니다.

모델 쪽에서는 두 가지가 예상과 달랐습니다. `--advisor` 는 도움말에 없는 옵션인데 OAuth 로그인 계정에서도 동작했습니다. 사용자 설정 파일의 최상위 `effortLevel` 은 Opus 5.5 부터 적용되지 않아서, 계정마다 다르게 적어 둔 값이 Opus 5.5 에서는 쓰이지 않았습니다.

| 하고 싶은 일 | 옵션·변수 |
|------|------|
| 다른 폴더의 스킬을 함께 쓰기 | `--add-dir <폴더>` |
| 그 폴더의 CLAUDE.md·규칙도 읽기 | `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` |
| 이번 세션만 설정 바꾸기 | `--settings '<JSON>'` |
| 계정 나누기 | `CLAUDE_CONFIG_DIR=<설정 폴더>` |
| 판단할 때만 더 센 모델에 묻기 | `--advisor <모델>` (도움말에 없음) |
| 생각 깊이 정하기 | `--effort low\|medium\|high\|xhigh\|max` |
| 한 번 답하고 끝내기 | `-p`, `--output-format json` |



## 이 문서의 기준

> 버전 2.1.295 의 도움말·공식 문서·실제 실행을 대조했습니다. 셋이 어긋나면 실행 결과를 따랐습니다.

<!-- no-diagram: 근거의 출처를 밝히는 메타 절이라 그릴 구조가 없습니다. -->

CLI 옵션은 버전마다 늘고 바뀝니다. 그래서 이 문서의 옵션 이름은 모두 `claude --help` 출력과 맞춰 보았습니다. 동작 설명은 실제로 창을 띄워 확인한 것만 적었습니다. effort 의 단계와 결정 순서는 공식 문서 model-config 페이지에서 옮겼습니다. 실행해 보지 않은 옵션은 마지막 절에 따로 모아 두었습니다.

다른 버전을 쓰고 있다면 먼저 `claude --version` 과 `claude --help` 로 옵션이 그대로 있는지 확인합니다. 특히 `--advisor` 처럼 도움말에 나오지 않는 옵션은 예고 없이 바뀔 수 있습니다.



## 다른 폴더에서 띄워도 같은 설정 보기 · --add-dir·--settings

> 워크트리에서 띄운 세션에 스킬은 `--add-dir`, CLAUDE.md 는 환경 변수, 메모리는 `--settings` 로 각각 따로 이어 줍니다.

Claude Code 는 시작한 폴더를 기준으로 프로젝트 설정을 찾습니다. 스킬과 규칙을 `~/claude` 라는 별도 저장소에 모아 두고 실제 코드는 다른 저장소의 워크트리에서 고친다고 해 봅시다. 그러면 워크트리에서 띄운 세션은 `~/claude` 의 어떤 설정도 보지 못합니다. 기능마다 워크트리를 나눠 세션을 여러 개 띄우는 작업에서 이 문제가 바로 드러났습니다.

### --add-dir 이 여는 것과 열지 않는 것

`--add-dir` 은 시작 폴더 밖의 폴더를 하나 더 읽고 쓸 수 있게 여는 옵션입니다. 이름만 보면 파일 접근 권한만 넓히는 것 같지만 그 폴더의 `.claude/skills/`·`.claude/commands/`·`.claude/agents/` 도 함께 로드합니다. 반면 같은 폴더에 있어도 따라오지 않는 것이 있습니다. 설정 파일 `permissions.additionalDirectories` 로 연 폴더는 파일 접근만 받고 이런 로드가 없어서, 실행 옵션 `--add-dir` 이나 세션 안 `/add-dir` 을 써야 합니다.

| 추가한 폴더에 있는 것 | 세션에 들어오는가 |
|------|------|
| `.claude/skills/`·`commands/`·`agents/` | 들어옵니다 |
| `disable-model-invocation: true` 인 스킬 | 모델이 보는 목록에는 없습니다. 사용자가 `/이름` 으로 부르면 동작합니다 |
| `.claude/settings.json` | `enabledPlugins`·`extraKnownMarketplaces` 키만 들어옵니다. hook 은 들어오지 않습니다 |
| `CLAUDE.md` 와 `.claude/rules/` | 환경 변수가 있어야 들어옵니다(다음 절) |

hook 이 따라오지 않는다는 점은 놓치기 쉽습니다. 예를 들어 문서 요청에 작성 스킬을 붙이는 hook 이 `~/claude` 에만 있다면 워크트리 세션에서는 그 hook 이 돌지 않습니다. 그래서 그런 세션에 일을 넘길 때는 "작성 스킬부터 부른다"를 지시문에 직접 적었습니다.

### CLAUDE.md 는 환경 변수가 있어야 읽는다

추가한 폴더의 CLAUDE.md 와 규칙은 `CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1` 을 켠 세션만 읽습니다. 옵션이 아니라 환경 변수라서 실행 줄 앞에 붙입니다.

```bash
CLAUDE_CODE_ADDITIONAL_DIRECTORIES_CLAUDE_MD=1 \
  claude --add-dir ~/claude --model sonnet
```

이 변수 없이 `--add-dir` 만 주면 스킬은 보이는데 프로젝트 규칙은 모르는 세션이 됩니다. 스킬은 규칙이 정한 경계를 전제로 쓰인 경우가 많습니다. 둘 중 하나만 들어오면 오히려 엉뚱하게 동작할 수 있습니다.

### --settings 에 JSON 을 바로 넘긴다

`--settings` 는 설정 파일 경로뿐 아니라 JSON 문자열도 받습니다. 그 세션에만 적용되고 디스크의 설정 파일은 바뀌지 않습니다. 메모리 폴더를 스킬 저장소 것으로 바꿀 때 이렇게 썼습니다.

```bash
claude --settings '{"autoMemoryDirectory":"/Users/me/claude/.claude-config/projects/-Users-me-claude/memory"}'
```

이 값을 주지 않으면 세션은 그 프로젝트 몫의 메모리 폴더를 따로 씁니다. 스킬 저장소에서 쌓은 교훈을 하나도 모르는 세션이 되는 것입니다. 실제로 이 옵션을 준 워크트리 세션에 "메모리 목록에 herdr 이 들어간 줄이 있는가?"를 물었을 때, 스킬 저장소의 메모리 줄을 인용해 답했습니다.

### 신뢰 질문은 옵션으로 넘길 수 없다

처음 보는 폴더에서 대화형으로 띄우면 질문이 두 개 뜹니다. 하나는 이 폴더를 신뢰하는지, 다른 하나는 외부 CLAUDE.md 의 import 를 허용하는지입니다. 두 번째 질문은 홈 폴더의 `~/.claude/CLAUDE.md` 가 `@RTK.md` 처럼 다른 파일을 불러오기 때문에 뜹니다. 이 둘을 넘기는 실행 옵션은 없습니다.

| 질문 | 승인값을 적는 키 | 키를 다는 경로 |
|------|------|------|
| 폴더 신뢰 | `hasTrustDialogAccepted` | 시작한 폴더(워크트리) |
| 외부 import 허용 | `hasClaudeMdExternalIncludesApproved`, `hasClaudeMdExternalIncludesWarningShown` | 본 저장소 루트 |

승인값은 계정 설정 폴더의 `.claude.json` 안 `projects` 항목에 경로별로 저장됩니다. 두 번째 질문이 워크트리가 아니라 본 저장소 루트를 키로 읽는다는 점이 예상 밖이었습니다. 워크트리 경로에 세 키를 다 적었는데도 import 질문이 계속 떠서, 바이너리에서 그 값을 읽는 경로를 찾아보고 나서야 원인을 알았습니다. 둘 다 적을 때는 Claude Code 가 같은 파일을 동시에 다시 쓸 수 있으니 잠금을 잡고 쓰고, 파일 권한(0600)을 유지합니다.

herdr 같은 터미널 도구의 `--trust-repository` 는 Git 의 safe.directory 신뢰라서 이 두 질문과 관계가 없습니다.



## 계정 나누기 · CLAUDE_CONFIG_DIR

> 계정마다 설정 폴더를 따로 두고 `CLAUDE_CONFIG_DIR` 로 고르면 한 기계에서 두 계정을 동시에 띄울 수 있습니다.

<!-- no-diagram: 환경 변수 하나의 쓰임이라 그릴 흐름이 없습니다. -->

개인 계정과 회사 계정을 함께 쓰면 로그인 정보·설정·세션 기록이 섞이면 안 됩니다. Claude Code 는 이 모두를 설정 폴더 하나에 두므로, 계정마다 폴더를 나누고 실행할 때 환경 변수로 고르면 됩니다. 저는 셸 alias 로 묶어 두었습니다.

```bash
alias cc-work='CLAUDE_CONFIG_DIR=$HOME/claude/.claude-config claude --dangerously-skip-permissions --chrome'
alias cc-oke='CLAUDE_CONFIG_DIR=$HOME/.claude-oke claude --dangerously-skip-permissions --chrome'
```

로그인 정보도 설정 폴더에 있어서 폴더마다 다른 계정으로 로그인해 두면 사용량 한도도 계정별로 따로 찹니다. 한도는 폴더가 아니라 로그인한 계정 기준입니다. 앞 절의 신뢰 승인값도 계정마다 따로 적어야 한다는 뜻이기도 합니다. 한 계정에서 승인한 폴더라도 다른 계정으로 띄우면 같은 질문이 다시 뜹니다.



## 모델과 생각 깊이 · --model·--advisor·--effort

> 주 모델은 `--model`, 판단할 때만 쓰는 더 센 모델은 숨은 옵션 `--advisor`, 생각 깊이는 `--effort` 로 정합니다. 사용자 설정 파일의 옛 `effortLevel` 은 Opus 5.5 부터 쓰이지 않습니다.

<!-- no-diagram: 옵션별 동작과 결정 순서를 표·목록으로 적는 참조 절입니다. -->

모델을 고르는 일은 비용과 품질을 맞바꾸는 일입니다. 실행 분량은 많은데 어려운 판단은 가끔만 나오는 일에 처음부터 끝까지 가장 비싼 모델을 쓰면 낭비가 큽니다. 반대로 가벼운 모델 하나로만 돌리면 그 가끔 나오는 판단에서 틀립니다. 이 절의 세 옵션은 이 둘 사이를 조절하는 손잡이입니다.

### --model

`opus`·`sonnet`·`haiku`·`fable` 같은 별칭이나 `claude-sonnet-5-5` 같은 전체 모델 이름을 받습니다. 아래 두 옵션과 짝을 맞출 때는 어느 모델이 주 모델인지가 기준이 됩니다.

### --advisor 는 도움말에 없는 옵션이다

`--advisor <모델>` 을 붙이면 주 모델이 일하다가 판단이 필요한 순간에만 더 센 모델에게 조언을 구합니다. Anthropic 이 2026년 3월 공개한 advisor 전략을 Claude Code 에서 쓰는 방법입니다. 도움말에는 나오지 않지만 2.1.295 에서 동작했고, 세션 안에서는 `/advisor <모델|off>`, 설정 파일에서는 `advisorModel` 키로도 켭니다.

예전에는 이 기능을 쓰려면 API 키 사용자 전용인 `--betas` 헤더가 필요하다고 알고 있었습니다. 실제로는 전용 경로가 따로 있었습니다. OAuth 로 로그인한 두 계정 모두에서 동작했습니다. `-p --output-format json` 결과의 `modelUsage` 에 advisor 모델이 따로 잡히는 것으로 호출 여부를 확인했습니다.

쓸 때 알아 둘 제약이 셋 있습니다.

- advisor 는 주 모델 이상이어야 합니다(haiku < sonnet < opus < fable). opus 를 주 모델로 두고 sonnet 을 advisor 로 주면 경고만 남기고 advisor 없이 돕니다. 실패하지 않아서 모르고 지나가기 쉽습니다.
- 언제 물을지는 주 모델이 정합니다. 묻지 않고 끝낼 수도 있습니다.
- 5.x advisor 의 조언은 암호화되어 돌아와 화면에서 읽을 수 없습니다. 조언이 무엇이었는지 사람이 확인할 수 없으니, 검증처럼 판단 자체가 일인 작업에는 advisor 를 붙이기보다 주 모델을 올리는 편이 낫습니다.

### --effort 와 결정 순서

`--effort` 는 모델이 한 단계마다 얼마나 깊이 생각할지 정합니다. 단계는 `low`·`medium`·`high`·`xhigh`·`max` 다섯입니다. 모델마다 지원하는 단계가 다릅니다. 지원하지 않는 단계를 주면 그 아래에서 가장 높은 지원 단계로 내려가 돕니다. 예를 들어 Opus 4.6 에 `xhigh` 를 주면 `high` 로 돕니다.

세션의 effort 는 아래 순서에서 먼저 걸리는 값으로 정해집니다.

1. 명시한 값 — 환경 변수 `CLAUDE_CODE_EFFORT_LEVEL`, 실행 옵션 `--effort`, 세션 안 `/effort`. 이 가운데 환경 변수가 가장 우선이라, 셸에 이 변수가 남아 있으면 `--effort` 를 줘도 바뀌지 않습니다
2. 설정 — 모델별로 저장한 값(`modelSettings`) 또는 최상위 `effortLevel`
3. 모델의 기본값 — 대부분 `high`, Opus·Sonnet·Haiku 5.5 는 `medium`, Opus 4.7 은 `xhigh`

함정은 2번에 있습니다. 공식 문서에 따르면 사용자 설정 파일의 최상위 `effortLevel` 은 `/effort` 가 모델별 저장을 하기 전의 옛 형식입니다. 그래서 Opus 5·Fable 5.1 과 그 이전 모델에만 계속 적용되고 Opus 5.5 와 그 뒤 모델은 자기 기본값에서 시작합니다. 같은 키라도 프로젝트·로컬·관리형 설정이나 `--settings` 로 넘긴 값은 모든 모델에 적용됩니다.

제 두 계정은 최상위 값을 `xhigh` 와 `high` 로 다르게 적어 두었는데, Opus 5.5 에는 둘 다 `modelSettings` 에 `high` 가 저장돼 있어 실제로는 같은 깊이로 돌고 있었습니다. 계정을 바꿔 띄우면 깊이가 달라질 거라고 짐작했던 것이 틀렸던 셈입니다.

단계별 쓰임은 공식 문서의 안내를 따랐습니다. 이름 바꾸기 같은 작은 변경은 `low`, 범위가 분명한 새 기능 구현은 `medium`, 기존 코드의 버그 수정처럼 검증이 중요한 일은 `high`, 더 깊은 추론이 필요하면 `xhigh` 입니다. `max` 는 문서도 지나치게 오래 생각하기 쉽다고 경고해서 필요할 때만 씁니다. 단계 이름이 같아도 모델마다 실제 깊이는 다르게 맞춰져 있다는 점도 문서에 적혀 있습니다.



## 권한 · --dangerously-skip-permissions 와 도구 목록

> 권한 확인을 모두 건너뛰는 옵션은 편합니다. 다만 그 세션에 무엇을 하지 말라고 할지는 지시문이 대신 맡아야 합니다.

<!-- no-diagram: 옵션 목록을 정리하는 참조 절이라 그릴 흐름이 없습니다. -->

여러 창에 일을 나눠 맡기면 창마다 권한 질문에 답할 사람이 없습니다. 그래서 위의 두 alias 에는 `--dangerously-skip-permissions` 가 들어 있습니다. 이 옵션은 파일 쓰기·명령 실행·외부 전송에 대한 모든 확인을 건너뜁니다. 대신 커밋·push·삭제처럼 되돌리기 어려운 행동을 금지 행동으로 지시문에 반드시 적었습니다.

| 옵션 | 하는 일 |
|------|------|
| `--dangerously-skip-permissions` | 모든 권한 확인을 건너뜁니다 |
| `--permission-mode <모드>` | plan·acceptEdits 같은 권한 모드로 시작합니다 |
| `--allowedTools`, `--disallowedTools` | 도구를 이름으로 허용하거나 막습니다 |
| `--tools <도구...>` | 쓸 수 있는 내장 도구 목록 자체를 정합니다 |

보고서만 쓰면 되는 검증 창이라면 뒤의 세 옵션으로 쓰기 도구를 빼는 편이 지시문보다 확실합니다. 다만 이 조합은 아직 실제로 시험하지 않았습니다.



## 한 번 답하고 끝내기 · -p·--output-format

> `-p` 는 대화창 없이 한 번 답하고 끝납니다. JSON 출력의 `modelUsage` 로 어떤 모델이 얼마나 쓰였는지 확인할 수 있습니다.

<!-- no-diagram: 옵션 목록을 정리하는 참조 절이라 그릴 흐름이 없습니다. -->

스킬이 제대로 발동하는지 같은 질문을 여러 번 돌려 채점하는 평가 스크립트는 대화창이 필요 없습니다. 이런 일에는 `-p`(`--print`)로 한 번 답하고 끝내는 비대화 실행을 씁니다.

| 옵션 | 하는 일 |
|------|------|
| `-p, --print` | 답 하나를 출력하고 끝납니다 |
| `--output-format json\|stream-json` | 결과를 JSON 으로 냅니다. `modelUsage` 에 모델별 사용량이 나옵니다 |
| `--max-budget-usd <금액>` | 이번 실행의 비용 상한입니다 |
| `--json-schema <스키마>` | 정해진 형식의 출력을 강제합니다 |
| `--no-session-persistence` | 세션 기록을 남기지 않습니다 |

`-p` 와 `--output-format stream-json` 을 함께 쓰면 `--verbose` 가 없을 때 "requires --verbose" 오류로 멈춥니다. 스트림에는 hook 이벤트와 메시지가 줄마다 나오지만 지금 세션의 effort 값은 들어 있지 않았습니다. effort 가 실제로 무엇으로 정해졌는지는 이 출력으로 확인할 수 없었습니다.



## 세션 이어 가기 · -n·-c·-r·--fork-session

> 세션에 이름을 붙이고 이어 가거나 갈라 시작하는 옵션입니다.

<!-- no-diagram: 옵션 목록을 정리하는 참조 절이라 그릴 흐름이 없습니다. -->

창을 여러 개 띄우면 나중에 어느 세션이 무슨 일을 했는지 찾기 어려워집니다. 이름을 붙여 두면 이어 갈 때 목록에서 바로 고를 수 있습니다.

| 옵션 | 하는 일 |
|------|------|
| `-n, --name <이름>` | 세션에 표시 이름을 붙입니다 |
| `-c, --continue` | 이 폴더의 가장 최근 세션을 이어 갑니다 |
| `-r, --resume [ID\|이름]` | 고른 세션을 이어 갑니다 |
| `--fork-session` | 이어 가되 새 세션 ID 로 갈라 원본을 보존합니다 |
| `--session-id <uuid>` | 세션 ID 를 직접 정합니다 |



## 아직 시험하지 않은 옵션

> 이번 작업과 관련 있지만 실제로 띄워 보지 않은 옵션입니다. 설명은 도움말 문구만 옮겼습니다.

<!-- no-diagram: 미검증 옵션 목록이라 그릴 구조가 없습니다. -->

| 옵션 | 도움말이 말하는 것 | 관련된 이유 |
|------|------|------|
| `-w, --worktree [이름]` | 이 세션을 위한 git worktree 를 새로 만듭니다. `--tmux` 와 함께 쓰면 tmux 세션도 만듭니다 | 기능마다 워크트리를 나눌 때 후보였지만, 터미널 작업 공간까지 함께 만들어야 해서 터미널 도구의 워크트리 명령을 썼습니다 |
| `--bare` | hook·플러그인·CLAUDE.md 자동 탐색·자동 메모리를 건너뛴 최소 모드로 띄웁니다. 인증은 `ANTHROPIC_API_KEY` 나 `apiKeyHelper` 만 읽고 OAuth 로그인은 읽지 않습니다 | 평가를 사용자 설정 없는 환경에서 돌릴 후보지만, OAuth 계정만 있으면 쓸 수 없습니다 |
| `--setting-sources <목록>` | 읽을 설정 출처(user·project·local)를 고릅니다 | 같은 이유입니다 |
| `--agent`, `--agents` | 세션을 특정 에이전트 정의로 띄우거나 에이전트를 JSON 으로 정의합니다 | 창마다 역할을 고정하는 방법이 될 수 있습니다 |
| `--append-system-prompt` | 기본 시스템 프롬프트 뒤에 지시를 덧붙입니다 | 매번 지시문에 적는 금지 행동을 고정할 수 있습니다 |
| `--fallback-model <모델>` | 과부하일 때 쓸 대체 모델을 정합니다 | 긴 작업이 한도에 걸려 멈추는 일을 줄일 수 있습니다 |
| `--bg, --background` | 세션을 백그라운드로 시작합니다 | 창을 지켜볼 필요가 없는 일에 쓸 수 있습니다 |
