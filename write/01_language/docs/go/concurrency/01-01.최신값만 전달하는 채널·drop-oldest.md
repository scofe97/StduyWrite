# 최신값만 전달하는 채널·drop-oldest

---

> 느린 소비자에게 옛 값을 쌓지 않으려면 버퍼 1짜리 채널을 쓰고, 발행자가 꽉 찬 버퍼의 옛 값을 버린 뒤 새 값을 넣게 합니다. 발행자가 둘 이상이면 이 "비우고 넣기" 를 뮤텍스로 감쌉니다.

## 핵심 요약

> 센서 값이나 설정 스냅샷처럼 새 값이 옛 값을 대체하는 데이터는 발행이 막히지 않고 읽을 때 최신 값만 보여야 합니다. 이 편은 그 동작을 채널 하나로 만드는 법과 발행자가 여럿일 때 뮤텍스가 필요한 이유를 다룹니다.

락 없는 변형은 발행자가 영원히 막히는데도 `go test -race` 가 아무것도 보고하지 않습니다. 이 편의 실측이 그 장면을 보입니다. `sync.Cond`·`atomic.Pointer`·`context` 와 견주는 선택 기준도 다룹니다.

모든 값을 빠짐없이 받아야 하는 이벤트에는 이 패턴을 쓰지 않습니다. 옛 값이 조용히 버려지기 때문입니다.



## 1. 버퍼 1 채널과 drop-oldest 발행

> 채널 버퍼를 1로 두고 발행자가 꽉 찬 버퍼의 옛 값을 꺼내 버린 뒤 새 값을 넣으면, 발행자는 막히지 않고 소비자는 항상 최신 값을 받습니다.

### 풀려는 문제

센서 값, 화면 상태, 설정 스냅샷은 새 값이 나오면 옛 값이 의미를 잃습니다. 이런 값을 보통 채널로 보내면 둘 중 하나가 깨집니다.

- 버퍼 없는 채널: 소비자가 느리면 발행자가 `send` 에서 막혀 생산 쪽까지 느려집니다. 명세는 받을 준비가 된 수신자가 있을 때만 `send` 가 진행된다고 정합니다[^spec-send].
- 버퍼 큰 채널: 발행자는 막히지 않지만 소비자가 옛 값부터 차례로 읽습니다. 지금 값을 보려 해도 큐에 쌓인 옛 값을 먼저 비워야 합니다.

원하는 동작은 "발행은 절대 막히지 않고, 읽을 때는 가장 최근 값만 보인다" 입니다. 버퍼가 가득 찼을 때 가장 오래된 값을 버리는 이 정책을 drop-oldest 라고 부릅니다.

### 동작 원리

버퍼 채널의 용량은 버퍼 크기를 정합니다. 버퍼가 차지 않았으면 `send` 가, 비어 있지 않으면 `receive` 가 막히지 않고 끝납니다[^spec-chan]. 용량이 1이면 값 하나가 들어 있을 때 다음 `send` 는 막힙니다.

여기에 `select` 의 `default` 를 붙이면 막히는 대신 다른 일을 할 수 있습니다. 어느 통신도 진행할 수 없을 때만 `default` 가 골라집니다[^spec-select].

두 규칙을 합치면 발행 함수의 순서가 나옵니다.

1. `select` 로 막히지 않는 `send` 를 시도합니다. 버퍼가 비어 있으면 성공하고 끝납니다.
2. 실패하면 `select` 로 막히지 않는 `receive` 를 시도해 옛 값을 꺼내 버립니다. 그 사이 소비자가 먼저 가져갔다면 `default` 로 빠집니다.
3. 1번으로 돌아가 다시 넣습니다.

### 최소 예제

제네릭 래퍼입니다. 발행자 4개가 동시에 1,000번씩 발행하고, 1ms 쉬는 느린 소비자가 읽습니다.

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

// Latest 는 가장 최근 값 하나만 보관하는 채널 래퍼입니다.
type Latest[T any] struct {
	mu sync.Mutex // 발행자끼리 "비우고 넣기" 를 직렬화합니다.
	ch chan T
}

func NewLatest[T any]() *Latest[T] {
	return &Latest[T]{ch: make(chan T, 1)}
}

// Publish 는 버퍼가 차 있으면 옛 값을 버리고 v 를 넣습니다. 절대 막히지 않습니다.
func (l *Latest[T]) Publish(v T) {
	l.mu.Lock()
	defer l.mu.Unlock()
	for {
		select {
		case l.ch <- v:
			return
		default:
		}
		select {
		case <-l.ch: // 옛 값을 꺼내 버립니다.
		default: // 그 사이 소비자가 먼저 가져갔습니다.
		}
	}
}

// C 는 소비자가 읽는 쪽입니다.
func (l *Latest[T]) C() <-chan T { return l.ch }

func main() {
	l := NewLatest[int]()

	var wg sync.WaitGroup
	for p := 0; p < 4; p++ { // 발행자 4개가 동시에 발행합니다.
		wg.Add(1)
		go func() {
			defer wg.Done()
			for i := 0; i < 1000; i++ {
				l.Publish(p*1000 + i)
			}
		}()
	}

	done := make(chan struct{})
	received := 0
	go func() { // 느린 소비자입니다.
		defer close(done)
		for {
			select {
			case <-l.C():
				received++
				time.Sleep(time.Millisecond)
			case <-time.After(50 * time.Millisecond):
				return
			}
		}
	}()

	wg.Wait()
	<-done
	fmt.Println("발행 4000, 수신", received)
}
```

Go 1.25.1 에서 `go vet` 과 `go run -race` 를 통과했고 출력은 `발행 4000, 수신 4` 였습니다. 수신 횟수는 실행마다 다릅니다. 소비자가 느릴수록 건너뛰는 값이 늘어나는 것이 이 패턴의 의도된 동작입니다.



## 2. 발행자 여럿과 뮤텍스

> 뮤텍스 없는 변형은 데이터 경쟁이 아니라 막힘으로 실패합니다. 채널 연산은 그 자체로 동기화되어 있어 `-race` 가 이 문제를 보고하지 않습니다.

### 막히는 변형

발행자가 하나뿐이면 1절의 순서에 뮤텍스가 필요 없습니다. 발행자가 둘 이상이면 2번과 3번 사이에 다른 발행자가 끼어들어 버퍼를 다시 채울 수 있습니다.

이때 3번을 막히는 `send` (`ch <- v`) 로 쓰면, 먼저 비웠던 발행자가 가득 찬 버퍼 앞에서 소비자가 읽어 줄 때까지 막힙니다.

```go
func publish(ch chan int, v int) {
	select {
	case ch <- v:
	default:
		select {
		case <-ch:
		default:
		}
		ch <- v // 다른 발행자가 그 사이 채웠다면 여기서 영원히 막힙니다.
	}
}
```

이 변형에 발행자 4개가 각각 10만 번 발행하게 하고 3초 안에 끝나는지 `go test -race` 로 3번 돌렸습니다. 3번 모두 3초 안에 끝나지 않았고, 출력에 `DATA RACE` 는 한 줄도 없었습니다. 뮤텍스로 감싼 1절의 `Publish` 는 같은 부하를 1.7초 안에 끝냈습니다.

### 뮤텍스가 막힘을 없애는 이유

뮤텍스로 "비우고 넣기" 전체를 감싸면 발행자끼리 직렬화되어 끼어들 틈이 사라집니다. 소비자는 뮤텍스를 쓰지 않고 읽기만 하는데, 소비자가 끼어들어도 안전합니다. 소비자는 값을 꺼내기만 하므로 비운 뒤에는 늘 자리가 있습니다.

1절 순서의 3번을 `for` 반복의 재시도로 쓴 것은 이 가정이 깨져도 막히지 않게 하는 보험입니다.

막힌 발행자 고루틴은 스스로 끝나지 않습니다. 고루틴은 가비지 컬렉션 대상이 아니라서 스스로 종료해야 한다고 Go 블로그가 적습니다[^blog-pipelines].



## 3. 대안과 비교

> 세 가지 대안은 "값을 전달하는 것" 과 "새 값이 왔다고 알리는 것" 중 어느 쪽을 맡는지가 서로 다릅니다.

| 방식 | 맡는 일 | 소비자가 새 값을 아는 법 | 맞는 경우 |
|------|---------|------------------------|-----------|
| 버퍼 1 채널 + drop-oldest | 값 전달과 알림 | 채널 수신으로 깨어남 | 새 값마다 소비자를 깨워야 할 때 |
| `atomic.Pointer[T]` | 최신 값 저장·읽기 | 알림 없음, 주기적으로 읽어야 함 | 읽을 때만 최신 값이 필요할 때 |
| `sync.Cond` | 조건 변수와 값 직접 관리 | `Wait` 에서 깨어남 | 여러 소비자를 한꺼번에 깨울 때 |
| `context` | 취소·마감·요청 범위 값 | `ctx.Done()` | 연속 데이터 전달에는 쓰지 않음 |

### sync.Cond

`Wait` 는 락을 풀고 잠들었다가 깨어나면 락을 다시 잡습니다. 깨어나도 조건이 참이라는 보장이 없어서 호출하는 쪽이 `for` 로 조건을 다시 검사해야 합니다.

문서는 단순한 경우에 `Cond` 보다 채널이 낫다고 적습니다[^cond-doc]. `Broadcast` 는 채널 닫기에, `Signal` 은 채널로 보내기에 대응합니다.

### atomic.Value·atomic.Pointer

최신 값을 락 없이 저장하고 읽습니다. 소비자는 값이 바뀌었는지 알림을 받지 못하므로 주기적으로 읽어야 합니다. 값이 바뀔 때마다 깨어나야 한다면 채널이나 `Cond` 가 필요합니다.

`atomic.Value` 는 같은 구체 타입만 `Store` 할 수 있습니다. 일관되지 않은 타입이나 `Store(nil)` 은 panic 입니다[^atomic-doc].

`Cond` 와 `atomic.Pointer` 를 쓴 짧은 예도 `go vet` 과 `go run -race` 를 통과했습니다.

```go
type Snapshot struct{ N int }

var latest atomic.Pointer[Snapshot]

// 쓰기: latest.Store(&Snapshot{N: 1})
// 읽기: latest.Load().N  (Store 전에는 nil 이므로 nil 검사 필요)

type Box struct {
	mu  sync.Mutex
	c   *sync.Cond
	v   int
	gen uint64
}

func (b *Box) Set(v int) {
	b.mu.Lock()
	b.v = v
	b.gen++
	b.mu.Unlock()
	b.c.Broadcast()
}

func (b *Box) Wait(seen uint64) (int, uint64) {
	b.mu.Lock()
	defer b.mu.Unlock()
	for b.gen == seen { // Wait 는 깨어나도 조건이 참이라는 보장이 없습니다.
		b.c.Wait()
	}
	return b.v, b.gen
}
```

### context

`context` 는 마감 시각, 취소 신호, 요청 범위 값을 나르는 도구입니다[^ctx-doc]. 연속으로 갱신되는 데이터를 나르는 용도가 아니므로 이 패턴의 대안이 아닙니다. 대신 이 패턴의 소비자 루프를 멈출 때 `ctx.Done()` 을 같은 `select` 에 넣어 함께 씁니다.

### 선택 기준

읽을 때만 최신 값이 필요하면 `atomic.Pointer[T]` 가 가장 단순합니다. 새 값이 올 때마다 소비자를 깨워야 하면 이 편의 버퍼 1 채널이 맞습니다.

여러 소비자를 한꺼번에 깨워야 하면 `Cond.Broadcast` 를 씁니다. 버퍼 1 채널은 값 하나를 소비자 한 명만 받기 때문입니다.



## 4. 흔한 함정

> 가장 위험한 함정은 모든 이벤트가 필요한 곳에 이 패턴을 쓰는 것입니다.

결제 완료, 주문 접수, 감사 로그처럼 하나라도 빠지면 안 되는 이벤트는 drop-oldest 가 조용히 버립니다. 이 패턴은 "다음 값이 이전 값을 대체한다" 는 의미가 있는 상태 값에만 씁니다.

그 밖의 함정은 다음과 같습니다.

- 뮤텍스를 빼고 마지막 `send` 를 막히는 `ch <- v` 로 쓰기. 2절 실측처럼 발행자가 막히는데 `-race` 는 보고하지 않습니다.
- 채널을 닫는 책임이 모호함. 닫힌 채널에 `send` 하면 run-time panic 입니다[^spec-closed]. 발행자 쪽이 닫을 때는 뮤텍스 안에서 닫힘 여부를 확인해야 합니다. 1절의 예제는 채널을 닫지 않고 소비자가 타이머로 끝납니다.
- 소비자가 값을 읽은 뒤 처리하는 중에 새 값이 오면 그 값은 다음 읽기 때 받습니다. 처리 중 도착한 값을 즉시 보고 싶다면 별도 취소 신호를 설계해야 합니다.
- 소비자가 여럿이면 값 하나를 한 소비자만 받습니다. 모두가 같은 최신 값을 봐야 하면 `atomic.Pointer` 로 읽거나 `Cond.Broadcast` 를 씁니다.
