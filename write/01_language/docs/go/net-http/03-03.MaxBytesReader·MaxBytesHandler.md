# MaxBytesReader·MaxBytesHandler

---

> `http.MaxBytesReader` 는 요청 본문을 읽을 수 있는 바이트 수에 상한을 두고, 넘으면 `*http.MaxBytesError` 를 돌려줍니다. 경로 전체에 같은 상한을 씌울 때는 `http.MaxBytesHandler` 로 핸들러를 감쌉니다.

## 핵심 요약

> 본문 크기는 클라이언트가 아니라 서버가 정합니다. 본문을 읽기 전에 `r.Body` 를 `MaxBytesReader` 로 바꾸고, 오류는 `errors.As` 로 가려 413 을 핸들러가 직접 씁니다.

`Server` 의 타임아웃([03-02](./03-02.Server%20%ED%83%80%EC%9E%84%EC%95%84%EC%9B%83%C2%B7Shutdown.md))은 시간을 제한할 뿐 본문 크기를 제한하지 않습니다. 크기 상한은 따로 둡니다.

이 편은 `MaxBytesReader` 와 `io.LimitReader` 의 차이를 다룹니다. `MaxBytesHandler` 를 겹쳐 쓸 때의 동작과 413 응답을 쓰는 법도 다룹니다.



## 1. 본문 상한과 MaxBytesReader

> `MaxBytesReader` 는 한도를 넘는 읽기에서 오류를 돌려주고 연결을 닫도록 서버에 알립니다. 조용히 잘라 내는 `io.LimitReader` 와 이 점이 다릅니다.

### 상한이 없을 때의 문제

`json.NewDecoder(r.Body).Decode(&v)` 와 `io.ReadAll(r.Body)` 는 클라이언트가 보내는 만큼 읽습니다. 수 기가바이트짜리 본문 하나로 서버 메모리가 바닥날 수 있습니다.

느린 대용량 전송은 연결과 고루틴을 오래 붙잡습니다. 악의가 없어도 클라이언트 버그로 같은 일이 생깁니다. 공식 문서도 이 함수의 목적을 실수든 악의든 큰 요청이 서버 자원을 낭비하는 것을 막는 일로 적습니다[^mbr-doc].

### LimitReader 와 다른 점

`MaxBytesReader(w, r.Body, n)` 는 `r.Body` 를 감싼 `io.ReadCloser` 를 돌려줍니다. `io.LimitReader` 는 `io` 패키지의 리더로, n 바이트까지만 읽게 해 줍니다. 요청 본문에는 이 둘 중 `MaxBytesReader` 를 씁니다.

| 항목 | `io.LimitReader` | `http.MaxBytesReader` |
|------|------------------|-----------------------|
| 한도를 넘는 읽기 | n 바이트에서 EOF 를 돌려줌 | `*http.MaxBytesError` 를 돌려줌 |
| 반환 타입 | `io.Reader` | `io.ReadCloser` |
| `Close` | 없음 | 원래 본문을 닫음 |
| 연결 | 상관하지 않음 | 가능하면 응답 뒤 연결을 닫도록 `ResponseWriter` 에 알림 |

`LimitReader` 는 잘린 본문이 정상 입력처럼 보이는 것이 문제입니다[^limit-doc]. 10바이트 본문을 한도 4 로 `io.ReadAll` 하면 `LimitReader` 는 `"xxxx"` 와 `nil` 을 돌려줍니다. `MaxBytesReader` 는 같은 `"xxxx"` 와 함께 오류를 돌려줍니다.

### MaxBytesError 와 읽기 동작

`MaxBytesError` 는 Go 1.19 에서 들어왔고 필드는 `Limit` 하나입니다[^api-119]. 그 전의 Go 1.18 은 `errors.New` 로 만든 일반 오류를 돌려줘서, 구분하려면 메시지 문자열을 비교해야 했습니다[^req-118]. `Error()` 의 문구는 `http: request body too large` 이고, 소스 주석이 이 문구를 바꿀 수 없다고 적습니다[^req-src].

go1.25.1 에서 로컬로 돌려 확인한 읽기 동작은 다음과 같습니다.

- 한도와 같은 크기의 본문은 오류 없이 모두 읽힙니다. 한도 4 에 `"abcd"` 는 통과합니다.
- 한도를 넘으면 한도만큼의 바이트와 오류가 함께 돌아옵니다. 넘친 바이트는 돌려주지 않습니다.
- 오류는 한 번 나면 이어지는 `Read` 에도 같은 값으로 돌아옵니다. 소스에서는 `err` 필드에 담아 두는 구조입니다[^req-src].
- 음수 한도는 0 으로 취급됩니다. 한도 -5 에 `"a"` 한 바이트만 있어도 `ReadAll` 이 `MaxBytesError` 로 끝납니다.
- `json.Decoder` 는 이 오류를 감싸지 않고 `*http.MaxBytesError` 그대로 돌려줍니다. `errors.As` 가 성공했습니다.

`MaxBytesReader` 는 `Content-Length` 헤더를 보지 않고 실제로 읽은 바이트만 셉니다. `Content-Length: 1000` 으로 1000바이트를 보낸 요청에서 핸들러가 본문을 읽지 않으면 한도 10 이어도 오류 없이 200 이 나갔습니다.

같은 요청에서 `Read` 로 5바이트를 읽으면 `n=5` 와 `nil` 이 돌아옵니다. `ReadAll` 로 나머지를 읽을 때 비로소 오류가 납니다. 큰 본문을 헤더만 보고 거절하려면 `r.ContentLength` 를 핸들러가 직접 비교해야 합니다. 청크 전송이면 이 값이 -1 이라 헤더로는 알 수 없습니다.



## 2. MaxBytesHandler 와 겹쳐 쓰기

> `MaxBytesHandler(h, n)` 는 핸들러 `h` 가 받는 `Request.Body` 를 `MaxBytesReader` 로 감쌉니다. 라우트 하나에 한도를 걸 때 핸들러를 고치지 않아도 됩니다.

핸들러마다 첫 줄에 `MaxBytesReader` 를 넣으면 한 곳을 빠뜨리기 쉽습니다. 이럴 때 `MaxBytesHandler` 로 라우트를 감쌉니다.

`MaxBytesHandler` 는 Go 1.18 에서 추가됐습니다[^api-118]. 요청을 얕게 복사해 `Body` 만 바꾼 뒤 `h` 를 호출하는 구조입니다[^handler-src]. 그래서 감싼 핸들러 아래의 모든 핸들러가 같은 한도를 받습니다.

핸들러 안에서도 `MaxBytesReader` 를 한 번 더 씌우면 두 한도가 모두 적용됩니다. 본문 8바이트에 대해 바깥 한도와 안쪽 한도를 바꿔 가며 돌려 보았습니다.

| 바깥 `MaxBytesHandler` | 안쪽 `MaxBytesReader` | 돌아온 `Limit` |
|------------------------|-----------------------|----------------|
| 10 | 4 | 4 |
| 4 | 10 | 4 |

작은 쪽 한도가 이깁니다. 오류의 `Limit` 은 걸린 쪽의 값이라서, 어느 한도에 걸렸는지 `Limit` 으로 알 수 있습니다.

두 곳에 한도를 쓰면 실제로 적용되는 값을 코드만 보고 알기 어렵습니다. 한도는 한 곳에서만 정합니다.



## 3. 413 응답과 연결 닫힘

> 오류를 돌려주는 것까지가 `MaxBytesReader` 의 일이고 413 은 핸들러가 씁니다. 한도를 넘은 연결은 서버가 응답 뒤에 닫습니다.

### 최소 예제

아래 서버는 `/items` 에 1 MiB, `/bulk` 에 8 MiB 한도를 걸고 한도 초과를 413 으로 돌려줍니다.

```go
package main

import (
	"encoding/json"
	"errors"
	"log"
	"net/http"
)

type payload struct {
	Name string `json:"name"`
}

func create(w http.ResponseWriter, r *http.Request) {
	r.Body = http.MaxBytesReader(w, r.Body, 1<<20) // 1 MiB

	var p payload
	if err := json.NewDecoder(r.Body).Decode(&p); err != nil {
		var mbe *http.MaxBytesError
		if errors.As(err, &mbe) {
			http.Error(w, "body too large", http.StatusRequestEntityTooLarge)
			return
		}
		http.Error(w, "bad json", http.StatusBadRequest)
		return
	}
	w.WriteHeader(http.StatusCreated)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("POST /items", create)
	// 경로 전체에 같은 한도를 씌우는 방법
	mux.Handle("POST /bulk", http.MaxBytesHandler(http.HandlerFunc(create), 8<<20))
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

이 예제는 Go 1.25.1 에서 `go vet` 과 `go build` 를 통과했습니다. `httptest` 서버로 돌려 보면 12바이트 JSON 은 201 입니다. 2 MiB 본문은 `/items` 와 `/bulk` 모두 413 이고, 깨진 JSON 은 400 입니다.

`/bulk` 는 8 MiB 한도를 먼저 받지만 핸들러 안의 1 MiB 한도가 더 작아서 2 MiB 본문이 413 이 됩니다. 앞 절의 표와 같은 동작입니다.

### 한도를 넘은 연결

`MaxBytesReader` 는 한도를 넘는 순간 `ResponseWriter` 에 `requestTooLarge` 를 알립니다. 서버 구현체는 그 응답 뒤에 연결을 닫도록 표시하고, 헤더를 아직 쓰기 전이면 `Connection: close` 를 붙입니다[^too-large-src].

원시 TCP 로 HTTP/1.1 요청을 보내 확인했습니다. 한도 10 에 50바이트를 보내면 413 응답의 `Close` 가 true 였고, 응답을 다 읽은 뒤 같은 연결을 읽으면 `EOF` 가 났습니다. 5바이트를 보낸 요청은 응답 뒤에도 연결이 살아 있었습니다.

HTTP/2 에서의 연결 처리는 확인하지 않았습니다.

### 흔한 함정

- `ReadAll` 이나 디코더를 만들기 전에 `r.Body` 를 바꿔야 한도가 적용됩니다.
- 오류 문자열을 비교하지 말고 `errors.As` 로 `*http.MaxBytesError` 를 가립니다.
- 413 은 핸들러가 직접 씁니다. 오류를 무시하면 핸들러가 정한 상태 코드가 나가고, 연결만 닫힙니다. 한도 10 에 1000바이트를 보내고 오류를 버린 핸들러는 200 을 돌려줬고 응답의 `Close` 는 true 였습니다.
- `Request.ParseForm` 은 `application/x-www-form-urlencoded` 본문에 10 MB 기본 한도를 둡니다. `r.Body` 가 이미 `MaxBytesReader` 이면 기본 한도는 빠지고 `MaxBytesReader` 한도만 남습니다[^parse-form-src]. 소스를 읽어 확인했고 실행하지는 않았습니다.
