# Cookie·SameSite·HMAC 서명

---

> 쿠키 값에 HMAC 서명을 붙이면 서버가 세션을 저장하지 않아도 변조를 가려낼 수 있습니다. Go 에서는 `hmac.New`·`hmac.Equal` 로 서명을 만들고 비교하고, `http.Cookie` 필드로 쿠키 속성을 정합니다.

## 핵심 요약

> 서명은 값이 바뀌지 않았음을 보일 뿐 값을 숨기지 않습니다. 서명을 `hmac.Equal` 로 비교하고, 만료 시각까지 서명 대상에 넣고, 속성은 `HttpOnly`·`Secure`·`SameSite` 로 잠급니다.

HMAC 이 무엇이고 단순 해시와 어떻게 다른지는 [암호학 기초 §4](../../../../99_ETC/security/01_concepts/2026-05-29_%EC%95%94%ED%98%B8%ED%95%99%20%EA%B8%B0%EC%B4%88%20%E2%80%94%20%EB%8C%80%EC%B9%AD%C2%B7%EB%B9%84%EB%8C%80%EC%B9%AD%C2%B7%ED%95%B4%EC%8B%9C%C2%B7HMAC.md)가 다룹니다. 세션과 토큰 중 무엇을 고를지는 [세션 vs 토큰](../../../../99_ETC/security/01_concepts/2026-05-29_%EC%84%B8%EC%85%98%20vs%20%ED%86%A0%ED%81%B0%20%E2%80%94%20%EC%83%81%ED%83%9C%20%EA%B8%B0%EB%B0%98%EA%B3%BC%20%EB%AC%B4%EC%83%81%ED%83%9C%20%EC%9D%B8%EC%A6%9D%EC%9D%98%20%ED%8A%B8%EB%A0%88%EC%9D%B4%EB%93%9C%EC%98%A4%ED%94%84.md)가 다룹니다.

이 편은 두 문서가 다루지 않는 Go 구현을 맡습니다. 서명을 만들고 검증하는 코드와 `http.Cookie` 의 필드, 그리고 서버 저장소가 없어서 생기는 한계를 다룹니다.



## 1. 서명 쿠키의 구조

> 쿠키 값을 `메시지.서명` 꼴로 만들고, 서버는 같은 키로 서명을 다시 계산해 비교합니다. 비교는 `hmac.Equal` 로 합니다.

### 서명이 없을 때의 문제

쿠키는 클라이언트가 마음대로 고칠 수 있습니다. `user=alice` 를 그대로 믿으면 `user=admin` 으로 바꾼 쿠키가 통과합니다.

세션 ID 를 서버 저장소에 두면 해결되지만 저장소를 운영해야 합니다. HMAC 은 비밀 키를 가진 서버만 만들 수 있는 서명을 값에 붙이는 방식이라, 저장소 없이 변조를 가려냅니다.

### hmac.New 와 hmac.Equal

`hmac.New(sha256.New, key)` 가 해시 객체를 만듭니다. `Write` 로 메시지를 넣고 `Sum(nil)` 로 서명을 얻습니다. 첫 인자는 해시 생성 함수라서, 호출할 때마다 새 `Hash` 를 돌려줘야 합니다[^hmac-doc].

쿠키 값은 `base64(메시지).base64(서명)` 으로 만듭니다. 메시지에는 사용자 식별자와 만료 시각을 넣습니다. 만료 시각을 서명 대상에 포함해야 클라이언트가 만료 시각만 늘리는 변조를 막을 수 있습니다.

서버는 쿠키를 받으면 같은 키로 서명을 다시 계산해 `hmac.Equal` 로 비교합니다. `Equal` 은 타이밍 정보를 흘리지 않고 두 MAC 을 비교합니다[^hmac-doc]. 패키지 개요도 수신자는 타이밍 부채널을 피하려고 `Equal` 로 비교하라고 안내합니다[^hmac-doc]. 소스에는 두 MAC 의 길이가 다르면 상수 시간일 필요가 없다는 주석이 있습니다[^equal-src].

`==` 나 `bytes.Equal` 같은 일반 비교는 처음 다른 바이트에서 멈출 수 있습니다. 응답 시간 차이가 서명 추측의 단서가 되므로 `Equal` 을 씁니다. 이 마지막 이유는 문서 문장이 아니라 타이밍 부채널(timing side-channel)에 대한 일반 설명입니다.

서명 길이는 SHA-256 기준 32바이트입니다. 길이가 다른 입력은 `Equal` 이 `false` 를 돌려줍니다.

### 서명과 암호화의 차이

서명은 값이 바뀌지 않았음을 보장할 뿐 내용을 숨기지 않습니다. 아래 예제가 만든 쿠키의 앞부분은 base64 만 풀면 `alice|만료시각` 평문이 그대로 나옵니다. 비밀번호나 개인정보를 쿠키에 담지 않습니다.



## 2. 쿠키 속성과 http.Cookie

> `http.Cookie` 의 필드가 `Set-Cookie` 헤더의 속성이 됩니다. 속성은 브라우저가 쿠키를 언제 보내고 누가 읽을 수 있는지를 정합니다.

속성을 잘못 고르면 쿠키가 교차 사이트 요청에 실려 가거나 스크립트에 읽힙니다. 속성 필드는 `HttpOnly`, `Secure`, `SameSite`, `Expires`, `MaxAge`, `Path`, `Domain` 입니다.

`http.Cookie` 는 응답의 `Set-Cookie` 헤더에 실리는 쿠키를 나타냅니다[^cookie-doc].

### SameSite 모드

`SameSite` 는 브라우저가 이 쿠키를 교차 사이트 요청에 실어 보내지 못하게 하는 속성입니다. Go 문서는 교차 출처 정보 유출 위험을 줄이고 CSRF 공격에 일부 보호를 준다고 설명합니다[^samesite-doc]. Go 1.11 에서 추가됐고 문서는 IETF 초안 draft-ietf-httpbis-cookie-same-site-00 을 참조합니다.

값은 네 가지이고, `Cookie.String()` 이 만드는 헤더 조각은 다음과 같았습니다.

| 상수 | 출력되는 속성 |
|------|---------------|
| `SameSiteDefaultMode` | 속성 없음 |
| `SameSiteLaxMode` | `SameSite=Lax` |
| `SameSiteStrictMode` | `SameSite=Strict` |
| `SameSiteNoneMode` | `SameSite=None` |

`SameSite` 필드를 비워 두면 값은 0 이라 어느 모드도 아닙니다. 이때 `SameSite` 속성이 헤더에 아예 붙지 않았습니다.

### MaxAge 의 세 갈래

`MaxAge` 는 세 가지로 갈립니다[^cookie-src].

- 0 이면 `Max-Age` 속성을 붙이지 않습니다.
- 0 보다 작으면 쿠키를 지금 삭제합니다. 헤더에는 `Max-Age=0` 으로 나갑니다.
- 0 보다 크면 그 초만큼의 수명입니다.

go1.25.1 에서 돌려 확인한 헤더입니다.

```bash
# 결과 (go1.25.1, Cookie.String())
MaxAge=0    -> a=b
MaxAge=-1   -> a=b; Max-Age=0
MaxAge=3600 -> a=b; Max-Age=3600
```

### HttpOnly 와 Secure

`HttpOnly` 와 `Secure` 는 불리언 필드입니다. 켜면 `Set-Cookie` 에 `HttpOnly; Secure` 가 붙습니다.

net/http 문서에는 이 속성이 브라우저에서 하는 일의 설명이 없습니다. 동작은 RFC 6265 로 확인했습니다.

- `Secure`: 브라우저가 TLS 같은 보안 채널로 보내는 요청에만 쿠키를 실어 보냅니다[^rfc-secure].
- `HttpOnly`: 스크립트에 쿠키를 보여 주는 비 HTTP API 에서 쿠키를 빼 줍니다[^rfc-httponly].

두 속성은 서로 독립이라 함께 쓸 수 있습니다. 같은 RFC 는 `Secure` 가 지키는 것이 기밀성뿐이라고도 적습니다. 능동적인 네트워크 공격자는 비보안 채널에서 `Secure` 쿠키를 덮어써 무결성을 해칠 수 있습니다[^rfc-secure].



## 3. 최소 예제와 한계

> 서명 쿠키 로그인은 서버 저장소가 필요 없는 대신, 발급한 쿠키를 만료 전에 무효로 만들 수 없습니다. 구분자 처리와 키 관리도 코드에서 챙깁니다.

### 최소 예제

아래 서버는 `/login` 에서 서명한 쿠키를 발급하고 `/me` 에서 검증합니다. 서명 대상은 `사용자|만료시각` 입니다. 예제 키는 설명용 문자열이고, 실제로는 환경변수나 시크릿에서 읽습니다.

```go
package main

import (
	"crypto/hmac"
	"crypto/sha256"
	"encoding/base64"
	"errors"
	"fmt"
	"log"
	"net/http"
	"strconv"
	"strings"
	"time"
)

var key = []byte("replace-with-32-random-bytes-from-env") // 실제로는 환경변수·시크릿에서 읽는다

func sign(user string, exp time.Time) string {
	msg := user + "|" + strconv.FormatInt(exp.Unix(), 10)
	mac := hmac.New(sha256.New, key)
	mac.Write([]byte(msg))
	sig := base64.RawURLEncoding.EncodeToString(mac.Sum(nil))
	return base64.RawURLEncoding.EncodeToString([]byte(msg)) + "." + sig
}

func verify(value string, now time.Time) (string, error) {
	msgB64, sigB64, ok := strings.Cut(value, ".")
	if !ok {
		return "", errors.New("malformed")
	}
	msg, err := base64.RawURLEncoding.DecodeString(msgB64)
	if err != nil {
		return "", errors.New("malformed")
	}
	got, err := base64.RawURLEncoding.DecodeString(sigB64)
	if err != nil {
		return "", errors.New("malformed")
	}
	mac := hmac.New(sha256.New, key)
	mac.Write(msg)
	if !hmac.Equal(got, mac.Sum(nil)) {
		return "", errors.New("bad signature")
	}
	user, expStr, ok := strings.Cut(string(msg), "|")
	if !ok {
		return "", errors.New("malformed")
	}
	exp, err := strconv.ParseInt(expStr, 10, 64)
	if err != nil || now.Unix() > exp {
		return "", errors.New("expired")
	}
	return user, nil
}

func login(w http.ResponseWriter, r *http.Request) {
	exp := time.Now().Add(time.Hour)
	http.SetCookie(w, &http.Cookie{
		Name:     "session",
		Value:    sign("alice", exp),
		Path:     "/",
		Expires:  exp,
		HttpOnly: true,
		Secure:   true,
		SameSite: http.SameSiteLaxMode,
	})
}

func me(w http.ResponseWriter, r *http.Request) {
	c, err := r.Cookie("session")
	if err != nil {
		http.Error(w, "no session", http.StatusUnauthorized)
		return
	}
	user, err := verify(c.Value, time.Now())
	if err != nil {
		http.Error(w, err.Error(), http.StatusUnauthorized)
		return
	}
	fmt.Fprintln(w, user)
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("POST /login", login)
	mux.HandleFunc("GET /me", me)
	log.Fatal(http.ListenAndServe(":8080", mux))
}
```

이 예제는 Go 1.25.1 에서 `go vet` 과 `go build` 를 통과했습니다. `httptest` 로 두 핸들러를 돌려 아래를 확인했습니다. 로그인 응답의 속성은 `Path=/; Expires=…; HttpOnly; Secure; SameSite=Lax` 순서였습니다.

| 요청 | 결과 |
|------|------|
| 로그인으로 받은 쿠키로 `/me` | 200, `alice` |
| 메시지를 `bob` 으로 바꾼 쿠키 | 401, `bad signature` |
| 만료 시각만 1년 늘린 쿠키 | 401, `bad signature` |
| 다른 키로 서명한 쿠키 | 401, `bad signature` |
| 만료 시각이 1분 전인 쿠키 | 401, `expired` |
| 쿠키 없음 | 401, `no session` |

### 로그아웃 뒤에도 남는 쿠키

서버가 세션을 저장하지 않으니 이미 발급한 쿠키를 만료 전에 무효로 만들 방법이 없습니다. 로그아웃은 `MaxAge: -1` 로 브라우저의 쿠키를 지울 뿐입니다. 이때 응답 헤더는 `session=; Path=/; Max-Age=0` 이었습니다.

로그아웃 전에 받아 둔 쿠키 값을 그대로 다시 보내면 `/me` 는 계속 200 과 `alice` 를 돌려줬습니다. 탈취된 쿠키를 막으려면 키를 바꾸거나 서버 쪽 폐기 목록이 필요합니다. 폐기 목록은 저장소를 되돌려 놓는 일이라 서명 쿠키의 이점이 줄어듭니다.

### 구분자가 사용자 값에 들어가면

예제는 `strings.Cut` 으로 첫 `|` 에서 메시지를 자릅니다. 사용자 값에 `|` 가 들어 있으면 파싱이 어긋납니다. `alice|9999999999` 라는 이름으로 서명한 쿠키는 서명은 맞지만 `/me` 가 401 과 `expired` 를 돌려줬습니다. 첫 `|` 뒤가 `9999999999|…` 라서 숫자로 읽히지 않기 때문입니다.

서명을 위조한 것이 아니라 서버가 만든 쿠키를 서버가 잘못 읽은 경우입니다. 사용자 값에 `|` 를 허용하지 않거나, 값 앞에 길이를 접두해 경계를 정하거나, 만료 시각을 마지막 `|` 로 잘라 읽습니다. 마지막 `|` 로 자르면 같은 메시지에서 사용자 `alice|9999999999` 와 만료 시각 `1800000000` 이 각각 나왔습니다.

### 키 교체

키 교체는 서명을 새 키로 만들되 검증은 현재 키와 이전 키를 모두 시도하는 방식이 흔합니다. 이 방식은 Go 문서에 나오는 내용이 아니라 일반적인 설계라서 돌려 보지 않았고, 공식 근거도 붙이지 않았습니다.

### 흔한 함정

- 서명 비교를 `==` 로 하면 타이밍 부채널이 열립니다. `hmac.Equal` 을 씁니다.
- 만료 시각을 서명 밖에 두면 클라이언트가 늘려 쓸 수 있습니다. 서명 대상 메시지에 포함합니다.
- 서명만으로는 비밀이 지켜지지 않습니다. 비밀번호나 개인정보를 쿠키에 담지 않습니다.
- 키를 소스에 적지 않습니다. 환경변수나 시크릿 저장소에서 읽습니다.
- `SameSite` 를 비워 두면 헤더에 속성이 붙지 않습니다. 모드를 코드에서 명시합니다.
