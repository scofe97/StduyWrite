# SSE·Flusher·ResponseController

---

> Go 서버가 SSE 스트림을 끊김 없이 보내려면 쓸 때마다 `Flush` 하고, 연결의 쓰기 기한을 풀고, 프록시 버퍼링과 유휴 끊김을 막아야 합니다. 이 편은 그 Go 쪽 구현을 다룹니다.

## 핵심 요약

> 일반 핸들러처럼 쓰기만 하면 이벤트는 핸들러가 끝나야 도착합니다. `ResponseController` 로 Flush 하고 쓰기 기한을 푼 뒤, 프록시용 헤더와 주기적인 주석 줄을 더합니다.

SSE(Server-Sent Events)는 응답을 끝내지 않고 이벤트를 계속 흘려보내는 HTTP 응답입니다. 프로토콜과 이벤트 형식은 [Spring 편](../../../../09_spring/03_network/realtime/02-01.SSE%20원리와%20Spring%20구현.md)이 설명하므로 다시 풀지 않습니다.

`Server.WriteTimeout` 의 동작 원리는 [03-02](./03-02.Server%20%ED%83%80%EC%9E%84%EC%95%84%EC%9B%83%C2%B7Shutdown.md) 가 다룹니다. 이 편은 그 값이 스트림을 자르는 장면과 푸는 방법을 봅니다.

이 편은 Flush 가 필요한 이유, 쓰기 기한 풀기, 프록시 뒤의 버퍼링과 ping, 완성 예제와 함정을 차례로 다룹니다.



## 1. Flush 와 Controller

> `ResponseWriter` 는 쓴 데이터를 버퍼에 모았다가 핸들러가 끝나거나 버퍼가 차면 내보냅니다. SSE 핸들러는 이벤트마다 Flush 로 버퍼를 비워야 합니다.

### Flush 가 없을 때의 문제

대시보드에 지표를 밀어 주려고 `fmt.Fprintf(w, ...)` 만 하면 이벤트가 브라우저에 도착하지 않습니다. 쓰기는 버퍼에만 쌓이기 때문입니다.

go1.25.1 에서 핸들러가 `data: a` 를 쓰고 3초 잠든 뒤 `data: b` 를 쓰게 해 보았습니다. 두 이벤트는 `curl -N` 에 3초 뒤 한꺼번에 도착했고, 첫 바이트까지 3.0초가 걸렸습니다.

첫 이벤트 뒤에 Flush 를 넣으면 같은 핸들러의 첫 바이트가 0.0004초에 도착했습니다. 두 번째 이벤트는 여전히 3초 뒤였습니다.

### Flusher 와 ResponseController

`http.Flusher` 의 `Flush()` 가 버퍼를 비웁니다. 기본 HTTP/1.x 와 HTTP/2 의 `ResponseWriter` 는 이 인터페이스를 구현합니다. 래퍼는 구현하지 않을 수 있어 런타임에 확인해야 합니다[^flusher-src].

Go 1.20 에서 `http.NewResponseController(w)` 가 들어왔습니다[^api-120]. `rc.Flush()` 는 같은 일을 하고 오류를 돌려줍니다. 지원하지 않는 `ResponseWriter` 이면 `ErrNotSupported` 와 일치하는 오류가 나옵니다[^rc-src]. Go 1.20 보다 오래된 코드는 `f, ok := w.(http.Flusher)` 로 단언한 뒤 `f.Flush()` 를 부릅니다.

`ResponseWriter` 의 선택 기능을 넓히는 설계 이유는 Learning Go 정독 노트 [13-04](../../../book/lgo_learning-go/13-04.net-http%20%EB%8A%94%20%ED%83%80%EC%9E%84%EC%95%84%EC%9B%83%EC%9D%84%20%EC%A7%81%EC%A0%91%20%EC%A0%95%ED%95%98%EA%B3%A0%20%EB%AF%B8%EB%93%A4%EC%9B%A8%EC%96%B4%EB%8A%94%20Handler%20%EB%A5%BC%20%EA%B0%90%EC%8B%B8%EB%A9%B0%20slog%20%EB%A1%9C%20%EA%B5%AC%EC%A1%B0%ED%99%94%20%EB%A1%9C%EA%B7%B8%EB%A5%BC%20%EB%82%A8%EA%B9%81%EB%8B%88%EB%8B%A4.md)가 설명합니다.

### 래퍼와 Unwrap

미들웨어가 `ResponseWriter` 를 struct 로 감싸면 `.(http.Flusher)` 단언이 실패합니다. 감싼 값이 `Flush` 를 직접 구현하지 않기 때문입니다.

감싼 값에 `Unwrap() http.ResponseWriter` 가 있으면 컨트롤러가 원래 writer 까지 따라갑니다[^rc-src]. 세 가지 writer 로 같은 핸들러에서 돌려 본 결과는 다음과 같습니다.

| 핸들러가 받은 writer | `.(http.Flusher)` 단언 | `rc.Flush()` 결과 |
|---------------------|------------------------|-------------------|
| 원래 writer | 성공 | `nil` |
| 감싸고 `Unwrap` 없음 | 실패 | `feature not supported` (`ErrNotSupported` 와 일치) |
| 감싸고 `Unwrap` 있음 | 실패 | `nil` |

그래서 `ResponseWriter` 를 감싸는 미들웨어는 `Unwrap` 을 둡니다. `Unwrap` 이 있는 래퍼는 단언이 실패해도 `ResponseController` 로는 Flush 에 성공합니다.



## 2. 쓰기 기한 풀기와 연결 종료

> `Server.WriteTimeout` 은 서버 전체에 걸린 값이라 스트림 핸들러가 길게 이어지면 연결이 잘립니다. 연결별로 `SetWriteDeadline(time.Time{})` 를 불러 그 연결의 기한만 풉니다.

### WriteTimeout 이 스트림을 자르는 장면

`WriteTimeout` 은 서버 전체에 걸리고, 소스 주석이 핸들러가 요청별로 정할 수 없다고 적습니다[^wt-src]. 응답이 끝나지 않는 SSE 는 이 값에 그대로 걸립니다.

`WriteTimeout` 6초, 이벤트 2초 간격, ping 5초 간격으로 서버 두 개를 띄워 `curl -N -m 14` 로 받았습니다. 한쪽은 쓰기 기한을 풀지 않았습니다.

- 기한을 풀지 않은 서버: 이벤트 2개와 ping 1개를 받고 연결이 끊겼습니다(curl 종료 코드 18). 서버 로그에는 `flush loop: write tcp ...: i/o timeout` 이 남았습니다.
- 기한을 푼 서버: 이벤트 6개와 ping 2개를 받고, 14초 제한으로 curl 이 끝났습니다(종료 코드 28).

### 연결별로 기한 풀기

`rc.SetWriteDeadline(time.Time{})` 는 그 연결의 쓰기 기한을 없앱니다. 영값은 기한 없음을 뜻합니다[^rc-deadline]. 서버가 요청마다 쓰기 기한을 다시 거는 방식은 03-02 가 설명하므로, 스트림 핸들러 안에서 풉니다.

`WriteTimeout` 자체를 키우거나 끄면 스트림이 아닌 엔드포인트의 보호까지 함께 약해집니다. 스트림 엔드포인트만 연결별로 푸는 쪽이 낫습니다.

### 끊긴 클라이언트 알아채기

탭을 닫은 클라이언트의 연결을 서버가 모르면 고루틴과 타이머가 계속 남습니다. `r.Context().Done()` 을 핸들러의 `select` 에 넣으면 연결이 닫힐 때 루프를 빠져나와 타이머를 정리합니다.

쓰기 오류도 같은 목적입니다. `Fprintf` 가 돌려주는 error 와 `Flush` 의 error 를 확인해 루프를 끝냅니다. 앞의 실험에서 `curl` 이 14초 뒤 연결을 닫자 서버 로그에 `client gone after id=7` 이 남았습니다.

클라이언트는 닫힌 연결에 다시 접속합니다. 서버가 HTTP 204 No Content 로 답하면 재연결이 멈춥니다[^spec-204].



## 3. 프록시 뒤의 버퍼링과 ping

> Flush 해도 사이에 낀 프록시가 응답을 모으거나 유휴 연결을 끊을 수 있습니다. nginx 는 응답 헤더 한 줄로 버퍼링을 끄고, 주석 줄을 주기적으로 보내 끊김을 막습니다.

### 프록시가 응답을 모을 때

Go 문서는 클라이언트가 HTTP 프록시로 연결돼 있으면 Flush 한 데이터가 응답이 끝나서야 도착할 수 있다고 적습니다[^flusher-src]. 서버 쪽에서 이 한계를 없앨 수는 없습니다.

nginx 뒤에 두는 경우의 기본값은 `proxy_buffering on` 이라 이벤트가 모여서 나갑니다. 응답 헤더 `X-Accel-Buffering: no` 로 그 응답만 버퍼링을 끌 수 있습니다[^nginx-doc].

### 주석 줄로 유휴 끊김 막기

`:` 로 시작하는 줄은 SSE 의 주석이라 클라이언트가 무시합니다. WHATWG 규격은 일부 오래된 프록시가 짧은 타임아웃 뒤 연결을 끊는다며, 15초쯤마다 주석 줄을 보내라고 권합니다[^spec-note].

`proxy_read_timeout` 의 기본값은 60초입니다. 서버가 그 시간 동안 아무것도 보내지 않으면 nginx 가 연결을 닫습니다[^nginx-doc]. ping 간격은 이 값보다 짧게 둡니다.

nginx 를 실제로 띄워 버퍼링과 타임아웃을 재 보지는 않았습니다. 이 절의 nginx 동작은 공식 문서에 근거한 것입니다.



## 4. 완성 예제와 함정

> 아래 서버는 앞의 세 절을 한 핸들러에 모은 것입니다. 함정은 대부분 Flush 와 헤더 순서에서 생깁니다.

### 최소 예제

`/events` 가 2초마다 `tick` 이벤트를, 15초마다 ping 을 보냅니다. 서버는 `WriteTimeout` 10초를 두지만 이 핸들러가 연결의 쓰기 기한을 풉니다.

```go
package main

import (
	"fmt"
	"log"
	"net/http"
	"time"
)

func events(w http.ResponseWriter, r *http.Request) {
	rc := http.NewResponseController(w)

	// 서버 전체 WriteTimeout 이 있어도 이 연결만 쓰기 기한을 푼다.
	if err := rc.SetWriteDeadline(time.Time{}); err != nil {
		log.Printf("write deadline: %v", err)
	}

	h := w.Header()
	h.Set("Content-Type", "text/event-stream")
	h.Set("Cache-Control", "no-cache")
	h.Set("X-Accel-Buffering", "no")
	w.WriteHeader(http.StatusOK)
	if err := rc.Flush(); err != nil {
		// 200 상태 줄은 이미 나갔으므로 http.Error 로 500 을 쓸 수 없다.
		log.Printf("flush: %v", err)
		return
	}

	events := time.NewTicker(2 * time.Second)
	defer events.Stop()
	ping := time.NewTicker(15 * time.Second)
	defer ping.Stop()

	id := 0
	for {
		select {
		case <-r.Context().Done():
			return
		case <-ping.C:
			if _, err := fmt.Fprint(w, ": ping\n\n"); err != nil {
				return
			}
		case t := <-events.C:
			id++
			if _, err := fmt.Fprintf(w, "id: %d\nevent: tick\ndata: %s\n\n", id, t.Format(time.RFC3339)); err != nil {
				return
			}
		}
		if err := rc.Flush(); err != nil {
			return
		}
	}
}

func main() {
	mux := http.NewServeMux()
	mux.HandleFunc("GET /events", events)
	srv := &http.Server{Addr: ":8080", Handler: mux, ReadHeaderTimeout: time.Minute, WriteTimeout: 10 * time.Second}
	log.Fatal(srv.ListenAndServe())
}
```

브라우저의 `EventSource` 는 두 경우에 연결을 실패로 처리합니다[^spec-fail]. 응답 상태가 200 이 아닌 경우와 `Content-Type` 이 `text/event-stream` 이 아닌 경우입니다. 예제는 두 조건을 모두 맞춥니다.

이 예제는 Go 1.25.1 에서 `go vet` 과 `go build` 를 통과했습니다. `curl -N` 으로 받은 결과는 아래 「직접 돌려 확인한 것」에 적었습니다.

### 흔한 함정

- 이벤트 끝의 빈 줄을 빼면 클라이언트가 이벤트를 전달하지 않습니다. 줄 끝은 `\n\n` 입니다.
- Flush 를 한 번만 하면 첫 이벤트만 도착합니다. 쓸 때마다 Flush 합니다.
- 헤더를 쓴 뒤에는 상태 코드를 바꿀 수 없습니다. `WriteHeader` 와 Flush 뒤에 `http.Error(w, "boom", 500)` 를 불러 보니 응답 상태는 그대로 200 이었습니다. 서버 로그에는 `http: superfluous response.WriteHeader call` 이 남았고, 본문 `boom` 이 스트림에 그대로 붙었습니다.
- 그래서 예제는 Flush 에 실패하면 로그만 남기고 돌아갑니다.
- 미들웨어가 래퍼를 씌우면 `Flusher` 가 가려집니다. 앞 절의 표처럼 `Unwrap` 을 둡니다.
- `r.Context().Done()` 을 보지 않으면 클라이언트가 떠난 뒤에도 고루틴과 타이머가 남습니다.

### 직접 돌려 확인한 것

go1.25.1(darwin/arm64)에서 위 예제를 그대로 `WriteTimeout` 10초로 띄우고 `curl -N` 으로 13초 동안 받았습니다. 이벤트 6개가 2초 간격으로 끊기지 않고 10초를 넘겨 이어졌고, 13초 제한으로 curl 이 끝났습니다.

`WriteTimeout` 이 없을 때 같은 코드가 끊기지 않는지는 이 편에서 따로 대조하지 않았습니다. 2절의 실험은 `WriteTimeout` 이 있는 서버에서 기한을 풀었을 때와 풀지 않았을 때를 비교한 것입니다.

HTTP/2 에서의 Flush 와 기한 동작은 확인하지 않았습니다.
