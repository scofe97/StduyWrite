# Go 제네릭은 일부러 작게 만들었고 성능을 위해 바꿀 도구가 아닙니다

---

> Learning Go 8장 끝입니다. Go 제네릭에서 빠진 기능과 그 이유, 제네릭이 바꾼 관용과 성능에 대한 현실적인 기대, 제네릭을 쓰기 시작한 표준 라이브러리, 앞으로 열릴 수 있는 합 타입을 다루고 장 끝 연습 문제를 풉니다.

## 핵심 요약

> 이 편이 매달린 하나의 생각은 Go 제네릭이 읽기 쉬움을 지키려고 기능을 덜어 냈고, 빠르게 하려고 쓰는 도구가 아니라는 것입니다.

Go 제네릭에는 연산자 오버로딩, 메서드의 추가 타입 매개변수, 가변 타입 매개변수, 특수화·커링·메타프로그래밍이 없습니다. 그래서 사용자 정의 컨테이너를 `[]` 로 인덱싱할 수 없습니다. Map·Reduce 를 메서드 사슬로 이을 수도 없습니다. 원문은 연산자 오버로딩을 뺀 이유로 Go 가 피하려는 가독성 문제를 듭니다. 매개변수화된 메서드를 뺀 이유는 Type Parameters Proposal 에 미룹니다.

원문은 인터페이스 매개변수를 성능 때문에 제네릭으로 바꾸지 말라고 권합니다. 지금 컴파일러는 구체 타입마다가 아니라 바탕 타입마다 함수를 만들고 포인터 타입은 모두 함수 하나를 함께 씁니다. 함께 쓰는 함수에는 넘어온 타입을 구별하는 실행 중 조회가 더해지는데, 원문은 이것을 느려지는 원인으로 봅니다. 표준 라이브러리는 Go 1.21 부터 `slices`·`maps`·`sync.OnceValue` 같은 제네릭 도구를 들였으니 직접 쓰지 말고 그것을 씁니다.



## 학습 목표

> 이 편을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. Go 제네릭에서 빠진 기능들과 연산자 오버로딩을 빼 원문의 이유를 말할 수 있습니다.
2. 메서드에 타입 매개변수를 더할 수 없어 Map·Reduce 를 메서드 사슬로 잇지 못하는 까닭을 코드로 보일 수 있습니다.
3. 인터페이스 매개변수를 제네릭으로 바꿔도 빨라지지 않을 수 있는 이유를 Go 의 구현 방식으로 설명할 수 있습니다.
4. 제네릭을 쓰는 표준 라이브러리 함수를 알고, 직접 구현하지 말아야 할 때를 판단할 수 있습니다.
5. 연습 문제 셋을 풀며 숫자 제약, 타입 요소와 메서드를 함께 둔 제약, 제네릭 연결 리스트를 쓸 수 있습니다.



## 1. 빠진 기능들 — Go 제네릭은 일부러 작습니다

> Go 는 연산자 오버로딩, 메서드의 추가 타입 매개변수, 가변 타입 매개변수를 넣지 않았습니다. 원문은 연산자 오버로딩을 뺀 이유로 연산자 수, 오버로딩이 없다는 점, 그리고 가독성을 듭니다.

원문은 Go 가 여전히 작고 집중된 언어이며, Go 제네릭 구현에는 다른 언어의 제네릭에 있는 기능이 많이 빠져 있다고 말합니다. 이 절은 첫 구현에 들어가지 않은 기능들을 설명합니다.

### 연산자 오버로딩은 없습니다

08-02 §3 에서 사용자 정의 타입과 내장 타입 모두에 동작하는 트리 하나를 만들었습니다. 원문은 Python·Ruby·C++ 같은 언어가 이 문제를 다르게 푼다고 말합니다. 사용자 정의 타입이 연산자의 구현을 정할 수 있게 하는 연산자 오버로딩입니다. Go 는 이 기능을 더하지 않을 것입니다. 그래서 사용자 정의 컨테이너 타입을 `range` 로 돌거나 `[]` 로 인덱싱할 수 없다고 원문은 말합니다.

원문 밖의 버전 차이가 하나 있습니다. Go 1.23 부터는 `func(yield func(T) bool)` 모양의 함수, 곧 `iter.Seq[T]` 를 `range` 로 돌 수 있습니다. 이 노트를 쓰면서 연습 문제 3 의 연결 리스트에 `All() iter.Seq[T]` 메서드를 더하니 `for v := range l.All()` 로 원소를 차례로 꺼낼 수 있었습니다. 연산자 오버로딩은 여전히 없지만, 사용자 정의 컨테이너를 `range` 로 도는 길은 이 방식으로 열렸습니다. `[]` 인덱싱은 지금도 안 됩니다.

원문이 드는 연산자 오버로딩을 뺀 이유는 셋입니다. Go 에는 연산자가 놀랄 만큼 많습니다. Go 에는 함수나 메서드 오버로딩도 없고, 타입마다 다른 연산자 기능을 지정할 방법이 필요해집니다.

또 연산자 오버로딩은 개발자가 기호에 영리한 뜻을 지어내면서 따라가기 어려운 코드를 낳을 수 있습니다. C++ 에서 `<<` 는 어떤 타입에서는 "비트를 왼쪽으로 민다"이고, 다른 타입에서는 "오른쪽 값을 왼쪽에 쓴다"입니다. 원문은 이런 것이 Go 가 피하려는 가독성 문제라고 말합니다. Java 가 사용자 정의 연산자 오버로딩을 아예 허용하지 않고 `String` 의 `+` 같은 것만 언어에 내장한 것과 같은 판단입니다. 이 비교는 원문 밖입니다.

### 메서드에는 타입 매개변수를 더할 수 없습니다

첫 구현에서 빠진 또 하나의 쓸모 있는 기능은 메서드의 추가 타입 매개변수입니다. 08-01 §3 의 Map·Reduce·Filter 를 돌아보면 이것들을 메서드로 두면 좋겠다고 생각할 수 있습니다.

```go
type functionalSlice[T any] []T

// THIS DOES NOT WORK
func (fs functionalSlice[T]) Map[E any](f func(T) E) functionalSlice[E] {
	out := make(functionalSlice[E], len(fs))
	for i, v := range fs {
		out[i] = f(v)
	}
	return out
}

// THIS DOES NOT WORK
func (fs functionalSlice[T]) Reduce[E any](start E, f func(E, T) E) E {
	out := start
	for _, v := range fs {
		out = f(out, v)
	}
	return out
}
```

이렇게 쓸 수 있으면 좋겠지만요.

```go
var numStrings = functionalSlice[string]{"1", "2", "3"}
sum := numStrings.Map(func(s string) int {
	v, _ := strconv.Atoi(s)
	return v
}).Reduce(0, func(acc int, cur int) int {
	return acc + cur
})
```

원문은 함수형 프로그래밍 애호가에게는 아쉽게도 이것이 동작하지 않는다고 말합니다. 메서드 호출을 사슬로 잇는 대신 함수 호출을 중첩하거나, 훨씬 읽기 쉬운 방식으로 함수를 하나씩 부르며 중간 값을 변수에 대입해야 합니다. 원문은 매개변수화된 메서드를 뺀 이유를 Type Parameters Proposal 이 자세히 다룬다고 소개합니다. Java 의 `Stream<T>.map(Function<T, R>)` 은 메서드가 자기 타입 매개변수 `R` 을 따로 가지는 바로 그 기능이라, Go 에서는 이 모양을 쓸 수 없습니다. 이 비교는 원문 밖입니다.

### 가변 타입 매개변수와 그 밖의 빠진 기능

Go 에는 가변 타입 매개변수도 없습니다. 05-01 에서 본 대로 개수가 정해지지 않은 매개변수를 받으려면 마지막 매개변수 타입을 `...` 로 시작합니다. 하지만 `string` 과 `int` 가 번갈아 오는 식의 타입 패턴을 가변 매개변수에 지정할 방법은 없습니다. 가변 변수는 모두 선언된 타입 하나에 맞아야 하고, 그 타입은 제네릭일 수도 아닐 수도 있습니다.

원문은 그 밖에 더 난해한 빠진 기능들을 나열합니다.

| 기능 | 원문의 설명 |
|------|------|
| 특수화(Specialization) | 함수나 메서드를 제네릭 판 말고 타입별 판 하나 이상으로 오버로딩합니다. Go 에는 오버로딩이 없어 고려 대상이 아닙니다 |
| 커링(Currying) | 다른 제네릭 함수나 타입의 타입 매개변수 일부를 지정해 부분적으로 인스턴스화합니다 |
| 메타프로그래밍 | 컴파일 시점에 돌아 실행 시점에 돌 코드를 만드는 코드를 지정합니다 |



## 2. 제네릭이 바꾼 관용과 성능에 대한 기대

> 제네릭으로 `float64` 로 모든 숫자를 받는 관행은 끝나지만 옛 코드를 서둘러 바꿀 필요는 없습니다. 인터페이스 매개변수를 성능 때문에 제네릭으로 바꾸지 말라고 원문은 권하며, 그 이유는 Go 가 바탕 타입 단위로 함수를 만드는 방식에 있습니다.

원문은 제네릭이 Go 를 관용적으로 쓰는 조언 일부를 분명히 바꾼다고 말합니다. 모든 숫자 타입을 `float64` 로 나타내는 관행은 끝납니다. 자료구조나 함수 매개변수의 정해지지 않은 타입에는 `interface{}` 대신 `any` 를 씁니다. 서로 다른 slice 타입을 함수 하나로 다룰 수 있습니다. 하지만 모든 코드를 당장 타입 매개변수로 바꿀 필요는 없다고 원문은 말합니다. 새 디자인 패턴이 만들어지고 다듬어지는 동안에도 옛 코드는 그대로 동작합니다.

원문은 제네릭이 성능에 주는 장기 영향을 판단하기는 아직 이르다고 말합니다. 이 글을 쓸 때 컴파일 시간에는 영향이 없었습니다. Go 1.18 컴파일러는 이전 판보다 느렸지만 Go 1.20 컴파일러가 이 문제를 풀었습니다. 실행 시간 영향에 대한 연구도 있었습니다. Vicent Marti 는 제네릭이 코드를 느리게 만드는 경우와 그 구현 세부를 자세히 다룬 블로그 글을 썼고, 반대로 Eli Bendersky 는 제네릭이 정렬 알고리즘을 빠르게 한다는 블로그 글을 썼습니다.

### 인터페이스 매개변수를 성능 때문에 제네릭으로 바꾸지 않습니다

원문은 특히 성능을 높이려고 인터페이스 매개변수를 가진 함수를 제네릭 타입 매개변수를 가진 함수로 바꾸지 말라고 말합니다.

```go
type Ager interface {
	age() int
}

func doubleAge(a Ager) int {
	return a.age() * 2
}

func doubleAgeGeneric[T Ager](a T) int {
	return a.age() * 2
}
```

원문은 이 사소한 함수를 제네릭으로 바꾸면 Go 1.20 에서 호출이 약 30% 느려졌다고 말합니다. 사소하지 않은 함수에서는 의미 있는 성능 차이가 없었다고 덧붙입니다. 벤치마크는 책 8장 저장소의 `sample_code/perf` 에 있습니다.

이 노트를 쓰면서 go1.25.1 · Apple M3 에서 두 함수를 인라인되지 않게 해 세 번씩 재 봤습니다. `doubleAge` 에 포인터를 담은 인터페이스를 넘기면 1.35~1.37ns, `doubleAgeGeneric` 에 같은 포인터를 넘기면 1.33~1.39ns, 값을 넘기면 1.33~1.35ns 로 차이가 측정 흔들림 안에 있었습니다. 원문의 벤치마크 코드를 그대로 쓴 것이 아니고 Go 버전과 CPU 도 달라서, 이 측정으로 원문의 1.20 수치를 반박할 수는 없습니다. 원문이 말한 대로 제네릭 구현이 성숙하면서 차이가 줄어들 수 있다는 정도로 읽습니다(원문 밖 측정).

### Go 는 바탕 타입마다 함수를 만들고 포인터는 함수 하나를 나눠 씁니다

원문은 이것이 다른 언어의 제네릭에 익숙한 개발자에게 놀라울 수 있다고 말합니다. 예를 들어 C++ 컴파일러는 추상 자료형에 쓴 제네릭을 이용해, 보통 실행 시점에 하던 일(어떤 구체 타입인지 알아내기)을 컴파일 시점으로 옮기고 구체 타입마다 고유한 함수를 만듭니다. 결과 바이너리는 커지지만 빨라집니다.

Vicent Marti 가 블로그 글에서 설명하듯, 지금 Go 컴파일러는 서로 다른 바탕 타입에 대해서만 고유한 함수를 만듭니다. 게다가 모든 포인터 타입은 만들어진 함수 하나를 함께 씁니다. 함께 쓰는 함수에 넘어온 서로 다른 타입을 구별하려고 컴파일러는 실행 중 조회를 더하고, 이것이 성능 저하를 부릅니다.

![Go 는 바탕 타입마다 함수를 만든다](./_assets/08-03.gc-shape.svg)

Java 제네릭은 타입 소거로 구현되어 `List<String>` 과 `List<Integer>` 가 실행 시점에 같은 `List` 코드를 씁니다. Go 는 C++ 처럼 모두 복제하지도 Java 처럼 모두 소거하지도 않고, 바탕 타입이 같은 타입끼리, 그리고 포인터 타입끼리 함수를 나눠 쓰는 중간 자리를 골랐다고 볼 수 있습니다. 이 비교와 해석은 원문 밖입니다.

원문은 제네릭 구현이 앞으로의 Go 판에서 성숙할수록 실행 성능이 나아질 것으로 기대하라고 말합니다. 언제나처럼 목표는 필요를 채울 만큼 빠르고 유지하기 쉬운 프로그램을 쓰는 것입니다. 코드를 재고 개선하려면 15장 「Using Benchmarks」에서 다룰 벤치마크와 프로파일링 도구를 쓰라고 합니다. 절 이름만 원문에 있고 장 번호는 노트가 찾아 붙였습니다.



## 3. 표준 라이브러리의 제네릭과 앞으로 열릴 기능

> Go 1.18 은 `any` 와 `comparable` 만 더한 보수적인 출발이었고, Go 1.21 부터 `slices`·`maps`·`sync.OnceValue` 같은 제네릭 함수가 들어왔습니다. 제네릭은 합 타입 같은 기능의 바탕이 될 수도 있습니다.

원문은 Go 1.18 의 첫 제네릭 출시가 아주 보수적이었다고 말합니다. universe 블록에 새 인터페이스 `any` 와 `comparable` 을 더했지만, 제네릭을 지원하려는 표준 라이브러리 API 변경은 없었습니다. 스타일 변경은 있었습니다. 표준 라이브러리의 `interface{}` 는 거의 모두 `any` 로 바뀌었습니다.

Go 커뮤니티가 제네릭에 익숙해지면서 변화가 더 보이기 시작했습니다. Go 1.21 부터 표준 라이브러리는 slice·map·동시성을 위한 흔한 알고리즘을 제네릭으로 구현한 함수들을 담습니다. 3장에서 `slices` 와 `maps` 패키지의 `Equal`·`EqualFunc` 를 다뤘습니다(03-01·03-02).

이 패키지들의 다른 함수도 slice 와 map 조작을 단순하게 해 줍니다. `slices` 패키지의 `Insert`·`Delete`·`DeleteFunc` 는 의외로 까다로운 slice 처리 코드를 직접 짜지 않게 해 줍니다. `maps.Clone` 은 Go 런타임을 이용해 map 의 얕은 복사를 더 빠르게 만듭니다.

원문은 「Run Code Exactly Once」에서 제네릭으로 한 번만 불리며 값 하나나 둘을 돌려주는 함수를 만드는 `sync.OnceValue` 와 `sync.OnceValues` 를 다룬다고 예고합니다. 원문은 직접 구현하기보다 이 패키지들의 함수를 쓰라고 권하며, 앞으로 표준 라이브러리에 제네릭을 쓰는 함수와 타입이 더 들어올 것이라고 내다봅니다.

### 합 타입이 열릴 수 있습니다

원문은 제네릭이 앞으로의 다른 기능의 바탕이 될 수 있다고 말합니다. 하나는 합 타입입니다. 타입 요소가 타입 매개변수에 들어갈 수 있는 타입을 지정하듯, 변수의 인터페이스에도 쓸 수 있다면 흥미로운 기능이 가능해집니다. 지금 Go 는 JSON 에서 흔한 상황, 곧 값 하나일 수도 값의 목록일 수도 있는 필드에서 곤란합니다. 제네릭이 있어도 이것을 다루는 유일한 방법은 `any` 타입 필드입니다.

합 타입이 더해지면 필드가 문자열이거나 문자열 slice 일 뿐 다른 것은 아니라고 지정하는 인터페이스를 만들 수 있습니다. 그러면 타입 스위치가 유효한 타입을 빠짐없이 나열해 타입 안전을 높일 수 있습니다.

원문은 이렇게 경계 있는 타입 집합을 지정하는 능력 덕에 Rust 와 Swift 를 비롯한 많은 현대 언어가 합 타입으로 열거형을 나타낸다고 말합니다. 07-02 §2 에서 본 Go 열거형 기능의 약점을 생각하면 매력적인 해법일 수 있지만, 이런 생각을 평가하고 탐구하는 데 시간이 걸릴 것이라고 원문은 덧붙입니다. Java 17 의 sealed interface 와 21 의 switch 패턴 매칭이 이 조합에 해당합니다. 이 비교는 원문 밖입니다.



## 연습 문제

> 원문 연습 문제 세 개를 `go1.25.1` 에서 풀고 `go vet` 까지 통과했습니다. 원문의 정답은 책의 Chapter 8 저장소의 `exercise_solutions` 에 있습니다.

### 1. 정수와 실수를 두 배로 만드는 제네릭 함수

넘어온 정수나 실수 값을 두 배로 만드는 제네릭 함수를 쓰고, 필요한 제네릭 인터페이스를 정의하는 문제입니다. 08-02 §1 의 `~` 붙은 정수 항에 실수 항을 더한 제약을 씁니다.

```go
type Number interface {
	~int | ~int8 | ~int16 | ~int32 | ~int64 |
		~uint | ~uint8 | ~uint16 | ~uint32 | ~uint64 | ~uintptr |
		~float32 | ~float64
}

func Double[T Number](v T) T {
	return v * 2
}
```

`Double(10)`, `Double(2.5)`, `Double(uint8(200))` 은 `20 5 144` 였습니다. 마지막 값은 400 이 `uint8` 범위를 넘어 256 을 뺀 값으로 넘친 것입니다. 상수 `2` 는 나열한 모든 타입에 담길 수 있어 08-02 §2 의 상수 규칙을 통과합니다. 이 풀이와 설명은 노트의 것입니다.

### 2. 타입 요소와 메서드를 함께 둔 Printable

`fmt.Stringer` 를 구현하고 바탕 타입이 `int` 나 `float64` 인 타입에 맞는 제네릭 인터페이스 `Printable` 을 정의합니다. 이 인터페이스를 만족하는 타입들을 정의하고, `Printable` 을 받아 `fmt.Println` 으로 화면에 찍는 함수를 씁니다.

```go
type Printable interface {
	~int | ~float64
	fmt.Stringer
}

type PrintInt int

func (pi PrintInt) String() string {
	return fmt.Sprintf("PrintInt(%d)", int(pi))
}

type PrintFloat float64

func (pf PrintFloat) String() string {
	return fmt.Sprintf("PrintFloat(%.2f)", float64(pf))
}

func PrintIt[T Printable](t T) {
	fmt.Println(t)
}
```

`PrintIt(PrintInt(5))` 와 `PrintIt(PrintFloat(3.5))` 는 `PrintInt(5)` 와 `PrintFloat(3.50)` 을 찍었습니다. 08-02 §1 의 `PrintableInt` 처럼 타입 요소와 메서드 요소를 한 인터페이스에 둔 모양입니다.

### 3. comparable 값을 담는 제네릭 연결 리스트

원소마다 비교 가능한 값과 다음 원소를 가리키는 포인터를 가진 제네릭 단일 연결 리스트를 씁니다. 구현할 메서드는 끝에 더하는 `Add(T)`, 지정한 위치에 넣는 `Insert(T, int)`, 값의 위치를 돌려주고 없으면 −1 인 `Index(T) int` 입니다.

```go
type Node[T comparable] struct {
	Value T
	Next  *Node[T]
}

type List[T comparable] struct {
	Head *Node[T]
	Tail *Node[T]
}

func (l *List[T]) Add(t T) {
	n := &Node[T]{Value: t}
	if l.Head == nil {
		l.Head = n
		l.Tail = n
		return
	}
	l.Tail.Next = n
	l.Tail = n
}

func (l *List[T]) Insert(t T, pos int) {
	n := &Node[T]{Value: t}
	if l.Head == nil {
		l.Head = n
		l.Tail = n
		return
	}
	if pos <= 0 {
		n.Next = l.Head
		l.Head = n
		return
	}
	cur := l.Head
	for i := 1; i < pos && cur.Next != nil; i++ {
		cur = cur.Next
	}
	n.Next = cur.Next
	cur.Next = n
	if cur == l.Tail {
		l.Tail = n
	}
}

func (l *List[T]) Index(t T) int {
	i := 0
	for cur := l.Head; cur != nil; cur = cur.Next {
		if cur.Value == t {
			return i
		}
		i++
	}
	return -1
}
```

`Add(5)`, `Add(10)`, `Insert(20, 0)`, `Insert(30, 2)`, `Insert(40, 100)` 뒤 리스트는 `20 5 30 10 40` 이었고, `Index` 로 20·30·40·99 를 찾으니 `0 2 4 -1` 이었습니다. `Index` 가 `cur.Value == t` 를 쓸 수 있는 것은 제약이 `comparable` 이기 때문입니다(08-01 §2). 리스트 길이를 넘는 위치는 끝에 붙이고 음수는 맨 앞에 넣도록 정했는데, 원문이 이 경계를 정하지 않아 노트가 고른 규칙입니다.
