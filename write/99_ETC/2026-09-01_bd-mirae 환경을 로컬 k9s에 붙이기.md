# bd-mirae 환경을 로컬 k9s에 붙이기 — kube context 등록 절차

---

> 사업개발팀 **bd-mirae**(= `bd-trb 3.0.5.1`) OpenShift 클러스터를 로컬 k9s에서 조회하려면, 클러스터의 관리자 kubeconfig를 가져와 로컬 `~/.kube/config`에 **컨텍스트 하나로 병합**해야 합니다. k9s는 자체 접속 설정을 갖지 않고 kubeconfig를 그대로 읽기 때문에, "k9s 설정"이라는 별도 단계는 존재하지 않습니다. 이 문서는 컨텍스트 이름을 `bd-tps-3.0.5.1`로 등록하는 이유, 병합 절차, 그리고 이 환경에서 특히 헷갈리는 지점(이름에 `tps`가 들어가지만 TPS 개발계가 아님, 80/443이 LoadBalancer로 안 잡힘)을 함께 정리합니다.

## 1. 전체 흐름

> 로컬에 이미 여러 클러스터가 등록돼 있으므로, 새 클러스터는 **덮어쓰기가 아니라 병합**으로 추가합니다. 병합 전 백업이 이 절차의 유일한 되돌릴 수 없는 지점입니다.

```
[bd-mirae 클러스터]                  [로컬 맥]
 OpenShift API                        ~/.kube/config
 10.255.28.46:6443                    (기존 컨텍스트 10개)
        │                                    │
        │ ① /etc/hosts 등록                   │
        │    (도메인 → IP 해석)                │
        │                                    │
        ├─ ② bastion SSH ────────────────────┤ ② 임시파일로 kubeconfig 획득
        │  10.255.28.221                      │    /tmp/bdmirae.conf
        │                                    │
        │                                    ├─ ③ 이름 rename
        │                                    │    → bd-tps-3.0.5.1-*
        │                                    │
        │                                    ├─ ④ --flatten 으로 병합
        │                                    │    (기존 컨텍스트 보존)
        │                                    │
        │                                    ├─ ⑤ 임시파일 삭제 (인증서 포함)
        │                                    │
        └─ ⑥ kubectl / k9s 조회 ─────────────┘
```

k9s는 ⑥ 단계에서 `KUBECONFIG` 환경변수가 가리키는 파일을 읽습니다. 로컬 셸에는 이미 `k9s: aliased to KUBECONFIG=$HOME/.kube/config k9s` 별칭이 걸려 있어, 병합만 끝나면 k9s 쪽에 추가 작업이 없습니다.



## 2. 기본 개념 — cluster · user · context 3분할

> kubeconfig는 접속 정보를 한 덩어리로 담지 않고 **`clusters` · `users` · `contexts` 세 배열로 나눠** 담습니다. 컨텍스트 하나가 동작하려면 세 블록이 모두 있어야 하지만, 세 개가 항상 같은 개수로 늘어나는 것은 아닙니다. 이 구조를 모르면 5절의 rename·병합 단계에서 무엇을 왜 바꾸는지 알 수 없습니다.

kubectl이 클러스터에 요청을 보내려면 두 가지를 알아야 합니다 — **어디로** 붙을지와 **누구로** 붙을지입니다. 이 둘을 하나로 합쳐 두면 조합을 바꿀 수 없으므로, 따로 정의하고 세 번째 블록이 조합을 가리키게 만든 구조입니다.

| 블록 | 답하는 질문 | 비유 | 담는 것 |
|------|-----------|------|--------|
| `cluster` | **어디로** 붙나 | 주소 | API 서버 URL + CA 인증서 |
| `user` | **누구로** 붙나 | 신분증 | 클라이언트 인증서·토큰 등 |
| `context` | 그 둘 중 **어느 조합**을 쓰나 | 북마크 | 위 두 블록의 **이름 참조만** |

### 세 블록이 이름으로 연결된다

context는 접속 정보를 하나도 갖지 않습니다. 이름 두 개를 참조하는 포인터일 뿐입니다.

```
  contexts:                          clusters:
  ┌─────────────────────────┐        ┌──────────────────────────────────┐
  │ name: bd-tps-3.0.5.1    │        │ name: bd-tps-3.0.5.1-cluster     │
  │   cluster: ─────────────┼───────▶│   server: https://api.mirae...   │
  │                         │        │           :6443                  │
  │                         │        │   certificate-authority-data:    │
  │                         │        │     (서버를 신뢰하는 근거)         │
  │                         │        └──────────────────────────────────┘
  │                         │        users:
  │                         │        ┌──────────────────────────────────┐
  │   user: ────────────────┼───────▶│ name: bd-tps-3.0.5.1-admin       │
  └─────────────────────────┘        │   client-certificate-data:       │
            ▲                        │     (내가 누구인지 증명)           │
            │                        │   client-key-data:               │
     kubectl --context               │     (그 증명의 개인키)             │
     에 넘기는 이름은 이것뿐            └──────────────────────────────────┘
```

`--context`에 넘기는 값은 **항상 context 이름**입니다. `-cluster`·`-admin`은 kubectl에 직접 넘기는 이름이 아니라, context가 내부적으로 참조하는 대상입니다.

접미사 `-cluster`·`-admin`은 **강제가 아니라 관례**입니다. kubectl은 문자열이 일치하는지만 봅니다. 그래서 이름이 한 글자라도 어긋나면, 컨텍스트는 `get-contexts` 목록에 멀쩡히 보이는데 조회만 실패하는 헷갈리는 실패 모드가 됩니다.

### 두 인증서의 방향이 반대다

이름이 비슷해 섞이기 쉬운데, 검증 방향이 서로 반대입니다.

| 필드 | 위치 | 검증 방향 | 유실 시 증상 |
|------|------|----------|------------|
| `certificate-authority-data` | `cluster` | **내가 서버를** 신뢰 | `x509: certificate signed by unknown authority` |
| `client-certificate-data` + `client-key-data` | `user` | **서버가 나를** 검증 | `Unauthorized` |

`user` 블록에 들어갈 수 있는 인증 형태는 여러 가지이고, 같은 파일 안에서 컨텍스트별로 달라도 됩니다.

| 인증 방식 | 필드 | 로컬 사용 예 |
|----------|------|------------|
| 클라이언트 인증서 | `client-certificate-data` + `client-key-data` | **`bd-tps-3.0.5.1` (이 환경)** |
| 베어러 토큰 | `token` | OpenShift `oc login` 기본 |
| 외부 플러그인 | `exec` | GKE (`gke_gcloud_auth_plugin`) |
| ID / PW | `username` + `password` | 거의 쓰지 않음 |

`~/.kube/`에 `gke_gcloud_auth_plugin_cache`가 있는 것은 다른 컨텍스트가 `exec` 방식을 쓰고 있다는 뜻입니다.

### 왜 나눠 놓았나 — cluster 하나에 user 여럿

이 구조의 값은 **조합을 자유롭게 만들 수 있다**는 점입니다. 같은 클러스터를 관리자 계정과 읽기전용 계정으로 각각 붙고 싶을 때, cluster 정의(주소·CA)를 중복해서 적지 않아도 됩니다.

```
클러스터 1개
      │
      ├─ cluster 블록 : 1개          ← 주소는 하나뿐이니 중복 불필요
      │
      ├─ user 블록    : 계정 수만큼
      │     ├─ ...-admin
      │     └─ ...-readonly
      │
      └─ context 블록 : 조합 수만큼
            ├─ ...-admin     → cluster + admin
            └─ ...-readonly  → cluster + readonly
```

그래서 **한 클러스터에 계정을 추가할 때는 `cluster` 블록을 복사하지 않습니다.** `user` + `context`만 추가합니다. cluster 블록을 중복 등록하면 주소·CA가 두 군데로 갈려, 나중에 주소가 바뀔 때 한쪽만 고치는 사고가 납니다.

반대 방향도 가능합니다 — 같은 인증서로 여러 클러스터에 붙는 구성이면 user 하나를 여러 context가 참조합니다.

### 참조 무결성 검증

세 블록의 개수가 맞는지, 참조가 실제로 연결되는지, 아무 context도 가리키지 않는 고아 항목이 없는지 한 번에 봅니다.

```bash
python3 - <<'PY'
import io, yaml, os
from collections import Counter
d = yaml.safe_load(io.open(os.path.expanduser('~/.kube/config'), encoding='utf-8').read())
cl = {c['name'] for c in d['clusters']}
us = {u['name'] for u in d['users']}
print('clusters=%d  users=%d  contexts=%d' % (len(cl), len(us), len(d['contexts'])))
for c in d['contexts']:
    ctx = c['context']
    flag = ('' if ctx.get('cluster') in cl else '  [MISSING cluster]') \
         + ('' if ctx.get('user') in us else '  [MISSING user]')
    print('%-34s -> %-34s %s%s' % (c['name'], ctx.get('cluster'), ctx.get('user'), flag))
cc = Counter(c['context'].get('cluster') for c in d['contexts'])
print('여러 context가 공유하는 cluster:', {k: v for k, v in cc.items() if v > 1} or 'none')
print('고아 cluster:', sorted(cl - {c['context'].get('cluster') for c in d['contexts']}) or 'none')
print('고아 user   :', sorted(us - {c['context'].get('user') for c in d['contexts']}) or 'none')
PY
```

`MISSING`이 뜨면 이름 참조가 끊긴 것이고, 고아 항목은 병합 과정에서 남은 잔재입니다. 개수가 `10 / 10 / 10`처럼 딱 맞는 것은 클러스터마다 계정을 하나씩만 등록했을 때의 결과이며, 3개가 항상 같아야 한다는 뜻은 아닙니다.

### 컨텍스트 하나를 손으로 추가할 때

파일을 통째로 병합하는 대신(5절) 항목만 붙여 넣으려면, **세 배열에 각각 하나씩** 넣습니다. 한 덩어리를 한 군데 붙이는 것이 아닙니다.

```yaml
# ① clusters: 배열 안에
  - cluster:
      certificate-authority-data: <base64>
      server: https://api.mirae.bd-mirae.trombone.okestro.cloud:6443
    name: bd-tps-3.0.5.1-cluster

# ② contexts: 배열 안에
  - context:
      cluster: bd-tps-3.0.5.1-cluster      # ← ①의 name 과 완전히 일치
      user: bd-tps-3.0.5.1-admin           # ← ③의 name 과 완전히 일치
    name: bd-tps-3.0.5.1

# ③ users: 배열 안에
  - name: bd-tps-3.0.5.1-admin
    user:
      client-certificate-data: <base64>
      client-key-data: <base64>
```

주의할 점 세 가지입니다.

- **들여쓰기가 문법이다.** 배열 항목은 스페이스 2개 + `- `, 하위 필드는 스페이스 6개입니다. 탭이 섞이면 파싱 자체가 실패합니다.
- **`current-context`는 건드리지 않는다.** 이 값을 바꾸면 다른 작업의 기본 클러스터가 함께 바뀝니다. 컨텍스트는 `--context` 플래그로 그때그때 지정합니다.
- **백업은 병합과 동일하게 필수다.** 복붙이 간단해 보여도 파일을 직접 편집하는 위험은 같습니다.

`context`에는 `namespace` 필드도 넣을 수 있습니다. 로컬 `kind-k8s-lab`에는 `default`가 지정돼 있고 `bd-tps-3.0.5.1`에는 없어서, 이 환경은 조회할 때마다 `-n`을 붙여야 합니다.

### 인증 방식이 다른 클러스터를 병합할 때 주의

5절의 rename 단계가 필요한 이유가 여기서 드러납니다. 내려받은 kubeconfig의 이름이 `kubernetes` / `kubernetes-admin` 같은 **일반적인 값**이면, 다른 kubeadm 클러스터를 나중에 병합할 때 이름이 충돌합니다. 로컬 `gcp-k8s` 컨텍스트가 실제로 그 이름을 쓰고 있어, 그 자리가 잠재적 충돌 지점입니다.

접미사 컨벤션도 로컬에서 이미 갈려 있습니다 — `bd-*`·`cmp-304`는 `-admin`, `tps-*`는 `-user`, `orbstack`·`kind-k8s-lab`은 접미사 없음입니다. 동작에는 영향이 없지만, 새로 등록할 때는 같은 계열의 기존 이름을 따르는 편이 낫습니다.



## 3. 왜 컨텍스트 이름이 `bd-tps-3.0.5.1`인가

> 이 환경의 컨텍스트 이름에는 `tps`가 들어가지만 **TPS 개발계가 아닙니다.** 사업개발팀 Trombone 3.0.5.1 환경이며, 이름은 당시 등록 컨벤션(`bd-` 접두 + 버전)을 따른 결과입니다.

로컬 kubeconfig에 실제로 등록돼 있는 값은 다음과 같습니다.

| 항목 | 값 |
|------|-----|
| 컨텍스트 | `bd-tps-3.0.5.1` |
| 클러스터 | `bd-tps-3.0.5.1-cluster` |
| 사용자 | `bd-tps-3.0.5.1-admin` |
| API 서버 | `https://api.mirae.bd-mirae.trombone.okestro.cloud:6443` |
| 인증 방식 | 클라이언트 인증서 (`client-certificate-data` + `client-key-data`) |

인증이 **토큰이 아니라 클라이언트 인증서**라는 점이 중요합니다. OpenShift는 보통 `oc login`으로 받은 단기 토큰을 쓰는데, 이 컨텍스트는 클러스터 관리자 kubeconfig의 인증서를 그대로 가져온 형태입니다. 그래서 토큰 만료로 끊기지 않는 대신, 인증서 파기·클러스터 재설치 시에는 다시 받아와야 합니다.

컨텍스트가 이 환경인지 확인하는 가장 확실한 방법은 이름이 아니라 **apps 도메인**입니다.

```bash
kubectl --context bd-tps-3.0.5.1 get ingresses.config/cluster \
  -o jsonpath='{.spec.domain}'
# apps.mirae.bd-mirae.trombone.okestro.cloud 가 나오면 bd-mirae 환경
```

### 같은 대역의 다른 환경과 혼동 주의

`10.255.28.x` 대역 안에 사업개발팀 환경이 여러 개 있고 IP 끝자리만 다릅니다. 끝자리로 판단하면 틀린 서버에 붙습니다.

| 컨텍스트 | 환경 | API 서버 |
|---------|------|---------|
| `bd-tps-3.0.5.1` | **bd-mirae Trombone 3.0.5.1 (이 문서)** | `api.mirae.bd-mirae.trombone.okestro.cloud:6443` (`10.255.28.46`) |
| `bd-3051cmp` | 사업개발팀 CMP v3.0.5.1 | `10.255.28.161:16443` |
| `cmp-304` | 사업개발팀 CMP 304 | — |
| `tps-dev` / `tps-v305p` / `tps-bok` | TPS 개발계·305p·한국은행 | — |

`3.0.5.1`이라는 버전 숫자가 bd-mirae Trombone과 CMP 양쪽에 붙어 있어, **버전이 아니라 컨텍스트 이름과 API 서버 주소로 판별**해야 합니다.



## 4. 사전 준비 — /etc/hosts 등록

> API 서버 주소가 도메인(`api.mirae.bd-mirae.trombone.okestro.cloud`)이므로, 로컬에서 이 도메인이 해석되지 않으면 컨텍스트를 등록해도 접속이 실패합니다. 사내 DNS에 없으므로 hosts 파일로 직접 매핑합니다.

macOS·Linux는 `/etc/hosts`, Windows는 `C:\Windows\System32\drivers\etc\hosts`에 아래를 추가합니다.

```
10.255.28.46 api.mirae.bd-mirae.trombone.okestro.cloud api-int.mirae.bd-mirae.trombone.okestro.cloud
10.255.28.47 console-openshift-console.apps.mirae.bd-mirae.trombone.okestro.cloud oauth-openshift.apps.mirae.bd-mirae.trombone.okestro.cloud
10.255.28.47 bd-mirae.trombone.okestro.cloud grafana.bd-mirae.trombone.okestro.cloud prometheus.bd-mirae.trombone.okestro.cloud argocd.bd-mirae.trombone.okestro.cloud jenkins.bd-mirae.trombone.okestro.cloud minio-console.bd-mirae.trombone.okestro.cloud ldap.bd-mirae.trombone.okestro.cloud sonarqube.bd-mirae.trombone.okestro.cloud phpldapadmin.bd-mirae.trombone.okestro.cloud
10.255.28.82 harbor.bd-mirae.okestro.cloud
10.255.28.75 gitlab.bd-mirae.okestro.cloud
10.255.28.197 nexus.bd-mirae.okestro.cloud
```

k9s 접속에 반드시 필요한 줄은 첫 번째(`10.255.28.46`)입니다. 나머지는 포탈·Grafana·ArgoCD 등 부가 서비스를 브라우저로 열 때 쓰입니다.

두 IP는 층위가 다릅니다. `10.255.28.46`은 **OpenShift API**(kubectl·k9s가 붙는 곳), `10.255.28.47`은 **apps 라우트**(브라우저가 붙는 곳)입니다. 둘을 섞어 쓰면 kubectl이 API가 아닌 라우터로 붙어 TLS 오류가 납니다.

### 도메인이 두 계열로 갈리는 것은 오타가 아니다

hosts 블록을 보면 `trombone`이 들어간 도메인과 빠진 도메인이 섞여 있습니다. 이는 원문 그대로이며, 클러스터 안/밖 구분과 정확히 일치합니다.

| 계열 | 대상 | 위치 |
|------|------|------|
| `*.bd-mirae.trombone.okestro.cloud` | 포탈·Grafana·ArgoCD·Jenkins·SonarQube | 클러스터 **내부** Route |
| `*.bd-mirae.okestro.cloud` (`trombone` 없음) | Harbor·GitLab·Nexus | 클러스터 **외부** 별도 VM |

hosts 등록 시 `trombone`을 임의로 넣거나 빼면 해석이 실패합니다.

### VPN

bd 개발환경 접근에는 FortiClient VPN이 필요합니다. VPN이 끊긴 상태에서는 hosts가 맞아도 `10.255.28.x`에 도달하지 못하므로, 접속 실패 시 가장 먼저 확인할 항목입니다.

```bash
nc -vz 10.255.28.46 6443    # API 도달 확인
```



## 5. kubeconfig 획득과 병합

> 기존 컨텍스트를 날리지 않는 것이 이 절차의 핵심입니다. `kubectl config view --flatten`으로 두 파일을 합치면 인증서가 파일 내부에 인라인되어 하나의 config로 정리됩니다.

### 5.1 백업 (건너뛰지 않는다)

```bash
cp ~/.kube/config ~/.kube/config.backup-bdmirae-$(date +%Y%m%d-%H%M%S)
```

로컬 `~/.kube/`에는 이미 `config.backup-bd3051-20260811-151745`, `config.backup-cmp304-20260806-145925` 같은 백업이 쌓여 있습니다. 같은 컨벤션(`config.backup-<환경>-<타임스탬프>`)을 따릅니다. 병합 명령은 원본 파일을 덮어쓰므로, 백업이 유일한 복구 수단입니다.

### 5.2 클러스터에서 kubeconfig 가져오기

bastion을 경유합니다. `~/.ssh/config`에 별칭이 등록돼 있어 비밀번호를 직접 입력하지 않습니다.

```bash
ssh bd-trombone-3.0.5.1-bastion   # 10.255.28.221, hostname: bd-mirae-deploy
```

OpenShift 설치 서버에는 설치 시 생성된 관리자 kubeconfig가 남아 있습니다. 경로가 배포 방식에 따라 다르므로 차례로 확인합니다.

```bash
# OpenShift(IPI/UPI) 설치 디렉토리 — 가장 흔한 위치
ls ~/*/auth/kubeconfig 2>/dev/null

# kubeadm 계열
ls /etc/kubernetes/admin.conf 2>/dev/null

# 그 외
ls ~/.kube/config 2>/dev/null
```

찾은 파일을 로컬 임시 경로로 내려받습니다.

```bash
ssh bd-trombone-3.0.5.1-bastion 'cat <찾은경로>' > /tmp/bdmirae.conf
```

### 5.3 이름 rename

내려받은 kubeconfig의 클러스터·사용자·컨텍스트 이름은 대개 `admin`이나 `kubernetes` 같은 일반적인 값입니다. 그대로 병합하면 기존 컨텍스트와 이름이 충돌합니다. 컨벤션에 맞춰 `bd-tps-3.0.5.1-*`로 바꿉니다.

```bash
kubectl --kubeconfig /tmp/bdmirae.conf config rename-context <원래이름> bd-tps-3.0.5.1
```

클러스터·사용자 이름은 `kubectl config` 서브커맨드로 직접 바꿀 수 없어 파일을 편집합니다. 최종 형태는 다음과 같아야 합니다.

| 종류 | 이름 |
|------|------|
| context | `bd-tps-3.0.5.1` |
| cluster | `bd-tps-3.0.5.1-cluster` |
| user | `bd-tps-3.0.5.1-admin` |

`server` 값은 **파일에 적힌 값을 확인해 그대로 씁니다.** 포트를 추측하지 않습니다. 이 환경은 `https://api.mirae.bd-mirae.trombone.okestro.cloud:6443`이지만, CMP 계열은 `:16443`을 쓰는 등 배포마다 다릅니다. 다만 server가 클러스터 내부 전용 IP나 VIP로 적혀 있으면 로컬에서 도달하지 못하므로, 그럴 때만 접근 가능한 주소로 교체합니다.

### 5.4 병합

```bash
KUBECONFIG=~/.kube/config:/tmp/bdmirae.conf kubectl config view --flatten > /tmp/merged \
  && mv /tmp/merged ~/.kube/config
```

`--flatten`이 인증서 파일 참조를 base64 데이터로 인라인해 하나의 파일로 정리합니다. 이것이 로컬 kubeconfig에서 `client-certificate-data`·`client-key-data`로 보이는 이유입니다.

### 5.5 임시파일 삭제

```bash
rm -f /tmp/bdmirae.conf
```

임시파일에는 클러스터 관리자 인증서가 들어 있습니다. 병합이 끝나면 즉시 지웁니다.

## 7. k9s에서 쓰기

> k9s는 kubeconfig의 `current-context`를 기본으로 열므로, 컨텍스트를 명시하거나 k9s 안에서 전환합니다.

로컬 셸에는 `KUBECONFIG=$HOME/.kube/config k9s` 별칭이 걸려 있습니다.

```bash
k9s --context bd-tps-3.0.5.1
```

k9s 안에서 전환하려면 `:ctx`로 컨텍스트 목록을 띄웁니다. 현재 `current-context`가 `orbstack`이므로, 명시하지 않으면 로컬 클러스터가 열립니다.

### 자주 쓰는 키

| 키 | 동작 |
|----|------|
| `:` | 명령 모드 (`:pod`, `:svc`, `:route`, `:ctx`, `:ns`) |
| `y` | 커서 올린 리소스의 **YAML 스펙 보기** |
| `d` | `describe` (이벤트·상태 포함) |
| `l` | 파드 로그 |
| `/` | 현재 목록 내 필터 |
| `0` | 전체 네임스페이스 |
| `Ctrl-a` | 조회 가능한 리소스 전체 목록 |
| `Esc` | 이전 화면 |

### OpenShift라서 다른 점 — Route가 1차 자료

이 클러스터는 OpenShift이므로 `:route`로 Route 리소스를 조회할 수 있습니다. 그리고 라우팅을 추적할 때 **Ingress만 보면 절반만 본 것**입니다. Ingress 리소스가 Route로 자동 샤딩 변환되어, `trb-app`의 `auth-ingress` 하나가 경로별로 `auth-ingress-25v2z`, `auth-ingress-pq84t` 같은 Route 여러 개로 쪼개집니다. HAProxy가 실제 참조하는 것은 Route입니다.

```bash
kubectl --context bd-tps-3.0.5.1 get routes -A
```

Trombone 앱 경로는 전부 호스트 `bd-mirae.trombone.okestro.cloud` 아래에 `edge/Redirect`(TLS 종단 + HTTP→HTTPS 리다이렉트)로 붙습니다.

| 경로 | 백엔드 서비스 |
|------|--------------|
| `/` | trb-app-react-app |
| `/pipeline/api` | trb-app-pipeline-api |
| `/workflow/api` | trb-app-workflow-api |
| `/ppln-logging/api` | trb-app-ppln-logging-api |
| `/common/api` | trb-app-common-api |
| `/pms/api` | trb-app-pms-api |
| `/scheduler/api` | trb-app-scheduler |
| `/notificator/api` | trb-app-notificator |
| `/sse` | trb-app-sse |

### 80/443을 `get svc`로 찾으면 안 나온다

`IngressController(default)`의 게시 전략이 **`HostNetwork`**입니다. LoadBalancer도 NodePort도 아니어서, `kubectl get svc -A`로 80/443을 찾아도 결과가 없습니다. router 파드가 `hostNetwork=true`로 노드의 80/443을 직접 리스닝합니다.

```json
{"hostNetwork":{"httpPort":80,"httpsPort":443,"protocol":"TCP","statsPort":1936},"type":"HostNetwork"}
```

`openshift-ingress` 네임스페이스의 `router-internal-default`는 ClusterIP(80/443/1936)라 **클러스터 내부 전용**이며 외부 진입점이 아닙니다. 진입점을 확인하는 순서는 다음과 같습니다.

```bash
# ① 게시 방식 — 여기가 SSOT
kubectl --context bd-tps-3.0.5.1 -n openshift-ingress-operator \
  get ingresscontroller default -o jsonpath='{.status.endpointPublishingStrategy}'

# ② 어느 노드가 지금 80/443을 물고 있는지
kubectl --context bd-tps-3.0.5.1 -n openshift-ingress get pods -o wide

# ③ 실제 접속 검증 (DNS 우회해 특정 노드로)
curl -kI https://bd-mirae.trombone.okestro.cloud \
  --resolve bd-mirae.trombone.okestro.cloud:443:10.255.28.188
```

router 파드가 뜬 노드만 80/443이 열립니다. 세 번째 워커(`10.255.28.183`)에는 router가 없어 닫혀 있습니다. router 파드는 재스케줄될 수 있으므로 노드 고정으로 취급하지 말고 ②로 조회해 확인합니다.

k9s에서 router 파드 스펙을 볼 때는 `:pod` → `0`(전체 네임스페이스) → `/router` 필터 → 커서 올리고 `y`입니다. YAML 화면에서도 `/`로 검색되므로 `hostNetwork`, `containerPort`를 바로 찾을 수 있습니다.

## 8. 실패할 때 확인 순서

> 실패 원인은 대개 네트워크·이름 해석·인증 셋 중 하나입니다. 아래 순서로 좁힙니다.

| 증상 | 원인 | 확인·조치 |
|------|------|----------|
| `dial tcp: lookup ... no such host` | hosts 미등록 | `/etc/hosts`에 `10.255.28.46` 줄 추가 |
| `i/o timeout`, `connection refused` | VPN 미연결 | `nc -vz 10.255.28.46 6443` 후 FortiClient 확인 |
| `x509: certificate signed by unknown authority` | 병합 시 CA 데이터 유실 | 백업에서 복구 후 `--flatten` 재실행 |
| `Unauthorized` | 인증서 파기·클러스터 재설치 | bastion에서 kubeconfig 재획득 |
| 기존 컨텍스트가 사라짐 | 병합이 아니라 덮어쓰기 | `~/.kube/config.backup-*`에서 복구 |
| k9s가 로컬 클러스터를 염 | `current-context`가 `orbstack` | `k9s --context bd-tps-3.0.5.1` 또는 k9s 안에서 `:ctx` |
| TLS 오류인데 hosts는 맞음 | API(`.46`) 대신 apps(`.47`)로 붙음 | kubeconfig `server` 값 재확인 |

백업 복구는 다음과 같습니다.

```bash
ls -t ~/.kube/config.backup-* | head -1        # 가장 최근 백업 확인
cp <백업파일> ~/.kube/config
kubectl config get-contexts                     # 복구 확인
```



## 9. 함께 알아 둘 것 — 이 환경의 DB

> 클러스터를 붙이는 목적이 대개 앱 조회이므로, 앱이 붙는 DB 정보를 같이 둡니다. 계정명과 스키마명이 TPS와 완전히 같아 특히 헷갈립니다.

| 항목 | 값 |
|------|-----|
| 호스트 | `10.255.28.230` |
| Port | `3306` |
| `@@hostname` | `bd-mirae-mariadb` |
| 엔진 | MariaDB `10.11.10` |
| 계정 | `trbuser` |

접속 문자열은 `log4jdbc`를 빼고 씁니다.

```bash
# DataGrip / JDBC
jdbc:mariadb://10.255.28.230:3306/TPS?allowMultiQueries=true

# CLI
mariadb -h 10.255.28.230 -P 3306 -u trbuser -p TPS
```

앱 설정(`backend-common-cm`)에는 `jdbc:log4jdbc:mariadb://...`로 적혀 있습니다. `log4jdbc`는 SQL 로깅용 프록시 드라이버여서 **DataGrip에서는 붙지 않습니다.**

접속정보 자체를 클러스터에서 확인하는 방법입니다.

```bash
kubectl --context bd-tps-3.0.5.1 -n trb-app get cm backend-common-cm \
  -o jsonpath='{.data.TRB_DATASOURCE_JDBC_URL}'
```

`trbuser` 계정과 `TPS` 스키마 이름이 TPS 프로젝트와 같으므로 **IP로만 구분**됩니다. `10.255.28.230`은 `@@hostname`이 `bd-mirae-mariadb`이고 `TB_TRB_*` 테이블이 0개(전부 `TB_TPS_*` 362개)라는 점으로 판별합니다.
