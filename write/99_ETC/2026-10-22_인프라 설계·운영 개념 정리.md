# 인프라 설계·운영 개념 정리
---
> 인프라를 고르고, 설계하고, 운영하며 장애를 좁혀 가는 흐름에서 쓰는 용어와 점검 항목을 참고용으로 정리합니다. 원본 메모의 잘못된 표현은 바로잡은 형태로 적습니다.

원본은 인프라 형태, 설계부터 구축까지, 운영과 장애 대응의 세 장으로 나뉜 메모입니다. 이 문서도 그 순서를 따릅니다. 다만 외울 정의보다 "무엇을 확인해야 하는가"를 남기는 데 맞췄습니다.




## 1. 인프라의 형태

> 물리 서버를 혼자 쓸지, 클라우드 자원을 빌릴지, 둘을 섞을지는 성능·비용·확장성·장애 대응·보안 요구로 정합니다.

어떤 형태를 고를지 정하려면 먼저 용어가 가리키는 범위를 맞춰야 합니다.

- 전용 서버: 특정 고객 한 곳이 독점해서 쓰는 서버입니다.
- 베어메탈: 가상 머신 없이 물리 서버의 하드웨어를 직접 쓰는 형태입니다. "애플리케이션 → OS → 물리 서버" 구성 전체를 부르는 이름은 아닙니다.
- VMware·OpenStack·CloudStack: 가상화 자원이나 클라우드 인프라를 관리하는 기술입니다.
- IaC(Infrastructure as Code): 서버·네트워크 구성을 코드로 정의해 같은 환경을 반복해서 만들고 바꾸는 방식입니다.

선택지는 세 가지입니다. 전용 서버·베어메탈만 쓰거나, 클라우드 IaaS 자원을 전용 서버로 옮기거나, 전용 서버와 IaaS 를 함께 씁니다.




## 2. 설계 초기에 정할 네 가지

> 구축은 요건 정의에서 운영까지 한 흐름입니다. 자원·안정성·보안·복구 네 질문에 답하지 않으면 뒤 단계에서 다시 돌아오게 됩니다.

전체 흐름은 요건 정의·제안 → 개요 설계 → 상세 설계 → 운영 설계 → 구축 → 배포 → 운영입니다. RFP(Request for Proposal, 제안요청서)에는 만들 시스템의 전체 모습, 의뢰 배경과 목적, 필요한 기능과 제안받을 내용을 담습니다.

| 질문 | 확인할 내용 |
|------|------------|
| 자원이 얼마나 필요한가? | CPU·메모리·네트워크·디스크의 용량과 성능 |
| 얼마나 안정적으로 운영해야 하는가? | 가용성 목표, 장애 허용 시간, SLA·SLO |
| 어떤 보안이 필요한가? | 물리 환경·OS·네트워크·애플리케이션별 책임과 대책 |
| 장애를 어떻게 복구할 것인가? | 담당 인력, 감시, 백업, 복구 절차와 목표 시간 |

현재 메모리 사용 현황은 Linux 에서 `free -h` 로 봅니다. 원본 메모의 "메모리 감사"는 이 사용 현황 점검을 가리킵니다.




## 3. 가용성·백업·이중화

> 가용성은 약속(SLA)과 목표(SLO)를 나눠 관리하며 고장 간격과 복구 시간으로 계산합니다. 이중화와 백업은 그 숫자를 지키는 수단입니다.

가용성 숫자를 말하기 전에 그 숫자를 누가 누구에게 약속했는지부터 가려야 합니다. SLA(Service Level Agreement)는 제공자와 이용자가 계약으로 약속한 서비스 수준입니다. 인프라를 고를 때는 보장 대상, 가용성 기준, 장애 시 보상 조건을 확인합니다. SLO(Service Level Objective)는 운영자가 스스로 달성하려는 목표라서 계약 조건과 따로 관리합니다.

가동률은 MTBF(평균 고장 간격)와 MTTR(평균 복구 시간)으로 계산합니다.

```pseudocode
가동률 = MTBF ÷ (MTBF + MTTR)
```

고장을 줄이거나(MTBF↑) 빨리 복구하면(MTTR↓) 가동률이 오릅니다. 이를 위한 수단은 다음과 같습니다.

- HA(High Availability, 고가용성): 일부 장비가 고장 나도 서비스가 이어지도록 이중화한 구성입니다.
- CDP(Continuous Data Protection): 바뀌는 데이터를 계속 보호하는 백업 방식입니다.
- DR(Disaster Recovery, 재해 복구): 큰 장애나 재해 때 다른 위치의 자원과 백업으로 복구하는 체계입니다.
- 본딩(Bonding): 여러 네트워크 인터페이스를 하나처럼 묶습니다. Active-Active 는 여러 회선을 함께 씁니다. Active-Standby 는 장애 때 대기 회선으로 넘어갑니다. 실제 동작은 본딩 방식과 스위치 설정에 따라 달라집니다.




## 4. 보안 대책

> 보안은 정책을 정하는 일부터 계층별 기술적 보호까지 이어집니다. 계층마다 무엇을 막는지로 나눠 봅니다.

| 계층 | 대책 |
|------|------|
| 관리·점검 | 정보보안 정책, 정보 유출 방지, 보안 진단, 침투 테스트, 감사, 교육 |
| 네트워크 | 방화벽·패킷 필터링, 접근 제어, 기기 인증, 무선 LAN 인증·암호화, 가짜 AP(Fake AP) 탐지·차단, DoS·DDoS 대응 |
| 침입 대응 | IDS 는 침입을 탐지하고, IPS 는 탐지한 공격을 차단 |
| 통신 보호 | IPsec·VPN 같은 경로 암호화, 전자서명 |
| 서버·애플리케이션 | 사용자 인증, OS 방화벽, 권한 관리, 패치, 안전한 웹 개발, 로그 관리, 악성코드 탐지, 백업, 부하 분산 |
| 데이터 | DBMS·파일 암호화, 메일과 MSG 형식 첨부파일 검사 |

원본 메모의 "FAKE API"는 Fake AP 의 오기입니다. "MSG 스캔"은 메일과 MSG 형식 첨부파일 검사입니다. "DNS 패킷 제한" 항목은 비정상 패킷·요청의 속도 제한으로 읽으면 됩니다. 메모의 "NDS"는 원뜻을 확인하지 못해 특정 제품이나 기술로 정하지 않았습니다.

서버 종류별로는 점검 질문이 달라집니다. 데이터베이스 서버는 다음을 봅니다.

- 누가 DB 에 접속할 수 있는가?
- 웹·애플리케이션 서버와 DB 서버 사이 통신을 보호하는가?
- 조회 결과와 데이터의 무결성을 확인할 수 있는가?
- DB 서버에 로그인하는 사용자와 권한을 통제하는가?
- DB 가 쓰는 디스크와 저장 데이터가 보호되는가?

메일 서버는 누구나 외부로 메일을 전달하는 오픈 릴레이가 되지 않게 설정합니다. 송수신 경로의 암호화도 점검합니다.




## 5. 웹 서비스 확장과 네트워크

> 요청 분산은 서버 상태를 확인하는 장치가 맡아야 합니다. TLS 를 앞단에서 끊는 구성에서는 그 뒤 구간을 암호화할지 따로 정합니다.

웹 요청을 여러 서버로 나누는 방법에는 DNS 라운드 로빈, 로드밸런서, 글로벌 서버 로드밸런싱이 있습니다. 브라우저의 재시도·페일오버도 쓸 수 있습니다. 하지만 서버 상태 확인과 요청 분산을 대신하지는 못합니다.

네트워크는 포트 기반 또는 태그 기반 VLAN 으로 논리적으로 나눕니다. VPN 은 연결 방식에 따라 L2VPN 과 L3VPN 으로 나뉩니다. 암호화할 경로는 클라우드 내부, 사용자와 서비스 사이, 거점 사이처럼 구간별로 봅니다.

로드밸런서나 WAF 가 TLS 연결을 끝내고 요청을 검사하는 구성이 있습니다. 이때는 그 장비와 웹 서버 사이 통신 방식을 따로 정해야 합니다. 필요하면 백엔드 구간에 TLS 를 다시 씌울 수 있습니다. 원본의 "암호화할 수 없는 구간"은 암호화가 불가능하다는 뜻이 아닙니다.

WAF(Web Application Firewall)는 웹 요청 내용을 검사해 주입 공격, 악성 파일 업로드, 원격 코드 실행 시도에 대응합니다. 배치 형태는 게이트웨이형, 가상 게이트웨이형, 웹 서버 모듈형이 있습니다. 원본의 "WAF = L4, IDS/IPS = L4 + α"는 역할을 잘못 설명하므로 외우지 않습니다.




## 6. 시스템 구성 예시

> 규모와 성격에 따라 늘리는 곳이 다릅니다. 각 구성에서 함께 확인할 점을 붙여 둡니다.

| 유형 | 구성과 확인할 점 |
|------|-----------------|
| 소규모 웹 서비스 | 로드밸런서, 웹 서버 2대, DB 서버 1~2대 |
| DB 확장 | 복제(Replication)로 사본 유지. 복제 지연과 장애 전환 방식 확인 |
| 데이터 보호 | DB 서버 밖 다른 위치에도 백업·복제본 보관 |
| 웹 서버 확장 | 여러 서버가 같은 사용자 요청을 처리하도록 세션 공유 방식 검토 |
| 대규모 사이트 | 웹·애플리케이션·DB 3계층. 동시 파일 접근 수와 DB 동시 접속 수 점검. 결제 카드 데이터를 다루면 PCI DSS 기준 확인 |
| 게임 시스템 | 짧은 응답 시간, 네트워크 배선, DB I/O 성능이 중요 |




## 7. 운영 설계와 감시

> 운영은 배포 뒤가 아니라 설계 단계에서 시작합니다. 감시 항목은 바로 알릴 것과 추세로 볼 것으로 나눕니다.

허용할 중단 시간, 장애 허용성, 보안 대책, 담당자와 복구 절차는 설계 때 정합니다.

| 즉시 알릴 항목 | 계속 수집할 항목 |
|---------------|-----------------|
| URL·포트·프로세스 장애 | CPU, 메모리·스왑 사용량 |
| 디스크·inode 부족 | 디스크 지연 시간과 사용량 |
| 애플리케이션 오류 로그 | 네트워크 송수신 트래픽 |
| 하드웨어 장애 | 방화벽 세션 수와 CPU 사용량 |
| 심각한 부하·스왑 증가 | 웹·DB 동시 접속 수, DB SELECT·UPDATE 실행 시간 |

하드웨어 상태는 제조사 관리 도구로도 봅니다. 원본은 Dell 의 `omreport`, HP 의 `hpacucli` 를 예로 들었습니다. 옵션과 지원 여부는 실제 장비에서 확인해야 합니다.

배포 전에는 ApacheBench·JMeter 로 부하를 걸어 성능을 봅니다. 그리고 다음 장애 상황을 실제로 시험합니다.

- 물리 장비나 소프트웨어가 멈추면 서비스가 어떻게 되는가?
- DB 서버가 멈추면 페일오버가 되고, 복구 뒤 페일백 절차가 작동하는가?
- 로드밸런서 아래 서버가 멈추면 요청 대상에서 빠지는가?
- 부하가 늘면 자동 확장이 제때 작동하는가?
- 본딩에서 활성 회선이 끊기면 대기 회선으로 넘어가는가?
- 새 환경으로 옮긴다면 마이그레이션 테스트를 마쳤는가?




## 8. 장애를 좁히는 순서

> 웹이든 메일이든 DNS → 네트워크 → 서버 → 애플리케이션·DB 순으로 범위를 좁힙니다. 메일 서버는 디스크와 큐를 더 봅니다.

웹 사이트에 접속할 수 없을 때는 바깥쪽부터 확인합니다.

- DNS: 새로 설정한 사이트면 `whois` 로 도메인과 네임서버를 봅니다. 갑자기 안 된다면 도메인 만료와 기본·보조 DNS 응답을 봅니다.
- 네트워크: 서버까지 닿는지 봅니다. `traceroute` 로 경로상의 끊긴 곳을 찾습니다.
- 웹 서버: 포트를 열고 있는지, 프로세스가 떠 있는지, 동시 접속 제한에 걸렸는지 봅니다.
- 애플리케이션·DB: CPU 를 많이 쓰는 프로세스와 DB 처리 지연을 봅니다. DB 접속 과정의 DNS 조회가 느린 경우도 있습니다.

```bash
whois example.com                 # 도메인·네임서버 정보
dig @ns1.example.com example.com  # 특정 DNS 서버에 직접 질의
traceroute example.com            # 경로 확인
ss -tlnp                          # 수신 중인 포트와 프로세스 (원본은 netstat)
ps aux --sort=-%cpu | head        # CPU 를 많이 쓰는 프로세스
```

원본 명령에는 경로·옵션 오타가 있으므로 그대로 복사하지 말고 해당 시스템의 형식에 맞춰 씁니다.

메일을 보내거나 받을 수 없을 때는 같은 순서에 다음을 더합니다.

```bash
df -h                     # 디스크가 찼는가
df -i                     # inode 가 바닥나 새 파일을 못 만드는가
dig -t TXT example.com    # 발송 서버를 지정하는 SPF 레코드가 있는가
mailq                     # 발송 대기 메일이 얼마나 쌓였는가
```

메일 서버 설정 오류나 대량 발송으로 큐가 밀렸는지도 봅니다. 원본의 `postsuper -d ALL` 은 대기 중인 메일을 전부 지우는 명령입니다. 원인 확인용이 아니므로 지울 메일과 영향 범위를 정한 뒤에만 씁니다.




## 9. 예방 운영과 유지보수

> 장애 전조를 잡는 예방 운영과, 서비스 중단 여부·계획 여부로 나누는 유지보수를 구분합니다. 작업 시간에는 복구 시간과 여유를 함께 잡습니다.

예방 운영은 장애 전조 감지, 성능 저하 추적과 정기 평가, 취약점 정보 수집과 대응으로 이뤄집니다.

유지보수는 두 기준으로 나눕니다.

- 활성 / 비활성: 서비스를 유지하며 작업하는지, 멈추고 작업하는지입니다. RAID 디스크 핫스왑이 활성 유지보수의 예입니다.
- 계획 / 긴급: 일정을 미리 정했는지, 사고 때문에 바로 하는지입니다. 보안 사고·장비 고장·심각한 소프트웨어 오류가 긴급 유지보수의 예입니다.

작업 계획에는 작업 시간과 복구·문제 대응 시간을 더하고 여유를 둡니다. 원본은 이 합계의 1.5~2배를 예로 듭니다. 영향받는 서비스와 사용자를 파악합니다. 정한 시점까지 끝나지 않으면 복구 절차로 넘어갈 기준도 미리 정합니다.
