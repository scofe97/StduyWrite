---

## 2. 런타임과 Pod 샌드박스 연결

> CNI 바이너리를 부르는 주체는 `kubelet` 이 아니라 `containerd` 나 `CRI-O` 같은 컨테이너 런타임입니다.

CRI 아키텍처와 `pause` 노트는 있지만 런타임 설정이 `/etc/cni/net.d/` 와 `/opt/cni/bin/` 을 고르는 규칙은 공식 문서로 보탭니다.

### 비어 있는 자료 읽는 순서

1. **containerd 설정 문서**: `docs/cri/config.md` 의 `Full configuration` 에서 `plugins.'io.containerd.cri.v1.runtime'.cni` 블록을 찾습니다. 필드 일곱 개 가운데 `bin_dirs`, `conf_dir`, `max_conf_num`, `conf_template` 네 개를 먼저 봅니다. `max_conf_num` 의 기본값은 `1` 이라 설정 파일 하나만 읽습니다.
2. **containerd CNI 템플릿**: 같은 문서 끝쪽의 `CNI Config Template` 절에서 CNI 설정 파일을 놓는 데몬이 없을 때 쓰는 Go 템플릿과 쓸 수 있는 값(`.PodCIDR`·`.PodCIDRRanges`·`.Routes`)을 봅니다.
3. **CRI-O 매뉴얼**: `crio.conf.5.md` 의 `CRIO.NETWORK TABLE` 에서 `network_dir`(기본 `/etc/cni/net.d/`) 과 `plugin_dirs`(기본 `/opt/cni/bin/`) 를 확인합니다. `cni_default_network` 가 비어 있으면 `network_dir` 에서 처음 찾은 설정을 고릅니다.

- **넘어가도 되는 기준**: Pod 네트워크가 비었을 때 `kubelet` 로그를 볼지, `/etc/cni/net.d/` 에서 런타임이 고른 설정 파일을 볼지 가르면 3단계로 갑니다.



## 3. CNI 명세와 참조 플러그인

> CNI 는 환경 변수와 표준 입력 JSON 으로 `ADD`·`DEL`·`CHECK`·`GC` 를 주고받는 실행 규약이며, 이 저장소에서 가장 비어 있는 핵심 구간입니다.

`04-02` §1 이 CNI 명세를 요약하지만 원전 정독·참조 플러그인·`Production Kubernetes` 5장 노트는 비어 있습니다. 아래 순서를 따라 명세 원전부터 참조 플러그인 동작까지 직접 읽습니다.

### 비어 있는 자료 읽는 순서

1. **`Production Kubernetes` 5장**: 앞부분 `Networking Considerations` 와 `IP Address Management (IPAM)` 을 먼저 읽습니다. 이어 `Routing Protocols` → `Encapsulation and Tunneling` → `05-cilium.conf` 예제를 순서대로 봅니다.
2. **CNI `SPEC.md` (`v1.3.1` / 스펙 `1.1.0`)**: `Section 1: Network configuration format` 에서 설정 JSON 의 키(`cniVersion`·`name`·`plugins`)를 읽습니다. 다음으로 `Section 2: Execution Protocol` 의 `CNI operations` 에서 연산 여섯 개(`ADD`·`DEL`·`CHECK`·`STATUS`·`VERSION`·`GC`)를 봅니다. 이어 `Section 3: Execution of Network Configurations` 의 `Deriving runtimeConfig` 를 읽습니다.
3. **위임과 결과 타입**: `Section 4: Plugin Delegation` 의 `Delegated plugin execution procedure` 에서 주 플러그인이 IPAM 플러그인을 호출하는 절차를 읽습니다. 마지막으로 `Section 5: Result Types` 와 `Appendix: Examples` 에서 `bridge` 가 `host-local` 에 위임하는 예의 JSON 입출력을 대조합니다.
4. **참조 플러그인 문서**: `cni.dev/plugins/current/` 의 `main/bridge` → `ipam/host-local` → `meta/portmap` 순으로 봅니다. 마지막으로 `ip netns` 에 `CNI_COMMAND=ADD` 환경 변수를 주고 직접 호출해 봅니다.

- **넘어가도 되는 기준**: `host-local` 이 왜 단독 실행이 아니라 위임 호출되는지, 설정의 `plugins` 목록에서 `prevResult` 가 어떻게 전달되는지 말하면 4단계로 갑니다.

- **`networking-and-kubernetes` 의 보조·일반론 편**: `00-01` 용어집과 `00-02` 결정 치트시트는 책 전체의 색인·압축본이라 단계 표에 싣지 않았습니다. `01-01` OSI 모델과 `01-02` TCP·TLS·UDP 는 CNI 이전의 네트워크 일반론이라 뺐습니다. `_mistakes.md` 는 복습 기록입니다.
- **`learning-ebpf` 나머지 14편**: BCC·libbpf·CO-RE·Go/Rust 라이브러리로 프로그램을 짜고 적재하는 장과 트레이싱·보안 장이라 CNI 데이터패스를 읽는 전제가 아닙니다. 7단계에 건 여섯 편만 실었습니다.
- **Ingress·서비스 메시 일반론**: `kubernetes-in-action` 12·13장, `kubernetes-up-and-running` 15장, `istio-in-action` 은 L7 진입·메시 계층이라 CNI 밖입니다. Cilium 구현과 `networking-and-kubernetes` `05-03` 은 7단계에, Istio Ambient 는 8단계에 있습니다.
- **Service 기초 중복편**: `kubernetes-up-and-running` 7장(Service Discovery)과 `kubernetes-patterns` 13장은 5단계의 `kubernetes-in-action` 11장과 같은 주제라 한 책만 걸었습니다. 토폴로지 인지 라우팅 사례(`troubleshooting/cloud`)는 Service 힌트 문제라 CNI 데이터패스 밖으로 보고 뺐습니다.
- **네트워크·OS 일반 책**: `cntd` 의 나머지 편, `tii`, `paw`, `npg`, `linux-kernel-programming`, `ostep` 은 CNI 를 직접 다루지 않습니다. `systems-performance` 10장의 성능 배경과 `learning-modern-linux` 6장은 단계 표의 노트가 같은 내용을 맡습니다.
- **보안·운영 책과 시트**: `cks-study-guide` 와 `container-security` 의 나머지 편은 보안 점검 중심이라 6단계의 정책 행에만 걸었습니다. `_digest/k8s` 의 플레이북 요약은 본 노트가 있는 주제와 겹칩니다. `troubleshooting` 의 502 사례와 `_drill` 기록, `02_os/docs/cmd/` 의 `netstat`·`firewall-cmd`·`nerdctl` 시트는 CNI 와 직접 닿지 않습니다.
