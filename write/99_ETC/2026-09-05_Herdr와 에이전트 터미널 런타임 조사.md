# Herdr와 에이전트 터미널 런타임 조사 — 무엇이 어느 계층을 막는가

---

> 코딩 에이전트를 동시에 여러 개 돌리는 환경에서 Herdr를 도입할지 판단한 기록입니다. 결론은 도입 보류이고, 이 문서는 그 판단의 근거와 판단을 뒤집을 조건을 함께 남깁니다.

이 조사에서 건진 것은 Herdr에 대한 평가 자체보다, **도구를 기능이 아니라 "막아 주는 사고"로 나누면 겹쳐 보이던 것들이 각자 다른 층에 앉는다**는 정리입니다. 그 정리는 4절에 있습니다.

## 1. 왜 조사했는가

> 에이전트를 다섯 개씩 병렬로 돌리고 있는데 그것을 받쳐 줄 계층이 비어 있다는 문제에서 출발했습니다.

터미널에서 코딩 에이전트를 하나만 쓸 때는 아무 문제가 없습니다. 명령을 넣고 결과를 보고 다음 명령을 넣으면 됩니다. 그런데 동시에 다섯 개를 돌리기 시작하면 두 가지가 한꺼번에 불편해집니다. 하나는 터미널 창을 닫는 순간 진행 중이던 작업이 같이 죽는다는 것이고, 다른 하나는 다섯 개 중 어느 것이 내 입력을 기다리며 멈춰 있는지 볼 방법이 없다는 것입니다.

Herdr는 이 두 가지를 정확히 겨냥한 도구라고 소개됩니다. 스스로를 "코딩 에이전트가 살아가는 런타임"이라 부르며, 터미널을 교체하지 않고 그 안에서 도는 백그라운드 멀티플렉서로 자신을 규정합니다. 설명만 보면 딱 맞는 도구인데, 정말 그런지 확인할 필요가 있었습니다.

확인이 필요했던 이유는 출발점이 외부에서 받은 비교 글이었기 때문입니다. 그 글은 Herdr, tmux, Zellij, cmux, Warp, Conductor, Emdash, Superset을 한 표에 놓고 비교하고 있었는데, 검증해 보니 사실 두 가지가 틀렸고 표에서 빠진 항목이 하나 있었습니다.



## 2. 1차 자료로 확정한 사실

> 라이선스와 버전이 틀려 있었습니다. 둘 다 도입 판단에 직접 영향을 주는 항목입니다.

요약 글의 서술을 그대로 옮기지 않고 GitHub API 응답, 저장소의 LICENSE 파일 원문, Homebrew 포뮬러로 직접 확인했습니다.

| 항목 | 외부 글의 서술 | 확정된 사실 | 확인처 |
|---|---|---|---|
| 라이선스 | AGPL-3.0-or-later 듀얼 + 상용 | Apache-2.0 | LICENSE 파일 원문, GitHub API, Homebrew 포뮬러 |
| 버전 | 언급 없음 | v0.8.2 (2026-08-19 릴리스) | GitHub Releases, `brew info herdr` |
| 설치 경로 | 언급 없음 | `brew install herdr` (homebrew-core 정식 등록) | `brew info herdr` |

라이선스를 짚는 이유는 판단이 갈리기 때문입니다. AGPL에 상용 라이선스가 붙은 구조라면 사내 도입에 법무 검토가 필요하지만, Apache-2.0이면 그 부담이 사라집니다. 요약본 하나를 믿고 넘어갔다면 없는 장벽을 있다고 여길 뻔했습니다.

나머지 확정 사실은 이렇습니다. 저장소는 2026-03-27에 생겼고 stars 35,303, open issue 268개이며 마지막 push가 2026-09-04로 개발이 활발합니다. Rust 단일 바이너리이고 macOS와 Linux를 정식 지원하며 Windows는 베타입니다. Claude Code와 Codex를 포함해 17종의 에이전트를 자동으로 감지합니다.

### Herdr가 하지 않는 일

공식 비교 문서와 통합 문서를 확인한 결과 **Herdr에는 git worktree 관리 기능이 없습니다.** 이것은 추측이 아니라 공식 문서 스스로 밝히는 내용입니다. Conductor나 Emdash 같은 worktree 관리 앱에 대해 "그들의 앱을 종료하면 에이전트가 멈추지만, Herdr는 모든 클라이언트를 detach해도 멈추지 않는다"고 쓰면서 자신을 그 아래 계층으로 규정합니다.

즉 Herdr와 worktree 관리 도구는 서로 대체하는 관계가 아닙니다. 이 사실이 4절의 정리로 이어집니다.



## 3. 비교표에서 빠져 있던 항목

> 비교 대상 여덟 개 중에 정작 이미 쓰고 있는 Claude Code가 없었습니다.

외부 글의 표에는 Herdr, tmux, Zellij, cmux, Warp, Conductor, Emdash, Superset이 있었습니다. 그런데 Claude Code 2.1.260의 `--help`에는 다음이 있습니다.

```bash
-w, --worktree [name]   Create a new git worktree for this session
    --tmux              Create a tmux session for the worktree (requires --worktree).
                        Uses iTerm2 native panes when available; use --tmux=classic
                        for traditional tmux.
```

Conductor와 Emdash와 Superset이 GUI 앱으로 파는 핵심 가치가 worktree 격리인데, 그것을 CLI 플래그 하나가 이미 덮고 있습니다. 이 행이 빠진 비교표는 결과적으로 외부 도구 쪽을 실제보다 후하게 평가한 셈입니다.

여기서 얻는 교훈은 Herdr에 관한 것이 아닙니다. **비교표를 받으면 "내가 이미 가진 것"이 그 표에 행으로 들어 있는지부터 봐야 합니다.** 없으면 그 표는 도입을 부추기는 방향으로 기울어 있습니다.

참고로 Ghostty에는 iTerm2 네이티브 pane에 해당하는 경로가 없으므로, `--tmux`는 classic tmux로 떨어집니다.



## 4. 계층으로 나눠 보기

> 기능으로 나열하면 겹쳐 보이지만, 막아 주는 사고로 나누면 겹치지 않습니다.

이 조사에서 가장 오래 남을 정리입니다. 도구 여덟 개를 "AI 에이전트 관리"라는 한 범주에 넣으면 무엇을 골라야 할지 알 수 없습니다. 대신 각 도구가 **어떤 사고를 막아 주는가**를 기준으로 세우면 세 층으로 갈라지고, 층끼리는 대체 관계가 아니게 됩니다.

| 계층 | 막아 주는 사고 | 도구 |
|---|---|---|
| 터미널 | 없음. 표시를 담당하는 층입니다 | Ghostty, cmux, Warp |
| 런타임 | 터미널을 닫으면 진행 중이던 에이전트가 죽습니다. 여러 개 중 어느 것이 막혀 있는지 모릅니다 | Herdr, tmux, Zellij |
| 격리 | 동시에 도는 세션이 같은 워킹 트리를 밟아 커밋과 파일이 서로를 삼킵니다 | `claude -w`, Conductor, Emdash, Superset |

세 번째 행이 중요합니다. 실제로 겪은 사고는 전부 격리 계층에서 났습니다. 동시 세션이 서로의 작업을 `git reset`으로 날린 일, 커밋이 다른 세션의 미완성 파일 개명을 통째로 삼킨 일, 중복을 지웠는데 다른 세션이 같은 절을 다시 쓰는 바람에 되살아난 일이 그렇습니다.

**이 사고들은 Herdr로는 하나도 막히지 않습니다.** Herdr를 넣으면서 격리 문제까지 해결됐다고 여기는 것이 이 조사에서 가장 경계할 오독입니다. 앞 절에서 확인했듯 Herdr에는 worktree 기능이 아예 없고, 공식 문서도 그렇게 말합니다.

반대 방향의 오독도 있습니다. `claude -w`로 worktree를 나눠도 터미널을 닫으면 그 안의 에이전트는 여전히 죽습니다. 격리와 지속성은 서로를 대신하지 못합니다.



## 5. 지금 도입하지 않는 이유

> 빈 자리를 정확히 메운다는 것과 지금 넣어야 한다는 것은 다른 판단입니다.

기술적으로는 Herdr가 런타임 계층에 잘 맞습니다. 그런데도 보류로 결론 낸 이유는 두 가지입니다.

첫째는 성숙도입니다. 저장소가 생긴 지 다섯 달이고 open issue가 268개입니다. 현재 환경은 권한 확인을 건너뛰는 옵션으로 에이전트를 다섯 개 돌리고 훅이 겹겹이 걸려 있어서, 새 런타임을 그 아래에 끼웠을 때 문제가 생기면 원인이 Herdr인지 기존 구성인지 가려내기 어렵습니다. 도입 여부보다 도입 시점을 고르는 편이 낫다고 판단했습니다.

둘째는 이 범주 자체가 흔들릴 조짐입니다. Ghostty를 만든 Mitchell Hashimoto가 2026년 7월에 Superlogical이라는 회사를 세웠는데, 첫 제품이 바로 서버사이드 영속 멀티플렉서입니다. MIT 라이선스인 libghostty 위에 짓는다고 밝혔습니다. 아직 출시 전이라 이것을 기다릴 이유는 없지만, 일 년 안에 선택지가 달라질 수 있는 영역이라는 뜻입니다.

덧붙이면 Ghostty 자체도 분할과 탭을 이미 제공하고 세션 지속성이 로드맵에 올라 있습니다. 다만 Ghostty의 지속성은 앱 재시작 후 화면 상태를 복원하는 것이지, tmux처럼 프로세스를 살려 두는 것과는 다릅니다. 이 둘을 같은 기능으로 읽으면 안 됩니다.



## 6. 도입을 결정할 트리거

> 보류는 영구 기각이 아닙니다. 아래 중 하나가 실제로 일어나면 5절의 판단을 다시 봅니다.

- 터미널을 닫거나 노트북을 덮어서 **진행 중이던 에이전트 작업을 실제로 잃은 일**이 생겼을 때. 지금은 겪은 손실이 아니라 예상되는 불편입니다. 이 차이가 보류와 도입을 가릅니다.
- 동시에 도는 에이전트가 다섯 개를 넘어, 어느 것이 막혀 있는지 눈으로 못 찾는 일이 반복될 때.
- Herdr가 1.0에 도달하거나 open issue 추세가 꺾일 때.
- Superlogical이 제품을 내놓을 때. 이때는 Herdr와 다시 비교합니다.

격리 계층은 트리거가 다릅니다. `claude -w`는 설치가 필요 없으므로 기다릴 대상이 아닙니다. **다음번에 같은 저장소에 세션을 두 개 이상 띄우는 순간 그냥 붙이면 됩니다.**



## 7. 나중에 쓸 명령

> 결정이 서면 이 절만 보면 됩니다. 지금은 실행하지 않습니다.

```bash
brew install herdr          # Apache-2.0, homebrew-core 정식 등록
herdr                       # 프로젝트 디렉토리에서 실행하면 기본 세션에 attach
                            # 패널에서 claude 나 codex 를 실행하면 자동 감지
                            # prefix+q 또는 창 닫기로 detach, 서버와 에이전트는 유지
herdr server stop           # 서버까지 완전 종료

claude -w <name>            # 세션마다 git worktree 격리, 설치 불필요
```

되돌리기는 `brew uninstall herdr` 한 줄입니다. 공식 문서에 별도의 셸 통합 단계나 uninstall 절차가 없어서, 셸 설정을 건드리지 않는다는 점이 시험 도입에 유리합니다.

사실이 낡았는지 다시 확인할 때는 요약본이 아니라 1차 자료를 봅니다.

```bash
gh api repos/herdrdev/herdr --jq '{stars:.stargazers_count,license:.license.spdx_id,pushed:.pushed_at,open_issues_count}'
gh api repos/herdrdev/herdr/releases/latest --jq '{tag:.tag_name,published:.published_at}'
brew info herdr | head -8
claude --help | grep -i -A2 worktree     # Claude Code 가 덮는 격리 범위
```
