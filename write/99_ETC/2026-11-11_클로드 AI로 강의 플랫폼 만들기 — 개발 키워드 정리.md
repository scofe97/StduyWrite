# 클로드 AI로 강의 플랫폼 만들기 — 개발 키워드 정리

---

> 강의 플랫폼을 클로드 AI로 만드는 영상의 대본을 ChatGPT가 분석한 글에서 백엔드 질문을 골라 공식 문서와 대조했습니다. 분석의 키워드 253개를 로드맵과 맞춰 본 결과와, 로드맵에 넣은 행도 함께 남깁니다.

분석 글은 강의 플랫폼을 만드는 과정을 단계로 나누고 단계마다 공부할 백엔드 주제를 덧붙였습니다. 화면은 웹사이트 제작 시연이지만 결제와 포인트, 가상 공간의 3D 렌더링, 동시성 제어, 메시징 같은 실무 질문이 그 아래에 깔려 있습니다.

키워드 목록은 로드맵이 맡습니다. 이 문서는 분석이 던진 질문마다 시스템이 어디서 실패하는지, 그 해결책이 공식 문서에서 어디까지 보장되는지를 적습니다.



## 1. 자료와 걸러 들을 부분

> 대본을 ChatGPT가 요약·분석한 글이고 영상 원본 링크는 없습니다. 발표자의 의견과 분석자가 덧붙인 구성을 나눠 읽어야 합니다.

자료는 사용자가 붙여 넣은 텍스트 한 편입니다. 영상 원본도, 대본 원문도 없어서 발표자가 실제로 한 말은 분석 글이 옮긴 범위에서만 확인됩니다.

분석 글에는 발표자의 의견과 분석자의 제안이 섞여 있습니다. 벡터 DB와 시계열 DB를 문서형 DB보다 깊게 공부하라는 말은 발표자의 의견입니다. 분석 글도 이 말이 모든 서비스에 해당하지는 않는다고 덧붙입니다. 상태 변화가 많은 작업은 함수형으로 쪼개기보다 객체가 상태와 행위를 함께 관리하는 편이 낫다는 대목도 발표자의 의견입니다. 반면 학습 우선순위 분류와 마지막 키워드 체크리스트는 분석자가 짠 구성입니다.

분석 글의 기술 설명 가운데 공식 문서나 실측과 어긋나거나 범위를 밝히지 않은 곳은 본문에서 다음처럼 바로잡았습니다.

- 키셋 페이지네이션의 행 비교 `(created_at, id) < (…)` 는 PostgreSQL 16에서 인덱스 조건으로 쓰입니다. MySQL 8.0에서는 범위 스캔이 되지 않아 OR 조건으로 풀어 씁니다(5절).
- Kafka의 정확히 한 번(Exactly-once)은 Kafka 토픽 사이에서 읽고 처리하고 쓰는 범위의 보장입니다. 외부 DB에 쓰는 일은 컨슈머가 따로 멱등하게 만들어야 합니다(4절).
- CloudFront의 OAC는 S3 오리진을 CDN 밖 직접 접근에서 막는 장치입니다. 유료 콘텐츠를 아무나 받지 못하게 하는 일은 서명된 URL이, 요청 내용을 검사하는 일은 WAF가 맡습니다. 오리진 쉴드는 이름이 비슷하지만 캐시 계층입니다(7절).
- three.js의 InstancedMesh는 같은 지오메트리와 재질을 쓰는 객체를 묶어 draw call 수를 줄이는 렌더링 기능입니다. Flyweight 패턴과 같은 층의 기법이 아닙니다(8절).
- 결제 취소 때 이미 쓴 포인트를 어떻게 처리하느냐는 분석 글이 질문만 하고 답하지 않았습니다. 3절에 사가로 풀 때 정해야 할 것을 적었습니다.



## 2. 로드맵 대비 누락 지도

> 분석 글의 키워드 253개 가운데 로드맵에 없고 넣을 자리가 있는 것은 65개였습니다. 데이터 저장과 런타임·설계 패턴 쪽에 많이 몰렸습니다.

분석 글에서 키워드 253개를 뽑아 `write/roadmap/` 의 로드맵 전체와 대조했습니다. 판정은 여섯 가지로 나눴고 개수는 다음과 같습니다.

| 판정 | 개수 | 뜻 |
|---|--:|---|
| 있음 | 125 | 로드맵에 같은 키워드가 있음 |
| 있음(표기차) | 6 | 개념은 같고 이름만 다름. 예: 정확히 한 번 전달과 Exactly-once Semantics |
| 덮임 | 19 | 일반어나 구현 세부라서 하위 키워드가 이미 덮음 |
| 없음→제안 | 65 | 빠져 있고 넣을 자리가 있음 |
| 없음→제외 후보 | 22 | 맞는 로드맵이 없음. 3D 렌더링 11개, 프런트엔드·디자인 9개, 제품 기획 2개 |
| 없음→넣지 않음 | 16 | 일반어이거나 제품 이름임. 예: HikariCP, Resilience4j, CloudFront |
| 합계 | 253 | |

빠진 65개를 [backend-keywords.md](../roadmap/backend-keywords.md) 의 국면별로 세면 데이터 저장이 18개로 가장 많았고 런타임과 애플리케이션 구조가 17개로 뒤를 이었습니다. 데이터 저장 쪽은 시계열 DB 운영과 데이터 모델별 DB, 커넥션 풀 고갈, 소프트 삭제와 유니크 제약이 빠져 있었습니다. 런타임 쪽 17개 가운데 11개는 함수형과 객체지향의 개념(순수 함수, 불변성, 캡슐화 등)입니다.

| 국면 | 빠진 키워드 수 | 예 |
|---|--:|---|
| 1. 런타임과 애플리케이션 구조 | 17 | 함수형 프로그래밍, 플라이웨이트 패턴, 빌더 패턴, 임계 구역 |
| 2. API 설계와 통신 | 2 | 키셋 페이지네이션, 안정 정렬 키 |
| 3. 데이터 저장 | 18 | 원장 패턴, 갱신 손실, 커넥션 풀 고갈, 소프트 삭제 유니크 제약 |
| 4. 캐시·메시징·데이터 흐름 | 11 | 썬더링 허드, TTL 지터, 오리진 보호, 벡터 유사도, HNSW |
| 5. 분산 시스템과 회복성 | 4 | 로드 밸런싱, 리버스 프록시, 모듈러 모놀리스 |
| 6. 보안 | 8 | 요청 필터링, IAM 역할, 신뢰 정책, STS AssumeRole |
| 7. 운영·배포·품질 | 3 | 결제 연동, 구독 관리, 이그레스 비용 |
| 다른 로드맵에만 | 2 | 이상 탐지(observability), 핸드오프(ai) |

대조하면서 이름이나 쓰임이 겹쳐 보여도 따로 구분한 것이 있습니다. 본문에서는 다음처럼 반영했습니다.

- 키셋 페이지네이션은 마지막 값으로 건너뛰는 SQL 기법입니다. 커서 기반 페이지네이션은 불투명한 토큰을 주고받는 API 계약이라 따로 둡니다(5절).
- Kafka의 정확히 한 번은 Kafka 토픽 안에서 읽고 처리하고 쓰는 범위로 밝혀 적습니다(4절).
- 플라이웨이트 패턴과 InstancedMesh는 공통 자원을 나눠 쓴다는 점만 닮았고 층이 다릅니다(8절).
- 오리진 보호는 오리진에 직접 들어오는 길을 막는 일입니다. 오리진 쉴드는 캐시 계층이라 이 일을 하지 않습니다(7절).
- OAC는 오리진에 CDN만 들어오게 하고 WAF는 요청 내용을 검사합니다(7절).
- TTL 지터는 캐시 만료 시각을 흩뜨립니다. 로드맵에 이미 있는 지터는 재시도 간격을 흩뜨리는 것이라 따로 둡니다(9절).



## 3. 기능이 백엔드 문제로 바뀌는 지점

> 포인트 지급과 한정판 구매 같은 단순 기능도 동시 요청과 분산 환경에서는 데이터 정합성 문제로 전환됩니다.

강의 완강에 따른 포인트 지급과 한정판 가구 구매는 단순 CRUD로 구현하면 결함이 생깁니다. 네트워크 지연과 동시성 경합이 겹치면 데이터가 틀어집니다.

첫째는 네트워크 재시도나 클라이언트 다중 클릭으로 완강 API가 중복 호출되는 문제입니다. 사용자가 같은 요청을 여러 번 보내면 포인트가 중복 적립됩니다. 클라이언트가 고유한 **멱등성 키**(Idempotency Key)를 헤더에 실어 보내야 합니다[^idempotency-key]. 서버는 이 키를 요청 처리 기록의 **유니크 제약**(Unique Constraint)에 걸어 같은 요청을 두 번 처리하지 않습니다.

둘째는 한정 수량 재고 차감이나 포인트 사용 시 발생하는 동시 요청 문제입니다. 두 트랜잭션이 잔액을 동시에 읽고 순차적으로 차감하면 갱신 손실이 일어납니다. 충돌 빈도가 낮다면 엔티티 버전 컬럼을 검증하는 **낙관적 락**(Optimistic Lock)을 씁니다. 경합이 심한 한정판 재고에는 `SELECT ... FOR UPDATE` 로 행을 먼저 잠그는 **비관적 락**(Pessimistic Lock)을 씁니다.

셋째는 잔액 단일 필드 갱신에 따른 추적성 상실 문제입니다. 계정 테이블의 포인트 숫자만 수정하면 언제 무엇 때문에 바뀌었는지 남지 않습니다. 적립과 사용을 한 건마다 고치지 않는 행으로 쌓는 **원장 패턴**(Ledger Pattern)을 도입해야 합니다. 현재 잔액은 원장 행을 모두 더한 값이 됩니다.

넷째는 포인트 지급과 랭킹 갱신, 트로피 지급 등 여러 서비스가 연계될 때 발생하는 부분 실패 문제입니다. 분산 환경에서는 단일 DB 트랜잭션으로 여러 서비스의 상태 변경을 묶을 수 없습니다. 완강 기록과 이벤트 메시지를 단일 로컬 DB 트랜잭션에 저장하는 **트랜잭셔널 아웃박스**(Transactional Outbox)를 사용합니다[^outbox].

**사가 패턴**(Saga Pattern)은 서비스마다의 로컬 트랜잭션을 차례로 잇는 방식입니다. 중간에 실패하면 앞서 끝난 단계를 보상 트랜잭션으로 되돌립니다[^saga]. 분석 글은 결제 취소 때 이미 쓴 포인트를 어떻게 처리하느냐고 묻기만 합니다. 사가로 풀면 결제 취소 단계의 보상 트랜잭션이 포인트를 되돌려야 합니다. 이미 쓴 포인트를 마이너스 잔액으로 남길지 환불액에서 뺄지는 서비스 정책으로 먼저 정해야 합니다.



## 4. 메시징 — 완강 이벤트가 중복·유실될 때

> 완강 이벤트를 발행할 때 네트워크 순단이나 장애가 발생하면 메시지 유실과 중복 전송 위험에 노출됩니다.

완강 이벤트를 메시지 브로커로 발행할 때 네트워크 순단이나 장애가 발생하면 이벤트가 유실되거나 중복 처리되는 문제가 생깁니다. 아웃박스 흐름은 이 문제를 막기 위해 완강 요청 처리와 비동기 발행을 분리합니다. 완강 시 단일 DB 트랜잭션 안에서 완강 기록과 Outbox 이벤트를 함께 저장합니다. 별도의 Outbox Publisher 프로세스가 이 테이블을 읽어 Kafka 토픽으로 이벤트를 발행합니다. Kafka 컨슈머 그룹은 이 이벤트를 구독해 포인트 지급과 랭킹 갱신, 트로피 지급을 처리합니다.

아웃박스는 유실을 막지만 중복은 막지 못합니다. 퍼블리셔가 메시지를 보낸 뒤 발행 완료를 기록하기 전에 죽으면 다시 떠서 같은 메시지를 또 보냅니다[^outbox]. 컨슈머도 메시지를 처리한 뒤 위치(오프셋)를 저장하기 전에 죽으면 이어받은 프로세스가 이미 처리한 메시지를 다시 받습니다[^kafka-semantics]. 리밸런싱으로 파티션 주인이 바뀌어도 새 주인은 마지막으로 커밋된 위치부터 읽으므로 같은 일이 생깁니다. 프로듀서 쪽 재시도 중복은 Kafka 3.0부터 기본으로 켜진 프로듀서 멱등성이 브로커에서 걸러 줍니다[^kafka-upgrade].

Exactly-once Semantics, 즉 EOS가 보장하는 범위는 좁습니다. Kafka 공식 문서는 정확히 한 번 처리를 프로듀서 멱등성과 트랜잭션 위에 세웁니다[^kafka-semantics].

이 보장은 Kafka 토픽에서 읽고 처리해 다른 토픽에 쓰는 범위에 해당합니다. 같은 문서는 다른 저장소로 가는 정확히 한 번 전달에는 그 저장소의 협력이 필요하다고 적습니다. 컨슈머가 관계형 DB에 포인트를 적립하거나 결제 취소 API를 부르는 일은 Kafka 트랜잭션 밖입니다.

따라서 외부 저장소의 정합성을 지키려면 컨슈머가 같은 메시지를 다시 받는다고 전제하고 설계되어야 합니다. **멱등 컨슈머**(Idempotent Consumer)로 중복 적립을 막아야 합니다. 메시지 고유 ID를 DB 유니크 키로 저장하거나 처리한 오프셋을 결과와 같은 DB 트랜잭션에 저장하는 컨슈머입니다.



## 5. 페이지네이션과 커넥션 풀

> 대규모 데이터에서 OFFSET 방식은 건너뛸 행까지 읽습니다. 느려진 쿼리가 커넥션을 오래 잡으면 같은 풀을 쓰는 다른 요청까지 실패합니다.

OFFSET 기반 페이지네이션은 건너뛸 행도 서버 안에서 모두 계산합니다[^pg-offset]. PostgreSQL 16.15에 20만 행 테이블을 만들고 `OFFSET 100000 LIMIT 20` 으로 읽어 보았습니다. 인덱스에서 100,020행을 읽은 뒤 앞의 10만 행을 버렸습니다. 페이지 번호가 뒤로 갈수록 읽는 행 수가 그만큼 늘어납니다.

대안으로 이전 페이지의 마지막 값을 기준으로 탐색하는 키셋 페이지네이션을 사용합니다. 커서 기반 페이지네이션이 클라이언트에 불투명한 토큰을 주는 API 약속이라면, 키셋은 그 토큰 뒤에서 자주 쓰이는 SQL 기법입니다. 단일 컬럼 기준 쿼리는 다음과 같습니다.

```sql
SELECT *
FROM lectures
WHERE created_at < :lastCreatedAt
ORDER BY created_at DESC
LIMIT 20;
```

정렬 안정성을 보장하려면 고유한 `id` 컬럼을 보조 정렬 키로 결합해야 합니다. `created_at` 값이 같은 행이 여럿이면 페이지 경계에서 행이 빠지거나 두 번 나오기 때문입니다.

```sql
SELECT *
FROM lectures
WHERE (created_at, id) < (:lastCreatedAt, :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

행 값 비교가 인덱스를 타는지는 데이터베이스마다 다릅니다. PostgreSQL은 행 생성자 비교 `(a, b) < (x, y)` 를 왼쪽 원소부터 차례로 비교하는 연산으로 정의합니다[^pg-row-comparison]. 같은 PostgreSQL 테이블에 `(created_at, id)` 복합 인덱스를 두고 실행했습니다. 이 비교가 인덱스 조건(`Index Cond`)으로 들어가 20행만 읽었습니다.

MySQL 8.0 공식 문서는 행 생성자가 인덱스 앞부분을 덮지 못하면 옵티마이저가 인덱스를 덜 쓴다고 적습니다. 이럴 때 행 생성자를 쓰지 않는 같은 뜻의 식으로 바꾸면 인덱스를 더 온전히 쓸 수 있다고 합니다[^mysql-row-opt].

같은 테이블을 MySQL 8.0.46에서 실행하자 인덱스 앞부분을 덮는 이 쿼리도 범위 스캔이 되지 않았습니다. 인덱스를 끝에서부터 훑으며 16만 1,141행을 걸렀습니다. 같은 결과를 OR 조건으로 풀어 쓴 쿼리는 범위 스캔으로 20행만 읽었습니다. 그래서 MySQL에서는 조건을 다음과 같이 풀어 씁니다.

```sql
SELECT *
FROM lectures
WHERE created_at < :lastCreatedAt
   OR (created_at = :lastCreatedAt AND id < :lastId)
ORDER BY created_at DESC, id DESC
LIMIT 20;
```

쿼리 최적화 실패는 단일 쿼리 지연에 그치지 않고 커넥션 풀 고갈로 이어질 수 있습니다. HikariCP 같은 커넥션 풀은 한정된 수의 물리 DB 커넥션을 공유합니다. 풀이 최대 크기에 이르고 쉬는 커넥션이 없으면 `getConnection()` 호출은 기다립니다. 이 대기가 `connectionTimeout`(기본 30초)을 넘으면 `SQLException` 이 납니다[^hikari]. 느린 페이징 쿼리가 커넥션을 오래 잡고 있으면 같은 풀을 쓰는 가벼운 조회까지 이 대기 끝에 실패합니다.



## 6. 소프트 삭제와 유니크 제약

> 물리적 삭제 대신 플래그를 두는 소프트 삭제는 복구를 돕지만 유니크 제약 위반과 인덱스 비대화를 유발합니다.

데이터를 데이터베이스에서 실제로 제거하는 하드 삭제는 삭제 여부 필터가 필요 없고 유니크 제약도 그대로 동작합니다. 대신 실수로 지운 행은 백업으로만 되살릴 수 있습니다. 다른 테이블이 참조하던 행이면 외래 키 처리도 함께 정해야 합니다. PostgreSQL에서는 `DELETE` 해도 옛 행이 바로 사라지지 않고 VACUUM이 나중에 공간을 회수합니다[^pg-vacuum].

반면 레코드에 `deleted_at` 타임스탬프를 남기는 소프트 삭제는 실수로 지운 데이터를 쉽게 되살립니다. 대신 모든 조회 쿼리에 삭제 여부 필터를 붙여야 하고 지운 행이 계속 쌓여 테이블과 인덱스가 커집니다.

소프트 삭제를 적용하면 재가입 시 유니크 제약 충돌이 발생합니다. 사용자가 회원 탈퇴를 진행한 후 동일한 이메일로 다시 가입하려고 할 때 일어납니다. 이메일 컬럼에 표준 UNIQUE 인덱스가 걸려 있다면 삭제된 기존 행의 이메일 값 때문에 중복 키 제약 조건 위반 오류가 발생합니다.

PostgreSQL 공식 문서가 안내하는 부분 인덱스를 사용하면 이 문제를 해결할 수 있습니다[^pg-partial-index].

```sql
CREATE UNIQUE INDEX uq_users_active_email
ON users (email)
WHERE deleted_at IS NULL;
```

이 부분 유니크 인덱스는 `deleted_at IS NULL` 조건을 만족하는 활성 행에 대해서만 유니크성을 검사합니다. 삭제된 행은 인덱스에 들어가지 않으므로 탈퇴 회원의 이메일로 다시 가입해도 충돌하지 않습니다. PostgreSQL 16.15에서 확인하니 탈퇴 처리한 행이 있어도 같은 이메일의 새 행이 들어갔습니다. 같은 이메일의 활성 행이 하나 더 들어오려 하자 `duplicate key value violates unique constraint` 로 거부됐습니다.



## 7. 회복성·트래픽·보안 키워드

> 외부 서비스 장애는 서킷 브레이커로 끊고, 콘텐츠와 계정 접근은 CDN·WAF·IAM이 각자 맡은 층에서 막습니다.

응답하지 않는 외부 서비스를 기다리는 호출이 쌓이면 그 호출을 잡은 스레드와 커넥션도 함께 묶입니다. **서킷 브레이커**(Circuit Breaker)는 실패가 이어지는 호출을 미리 끊어 이 대기를 줄입니다.

Resilience4j의 서킷 브레이커는 닫힘·열림·반열림 세 상태를 오가는 상태 기계입니다[^resilience-cb]. 닫힘 상태에서 실패율이 설정한 임계치 이상이 되면 열림으로 바뀝니다. 열림 상태에서는 호출을 `CallNotPermittedException` 으로 거절합니다. 대체 응답(fallback)은 호출하는 쪽이 따로 정합니다. 대기 시간이 지나면 반열림으로 바뀌어 정해진 수의 호출만 보내 보고 그 결과로 닫힘과 열림 중 하나로 돌아갑니다.

CDN과 WAF는 트래픽 보호 계층에서 서로 다른 문제를 다룹니다. CloudFront의 Origin Access Control(OAC)은 CloudFront가 S3 오리진에 인증된 요청을 보내게 합니다[^aws-oac]. S3 버킷 정책이 CloudFront 서비스 주체의 요청만 허용하면, 사용자가 S3 주소로 직접 들어오는 길이 막힙니다. 이것이 분석 글이 말하는 오리진 보호입니다. 이름이 비슷한 오리진 쉴드는 CloudFront 캐시에 한 층을 더 두어 오리진의 부하를 줄입니다. 접근을 막는 기능이 아닙니다[^aws-origin-shield].

반면 서명된 URL이나 서명된 쿠키는 유료 강의 영상처럼 정해진 사용자만 받아야 하는 콘텐츠를 지킵니다[^aws-signed-url]. 서명된 URL에는 만료 일시가 들어갑니다. 사용자 지정 정책을 쓰면 허용할 IP 범위도 넣을 수 있습니다. AWS는 사용자가 오리진 주소로 이 제한을 우회하지 못하도록 OAC 같은 오리진 접근 제한을 함께 쓰라고 권합니다.

AWS WAF는 이와 달리 L7 애플리케이션 계층에서 웹 요청의 내용을 검사합니다. SQL Injection과 크로스 사이트 스크립팅 공격 패턴을 찾아 막습니다. Rate-based 규칙을 통해 특정 클라이언트의 비정상적인 요청 폭주도 걸러냅니다[^aws-waf-rate].

클라우드 보안 거버넌스에서는 AWS IAM의 정책 평가 순서를 정확히 이해해야 합니다. AWS 계정 루트 사용자를 빼면 모든 요청은 기본적으로 묵시적으로 거부됩니다[^aws-iam-eval]. 평가는 적용되는 모든 정책에서 명시적 거부(Deny)를 먼저 찾습니다. 하나라도 있으면 그대로 거부로 끝납니다.

명시적 거부가 없으면 Organizations의 RCP와 SCP, 리소스 기반 정책, 자격 증명 기반 정책, 권한 경계, 세션 정책 순으로 허용을 확인합니다. 같은 계정 안에서는 리소스 기반 정책의 허용만으로 접근이 허락되는 경우도 있어서 모든 단계의 허용이 늘 필요한 것은 아닙니다.



## 8. 프런트엔드·AI 개발 흐름

> 가상 공간의 같은 가구를 하나씩 따로 그리면 draw call이 늘어 화면이 끊길 수 있습니다. 접근성과 에이전트 스킬도 이 절에서 함께 봅니다.

가상 공간에 수백 개의 가구 객체를 개별 Mesh로 생성하면 객체마다 draw call이 생겨 화면이 끊길 수 있습니다. three.js 공식 문서는 같은 지오메트리와 재질을 쓰고 위치·회전만 다른 객체를 많이 그릴 때 `InstancedMesh` 를 쓰라고 합니다. 그 효과는 draw call 수를 줄이는 것으로 설명합니다[^threejs-instanced-mesh]. 인스턴스마다의 변환은 `instanceMatrix` 속성 하나에 모아 둡니다.

분석 글도 Flyweight와 InstancedMesh를 다른 개념이라고 먼저 선을 긋습니다. 그다음 공통 자원을 공유한다는 관점에서만 둘을 함께 봅니다. Flyweight는 여러 객체가 바뀌지 않는 공통 상태를 함께 참조해 메모리를 줄이는 설계 패턴입니다. InstancedMesh는 GPU에 보내는 그리기 호출을 줄이는 렌더링 기능이라, 같은 문제를 다른 층에서 다룹니다.

웹 접근성의 기준은 W3C 권고안인 WCAG 2.2입니다[^w3c-wcag22]. 3D 공간을 마우스로만 조작하게 만들면 키보드 조작 기준을 놓치기 쉽습니다. 이 문서에서 짚는 성공 기준과 등급은 다음과 같습니다.

| 성공 기준 | 요구 | 등급 |
|---|---|---|
| 2.1.1 Keyboard | 모든 기능을 키보드로 조작할 수 있음 | A |
| 2.4.7 Focus Visible | 키보드 포커스가 보임 | AA |
| 1.4.3 Contrast (Minimum) | 텍스트 명도 대비 | AA |
| 2.4.13 Focus Appearance | 포커스 표시의 외관, 2.2에서 새로 추가 | AAA |

분석 글은 프롬프트와 에이전트 스킬의 차이도 짚습니다. 프롬프트는 지금 하는 작업의 요청이며 스킬은 여러 작업에서 다시 쓰는 지식과 작업 절차에 가깝다는 설명입니다. 예로 Spring Boot API 설계, PostgreSQL 쿼리 최적화, Kubernetes 문제 해결 스킬을 듭니다.



## 9. 키워드를 공부하는 네 질문

> 기술 용어를 단순 암기하면 실제 운영 환경의 장애 상황에서 기술을 적절히 선택하지 못합니다.

기술 용어를 단순 암기하면 실제 운영 환경의 장애 상황에서 기술을 적절히 선택하지 못합니다. 분석 글은 키워드를 만날 때마다 다음 네 가지를 물으라고 권합니다.

1. 이 기술은 어떤 문제를 해결하기 위해 등장했는가?
2. 기존 방식에는 어떤 한계가 있었는가?
3. 실제 운영 환경에서 어떤 장애나 비용을 줄여 주는가?
4. 어떤 조건에서는 사용하지 않는 것이 더 나은가?

AI 코딩 에이전트에 작업을 지시할 때도 이 사고의 깊이가 결과물의 수준을 결정합니다. "Redis를 사용해서 캐시를 구현해 주세요"라는 요청은 단순한 기술 호출에 불과합니다. 캐시 무효화나 장애 복구 로직이 누락된 취약한 코드를 낳기 쉽습니다.

분석 글은 같은 요청을 다음처럼 구체화한 예를 듭니다.

> 조회 빈도가 높은 데이터에 Redis Cache-Aside를 적용하되, 데이터 변경 시 캐시 무효화 전략을 설계해 줘. Cache Stampede와 Thundering Herd를 고려하고, TTL Jitter 및 동시성 제어를 적용해 줘. 캐시 장애 시 DB로의 요청이 급증하지 않도록 Fallback과 Rate Limiting도 고려해 줘.

이 요청에서 TTL 지터는 캐시 키의 만료 시각을 무작위로 흩뜨려 여러 키가 한꺼번에 만료되지 않게 하는 장치입니다. 재시도 사이 간격을 흩뜨리는 백오프의 지터와는 적용 대상이 다릅니다.

기술의 이름 뒤에 숨은 장애 시나리오와 트레이드오프를 질문으로 분해할 수 있을 때 기술 키워드는 비로소 운영 가능한 아키텍처 지식으로 축적됩니다.
