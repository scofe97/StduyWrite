**신입을 채용하는 이유가 달라짐.** `[표]`

**신입에게 기대하는 일도 달라짐.** (제목만 있는 전환 슬라이드)

**AI가 가져간 영역.** 설명이 분명한 작업은 AI가 빠르게 시작한다. 코드 초안, 테스트 뼈대, API 사용 예와 단순한 수정은 이미 자동화 가능한 영역.

`[이미지]` THE CHANGING STARTING POINT. "신입에게 요구되는 출발점의 변화." 정해진 일을 수행하며 배우던 단계가 짧아지고, 판단을 요구받는 시점이 빨라졌다.

| 상황 | 예전 신입의 주요 업무 (수행하면서 배우기) | 현재 더 빨리 요구되는 능력 (판단하면서 배우기) |
|---|---|---|
| 작업 시작 | 선임이 정리한 요구사항을 전달받는다 | 불완전한 요구사항에서 확인할 질문을 찾는다 |
| 구현 | 정해진 범위의 기능과 반복 코드를 작성한다 | AI가 만든 코드를 읽고 수정해 시스템에 연결한다 |
| 검증 | 주어진 테스트를 실행하고 결과를 보고한다 | 가정과 예외를 의심하고 반례를 만든다 |
| 문제 해결 | 문제를 재현한 뒤 선임에게 전달한다 | 원인을 좁히고 해결안의 비용을 비교한다 |
| 운영 | 코드 병합이나 배포 시점에서 작업을 넘긴다 | 배포 뒤 지표와 장애를 보며 끝까지 추적한다 |
| 학습 | 조직이 쓰는 기술을 순서대로 익힌다 | 필요한 기술을 골라 빠르게 깊이를 조절한다 |

발표의 논지를 정리한 일반화된 비교.

`[이미지]` WHERE THE WORK BEGINS. "일의 시작점이 달라졌다." 작성 시간이 줄어든 만큼, 더 이른 시점부터 결과를 판단해야 한다. 그래프: 가로축 업무 시간, 세로축 결과물 완성도(배포 가능 선). 예전 곡선은 "빈 파일"에서 시작해 천천히 올라간다. 현재 곡선은 "AI가 만든 초안"에서 높게 시작하고, "검토하면서 문제를 발견(틀린 가정과 빠진 조건을 찾는다)"에서 한 번 내려갔다가 "판단한 뒤 수정"으로 다시 올라가 배포 가능 선에 먼저 닿는다. 결론: 구현의 시작점은 높아졌고, 판단의 시작점은 앞당겨졌다.

## 14~21장. 공부 방법 01 — 운영하기

**AI의 시대.** 구현을 위한 지식에서 판단을 위한 지식으로. 대학생때 기술을 공부하는 방법.

**대학생때의 공부 방법.** (전환 슬라이드)

**01. 만드는 것보다 운영해보는 것.** 기술의 숨은 제약은 실제 사용자를 통해서 드러난다.

**만들기와 운영하기.**
- 만들기: 정상 경로에서 동작한다.
- 운영하기: 데이터와 사용 방식이 변해도 계속 동작한다.
- 완성은 기술 공부의 끝이 아니라 관찰을 시작할 수 있는 상태다.

**운영하기를 통한 학습.** (전환 슬라이드)

**운영하기에서 배울 수 있는 것.**
- 예상하지 못한 입력과 사용 방법
- 데이터 증가에 따른 성능 변화
- 동시 실행과 재시도
- 각종 장애 처리

**운영하기에 대한 오해 #1 — 사용자가 많아야 운영이다.**
- 중요한 것은 사용자 수보다 실제로 반복해서 사용되는가이다.
- 사용자가 3~4명도 충분함.
- 나 자신이 매일 사용해야 한다.
- 나와 다른 방식으로 사용하는 사람이 있다면 더 좋다.
- 같은 기능을 반복해서 사용해야 불편과 예외 상황이 보인다.

**운영하기에 대한 오해 #2 — 배포만 하면 운영이다.**
- 서비스를 배포한 것과 운영은 다르다.
- 다음 질문들에 대해서 답할 수 있어야 함.
  - 지금 정상적으로 동작하고 있는가?
  - 응답이 느려지고 있지는 않은가?
  - 오류는 얼마나 발생하는가?
  - CPU, Memory, Disk 등의 자원 사용량은 얼마인가?
- 운영은 기능 추가가 아니라, 안정적인 기능을 계속 유지하는 것

## 22~26장. 역할 변화와 판단 능력

**AI가 유능해질수록 채택한 사람의 책임은 커진다.** 무엇을 맡기고, 어느 결과를 믿고, 언제 배포할지 사람이 결정한다.

**역할 변화 — 벤치마크와 실제 개발.**
- 벤치마크: 문제와 성공 조건이 주어진다.
- 실제 개발: 무엇을 성공으로 볼지 정해야 한다.
- AI는 주어진 문제를 잘 푼다. 개발자는 풀 문제를 정한다.

**역할 변화 — 개발자가 내려야 하는 판단.**
- 이 문제를 AI에게 맡겨도 되는가
- 결과가 우리 데이터와 운영 조건에 맞는가
- 실패 가능성을 어디까지 확인해야 하는가
- 문제가 생기면 되돌릴 수 있는가
- 코드를 누가 작성했는지보다 누가 배포를 승인했는지가 중요하다.

**판단 능력을 키워야 한다.** 정답을 학습하는 것보다 자기의 생각을 만드는 시간이 필요하다.

**판단 능력을 키우기 위해서…** 틀린 답을 내는 것보다 너무 빨리 정답을 아는 것이 더 위험하다.

`[이미지]` DATABASE CAPACITY. "한 대의 DB 서버보다 데이터가 커지면?" 저장할 데이터 1.4 TB, DB 서버 디스크 용량 1.0 TB / 1.0 TB, 남은 0.4 TB가 서버 밖으로 밀려나 있다. (뒤 Neo4j 사례의 문제 상황을 미리 보여주는 그림)

## 28~37장. 공부 방법 02 — 판단을 위한 학습

**"AI에게 묻기 전에 내 예상을 먼저 적는다."** 판단을 위한 학습의 첫 번째 규칙.

**답을 보기 전에 적을 것.**
- 어떤 결과가 나올 것으로 예상하는가
- 왜 그런 결과가 나온다고 생각하는가
- 무슨 결과가 나오면 내 생각이 틀렸다고 인정할 것인가
- 오래 고민하라는 말이 아니라 검증 가능한 생각을 만들라는 뜻이다.

**판단을 만드는 학습 과정.** 1 현상 → 2 예상 → 3 가설 → 4 실험 → 5 근거 → 6 판단 수정. 검색과 AI는 가설을 만든 뒤에 사용한다.

**예상.** 실행하기 전에 결과를 한 줄로 적는다. 예상이 있어야 실제 결과와의 차이가 보인다.

**가설.** 원인을 하나 골라 설명해본다. 모든 가능성을 나열하지 말고 먼저 확인할 설명을 정한다.

**반증 조건.** 내 생각이 틀렸음을 보여줄 결과를 먼저 정한다. 맞는 증거만 찾는 습관에서 벗어나게 해준다.

**근거의 순서.**
- 작게 재현한 실행 결과
- 같은 조건을 반복한 테스트
- 공식 문서와 실제 코드
- 운영 환경에서 다시 관찰한 결과
- 설명보다 실행 결과가 강하고, 한 번의 결과보다 반복된 결과가 강하다.

**AI를 쓰는 시점.**
- 바로 질문: 생각 없이 답을 채택하기 쉽다.
- 가설 뒤 질문: 반례와 검증 방법을 비교할 수 있다.
- AI가 생각을 대신하지 않고 생각을 넓혀준다.

**AI에게 물어볼 질문.**
- 내 가설이 틀릴 수 있는 조건은 무엇인가
- 이 문제를 더 작게 재현하는 방법은 무엇인가
- 서로 다른 해결책이 감수하는 비용은 무엇인가
- 어느 공식 문서와 코드를 확인해야 하는가
- 좋은 질문은 이미 문제를 상당히 이해했다는 증거다.

**학습 목표.** 정답을 얻는 데서 끝내지 않고 내 판단을 수정한다. 처음 생각과 결과가 어떻게 달랐는지 기록할 때 경험이 지식으로 남는다.

## 38~52장. Neo4j 사례

**Neo4j를 공부하는 한 가지 방법.** 기능 목록부터 읽지 않고 운영에서 생긴 질문을 끝까지 따라간다.

**운영 중 생긴 문제.** Neo4j 한 대의 저장공간이 거의 가득 찼다. 서버를 한 대 더 추가하려고 한다.

**첫 번째 생각.** 노드를 절반씩 나누면 되지 않을까? 아직 문서를 보지 않고 자신이 생각한 가장 단순한 해결책부터 적는다.

**절반으로 나눈 뒤.**
- 얻은 것: 서버별 저장량이 줄었다.
- 새로 생긴 것: 서버를 넘는 간선이 생겼다.
- 저장공간 문제를 해결하면서 탐색 비용을 만들었다.

**서버 경계를 넘는 탐색.** (슬라이드 라벨은 "학습 사례")
- 질의: 사용자에서 구매한 상품을 따라간다.
- 배치: 사용자는 A, 상품은 B에 저장됐다.
- 실행: 간선을 따라갈 때 네트워크 요청이 필요하다.
- 그래프 탐색의 비용은 노드 수만으로 정해지지 않는다.

**두 번째 질문.** 서로 연결된 노드가 자주 함께 조회된다면? 균등한 저장보다 탐색의 지역성이 더 중요할 수 있다.

**분할 기준의 충돌.**
- 저장량 균등: 두 서버의 용량과 기본 부하를 맞춘다.
- 탐색 지역성: 자주 함께 찾는 노드를 같은 서버에 둔다.
- 두 목표를 동시에 완벽하게 만족시키기 어렵다.

**먼저 확인할 실제 질의.**
- 한 단계 이웃 조회가 대부분인가
- 여러 단계를 연속해서 탐색하는가
- 특정 종류의 노드 사이를 반복해서 오가는가
- 전체 그래프를 분석하는 작업이 있는가
- 그래프 구조만 보지 말고 서비스의 질의 기록을 본다.

**질문이 바뀌었다.** 어떻게 절반으로 나눌까에서 무엇을 함께 둘까로 바뀌었다. 이 순간부터 단순 분할이 그래프 파티셔닝 공부로 이어진다.

**Edge cut과 vertex cut.**
- 간선을 자른다: 노드는 한 곳에 두고 원격 간선을 만든다.
- 노드를 복제한다: 탐색을 줄이지만 동기화 비용이 생긴다.
- 분할 방법은 읽기와 쓰기의 비율에 따라 달라진다.

**슈퍼노드.** 연결이 몰린 노드 하나가 서버의 균형을 깨뜨린다. 유명 사용자나 인기 상품은 노드 수가 균등해도 부하를 한곳에 모은다.

**복제의 대가.**
- 읽기: 가까운 복제본에서 빠르게 탐색한다.
- 쓰기: 모든 복제본의 최신 상태를 맞춰야 한다.
- 읽기 성능을 얻는 대신 쓰기와 일관성 비용을 낸다.

**시간이 만든 문제.** 오늘의 좋은 분할이 다음 달에도 좋을까? 간선이 늘고 인기 노드가 바뀌면 데이터 이동과 재분할이 필요하다.

**이 질문으로 공부하게 된 것.**
- 그래프 파티셔닝과 지역성
- 서버 사이의 네트워크 비용
- 복제와 일관성
- 부하 집중과 데이터 재배치
- 제품 설명서를 외우지 않았지만 공부의 범위가 구체적으로 정해졌다.

**이제 AI에게 묻는다.**
- 처음부터: "Neo4j를 분산하는 법을 알려줘"
- 고민한 뒤: "이 질의 패턴에서 내 분할 가설의 반례를 찾아줘"
- 같은 AI라도 질문하는 사람이 만든 학습 결과는 다르다.

## 53~58장. 대학생의 장점과 마무리

**대학생은 실패하기 좋은 시기다.** 책임질 실제 고객은 적고, 잘못된 선택을 다시 해볼 시간은 상대적으로 많다.

**현업과 대학생의 실패.**
- 현업: 장애가 고객과 매출에 영향을 준다.
- 대학생: 안전한 환경에서 실패를 설계할 수 있다.
- 실패 비용이 낮다는 사실을 학습에 사용한다.

**학생이 직접 만들 수 있는 실패.**
- 프로세스를 중간에 종료한다
- 두 요청이 동시에 같은 데이터를 수정하게 한다
- 데이터를 백 배 늘려 다시 측정한다
- 캐시와 원본 값을 일부러 다르게 만든다
- 실패를 기다리지 않고 검증할 조건을 만든다.

**실패의 조건.** 예측과 기록이 없는 실패는 그냥 시행착오로 끝난다. 실패 전 예상, 실패 후 관찰, 다음 실험이 함께 있어야 한다.

**"학생 때 실패해도 된다는 말은 더 많이 검증해도 된다는 뜻이다."** 실패를 준비 자산으로 바꾸는 방법.
