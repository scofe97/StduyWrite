# 서비스 디스커버리와 relabeling
---

## 핵심 요약

> **서비스 디스커버리는 "무엇을 스크레이프할지" 를 알아 오는 절반일 뿐입니다.** 나머지 절반은 **relabeling** 이고 저자의 표현으로 마법은 전부 거기서 일어납니다.
>
> 디스커버리 프로바이더가 내주는 것은 후보 타깃 목록과 `__meta_` 접두사가 붙은 메타데이터 라벨 한 뭉치입니다. 이 라벨은 relabeling 이 도는 동안에만 보입니다. 무엇을 남기고(`keep`) 무엇을 버리며(`drop`) 어떤 라벨을 어디서 가져다 붙일지(`replace`) 정하는 일이 relabeling 이고 그 결과가 실제 스크레이프 대상이 됩니다.
>
> relabeling 은 두 번 돕니다. 표준 relabeling 은 스크레이프 **전에** 돌아 대상을 고르고 메트릭 relabeling 은 스크레이프 **후 저장 전에** 돌아 시계열을 버리거나 고칩니다. 이 두 시점을 헷갈리면 "왜 타깃이 안 잡히지" 와 "왜 이 시계열이 계속 쌓이지" 를 영영 같은 곳에서 찾게 됩니다.



## 학습 목표

> 이 절을 읽고 나면 아래 여섯 가지를 스스로 해낼 수 있습니다.

1. 표준 relabeling 과 메트릭 relabeling 이 각각 언제 도는지 말하고 문제를 어느 쪽에서 찾을지 고를 수 있습니다.
2. Prometheus Operator 환경에서 Kubernetes SD 와 그 밖의 SD 가 서로 다른 경로로 설정에 들어간다는 사실을 설명할 수 있습니다.
3. 두 relabeling 을 설정 파일의 절 이름과 Operator CR 의 필드 이름으로 각각 짚을 수 있습니다.
4. `/targets` 와 `/service-discovery` 페이지 중 무엇으로 relabeling 을 디버깅할지 판단할 수 있습니다.
5. SD 프로바이더가 `Discoverer` 인터페이스를 어떻게 구현하는지, 왜 `__address__` 외의 라벨을 내주지 않는지 말할 수 있습니다.
6. 자체 소스에서 타깃을 가져와야 할 때 `http_sd` 엔드포인트를 설계할 수 있습니다.



## 1. 왜 서비스 디스커버리인가

> 클라우드 네이티브 환경에서는 타깃이 수시로 늘고 줄어, "무엇을 감시할지 미리 안다"는 전통적 전제가 무너집니다. SD 가 그 목록을 동적으로 채웁니다.

전통적인 모니터링 환경에서는 관리자가 무엇을 감시할지 미리 알고 있거나 push 기반 시스템을 설정해 두어야 했습니다. 감시 대상 서버와 장비가 자주 바뀌지 않았으니 대상 추가·제거에 설정 변경이 따라붙는 편이 받아들일 만했습니다. 애플리케이션 인스턴스가 수시로 늘고 줄고 교체되는 클라우드 네이티브 환경에서는 그 전제가 무너집니다.

**Prometheus 는 이 문제를 서비스 디스커버리로 풉니다.** 

- 스크레이프 타깃을 동적으로 가져와 추가하는 방법을 **두 다스 넘게** 제공합니다. 
- AWS·Azure·Akamai(Linode) 같은 클라우드 프로바이더부터 Docker 와 Kubernetes 를 거쳐 파일 기반이나 범용 HTTP 디스커버리 같은 수동에 가까운 구성까지 폭이 넓습니다.

설정 파일에서 각 프로바이더는 스크레이프 잡 안의 `<type>_sd_configs` 라는 이름 규칙을 따르는 절에 들어갑니다. `kubernetes_sd_configs`, `azure_sd_configs` 같은 식입니다.

여기서 SD 가 무엇을 하는 장치인지 먼저 갈라 둘 필요가 있습니다. Prometheus 가 메트릭을 모으려면 **어디로 갈지**와 **거기서 무엇을 받을지** 두 가지를 알아야 하는데, SD 는 앞쪽만 담당합니다.

![서비스 디스커버리는 주소 목록만 주고 메트릭 값은 각 앱의 exporter 가 낸다. 둘은 서로를 대신할 수 없다](../_assets/04-01.list-vs-value.svg)

- SD 프로바이더가 돌려주는 것은 `10.0.1.5:8080` 같은 **주소 목록**입니다. 값은 하나도 들어 있지 않습니다. 값은 그 주소로 실제 요청이 갔을 때 각 앱의 exporter 가 응답합니다.

둘은 서로를 대신할 수 없습니다. 인벤토리 시스템은 서버가 몇 대인지 알지만 남의 JVM 힙 사용량을 알 도리가 없고, 앱은 자기 상태를 알지만 옆 서버가 몇 대인지 모릅니다. 그래서 "목록을 아는 쪽"과 "값을 아는 쪽"에 각각 따로 물어봅니다.

이 구분이 흐려지면 "인벤토리에서 메트릭을 직접 보내면 되지 않나" 라는 방향으로 새기 쉽습니다. Prometheus 는 pull 모델이므로 **긁으러 갈 주소를 먼저 알아야** 하고, 그 목록을 얻는 단계가 서비스 디스커버리입니다.



## 2. Operator 환경에서 SD 가 들어가는 두 경로

> Kubernetes SD 는 Operator 가 CRD 를 보고 자동 생성합니다. 그 밖의 SD 는 `additionalScrapeConfigs` 로 직접 넣습니다. 경로가 갈립니다.

2장에서 세운 Prometheus Operator 환경에서는 설정 파일을 직접 만지지 않습니다. Kubernetes 에서 오지 **않는** 모든 종류의 서비스 디스커버리는 Prometheus CRD 의 `additionalScrapeConfigs` 필드로 들어갑니다. 이름 그대로입니다.

Kubernetes SD 는 다릅니다. Operator 가 `ServiceMonitor`·`PodMonitor`·`Probe` 리소스를 보고 `kubernetes_sd_configs` 절과 그에 딸린 스크레이프 잡을 설정 파일에 알아서 만들어 줍니다. 사용자는 CRD 만 쓰고 Operator 가 SD 설정으로 번역합니다.

![Operator 환경에서 SD 설정이 들어가는 두 경로 — CRD 는 Operator 가 번역하고 additionalScrapeConfigs 는 그대로 이어붙는다](../_assets/04-01.operator-two-paths.svg)

두 경로는 **번역 단계가 있느냐**로 갈립니다. 왼쪽은 사용자가 selector 같은 쿠버네티스 어휘로 쓰면 Operator 가 그것을 SD 문법으로 옮겨 줍니다. 오른쪽에는 옮겨 줄 사람이 없으므로 사용자가 처음부터 SD 문법으로 씁니다.

`additionalScrapeConfigs` 는 YAML 을 직접 받지 않고 **Secret 의 키를 가리킵니다.**[^promop-additional] 스크레이프 잡에는 클라우드 API 자격증명이 섞여 들어가기 쉬우므로, 평문 필드가 아니라 Secret 을 거치게 한 설계입니다.

두 경로의 결과는 결국 한 파일에서 만납니다. Operator 가 생성한 잡과 사용자가 적은 잡을 이어붙여 하나의 `prometheus.yaml` 을 만들고, 그것을 Secret 에 넣으면 config-reloader 사이드카가 변경을 감지해 Prometheus 에 재적재합니다.

kube-prometheus 가 Node Exporter 를 위해 기본으로 만드는 `ServiceMonitor` 가 그 예입니다.

```yaml
# kubectl --context kind-k8s-lab -n mon-lab get servicemonitor kube-prom-prometheus-node-exporter -o yaml

apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: mastering-prometheus-prometheus-node-exporter
  namespace: prometheus                # 이 CR 이 사는 네임스페이스
spec:
  attachMetadata:
    node: false                        # 노드 메타데이터를 라벨로 붙이지 않음
  endpoints:
    - port: http-metrics               # Service 에 정의된 포트 "이름" (번호 아님)
      scheme: http
  jobLabel: jobLabel                   # 이 라벨의 "값" 이 최종 job 라벨이 됨
  selector:
    matchLabels:                       # 이 두 라벨이 다 붙은 Service 만 대상
      app.kubernetes.io/instance: mastering-prometheus
      app.kubernetes.io/name: prometheus-node-exporter
```

- 이 한 장은 Operator 에게 세 가지를 시킵니다. 두 라벨이 붙은 서비스를 찾고 발견한 서비스의 `jobLabel` 라벨 값으로 Prometheus 잡 이름을 짓고 `http-metrics` 라는 이름의 포트로 스크레이프하라는 지시입니다.
- `port` 가 번호가 아니라 **이름**이라는 점은 짚어 둘 만합니다. 파드가 옮겨 다니며 포트 번호가 바뀌어도 이름은 그대로이므로, 이름으로 걸어 두면 CR 을 고칠 일이 없습니다. `jobLabel` 은 `job` 라벨을 덮어쓰는 규칙으로 번역되며(§8), 시계열을 찾을 때 쓰는 이름이 여기서 정해집니다.





## 3. relabeling 은 두 번 돈다

> 표준 relabeling 은 스크레이프 **전**에 돌아 타깃을 고르고, 메트릭 relabeling 은 스크레이프 **후 저장 전**에 돌아 시계열을 거릅니다.
>
> 문제를 어느 쪽에서 찾을지가 이 시점으로 갈립니다.

Prometheus 의 relabeling 은 표준 relabeling 과 메트릭 relabeling 두 종류입니다. 목적이 다르고 스크레이프 과정의 서로 다른 시점에 일어납니다.

![표준 relabeling 은 스크레이프 전에 타깃을 거르고 메트릭 relabeling 은 저장 전에 시계열을 거른다](../_assets/04-01.relabeling-pipeline.svg)

두 단계가 **버리는 대상이 다릅니다.** 앞은 타깃을, 뒤는 시계열을 거릅니다. 도식의 수량은 쿠버네티스 환경의 전형적인 규모를 잡은 것입니다.

`static_configs` 로 타깃을 직접 적을 때는 걸러 낼 것이 없습니다. 적은 것이 곧 감시 대상이니까요. SD 는 다릅니다. **묻는 것이지 아는 것이 아니어서**, `role: pod` 로 물으면 coredns 부터 남의 팀 배치 잡까지 클러스터의 파드가 전부 후보로 들어옵니다. 그중 메트릭 엔드포인트가 있는 것은 일부이고, 나머지를 긁으면 연결 거부나 404 로 `up=0` 이 수백 개 쌓입니다.

그래서 SD 를 쓰는 쪽은 목록이 아니라 **조건**을 적습니다. "이것들을 긁어라" 대신 "이런 것을 긁어라" 를 쓰는 자리가 표준 relabeling 입니다. 

- 목록이 계속 변하는 환경에서 사람이 목록을 관리할 수 없으니 조건으로 옮긴 셈입니다.

이름이 둘 다 `relabel` 인 것은 역사적 사정입니다. 

- 원래는 라벨을 옮겨 담는(re-label) 기능이었고, 나중에 "라벨 값을 보고 버린다" 는 `keep`·`drop` 액션이 같은 규칙 문법에 붙었습니다. 
- 지금은 필터링이 주 용도인데 이름은 그대로 남았습니다.

**표준 relabeling** 은 타깃이 스크레이프되기 **전에** 돕니다. 

- 서비스 디스커버리 프로바이더를 추가로 설정하는 자리이고 발견된 스크레이프 타깃에 라벨을 붙이거나 스크레이프할 타깃을 걸러 냅니다.

**메트릭 relabeling** 은 스크레이프가 일어난 **후**, 시계열이 청크에 저장되기 **전에** 돕니다. 

- 여러 기준으로 시계열을 버리거나 고치는 자리입니다. 이쪽은 7장의 카디널리티 문제에서 다시 나옵니다.

둘의 정의 방식은 비슷합니다. 소스 라벨 목록을 받아 거기에 어떤 액션을 수행하는 형태입니다. 어떤 설정 항목이 있는지는 [설정 문서](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)가 정본입니다.

Prometheus 답게, 서비스 디스커버리에서 얻는 것은 결국 라벨 한 집합입니다. 모든 SD 프로바이더는 `__meta_$provider_` 접두사가 붙은 여러 라벨에 메타데이터를 잔뜩 실어 보내며 **이 라벨은 relabeling 중에만 접근할 수 있습니다**.[^prom-meta-labels]



## 4. 규칙 하나는 무엇으로 이루어지나

> 규칙은 부품 넷(`source_labels`·`regex`·`action`·`target_label`)으로 이루어지고, 여러 개일 때는 목록이 아니라 **순서 있는 파이프라인**입니다.
>
> 후보 수를 바꾸는 액션은 `keep`·`drop` 둘뿐입니다.

규칙 하나는 부품 넷으로 이루어집니다.

| 필드 | 뜻 | 생략하면 |
|---|---|---|
| `source_labels` | 어떤 라벨의 값을 볼 것인가 | 읽을 값이 없음 — `replacement` 가 상수로 쓰임 |
| `regex` | 그 값이 이 패턴에 맞는가 | `(.*)` — 무엇이든 매칭 |
| `action` | 맞으면 무엇을 할 것인가 | `replace` |
| `target_label` | (`replace` 일 때) 어느 라벨에 쓸 것인가 | — |

`source_labels` 가 여럿이면 값들이 `separator`(기본 `;`)로 이어져 **하나의 문자열**이 되고, `regex` 는 그 이어붙인 문자열에 걸립니다. `(kube-prom);true` 같은 정규식이 그래서 나옵니다.

액션은 여럿이지만 실무에서 쓰는 것은 다섯입니다. **후보 수를 바꾸는 것과 안 바꾸는 것으로 갈립니다.**

| 액션 | 하는 일 | 후보 수 | 언제 |
|---|---|---|---|
| `keep` | 매칭되는 것만 남김 (allow-list) | **줄어듦** | 긁을 것을 고를 때 |
| `drop` | 매칭되는 것을 버림 (deny-list) | **줄어듦** | 특정 대상을 뺄 때 |
| `replace` | 읽은 값을 `target_label` 에 씀 | 안 바뀜 | `__meta_` 를 일반 라벨로 승격할 때 |
| `labeldrop` | `regex` 에 맞는 **라벨 이름**을 지움 | 안 바뀜 | 카디널리티를 줄일 때 |
| `labelkeep` | `regex` 에 맞는 라벨만 남김 | 안 바뀜 | 위와 같으나 allow-list |

`keep` 과 `drop` 은 서로 반대이므로 하나로 같은 일을 표현할 수 있습니다. "prod 만" 은 `keep(regex: prod)` 이고 `drop(regex: dev|staging)` 이기도 합니다. **정규식이 단순해지는 쪽**을 고르는 것이 관례입니다.

`labeldrop` 과 `replace` 를 헷갈리기 쉽습니다. `replace` 는 **값**을 옮기고, `labeldrop` 은 **라벨 자체**를 없앱니다. 그리고 `labeldrop` 의 `regex` 는 라벨 *값*이 아니라 라벨 *이름*에 걸립니다 — `source_labels` 를 쓰지 않는 이유입니다.

규칙이 여러 개일 때 이들은 목록이 아니라 **순서 있는 파이프라인**입니다. 각 규칙이 앞 규칙을 통과한 후보만 보고, 통과한 것이 다음 규칙으로 넘어갑니다.

![relabel 규칙이 후보 500 개를 120 개, 40 개로 줄이고 마지막 replace 규칙은 수를 바꾸지 않는다](../_assets/04-01.relabel-filter-funnel.svg)

도식의 세 단계를 코드로 옮기면 이렇습니다. 규칙을 적은 순서가 그대로 실행 순서입니다.

```yaml
relabel_configs:
  # 1. 500 에서 120 으로 — 어노테이션이 붙은 파드만 남긴다
  - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
    regex: "true"
    action: keep

  # 2. 120 에서 40 으로 — 죽은 파드를 뺀다
  - source_labels: [__meta_kubernetes_pod_phase]
    regex: (Failed|Succeeded)
    action: drop

  # 3. 40 에서 40 으로 — 수는 그대로, 라벨만 붙는다
  - source_labels: [__meta_kubernetes_namespace]
    target_label: namespace
```

수를 줄이는 것은 `keep` 과 `drop` 뿐입니다. 세 번째는 `replace`(기본 액션)라서 후보 40 개가 그대로 40 개로 남고, 바뀌는 것은 라벨의 **값**입니다.

**규칙을 뒤집으면 결과가 달라집니다.** 2 번을 1 번 위로 올리면 어노테이션 없는 파드까지 phase 검사를 거치므로 계산이 늘고, 반대로 3 번을 맨 위로 올리면 나중에 버려질 460 개에도 라벨을 붙이는 헛일을 합니다. **거르는 규칙을 앞에, 라벨을 붙이는 규칙을 뒤에** 두는 것이 관례인 이유입니다.

이 구분이 디버깅에서 갈림길이 됩니다. 타깃 수가 예상과 다르면 `keep`·`drop` 의 정규식을 봅니다. 수는 맞는데 라벨 값이 이상하면 `replace` 규칙을 봅니다.



## 5. 적는 자리가 둘 — 설정 파일과 ServiceMonitor

> 같은 규칙을 설정 파일(`relabel_configs`, snake_case)과 `ServiceMonitor`(`relabelings`, camelCase) 두 곳에 적을 수 있습니다.
>
> 규칙을 배우려면 앞쪽, 운영하려면 뒤쪽입니다.

같은 relabeling 을 적을 수 있는 자리가 둘입니다. 문법도 다르고 **보이는 것**도 다릅니다.

| | 설정 파일 (`scrape_configs`) | Operator 오브젝트 (`ServiceMonitor`) |
|---|---|---|
| 표기 | `relabel_configs`·`metric_relabel_configs` | `relabelings`·`metricRelabelings` |
| 이름 규칙 | snake_case | camelCase |
| 규칙을 쓰는 주체 | **사람** | 사람이 일부, **Operator 가 나머지** |
| 최종 설정에 규칙 몇 개 | 내가 쓴 것만 | 내가 쓴 것 + Operator 생성분 |
| SD 설정 | 내가 `kubernetes_sd_configs` 를 씀 | Operator 가 selector 를 번역해 만듦 |
| 어디에 유리한가 | 규칙 전체가 눈에 보임 | 운영. 반복이 없고 CR 만 관리 |

**규칙을 배우려면 앞쪽, 운영하려면 뒤쪽입니다.** 뒤쪽은 Operator 가 대신 써 주는 규칙이 많아(실측 20개 중 13개가 Operator 생성분) 내가 쓴 두 줄이 어디서 작동하는지 보이지 않습니다. 앞쪽은 내가 쓴 것이 전부라 파이프라인이 그대로 드러납니다.

Operator 환경에서 앞쪽 방식을 쓰려면 `additionalScrapeConfigs` 통로가 있습니다(§2). 그래서 두 방식이 배타적이지 않고, 한 Prometheus 안에 나란히 놓입니다.

설정 파일을 직접 쓰는 환경에서 둘은 같은 스크레이프 잡 안에 나란히 놓입니다. 이름이 비슷해 헷갈리지만 `metric_` 접두사가 붙은 쪽이 스크레이프 **후**입니다.

```yaml
scrape_configs:
  - job_name: k8s-pods
    kubernetes_sd_configs:
      - role: pod                       # 후보를 가져오는 자리
      
    relabel_configs:                    # 스크레이프 전 — 타깃을 고름
      - source_labels: [__meta_kubernetes_pod_annotation_prometheus_io_scrape]
        regex: "true"
        action: keep                    # 이 애너테이션이 true 인 파드만
        
    metric_relabel_configs:             # 스크레이프 후 — 시계열을 버림
      - source_labels: [__name__]
        regex: go_gc_duration_seconds.* # 안 볼 메트릭 이름
        action: drop
```

이 방식에서 `relabel_configs` 는 **후보를 거르는 조건**이고 `metric_relabel_configs` 는 **저장할 시계열을 고르는 조건**입니다. 규칙이 넷이면 최종 설정에도 넷이고, 그 사이에 아무것도 끼어들지 않습니다.



## 6. Operator 는 내가 적은 규칙 앞에 자기 규칙을 붙인다

> 같은 두 절이 CR 에서는 `relabelings`·`metricRelabelings` 필드입니다. Operator 가 이를 설정 파일로 번역하면서 자기 규칙을 앞에 붙입니다.
>
> 두 줄을 적었는데 최종 설정에는 **20개**가 됩니다.

Operator 환경에서는 이 두 절을 직접 쓰지 않습니다. 각각 CR 의 필드로 올라가 있고 Operator 가 앞 절의 YAML 로 번역합니다.

| 설정 파일의 절 | Operator 오브젝트의 필드 | 사는 곳 | 도는 시점 |
|---|---|---|---|
| `relabel_configs` | `relabelings` | `ServiceMonitor`·`PodMonitor` 의 `spec.endpoints[]` | 스크레이프 전 |
| `metric_relabel_configs` | `metricRelabelings` | 같은 `spec.endpoints[]` | 스크레이프 후·저장 전 |

- 공식 API 레퍼런스가 `metricRelabelings` 를 "RelabelConfig to apply to samples before ingestion" 으로 적습니다.[^promop-relabel] 
- 두 필드 모두 엔드포인트마다 따로 두므로, 한 `ServiceMonitor` 가 포트를 여러 개 노출하면 포트별로 다른 규칙을 걸 수 있습니다.

§2 의 `ServiceMonitor` 에 두 relabeling 을 더하면 이렇게 됩니다.

```yaml
spec:
  endpoints:
    - port: http-metrics

      # ── 스크레이프 전 ──
      relabelings:
        # 메타 라벨 값을 일반 라벨로 승격한다.
        - sourceLabels: [__meta_kubernetes_service_label_jobLabel]
          targetLabel: job

        # sourceLabels 가 없으면 replacement 값이 상수로 붙는다.
        # 읽을 라벨이 없으니 모든 타깃에 같은 값이 박힌다.
        - targetLabel: scrape_via
          replacement: servicemonitor

      # ── 스크레이프 후·저장 전 ──
      metricRelabelings:
        # node_scrape_collector_* 계열을 버린다.
        - sourceLabels: [__name__]
          regex: node_scrape_collector_.*
          action: drop
```

- 두 번째 `relabelings` 규칙이 `sourceLabels` 없이 `targetLabel`·`replacement` 만 씁니다. 
- 읽을 라벨이 없으므로 **모든 타깃에 같은 값을 상수로** 붙입니다. `job` 이 덮어써져 구별이 안 될 때 어느 설정에서 온 시계열인지 표시하는 관용입니다.

**Operator 는 사용자가 적은 규칙을 자기가 만든 규칙 뒤에 이어붙입니다.** selector 를 옮긴 `keep` 규칙이 먼저 돌고 사용자 규칙이 그다음이므로, 이미 버려진 후보를 사용자 규칙으로 되살릴 수는 없습니다.

그래서 최종 설정의 규칙 수가 CR 에 적은 것보다 훨씬 많아집니다. 위처럼 두 줄을 적었을 때 실제 생성된 `relabel_configs` 는 **20개**였고 그 배치가 이랬습니다.

```
 1~13.  Operator 생성분   keep 3 · 라벨 승격 7 · drop 1 · job 덮어쓰기 1 · endpoint 1
14~15.  사용자 규칙       위 두 줄
16~20.  샤딩 규칙         __tmp_hash 계열 (Prometheus 여러 대로 나눌 때, 6장)
```

사용자 규칙이 Operator 생성분 뒤인 것은 맞지만 **맨 뒤는 아닙니다.** 샤딩 규칙이 그 뒤에 붙습니다. 동작에는 영향이 없으나 "내가 쓴 것이 마지막"이라고 가정하면 어긋납니다.



## 7. 자리에 따라 읽을 수 있는 라벨이 다르다

> `__meta_` 는 표준 relabeling 이 끝나면 사라지고, `__name__` 은 스크레이프 전에는 없습니다.
>
> 잘못된 자리에 적어도 **오류가 나지 않아** 조용히 지나갑니다.

같은 규칙을 어느 필드에 적느냐로 **읽을 수 있는 라벨이 갈립니다.** `__meta_` 는 표준 relabeling 이 끝나면 제거되므로(§심화), 메트릭 relabeling 에서는 접근이 불가능합니다.

```yaml
metricRelabelings:
  - sourceLabels: [__meta_kubernetes_pod_name]   # 이미 사라진 라벨
    targetLabel: from_meta
```

이 규칙은 **오류를 내지 않습니다.** 문법이 유효하고 적용도 되고 설정에도 들어갑니다. 그저 읽을 라벨이 없어 빈 문자열이 되고, 빈 값은 라벨로 붙지 않아 `from_meta` 가 아예 생기지 않습니다. 실측에서 라벨 값 목록이 비어 있는 것으로 확인됩니다.

| | `relabelings` | `metricRelabelings` |
|---|---|---|
| `__meta_*` | **읽을 수 있음** | 이미 제거됨 |
| `__address__` | 읽고 쓸 수 있음 | 제거됨 |
| `__name__` | 아직 없음(스크레이프 전) | **읽을 수 있음** |
| 일반 라벨(`job`·`instance`) | 읽고 쓸 수 있음 | 읽고 쓸 수 있음 |

세 번째 줄이 짝을 이룹니다. `__name__` 은 반대로 **스크레이프 전에는 없습니다** — 메트릭을 받아 오기 전이니 이름이 있을 수 없습니다. 그래서 메트릭 이름으로 거르는 일은 `metricRelabelings` 에서만 됩니다.

**두 필드는 같은 문법을 쓰지만 볼 수 있는 것이 다릅니다.** 오류가 안 나므로 잘못된 자리에 적어도 조용히 지나갑니다.

범위도 갈립니다. `metric_relabel_configs` 는 **그 잡이 긁어온 메트릭에만** 걸립니다. 같은 이름의 메트릭이 클러스터 다른 잡에 있어도 건드리지 않습니다.

```pseudocode
# 규칙을 건 잡
count({job="my-job", __name__=~"go_gc_duration_seconds.*"})   → 0

# 같은 메트릭이 다른 잡에는 그대로 남습니다
count({__name__=~"go_gc_duration_seconds.*"})                 → 140
```

그래서 대상이 그 메트릭을 내지 않는 잡에 규칙을 걸면 **효과가 0** 입니다. 문법은 유효하고 설정에도 들어가지만 버릴 것이 없습니다. 규칙을 적었다는 사실만으로 카디널리티가 줄었다고 보면 안 되고, **적용 전후를 세어 봐야** 합니다.

```pseudocode
count({job="my-job"})                       # 전체
count({job="my-job", __name__=~"버릴패턴"})   # 버릴 대상
```



## 8. 라벨 하나가 시계열을 가른다

> `jobLabel` 이 `job` 을 덮어쓰는 규칙으로 번역됩니다. 그래서 설정 파일에 적힌 잡 이름으로는 시계열이 잡히지 않습니다.

§2 에서 `jobLabel: jobLabel` 이 `job` 라벨을 덮어쓰는 규칙으로 번역된다고 했습니다. 그 규칙이 실제로 둘입니다.

```yaml
# 1차 — Service 이름으로. regex 가 없으니 무조건 발동합니다
- source_labels: [__meta_kubernetes_service_name]
  target_label: job

# 2차 — jobLabel 라벨 값이 있으면 다시 덮어씁니다
- source_labels: [__meta_kubernetes_service_label_jobLabel]
  regex: (.+)
  target_label: job
```

- `regex: (.+)` 가 "값이 있을 때만"을 표현합니다. 소스 라벨이 비어 있으면 매칭에 실패해 그 규칙을 건너뛰므로, `jobLabel` 을 지정하지 않았다면 **1차 결과(Service 이름)가 최종값**으로 남습니다.

그래서 설정 파일에 적힌 잡 이름으로는 시계열이 잡히지 않습니다.

```bash
$ promtool query instant 'count({job="serviceMonitor/mon-lab/kube-prom-prometheus-node-exporter/0"})'
[]                                              # 빈 결과

$ promtool query instant 'count({job="node-exporter"})'
[{"metric":{},"value":[...,"4966"]}]            # jobLabel 값으로 찾아야 나옵니다
```

- 중간값도 남지 않습니다. `job` 라벨 값 목록에 Service 이름(`kube-prom-prometheus-node-exporter`)이 **없습니다** — 1차 결과가 2차에 완전히 덮였다는 뜻입니다.
- 저자의 클러스터에서는 이 숫자가 2,234 였습니다. 노드 수와 exporter 버전에 따라 달라지므로 값 자체보다 **"긴 이름으로는 0, 짧은 이름으로는 전부"** 라는 대비가 요점입니다.



## 9. relabeling 디버깅 — 두 화면

> 타깃이 아예 없으면 `/service-discovery`, 있는데 DOWN 이면 `/targets` 의 `lastError` 를 봅니다.
>
> `up=0` 은 "실패했다"만 말하고 이유는 말하지 않습니다.

타깃의 라벨 값이 어디서 정해졌는지가 늘 분명하지는 않습니다. Prometheus 는 두 개의 화면을 줍니다.

`/targets` 페이지(헤더의 Status 드롭다운)에서 타깃의 라벨에 마우스를 올리면 relabeling **전에** 어떤 메타데이터 라벨이 붙어 있었는지 보입니다.

`/service-discovery` 페이지는 어떤 타깃이 발견됐고 그중 무엇이 버려졌는지 보여 줍니다. relabeling **전후** 라벨을 나란히 보여 주므로 `/targets` 를 대체할 수 있습니다. 저자는 서비스 디스커버리 디버깅에서 이쪽이 훨씬 쓸모 있었다고 적었습니다.

두 화면이 답하는 질문이 다릅니다.

| 증상 | 어느 화면 | 무엇을 보는가 |
|---|---|---|
| 타깃이 **아예 없다** | `/service-discovery` | 발견 목록에 있나. 있으면 버려진 이유 |
| 타깃은 있는데 **DOWN** | `/targets` | `lastError` 문구 |
| 라벨 값이 예상과 다르다 | `/service-discovery` | relabeling 전후 대조 |

**`up=0` 은 "실패했다"만 말하고 왜 실패했는지는 말하지 않습니다.** `lastError` 를 읽어야 갈립니다.

| `lastError` | 뜻 | 볼 곳 |
|---|---|---|
| `connection refused` | 그 주소·포트에서 **아무도 듣지 않음** | 대상의 바인딩 주소 |
| `404 Not Found` | 서버는 있는데 **경로가 틀림** | `metrics_path` |
| `context deadline exceeded` | 응답이 **느림** | `scrape_timeout`, 대상 부하 |
| `no such host` | **DNS 실패** | 주소 표기 |

`connection refused` 가 kubeadm 계열 클러스터에서 특히 자주 나옵니다. 컨트롤 플레인 구성요소가 메트릭을 **루프백에만** 바인딩하기 때문입니다.

```
kube-controller-manager   --bind-address=127.0.0.1
kube-scheduler            --bind-address=127.0.0.1
etcd                      --listen-metrics-urls=http://127.0.0.1:2381
kube-proxy                metricsBindAddress: ""        # 빈 값이면 루프백
```

`127.0.0.1` 은 그 컨테이너 자신이므로 다른 파드에서 오는 Prometheus 는 닿지 못합니다. **설정 실수가 아니라 보안 기본값입니다.** 그래서 kube-prometheus-stack 을 갓 설치하면 이 넷이 DOWN 인 채로 보이고, 감시하려면 대상 쪽 바인딩을 열어 줘야 합니다.

여기서 구분이 중요합니다. **ServiceMonitor 와 relabeling 은 제 할 일을 다 했습니다** — 타깃을 발견하고 라벨을 붙여 스크레이프 목록에 올렸습니다. 실패는 그 다음 층, 대상이 그 주소에서 듣느냐에서 났습니다. `/service-discovery` 가 정상인데 `/targets` 가 DOWN 이면 relabeling 을 고칠 일이 아닙니다.



## 10. 프로바이더는 안에서 무엇을 하는가 — Linode 사례

> 모든 SD 프로바이더는 함수 하나짜리 `Discoverer` 인터페이스를 구현합니다. 
>
> Linode 는 이벤트 폴링으로 비싼 전체 조회를 아끼고, `__address__` 외의 라벨은 내주지 않습니다.

저자는 집필 시점에 Linode 에서 일했고 예전 동료(TJ Hoplock)가 Linode SD 프로바이더를 기여했다는 이유로 이 프로바이더를 뜯어 봅니다. 코드는 모두 Prometheus **2.46.0** 릴리스 기준입니다.

대부분의 디스커버리 프로바이더는 단순합니다. 디렉토리에 `.go` 파일이 한두 개뿐이고 전부 함수가 하나뿐인 `Discoverer` 인터페이스를 구현합니다.

```go
type Discoverer interface {
    // Run hands a channel to the discovery provider (Consul, DNS, etc.)
    // through which it can send updated target groups.
    Run(ctx context.Context, up chan<- []*targetgroup.Group)
}
```

Linode SD 는 `Run` 을 직접 짜지 않고 `refresh.Discovery` 타입에 위임합니다.

```go
d.Discovery = refresh.NewDiscovery(
    logger, "linode", time.Duration(conf.RefreshInterval), d.refresh,
)
```

- 네 번째 인자가 디스커버리 매니저가 `Run` 을 부를 때 실행할 갱신 함수입니다. Linode SD 의 갱신 함수는 곧장 전체 목록을 긁지 않습니다. 마지막 갱신 이후 계정에 이벤트가 있었는지부터 확인합니다. 기본 주기는 **60초**이고 이벤트는 VM 생성·삭제 같은 계정 활동을 뜻합니다. 이벤트가 없으면 목록을 다시 가져오지 않습니다.

여기에 안전장치가 하나 붙습니다. 이벤트 없는 갱신 주기가 **10번** 지나면 그래도 한 번 전체 갱신을 수행합니다. 이렇게 하는 이유는 Linode 와 IP 주소 전체를 나열하는 호출이 API 상 비싼 연산이기 때문입니다. 이벤트 API 는 싸고 빠르게 답합니다. 이벤트 읽기 권한이 없는 토큰을 쓰면 프로바이더가 이벤트 폴링을 스스로 끄고 매번 전체 갱신을 합니다. 저자는 권장하지 않는다고 못 박습니다.

전체 갱신이 일어나면 `[]*targetgroup.Group` 을 돌려줍니다.

```go
type Group struct {
    Targets []model.LabelSet   // 각 타깃은 address 라벨로 유일하게 식별됩니다
    Labels  model.LabelSet     // 그룹의 모든 타깃이 공유하는 라벨
    Source  string             // 타깃 그룹을 설명하는 식별자
}
```

- Prometheus 의 다른 모든 것과 마찬가지로 타깃 집합도 결국 라벨 집합입니다. Linode 프로바이더가 채우는 비-메타데이터 라벨은 `__address__` 하나뿐이며 Linode 의 공인 IP 에 포트를 붙인 값입니다(기본 80). 
- 나머지 라벨은 잡 설정에 적거나 relabeling 으로 붙여야 합니다. 이것은 Linode 만의 사정이 아닙니다. Prometheus 코드는 프로바이더가 `__address__` 와 `__meta_` 접두사 라벨 외에는 어떤 라벨도 노출해서는 안 된다고 명시합니다.



## 11. `http_sd` — 왜 생겼고 무엇을 지켜야 하는가

> 커스텀 프로바이더 PR 은 오래 막혀 있었습니다. 2019년 말 해제됐지만 여전히 "여러 조직이 쓰는 것" 만 받으므로, 사내 전용 소스를 위한 범용 `http_sd` 가 2021년 등장했습니다. 
>
> 엔드포인트가 지킬 것은 셋뿐입니다 — HTTP 200, `Content-Type: application/json`, UTF-8.

Prometheus 출시 후 몇 해 동안 커스텀 SD 프로바이더를 추가하는 PR 에는 모라토리엄이 걸려 있었습니다. 더 급한 일이 있는데 프로바이더를 유지보수하고 새 제출을 리뷰하는 부담이 컸던 탓입니다. **2019년 말** 그 모라토리엄이 풀렸고 프로바이더 수는 **11개에서 25개로** 크게 늘었습니다.

그렇다고 모든 것이 업스트림 프로바이더가 될 수는 없습니다. 새 프로바이더를 받아들이는 조건 하나가 "디스커버리 대상이 여러 조직에 걸쳐 널리 쓰이는 잘 정착된 것" 이어야 한다는 요구입니다. 회사나 개인에게만 있는 진실 공급원(source of truth)을 붙이고 싶은 사례는 남습니다.

과거에는 커스텀 디스커버리 로직을 cron 잡으로 돌려 파일을 뱉게 하고 `file_sd` 프로바이더로 읽는 우회가 쓰였습니다. 이상적인 방법이 아닙니다. 가시성이 떨어지는 다른 프로세스에 맡기느니 Prometheus 가 직접 디스커버리를 하는 편이 낫습니다. Prometheus 메인테이너 **Julien Pivotto** 가 **2021년** 범용 `http_sd` 를 도입했고 지금은 Prometheus 에 아직 없는 커스텀 디스커버리 로직을 구현하는 **권장 방법**입니다.

### 엔드포인트가 지켜야 할 것

`http_sd` 가 하는 일은 인벤토리 앞에 **번역기 하나를 두는 것**입니다. Prometheus 는 사내 스키마를 모르고 그 회사만을 위한 내장 프로바이더가 생길 일도 없으니, 대신 자기가 아는 JSON 모양으로 목록을 내주는 URL 을 요구합니다.

![http_sd 는 사내 인벤토리 앞에 두는 번역기이며 목록만 내주고 메트릭은 각 앱이 낸다](../_assets/04-01.http-sd-translator.svg)

번역기가 내놓는 것은 **주소 목록뿐**입니다. 메트릭은 여전히 각 앱이 냅니다. 방향도 여전히 pull 이어서 Prometheus 가 목록을 물어보러 오고 받은 주소마다 다시 긁으러 옵니다.

만들 때 지킬 요구사항은 셋뿐입니다.[^prom-httpsd]

- HTTP **200** 상태 코드를 반환할 것
- 응답에 `Content-Type: application/json` 헤더를 포함할 것
- 응답이 **UTF-8** 로 인코딩될 것

공식 문서가 하나를 덧붙입니다. 보낼 타깃이 하나도 없을 때도 **200 과 빈 배열 `[]`** 를 내야 합니다. Prometheus 는 타깃 목록을 캐시해 두고 갱신에 실패하면 **직전 목록을 계속 씁니다.** 그래서 엔드포인트가 오류로 답하면 "타깃이 사라졌다" 가 아니라 "옛 목록이 그대로 남는" 결과가 됩니다.

![오류로 답하면 갱신 실패로 읽혀 옛 목록이 남고, 빈 배열로 답하면 타깃이 제거된다](../_assets/04-01.empty-vs-error.svg)

갈리는 것은 **"없다" 와 "모른다" 의 구별**입니다. 빈 배열은 "조회했고 0 대였다" 이고, 오류는 "조회에 실패해 모른다" 입니다. Prometheus 는 후자일 때 옛 목록을 유지하는 쪽을 골랐습니다. 목록 서비스 장애가 감시 중단으로 번지지 않게 한 판단입니다. 그래서 서버가 정말 0 대일 때 오류로 답하면, 이미 내려간 서버를 계속 긁어 `up=0` 알림이 쏟아집니다.

이 캐시에는 **만료가 없습니다.** 메트릭 쪽 lookback delta 가 5 분이면 그 뒤 시계열이 사라지는 것과 다릅니다. 인벤토리 API 가 사흘간 죽어 있으면 사흘 전 목록을 그대로 씁니다 — 새로 뜬 서버는 안 잡히고 내려간 서버는 계속 긁힙니다. 스스로 포기하지 않으니 증상도 없습니다.

그래서 실패를 드러내는 일이 알림 하나에 걸려 있습니다. Prometheus 는 갱신 실패를 `prometheus_sd_refresh_failures_total` 카운터로 노출합니다.

```pseudocode
rate(prometheus_sd_refresh_failures_total[5m]) > 0
```

이것이 없으면 목록이 조용히 얼어붙습니다. [01-01](../01-01.관측%20가능성·모니터링·Prometheus의%20자리.md) 의 **조용한 실패**가 SD 층에서 되돌아오는 자리입니다.

응답 구조는 static config 와 같은 모양이되 YAML 대신 JSON 입니다. YAML 로 이렇게 쓰던 것을

```yaml
- targets:
    - web1.example.com:443
    - web2.example.com:443
  labels:
    component: website
    environment: production
```

JSON 으로 이렇게 돌려주면 됩니다.

```json
[{
  "targets": [ "web1.example.com:443", "web2.example.com:443" ],
  "labels": { "component": "website", "environment": "production" }
}]
```

저자는 Prometheus 가 Go 로 쓰였다는 이유로 Go 와 SQLite 로 예제를 만들지만 HTTP 요청에 응답할 수 있는 언어나 서비스라면 무엇이든 됩니다. 서버는 결국 두 줄입니다.

```go
func runHTTPServer() {
    http.HandleFunc("/targets", handler)
    http.ListenAndServe("0.0.0.0:8888", nil)
}
```

Prometheus 쪽 설정도 짧습니다.

```yaml
- job_name: http_sd_test
  http_sd_configs:
    - url: "http://http_sd:8888/targets"
```



## 12. `instance` 와 `__address__` 를 갈라 두는 이유

> `instance` 를 안 정하면 `__address__` 값이 그대로 들어갑니다. 접속은 IP 로 하되 `instance` 엔 사람이 읽는 이름을 넣으면, DNS 장애가 모니터링 장애로 번지지 않습니다.

Prometheus 는 숨은 `__address__` 라벨로 어느 호스트명 또는 IP 에 접속할지 정합니다. 대개 `instance` 와 `__address__` 는 같은 값입니다. 공식 문서의 표현대로 **relabeling 이 끝난 뒤에도 `instance` 가 정해지지 않았으면** `__address__` 값이 기본으로 들어가기 때문입니다.[^prom-instance]

고급 사례에서는 둘을 갈라 두는 편이 이롭습니다. 저자의 예제는 `instance` 라벨에 서버의 알아보기 쉬운 이름을 넣고 접속에는 IP 주소를 쓰게 합니다. 이렇게 하면 **DNS 때문에 생기는 모니터링 장애를 피하면서** 사람이 읽는 라벨은 그대로 남습니다.



## 심화 학습

> 책이 흐릿하게 남긴 지점과 공식 문서로 보강할 내용을 답니다.

책 밖에서 확인한 사실을 덧붙입니다.

**`__` 로 시작하는 라벨은 최종 시계열에 남지 않습니다.** 공식 문서의 문장은 "Labels starting with `__` will be removed from the label set after target relabeling is completed" 입니다.[^prom-meta-labels] `__meta_` 든 `__address__` 든 마찬가지입니다. relabeling 이 라벨 배정의 마지막 단계라서 앞 단계가 붙인 라벨을 전부 덮어쓸 수 있으며 그 결과로 남는 평평한 라벨 집합만 시계열에 붙습니다. 남기고 싶은 값은 relabeling 중에 `replace` 로 일반 라벨에 옮겨 담아야 합니다.

같은 문서가 규약 하나를 더 줍니다. relabeling 단계가 값을 **다음 단계의 입력으로만** 잠깐 보관해야 한다면 `__tmp` 접두사를 쓰라는 안내입니다. Prometheus 가 이 접두사를 내장 라벨에 절대 쓰지 않겠다("guaranteed to never be used by Prometheus itself")고 약속했으므로 이름 충돌을 걱정할 필요가 없습니다.[^prom-meta-labels]

디스커버리의 역사적 배경은 [Advanced service discovery (2015)](https://prometheus.io/blog/2015/06/01/advanced-service-discovery/) 가 잘 정리해 둡니다.

**본문의 "두 다스 넘게" 와 "25개" 는 집필 시점 값입니다.** 4장 첫머리는 "over two dozen different methods" 라 쓰고 `http_sd` 절에서는 모라토리엄 해제 후 프로바이더가 "11개에서 25개로" 늘었다고 적습니다. 앞의 표현이 뒤의 숫자를 반올림한 것이라 보면 어긋나지 않습니다.

다만 프로바이더 수는 릴리스마다 늘어납니다. 현행 [설정 문서](https://prometheus.io/docs/prometheus/latest/configuration/configuration/)의 `<*_sd_config>` 절을 세면 **31개**입니다(2026-08-03 확인). 책이 쓰인 뒤로도 계속 붙고 있는 셈입니다.

이 숫자는 확인한 날짜와 함께 읽어야 합니다. 세는 방법에 따라 값이 달라지기 때문입니다. `aws_sd_config` 는 `ec2`·`lightsail` 을 묶는 상위 항목이라 어떻게 세느냐에 따라 하나가 오갑니다. 지금 값이 필요하면 그 목록을 직접 세는 편이 확실합니다.

**`file_sd` 는 죽지 않았습니다.** 본문은 cron + `file_sd` 조합을 `http_sd` 이전의 우회로 소개하지만 파일을 쓰는 주체가 이미 신뢰할 만한 배포 도구(예: 구성 관리 시스템)라면 여전히 정당한 선택입니다. `http_sd` 가 이기는 지점은 "Prometheus 가 직접 물어본다" 는 가시성이지, 파일 방식이 틀렸다는 뜻은 아닙니다.

| 타깃이 몇 개뿐이고 변하지 않음 | `static_configs` | 디스커버리를 도입할 이유가 없습니다 |

| 증상 | 먼저 볼 곳 |
|------|-----------|
| 타깃이 아예 안 잡힌다 · 버려졌다 | `/service-discovery` — 표준 relabeling(스크레이프 전) |
| 잡 이름·라벨 값이 예상과 다르다 | `/service-discovery` 의 relabeling 전후 비교 |
| 시계열이 계속 쌓인다 · 카디널리티 폭발 | 메트릭 relabeling(스크레이프 후) — 7장 |



## Spring 앱 개발 관점

> 이 장의 SD 선택이 Spring 환경에서 어디로 떨어지는지입니다. K8s 면 `ServiceMonitor`, VM+Eureka 면 내장 `eureka_sd_configs`, 자체 소스면 `http_sd`.

**Kubernetes 위의 Spring Boot 는 이미 답이 나와 있습니다.** 2장 노트의 `ServiceMonitor` 를 그대로 쓰되 `path` 를 `/actuator/prometheus` 로 지정합니다. 그 뒤는 Operator 가 `kubernetes_sd_configs` 로 번역하므로 SD 를 직접 만질 일이 없습니다.

**Eureka 를 쓰는 VM 환경이라면 `http_sd` 를 짜지 마십시오.** Prometheus 에는 `eureka_sd_configs` 가 내장돼 있습니다. Eureka 레지스트리를 SD 프로바이더로 직접 물어보므로 중간 어댑터가 필요 없습니다.

```yaml
- job_name: spring-apps
  metrics_path: /actuator/prometheus
  eureka_sd_configs:
    - server: http://eureka:8761/eureka   # 필수
      refresh_interval: 30s               # 기본값
  relabel_configs:
    - source_labels: [__meta_eureka_app_instance_status]
      regex: UP
      action: keep                        # 살아 있는 인스턴스만
    - source_labels: [__meta_eureka_app_name]
      target_label: job                   # 잡 이름을 앱 이름으로
```

Eureka SD 는 REST API 를 주기적으로 확인해 앱 인스턴스마다 타깃을 하나씩 만듭니다. relabeling 중에 쓸 수 있는 메타 라벨 중 자주 쓰는 것은 이렇습니다.

| 메타 라벨 | 담는 값 |
|----------|---------|
| `__meta_eureka_app_name` | 앱 이름 (잡 이름으로 흔히 승격) |
| `__meta_eureka_app_instance_id` | 인스턴스 ID |
| `__meta_eureka_app_instance_hostname` | 인스턴스 호스트명 |
| `__meta_eureka_app_instance_ip_addr` | 인스턴스 IP |
| `__meta_eureka_app_instance_port` | 인스턴스 포트 |
| `__meta_eureka_app_instance_status` | `UP`/`DOWN` 등 상태 (살아 있는 것만 `keep`) |

앱 인스턴스 메타데이터는 `__meta_eureka_app_instance_metadata_<이름>` 으로 들어옵니다. Spring 쪽 `eureka.instance.metadata-map` 에 심어 둔 값을 그대로 라벨로 끌어올 수 있다는 뜻입니다. 전체 목록은 [`eureka_sd_config` 절](https://prometheus.io/docs/prometheus/latest/configuration/configuration/#eureka_sd_config)에 있습니다.

이름이 헷갈릴 때 문서를 뒤지는 대신 이 장이 가르친 방법을 쓰면 됩니다. 실행 중인 Prometheus 의 `/service-discovery` 페이지가 relabeling 전 라벨을 그대로 보여 줍니다.

Consul 을 서비스 레지스트리로 쓰는 경우도 같습니다. `consul_sd_configs` 가 내장이므로 커스텀 엔드포인트를 만들 이유가 없습니다.

**`http_sd` 가 정당해지는 경우는 사내 CMDB 나 자체 인벤토리 API 처럼 업스트림 프로바이더가 존재할 수 없는 진실 공급원입니다.** 이때 엔드포인트는 Spring Boot 로도 몇 줄입니다. 지킬 것은 앞서 본 세 가지(200 · `Content-Type: application/json` · UTF-8)뿐입니다.

```java
@RestController
class TargetsController {

    @GetMapping(value = "/targets", produces = MediaType.APPLICATION_JSON_VALUE)
    List<TargetGroup> targets() {
        return inventory.findScrapeTargets();   // static config 와 같은 모양
    }

    record TargetGroup(List<String> targets, Map<String, String> labels) {}
}
```

`produces` 로 `Content-Type` 이 정해지고 Spring Boot 의 기본 인코딩이 UTF-8 이므로 요구사항 셋이 자연스럽게 채워집니다.

**`instance` 를 사람이 읽을 이름으로 두는 요령은 Spring 환경에서 특히 값어치가 있습니다.** `targets` 에는 IP 와 포트를 담아 DNS 장애로 모니터링이 함께 무너지는 상황을 피하고 `labels.instance` 에는 `order-api-prod-3` 같은 이름을 넣습니다. 알림 문구와 대시보드는 후자를 읽고 스크레이프는 전자로 갑니다.

## 정답 (자답 후 펼치기)

> 위 §면접에서 받을 만한 질문 의 8개에 *먼저 자답한 뒤* 아래를 읽으세요. 자답 없이 먼저 읽으면 학습 효과가 0 입니다. 질문 번호와 1:1 로 대응합니다.

### 정답 1 — 두 relabeling 의 차이

도는 시점이 다릅니다. 표준 relabeling 은 타깃을 스크레이프하기 전에 돌아 대상을 걸러 내고 라벨을 붙입니다. 메트릭 relabeling 은 스크레이프가 끝난 뒤 시계열이 청크에 저장되기 전에 돌아 시계열을 버리거나 고칩니다. 그래서 "타깃이 안 잡힌다" 는 전자를, "쓸데없는 시계열이 쌓인다" 는 후자를 봅니다.

### 정답 2 — `__meta_` 가 시계열에 없는 이유

`__meta_` 는 서비스 디스커버리가 붙여 주는 메타데이터이고 relabeling 이 도는 동안에만 접근할 수 있습니다. relabeling 이 라벨 배정의 마지막 단계이며 `__` 로 시작하는 라벨은 그 뒤 최종 시계열에서 제외됩니다.[^prom-meta-labels] 남기고 싶으면 relabeling 중에 `replace` 로 일반 라벨에 옮겨 담아야 합니다.

### 정답 3 — Operator 환경에서 EC2 타깃 붙이기

`ServiceMonitor` 로는 되지 않습니다. Operator 가 자동으로 `kubernetes_sd_configs` 를 만들어 주는 대상은 `ServiceMonitor`·`PodMonitor`·`Probe` 뿐입니다. Kubernetes 에서 오지 않는 SD 는 Prometheus CRD 의 `additionalScrapeConfigs` 필드에 스크레이프 잡을 직접 적습니다.

### 정답 4 — 프로바이더가 라벨을 아끼는 이유

Prometheus 코드가 프로바이더는 `__address__` 와 `__meta_` 접두사 라벨 외에 어떤 라벨도 노출해서는 안 된다고 명시합니다. 최종 라벨을 무엇으로 할지 결정하는 권한을 프로바이더가 아니라 사용자의 relabeling 설정에 두는 설계입니다. 프로바이더는 사실만 실어 보내고 해석은 relabeling 이 합니다.

### 정답 5 — 자체 인벤토리에서 타깃 가져오기

`http_sd` 입니다. 200 응답, `Content-Type: application/json`, UTF-8 세 가지만 지키고 static config 와 같은 모양의 JSON 을 돌려주면 됩니다.[^prom-httpsd] cron 으로 파일을 뱉어 `file_sd` 로 읽는 예전 우회보다, Prometheus 가 직접 물어보는 쪽이 가시성 면에서 낫습니다.

보낼 타깃이 없을 때도 200 과 빈 배열을 내야 한다는 점을 덧붙이면 좋습니다. 오류로 답하면 Prometheus 가 직전 목록을 계속 쓰기 때문에, 사라진 타깃이 화면에 남는 방향으로 틀어집니다.

### 정답 6 — `instance` 와 `__address__` 를 가르는 실익

`instance` 를 따로 정의하지 않으면 `__address__` 값이 그대로 들어갑니다.[^prom-instance] 접속은 IP 로 하면서 `instance` 에는 사람이 읽는 이름을 붙이면 DNS 장애가 모니터링 장애로 번지는 일을 막으면서 알림과 대시보드의 가독성을 지킬 수 있습니다.

### 정답 7 — 타깃이 안 잡힐 때 여는 화면

`/service-discovery` 를 먼저 엽니다. 이 화면은 발견된 타깃과 그중 버려진 것을 함께 보여 주고 relabeling **전후** 라벨을 나란히 놓습니다. `/targets` 는 relabeling 전 메타 라벨만 보여 주므로 "왜 버려졌는지" 를 답해 주지 못합니다.

보는 순서는 이렇습니다. 먼저 타깃이 발견 목록에 아예 없는지 확인합니다. 없으면 SD 설정 자체의 문제이고, 있는데 버려졌다면 `keep`·`drop` 규칙의 정규식을 의심합니다. 잡 이름이나 라벨 값이 예상과 다를 때는 전후 비교에서 어느 규칙이 덮어썼는지 짚습니다.

### 정답 8 — 저장 단계에서 메트릭 버리기

`ServiceMonitor`(또는 `PodMonitor`)의 `spec.endpoints[].metricRelabelings` 입니다.[^promop-relabel] Operator 가 이것을 설정 파일의 `metric_relabel_configs` 로 번역합니다.

같은 엔드포인트의 `relabelings` 와 헷갈리지 않아야 합니다. 그쪽은 스크레이프 *전* 에 돌아 타깃을 고르므로, 거기에 메트릭 이름 조건을 적으면 아무것도 걸러지지 않습니다. 스크레이프 시점에는 아직 메트릭이 없기 때문입니다.
