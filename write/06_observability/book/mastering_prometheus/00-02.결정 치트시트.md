# 결정 치트시트 — Mastering Prometheus 정독 노트

---



## 핵심 요약

> *Mastering Prometheus* 를 관통하는 "X 냐 Y 냐"의 결정 축을 한자리에 모읍니다. 용어의 뜻은 [`00-01.용어집`](./00-01.용어집.md) 이 맡고 이 편은 **언제 무엇을 고르는가**만 다룹니다.
>
> 이 책 전체를 관통하는 한 원칙이 있습니다 — **Prometheus 는 pull 시스템이고 push 로 벗어나는 데는 그럴 만한 이유가 있어야 한다.** remote write(9장)·OTLP 수신(14장) 모두 이 원칙의 예외이지 기본이 아닙니다.



## 저장·확장 — 어디에 오래 둘까

**단일 Prometheus 의 한계(카디널리티·장기보존·단일 노드)를 넘어야 할 때** 세 갈래 답이 있습니다.

| 상황 | 선택 | 이유 | 근거 |
|---|---|---|---|
| 중앙집중형 remote-write 저장소 | Mimir / VictoriaMetrics | Prometheus 가 밀어 넣는 방식. 오브젝트/블록 스토리지 | [09-02](./09-02.VictoriaMetrics%20와%20Grafana%20Mimir.md) |
| 사이드카·오브젝트 스토리지 분산형 | Thanos | Prometheus 를 그대로 두고 사이드카가 블록 업로드. 글로벌 쿼리 | [10-01](./10-01.Thanos%20저장%20경로%20—%20Sidecar·Compactor·Store.md) |
| 저장 효율 극단 | VictoriaMetrics | ~0.3 B/sample (Mimir ~2 B/sample) — 단 수치 대부분 VM 자체 벤치 | [09-02](./09-02.VictoriaMetrics%20와%20Grafana%20Mimir.md) |
| 멀티테넌시·HA-tracker 필요 | Mimir | `X-Scope-OrgID` 테넌트 분리·리더 선출 | [09-02](./09-02.VictoriaMetrics%20와%20Grafana%20Mimir.md) |
| 이미 Prometheus 여러 대·수평 확장 | 샤딩+페더레이션 | 상위 Prometheus 가 하위를 선별 수집 | [06-01](./06-01.샤딩·페더레이션·고가용성.md) |

> **Thanos vs Mimir** 는 "같은 문제(단일 Prometheus 한계)의 다른 해법" 입니다 — Mimir=중앙 remote-write, Thanos=사이드카+오브젝트 스토리지. 나란히 대조하면 좋습니다.



## Thanos 내부 — 쿼리 엔진과 압축

| 결정 | 선택 축 | 근거 |
|---|---|---|
| PromQL 엔진 | 기본(단일 스레드, 전체 시계열 pull) vs Thanos(멀티 스레드, 집계 push-down). 단 `avg` 는 push-down 불가 | [10-02](./10-02.Thanos%20쿼리%20경로%20—%20Query·Query%20Frontend·Ruler·Receiver.md) |
| Query Frontend | 24h 분할·수직 샤딩·캐싱. **범위 쿼리에만** 적용 | [10-02](./10-02.Thanos%20쿼리%20경로%20—%20Query·Query%20Frontend·Ruler·Receiver.md) |
| 다운샘플링 켤까 | 용량이 아니라 **긴 쿼리 속도**를 위해. 용량은 오히려 2~3배 늚 | [10-01](./10-01.Thanos%20저장%20경로%20—%20Sidecar·Compactor·Store.md) |
| Store 샤딩 | relabel 은 keep/drop/hashmod 만. `__block_id` hashmod | [10-02](./10-02.Thanos%20쿼리%20경로%20—%20Query·Query%20Frontend·Ruler·Receiver.md) |
| Ruler | 규칙 평가를 Thanos 로 옮김 — Prometheus 규칙에 **추가**지 대체가 아님 | [10-02](./10-02.Thanos%20쿼리%20경로%20—%20Query·Query%20Frontend·Ruler·Receiver.md) |



## SLO — 타입과 도구

**요청 기반 vs 윈도우 기반** 은 서비스 성격으로 갈립니다.

| 서비스 | SLO 타입 | 이유 |
|---|---|---|
| 꾸준한 트래픽, 실패=매출 손실(결제 API) | 요청 기반 | 실패 요청 하나하나가 중요 |
| 저트래픽(분당 몇 건) | 윈도우 기반 | 요청 하나가 SLO 를 크게 흔듦 |
| 가용성="몇 분 죽었나"(Prometheus 자체) | 윈도우 기반 | 실패 건수보다 지속 시간이 중요 |
| 이상 폭증 잦음 | 윈도우 기반 | 폭증 규모가 계산에 안 들어옴(회복 3.75h vs 16d) |

**SLO 자동 생성 도구:**

| 축 | Sloth | Pyrra |
|---|---|---|
| 실행 | 규칙 생성기(`generate`) | 상주 프로세스(Prometheus 당 하나) |
| 설정 | 자체 YAML | 쿠버네티스 CRD |
| 웹 UI | 없음 | 있음(시각화) |
| 창 | 30일, 깔끔(5m~30d) | 28일 하드코딩, 어긋남(32m·1h4m…) |
| PromQL | `clamp_min` 등 가능 | 벡터 선택자만, `grouping` |

> 상세·근거: [13-01](./13-01.SLO%20를%20Prometheus%20로%20정의하고%20알림하기%20—%20요청·윈도우%20기반과%20Sloth·Pyrra.md). 알림은 항상 **에러 비율**에 겁니다(성공 비율 `>` 는 정상 시 항상 발화 — 책의 정오표). burn rate 임계값 표는 [01-04](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md).



## CI 검증 — 세 계층

| 계층 | 도구 | 어디서 | 무엇을 |
|---|---|---|---|
| 문법 | `promtool check config/rules`, `amtool check-config` | CI(push·PR) | 파일이 파싱되는가 |
| 동작 | `promtool test rules`, `amtool config routes test` | CI | 규칙·라우팅이 의도대로인가 |
| 살아있는 검사 | `pint lint` | 서버에 닿는 곳 | 메트릭이 실제로 있는가 |

> Pint 는 promtool 을 **대체가 아니라 포함+확장**합니다. 서버에 못 닿아도 `--offline` 으로 정적 검사(주석·라벨·정규식)는 유지 — promtool 보다 여전히 많이 잡습니다. 상세: [12-01](./12-01.CI%20파이프라인으로%20Prometheus%20검증%20—%20promtool·amtool·Pint.md).

| 결정 | 선택 | 근거 |
|---|---|---|
| Collector 릴리스 | 시작=`otelcol-contrib`(전부), 성숙=builder(선별), 이 책 예제=core(Prometheus 컴포넌트 포함) | [14-01](./14-01.Prometheus%20와%20OpenTelemetry%20통합%20—%20규격·Collector·OTLP%20수신구.md) |
| OTLP 전송 | gRPC(원조·권장) vs HTTP(=HTTP/1.1, 호환성). Prometheus API 는 HTTP 라 `otlphttp` | [14-01](./14-01.Prometheus%20와%20OpenTelemetry%20통합%20—%20규격·Collector·OTLP%20수신구.md) |
| Prometheus 로 push? | 상시 서비스=pull 유지. pull 불가(에페메럴·격리)일 때만 OTLP push 예외 | [14-01](./14-01.Prometheus%20와%20OpenTelemetry%20통합%20—%20규격·Collector·OTLP%20수신구.md) |

## 세 신호 — 무엇을 어디에

| 신호 | 자리 | 하지 말 것 |
|---|---|---|
| 메트릭(Prometheus) | 전체 조망, 미리 정의 | — |
| 로그(Loki) | 최후의 보루, 세부 | 로그에서 메트릭·트레이스 추출(취약한 번역 계층) |
| 트레이스(Tempo) | 드릴다운, 샘플링 필수 | 전체 조망 대용으로 쓰기(샘플링하니 불가) |

> 원칙은 **잇되 의존시키지 않는다** — 라벨 일관성(`app=servicex` 통일)·exemplar 로 잇되, 한 신호가 깨져도 나머지가 살게 독립 생산. 상세: [15-01](./15-01.Prometheus%20너머%20—%20세%20신호를%20잇는%20관측%20가능성과%20exemplar.md).



## 수신구 플래그 계열 — 한눈에

Prometheus 가 push 를 받는 수신구는 모두 켜야 열리고 기본은 꺼져 있습니다(인증 없는 수신은 위험).

| 수신구 | 현행 플래그 | 상태 |
|---|---|---|
| remote-write | `--web.enable-remote-write-receiver` | 승격됨 | 
| OTLP | `--web.enable-otlp-receiver` (책의 `otlp-write-receiver` 는 3.0 승격) | 승격됨 |
| exemplar 저장 | `--enable-feature=exemplar-storage` | **여전히 실험**(승격 안 됨) |

> 앞 둘은 `--web.enable-*-receiver` 계열로 졸업했지만 exemplar-storage 만 아직 feature flag 입니다. 근거: [14-01](./14-01.Prometheus%20와%20OpenTelemetry%20통합%20—%20규격·Collector·OTLP%20수신구.md) · [15-01](./15-01.Prometheus%20너머%20—%20세%20신호를%20잇는%20관측%20가능성과%20exemplar.md).
