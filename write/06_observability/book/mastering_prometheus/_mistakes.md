# Mastering Prometheus 오답 노트

> 편별 Phase 1·복습에서 막힌 지점을 기록합니다. 각 항목은 **자기 답 · 정답 · 원인 추정 · 참고 챕터 · 재방문 트리거**로 씁니다.
> 형식은 `08_cloud/book/kubernetes-in-action/_mistakes.md` 와 같습니다.

## 2026-07-29 — 자기 답을 끝까지 밀지 않음 + ⭐ 반문 셋이 전부 다음 층을 겨냥 (03-01 Phase 1)

- **자기 답**: 03-01 다섯 축을 예측·채점으로 돌린 결과. (1) 시계열 위에 쌓이는 것을 **"시간에 대한 정보"** 로 답해 시각은 자력으로 짚었으나 값과 **'샘플'** 이라는 이름은 힌트 후에 나왔습니다("시간과 값이 나와야 x-y 축이 나오겠지"). 이때 **"메트릭에 이름밖에 없는 거였어? 라벨이 메트릭에 붙는 게 정상인 줄 알았는데"** 를 물었습니다. (2) 라벨 순서만 다른 두 줄을 **"같은 시계열"** 로 자력 정답했으나, 이어 **"둘 다 저장되어야 합니다 값이 다르니 샘플이 서로 다르게 저장되는 거 아닐까요"** 로 답해 **자기 1번 답과 모순**했습니다. (3) WAL 축은 "디스크가 비싸니 메모리에 올려 두고 배치로", "앱이 죽으면 데이터가 사라져 **장애 발생 시 모니터링에 구멍**" 을 **둘 다 자력 정답**하고 장치는 **"파일로 임시 저장해 두나요?"** 로 이름 직전까지 도달했습니다. (4) 블록 불변의 이유를 **"하나의 데이터 흐름이라 중간 수정이 아닌 추가 방식 (이벤트 스토어 개념?)"** 으로 자력 정답. 툼스톤은 **"useYn 같은 라벨로 N 을 남기는 개념"** 으로 발상은 맞고 **위치가 어긋났습니다**(행 안 vs 블록 밖). (5) 컴팩션 이유를 "작은 블록이 많으면 조회가 힘들어진다"로 자력 정답하고 **"합치면 특정 범위만 읽어야 하는데 전체가 조회되면 무겁지 않을까?"** 를 되물었습니다. 툼스톤을 컴팩션의 답으로 **맞혔다가 스스로 정정해** 보존의 답으로 옮겼습니다.
- **정답**: (1) 3층은 **메트릭(이름) → 시계열(이름+라벨 조합) → 샘플(시각+값)** 입니다. 라벨을 붙이는 순간 그것은 이미 시계열이고, 메트릭은 그 조합들을 묶어 부르는 **가족 이름**입니다. `instance` 가 100대면 메트릭 1개에 시계열 100개입니다. (2) 라벨은 **집합**이라 순서가 정체성에 영향을 주지 않습니다. 같은 시계열이므로 **같은 시각에 값이 둘**이 되고, 시계열은 시각 하나에 값 하나가 전제라 성립할 수 없습니다. 그래서 Prometheus 는 둘 중 하나를 고르지 않고 **스크레이프 전체를 실패**시키며 `up` 이 0 이 됩니다. 02-01 §5 의 "`up` 은 HTTP 만 본다" 와 어긋나 보이지만 예외가 아닙니다 — HTTP 는 왔고 **파싱에서 실패**했으며, 스크레이프 성공은 수신과 파싱 **둘 다** 필요합니다(깨진 `.prom` 은 Node Exporter 가 자기 안에서 처리해 정상 응답을 냈으므로 다른 경우). 애매한 데이터를 조용히 들이느니 안 받고 `up` 으로 드러내는 설계입니다. (3) 장치는 **WAL(Write-Ahead Log)** 이고 이름이 순서를 가리킵니다 — **디스크(WAL)가 먼저, 메모리(head)가 나중**. 디스크 쓰기가 비싸다는 것과 모순되지 않는 이유는 **append 는 순차 쓰기**라 디스크가 가장 잘하는 동작이기 때문입니다. WAL 은 평소에 **절대 읽지 않고 재시작 때 한 번만** 읽습니다. (4) 표시는 **행 안이 아니라 블록 밖**에 둡니다 — **툼스톤(tombstone)**, 블록 폴더 옆 별도 파일에 "이 시계열의 이 시간 범위는 무효" 를 적습니다. 원본은 손대지 않고, 실제 제거는 **컴팩션 때** 일어납니다. (5) 합쳐도 안 무거운 이유는 **인덱스 2단** 입니다 — 포스팅 인덱스가 라벨로 시계열을 좁히고 시리즈 인덱스가 시간으로 chunk 를 찾아 **필요한 청크만** 읽습니다. 삭제는 **단위가 갈립니다** — 사용자 삭제는 블록 *일부*라 툼스톤, 보존 만료는 블록 *전체*라 **폴더째 삭제**. 그러니 툼스톤은 컴팩션(2번)의 답이 맞고, 스스로 한 정정이 틀렸습니다.
- **★ 반문 셋이 전부 다음 층을 겨냥했습니다**: ① **"append 여도 시스템콜은 나는데 큰 거 아닌가"** → 갈리는 것은 디스크에 쓰느냐가 아니라 **어떻게 쓰느냐**(순차/임의 · 읽기 유무 · CPU)이고, 매 샘플 `fsync` 가 아니라 버퍼에 모아 페이지 단위로 씁니다. ② **"RDB 도 순차 PK 로 삽입만 하면 같아지지 않나"** → 쓰기 패턴은 흉내 낼 수 있지만 **저장 밀도는 못 따라옵니다.** 남는 차이 셋 — 행마다 붙는 트랜잭션 메타데이터(샘플 16B 보다 큼) · delta-of-delta+XOR 은 **연속 샘플이 물리적으로 나란해야** 성립(행 지향에서 원리적 불가) · 읽기 패턴(범위 스캔 vs 한 건 찾기). TimescaleDB 가 PostgreSQL 위에서 **청크로 쪼개고 열 지향 압축**을 하는 것이 같은 결론입니다. ③ **"합치면 범위 조회가 무겁지 않나"** → 이 편의 §6(인덱스)이 그 답이며, 학습자가 답을 스스로 불러냈습니다.
- **원인 추정**: 미달 둘((2)(5))의 결이 **"자기 답을 끝까지 밀지 않음"** 하나입니다. (2)는 "같은 시계열" 이라 해 놓고 그 귀결(같은 시각에 값 둘)을 안 따졌고, (5)는 맞은 답을 **스스로 뒤집었습니다.** 어제 02-01 의 층 혼동과는 다른 결이고, 오히려 01-01 의 **"사실은 인출하고 그것이 무엇을 갈리게 하는지에서 멈춤"** 과 같은 계보입니다. (4)의 툼스톤 위치 착오도 같은 결 — 불변을 자력으로 세워 놓고 "그러면 행을 못 고친다" 까지 밀지 않아 `useYn` 이 나왔습니다. 반면 **반문 셋은 전부 정확했고**, 특히 ③은 다음 절의 답을 스스로 호출했습니다. 인출이 약한 게 아니라 **자기 답의 귀결을 검산하는 단계가 빠진** 것입니다.
- **참고 챕터**: 03-01 §1(3층·중복 실패)·§4(WAL)·§5(불변·chunk 압축·툼스톤)·§6(포스팅/시리즈 인덱스)·§7(컴팩션·보존). 보강 TODO 는 `_todo-03-01-보강.md`(**3항목만** — 6개 후보 중 셋은 문서에 이미 있어 제외). "**메트릭·시계열·샘플 3층 / 라벨은 집합이라 순서 무관, 겹치면 스크레이프 전체 실패 / WAL 은 먼저 쓰고 재시작 때만 읽는다 / 블록이 불변이라 삭제는 블록 밖 툼스톤으로 흉내 낸다 / 일부 삭제는 표시로, 전체 만료는 폴더째**" 한 줄.
- **재방문 트리거**: 다음 복습에서 (1) 라벨 순서만 다른 두 줄이 들어오면 **무슨 일이 벌어지는지**와 그때 `up` 이 왜 0 인지(02-01 §5 와 어긋나 보이는 이유까지), (2) WAL 을 **언제 읽는지**와 쓰기 순서가 왜 디스크 먼저인지, (3) ⭐ 툼스톤을 **어디에** 두는지(행 안이 아님 — 위치 착오 1회차) 와 실제 제거가 언제인지, (4) 삭제 둘의 **단위 차이**(오늘 맞았다가 스스로 뒤집음 — 반드시 확인), (5) 블록을 합쳐도 범위 조회가 안 무거운 이유(인덱스 2단), (6) **자기 답의 귀결을 검산하기** — "그렇다면 무슨 일이 벌어지는가" 를 한 걸음 더 묻는 습관이 이번 미달 둘의 공통 처방.

(1) §4 L137 뒤 — "디스크에 쓰느냐가 아니라 **어떻게** 쓰느냐" 3축 표(순차/임의 · 기존 데이터 읽기 · CPU). (2) §심화 머리 — **"RDB 로는 왜 안 되는가"**, 반문을 먼저 인정하고("쓰기 패턴은 흉내 낼 수 있습니다") 남는 차이 셋을 댄 뒤 TimescaleDB 반례로 닫았습니다. ## 2026-07-29 — 층 혼동이 방향만 바꿔 재발 + ⭐ 반문이 한 겹 깊어짐 (02-01 복습, 즉석 모드 5축)

- **자기 답**: (1) Prometheus 스택 넷을 묻자 **"스크레이핑 매니저·TSDB·Rule·UI"** 로 답했습니다(= §2 의 내부 부품). LGTM 넷은 "Loki·Grafana·Trace·Mimir" 로 거의 정답이고 겹치는 것이 Grafana 하나라는 것도 자력 정답이었으나, 두 묶음의 차이를 **"프로메테우스를 구성하는 4가지 vs 시스템 모니터링 전체 기술스택 4가지"** 로 잡았습니다. (2) 내부 4부품에서 중심이 TSDB 임은 자력 정답, 스크레이프=저장·룰=조회도 정답이나 **웹 UI 를 "조회·수정"** 으로 봤고, Grafana 가 붙는 자리를 **"TSDB 의 API"** 로 답했습니다("웹UI 의 데이터를 쓰진 않을 것 같은데"). (3) 50건 병목을 **"사람이 병목"** 으로 자력 정답. 도구는 그룹핑을 먼저 댔으나 억제의 동작을 **"침묵"** 이라 불렀고, 화면에 50줄이 남는 이유는 **"Rule 을 보는 거라면 정상인 것 같다"** 로 상자↔줄 2층에 못 닿았습니다. (4) textfile vs Pushgateway 에서 **"파일에 남는지 내부 메모리에 남는지"** 축 하나만 인출하고 나머지 둘(귀속·새 인프라)이 빠졌으며, Prometheus 의 **과거 값**을 묻는 후속에 무응답이었습니다. 대신 **"PushGateway 도 파일 방식으로 바꾸면 완전히 동일해지는가?"** 를 되물었습니다. (5) 깨진 `.prom` 상황에서 `up`=1 과 판정 기준(HTTP 성공만), CPU·메모리 정상 노출을 **둘 다 자력 정답**했고, 사고를 알리는 신호만 "메타데이터가 조회된다"로 이름을 못 댔습니다. 중간에 **"배치라는 게 프로메테우스가 주기적으로 pull 한다는 의미인가?"** 를 물었습니다.
- **정답**: (1) 스택 넷은 **Prometheus·Alertmanager·exporter·Grafana**(프로세스 층)이고 학습자가 답한 넷은 **`:9090` 한 프로세스 안의 부품**입니다. 두 묶음의 차이는 "Prometheus 구성 vs 전체 스택"이 아니라 **메트릭 한 축 안의 역할 분담(스택) vs 신호 종류별 도구 모음(LGTM)** 이며, 둘 다 프로세스 층입니다. 부품 넷은 그 아래 한 겹 더 들어간 **세 번째 층**입니다. 판별 기준은 **포트** — 포트가 다르면 프로세스, 같은 포트 아래 화면만 갈리면 부품. (2) 웹 UI 는 **읽기 전용**이고 값을 고치는 창구가 아닙니다. Grafana 가 붙는 곳은 TSDB 가 아니라 **웹 UI 부품의 아랫면인 REST API** 입니다 — 넷 중 **바깥으로 열린 창구를 가진 것은 웹 UI 하나뿐**이고 나머지 셋은 안에서만 TSDB 를 향합니다. `:9090/graph`(화면)와 `:9090/api/v1/query`(API)가 같은 포트라는 것이 증거입니다. 룰 매니저는 조회로 끝나지 않고 **평가**하며, 레코딩 룰은 결과를 **TSDB 에 되쓰고** 알림 룰은 **밖으로** 냅니다(넷 중 유일한 양방향). (3) **억제**(inhibition)는 다른 알림이 눌러 주는 것이고 **침묵**(silence)은 사람이 점검 구간에 미리 꺼 두는 것으로, 계기가 다릅니다. 화면에 50줄이 남는 것은 정상이며 모순이 아닌 이유는 **2층 구조** 때문입니다 — 그룹핑은 줄을 지우지 않고 **상자 하나에 담습니다.** "50건 → 1건"의 1은 줄 수가 아니라 **상자 수**이고, 사람이 받는 것은 메일 **한 통**(`[FIRING:50]`)입니다. 상자를 무엇으로 가를지는 **`group_by`** 가 정합니다. (4) 축은 셋 — ① 값의 수명(덮어쓰기 vs 수동 삭제 전까지 영원히) ② **값의 귀속**(textfile 은 `job="node-exporter"` 가 붙어 배치의 정체를 잃고, Pushgateway 는 URL 에 이름이 박혀 보존) ③ **새 인프라**(Pushgateway 는 별도 서버 = SPOF). (5) 신호 이름은 **`node_textfile_scrape_error`**(1 = 읽기 실패)이고, `up` 과 **다른 축**이라 알림을 따로 걸어야 합니다. `up` 만 보면 이 사고는 초록불에 가려 안 보입니다.
