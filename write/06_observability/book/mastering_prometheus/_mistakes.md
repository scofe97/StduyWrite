## 2026-07-28 — 층이 밖으로 나감 + ⭐ 어제 트리거 자력 인출 (02-01 Phase 1)

- **자기 답**: 02-01 다섯 축을 예측·채점으로 돌린 결과. (1) Prometheus 스택 넷을 물었을 때 **"LGTM 을 의미하며 Grafana, Loki, Trace"** 로 답했습니다. (2) Prometheus **내부** 4부품을 물었을 때 **"AlertManager, Exporter 2개이고 중심은 프로메테우스"** 로 답했습니다. (3) Alertmanager 의 책임 경계는 "룰 매니저를 통해 Alertmanager 로 전달"을 자력으로 맞혔으나, 알림을 보낼 대상 판단을 Prometheus 몫으로 봤고 50건 상황의 병목을 **"한 번에 50개 요청이 들어가고 50번 쏴야 한다"**(기계 부하)로 답했습니다. 이어 "억제가 AlertManager 의 핵심이란건가?"를 물었습니다. (4) ⭐ 단명 프로세스는 **(a)(b) 자력 통과** — "실제 살아있는건 2번인데 15초주기로 계속해서 체크", "애초에 40초만 살아있는 앱에서 그 시간을 벗어난건 0인게 정상인데 알람으로 쓸수없다". (5) textfile collector 는 (a) "배치가 파일로 남기고 exporter 가 노출"을 자력 정답, (b) **"정상적인 파일이 아니라면 0이라서 실패"** 로 `up` 판정 기준을 오해하고 "이러면 앱 때문에 노드 정보도 못 들고 오는 거 아님?"을 걱정, (c) Pushgateway 문제를 "배치가 데이터를 보내지 않았을 때 이유를 모른다"로 방향만. 세션 말미에 **"파일에 데이터를 담아 보내는 방식이 결국 push 방식과 다를 게 있는가?"** 를 물었습니다.
- **정답**: (1) 스택 넷은 **Prometheus · Alertmanager · exporter · Grafana** 입니다. LGTM(Loki·Grafana·Tempo·Mimir)은 **축이 다른 묶음** — 이쪽은 메트릭 **한 축 안에서** 역할 분담이고 LGTM 은 **신호 종류별** 도구 모음입니다. **Grafana 만 겹칩니다.** Loki·Tempo 는 01-01 이 "별도 시스템"이라 한 로그·트레이스 담당이라 Prometheus 스택에 들어오지 않습니다. (2) 내부 4부품은 **TSDB · 스크레이프 매니저 · 룰 매니저 · 웹UI(REST API)** 이고 Alertmanager·exporter 는 **별개 프로세스**(스택 층)입니다. 중심은 **TSDB** — 스크레이프 매니저가 넣고, 룰 매니저가 읽어 평가하고, 웹UI 가 꺼냅니다. Grafana 는 그 웹UI 가 올라앉은 **REST API** 를 씁니다. (3) Prometheus 책임은 **룰 평가 → firing 판정 → 페이로드 전송**까지이고 "누구에게 알릴지"는 판단하지 않습니다(그것이 라우팅 트리 = Alertmanager 본업). 병목은 기계가 아니라 **사람** — 당직자가 50건을 읽지 못하고 원인 1건이 49건에 묻힙니다(알림 피로). Alertmanager 는 발송 대행이 아니라 **알림을 사람이 감당할 형태로 가공하는 층**이고 도구가 넷(그룹핑·억제·침묵·라우팅)입니다. **억제가 핵심은 아니고** 실무 기본은 그룹핑입니다(억제는 원인-결과 계층을 미리 알아야 설정 가능해 상대적으로 특수). 분리 이유 두 축 — 책임 성격이 다름(알림 가공은 별개 상태 관리), Prometheus HA 2대가 같은 알림을 쏠 때 **Alertmanager 공유로 중복 제거**. (4) 자력 통과. 덧붙이면 배치가 5초면 **한 번도 못 긁힐 수 있고**, 처리 건수 확정 시점이 하필 끝나기 직전이라 그 순간을 놓치면 최종값을 영영 못 봅니다. push 라면 **1번** 보내고 끝(2~3번이 아님) — 자기가 언제 끝나는지 아는 쪽이 보내니까요. (5) **`up` 은 파일 내용과 무관하고 HTTP 스크레이프 성공 여부만 봅니다.** 파일이 깨져도 **나머지 시스템 메트릭은 정상 노출**되고 그 파일만 건너뛰며 `node_textfile_scrape_error` 를 올립니다 — `up` 과 다른 축의 신호입니다. 이유는 **편승 기능이 본업을 망가뜨리면 안 되기** 때문입니다. Pushgateway 의 진짜 문제는 "이유를 모른다"보다 **값이 영원히 남는 것** — 배치가 안 돌아도 마지막 성공 값이 초록불로 살아 있어 **조용한 실패**가 됩니다.
- **★ "파일 쓰기도 push 아닌가" — 학습자가 스스로 발견한 정당한 의문**: 배치 입장에서는 둘 다 "쓰기"이고 **마지막 구간은 둘 다 pull** 이라 push/pull 로는 구별되지 않습니다. 갈리는 축 셋 — ① **값의 귀속**(textfile 은 노드 메트릭으로 `instance` 라벨이 붙고 노드가 사라지면 같이 사라짐 / Pushgateway 는 소유자 없는 데이터) ② **값이 사라질 수 있는가**(덮어쓰기는 갱신 시각이 남고 밀어 넣기는 영원히 초록불) ③ **새 인프라**(Pushgateway 는 별도 서버 = SPOF). 프레임 한 줄 — **textfile collector 는 "push 가 아니다"가 아니라 push 를 노드 안으로 국소화한 것**입니다.
- **원인 추정**: 미달 둘((1)(2))의 뿌리가 **층 혼동** 하나입니다 — (1)은 밖으로(다른 묶음), (2)도 밖으로(별개 프로세스). 어제 k8s 12-02(ConfigMap↔annotation)·13-03(네트워크 통신↔오브젝트 참조)과 **같은 결**이고, 개별 사실은 아는데 **"이것은 어느 층의 이야기인가"** 를 세우지 못합니다. (2)는 문서 구조도 한몫했습니다 — §1 이 프로세스 "넷"을 나열한 직후 §2 가 부품 "넷"으로 시작해 같은 수가 연달아 나옵니다. (3)의 병목 오답과 (5)의 `up` 오해는 다른 결로, **인과를 자기 모델로 메운 것**(요청 수가 많으면 기계가 힘들 것 / 파일이 깨지면 스크레이프가 실패할 것)입니다. 반면 (4) 자력 통과는 **어제 오답 노트 재방문 트리거를 하루 만에 인출**한 것이라 개념이 굳었다고 봅니다.
- **참고 챕터**: 02-01 §1(스택 넷)·§2(내부 4부품·TSDB 중심)·§3(Alertmanager 분리)·§4(단명 프로세스·textfile collector)·§심화(분리 근거·textfile vs Pushgateway). 보강 TODO 는 `_todo-02-01-보강.md`(6항목). "**스택은 메트릭 한 축 안의 역할 분담이고 LGTM 은 신호 종류별 묶음 / 내부는 TSDB 중심 4부품, Alertmanager·exporter 는 별개 프로세스 / 병목은 기계가 아니라 사람 / `up` 은 HTTP 성공만 본다 / textfile 은 push 를 노드 안으로 국소화한 것**" 한 줄.
- **재방문 트리거**: 다음 복습에서 (1) Prometheus 스택 넷과 LGTM 넷을 **각각 나열하고 축이 어떻게 다른지**, 겹치는 것 하나가 무엇인지, (2) Prometheus **내부** 4부품을 대고 **무엇이 중심이며 나머지 셋이 그것과 어떤 관계**인지 (Alertmanager 가 답에 들어가면 층 혼동 재발), (3) 스위치 1대로 서버 50대가 알림을 낼 때 **병목이 무엇인지**와 Alertmanager 의 도구 넷 중 **실무 기본이 무엇인지**, (4) ⭐ **"파일에 쓰는 것과 Pushgateway 는 무엇이 다른가"** — 학습자가 미해결로 남긴 물음이므로 최우선, 축 셋으로 답하기, (5) `up` 이 **무엇을 기준으로** 1/0 이 되는지와 파일이 깨졌을 때 노드 메트릭이 어떻게 되는지, (6) 왜 하필 **Node Exporter** 가 textfile collector 를 갖는지.

## 2026-07-28 — "그래서 무엇이 갈리는가"까지 못 감 (01-01 Phase 1)

- **자기 답**: 01-01 네 축을 예측·채점으로 돌린 결과. (1) 체크 기반이 월~목 `OK` 만 남긴다는 것은 **자력 정답**했으나, 금요일 경고에서 모르는 것을 **"어떻게 예외로 왔는지를 모른다"** 까지만 답하고 그것이 왜 문제인지에 못 닿았습니다. (2) 체크 기반이 "내가 상상하지 못한 예외를 잡지 못한다"는 **자력 정답**. 다만 원인 기반의 반대가 무엇이냐에 **"단순 특정 값의 임계값이 아닌 다른 거? 잘 모르겠다"** 로 막혔습니다. (3) pull·push 에서 push 는 "일정 시간 데이터가 안 올 때 인지한다"까지 맞혔으나 **"확인하려면 다시 pull 해 봐야 한다"** 고 답했습니다(push 에는 pull 수단이 없음). pull 의 단점으로 **"한 서버에서 모두 가져오니 과부하"**(정확 — 6장 샤딩)와 **"앱이 죽었을 때도 지속적으로 체크해야 하는 번거로움"**(오해)을 들었습니다. (4) 상세도·비용 4칸에서 메트릭=싸고 대략적, 트레이스=비싸고 상세, **빈 칸=싸고 상세**를 **전부 자력 통과**했습니다.
- **정답**: (1) 모르는 것은 **기울기**입니다. `82%` 라는 경고만으로는 **며칠에 걸쳐 서서히 찬 것(A)인지 10분 만에 튄 것(B)인지** 구분할 수 없고, **대응이 정반대**입니다 — A 는 증설 계획을 세울 일이고 B 는 지금 당장 로그를 뒤져야 할 사고입니다. 원인은 압축 — `78.3` 이 `WARNING` 으로 눌리면 되돌릴 수 없습니다. 시계열은 숫자와 시각을 쌍으로 남겨 기울기가 보존되므로 임계치 도달 *전에* 계산할 수 있습니다(`predict_linear`). 체크 기반의 한계는 **두 축**입니다 — *알려진 미지*(무엇을 감시할지)와 *압축*(어떻게 기록할지). (2) 반대는 **증상 기반(symptom-based)** 입니다. 비대칭이 핵심 — **원인의 목록은 무한하지만**(커넥션 풀·데드락·외부 API·인증서·DNS·배포…) **드러나는 창구는 유한**합니다(실패하는가·느린가). 그래서 증상에 걸면 원인을 미리 상상하지 않아도 잡힙니다. 단 완전 대체는 아니고 실무는 **증상엔 호출, 원인엔 티켓**으로 나눕니다. (3) push 의 진짜 어려움은 중앙 서버가 **누가 보내야 하는지 모른다**는 것입니다 — "안 오는 것"과 "없는 것"(오토스케일 정상 축소·애초에 없던 대상)이 구별되지 않습니다. pull 은 서비스 디스커버리로 대상 목록을 알아 **`up == 0` 으로 부재를 데이터화**합니다. 죽은 대상을 계속 긁는 것은 낭비가 아니라 **회복 감지의 필수 조건**입니다 — 멈추면 언제 살아났는지 알 수 없습니다. (4) 자력 통과. 빈 칸이 없는 이유는 **상세함을 유지하려면 개별 사건을 다 남겨야 하고 값을 싸게 하려면 집계해야** 하므로, 둘은 거래 관계입니다.
- **원인 추정**: 공통 결은 **"사실은 인출하고 그것이 무엇을 갈리게 하는지에서 멈춤"** 입니다. (1)에서 `OK` 만 남는 것은 맞혔는데 그래서 대응이 정반대로 갈린다는 데까지 못 갔고, (3)에서 push 가 시간으로 판정한다는 것은 맞혔는데 "무엇과 구별이 안 되는가"를 안 세웠습니다. 어제 k8s 12-01·13-01 의 **"결론은 맞고 근거가 얕음"** 과 같은 유형입니다. (3)의 "죽은 앱을 계속 긁는 게 번거롭다"는 다른 결 — **실패 상태를 계속 확인하는 것이 회복 감지의 조건**이라는 설계 논리를 놓친 것이고, 어제 13-01 에서 "명단에서 빠지면 probe 도 멈추나?"라고 물은 것과 **같은 패턴 2회차**입니다. 반면 (4) 자력 통과와 (3)의 샤딩 직관은 좋았습니다.
- **★ 어제와 달라진 점**: k8s 13장에서 다섯 편·여섯 번 놓친 **"조용한 실패"** 를 이번에는 **먼저 물어보고**("조용한 실패는 사용자가 인지하기 힘든 실패라는 의미이고, 이를 줄이기 위해 pull 모델을 쓴다는 건가?") 이해도 맞췄습니다. 다만 정확히는 *사용자* 가 아니라 **모니터링 시스템** 이 인지하지 못하는 실패입니다.
