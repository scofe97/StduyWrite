# 5-2. 견고한 알림과 룰 단위 테스트
---



## 핵심 요약

> 좋은 알림과 시끄러운 알림의 차이는 대개 임계값이 아니라 **`for` 기간 하나**입니다. 저자의 경험칙은 warning 은 15분보다 짧지 않게, critical 은 15분보다 길지 않게입니다.
>
> Prometheus 가 Nagios 같은 체크 기반 도구와 갈리는 지점도 여기입니다. 메모리 사용률만 보고 알리는 대신 **메모리 사용률이 높으면서 동시에 메이저 페이지 폴트 비율도 높을 때**만 알릴 수 있습니다. `and`·`or`·`unless` 가 그 조건을 표현합니다. 알림은 증상이 실제로 보일 때만 울려야 합니다.
>
> 긴 `for` 를 쓰면 새 함정이 생깁니다. 스크레이프가 한 번 실패하면 쿼리가 빈 결과를 내고 알림이 pending 상태에서 떨어집니다. `last_over_time` 같은 `_over_time` 함수가 그 초기화를 막습니다.
>
> 그리고 알림도 코드이므로 테스트합니다. `promtool test rules` 로 시계열을 지어 넣고 몇 분에 무엇이 발화해야 하는지 단언합니다.



## 학습 목표

> 이 절을 읽고 나면 아래 다섯 가지를 스스로 해낼 수 있습니다.

1. `unless` 로 재부팅 직후 오탐을 걷어 내는 알림을 쓸 수 있습니다.
2. warning 과 critical 에 각각 어울리는 `for` 기간을 고르고 평가 주기와의 관계를 설명할 수 있습니다.
3. 스크레이프 실패가 `for` 상태를 초기화하는 문제를 `_over_time` 으로 막을 수 있습니다.
4. `max_over_time` 을 쓰면 왜 발화가 늦어지는지 계산할 수 있습니다.
5. `promtool test rules` 로 알림 룰의 단위 테스트를 작성하고 실패를 읽을 수 있습니다.



## 본문 정리

### 논리·집합 연산자로 오탐 줄이기

견고한 알림을 만드는 능력은 Prometheus 가 Nagios 같은 전통적 체크 기반 모니터링과 갈리는 지점 중 하나입니다. 여러 조건을 함께 고려할 수 있기 때문입니다. 서버의 메모리 사용률이 높다는 사실만으로 알리는 대신, 메모리 사용률이 높으면서 **메이저 페이지 폴트 비율도 높을 때** 알리는 편이 메모리 압박을 훨씬 잘 가리킵니다.

핵심은 오탐을 최대한 줄여 **실제로 눈에 보이는 영향이 있을 때만** 알림이 울리게 만드는 데 있습니다. 증상에 알릴 것이냐 원인에 알릴 것이냐는 더 큰 논의이고 Rob Ewaschuk 의 문서 *My Philosophy on Alerting* 이 그 주제를 깊이 다룹니다.

3장에서 본 `and`·`or`·`unless` 를 아낌없이 씁니다. 서버의 NTP 동기화를 감시하고 싶은데 재부팅 직후에는 NTP 가 어긋나 있을 수 있습니다. 노드의 부팅 시각을 알림 조건에 끌어들이면 됩니다.

```promql
node_timex_offset_seconds > 0.05
unless on (instance)
changes(node_boot_time_seconds[30m]) > 0
```

재부팅 후 대략 30분 동안(설정한 `for` 기간이 더해집니다) NTP 알림이 발화하지 않습니다.

> **`_info` 메트릭 패턴** — 값이 항상 `1` 인 게이지에 `_info` 접미사를 붙이고 정보성 라벨을 잔뜩 매다는 관례입니다. 라벨 값이 바뀔 때 모든 시계열이 갈라지는 대신 이 메트릭 하나만 바뀌므로 churn 이 줄어듭니다. 2장에서 kube-prometheus 와 함께 배포한 kube-state-metrics 가 클러스터 노드 정보를 담은 `kube_node_info` 를 내놓습니다.

### `for` 기간이 알림의 품질을 가른다

시끄러운 알림과 좋은 알림의 차이는 대개 `for` 기간을 늘리는 것만큼 단순합니다. 1시간이나 2시간짜리 `for` 를 겁내지 말고 짧은 `for`(`0m`, `5m`)는 critical 알림에 아껴 둡니다. 저자의 경험칙은 이렇습니다.

- warning 알림의 `for` 는 **15분보다 짧지 않게**
- critical 알림의 `for` 는 **15분보다 길지 않게**

여기에 놓치기 쉬운 제약이 하나 붙습니다. `for` 기간은 룰의 **평가 주기보다 길어야** 의미가 있습니다. 알림 룰을 5분마다 평가하도록 설정해 두고 `for: 3m` 을 걸면 그 3분은 아무 일도 하지 않습니다.

### 스크레이프 실패가 `for` 를 지운다

긴 `for` 를 쓰면 마주치는 문제가 있습니다. 스크레이프가 한 번 실패하면 그 뒤 룰을 평가할 때 쿼리 표현식이 아무 데이터도 돌려주지 않고 알림은 더 이상 pending 상태가 아니게 됩니다. 쌓아 온 시간이 날아갑니다.

`last_over_time`·`avg_over_time`·`max_over_time` 같은 `_over_time` 함수가 이 문제를 우회합니다. 지정한 시간 범위 안에 데이터가 조금이라도 있으면 스크레이프 실패가 `for` 상태를 초기화하지 못합니다.

```promql
# 나쁨
probe_success{job="blackbox_ssh"} != 1

# 좋음
last_over_time(probe_success{job="blackbox_ssh"}[5m]) != 1
```

시간 범위를 몇 분보다 길게 잡지 않기를 저자는 권합니다. 알림의 발화와 해소가 최대한 제때 일어나야 하기 때문입니다. 스크레이프 실패로부터 `for` 를 지키는 목적이라면 대개 `last_over_time` 이 최선입니다.

`max_over_time` 같은 다른 함수를 쓰면 알림 동작 자체가 바뀝니다. 위 예제에 `max_over_time` 을 넣으면 시계열이 5분 내내 `1` 이 아니라 `0` 이어야 표현식이 참이 됩니다. 설정한 `for` 기간 위에 지연이 더 얹히는 셈입니다.

> **이상 탐지** — 대부분의 알림은 `디스크 사용률 > 95%`, `up == 0` 처럼 뚜렷한 임계값을 갖지만 Prometheus 데이터로 이상 탐지를 할 여지도 분명히 있습니다. 표준편차 같은 값을 계산해 단순한 이상 탐지를 만들 수 있습니다. 통계 지식이 필요한 주제라 이 책의 범위를 벗어나며 저자는 z-score 와 계절성을 다룬 [GitLab 의 글](https://about.gitlab.com/blog/2019/07/23/anomaly-detection-using-prometheus/)을 권합니다.

### 알림 룰 단위 테스트

알림 테스트는 Prometheus 기능 중 덜 이야기되는 축입니다. 사고가 났던 시간 범위를 놓고 쿼리를 돌려 "이 쿼리라면 잡았겠군" 하고 확인하는 방식이 흔합니다. 유효한 방법이지만 룰을 이리저리 손본 뒤에도 계속 동작하리라는 보장은 주지 못합니다.

알림은 Prometheus 안에서 정의되고 평가되므로 `amtool` 이 아니라 **`promtool`** 을 씁니다. 단순 검증과 단위 테스트는 다른 명령입니다.

```console
$ promtool check rules ch5/test-rule.yaml    # 문법만 검사
$ promtool test rules unit-test.yaml         # 기대대로 발화하는지 검사
```

테스트할 룰부터 둡니다.

```yaml
groups:
  - name: chapter5
    rules:
      - alert: SSHDown
        expr: >
          max_over_time(
            probe_success{job="blackbox_ssh"}[5m]
          ) != 1
        for: 5m
        labels:
          severity: warning
          team: sre
        annotations:
          description: "Cannot SSH to {{ $labels.instance }}"
```

그 다음 테스트 파일을 씁니다. 어느 룰 파일을 대상으로 할지, 얼마나 자주 평가할지, 어떤 입력 시계열을 넣을지 적습니다.

```yaml
rule_files:
  - ./test-rule.yaml

evaluation_interval: 1m

tests:
  - interval: 1m
    input_series:
      - series: 'probe_success{instance="server1", job="blackbox_ssh"}'
        values: "1 1 1 1 0+0x12"
      - series: 'probe_success{instance="server2", job="blackbox_ssh"}'
        values: "1 1 1 _ 1+0x12"
```

`server1` 은 처음 4분 동안 성공하다가 그 뒤로 실패합니다. `server2` 는 3분 성공한 뒤 스크레이프를 한 번 놓치고(`_` 로 표시합니다) 계속 성공합니다.

![단위 테스트의 알림 타임라인](./_assets/05-02.alert-timeline.svg)

`server1` 이 14분 지점에서 알림을 시작하리라 예상하는 근거가 여기 있습니다. `max_over_time` 이 9분이 되어서야 `0` 을 돌려주기 시작하고 룰의 `for` 기간이 5분이므로 14분이 됩니다.

> **확장 표기법** — `values` 필드는 샘플 값을 일일이 적는 대신 `A+BxC` 형태로 줄여 씁니다. `A` 는 시작 값, `B` 는 샘플마다 더할 증분, `C` 는 덧붙일 샘플 수입니다. 뺄셈(`A-BxC`)도 되지만 곱셈과 나눗셈은 되지 않습니다.

이제 무엇이 언제 발화해야 하는지 단언합니다. 9분에는 아무 알림도 발화하지 않아야 합니다.

```yaml
alert_rule_test:
  - alertname: SSHDown
    eval_time: 9m
    exp_alerts: []
  - alertname: SSHDown
    eval_time: 14m
    exp_alerts:
      - exp_labels:
          severity: warning
          team: sre
          instance: server1
          job: blackbox_ssh
        exp_annotations:
          description: "Cannot SSH to server1"
```

14분 쪽 테스트는 기대하는 라벨과 애노테이션을 전부 적게 하므로 **템플릿이 제대로 렌더되는지까지 검증**됩니다. `eval_time` 을 13분으로 낮추면 아직 발화 전이라 테스트가 실패합니다. 값을 이리저리 바꿔 보며 반응을 확인하기 좋은 지점입니다.

```console
$ promtool test rules unit-test.yaml
Unit Testing:  unit-test.yaml
  SUCCESS
```

여러 시계열에서 데이터를 끌어오는 견고한 알림을 테스트하려면 시계열을 정의하는 부분이 꽤 복잡해집니다. 그래도 그 복잡한 알림이 기대대로 동작한다는 확신을 얻을 값어치가 있습니다.



## 심화 학습

**원문의 확장 표기법 설명은 시작 값을 빠뜨립니다.** 본문은 `1+0x12` 가 `1+(0*1) 1+(0*2) 1+(0*3) … 1+(0*12)` 로 펼쳐진다고 적어 샘플 12개를 만드는 것처럼 읽힙니다. 공식 문서는 다르게 적습니다.

> `'a+bxn'` becomes `'a a+b a+(2*b) a+(3*b) … a+(n*b)'` — Read this as series starts at a, then n further samples incrementing by b.

시작 값 `a` 가 먼저 놓이고 그 **뒤에** `n` 개가 더 붙으므로 `1+0x12` 는 샘플 **13개**입니다. 본문의 나열에는 첫 항 `1+(0*0)` 이 빠져 있습니다. 이 차이는 테스트를 직접 돌려 볼 때 드러납니다. 문서는 `axn` 이 `a+0xn` 의 축약이며 `a` 를 `n+1` 번 반복한다고 명시해 같은 규칙을 다시 확인해 줍니다. 원문이 말하는 "16분 어치 데이터" 는 샘플 개수가 아니라 `0분`부터 `16분`까지 흐른 시간으로 읽으면 어긋나지 않습니다. ([Unit testing rules](https://prometheus.io/docs/prometheus/latest/configuration/unit_testing_rules/))

**`_` 말고 `stale` 도 있습니다.** 본문은 놓친 스크레이프를 `_` 로 표시하는 것만 소개합니다. 문서는 stale 마커도 함께 정의하며 `1 _x3 stale` 같은 표기를 예로 듭니다. 결측과 stale 은 PromQL 에서 다르게 취급되므로 staleness 를 다루는 알림을 테스트할 때 구분이 필요합니다.

**`last_over_time` 이 기본값이어야 하는 이유를 한 번 더 짚습니다.** 본문의 예제 룰은 정작 `max_over_time` 을 씁니다. 발화 시점을 14분으로 만들어 설명하기 좋기 때문인데, 실전에서 스크레이프 실패로부터 `for` 를 지키는 것이 목적이라면 `last_over_time` 이 지연을 만들지 않습니다. 위 SVG 에서 `max_over_time` 때문에 발화가 5분 늦어지는 구간이 바로 그 대가입니다.

**증상에 알린다는 원칙은 SLO 노트와 이어집니다.** 이 책이 권하는 "실제로 보이는 영향이 있을 때만 울려라" 는 기존 [`01-04. SLO와 알림`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) 편의 번 레이트 알림과 같은 뿌리입니다. 13장에서 Sloth·Pyrra 로 다시 만납니다.



## 결정 치트시트

> 알림을 덜 시끄럽게 만들 때 고르는 표입니다.

| 증상 | 손잡이 | 이유 |
|------|--------|------|
| 잠깐 튀는 값에 알림이 운다 | `for` 를 늘린다 | 시끄러운 알림과 좋은 알림의 차이는 대개 이것뿐입니다 |
| `for` 를 걸었는데 효과가 없다 | 평가 주기를 확인한다 | `for` 가 평가 주기보다 짧으면 무의미합니다 |
| 스크레이프 한 번 실패에 `for` 가 초기화된다 | `last_over_time(...[5m])` | 범위 안에 값이 있으면 상태가 유지됩니다 |
| 원인 하나에 알림이 여러 개 운다 | `unless` · 억제 규칙 | 조건 자체를 좁히거나 Alertmanager 에서 죽입니다 |
| 재부팅 직후 오탐 | `unless on (instance) changes(node_boot_time_seconds[30m]) > 0` | 같은 시계열에서 값이 바뀔 때만 잡힙니다 |
| 배포·재시작 직후 오탐 | `unless on (instance) (time() - process_start_time_seconds) < 600` | 새 시계열이 생기는 파드에도 통합니다 |
| 임계값을 정할 수 없다 | 이상 탐지(표준편차·z-score) | 정적 임계값이 없는 지표에 씁니다 |

| `for` 기간 | 등급 | 근거 |
|-----------|------|------|
| `0m` · `5m` | critical | 즉시 사람이 움직여야 하는 알림에 아껴 씁니다 |
| `15m` 이상 | warning | 저자 경험칙 — warning 은 15분보다 짧지 않게 |
| `15m` 이하 | critical | 저자 경험칙 — critical 은 15분보다 길지 않게 |
| `1h` · `2h` | 느린 추세 | 겁내지 말고 쓰라고 저자가 권합니다 |



## Spring 앱 개발 관점

**Spring 앱의 오류율 알림도 `and` 로 조여야 실용적입니다.** 오류율만 보면 트래픽이 거의 없는 새벽에 요청 두 건 중 한 건이 실패해도 50% 가 됩니다. 처리량 조건을 함께 걸면 이 오탐이 사라집니다.

```promql
  sum(rate(http_server_requests_seconds_count{status=~"5.."}[5m])) by (service)
/ sum(rate(http_server_requests_seconds_count[5m])) by (service)
  > 0.05
and
  sum(rate(http_server_requests_seconds_count[5m])) by (service) > 1
```

`http_server_requests_seconds_count` 는 Spring Boot Actuator 가 Micrometer 를 통해 내보내는 기본 HTTP 서버 메트릭입니다. 뒤쪽 조건은 초당 요청이 1건을 넘을 때만 알림을 허용합니다.

**배포 직후 오탐도 같은 자리에서 잡습니다.** 앱 재시작 직후의 워밍업 구간은 프로세스 시작 시각으로 걸러 냅니다. Micrometer 의 `UptimeMetrics` 가 `process.start.time` 게이지를 등록하고 Prometheus 쪽에서는 `process_start_time_seconds` 로 나옵니다.

```promql
<알림 조건>
unless on (instance)
(time() - process_start_time_seconds) < 600
```

NTP 예제처럼 `changes(process_start_time_seconds[10m]) > 0` 을 쓰지 않는 데는 이유가 있습니다. `changes` 는 **같은 시계열 안에서** 값이 바뀌어야 잡아냅니다. 재부팅해도 인스턴스 식별자가 유지되는 노드에서는 성립하지만 재시작하며 새 주소를 받는 Kubernetes 파드는 아예 **새 시계열**이 되어 변화를 관측할 대상이 없습니다. 시작 시각으로부터 흐른 시간을 직접 재면 시계열이 새것이든 아니든 똑같이 동작합니다.

**`for` 를 늘리기 전에 평가 주기를 봅니다.** Prometheus Operator 를 쓰면 룰 평가 주기는 `Prometheus` CRD 의 설정을 따르고 기본값이 30초입니다. `for: 15m` 은 문제없지만 평가 주기를 길게 바꾼 환경에서 짧은 `for` 를 걸면 조용히 무력해집니다.

**알림 룰도 CI 에서 테스트합니다.** `promtool check rules` 와 `promtool test rules` 는 바이너리 하나로 도는 명령이라 파이프라인에 넣기 쉽습니다. `PrometheusRule` CRD 로 룰을 관리한다면 CRD 의 `spec.groups` 부분만 떼어 낸 YAML 을 테스트 대상으로 두면 됩니다. 이 흐름은 12장(CI 파이프라인·Pint) 에서 본격적으로 다뤄집니다.



## 면접 대비

**Q. 시끄러운 알림을 조용하게 만드는 가장 단순한 방법은 무엇입니까?**
`for` 기간을 늘립니다. 대부분의 경우 임계값을 바꾸는 것보다 효과가 큽니다. 다만 `for` 는 룰 평가 주기보다 길어야 의미가 있습니다. 5분마다 평가하는 룰에 `for: 3m` 을 걸면 아무 일도 하지 않습니다.

**Q. 스크레이프가 한 번 실패하면 `for` 가 왜 초기화됩니까?**
실패한 스크레이프 뒤 룰을 평가하면 쿼리 표현식이 아무 데이터도 돌려주지 않습니다. 알림 조건이 참이 아니게 되므로 pending 상태에서 떨어지고 쌓아 온 시간이 사라집니다. `last_over_time(...[5m])` 처럼 범위 안의 마지막 값을 쓰면 결측 한 번이 상태를 지우지 못합니다.

**Q. `last_over_time` 대신 `max_over_time` 을 쓰면 무엇이 달라집니까?**
알림 동작 자체가 바뀝니다. `probe_success != 1` 예제에서 `max_over_time(...[5m])` 은 5분 창 안의 최댓값이 `1` 이 아니어야 참이 되므로, 시계열이 5분 내내 `0` 이어야 합니다. `for` 기간 위에 창 길이만큼 지연이 더 얹힙니다.

**Q. 메모리 사용률이 높다는 이유만으로 알리지 않는 이유는 무엇입니까?**
높은 메모리 사용률 자체는 문제가 아닐 수 있습니다. 메이저 페이지 폴트 비율이 함께 높을 때가 메모리 압박의 더 나은 지표입니다. `and` 로 두 조건을 묶으면 실제 영향이 있을 때만 알림이 울립니다. 증상에 알리고 원인에는 알리지 않는다는 원칙의 한 사례입니다.

**Q. 알림 룰을 테스트하려면 `amtool` 을 씁니까?**
아닙니다. 알림은 Prometheus 안에서 정의되고 평가되므로 `promtool` 을 씁니다. `promtool check rules` 는 문법만 보고 `promtool test rules` 는 입력 시계열을 지어 넣어 특정 시점에 어떤 알림이 어떤 라벨·애노테이션으로 발화하는지 단언합니다. `amtool` 은 Alertmanager 쪽 설정과 템플릿을 다룹니다.

**Q. 단위 테스트로 템플릿까지 검증할 수 있습니까?**
됩니다. `exp_alerts` 에 기대하는 `exp_labels` 와 `exp_annotations` 를 전부 적으므로, 애노테이션 안의 `{{ $labels.instance }}` 가 `server1` 로 렌더되는지까지 확인됩니다.



## 핵심 개념 체크리스트

- [ ] `and`·`or`·`unless` 로 알림 조건을 좁히는 예를 들 수 있는가?
- [ ] `unless on (instance) changes(...) > 0` 이 무엇을 걸러 내는지 설명할 수 있는가?
- [ ] `_info` 메트릭 패턴의 값과 목적을 아는가?
- [ ] warning 과 critical 의 `for` 경험칙을 말할 수 있는가?
- [ ] `for` 가 평가 주기보다 길어야 하는 이유를 아는가?
- [ ] 스크레이프 실패가 `for` 상태를 초기화하는 메커니즘을 설명할 수 있는가?
- [ ] `last_over_time` 이 기본 선택인 이유를 아는가?
- [ ] `max_over_time` 을 쓸 때 생기는 추가 지연을 계산할 수 있는가?
- [ ] 알림 테스트에 `promtool` 을 쓰는 이유를 아는가?
- [ ] `promtool check rules` 와 `promtool test rules` 의 차이를 아는가?
- [ ] `input_series` 의 `_` 가 무엇을 뜻하는지 아는가?
- [ ] 확장 표기법 `A+BxC` 의 세 인자를 설명할 수 있는가?
- [ ] 단위 테스트가 애노테이션 템플릿까지 검증한다는 사실을 아는가?
