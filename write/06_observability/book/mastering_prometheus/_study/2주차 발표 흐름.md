# 2주차 발표 흐름 — 각 슬라이드가 무엇을 전달하는가

> `2주차 발표자료.pdf` (41장) 의 발표자용 노트입니다. 각 슬라이드가 **무엇을 말하는지**와 **왜 그 자리에 있는지**를 적었습니다.
> 원문 범위: Mastering Prometheus 3·4·5·8장. 예상 소요 50~60분.

---

## 전체 흐름 — 한 문장

**대상을 찾는다 → 값을 긁는다 → 시계열로 저장한다 → 규칙을 평가한다 → 알림을 묶어 사람에게 보낸다.**

이 한 줄이 덱의 척추이고, **슬라이드 순서가 이 흐름을 그대로 따릅니다.** 값이 태어나는 자리에서 시작해 사람에게 도착하는 데서 끝납니다.

| 구간 | 슬라이드 | 장수 | 시간 | 전달 목표 |
|---|---|---|---|---|
| **시작** 지도 | 1–2 | 2 | 4분 | 지도와 최소 용어 |
| **수집** 대상 선별 + 값 생성 | 3–17 | 15 | 22분 | 무엇을 긁을지 고르고, 값은 누가 만드는가 |
| **저장** 데이터·TSDB·PromQL | 18–28 | 11 | 16분 | 그 값이 어떤 모양으로 쌓이고 질의되는가 |
| **알림** 두 프로그램 | 29–38 | 10 | 14분 | 책임 분리와 통지 제어 |
| **종합** 연결과 회상 | 39–41 | 3 | 4분 | 전체 연결과 회상 |

각 구간은 **간지 슬라이드**(3·18·29)로 열립니다. `STEP n / 3` 표시와 그 구간이 파이프라인의 어느 토막인지, 다룰 소재를 한 화면에 둡니다.

> **Exporter는 수집에 속합니다.** "값을 만드는 쪽"이므로 SD·relabeling과 같은 구간에 두었습니다. 다만 CPU 계산 슬라이드(28)만은 `rate`·`sum without`를 쓰기 때문에 **PromQL을 배운 뒤인 저장 구간 끝**으로 뺐습니다 — 안 배운 문법을 먼저 보여 주지 않기 위해서입니다.

> 슬라이드에는 책의 장 번호를 노출하지 않습니다. 좌상단 라벨과 푸터는 **주제명**(시작·수집·저장·알림·종합)입니다.

## 시작 (1–2) — 지도를 먼저 준다

| # | 슬라이드 | 전달 목표 |
|---|---|---|
| 1 | 표지 | 오늘의 프레임을 한 문장으로: "관측값을 **믿을 만한 신호**로 만드는 과정". 기능 나열이 아니라 하나의 파이프라인을 본다는 선언 |
| 2 | 오늘 따라갈 한 줄 | **덱 전체의 목차.** 다섯 동사를 심고 용어 넷(메트릭·라벨·스크레이프·알림)을 압축. 오른쪽 카드로 세 구간을 예고하고 **"다섯 동사를 그 순서 그대로 따라간다"**를 못 박음 |

> 발표 팁: 2번에서 "앱이 보내는 게 아니라 서버가 가져간다"(pull)를 강조하면 뒤의 SD·relabeling·staleness가 전부 이 전제 위에 얹힙니다.

## 수집 (3–17) — 무엇을 긁을지 고르고, 값은 누가 만드는가

가장 긴 구간입니다. 두 덩어리로 나뉩니다: **대상 선별(4–11) → 값 생성(12–18)**.

### 대상 선별 (3–10)

| # | 슬라이드 | 전달 목표 |
|---|---|---|
| 3 | **간지 — 수집** | `STEP 1 / 3`. "대상을 찾는다 → 값을 긁는다" |
| 4 | 서비스 디스커버리는 후보만 만듭니다 | **Prometheus는 스스로 대상을 모른다.** 주소 목록을 대신 받아 오는 일. 흐름 한 줄로 SD→relabel→scrape 예고 |
| 5 | relabeling은 두 번 돌고, 거르는 것이 다릅니다 | **글·표로 두 relabeling을 가름.** 언제/무엇을/무엇이 줄고/못 하는 일 4축 비교 |
| 6 | 후보에서 저장까지, 무엇이 걸러지는가 | **통째 흐름도.** 4단계 + 단계별 개수(120→40→8천→5천) + `__meta_*`가 어디서 생겨 어디서 사라지는지 + 남기는 법 |
| 7 | 규칙 하나는 부품 다섯으로 읽습니다 | **좌 YAML · 우 필드표.** `app=api`만 긁는 실제 규칙으로 부품 다섯을 읽음. regex 양끝 앵커링 |
| 8 | 후보 수를 바꾸는 액션은 둘뿐입니다 | **좌 YAML · 우 액션표.** `keep`/`drop`만 후보를 줄이고 나머지는 라벨만 손댐 |
| 9 | 쿠버네티스에서는 Operator가 대신 씁니다 | 앞 장들의 설정을 **손으로 쓰지 않는다**는 연결. ServiceMonitor→번역→prometheus.yaml 흐름 |
| 10 | 안 긁힐 때는 증상으로 화면을 고릅니다 | 두 화면의 역할 구분(발견·선별 vs 연결). SD 정상인데 DOWN이면 **고칠 곳은 대상 쪽** |

### 값 생성 — Exporter (11–17)

| # | 슬라이드 | 전달 목표 |
|---|---|---|
| 11 | Exporter는 다른 시스템의 값을 번역합니다 | 세 부품. **`Collect`는 스크레이프 때 값을 만든다** = 미리 담아 두지 않음. 4번에서 예고한 "값은 exporter가 만든다"의 회수 |
| 12 | collector는 병렬로 실행됩니다 | **전체 시간 ≈ 가장 느린 하나.** 기본 45개가 고루틴으로 동시 실행 |
| 13 | 메모리는 free와 available을 구분합니다 | **`MemFree`를 임계값에 쓰면 멀쩡한 서버가 부족해 보인다.** 리눅스가 남는 메모리를 캐시로 쓰기 때문 |
| 14 | loadavg 대신 pressure를 보십시오 | 커널 주석("실없는 숫자") 인용. PSI의 waiting/stalled 구분. **디스크·메모리를 우선 감시** |
| 15 | 타임아웃은 duration으로 범인을 찾습니다 | `collector_duration_seconds`부터. **`success=0`이 하드웨어 부재일 수도** |
| 16 | textfile collector는 짧은 작업의 기록을 노출합니다 | cron·배치처럼 금방 끝나는 작업. `mtime`으로 조용한 실패 방지 |
| 17 | 복습: exporter를 의심하는 순서 | 증상→먼저 볼 것 표. Q&A로 12번(병렬)을 회수하고 **수집 구간을 닫음** |

## 저장 (18–28) — 그 값이 어떤 모양으로 쌓이는가

| # | 슬라이드 | 전달 목표 |
|---|---|---|
| 18 | **간지 — 저장** | `STEP 2 / 3`. "시계열로 저장한다 → 질의한다" |
| 19 | 라벨 전체가 시계열 하나를 정합니다 | 메트릭·시계열·샘플 3층 + 좋은/위험한 라벨. 결론은 "라벨 값 하나가 달라지면 별도 시계열" → **카디널리티 비용의 출발점** |
| 20 | 타입은 관측 하나가 시계열 몇 개가 되는지를 정합니다 | 4타입을 **저장 관점**으로 재정렬. Histogram=버킷+2. 19번의 카디널리티가 타입 문제로 되돌아옴 |
| 21 | 샘플 하나는 WAL과 head로 동시에 갑니다 | **▶ 인터랙티브 시연 1.** 두 갈래(WAL 먼저, head 동시)와 2시간 주기를 보이고 `02-01`로 전환 |
| 22 | WAL은 아직 블록이 아닌 데이터를 지킵니다 | WAL의 존재 이유 = **재시작 복구**. "없으면 최대 2시간치가 증발" |
| 23 | 블록은 불변이고, 그 제약이 나머지를 규정합니다 | 네 조각 + **불변성이 tombstone·컴팩션·보존을 어떻게 강제하는지**. 이 구간의 열쇠 |
| 24 | 인덱스는 라벨에서 샘플까지 두 단을 거칩니다 | 포스팅(라벨→ID) · 시리즈(ID→위치), 교집합 예시. 질의가 왜 빠른지 |
| 25 | 컴팩션이 키우고 보존이 지웁니다 | 2h→6h→18h→54h. **왜 합치나 = 인덱스 반복 낭비.** 보존이 폴더째인 이유는 23번 불변성 회수 |
| 26 | PromQL은 순간과 범위에서 출발합니다 | 대괄호 경계 + `rate` + **`by`(닫힌)/`without`(열린)**. 운영에서 실제로 물리는 지점 |
| 27 | 그래프의 구멍은 대개 staleness입니다 | **이 구간의 클라이맥스.** 5분 lookback delta. "선 없음"이 *0건*인지 *앱이 죽음*인지 구별 불가 → **값이 0이어도 계속 내보내야 한다** |
| 28 | 배운 PromQL로 실제 값을 읽어 봅니다 | **26번의 문법을 11~16번의 Node Exporter 값에 적용하는 다리.** CPU는 초로 나오고, **`mode="idle"`이 필수인 이유**를 설명 |

> 27번은 원문이 "저자가 가장 자주 걸려 넘어지는 함정"으로 꼽은 개념입니다. 시간이 부족해도 이 슬라이드는 남기십시오.
>
> 28번은 수집 구간과 저장 구간을 잇는 자리입니다. "아까 본 그 메트릭을 이제 읽을 수 있다"로 넘어가면 자연스럽습니다.

## 알림 (29–38) — 두 프로그램의 책임 분리

이 구간의 **단 하나의 메시지**: Prometheus의 상태와 Alertmanager의 상태는 다른 것이다.

| # | 슬라이드 | 전달 목표 |
|---|---|---|
| 29 | **간지 — 알림** | `STEP 3 / 3`. "규칙을 평가한다 → 묶어서 보낸다" |
| 30 | 알림은 두 프로그램이 나눠 맡습니다 | 책임 분리 선언. **Prometheus는 알림을 보내지 않는다.** 실습: AM을 멈춰도 firing은 유지 |
| 31 | `for`는 순간 이상과 지속 이상을 가릅니다 | **▶ 인터랙티브 시연 2.** 상태 머신 SVG + `02-02`에서 세 시나리오 비교 |
| 32 | `for`를 얼마로 둘지에는 경험칙이 있습니다 | warning ≥15분 / critical ≤15분. **평가 주기보다 길어야 의미가 있다.** 반대편 손잡이 `keep_firing_for` |
| 33 | 짧은 실패가 `for`를 되돌릴 수 있습니다 | 스크레이프 한 번 실패 → pending 0분. **27번 staleness가 알림에서 되돌아오는 자리.** `last_over_time()` |
| 34 | 그룹핑은 폭풍을 한 묶음으로 바꿉니다 | 노드 100대 = 메일 한 통. 세 타이머의 역할 구분 |
| 35 | 라우트 트리와 시간 구간이 수신자를 정합니다 | 첫 매치에서 멈춤 + `continue`, mute/active 구간. **최상위 라우트엔 못 건다** |
| 36 | 억제는 원인이 결과 알림을 가립니다 | source/target/equal. **`equal`이 없으면 다른 클러스터 장애까지 가려짐** |
| 37 | `promtool test rules`로 알림을 테스트합니다 | `check`(문법) vs `test`(발화). amtool이 아닌 이유. **알림도 코드다** |
| 38 | Alertmanager 앞에 로드밸런서를 두지 마십시오 | 가십은 *침묵·발송 사실*만 공유, *받은 알림*은 공유 안 함 → **LB를 두면 알림이 유실됨** |

> 38번은 잘못 구성하면 **장애 시 알림이 안 가는** 구성입니다. 운영 청중이 있으면 여기서 시간을 더 쓰십시오.

## 시간이 부족할 때 줄일 순서

1. **8** (액션표) — 7번만 있어도 문법은 읽힘
2. **9** (Operator 두 경로) — K8s 환경이 아니면 생략 가능
3. **32** (`for` 경험칙) — 31번이 개념을 이미 전달함
4. **13** (free vs available) — 14번 pressure가 더 중요

**절대 빼지 말 것**: 5–6(두 relabeling·전체 흐름도) · 27(staleness) · 30(책임 분리) · 38(LB 금지) · 40(진단표). 간지(3·18·29)도 유지하십시오 — 구간 전환 신호입니다.
