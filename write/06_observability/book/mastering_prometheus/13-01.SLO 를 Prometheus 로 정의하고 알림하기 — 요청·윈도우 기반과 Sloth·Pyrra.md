# SLO 를 Prometheus 로 정의하고 알림하기 — 요청·윈도우 기반과 Sloth·Pyrra

---



## 핵심 요약

> SLO 는 서비스가 얼마나 잘 도는지를 0–100% 하나의 숫자로 재는 약속입니다. SLI(원시 지표) 위에 얹히고 SLA(계약·벌칙)는 그 위에 얹힙니다. Prometheus 는 메트릭 시스템이라 SLI 의 이상적인 공급원입니다.
>
> SLO 는 두 종류입니다. **요청 기반**은 좋은 요청 ÷ 전체 요청이라 흔하고 단순하지만 트래픽이 적거나 이상 폭증이 있으면 왜곡됩니다. **윈도우 기반**은 좋은 창 ÷ 전체 창이라 폭증에 강하지만 데이터 해상도를 잃습니다. 대개 둘을 섞어 씁니다.
>
> Prometheus 에서 SLO 는 recording rule 로 미리 계산하고 알림은 **error budget 소진 속도(burn rate)** 에 겁니다. burn rate 이론 자체는 [`01-04.SLO와 알림`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) 에 정리돼 있으므로, 이 편은 이 책이 새로 더하는 것 — 요청·윈도우 기반의 PromQL, `clamp_min` 안전장치, `>= bool` 창 판정, 그리고 규칙을 자동 생성하는 **Sloth·Pyrra** — 에 집중합니다.
>
> 손으로 쓰면 창마다 recording·alert 규칙이 수십 개로 불어납니다. Sloth 는 SLO 설정 하나에서 **17개 규칙을 3개 그룹**으로 생성합니다(실측 확인). Pyrra 는 같은 일을 CRD 형식과 웹 UI 로 합니다.



## 학습 목표

> - SLI·SLO·SLA 의 층위와, 어떤 Prometheus 메트릭이 좋은 SLI 인지 판별할 수 있습니다.
> - 요청 기반과 윈도우 기반 SLO 의 차이를 이상 트래픽 회복 시나리오로 설명하고 서비스에 맞는 쪽을 고를 수 있습니다.
> - recording rule 로 SLO 를 미리 계산하고 `>= bool` 과 `[30d:5m]` 서브쿼리로 윈도우 기반 SLO 를 만들 수 있습니다.
> - burn rate 알림이 [`01-04`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) 의 다중 윈도우 패턴과 어떻게 이어지는지 압니다.
> - Sloth 와 Pyrra 가 규칙을 자동 생성하는 방식과 둘의 차이(30일 vs 28일 창 등)를 설명할 수 있습니다.



## 본문 정리

### SLI · SLO · SLA — 세 층위

세 약어는 층을 이룹니다.

- **SLI**(지표) — 가장 낮은 층. 개별 원시 메트릭입니다. 예: 애플리케이션의 에러 응답 수. Prometheus 가 바로 이 층을 공급합니다.
- **SLO**(목표) — 하나 이상의 SLI 를 묶어 0–100% 로 재는 성능 척도. 흔히 "나인(nines)"으로 셉니다 — 99.9% 는 three nines, 99.99% 는 four nines. 예: "요청의 99.9% 는 에러 없이 처리된다."
- **SLA**(계약) — SLO 에 계약과 벌칙(예: 서비스 크레딧)을 붙인 것. 이 책은 기술 중심이라 SLA 는 깊이 다루지 않습니다.

> 이 세 층은 [`01-04`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) §2 에서도 다룹니다. 그쪽은 SRE 진영의 표준 어휘로, 이쪽은 Prometheus 메트릭을 SLI 로 쓰는 관점으로 봅니다.

모든 Prometheus 메트릭이 좋은 SLI 는 아닙니다. `prometheus_build_info` 같은 정보성 메트릭은 서비스가 잘 도는지 아무것도 말해 주지 않아 나쁜 SLI 입니다. 반면 `prometheus_http_requests_total` 은 요청 수와 응답 상태를 말해 주므로 좋은 SLI 입니다. OKR·KPI 라는 비즈니스 용어와도 겹치는데, KPI 가 SLI 에, OKR 이 SLO 에 대체로 대응합니다.

### SLO 는 아래에서 위로 정하는 게 좋습니다

저자의 경험칙 하나. SLO 는 **탑다운보다 보텀업**일 때 효과적입니다. 서비스를 운영하는 팀이 정하고 그 위 임원은 검토·승인합니다. 다만 error budget 을 넘겼을 때 다른 프로젝트를 미루고 신뢰성에 집중하는 결정은 리더십의 buy-in 이 필요하므로, 리더십도 SLO 에 공식 합의해야 합니다.

100% 가동을 목표로 삼지 않는 것도 원칙입니다. 네트워크·전원 장애, 하드웨어 고장, 하류 의존성 같은 통제 밖 요인이 너무 많기 때문입니다. 그래서 **희망이 아니라 현실로** SLO 를 잡습니다. 구글은 SLO 를 과도하게 초과 달성할 때 일부러 통제된 장애를 내기도 합니다 — 소비자가 팀이 약속한 것보다 높은 가용성에 의존하지 않게 하려고요.

### 두 종류의 SLO — 요청 기반과 윈도우 기반

**요청 기반**은 가장 흔하고 단순합니다. 좋은 요청과 전체 요청의 비율입니다. 꾸준한 트래픽을 받는 서비스에 잘 맞습니다.

**윈도우 기반**은 요청이 아니라 시간 창으로 잽니다. 좋은 창과 나쁜 창을 가르는 기준을 하나 두고 좋은 창의 비율을 SLO 로 삼습니다. 그래서 목표가 둘입니다 — 창이 좋은지 나쁜지 가르는 임계값, 그리고 좋은 창의 목표 비율.

둘의 차이는 이상 트래픽에서 극명합니다.

![요청 기반 vs 윈도우 기반 SLO](_assets/13-01.request-vs-window-slo.svg)

책의 예시가 이를 잘 보여 줍니다. 평소 분당 20건인 서비스가 나쁜 창 하나 동안 초당 500건의 이상 트래픽을 받아 전부 실패했다면 — **요청 기반**에서는 그 많은 실패 요청을 정상 요청으로 희석해야 해서 50% 로 돌아오는 데 약 **16일**이 걸립니다. **윈도우 기반**에서는 그것이 나쁜 창 하나로만 계산되므로, 좋은 창 15개(3.75시간)면 95% 로 회복됩니다.

그렇다고 윈도우 기반이 늘 낫지는 않습니다. 실패 요청이 곧 매출 손실인 결제 API 는 요청 하나하나가 중요하니 요청 기반이 맞습니다. "몇 분이나 죽었나"가 더 중요한 Prometheus 자체 가용성은 윈도우 기반이 맞습니다. 그리고 윈도우 기반은 해상도를 잃습니다 — 15분 창이면 30초마다 긁어도 좋은지 나쁜지 판정은 15분에 한 번뿐입니다.

### recording rule 로 SLO 정의하기

SLO 는 보통 **recording rule** 로 정의합니다. SLI 는 여러 인스턴스·차원에 걸쳐 집계해야 하므로, 긴 시간 범위 쿼리를 매번 돌리기보다 미리 계산해 두는 편이 낫습니다. 결과 시계열 이름을 서비스마다 통일하고 라벨로만 구분하면, SLO 를 서비스 간에 쉽게 조회할 수 있습니다.

요청 기반 SLI 의 recording rule 은 이렇게 생겼습니다(핵심만).

```yaml
- record: slo:sli_success:ratio5m
  expr: |
    clamp_min(
      sum without (pod, instance) (
        increase(prometheus_http_request_duration_seconds_bucket{le="0.1"}[5m])
      ), 1
    )
    / ignoring (le)
    clamp_min(
      sum without (pod, instance) (
        increase(prometheus_http_request_duration_seconds_bucket{le="+Inf"}[5m])
      ), 1
    )
  labels:
    service: prometheus
    slo: prometheus-request-latency
    window: 5m
```

5분 동안 100ms(`le="0.1"`) 이내에 처리된 요청을 전체 요청(`le="+Inf"`)으로 나눠, 엔드포인트별로 0.0–1.0 값을 냅니다. `clamp_min(..., 1)` 이 핵심 안전장치입니다. 분모·분자를 최소 1로 바닥을 깔아, **요청이 하나도 없던 엔드포인트도 100% 로 보고**되게 합니다. 값이 없어 NaN 이 되는 것을 막습니다.

> **저자가 인정한 엣지 케이스.** 이 안전장치에는 틈이 있습니다. 한 창에 요청이 딱 하나뿐이고 그것이 100ms 를 넘겼다면, 분자의 `clamp_min` 때문에 SLO 가 100% 로 잘못 나옵니다. PromQL 을 더 붙여 우회할 수 있지만 책은 단순함을 위해 생략하고 처리한 쿼리는 GitHub 저장소에 두었다고 밝힙니다.

30일치로 재려면 5분 규칙을 다시 평균 내는 규칙을 하나 더 둡니다.

```yaml
- record: slo:sli_success:ratio30d
  expr: |
    sum_over_time(slo:sli_success:ratio5m{...}[30d])
    / ignoring (window)
    count_over_time(slo:sli_success:ratio5m{...}[30d])
```

`avg_over_time` 대신 `sum_over_time / count_over_time` 을 쓰는 게 눈에 띕니다. 저자는 이를 Sloth·Pyrra 같은 대중적 SLO 도구와 **일관성을 맞추기 위해서**라고 설명합니다.

### 윈도우 기반은 `>= bool` 로 만듭니다

윈도우 기반 SLO 는 서브쿼리(→ `3장` <!-- 링크 끊김(2026-08): ./03-02.PromQL 기초.md -->)와 PromQL 의 `bool` 키워드로 만듭니다. `bool` 은 비교 연산의 결과를 값 자체가 아니라 **0 또는 1** 로 돌려줍니다. 창이 좋은지(임계값 충족) 나쁜지를 1/0 으로 찍는 데 씁니다.

```yaml
- record: slo:sli_success:ratio30d
  expr: |
    avg_over_time(
      (
        ( <위의 성공비율 쿼리> ) >= bool 0.999
      )[30d:5m]
    )
  labels:
    window: 30d
    sli_window: 5m
```

`>= bool 0.999` 가 각 5분 창을 "성공률 99.9% 이상이면 1, 아니면 0" 으로 만듭니다. 서브쿼리 `[30d:5m]` 은 "30일 범위를 5분 간격으로" 라는 뜻으로, 30일 동안의 5분 창들을 만들어 줍니다. 그 1/0 들을 `avg_over_time` 으로 평균 내면 좋은 창의 비율, 곧 윈도우 기반 SLO 가 됩니다.

### SLO 알림 — burn rate 에 겁니다

SLO 알림은 "목표 아래로 떨어졌다"가 아니라 "**목표를 향해 빠르게 타들어 간다**"에 겁니다. 이미 떨어진 뒤 알리면 늦기 때문입니다. 그래서 error budget 을 얼마나 빨리 소진하는지(burn rate)를 봅니다.

이 이론은 [`01-04`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) §4 에 이미 정리돼 있습니다. error budget = 100% − 목표, 다중 윈도우·다중 burn rate, 14.4 라는 숫자의 유래가 거기 있습니다. 이 책이 인용하는 임계값 표(Table 13.1)도 같은 출처(Google SRE Workbook Ch.5)입니다.

| 짧은 창 | 긴 창 | Burn Rate | 소진 budget |
|---|---|---|---|
| 5m | 1h | 14.4 | 2% |
| 30m | 6h | 6 | 5% |
| 2h | 24h | 3 | 10% |
| 6h | 3d | 1 | 10% |

> **주의 — 책의 알림 예시는 부호가 뒤집혀 있습니다.** 이 정오표는 심화 학습에서 자세히 봅니다. 요지만 먼저 적으면, 책의 `SLOBurnRateHigh` 알림은 **성공** 비율(`slo:sli_success:ratio`)을 burn rate 임계값과 `>` 로 비교하는데, SRE Workbook 의 정본은 **에러** 비율을 `>` 로 비교합니다. 성공 비율(정상 시 ~0.999)을 `> 0.0144` 로 비교하면 **정상일 때 발화**하고 오히려 심한 장애 때 조용해지는, 뒤집힌 알림이 됩니다.



## 심화 학습

### 책의 burn rate 알림은 정본과 부호가 어긋납니다

이 장에서 가장 조심할 지점입니다. 책이 인쇄한 `SLOBurnRateHigh` 알림은 이렇게 시작합니다.

```yaml
- alert: SLOBurnRateHigh
  expr: |
    (
        slo:sli_success:ratio5m{slo="prometheus-request-latency"} > (14.4 * 0…
      and
        slo:sli_success:ratio1h{slo="prometheus-request-latency"} > (14.4 * 0…
    )
    or …
```

여기서 비교 대상이 `slo:sli_success:ratio` — **성공** 비율입니다. 이 책의 앞선 recording rule(위 §recording rule 로 SLO 정의하기)이 이 시계열을 명시적으로 "좋은 요청 ÷ 전체 요청" 으로 정의했습니다. 성공 비율은 정상일 때 0.999 근처이고 `14.4 * 0.001 = 0.0144` 보다 언제나 큽니다. 즉 이 알림은 **정상일 때 항상 발화**합니다. burn rate 알림의 의도와 정반대입니다.

이 책이 임계값 표의 출처로 대는 Google SRE Workbook 의 정본은 **에러** 비율을 비교합니다. 공식 문서를 직접 확인했습니다.

```pseudocode
job:slo_errors_per_request:ratio_rate1h{job="myjob"} > (14.4*0.001)
```

`slo_errors_per_request` — 에러 비율입니다. 에러 비율은 정상일 때 0 근처이고 나쁠 때 커지므로, `> 0.0144` 가 "지금 error budget 을 14.4배 속도로 태우고 있다"를 올바로 잡아냅니다. 우리 저장소의 [`01-04`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) §6 알림 룰도 이 정본을 따라 `job:slo_errors_per_request:ratio_rate1h > (14.4 * 0.001)` 로 되어 있습니다.

그래서 책의 알림 예시는 시계열 이름을 `sli_error` 로 바꾸거나 비교를 뒤집어야 맞습니다. 앞의 recording rule 이 `sli_success` 를 만들었으니, 알림도 그 이름을 그대로 쓴 것이 부호 오류로 이어졌습니다.

> **읽어낼 수 없던 부분.** 책 PDF 는 임계값을 페이지 너비에서 잘라 `(14.4 * 0…`, `(6 * 0.0…` 까지만 보입니다(`pdftotext` 의 `-layout`·`-raw` 양쪽 모두 동일하게 잘림). 그래서 책이 의도한 정확한 임계값 수치는 원문에서 확인할 수 없었습니다. 정본 기준으로는 `14.4 * 0.001`(=0.0144), `6 * 0.001`(=0.006)이 그 자리에 옵니다. 여기서는 잘린 사실을 밝혀 두고 정본 수치를 근거로 논지를 폅니다.
>
> 검증: [Google SRE Workbook — Alerting on SLOs](https://sre.google/workbook/alerting-on-slos/) 의 예시 알림 형태를 직접 확인했습니다.

### Sloth 는 설정 하나에서 17개 규칙을 냅니다 — 실측

책은 Sloth 가 "SLO 하나에서 3개 그룹에 걸쳐 17개 규칙"을 낸다고 하고 전체 출력은 생략합니다. Sloth v0.11.0(책의 버전)을 빌드해 책의 `sloth.yaml` 을 그대로 돌려 확인했습니다.

```bash
sloth generate -i sloth.yaml -o sloth-generated.yaml
INFO SLI recording rules generated       rules=8   window=30d
INFO Metadata recording rules generated  rules=7   window=30d
INFO SLO alert rules generated           rules=2   window=30d
INFO Prometheus rules written            groups=3
```

8 + 7 + 2 = **17개, 3개 그룹**. 책과 정확히 일치합니다. 생성된 창도 책이 적은 Sloth 의 창 집합과 정확히 같았습니다 — **5m, 30m, 1h, 2h, 6h, 1d, 3d, 30d** 입니다(`ratio_rate*` 레코드 이름으로 확인).

Sloth 설정에서 눈여겨볼 점 둘. 첫째, 창을 직접 쓰지 않고 `{{.window}}` 를 범위 선택자에 둡니다. Sloth 가 Go 템플릿으로 여러 창의 규칙을 찍어낼 때 이 자리를 치환합니다. 둘째, 비율의 분자를 **성공이 아니라 에러**로 바꿔야 합니다(`error_query`) — 전체에서 임계 충족분을 빼서 에러 수를 만듭니다. 앞의 부호 문제와 이어지는 지점입니다. 정본 도구는 에러 비율로 셈합니다.

`alerting` 의 `page_alert`·`ticket_alert` 는 이름이 임의적이라 헷갈립니다. **page** 는 budget 을 빠르게 태워 즉시 대응이 필요한 critical 알림, **ticket** 은 언젠가 소진되겠지만 시간 여유가 있는 warning 입니다. 각각 `disable: true` 로 끌 수 있습니다.

### Pyrra 는 28일 창을 하드코딩합니다

Pyrra 는 같은 일을 다르게 합니다 — 웹 UI 가 있고(정의는 여전히 YAML), Prometheus 옆에 상주하는 프로세스로 돌리도록 설계됐으며 설정이 쿠버네티스 CRD 형식(`apiVersion: pyrra.dev/v1alpha1`, `kind: ServiceLevelObjective`)입니다.

책이 짚는 실무적 함정 하나. Pyrra 는 burn rate 창을 **28일 슬라이딩 윈도우 가정**으로 하드코딩해서, Sloth 의 깔끔한 창(5m, 30m, 1h, 2h, 6h, 1d, 3d, 30d)과 달리 어긋난 창(5m, 32m, 1h4m, 2h9m, 6h26m, 1d1h43m, 4d6h51m)을 냅니다. 큰 문제는 아니나, 조직의 다른 팀에 Pyrra 를 권할 때 "왜 창이 이렇게 지저분하냐"는 질문을 부릅니다.

> 이 28일 vs 30일 차이는 [Pyrra 문서](https://github.com/pyrra-dev/pyrra)·SLO 도구 관례로 확인했으나, 어긋난 창 값 자체(`32m`·`1h4m` 등)는 **직접 재현하지 못했습니다.** Pyrra v0.7.2 는 웹 UI(`ui/build`)를 `go:embed` 로 포함해 `go install` 만으로는 빌드되지 않습니다. Sloth 는 실측했고(위), Pyrra 의 정확한 창 값은 책 서술을 그대로 옮긴 것임을 밝혀 둡니다.

또 Pyrra 는 `metric` 필드에 벡터 선택자만 받고 PromQL 함수를 못 써서, `clamp_min` 안전장치와 `without` 로 보존하던 라벨을 포기해야 합니다. 대신 `grouping` 필드로 `by` 집계에 넣을 라벨을 지정합니다. 반대로 Pyrra 는 latency SLO 타입을 네이티브로 지원해, 에러율 유도 쿼리를 손댈 필요가 없다는 장점이 있습니다.

### 왜 `avg_over_time` 을 안 쓰는가 — 도구 호환의 흔적

앞서 30일 평균을 `sum_over_time / count_over_time` 으로 냈습니다. 수학적으로는 `avg_over_time` 과 같은데도요. 저자는 이를 Sloth·Pyrra 와의 호환 때문이라 설명합니다. 이 도구들이 생성하는 규칙이 그 형태라, 손으로 쓰는 규칙도 같은 꼴로 맞춰 두면 나중에 도구로 옮기거나 섞어 쓸 때 시계열 의미가 어긋나지 않습니다. 사소해 보이지만 SLO 규칙을 손→도구로 이관할 조직이라면 처음부터 맞춰 두는 편이 낫다는 실무 판단입니다.



## 실무 적용

> Sloth 와 Pyrra 는 실행 모델부터 다릅니다. 도구를 고르는 축과 손으로 쓸 때 지킬 것, 그리고 어느 SLO 타입을 고를지를 차례로 정리합니다.

### SLO 도구 선택 — Sloth vs Pyrra

| 축 | Sloth | Pyrra |
|---|---|---|
| 실행 모델 | 규칙 생성기(`generate` 실행) | 상주 프로세스(Prometheus 당 하나 권장) |
| 설정 형식 | 자체 YAML | 쿠버네티스 CRD |
| 웹 UI | 없음 | 있음(시각화 전용) |
| SLO 창 | 30일 기반, 깔끔한 창 | 28일 하드코딩, 어긋난 창 |
| PromQL 자유도 | `clamp_min` 등 함수 사용 가능 | 벡터 선택자만, `grouping` 으로 라벨 지정 |
| 성숙도 | 저자 曰 사실상 완성형(추가 기능 계획 없음, [issue #521](https://github.com/slok/sloth/issues/521)) | 더 활발히 개발 중 |

둘 다 2021년부터 있었고 저자는 어느 쪽도 명확한 우위는 없으니 둘 다 써 보고 직관에 맞는 쪽을 고르라고 권합니다. Pyrra 로 짜면 손으로 쓸 때보다 **80% 이상 적은 줄**로 같은 SLO 를 정의할 수 있습니다.

### 손으로 쓸 때 지킬 것

도구를 안 쓰고 손으로 SLO 규칙을 쓸 때의 체크포인트입니다.

1. SLI 는 recording rule 로 미리 계산합니다(긴 범위 쿼리를 매번 돌리지 않게).
2. 결과 시계열 이름을 서비스 간 통일하고 라벨로만 구분합니다.
3. `clamp_min(..., 1)` 로 요청 없는 엔드포인트의 NaN 을 막되, "요청 1건이 느릴 때 100% 로 오판"하는 엣지 케이스를 인지합니다.
4. 30일 평균은 `avg_over_time` 이 아니라 `sum_over_time / count_over_time` 으로 — 도구 호환.
5. **알림은 에러 비율에 겁니다.** 성공 비율을 `>` 로 비교하지 않습니다(책의 오류를 답습하지 않기).
6. burn rate 알림 룰은 [`01-04`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) §6 의 한 벌을 참조합니다.

### 어느 SLO 타입을 고를까

| 서비스 성격 | 권장 | 이유 |
|---|---|---|
| 꾸준한 트래픽, 실패=매출 손실(결제 API) | 요청 기반 | 실패 요청 하나하나가 중요 |
| 저트래픽(분당 몇 건) | 윈도우 기반 | 요청 하나가 SLO 를 크게 흔듦 |
| 가용성 = "몇 분 죽었나"(Prometheus 자체) | 윈도우 기반 | 실패 건수보다 지속 시간이 중요 |
| 이상 폭증이 잦음 | 윈도우 기반 | 폭증 규모가 계산에 안 들어옴 |

대부분의 조직은 서비스마다 달라 **두 타입을 섞어** 쓰게 됩니다.



## 체크리스트

- [ ] SLI 로 쓸 메트릭이 서비스 성능을 실제로 말해 주는가(정보성 메트릭은 나쁜 SLI)
- [ ] 서비스 성격에 맞는 SLO 타입(요청/윈도우)을 골랐는가
- [ ] SLO 를 recording rule 로 미리 계산하고 시계열 이름을 통일했는가
- [ ] `clamp_min` 안전장치와 그 엣지 케이스(요청 1건 오판)를 이해했는가
- [ ] 윈도우 기반이면 `>= bool` + `[SLO기간:창크기]` 서브쿼리로 구성했는가
- [ ] 알림을 **에러** 비율의 burn rate 에 걸었는가(성공 비율 `>` 금지)
- [ ] burn rate 임계값을 [`01-04`](../../01_Foundations/01-04.SLO와%20알림%20—%20Error%20Budget,%20Burn%20Rate.md) 의 표에 맞췄는가
- [ ] 도구(Sloth/Pyrra)를 쓴다면 창 기준(30일/28일)과 PromQL 제약을 확인했는가



## 면접 관점

**Q. 요청 기반 SLO 와 윈도우 기반 SLO 는 언제 각각 씁니까?**

요청 기반은 좋은 요청 ÷ 전체 요청이라 꾸준한 트래픽에 맞고 실패 하나하나가 중요한 결제 API 처럼 실패=손실인 경우에 적합합니다. 다만 저트래픽이거나 이상 폭증이 있으면 왜곡됩니다 — 실패 요청 수가 오래 분모·분자에 남기 때문입니다. 윈도우 기반은 좋은 창 ÷ 전체 창이라 폭증에 강합니다(창 하나의 실패가 몇 건이든 한 표). 대신 데이터 해상도를 잃습니다. 실제로는 서비스마다 달라 둘을 섞어 씁니다.

**Q. `clamp_min` 을 SLO 쿼리에 왜 씁니까? 그 한계는?**

요청이 하나도 없던 엔드포인트는 비율이 0/0 = NaN 이 됩니다. `clamp_min(..., 1)` 로 분모·분자를 최소 1로 깔면 그런 엔드포인트도 100% 로 보고돼 시계열이 끊기지 않습니다. 한계는, 한 창에 요청이 딱 하나뿐이고 그것이 느렸을 때 분자의 clamp 때문에 100% 로 오판된다는 점입니다. PromQL 을 더 붙여 우회할 수 있지만 복잡해집니다.

**Q. burn rate 알림을 성공 비율에 걸면 왜 안 됩니까?**

burn rate 알림은 error budget 을 얼마나 빠르게 태우는지에 겁니다. 정본(SRE Workbook)은 **에러** 비율을 임계값과 `>` 로 비교합니다 — 에러율은 정상일 때 0 근처, 나쁠 때 커지므로 `> 0.0144` 가 "14.4배 속도로 태운다"를 올바로 잡습니다. 성공 비율은 정상일 때 0.999 근처라 그 임계값보다 언제나 커서, `>` 로 비교하면 정상일 때 항상 발화합니다. (이 책의 알림 예시가 실제로 이 부호 오류를 담고 있습니다.)

**Q. Sloth 와 Pyrra 는 어떻게 다릅니까?**

둘 다 SLO 설정 하나에서 recording·alert 규칙을 자동 생성합니다(Sloth 는 실측상 17개/3그룹). Sloth 는 실행형 생성기이고 30일 기반의 깔끔한 창을 냅니다. Pyrra 는 Prometheus 옆에 상주하고 웹 UI·CRD 형식을 쓰며 28일을 하드코딩해 어긋난 창을 냅니다. Pyrra 는 `metric` 에 벡터 선택자만 받아 `clamp_min` 을 못 쓰는 대신 latency SLO 를 네이티브 지원합니다. 어느 쪽이든 손으로 수십 개 규칙을 쓰는 것보다 낫습니다.
