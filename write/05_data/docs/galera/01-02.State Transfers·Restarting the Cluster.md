# State Transfers·Restarting the Cluster

---

> 클러스터에서 이탈한 노드가 다시 합류할 때 사용하는 두 가지 상태 전송 경로를 비교하고, 링 버퍼 용량이 허용하는 이탈 시간과 전체 장애 발생 시 안전한 단일 노드 부트스트랩 순서를 다룹니다.

## 학습 목표

> 이 문서를 읽고 나면 노드 복구 방식과 전체 클러스터 정지 복구 절차를 시스템 수준에서 설명할 수 있습니다.

1. 증분 상태 전송(IST)과 스냅샷 상태 전송(SST)이 동작하는 조건과 기증자 노드에 미치는 부하 차이를 비교할 수 있습니다.
2. 쓰기 집합 캐시(GCache)의 링 버퍼 순환 구조가 노드의 안전 이탈 시간 상한을 결정하는 원리를 도출할 수 있습니다.
3. 전체 클러스터 정지 후 `grastate.dat` 상태 파일과 복구 명령으로 최신 노드를 식별하여 부트스트랩하는 순서를 설계할 수 있습니다.
4. 노드 내부 복구 한계를 파악하고 외부 백업 복원과의 경계를 설정할 수 있습니다.



## 1. IST 와 SST 의 상태 전송 방식

> 노드가 클러스터에 다시 들어올 때 빠진 트랜잭션만 가져오는 증분 전송과 전체 저장소를 복사하는 스냅샷 전송의 두 경로로 갈립니다.

![IST 와 SST 의 상태 전송 경로와 Donor 영향](./_assets/01-02.State%20Transfers·Restarting%20the%20Cluster.state-transfers.svg)

일시적인 네트워크 순단이나 점검으로 노드가 분리되면, 복귀 시점에 기존 노드와 데이터 격차가 벌어집니다. 격차를 메우려고 매번 전체 데이터를 복사하면 네트워크 대역폭과 디스크 I/O 가 포화됩니다. 정상 노드의 서비스 처리까지 함께 흔들립니다. Galera Cluster 는 이 부담을 줄이기 위해 증분 상태 전송과 스냅샷 상태 전송의 두 경로를 제공합니다[^ist-mariadb]. 데이터를 제공하는 기존 노드를 도너(Donor), 동기화를 받는 수신 노드를 조이너(Joiner)라고 부릅니다. 이 과정에서 노드 상태가 `JOINER`·`DONOR` 로 바뀌는 순서는 [앞 편](./01-01.Certification-Based%20Replication·Quorum%20Components.md) §2 에서 다뤘습니다.

### 증분 상태 전송과 스냅샷 상태 전송

증분 상태 전송(IST, Incremental State Transfer)은 누락된 쓰기 집합만 골라 복제하는 기법입니다[^ist-mariadb]. 조이너는 자신이 마지막으로 적용한 트랜잭션의 전역 순번(`seqno`)을 알립니다. 도너는 자기 캐시에서 그다음 순번부터 쓰기 집합을 꺼내 스트리밍으로 보냅니다[^ist-mariadb].

IST 가 동작하려면 두 조건이 맞아야 합니다[^ist-mariadb].
- 동일 클러스터 이력: 조이너의 상태 식별자(UUID)가 활성 클러스터와 일치해야 합니다.
- 캐시 보존: 누락된 순번의 쓰기 집합이 도너의 캐시에 남아 있어야 합니다.

IST 가 도는 동안에도 도너는 읽기와 쓰기를 계속 처리합니다[^ist-mariadb].

반면 스냅샷 상태 전송(SST, State Snapshot Transfer)은 도너의 데이터 전체를 복사합니다[^sst-mariadb]. 새 노드가 처음 합류할 때 이 방식으로 데이터를 받습니다[^sst-mariadb]. 이탈이 길어 캐시에 이력이 없는 등 IST 조건이 맞지 않을 때도 클러스터가 자동으로 SST 로 넘어갑니다[^ist-mariadb].

### SST 전송 방식별 도너 잠금과 영향

SST 는 데이터베이스 전체를 복사하므로 도너 노드의 시스템 자원을 크게 소모합니다. 구현 방식은 `wsrep_sst_method` 시스템 변수로 정합니다. 기본값은 `rsync` 입니다[^sysvars-mariadb]. 도너와 조이너가 같은 방식을 써야 하므로 모든 노드에 같은 값을 두라고 공식 문서는 권합니다[^sst-mariadb].

`rsync` 방식은 도너의 데이터 파일을 그대로 복사합니다. 전송하는 동안 도너에는 읽기 잠금이 걸려 쓰기를 처리하지 못합니다[^sst-mariadb]. 대신 바이너리 파일을 그대로 옮기므로 가장 빠른 SST 방식입니다. 공식 문서는 전송 중 도너가 쿼리를 받을 필요가 없을 때 이 방식을 권합니다[^sst-mariadb]. 노드를 세 대 이상 두는 이유도 여기서 하나 더 나옵니다. 한 대가 조이너, 한 대가 잠긴 도너가 되어도 나머지 한 대가 쿼리를 받습니다[^sst-mariadb].

`mariadb-backup` 방식은 같은 이름의 온라인 물리 백업 도구로 데이터를 복사합니다[^sst-mariadb]. 잠그지 않는 방식이라 복사하는 동안에도 도너가 쿼리를 받습니다[^sst-mariadb]. 다만 백업 끝에 잠깐 시스템 전체 잠금(`BACKUP STAGE BLOCK_COMMIT`)을 겁니다[^mbsst-mariadb]. 쓰기를 한 노드로 모으는 구성이라면 그 노드는 도너로 쓰지 않는 편이 낫습니다. 공식 문서는 `wsrep_sst_donor` 로 다른 노드를 도너로 지정하라고 권합니다[^mbsst-mariadb]. 쓰기를 한 노드로 모으는 이유는 [앞 편](./01-01.Certification-Based%20Replication·Quorum%20Components.md) §4 에 있습니다.

| 전송 방식 | 전송 데이터 범위 | Donor 쿼리 차단 여부 | 네트워크 및 디스크 부하 | 주요 발생 시점 |
|---|---|---|---|---|
| 증분 전송 (IST) | 누락된 쓰기 집합 (Write-Set) | 차단 없음 (읽기·쓰기 계속 처리) | 빠진 쓰기 집합의 양에 비례 | 짧은 이탈 뒤 재합류 |
| 스냅샷 전송 (`mariadb-backup`) | 도너의 데이터 전체 | 차단 없음 (백업 끝에 잠깐 전역 잠금) | 높음 (전체 DB 크기 비례) | 새 노드 합류, GCache 이력 초과 |
| 스냅샷 전송 (`rsync`, 기본값) | 도너의 데이터 전체 | 전송 내내 읽기 잠금으로 쓰기 차단 | 높음 (전체 DB 크기 비례, 가장 빠른 SST) | 새 노드 합류, GCache 이력 초과 |



## 2. GCache 용량과 IST 허용 범위

> 쓰기 집합 캐시의 링 버퍼 크기가 노드가 전체 복원(SST) 없이 안전하게 자리를 비울 수 있는 시간 상한을 결정합니다.

![GCache 링 버퍼 구조와 노드 이탈 시간에 따른 전송 분기](./_assets/01-02.State%20Transfers·Restarting%20the%20Cluster.gcache-ringbuffer.svg)

노드를 잠시 재기동했을 뿐인데 전체 데이터를 복사하는 스냅샷 전송이 발생하면 운영 환경에 큰 부하가 걸립니다. 가벼운 증분 전송 대신 무거운 전체 복사가 일어나는 가장 흔한 원인은 캐시 용량 부족입니다[^ist-mariadb]. Galera Cluster 는 최근 쓰기 집합을 노드마다 있는 캐시에 보관합니다. 이 캐시를 쓰기 집합 캐시(GCache, Galera Cache)라고 부릅니다. 주된 목적은 IST 를 가능하게 하는 것입니다[^ist-mariadb].

### GCache 링 버퍼 구조와 순번 순환

GCache 는 디스크의 링 버퍼 파일(기본 이름 `galera.cache`)을 노드가 시작할 때 미리 잡아 둡니다. 크기는 `wsrep_provider_options` 안의 `gcache.size` 로 정하며 기본값은 `128M` 입니다[^provopts-mariadb].

링 버퍼는 공간이 차면 가장 오래된 쓰기 집합부터 밀어냅니다. 그래서 캐시에 남은 가장 오래된 순번은 쓰기가 쌓일수록 계속 커집니다.

조이너가 마지막으로 적용한 순번을 알리면 도너는 그 바로 다음 순번이 자기 GCache 에 있는지 봅니다[^ist-mariadb]. 있으면 그 뒤 쓰기 집합을 모두 보내는 IST 가 됩니다. 이미 밀려났으면 IST 를 할 수 없어 SST 로 넘어갑니다[^ist-mariadb].

### 쓰기 처리량과 노드 허용 다운타임

노드가 안전하게 이탈할 수 있는 시간 $T$ 는 GCache 크기와 초당 쓰기량으로 정해집니다. 공식 문서는 쓰기량을 `wsrep_received_bytes` 상태 변수로 잽니다. 붐비는 시간에 한 시간 간격으로 두 번 읽고 차이를 경과 시간으로 나눕니다[^ist-mariadb].

$$T \approx \frac{\text{gcache.size}}{\text{초당 쓰기 집합 생성량}}$$

공식 문서 예시에서는 쓰기량이 초당 20,346 바이트였습니다. 노드가 두 시간(7,200초) 멈춰도 IST 로 돌아오게 하려면 약 140MiB 가 필요합니다[^ist-mariadb]. 같은 쓰기량에서 기본값 128M 이 버티는 시간을 위 식으로 셈하면 약 6,600초, 1시간 50분 정도입니다. 쓰기량이 열 배가 되면 약 11분으로 줄어듭니다.

범위를 벗어난 조이너는 IST 를 쓰지 못하고 클러스터가 자동으로 SST 로 넘어갑니다[^ist-mariadb]. 그러면 데이터 전체 크기만큼 복사가 일어나 네트워크 대역폭을 점유합니다. 노드가 SST 를 자주 요청하면 `gcache.size` 가 작다는 분명한 신호라고 공식 문서는 말합니다[^ist-mariadb]. 정기 점검 시간과 쓰기 처리량을 함께 보고 `gcache.size` 를 잡아야 합니다.



## 3. 전체 정지 뒤 안전한 부트스트랩 순서

> 모든 노드가 동시에 정지한 재해 상황에서는 가장 앞선 트랜잭션 순번을 가진 단 하나의 노드에서만 새 클러스터를 부트스트랩해야 합니다.

![전체 정지 뒤 안전한 첫 노드 선정과 부트스트랩 절차](./_assets/01-02.State%20Transfers·Restarting%20the%20Cluster.bootstrap-flow.svg)

전력 중단이나 네트워크 장애로 클러스터의 모든 노드가 동시에 내려가면 쿼럼이 사라집니다. 쿼럼과 Primary Component 는 [앞 편](./01-01.Certification-Based%20Replication·Quorum%20Components.md) §2 에서 다뤘습니다. 이때는 노드를 평소처럼 켜도 합류할 Primary Component 가 없습니다. 노드 하나에서 새 Primary Component 를 손으로 시작하는 부트스트랩을 해야 서비스가 돌아옵니다[^quorum-mariadb].

예외가 하나 있습니다. 기본으로 켜져 있는 `pc.recovery` 는 노드가 Primary Component 에 있는 동안 그 구성을 `gvwstate.dat` 파일에 저장합니다. 클러스터가 통째로 내려가도 마지막 구성원이 모두 다시 연결되면 스스로 복구를 시도합니다[^recover-mariadb]. 정상 종료하면 이 파일이 지워지므로, 차례로 정상 종료한 클러스터는 손으로 부트스트랩합니다[^recover-mariadb].

### grastate.dat 와 안전 노드 판정

부트스트랩 시작점은 마지막 트랜잭션을 커밋한 노드, 곧 가장 앞선 노드여야 합니다. 다른 노드에서 시작하면 데이터를 잃을 수 있습니다[^reset-mariadb]. 나머지 노드는 시작점의 상태에 맞춰 합류하기 때문입니다.

최종 상태는 노드마다 데이터 디렉터리의 `grastate.dat` 파일에 있습니다[^reset-mariadb]. 기본 경로는 `/var/lib/mysql/grastate.dat` 입니다. 아래는 공식 문서의 예시입니다.

```ini
# GALERA saved state
version: 2.1
uuid:    9acf4d34-acdb-11e6-bcc3-d3e36276629f
seqno:   15
safe_to_bootstrap: 1
```

`safe_to_bootstrap` 은 클러스터를 차례로 정상 종료했을 때 마지막에 멈춘 노드에만 `1` 로 적힙니다. 그 노드가 가장 최신이므로 시작점으로 잡습니다[^quorum-mariadb]. 이 값이 `0` 인 노드에서 부트스트랩하려 하면 Galera 가 거부하고 로그에 메시지를 남깁니다[^reset-mariadb].

클러스터 전체가 비정상 종료했다면 모든 노드의 값이 `0` 일 가능성이 큽니다[^quorum-mariadb]. 그때는 `seqno` 가 가장 큰 노드를 찾습니다. 비정상 종료한 노드는 `seqno` 가 `-1` 로 남아 있을 수 있습니다. 그러면 파일로는 비교할 수 없습니다[^gs-mariadb].

이때는 노드마다 `--wsrep-recover` 옵션으로 `mysqld` 를 실행합니다. InnoDB 로그를 읽어 마지막 트랜잭션 위치를 에러 로그에 남깁니다[^reset-mariadb].

```bash
# 노드마다 실행: InnoDB 로그를 읽어 마지막 트랜잭션 위치를 에러 로그에 남긴다
mysqld --wsrep-recover
# 에러 로그 예 (공식 문서): [Note] WSREP: Recovered position: 37bb872a-ad73-11e6-819f-f3b71d9c5ada:345628
```

콜론 뒤의 숫자가 순번입니다. 모든 노드의 값을 비교해 가장 큰 노드를 시작점으로 고릅니다[^reset-mariadb].

### 단일 부트스트랩 실행과 순차 합류

비정상 종료 뒤에 고른 노드는 `safe_to_bootstrap` 이 `0` 이라 Galera 가 부트스트랩을 거부합니다. 그래서 그 노드의 `grastate.dat` 에서만 값을 `1` 로 고칩니다[^gs-mariadb]. 그다음 모든 노드가 멈춘 상태에서 그 노드에서만 부트스트랩을 실행합니다[^reset-mariadb].

```bash
# 최신 노드에서만 새 Primary Component 부트스트랩 실행
galera_new_cluster
```

`galera_new_cluster` 는 `--wsrep-new-cluster` 옵션을 붙여 `mariadbd` 를 띄우는 스크립트입니다. 실행은 systemd 를 거칩니다[^gs-mariadb]. 이 옵션은 붙을 기존 클러스터가 없다고 노드에 알립니다. 그러면 노드는 새 클러스터를 가리킬 UUID 를 만듭니다[^gs-mariadb]. 이 옵션을 켠 채 재시작하면 매번 새 UUID 를 만들어 옛 클러스터로 돌아가지 못하므로 첫 기동에만 씁니다[^gs-mariadb].

둘 이상의 노드에서 부트스트랩하면 안 됩니다. 각자 Primary Component 가 되어, 데이터가 서로 갈라진 두 클러스터가 따로 돌아가는 스플릿 브레인이 일어납니다[^quorum-mariadb].

첫 노드가 새 Primary Component 를 이루면 `wsrep_cluster_status` 가 `Primary` 가 됩니다. 그때 나머지 노드를 일반 명령(`systemctl start mariadb`)으로 켭니다[^reset-mariadb]. 나머지 노드는 새 Primary Component 를 찾아 붙고 상태 전송(IST 또는 SST)으로 데이터를 맞춘 뒤 합류합니다[^reset-mariadb].



## 4. 백업 기반 복구와 재합류의 한계

> 디스크가 깨진 노드 하나는 상태 전송으로 다시 채우지만, 잘못된 쿼리로 모든 노드가 함께 오염되면 외부 백업 저장소에서 복원해야 합니다.

노드 한 대의 디스크가 깨진 경우는 클러스터 안에서 해결됩니다. 노드가 세 대 이상이면 나머지가 쿼럼을 유지합니다. 고친 노드를 다시 켜면 상태 전송으로 데이터를 받습니다[^recover-mariadb]. 데이터가 비어 있으니 이때는 SST 입니다.

잘못된 쿼리로 데이터를 지운 경우는 다릅니다. Galera 는 그 쓰기도 다른 쓰기와 똑같이 모든 노드에 복제합니다. 그래서 IST 나 SST 로 받아 올 깨끗한 상태가 클러스터 안에 없습니다. 외부 백업에서 복원해야 합니다. 모든 노드의 디스크를 한꺼번에 잃은 경우도 같습니다.

Galera 클러스터에서 백업을 받을 때는 단일 노드만 대상으로 삼습니다. 정상 클러스터는 모든 노드가 같은 데이터를 가지므로, 한 노드의 전체 백업이 곧 클러스터 전체의 스냅샷이기 때문입니다[^backup-mariadb]. 공식 절차는 백업하는 동안 그 노드의 복제 적용을 `wsrep_desync=ON` 으로 멈춰 백업 안의 시점을 맞춥니다. 끝나면 `OFF` 로 되돌려 빠진 쓰기를 IST 로 받게 합니다[^backup-mariadb]. 그래서 백업에 걸리는 시간도 §2 의 GCache 범위 안에 들어야 IST 로 돌아옵니다.

컨테이너 환경의 MariaDB Operator 는 `Backup`·`Restore` CR 로 백업과 복구를 선언해 맡깁니다. 다만 위 `wsrep_desync` 단계는 Operator 문서에 나오지 않으므로, Operator 가 무엇을 대신하는지는 [MariaDB Operator Backup·Restore](../mariadb-operator/Backup·Restore.md) §5 에서 확인합니다.
