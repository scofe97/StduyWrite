# Certification-Based Replication·Quorum Components

---

> Galera Cluster 는 분산 잠금 없이 낙관적으로 트랜잭션을 실행하고 커밋 시점에 충돌을 검증하는 인증 기반 복제를 구현합니다. 과반수 쿼럼 판정으로 스플릿 브레인을 방지하고, 쓰기 노드를 집중화하여 복제 충돌과 교착 상태를 완화하는 원리를 다룹니다.

## 학습 목표

> 이 문서를 읽고 나면 인증 기반 복제와 쿼럼 컴포넌트의 동작을 시스템 수준에서 설명할 수 있습니다.

1. 원격 잠금 없이 낙관적으로 실행된 트랜잭션이 전역 순번으로 인증되는 과정을 추적할 수 있습니다.
2. 네트워크 단절 시 Primary Component 판정 원리와 노드 상태 전이 순서를 설명할 수 있습니다.
3. 2노드 구성에서 1대 장애 시 클러스터가 멈추는 원인과 garbd 중재자의 해결책을 도출할 수 있습니다.
4. 다중 마스터 환경에서도 쓰기 노드를 단일 노드로 집중화하는 이유를 설명할 수 있습니다.
5. 동시 쓰기 충돌이 애플리케이션에 1213 교착 상태 오류로 전달되는 경로와 대응 방안을 설계할 수 있습니다.



## 1. 인증 기반 복제와 전역 순서

> 전통적인 2단계 커밋 대신 낙관적 실행과 커밋 시점의 결정적 인증으로 분산 데이터 정합성을 보장합니다.

![인증 기반 복제의 트랜잭션 수명주기와 결정적 검증](./_assets/01-01.Certification-Based%20Replication·Quorum%20Components.certification-path.svg)

여러 데이터베이스 노드에 동시에 쓰기를 처리하려면 네트워크 지연과 분산 잠금 충돌이라는 난제를 풀어야 합니다. 전통적인 동기식 복제는 2단계 커밋과 노드 간 분산 잠금에 의존합니다. 분산 잠금은 트랜잭션 실행 내내 모든 노드와 네트워크 왕복 통신을 일으킵니다. 그 결과 지연 시간이 크게 늘어나고 분산 교착 상태가 빈번해집니다. Galera Cluster 는 이 병목을 풀기 위해 인증 기반 복제 메커니즘을 사용합니다[^cbr-galera].

### 낙관적 로컬 실행과 쓰기 집합

클라이언트가 특정 노드에 접속하여 트랜잭션을 실행할 때, Galera 는 원격 노드에 어떤 잠금도 요청하지 않습니다. 로컬 스토리지 엔진(InnoDB)의 표준 행 잠금과 MVCC 스냅샷만 사용하여 쿼리를 낙관적으로 처리합니다.

트랜잭션이 `COMMIT` 문을 호출하는 시점에 비로소 복제 프로세스가 시작됩니다. 로컬 노드는 트랜잭션이 데이터베이스에 가한 변경 내용과 바뀐 행의 기본 키를 모읍니다. 이를 쓰기 집합(Write-Set)이라는 단일 페이로드로 묶습니다[^cbr-galera].

### GComm 전역 순번과 결정적 인증

생성된 쓰기 집합은 그룹 통신 프레임워크(GComm)를 통해 모든 노드로 브로드캐스트됩니다. GComm 은 여러 노드에서 온 메시지에 하나의 총 순서(Total Order)를 매깁니다[^gcomm-mariadb]. Galera 는 이 순서에 따라 모든 트랜잭션에 클러스터 전역 순번(`seqno`)을 부여합니다[^cbr-galera].

모든 노드는 전달받은 쓰기 집합을 동일한 `seqno` 순서로 독립 검증합니다. 쓰기 집합을 만든 노드도 똑같이 검사합니다. 이를 인증 검사(Certification Test)라고 부릅니다. 노드는 이 트랜잭션의 `seqno` 를 마지막으로 성공한 트랜잭션의 `seqno` 와 맞댑니다. 두 번호 사이에 든 트랜잭션들은 서로의 결과를 보지 못한 채 실행됐습니다. 그래서 이 구간의 트랜잭션과 기본 키가 겹치는지 검사하고, 겹치면 인증이 실패합니다[^cbr-galera].

모든 노드가 동일한 입력 데이터와 동일한 순서를 바탕으로 검사하므로 판정은 완전히 결정적입니다. 노드 간에 별도의 투표나 확인 왕복 통신 없이 각 노드가 독립적으로 커밋 여부를 확정합니다.

| 복제 방식 | 잠금 획득 시점 | 네트워크 왕복 | 데이터 일관성 | 동시 쓰기 충돌 결과 |
|---|---|---|---|---|
| 비동기 복제 (MySQL 표준) | 로컬 트랜잭션 실행 중 | 없음 (복제 지연 발생) | 최종 일관성 (복제본 읽기 지연) | 슬레이브 충돌 시 복제 중단 |
| 분산 잠금 + 2단계 커밋 (2PC) | 실행 중 모든 노드 분산 락 | 다수 왕복 (준비 및 커밋 단계) | 엄격한 즉각 일관성 | 분산 교착 상태 및 지연 급증 |
| 인증 기반 복제 (Galera) | 로컬만 실행 중, 원격은 커밋 시 | 커밋 시 1회 브로드캐스트 | 사실상 동기 (Virtually Synchronous) | 늦은 트랜잭션 자동 롤백 |



## 2. Primary Component 와 상태 전이

> 과반수 투표권을 확보한 파티션만 쓰기를 허용하여 네트워크 분할 시 데이터 분열을 방지합니다.

분산 클러스터에서 네트워크 단절이 발생하면 노드 집합이 둘 이상으로 나뉠 수 있습니다. 나뉜 양쪽 노드 그룹이 모두 쓰기 요청을 받으면 데이터가 서로 다르게 갈라지는 스플릿 브레인이 일어납니다.

### 쿼럼과 과반수 판정

Galera 는 스플릿 브레인을 막기 위해 쿼럼 기반 과반수 판정을 수행합니다. 새로 나뉜 노드 집합의 가중치 합이 직전 Primary Component 가중치 합계의 절반을 엄격하게 넘을 때만 그 집합이 Primary Component 로 남습니다. 이때 직전 합계에서 정상 종료로 떠난 노드의 가중치는 뺍니다[^weight-galera]. 그래서 노드를 하나씩 정상 종료하면 쿼럼이 유지되고, 장애나 네트워크 단절로 사라질 때만 남은 쪽의 표가 모자라게 됩니다.

과반수 표를 얻지 못한 소수 그룹은 Non-Primary 상태로 바뀝니다. Non-Primary 노드의 상태 변수 `wsrep_cluster_status` 는 `NON_PRIMARY` 를 보입니다[^status-mariadb]. 이후 노드는 쿼리를 거부합니다. 쿼리를 보내면 아래 오류가 돌아옵니다[^quorum-mariadb][^guide-mariadb].

```sql
ERROR 1047 (08S01): WSREP has not yet prepared node for application use
```

쿼리 거부는 데이터 불일치를 막기 위해 서비스 제공을 스스로 멈추는 안전장치입니다.

### 노드 상태 전이 순서

클러스터에 새 노드가 투입되거나 재시작된 노드가 합류할 때, 노드는 정해진 상태 전이 단계를 순서대로 거칩니다[^states-mariadb].

1. `OPEN`: 노드 프로세스가 시작된 상태입니다.
2. `PRIMARY`: Primary Component 에 들어간 상태입니다.
3. `JOINER`: 기증자(Donor) 노드에 상태 전송(IST 또는 SST)을 요청하고 받는 단계입니다.
4. `JOINED`: 상태 전송을 마치고, 그동안 쌓인 트랜잭션을 적용해 따라잡는 단계입니다.
5. `SYNCED`: 클러스터를 완전히 따라잡아 정상 운영되는 상태입니다.

`SYNCED` 노드가 다른 노드에 SST 를 보내 주는 동안에는 `DONOR` 상태가 됩니다. 전송을 마치면 `JOINED` 를 거쳐 다시 `SYNCED` 로 돌아옵니다. 지금 상태는 `wsrep_local_state_comment` 로 읽습니다. 여기에는 `Joining`·`Joined`·`Synced`·`Donor`·`Initialized` 같은 값이 나옵니다[^states-mariadb].



## 3. 2노드 쿼럼과 Galera 중재자

> 노드가 두 대인 구성은 한 대만 장애가 발생해도 과반수를 충족하지 못해 클러스터 전체가 멈춥니다.

![2노드 클러스터의 쿼럼 붕괴와 Galera Arbitrator 중재](./_assets/01-01.Certification-Based%20Replication·Quorum%20Components.quorum-garbd.svg)

고가용성을 목적으로 노드 2대를 배치한 클러스터는 장애 복원력 관점에서 취약한 모순을 안고 있습니다. 기본 설정에서 각 노드는 1의 투표 가중치(`pc.weight=1`)를 가집니다[^weight-galera].

### 2노드 클러스터의 가용성 역설

노드가 2대이면 클러스터의 총 투표수는 2표입니다. 과반수 쿼럼을 충족하려면 50% 를 넘어야 하므로 최소 2표가 필요합니다. 만약 2번 노드가 전원 장애나 네트워크 단절로 이탈하면, 남은 1번 노드는 1표(50%)만 갖습니다.

50% 는 50% 초과 조건을 만족하지 못하므로 쿼럼이 깨집니다. 살아 있는 1번 노드마저 Non-Primary 로 전환되어 모든 트랜잭션을 멈춥니다. 외부 투표 구성원이 없는 2노드 클러스터는 1대 장애도 견디지 못합니다[^quorum-mariadb]. 어느 쪽이 죽어도 서비스가 멈추므로, 1대 장애를 견디려고 들인 두 번째 노드가 그 목적을 이루지 못합니다.

### 가중치 조절과 중재자 해법

이 문제를 푸는 방법은 가중치 비대칭 부여와 Galera Arbitrator 데몬 도입의 두 가지입니다.

첫째는 `wsrep_provider_options` 의 `pc.weight` 옵션으로 노드 간 가중치를 다르게 두는 방법입니다. 가중치는 0 부터 255 까지 줄 수 있습니다. 공식 문서의 2노드 예는 1번 노드에 가중치 1, 2번 노드에 가중치 0을 줍니다. 총 1표이므로 2번 노드가 꺼지거나 네트워크가 갈라져도 1번 노드는 1표 전부로 과반수를 유지합니다. 하지만 1번 노드가 죽으면 가중치 0인 2번 노드는 홀로 Primary 가 되지 못하는 비대칭 위험이 남습니다[^weight-galera].

둘째는 짝수 노드 클러스터의 표준 해법인 Galera Arbitrator(`garbd`)를 투입하는 방식입니다. `garbd` 는 완전한 데이터베이스 노드가 아니면서 투표 구성원으로 쿼럼 계산에 참여하는, 상태를 갖지 않는 경량 데몬입니다[^arbitrator-galera]. DB 노드 2대와 `garbd` 1대면 총 3표의 홀수 쿼럼이 됩니다. 어느 DB 노드 1대가 죽어도 남은 DB 노드와 `garbd` 가 2표(66.7%)를 확보하여 서비스를 이어 갑니다. 다만 `garbd` 를 DB 노드와 같은 서버에 두면 그 서버가 죽을 때 2표를 함께 잃으므로, 따로 떨어진 곳에 둬야 이 계산이 성립합니다.

| 클러스터 구성 방식 | 총 투표수 | 1대 장애 시 남은 표 | 쿼럼 유지 여부 | 평가와 특징 |
|---|---|---|---|---|
| 2노드 단독 (기본값) | 2표 | 1표 (50.0%) | 쿼럼 상실 (중단) | 1대 장애 시 전체 서비스 중단 |
| 2노드 가중치 비대칭 (pc.weight 1:0) | 1표 | 1표 또는 0표 | 조건부 유지 | 보조 노드 장애만 극복 가능 |
| 2노드 + garbd 중재자 | 3표 | 2표 (66.7%) | 쿼럼 유지 (정상) | 추가 DB 비용 없이 완전한 1대 장애 극복 |
| 3노드 데이터베이스 클러스터 | 3표 | 2표 (66.7%) | 쿼럼 유지 (정상) | 완전한 데이터 삼중화와 무중단 복원력 |



## 4. 다중 마스터의 단일 노드 쓰기 집중화

> 모든 노드가 쓰기를 수용할 수 있음에도 실무 아키텍처에서는 단일 쓰기 노드 구성을 채택합니다.

Galera Cluster 는 기술적으로 모든 노드가 읽기와 쓰기를 동시에 처리하는 다중 마스터 구조를 지원합니다[^usage-mariadb]. 그래도 운영 환경에서는 앞단에 로드밸런서나 프록시를 두라고 권장합니다[^usage-mariadb]. MariaDB MaxScale 의 Galera Monitor 는 기본적으로 `wsrep_local_index` 가 가장 낮은 노드 하나에 쓰기 역할을 줍니다. 그래서 MaxScale 이 여러 대여도 모두 같은 노드로 쓰기를 보냅니다[^galeramon]. 쓰기를 노드 하나로 모으는 구성이 이렇게 프록시 기본값에 들어 있습니다.

### 인증 실패와 트랜잭션 롤백 방지

여러 노드에 쓰기를 분산하면 서로 다른 노드에서 동일한 레코드를 동시에 수정할 가능성이 커집니다. 인증 기반 복제는 커밋 시점까지 충돌 검사를 미룹니다. 그래서 동시 수정이 일어나면 나중에 도달한 쓰기 집합이 인증에 실패하여 트랜잭션이 강제 롤백됩니다[^cbr-galera]. Galera Monitor 문서도 쓰기가 엉뚱한 노드로 가면 deadlock 오류가 늘어난다고 적습니다[^galeramon].

쓰기 노드를 하나로 모으면 같은 행을 고치는 트랜잭션들이 그 노드의 일반 행 잠금에서 차례를 기다립니다. 노드 사이의 인증 충돌이 사라지므로, 인증 실패에서 오는 롤백과 애플리케이션 재시도가 크게 줄어듭니다. 같은 노드 안에서 생기는 보통의 잠금 대기와 교착 상태는 단일 DB 와 똑같이 남습니다.

### 복제 스레드의 고우선순위 강제 중단

원격 노드에서 인증을 통과한 쓰기 집합이 로컬 노드에 도착하면, 복제 적용(applier) 스레드가 그 쓰기 집합을 적용합니다.

로컬 클라이언트가 같은 행을 수정하는 트랜잭션을 아직 실행하는 중일 수 있습니다. 이 트랜잭션이 복제 단계에 들어가기 전이면 적용 스레드가 실행을 끊고 롤백합니다. MariaDB 문서는 이를 고우선순위 중단(High-Priority Abort)이라 부릅니다. 그리고 인증 실패와 함께 클러스터 전역 충돌의 두 원인으로 듭니다[^wsrep-retry-mariadb]. 로컬 트랜잭션은 자기 노드에서 아무 잠금 충돌을 겪지 않았는데도 롤백을 받습니다. 쓰기를 여러 노드에 나눌수록 이런 중단을 만날 기회가 늘어납니다.



## 5. 동시 쓰기 충돌과 교착 상태 오류

> 낙관적 복제 충돌은 실행 단계가 아니라 커밋 문을 실행하는 순간 교착 상태 예외로 드러납니다.

Galera 클러스터를 처음 다룰 때 가장 당황스러운 장애는 쿼리 실행 시점과 에러 반환 시점의 불일치입니다.

### 커밋 시점의 ERROR 1213 반환

단일 DB 에서는 두 트랜잭션이 충돌할 때 `UPDATE` 문을 실행하는 단계에서 잠금 대기가 발생하거나 교착 상태가 감지됩니다.

반면 Galera 다중 쓰기 환경에서는 각 노드가 로컬에서 낙관적으로 쿼리를 실행하므로, `INSERT` 나 `UPDATE` 문 자체는 즉시 성공합니다. 인증 충돌은 마지막 `COMMIT` 문을 호출하여 클러스터 전역 인증을 수행하는 순간에 비로소 드러납니다[^cbr-galera]. 인증에 진 트랜잭션은 롤백되고, 클라이언트는 교착 상태(deadlock) 오류를 받습니다[^wsrep-retry-mariadb][^galeramon]. 앞 절의 고우선순위 중단을 당한 트랜잭션은 커밋 전, 실행 중인 문에서 같은 오류를 받을 수 있습니다. 오류 번호와 문구는 InnoDB 교착 상태와 같습니다[^e1213-mariadb].

```sql
ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction
```

클라이언트 입장에서는 행 잠금을 대기한 적이 없음에도 교착 상태 오류를 받게 됩니다. 이 오류를 받으면 마지막 문이 아니라 트랜잭션 전체가 롤백됩니다[^e1213-mariadb].

### 자동 커밋 재시도와 한계

MariaDB 는 단일 쿼리 자동 커밋 충돌을 완화하는 `wsrep_retry_autocommit` 변수를 제공합니다[^wsrep-retry-mariadb].

기본값은 1 이고 0 부터 10000 까지 줄 수 있습니다. 1 이상이면 `autocommit=1` 로 실행된 문이 클러스터 전역 충돌로 실패할 때, 서버가 오류를 돌려주기 전에 설정 횟수만큼 다시 실행합니다. 0 이면 재시도하지 않습니다. 재시도가 성공하면 애플리케이션에는 에러가 나타나지 않습니다[^wsrep-retry-mariadb].

그러나 `BEGIN` 과 `COMMIT` 으로 감싼 명시적 다중 쿼리 트랜잭션에는 이 자동 재시도가 동작하지 않습니다. 데이터베이스 엔진은 애플리케이션의 중간 비즈니스 로직을 알지 못하므로 다중 쿼리를 임의로 다시 실행할 수 없습니다. 따라서 명시적 트랜잭션에서 인증 충돌이 발생하면 `ERROR 1213` 이 애플리케이션으로 바로 전달됩니다.

애플리케이션은 트랜잭션 커밋 구간에서 발생하는 `SQLState 40001` 또는 에러 코드 1213 예외를 반드시 잡아야 합니다. 그리고 트랜잭션 전체를 처음부터 다시 실행하는 재시도 로직을 구현해야 합니다.
