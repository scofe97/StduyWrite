# Database Server Status Variables·Flow Control

---

> Galera Cluster 의 운영 상태를 wsrep 상태 변수로 계층별 진단하고, 느린 노드가 수신 큐 임계값을 넘어 전체 클러스터의 쓰기를 일시 정지시키는 흐름 제어 메커니즘과 병목 추적 경로를 다룹니다.

## 학습 목표

> 이 문서를 읽고 나면 wsrep 상태 변수로 노드와 클러스터 건강을 진단하고, 흐름 제어로 인한 쓰기 병목 원인을 시스템 수준에서 추적할 수 있습니다.

1. 쿼럼·크기·상태·준비 변수를 순서대로 대조하여 노드 장애를 판정할 수 있습니다.
2. 수신 큐 변수와 흐름 제어 변수로 복제 지연 및 정체 비율을 측정할 수 있습니다.
3. 흐름 제어 상한과 하한의 동작 순서를 추적하여 병목 원리를 도출할 수 있습니다.
4. 흐름 제어 송수신 변수를 비교하여 병목 노드를 식별하고 완화책을 설계할 수 있습니다.



## 1. wsrep 상태 변수로 읽는 클러스터 건강

> 노드가 쿼리를 받지 못하는 원인은 쿼럼 상실, 데이터 동기화 지연, 프로바이더 미준비로 갈리므로 상태 변수를 정해진 계층 순서로 읽어야 합니다.

![상태 변수로 확인하는 클러스터 건강 진단 계층](./_assets/01-03.Database%20Server%20Status%20Variables·Flow%20Control.health-hierarchy.svg)

데이터베이스 노드가 클라이언트 요청에 에러를 돌려줄 때, 단일 상태 변수 하나만으로는 문제의 원인을 진단할 수 없습니다. 노드가 쓰기를 거부하는 이유는 네트워크 단절로 쿼럼을 잃었거나, 상태 전송(SST/IST)으로 동기화 중이거나, 복제 엔진이 아직 초기화되지 않았기 때문입니다. Galera Cluster 는 수십 가지 상태 변수를 제공합니다[^status-mariadb]. 이들을 계층적 순서로 대조해야 정확한 장애 지점을 짚어낼 수 있습니다.

### 쿼럼과 클러스터 크기 판정

가장 먼저 노드가 속한 컴포넌트의 상태를 `wsrep_cluster_status` 로 확인합니다[^status-mariadb].
건강한 값은 `Primary` 하나이고 다른 값은 모두 문제를 뜻합니다[^monitoring-mariadb].

`Non-Primary` 는 과반수를 잃은 쪽에 남았다는 뜻입니다. 트랜잭션은 Primary Component 만 처리하므로 이 노드는 쓰기를 받지 않습니다[^monitoring-mariadb]. 과반수 판정과 Non-Primary 노드가 돌려주는 오류는 [01-01](./01-01.Certification-Based%20Replication·Quorum%20Components.md) 의 「Primary Component 와 상태 전이」에서 다뤘습니다. `Disconnected` 는 어느 그룹에도 연결되지 못해 다시 연결을 시도하는 상태입니다[^status-mariadb].

쿼럼이 확인되면 `wsrep_cluster_size` 로 현재 컴포넌트의 노드 수를 점검합니다[^status-mariadb].
이 값은 기대한 전체 노드 수와 같아야 합니다[^monitoring-mariadb]. 3노드 클러스터에서 이 값이 2로 줄었다면 1대가 이탈했음을 뜻합니다. 남은 2대는 과반수(2/3)를 만족하므로 서비스를 유지합니다.

### 노드 동기화 단계와 준비 상태

클러스터 전체 쿼럼이 정상이라도 개별 노드가 서비스를 제공할 준비가 되었는지는 별도로 판정해야 합니다.
`wsrep_local_state_comment` 는 노드의 현재 상태를 사람이 읽을 수 있는 문자열로 보여줍니다[^monitoring-mariadb]. 자주 보이는 값은 다음과 같습니다[^monitoring-mariadb]. 상태가 바뀌는 순서는 [01-01](./01-01.Certification-Based%20Replication·Quorum%20Components.md) 의 「노드 상태 전이 순서」에서 다뤘습니다.
- `Joining`: 클러스터와 연결을 맺고 동기화를 시작하는 단계입니다.
- `Donor`: 다른 노드에 SST 를 보내 주는 중입니다. 이때는 보통 읽기 전용입니다.
- `Joined`: 상태 전송을 받은 뒤 밀린 트랜잭션을 적용하며 따라잡는 단계입니다.
- `Synced`: 클러스터의 정상 구성원으로 완전히 동작하는 상태입니다.
- `Initialized`: 어느 클러스터 컴포넌트에도 연결되지 않은 상태입니다.

정상 서비스 노드는 `Synced` 상태여야 합니다[^monitoring-mariadb].
동시에 `wsrep_ready` 상태 변수가 `ON` 인지 확인합니다[^status-mariadb]. 이 값이 `OFF` 이면 노드가 거의 모든 쿼리를 거부합니다[^monitoring-mariadb]. `wsrep_connected` 는 MariaDB 가 wsrep 프로바이더에 연결돼 있는지 나타냅니다[^status-mariadb]. 이 값이 `OFF` 이면 노드가 다른 노드와 끊겨 고립된 상태입니다[^monitoring-mariadb].

또한 `wsrep_cluster_state_uuid` 와 `wsrep_local_state_uuid` 가 일치하는지 비교합니다[^status-mariadb]. 두 UUID 가 같으면 노드와 클러스터의 상태가 맞춰져 있다는 뜻입니다[^status-mariadb].

| 진단 계층 | 확인 변수 | 정상 기준값 | 이상 발생 시 값 | 뜻과 조치 |
|---|---|---|---|---|
| 1단계: 쿼럼 성립 | `wsrep_cluster_status` | `Primary` | `Non-Primary`, `Disconnected` | 트랜잭션 처리 중단, 네트워크 분리 점검 |
| 2단계: 구성원 수 | `wsrep_cluster_size` | 기대 노드 수 | 기대 수 미달 | 노드 이탈 감지, 남은 노드의 과반수 여유 확인 |
| 3단계: 노드 동기화·준비 | `wsrep_local_state_comment` / `wsrep_ready` / `wsrep_connected` | `Synced` / `ON` / `ON` | `Joining`·`Donor`·`Joined` / `OFF` | 상태 전송이나 따라잡기 중, `OFF` 면 쿼리 거부 |
| 4단계: 지연 관측 | `wsrep_local_recv_queue_avg` / `wsrep_flow_control_paused` | 0.0 에 가까움 | 0.0 보다 눈에 띄게 큼 | 적용이 밀림, 흐름 제어 발동 위험 |



## 2. 수신 대기열과 복제 지연 관측

> 인증을 마친 트랜잭션이 스토리지 엔진에 제때 반영되지 못하면 수신 대기열이 쌓이고 복제 지연이 발생합니다.

다른 노드에서 쓰기 집합이 적용 속도보다 빨리 들어오면 수신 대기열이 늘어납니다[^flow-control-mariadb]. 받은 쓰기 집합을 로컬 InnoDB 에 반영하는 일은 복제 스레드(앱플라이어 스레드)가 맡습니다[^system-mariadb]. 쓰기 집합이 인증을 거쳐 각 노드에 적용되는 과정은 [01-01](./01-01.Certification-Based%20Replication·Quorum%20Components.md) 의 「인증 기반 복제와 전역 순서」에서 다뤘습니다.

### 수신 대기열과 차동 통계 변수

수신 대기열 상태는 `wsrep_local_recv_queue` 로 관측합니다[^status-mariadb].
이 변수는 적용을 기다리는 쓰기 집합의 현재 개수입니다[^status-mariadb]. 평상시 정상적인 노드에서는 이 값이 `0` 이거나 0에 가까운 작은 수치로 유지됩니다.

장애 징후를 추적할 때는 순간값보다 평균값을 봅니다.
`wsrep_local_recv_queue_avg` 는 수신 대기열의 평균 길이입니다[^status-mariadb]. 이 값이 0 보다 눈에 띄게 크면 노드가 들어오는 쓰기 집합을 제때 적용하지 못하는 과부하 상태일 가능성이 큽니다[^status-mariadb]. `wsrep_local_recv_queue_min` 과 `wsrep_local_recv_queue_max` 는 마지막 `FLUSH STATUS` 이후의 최솟값과 최댓값입니다[^status-mariadb]. 둘을 함께 보면 큐의 변동 폭이 보입니다.

이런 상태 변수 상당수는 차동(differential) 값입니다. `FLUSH STATUS` 를 실행할 때마다 처음부터 다시 셉니다[^monitoring-mariadb].

집계 구간은 변수마다 표현이 다릅니다. Status Variables 문서는 `_avg` 를 「가장 최근 상태 조회 이후」 값으로 적습니다. 반면 `_min`·`_max` 와 `wsrep_flow_control_paused` 는 「마지막 `FLUSH STATUS` 이후」 값입니다[^status-mariadb]. 그래서 부하 시험이나 장애 분석처럼 특정 구간만 보고 싶을 때는 시작 시점에 `FLUSH STATUS` 를 실행해 구간을 맞춘 뒤 값을 읽습니다.

### 송신 대기열과 병렬 적용 의존성 거리

복제 지연은 수신 측만이 아니라 송신 측에서도 발생할 수 있습니다.
`wsrep_local_send_queue` 와 `wsrep_local_send_queue_avg` 는 송신 대기열을 나타냅니다[^status-mariadb]. 전송을 기다리는 쓰기 집합의 개수입니다. 평균이 0 보다 눈에 띄게 크면 네트워크 처리량이 부족하거나 복제가 흐름 제어로 묶여 있을 가능성이 큽니다[^status-mariadb].

워크로드의 병렬 복제 여지는 `wsrep_cert_deps_distance` 로 확인합니다[^status-mariadb].
이 값은 병렬로 적용될 수 있는 가장 높은 순번(`seqno`)과 가장 낮은 순번 사이의 평균 거리입니다[^status-mariadb]. 거리가 클수록 함께 적용할 수 있는 트랜잭션이 많다는 뜻입니다. 그래서 앱플라이어 스레드 수(`wsrep_slave_threads`)를 정할 때 참고값으로 씁니다[^monitoring-mariadb].



## 3. 흐름 제어 메커니즘과 동작 순서

> 저속 노드의 수신 큐가 임계값을 넘어서면 흐름 제어가 발동하여 클러스터 전체 노드의 신규 트랜잭션 복제를 일시 정지시킵니다.

![수신 큐 임계값과 흐름 제어 일시 정지 및 재개 순환](./_assets/01-03.Database%20Server%20Status%20Variables·Flow%20Control.flow-control.svg)

특정 노드의 처리 속도가 떨어져 수신 큐가 한없이 불어나면, 시스템 메모리가 고갈되어 프로세스가 강제 종료되는 장애가 발생합니다. 노드 간 데이터 정합성 격차도 벌어집니다. Galera Cluster 는 이 문제를 막기 위해 피드백 기반 속도 조절 메커니즘인 흐름 제어를 사용합니다[^flow-control-mariadb].

### 흐름 제어의 발동과 해제 순환

흐름 제어는 수신 대기열의 크기에 따라 도는 자동 피드백 순환입니다. 공식 문서의 7단계를 다섯으로 묶으면 다음과 같습니다[^flow-control-mariadb].
1. 큐 적재: 저속 노드가 클러스터로부터 트랜잭션을 수신하여 `wsrep_local_recv_queue` 에 쌓습니다.
2. 상한 도달: 수신 큐 크기가 `wsrep_provider_options` 에 정의된 `gcs.fc_limit` 임계값을 초과합니다.
3. 일시 정지 전파: 저속 노드가 클러스터 전체에 `FC_PAUSE` 메시지를 브로드캐스트합니다.
4. 전체 복제 정지: 메시지를 받은 모든 노드는 새 트랜잭션의 복제를 잠시 멈춥니다. 이미 큐에 들어온 트랜잭션은 계속 처리합니다.
5. 하한 도달 및 재개: 저속 노드의 큐가 `gcs.fc_limit` × `gcs.fc_factor` 아래로 줄어들면 그 노드가 `FC_RESUME` 메시지를 보냅니다. 클러스터 전체 복제가 정상 재개됩니다.

이 순환 메커니즘 때문에 클러스터 전체의 최대 쓰기 처리량은 가장 느린 단일 노드의 반영 속도로 제한됩니다. 고사양 노드 여러 대를 두더라도 한 대의 디스크 I/O 가 느리면 전체 클러스터가 주기적으로 멈춰 섭니다.

### 흐름 제어 파라미터와 정지 비율 계산

흐름 제어의 동작 강도는 두 가지 파라미터로 결정됩니다[^provider-mariadb].
`gcs.fc_limit` 는 흐름 제어를 작동시키는 수신 큐의 상한선입니다[^provider-mariadb]. 기본값은 16 입니다. 이 값이 작을수록 버스트 쓰기에도 민감하게 반응하여 복제가 자주 멈춥니다.
`gcs.fc_factor` 는 정지된 복제를 다시 시작하는 하한 비율입니다[^provider-mariadb]. 기본값은 1.0 입니다. 예를 들어 `gcs.fc_limit=100`, `gcs.fc_factor=0.5` 라면 큐가 50 미만으로 줄어야 복제가 풀립니다.

기본값은 같은 MariaDB 문서 안에서도 쪽마다 다르게 적혀 있습니다.
wsrep_provider_options 쪽은 16 과 1.0 입니다[^provider-mariadb]. Flow Control 쪽 표는 100 과 0.8 입니다[^flow-control-mariadb]. 운영 노드에서는 `wsrep_provider_options` 변수 값을 직접 읽어 실제 설정을 확인합니다.

다중 쓰기 구성에서는 설정한 한도가 그대로 쓰이지도 않습니다.
`gcs.fc_single_primary` 가 기본값 `no` 이면 `gcs.fc_limit` 가 클러스터 크기의 제곱근 배로 늘어납니다[^provider-mariadb]. 4노드라면 설정값의 두 배가 됩니다[^provider-mariadb].

흐름 제어가 서비스에 미친 영향은 `wsrep_flow_control_paused` 로 측정합니다[^status-mariadb].
마지막 `FLUSH STATUS` 이후 흐름 제어로 복제가 멈춰 있던 시간의 비율입니다[^status-mariadb].
- 0.0 근처: 건강한 상태입니다[^flow-control-mariadb].
- 0.2 이상: 그 구간 시간의 20% 이상 복제가 멈췄다는 뜻이며 문제가 있다는 신호입니다[^flow-control-mariadb].

어느 노드가 원인인지는 송수신 카운트를 비교하여 판정합니다[^flow-control-mariadb].
`wsrep_flow_control_sent` 는 가장 최근 상태 조회 이후 이 노드가 보낸 `FC_PAUSE` 횟수입니다[^status-mariadb]. 이 값이 높은 노드가 클러스터를 멈추게 만든 병목 원인입니다[^flow-control-mariadb].
`wsrep_flow_control_recv` 는 받은 `FC_PAUSE` 횟수인데 자기가 보낸 것도 함께 셉니다[^status-mariadb]. 로컬 노드의 `sent` 는 0 인데 `recv` 가 크다면 다른 저속 노드 때문에 멈춘 정상 노드입니다.



## 4. 흐름 제어 병목 진단과 튜닝 한계

> 임계값을 키우면 멈춤은 줄지만 큐와 적용 지연이 함께 커지므로 느린 원인부터 찾아 고칩니다.

`wsrep_flow_control_paused` 가 높을 때 먼저 떠오르는 대응은 `gcs.fc_limit` 를 늘리는 것입니다.
임계값을 올리면 정지 빈도는 일시적으로 줄어듭니다. 하지만 이는 병목을 해결한 것이 아니라 증상을 뒤로 미룬 것에 불과합니다[^flow-control-mariadb].

### 단순 fc_limit 증설의 부작용

`gcs.fc_limit` 는 느린 노드가 쌓아 둘 수 있는 쓰기 집합의 상한입니다. 상한을 올리면 다음 두 가지가 함께 커집니다.

- 메모리 사용: 흐름 제어가 막던 것이 바로 큐의 무한 증가와 OOM 종료입니다[^flow-control-mariadb]. 상한이 높을수록 큐가 더 커질 수 있고 메모리도 그만큼 씁니다.
- 적용 지연: 큐가 길수록 느린 노드는 다른 노드보다 더 뒤처진 채 쓰기를 적용합니다. 공식 문서도 다중 쓰기 구성에서 한도를 키우는 보정을 「노드가 조금 더 뒤처져도 되게 여유를 주는 것」으로 설명합니다[^provider-mariadb]. 그 노드에서 읽으면 다른 노드보다 오래된 값을 볼 수 있습니다.

공식 문서는 이 값 조정을 고급 튜닝 단계로 봅니다. 대부분은 흐름 제어 한도를 늦추기보다 병목의 근본 원인을 고치는 편이 낫다고 권합니다[^flow-control-mariadb].

### 앱플라이어 스레드와 병목 완화 대안

흐름 제어 병목을 완화하는 정석 접근법은 쓰기 집합을 반영하는 쪽의 처리량을 늘리는 것입니다.
먼저 볼 파라미터는 `wsrep_slave_threads` 입니다[^system-mariadb].
기본값은 1 로, 들어오는 쓰기 집합을 스레드 하나가 적용합니다[^system-mariadb]. 멀티코어 서버에서는 스레드가 모자라 병목이 될 수 있으므로 CPU 코어 수에 맞춰 늘립니다[^flow-control-mariadb]. 복제 스레드는 어떤 쓰기 집합을 병렬로 적용해도 안전한지 스스로 가립니다[^system-mariadb].

다만 노드 사이 일관성 문제가 자주 생기면 1 로 되돌리면 대개 해결된다고 문서에 적혀 있습니다[^system-mariadb].

공식 문서가 꼽는 나머지 원인도 함께 점검합니다[^flow-control-mariadb].
- 느린 노드 하나: 하드웨어가 다르거나 네트워크 지연이 크거나 다른 작업과 자원을 다투면 그 노드만 느려집니다. 자원을 올리거나 작업을 옮깁니다.
- 큰 트랜잭션: 큰 `UPDATE`·`DELETE`·`INSERT` 는 큰 쓰기 집합을 만들어 다른 노드의 적용을 늦춥니다. 작은 배치로 나눕니다.
- 오래 도는 `SELECT`: InnoDB 테이블에 오래 걸리는 읽기가 잠금을 잡으면 복제 적용이 막혀 수신 큐가 늘어납니다. 읽기 쿼리를 최적화합니다.

쓰기가 한 노드에서만 나오는 구성이라면 `gcs.fc_single_primary` 로 그 사실을 알릴 수 있습니다. `yes` 로 켜면 앞에서 본 클러스터 크기 보정이 빠져 설정한 한도가 그대로 쓰입니다[^provider-mariadb]. 흐름 제어가 더 일찍 걸릴 수 있다는 뜻이므로 처리량을 늘리는 옵션으로 보면 안 됩니다. 동적으로 바꿀 수 없는 옵션이라 재시작이 필요합니다[^provider-mariadb].

| 조치 방안 | 대상 파라미터 또는 영역 | 기대 효과 | 트레이드오프와 차이점 |
|---|---|---|---|
| 병렬 앱플라이어 증설 | `wsrep_slave_threads` | 여러 스레드가 수신 큐를 나눠 비움 | 노드 사이 일관성 문제가 잦으면 1 로 되돌리라는 안내가 있음 |
| 수신 큐 임계값 조정 | `gcs.fc_limit` / `gcs.fc_factor` | 짧은 쓰기 폭주에서 멈춤 횟수 감소 | 큐가 커지는 만큼 메모리와 적용 지연이 늘어남 |
| 큰 트랜잭션 분할 | 애플리케이션의 배치 크기 | 쓰기 집합이 작아져 다른 노드의 적용이 빨라짐 | 배치 처리 코드를 고쳐야 함 |
| 긴 읽기 정리 | 오래 도는 `SELECT` | 복제 적용을 막는 잠금이 줄어듦 | 쿼리 최적화 작업이 필요함 |
| 느린 노드 자원 보강 | 해당 노드의 하드웨어·작업 배치 | 가장 느린 노드의 적용 속도가 올라감 | 비용이 들거나 다른 작업을 옮겨야 함 |
